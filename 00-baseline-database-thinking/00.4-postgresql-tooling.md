# 00.4 — PostgreSQL Tooling

> **Phase:** 00 — Baseline & Database Thinking  
> **Chapter:** 00.4  
> **Theme:** PostgreSQL Tooling  
> **Target mastery:** L0 → L7  
> **Primary outcome:** Stop treating PostgreSQL tooling as a collection of commands. Learn to select the correct instrument for the question being asked, understand what evidence each tool can and cannot provide, and build a repeatable diagnostic workflow.

---

## 1. Why This Chapter Exists

A developer can know SQL and still be operationally weak at PostgreSQL.

Typical symptoms:

- They can write `SELECT` queries but cannot tell whether the server is reachable.
- They use `psql` for everything without understanding what it is actually doing.
- They run `pg_dump` and call it a complete production backup strategy.
- They inspect a slow query without `EXPLAIN (ANALYZE, BUFFERS)`.
- They look at CPU and conclude the database is slow, without checking waits, locks, I/O, or query behavior.
- They change configuration before collecting evidence.
- They use a GUI but cannot reproduce the same diagnosis from the command line.
- They trust generated commands from AI without checking which server, database, role, cluster, or environment the command will affect.

An expert database engineer thinks differently:

> **Every database question needs an instrument whose observation model matches the question.**

Examples:

| Question | Appropriate instrument |
|---|---|
| Is the PostgreSQL server accepting connections? | `pg_isready` |
| Can I actually authenticate and execute SQL? | `psql` |
| What database/role am I connected to? | `psql` + `\conninfo` / SQL functions |
| What is a query's execution plan? | `EXPLAIN` |
| What is the query actually doing at runtime? | `EXPLAIN ANALYZE` |
| Which statements consume the most execution time? | `pg_stat_statements` |
| What sessions are active right now? | `pg_stat_activity` |
| Who is blocking whom? | lock views / `pg_stat_activity` |
| What database objects exist? | `psql` meta-commands + catalogs |
| Can I export one database logically? | `pg_dump` |
| Can I restore an archive? | `pg_restore` |
| Can I test a backup's integrity? | `pg_verifybackup` for supported physical-backup workflows |
| How does the workload behave under benchmark traffic? | `pgbench` |
| What PostgreSQL binaries/version am I using? | `pg_config`, `psql --version`, server version SQL |
| Is a physical cluster reachable? | `pg_isready` + actual client connection |
| Is the OS constrained? | `top`, `vmstat`, `iostat`, filesystem tools |

PostgreSQL 18 exposes a broad family of client applications for these jobs, including `psql`, `pg_dump`, `pg_restore`, `pg_basebackup`, `pg_isready`, `pgbench`, `pg_amcheck`, `pg_config`, and `vacuumdb`. citeturn308073search1turn308073search2

# 2. Learning Objectives

By the end of this chapter, you should be able to:

1. Explain PostgreSQL's client/server tooling model.
2. Distinguish **connection tools**, **interactive clients**, **diagnostic tools**, **maintenance tools**, **backup tools**, and **benchmarking tools**.
3. Use `psql` fluently rather than merely as a SQL terminal.
4. Determine exactly which PostgreSQL server, port, database, role, and environment you are interacting with.
5. Understand how libpq connection parameters and environment variables affect client behavior.
6. Diagnose connectivity failures systematically instead of guessing.
7. Use `EXPLAIN` as an evidence-producing instrument rather than a formatting command.
8. Use server statistics views to investigate active sessions, waits, locks, and workload behavior.
9. Understand what `pg_stat_statements` does and why it requires server configuration.
10. Understand what `pg_dump` is good at and what it is **not** a substitute for.
11. Build repeatable CLI workflows for local development, Docker, CI/CD, staging, and production.
12. Recognize unsafe AI-generated database commands before executing them.
13. Design a tooling workflow that preserves evidence, reproducibility, and operational safety.

# 3. The Core Mental Model

PostgreSQL tooling is easiest to understand as a set of layers.

```text
┌───────────────────────────────────────────────────────────────┐
│ Human / Automation / CI / Application                        │
└──────────────────────────────┬────────────────────────────────┘
                               │
                               ▼
┌───────────────────────────────────────────────────────────────┐
│ Client Applications                                          │
│ psql | pg_dump | pg_restore | pgbench | pg_isready | ...    │
└──────────────────────────────┬────────────────────────────────┘
                               │
                               ▼
┌───────────────────────────────────────────────────────────────┐
│ libpq / PostgreSQL Client Protocol                           │
│ connection parameters | authentication | protocol            │
└──────────────────────────────┬────────────────────────────────┘
                               │
                               ▼
┌───────────────────────────────────────────────────────────────┐
│ PostgreSQL Server                                             │
│ sessions | SQL engine | planner | executor | storage         │
└──────────────────────────────┬────────────────────────────────┘
                               │
                               ▼
┌───────────────────────────────────────────────────────────────┐
│ OS / Kernel / Filesystem / Network / Hardware / Cloud        │
└───────────────────────────────────────────────────────────────┘
```

The key insight is:

> `psql` is not PostgreSQL itself. It is a client that communicates with a PostgreSQL server.

The same distinction applies to `pg_dump`, `pg_restore`, `pgbench`, and most other utilities.

This matters because a command can fail for entirely different reasons:

```text
Client binary problem
    ↓
Wrong client version/path
    ↓
Connection parameter problem
    ↓
Network/socket problem
    ↓
Server availability problem
    ↓
Authentication problem
    ↓
Database/role/permission problem
    ↓
SQL/problem inside the database
```

An expert identifies the failing layer before changing anything.

# 4. Tool Taxonomy

## 4.1 Interactive client tools

### `psql`

`psql` is PostgreSQL's terminal-based interactive client. It can execute SQL interactively, run files, and provides its own meta-commands and scripting features. citeturn308073search6

Typical uses:

- exploratory SQL
- migrations and scripts
- database inspection
- role inspection
- transaction testing
- connection verification
- operational triage
- reproducible command-line diagnostics

Example:

```bash
psql -h localhost -p 5432 -U postgres -d app_db
```

Once connected:

```sql
SELECT version();
SELECT current_database();
SELECT current_user;
SELECT current_schema();
```

Then:

```text
\conninfo
```

`\conninfo` is especially important because it tells you what connection `psql` is actually using, including SSL-related information when applicable. citeturn308073search6

A beginner often sees this:

```text
psql
  ↓

```

An expert sees:

```text
psql

├── meta-command environment
```

# 6. Connection Parameters: The Hidden Source of Many Bugs

A connection is not just:

```text
DATABASE_URL
```

Conceptually, a PostgreSQL client needs values such as:

```text
host
port
user
password / authentication method
 database name
SSL settings
connection options
```

`psql` exposes these through options such as `-h`, `-p`, `-U`, and `-d`. When host is omitted, PostgreSQL commonly attempts a Unix-domain socket connection on Unix-like systems. citeturn308073search6

Example:

```bash
psql -h localhost -p 5432 -U app_user -d inventory
```

Do not mentally compress this into “connect to Postgres.”

It means:

```text
client binary
   ↓
localhost
   ↓
TCP port 5432
   ↓
PostgreSQL server listening there
   ↓
authenticate as app_user
   ↓
connect to database inventory
```

Every one of those steps can fail independently.

# 7. Environment Variables and Implicit Configuration

PostgreSQL client applications use libpq connection conventions. Common environment variables include:

```text
PGHOST
PGPORT
PGUSER
PGDATABASE
```

For example:

```bash
export PGHOST=localhost
export PGPORT=5432
export PGUSER=app_user
export PGDATABASE=inventory
```

Now:

```bash
psql
```

may connect using those defaults.

This is convenient—and dangerous when debugging.

An apparently innocent command:

```bash
psql
```

may connect somewhere different from what you believe.

Therefore, during troubleshooting, make implicit state visible:

```bash
env | grep '^PG'
psql --version
psql -d postgres -c 'SELECT version();'
```

And inside `psql`:

```text
\conninfo
```

The official documentation lists `PGDATABASE`, `PGHOST`, `PGOPTIONS`, `PGPORT`, and `PGUSER` as relevant connection environment variables for PostgreSQL utilities. citeturn439139search0

# 8. Client Version vs Server Version

One of the most important operational distinctions:

```text
psql --version
```

answers a **client binary** question.

Whereas:

```sql
SELECT version();
```

answers a **server** question.

Do not confuse them.

Example:

```text
psql --version
psql (PostgreSQL) 18.x
```

while the connected server could theoretically be another supported version.

The tools ecosystem is intentionally designed around client/server interaction, and PostgreSQL utilities have version compatibility boundaries that matter for operations such as dumping and restoring databases. For example, current PostgreSQL documentation states that `pg_dump` can dump servers older than its own major version, but it cannot dump from a server newer than its own major version. citeturn439139search0

### Expert rule

Whenever a command behaves unexpectedly, capture both:

```bash
psql --version
```

and:

```sql
SELECT version();
```

# 9. `pg_isready`: Liveness Is Not Successful Application Access

`pg_isready` answers a narrow question:

> Is the PostgreSQL server accepting connection attempts at the specified endpoint?

Example:

```bash
pg_isready -h localhost -p 5432
```

Possible outcomes include:

```text
accepting connections
rejecting connections
no response
```

The PostgreSQL documentation defines exit statuses for these states, which makes `pg_isready` useful in scripts and orchestration. citeturn308073search12

But understand the boundary:

```text
pg_isready = server availability signal

psql       = actual connection + authentication + SQL execution
```

A server may be reachable while your application cannot log in.

Therefore:

```text
Liveness ≠ readiness for your application ≠ authorization
```

This distinction becomes crucial with Kubernetes, Docker Compose, load balancers, and cloud-managed databases.

# 10. Connectivity Troubleshooting Ladder

When an application cannot connect, use this sequence.

## Level 1 — Is the binary available?

```bash
which psql
psql --version
which pg_isready
pg_isready --version
```

## Level 2 — Is the endpoint reachable?

```bash
pg_isready -h localhost -p 5432
```

## Level 3 — Can a real client connect?

```bash
psql -h localhost -p 5432 -U app_user -d inventory
```

## Level 4 — What endpoint did I actually reach?

```text
\conninfo
```

## Level 5 — Which server am I talking to?

```sql
SELECT version();
SELECT inet_server_addr(), inet_server_port();
```

## Level 6 — Which identity am I using?

```sql
SELECT current_user;
SELECT session_user;
```

## Level 7 — What privileges do I have?

```text
\du
\dp
```

## Level 8 — Can I execute the specific operation?

Test the smallest relevant SQL statement.

Do not jump directly to changing `postgresql.conf`, firewall rules, roles, or passwords.

# 11. Diagnostic vs Observability Tools

Another critical distinction:

## Point-in-time diagnostic

Answers:

> What is happening with this query/session right now?

Examples:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

```sql
SELECT * FROM pg_stat_activity;
```

## Historical workload observation

Answers:

> What has been happening repeatedly over time?

Example:

```sql
SELECT * FROM pg_stat_statements;
```

PostgreSQL's `pg_stat_statements` module tracks planning and execution statistics for SQL statements. It requires `shared_preload_libraries` configuration and therefore a server restart when adding or removing it; query identifier calculation is also required. citeturn439139search4

These tools solve different questions.

```text
EXPLAIN
    ↓
one query / one plan

pg_stat_activity
    ↓
current sessions / current activity

pg_stat_statements
    ↓
aggregate statement workload history
```

# 12. `EXPLAIN`: Observe the Planner's Decision

A frequent novice mistake is:

```sql
SELECT ...;
```

then guessing why it is slow.

Use:

```sql
EXPLAIN
SELECT ...;
```

This shows the planned execution strategy.

For actual runtime behavior:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Important distinction:

```text
EXPLAIN
    → estimated plan

EXPLAIN ANALYZE
    → executes the query and reports actual execution statistics
```

That means `EXPLAIN ANALYZE` is not a harmless visualization command. It executes the statement.

This becomes dangerous with:

```sql
UPDATE
DELETE
INSERT
```

Therefore an expert is especially careful when adding `ANALYZE` to mutating statements.

PostgreSQL documentation explicitly includes `EXPLAIN` as a primary mechanism for understanding individual query behavior and performance. citeturn308073search7turn308073search8

# 13. `pg_stat_activity`: What Is the Server Doing Right Now?

`pg_stat_activity` provides one row per server process with information about current activity. citeturn439139search2

A practical starting query:

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    state_change,
    query
FROM pg_stat_activity
ORDER BY query_start;
```

Now you can reason about:

- active sessions
- idle sessions
- long-running transactions
- waiting sessions
- blocked sessions
- application sources
- database usage
- suspicious connection accumulation

This is one of the most valuable production skills in the entire roadmap.

# 14. Wait Events: Stop Saying “The Query Is Slow”

A slow query can be slow because it is:

- consuming CPU
- waiting on I/O
- waiting on a lock
- waiting for another PostgreSQL subsystem
- stalled by external conditions
- processing far more rows than expected

`pg_stat_activity` exposes wait-related information.

The correct question is not:

> Why is the query slow?

It is:

> What phase is the session spending its time in?

This turns vague debugging into evidence-driven diagnosis.

---

# 15. Lock Investigation

A production incident can look like:

```text
API latency ↑
    ↓
PostgreSQL query latency ↑
    ↓
CPU normal
    ↓
I/O normal
    ↓
multiple sessions waiting
    ↓
lock contention
```

The correct instrument is not “add an index.”

First inspect activity and locks.

A useful conceptual workflow is:

```text
pg_stat_activity
       ↓
find waiting sessions
       ↓
identify wait event
       ↓
inspect lock relationships
       ↓
find blocking PID
       ↓
identify transaction
       ↓
identify application request
       ↓
fix transaction / lock ordering / workload design
```

Do not terminate sessions blindly.

`pg_terminate_backend()` is an operational action, not an investigative query.

---

# 16. `pg_stat_statements`: Workload-Level Evidence

Suppose a production service executes 50,000 different query calls.

Looking at one request is insufficient.

You want to know:

- which statements consume the most total execution time?
- which statements are executed most frequently?
- which statements have high average latency?
- which query fingerprints dominate workload?
- which queries are generating the largest resource cost?

That is where `pg_stat_statements` becomes powerful.

Example exploration:

```sql
SELECT
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

The precise available columns should always be checked against the PostgreSQL version in use.

The strategic model is:

```text
One query problem
    → EXPLAIN

One live session problem
    → pg_stat_activity

One workload pattern problem
    → pg_stat_statements
```

# 17. Backup and Transfer Tooling

## 17.1 `pg_dump`

`pg_dump` creates a logical export of a single PostgreSQL database. It can produce SQL scripts or archive formats and is designed to make a consistent export while the database is concurrently used. citeturn439139search0

Example:

```bash
pg_dump -Fc inventory > inventory.dump
```

The `-Fc` custom archive format is useful with `pg_restore`.

Schema-only:

```bash
pg_dump --schema-only inventory > schema.sql
```

Data-only:

```bash
pg_dump --data-only inventory > data.sql
```

### Critical boundary

`pg_dump` is a **logical dump tool**, not a universal replacement for a production physical backup + WAL/PITR strategy.

The official documentation explicitly notes that, except for simple cases, `pg_dump` is generally not the right choice for regular production backups. citeturn439139search0

---

# 18. `pg_restore`

For archive formats:

```bash
pg_restore -d inventory_restore inventory.dump
```

You can also inspect or selectively restore archive contents.

The important engineering idea is:

```text
backup creation
       ↓
backup validation
       ↓
restore procedure
       ↓
application verification
```

A dump that exists is not the same as a recovery strategy that has been proven.

---

# 19. `pg_dumpall`

`pg_dump` works at the database level.

`pg_dumpall` can capture cluster-wide logical information, including global objects such as roles and tablespaces. citeturn439139search0

This distinction matters:

```text
DATABASE
    ↓
pg_dump

CLUSTER GLOBAL OBJECTS
    ↓
pg_dumpall-related workflows
```

Do not assume a single `pg_dump mydb` captures every operational object required to rebuild an entire PostgreSQL environment.

# 21. `pgbench`: Benchmarking Is Experimental Science

`pgbench` is PostgreSQL's benchmarking utility. citeturn308073search1

A benchmark is useful only when the experiment is controlled.

Bad benchmark:

```text
change config
→ run one query
→ feels faster
→ keep config
```

Good benchmark:

```text
Hypothesis
   ↓
Baseline
   ↓
Controlled change
   ↓
Repeat workload
   ↓
Measure
   ↓
Compare
   ↓
Reject or accept hypothesis
```

You will revisit this philosophy extensively in the performance-engineering phase.

# 22. `pg_config`

`pg_config` reports installation and build information such as include/library directories and PostgreSQL version information.

This can help when diagnosing:

- multiple PostgreSQL installations
- extension compilation issues
- PATH confusion
- wrong binary selection
- package vs source installations

# 23. `pg_amcheck`

`pg_amcheck` is a PostgreSQL tool for checking for corruption in one or more databases. citeturn308073search1

The important conceptual lesson:

```text
performance problem
≠
logical correctness problem
≠
physical corruption problem
```

Use the instrument that corresponds to the failure class.

Do not use query tuning techniques to diagnose a suspected storage-integrity issue.

# 24. `pg_verifybackup`

For physical base-backup workflows, PostgreSQL provides `pg_verifybackup` to verify the integrity of a backup manifest. The current client-tool reference includes it among the standard PostgreSQL utilities. citeturn308073search1turn308073search2

Again:

```text
backup produced
    ≠
backup verified
    ≠
restore tested
    ≠
DR strategy validated
```

Those are separate engineering states.

# 25. `psql` Scripting and Automation

A production-grade engineer should be comfortable taking manual diagnostics and turning them into deterministic scripts.

Example:

```bash
psql \
  -v ON_ERROR_STOP=1 \
  -h "$PGHOST" \
  -p "$PGPORT" \
  -U "$PGUSER" \
  -d "$PGDATABASE" \
  -f diagnostics.sql
```

This is much safer in CI than pasting commands interactively.

A diagnostic script might emit:

```sql
SELECT now();
SELECT version();
SELECT current_database();
SELECT current_user;
SELECT inet_server_addr(), inet_server_port();

SELECT
    pid,
    usename,
    datname,
    state,
    wait_event_type,
    wait_event,
    query_start,
    query
FROM pg_stat_activity;
```

The goal is not “more commands.”

The goal is a **repeatable evidence bundle**.

# 28. Production Diagnostic Workflow

When an incident starts, avoid random commands.

Use a structured sequence.

## Step 1 — Establish identity

```bash
hostname
pwd
whoami
psql --version
```

## Step 2 — Establish target

```bash
env | grep '^PG'
```

Then:

```bash
pg_isready -h "$PGHOST" -p "$PGPORT"
```

## Step 3 — Make a real connection

```bash
psql -X
```

The `-X` option is useful when you want to avoid loading `psqlrc` configuration during controlled troubleshooting or restores. PostgreSQL also recommends `-X` when restoring a plain-text `pg_dump` script to avoid interference from local `psql` settings. citeturn439139search0

## Step 4 — Record session identity

```text
\conninfo
```

```sql
SELECT
    version(),
    current_database(),
    current_user,
    session_user,
    inet_server_addr(),
    inet_server_port();
```

## Step 5 — Inspect server activity

```sql
SELECT
    pid,
    usename,
    datname,
    state,
    wait_event_type,
    wait_event,
    query_start,
    query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY query_start;
```

## Step 6 — Narrow the incident

Classify:

```text
connectivity
authentication
authorization
SQL correctness
query performance
locking
resource saturation
storage
replication
application behavior
```

## Step 7 — Use the smallest relevant instrument

Do not collect everything “just in case.”

Good diagnosis is targeted observation.

# 29. Evidence Discipline

Every diagnostic conclusion should have evidence.

Bad:

> “Postgres is overloaded.”

Better:

> “At 14:03 UTC, 78 active sessions were present, 51 were waiting on a lock-related event, and the oldest blocking transaction began at 13:41 UTC.”

Bad:

> “The index is not working.”

Better:

> “The observed plan uses a sequential scan because the planner estimates a large qualifying row count; `EXPLAIN ANALYZE` shows the estimate/actual divergence.”

Bad:

> “The database connection is broken.”

Better:

> “TCP connectivity succeeds, `pg_isready` reports accepting connections, but the application login fails at authentication.”

This evidence discipline is what separates database engineering from database superstition.

# 30. Common Mistakes

## Mistake 1 — “`pg_isready` succeeded, so my app should work.”

### Why it fails
`pg_isready` checks server responsiveness, not whether your specific role, database, password, TLS settings, or authorization succeeds. citeturn308073search12

### Correct mental model
Use:

```text
pg_isready → server state
psql       → real application-like connection test
```

---

## Mistake 2 — “`psql --version` tells me my database version.”

### Why it fails
It identifies the local client binary.

### Correct mental model
Use SQL against the connected server for server version.

---

## Mistake 3 — “`pg_dump` means I have production backups solved.”

### Why it fails
`pg_dump` is a logical database export. PostgreSQL explicitly distinguishes this from the broader production backup problem. citeturn439139search0

### Production consequence
You may lack:

- point-in-time recovery
- fast physical restore
- validated WAL chain
- tested disaster recovery

---

## Mistake 4 — “Run `EXPLAIN ANALYZE` on anything.”

### Why it fails
`ANALYZE` executes the statement.

### Production consequence
You can accidentally mutate production data with `UPDATE`, `DELETE`, or `INSERT`.

---

## Mistake 5 — “The GUI shows the server, so I know the environment.”

### Why it fails
A GUI can obscure implicit connection profiles, ports, roles, or environment differences.

### Better approach
Always know how to prove the target using CLI/SQL evidence.

---

## Mistake 6 — “Just restart PostgreSQL.”

### Why it fails
A restart destroys useful runtime state, may terminate workloads, and can convert a diagnosable incident into a less observable one.

### Expert rule
Preserve evidence before destructive operational actions unless immediate mitigation is required.

# 31. AI / Vibe-Coding Failure Modes

AI-generated database commands are especially dangerous because they often look plausible.

## Failure pattern 1 — Wrong target

AI proposes:

```bash
psql -d production -c 'DROP ...'
```

without proving which environment is targeted.

### Defense
Require explicit environment confirmation:

```text
host
port
database
role
environment
```

---

## Failure pattern 2 — Destructive command hidden in “cleanup”

Generated code may contain:

```sql
DELETE FROM orders;
```

inside a migration or test script.

### Defense
Inspect every write operation and transaction boundary.

---

## Failure pattern 3 — Unsafe troubleshooting

AI says:

> “Kill the long-running backend.”

That may be correct—or may kill the blocking transaction that needs forensic examination.

### Defense
Identify:

```text
PID
role
application_name
query
transaction age
blocking chain
business impact
```

before termination.

---

## Failure pattern 4 — Version-incompatible flags

AI-generated commands may be copied from documentation for another PostgreSQL major version.

### Defense
First establish:

```bash
psql --version
```

and:

```sql
SHOW server_version;
```

Then verify the command against the relevant version's official documentation.

```text
   ↓
```

# 33. Docker Tooling Scenario

A frequent error:

```text
host = localhost
```

inside a container.

Inside a container, `localhost` refers to the container itself—not automatically to the host or another container.

Therefore the tooling question becomes:

```text
Where is the PostgreSQL server?
Where is the client?
What network namespace is the client inside?
What DNS name resolves to the database?
What port is exposed vs internally reachable?
```

Example Compose-style mental model:

```text
nestjs container
     │
     │ db:5432
     ▼
postgres container
```

The application may need the service name `db`, not host `localhost`.

This is why connection debugging must understand the environment, not just the command.

# 35. Safety Model for Database Commands

Before executing an unfamiliar command, classify it.

```text
READ-ONLY
    ↓
LOW RISK WRITE
    ↓
TRANSACTIONAL WRITE
    ↓
DDL
    ↓
LOCK-ACQUIRING CHANGE
    ↓
DESTRUCTIVE CHANGE
    ↓
SERVER-WIDE / CLUSTER-WIDE OPERATION
```

Examples:

```sql
SELECT ...                 -- normally read-only
CREATE INDEX ...           -- DDL, operational impact
ALTER TABLE ...            -- DDL + locking considerations
DELETE ...                 -- destructive write
DROP TABLE ...             -- destructive DDL
pg_terminate_backend(...)  -- operational intervention
```

The more destructive the operation, the stronger the evidence and environment verification should be.

# 36. Tooling Decision Matrix

| Goal | Primary tool | Secondary evidence | Main danger |
|---|---|---|---|
| Check server availability | `pg_isready` | `psql` | false confidence |
| Execute SQL | `psql` | application client | wrong target |
| Inspect schema | `psql` meta-commands | catalogs | incomplete context |
| Understand query plan | `EXPLAIN` | catalog/statistics data | misreading estimates |
| Measure actual query | `EXPLAIN ANALYZE` | logs/statistics | executes statement |
| Inspect live workload | `pg_stat_activity` | OS tools | snapshot is incomplete |
| Investigate aggregate workload | `pg_stat_statements` | logs | misinterpreting averages |
| Export database logically | `pg_dump` | `pg_restore` | assuming it is full DR |
| Restore logical archive | `pg_restore` | application checks | untested recovery |
| Benchmark | `pgbench` | custom telemetry | invalid experiment |
| Check physical backup | `pg_verifybackup` | restore rehearsal | confusing verification with DR |
| Check corruption | `pg_amcheck` | storage/OS evidence | wrong problem class |
| Diagnose installation | `pg_config` | PATH/package manager | mixed versions |

# 41. Hands-On Lab 5 — Build a Diagnostic Script

Create `diagnostics.sql`:

```sql
\echo '=== SERVER ==='
SELECT version();

\echo '=== SESSION ==='
SELECT
    current_database() AS database,
    current_user AS current_user,
    session_user AS session_user,
    inet_server_addr() AS server_addr,
    inet_server_port() AS server_port;

\echo '=== ACTIVITY ==='
SELECT
    pid,
    usename,
    datname,
    application_name,
    state,
    wait_event_type,
    wait_event,
    query_start,
    query
FROM pg_stat_activity
ORDER BY query_start;
```

```bash

```


### Expert response

Because the symptom is:

not:

```text
PostgreSQL configuration
```

Always identify the bottleneck before selecting the remedy.

# 45. Expert Diagnostic Framework

## 2. What layer owns that fact?

```text
your authentication
```

This final question is the expert differentiator.

# 46. “Why Not?” Challenge System

Before using a tool, challenge yourself.

### Why `pg_isready` instead of `psql`?

Because you may only need endpoint liveness.

### Why `psql` instead of a GUI?

Because it is reproducible, scriptable, explicit, and easy to automate.

### Why `EXPLAIN` before `EXPLAIN ANALYZE`?

Because the estimated plan can be inspected without executing the query.

### Why `EXPLAIN ANALYZE`?

Because planner estimates alone do not reveal actual runtime behavior.

### Why `pg_stat_activity` before changing configuration?

Because live waits and transactions may expose the immediate cause.

### Why `pg_stat_statements`?

Because one query sample does not describe an entire workload.

### Why not use `pg_dump` as the entire DR plan?

# 47. Anti-Pattern Catalog

## Anti-pattern: command memorization

Knowing 50 commands is less valuable than knowing when each command is the right instrument.

## Anti-pattern: implicit targeting

Running `psql` without verifying the target during an incident.

## Anti-pattern: GUI-only operations

Being unable to reproduce or document a critical diagnostic.

## Anti-pattern: speculative tuning

Changing configuration before measuring.

## Anti-pattern: destructive diagnostics

Using mutation or restart as the first investigative action.

## Anti-pattern: backup illusion

Creating dumps without restore testing.

## Anti-pattern: one-signal diagnosis

Concluding “CPU issue,” “lock issue,” or “index issue” from one metric.

## Anti-pattern: version blindness

Using commands without establishing the PostgreSQL major version.
