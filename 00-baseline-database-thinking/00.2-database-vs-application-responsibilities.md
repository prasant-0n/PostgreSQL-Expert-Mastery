# 00.2 — Database vs Application Responsibilities

> **Phase:** 00 — Baseline & Database Thinking  
> **Chapter:** 00.2  
> **Target:** PostgreSQL Engineer / Backend Engineer / Database Architect  
> **Primary Outcome:** Learn to decide, deliberately and defensibly, what belongs in PostgreSQL, what belongs in application code, and what must be coordinated across both.

---

## 1. Chapter Mission

A production database is not merely a passive place where an application stores objects. It is an enforcement point, concurrency boundary, transactional system, query engine, durability system, and security boundary.

The application is also not merely a thin SQL client. It owns user interaction, orchestration, external integrations, domain workflows, and application-facing error handling.

The engineering problem is therefore not:

> **“Should logic be in the database or in the application?”**

The better question is:

> **“Which layer is the strongest and most appropriate authority for this invariant, rule, transformation, or workflow?”**

This chapter develops that judgment.

---

## 2. What You Must Be Able to Do After This Chapter

By the end of this chapter, you should be able to:

- distinguish **data integrity** from **business workflow logic**;
- explain why some rules must be enforced by PostgreSQL even when the application validates them;
- recognize rules that are unsafe to enforce only in application code under concurrency;
- identify logic that should remain application-side because it depends on external systems, user interaction, or orchestration;
- reason about **single source of truth**, defense in depth, and duplicated validation;
- design transaction boundaries across Node.js/NestJS and PostgreSQL;
- understand the performance and failure implications of moving logic across the boundary;
- review AI-generated backend/database code for misplaced responsibilities;
- design systems where both layers cooperate without becoming inconsistent;
- defend architectural decisions using correctness, concurrency, operability, security, and performance rather than preference.

# 3. The Core Mental Model

Think of the system as a chain of authority:

```text
User / Client
      ↓
Application / API
      ↓
Transaction Boundary
      ↓
PostgreSQL
      ↓
Durable State
```

A more useful architectural picture is:

```text
                    ┌─────────────────────────┐
                    │      Application        │
                    │                         │
                    │ UX / orchestration      │
                    │ external APIs           │
                    │ domain workflows        │
                    │ input normalization     │
                    │ API contracts           │
                    └───────────┬─────────────┘
                                │
                         commands / queries
                                │
                    ┌───────────▼─────────────┐
                    │       PostgreSQL        │
                    │                         │
                    │ integrity               │
                    │ constraints             │
                    │ transactions            │
                    │ concurrency             │
                    │ durable state           │
                    │ authorization*          │
                    │ query processing        │
                    └─────────────────────────┘
```

`*` PostgreSQL can enforce authorization and row-level policies in suitable architectures. Whether it should do so depends on the security and service-boundary design.

The key idea is:

> **The application proposes operations. PostgreSQL protects the correctness of the durable relational state and executes them according to transactional and concurrency rules.**

This is a default, not an absolute law. Good architects know when to break the default and can explain why.

# 4. Five Different Kinds of “Logic”

Many architecture arguments become confused because engineers call everything “business logic.” Separate the categories.

## 4.1 Input Validation

Examples:

- username must not be empty;
- password must satisfy a product requirement;
- request body must contain a required property;
- an API field must have the expected shape;
- a file must be within an application-level size limit.

This usually belongs primarily at the **application boundary** because the application is responsible for producing useful client-facing errors.

Input validation, however, is not the same thing as data integrity.

---

## 4.2 Data Integrity Invariants

Examples:

- email must be unique;
- quantity cannot be negative;
- an order item must reference an existing order;
- a persisted identifier must be unique;
- a tenant-local business identifier must not collide;
- a required relationship must exist.

These are excellent candidates for PostgreSQL constraints and transactional mechanisms.

PostgreSQL provides `CHECK`, `UNIQUE`, `PRIMARY KEY`, and `FOREIGN KEY` constraints specifically to restrict invalid table state; violating writes are rejected. citeturn860751search1

The principle is:

> **If invalid state must never become durable, put an enforcement mechanism at or very close to the durable-state boundary.**

---

## 4.3 Domain Rules

Examples:

- a premium customer gets a different discount;
- an order above a threshold needs manager approval;
- a customer enters a risk state after a pattern of events;
- shipping choice depends on destination, inventory, service level, and carrier rules.

Some domain rules can be represented by database constraints or queries. Others are better expressed in application/domain services.

The key distinction is often:

```text
state invariant
vs.
workflow decision
```

---

## 4.4 Workflow / Orchestration Logic

Example:

```text
Create order
→ reserve stock
→ charge payment provider
→ publish event
→ send confirmation
```

This is usually application orchestration.

PostgreSQL can execute sophisticated logic, but its ability to express something does not mean it should own the entire distributed workflow.

---

## 4.5 Database / Operational Responsibilities

Examples:

- indexes;
- query planning;
- transaction isolation;
- locks;
- WAL and durability;
- vacuum;
- replication;
- backup/recovery mechanisms;
- storage and memory management.

These are fundamentally database-system responsibilities. A backend engineer uses these mechanisms; they do not recreate them in TypeScript.

---

# 5. The Most Important Distinction: Validation vs Enforcement

A common beginner architecture is:

```text
Request
  ↓
Application validates
  ↓
Application inserts
  ↓
Database stores
```

The hidden assumption is:

> “Because the application checked it, the database can trust it.”

That assumption breaks under concurrency and multiple writers.

Consider:

```ts
const existing = await findByEmail(email);
if (!existing) {
  await insertUser(email);
}
```

Two requests can execute concurrently:

```text
T1: SELECT email → not found
T2: SELECT email → not found

T1: INSERT email
T2: INSERT email
```

The application performed validation. It did not establish uniqueness.

A PostgreSQL `UNIQUE` constraint gives the database authority over that persisted invariant. PostgreSQL rejects a write that violates it. citeturn860751search1

Therefore:

```text
Validation ≠ Enforcement
```

Application validation is primarily about:

- user experience;
- API ergonomics;
- early feedback;
- request rejection;
- domain workflow behavior.

Database enforcement is about:

- durable correctness;
- concurrency correctness;
- integrity across writers;
- protection against scripts, jobs, imports, tools, and future services.

---

# 6. Why the Database Cannot Simply “Trust the Application”

Imagine a system with multiple writers:

```text
                 ┌─ REST API
                 ├─ GraphQL API
                 ├─ Worker
                 ├─ Cron job
                 ├─ Admin tool
                 ├─ Import script
                 ├─ Migration
                 └─ Future service
                         ↓
                    PostgreSQL
```

If an invariant exists only inside one endpoint, every other writer can bypass it.

This yields a critical rule:

> **An invariant that must hold across all relevant writers should be enforced at a boundary shared by all relevant writers.**

Frequently, that boundary is PostgreSQL itself.

This is particularly important in mature systems where direct SQL access, batch jobs, data fixes, migrations, and operational scripts are real—not theoretical—writers.

---

# 7. What Belongs in PostgreSQL?

A strong default is to consider PostgreSQL first when the rule describes the validity of stored relational state.

## 7.1 Identity

Examples:

```sql
PRIMARY KEY
UNIQUE
```

Question:

> Can two persisted rows legally represent the same identity?

If the answer is no, database enforcement is usually appropriate.

---

## 7.2 Relationships

Example:

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(id)
```

Question:

> Can a child row legally exist without its parent?

When this is a true referential invariant, PostgreSQL is an appropriate enforcement point.

---

## 7.3 Value Constraints

Example:

```sql
CHECK (quantity > 0)
```

Question:

> Can this value ever be valid when this condition is false?

If not, enforce it close to storage.

---

## 7.4 Cross-Row Uniqueness

Example:

```sql
UNIQUE (tenant_id, sku)
```

This is crucial in multi-tenant systems.

Application checks can race. A database uniqueness constraint remains authoritative for the committed state.

---

## 7.5 Transactional State Changes

When several writes must succeed or fail as one unit, PostgreSQL transactions are a natural part of the solution.

Example:

```text
Create order
+ create order items
+ reserve stock
+ create audit record
```

If these state transitions must be atomic, the transaction boundary must include them.

PostgreSQL documents `READ COMMITTED` as its default isolation level; stronger isolation such as `SERIALIZABLE` provides stricter guarantees but can result in serialization failures that applications need to retry. citeturn860751search0turn860751search9

---

# 8. What Usually Belongs in the Application?

The application is usually the better home for logic requiring:

- user interaction;
- HTTP or other API protocols;
- external service calls;
- payment providers;
- email delivery;
- feature flags;
- request-specific orchestration;
- API-specific presentation;
- workflow sequencing;
- policies involving several systems;
- retries around unreliable external dependencies.

Example:

```text
Request
  ↓
Validate input
  ↓
Load domain state
  ↓
Calculate business decision
  ↓
Coordinate external provider
  ↓
Persist durable result
  ↓
Publish follow-up work
```

A database is not automatically the right owner merely because it contains some of the involved data.

---

# 9. The Database Should Not Accidentally Become the Workflow Engine

A powerful database can tempt engineers to put everything into it:

```text
API
 ↓
Stored procedure
 ↓
Trigger
 ↓
Function
 ↓
Trigger
 ↓
Notification
 ↓
Worker
```

This can be valid in carefully designed systems, but uncontrolled database-side behavior can create:

- hidden control flow;
- debugging difficulty;
- deployment coupling;
- difficult local development;
- reduced portability;
- unclear ownership;
- recursive side effects;
- complicated tests.

PostgreSQL triggers can execute functions automatically for supported operations, with row-level and statement-level behavior; trigger cascades and recursion are possible. citeturn860751search6turn860751search7

Therefore:

> **Do not introduce invisible behavior merely because the database makes it technically possible.**

This does **not** mean “never use triggers.” It means every trigger should have an explicit reason, ownership, test strategy, and operational story.

# 10. Responsibility Decision Framework

For every piece of logic, ask these questions.

### Question 1 — Is it a hard data invariant?

Examples:

```text
must be unique
must reference an existing row
must be positive
must satisfy a structural relational rule
```

Strong database candidate.

### Question 2 — Must it hold regardless of writer?

If yes, strongly consider database enforcement.

### Question 3 — Does correctness depend on concurrency?

If yes, database transaction/constraint/locking mechanisms deserve primary consideration.

### Question 4 — Does the rule depend on external systems?

If yes, application orchestration is usually required.

### Question 5 — Is it mainly about API or UX semantics?

Usually application-side.

### Question 6 — Would storing the invalid result ever be acceptable?

If no, database enforcement should usually be considered.

### Question 7 — Is the control flow hidden from ordinary application readers?

If yes, scrutinize triggers/functions especially carefully.

### Question 8 — Is the operation data-intensive?

Do not automatically move it into Node.js. PostgreSQL may be much more efficient when computation can be executed set-wise beside the data.

# 11. The Two-Layer Validation Pattern

A mature system often validates in both layers, but for different reasons:

```text
                 Application
              ┌───────────────┐
              │ API validation│
              │ UX feedback   │
              │ Domain checks │
              └───────┬───────┘
                      │
                      ▼
                 PostgreSQL
              ┌───────────────┐
              │ Constraints   │
              │ Transactions  │
              │ Concurrency   │
              │ Integrity     │
              └───────────────┘
```

Example:

Application:

```ts
if (price <= 0) {
  throw new BadRequestException('Price must be positive');
}
```

Database:

```sql
CHECK (price > 0)
```

They are not necessarily redundant.

Application asks:

> “How should this request be communicated to the caller?”

Database asks:

> “Can this invalid state be persisted?”

# 12. Single Source of Truth vs Defense in Depth

## Single Source of Truth

There should be an explicit authority for durable correctness.

Example:

```text
Uniqueness authority → database UNIQUE constraint
```

The application may pre-check for a friendly message, but the constraint remains authoritative.

## Defense in Depth

Multiple layers may detect or prevent the same bad input for different reasons:

```text
Frontend
  ↓
API
  ↓
Domain service
  ↓
Database
```

The mistake is thinking that duplicated validation automatically creates duplicated authorities.

A mature design states the authority explicitly.

---

# 13. Concurrency Changes the Entire Decision

Many application-only rules appear correct when reasoning about one request.

Example:

```ts
const existing = await repo.findByEmail(email);

if (existing) {
  throw new ConflictException('Already exists');
}

await repo.insert({ email });
```

Under concurrency:

```text
Request A                  Request B
---------                  ---------
SELECT → none              SELECT → none
INSERT                     INSERT
```

The bug is not simply “two requests ran.”

The deeper failure is:

```text
Invariant:
email must be unique

Enforcement:
application pre-check

Concurrency:
pre-check and write are separate operations

Result:
state transition is not protected atomically
```

A stronger design is:

```sql
ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);
```

Then:

```text
Application:
attempt operation + handle conflict

Database:
enforce uniqueness
```

This pattern generalizes to many concurrency problems.

---

# 14. Transactions: The Application Defines the Business Unit, PostgreSQL Provides Transaction Semantics

A transaction is not merely a SQL wrapper.

The application determines:

> “Which state changes belong to the same business operation?”

PostgreSQL provides the actual transaction machinery and concurrency semantics.

For example:

```text
Transfer ₹1,000

Debit A
Credit B
Create audit entry
```

The application may define:

```text
BEGIN
  debit
  credit
  audit
COMMIT
```

PostgreSQL then provides the guarantees governing that transaction.

PostgreSQL isolation controls what concurrent transactions can observe. Serializable transactions can fail with `serialization_failure`; callers must therefore understand retry semantics. citeturn860751search0turn860751search9

Useful mental model:

> **The application owns the business transaction boundary; PostgreSQL owns the execution guarantees of that transaction.**

---

# 15. Example — Inventory Reservation

Suppose:

```text
product_id = 42
available = 1
```

Two customers attempt to buy the last unit.

Naive logic:

```text
Read available
if available > 0
    write available - 1
```

Possible schedule:

```text
T1 reads 1
T2 reads 1
T1 writes 0
T2 writes 0
```

If two orders are created, the system has oversold despite the final inventory value looking plausible.

A stronger approach can turn the condition and state transition into one database operation:

```sql
UPDATE inventory
SET available = available - 1
WHERE product_id = $1
  AND available > 0
RETURNING product_id, available;
```

The application checks whether a row was returned.

The important principle is:

> **When possible, encode the concurrency-sensitive state transition as one atomic database operation rather than relying on a separate read and write.**

The exact design may later require row locks, isolation changes, idempotency, reservation tables, or other mechanisms. The lesson here is responsibility placement.

---

# 16. Example — Order Creation

Suppose an order involves:

```text
orders
order_items
inventory_reservations
payments
audit_log
```

A weak design might perform independent commits:

```text
insert order → commit
reserve stock → commit
charge payment → commit
insert audit → commit
```

Now crashes can leave partial state.

A better design asks:

```text
Which changes must be locally atomic?
Which operations are external?
Which operations can be retried?
Which effects must become durable before external work begins?
```

Possible architecture:

```text
Application
   │
   ├── validate
   │
   ├── BEGIN
   │     ├── create order
   │     ├── create items
   │     ├── reserve inventory
   │     └── create durable outbox event
   │
   ├── COMMIT
   │
   └── Worker
         ├── payment provider
         ├── email
         └── integration events
```

This separates:

```text
local durable consistency
from
external side effects
```

Later chapters will deepen this into outbox, idempotency, distributed systems, and recovery design.

# 17. Stored Procedures and Functions

PostgreSQL can execute server-side functions and procedures.

Good reasons to use database-side code can include:

- data-intensive transformations;
- reusable database-centric operations;
- reducing excessive network round trips;
- carefully controlled security boundaries;
- atomic operations tightly coupled to stored data.

But server-side execution has operational implications.

PostgreSQL warns that functions, triggers, and row-level security policies introduce executable logic into the backend environment and therefore require careful control of object ownership and `search_path` behavior. citeturn860751search3

Treat database-side code as production software:

```text
version control
code review
migration discipline
tests
security review
observability
rollback strategy
```

---

# 18. When Database-Side Computation Is Better

Imagine processing millions of rows already inside PostgreSQL.

If the transformation is set-oriented and can run safely inside the database, moving every row to Node.js creates unnecessary movement:

```text
PostgreSQL
   ↓
network
   ↓
Node.js
   ↓
network
   ↓
PostgreSQL
```

Where appropriate:

```text
PostgreSQL
└── set-based transformation
```

This can reduce network transfer and exploit the database's strengths in relational processing.

Therefore:

> **“All business logic belongs in the application” is as simplistic as “all business logic belongs in the database.”**

Architecture requires workload-aware reasoning.

---

# 19. When Application Logic Is Better

Consider a decision depending on:

```text
customer state
subscription plan
promotion service
fraud service
currency service
shipping provider
feature flag
experiment assignment
```

Turning PostgreSQL into an integration hub may produce:

- external dependency coupling;
- long transactions;
- fragile failure handling;
- operational difficulty;
- complicated security boundaries;
- reduced service autonomy.

This is usually a better application/service responsibility.

---

# 20. Performance Implications of Responsibility Placement

Moving logic across the boundary changes the cost model.

## Application-side work can increase

```text
network round trips
serialization / deserialization
memory pressure
object allocation
result transfer
CPU duplicated across layers
```

## Database-side work can increase

```text
DB CPU usage
lock duration
memory pressure
transaction duration
contention
operational coupling
```

Therefore:

> **Do not choose the layer for performance based on intuition alone. Measure the actual workload.**

A database-side operation can replace thousands of network round trips.

A poorly designed database-side workflow can also turn the primary database into a system-wide bottleneck.

---

# 21. The Transaction Duration Trap

One of the worst boundary mistakes is putting external network calls inside a database transaction.

Bad pattern:

```text
BEGIN
  update order
  call payment provider      ← external latency
  call tax provider          ← external latency
  call shipping provider     ← external latency
COMMIT
```

This can prolong:

- locks;
- connection usage;
- transaction age;
- contention;
- recovery complexity.

A mature design normally keeps database transactions focused on local atomic state changes and uses durable workflow mechanisms for external effects.

---

# 22. Error Ownership

A mature architecture maps failures to meaningful ownership.

Examples:

```text
400 Bad Request
→ invalid API input

404 Not Found
→ API resource semantics

409 Conflict
→ resource/business conflict

unique_violation
→ database-enforced uniqueness failed

foreign_key_violation
→ database-enforced relationship failed

serialization_failure
→ transaction cannot safely commit under chosen isolation
```

The application should translate database failures into meaningful API behavior while respecting their semantics.

Example:

```ts
try {
  await tx.user.create({ data: { email } });
} catch (error) {
  if (isUniqueViolation(error)) {
    throw new ConflictException('Email already exists');
  }

  throw error;
}
```

This is stronger than relying on a race-prone existence pre-check.

---

# 23. Security Responsibilities

Security spans both layers.

Application responsibilities may include:

- authentication workflow;
- sessions or tokens;
- API authorization;
- rate limiting;
- input validation;
- user-facing policy decisions.

Database responsibilities may include:

- roles;
- privileges;
- ownership;
- row-level security;
- controlled execution of database functions.

PostgreSQL roles can represent users or groups, own objects, receive privileges, and inherit role memberships. citeturn860751search4

Database function security deserves particular attention because executable backend functions run with database-server context; PostgreSQL specifically warns about unsafe object resolution and `search_path` usage. citeturn860751search3

The correct boundary depends on the system's threat model and architecture.

# 24. AI / Vibe-Coding Failure Patterns

AI-generated backend code frequently produces responsibility mistakes that look correct in isolation.

## Failure 1 — Pre-checking uniqueness

```ts
const exists = await findByEmail(email);
if (exists) throw new Error('duplicate');
await createUser(email);
```

**Problem:** race condition.

**Correct model:** database owns uniqueness; application handles conflict.

---

## Failure 2 — Manually enforcing referential integrity

```ts
const customer = await findCustomer(customerId);
if (!customer) throw new Error('invalid customer');
await createOrder(customerId);
```

**Problem:** the rule must be remembered by every writer and still does not replace proper relational integrity.

**Better model:** use a foreign key when the relationship is a real invariant.

---

## Failure 3 — Long transaction around external APIs

```ts
await db.transaction(async tx => {
  await tx.order.create(...);
  await paymentApi.charge(...);
  await emailApi.send(...);
});
```

**Problem:** external latency occurs while database resources remain associated with the transaction.

**Better model:** narrow local transactions and coordinate external work through durable workflow mechanisms.

---

## Failure 4 — “Everything in SQL”

AI places an entire distributed workflow into procedures and triggers because SQL can express it.

**Problem:** expressibility is not architecture.

**Correct question:** Who owns it? How is it tested? How is it observed? How is it deployed? How does it retry? What happens during partial failure?

---

## Failure 5 — “Everything in TypeScript”

AI implements every integrity rule in services and leaves the schema weak.

**Problem:** alternate writers can violate assumptions.

**Correct model:** enforce durable invariants at the durable boundary where practical.

# 25. Production Scenario — Multi-Tenant ERP

Suppose:

```text
tenant_id
branch_id
product_id
sku
price
stock
```

Business rule:

> SKU must be unique per tenant.

Weak application logic:

```ts
find({ tenantId, sku });
if (!found) create();
```

Database invariant:

```sql
UNIQUE (tenant_id, sku)
```

The application can provide early feedback, but PostgreSQL remains the final authority over committed state.

The pattern applies to:

```text
tenant + email
tenant + external_id
tenant + invoice_number
tenant + barcode
branch + product + active-price identity
```

The schema is expressing a domain fact—not merely storing fields.

---

# 26. Production Scenario — Soft Delete

Suppose:

```text
users(id, email, deleted_at)
```

Requirement:

> Active users need unique emails, while historical deleted users may retain the old email.

A global:

```sql
UNIQUE (email)
```

may be too restrictive.

A database-aware solution can express the active-row invariant with a partial unique index:

```sql
CREATE UNIQUE INDEX users_active_email_key
ON users(email)
WHERE deleted_at IS NULL;
```

This illustrates a wider lesson:

> **Relational schema design can encode nuanced business invariants more safely than application-only conventions.**

---

# 27. Production Scenario — Audit Timestamp

Requirement:

> Every meaningful update must maintain `updated_at`.

Application-only approach:

```ts
entity.updatedAt = new Date();
await save(entity);
```

Risk:

```text
writer A remembers
writer B forgets
writer C uses a script
```

Database-side mechanisms such as triggers can centralize the invariant, but they introduce hidden execution and must therefore be justified.

This is a good architectural trade-off example:

```text
centralized enforcement
vs.
explicit application behavior
```

The right choice depends on write paths, ownership, observability, and operational complexity.

---

# 28. Production Scenario — Financial Ledger

Imagine a transfer requires:

```text
debit entry
credit entry
transaction record
```

The application decides:

```text
this request is a transfer
```

The database transaction ensures the related durable writes can be committed atomically.

Additional database constraints and carefully designed schema structures can enforce structural validity, while the application owns workflow semantics such as authorization, external communication, and retry policy.

Financial correctness requires stronger reasoning than “the application validated it.” Later phases build this into immutable ledgers, exact numeric modeling, idempotency, auditability, and concurrency.

# 30. The “Every Writer” Test

When deciding where an invariant belongs, enumerate every writer:

```text
REST API
Admin API
Background worker
Import job
Migration
Support tool
Data repair script
Future service
Direct SQL access
```

Ask:

> **Does every writer pass through the application code that enforces the rule?**

If not, application-only enforcement is suspect.

This question catches many production integrity bugs.

---

# 31. The “Invalid State Escape” Test

Ask:

> **Can the invalid state exist in the database after a successful commit?**

If the answer must be no, database enforcement deserves serious consideration.

Examples:

```text
duplicate invoice number
orphan order item
negative stock
invalid tenant relationship
invalid parent reference
```

This is stronger than:

> “We validate it in NestJS.”

---

# 32. The “Atomicity” Test

Ask:

> **If the process crashes after step 3 but before step 4, what durable state remains?**

If the answer is:

```text
partially completed business operation
```

reconsider:

- transaction boundaries;
- state transitions;
- outbox/event mechanisms;
- idempotency;
- workflow design;
- rollback/recovery behavior.

The database/application boundary is also a **failure-semantics boundary**.

---

# 33. The “Data Gravity” Test

Ask:

> **Where is the data already located?**

If a transformation can be expressed safely and efficiently inside PostgreSQL, moving a large dataset through Node.js may be unnecessarily expensive.

If an operation mainly depends on external APIs, user interaction, or distributed workflow, keeping it inside PostgreSQL may be equally harmful.

Therefore ask:

```text
Where does the data live?
Where does computation live?
Where does contention live?
Where does failure live?
Where does ownership live?
```

---

# 34. The “Ownership” Test

Every important responsibility should have a clear owner.

Examples:

```text
API contract → API/application team
Durable uniqueness → PostgreSQL
Payment workflow → payment/application domain
Database schema invariants → database/backend ownership
```

Shared responsibility without explicit ownership often becomes:

```text
Everybody assumes somebody else protects it.
```

That is a production failure pattern.

---

# 35. Advanced Mental Model: Valid States and State Transitions

Let:

```text
S = all possible persisted states
V ⊂ S = valid persisted states
```

The schema, constraints, and transactional mechanisms help enforce:

```text
state ∈ V
```

The application proposes business transitions:

```text
s₁ → s₂
```

The database protects the durable shared state while concurrent requests attempt transitions.

This gives a powerful split:

```text
Application:
“What business operation is being attempted?”

Database:
“Can the resulting durable state and transaction be accepted?”
```

This model becomes increasingly useful as concurrency and distributed workflows are introduced.

---

# 36. Advanced Mental Model: Invariant vs Algorithm vs Workflow

Separate three concepts:

```text
Invariant = what must always be true
Algorithm  = how a decision is calculated
Workflow   = which actions occur and in what sequence
```

Examples:

```text
Invariant:
email must be unique
→ database

Algorithm:
calculate best discount
→ usually application/domain service

Workflow:
reserve → charge → fulfill
→ application/orchestration
```

Some rules span layers, but separating the concepts prevents many architecture arguments from becoming vague.

---

# 37. Advanced Mental Model: Explicit vs Hidden Control Flow

Application code usually exposes sequence:

```ts
await createOrder();
await reserveInventory();
await publishEvent();
```

Database triggers can hide additional behavior:

```sql
INSERT INTO orders ...;
```

which may actually mean:

```text
INSERT
 → trigger
   → function
     → audit insert
       → second trigger
```

Hidden control flow is not automatically wrong, but it increases the burden on:

- documentation;
- debugging;
- testing;
- observability;
- dependency discovery;
- operational understanding.

# 41. Expert “Why?” Drill

Knowing the recommendation is not enough.

Example:

**Why use a UNIQUE constraint?**  
Because uniqueness is a durable state invariant.

**Why is the application pre-check insufficient?**  
Because concurrent requests can observe the same pre-write state.

**Why is the database a stronger enforcement point?**  
Because it owns the shared persisted state and can reject conflicting writes.

**What happens when enforcement fails?**  
The database rejects the write with a database error.

**What should the application do?**  
Translate the failure into appropriate domain/API behavior, or retry when the failure is retryable and semantics allow it.

**What if there are multiple writers?**  
The database remains the shared enforcement point.

This depth of reasoning is the expected standard for future chapters.

# 42. Anti-Patterns

```text
❌ “The API validates it, so the database does not need a constraint.”

❌ “All business logic belongs in PostgreSQL.”

❌ “All business logic belongs in TypeScript.”

❌ “We can SELECT first, then INSERT safely.”

❌ “A long transaction is fine because the API calls are short.”

❌ “Triggers are always bad.”

❌ “Triggers solve everything.”

❌ “ORM validation equals database integrity.”

❌ “If SQL can express it, SQL should own it.”

❌ “If TypeScript can express it, TypeScript should own it.”
```

Replace these with:

```text
✅ Identify the invariant.
✅ Identify every writer.
✅ Identify concurrency.
✅ Identify the atomic unit.
✅ Identify external dependencies.
✅ Identify the authoritative layer.
✅ Measure the workload.
✅ Make failure semantics explicit.
✅ Make ownership explicit.
```

# 44. Key Takeaways

```text
1. Validation is not enforcement.
2. Durable invariants belong close to durable state.
3. Application-only checks can race.
4. PostgreSQL constraints encode data correctness.
5. The application owns user-facing and cross-system workflow behavior.
6. PostgreSQL owns relational and transactional enforcement mechanisms.
7. Both layers may validate the same input for different purposes.
8. Responsibility placement affects performance and failure semantics.
9. External calls generally should not sit inside long database transactions.
10. Database-side code is production software and requires security, testing, versioning, and operational discipline.
11. Neither “everything in SQL” nor “everything in TypeScript” is a sound architecture rule.
12. Use invariants, concurrency, data locality, failure semantics, ownership, security, and measured workload to decide.
```
