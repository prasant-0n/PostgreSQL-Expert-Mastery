# Chapter 00.1 — Relational Database Mental Model

**Phase:** 00 — Baseline & Database Thinking  
**Target mastery:** L7 — Internal Mastery  
**Audience:** Developer with programming, backend, and basic SQL knowledge

---

## 1. Chapter Objective

This chapter establishes the mental model required for the rest of the PostgreSQL curriculum.

The objective is not to memorize definitions such as "a table contains rows and columns." The objective is to understand the relational model well enough to reason about:

- what data represents
- what a relation represents
- why rows and columns are not the whole story
- how relationships are represented
- what keys actually mean
- how constraints encode invariants
- why SQL is declarative and set-oriented
- why relational thinking differs from object-oriented thinking
- why application objects should not be treated as a database schema
- why database correctness must be modeled explicitly
- how these ideas eventually connect to transactions, MVCC, indexes, query planning, and distributed systems

PostgreSQL's current documentation describes a table as a relation-like structure made of rows and columns, with a fixed column definition and a variable number of rows; it also emphasizes that SQL does not guarantee row ordering unless an explicit ordering is requested. citeturn313630view0

---

# 2. Why This Chapter Matters

Most backend developers learn databases in this order:

```text
CREATE TABLE
↓
INSERT
↓
SELECT
↓
UPDATE
↓
DELETE
↓
JOIN
```

That is enough to build CRUD applications.

It is not enough to become a database engineer.

A database engineer must reason about the **meaning and invariants of data** before thinking about queries.

Consider an order system.

A shallow model is:

```text
orders
users
products
```

A stronger model asks:

```text
What is an order?
Can an order exist without a customer?
Can one order contain multiple products?
Can the same product occur twice in an order?
Can an order be created before payment?
What makes an order unique?
What does "cancelled" mean?
Can a cancelled order become paid?
Who owns the order?
What data must never change after confirmation?
Which business invariants must the database guarantee?
```

Those questions are relational modeling questions.

The database does not know your business rules simply because your TypeScript interfaces do.

# 3. Three Levels of Definition

## 3.1 Simple Definition

A relational database stores structured data in relations, commonly represented through tables containing rows and columns.

## 3.2 Engineering Definition

A relational database models data as sets of related values with defined domains, keys, relationships, and integrity constraints, and provides a declarative language for manipulating and querying those relations.

## 3.3 Expert Definition

The relational model is a mathematical model for representing information as relations over attributes with defined domains, where correctness is expressed through predicates, keys, and integrity constraints, and operations are primarily defined over sets rather than individual application objects.

The important consequence is this:

> **The database model describes valid states of data, not merely the shape of application objects.**

This distinction becomes foundational when we later study transactions, concurrency, isolation, indexing, and distributed consistency.

---

# 4. The Core Mental Model

Think of a relational database as a system that maintains a collection of facts subject to rules.

```text
                         DATABASE
                            │
             ┌──────────────┼──────────────┐
             │              │              │
          Relations      Constraints    Transactions
             │              │              │
        Represent data   Define valid   Control state
             │              │          transitions
             └──────────────┼──────────────┘
                            │
                      SQL Operations
                            │
                    Query / Mutate State
```

The key idea is:

> **Tables are a representation. Relationships and invariants are the deeper model.**

# 5. Relation, Tuple, Attribute, Domain

These concepts are frequently used loosely. At expert level, distinguish them carefully.

## 5.1 Relation

A relation is the logical structure representing a set of tuples over named attributes.

In practical PostgreSQL work, tables are the primary implementation of persistent relational data.

Do not confuse:

```text
relation
```

with:

```text
row
```

or with:

```text
table-as-physical-storage
```

A table has a logical schema, while PostgreSQL also has a physical storage representation. We will study the physical layer in Phase 03.

## 5.2 Tuple

A tuple is one record/value combination in a relation.

Developers commonly call this a "row."

For practical work:

```text
Tuple ≈ row
```

but the relational concept is broader and more precise.

## 5.3 Attribute

An attribute is a named component of a relation.

Developers commonly call this a "column."

```text
customer_id
name
email
created_at
```

## 5.4 Domain

A domain describes the set of values that are valid for an attribute.

For example:

```text
customer_id → integer-like identifier domain
email       → text values satisfying the application's integrity requirements
created_at  → timestamp values
```

PostgreSQL data types constrain the set of possible values and give stored values semantics for operations. citeturn313630view0

The deeper principle is:

> **A column is not merely a place to store a value. It represents a business or technical concept with an expected domain.**

# 6. Tables Are Not Ordered Collections

One of the first mental-model corrections to make is that a SQL table does not inherently have a meaningful row order.

This is explicitly documented by PostgreSQL: query results are unordered unless an `ORDER BY` specifies the desired ordering. citeturn313630view0

This means:

```sql
SELECT * FROM users;
```

does **not** mean:

> Give me users in insertion order.

Nor does it mean:

> Give me users in primary-key order.

Nor does a previous observed ordering become a guarantee.

If ordering matters:

```sql
SELECT *
FROM users
ORDER BY created_at, id;
```

The inclusion of a deterministic tie-breaker is often important:

```sql
ORDER BY created_at, id
```

rather than:

```sql
ORDER BY created_at
```

when multiple rows can share the same timestamp.

### Expert principle

> **Never infer guarantees from an implementation detail you did not explicitly request.**

This principle will reappear throughout the curriculum.

---

# 7. Set-Based Thinking

A common beginner mental model is:

```text
Loop over rows
↓
Process row 1
↓
Process row 2
↓
Process row 3
```

SQL is more naturally thought of as:

```text
Define the set you want
↓
Describe the transformation
↓
Let PostgreSQL choose an execution strategy
```

For example:

```sql
SELECT id, name
FROM customers
WHERE status = 'active';
```

You are not specifying:

```text
open table
for each row
check status
copy matching row
```

You are declaring:

> Return the projection of customers satisfying the predicate `status = 'active'`.

PostgreSQL is then free to choose an execution strategy through planning and execution.

This distinction becomes extremely important later when we study query plans.

---

# 8. Declarative vs Procedural Thinking

## Procedural Thinking

You specify **how** to perform an operation.

Example:

```text
for every customer:
    if customer.status == 'active':
        append customer to result
```

## Declarative Thinking

You specify **what result must be produced**.

```sql
SELECT *
FROM customers
WHERE status = 'active';
```

The database can choose among possible execution strategies.

For the same logical request, PostgreSQL might eventually use:

```text
Sequential Scan
```

or:

```text
Index Scan
```

or:

```text
Bitmap Heap Scan + Bitmap Index Scan
```

or another plan.

The application declares the result requirement; PostgreSQL selects a physical strategy.

---

# 9. The Three Layers You Must Keep Separate

Expert database reasoning depends on separating three different layers.

## Layer 1 — Logical Model

What does the data mean?

```text
Customer
Order
Product
Payment
```

## Layer 2 — SQL Representation

How are those concepts expressed?

```sql
CREATE TABLE customers (...);
CREATE TABLE orders (...);
```

## Layer 3 — Physical Implementation

How does PostgreSQL store and execute it?

```text
heap pages
indexes
buffers
WAL
MVCC tuples
executor nodes
```

Do not mix these layers.

A logical decision can remain stable while physical implementation changes.

For example:

```text
Logical question:
"Find active customers."

SQL:
SELECT ... WHERE status = 'active';

Physical plan:
Index Scan / Seq Scan / Bitmap Scan
```

We will progressively descend from logical semantics to physical execution throughout this curriculum.

# 10. Entity vs Relation

Application developers often begin with classes or TypeScript interfaces:

```ts
interface User {
  id: string;
  name: string;
  email: string;
}
```

That is useful, but it is not automatically a correct relational model.

Why?

Because an application object answers:

> What fields does this object expose?

A database model must additionally answer:

> What states of the world are valid?

For example:

```text
User
```

may need:

```text
id UNIQUE NOT NULL
email UNIQUE
status constrained to valid states
created_at NOT NULL
```

A TypeScript interface alone does not enforce these invariants in PostgreSQL.

---

# 11. Keys: Identity vs Attribute

A key is not simply "an ID column."

A key expresses a uniqueness property.

Suppose:

```text
customers
--------------------------------
id | name | email
```

A candidate key might be:

```text
email
```

if the business rule guarantees that no two customers may share the same email.

Another candidate key could be:

```text
id
```

The choice of primary key is therefore an architectural decision, not merely an ORM convention.

---

# 12. Candidate Key

A candidate key is a minimal set of attributes capable of uniquely identifying a tuple within the modeled relation.

Example:

```text
Employee
--------------------------------
employee_id
company_id + employee_number
```

Both might theoretically identify an employee.

One could become the primary key while the other remains protected through a unique constraint.

---

# 13. Primary Key

A PostgreSQL primary key requires uniqueness and non-nullability. PostgreSQL automatically creates a unique B-tree index for a primary key and enforces the relevant `NOT NULL` property. A table can have only one primary key, although it may have multiple unique constraints. citeturn313630view1

Example:

```sql
CREATE TABLE customers (
    id bigint PRIMARY KEY,
    name text NOT NULL,
    email text NOT NULL
);
```

The important conceptual distinction is:

```text
Primary Key
    ↓
Identity / key constraint
    ↓
Uniqueness + non-nullability
```

The physical index is an implementation mechanism supporting that logical constraint.

Do not reverse the relationship mentally and say:

> "The primary key is an index."

More precisely:

> **The primary key is a constraint; PostgreSQL uses a unique B-tree index to enforce and support it.**

---

# 14. Foreign Keys and Relationships

Suppose:

```text
customers
    │
    │ 1:N
    ▼
orders
```

A foreign key expresses the relationship.

```sql
CREATE TABLE orders (
    id bigint PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(id)
);
```

PostgreSQL documents a foreign key as a referential-integrity constraint requiring values in the referencing column(s) to match appropriate values in the referenced table. citeturn313630view1

This is more powerful than saying:

> "`customer_id` is an integer that happens to contain another ID."

It says:

> **An order's customer reference must correspond to a valid customer according to the database's integrity rules.**

---

# 15. Relationships Are Constraints, Not Just Joins

A common shallow mental model is:

> Foreign key = something I use for JOIN.

That is incomplete.

The more important role is integrity.

Without a foreign key, an application could accidentally create:

```text
orders.customer_id = 999999
```

when customer `999999` does not exist.

A JOIN might then simply return no matching customer.

The database would have accepted an invalid state.

With a foreign key, PostgreSQL rejects the invalid relationship according to the constraint rules. citeturn313630view1

### Expert principle

> **Relationships are part of the data model, not merely query syntax.**

---

# 16. Constraints Encode Invariants

A database is valuable partly because it can reject invalid states.

PostgreSQL supports constraints including:

- `CHECK`
- `NOT NULL`
- `UNIQUE`
- `PRIMARY KEY`
- `FOREIGN KEY`
- exclusion constraints

The PostgreSQL documentation describes constraints as mechanisms for limiting valid data and raising errors when attempted modifications violate those rules. citeturn313630view1

Example:

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    name text NOT NULL,
    price numeric NOT NULL CHECK (price > 0)
);
```

The application can validate price too.

But the database constraint provides a stronger boundary:

```text
Application validation
        AND
Database integrity
```

not:

```text
Application validation
instead of
Database integrity
```

---

# 17. A Critical Correction: Data Type ≠ Full Business Validity

Suppose:

```sql
price numeric
```

This tells PostgreSQL that the value is numeric.

It does not automatically mean:

```text
price > 0
```

For that:

```sql
CHECK (price > 0)
```

is appropriate when the invariant belongs at that level.

PostgreSQL's documentation uses positive product pricing as a canonical example of where a data type alone is too coarse and a `CHECK` constraint expresses the additional invariant. citeturn313630view1

This generalizes:

```text
Type
↓
Basic value domain

Constraint
↓
Additional invariant

Relationship constraint
↓
Cross-table integrity
```

---

# 18. NULL Is Not "Empty"

This mental model must be established early because NULL affects relational reasoning everywhere.

Do not think:

```text
NULL = empty string
NULL = zero
NULL = false
NULL = missing object
```

A NULL value represents the absence of a known value or a value not present under the column's semantics.

It introduces three-valued logic:

```text
TRUE
FALSE
UNKNOWN
```

For example:

```sql
WHERE email = 'x@example.com'
```

does not match rows where `email IS NULL`.

And:

```sql
WHERE email <> 'x@example.com'
```

does not mean "all rows except this email" when NULLs exist.

NULL behavior becomes critical in:

- joins
- uniqueness
- constraints
- filtering
- aggregates
- anti-joins
- boolean expressions
- application serialization

We will revisit NULL extensively in Phase 01.

---

# 19. Functional Dependencies

A functional dependency expresses that one set of attributes determines another.

Conceptually:

```text
customer_id → customer_name
```

means:

> Once customer_id is known, customer_name is determined within the modeled data.

This matters because functional dependencies help explain:

- normalization
- redundancy
- candidate keys
- update anomalies
- schema design

Example of suspicious duplication:

```text
orders
------------------------------------------------
order_id | customer_id | customer_name | amount
```

If `customer_id` determines `customer_name`, repeating the name in every order introduces redundancy.

That may or may not be intentionally useful, but the trade-off should be explicit.

---

# 20. Normalization Is About Dependencies and Anomalies

Do not reduce normalization to memorized definitions:

```text
1NF
2NF
3NF
BCNF
```

The deeper reason is to control redundancy and preserve coherent dependencies.

Poorly modeled duplication creates anomalies such as:

```text
Update anomaly
Insert anomaly
Delete anomaly
```

Example:

```text
order_id | customer_id | customer_email
```

If customer email changes, many order rows may need updating.

That is a modeling question before it is a query-performance question.

---

# 21. Set Semantics vs Application Collections

This distinction is extremely important.

Application developers often think in terms of:

```text
Array<User>
Map<ProductId, Product>
Set<Order>
```

SQL instead describes relations and operations over sets/multisets.

This affects how you think about:

```sql
JOIN
GROUP BY
UNION
INTERSECT
EXCEPT
EXISTS
NOT EXISTS
```

The question becomes:

> What relation does this expression produce?

rather than:

> Which loop should I write?

---

# 22. A Relational Query Is a Transformation

Consider:

```sql
SELECT c.id, c.name
FROM customers c
WHERE c.status = 'active';
```

Mentally model this as:

```text
Customers
   │
   │ selection: status = 'active'
   ▼
Active Customers
   │
   │ projection: id, name
   ▼
Result Relation
```

This way of thinking becomes extremely useful when queries become complex.

---

# 23. Projection

Projection means choosing attributes from a relation.

SQL example:

```sql
SELECT id, name
FROM customers;
```

The logical operation is roughly:

```text
Customers(id, name, email, status)
            ↓
Customers(id, name)
```

This is more than vocabulary.

It helps you understand why a query does not have to retrieve every attribute from the underlying relation.

---

# 24. Selection

Selection means choosing tuples satisfying a predicate.

SQL:

```sql
SELECT *
FROM customers
WHERE status = 'active';
```

Conceptually:

```text
Customers
   ↓
Predicate(status = active)
   ↓
Matching tuples
```

Later, the planner can choose how to physically produce those tuples.

---

# 25. Join as Relationship Composition

Consider:

```sql
SELECT
    o.id,
    c.name
FROM orders o
JOIN customers c
    ON c.id = o.customer_id;
```

Do not think merely:

> The database loops through two tables.

Think:

> Combine rows whose relationship predicate is satisfied.

Later PostgreSQL might execute that logical request through:

```text
Nested Loop
Hash Join
Merge Join
```

The logical join remains the same while the physical strategy changes.

This is one of the most important foundations for understanding the optimizer.

---

# 26. Logical Equality vs Physical Equality

Two representations can be logically equivalent while having different physical consequences.

For example:

```sql
WHERE id = 10
```

may be executed using an index.

Another logically equivalent query under some conditions may be transformed by the planner into a different physical strategy.

Therefore always distinguish:

```text
Logical query meaning
vs
Physical execution plan
```

Phase 06 will make this distinction central.

---

# 27. The Database Is a State Machine

A useful expert mental model is:

```text
Database State N
      │
      │ Transaction / mutation
      ▼
Database State N+1
```

But the transition must obey invariants.

Example:

```text
State:
Inventory(product=A) = 5

Transaction:
Reserve 2 units

New state:
Inventory available = 3
```

If two concurrent requests reserve the same inventory incorrectly, the problem is not simply "a coding bug."

It is a violation of state-transition correctness.

This leads directly into:

```text
transactions
MVCC
locks
isolation
concurrency
```

---

# 28. The Database Is Not Just a Persistence Layer

A common backend abstraction is:

```text
Node.js
   ↓
Service
   ↓
Repository
   ↓
Database
```

and the database is treated as passive storage.

That is an incomplete model.

PostgreSQL actively provides:

- integrity constraints
- transaction semantics
- concurrency control
- query planning
- durability
- recovery
- indexing
- security boundaries
- relational operations

Therefore database design is part of **system design**.

---

# 29. Application Validation vs Database Integrity

Consider:

```ts
if (price <= 0) {
  throw new Error('Invalid price');
}
```

This is useful.

But another application, migration, script, admin tool, ETL process, or future code path may write directly to the database.

A database-level invariant:

```sql
CHECK (price > 0)
```

creates a stronger boundary for the data regardless of which application path attempts the mutation.

PostgreSQL evaluates constraints as part of data modification and raises an error when the constraint is violated. citeturn313630view1

### Expert principle

> **Business-critical invariants should have the strongest practical enforcement boundary.**

This does not mean every business rule belongs in SQL. It means the enforcement boundary must be intentional.

---

# 30. What Belongs in the Database?

A useful classification is:

## Strong Database Candidates

Rules such as:

```text
id must exist
email must be unique
price must be positive
order.customer_id must reference a customer
quantity must not be negative
```

are often naturally expressed through constraints.

## Application-Oriented Logic

Rules involving complex external workflows may belong primarily in application/service layers.

Example:

```text
Call external payment provider
Wait for provider response
Send notification
Update CRM
```

These are not simply relational integrity constraints.

## Shared Invariants

Some rules require coordinated design between application and database.

Example:

```text
Order cannot be shipped before payment is confirmed.
```

The exact enforcement strategy depends on the state model, transaction boundaries, and architecture.

The goal is not "database does everything".

The goal is **explicit ownership of correctness**.

# 31. Common Developer Mistakes

## Mistake 1 — Treating Tables as Objects

```text
One class = one table
```

This can be useful in some systems but is not a universal modeling principle.

## Mistake 2 — Treating IDs as Mere Numbers

A key is an identity/integrity mechanism, not just an integer field.

## Mistake 3 — No Constraints Because "The API Validates It"

This creates weak integrity boundaries.

## Mistake 4 — Assuming Query Order

```sql
SELECT * FROM orders;
```

does not promise insertion order. citeturn313630view0

## Mistake 5 — Thinking Foreign Keys Exist Only for JOINs

They also enforce referential integrity. citeturn313630view1

## Mistake 6 — Using NULL as a Generic Missing Value

NULL has semantic and logical consequences.

## Mistake 7 — Designing Tables Before Understanding Relationships

This produces schemas that reflect screens rather than domain facts.

## Mistake 8 — Storing Everything as Text

This discards useful type semantics.

PostgreSQL data types constrain valid values and give stored values appropriate semantics. citeturn313630view0

## Mistake 9 — Assuming the ORM Schema Is the Domain Model

An ORM schema is an implementation representation, not automatically a correct business model.

## Mistake 10 — Assuming "Normalized" Means "Finished"

Normalization solves some forms of redundancy and dependency problems, but performance, workload, and operational requirements may lead to deliberate denormalization later.

# 32. Vibe-Coding / AI-Generated Mistakes

AI-generated database code frequently looks convincing because the syntax is correct while the model is wrong.

Watch for:

### 32.1 Screen-Driven Schema Design

```text
Create columns for every field visible in the UI.
```

Problem:

The UI is not necessarily the domain model.

### 32.2 No Constraints

AI-generated CRUD examples often omit:

- foreign keys
- unique constraints
- check constraints
- not-null requirements

because the example focuses on API functionality.

### 32.3 One Giant Table

Everything gets placed into one table to avoid joins.

This usually destroys meaningful relationships and creates update anomalies.

### 32.4 JSONB Everywhere

"Flexible" data is put into JSONB without identifying stable relational attributes.

### 32.5 ID Everywhere Without Semantics

Every table gets `id`, but there is no thought given to:

- candidate keys
- natural uniqueness
- tenant scope
- business identifiers

### 32.6 Application-Only Integrity

The AI says:

> "Validation is already handled in the service."

That does not automatically make the database safe.

### 32.7 ORM-First Modeling

The developer starts with ORM syntax instead of first understanding the domain and invariants.

### 32.8 Accidental Ordering

An AI-generated endpoint returns a list without `ORDER BY`, then the frontend silently assumes a stable order.

### 32.9 Foreign Keys Added Without Delete Semantics

The schema has relationships but no deliberate decision about what should happen when referenced rows change or are deleted.

### 32.10 Copy-Paste Normalization

AI can mechanically apply normalization rules without understanding the actual business dependencies.

### Expert AI-audit question

> **Does this schema encode the domain, or does it merely encode the code that happens to exist today?**

# 33. Production Scenario 1 — Duplicate Email

## Problem

Two users register with:

```text
email = prasanta@example.com
```

The application checks first:

```sql
SELECT 1
FROM users
WHERE email = $1;
```

If none exists, it inserts.

### Naive Reasoning

> "We checked first, so duplicates are impossible."

### Expert Reasoning

Two concurrent transactions can both observe no matching row before either commits the insert.

The race exists between check and write.

A database-level uniqueness guarantee addresses the invariant:

```sql
UNIQUE (email)
```

PostgreSQL unique constraints enforce uniqueness and create a supporting unique B-tree index. citeturn313630view1

The key lesson for this chapter is:

> **A relational invariant should not depend on a race-prone application pre-check when the database can enforce it directly.**

Concurrency details will be studied deeply in Phase 04.

---

# 34. Production Scenario 2 — Orphaned Orders

Suppose an API can create:

```text
orders.customer_id = 100
```

but customer 100 does not exist.

The UI might show:

```text
Unknown customer
```

The application may eventually fail in another workflow.

A foreign key turns the invalid state into a write-time integrity violation rather than allowing the database to persist an orphaned relationship. citeturn313630view1

---

# 35. Production Scenario 3 — "The Results Keep Coming Back in the Same Order"

A developer observes:

```sql
SELECT id, name
FROM users;
```

returns the same ordering every time.

They build cursor logic around it.

Later, a planner or storage change produces a different order.

The developer claims:

> "PostgreSQL changed its behavior."

The real issue is that the application depended on an ordering guarantee it never requested.

PostgreSQL explicitly states that table row order is unspecified unless ordering is requested. citeturn313630view0

---

# 36. Production Scenario 4 — One Database Column for Multiple Concepts

Suppose:

```text
status = "paid-delivered-notified"
```

This is a modeling smell.

Multiple independent concepts have been compressed into one string.

A stronger domain model might separate:

```text
payment_status
fulfillment_status
notification_status
```

The exact design depends on domain requirements, but the principle is:

> **Model independent business concepts independently unless there is a deliberate reason to couple them.**

# 37. Trade-Off: Natural Key vs Surrogate Key

Suppose an employee has:

```text
employee_number = "EMP-2026-00142"
```

Should that become the primary key?

There is no universal answer.

## Natural Key Advantages

- meaningful
- directly represents a business identifier
- may already be unique

## Natural Key Risks

- business meaning may change
- wider indexes
- compound natural keys can propagate through foreign keys
- external identifiers may not be immutable

## Surrogate Key Advantages

- stable technical identity
- usually compact
- decouples physical identity from business meaning

## Surrogate Key Risks

- does not automatically enforce business uniqueness
- developers may wrongly assume it represents a business identity

A mature schema may use both:

```sql
id bigint PRIMARY KEY,
employee_number text NOT NULL UNIQUE
```

This separates:

```text
technical identity
vs
business identity
```

---

# 38. Trade-Off: Normalize vs Denormalize

Do not treat these as competing religions.

Ask:

```text
What data dependency exists?
What duplication is introduced?
What queries dominate?
What consistency guarantees are required?
What is the write cost?
What is the read cost?
How large is the data?
How frequently does it change?
```

Default relational modeling should be principled.

Denormalization should be deliberate and measurable.

Do not prematurely optimize based on imagined future query performance.

---

# 39. Trade-Off: Strict Constraints vs Workflow Flexibility

A constraint should encode an invariant that must actually hold.

Overly strict schema rules can make legitimate workflows difficult.

Under-constrained schemas can permit invalid states.

The expert task is to identify:

```text
Invariant
↓
Ownership
↓
Enforcement boundary
↓
Failure behavior
```

This is architecture, not simply SQL syntax.

---

# 40. Relational Model and Microservices

A common misconception is:

> "If we use microservices, relationships stop mattering."

They do not.

Relationships still exist in business reality.

The question becomes whether a relationship should be enforced:

- synchronously in one database
- through service APIs
- through events
- through local read models
- through reconciliation

Distributed architecture does not remove data modeling problems. It changes the location and strength of some guarantees.

We will examine this in Phase 17.

# 41. Relational Thinking and JSONB

JSONB is powerful, but "schema flexibility" is not automatically superior.

Consider:

```json
{
  "customerId": 12,
  "status": "active",
  "creditLimit": 50000
}
```

If these fields are stable, heavily queried, constrained, and meaningful to the relational model, ordinary columns may be more appropriate.

JSONB becomes more compelling when:

- the structure is genuinely variable
- the variability is part of the domain
- relational constraints are not the primary requirement
- query patterns support the choice

The correct question is not:

> "Can PostgreSQL store this as JSONB?"

It is:

> **"Which representation best preserves domain meaning and operational requirements?"**

# 47. Trick Questions

### Trick 1

> "Every table must have a primary key because PostgreSQL rejects tables without one."

False.

PostgreSQL does not require every table to declare a primary key, although a primary key is usually desirable where the relation has a natural row identity. citeturn313630view1

### Trick 2

> "A foreign key automatically creates an index on the referencing column."

Do not assume this.

PostgreSQL does not automatically create an index on the referencing side merely because the foreign key exists; indexing that side can still be important depending on workload and referential actions. citeturn563068search2

### Trick 3

> "UNIQUE means there can only be one NULL."

Not under PostgreSQL's default unique semantics. By default, NULLs are not treated as equal for a unique constraint; PostgreSQL also supports `NULLS NOT DISTINCT` when that behavior is desired. citeturn313630view1

### Trick 4

> "A table is like an ordered array of rows."

False.

SQL does not guarantee row ordering without explicit ordering. citeturn313630view0

### Trick 5

> "The primary key is an index."

Incomplete.

The primary key is a logical constraint; PostgreSQL creates a supporting unique B-tree index. citeturn313630view1

# 48. Production Review Checklist

When reviewing a relational schema, ask:

## Domain

- Does every table represent a coherent concept?
- Are unrelated concepts incorrectly combined?

## Identity

- What identifies each relation's tuples?
- Are candidate keys understood?
- Are business identifiers protected?

## Relationships

- Are relationships explicit?
- Are cardinalities correct?
- Are foreign keys appropriate?

## Integrity

- Which fields are required?
- Which values must be unique?
- Which numeric/state constraints exist?
- Which invariants are enforced by the database?

## Semantics

- Is NULL being used intentionally?
- Are columns typed correctly?
- Are independent concepts represented separately?

## Evolution

- What happens when the domain changes?
- Which attributes are stable?
- Which fields are temporary application concerns?

## Scale

- Will this model still make sense at large volume?
- Are repeated values intentional?
- Is denormalization justified by workload evidence?

## Concurrency

- Which invariants can race?
- Which guarantees require database enforcement?

## Security

- Which tenant owns each record?
- Can cross-tenant references occur?

# 49. Expert-Level Insights

## Insight 1 — Data Modeling Is Constraint Modeling

The real goal is not to draw boxes and arrows.

It is to define:

```text
What states are valid?
What states are invalid?
What relationships must exist?
What values must be unique?
```

## Insight 2 — Database Design Is Part of Business Logic

Not all business logic belongs in SQL, but durable business invariants necessarily affect database design.

## Insight 3 — A Schema Is an API for Data

Applications depend on database semantics just as clients depend on API contracts.

Schema changes therefore require compatibility thinking.

## Insight 4 — Constraints Are Executable Documentation

A declared constraint communicates:

> This condition is part of the data contract.

## Insight 5 — Logical and Physical Models Must Be Separated

The logical schema describes meaning.

PostgreSQL's physical implementation determines how that meaning is stored and executed.

## Insight 6 — Good Database Engineers Think in Invariants

Instead of asking only:

> What query should I write?

ask:

> What must always be true?

That question leads to better schemas, safer transactions, and more reliable systems.
