# 01.21 — Advanced SQL Quality

> **Phase 01 — Advanced SQL**  
> **Focus:** correctness, readability, determinism, safety, maintainability, planner-awareness, and production-grade SQL discipline.

---

## 1. Chapter Objective

Advanced SQL quality is the discipline of writing SQL that is not merely *valid*, but demonstrably correct, explainable, maintainable, observable, secure, and appropriately efficient for the workload.

A query can execute successfully and still be wrong. It can return the right answer today and become nondeterministic tomorrow. It can be fast on 10,000 rows and collapse at 100 million. It can be safe under one `search_path` and become dangerous inside a privilege boundary. It can look elegant while hiding a many-to-many row explosion.

This chapter establishes the engineering standard for SQL used in production PostgreSQL systems.

### By the end of this chapter, you should be able to

- distinguish syntactic validity from semantic correctness;
- reason about query grain before writing joins or aggregates;
- make result ordering deterministic when the contract requires it;
- control null behavior intentionally;
- eliminate accidental duplicate rows;
- identify row multiplication and cardinality errors;
- choose explicit column projections instead of fragile `SELECT *` contracts;
- write SQL that is safe under parameterization and changing inputs;
- understand when query structure helps or hurts the planner;
- use `EXPLAIN` and `EXPLAIN (ANALYZE, BUFFERS)` as evidence rather than decoration;
- reason about volatile, stable, and immutable functions;
- understand security implications of `search_path`, functions, views, and user-controlled SQL fragments;
- design predictable pagination;
- keep application code from becoming a hidden second query engine;
- review AI-generated SQL critically rather than trusting plausible syntax;
- build a repeatable SQL review, testing, and performance-debugging workflow.

---

# 2. Three Levels of Definition

## 2.1 Simple definition

**SQL quality means the query reliably returns the intended result, safely and predictably, without creating avoidable operational problems.**

## 2.2 Engineering definition

SQL quality is the intersection of:

```text
Correctness
+ Determinism
+ Maintainability
+ Security
+ Observability
+ Performance suitability
+ Operational safety
```

## 2.3 Expert definition

A production SQL statement is a contract between the application, PostgreSQL's semantic model, the optimizer, the storage engine, and the data model. SQL quality therefore means that the statement's semantics, cardinality, evaluation assumptions, dependency surface, and operational characteristics are explicit enough to survive data growth, concurrency, schema evolution, planner changes, and adversarial input.

---

# 3. First Principle: “Runs” Is Not a Correctness Test

A query returning rows proves only that PostgreSQL accepted the statement and produced a result according to PostgreSQL's rules.

It does **not** prove that:

- the rows represent the intended entities;
- duplicates are legitimate;
- missing rows are handled correctly;
- nulls represent the intended business state;
- ordering is deterministic;
- pagination is stable;
- totals are computed at the correct grain;
- tenant boundaries are preserved;
- access control predicates are complete;
- a function was evaluated at the intended frequency;
- the query remains efficient under realistic cardinality.

The first question during SQL review should therefore be:

> **What exactly is one output row supposed to represent?**

That question prevents a remarkable number of production bugs.

---

# 4. The Query Contract

Before writing SQL, define its contract.

A useful contract contains:

```text
Input
→ Business condition
→ Row grain
→ Cardinality expectation
→ Null semantics
→ Ordering contract
→ Pagination contract
→ Security boundary
→ Mutation behavior, if any
→ Performance expectation
→ Failure behavior
```

Example:

> Return one row per invoice for tenant `T`, containing invoices created during a requested interval, with their current customer name. Include invoices even when a customer record is temporarily unavailable. Sort newest invoice first and make ties deterministic. Return at most 50 rows.

That contract immediately implies several SQL decisions:

- `LEFT JOIN` may be appropriate rather than `INNER JOIN`;
- output grain is **invoice**;
- duplicate customer rows would violate the contract;
- ordering must include a unique tie-breaker;
- tenant filtering must apply consistently;
- pagination must be tied to deterministic ordering.

# 5. Query Grain: The Most Important Hidden Property

## 5.1 What is grain?

The **grain** of a query describes what one result row represents.

Examples:

```text
One row = one customer
One row = one order
One row = one order line
One row = one customer per month
One row = one SKU per warehouse
```

When the intended grain is not explicit, joins and aggregates become dangerous.

## 5.2 Grain mismatch

Suppose:

```text
customers: 1 row per customer
orders:    many rows per customer
payments:  many rows per order
```

A direct join like:

```sql
SELECT c.id,
       SUM(o.total_amount),
       SUM(p.amount)
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN payments p ON p.order_id = o.id
GROUP BY c.id;
```

can overcount payments or order totals when one order has multiple payments.

### Why?

The join does not know that the business totals belong to different grains. It creates a combined row space first.

If an order has 1 row in `orders` and 3 payment rows, that order participates in 3 joined rows.

The database is behaving correctly.

The query's **grain reasoning is wrong**.

## 5.3 Correct approach

Aggregate each one-to-many relationship to the required grain before combining them when necessary:

```sql
WITH order_totals AS (
    SELECT customer_id,
           SUM(total_amount) AS order_total
    FROM orders
    GROUP BY customer_id
),
payment_totals AS (
    SELECT o.customer_id,
           SUM(p.amount) AS payment_total
    FROM payments p
    JOIN orders o ON o.id = p.order_id
    GROUP BY o.customer_id
)
SELECT c.id,
       COALESCE(ot.order_total, 0) AS order_total,
       COALESCE(pt.payment_total, 0) AS payment_total
FROM customers c
LEFT JOIN order_totals ot ON ot.customer_id = c.id
LEFT JOIN payment_totals pt ON pt.customer_id = c.id;
```

The CTEs are not valuable merely because they are “cleaner.” They make the aggregation grain explicit.

# 6. Cardinality Reasoning

For every join, ask:

```text
1 → 1 ?
1 → many ?
many → 1 ?
many → many ?
```

Then ask:

> What does that do to the number of rows?

A rough cardinality model is often enough to detect mistakes before execution.

For example:

```text
10 customers
× 100 orders per customer
× 4 payments per order
≈ 4,000 joined rows
```

A report intended to produce 10 customer rows must eventually collapse that row space correctly.

## Cardinality checklist

For each join:

- identify uniqueness on both sides;
- identify whether the join key is actually unique;
- account for nullable relationships;
- determine whether a filtering predicate changes the relationship;
- test with duplicate-rich fixtures, not only ideal data;
- compare expected row counts with actual row counts.

# 7. Explicit Projection

## 7.1 Why `SELECT *` is fragile

This is convenient:

```sql
SELECT * FROM users;
```

But production SQL often needs a stable interface.

Problems include:

- schema changes silently change result shape;
- unnecessary columns increase transfer and decoding work;
- joins can introduce duplicate or ambiguous columns;
- APIs may accidentally expose newly added sensitive fields;
- generated code can become coupled to the physical table definition.

Prefer:

```sql
SELECT
    u.id,
    u.email,
    u.created_at
FROM users AS u;
```

## 7.2 `SELECT *` is especially risky at security boundaries

A new column such as:

```text
password_hash
internal_notes
risk_score
private_metadata
```

could become visible to code that was written years earlier and never changed.

Explicit projection turns schema evolution into a visible review event.

---

# 8. Alias Discipline

Use aliases to make ownership of columns explicit:

```sql
SELECT
    o.id AS order_id,
    c.id AS customer_id,
    c.name AS customer_name
FROM orders AS o
JOIN customers AS c
  ON c.id = o.customer_id;
```

Avoid ambiguous shorthand such as:

```sql
SELECT id, name
FROM orders
JOIN customers ...;
```

Explicit aliases reduce maintenance risk, especially as queries grow.

---

# 9. Determinism

## 9.1 The hidden trap

This query:

```sql
SELECT id, name
FROM users
LIMIT 20;
```

does **not** express which 20 rows should be returned.

Likewise:

```sql
ORDER BY created_at DESC
LIMIT 20;
```

is only partially deterministic when many rows share the same `created_at`.

## 9.2 Stable ordering

Use a unique tie-breaker:

```sql
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Now the ordering contract is much stronger.

## 9.3 Why this matters for pagination

Suppose page 1 and page 2 are computed using an ordering that is not unique. Rows with equal sort values can move between pages as the planner, data visibility, or concurrent writes change.

For stable page boundaries, use a deterministic ordering key.

---

# 10. Pagination Quality

## 10.1 Offset pagination

```sql
SELECT id, created_at, name
FROM customers
ORDER BY created_at DESC, id DESC
LIMIT 50 OFFSET 50000;
```

Advantages:

- simple;
- easy to understand;
- naturally maps to page numbers.

Costs can grow as the offset grows because PostgreSQL still needs to identify and skip preceding rows.

## 10.2 Keyset pagination

Instead of saying “skip 50,000 rows,” say “continue after this known position.”

```sql
SELECT id, created_at, name
FROM customers
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

This is generally the stronger design for large sequential result sets when the application does not require arbitrary page jumps.

### Keyset principle

```text
Cursor = last deterministic ordering key
Next page = rows strictly after/before cursor
```

The exact comparison depends on sort direction.

## 10.3 Cursor design

A production cursor should encode enough information to reconstruct the boundary.

For:

```sql
ORDER BY created_at DESC, id DESC
```

both values belong in the cursor.

Using only `created_at` is unsafe when timestamps collide.

# 11. Null Discipline

SQL uses three-valued logic. Quality SQL makes this explicit.

Do not casually treat:

```text
NULL
0
''
false
'unknown'
```

as interchangeable states.

Examples:

```sql
WHERE deleted_at = NULL
```

is incorrect for testing SQL null.

Use:

```sql
WHERE deleted_at IS NULL
```

or:

```sql
WHERE deleted_at IS NOT NULL
```

## `COALESCE` is not a universal null fix

This may be valid:

```sql
COALESCE(balance, 0)
```

but the correct default is business-specific.

For a nullable tax rate, converting `NULL` to `0` may change the meaning from “not configured” to “explicitly zero.”

Ask first:

> Does NULL mean “unknown,” “not applicable,” “not supplied,” or “zero”?

---

# 12. Boolean Logic and Parentheses

Never rely on readers remembering operator precedence in complicated business predicates.

Prefer:

```sql
WHERE tenant_id = $1
  AND (
       status = 'pending'
       OR status = 'awaiting_payment'
  )
```

over a compressed expression whose intended grouping is not obvious.

Readable boolean structure is part of correctness.

---

# 13. Predicate Placement: `ON` vs `WHERE`

These are not always equivalent.

```sql
SELECT ...
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.status = 'paid';
```

means “keep all customers, attach paid orders when present.”

Compare:

```sql
SELECT ...
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
WHERE o.status = 'paid';
```

The `WHERE` condition removes rows where `o.status` is null, effectively changing the outer join behavior.

## Rule

Ask:

> Is this predicate part of the relationship being joined, or is it a filter on the final result?

The answer determines where it belongs.

---

# 14. `EXISTS` vs Join for Existence Tests

Suppose the goal is:

> Return customers who have at least one paid order.

A common query is:

```sql
SELECT DISTINCT c.id
FROM customers c
JOIN orders o
  ON o.customer_id = c.id
WHERE o.status = 'paid';
```

This can work, but it creates joined rows and then removes duplicates.

When the intent is purely existential, use:

```sql
SELECT c.id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
      AND o.status = 'paid'
);
```

The two statements express different logical ideas:

```text
JOIN
= combine row sets

EXISTS
= prove existence
```

Choose the construct that communicates the actual requirement.

---

# 15. `IN`, `EXISTS`, and `NOT EXISTS`

Quality SQL considers semantics, not folklore.

## `IN`

```sql
WHERE customer_id IN (...)
```

can be appropriate when testing membership in a value set.

## `EXISTS`

Best when the condition is naturally relational/existential:

```sql
WHERE EXISTS (...)
```

## `NOT EXISTS`

Often the clearest anti-join pattern:

```sql
SELECT c.id
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

This means:

> customer has no matching order.

Be especially careful with `NOT IN` and nulls. A null appearing in the compared set can make the result follow SQL's three-valued logic in ways developers do not expect.

---

# 16. `DISTINCT` Is Not a Duplicate-Row Repair Strategy

This pattern is suspicious:

```sql
SELECT DISTINCT ...
FROM ...many joins...
```

`DISTINCT` may be exactly right, but it should not automatically conceal an unexplained row explosion.

### Naive Approach

```sql
SELECT DISTINCT c.id, c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN tags t ON t.customer_id = c.id;
```

### Why It Fails

The join may produce a large number of rows per customer before `DISTINCT` collapses them.

The query may appear correct while doing substantially more work than necessary.

### Improved Approach

If the requirement is existence:

```sql
SELECT c.id, c.name
FROM customers c
WHERE EXISTS (...)
  AND EXISTS (...);
```

### Why It Works

The query expresses the actual business predicate without materializing unnecessary combinations.

---

# 17. Avoid Accidental Cross Joins

A missing join predicate can produce a Cartesian product:

```sql
SELECT *
FROM customers c
JOIN orders o;
```

Even when a cross join is intentional, make it explicit:

```sql
FROM customers AS c
CROSS JOIN reporting_dates AS d
```

This makes the unusual cardinality visible in review.

---

# 18. Common Table Expressions: Quality over Fashion

CTEs can improve structure, but “CTE = optimization” is not a universal rule.

Use a CTE when it helps:

- name an intermediate concept;
- separate logical stages;
- reuse a sub-result;
- create a recursive structure;
- make a complex query reviewable.

Do not create five CTEs for a trivial query merely because the result looks more “senior.”

The real question is:

> Does this structure make the intended relational operations clearer without introducing unnecessary execution consequences?

Inspect the actual plan when performance matters.

---

# 19. Subqueries vs Joins: Prefer Semantics Over Style Wars

There is no universal rule:

```text
“Always use joins.”
“Never use subqueries.”
“CTEs are faster.”
“EXISTS is always faster.”
```

These are cargo-cult statements.

A quality review asks:

1. What does the query mean?
2. What is the expected cardinality?
3. What does the planner choose?
4. How large is the data?
5. Which indexes exist?
6. Are duplicates possible?
7. Is the query part of a security boundary?
8. What happens under realistic selectivity?

Then measure.

---

# 20. Sargability and Expression Design

A predicate is often easier for an index to support when the indexed column is compared in a form compatible with the index.

For example, with an index on:

```sql
created_at
```

prefer a range predicate such as:

```sql
WHERE created_at >= $1
  AND created_at <  $2
```

over wrapping the indexed column in a function such as:

```sql
WHERE date(created_at) = $1
```

unless an appropriate expression index is intentionally designed.

The principle is broader than one syntax trick:

> **Do not accidentally transform a searchable predicate into a form for which your intended index cannot be used effectively.**

---

# 21. Functions and Planner Semantics

PostgreSQL functions have volatility categories that communicate how their results behave.

```text
IMMUTABLE
STABLE
VOLATILE
```

Conceptually:

### IMMUTABLE

Same input means same result forever, independent of database state.

Appropriate for deterministic calculations.

### STABLE

Result is stable within a single statement but can depend on database state.

### VOLATILE

May change during execution and can include side effects.

PostgreSQL uses these declarations when determining what optimizations are safe. A function with side effects must be treated as volatile so calls cannot be incorrectly optimized away. citeturn871731search0

## Quality rule

Never label a function `IMMUTABLE` merely because it “usually returns the same thing.”

An incorrect volatility declaration is a semantic lie to the optimizer.

---

# 22. Function Cost and Row Estimates

For user-defined functions, metadata such as estimated execution cost and result row count can influence planning.

These parameters are not performance decorations.

They are part of the contract between your function and PostgreSQL's planner.

Changing them without evidence can make planning worse.

Measure first.

---

# 23. Search Path Discipline

PostgreSQL resolves unqualified names according to `search_path`. The current PostgreSQL 18 documentation describes it as the order of schemas searched for unqualified tables, types, functions, operators, and related objects. citeturn871731search12

That has both maintainability and security implications.

Instead of assuming:

```sql
SELECT * FROM orders;
```

is permanently bound to one relation, understand the active schema resolution environment.

For privileged `SECURITY DEFINER` functions, this becomes especially important. PostgreSQL documents that unsafe search paths can allow an attacker to create objects that mask objects the privileged function intended to use. The documented defense is to constrain `search_path` to trusted schemas and place `pg_temp` last when it is needed. citeturn871731search0turn871731search1

# 24. SQL Injection: The Query Structure Must Be Separated from Values

## Unsafe

```ts
const sql = `
  SELECT id, email
  FROM users
  WHERE email = '${email}'
`;
```

The application has merged data into SQL source text.

## Safer

```ts
await pool.query(
  `SELECT id, email
   FROM users
   WHERE email = $1`,
  [email]
);
```

The value is treated as a parameter rather than SQL syntax.

## But parameters do not solve every dynamic SQL problem

You often cannot parameterize SQL identifiers or arbitrary syntax fragments in the same way as values.

For example, a dynamic sort column requires controlled identifier selection:

```ts
const allowedSorts = {
  newest: 'created_at',
  name: 'name',
  id: 'id',
} as const;

const sortColumn = allowedSorts[inputSort as keyof typeof allowedSorts];

if (!sortColumn) {
  throw new Error('Unsupported sort field');
}
```

Do not pass raw user input into SQL syntax positions merely because value parameters are being used elsewhere.

---

# 25. Dynamic SQL and Allow-Lists

Dynamic SQL usually has two different categories:

```text
Dynamic values
→ parameterize

Dynamic SQL structure
→ constrain / allow-list / safely construct
```

Typical structural inputs:

- sort column;
- sort direction;
- optional filter clause;
- table selection in administrative tooling;
- schema selection;
- report grouping dimension.

An enum-like mapping is safer than concatenating raw text.

---

# 26. Security Barrier Thinking

SQL quality also includes understanding where predicates may legally and safely move.

PostgreSQL documents `security_barrier` views as a mechanism that prevents user-supplied predicates involving non-leakproof functions from being pushed below the security boundary in ways that could reveal information. PostgreSQL also notes that this protection can restrict otherwise-fast plans and therefore has a performance trade-off. citeturn871731search8

The larger lesson is:

> Security constraints can deliberately limit planner freedom.

Never optimize away a security boundary because a normal view happens to run faster.

---

# 27. Row-Level Security and SQL Quality

When Row-Level Security (RLS) is used, query correctness must include authorization correctness.

A query can return the expected data in a privileged development session while behaving differently under the application role.

Test with the real role model.

For multi-tenant systems, treat tenant isolation as part of query semantics, not merely an application convention.

Bad:

```sql
SELECT * FROM orders;
```

and assuming the application “will always filter tenant_id.”

Stronger designs combine:

```text
schema/data model constraints
+ RLS where appropriate
+ application authorization
+ explicit tenant semantics
+ tests under actual roles
```

---

# 28. Prefer Constraints Over Repeated Defensive SQL

If the business rule is structural, enforce it structurally.

Examples:

```sql
CHECK (quantity > 0)
UNIQUE (tenant_id, external_code)
FOREIGN KEY (customer_id) REFERENCES customers(id)
```

Do not rely on every application query to remember a rule that the database can enforce.

Quality SQL is partly about what the query **does not have to defend against** because the schema already guarantees it.

---

# 29. Type Discipline

Do not casually cast everything to text:

```sql
WHERE id::text = $1
```

when the application can provide the correct type.

Type-aware predicates often communicate intent more clearly and avoid unnecessary transformations.

Use explicit casts when they are semantically meaningful:

```sql
$1::uuid
$2::timestamptz
$3::numeric(12,2)
```

but do not spray casts throughout a query without understanding their planner and type-resolution implications.

---

# 30. Date and Time Quality

Temporal SQL deserves especially strict review.

Prefer half-open intervals for many time-window queries:

```sql
WHERE occurred_at >= $1
  AND occurred_at <  $2
```

This avoids many boundary problems such as double-counting adjacent windows.

For example:

```text
[2026-01-01, 2026-02-01)
[2026-02-01, 2026-03-01)
```

share no instant and leave no gap at the boundary.

For cross-time-zone systems, be explicit about whether a timestamp represents:

```text
an absolute instant
or
an intentionally local civil time
```

Do not solve timezone ambiguity by blindly converting everything to text.

---

# 31. Aggregation Quality

Before writing:

```sql
SUM(...)
COUNT(...)
AVG(...)
```

write down:

```text
What is one group?
What rows belong to each group?
Can joins multiply rows?
What should empty groups mean?
```

## `COUNT(*)` vs `COUNT(column)`

These are different:

```sql
COUNT(*)
```

counts rows.

```sql
COUNT(column)
```

counts non-null values of that column.

An apparently small distinction can materially change report totals.

---

# 32. Empty Aggregates and Default Semantics

Consider:

```sql
SELECT SUM(amount)
FROM orders
WHERE customer_id = $1;
```

If no input rows satisfy the condition, the result is not automatically the numeric zero.

If the business meaning is “zero when no rows exist,” encode that intentionally:

```sql
SELECT COALESCE(SUM(amount), 0)
FROM orders
WHERE customer_id = $1;
```

This is a quality decision, not a formatting trick.

---

# 33. Window Functions: Specify the Frame Intentionally

A window definition is not merely:

```sql
OVER (ORDER BY created_at)
```

You should understand what peer rows and frame semantics mean for the function being used.

For cumulative metrics, make the intended order and frame semantics explicit when correctness depends on them.

Do not assume that a window function automatically means “running total of exactly the previous rows I can see in my head.”

---

# 34. `ORDER BY` in Aggregated and Windowed Queries

Ordering in one SQL level does not magically define ordering at another logical level.

A subquery's ordering should not be treated as a durable application-level contract unless the outer query establishes the required final ordering.

At the API boundary, sort the final relation being returned.

---

# 35. Avoid Hidden Dependence on Physical Row Order

Never rely on:

```text
heap insertion order
index traversal order without ORDER BY
current execution plan shape
```

as a business ordering contract.

Physical access behavior is an implementation detail.

If order matters, write `ORDER BY`.

---

# 36. Query Comments: Useful, But Explain Why

A comment like:

```sql
-- get users
```

adds almost no value.

A good comment explains a non-obvious constraint:

```sql
-- Half-open range avoids double-counting events exactly at the next interval boundary.
WHERE occurred_at >= $1
  AND occurred_at <  $2
```

or:

```sql
-- This EXISTS is intentional: we only need membership, not child-row materialization.
WHERE EXISTS (...)
```

Comments should explain **why the unusual structure exists**, not restate the syntax.

---

# 37. Readability Is an Operational Feature

Readable SQL is easier to:

- review;
- debug;
- explain during incidents;
- compare during migrations;
- modify safely;
- hand over between engineers;
- validate against business requirements.

Prefer:

```sql
SELECT
    o.id,
    o.total_amount,
    c.name AS customer_name
FROM orders AS o
JOIN customers AS c
  ON c.id = o.customer_id
WHERE o.tenant_id = $1
  AND o.status = 'paid'
  AND o.created_at >= $2
  AND o.created_at < $3
ORDER BY o.created_at DESC, o.id DESC;
```

over compressed one-line SQL that saves visual space but increases cognitive load.

---

# 38. Query Structure Should Match Business Concepts

A useful heuristic:

```text
SELECT
→ What is returned?

FROM / JOIN
→ What entities participate?

WHERE
→ Which rows qualify?

GROUP BY
→ What is the reporting grain?

HAVING
→ Which groups qualify?

WINDOW
→ What analytic context is needed?

ORDER BY
→ What deterministic presentation contract exists?
```

Do not write all clauses first and then try to retrofit the meaning.

Start from the output contract and work backward.

---

# 39. Explain Plans: Quality Requires Evidence

A query that “looks optimized” is not necessarily optimized.

Use:

```sql
EXPLAIN
SELECT ...;
```

for planning analysis.

When safe to execute the workload in the target environment or a representative test system:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

This gives actual execution information and buffer activity that can reveal where time and I/O are being spent.

Do not confuse:

```text
estimated cost
```

with:

```text
elapsed execution time
```

Planner cost is an internal model, not a stopwatch.

---

# 40. Read the Plan Like an Engineer

Focus on:

```text
Estimated rows
vs
Actual rows

Estimated loops
vs
Actual loops

Chosen access path

Join strategy

Sort / hash memory behavior

Buffer hits / reads

Rows removed by filters
```

## Cardinality estimate mismatch

A classic signal:

```text
Plan estimate: 100 rows
Actual:        500,000 rows
```

When an early estimate is dramatically wrong, later planner choices can also become poor.

Do not immediately blame the final operator.

Find the earliest major estimation divergence.

---

# 41. Nested Loop Is Not “Bad”

A common beginner mistake is:

> Nested Loop = slow.

Wrong.

A nested loop can be excellent when the outer relation is small and the inner side is efficiently indexed.

Example:

```text
outer rows = 20
inner lookup = indexed by primary key
```

can be far better than scanning or hashing a huge relation unnecessarily.

The correct question is:

> **Is this join strategy appropriate for the actual cardinalities and access paths?**

---

# 42. Sequential Scan Is Not “Bad”

Another cargo-cult rule:

> Sequential scans are always bad.

Wrong.

For a table where a query needs a large fraction of rows, a sequential scan may be cheaper than random index-driven access.

Quality performance reasoning begins with workload selectivity and data size.

---

# 43. `EXPLAIN ANALYZE` Can Change Production Risk

`EXPLAIN (ANALYZE, BUFFERS)` executes the statement. For reads, that means the query actually runs; for writes, it can mutate data.

Never run a write query with `ANALYZE` casually against production data.

For mutation analysis, use controlled environments, transactions where appropriate, or safe replicas/test systems.

---

# 44. The Performance Debugging Ladder

Use a repeatable sequence:

```text
1. Reproduce
2. Define the expected behavior
3. Measure execution time
4. Inspect EXPLAIN
5. Compare estimated vs actual rows
6. Identify the first major divergence
7. Inspect join cardinality
8. Inspect filters/selectivity
9. Inspect indexes/access paths
10. Inspect I/O and memory behavior
11. Change one thing
12. Re-measure
```

Do not start with:

```text
“Add an index.”
```

An index may be correct, irrelevant, or harmful depending on the workload.

---

# 45. Index Quality: Match the Predicate

For each candidate index, ask:

```text
Which query uses it?
Which predicate is selective?
What ordering does it provide?
What columns must be returned?
How frequently does the workload write?
What is the index maintenance cost?
```

A giant index containing every selected column is not automatically a good index.

An index is part of a workload design, not a trophy.

---

# 46. Query Shape Stability

Good production SQL should behave predictably as data evolves.

Watch for queries whose cost changes drastically when:

- selectivity changes;
- one tenant becomes much larger;
- a status distribution becomes skewed;
- historical rows dominate current rows;
- a “rare” value becomes common;
- a join relationship changes from mostly-one to heavily-many.

Test representative distributions, not just representative syntax.

---

# 47. Parameterization Does Not Eliminate Plan Reasoning

Prepared statements protect values from SQL injection, but application-level performance still depends on parameter distributions, query shapes, statistics, and the selected plan strategy.

Do not assume:

```text
parameterized = always fast
```

Parameterization is primarily a correctness/security concern; plan behavior is a separate engineering concern.

---

# 48. Avoid N+1 Query Design

Consider:

```text
1 query for customers
+ N queries for each customer's orders
```

Even when each query is individually fast, the total latency can be poor.

Possible alternatives:

- join when the result grain permits it;
- aggregate child data in SQL;
- batch IDs;
- use `IN` or `ANY` appropriately;
- use a dedicated reporting query;
- precompute when justified by workload.

The goal is not “one SQL query at all costs.”

The goal is a sensible data-access architecture.

---

# 49. Avoid the Opposite Extreme: Monster Queries

The cure for N+1 is not “one query containing the entire application.”

A giant query can become:

- difficult to test;
- difficult to review;
- difficult to optimize;
- fragile under feature changes;
- overloaded with unrelated responsibilities.

Use SQL to express relational work strongly suited to SQL.

Keep application orchestration where orchestration belongs.

---

# 50. SQL Boundaries in Node.js / NestJS

A production data-access layer should make query semantics visible.

Example:

```ts
const result = await this.db.query<InvoiceRow>(
  `
  SELECT
      i.id,
      i.invoice_number,
      i.total_amount,
      i.created_at
  FROM invoices AS i
  WHERE i.tenant_id = $1
    AND i.created_at >= $2
    AND i.created_at < $3
  ORDER BY i.created_at DESC, i.id DESC
  LIMIT $4
  `,
  [tenantId, from, to, limit],
);
```

The application code should make the boundary explicit:

```text
controller
→ service
→ repository/data-access
→ parameterized SQL
→ PostgreSQL
```

Do not scatter raw SQL fragments across controllers.

---

# 51. Validate Application Inputs Before SQL

SQL parameterization prevents a class of injection problems, but business validation remains necessary.

Examples:

```text
limit must be within an allowed maximum
from < to
sort must belong to an allow-list
status must belong to known domain
UUID must be syntactically valid
```

Database and application validation can complement each other.

---

# 52. SQL Quality and API Contracts

API response contracts should not accidentally inherit every database detail.

A database row may contain:

```text
internal_id
created_at
updated_at
soft_deleted_at
version
private_metadata
```

The API may only need:

```text
id
name
status
```

Explicit SQL projection helps enforce this boundary, but the final API serializer should also be intentional.

# 53. Testing Strategy

SQL quality requires more than unit-testing that a query returns one happy-path row.

## Layer 1 — Syntax / migration validation

Does the SQL parse and execute against the intended PostgreSQL version?

## Layer 2 — Semantic examples

Test:

```text
normal case
empty case
multiple matches
no matches
null values
boundary values
duplicate values
```

## Layer 3 — Property-style checks

Examples:

```text
Adding an unrelated order should not change another customer's total.
Changing row insertion order should not change ordered API output.
A tenant must never observe another tenant's row.
Adjacent date windows must not double-count boundary events.
```

## Layer 4 — Performance regression

Run representative fixtures and capture plan/time metrics.

## Layer 5 — Concurrency tests

For writes, test race conditions and conflicting transactions where relevant.

---

# 54. Fixtures Must Contain Pathological Data

A weak fixture:

```text
1 customer
1 order
1 payment
```

A strong fixture contains:

```text
multiple children
missing children
duplicate-like business conditions
NULLs
shared timestamps
large cardinality differences
multiple tenants
edge dates
boundary values
```

A query that passes only ideal data has not been meaningfully validated.

---

# 55. Golden-Result Testing

For complex reporting SQL, keep known expected outputs for carefully designed fixtures.

Example:

```text
fixture: reporting_case_07
expected total_sales = 1,250,000
expected paid_count = 17
expected customer_count = 12
```

When SQL is refactored, the result contract remains testable.

---

# 56. Mutation Testing for Query Logic

To challenge a query, deliberately change data:

```text
add an extra child row
remove a child row
insert a null
change a timestamp to the boundary
add a second matching status
add another tenant's data
```

Then verify which outputs should and should not change.

This is especially powerful for finding accidental join multiplication.

---

# 57. AI / Vibe-Coding SQL Failures

AI can generate SQL that is syntactically polished and semantically dangerous.

Common patterns:

### Failure 1 — `DISTINCT` as magic duplicate remover

AI sees duplicate results and adds `DISTINCT` without identifying the join cardinality error.

### Failure 2 — `SELECT *`

Convenient during generation, unsafe as a stable interface.

### Failure 3 — `INNER JOIN` everywhere

Rows with missing optional relationships silently disappear.

### Failure 4 — `LEFT JOIN` + `WHERE child.column = ...`

The generated query accidentally behaves like an inner join.

### Failure 5 — `ORDER BY created_at DESC LIMIT ...`

Pagination becomes unstable when timestamps tie.

### Failure 6 — application-side aggregation

The model fetches thousands of rows and loops in JavaScript for work PostgreSQL could aggregate correctly and efficiently.

### Failure 7 — function-wrapped indexed columns

AI writes:

```sql
WHERE DATE(created_at) = $1
```

without considering the existing index and selectivity.

### Failure 8 — unbounded `ILIKE '%term%'`

A plausible search query becomes expensive at scale.

### Failure 9 — unsafe dynamic identifiers

Values are parameterized but sort columns or SQL fragments are concatenated from raw user input.

### Failure 10 — incorrect tenant predicate placement

The SQL works in single-tenant development but leaks or mixes data when the database actually contains multiple tenants.

### Failure 11 — `NOT IN` with nullable subqueries

Semantics change because of SQL null behavior.

### Failure 12 — false performance certainty

The model claims “this uses the index” without checking the actual plan.

### Rule

> **Treat AI-generated SQL as an unreviewed junior engineer's proposal until semantics and plans prove otherwise.**

---

# 58. AI SQL Review Checklist

When reviewing generated SQL, ask the model's output these questions:

```text
What is the output grain?
What is the cardinality of every join?
Can any join multiply rows?
What happens when a child relation is missing?
What happens when values are NULL?
Is ordering deterministic?
Is pagination stable?
What assumptions are made about uniqueness?
What indexes does this query expect?
What does EXPLAIN predict?
What does EXPLAIN ANALYZE show?
What happens at 10x and 100x data volume?
What happens with malicious input?
What happens across tenant boundaries?
```

If the generated answer cannot explain these, do not trust the query merely because it looks professional.

## A — Correctness

- [ ] Output grain is explicit.
- [ ] Join cardinality is understood.
- [ ] Null behavior is intentional.
- [ ] Boundary conditions are tested.
- [ ] Aggregation grain is correct.
- [ ] Duplicate behavior is understood.

## B — Determinism

- [ ] Required ordering uses `ORDER BY`.
- [ ] Tie-breaking is deterministic.
- [ ] Pagination cursor contains the required ordering keys.

## C — Security

- [ ] Values are parameterized.
- [ ] Dynamic identifiers are allow-listed.
- [ ] Tenant/authorization semantics are enforced.
- [ ] Privileged functions use safe search-path discipline.

## D — Performance

- [ ] Realistic cardinalities were considered.
- [ ] Relevant indexes exist or are intentionally absent.
- [ ] `EXPLAIN` was inspected for critical queries.
- [ ] Actual runtime was measured for regressions.

## E — Maintainability

- [ ] Projection is explicit.
- [ ] Aliases are clear.
- [ ] Business concepts are recognizable in the query.
- [ ] Complex logic is structured without pointless abstraction.
- [ ] Important non-obvious choices are documented.

# 60. Production Scenario — Jewellery ERP Sales Report

Suppose a multi-branch jewellery ERP contains:

```text
branches
customers
sales
sale_items
payments
inventory_movements
```

Requirement:

> Return branch sales totals for a date interval, while preserving branches with zero sales.

A careless implementation may:

- start from `sales`, thereby losing zero-sales branches;
- join `sale_items`, multiplying sale rows;
- join `payments`, multiplying them again;
- aggregate everything in one query;
- add `DISTINCT` at the end;
- paginate by an unstable timestamp.

A higher-quality design begins with the contract:

```text
grain = one row per branch
population = all active branches
sales = optional relationship
items = separately aggregated if needed
payments = separately aggregated if needed
zero sales = numeric 0
ordering = explicit
tenant/branch scope = explicit
```

The SQL structure should follow that reasoning.

---

# 61. Evidence-Driven Debugging Example

### Symptom

A monthly sales report says:

```text
₹1,820,000
```

Finance says the correct value is:

```text
₹1,240,000
```

### Wrong diagnosis

> “PostgreSQL SUM is wrong.”

### Evidence-first process

1. Verify raw sales rows for the month.
2. Check expected report grain.
3. Inspect every join.
4. Count rows before and after each join.
5. Identify a many-to-many path.
6. Compare totals before aggregation.
7. Rewrite at explicit grains.
8. Re-run the report.
9. Add a regression test with multiple payment rows per sale.
10. Measure the plan after the semantic fix.

The root problem is almost certainly in query structure or data assumptions, not the aggregate function itself.

# 62. Reliability: Timeouts and Bounded Work

A production query should have operational expectations.

Examples:

- maximum API page size;
- maximum report interval for interactive endpoints;
- statement timeout for specific workloads where appropriate;
- batch jobs separated from latency-sensitive traffic;
- cancellation support from the application;
- retry discipline that does not amplify load.

A query can be logically correct and still operationally unsafe if it permits unbounded work from a public endpoint.

---

# 63. Do Not Hide Expensive Work Behind “Simple” APIs

A REST endpoint such as:

```text
GET /orders?search=...
```

may eventually become:

```text
JOIN 8 tables
→ aggregate
→ sort millions of rows
→ distinct
→ paginate with OFFSET 500000
```

The SQL layer must communicate workload constraints to the API design.

Database quality and API quality are connected.

---

# 64. Observability

Critical SQL should be observable through:

```text
query latency
query frequency
rows returned
rows scanned where available
slow-query logs / monitoring
plan regressions
connection pool saturation
lock/wait behavior where relevant
```

For important query families, keep enough metadata to answer:

> Which query shape became slow, for which workload, at what data volume, and after which change?

Do not log sensitive SQL parameter values indiscriminately.

---

# 65. Logging Quality

A useful diagnostic record can include:

```text
query identifier / operation name
request or trace identifier
tenant identifier in a privacy-safe form
duration
result count
error class
transaction context
```

Avoid dumping:

```text
passwords
access tokens
full personal data
payment credentials
sensitive business payloads
```

Observability must not become a data-exfiltration path.

---

# 66. Transactions and SQL Quality

A query can be correct in isolation and incorrect in a transaction sequence.

Example:

```text
SELECT available_stock
UPDATE stock
INSERT sale
```

Without appropriate transaction and concurrency reasoning, two requests may both observe the same inventory.

SQL quality therefore includes understanding the transaction protocol around the statement.

Do not evaluate a critical write query independently of the transaction that gives it meaning.

---

# 67. Retry Safety

Before retrying a failed database operation, ask:

```text
Was the statement executed?
Was the transaction committed?
Could the operation have side effects?
Is the operation idempotent?
```

A network error does not always mean the database did nothing.

This is especially important for mutation APIs and distributed systems.

---

# 68. Migration Compatibility

High-quality SQL should survive schema evolution deliberately.

Watch for:

```text
SELECT * dependencies
implicit type assumptions
column order assumptions
renamed columns
removed indexes
changed nullability
changed uniqueness
new row-level security policies
```

A migration is not safe merely because it executes successfully.

Validate its impact on query contracts.

# 70. Quality Patterns

## Pattern A — Explicit relation aliases

```sql
FROM orders AS o
JOIN customers AS c
  ON c.id = o.customer_id
```

## Pattern B — Explicit projection

```sql
SELECT o.id, o.total_amount
```

## Pattern C — Deterministic pagination

```sql
ORDER BY o.created_at DESC, o.id DESC
```

## Pattern D — Existence semantics

```sql
WHERE EXISTS (...)
```

## Pattern E — Half-open temporal interval

```sql
WHERE ts >= $1 AND ts < $2
```

## Pattern F — Parameterized values

```sql
WHERE email = $1
```

## Pattern G — Explicit grain before aggregation

```text
aggregate child relation
→ join aggregated relation
```

---

# 71. Anti-Patterns

## Anti-pattern 1 — `SELECT *` in API contracts

**Problem:** accidental schema coupling.

**Better:** explicit columns.

## Anti-pattern 2 — `DISTINCT` after unexplained joins

**Problem:** hides cardinality errors.

**Better:** identify the required grain.

## Anti-pattern 3 — Pagination without deterministic ordering

**Problem:** unstable page boundaries.

**Better:** unique ordering tuple.

## Anti-pattern 4 — `OFFSET` for indefinitely deep pagination

**Problem:** increasing skip work.

**Better:** keyset pagination when appropriate.

## Anti-pattern 5 — Raw user input in dynamic SQL syntax

**Problem:** injection risk.

**Better:** parameterize values and allow-list structural choices.

## Anti-pattern 6 — Blind function wrapping of indexed columns

**Problem:** may prevent intended index usage.

**Better:** write searchable predicates or use an intentional expression index.

## Anti-pattern 7 — Giant SQL because “database is faster”

**Problem:** unclear boundaries and difficult maintenance.

**Better:** place work where it belongs.

## Anti-pattern 8 — Many tiny SQL calls because “each is simple”

**Problem:** network and coordination overhead.

**Better:** batch or consolidate relational work where appropriate.

# 72. Naive → Improved → Production

## Scenario: Search customers by name

### Naive approach

```sql
SELECT *
FROM customers
WHERE LOWER(name) LIKE '%john%'
LIMIT 50;
```

### Why it can fail

- broad wildcard search may scan many rows;
- explicit projection is absent;
- case-folding semantics may not match product requirements;
- no deterministic ordering;
- no tenant scope shown.

### Improved approach

```sql
SELECT
    c.id,
    c.name,
    c.created_at
FROM customers AS c
WHERE c.tenant_id = $1
  AND c.name ILIKE $2
ORDER BY c.name ASC, c.id ASC
LIMIT $3;
```

Then measure the workload and choose an appropriate search/index strategy.

### Production considerations

If substring search is a core feature at scale, investigate the specific search requirements and supporting indexes/extensions rather than blindly adding a B-tree index that does not match the predicate.

# 73. Expert Mental Model: SQL as a Proof

Think of a strong query as a proof that the result contract follows from the data model.

For example:

```text
Requirement:
One row per customer with total paid amount.

Proof structure:
1. identify customer population
2. identify paid-payment relation
3. reduce payments to one row per customer
4. outer join aggregate to population
5. replace absent totals with 0 when required
6. order deterministically if exposed to API
```

This is much safer than starting with syntax and improvising until the output “looks right.”

# 74. SQL Review Questions

Before approving a critical query, answer:

### Semantics

1. What does one row represent?
2. What entities are included?
3. What entities are intentionally excluded?
4. What happens when a related row is missing?
5. What happens when there are multiple related rows?

### Nulls

6. What does `NULL` mean here?
7. Is `COUNT(column)` intentional?
8. Is `COALESCE` using a truthful business default?

### Determinism

9. Is order required?
10. If yes, is ordering unique?
11. Is pagination stable?

### Performance

12. What is the expected row count at each stage?
13. Which join can multiply rows?
14. What indexes support the access pattern?
15. What does `EXPLAIN` show?
16. What is the biggest estimated-vs-actual mismatch?

### Security

17. Are values parameterized?
18. Are identifiers allow-listed?
19. Can tenant or authorization boundaries be bypassed?
20. Does `search_path` matter?

### Operations

21. Is the query bounded?
22. What happens at 10x data volume?
23. Can it be cancelled safely?
24. Is retry behavior safe?

# 84. Professional SQL Standards

For a production codebase, adopt these defaults:

```text
1. Define the output grain before writing joins.
2. Prefer explicit projections.
3. Parameterize values.
4. Allow-list dynamic SQL structure.
5. Make null behavior explicit.
6. Make required ordering deterministic.
7. Prefer existence semantics for existence requirements.
8. Do not use DISTINCT to hide unexplained cardinality.
9. Measure critical queries with EXPLAIN.
10. Compare estimated and actual rows.
11. Treat indexes as workload-specific decisions.
12. Test pathological data, not just happy paths.
13. Treat tenant isolation as a correctness property.
14. Keep privileged SQL security-aware.
15. Treat AI-generated SQL as review-required code.
16. Record the PostgreSQL major version for important operational behavior.
17. Change one performance variable at a time and re-measure.
18. Optimize the root cause, not the visible symptom.
```

# 87. Final Takeaways

The deepest lessons of advanced SQL quality are not syntax tricks.

They are reasoning habits:

```text
Define the grain.

Understand every join's cardinality.

Treat NULL as a semantic state.

Make ordering deterministic when it matters.

Separate values from SQL structure.

Use constraints to enforce invariants.

Measure plans instead of guessing.

Compare estimates with actual execution.

Do not confuse “valid SQL” with “correct SQL.”

Do not confuse “fast on my laptop” with “production-safe.”

Do not let AI-generated SQL bypass engineering review.

Optimize only after correctness is established.
```

The ultimate standard is:

> **A production-quality query should be explainable as a proof of the business requirement, executable within a known operational envelope, safe under its trust boundaries, and measurable under realistic workload.**
