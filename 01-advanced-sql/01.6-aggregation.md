# Chapter 01.6 — Aggregation

> **Phase 01 — Advanced SQL**  
> **Focus:** turning a relation containing many rows into mathematically and semantically correct summaries.

## 1. Chapter Mission

Aggregation is not merely “using `COUNT()` and `SUM()`.” It is the discipline of defining a population, defining a grouping grain, applying a reduction over that population, and proving that the resulting number means what the business thinks it means.

An expert must be able to answer four questions before trusting an aggregate query:

1. **What is the input population?**
2. **What is one row of the input relation?**
3. **What is the grouping grain of the result?**
4. **What exact mathematical quantity does each aggregate compute?**

A query can be syntactically valid, fast, and completely wrong. The most dangerous aggregation failures are therefore semantic rather than syntactic.

---

## 2. Learning Outcomes

By the end of this chapter you should be able to:

- distinguish row-level expressions from aggregate expressions;
- explain why `GROUP BY` changes the result grain;
- derive the result of an aggregate query before running it;
- correctly use `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `BOOL_*`, `array_agg`, `string_agg`, JSON aggregates, and statistical aggregates;
- reason precisely about `NULL` and empty input sets;
- distinguish `COUNT(*)`, `COUNT(column)`, and `COUNT(DISTINCT column)`;
- explain why joins can silently inflate totals;
- identify the difference between `WHERE`, `HAVING`, and aggregate `FILTER`;
- use conditional aggregation safely;
- understand aggregate ordering and deterministic output;
- reason about ordered-set and hypothetical-set aggregates;
- understand how PostgreSQL may implement aggregation internally;
- read aggregate plans in `EXPLAIN (ANALYZE, BUFFERS)`;
- detect memory, sort, hash, and cardinality problems;
- design production-grade financial, temporal, inventory, and reporting queries;
- review ORM-generated aggregation SQL;
- audit AI-generated aggregation code for semantic errors;
- choose between aggregation, window functions, subqueries, pre-aggregation, materialized views, and summary tables.

---

## 3. The Core Mental Model

A useful abstraction is:

```text
Base relation
    ↓
Define population
    ↓
Filter rows
    ↓
Define grouping grain
    ↓
Partition rows into groups
    ↓
Aggregate each group
    ↓
Filter groups (HAVING)
    ↓
Produce final relation
```

Do not confuse the above **logical model** with PostgreSQL's physical execution order. The optimizer is free to transform the execution strategy while preserving observable semantics.

The key invariant is:

> **Every output aggregate must correspond to a clearly defined set of input rows.**

# 4. Aggregation from First Principles

## 4.1 What is an aggregate function?

An aggregate function consumes a collection of input values and produces one value for a group.

Examples:

```sql
COUNT(*)
SUM(amount)
AVG(amount)
MIN(created_at)
MAX(created_at)
```

Conceptually:

```text
x1, x2, x3, ..., xn
        ↓
    aggregate
        ↓
       result
```

For a grouped query:

```text
Rows
 ↓
Group A → aggregate → one result row
Group B → aggregate → one result row
Group C → aggregate → one result row
```

PostgreSQL stores metadata about aggregate functions in `pg_aggregate`; built-in aggregates include general-purpose aggregates, statistical aggregates, ordered-set aggregates, hypothetical-set aggregates, and grouping operations. PostgreSQL also marks aggregates that support Partial Mode, which allows them to participate in optimizations such as parallel aggregation. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/functions-aggregate.html)

---

## 5. Result Grain — The Most Important Idea

Before writing a `GROUP BY`, define the result grain in plain English.

Examples:

```text
one row per customer
one row per branch
one row per branch per month
one row per product per warehouse
one row per tenant per day
```

Then map the grain to grouping keys.

```sql
SELECT
    branch_id,
    date_trunc('month', sold_at) AS month,
    SUM(amount) AS revenue
FROM sales
GROUP BY
    branch_id,
    date_trunc('month', sold_at);
```

The result grain is:

```text
(branch_id, month)
```

This simple habit prevents a large class of reporting bugs.

### Expert rule

**Never start an aggregation query with the aggregate function. Start with the grain.**

---

# 6. GROUP BY Semantics

`GROUP BY` partitions rows that have the same grouping-key values into groups, after which aggregate expressions can produce one value per group.

Example:

```sql
SELECT
    department_id,
    COUNT(*) AS employee_count
FROM employees
GROUP BY department_id;
```

If the input is:

| department_id | employee |
|---|---|
| 10 | A |
| 10 | B |
| 20 | C |
| 20 | D |
| 20 | E |

Then the logical groups are:

```text
department 10 → 2 rows
 department 20 → 3 rows
```

and the result has exactly two rows.

PostgreSQL requires selected expressions in grouped queries to be either grouped expressions, aggregate expressions, or otherwise provably functionally dependent in cases supported by PostgreSQL's grouping rules. PostgreSQL 18 also contains planner improvements that can omit redundant `GROUP BY` columns when uniqueness proves functional dependency. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/queries-table-expressions.html) [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html)

---

# 7. `COUNT` — Five Different Questions

## 7.1 `COUNT(*)`

```sql
SELECT COUNT(*)
FROM orders;
```

Question:

> How many rows are in the input relation?

It counts rows, including rows whose individual columns are `NULL`.

---

## 7.2 `COUNT(column)`

```sql
SELECT COUNT(email)
FROM customers;
```

Question:

> How many input rows have a non-NULL `email` value?

This is **not** equivalent to `COUNT(*)`.

---

## 7.3 `COUNT(DISTINCT column)`

```sql
SELECT COUNT(DISTINCT email)
FROM customers;
```

Question:

> How many distinct non-NULL values occur in this expression?

This is frequently used incorrectly when the actual business question is “number of customers.”

---

## 7.4 Conditional count

A robust modern form is:

```sql
SELECT COUNT(*) FILTER (WHERE status = 'paid')
FROM orders;
```

This counts rows satisfying the filter within the aggregate input.

Alternative:

```sql
SELECT COUNT(CASE WHEN status = 'paid' THEN 1 END)
FROM orders;
```

Both can express the same business question, but `FILTER` often communicates intent more directly.

---

## 8. `SUM` and the Empty-Set Trap

Consider:

```sql
SELECT SUM(amount)
FROM payments
WHERE false;
```

The result is `NULL`, not `0`.

PostgreSQL documentation explicitly notes that except for `count`, built-in aggregates return `NULL` on no input rows; in particular, `sum` over an empty set returns `NULL`. Use `COALESCE` where the business meaning requires a zero. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/functions-aggregate.html)

```sql
SELECT COALESCE(SUM(amount), 0)
FROM payments
WHERE false;
```

### Why this matters

These are different states:

```text
NULL → there was no aggregate value
0    → the mathematical result is zero
```

In financial systems that distinction can matter for reconciliation, API contracts, downstream calculations, and accounting semantics.

---

# 9. `AVG` — Do Not Blindly Average Stored Averages

This is wrong in many reporting systems:

```sql
SELECT AVG(branch_average)
FROM monthly_branch_summary;
```

Suppose:

```text
Branch A: 100 transactions, average 10
Branch B:  10 transactions, average 20
```

A simple average gives:

```text
(10 + 20) / 2 = 15
```

But the true transaction-level average is:

```text
(100*10 + 10*20) / 110 = 10.909...
```

When combining pre-aggregated data, preserve the sufficient statistics required by the mathematical operation.

For an average, that often means storing:

```text
sum
count
```

Then recompute:

```sql
SUM(total_amount) / NULLIF(SUM(transaction_count), 0)
```

---

# 10. NULL Semantics in Aggregation

`NULL` must be treated as “unknown/missing,” not automatically as zero.

For common numeric aggregates:

```sql
SUM(amount)
AVG(amount)
MIN(amount)
MAX(amount)
```

`NULL` input values are generally ignored by these aggregates.

Example:

```text
amount
------
100
NULL
200
```

Then:

```text
SUM = 300
AVG = 150
COUNT(amount) = 2
COUNT(*) = 3
```

This difference is often the source of apparent contradictions in reports.

---

# 11. `COUNT(*)` vs `COUNT(column)` — Production Example

Suppose an ERP contains:

```text
customers
---------
id
name
phone
```

Query:

```sql
SELECT COUNT(*) FROM customers;
```

means:

> number of customer rows.

While:

```sql
SELECT COUNT(phone) FROM customers;
```

means:

> number of customers with a non-NULL phone.

Naming the result as `customer_count` for the second query would be a semantic bug.

Prefer explicit names:

```sql
SELECT
    COUNT(*) AS customer_count,
    COUNT(phone) AS customers_with_phone
FROM customers;
```

---

# 12. Conditional Aggregation

Conditional aggregation allows several related metrics to be computed in one pass over a population.

```sql
SELECT
    branch_id,
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (WHERE status = 'paid') AS paid_orders,
    COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled_orders,
    COALESCE(SUM(amount) FILTER (WHERE status = 'paid'), 0) AS paid_revenue
FROM orders
GROUP BY branch_id;
```

This is often much cleaner than issuing many unrelated queries.

### But ask a deeper question

What is the population?

If cancelled rows should not participate in revenue, filtering only the aggregate is appropriate.

If cancelled rows should be removed from the entire query, use `WHERE` instead.

---

# 13. WHERE vs HAVING vs FILTER

These three mechanisms answer different questions.

## WHERE

Filters input rows before grouping.

```sql
SELECT branch_id, SUM(amount)
FROM orders
WHERE status = 'paid'
GROUP BY branch_id;
```

Population:

```text
paid orders only
```

---

## HAVING

Filters groups after aggregation.

```sql
SELECT
    branch_id,
    SUM(amount) AS revenue
FROM orders
GROUP BY branch_id
HAVING SUM(amount) > 100000;
```

Question:

> Which already-formed groups qualify?

---

## FILTER

Filters input rows for a specific aggregate expression.

```sql
SELECT
    branch_id,
    COUNT(*) AS total,
    COUNT(*) FILTER (WHERE status = 'paid') AS paid
FROM orders
GROUP BY branch_id;
```

The group still contains all orders; only the `paid` aggregate receives the filtered subset.

### Mental model

```text
WHERE  → which rows enter the grouping operation?
FILTER → which rows enter this aggregate?
HAVING → which groups survive?
```

---

# 14. The Most Dangerous Aggregation Bug: Join Multiplication

Consider:

```text
orders
------
order_id
customer_id

after:

order_items
-----------
order_id
item_id
qty

payments
--------
order_id
payment_id
amount
```

Suppose an order has:

```text
3 items
2 payments
```

Joining both child tables can produce:

```text
3 × 2 = 6 rows
```

If you then do:

```sql
SUM(payment.amount)
```

you may count each payment multiple times.

The query may look completely reasonable and pass superficial tests.

### Wrong approach

```sql
SELECT
    o.order_id,
    SUM(oi.qty) AS total_qty,
    SUM(p.amount) AS total_paid
FROM orders o
LEFT JOIN order_items oi ON oi.order_id = o.order_id
LEFT JOIN payments p ON p.order_id = o.order_id
GROUP BY o.order_id;
```

### Why it fails

The join changed the grain before aggregation.

Input grain became approximately:

```text
order × item × payment
```

not:

```text
order × item
```

or:

```text
order × payment
```

### Correct strategy: pre-aggregate each independent child relation

```sql
WITH item_totals AS (
    SELECT
        order_id,
        SUM(qty) AS total_qty
    FROM order_items
    GROUP BY order_id
), payment_totals AS (
    SELECT
        order_id,
        SUM(amount) AS total_paid
    FROM payments
    GROUP BY order_id
)
SELECT
    o.order_id,
    COALESCE(i.total_qty, 0) AS total_qty,
    COALESCE(p.total_paid, 0) AS total_paid
FROM orders o
LEFT JOIN item_totals i ON i.order_id = o.order_id
LEFT JOIN payment_totals p ON p.order_id = o.order_id;
```

Now each derived relation has grain:

```text
item_totals   → one row per order
payment_totals → one row per order
orders         → one row per order
```

The joins preserve the intended grain.

---

# 15. A Better Rule for Multi-Table Aggregation

Before every aggregate query, write a grain ledger.

Example:

```text
orders        = 1 row / order
order_items   = N rows / order
payments      = N rows / order
shipments     = N rows / order
```

Then ask:

> If I join all of these before aggregating, what does one resulting row represent?

If the answer becomes:

```text
order × item × payment × shipment
```

you must evaluate multiplication risk.

---

# 16. `DISTINCT` Is Not a Universal Repair

A common reaction to inflated totals is:

```sql
SUM(DISTINCT p.amount)
```

This is usually unsafe.

Suppose legitimate payments are:

```text
100
100
```

`SUM(DISTINCT amount)` returns:

```text
100
```

but the real total is:

```text
200
```

The issue is not duplicate values. It is duplicate **rows caused by join cardinality**.

Correct the relational shape rather than hiding the symptom with `DISTINCT`.

---

# 17. `MIN` and `MAX` Are Not “First” and “Last”

This distinction matters.

```sql
MIN(created_at)
```

means:

> minimum value according to the type's ordering.

It does not mean:

> first row PostgreSQL happened to encounter.

Similarly:

```sql
MAX(created_at)
```

is not a statement about physical storage order.

For deterministic “latest row” selection, aggregation alone is often insufficient; use an appropriate ordering strategy, `DISTINCT ON`, a window function, or a lateral/anti-join pattern depending on the problem.

---

# 18. Ordered Aggregates

Some aggregate results depend on input order.

For example:

```sql
SELECT string_agg(name, ', ' ORDER BY name)
FROM customers;
```

Without an explicit order, the ordering of inputs is not generally guaranteed for order-sensitive aggregates.

PostgreSQL documentation specifically notes that aggregates such as `array_agg`, `json_agg`, `jsonb_agg`, `string_agg`, and `xmlagg` can produce different results depending on input order, and the default ordering is unspecified. The recommended deterministic form is to provide `ORDER BY` inside the aggregate call where appropriate. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/functions-aggregate.html)

### Example

Bad for deterministic application output:

```sql
SELECT string_agg(tag, ', ')
FROM product_tags;
```

Better:

```sql
SELECT string_agg(tag, ', ' ORDER BY tag)
FROM product_tags;
```

---

# 19. `array_agg` and JSON Aggregates

Aggregation is not restricted to numeric calculations.

```sql
SELECT
    customer_id,
    array_agg(product_id ORDER BY product_id) AS product_ids
FROM order_items
GROUP BY customer_id;
```

Likewise JSON-oriented aggregation can construct application-facing structures.

However, avoid using JSON aggregation merely to compensate for poor relational modeling. Ask whether the resulting document is:

- a true application boundary representation;
- a reporting convenience;
- a cache/precomputation;
- or an attempt to avoid understanding relational shape.

Also be aware that order-sensitive aggregates should receive an explicit order when output stability matters.

---

# 20. Ordered-Set Aggregates

PostgreSQL supports ordered-set aggregates such as:

```sql
percentile_cont(0.5) WITHIN GROUP (ORDER BY amount)
```

This can compute a continuous percentile.

Example:

```sql
SELECT
    percentile_cont(0.50) WITHIN GROUP (ORDER BY response_ms) AS p50,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY response_ms) AS p95,
    percentile_cont(0.99) WITHIN GROUP (ORDER BY response_ms) AS p99
FROM request_log;
```

This is extremely useful for performance reporting because mean latency can hide tail behavior.

PostgreSQL's ordered-set aggregates include `mode`, `percentile_cont`, and `percentile_disc`, with documented differences between continuous interpolation and discrete selection. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/functions-aggregate.html)

---

# 21. `percentile_cont` vs `percentile_disc`

### Continuous

```sql
percentile_cont(0.95)
```

May interpolate between adjacent input values.

### Discrete

```sql
percentile_disc(0.95)
```

Returns an actual value from the ordered input set.

Choose based on the meaning of the metric rather than habit.

---

# 22. Aggregation and Window Functions Are Different

Aggregate query:

```sql
SELECT
    branch_id,
    SUM(amount) AS branch_revenue
FROM sales
GROUP BY branch_id;
```

Result:

```text
one row per branch
```

Window expression:

```sql
SELECT
    branch_id,
    sale_id,
    amount,
    SUM(amount) OVER (PARTITION BY branch_id) AS branch_revenue
FROM sales;
```

Result:

```text
one row per sale
plus repeated branch total
```

The first **reduces rows**. The second **preserves rows while computing across a window**.

PostgreSQL documents that non-window aggregate functions execute before window functions, which allows patterns where an aggregate feeds a window expression. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/tutorial-window.html)

# 23. Aggregating an Aggregate

Sometimes the correct architecture is multiple aggregation layers.

Example:

```text
transactions
    ↓
monthly customer totals
    ↓
monthly branch totals
    ↓
company totals
```

Do not assume one `GROUP BY` can express every business level safely.

Example:

```sql
WITH customer_month AS (
    SELECT
        branch_id,
        customer_id,
        date_trunc('month', sold_at) AS month,
        SUM(amount) AS customer_total
    FROM sales
    GROUP BY branch_id, customer_id, date_trunc('month', sold_at)
)
SELECT
    branch_id,
    month,
    SUM(customer_total) AS branch_total
FROM customer_month
GROUP BY branch_id, month;
```

This is valuable when each intermediate layer has business meaning or when it prevents an invalid direct aggregation.

---

# 24. Functional Dependency and Grouping

Suppose:

```text
customers
---------
id PRIMARY KEY
name
```

and a query groups by the unique identifier.

```sql
SELECT id, name, COUNT(*)
FROM customers
GROUP BY id;
```

PostgreSQL can recognize functional dependency in supported cases because `id` uniquely determines `name`.

Do not interpret this as permission to ignore relational reasoning. It is a consequence of a schema invariant:

```text
id → name
```

The deeper principle is that grouping legality depends on whether an expression has a single well-defined value per group.

---

# 25. Aggregation and Joins — A Formal Way to Think

Let:

```text
A = one row per order
B = many rows per order
C = many rows per order
```

Then:

```text
A JOIN B JOIN C
```

can create:

```text
|B(order)| × |C(order)|
```

rows per order.

An aggregate over B after that join does not know which multiplication came from C.

Therefore:

> **Aggregate a many-side relation before joining it to another independent many-side relation whenever the target metric is defined at the parent grain.**

This is one of the most reusable SQL rules in real systems.

---

# 26. Financial Correctness

Financial aggregation deserves stricter rules.

Avoid silently mixing:

- net and gross amounts;
- different currencies;
- tax-inclusive and tax-exclusive amounts;
- posted and unposted entries;
- authorized and settled payments;
- business dates and system timestamps;
- rounded and unrounded quantities.

### Example

A revenue report should specify:

```text
population:
    posted sales

currency:
    INR

time basis:
    business settlement date

grain:
    branch × month

amount definition:
    net taxable revenue before payment reconciliation
```

A query can be mathematically correct yet financially meaningless if these definitions are ambiguous.

---

# 27. Monetary Types and Aggregation

For exact financial arithmetic, prefer types and formulas that preserve the intended precision; do not rely on binary floating-point for accounting semantics merely because it is convenient.

Example:

```sql
SUM(amount_numeric)
```

Then explicitly define rounding policy:

```sql
ROUND(SUM(amount_numeric), 2)
```

But do not round each row before aggregation unless business rules require per-line rounding:

```sql
-- different mathematical operation
SUM(ROUND(amount, 2))
```

is not necessarily equal to:

```sql
ROUND(SUM(amount), 2)
```

This distinction becomes important in invoicing and tax systems.

---

# 28. Temporal Aggregation

“Daily revenue” is not purely a SQL formatting problem.

You must define:

```text
time zone
business day boundary
source timestamp
inclusive/exclusive interval semantics
```

Example:

```sql
GROUP BY date_trunc('day', sold_at)
```

is only meaningful if the session/time-zone assumptions match the business definition of a day.

For timezone-sensitive systems, explicitly normalize or convert timestamps before deriving reporting buckets.

---

# 29. Multi-Tenant Aggregation

Every tenant-aware aggregation query should make tenant scope explicit when the schema requires it.

Example:

```sql
SELECT
    tenant_id,
    branch_id,
    SUM(amount) AS revenue
FROM invoices
WHERE tenant_id = $1
GROUP BY tenant_id, branch_id;
```

Do not rely on application assumptions such as:

> “This endpoint always sends the current tenant.”

Database-level isolation and query-level predicates must be designed consistently with the tenancy architecture.

---

# 30. Common Incorrect Pattern: Grouping at the Wrong Grain

Suppose the requirement is:

> one row per branch per month.

Bad:

```sql
SELECT branch_id, SUM(amount)
FROM sales
GROUP BY branch_id;
```

This produces:

```text
one row per branch
```

not:

```text
one row per branch per month
```

Correct:

```sql
SELECT
    branch_id,
    date_trunc('month', sold_at) AS month,
    SUM(amount) AS revenue
FROM sales
GROUP BY branch_id, date_trunc('month', sold_at);
```

The bug is semantic, not syntactic.

---

# 31. Common Incorrect Pattern: HAVING Instead of WHERE

Bad:

```sql
SELECT
    branch_id,
    SUM(amount) AS revenue
FROM sales
GROUP BY branch_id
HAVING sold_at >= DATE '2026-01-01';
```

This confuses row filtering with group filtering.

Correct:

```sql
SELECT
    branch_id,
    SUM(amount) AS revenue
FROM sales
WHERE sold_at >= DATE '2026-01-01'
GROUP BY branch_id;
```

`HAVING` is for group-level predicates such as:

```sql
HAVING SUM(amount) > 100000
```

---

# 32. Common Incorrect Pattern: `COUNT(DISTINCT id)` to Hide Join Bugs

Suppose:

```sql
COUNT(DISTINCT order_id)
```

produces a plausible order count while:

```sql
SUM(amount)
```

is inflated because of join multiplication.

The query now gives:

```text
order_count = plausible
revenue     = wrong
```

This can make debugging harder because one metric appears to validate the query.

### Expert response

Check the relational grain before aggregation. Do not validate one aggregate with another when their duplicate sensitivity differs.

---

# 33. Empty Groups and LEFT JOIN

Consider:

```sql
SELECT
    c.id,
    COUNT(o.id) AS order_count
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id;
```

A customer with no orders still appears, with:

```text
COUNT(o.id) = 0
```

because `o.id` is `NULL` for the outer-join-generated row.

But:

```sql
COUNT(*);
```

would count the preserved customer row and therefore return `1`.

This is one of the strongest examples of why `COUNT(*)` and `COUNT(column)` express different questions.

---

# 34. Boolean Aggregates

PostgreSQL provides aggregates such as:

```sql
bool_and(condition)
bool_or(condition)
```

These can encode business rules directly.

Example:

```sql
SELECT
    customer_id,
    bool_and(status = 'verified') AS all_verified,
    bool_or(status = 'blocked') AS any_blocked
FROM accounts
GROUP BY customer_id;
```

This can be more expressive than manually encoding multiple counts, depending on the business rule.

---

# 35. `FILTER` as a Metric DSL

For dashboard workloads, `FILTER` can act almost like a small metric definition language.

```sql
SELECT
    COUNT(*) AS total,
    COUNT(*) FILTER (WHERE status = 'paid') AS paid,
    COUNT(*) FILTER (WHERE status = 'pending') AS pending,
    COUNT(*) FILTER (WHERE status = 'failed') AS failed,
    SUM(amount) FILTER (WHERE status = 'paid') AS paid_amount,
    SUM(amount) FILTER (WHERE status = 'failed') AS failed_amount
FROM payments;
```

This makes related metrics share one population and one query boundary, while preserving separate aggregation predicates.

---

# 36. Performance Model of Aggregation

Aggregation cost depends on more than the number of output rows.

Conceptually:

```text
Cost ≈ input rows scanned
     + grouping work
     + aggregate transition work
     + sorting/hashing cost
     + memory pressure
     + spill I/O
     + parallel coordination
```

Two queries that return 100 rows can have radically different costs if one scans 10,000 rows and another scans 1 billion rows.

The first performance question is therefore:

> How many rows reach the aggregate stage?

---

# 37. Hash Aggregation vs Group Aggregation

PostgreSQL may use different physical strategies for aggregation.

A common conceptual distinction is:

```text
Hash Aggregate
----------------
Input
 ↓
hash grouping structure
 ↓
aggregate states
 ↓
output
```

versus a sorted/grouped strategy:

```text
Input
 ↓
Sort / ordered input
 ↓
Group Aggregate
 ↓
output
```

Hash aggregation can be attractive when hashing groups is efficient and memory is sufficient. Group aggregation can exploit already-ordered input or an explicit sort strategy.

Do not choose an algorithm by intuition alone. Inspect the actual plan.

---

# 38. Memory Pressure and Hash Aggregation

If a hash aggregate cannot remain within available memory, PostgreSQL may use batching/spilling mechanisms depending on the plan and configuration.

Symptoms can include:

- temporary file growth;
- high I/O during aggregation;
- latency increases as distinct group count grows;
- memory pressure at concurrency.

The important relationship is:

```text
number of groups
×
state size per group
×
concurrent operations
```

A query with 100 million distinct grouping keys is qualitatively different from one with 100 groups.

---

# 39. Cardinality Matters More Than Output Size

Consider:

```sql
SELECT customer_id, SUM(amount)
FROM transactions
GROUP BY customer_id;
```

If there are:

```text
1,000,000,000 transactions
10,000 customers
```

then the output has only 10,000 rows, but the input still contains 1 billion rows.

Optimization must target the work required to consume the input and construct the groups, not merely the result size.

---

# 40. Pre-Aggregation as a Performance Tool

The correctness pattern of pre-aggregation can also be a performance pattern.

Instead of:

```text
large child relation
   ↓
join
   ↓
large intermediate relation
   ↓
aggregate
```

use:

```text
large child relation
   ↓
aggregate
   ↓
small relation
   ↓
join
```

This can reduce join volume, memory pressure, and intermediate cardinality.

But do not pre-aggregate blindly: if the final business question needs row-level correlations between two child tables, pre-aggregation may destroy necessary information.

---

# 41. `EXPLAIN`-First Aggregation Debugging

For a suspicious aggregate query use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Inspect:

```text
actual rows
estimated rows
loops
sort method
memory
temporary I/O
aggregate node
join nodes before aggregation
```

A useful diagnostic pattern is:

```text
estimated rows ≪ actual rows
```

which can indicate statistics/cardinality-estimation problems.

Another is:

```text
huge rows before Aggregate
```

which may reveal a join-multiplication or late-filtering issue.

---

# 42. Aggregation + Join Plan Reading

Suppose the plan is roughly:

```text
Aggregate
  -> Hash Join
       -> Seq Scan orders
       -> Hash
            -> Seq Scan payments
```

Do not focus only on the Aggregate node.

Ask:

> How many rows did the join produce before aggregation?

A correct aggregate over a disastrous intermediate relation can still be a performance failure.

---

# 43. Parallel Aggregation

Some aggregates support Partial Mode and can participate in parallel aggregation. The PostgreSQL documentation identifies Partial Mode support for many built-in aggregates. [PostgreSQL 18 docs](https://www.postgresql.org/docs/18/functions-aggregate.html)

Conceptually:

```text
Worker A → partial aggregate ┐
Worker B → partial aggregate ├→ combine/finalize
Worker C → partial aggregate ┘
```

This is attractive for large scans, but parallelism has overhead and is not automatically faster for every workload.

Consider:

```text
input size
worker startup cost
CPU availability
I/O bottleneck
aggregate combinability
concurrency
```

---

# 44. Aggregate Functions and Parallel Safety

Do not assume every user-defined aggregate behaves like a built-in aggregate.

When extending PostgreSQL, understand whether the aggregate has the support needed for partial/parallel processing and whether its state transition and combination semantics are correct.

A logically associative operation is not automatically a correctly implemented parallel aggregate; the intermediate state and combine logic must preserve the intended result.

---

# 45. Common AI / Vibe-Coding Aggregation Failures

AI-generated SQL often contains patterns that look polished but are semantically unsafe.

### Failure 1 — Blind `SUM(DISTINCT amount)`

Reason given:

> “Remove duplicate amounts.”

Problem:

Different legitimate rows can contain the same amount.

Correct audit question:

> Are duplicate rows values, or are they duplicate relational paths?

---

### Failure 2 — Joining every table and then aggregating

Reason:

> “Get all needed fields in one query.”

Problem:

Independent one-to-many joins multiply rows.

Correct response:

Establish grain for every relation before joining.

---

### Failure 3 — `COUNT(*)` used for child existence

With a `LEFT JOIN`, `COUNT(*)` counts the preserved parent row.

Often the intended expression is:

```sql
COUNT(child.id)
```

---

### Failure 4 — Averaging averages

AI may suggest:

```sql
AVG(monthly_average)
```

without considering different sample sizes.

Correct approach:

Aggregate sufficient statistics.

---

### Failure 5 — Missing deterministic order in list aggregation

Example:

```sql
array_agg(tag)
```

when consumers compare exact serialized output.

Correct:

```sql
array_agg(tag ORDER BY tag)
```

---

### Failure 6 — Wrong temporal bucket

Example:

```sql
date_trunc('day', created_at)
```

without defining the reporting timezone.

---

### Failure 7 — Aggregating data across tenants

The query is syntactically valid but omits tenant boundaries.

This is a correctness and potentially security failure.

---

# 46. Production Reporting Example — Branch Revenue

Requirement:

> Show each branch's paid invoice count and paid revenue for March 2026.

Start with the contract:

```text
population = paid invoices
result grain = branch
period = 2026-03-01 inclusive to 2026-04-01 exclusive
```

Query:

```sql
SELECT
    branch_id,
    COUNT(*) AS paid_invoice_count,
    COALESCE(SUM(total_amount), 0) AS paid_revenue
FROM invoices
WHERE status = 'paid'
  AND paid_at >= TIMESTAMPTZ '2026-03-01 00:00:00+00'
  AND paid_at <  TIMESTAMPTZ '2026-04-01 00:00:00+00'
GROUP BY branch_id;
```

Notice that the time interval uses:

```text
>= start
< end
```

which composes cleanly across adjacent periods.

---

# 47. Production Example — Customer Activity Metrics

Requirement:

> one row per customer with total orders, successful orders, total spend, and largest order.

```sql
SELECT
    customer_id,
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (WHERE status = 'completed') AS completed_orders,
    COALESCE(SUM(amount) FILTER (WHERE status = 'completed'), 0) AS completed_spend,
    MAX(amount) FILTER (WHERE status = 'completed') AS largest_completed_order
FROM orders
GROUP BY customer_id;
```

This illustrates the importance of defining each metric independently even though they share the same population relation.

---

# 48. Production Example — Inventory Aggregation

Suppose:

```text
stock_movements
---------------
warehouse_id
product_id
movement_type
quantity
```

Requirement:

> current net movement per product per warehouse.

A common expression is:

```sql
SELECT
    warehouse_id,
    product_id,
    SUM(
        CASE
            WHEN movement_type = 'IN' THEN quantity
            WHEN movement_type = 'OUT' THEN -quantity
            ELSE 0
        END
    ) AS net_quantity
FROM stock_movements
GROUP BY warehouse_id, product_id;
```

The business invariant is:

```text
net stock movement = inbound - outbound
```

An expert review checks:

- whether returns are represented correctly;
- whether cancelled movements are excluded;
- whether transfers have both sides represented;
- whether the ledger is append-only or mutable;
- whether unit conversions exist;
- whether quantities can be fractional.

# 49. Production Example — Reconciliation

A reconciliation system may compare:

```text
invoice totals
payment totals
ledger totals
```

Each total must be aggregated from a clearly matching population and grain.

A robust reconciliation report often calculates:

```text
invoice_total
payment_total
ledger_total
payment_difference
ledger_difference
```

The system should not “fix” discrepancies with rounding or `DISTINCT` unless that behavior is part of an explicit business rule.

# 50. Testing Aggregation Queries

Aggregation tests should contain adversarial data.

At minimum include:

```text
0 child rows
1 child row
multiple child rows
NULL values
duplicate numeric values
multiple independent child tables
same timestamps
boundary timestamps
multiple tenants
multiple currencies
cancelled states
```

Example fixture designed to expose join multiplication:

```text
order 1
  items: 3
  payments: 2
```

If expected totals are not preserved, the test should fail.

---

# 51. Property-Based Thinking

Good aggregate tests can assert invariants rather than only fixed outputs.

For example:

```text
sum of branch totals = company total
```

provided all branches and filters represent the same population.

Likewise:

```text
completed + cancelled + pending = total
```

only if statuses are mutually exclusive and exhaustive.

These assumptions must be explicit. Otherwise the identity may be false by design.

# 52. Aggregation Review Checklist

Before merging an aggregate query, ask:

### Semantics
- What is the source population?
- What is one input row?
- What is one output row?
- What exactly does each metric mean?

### Nulls
- Should empty input mean `NULL` or `0`?
- Are nullable columns being counted intentionally?

### Joins
- Is there any one-to-many join?
- Are there multiple independent many-side joins?
- Can row multiplication inflate an aggregate?

### Time
- What timezone defines the bucket?
- Are interval boundaries correct?

### Finance
- What currency is being aggregated?
- When does rounding occur?
- Are refunds/voids/cancellations included?

### Performance
- How many rows reach the aggregate?
- What aggregate strategy is used?
- Is there sort/hash spilling?
- Is the query repeatedly run at high concurrency?

### Security
- Is tenant scope enforced?
- Could a missing predicate leak cross-tenant metrics?

### Reliability
- What happens on empty data?
- What happens when a group disappears?
- Are downstream API types compatible with `NULL`?

# 53. Aggregation Debugging Framework

When a number is wrong, do not immediately change the aggregate function.

Use this sequence:

```text
1. Define expected metric
2. Define expected grain
3. Count source rows
4. Inspect joins before aggregation
5. Compare row counts after each join
6. Isolate each child relation
7. Verify NULL behavior
8. Verify filters
9. Verify time boundaries
10. Compare against independent calculation
11. Run EXPLAIN ANALYZE
12. Add regression test
```

A powerful debugging technique is to materialize or inspect intermediate relations before the final aggregate.

---

# 54. The Grain Ledger Technique

For difficult SQL, write this beside the query:

```text
Relation             Grain
--------------------------------------
orders               1 / order
order_items          N / order
payments             N / order
customers             1 / customer
item_totals           1 / order
payment_totals        1 / order
final result          1 / customer
```

Whenever the query changes, update the ledger.

This is a practical expert habit because it converts invisible cardinality assumptions into explicit engineering documentation.

# 55. When to Use Aggregation vs Other Techniques

## Use aggregation when

The question naturally reduces many rows into a summary.

Examples:

```text
revenue by branch
orders by customer
sales by month
```

## Use a window function when

You need the aggregate result while preserving row detail.

## Use a subquery/CTE when

You need multiple semantic aggregation layers or isolated populations.

## Use a materialized view when

Repeated expensive aggregation can be precomputed with acceptable freshness semantics.

## Use a summary table when

The business process requires explicitly maintained precomputed state.

The right choice depends on freshness, write/read ratio, correctness guarantees, and operational complexity.

# 57. Expert “Why?” Drills

You should be able to answer these without memorized syntax.

### Why does `COUNT(*)` differ from `COUNT(id)` after a `LEFT JOIN`?

Because the outer join preserves the parent row while the child columns become `NULL`; `COUNT(*)` counts the preserved row while `COUNT(id)` ignores the `NULL` child identifier.

### Why can a correct `SUM()` produce a wrong business result?

Because the mathematical reduction can be correct over the wrong population or wrong grain.

### Why is `DISTINCT` frequently a symptom rather than a fix?

Because it can remove duplicate output/value combinations without correcting the relational path that caused row multiplication.

### Why does pre-aggregation often improve both correctness and performance?

It establishes a controlled grain before joining and can reduce intermediate cardinality.

### Why does output row count tell you little about aggregate cost?

Because the expensive work may be scanning, joining, grouping, hashing, sorting, or spilling millions/billions of input rows to produce a small result.

# 61. Expert Summary

Aggregation is fundamentally a **relational-shape problem** before it is a function-selection problem.

Remember the sequence:

```text
Population
   ↓
Input grain
   ↓
Joins
   ↓
Grouping grain
   ↓
Aggregate definition
   ↓
NULL / empty semantics
   ↓
Business semantics
   ↓
Physical execution
   ↓
Performance
   ↓
Validation
```

The most important rule in this chapter is:

> **A mathematically correct aggregate over the wrong relation is still a wrong result.**

And the second:

> **Never trust a reporting number until you can explain its population, grain, filters, cardinality, and business meaning.**
