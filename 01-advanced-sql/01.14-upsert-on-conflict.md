# 01.14 — UPSERT / ON CONFLICT

> **Phase 01 — Advanced SQL**  
> **Topic:** Atomic insert-or-update semantics, conflict arbitration, idempotent writes, and concurrency-safe state transitions  
> **Target mastery:** L0–L7, with production work targeting L6–L7

---

## 1. Chapter Objective

This chapter establishes a production-grade mental model for PostgreSQL UPSERTs. The goal is not merely to memorize:

```sql
INSERT ... ON CONFLICT ...
```

The goal is to reason about a write as a **concurrency-sensitive state transition**:

```text
Incoming Event
     │
     ▼
Candidate Row
     │
     ▼
Conflict Arbiter
(unique index / constraint)
     │
 ┌───┴───────────────┐
 ▼                   ▼
No Conflict       Conflict
 │                   │
INSERT            DO NOTHING
 │                   │
 │                or DO UPDATE
 └──────────┬────────┘
            ▼
        New State
            │
            ▼
       RETURNING
            │
            ▼
      API / Event / Job
```

A correct UPSERT design must answer:

1. What makes two records the **same logical entity**?
2. Which unique constraint/index is the **authoritative arbiter**?
3. What happens when two writers arrive concurrently?
4. Is the operation actually **idempotent**?
5. Should a conflict overwrite data, merge fields, ignore the input, or reject it?
6. What happens when the incoming batch itself contains duplicates?
7. Does the update create a new logical state or merely rewrite an identical value?
8. Which values belong to the existing row versus the proposed `EXCLUDED` row?
9. Can partial indexes, triggers, RLS, or generated values change the result?
10. Can the operation be safely retried after a timeout?

# 2. Precise Definitions

## 2.1 Simple definition

**UPSERT** means: insert a row when no relevant conflict exists; otherwise update an existing conflicting row.

In PostgreSQL this is expressed with `INSERT ... ON CONFLICT DO UPDATE`.

## 2.2 Engineering definition

An UPSERT is a database-enforced state transition whose decision boundary is a unique or exclusion-related constraint/index conflict, rather than an application-side pre-check.

## 2.3 Expert definition

A production UPSERT is an **atomic conflict-arbitrated write** in which a candidate row is checked against an appropriate non-deferrable uniqueness arbiter, and PostgreSQL guarantees an insert-or-update outcome for each candidate row unless an independent error occurs. The correctness of the design therefore depends on the semantics and ownership of the conflict arbiter, the update expression, concurrency model, transaction boundary, and retry contract.

PostgreSQL 18 documents `ON CONFLICT DO UPDATE` as guaranteeing an atomic `INSERT` or `UPDATE` outcome, including under high concurrency. citeturn343089search0

# 3. Why UPSERT Exists

The classic naive pattern is:

```sql
SELECT id
FROM users
WHERE email = 'alice@example.com';

-- if not found
INSERT INTO users(email)
VALUES ('alice@example.com');
```

This looks reasonable in single-threaded code.

Under concurrency:

```text
Transaction A                     Transaction B
------------                      ------------
SELECT → not found                SELECT → not found
        │                                  │
        ▼                                  ▼
INSERT                              INSERT
        │                                  │
        └──────────── race ────────────────┘
```

If `email` is unique, one writer will eventually conflict; if the application handles that conflict correctly, the invariant survives. But the read-then-insert pattern itself is not an atomic logical operation.

UPSERT moves the race-sensitive decision into one database statement:

```sql
INSERT INTO users (email)
VALUES ('alice@example.com')
ON CONFLICT (email)
DO UPDATE
SET updated_at = now();
```

The unique index is now the **authority** that decides identity.

---

# 4. First Principles: Identity Before UPSERT

The most important question is not:

> “How do I write the UPSERT?”

It is:

> **“What proves that these two rows represent the same entity?”**

Example:

```text
Customer identity = email?
Customer identity = tenant_id + external_customer_id?
Customer identity = phone?
```

For a multi-tenant application, this is usually:

```sql
UNIQUE (tenant_id, external_customer_id)
```

not:

```sql
UNIQUE (external_customer_id)
```

The UPSERT can only be as correct as the uniqueness model behind it.

---

# 5. The Conflict Arbiter

PostgreSQL can use unique-index inference or an explicit constraint name.

Typical form:

```sql
INSERT INTO accounts (email, name)
VALUES ('alice@example.com', 'Alice')
ON CONFLICT (email)
DO UPDATE
SET name = EXCLUDED.name;
```

Or:

```sql
ON CONFLICT ON CONSTRAINT accounts_email_key
DO UPDATE ...
```

PostgreSQL supports inference using indexed columns/expressions and an optional predicate. Only appropriate non-deferrable unique constraints/indexes can act as arbiters for `ON CONFLICT DO UPDATE`. citeturn343089search0

### Expert rule

**The conflict target is not merely syntax. It defines the identity boundary of the operation.**

---

# 6. Unique Index vs Business Meaning

Suppose:

```sql
CREATE UNIQUE INDEX users_email_key
ON users (lower(email));
```

Then this may be the real identity rule:

```text
ALICE@example.com
alice@example.com
Alice@Example.com
        ↓
 same logical identity
```

A correct UPSERT may therefore be:

```sql
INSERT INTO users (email, name)
VALUES ('Alice@Example.com', 'Alice')
ON CONFLICT ((lower(email)))
DO UPDATE
SET name = EXCLUDED.name;
```

The important concept is **identity through the same expression enforced by the unique index**.

---

# 7. `EXCLUDED` — The Proposed Row

Inside `DO UPDATE`:

```sql
EXCLUDED.column_name
```

represents the row proposed for insertion that encountered the conflict.

Suppose the table contains:

```text
id | email              | name  | login_count
---+--------------------+-------+------------
42 | alice@example.com  | Alice | 10
```

Incoming data:

```text
email              | name   | login_count
--------------------+--------+------------
alice@example.com  | Alicia | 1
```

Then:

```sql
DO UPDATE
SET name = EXCLUDED.name,
    login_count = users.login_count + 1;
```

means:

```text
existing row → users.column
incoming row  → EXCLUDED.column
```

The names must not be mentally reversed.

---

# 8. Existing State vs Incoming State

An UPSERT often performs a merge:

```text
Existing State       Proposed State
      │                    │
      └────────┬───────────┘
               ▼
         Merge Function
               │
               ▼
          New State
```

Example:

```sql
INSERT INTO inventory (tenant_id, sku, quantity)
VALUES (10, 'SKU-100', 5)
ON CONFLICT (tenant_id, sku)
DO UPDATE
SET quantity = inventory.quantity + EXCLUDED.quantity;
```

This is fundamentally different from:

```sql
SET quantity = EXCLUDED.quantity;
```

The first means **increment**.

The second means **replace**.

Never choose between them based on coding style. Choose based on the domain state transition.

---

# 9. UPSERT as a State-Transition Function

A useful abstract model is:

```text
new_state = merge(existing_state, incoming_state)
```

Examples:

### Replace

```text
merge(old, incoming) = incoming
```

### Counter accumulation

```text
merge(old, incoming) = old + incoming
```

### Max watermark

```text
merge(old, incoming) = greatest(old, incoming)
```

### Last-write-wins timestamp

```text
merge(old, incoming) = incoming if incoming.updated_at > old.updated_at
```

### Never regress status

```text
merge(old, incoming) = highest_allowed_state(old, incoming)
```

This turns the UPSERT from a generic SQL trick into an explicit domain function.

# 10. `DO NOTHING`

Use:

```sql
ON CONFLICT (...) DO NOTHING;
```

when the business rule is:

> “The first valid writer owns this key; later duplicates are ignored.”

Example:

```sql
INSERT INTO idempotency_keys (key, response_hash)
VALUES ($1, $2)
ON CONFLICT (key)
DO NOTHING;
```

This is particularly useful for:

- idempotency keys
- deduplication
- event ingestion
- immutable facts
- exactly-once-effect boundaries
- claim-once workflows

But `DO NOTHING` does **not** mean “the row definitely already existed from my transaction's normal snapshot.” Under Read Committed, PostgreSQL documents that `DO NOTHING` can skip insertion because of another transaction whose effects were not yet visible to the command snapshot. citeturn343089search2

---

# 11. `DO UPDATE`

Basic form:

```sql
INSERT INTO products (sku, price)
VALUES ('P100', 599.00)
ON CONFLICT (sku)
DO UPDATE
SET price = EXCLUDED.price;
```

This is appropriate when the incoming value is authoritative.

It is **not** appropriate if incoming values are stale.

That distinction matters enormously in synchronization systems.

---

# 12. Preventing Stale-Write Regression

Suppose two sources send updates:

```text
Event A: version = 10
Event B: version = 9
```

The system must not allow event B to overwrite version 10.

Use a condition:

```sql
INSERT INTO customer_snapshot (
    customer_id,
    version,
    payload
)
VALUES ($1, $2, $3)
ON CONFLICT (customer_id)
DO UPDATE
SET version = EXCLUDED.version,
    payload = EXCLUDED.payload
WHERE customer_snapshot.version < EXCLUDED.version;
```

This expresses:

```text
update only if incoming state is newer
```

PostgreSQL evaluates the `WHERE` condition after identifying the conflict; rows that fail the condition are locked but are not updated and are not returned by `RETURNING`. citeturn343089search0

### Critical distinction

```text
Conflict found
      ↓
Candidate target identified
      ↓
Locking can occur
      ↓
DO UPDATE WHERE condition evaluated
      ↓
Update may or may not happen
```

Therefore:

> **A conflict does not guarantee that an update occurs.**

---

# 13. Idempotency

A genuinely idempotent API operation has the property:

```text
apply(request)
apply(request)
apply(request)
```

and reaches the same intended business state as one successful application.

UPSERT helps implement this, but **UPSERT itself does not automatically make an operation idempotent**.

Bad example:

```sql
DO UPDATE
SET balance = accounts.balance + EXCLUDED.balance;
```

Retrying the same message doubles the increment.

Potentially idempotent pattern:

```sql
INSERT INTO payments (payment_id, amount)
VALUES ($1, $2)
ON CONFLICT (payment_id)
DO NOTHING;
```

The payment identifier becomes the deduplication key.

### Expert distinction

```text
Atomicity ≠ Idempotency
Uniqueness ≠ Idempotency
UPSERT ≠ Idempotency
```

UPSERT can be the mechanism that enforces an idempotency boundary when the data model is designed around a stable operation identity.

---

# 14. The Application Pre-Check Anti-Pattern

Avoid:

```sql
SELECT 1 FROM users WHERE email = $1;
```

then:

```text
if exists:
    UPDATE
else:
    INSERT
```

Why it fails:

- race conditions
- more round trips
- larger transaction windows
- more application logic
- harder retry semantics
- duplicated identity rules

Prefer a database-enforced invariant.

---

# 15. UPSERT Under Concurrency

Consider two transactions:

```text
T1: INSERT key = K
T2: INSERT key = K
```

A unique index is the arbiter.

One transaction's conflicting write can cause the other to wait and then determine its alternative path. PostgreSQL explicitly documents special Read Committed behavior for `ON CONFLICT`, including an atomic insert-or-update outcome for `DO UPDATE` even when the conflicting transaction's row version was not visible to the original command snapshot. citeturn343089search2

Mental model:

```text
           candidate K
               │
               ▼
        Unique index arbiter
               │
      ┌────────┴─────────┐
      │                  │
  available          conflicting
      │                  │
      ▼                  ▼
   INSERT          lock / resolve
                         │
                         ▼
                     UPDATE
```

Do not think of the UPSERT as a magical non-blocking command. Unique conflicts can involve waiting and locking.

---

# 16. The `WHERE` Trap in `DO UPDATE`

Example:

```sql
INSERT INTO users (email, version, payload)
VALUES ($1, $2, $3)
ON CONFLICT (email)
DO UPDATE
SET version = EXCLUDED.version,
    payload = EXCLUDED.payload
WHERE users.version < EXCLUDED.version;
```

A common incorrect assumption is:

> “If `ON CONFLICT` matched, `RETURNING` will always contain a row.”

Not necessarily.

If the condition is false:

```text
conflict → target locked → WHERE false → no update → no RETURNING row
```

PostgreSQL explicitly documents this behavior. citeturn343089search0

Production implication: API code must distinguish:

```text
inserted
updated
not applied because stale
```

rather than reducing all outcomes to “success.”

---

# 17. Batch UPSERTs

Example:

```sql
INSERT INTO inventory (tenant_id, sku, quantity)
VALUES
  (1, 'A', 5),
  (1, 'B', 10),
  (1, 'C', 20)
ON CONFLICT (tenant_id, sku)
DO UPDATE
SET quantity = EXCLUDED.quantity;
```

This is efficient and reduces round trips.

But there is a crucial deterministic-statement constraint: PostgreSQL does not allow one `INSERT ... ON CONFLICT DO UPDATE` statement to affect the same existing row more than once. If proposed rows duplicate the arbiter key, a cardinality violation can be raised. citeturn343089search0

Bad batch:

```text
(tenant=1, sku=A, quantity=5)
(tenant=1, sku=A, quantity=7)
```

Normalize/deduplicate the source first when necessary:

```sql
INSERT INTO inventory AS i (tenant_id, sku, quantity)
SELECT tenant_id, sku, sum(quantity)
FROM incoming_inventory
GROUP BY tenant_id, sku
ON CONFLICT (tenant_id, sku)
DO UPDATE
SET quantity = i.quantity + EXCLUDED.quantity;
```

Now the source has one row per logical target key.

---

# 18. UPSERT + Aggregation = Important Pipeline

For event ingestion:

```text
Raw events
   ↓
Deduplicate / canonicalize
   ↓
Aggregate by logical key
   ↓
UPSERT
```

Do not blindly feed a many-row event stream into an UPSERT when multiple events can target the same logical row.

The correct grain may be:

```text
one row per tenant + SKU
```

rather than:

```text
one row per event
```

---

# 19. Partial Unique Indexes

Suppose only active usernames must be unique:

```sql
CREATE UNIQUE INDEX users_active_username_key
ON users (tenant_id, username)
WHERE deleted_at IS NULL;
```

Then conflict inference may need the predicate:

```sql
ON CONFLICT (tenant_id, username)
WHERE deleted_at IS NULL
DO UPDATE ...
```

This is an advanced identity rule:

```text
same key
+ same conflict predicate
= same conflict domain
```

Be extremely careful with soft-delete models. The business rule may actually require:

```text
one active row per tenant + username
```

not global uniqueness.

PostgreSQL's documentation describes unique-index inference with optional predicates and notes that non-partial unique indexes satisfying the other criteria can also be inferred. citeturn343089search0

---

# 20. `ON CONFLICT ON CONSTRAINT`

Example:

```sql
ON CONFLICT ON CONSTRAINT accounts_pkey
DO NOTHING;
```

This explicitly names the arbiter constraint.

However, PostgreSQL notes that unique-index inference is often preferable because it can continue to work when the underlying index is replaced by an equivalent overlapping index, such as during index replacement workflows. citeturn343089search0

### Engineering rule

Use:

```text
index inference → when you want structural resilience
constraint name → when explicit constraint identity is itself meaningful
```

---

# 21. UPSERT and Triggers

Triggers execute within the same transaction as the triggering statement.

For an `INSERT ... ON CONFLICT DO UPDATE`, PostgreSQL documents that row-level `BEFORE INSERT` and `BEFORE UPDATE` triggers can both participate, and statement-level trigger ordering has specific semantics. Changes made by `BEFORE INSERT` triggers can also affect `EXCLUDED` values. citeturn343089search3

Therefore, when debugging:

```sql
EXCLUDED.price
```

is not necessarily identical to the raw value in the application's request.

Ask:

```text
Application value
   ↓
BEFORE INSERT transformation?
   ↓
Candidate row
   ↓
Conflict
   ↓
BEFORE UPDATE transformation?
   ↓
Final stored row
```

Triggers make hidden state transitions possible, so UPSERT-heavy systems require strong observability and documentation.

# 22. UPSERT + `RETURNING`

PostgreSQL 18 supports old/new value references in `RETURNING`.

Example:

```sql
INSERT INTO counters (key, value)
VALUES ('a', 1)
ON CONFLICT (key)
DO UPDATE
SET value = counters.value + EXCLUDED.value
RETURNING OLD.value AS old_value,
          NEW.value AS new_value;
```

This is particularly valuable for APIs, auditing, and event generation.

The current PostgreSQL 18 `INSERT` documentation explicitly documents `OLD` and `NEW` in `RETURNING`, including for `ON CONFLICT DO UPDATE`. citeturn343089search0

# 23. Detecting Insert vs Update

A production API may need to know whether a request created a record or modified an existing one.

A common PostgreSQL 18 pattern is to return old/new values:

```sql
RETURNING OLD.id,
          NEW.id,
          OLD.updated_at,
          NEW.updated_at;
```

You must design the result contract carefully.

Possible API result:

```json
{
  "status": "updated",
  "id": 42,
  "oldVersion": 7,
  "newVersion": 8
}
```

Do not force every UPSERT into a boolean `success` response if the downstream workflow depends on the transition type.

---

# 24. UPSERT for Multi-Tenant ERP Data

A realistic ERP identity might be:

```sql
UNIQUE (tenant_id, branch_id, external_reference)
```

Then:

```sql
INSERT INTO invoices (
    tenant_id,
    branch_id,
    external_reference,
    total_amount,
    status
)
VALUES ($1, $2, $3, $4, 'posted')
ON CONFLICT (tenant_id, branch_id, external_reference)
DO UPDATE
SET total_amount = EXCLUDED.total_amount,
    status = EXCLUDED.status;
```

### Security invariant

The tenant boundary belongs in the identity key when records must be isolated by tenant.

Bad:

```sql
UNIQUE (external_reference)
```

when two tenants can legitimately use the same reference.

Good:

```sql
UNIQUE (tenant_id, external_reference)
```

The database constraint itself becomes part of tenant isolation.

---

# 25. Financial Systems: UPSERT Can Be Dangerous

Do not use mutable UPSERT semantics for immutable ledger facts unless the domain explicitly allows correction.

For a ledger:

```text
Transaction 1001
Transaction 1002
Transaction 1003
```

replacing a historical fact can destroy auditability.

Prefer:

```text
immutable event/fact
        ↓
correction / reversal event
```

rather than:

```text
existing financial row
        ↓
UPSERT overwrites history
```

UPSERT is usually much safer for:

- current balance snapshots
- derived summaries
- exchange-rate caches
- integration state
- synchronization cursors
- reference data

than for immutable accounting facts.

---

# 26. Temporal / Versioned Data

For temporal snapshots:

```sql
INSERT INTO product_snapshot (product_id, version, payload)
VALUES ($1, $2, $3)
ON CONFLICT (product_id)
DO UPDATE
SET version = EXCLUDED.version,
    payload = EXCLUDED.payload
WHERE product_snapshot.version < EXCLUDED.version;
```

This creates a monotonic version invariant:

```text
version_new >= version_old
```

But remember the difference between:

```text
current state table
```

and:

```text
historical event table
```

Do not accidentally turn the latter into the former.

---

# 27. Compare-and-Set Thinking

An advanced UPSERT can implement optimistic concurrency:

```sql
INSERT INTO documents (id, version, body)
VALUES ($1, $2, $3)
ON CONFLICT (id)
DO UPDATE
SET version = EXCLUDED.version,
    body = EXCLUDED.body
WHERE documents.version = EXCLUDED.version - 1;
```

This is conceptually:

```text
IF current_version = expected_version
THEN
    write new state
ELSE
    reject transition
```

This is closely related to compare-and-swap patterns in concurrent systems.

The database becomes the concurrency gate.

---

# 28. UPSERT vs MERGE

PostgreSQL 18 supports both `ON CONFLICT` and the SQL-standard `MERGE` command.

Use `ON CONFLICT` when the core problem is:

```text
insert unless a uniqueness conflict occurs
```

Use `MERGE` when the problem is a broader conditional synchronization problem involving matched/unmatched source and target rows and potentially different actions.

Do not choose `MERGE` merely because it looks more expressive.

Decision rule:

```text
Unique-conflict semantics      → ON CONFLICT
General source-target sync    → MERGE
Single-row atomic identity    → ON CONFLICT often simpler
Complex multi-action sync     → MERGE may be clearer
```

PostgreSQL's transaction-isolation documentation notes that `MERGE` resembles an insert/update combination but does not provide the same guarantee that either an insert or update will occur. citeturn343089search2

---

# 29. RLS and UPSERT

Row-level security adds another layer of correctness.

PostgreSQL documents specific `INSERT ... ON CONFLICT` policy behavior: proposed rows can be checked by `INSERT` policies even when they eventually follow the conflict path, and the `DO UPDATE` path is subject to applicable policies for the existing and new row. citeturn343089search1

For a multi-tenant system, verify:

```text
INSERT policy
      +
UPDATE policy
      +
conflict target
      +
application tenant context
      ↓
complete isolation model
```

A correct unique key does not replace RLS, and RLS does not replace correct uniqueness.

---

# 30. Privileges

An UPSERT is not necessarily equivalent to a simple INSERT privilege.

PostgreSQL requires appropriate privileges for both the insert side and the update side, plus `SELECT` privilege on columns read through the conflict target, expressions, conditions, or `RETURNING`. citeturn343089search0

This matters when a restricted database role suddenly gets:

```text
INSERT works
but UPSERT fails
```

The failure may be privilege-related rather than SQL-related.

# 31. AI / Vibe-Coding Failure Modes

## Failure 1 — Read before write

AI generates:

```text
SELECT → if exists UPDATE → else INSERT
```

### Problem
Race window.

### Correct mental model
Let the database's uniqueness mechanism arbitrate identity.

---

## Failure 2 — Wrong conflict key

AI assumes:

```sql
ON CONFLICT (email)
```

but business identity is:

```sql
(tenant_id, external_id)
```

### Problem
Cross-tenant collisions or incorrect updates.

---

## Failure 3 — Replace instead of merge

AI writes:

```sql
SET quantity = EXCLUDED.quantity
```

for an additive inventory event.

### Problem
Lost increments.

---

## Failure 4 — Increment on retry

AI writes:

```sql
SET balance = balance + EXCLUDED.amount
```

without an idempotency key.

### Problem
Repeated delivery changes business state repeatedly.

---

## Failure 5 — Assuming `DO UPDATE WHERE` still returns the row

### Problem
No returned row may mean “stale and intentionally not applied,” not “query failed.”

---

## Failure 6 — Duplicate source keys

AI bulk-loads duplicate candidate rows against one arbiter key.

### Problem
A deterministic UPSERT can fail with a cardinality violation instead of applying the same existing row multiple times. citeturn343089search0

---

## Failure 7 — Forgetting triggers

AI compares raw input against `EXCLUDED` and assumes they are identical.

### Problem
`BEFORE INSERT` trigger changes can affect the excluded values. citeturn343089search3

# 32. Production Failure Scenarios

## Scenario A — Duplicate customer creation

**Symptom:** duplicate signup requests intermittently create conflicts.

**Investigation:**

1. Inspect uniqueness definition.
2. Inspect application pre-checks.
3. Identify concurrent request behavior.
4. Confirm `ON CONFLICT` target.
5. Confirm retry semantics.

**Root cause pattern:** split identity logic between application and database.

**Fix:** one authoritative uniqueness invariant + atomic write.

---

## Scenario B — Inventory loses updates

**Symptom:** two concurrent stock increments result in one increment.

**Likely root cause:**

```sql
quantity = EXCLUDED.quantity
```

instead of:

```sql
quantity = inventory.quantity + EXCLUDED.quantity
```

This is a **state-transition bug**, not merely a syntax bug.

---

## Scenario C — Event replay duplicates money

**Symptom:** the same payment event increases a financial snapshot twice.

**Root cause:** additive UPSERT without a durable operation identity.

**Fix:** store the event/payment ID under a uniqueness constraint and separate immutable fact ingestion from derived-state updates.

---

## Scenario D — Stale integration overwrites fresh state

**Symptom:** newer data disappears after an integration retry.

**Root cause:** unconditional `DO UPDATE`.

**Fix:** compare version/timestamp/watermark in the conflict `WHERE` condition.

---

## Scenario E — Batch sync fails unexpectedly

**Symptom:** one large UPSERT raises a cardinality violation.

**Root cause:** candidate rows contain duplicate arbiter keys.

**Fix:** canonicalize and deduplicate source rows before the UPSERT.

# 34. Testing Strategy

## Unit-level

Test:

```text
insert when absent
update when present
DO NOTHING
stale update rejection
NULL behavior
partial-key behavior
```

## Concurrency-level

Run:

```text
N concurrent writers
same business key
same tenant
same operation
```

Verify invariants:

```text
row count = 1
unique key preserved
expected final value
no lost update
```

## Retry-level

Execute the same request repeatedly.

Ask:

```text
Does final state equal exactly one application?
```

## Failure-level

Inject:

- transaction abort
- connection timeout after commit
- duplicate batch keys
- stale version
- trigger mutation
- permission failure
- RLS denial
- concurrent conflicting writes

# 35. EXPLAIN / Performance Reasoning

UPSERT performance is not determined by the `INSERT` keyword alone.

The conflict path depends critically on the arbiter index.

Think:

```text
Incoming row
   ↓
unique-index lookup
   ↓
conflict decision
   ↓
possible row locking
   ↓
possible UPDATE
   ↓
index/table/WAL work
```

Important performance drivers:

- arbiter index size
- cache residency
- hot-key contention
- row width
- number of indexes maintained
- update frequency
- trigger cost
- WAL volume
- batch size
- lock waits

For hot keys, a syntactically elegant UPSERT can become a concurrency bottleneck.

---

# 36. Hot-Key Contention

Consider:

```sql
ON CONFLICT (account_id)
DO UPDATE
SET balance = balance + EXCLUDED.delta;
```

If one `account_id` receives thousands of writes per second, all writers may contend around the same logical row.

The problem is no longer:

```text
“Is the SQL correct?”
```

It becomes:

```text
“Can this state representation sustain the workload?”
```

Potential architectural alternatives include:

```text
append events
      ↓
periodic aggregation
      ↓
current snapshot
```

or sharding the write stream by a more granular key when domain semantics permit it.

Never solve a hot-key problem by blindly adding retries.

---

# 37. UPSERT and Network Efficiency

Instead of:

```text
SELECT
UPDATE/INSERT
SELECT again
```

a single statement can often produce the final state directly through `RETURNING`.

This can reduce:

- application round trips
- transaction duration
- race windows
- duplicated application logic

But fewer round trips do not automatically mean less database work.

Always measure.

---

# 38. Transaction Boundary

UPSERT is atomic at the statement level, but your **business operation** may span multiple statements.

Example:

```text
UPSERT inventory
      ↓
insert audit row
      ↓
publish outbox event
```

If these must succeed together, they belong in an appropriate transaction boundary.

A correct UPSERT cannot make unrelated statements atomic by itself.

---

# 39. UPSERT + Transactional Outbox

A common production pattern:

```sql
BEGIN;

INSERT INTO orders (...)
VALUES (...)
ON CONFLICT (external_id)
DO UPDATE
SET ...
RETURNING ...;

INSERT INTO outbox (...)
VALUES (...);

COMMIT;
```

The important question is:

> What event corresponds to the actual state transition?

An update that does not happen because its `WHERE` condition is false should generally not publish an event claiming that the state changed.

---

# 40. Migration Engineering

Changing an UPSERT's conflict target can change business identity.

Example:

```text
OLD
UNIQUE (email)

NEW
UNIQUE (tenant_id, email)
```

This is not merely an index migration.

It changes the semantics of:

```text
who conflicts with whom
```

Migration checklist:

```text
model invariant
→ identify existing duplicates
→ backfill / reconcile
→ add replacement unique index safely
→ update application writes
→ verify conflict behavior
→ remove obsolete invariant
```

Be especially careful when replacing unique indexes concurrently; PostgreSQL warns that `INSERT ... ON CONFLICT` may unexpectedly encounter a unique violation while a unique index is being built/reindexed concurrently. citeturn343089search0

---

# 41. Decision Framework

Use `DO NOTHING` when:

```text
first writer wins
and duplicates are harmless/expected
```

Use unconditional `DO UPDATE` when:

```text
incoming state is authoritative
```

Use conditional `DO UPDATE ... WHERE` when:

```text
incoming state must satisfy a freshness / ownership rule
```

Use aggregation before UPSERT when:

```text
many input rows can target one logical key
```

Use an idempotency key when:

```text
same operation may be retried
```

Use immutable events when:

```text
historical facts must never be overwritten
```

Consider `MERGE` when:

```text
source-target synchronization requires multiple conditional actions
```

# 46. Anti-Pattern Catalog

| Anti-pattern | Failure | Better approach |
|---|---|---|
| Read-then-insert | Race | Atomic `ON CONFLICT` |
| Wrong conflict key | Incorrect identity | Align unique invariant with domain identity |
| Blind overwrite | Lost state | Explicit merge function |
| Additive retry without key | Double effect | Idempotency key |
| Duplicate source keys | Cardinality violation | Deduplicate/aggregate first |
| Unconditional last-write | Stale regression | Version/timestamp condition |
| Mutable ledger facts | Audit corruption | Append-only events/reversals |
| Ignore triggers | Hidden transformations | Trace trigger effects |
| Ignore RLS | Isolation failure | Validate both policies and key design |
| Treat hot keys as SQL-only issue | Throughput collapse | Revisit state architecture |

# 49. Final Expert Takeaways

1. **UPSERT is an atomic state-transition mechanism, not a shortcut for CRUD.**
2. **The unique invariant defines who conflicts with whom.**
3. **`EXCLUDED` is the proposed incoming row, not the existing row.**
4. **Atomicity does not imply idempotency.**
5. **A retry-safe operation needs a stable operation identity or another explicit deduplication strategy.**
6. **`DO UPDATE ... WHERE` can turn a conflict into a deliberate no-op.**
7. **Batch UPSERT source data must respect the target key grain.**
8. **Triggers, RLS, privileges, and generated state can change the effective behavior.**
9. **Hot-key contention is often an architecture problem rather than a SQL-tuning problem.**
10. **Immutable historical facts should not be casually converted into mutable UPSERT state.**
11. **Use `RETURNING` to expose actual database state and state transitions instead of re-reading unnecessarily.**
12. **When reviewing AI-generated UPSERTs, challenge the identity key, merge function, retry behavior, and concurrency assumptions before reviewing syntax.**
