# 01.7 — GROUPING SETS, ROLLUP & CUBE

> **Phase:** 01 — Advanced SQL  
> **Chapter:** 01.7  
> **Level:** Advanced → Expert  
> **Primary skill:** Multi-dimensional aggregation without losing semantic correctness

---

## 1. Chapter Objective

This chapter teaches how PostgreSQL can produce multiple aggregation levels in a single relational operation using:

- `GROUPING SETS`
- `ROLLUP`
- `CUBE`
- `GROUPING()`
- `GROUPING_ID`-style reasoning through grouping-bit patterns

The objective is **not** to memorize syntax. The objective is to understand the dimensional model that makes these constructs correct, predictable, and useful in production analytics.

By the end of this chapter, you should be able to look at a requirement such as:

> “Give revenue by branch, branch + category, category, and grand total in one result.”

and reason from the required **aggregation lattice** to the correct SQL, then validate its cardinality, NULL semantics, performance characteristics, and downstream API/reporting implications.

---

# 2. Why This Chapter Matters

A normal `GROUP BY` produces one grouping level.

```sql
SELECT branch_id, SUM(total_amount)
FROM sales
GROUP BY branch_id;
```

Real analytical workloads often need several levels simultaneously:

```text
Grand Total
├── Region Totals
│   ├── Branch A
│   └── Branch B
└── Region B Totals
    ├── Branch C
    └── Branch D
```

For example:

- total company revenue
- revenue by region
- revenue by region + branch
- revenue by branch + product category
- revenue by month + region
- subtotals and grand totals

A naïve implementation may run many independent queries and merge them in application code. That approach can create extra scans, inconsistent filters, duplicated logic, and difficult-to-audit results.

`GROUPING SETS`, `ROLLUP`, and `CUBE` express the intended aggregation levels directly in SQL.

# 3. Precise Definitions

## 3.1 Simple Definition

### GROUPING SETS
A `GROUP BY` extension that explicitly requests multiple grouping combinations in one query.

### ROLLUP
A shorthand for hierarchical grouping sets that progressively removes grouping dimensions from right to left.

### CUBE
A shorthand for generating grouping sets for every combination of the specified dimensions.

### GROUPING()
A function that tells you whether a particular grouping column is absent from the current grouping level rather than merely containing a NULL data value.

---

## 3.2 Engineering Definition

These constructs transform one input relation into a **set of aggregate result relations at multiple grains** and then combine those relations into one result set.

Conceptually:

```text
Input rows
   ↓
Multiple requested grouping grains
   ↓
Aggregate each grain
   ↓
Combine result rows
   ↓
Annotate grouping level
```

The result is not “one mysterious super-group.” It is a structured collection of aggregation levels represented in a single SQL result.

---

## 3.3 Expert Definition

`GROUPING SETS` provides a declarative representation of an **aggregation lattice subset**.

Given dimensions:

```text
A = region
B = branch
C = category
```

a normal grouping is one node:

```text
(A, B, C)
```

`GROUPING SETS` can request any subset of nodes:

```text
(A, B, C)
(A, B)
(A)
()
```

`ROLLUP(A, B, C)` expands to the hierarchical chain:

```text
(A, B, C)
(A, B)
(A)
()
```

`CUBE(A, B, C)` expands to all combinations:

```text
(A, B, C)
(A, B)
(A, C)
(B, C)
(A)
(B)
(C)
()
```

The empty grouping set `()` represents the grand total.

# 4. First Principles

## 4.1 Aggregation Is About Grain

Before writing SQL, define the output grain.

Examples:

```text
branch
branch + category
region
month + region
month + region + category
company total
```

A grouping set is simply an explicit declaration of which grains you want.

### Core rule

> **Every output row must have a clearly defined grain.**

If you cannot describe the grain of a result row in one sentence, your query is probably not yet understood.

---

## 4.2 Think in Lattices, Not Syntax

For dimensions:

```text
region
branch
category
```

you can visualize the aggregation lattice:

```text
             ()
          /   |   \
       (region) (branch) (category)
       /    \      |      /    \
(region,branch) ...        
              \
      (region,branch,category)
```

You do not always need the complete cube. You often need only a subset.

That is why `GROUPING SETS` is the most general form.

# 6. Baseline GROUP BY

```sql
SELECT region, SUM(amount) AS revenue
FROM sales
GROUP BY region
ORDER BY region;
```

Output grain:

```text
1 row = 1 region
```

You cannot get branch and grand-total rows from this query unless you change the grouping definition.

---

# 7. GROUPING SETS

## 7.1 Basic Example

```sql
SELECT
    region,
    branch,
    SUM(amount) AS revenue
FROM sales
GROUP BY GROUPING SETS (
    (region, branch),
    (region),
    ()
);
```

Requested grains:

```text
(region, branch)
(region)
()
```

The result contains:

- branch-level rows
- region subtotal rows
- grand total row

---

## 7.2 Why `GROUPING SETS` Is Powerful

Suppose the report requires exactly:

```text
region + branch
region
category
grand total
```

Use:

```sql
GROUP BY GROUPING SETS (
    (region, branch),
    (region),
    (category),
    ()
)
```

This expresses the business requirement precisely.

You are not forced to generate irrelevant grouping combinations.

---

# 8. ROLLUP

## 8.1 Basic Semantics

```sql
SELECT
    region,
    branch,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, branch);
```

Equivalent grouping-set intent:

```text
(region, branch)
(region)
()
```

### Important

The order matters.

```sql
ROLLUP(region, branch)
```

is not equivalent to:

```sql
ROLLUP(branch, region)
```

because the hierarchy is determined by the order of dimensions.

---

## 8.2 Business Interpretation

`ROLLUP(region, branch)` naturally models:

```text
Region + Branch
      ↓
Region subtotal
      ↓
Company total
```

This is ideal for hierarchical reports.

Examples:

```text
Year → Month
Region → Branch
Department → Team
Category → Subcategory
```

---

# 9. CUBE

## 9.1 Basic Semantics

```sql
SELECT
    region,
    branch,
    SUM(amount) AS revenue
FROM sales
GROUP BY CUBE (region, branch);
```

Conceptually requests:

```text
(region, branch)
(region)
(branch)
()
```

With three dimensions:

```sql
GROUP BY CUBE (region, branch, category)
```

there are up to:

```text
2^3 = 8 grouping sets
```

For `n` dimensions, the full cube contains:

```text
2^n
```

grouping combinations.

### Scalability warning

This exponential growth matters.

```text
5 dimensions  → 32 grouping sets
10 dimensions → 1024 grouping sets
15 dimensions → 32768 grouping sets
```

A full `CUBE` can become analytically expensive or operationally inappropriate long before the base table itself becomes huge.

---

# 10. GROUPING() — The Critical NULL Distinction

Consider:

```sql
SELECT
    region,
    branch,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP(region, branch);
```

Subtotal rows often show:

```text
region = North
branch = NULL
```

But a real base row might also legitimately have:

```text
branch = NULL
```

These two meanings are completely different.

## 10.1 Use GROUPING()

```sql
SELECT
    region,
    branch,
    GROUPING(region) AS g_region,
    GROUPING(branch) AS g_branch,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP(region, branch);
```

Interpretation:

```text
GROUPING(column) = 1
→ column is not part of this grouping set

GROUPING(column) = 0
→ column participates in this grouping level
```

This is fundamental for reliable reporting.

---

# 11. GROUPING() Is Not a Data-NULL Detector

Bad reasoning:

> “branch IS NULL, so this must be a subtotal.”

Incorrect.

You must distinguish:

```text
Data NULL
vs
Rollup-generated NULL
```

Correct pattern:

```sql
CASE
    WHEN GROUPING(branch) = 1 THEN 'ALL BRANCHES'
    ELSE branch
END
```

This prevents presentation logic from confusing missing data with aggregate hierarchy.

---

# 12. Labeling Aggregation Levels Safely

```sql
SELECT
    CASE
        WHEN GROUPING(region) = 1 THEN 'ALL REGIONS'
        ELSE region
    END AS region_label,
    CASE
        WHEN GROUPING(branch) = 1 THEN 'ALL BRANCHES'
        ELSE branch
    END AS branch_label,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP(region, branch)
ORDER BY
    GROUPING(region),
    region,
    GROUPING(branch),
    branch;
```

Keep the raw grouping columns available when possible. Presentation labels should not destroy semantic information needed by downstream consumers.

---

# 13. Empty Grouping Set `()`

```sql
GROUP BY ()
```

means:

> Treat the complete input as one group.

Example:

```sql
SELECT SUM(amount)
FROM sales;
```

is conceptually equivalent to the grand-total grouping set:

```sql
SELECT SUM(amount)
FROM sales
GROUP BY ();
```

The empty grouping set is particularly important when mixed with other grouping sets.

---

# 14. Combining Ordinary GROUP BY Elements with GROUPING SETS

PostgreSQL allows structured grouping specifications.

For example:

```sql
GROUP BY
    region,
    GROUPING SETS (
        (branch),
        (category),
        ()
    )
```

Conceptually produces:

```text
(region, branch)
(region, category)
(region)
```

This lets you build controlled aggregation families instead of manually enumerating every combination.

---

# 15. GROUPING SETS vs Multiple UNION Queries

A common alternative is:

```sql
SELECT region, branch, SUM(amount)
FROM sales
GROUP BY region, branch

UNION ALL

SELECT region, NULL, SUM(amount)
FROM sales
GROUP BY region

UNION ALL

SELECT NULL, NULL, SUM(amount)
FROM sales;
```

This can produce the desired result, but it duplicates query logic.

Potential problems:

- repeated filters
- repeated joins
- repeated expressions
- inconsistent predicates
- maintenance cost
- more complex auditing
- potentially repeated base-table work

The `GROUPING SETS` form describes the intent directly:

```sql
GROUP BY GROUPING SETS (
    (region, branch),
    (region),
    ()
)
```

### Important performance qualification

Do **not** assume that the grouping-set version is always faster than every hand-written alternative. Query planning, aggregation strategy, indexes, data distribution, memory, and query shape matter. Measure the actual plan.

---

# 16. Aggregation Grain Validation

For every grouping set, write the expected grain before running SQL.

Example:

```text
Grouping set 1 → one row per region + branch
Grouping set 2 → one row per region
Grouping set 3 → one company total
```

Then derive expected cardinality.

If:

```text
5 regions
40 branches
```

you cannot simply assume:

```text
5 × 40 = 200
```

because not every region necessarily contains every branch combination.

The actual row count depends on the distinct combinations present in the data.

---

# 17. Duplicate Semantics

Grouping sets produce rows for distinct groups at each requested grain.

The same dimension value may legitimately appear on several rows because the rows represent different aggregation levels.

For example:

```text
North / N1 / 1000
North / N2 / 1200
North / NULL / 2200
NULL  / NULL / 5400
```

These are not duplicates in the semantic sense.

Applying a careless outer `DISTINCT` can hide a modeling problem instead of fixing it.

---

# 18. Financial Reporting Example

Suppose an ERP needs:

```text
Branch + metal
Branch subtotal
Company total
```

Use:

```sql
SELECT
    branch,
    metal,
    SUM(net_amount) AS net_sales
FROM invoice_lines
WHERE invoice_status = 'POSTED'
GROUP BY ROLLUP (branch, metal);
```

But a production system must also answer:

- Are cancelled invoices excluded?
- Are returns negative rows or separate documents?
- Is tax included?
- Is `net_amount` already normalized to company currency?
- Is the metric sale-date based or posting-date based?
- Does one invoice line represent one economic event?
- Are multiple currencies present?
- Is branch a tenant-local branch or globally unique branch?

`ROLLUP` solves grouping structure, not business-definition ambiguity.

---

# 19. Multi-Tenant ERP Example

Suppose the database stores:

```text
tenant_id
region
branch_id
category
amount
```

A tenant-safe report may require:

```sql
SELECT
    tenant_id,
    region,
    branch_id,
    category,
    SUM(amount) AS amount
FROM sales
WHERE tenant_id = $1
GROUP BY ROLLUP (tenant_id, region, branch_id, category);
```

However, including `tenant_id` as a rollup dimension can create an unwanted global total if the filter is later removed.

A safer reporting design may be:

```sql
WHERE tenant_id = $1
GROUP BY ROLLUP (region, branch_id, category)
```

with tenant identity treated as a fixed filter/context rather than a report hierarchy dimension.

### Security principle

> **Do not rely on a report's grouping structure to provide tenant isolation.**

Tenant isolation must come from the data-access boundary: explicit predicates, secure views, RLS, or another enforced mechanism.

---

# 20. Temporal Reporting

A common hierarchy is:

```text
year
month
```

```sql
SELECT
    EXTRACT(YEAR FROM sold_at) AS year,
    EXTRACT(MONTH FROM sold_at) AS month,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (
    EXTRACT(YEAR FROM sold_at),
    EXTRACT(MONTH FROM sold_at)
);
```

But production systems should usually derive reporting periods consistently rather than duplicating expressions across the query.

For example, use a CTE/subquery or date dimension when business calendars, fiscal months, timezone boundaries, or holiday logic matter.

---

# 21. Timezone Correctness

A timestamp can map to different local dates in different timezones.

Bad:

```sql
GROUP BY sold_at::date
```

when business reporting is defined in a local business timezone but `sold_at` is `timestamptz`.

Better reasoning:

```sql
GROUP BY (sold_at AT TIME ZONE 'Asia/Kolkata')::date
```

The correct timezone must come from the business definition, not from developer convenience.

---

# 22. GROUPING() Bitmask Reasoning

For several grouped columns, you can inspect the grouping-state bits:

```sql
SELECT
    region,
    branch,
    category,
    GROUPING(region)   AS g_region,
    GROUPING(branch)   AS g_branch,
    GROUPING(category) AS g_category,
    SUM(amount) AS revenue
FROM sales
GROUP BY CUBE (region, branch, category);
```

The `GROUPING()` values form a compact description of the current aggregation level.

For example:

```text
0 0 0 → all three dimensions participate
0 0 1 → category rolled up
0 1 1 → branch + category rolled up
1 1 1 → grand total
```

This is extremely useful for:

- report-level identification
- API output shaping
- sorting
- subtotal formatting
- downstream ETL
- debugging

---

# 23. Ordering Results Correctly

Do not assume the generated order is automatically the business-report order.

Use explicit ordering.

Example:

```sql
ORDER BY
    GROUPING(region),
    region,
    GROUPING(branch),
    branch;
```

You can also define a report-level label:

```sql
CASE
    WHEN GROUPING(region) = 1 THEN 3
    WHEN GROUPING(branch) = 1 THEN 2
    ELSE 1
END AS sort_level
```

Then:

```sql
ORDER BY sort_level, region, branch;
```

---

# 24. HAVING with GROUPING SETS

`HAVING` is applied to groups produced by the grouping specification.

Example:

```sql
SELECT
    region,
    branch,
    SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, branch)
HAVING SUM(amount) >= 1000;
```

This condition affects both regular groups and subtotal/grand-total groups.

If the business requirement is:

> “Filter branch-level rows but retain all subtotals,”

you need explicit grouping-aware logic.

Example pattern:

```sql
HAVING
    GROUPING(branch) = 1
    OR SUM(amount) >= 1000
```

This distinction is easy to miss and can silently change report totals.

---

# 25. Conditional Measures with FILTER

Grouping sets can be combined with aggregate filters.

```sql
SELECT
    region,
    branch,
    SUM(amount) AS total_sales,
    SUM(amount) FILTER (WHERE category = 'Gold') AS gold_sales,
    SUM(amount) FILTER (WHERE category = 'Silver') AS silver_sales
FROM sales
GROUP BY ROLLUP (region, branch);
```

This can produce a multi-level report with several measures without duplicating the grouping query.

But every measure must have a clearly defined business population.

---

# 26. The Join Multiplication Trap Still Applies

`ROLLUP` does **not** repair an incorrect join.

Suppose:

```text
customer
  1 → 3 orders
  1 → 4 payments
```

Joining both child tables before aggregation can create:

```text
3 × 4 = 12 rows
```

Then:

```sql
SUM(order_total)
```

can be multiplied incorrectly.

Correct pattern may require pre-aggregation:

```text
orders       → aggregate at customer grain
payments     → aggregate at customer grain
             ↓
         join summaries
             ↓
      grouping sets / rollup
```

The aggregation operator cannot compensate for a wrong relational grain upstream.

---

# 27. Performance Model

The relevant question is not:

> “Is ROLLUP faster?”

The relevant questions are:

```text
How many input rows exist?
How many grouping sets exist?
How many distinct groups exist at each level?
How much memory is required?
Will aggregation spill to disk?
Can PostgreSQL use a sorted strategy?
Can it use hashing?
Can partial aggregation help?
How many result rows are produced?
```

Use evidence.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    region,
    branch,
    SUM(amount)
FROM sales
GROUP BY ROLLUP (region, branch);
```

Do not optimize by syntax folklore.

---

# 28. Hash Aggregation vs Sorted Aggregation

PostgreSQL may choose different aggregation strategies depending on the query and planner estimates.

A plan can involve concepts such as:

```text
HashAggregate
GroupAggregate
Sort
Incremental Sort
Partial Aggregate
Finalize Aggregate
```

Your job is not to force a specific operator by default.

Your job is to understand:

```text
input size
→ grouping cardinality
→ memory requirements
→ sort/hash cost
→ parallel opportunities
→ actual runtime behavior
```

---

# 29. Memory and Spills

Multi-dimensional aggregation can increase memory requirements because multiple grouping states may be maintained.

At large scale, inspect:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
...
```

and relevant server statistics/configuration.

If an analytical aggregation spills, increasing memory may help, but do not automatically raise global memory settings. Understand concurrency first.

A memory increase that makes one query faster can make the system less stable when many such queries run concurrently.

# 30. CUBE Explosion

Consider:

```sql
GROUP BY CUBE (
    tenant,
    region,
    branch,
    category,
    salesperson,
    month,
    payment_method
)
```

Seven dimensions can imply:

```text
2^7 = 128 grouping sets
```

Ten dimensions imply:

```text
1024 grouping sets
```

This can generate a huge output and substantial computation.

### Expert rule

> Use `CUBE` because the business genuinely needs the dimensional combinations, not because it is shorter to type than an intentional `GROUPING SETS` list.

# 31. Choosing Between GROUPING SETS, ROLLUP and CUBE

## Choose GROUPING SETS when

You know exactly which grains are needed.

```text
(region, branch)
(region)
(category)
()
```

## Choose ROLLUP when

The report is hierarchical.

```text
year → month → day
region → branch
category → subcategory
```

## Choose CUBE when

You genuinely need every combination of dimensions.

```text
product × region × channel
```

and the resulting size is acceptable.

# 32. Common Wrong Approaches

## Wrong Approach 1 — Treating subtotal NULL as data NULL

### Your assumption

```text
branch IS NULL → branch is missing
```

### Problem

The NULL may represent a rolled-up dimension.

### Why it fails

You cannot distinguish data absence from aggregation hierarchy.

### Correct mental model

Use `GROUPING(branch)`.

### Production consequence

Reports mislabel subtotals as “Unknown” or accidentally merge different semantic rows.

---

## Wrong Approach 2 — Using CUBE Everywhere

### Your assumption

“CUBE gives the most complete report.”

### Problem

The result space grows exponentially with the number of dimensions.

### Production consequence

Large result sets, high CPU/memory usage, slow dashboards, expensive downstream processing.

---

## Wrong Approach 3 — Trusting Query Result Order

### Your assumption

“PostgreSQL returns rollup rows in hierarchy order.”

### Problem

Without explicit ordering, result order is not a business contract.

### Production consequence

Unstable report rendering and flaky tests.

---

## Wrong Approach 4 — Assuming Grouping Sets Fix Join Duplicates

### Your assumption

“Aggregation will collapse duplicates anyway.”

### Problem

The aggregate sees duplicated input rows and sums the duplicated values.

### Production consequence

Incorrect revenue, inventory, tax, commission, or financial reports.

---

## Wrong Approach 5 — Performing All Report Semantics in Application Code

### Your assumption

“SQL returns raw rows; Node.js can calculate subtotals.”

### Problem

Business logic becomes duplicated across services, pagination becomes difficult, and database filters may no longer apply consistently.

### Better approach

Use SQL for relational aggregation and application code for presentation/business orchestration that truly belongs outside the database.

---

# 33. AI / Vibe-Coding Failure Patterns

AI-generated SQL frequently makes these mistakes:

### Failure A

```sql
GROUP BY CUBE (every_column_in_the_report)
```

because it is syntactically concise.

### Failure B

```sql
COALESCE(branch, 'TOTAL')
```

without checking `GROUPING(branch)`.

### Failure C

Using `DISTINCT` after a wrong aggregation to “remove duplicates.”

### Failure D

Generating several `UNION ALL` queries with slightly different filters.

### Failure E

Returning grouping-set rows to an API without exposing the aggregation level.

### Audit questions

Before accepting AI-generated SQL ask:

```text
What is the grain of every row?
Which grouping sets are intentional?
How are subtotal rows distinguished from real NULLs?
How many result rows can this produce?
What happens when dimensions become high-cardinality?
Is the upstream join grain correct?
What does EXPLAIN say?
```

# 34. Production API Design

Do not expose an ambiguous schema like:

```json
{
  "region": "North",
  "branch": null,
  "revenue": 420000
}
```

because consumers cannot know whether `branch: null` means:

- unknown branch
- no branch
- subtotal
- malformed source data

Prefer explicit semantics:

```json
{
  "region": "North",
  "branch": null,
  "revenue": 420000,
  "aggregationLevel": "REGION"
}
```

or:

```json
{
  "grouping": {
    "region": true,
    "branch": false
  },
  "region": "North",
  "branch": null,
  "revenue": 420000
}
```

The database already exposes grouping semantics. Your API should preserve them rather than forcing clients to infer intent from NULL values.

# 35. Testing Strategy

A serious report should test at least:

## Test 1 — Grand total reconciliation

```text
SUM(detail rows) = grand total
```

when the metric definition makes that mathematically valid.

## Test 2 — Subtotal reconciliation

```text
SUM(branches in region) = region subtotal
```

subject to the same population definition.

## Test 3 — Grouping-state correctness

Verify `GROUPING()` flags for every aggregation level.

## Test 4 — NULL distinction

Insert a legitimate NULL dimension value and verify it is not confused with a subtotal.

## Test 5 — Empty input

Verify expected behavior when no rows match the filter.

## Test 6 — High-cardinality dimension

Test runtime and output size with realistic cardinality.

# 42. Debugging Framework

When a grouping-set report is wrong, debug in this order:

```text
1. Define the metric population
2. Define input grain
3. Validate joins
4. Validate filters
5. Enumerate grouping sets
6. Validate NULL semantics
7. Validate GROUPING() flags
8. Reconcile subtotals
```

# 44. Expert “Why?” Drills

You should be able to answer all of these without memorized syntax.

### Why does `ROLLUP(a,b,c)` include `(a,b)`, `(a)`, and `()`?

Because it represents a hierarchical reduction of dimensions from the full grain toward the grand total.

### Why can `CUBE` become dangerous at high dimension counts?

Because the number of requested grouping combinations grows as `2^n`.

### Why isn't `COALESCE(branch, 'TOTAL')` enough?

Because a real data NULL and a grouping-generated NULL are different semantic states.

### Why can `UNION ALL` sometimes be preferable?

Because explicit separate queries may be easier to reason about or may allow different predicates/strategies for genuinely different populations. The correct choice is workload-dependent; measure and compare.

### Why must aggregation grain be defined before SQL syntax?

Because correctness depends on what one output row represents, not on which grouping keyword was used.
