# 01.1 — SELECT Semantics

> **Phase:** 01 — Advanced SQL  
> **Level:** Foundation → Expert  
> **Primary Goal:** Understand what a PostgreSQL `SELECT` means, how its logical result is formed, why SQL is declarative rather than procedural, and how to reason about correctness, determinism, visibility, performance, and edge cases without relying on trial and error.

---

## 0. Why This Chapter Exists

Most developers learn SQL as a collection of clauses:

```sql
SELECT ...
FROM ...
WHERE ...
GROUP BY ...
ORDER BY ...
LIMIT ...;
```

That is enough to write queries. It is not enough to reason like a database engineer.

A PostgreSQL engineer must be able to answer questions such as:

- What is the conceptual input to `SELECT`?
- Why can a `SELECT` return duplicate rows even when the source table has unique rows?
- Why does `ORDER BY` matter for `LIMIT`, even when the query “usually” returns the same rows?
- Why can a column alias be referenced by `ORDER BY` but not by `WHERE`?
- Why can a query be syntactically valid yet logically wrong?
- What exactly does `DISTINCT` remove?
- Why is `SELECT *` risky in production code?
- What is the difference between the **logical query model** and the **physical execution plan**?
- Why is “SQL runs top-to-bottom” a dangerous mental model?
- How can PostgreSQL legally execute a query in a way that looks different from its written order while returning the same result?
- When does an apparently harmless `LIMIT 20` become nondeterministic?
- How do aliases, expressions, `NULL`, collation, and row identity affect result semantics?
- How should an API endpoint query be designed so that its result is deterministic and stable under growth and concurrency?

This chapter builds the mental model required to answer those questions.

# 2. PostgreSQL's Definition of a Query

PostgreSQL defines a query as the process of retrieving data or the command used to retrieve it. `SELECT` is the SQL command used to specify queries. A general form is:

```sql
[WITH with_queries]
SELECT select_list
FROM table_expression
[sort_specification];
```

A query does not have to read from a table. PostgreSQL can evaluate expressions directly:

```sql
SELECT 3 * 4;

SELECT random();
```

A `FROM` clause can be complex and can contain base tables, joins, subqueries, and other table expressions. citeturn851187view1

This matters because `SELECT` is not fundamentally “a command that loops through a table.” It is a declarative description of a result.

---

# 3. The Most Important Mental Model

Do **not** think:

```text
Read line 1
↓
Execute line 2
↓
Execute line 3
↓
Return line 4
```

Think:

```text
Declare the result you want
        ↓
Define the row source
        ↓
Define which candidate rows qualify
        ↓
Define grouping/aggregation when applicable
        ↓
Define the output shape
        ↓
Define duplicate semantics
        ↓
Define order
        ↓
Define which slice of that ordered result is returned
```

Then separately think:

```text
PostgreSQL Planner
        ↓
Chooses a physical strategy
        ↓
Executor produces the result
```

The written SQL is a **declaration of meaning**. PostgreSQL is free to choose a different physical strategy when that strategy preserves the required semantics.

---

# 4. Written Order vs Logical Processing Order vs Physical Execution

This distinction is one of the most important concepts in SQL.

## 4.1 Written Order

A common query is written as:

```sql
SELECT ...
FROM ...
WHERE ...
GROUP BY ...
HAVING ...
ORDER BY ...
LIMIT ...;
```

This is the syntax the developer writes.

## 4.2 Logical Query Processing

For reasoning purposes, a simplified conceptual model is:

```text
FROM
  ↓
WHERE
  ↓
GROUP BY / aggregation
  ↓
HAVING
  ↓
SELECT output expressions
  ↓
DISTINCT
  ↓
ORDER BY
  ↓
LIMIT / OFFSET / FETCH
```

This is a **semantic model**, not a promise about physical execution.

PostgreSQL's `SELECT` documentation describes the result formation in terms of table expressions, output expressions, duplicate elimination, ordering, and limiting. PostgreSQL can also defer some output-expression evaluation until after sorting and limiting when those expressions do not participate in earlier result-shaping clauses. citeturn833341search1

## 4.3 Physical Execution

The planner may choose strategies such as:

```text
Sequential Scan
Index Scan
Bitmap Scan
Nested Loop
Hash Join
Merge Join
Sort
Top-N behavior
Parallel operators
```

Those choices are execution mechanisms, not SQL semantics.

Example:

```sql
SELECT id
FROM users
WHERE email = 'a@example.com';
```

The semantic request is:

> Return `id` values from `users` for rows where `email` equals the specified value.

PostgreSQL might satisfy this using an index or a sequential scan. Both can be semantically correct.

---

# 5. A `SELECT` Produces a Relation-Like Result

At the conceptual level, a query produces a set/table-shaped result with:

- columns,
- column types,
- column names/labels,
- rows.

Do not confuse this with the mathematical idea of a pure set in every SQL context.

SQL is fundamentally **duplicate-preserving by default**.

Therefore:

```sql
SELECT customer_id
FROM orders;
```

can return:

```text
customer_id
-----------
101
101
101
205
205
```

The query is valid and correct if the source contains those rows.

`SELECT ALL` is the default behavior. `SELECT DISTINCT` explicitly removes duplicate result rows. citeturn833341search1

---

# 6. Row Identity Is Not Automatically Preserved

A frequent beginner assumption is:

> “Every row in the result corresponds one-to-one with a physical row in the table.”

That is not generally true.

Projection can collapse information:

```sql
SELECT status
FROM orders;
```

Many physically distinct rows may produce identical output rows.

Joining can multiply rows:

```sql
SELECT c.id, o.id
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

One customer row can contribute to many result rows.

Aggregation can transform many rows into one group:

```sql
SELECT customer_id, count(*)
FROM orders
GROUP BY customer_id;
```

A result row is therefore a **derived result tuple**, not necessarily a source-row identity.

This idea becomes essential later when we study joins, grouping, windows, `DISTINCT`, and query planning.

---

# 7. The `FROM` Clause Defines the Row Source

A simple query:

```sql
SELECT *
FROM users;
```

starts from `users` as its table expression.

But `FROM` can describe much more than one table:

```sql
FROM users u
JOIN orders o ON o.user_id = u.id
```

or:

```sql
FROM (
    SELECT *
    FROM users
    WHERE active = true
) u
```

or a set-returning/table-producing construct.

The conceptual principle is:

> `FROM` creates the candidate row source to which later relational operations apply.

That is why this is such an important reasoning boundary.

---

# 8. The `WHERE` Clause Filters Candidate Rows

Example:

```sql
SELECT id, email
FROM users
WHERE active = true;
```

Conceptually:

```text
All candidate rows
      ↓
Apply predicate
      ↓
Keep qualifying rows
```

The predicate is not a programming-language `if` statement executed in source-code order by the application. It is part of the declarative query expression.

---

# 9. `WHERE` Is About Qualification, Not Projection

Consider:

```sql
SELECT email AS contact_email
FROM users
WHERE active = true;
```

A common mistake is expecting:

```sql
WHERE contact_email = 'a@example.com'
```

to work simply because `contact_email` appears in the `SELECT` list.

It does not work that way. PostgreSQL documents that an output column name can be referenced in `ORDER BY` and `GROUP BY`, but not in `WHERE` or `HAVING`; those clauses need the input expression instead. citeturn833341search1

Correct:

```sql
SELECT email AS contact_email
FROM users
WHERE email = 'a@example.com';
```

Mental model:

```text
WHERE operates on the query's input-side expressions.
SELECT defines the output-side expressions.
```

---

# 10. Projection: What Does `SELECT` Actually Do?

The select list determines the output columns.

Example:

```sql
SELECT
    id,
    email,
    created_at,
    balance_cents / 100.0 AS balance
FROM accounts;
```

The result has four output expressions:

```text
id
email
created_at
balance
```

The output does not have to mirror the underlying table.

You can:

- select fewer columns,
- rename columns,
- compute expressions,
- call functions,
- construct derived values.

PostgreSQL explicitly allows select-list expressions and calculations over input columns. citeturn851187view1

---

# 11. Why `SELECT *` Is Usually a Poor Production Contract

`SELECT *` means all columns provided by the table expression.

It is convenient for exploration:

```sql
SELECT * FROM users;
```

But production application code often benefits from explicit columns:

```sql
SELECT
    id,
    email,
    display_name,
    created_at
FROM users;
```

Why?

## 11.1 Schema Evolution Risk

If a new large column is added, `SELECT *` may start moving much more data.

## 11.2 Network Cost

The database may be efficient internally while the application becomes slower because additional columns must cross the connection.

## 11.3 API Coupling

An API response based on `SELECT *` can accidentally change when the schema changes.

## 11.4 Hidden Sensitive Data

New columns can introduce information that was not intended for a response.

## 11.5 Reviewability

Explicit projection makes the query contract visible.

### Important nuance

`SELECT *` is not inherently “bad SQL.” It is a tool. It is often perfectly appropriate for debugging, interactive exploration, ad hoc analysis, and controlled internal queries.

The engineering rule is:

> Use explicit projection when the query is part of a durable production contract.

---

# 12. Column Aliases Are Labels, Not Variables

Example:

```sql
SELECT
    first_name || ' ' || last_name AS full_name
FROM users;
```

`full_name` is an output name.

It does not create a procedural variable that can automatically be reused everywhere in the same query level.

This distinction explains why:

```sql
ORDER BY full_name
```

can be valid while:

```sql
WHERE full_name = 'Ada Lovelace'
```

is not treated the same way. PostgreSQL specifically permits output-column names in `ORDER BY` and `GROUP BY`, but not in `WHERE` or `HAVING`. citeturn833341search1

---

# 13. `ORDER BY` Defines Result Ordering

This principle must become automatic:

> A SQL query does not guarantee a particular row order unless an `ORDER BY` establishes that order.

Without:

```sql
ORDER BY created_at DESC
```

you cannot safely assume the newest rows come first.

PostgreSQL explicitly states that without `ORDER BY`, rows are returned in whatever order the system finds fastest to produce. The physical order observed in one execution plan, environment, or dataset must not be treated as an API contract. citeturn833341search1turn563948search0

---

# 14. “It Always Comes Back in ID Order” Is Not a Guarantee

Suppose you write:

```sql
SELECT id, email
FROM users
LIMIT 20;
```

And you observe:

```text
1
2
3
...
20
```

A developer may conclude:

> PostgreSQL returns rows in primary-key order.

That conclusion is invalid.

The observed order may be a side effect of:

- the selected scan path,
- physical table layout,
- index usage,
- parallel execution,
- planner changes,
- table rewrites,
- vacuum effects,
- data distribution,
- or other implementation details.

Only an explicit `ORDER BY` establishes requested ordering.

---

# 15. `LIMIT` Without `ORDER BY` Is a Semantic Trap

Consider:

```sql
SELECT id
FROM jobs
LIMIT 10;
```

Question:

> Which 10 jobs?

The query does not define a meaningful answer.

PostgreSQL documentation is explicit: using `LIMIT` without an `ORDER BY` leaves the chosen subset unpredictable. The planner may also choose different plans for different `LIMIT`/`OFFSET` values, making observed subsets change. citeturn563948search0

Correct when you mean “10 oldest jobs”:

```sql
SELECT id
FROM jobs
ORDER BY created_at ASC, id ASC
LIMIT 10;
```

The second ordering column is important when `created_at` is not unique.

---

# 16. Deterministic Ordering Requires Tie-Breakers

Consider:

```sql
SELECT id, created_at
FROM orders
ORDER BY created_at DESC
LIMIT 20;
```

What if 300 rows have exactly the same `created_at` value?

The order among tied rows is not fully defined.

A more deterministic contract is:

```sql
SELECT id, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Now the pair:

```text
(created_at, id)
```

defines a total ordering if `id` is unique.

PostgreSQL documents that rows equal on all specified sort expressions are returned in implementation-dependent order. citeturn563948search22turn833341search1

### Production rule

When pagination, synchronization, exports, or “latest N” semantics matter:

> Prefer a deterministic ordering with a unique or otherwise sufficient tie-breaker.

---

# 17. `ORDER BY` Can Refer to Output Names

Valid:

```sql
SELECT
    price * quantity AS total
FROM order_lines
ORDER BY total DESC;
```

Also valid:

```sql
SELECT
    price * quantity AS total
FROM order_lines
ORDER BY 1 DESC;
```

But positional `ORDER BY 1` can reduce readability and become fragile when the select list changes.

Prefer the named expression or alias in maintainable application code unless positional ordering is intentional.

PostgreSQL supports output-column names and ordinal positions in `ORDER BY`. citeturn833341search1

---

# 18. `NULL` Changes Ordinary Intuition

SQL's `NULL` means “unknown/missing/not present,” not simply zero or an empty string.

Therefore:

```sql
WHERE deleted_at = NULL
```

does not mean “where deleted_at is null.”

Correct:

```sql
WHERE deleted_at IS NULL
```

And:

```sql
WHERE deleted_at IS NOT NULL
```

This chapter does not yet fully cover SQL's three-valued logic—that belongs in deeper predicate semantics—but it is essential to recognize that boolean reasoning in SQL is not identical to ordinary two-valued programming-language logic.

---

# 19. Boolean Predicates Are Not Just True/False

SQL predicate evaluation involves:

```text
TRUE
FALSE
UNKNOWN
```

For example:

```sql
NULL = 5
```

is `UNKNOWN`, not `FALSE` in the semantic model.

And a `WHERE` clause keeps rows for which the predicate is `TRUE`.

That distinction becomes critical in expressions involving nullable columns, `NOT`, joins, conditional filters, and anti-joins.

We will revisit this in depth in Chapter `01.15 — NULL Semantics`.

---

# 20. Expressions Are Typed

A `SELECT` list is not a textual template. PostgreSQL analyzes expressions using data types and operators.

Examples:

```sql
SELECT 10 + 20;
```

```sql
SELECT price * quantity
FROM order_lines;
```

```sql
SELECT created_at + interval '1 day'
FROM events;
```

The result type depends on PostgreSQL's type system and operator/function definitions.

This becomes important later for:

- implicit casts,
- operator selection,
- indexes,
- expression indexes,
- timestamps,
- numeric precision,
- JSON operators,
- custom types.

---

# 21. PostgreSQL Does Not Promise “Source Code Evaluation Order”

A dangerous assumption is:

```sql
SELECT expensive_function(x)
FROM t
WHERE cheap_predicate(x);
```

and then reasoning:

> PostgreSQL must evaluate the `WHERE` clause for every row, and only then evaluate `expensive_function` for surviving rows.

The SQL semantics require the correct result, but physical evaluation timing can be more flexible than this simple procedural story.

PostgreSQL's documentation explicitly notes that output expressions can effectively be evaluated after sorting and limiting when they are not referenced by `DISTINCT`, `ORDER BY`, or `GROUP BY`. This behavior avoids unnecessary evaluations for rows that never appear in the final result. citeturn833341search1

Therefore:

> Never design correctness around an assumed physical evaluation order unless PostgreSQL explicitly guarantees the behavior you rely on.

---

# 22. Query Semantics vs Planner Optimization

Suppose two execution strategies exist:

```text
Plan A → reads every row → filters

Plan B → uses an index → reads only matching rows
```

If both produce the same logically valid result, PostgreSQL can choose either.

This gives us a crucial separation:

```text
Correctness layer:
“What result is requested?”

Performance layer:
“How can PostgreSQL produce that result efficiently?”
```

Do not mix them.

A faster query is not automatically a more correct query.

A slower plan is not automatically a semantic bug.

Later chapters on indexes and query planning will build on this distinction.

---

# 23. `DISTINCT` Changes the Result Contract

Without `DISTINCT`:

```sql
SELECT department_id
FROM employees;
```

If the source has 100 employee rows, you can get 100 result rows.

With:

```sql
SELECT DISTINCT department_id
FROM employees;
```

you get one result row per distinct `department_id` value.

PostgreSQL defines `SELECT DISTINCT` as eliminating duplicate result rows. `SELECT ALL` is the default. citeturn833341search1

Important:

```sql
DISTINCT is applied to the selected result values.
```

Therefore:

```sql
SELECT DISTINCT first_name
FROM users;
```

is not equivalent to:

```sql
SELECT DISTINCT id, first_name
FROM users;
```

because the comparison key is the complete projected row.

---

# 24. Projection Can Change Duplicate Behavior

Suppose:

```text
id | status
---+--------
1  | active
2  | active
3  | disabled
```

Then:

```sql
SELECT id, status
FROM users;
```

returns three distinct rows.

But:

```sql
SELECT status
FROM users;
```

also returns three rows because `DISTINCT` is not implied.

And:

```sql
SELECT DISTINCT status
FROM users;
```

returns:

```text
active
inactive/disabled
```

depending on the data.

Projection and duplicate semantics are therefore related but not identical concepts.

---

# 25. `DISTINCT ON` Is PostgreSQL-Specific and Powerful

PostgreSQL provides:

```sql
SELECT DISTINCT ON (customer_id)
    customer_id,
    id,
    created_at,
    total
FROM orders
ORDER BY customer_id, created_at DESC, id DESC;
```

This is a common PostgreSQL pattern for “one best row per group.”

For each set of rows sharing the `DISTINCT ON` expressions, PostgreSQL keeps the first row according to the ordering.

Crucially, without a compatible `ORDER BY`, the chosen “first” row is unpredictable.

PostgreSQL requires the `DISTINCT ON` expressions to match the leftmost `ORDER BY` expressions. The documentation gives the canonical “most recent report per location” pattern. citeturn833341search1

This becomes particularly useful later for:

- latest-record retrieval,
- de-duplication,
- state snapshots,
- “latest price per product,”
- “last event per entity.”

---

# 26. The Difference Between “One Row Per Entity” and “One Row Per Source Row”

These two requirements are often confused.

### Requirement A

> Give me every order.

```sql
SELECT *
FROM orders;
```

### Requirement B

> Give me the latest order for every customer.

That is not a basic row retrieval problem. It is a grouping/ranking problem.

For example:

```sql
SELECT DISTINCT ON (customer_id)
    customer_id,
    id,
    created_at
FROM orders
ORDER BY customer_id, created_at DESC, id DESC;
```

or later via a window function:

```sql
SELECT *
FROM (
    SELECT
        o.*,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, id DESC
        ) AS rn
    FROM orders o
) x
WHERE rn = 1;
```

The mental lesson is more important than the syntax:

> “One row per entity” is a result-shaping requirement, not an assumption about the table's physical structure.

---

# 27. `OFFSET` Is a Result-Slicing Operation

Example:

```sql
SELECT id
FROM users
ORDER BY id
LIMIT 20 OFFSET 40;
```

Conceptually:

```text
Ordered result
↓
Skip first 40
↓
Return next 20
```

PostgreSQL explicitly notes that skipped rows still have to be computed inside the server, so a large `OFFSET` can become inefficient. citeturn563948search0

This will matter later in Chapter `07.6 — Pagination` and `07.7 — Keyset Pagination`.

---

# 28. `LIMIT/OFFSET` Is About a Query Result, Not a Table Range

This is subtle.

Wrong mental model:

```text
OFFSET 100 = start at physical row 101
```

Correct mental model:

```text
Evaluate the query result according to its semantics
↓
Apply ordering if requested
↓
Skip N result rows
↓
Return the limited slice
```

Physical storage does not define the meaning of `OFFSET`.

---

# 29. `FETCH FIRST` Is Another Row-Limiting Form

PostgreSQL supports standard-style syntax such as:

```sql
SELECT id
FROM users
ORDER BY id
FETCH FIRST 20 ROWS ONLY;
```

The semantics are analogous to `LIMIT` for common use cases.

PostgreSQL's current `SELECT` syntax also supports `FETCH FIRST ... WITH TIES`, where additional rows tied for the last ordering position may be returned. `ORDER BY` is required for `WITH TIES`. citeturn833341search1

---

# 30. `WITH TIES` Changes the Row-Count Contract

Example:

```sql
SELECT id, score
FROM leaderboard
ORDER BY score DESC
FETCH FIRST 10 ROWS WITH TIES;
```

You may receive 10 rows, but you can receive more if multiple rows tie with the 10th row's ordering value.

That is a semantic choice.

It is not “LIMIT 10 but PostgreSQL sometimes ignores it.”

The contract is explicitly different.

---

# 31. Nested Queries Change the Name and Scope Context

Consider:

```sql
SELECT *
FROM (
    SELECT
        id,
        email AS contact_email
    FROM users
) u
WHERE u.contact_email = 'a@example.com';
```

Now `contact_email` is a real column of the derived table `u` from the outer query's perspective.

This explains a common technique:

```text
Inner query
    ↓
creates named output columns
    ↓
Outer query treats those outputs as input columns
```

This is one way to reuse derived expressions without pretending that aliases are procedural variables.

---

# 32. Why a Subquery Can Change What Is Legally Referenced

Compare:

```sql
SELECT
    price * quantity AS total
FROM order_lines
WHERE total > 1000;
```

with:

```sql
SELECT *
FROM (
    SELECT
        price * quantity AS total
    FROM order_lines
) x
WHERE x.total > 1000;
```

In the first query, `total` is an output alias at the same query level and cannot simply be treated as an input name for `WHERE`.

In the second query, the inner `SELECT` creates the derived table's output schema, and the outer query can filter that schema.

This is a powerful scoping mental model.

---

# 33. `ORDER BY` Is Not “Just Cosmetic”

Developers sometimes treat sorting as a presentation concern.

That is wrong whenever row selection depends on order.

For:

```sql
LIMIT
OFFSET
FETCH FIRST
DISTINCT ON
WITH TIES
Top-N retrieval
pagination
```

ordering can be part of the semantics of **which rows are returned**, not merely how they are displayed.

PostgreSQL explicitly recommends combining `LIMIT` with an `ORDER BY` that constrains the result to a unique order when a predictable subset is required. citeturn563948search0

---

# 34. Indexes Can Satisfy `ORDER BY`, but That Is an Execution Detail

A B-tree index may be able to deliver rows in the requested order, which can avoid a separate sort operation.

However:

```text
ORDER BY semantics
```

come from SQL, while:

```text
use an index to deliver that order
```

is a planner/executor strategy.

PostgreSQL documents that B-tree indexes can produce sorted output, while other supported index types do not provide a general sorted order in the same way. citeturn563948search5

This distinction will become central in the Index Engineering phase.

---

# 35. A Query Can Be Logically Correct but Operationally Poor

Example:

```sql
SELECT *
FROM huge_orders
ORDER BY created_at DESC;
```

Semantically, this may be perfectly correct.

Operationally, it may be terrible if:

- millions of rows are returned,
- only the first 20 are needed,
- the client does not need every column,
- a useful index is absent.

A production engineer asks two different questions:

```text
1. Is the result correct?
2. Is the way we obtain and transfer it appropriate for the workload?
```

Never answer the second question by changing the first question's semantics accidentally.

---

# 36. Query Correctness Has Multiple Dimensions

A production `SELECT` should be reviewed across at least these dimensions:

| Dimension | Question |
|---|---|
| Row correctness | Are these the right rows? |
| Column correctness | Are these the right fields/expressions? |
| Duplicate correctness | Should duplicates exist? |
| Ordering correctness | Is order required and fully defined? |
| Null correctness | Are missing values handled correctly? |
| Type correctness | Are expressions using intended types? |
| Temporal correctness | Is the time interpretation correct? |
| Tenant correctness | Can rows cross tenant boundaries? |
| Security correctness | Could unintended fields/rows leak? |
| Performance correctness | Is the query safe for the workload? |
| Operational correctness | Can it behave predictably under load and schema evolution? |

“Query works” is therefore too weak a review standard.

# 37. Production Scenario — API List Endpoint

Suppose you build:

```http
GET /orders?page=2&limit=20
```

A naive query:

```sql
SELECT *
FROM orders
LIMIT 20 OFFSET 20;
```

has several problems:

### Problem 1 — No deterministic order

Which rows are page 1 and page 2?

The query does not define that.

### Problem 2 — Large-offset cost

Later pages may require increasingly more rows to be processed/skipped. PostgreSQL explicitly documents this cost behavior. citeturn563948search0

### Problem 3 — Schema coupling

`SELECT *` creates an accidental output contract.

### Better starting point

```sql
SELECT
    id,
    customer_id,
    status,
    total_cents,
    created_at
FROM orders
WHERE tenant_id = $1
ORDER BY created_at DESC, id DESC
LIMIT $2
OFFSET $3;
```

Now the query has an explicit:

- tenant boundary,
- projection,
- ordering,
- page size,
- offset.

Later we will improve the pagination strategy further with keyset pagination.

# 38. Production Scenario — Multi-Tenant ERP

Consider a jewellery ERP:

```text
tenant_id
branch_id
invoice_id
created_at
```

A dangerous query is:

```sql
SELECT id, total_cents
FROM invoices
ORDER BY created_at DESC
LIMIT 50;
```

The query may be technically valid while being architecturally invalid.

The correct business query may require:

```sql
SELECT
    id,
    branch_id,
    total_cents,
    created_at
FROM invoices
WHERE tenant_id = $1
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

The missing tenant predicate is not a performance issue first. It is a **correctness and security boundary** issue.

Mental rule:

> A database query must encode the business isolation boundary when the database is responsible for enforcing that boundary.

Later phases will expand this into schema design, RLS, indexing, and multi-tenant architecture.

# 39. Production Scenario — “Latest Price”

Suppose products have many price records.

Requirement:

> Return the latest effective price for every product.

A naive query:

```sql
SELECT DISTINCT product_id, price
FROM product_prices;
```

is wrong. It returns distinct combinations, not the latest one.

A PostgreSQL-specific pattern is:

```sql
SELECT DISTINCT ON (product_id)
    product_id,
    price,
    effective_at,
    id
FROM product_prices
ORDER BY product_id, effective_at DESC, id DESC;
```

The ordering is part of the correctness of the query because `DISTINCT ON` keeps the first row in each group. citeturn833341search1

# 40. Production Scenario — Dashboard Query

Suppose a dashboard requires:

- current-day orders,
- only paid orders,
- newest first,
- maximum 100 rows.

A weak query:

```sql
SELECT *
FROM orders
LIMIT 100;
```

A stronger semantic contract:

```sql
SELECT
    id,
    customer_id,
    total_cents,
    paid_at,
    created_at
FROM orders
WHERE status = 'paid'
  AND created_at >= CURRENT_DATE
ORDER BY created_at DESC, id DESC
LIMIT 100;
```

The second query makes the business intent visible.

# 41. Production Scenario — “Newest Record” Is Ambiguous

Consider:

```sql
ORDER BY updated_at DESC
LIMIT 1
```

What happens if two rows share the same `updated_at`?

The query has not fully defined a winner.

Better:

```sql
ORDER BY updated_at DESC, id DESC
LIMIT 1
```

Now you have a deterministic tie-breaker.

### Engineering question

Ask:

> What makes two rows tied, and if they are tied, which one should win?

That question often reveals missing requirements.

# 42. Common Developer Mistakes

## Mistake 1 — “SQL executes top-to-bottom.”

### Your assumption
The query is evaluated in textual order.

### Problem
SQL is declarative, and PostgreSQL can optimize physical execution.

### Correct mental model
Separate written syntax, logical semantics, and physical execution.

### Production consequence
You may write incorrect assumptions about evaluation timing, ordering, aliases, and performance.

### Better approach
Reason semantically first; inspect plans when physical behavior matters.

---

## Mistake 2 — “Without `ORDER BY`, rows come back naturally sorted.”

### Problem
No result order is guaranteed.

### Better approach
Declare the ordering explicitly.

---

## Mistake 3 — “`LIMIT 10` means the first 10 rows.”

### Problem
There is no meaningful “first” unless an order is defined.

### Better approach
Use:

```sql
ORDER BY ...
LIMIT 10
```

---

## Mistake 4 — “An alias is a variable.”

### Problem
Aliases label output columns; they do not automatically become same-level input variables.

### Better approach
Use the source expression, a subquery, or a CTE according to the needed scope.

---

## Mistake 5 — “`DISTINCT` means one source row per entity.”

### Problem
`DISTINCT` removes duplicate **projected result rows**.

### Better approach
Define the entity-level selection rule explicitly.

---

## Mistake 6 — “`SELECT *` is harmless forever.”

### Problem
Schema evolution, hidden columns, transfer cost, and API coupling.

### Better approach
Use explicit projection for durable application contracts.

---

## Mistake 7 — “Sorting is only for UI.”

### Problem
Sorting can determine which rows survive `LIMIT`, pagination, `DISTINCT ON`, or `WITH TIES`.

### Better approach
Treat order as part of the query contract when selection depends on it.

# 43. AI / Vibe-Coding Failure Patterns

Generative AI often produces syntactically plausible SQL that has incorrect semantics.

## Pattern 1 — Pagination Without Ordering

AI may produce:

```sql
SELECT *
FROM orders
LIMIT $1 OFFSET $2;
```

Looks valid.

Semantically incomplete if pages need stable membership.

---

## Pattern 2 — `DISTINCT` Used as a Band-Aid for Duplicate Joins

AI may generate:

```sql
SELECT DISTINCT o.*
FROM orders o
JOIN order_items i ON i.order_id = o.id;
```

This may suppress duplicate output rows without addressing why the join multiplies rows or whether the join itself is the correct business operation.

### Audit question

> Should the query logically return one row per order, or should it return one row per order-item relationship?

---

## Pattern 3 — Missing Tenant Predicate

AI may write:

```sql
SELECT *
FROM invoices
WHERE status = 'open';
```

while the application requires:

```sql
WHERE tenant_id = $1
  AND status = 'open'
```

This is potentially a serious isolation failure.

---

## Pattern 4 — Ordering by a Non-Unique Column

AI may write:

```sql
ORDER BY created_at DESC
LIMIT 50;
```

without considering ties.

### Audit question

> Is the ordering total and deterministic enough for pagination or “latest N” semantics?

---

## Pattern 5 — `WHERE alias = ...`

AI may produce:

```sql
SELECT price * quantity AS total
FROM order_lines
WHERE total > 1000;
```

The fix is not merely “change syntax.” The deeper question is scope: which query level defines `total`?

# 44. Advanced Reasoning: Semantic Equivalence vs Textual Similarity

Two queries may look very different while representing equivalent semantics.

For example, a simple filter can sometimes be expressed through a different relational structure.

Conversely, two queries that look similar can have different semantics because of:

- placement of predicates,
- join multiplicity,
- null behavior,
- grouping,
- duplicate elimination,
- ordering,
- or limiting.

Therefore, expert SQL review asks:

> Are these queries equivalent under all relevant data conditions?

not merely:

> Do these queries look similar?

# 45. Query Contracts

A production query should be viewed as a contract.

A useful contract template is:

```text
INPUT SCOPE
↓
QUALIFICATION RULES
↓
OUTPUT SHAPE
↓
DUPLICATE RULE
↓
ORDERING RULE
↓
ROW LIMITING RULE
↓
SECURITY / TENANT RULES
```

Example:

```text
Input:
  invoices for tenant 42

Qualification:
  status = paid
  created_at >= 2026-09-01

Output:
  id, customer_id, total_cents, created_at

Duplicates:
  one row per invoice

Ordering:
  created_at DESC, id DESC

Limit:
  50 rows

Security:
  tenant_id is mandatory
```

Then the SQL becomes an implementation of a known contract rather than a guess.

# 46. A Strong Query Review Method

When reviewing any `SELECT`, walk through this sequence.

## Step 1 — What entities are we trying to return?

Examples:

```text
users
orders
latest order per user
one row per invoice
all order items
```

## Step 2 — What is the candidate row source?

Inspect `FROM` and joins.

## Step 3 — What makes a row qualify?

Inspect predicates.

## Step 4 — Can joins multiply rows?

Count expected cardinality.

## Step 5 — What exactly is the output shape?

Inspect the select list.

## Step 6 — Are duplicates meaningful?

Do not use `DISTINCT` automatically.

## Step 7 — Is ordering required?

If yes, define it explicitly.

## Step 8 — Is the ordering deterministic?

Check tie-breakers.

## Step 9 — Is limiting based on that order?

If yes, order is part of correctness.

## Step 10 — What can change under schema evolution or workload growth?

Review production behavior, not just today's result.

# 52. EXPLAIN Thinking for This Chapter

At this stage, do not try to master the entire planner.

Instead, establish one rule:

```text
SQL semantics first.
Execution plan second.
```

A useful progression is:

```sql
EXPLAIN
SELECT ...;
```

then:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

The first asks:

> What plan does PostgreSQL intend to use?

The second also executes the query and provides runtime information.

Do not jump into plan interpretation before you can state the intended result independently of the plan.

# 53. Performance Principles Introduced Here

## Principle 1 — Correctness before optimization

Do not optimize a query whose result semantics are wrong.

## Principle 2 — Determinism before pagination

Do not build stable pages on an unordered result.

## Principle 3 — Explicit projection for stable contracts

Do not accidentally move data your application does not need.

## Principle 4 — Do not confuse planner behavior with SQL guarantees

# 55. Reliability Principles Introduced Here

A reliable query should have stable semantics under:

- schema evolution,
- concurrent activity,

- null values,
- new indexes,

The goal is not:

# 57. Expert “Why?” Drill

You should be able to answer these without documentation lookup.

### Why does SQL not guarantee row order without `ORDER BY`?

Because ordering is not part of the result contract unless explicitly requested; physical scan and join strategies may produce different orders.

### Why can `LIMIT` without `ORDER BY` return different rows?

Because the subset is not uniquely defined, and PostgreSQL may choose different plans or execution orders. citeturn563948search0

### Why can `ORDER BY` use an alias?

Because the alias names an output column and PostgreSQL allows output-column names in `ORDER BY`. citeturn833341search1

### Why can the same alias not simply be used in `WHERE`?

Because `WHERE` operates in the query's input-side context, while the alias labels a select-list output at that query level. PostgreSQL explicitly documents this restriction. citeturn833341search1

### Why does `DISTINCT ON` require compatible leading `ORDER BY` expressions?

Because PostgreSQL needs the desired “first row” of each distinct group to be determined by the ordering. citeturn833341search1

### Why is `SELECT *` risky in application code?

Because it makes the output contract implicitly depend on the table schema.

### Why isn't an execution plan part of SQL semantics?

Because the plan is a chosen physical strategy for producing a semantically required result.

# 62. “Why Not?” Challenge System

For every design decision, challenge yourself.

### Why not `SELECT *`?

Because the production contract should be explicit.

### Why not `LIMIT 50` without ordering?

Because “which 50?” is unspecified.

### Why not `ORDER BY created_at` alone?

Because ties can remain nondeterministic.

### Why not add `DISTINCT` whenever duplicates appear?

Because duplicates may indicate an incorrect join or incorrect result shape.

### Why not rely on observed primary-key order?

Because observed order is not a semantic guarantee.

### Why not optimize by forcing an index immediately?

Because the query may be semantically wrong, and plan choice should be evidence-driven.

# 63. Anti-Pattern Catalog

| Anti-pattern | Why it fails | Better approach |
|---|---|---|
| `LIMIT` without `ORDER BY` | Unspecified subset | Explicit deterministic ordering |
| `ORDER BY` non-unique column for pagination | Tied rows can be unstable | Add unique tie-breaker |
| `SELECT *` in API contracts | Schema coupling | Explicit projection |
| `DISTINCT` as duplicate band-aid | Hides cardinality bug | Fix result-shape/join semantics |
| Assuming scan order | Implementation detail | `ORDER BY` |
| Treating aliases as variables | Scope mismatch | Expression/subquery/CTE |
