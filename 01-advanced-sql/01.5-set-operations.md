# 01.5 — Set Operations

> **Phase 01 — Advanced SQL**  
> **Level:** L2 → L7  
> **Status:** Mastery Module  
> **Target Database:** PostgreSQL 18+

---

## 1. Chapter Objective

Set operations are not merely alternative syntax for combining query results. They express **relational operations between complete result sets**: union, intersection, and difference.

By the end of this chapter, you should be able to:

- explain set operations from relational-algebra first principles;
- distinguish `UNION` from `UNION ALL` based on semantics, not habit;
- reason precisely about duplicate rows and duplicate multiplicity;
- use `INTERSECT`, `INTERSECT ALL`, `EXCEPT`, and `EXCEPT ALL` correctly;
- determine whether two query arms are union-compatible;
- predict result data types and understand PostgreSQL's type-resolution rules;
- understand operator precedence and when parentheses change meaning;
- reason about `ORDER BY`, `LIMIT`, and `OFFSET` at the set-operation level;
- recognize when joins, `EXISTS`, aggregation, or set operations are the better abstraction;
- analyze performance with `EXPLAIN (ANALYZE, BUFFERS)`;
- identify duplicate-elimination costs and planner implications;
- design safe multi-tenant, reporting, audit, reconciliation, and synchronization queries;
- detect subtle `NULL`, type, ordering, and cardinality bugs;
- audit AI-generated set-operation SQL;
- defend design choices at senior/staff/principal level.

---

## 2. Core Mental Model

A query produces a relation-like result. A set operation then combines the results of two query expressions.

Think in this form:

```text
                 Query A
                    │
                    ▼
             Result relation A
                    │
                    │     Set operator
                    ├───────────────┐
                    │               │
                    ▼               ▼
             UNION / INTERSECT / EXCEPT
                    │
                    ▼
             Combined relation
```

The essential distinction is:

```text
JOIN
→ combines columns horizontally
→ matches rows according to predicates

SET OPERATION
→ combines rows vertically / relationally
→ compares complete output rows
```

A join asks:

> Which rows from these relations should be combined into wider rows?

A set operation asks:

> How should these two already-shaped result relations be combined?

That distinction is foundational.

---

## 3. Relational Algebra Foundation

At the conceptual level:

```text
Union        A ∪ B
Intersection A ∩ B
Difference   A − B
```

Traditional mathematical set theory assumes no duplicates. SQL operates on **bag/multiset semantics by default**, which means duplicate rows can carry multiplicity.

PostgreSQL exposes this distinction with `ALL` variants:

```sql
UNION
UNION ALL

INTERSECT
INTERSECT ALL

EXCEPT
EXCEPT ALL
```

Therefore, do not build the incorrect mental model:

> “SQL is just sets.”

A more accurate engineering model is:

```text
SQL result
= relation-shaped rows
+ duplicate multiplicity unless a construct removes it
```

`UNION`, `INTERSECT`, and `EXCEPT` remove duplicates unless their corresponding `ALL` form is used. PostgreSQL documents these semantics explicitly. [PostgreSQL 18 — Combining Queries](https://www.postgresql.org/docs/18/queries-union.html)

---

## 4. Union Compatibility

For:

```sql
query_a
UNION
query_b
```

the two query results must be **union-compatible**.

At minimum:

1. They must emit the same number of columns.
2. Corresponding columns must have compatible data types.

Example:

```sql
SELECT id, email
FROM customers

UNION ALL

SELECT id, email
FROM archived_customers;
```

Valid because the two query arms have the same column structure.

This is not valid:

```sql
SELECT id, email
FROM customers

UNION ALL

SELECT id
FROM archived_customers;
```

The arity is different.

PostgreSQL resolves the corresponding output columns independently. The type-resolution rules are documented in PostgreSQL 18's type-conversion chapter. [PostgreSQL 18 — UNION, CASE, and Related Constructs](https://www.postgresql.org/docs/18/typeconv-union-case.html)

## 5. UNION

### 5.1 Semantics

```sql
SELECT email FROM customers
UNION
SELECT email FROM prospects;
```

Conceptually:

```text
all rows from customers
+ all rows from prospects
→ remove duplicate result rows
```

If both sources contain:

```text
alice@example.com
bob@example.com
alice@example.com
```

and the second source contains:

```text
alice@example.com
carol@example.com
```

then `UNION` returns one row for `alice@example.com`.

### 5.2 Important consequence

`UNION` is not merely append.

It is effectively:

```text
append
→ duplicate elimination
→ output
```

That duplicate-elimination step can require additional CPU, memory, and/or disk work depending on the chosen execution strategy and data volume.

---

## 6. UNION ALL

```sql
SELECT email FROM customers
UNION ALL
SELECT email FROM prospects;
```

This preserves duplicate multiplicity.

For large workloads, `UNION ALL` is frequently preferable when duplicate elimination is not part of the business requirement.

### Golden rule

> Never use `UNION` because it “looks cleaner.” Choose it only when duplicate elimination is semantically required.

This matters because an unnecessary deduplication step is both a semantic change and a potential performance cost.

---

## 7. UNION vs UNION ALL — Engineering Decision

| Requirement | Preferred construct |
|---|---|
| Combine rows and preserve every occurrence | `UNION ALL` |
| Combine rows and treat duplicate output rows as one | `UNION` |
| Event streams / append-only history | Usually `UNION ALL` |
| Consolidating two naturally disjoint partitions | Usually `UNION ALL` |
| Producing unique people/emails/IDs across sources | `UNION` |
| Reporting where multiplicity matters | Usually `UNION ALL` |
| Unknown duplicate semantics | Stop and clarify the requirement |

The last row is important. Performance optimization cannot repair an unclear semantic requirement.

---

## 8. INTERSECT

`INTERSECT` returns rows appearing in both query results.

```sql
SELECT customer_id
FROM orders_2025

INTERSECT

SELECT customer_id
FROM orders_2026;
```

Interpretation:

> Customers who appear in both datasets.

Duplicates are removed unless `INTERSECT ALL` is used.

This is often useful for overlap analysis, cohort comparison, reconciliation, and feature eligibility.

---

## 9. INTERSECT ALL

`INTERSECT ALL` preserves duplicate multiplicity according to the overlap available on both sides.

Suppose A contains:

```text
X
X
X
Y
```

and B contains:

```text
X
X
Z
```

then conceptually:

```text
INTERSECT ALL
→ X
→ X
```

The multiplicity of each value is constrained by the lower multiplicity in the two inputs.

This is a powerful reminder that `ALL` is not cosmetic. It changes the mathematical semantics of the result.

---

## 10. EXCEPT

`EXCEPT` returns rows present in the left query result but absent from the right query result.

```sql
SELECT customer_id
FROM customers

EXCEPT

SELECT customer_id
FROM blocked_customers;
```

Interpretation:

> Customers who are not in the blocked set.

Direction matters.

```text
A EXCEPT B
≠
B EXCEPT A
```

Do not mentally treat `EXCEPT` as a symmetric “difference.” It is directional set subtraction.

---

## 11. EXCEPT ALL

`EXCEPT ALL` preserves multiplicity after subtracting matching occurrences from the right side.

If A contains:

```text
X
X
X
Y
```

and B contains:

```text
X
X
Z
```

then conceptually:

```text
A EXCEPT ALL B
→ X
→ Y
```

One occurrence of `X` remains because three occurrences existed on the left and two were canceled by the right.

This matters in reconciliation workloads where multiplicity itself carries information.

---

## 12. Complete Semantic Table

| Operator | Duplicate behavior | Direction | Meaning |
|---|---|---|---|
| `UNION` | removes duplicates | symmetric | rows in A or B |
| `UNION ALL` | preserves duplicates | symmetric | append A and B |
| `INTERSECT` | removes duplicates | symmetric | rows in both |
| `INTERSECT ALL` | preserves multiplicity | symmetric | common rows with overlap counts |
| `EXCEPT` | removes duplicates | directional | rows in A not in B |
| `EXCEPT ALL` | preserves multiplicity | directional | subtract B occurrences from A |

## 13. Row Equality Is Important

Set operations compare **complete output rows**, not arbitrary business keys.

Consider:

```sql
SELECT customer_id, status
FROM a

UNION

SELECT customer_id, status
FROM b;
```

These rows are distinct:

```text
42 | active
42 | suspended
```

Even though `customer_id` is the same.

So ask:

> What exactly is the identity of a result row?

This is a crucial design question.

If your business identity is `customer_id` but your output contains `customer_id, status, source`, then `UNION` will deduplicate based on all emitted columns—not just `customer_id`.

---

## 14. A Classic Production Bug

Suppose:

```sql
SELECT customer_id, 'live' AS source
FROM customers

UNION

SELECT customer_id, 'archive' AS source
FROM archived_customers;
```

A customer present in both tables produces:

```text
42 | live
42 | archive
```

`UNION` does **not** collapse those rows because they are different complete rows.

A developer may expect:

```text
42
```

but the query does not express that requirement.

Correct engineering response:

1. Define the desired grain.
2. Define the business identity.
3. Select or aggregate accordingly.
4. Then choose the set operation.

---

## 15. Set Operations vs DISTINCT

These are related but not interchangeable concepts.

```sql
SELECT x FROM a
UNION
SELECT x FROM b;
```

performs duplicate elimination over the combined result.

Compare:

```sql
SELECT DISTINCT x
FROM (
    SELECT x FROM a
    UNION ALL
    SELECT x FROM b
) AS combined;
```

These may express equivalent high-level semantics, but they expose different query shapes and can lead to different plans.

The right question is not:

> Which syntax is shorter?

It is:

> Which query shape expresses the intent most clearly and gives the planner a good starting point for the workload?

Benchmark before making performance claims.

---

## 16. Type Resolution

Corresponding output columns must be type-compatible. PostgreSQL resolves their common result type according to its type-conversion rules.

Example:

```sql
SELECT 1
UNION
SELECT 2.5;
```

The result type is resolved to a compatible numeric type rather than requiring the two arms to be textually identical.

Type resolution occurs independently per corresponding column.

For example:

```sql
SELECT 1, 'alpha'
UNION
SELECT 2.5, 'beta';
```

The first output column and second output column are resolved separately.

Do not assume PostgreSQL merely copies the type from the first query arm.

---

## 17. The NULL Type-Resolution Trap

A subtle PostgreSQL behavior:

```sql
SELECT NULL
UNION
SELECT NULL
UNION
SELECT 1;
```

This can fail because set operations are resolved pairwise, and the inner `NULL UNION NULL` can resolve to `text`, producing a later incompatibility with `integer`.

Prefer an explicit type when intent matters:

```sql
SELECT NULL::integer
UNION
SELECT NULL::integer
UNION
SELECT 1;
```

This is a major lesson:

> “NULL” is not a universal type.

PostgreSQL's documented type-resolution algorithm explicitly covers this pairwise behavior. [PostgreSQL 18 — Type Resolution](https://www.postgresql.org/docs/18/typeconv-union-case.html)

---

## 18. Domains and Type Preservation

PostgreSQL also has domain-specific type-resolution rules. A domain can be reduced to its base type during resolution unless the query arms carefully preserve the exact domain type.

This matters in strongly governed schemas where domains encode business constraints.

Example principle:

```text
Domain-aware schema
        ↓
Set operation
        ↓
Potential type-resolution change
        ↓
Possibly lose domain identity
```

Do not treat output type preservation as automatic when set-operation arms use domain types.

---

## 19. Column Names

The output column names of a set operation are derived from the first query arm.

Example:

```sql
SELECT customer_id AS id
FROM customers

UNION ALL

SELECT customer_id AS customer_identifier
FROM archived_customers;
```

The result column is named according to the first arm.

This has practical API consequences.

If a Node.js service maps the result by property name, changing the first arm can change the externally visible field name even if the later arm remains unchanged.

Therefore:

> The leftmost query arm often acts as the output contract.

Treat it accordingly.

---

## 20. ORDER BY Belongs to the Combined Result Unless Scoped

This is a frequent mistake.

```sql
SELECT id FROM a
UNION ALL
SELECT id FROM b
ORDER BY id;
```

The `ORDER BY` applies to the combined result.

It does not mean:

```text
sort A
→ append B
```

If you need an input query to have its own `LIMIT`, `OFFSET`, or other clause, use parentheses.

```sql
(
    SELECT id
    FROM a
    ORDER BY id
    LIMIT 10
)
UNION ALL
(
    SELECT id
    FROM b
    ORDER BY id
    LIMIT 10
)
ORDER BY id;
```

PostgreSQL documents this parsing behavior explicitly. [PostgreSQL 18 — Combining Queries](https://www.postgresql.org/docs/18/queries-union.html)

---

## 21. LIMIT/OFFSET and Parentheses

This query:

```sql
SELECT id FROM a
UNION ALL
SELECT id FROM b
LIMIT 10;
```

means:

```sql
(
    SELECT id FROM a
    UNION ALL
    SELECT id FROM b
)
LIMIT 10;
```

It does **not** mean:

```sql
SELECT id FROM a
UNION ALL
(
    SELECT id FROM b
    LIMIT 10
);
```

If the limit belongs to one arm, scope that arm explicitly.

This is a semantic issue first and a performance issue second.

---

## 22. Operator Precedence

Without parentheses:

```sql
A UNION B INTERSECT C
```

means:

```text
A UNION (B INTERSECT C)
```

because `INTERSECT` binds more tightly than `UNION` and `EXCEPT`.

`UNION` and `EXCEPT` associate left-to-right.

Therefore:

```sql
A UNION B EXCEPT C
```

means:

```text
(A UNION B) EXCEPT C
```

Do not rely on memory when a query becomes non-trivial. Parentheses are cheap; semantic ambiguity is expensive.

---

## 23. Set Operations and Ordering Guarantees

A set operation does **not** guarantee that rows from the first query appear before rows from the second query.

This is invalid reasoning:

> “UNION ALL preserves input order, so I can rely on it for API ordering.”

You cannot.

If deterministic order matters:

```sql
...
UNION ALL
...
ORDER BY created_at, id;
```

Even then, make the ordering key sufficient to define the required deterministic sequence.

PostgreSQL explicitly warns that `UNION` does not guarantee that the second query's rows are physically returned after the first query's rows. The broader SQL rule is that ordering requires explicit `ORDER BY`. [PostgreSQL 18 — Combining Queries](https://www.postgresql.org/docs/18/queries-union.html)

## 24. Choosing Between UNION ALL and JOIN

Suppose you need a single list of account IDs from two sources:

```sql
SELECT account_id FROM active_accounts
UNION ALL
SELECT account_id FROM recently_closed_accounts;
```

This is a natural set operation because the output is vertically shaped:

```text
account_id
---------
1
2
3
4
```

A join would be conceptually different and usually require a fabricated relationship.

Use a join when you need to combine attributes:

```sql
SELECT a.account_id, c.customer_name
FROM active_accounts a
JOIN customers c ON c.id = a.account_id;
```

Mental rule:

```text
Same kind of rows from multiple sources
→ set operation

Related facts that should become wider rows
→ join
```

---

## 25. UNION vs OR

Sometimes developers rewrite:

```sql
SELECT id
FROM customers
WHERE country = 'IN'

UNION

SELECT id
FROM customers
WHERE country = 'US';
```

as:

```sql
SELECT id
FROM customers
WHERE country IN ('IN', 'US');
```

When the source relation is the same and the semantics are just alternative predicates, the single-query form is often simpler.

However, the two forms are not universally interchangeable when the query arms differ in source tables, projections, joins, limits, or other relational operations.

Always compare semantics before rewriting.

---

## 26. UNION vs OR — Duplicate Semantics

Consider:

```sql
SELECT id FROM customers WHERE is_vip
UNION ALL
SELECT id FROM customers WHERE has_overdue_balance;
```

A customer meeting both predicates appears twice.

But:

```sql
SELECT id
FROM customers
WHERE is_vip OR has_overdue_balance;
```

returns that customer once.

Therefore:

```text
UNION ALL
≠
OR
```

in duplicate-sensitive workloads.

A `UNION` without `ALL` may restore unique output, but it still expresses a different query shape and may have different performance characteristics.

---

## 27. EXCEPT vs NOT EXISTS

These can express similar business questions but are not identical syntax.

Set-based form:

```sql
SELECT customer_id
FROM customers
EXCEPT
SELECT customer_id
FROM blocked_customers;
```

Predicate form:

```sql
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM blocked_customers b
    WHERE b.customer_id = c.customer_id
);
```

Ask:

1. What is the intended row grain?
2. Are duplicate multiplicities meaningful?
3. Do I naturally have a relation to filter, or two relations to compare?
4. Which form is clearer to future maintainers?
5. Which form produces the best measured plan for this workload?

Do not invent a universal “EXCEPT is always faster” or “NOT EXISTS is always faster” rule.

---

## 28. INTERSECT vs EXISTS

Similarly:

```sql
SELECT customer_id
FROM customers
INTERSECT
SELECT customer_id
FROM newsletter_subscribers;
```

can be expressed as:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM newsletter_subscribers n
    WHERE n.customer_id = c.customer_id
);
```

They can have equivalent set-oriented intent under appropriate conditions, but duplicates, projections, and optimizer choices matter.

A production engineer asks first:

> What exact relation and multiplicity do I want?

Only after that:

> Which syntax is the best representation?

## 29. Multi-Tenant Safety

Set operations can create tenant-isolation bugs just as joins can.

Dangerous:

```sql
SELECT id
FROM invoices_current
WHERE status = 'OPEN'

UNION ALL

SELECT id
FROM invoices_archive
WHERE status = 'OPEN';
```

If the architecture is multi-tenant, the query may need a tenant boundary in **every arm**:

```sql
SELECT id
FROM invoices_current
WHERE tenant_id = $1
  AND status = 'OPEN'

UNION ALL

SELECT id
FROM invoices_archive
WHERE tenant_id = $1
  AND status = 'OPEN';
```

Failure mode:

```text
tenant predicate missing in one arm
→ rows from another tenant enter the result
→ application cannot reliably “filter it later”
→ data isolation failure
```

For security-sensitive systems, enforce isolation at database boundaries where appropriate, including schema/RLS architecture rather than depending solely on developer memory.

## 30. Financial Reconciliation Use Case

Set operations are useful for identifying missing or extra records.

Example: compare posted ledger transaction IDs to settlement transaction IDs.

```sql
SELECT transaction_id
FROM ledger_entries

EXCEPT

SELECT transaction_id
FROM settlement_entries;
```

Meaning:

> Ledger transactions not found in settlement.

Reverse direction:

```sql
SELECT transaction_id
FROM settlement_entries

EXCEPT

SELECT transaction_id
FROM ledger_entries;
```

Meaning:

> Settlement transactions not found in ledger.

These are not symmetric questions.

A reconciliation system should typically record both directions because:

```text
missing-from-B
and
extra-in-B
```

are distinct failure classes.

---

## 31. Temporal / Archive Union

A common production architecture splits hot and cold data:

```text
orders_current
orders_archive
```

and an API requires a unified view:

```sql
SELECT id, customer_id, created_at, total_amount
FROM orders_current

UNION ALL

SELECT id, customer_id, created_at, total_amount
FROM orders_archive;
```

Why `UNION ALL` is frequently appropriate:

- each row represents an actual stored order;
- duplicate elimination is not part of the domain rule;
- the partitioning/lifecycle process should ensure logical identity;
- unnecessary global deduplication can add cost.

But do not blindly assume the tables are disjoint. Validate the lifecycle invariant.

---

## 32. Partitioning and Set Operations

A manual archive-plus-current query may resemble partitioned data access:

```text
current partition
archive partition 1
archive partition 2
archive partition 3
        ↓
    UNION ALL
```

Declarative partitioning allows PostgreSQL to reason about partitions more directly, including partition pruning under suitable predicates.

Therefore, a manual set operation can be a useful transitional architecture, but it should not automatically be preferred over native partitioning when partitioning is the actual modeling need.

## 33. Performance: Why UNION Can Cost More

`UNION` requires duplicate elimination.

A useful abstract model is:

```text
cost(query A)
+
cost(query B)
+
cost(combine)
+
cost(deduplicate)
```

while:

```text
UNION ALL
≈
cost(query A)
+
cost(query B)
+
cost(combine)
```

The actual PostgreSQL plan depends on cardinalities, row width, statistics, available memory, parallelism, and planner decisions.

Never claim a fixed complexity from syntax alone.

## 34. EXPLAIN the Combined Query

Start with:

```sql
EXPLAIN
SELECT ...
UNION
SELECT ...;
```

Then investigate runtime and I/O:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
UNION
SELECT ...;
```

Look for:

- actual rows vs estimated rows;
- sort or hashing operations;
- memory-intensive nodes;
- temporary reads/writes;
- large scans in either branch;
- duplicate-elimination bottlenecks;
- branch asymmetry;
- unexpected row multiplication upstream.

A set operation can be innocent while one query arm is the actual bottleneck.

---

## 35. Query-Arm Asymmetry

Never optimize only the visible set operator.

For:

```sql
SELECT ... FROM a
UNION ALL
SELECT ... FROM b;
```

performance is often dominated by the slower branch.

Debug each arm independently:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... FROM a;
```

and:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... FROM b;
```

Then compare the combined plan.

This creates a powerful debugging workflow:

```text
Combined query
      ↓
Identify expensive node
      ↓
Identify branch
      ↓
Run branch independently
      ↓
Determine root cause
```

---

## 36. Common Production Performance Failure

### Symptom
A dashboard query suddenly becomes slow after archive migration.

### Query

```sql
SELECT ... FROM live_orders
UNION
SELECT ... FROM archived_orders;
```

### Hidden issue
The archive table contains billions of rows, and the product requirement did not actually require duplicate elimination.

### Root-cause candidates

- unnecessary `UNION` instead of `UNION ALL`;
- missing predicates on the archive branch;
- missing indexes;
- poor statistics;
- wider-than-needed projections;
- historical rows being scanned unnecessarily;
- API query requesting a page but forcing a large global combination.

### Correct response
Measure first. Then change the query according to the actual semantic requirement.

## 37. Pagination Across Multiple Sources

Suppose a feed combines:

```text
live_events
historical_events
```

A naïve query:

```sql
SELECT ... FROM live_events
UNION ALL
SELECT ... FROM historical_events
ORDER BY created_at DESC
LIMIT 50;
```

may still require significant work from both sources depending on the plan and available ordering/indexes.

A more advanced design may push filtering/order/limits into subqueries when the semantics permit:

```sql
(
    SELECT ...
    FROM live_events
    WHERE tenant_id = $1
    ORDER BY created_at DESC
    LIMIT 50
)
UNION ALL
(
    SELECT ...
    FROM historical_events
    WHERE tenant_id = $1
    ORDER BY created_at DESC
    LIMIT 50
)
ORDER BY created_at DESC
LIMIT 50;
```

But this is not automatically equivalent for every problem. It relies on each branch contributing no more than the final page can need.

The optimization question is:

> Can each branch safely contribute a bounded candidate set without changing the final top-N result?

That is a reasoning problem, not a syntax trick.

---

## 38. Type Discipline in Production APIs

Do not let implicit type resolution accidentally shape an API contract.

Example:

```sql
SELECT order_id, total_amount
FROM current_orders

UNION ALL

SELECT order_id, total_amount
FROM archive_orders;
```

Suppose one branch evolves from `numeric` to another compatible numeric type while the application assumes a specific JSON representation.

The database result type, driver conversion, and application serialization together define the actual API behavior.

Production checklist:

```text
DB type
→ PostgreSQL result type
→ driver mapping
→ application type
→ JSON serialization
```

Review the entire pipeline.

## 39. AI / Vibe-Coding Failure Patterns

AI-generated SQL commonly fails by:

### Failure 1 — Using UNION instead of UNION ALL

```sql
SELECT id FROM a
UNION
SELECT id FROM b;
```

when the requirement is to preserve every record.

### Failure 2 — Assuming UNION guarantees source order

```sql
SELECT ... FROM current
UNION ALL
SELECT ... FROM archive;
```

and assuming current rows arrive first.

They do not have that guarantee.

### Failure 3 — Missing tenant predicates

One query arm contains `tenant_id = $1`, the other does not.

### Failure 4 — Wrong deduplication key

The model uses `UNION` expecting deduplication by `id` while projecting additional columns.

### Failure 5 — Mis-scoped LIMIT

A generated query accidentally limits the combined result instead of one arm—or vice versa.

### Failure 6 — Implicit type assumptions

An AI-generated union combines literals, `NULL`, domains, numerics, UUIDs, or enums without explicitly checking the resolved output type.

### Failure 7 — Rewriting EXCEPT as NOT IN

This can introduce different NULL semantics.

### Failure 8 — Optimizing syntax without measuring

The model changes `UNION` to `UNION ALL` purely for speed without establishing whether duplicates are semantically valid.

## 40. `EXCEPT` vs `NOT IN` and NULL

A dangerous rewrite is:

```sql
SELECT id FROM a
EXCEPT
SELECT id FROM b;
```

to:

```sql
SELECT id
FROM a
WHERE id NOT IN (
    SELECT id FROM b
);
```

`NOT IN` has special three-valued-logic behavior when the subquery can contain `NULL`.

Therefore:

```text
EXCEPT
≠
NOT IN
```

as a blind mechanical substitution.

When expressing anti-membership, `NOT EXISTS` is often a safer predicate pattern because its semantics differ from `NOT IN` in the presence of nulls.

The correct choice still depends on the data model and intended multiplicity.

---

## 41. Result Grain Before Set Operation

Before writing a set operation, explicitly write the row grain.

Example:

```text
Desired grain:
one row per customer
```

Then check:

```sql
SELECT customer_id, region
FROM a
UNION
SELECT customer_id, region
FROM b;
```

This actually expresses:

```text
one row per distinct (customer_id, region)
```

not necessarily one row per customer.

If a customer can have different regions, you will receive multiple rows.

This is one of the most important advanced-SQL habits:

> Never choose a set operator before defining the grain of the intermediate and final result.

---

## 42. Set Operations in Reporting

Consider a report requiring:

```text
New customers
Returning customers
```

These may be built from separate query branches.

If the report wants two labeled categories:

```sql
SELECT customer_id, 'new' AS customer_type
FROM new_customers

UNION ALL

SELECT customer_id, 'returning' AS customer_type
FROM returning_customers;
```

`UNION ALL` is usually correct if the categories are logically intended to remain distinct.

If the same customer can appear in both categories, the resulting duplicates may be a business signal rather than a bug.

Never deduplicate a report merely because duplicates “look wrong.”

---

## 43. When Set Operations Are the Wrong Tool

Avoid set operations when:

- one query should enrich another with related columns;
- the intended relationship is key-based row matching;
- a predicate naturally expresses the requirement more clearly;
- aggregation would define the required grain more directly;
- a window function models ranking or “latest row” semantics better;
- a partitioned table already provides the required physical organization;
- the set operation is being used to compensate for poor schema design.

The principle is:

> Choose the relational abstraction that matches the problem.

---

## 44. When Set Operations Are Exactly the Right Tool

Use them when the problem naturally says:

```text
combine these row sets
find their overlap
find what is missing
find what exists only on one side
```

Typical production domains:

- reconciliation;
- reporting;
- audit comparison;
- migration validation;
- hot/archive consolidation;
- permission-set comparison;
- feature cohort comparison;
- data-quality diagnostics;
- synchronization checks;
- cross-system completeness checks.

---

## 45. Migration Validation Pattern

During a migration, compare old and new data:

```sql
SELECT id
FROM old_orders

EXCEPT

SELECT id
FROM new_orders;
```

This detects rows missing from the destination.

Reverse check:

```sql
SELECT id
FROM new_orders

EXCEPT

SELECT id
FROM old_orders;
```

This detects unexpected destination-only rows.

Then compare changed attributes separately:

```sql
SELECT id, total_amount
FROM old_orders

EXCEPT

SELECT id, total_amount
FROM new_orders;
```

This detects differences in the complete projected row, not merely existence.

For large migrations, run these checks with carefully designed predicates, batches, indexes, and representative samples where full comparison is operationally too expensive.

---

## 46. Audit / Permission Comparison

Example:

```sql
SELECT permission
FROM role_a_permissions

EXCEPT

SELECT permission
FROM role_b_permissions;
```

Meaning:

> Permissions role A has that role B does not.

Reverse it for the opposite difference.

This is an excellent use case because the query language mirrors the business question directly.

---

## 47. Nested Set Operations

You can combine operations:

```sql
SELECT ...
UNION
SELECT ...
INTERSECT
SELECT ...;
```

But nested expressions can become difficult to reason about.

Prefer explicit parentheses for non-trivial logic:

```sql
(
    SELECT ...
    UNION
    SELECT ...
)
EXCEPT
(
    SELECT ...
    INTERSECT
    SELECT ...
);
```

Readable relational logic is a production safety feature.

---

## 48. CTEs for Complex Set Logic

For complex business logic, CTEs can make the intermediate relations explicit:

```sql
WITH current_ids AS (
    SELECT id FROM current_orders
),
archive_ids AS (
    SELECT id FROM archived_orders
),
missing AS (
    SELECT id FROM current_ids
    EXCEPT
    SELECT id FROM archive_ids
)
SELECT id
FROM missing;
```

This can improve maintainability even if a more compact query exists.

Do not assume CTE syntax alone makes a query slower or faster. Examine the actual PostgreSQL plan and the relevant version-specific behavior.

## 49. Production Debugging Framework

When a set-operation query returns unexpected rows:

### Step 1 — State the desired grain

```text
One row per customer?
One row per invoice?
One row per (customer, status)?
```

### Step 2 — Run each arm independently

Verify cardinality and duplicate patterns.

### Step 3 — Compare projections

Check whether extra columns are preventing expected deduplication.

### Step 4 — Check tenant/security predicates

Verify every arm enforces the same security boundary.

### Step 5 — Check type resolution

Inspect nulls, literals, casts, domains, enums, numerics, UUIDs, and timestamps.

### Step 6 — Check operator semantics

Confirm whether `ALL` is required.

### Step 7 — Check parentheses

Especially around `LIMIT`, `ORDER BY`, nested operations, and mixed operators.

### Step 8 — Examine execution plans

Use `EXPLAIN (ANALYZE, BUFFERS)` where safe.

### Step 9 — Measure before rewriting

Never optimize from appearance alone.

## 50. Failure Classification

When a set-operation query is wrong, classify the failure.

| Failure class | Example |
|---|---|
| Semantic | `UNION` used when multiplicity matters |
| Grain | dedup expected by ID, but extra columns differ |
| Security | tenant filter missing in one arm |
| Type | incompatible result types |
| Ordering | relying on implicit output order |
| Scope | wrong `LIMIT` / `ORDER BY` scope |
| NULL | unsafe `EXCEPT` → `NOT IN` rewrite |
| Performance | unnecessary duplicate elimination |
| Architecture | manual union masking a lifecycle/partitioning issue |
| Maintainability | deeply nested unparenthesized set logic |

This classification helps distinguish the fix from the symptom.

## 51. Testing Strategy

For each set operation, test at least:

1. Empty A, non-empty B.
2. Non-empty A, empty B.
3. Both empty.
4. Identical inputs.
5. Disjoint inputs.
6. Partial overlap.
7. Duplicate rows within each input.
8. Different duplicate multiplicities.
9. `NULL` values where relevant.
10. Type boundary cases.
11. Multi-tenant isolation.
12. Large-cardinality workloads.
13. Deterministic ordering requirements.
14. Pagination behavior.

Set-operation tests should validate **both content and cardinality**.

## 59. Interview Questions — Foundation

### Q1. What is UNION?

Expected answer:

> It combines two union-compatible query results and removes duplicate complete rows.

### Q2. UNION vs UNION ALL?

> `UNION` removes duplicates; `UNION ALL` preserves them.

### Q3. Does UNION preserve order?

> No. Explicit `ORDER BY` is required for ordering guarantees.

### Q4. What does EXCEPT do?

> Returns distinct rows from the left query that are absent from the right query.

### Q5. What does INTERSECT do?

> Returns distinct rows occurring in both query results.

### Q6. What does UNION-compatible mean?

> Same number of output columns with corresponding compatible types.

---

## 60. Interview Questions — Senior

### Q1. Why can UNION be slower than UNION ALL?

Because `UNION` must eliminate duplicates, adding work beyond executing the two query arms.

### Q2. Why might UNION fail to deduplicate a business entity?

Because deduplication compares complete result rows, not an implicit business key.

### Q3. How would you compare two migrated tables?

Use directional `EXCEPT` checks for missing/extra rows and project business attributes for changed-row comparisons.

### Q4. Why can EXCEPT and NOT IN differ?

`NOT IN` has special three-valued logic around `NULL`, so they are not interchangeable rewrites.

### Q5. When would you use UNION ALL in an archive/current architecture?

When rows are logically independent and duplicate elimination is not part of the business rule, subject to verified lifecycle invariants.

## 66. Final Mental Model

Remember this:

```text
SET OPERATION = combine already-shaped relations

UNION
→ A or B
→ distinct rows

UNION ALL
→ A + B
→ preserve multiplicity

INTERSECT
→ A and B
→ distinct common rows

INTERSECT ALL
→ A and B
→ preserve common multiplicity

EXCEPT
→ A − B
→ distinct directional difference

EXCEPT ALL
→ A − B
→ preserve subtraction multiplicity
```

And always reason in this order:

```text
Business question
      ↓
Result grain
      ↓
Duplicate semantics
      ↓
Set operator
      ↓
Type compatibility
      ↓
Scope / parentheses
      ↓
Security boundaries
      ↓
Ordering / pagination
      ↓
Execution plan
      ↓
Measured performance
```
