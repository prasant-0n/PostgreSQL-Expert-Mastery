# 01.9 — Common Table Expressions (CTEs)

> **Phase:** 01 — Advanced SQL  
> **Chapter:** 01.9  
> **Target mastery:** L0 → L7  
> **Primary principle:** A CTE is a named query expression that improves composability and can participate in SELECT, INSERT, UPDATE, or DELETE workflows. It is a semantic tool first—not automatically a performance optimization, temporary table, or guaranteed materialization boundary.

---

## 1. Learning Objective

By the end of this chapter, you should be able to:

- explain what a CTE is in relational and SQL terms;
- distinguish a CTE from a temporary table, view, subquery, and derived table;
- reason about CTE scope, column naming, dependency order, and data flow;
- use multiple CTEs to build readable multi-stage queries without losing correctness;
- understand when PostgreSQL can inline a CTE and when materialization matters;
- deliberately use `MATERIALIZED` or `NOT MATERIALIZED` when appropriate;
- use data-modifying CTEs safely and understand their execution semantics;
- design recursive CTEs for trees, graphs, hierarchies, and dependency traversal;
- diagnose recursive termination and duplicate-path problems;
- reason about CTE effects on performance, cardinality, memory, and planning;
- audit AI-generated CTE-heavy SQL for hidden correctness and performance problems;
- choose between CTEs, subqueries, views, temporary tables, functions, and application code based on workload and invariants;
- defend your design at interview, production-review, and principal-engineer levels.

---

## 2. The Core Mental Model

A common beginner model is:

> “A CTE is like a temporary table declared with `WITH`.”

That model is useful only as a rough visual analogy and becomes dangerous when used literally.

A better model is:

```text
WITH
  stage_1 AS (...),
  stage_2 AS (... stage_1 ...),
  stage_3 AS (... stage_2 ...)
SELECT ...
FROM stage_3;
```

Think of the statement as a **single query graph**:

```text
Base Relations
      ↓
  CTE stage A
      ↓
  CTE stage B
      ↓
  CTE stage C
      ↓
Final Query
```

The CTE names create **logical names for intermediate relational expressions**.

That is the important abstraction.

### The engineering distinction

A CTE gives you:

- a name;
- a scope;
- a reusable relational expression within the statement;
- a way to structure dependencies;
- a place to isolate business logic into stages.

It does **not**, by definition, mean:

- a permanent object;
- a normal database table;
- an indexed table;
- a separately committed transaction;
- a guaranteed performance optimization;
- a guaranteed optimizer fence;
- persistence after the statement completes.

---

## 3. First Principles

SQL is fundamentally about describing a transformation from relations to a result relation.

A complicated query often has a logical pipeline:

```text
raw rows
→ filter
→ join
→ derive
→ group
→ rank
→ select final rows
```

Without CTEs, all stages may be embedded in one deeply nested expression.

With CTEs, the same logical pipeline can be named:

```text
WITH
filtered_orders AS (...),
order_totals AS (...),
ranked_customers AS (...)
SELECT ...;
```

The core value is therefore **composability and reasoning clarity**.

### CTEs and relational thinking

A non-recursive CTE can be viewed as:

```text
name := relational_expression
```

The final statement consumes the named expressions.

This is conceptually closer to **named query expressions in a statement** than to an application-managed temporary table.

---

## 4. Basic Syntax

```sql
WITH cte_name AS (
    SELECT ...
)
SELECT ...
FROM cte_name;
```

Multiple CTEs:

```sql
WITH
customer_base AS (
    SELECT id, tenant_id, status
    FROM customers
),
active_customers AS (
    SELECT *
    FROM customer_base
    WHERE status = 'active'
)
SELECT *
FROM active_customers;
```

### Explicit column names

```sql
WITH customer_base(customer_id, tenant_id, status) AS (
    SELECT id, tenant_id, status
    FROM customers
)
SELECT *
FROM customer_base;
```

Explicit names are especially useful when a complex expression would otherwise produce unclear column names.

---

## 5. CTE Scope

A CTE exists only for the statement in which its `WITH` clause appears.

```sql
WITH x AS (
    SELECT 1 AS value
)
SELECT * FROM x;
```

This is valid.

```sql
SELECT * FROM x;
```

This is not valid because `x` is no longer in scope.

### Scope principle

```text
statement
└── WITH scope
    ├── cte_a
    ├── cte_b
    └── final statement
```

Do not confuse this with:

- a temporary table, which is a database object with a session-oriented lifecycle;
- a view, which is a persistent schema object;
- a subquery alias, whose scope is local to its containing query expression.

---

## 6. CTE Dependency Ordering

Later CTEs can reference earlier CTEs in the same `WITH` list.

```sql
WITH
base AS (
    SELECT id, amount
    FROM payments
),
positive AS (
    SELECT *
    FROM base
    WHERE amount > 0
),
summarized AS (
    SELECT COUNT(*) AS count
    FROM positive
)
SELECT *
FROM summarized;
```

Think of the CTE list as a directed dependency graph:

```text
base
 ↓
positive
 ↓
summarized
```

A well-structured chain should generally make these dependencies easy to inspect.

### Engineering smell

A CTE chain like:

```text
cte1 → cte2 → cte3 → cte4 → cte5 → cte6 → cte7 → final
```

is not automatically wrong.

But excessive staging can indicate:

- duplicated transformations;
- unclear data grain;
- hidden business logic;
- repeated scans;
- poor query decomposition;
- a query being used as an application program.

The question is not “How many CTEs are there?”

The question is:

> “Does each stage create a useful, explainable semantic boundary?”

---

## 7. CTE vs Subquery

### Subquery

```sql
SELECT *
FROM (
    SELECT id, amount
    FROM payments
    WHERE amount > 0
) AS positive;
```

### CTE

```sql
WITH positive AS (
    SELECT id, amount
    FROM payments
    WHERE amount > 0
)
SELECT *
FROM positive;
```

These can express similar logic.

The difference is primarily structural readability, reuse within the statement, and the specific planning/materialization behavior of the resulting query.

### Rule

Use a CTE when naming an intermediate relation materially improves reasoning.

Do not mechanically rewrite every subquery into a CTE.

---

## 8. CTE vs Temporary Table

| Concern | CTE | Temporary Table |
|---|---|---|
| Lifetime | One statement | Session/transaction-oriented depending on definition |
| Schema object | No | Yes |
| Indexable separately | No | Yes |
| Can be reused across statements | No | Yes |
| Stats collected as independent table | No | Can be |
| Explicit materialization control | Yes, in supported cases | Naturally materialized |
| Best for | Query composition | Multi-step workflows |

### Decision rule

Use a CTE when the intermediate relation is part of **one logical statement**.

Use a temporary table when the intermediate result is itself an operational artifact that must:

- survive across statements;
- be independently indexed;
- be inspected repeatedly;
- participate in multiple subsequent operations;
- have independently managed statistics or lifecycle.

---

## 9. CTE vs View

A view is a persistent schema object.

```sql
CREATE VIEW active_customers AS
SELECT ...;
```

A CTE is local to one statement.

```sql
WITH active_customers AS (...)
SELECT ...;
```

### Good mental model

```text
CTE  = local query composition
VIEW = reusable schema-level abstraction
TEMP = operational intermediate state
```

---

## 10. Reusing a CTE

A CTE can be referenced multiple times.

```sql
WITH recent_orders AS (
    SELECT id, customer_id, total
    FROM orders
    WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT
    (SELECT COUNT(*) FROM recent_orders) AS order_count,
    (SELECT COALESCE(SUM(total), 0) FROM recent_orders) AS revenue;
```

This is where materialization behavior becomes important.

A logical expression may be referenced multiple times, but the actual execution strategy depends on PostgreSQL's planning decisions and explicit materialization directives.

---

## 11. Materialization: The Critical PostgreSQL Concept

A common misconception is:

> “Every CTE is always materialized first, then consumed.”

That is not the correct modern PostgreSQL mental model.

PostgreSQL can inline eligible non-recursive, side-effect-free CTEs into the surrounding query. This allows the planner to optimize the combined query rather than necessarily treating the CTE as a separate materialized relation.

### `MATERIALIZED`

You can explicitly request materialization:

```sql
WITH recent_orders AS MATERIALIZED (
    SELECT id, customer_id, total
    FROM orders
    WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT *
FROM recent_orders;
```

### `NOT MATERIALIZED`

You can explicitly request folding into the parent query where supported:

```sql
WITH recent_orders AS NOT MATERIALIZED (
    SELECT id, customer_id, total
    FROM orders
    WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT *
FROM recent_orders;
```

### Expert principle

```text
CTE keyword
   ≠
execution plan
```

The SQL text defines relational semantics; the planner determines the physical strategy subject to PostgreSQL's rules and explicit directives.

---

## 12. When Materialization Can Help

Materialization can be useful when an expensive intermediate computation is intentionally shared.

Conceptually:

```text
expensive CTE
   ↙       ↘
consumer A consumer B
```

Without a materialization boundary, the planner may choose a strategy that repeats work or otherwise optimizes each reference independently.

A deliberate materialization decision can make sense when:

- the intermediate result is expensive to compute;
- multiple consumers genuinely reuse it;
- recomputation would be costly;
- evaluating the expression once is desirable.

But this is not a generic rule.

Materialization can also hurt by:

- blocking useful predicate pushdown;
- preventing join reordering opportunities across the boundary;
- writing/reading a larger intermediate result;
- increasing memory or temporary I/O pressure;
- eliminating an efficient index-driven plan that could have been chosen after inlining.

Therefore:

> **Materialize because evidence supports it—not because “CTEs are faster.”**

---

## 13. `MATERIALIZED` vs `NOT MATERIALIZED`: Decision Framework

Ask four questions:

### Question 1 — Is the CTE expensive?

If not, the optimization may not matter.

### Question 2 — Is it referenced more than once?

A reused expensive expression is a stronger candidate for deliberate materialization.

### Question 3 — Can outer predicates safely push into the CTE?

If yes, inlining may enable substantially better plans.

### Question 4 — What does `EXPLAIN (ANALYZE, BUFFERS)` show?

That is the evidence.

---

## 14. A Classic CTE Performance Comparison

Suppose:

```sql
WITH expensive_orders AS (
    SELECT *
    FROM orders
    WHERE expensive_condition(order_payload)
)
SELECT COUNT(*)
FROM expensive_orders
WHERE tenant_id = 42;
```

One question is whether the planner can push the tenant restriction into the CTE's underlying relation.

If the query is instead forced into an unnecessary materialization boundary, PostgreSQL may have to produce a much larger intermediate result before filtering.

The engineering question is:

```text
Can we reduce the amount of data as early as possible?
```

but not blindly:

```text
“Push every filter everywhere.”
```

Correctness and planner semantics still come first.

---

## 15. CTEs and Data Grain

Every CTE should have an explicit mental grain.

For example:

```text
orders                → one row per order
order_items           → one row per order item
customer_monthly      → one row per customer per month
customer_summary      → one row per customer
```

This matters because CTE chains can hide grain changes.

### Dangerous example

```sql
WITH customer_orders AS (
    SELECT c.id, o.id AS order_id
    FROM customers c
    JOIN orders o ON o.customer_id = c.id
),
summary AS (
    SELECT id, COUNT(*)
    FROM customer_orders
    GROUP BY id
)
SELECT ...;
```

The query is only obviously correct if you understand:

```text
customer_orders = one row per customer-order relationship
summary         = one row per customer
```

A CTE name does not tell you its grain.

You must infer and document it yourself.

---

## 16. CTEs and Aggregation Safety

Consider an ERP reporting query with:

- one customer;
- many invoices;
- many invoice lines;
- many payments.

Naively joining everything can multiply rows.

A safer staged design may be:

```sql
WITH invoice_totals AS (
    SELECT customer_id, SUM(total) AS invoiced
    FROM invoices
    GROUP BY customer_id
),
payment_totals AS (
    SELECT customer_id, SUM(amount) AS paid
    FROM payments
    GROUP BY customer_id
)
SELECT
    c.id,
    COALESCE(i.invoiced, 0) AS invoiced,
    COALESCE(p.paid, 0) AS paid
FROM customers c
LEFT JOIN invoice_totals i ON i.customer_id = c.id
LEFT JOIN payment_totals p ON p.customer_id = c.id;
```

The important part is not “CTE syntax.”

The important part is **pre-aggregation to the intended grain before combining independently repeating relationships**.

The CTE simply makes that design explicit.

---

## 17. CTEs and Window Functions

CTEs are commonly used to separate aggregation/window stages because window functions operate on the rows visible at their stage.

Example:

```sql
WITH customer_totals AS (
    SELECT
        customer_id,
        SUM(total) AS revenue
    FROM orders
    GROUP BY customer_id
)
SELECT
    customer_id,
    revenue,
    RANK() OVER (ORDER BY revenue DESC) AS revenue_rank
FROM customer_totals;
```

Mental model:

```text
orders
 ↓
GROUP BY customer
 ↓
customer_totals
 ↓
window ranking
```

This makes the intended grain transition obvious.

---

## 18. CTEs and DML

PostgreSQL allows data-modifying statements inside a `WITH` clause.

For example:

```sql
WITH deleted_rows AS (
    DELETE FROM sessions
    WHERE expires_at < now()
    RETURNING id
)
SELECT COUNT(*)
FROM deleted_rows;
```

This is powerful because a modification can produce rows through `RETURNING` that subsequent parts of the statement can consume.

### Critical principle

A data-modifying CTE is part of **one statement**.

Do not reason about it like a sequence of separately committed SQL commands.

The statement's transactional semantics still govern the complete operation.

---

## 19. Data-Modifying CTE Example: Move Data

A classic pattern is:

```sql
WITH moved AS (
    DELETE FROM active_orders
    WHERE status = 'cancelled'
    RETURNING *
)
INSERT INTO cancelled_orders
SELECT *
FROM moved;
```

The conceptual workflow is:

```text
identify rows
   ↓
DELETE
   ↓ RETURNING
intermediate relation
   ↓
INSERT
```

This is useful for tightly coupled operations that should form one statement-level unit.

### Production caution

The moment the logic becomes complex enough that correctness depends on subtle side-effect ordering assumptions, stop and inspect the exact PostgreSQL semantics. A CTE chain is not a general-purpose procedural workflow language.

---

## 20. Recursive CTEs

A recursive CTE references itself.

General shape:

```sql
WITH RECURSIVE cte_name AS (
    -- non-recursive seed
    SELECT ...

    UNION ALL

    -- recursive step
    SELECT ...
    FROM cte_name
    JOIN ...
)
SELECT *
FROM cte_name;
```

Think:

```text
seed
 ↓
iteration 1
 ↓
iteration 2
 ↓
iteration 3
 ↓
...
 ↓
termination
```

---

## 21. Recursive CTE Mental Model

A recursive query has two conceptual components:

```text
Anchor / Seed
     ↓
Recursive Term
     ↓
New Rows
     ↓
Recursive Term
     ↓
New Rows
     ↓
Termination
```

This is fundamentally different from a normal CTE.

A normal CTE describes a non-recursive relational expression.

A recursive CTE describes an iterative fixpoint-style computation over query results.

---

## 22. Simple Hierarchy Example

Suppose:

```text
CEO
├── VP Engineering
│   ├── Backend Lead
│   └── Frontend Lead
└── VP Sales
    └── Sales Manager
```

Table:

```sql
employees(
    id,
    name,
    manager_id
)
```

Recursive query:

```sql
WITH RECURSIVE org AS (
    SELECT
        id,
        name,
        manager_id,
        0 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT
        e.id,
        e.name,
        e.manager_id,
        o.depth + 1
    FROM employees e
    JOIN org o
      ON e.manager_id = o.id
)
SELECT *
FROM org
ORDER BY depth, id;
```

The seed finds roots.

Each recursive step finds children of the rows discovered previously.

---

## 23. Recursive Termination

A recursive query must converge toward termination.

Dangerous pattern:

```text
A → B → C → A → B → C → ...
```

Possible causes include:

- cyclic data;
- an incorrect recursive join;
- no visited-state tracking;
- a recursive predicate that does not reduce the search space.

For production systems, treat recursive correctness as a graph problem, not simply a SQL syntax problem.

---

## 24. Recursive Paths and Cycle Detection

When traversing graphs, you may need to carry a path.

Conceptually:

```text
current node
+
visited path
```

Example pattern:

```sql
WITH RECURSIVE graph AS (
    SELECT
        id,
        ARRAY[id] AS path
    FROM nodes
    WHERE id = 1

    UNION ALL

    SELECT
        e.child_id,
        g.path || e.child_id
    FROM graph g
    JOIN edges e
      ON e.parent_id = g.id
    WHERE NOT e.child_id = ANY(g.path)
)
SELECT *
FROM graph;
```

The path is now both:

- traversal state;
- a cycle-prevention mechanism.

### Cost

Maintaining a path has a cost that grows with traversal depth.

Do not add path tracking blindly on a massive graph without understanding the workload.

---

## 25. `UNION ALL` vs `UNION` in Recursion

This distinction is critical.

### `UNION ALL`

Preserves duplicates.

Advantages:

- cheaper;
- avoids global duplicate elimination;
- often the expected recursive primitive.

Risk:

- duplicate expansion can explode;
- cycles can become disastrous.

### `UNION`

Performs duplicate elimination.

This can act as part of a termination/deduplication strategy, but it may also introduce substantial work.

Never choose between them by habit.

Ask:

```text
Should duplicate rows represent distinct paths,
or are repeated states logically the same state?
```

---

## 26. Recursive CTEs for Bill of Materials

A manufacturing ERP may have:

```text
finished product
   ↓
subassembly
   ↓
component
   ↓
raw material
```

A recursive CTE can expand the dependency graph.

The engineering questions become:

- What is the node identity?
- What defines an edge?
- Can cycles exist?
- What does quantity multiplication mean across levels?
- What is the maximum expected depth?
- Should repeated components be merged by identity or preserved by path?
- How do effective dates affect edge validity?

SQL syntax is the easy part.

The graph semantics are the hard part.

---

## 27. Recursive CTEs for Permission Inheritance

For hierarchical permissions:

```text
organization
  ↓
department
  ↓
team
  ↓
user
```

A recursive query might calculate inherited visibility.

But production security requires asking:

- Is inheritance additive or overriding?
- Are deny rules possible?
- Are cycles impossible by constraint?
- Is tenant isolation maintained at every edge?
- Can a user escape a tenant through an incorrect recursive join?

A recursive CTE can compute a correct graph while still implementing the wrong security model.

---

## 28. CTEs and Multi-Tenancy

A CTE can accidentally remove tenant boundaries.

Dangerous:

```sql
WITH recent_orders AS (
    SELECT *
    FROM orders
    WHERE created_at >= now() - INTERVAL '30 days'
)
SELECT ...
FROM recent_orders;
```

If downstream logic assumes tenant filtering already occurred, the query is unsafe.

Safer design:

```sql
WITH recent_orders AS (
    SELECT *
    FROM orders
    WHERE tenant_id = $1
      AND created_at >= now() - INTERVAL '30 days'
)
SELECT ...
FROM recent_orders;
```

### Expert rule

For tenant-sensitive data, explicitly identify the invariant:

```text
Every path from source table
→ intermediate relation
→ final result
must preserve tenant isolation.
```

Never infer that from a CTE name such as `tenant_orders`.

---

## 29. CTEs and Financial Correctness

Suppose you need:

```text
invoice total
- payment total
= outstanding balance
```

A safe architecture can calculate each independently at the correct grain:

```sql
WITH invoice_totals AS (
    SELECT customer_id, SUM(total) AS invoice_total
    FROM invoices
    GROUP BY customer_id
),
payment_totals AS (
    SELECT customer_id, SUM(amount) AS payment_total
    FROM payments
    GROUP BY customer_id
)
SELECT
    c.id,
    COALESCE(i.invoice_total, 0) - COALESCE(p.payment_total, 0) AS outstanding
FROM customers c
LEFT JOIN invoice_totals i ON i.customer_id = c.id
LEFT JOIN payment_totals p ON p.customer_id = c.id;
```

The CTE structure protects the calculation from cross-product multiplication.

But additional correctness questions remain:

- currency consistency;
- rounding policy;
- reversal/void semantics;
- settlement timing;
- partial payments;
- credit notes;
- timezone boundaries for reporting periods.

A readable CTE does not automatically make a financial query correct.

---

## 30. CTEs and Temporal Logic

A useful pattern is staging temporal boundaries:

```sql
WITH period AS (
    SELECT
        TIMESTAMPTZ '2026-01-01 00:00:00+00' AS start_at,
        TIMESTAMPTZ '2026-02-01 00:00:00+00' AS end_at
),
orders_in_period AS (
    SELECT o.*
    FROM orders o
    CROSS JOIN period p
    WHERE o.created_at >= p.start_at
      AND o.created_at < p.end_at
)
SELECT COUNT(*)
FROM orders_in_period;
```

The half-open interval:

```text
[start, end)
```

is usually easier to compose than an inclusive end boundary.

The CTE here gives the reporting period a name and makes its scope explicit.

---

## 31. CTEs and Query Readability

A professional CTE should have a meaningful semantic name:

Good:

```text
active_customers
monthly_revenue
unpaid_invoices
eligible_inventory
ranked_products
```

Poor:

```text
t1
t2
temp
data1
result2
```

A CTE name should communicate **what relation it represents**, not how it was produced.

---

## 32. CTE Naming as Documentation

A strong chain can read almost like a specification:

```sql
WITH
eligible_orders AS (...),
settled_orders AS (...),
customer_revenue AS (...),
ranked_customers AS (...)
SELECT ...;
```

The naming should let another engineer answer:

- What business concept does this stage represent?
- What is its row grain?
- What filters have been applied?
- What invariants are established?

without reverse-engineering every expression immediately.

---

## 33. The “One Transformation per CTE” Heuristic

A useful heuristic is to let each CTE establish one meaningful transformation:

```text
CTE 1 → filter
CTE 2 → normalize
CTE 3 → aggregate
CTE 4 → rank
```

This is not a law.

Too many microscopic CTEs can make a query harder to follow.

The correct unit is a **semantic transformation**, not a line count.

---

## 34. When CTEs Become Over-Engineering

A query like:

```sql
WITH a AS (SELECT ...),
b AS (SELECT * FROM a),
c AS (SELECT * FROM b),
d AS (SELECT * FROM c)
SELECT * FROM d;
```

adds no useful abstraction.

The extra layers increase cognitive load.

### Anti-pattern

```text
CTE because “professional SQL uses CTEs”
```

No.

Professional SQL uses the simplest representation that makes semantics correct, reviewable, and operationally appropriate.

---

## 35. CTEs and the Planner

A CTE must never be analyzed only from the written SQL.

For production performance, inspect the actual plan:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
WITH ...
SELECT ...;
```

Questions to ask:

- Was the CTE inlined?
- Is there a materialization node?
- Did predicates get pushed down?
- Did row estimates match reality?
- Are repeated references causing repeated work?
- Did the intermediate relation become unexpectedly large?
- Is there disk spilling?
- Did the CTE prevent an otherwise better join order?

---

## 36. CTE Performance Investigation Workflow

Use this sequence:

```text
1. Establish expected semantics
2. Establish row grain
3. Identify intermediate cardinalities
4. Run EXPLAIN
5. Run EXPLAIN ANALYZE
6. Add BUFFERS when appropriate
7. Compare estimates vs actuals
8. Inspect materialization/inlining behavior
9. Test alternative SQL shape
10. Measure before choosing
```

Never optimize a CTE because it “looks slow.”

Measure the actual bottleneck.

---

## 37. CTEs and Predicate Pushdown

One major advantage of inlining is that the surrounding query may be able to constrain the underlying scan earlier.

Conceptually:

```text
Without useful optimization boundary:
large intermediate relation
      ↓
filter

With successful pushdown:
base scan + filter
      ↓
smaller relation
```

This can dramatically reduce:

- rows read;
- join input size;
- memory use;
- sort work;
- aggregation work.

Therefore an unnecessary materialization boundary can be expensive.

---

## 38. CTEs and Predicate Pushdown: Do Not Oversimplify

“Predicate pushdown is always good” is also an unsafe slogan.

The actual query may involve:

- volatile expressions;
- security semantics;
- data-modifying statements;
- recursion;
- duplicate-sensitive operations;
- expensive expressions where repeated evaluation matters.

Optimization must preserve semantics.

The planner is solving a constrained optimization problem—not following a generic “push filters” checklist.

---

## 39. CTEs and Volatility / Side Effects

Not all CTE expressions are interchangeable from an optimization perspective.

When a query expression has observable side effects or special evaluation behavior, PostgreSQL must preserve the required semantics.

This is one reason the simplistic model:

> “A CTE is just text substitution.”

is wrong.

And the opposite model:

> “A CTE is always a temp table.”

is also wrong.

The correct model is planner-aware relational composition governed by SQL semantics and PostgreSQL's optimization rules.

---

## 40. CTEs and `SELECT *`

Avoid excessive `SELECT *` in long CTE pipelines.

Why?

Because intermediate relations can carry unnecessary columns through:

```text
storage
→ scan
→ join
→ sort
→ aggregate
→ materialization
→ downstream consumer
```

Selecting only the needed columns can improve readability and sometimes reduce data movement/materialization costs.

Prefer:

```sql
SELECT customer_id, total
FROM orders
```

over:

```sql
SELECT *
FROM orders
```

when the downstream schema is known.

---

## 41. CTEs as a Debugging Instrument

A powerful production-debugging technique is to expose stages temporarily.

Suppose a final query returns incorrect totals.

Instead of debugging the entire statement at once:

```text
final result
```

inspect:

```text
eligible_orders
↓
order_totals
↓
customer_totals
↓
ranked_customers
```

At each stage measure:

- row count;
- distinct key count;
- NULL frequency;
- duplicate frequency;
- numeric totals;
- tenant count;
- min/max timestamps.

This converts a vague final-result bug into a stage-local invariant failure.

---

## 42. CTEs as a Data-Quality Firewall

A staging CTE can establish invariants:

```sql
WITH valid_orders AS (
    SELECT id, customer_id, total
    FROM orders
    WHERE customer_id IS NOT NULL
      AND total >= 0
)
SELECT ...
FROM valid_orders;
```

But remember:

```text
query-time filtering
≠ database-level integrity
```

If the business invariant is:

> “Every order must have a valid customer,”

then a CTE filter only hides invalid rows from that particular query.

A database constraint may be the actual correct enforcement mechanism.

---

## 43. CTEs vs Constraints

Bad design:

```text
bad data exists
↓
CTE filters it everywhere
```

Better:

```text
data invariant
↓
constraint / schema enforcement
↓
CTE expresses query-specific business logic
```

Use CTEs to derive information.

Use constraints to enforce structural invariants whenever the invariant truly belongs to the database layer.

---

## 44. Security: CTEs Do Not Create Security Boundaries

A CTE name such as:

```text
safe_customers
```

does not make the data secure.

Security depends on:

- roles;
- privileges;
- row-level security;
- secure function behavior;
- tenant predicates;
- `search_path` and object resolution where relevant;
- application authorization.

Treat CTEs as query composition, not authorization.

---

## 45. AI-Generated CTE Failure Pattern #1 — “CTE = Faster”

AI may generate:

```text
WITH filtered AS (...)
SELECT ...
```

and imply that breaking the query into CTEs automatically improves performance.

Wrong mental model:

```text
more CTEs → more optimization → faster
```

Correct:

```text
CTE structure → clearer semantics
planner behavior → actual physical strategy
workload + evidence → performance conclusion
```

---

## 46. AI-Generated CTE Failure Pattern #2 — Hidden Cardinality Changes

An AI-generated CTE may silently add:

```sql
DISTINCT
```

or an aggregate to “clean duplicates.”

This may hide a join bug while changing business semantics.

Audit:

```text
What duplicates existed?
Why were they produced?
Should duplicates exist logically?
What business grain should remain?
```

Never accept `DISTINCT` as a universal duplicate fix.

---

## 47. AI-Generated CTE Failure Pattern #3 — Tenant Filter Applied Too Late

Bad generated structure:

```sql
WITH all_data AS (
    SELECT ... FROM orders
),
filtered AS (
    SELECT * FROM all_data
    WHERE tenant_id = $1
)
...
```

This may still be logically correct in some cases, but the security/performance review should not stop at the final predicate.

Ask:

- Are all intermediate joins tenant-safe?
- Can another branch of the query reintroduce cross-tenant data?
- Does RLS provide defense in depth?
- Is there a more efficient stage at which to enforce the known tenant boundary?

---

## 48. AI-Generated CTE Failure Pattern #4 — Recursive Query Without a Termination Argument

Never approve a recursive CTE because it “returns results on test data.”

Require a termination argument:

```text
What strictly limits expansion?
How are cycles handled?
What is the maximum expected depth?
What prevents repeated states?
What happens with malformed data?
```

A recursive query can be correct for a tree fixture and dangerous for a production graph containing one unexpected cycle.

---

## 49. Wrong Approach → Better Approach

### Wrong

> “I always use CTEs because they are more readable and faster.”

### Problem

Readability and performance are separate dimensions.

### Better

Ask:

```text
Does naming this relation improve comprehension?
What is its grain?
Will the planner inline it?
If not, is that boundary beneficial?
What evidence supports the chosen shape?
```

## 50. Production Scenario — ERP Customer Statement

Requirement:

> Show every customer with invoice total, payment total, outstanding amount, last payment date, and rank by outstanding balance within the tenant.

A strong design decomposes the semantics:

```text
invoices → invoice totals
payments → payment totals + last payment
combine at customer grain
rank within tenant
```

Potential CTE architecture:

```text
invoice_totals
payment_summary
customer_balance
ranked_balances
final
```

Each stage has a clear grain.

The final query becomes easier to review for:

- tenant safety;
- duplicate multiplication;
- monetary correctness;
- ranking semantics;
- pagination behavior.

The CTEs are valuable because they expose the architecture of the query.

---

## 51. Production Scenario — Inventory Reservation

Suppose you need:

```text
available stock
= on_hand
- reserved
- allocated
```

A dangerous query can multiply warehouse rows, reservation rows, and allocation rows.

A CTE-based approach can calculate each independently:

```text
stock_by_sku
reservation_by_sku
allocation_by_sku
availability_by_sku
```

The critical invariant is:

```text
one row per tenant + warehouse + SKU
```

before combining the components.

The CTE architecture is therefore a **grain-control mechanism**.

---

## 52. Production Scenario — Audit / Reconciliation

For reconciliation:

```text
source ledger
      ↓
source aggregate
      ↓
reported aggregate
      ↓
comparison
```

CTEs make the reconciliation stages explicit:

```sql
WITH source AS (...),
reported AS (...),
diff AS (
    SELECT ...
)
SELECT * FROM diff;
```

This is an excellent use case because each intermediate relation has a concrete business meaning and can be inspected during incident analysis.

---

## 53. Testing CTE-Based Queries

A professional query test should not only validate the final row.

For critical SQL, validate invariants such as:

```text
expected grain
expected tenant count
expected distinct keys
expected total amount
expected non-negative balances
expected date boundaries
expected no duplicate logical entities
```

### Example test ideas

For `customer_totals`:

```sql
SELECT COUNT(*)
FROM customer_totals;
```

Compare with:

```sql
SELECT COUNT(DISTINCT customer_id)
FROM customers;
```

The counts may differ legitimately because not every customer has transactions, but the difference should be explainable.

## 54. Benchmarking CTE Variants

When performance matters, test competing shapes:

```text
A: nested subquery
B: plain CTE
C: MATERIALIZED CTE
D: NOT MATERIALIZED CTE
E: pre-aggregated derived tables
F: temporary table
```

Compare:

- execution time;
- planning time;
- buffers hit/read;
- rows processed;
- sort behavior;
- memory usage;
- temporary I/O;
- concurrency behavior.

Do not conclude from a single warm-cache run.

For meaningful benchmarks, control:

- data size;
- statistics freshness;
- cache state where relevant;
- parameter distribution;
- concurrency;
- repeated execution count.

---

## 55. CTE Anti-Patterns

### Anti-pattern 1 — CTE everywhere

Creates artificial complexity.

### Anti-pattern 2 — CTE as a performance superstition

Confuses logical structure with physical execution.

### Anti-pattern 3 — `SELECT *` through every stage

Carries unnecessary columns.

### Anti-pattern 4 — Recursive CTE without graph invariants

Can produce runaway work or incorrect traversal.

### Anti-pattern 5 — Using a CTE to hide bad schema design

Query complexity can become a bandage for structural problems.

### Anti-pattern 6 — Using CTEs as procedural code

A large CTE chain can become difficult to reason about and may be better represented by a schema-level design, procedure, temporary staging workflow, or application orchestration.

### Anti-pattern 7 — Ignoring the execution plan

A syntactically elegant query can still be operationally terrible.

## 56. Decision Matrix

| Need | Strong candidate |
|---|---|
| Name one logical stage in one statement | CTE |
| Reuse stage in many statements | View / temp table |
| Independently index intermediate result | Temp table |
| Persistent reusable abstraction | View |
| Complex multi-step stateful workflow | Temp/staging workflow or application/process logic |
| Recursive hierarchy/graph traversal | Recursive CTE, when workload fits relational execution |
| Enforce invariant | Constraint / database mechanism |
| Authorization | Roles / RLS / secure access patterns |
| Optimize a query | Evidence + plan analysis, not “more CTEs” |

## 57. Expert Review Checklist

Before approving a non-trivial CTE query, ask:

### Semantics

- What does each CTE represent?
- What is the grain of each stage?
- What columns are required?
- Where are duplicates intentionally preserved or removed?

### Correctness

- Are joins cardinality-safe?
- Are NULL semantics explicit?
- Are temporal boundaries correct?
- Are financial calculations at the correct grain?
- Are tenant boundaries preserved?

### Planner

- Is the CTE likely to be inlined?
- Is materialization intentional?
- Does `EXPLAIN` support the expected plan?
- Are estimates reasonable?

### Recursive queries

- What is the seed?
- What is the recursive step?
- What is the termination argument?
- How are cycles handled?
- What is the maximum expected depth?

### Operations

- What happens at 10× the data volume?
- What happens under concurrency?
- Can the intermediate result become huge?
- Is temporary disk usage bounded?

## 65. The Deeper Lesson

CTEs teach an important database-engineering principle:

> **Readable SQL is not merely shorter SQL. It is SQL whose semantic stages are visible.**

A good CTE chain exposes:

```text
data meaning
→ grain
→ transformation
→ invariant
→ business result
```

A bad CTE chain merely wraps complexity in names.

The goal is not to maximize CTE usage.

The goal is to maximize **semantic clarity without sacrificing correctness or operational efficiency**.

---

## 66. What an Expert Should Be Able to Say

A weak answer:

> “CTEs are temporary tables for complex queries.”

A stronger answer:

> “A CTE is a statement-scoped named query expression that lets us structure a query into semantic stages.”

An expert answer:

> “I first treat each CTE as a relational expression with an explicit grain and invariant. Then I determine whether PostgreSQL can inline it, whether deliberate materialization changes the available optimization space, and whether that physical choice is beneficial for the workload. For recursive CTEs, I additionally reason about graph identity, duplicate/path semantics, termination, and cycle handling. I validate the conclusion with execution plans and workload evidence rather than assuming the `WITH` syntax determines performance.”

That is the level this curriculum is targeting.
