# 01.19 — Range Types

> **Phase 01 — Advanced SQL**  
> **Chapter objective:** Master PostgreSQL range and multirange types as first-class data-modeling primitives for intervals, scheduling, validity windows, versioning, pricing bands, availability, temporal integrity, and overlap-aware querying.

---

## 1. Why This Chapter Exists

Many applications model an interval using two scalar columns:

```sql
start_at TIMESTAMPTZ,
end_at   TIMESTAMPTZ
```

That representation is simple, but the database now has to infer the meaning of the pair every time a query needs to ask a range question:

- Does one interval contain a point?
- Do two intervals overlap?
- Are they adjacent?
- Which interval starts first?
- Does a requested booking conflict with an existing booking?
- How should open-ended intervals be represented?
- Are endpoints inclusive or exclusive?
- Can the database enforce non-overlap under concurrency?

PostgreSQL provides **range types** so the interval itself becomes a typed value.

Instead of:

```sql
start_at TIMESTAMPTZ,
end_at   TIMESTAMPTZ
```

we can model:

```sql
during TSTZRANGE
```

Then the domain concept becomes directly queryable:

```sql
WHERE during && tstzrange($1, $2, '[)')
```

That is more than syntactic convenience. It changes the semantic boundary of the model.

A range can encode:

```text
lower bound
upper bound
lower inclusivity
upper inclusivity
unboundedness
emptiness
subtype
```

and PostgreSQL provides operators, functions, indexes, aggregates, multiranges, and constraints around those semantics.

Current PostgreSQL 18 documentation describes ranges as types that represent a range of values of a subtype, with built-in range and corresponding multirange types, plus support for user-defined range types. citeturn700328search2turn700328search5

# 3. Three Levels of Definition

## 3.1 Simple Definition

A PostgreSQL range is a single value representing an interval between a lower and upper boundary.

Examples:

```text
[1, 10)
[2026-01-01, 2026-02-01)
[09:00, 17:00)
```

The brackets matter.

```text
[  = inclusive
(  = exclusive
```

For example:

```text
[1, 10)
```

contains 1 but does not contain 10.

---

## 3.2 Engineering Definition

A range is a typed PostgreSQL value whose bounds belong to a specific subtype and whose representation carries interval semantics such as bound inclusivity, unboundedness, and emptiness.

Examples:

```sql
int4range
int8range
numrange
daterange
tsrange
tstzrange
```

A range therefore packages data and the rules for interpreting that data into one database value.

---

## 3.3 Expert Definition

A range is a first-class domain value over an ordered subtype. PostgreSQL supplies type-specific operators, comparison semantics, canonicalization for suitable discrete ranges, GiST/SP-GiST indexing support where applicable, multirange counterparts, and declarative mechanisms such as exclusion constraints and `WITHOUT OVERLAPS`.

The important architectural shift is:

> **Do not model an interval as two unrelated columns when the interval itself is the business concept.**

---

# 4. First Principles: What Is an Interval?

Consider a booking:

```text
start = 10:00
end   = 11:00
```

The application usually means a set of points in time.

That set may be represented as:

```text
[10:00, 11:00)
```

meaning:

```text
10:00 <= t < 11:00
```

This is extremely useful for consecutive intervals.

Consider:

```text
[10:00, 11:00)
[11:00, 12:00)
```

They touch but do not overlap.

This convention is particularly useful for scheduling and temporal validity because the endpoint `11:00` belongs to the second interval and not the first.

That gives a composable partition:

```text
[10, 11) + [11, 12) = [10, 12)
```

without double-counting `11`.

---

# 5. Mental Model

Think of a range as a mathematical set with metadata describing its boundaries.

For a range:

```text
[10, 20)
```

think:

```text
10 <= x < 20
```

For:

```text
(10, 20]
```

think:

```text
10 < x <= 20
```

For:

```text
(,20)
```

think:

```text
x < 20
```

For:

```text
[10,)
```

think:

```text
x >= 10
```

For:

```text
empty
```

think:

```text
there are no values in the set
```

The mental shift is important:

```text
start/end fields
```

become:

```text
one value answering interval questions
```

# 6. Built-in Range Types

PostgreSQL provides built-in ranges over commonly used ordered types.

| Range | Subtype |
|---|---|

| `numrange` | `numeric` |
| `tsrange` | `timestamp without time zone` |
| `tstzrange` | `timestamp with time zone` |
| `daterange` | `date` |

Each built-in range has a corresponding multirange type. citeturn700328search5

Examples:

```sql

int8multirange
nummultirange

```

# 7. Choosing the Correct Temporal Range

This decision matters.

## `tsrange`

Use when the business meaning is based on a `timestamp without time zone`.

```sql
tsrange
```

This is suitable when the time value is intentionally interpreted without a global timezone identity.

## `tstzrange`

Use when the business meaning is based on an absolute point in time represented by PostgreSQL's timestamp-with-time-zone semantics.

For globally relevant events, bookings, audit windows, synchronization windows, or distributed systems, this is often the stronger choice.

## `daterange`

Use when time-of-day is not part of the business concept.

For example:

```text
employee leave: 2026-09-10 through 2026-09-15
```

If the business wants calendar dates rather than timestamps, `daterange` expresses that directly.

---

# 8. Constructing Ranges

There are several ways to construct ranges.

## 8.1 Constructor Functions

Prefer explicit constructors when clarity matters:

```sql
SELECT int4range(1, 10);
```

Result conceptually:

```text
[1,10)
```

Timestamp:

```sql
SELECT tstzrange(
    '2026-09-01 09:00+05:30',
    '2026-09-01 17:00+05:30',
    '[)'
);
```

Date:

```sql
SELECT daterange('2026-09-01', '2026-10-01', '[)');
```

---

## 8.2 Range Literal Casting

```sql
SELECT '[1,10)'::int4range;
```

Timestamp range:

```sql
SELECT '[2026-09-01 09:00,2026-09-01 17:00)'::tsrange;
```

For production SQL, constructor functions are often easier to read when input values originate from parameters.

---

# 9. The Bounds String

The third argument to range constructors controls inclusivity.

```sql
'[)'
```

means:

```text
lower inclusive
upper exclusive
```

Other possibilities:

```text
[]  inclusive / inclusive
()  exclusive / exclusive
[)  inclusive / exclusive
(]  exclusive / inclusive
```

Examples:

```sql
SELECT int4range(1, 5, '[]');
SELECT int4range(1, 5, '[)');
SELECT int4range(1, 5, '(]');
SELECT int4range(1, 5, '()');
```

Do not casually change endpoint semantics because an API designer finds one representation visually easier.

Endpoint semantics are part of the domain model.

---

# 10. Open-Ended and Unbounded Ranges

A range can omit one or both boundaries.

```sql
SELECT int4range(NULL, 10);
SELECT int4range(10, NULL);
SELECT int4range(NULL, NULL);
```

Conceptually:

```text
(,10)
[10,)
(,)
```

These are not the same thing as SQL `NULL` for the entire range column.

This distinction is fundamental.

---

# 11. NULL Range vs Unbounded Range

Consider:

```sql
CREATE TABLE plans (
    id bigint,
    valid_period daterange
);
```

These values communicate different meanings:

```sql
NULL
```

may mean:

> No validity interval has been defined.

Whereas:

```sql
[2026-01-01,)
```

means:

> Valid from 2026-01-01 indefinitely into the future.

And:

```sql
(,2026-12-31]
```

means:

> Valid indefinitely into the past up to the specified boundary.

Never collapse these meanings without an explicit business decision.

---

# 12. Empty Ranges

An empty range contains no values.

```sql
SELECT int4range(10, 10, '[)');
```

For the half-open representation, this is empty.

Test it:

```sql
SELECT isempty(int4range(10, 10, '[)'));
```

The result is:

```text
true
```

An empty range is not equivalent to SQL `NULL`.

That distinction affects:

- constraints
- containment
- overlap
- aggregates
- application logic
- API serialization

---

# 13. Canonicalization

Discrete subtypes such as integers and dates can be represented using equivalent endpoint conventions.

For example, these describe the same set of dates:

```text
[2026-01-01, 2026-02-01)
[2026-01-01, 2026-01-31]
```

For canonical discrete ranges, PostgreSQL can normalize equivalent representations to a standard form.

This is one reason ranges should not be mentally modeled as merely two endpoint fields.

The logical set is more important than a particular textual spelling.

The catalog for range types records optional canonicalization and subtype-difference functions; `rngcanonical` is used for discrete range types, while `rngsubdiff` can improve GiST index performance. citeturn700328search0

---

# 14. Continuous vs Discrete Semantics

## Discrete subtype

Examples:

```text
integer
bigint
date
```

There is a notion of the next representable value.

For dates:

```text
2026-01-01
2026-01-02
2026-01-03
```

## Continuous-like subtype

Examples:

```text
numeric
timestamp
```

There is not necessarily a single obvious next value with business meaning.

Do not assume that canonicalization rules from `daterange` translate directly to `numrange` or timestamp ranges.

# 15. Inspecting a Range

Useful functions include:

```sql
lower(r)
upper(r)
lower_inc(r)
upper_inc(r)
lower_inf(r)
upper_inf(r)
isempty(r)
```

Example:

```sql
SELECT
    lower(period),
    upper(period),
    lower_inc(period),
    upper_inc(period),
    lower_inf(period),
    upper_inf(period),
    isempty(period)
FROM subscriptions;
```

PostgreSQL 18 documents these range inspection functions and notes that `lower`/`upper` return `NULL` for empty or unbounded sides as appropriate. citeturn700328search12

# 16. Core Range Operators

These are the operators you should recognize immediately.

| Operator | Meaning |
|---|---|
| `@>` | contains |
| `<@` | contained by |
| `&&` | overlaps |
| `<<` | strictly left of |
| `>>` | strictly right of |
| `&<` | does not extend right of |
| `&>` | does not extend left of |
| `-|-` | adjacent |
| `+` | union, producing one range |
| `*` | intersection |
| `-` | difference |

PostgreSQL supplies these specialized operators for range values. citeturn700328search13

---

# 17. Containment: `@>`

Range contains range:

```sql
SELECT int4range(1, 10) @> int4range(3, 5);
```

Conceptually:

```text
[1,10) contains [3,5)
```

Range contains element:

```sql
SELECT int4range(1, 10) @> 5;
```

This is one of the most useful operations for availability and validity models.

Example:

```sql
SELECT *
FROM employee_contracts
WHERE valid_period @> CURRENT_DATE;
```

Meaning:

> Find contracts valid at the current date.

---

# 18. Reverse Containment: `<@`

```sql
SELECT int4range(3, 5) <@ int4range(1, 10);
```

Read this as:

> Does the left range lie completely inside the right range?

It is often easier to read SQL when you choose the operator orientation that matches the business sentence.

---

# 19. Overlap: `&&`

This is the most important operator for many scheduling systems.

```sql
SELECT
    tstzrange('2026-09-10 10:00+00', '2026-09-10 11:00+00', '[)')
    &&
    tstzrange('2026-09-10 10:30+00', '2026-09-10 11:30+00', '[)');
```

Result:

```text
true
```

This directly expresses:

> Do these intervals overlap?

Compare that with the traditional scalar-column expression:

```sql
WHERE requested_start < existing_end
  AND existing_start < requested_end
```

Both can be correct, but the range representation gives the interval a first-class type and opens the door to range-specific operators and constraints.

---

# 20. The Boundary Case That Exposes Bad Models

Consider:

```text
A = [10:00, 11:00)
B = [11:00, 12:00)
```

Do they overlap?

No.

```sql
A && B
```

is false.

Are they adjacent?

Yes.

```sql
A -|- B
```

is true.

This is exactly why boundary semantics must be deliberate.

---

# 21. Left and Right Relationships

Strictly left:

```sql
A << B
```

means the first range ends before the second in the range ordering relationship.

Strictly right:

```sql
A >> B
```

means the first range is to the right.

Additional relationships:

```sql
A &< B
A &> B
```

These ask whether one range does not extend beyond the corresponding side of the other.

Do not memorize these in isolation. Practice translating them into diagrams.

---

# 22. Union, Intersection, Difference

## Union

```sql
SELECT
    int4range(1, 5) + int4range(5, 10);
```

The result is one continuous range when the values overlap or are adjacent.

## Intersection

```sql
SELECT
    int4range(1, 10) * int4range(5, 15);
```

Result:

```text
[5,10)
```

## Difference

```sql
SELECT
    int4range(1, 10) - int4range(4, 6);
```

This produces two disjoint pieces conceptually:

```text
[1,4)
[6,10)
```

A single range cannot represent two disjoint pieces.

That leads directly to multiranges.

---

# 23. Why Multiranges Exist

A multirange is an ordered collection of non-contiguous, non-empty, non-null ranges.

For example:

```text
{[1,4), [6,10)}
```

represents a set with a gap.

This is exactly what you need for:

- availability windows
- business hours with lunch breaks
- employee working time
- blackout periods
- multiple active validity windows
- fragmented inventory availability

PostgreSQL provides a corresponding multirange type for each built-in range type. citeturn700328search5

---

# 24. Multirange Construction

Example:

```sql
SELECT '{[1,4), [6,10)}'::int4multirange;
```

Or create from ranges using constructors/aggregates appropriate to the workload.

PostgreSQL 18 also exposes range aggregation such as:

```sql
range_agg(range_value)
```

which returns a multirange representing the union of non-null inputs. citeturn700328search4

---

# 25. Range vs Multirange

Use a **range** when the business concept is one interval.

Use a **multirange** when the business concept is multiple disjoint intervals as one value.

Examples:

```text
Reservation:
    tstzrange

Store weekly availability:
    tsmultirange

Contract valid continuously from Jan to Dec:
    daterange

Customer eligibility with several separate periods:
    datemultirange
```

Do not choose multirange merely because it looks more powerful.

Choose it because the domain actually permits multiple disjoint intervals.

---

# 26. Multirange Operations

Multiranges support analogous interval reasoning.

Examples:

```sql
SELECT
    '{[1,10), [20,30)}'::int4multirange
    &&
    int4range(5, 6);
```

Intersection:

```sql
SELECT
    '{[1,10), [20,30)}'::int4multirange
    *
    '{[5,15), [25,40)}'::int4multirange;
```

The result may contain multiple ranges.

For disjoint union and difference, multiranges solve the representational limitation of a single range. PostgreSQL's documentation explicitly notes that range union/difference can fail when a result would require two disjoint pieces, while multirange operations can represent that result. citeturn700328search13

---

# 27. Aggregating Ranges

Suppose a resource has several occupied windows:

```sql
SELECT resource_id, range_agg(during)
FROM reservations
GROUP BY resource_id;
```

This produces a multirange describing the union of the non-null input ranges.

Other useful aggregation logic includes intersection through:

```sql
range_intersect_agg(...)
```

PostgreSQL 18 documents both `range_agg` and `range_intersect_agg`. citeturn700328search4

---

# 28. Production Scheduling Model

A strong schema for one reservation per resource might be:

```sql
CREATE TABLE reservations (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    resource_id bigint NOT NULL,
    during      tstzrange NOT NULL,
    customer_id bigint NOT NULL,
    CHECK (NOT isempty(during))
);
```

Example insert:

```sql
INSERT INTO reservations (
    resource_id,
    during,
    customer_id
)
VALUES (
    42,
    tstzrange(
        '2026-09-15 10:00+00',
        '2026-09-15 11:00+00',
        '[)'
    ),
    9001
);
```

The important part is that the reservation duration itself is one value.

# 29. Enforcing Non-Overlap

A race condition exists in application-only validation.

Bad approach:

```text
Request A checks for conflict → none found
Request B checks for conflict → none found
Request A inserts
Request B inserts
```

Both requests observed the database before the conflicting write became visible.

The database should own the invariant.

PostgreSQL exclusion constraints are designed for this class of problem. The constraint ensures that the specified operator comparisons cannot all be true for two rows, and the constraint automatically creates the corresponding index. citeturn375829search1

Example:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE reservations
ADD CONSTRAINT reservations_no_overlap
EXCLUDE USING gist (
    resource_id WITH =,
    during      WITH &&
);
```

Meaning:

> For the same `resource_id`, no two `during` ranges may overlap.

This is vastly stronger than:

```ts
await checkConflict();
await insertReservation();
```

performed purely in application code.

---

# 30. Why `btree_gist` Appears

A multicolumn exclusion constraint may compare:

```text
resource_id WITH =
during      WITH &&
```

The range uses GiST-native support. The scalar equality column can use GiST-equivalent behavior supplied by the `btree_gist` extension.

Current PostgreSQL documentation says `btree_gist` supplies GiST operator classes with B-tree-like behavior for many scalar types and is useful when a multicolumn GiST index mixes a range-indexable value with ordinary scalar comparisons. citeturn375829search20turn375829search2

Important:

> `btree_gist` does not mean "GiST is a better B-tree." It exists to provide GiST operator classes for cases where a multicolumn GiST strategy or exclusion constraint needs them.

---

# 31. PostgreSQL 18 `WITHOUT OVERLAPS`

PostgreSQL 18 supports temporal-style uniqueness through `WITHOUT OVERLAPS`.

For example, a constraint can express the concept of:

```sql
UNIQUE (resource_id, during WITHOUT OVERLAPS)
```

The documentation describes this as behaving like an exclusion constraint conceptually equivalent to equality on the ordinary columns plus `&&` on the range. citeturn375829search0

This gives schema designers a more declarative way to state temporal uniqueness.

The critical mental model is still:

```text
same identity key
AND
no overlapping validity intervals
```

Do not treat the syntax as magic. Understand the underlying invariant.

---

# 32. Exclusion Constraint vs Application Validation

## Naive Approach

```text
1. SELECT for conflicting interval
2. If none exists, INSERT
```

## Why It Fails

Concurrent transactions can both pass the check.

## Improved Approach

Use a database constraint:

```sql
EXCLUDE USING gist (...)
```

or the supported temporal uniqueness syntax where appropriate.

## Why It Works

The invariant is enforced by the database, not by timing-sensitive application code.

## Production Considerations

Handle the resulting constraint violation as a normal expected business conflict:

```text
reservation attempt
    ↓
constraint conflict
    ↓
translate database error
    ↓
HTTP 409 / domain conflict
```

Do not return HTTP 500 for every reservation race.

---

# 33. Indexing Range Queries

GiST is the central indexing technology for range-aware operations.

Example:

```sql
CREATE INDEX reservations_during_gist_idx
ON reservations
USING gist (during);
```

Then:

```sql
SELECT *
FROM reservations
WHERE during && tstzrange($1, $2, '[)');
```

can become indexable depending on table size, selectivity, statistics, and planner costing.

GiST stands for Generalized Search Tree. It is an extensible balanced tree framework that supports specialized data semantics rather than only ordinary scalar ordering. citeturn375829search2

---

# 34. Do Not Assume an Index Will Always Be Used

This query:

```sql
WHERE during && $requested_range
```

may use a GiST index.

But PostgreSQL may still choose a sequential scan when:

- the table is small
- the predicate is not selective
- statistics indicate many matches
- the cost of index access exceeds scanning
- the query returns a large fraction of the table

This is normal planner behavior.

Never diagnose "missing index" from a query plan without measuring the workload.

# 36. Range Comparison Is Not the Same as Set Relationship

Range types also support ordinary comparison operators, but their ordering is primarily useful for sorting and internal mechanisms rather than as a replacement for semantic operators such as `&&` and `@>`. PostgreSQL documents comparison ordering in terms of lower and then upper bounds and notes that this ordering is usually not the useful business concept. citeturn700328search3

Therefore:

```sql
ORDER BY during
```

is valid.

But do not replace:

```sql
WHERE during && $query_range
```

with a collection of `<` and `>` conditions merely because you know the values have endpoints.

Use the operator that expresses the business relation.

---

# 37. Range Types vs Two Timestamp Columns

## Two Columns

```sql
start_at timestamptz,
end_at   timestamptz
```

Advantages:

- familiar to most developers
- simple ORM mapping
- straightforward reporting
- easy interoperability with systems that do not understand ranges

Disadvantages:

- interval semantics are split across columns
- overlap logic must be repeated
- bound semantics can drift
- open-ended values need conventions
- database constraints become more verbose
- range-specific operators are unavailable

## Range Column

```sql
during tstzrange
```

Advantages:

- interval is first-class
- operators directly express the domain
- GiST indexing
- exclusion constraints
- multirange integration
- fewer duplicated interval expressions

Disadvantages:

- some ORMs have weaker native support
- application developers may be unfamiliar with range syntax
- API serialization needs a defined contract
- BI/reporting tools may expect scalar start/end fields

The right decision depends on the system boundary, not ideology.

---

# 38. Range vs Array

An array represents multiple values.

```sql
integer[]
```

A range represents a continuous interval over an ordered subtype.

```sql
int4range
```

Do not model:

```text
1 through 1,000,000
```

as an array of one million integers when the business concept is simply a continuous interval.

Use a range when the semantics are:

```text
all values between A and B
```

Use an array when the semantics are:

```text
these specific discrete values
```

---

# 39. Range vs JSONB

Bad schema:

```json
{
  "start": "2026-09-15T10:00:00Z",
  "end": "2026-09-15T11:00:00Z"
}
```

when interval overlap is a first-class domain operation.

A proper range gives the database native interval semantics.

JSONB may still be appropriate when the interval configuration is only one small part of a polymorphic document and interval querying is not a core query pattern.

The architectural question is:

> Does the database need to understand the interval as an interval?

If yes, a native range deserves serious consideration.

---

# 40. Range vs Child Table

Suppose a customer has many validity windows.

Option A:

```sql
customer.valid_period datemultirange
```

Option B:

```sql
customer_validity_periods (
    customer_id,
    valid_period
)
```

Choose a child table when each interval needs independent identity, metadata, audit history, permissions, relationships, or lifecycle.

Choose a multirange when the collection behaves as one mathematical set belonging to the parent.

This distinction prevents overusing multiranges as an alternative to relational modeling.

---

# 41. Temporal Validity Pattern

A common design is:

```sql
CREATE TABLE product_prices (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id    bigint NOT NULL,
    price         numeric(12,2) NOT NULL,
    valid_during  tstzrange NOT NULL,
    EXCLUDE USING gist (
        product_id WITH =,
        valid_during WITH &&
    )
);
```

This says:

> Two price records for the same product cannot be active during overlapping periods.

That is substantially stronger than an application convention such as:

```text
"We always remember to close the old record before creating the new one."
```

# 42. Temporal Versioning Pattern

Imagine:

```text
Customer tier:
    Silver   [Jan 1, Mar 1)
    Gold     [Mar 1, Jun 1)
    Platinum [Jun 1, )
```

The range column can directly represent the validity period.

Queries become natural:

```sql
SELECT *
FROM customer_tiers
WHERE customer_id = $1
  AND valid_during @> $effective_at;
```

The query asks exactly what the business asks:

> Which version is valid at this moment?

# 43. Bitemporal Thinking

A more advanced model may distinguish:

```text
valid time
transaction/system time
```

For example:

```sql
valid_during    tstzrange,
recorded_during tstzrange
```

This enables questions such as:

> What was believed to be true on September 1 about the state that was valid on August 15?

This is a much larger modeling topic, but mastering native ranges is foundational for serious temporal data engineering.

# 44. Timezone Danger

Consider these concepts:

```text
10:00 local time
10:00 UTC
10:00 Asia/Kolkata
```

They are not interchangeable.

For globally meaningful instants, prefer:

```sql
tstzrange
```

and pass timezone-aware instants from the application.

Do not silently:

```text
parse local time
→ attach server timezone
→ convert
→ store
```

without explicitly understanding the business timezone.

DST transitions make this particularly dangerous.

A range model cannot rescue a wrong temporal interpretation at the application boundary.

# 45. Node.js / NestJS Boundary

Your API may receive:

```json
{
  "start": "2026-09-15T10:00:00+05:30",
  "end": "2026-09-15T11:00:00+05:30"
}
```

The service should validate:

```text
start exists
end exists
start < end
timezone interpretation is explicit
```

Then bind parameters and construct the range in PostgreSQL:

```sql
tstzrange($1::timestamptz, $2::timestamptz, '[)')
```

Avoid string concatenation:

```ts
`'[${start},${end})'`
```

Parameterize values and let PostgreSQL construct a typed range.

This is both safer and more explicit.

# 46. API Design: Range Serialization

A range should not be serialized into an ambiguous string and left undocumented.

A practical API contract can expose:

```json
{
  "start": "2026-09-15T10:00:00Z",
  "end": "2026-09-15T11:00:00Z",
  "bounds": "[)"
}
```

or, when the application standard is fixed:

```json
{
  "start": "2026-09-15T10:00:00Z",
  "end": "2026-09-15T11:00:00Z"
}
```

with `[)` documented as the invariant.

For open-ended values, define whether the API uses:

```json
"end": null
```

for an unbounded upper range versus:

```json
"period": null
```

for an absent range.

These must mean different things if the database model distinguishes them.

# 47. Common Mistake: `NULL` Means Everything

Incorrect reasoning:

```text
valid_period IS NULL
=> valid forever
```

That is a business convention, not PostgreSQL range semantics.

Correct model:

```text
NULL       = no range value
[date, )   = open-ended range
```

Keep the distinction.

---

# 48. Common Mistake: Wrong Endpoint Convention

Suppose a booking system uses inclusive end times:

```text
10:00–11:00 inclusive
11:00–12:00 inclusive
```

Then 11:00 belongs to both bookings.

Developers may then add arbitrary one-second adjustments:

```text
end = 10:59:59
```

This is fragile.

A half-open convention is usually much cleaner:

```text
[10:00,11:00)
[11:00,12:00)
```

The exact convention is a domain decision, but it should be explicit and consistent.

---

# 49. Common Mistake: Application-Only Overlap Checks

Incorrect:

```sql
SELECT 1
FROM reservations
WHERE resource_id = $1
  AND during && $requested
LIMIT 1;
```

then, if no row is returned:

```sql
INSERT ...
```

This is useful as an early user-friendly check, but it is not a sufficient concurrency invariant.

The database constraint remains the final authority.

---

# 50. Common Mistake: Trigger Instead of Constraint

A trigger may be able to detect overlapping ranges, but that does not automatically make it the best tool.

A declarative exclusion constraint directly states the invariant.

Prefer the simplest mechanism that fully enforces the requirement.

Use triggers only when the rule genuinely requires procedural logic beyond what constraints express.

---

# 51. Common Mistake: Treating `+` as Set Union Without Checking Representation

This can fail:

```sql
SELECT int4range(1, 3) + int4range(5, 8);
```

because the result would require two disjoint intervals and a single range cannot represent that.

When disjoint output is valid, use multirange semantics instead.

This is a powerful lesson:

> The type's representational model constrains which algebraic operations are possible.

---

# 52. Common Mistake: Using Scalar Comparisons Instead of Range Operators

Developers sometimes expand:

```sql
WHERE during && $requested
```

into manually extracted bounds.

That can introduce mistakes around:

- unbounded ranges
- empty ranges
- inclusivity
- canonicalization
- nullability

Prefer the native operator whenever it expresses the requirement.

# 53. AI / Vibe-Coding Failure Patterns

AI-generated PostgreSQL code commonly makes mistakes such as:

### Failure 1 — Inventing an interval type

```sql
intervalrange
```

There is no generic built-in range type named like that. Choose an actual range type based on the subtype.

### Failure 2 — Mixing `timestamp` and `timestamptz`

```sql
tstzrange(timestamp_column, timestamptz_column)
```

without understanding implicit conversion and business timezone semantics.

### Failure 3 — String-building range literals

```ts
`[${start},${end})`
```

without robust escaping and type-aware parameterization.

### Failure 4 — Checking conflicts in JavaScript only

```ts
const conflict = await repo.find(...);
if (!conflict) await repo.insert(...);
```

without a database invariant.

### Failure 5 — Assuming GiST automatically means fast

An index can exist and still be the wrong index or the wrong plan.

### Failure 6 — Using a multirange because "it supports many values"

A multirange is not a generic array replacement.

### Failure 7 — Treating `NULL` as unbounded

These are different semantic states.

# 54. Security Considerations

Ranges themselves are not an authorization mechanism.

Consider:

```sql
WHERE tenant_id = $tenant
  AND valid_during @> $now
```

A range predicate does not replace tenant isolation.

For a multi-tenant system, authorization predicates must remain part of the query architecture.

Also:

- parameterize endpoints
- validate client-provided timestamps
- avoid SQL string construction
- constrain impossible intervals
- audit changes to sensitive validity windows

# 55. Reliability Considerations

A robust range schema should define:

```text
1. subtype
2. timezone semantics
3. bound convention
4. whether empty is legal
5. whether unbounded endpoints are legal
6. whether overlaps are allowed
7. whether adjacent ranges should merge logically
8. who owns conflict handling
```

For example:

```sql
period tstzrange NOT NULL,
CHECK (NOT isempty(period))
```

plus an exclusion constraint if overlap is forbidden.

The database should reject impossible states rather than relying on developer discipline.

# 57. Testing Strategy

Do not test only:

```text
normal interval overlaps normal interval
```

Test the boundary matrix.

### Case A — Exact adjacency

```text
A = [10,11)
B = [11,12)
```

Expected:

```text
overlap = false
adjacent = true
```

### Case B — Partial overlap

```text
A = [10,12)
B = [11,13)
```

Expected:

```text
overlap = true
```

### Case C — Full containment

```text
A = [10,20)
B = [12,15)
```

Expected:

```text
A @> B = true
```

### Case D — Identical ranges

```text
A = [10,20)
B = [10,20)
```

Expected:

```text
overlap = true
```

### Case E — Empty range

Must be tested separately.

### Case F — Unbounded lower

```text
(,20)
```

### Case G — Unbounded upper

```text
[10,)
```

### Case H — `NULL` range

Must remain semantically distinct from unboundedness.

# 58. Property-Based Testing Ideas

Advanced test suites should verify invariants rather than only examples.

For generated intervals A and B:

```text
If A and B overlap, their intersection should not be empty.

If A is contained by B, then A && B must be true unless A is empty.

For a continuous valid range A:
    lower(A) <= upper(A)
```

Also test algebraic properties where applicable:

```text
A * B = B * A
A + B = B + A
```

with the caveat that not every pair of ranges has a representable single-range union.

The goal is to test the mathematical contract, not just the SQL syntax.

# 62. Custom Range Types

PostgreSQL can define custom range types over suitable subtypes.

Conceptually:

```sql

```

Custom ranges are an advanced capability and should be introduced only when the domain genuinely needs a first-class interval type beyond the built-ins.

A custom range design should carefully consider:

- canonical representation
- subtype difference function

- empty representation

# 63. Range Indexing Is Domain-Specific

A B-tree answers questions efficiently in scalar ordering.

A range overlap query asks something more complex:

```text
Does these two sets have any points in common?
```

GiST exists specifically to support generalized search semantics.

PostgreSQL describes GiST as an extensible framework in which specialized data types can define appropriate search behavior, with the index framework handling core concerns such as searching, concurrency, and logging. citeturn375829search2

That is the deeper reason GiST appears so often with ranges.

# 64. Performance: Large Tables

For millions of bookings, a naive overlap query can become a serious bottleneck.

A common production shape is:

```sql
WHERE resource_id = $1
  AND during && $2
```

The schema should be designed around both dimensions:

```text
resource identity
interval relationship
```

An exclusion constraint often naturally models that combination using a multicolumn GiST index.

But measure:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

Do not assume theoretical indexability equals production performance.

# 65. Performance: Hotspot Resources

Imagine one resource receives 80% of all booking attempts.

Even a correct GiST index cannot eliminate application-level contention around the same logical resource.

You may observe:

```text
high conflict rate
transaction retries
queueing
lock waits
constraint exceptions
```

This is now a workload/concurrency problem, not merely an indexing problem.

The next architectural questions may involve:

- request deduplication
- transaction scope
- retry policy
- queueing

- resource partitioning

# 66. Performance: Avoid Unnecessary Range Rewrites

For mutable schedule data, updating a range may rewrite the row and index entries.

If the range changes frequently, examine:

```text
row width
index count
WAL volume
vacuum behavior
hot update possibilities
```

The best representation is the one that supports the workload without creating unnecessary write amplification.

# 74. Wrong Implementation: JavaScript Interval Algebra

Naive approach:

```ts
const intervals = await repo.find({ resourceId });

intervals.sort(...);

// manually merge and subtract ranges
```

Why this can fail:

- more data crosses the network
- logic duplicates database semantics
- concurrency can invalidate the read set
- timezone normalization is duplicated
- large datasets increase application CPU and memory

Improved approach:

> Push set-oriented interval operations to PostgreSQL when PostgreSQL already has the semantic primitives.

Do not move data processing into Node.js merely because Node.js feels easier to write.

# 75. Wrong Implementation: Range as String

Bad schema:

```sql
period text
```

containing:

```text
2026-09-15T10:00:00Z/2026-09-15T11:00:00Z
```

Now every query has to parse and reinterpret the string.

You lose:

- native type checking
- range operators
- range functions
- native range indexing
- exclusion semantics

A string is not a temporal model merely because its contents look like a timestamp pair.

# 76. Wrong Implementation: Integer Duration Instead of Range

Suppose:

```sql
duration_minutes integer
```

is stored without a start time.

This may be fine when duration alone is the concept.

But if the business asks:

> Does this interval overlap another interval?

then duration alone is insufficient.

A duration is not a range.

```text
duration = how long
range = where the interval lies
```

# 77. Decision Framework

Use this flow:

```text
Do you have an interval?
        |
        +-- No → use scalar type
        |
        +-- Yes
             |
             +-- One continuous interval?
             |       |
             |       +-- Yes → range
             |
             +-- Multiple disjoint intervals as one value?
                     |
                     +-- Yes → multirange
```

Then ask:

```text
Does every interval have independent metadata or identity?
        |
        +-- Yes → child table is likely better
```

Then ask:

```text
Must overlap be prohibited?
        |
        +-- Yes → database constraint
```

Then:

```text
Will overlap/containment queries be frequent?
        |
        +-- Yes → evaluate GiST indexing
```

This is architecture-first reasoning.

# 84. Interview Questions — Foundation

### Q1. What is a PostgreSQL range type?

A typed value representing an interval over an ordered subtype, including boundary semantics and support for range-specific operations.

### Q2. Difference between `tsrange` and `tstzrange`?

They use different timestamp subtypes and therefore represent different temporal semantics.

### Q3. What does `[)` mean?

Lower inclusive, upper exclusive.

### Q4. Difference between `NULL` range and an unbounded range?

`NULL` means no range value; an unbounded range has an actual interval with an omitted boundary.

### Q5. What does `&&` mean?

The two ranges overlap.

### Q6. What does `@>` mean?

Contains; it can apply to another range or an element, depending on operand types.

### Q7. Why use GiST with ranges?

It supports generalized range-search semantics such as overlap and containment.

### Q8. Why use an exclusion constraint?

To enforce cross-row invariants such as no overlapping periods.

---

# 85. Interview Questions — Intermediate

### Q1. Why are half-open ranges useful?

They allow adjacent intervals to touch without overlapping and reduce endpoint ambiguity.

### Q2. Why can range union fail?

A single range can only represent one continuous interval; disjoint output requires multiple ranges.

### Q3. Why use multirange?

To represent multiple disjoint intervals as one value and support set-like range algebra.

### Q4. Why isn't application-side conflict checking sufficient?

Concurrent requests can both pass the check before either inserts; the database must enforce the invariant.

### Q5. When might a child table be better than a multirange?

When each interval needs independent metadata, identity, relationships, permissions, lifecycle, or auditability.

---

# 86. Expert Questions

### Q1. How does canonicalization affect equality?

For discrete range types with canonical functions, equivalent set representations can normalize into a canonical representation, reducing semantic ambiguity.

### Q2. What metadata does `pg_range` expose?

Subtype, multirange relationship, collation, subtype operator class, optional canonicalization, and optional subtype-difference support. citeturn700328search0

### Q3. Why can `btree_gist` be necessary in an exclusion constraint?

Because the constraint may need GiST operator classes for scalar equality alongside a range overlap operator.

### Q4. What is the conceptual relationship between `WITHOUT OVERLAPS` and exclusion?

PostgreSQL documents temporal uniqueness using `WITHOUT OVERLAPS` as behaving like an equality constraint on the key plus non-overlap semantics on the range. citeturn375829search0

### Q5. Why should range comparison ordering not be confused with overlap semantics?

Because ordering is a sort relation, while overlap/containment are domain relations. A sorted order does not directly answer whether two intervals intersect.

```text
"How can the database search these domain-specific relationships efficiently?"
```

An exclusion constraint answers:

```text
"What cross-row interval relationships are forbidden?"
```

And a strong temporal architecture answers:

```text
"What is valid, when is it valid, and who guarantees that the invariant remains true under concurrency?"
```

That is the real purpose of PostgreSQL range types.

# 91. What You Should Never Forget

> **A range is not just two timestamps stored together.**

It is a typed domain value with semantics.

> **`NULL`, unbounded, and empty are different states.**

Do not collapse them casually.

> **`[)` is a convention, not a law.**

Choose endpoint semantics deliberately and enforce them consistently.

> **Application checks are not concurrency constraints.**

When overlap is forbidden, make the database own the invariant.

> **GiST is not "the index for everything."**

Measure whether the workload benefits from it.

> **Multirange is for disjoint intervals, not generic collections.**

Use it when the mathematical model actually requires it.

> **Temporal bugs are usually semantic bugs before they are SQL bugs.**

Timezone, endpoint, and validity semantics must be correct before optimization begins.

> **Model the domain directly whenever PostgreSQL has a type that expresses it.**

That is the deepest lesson of this chapter.

# 92. Chapter Summary

PostgreSQL range types provide a native representation for interval-valued data. They support boundary-aware containment, overlap, adjacency, ordering relationships, intersection, union, and difference. PostgreSQL also provides multiranges for sets of disjoint intervals. Built-in range types cover integer, numeric, date, timestamp, and timestamp-with-time-zone domains, with user-defined ranges also possible. citeturn700328search5turn700328search0

The production significance is larger than the syntax. Range types let schemas model temporal and interval invariants directly. GiST makes range-aware indexing possible, while exclusion constraints can enforce no-overlap requirements at the database boundary. PostgreSQL 18 additionally provides temporal uniqueness syntax through `WITHOUT OVERLAPS`. citeturn375829search2turn375829search1turn375829search0

The expert's job is not to memorize every operator. It is to reason precisely about:

```text
meaning
→ representation
→ invariants
→ concurrency
→ indexing
→ workload
→ application boundary
→ observability
```

When those decisions are correct, range types become one of PostgreSQL's most powerful tools for temporal and interval-heavy systems.
