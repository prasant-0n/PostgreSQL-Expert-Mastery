# 01.12 — INSERT / UPDATE / DELETE

> **Phase:** 01 — Advanced SQL  
> **Level:** Advanced → Expert  
> **Primary goal:** Build a correct mental model for PostgreSQL data-modification statements and learn to design writes that remain correct under concurrency, constraints, triggers, large datasets, multi-tenancy, APIs, retries, and failures.

---

## 1. Why This Chapter Matters

Reading data is only half of database engineering. Production systems spend enormous effort making writes safe.

A write can fail because of:

- invalid input
- violated constraints
- concurrent changes
- foreign-key dependencies
- locks
- stale assumptions
- triggers
- row-level security
- statement timeouts
- deadlocks
- application retries
- transaction boundaries
- partial batches
- duplicate requests
- incorrect `WHERE` clauses
- incorrect join cardinality
- poor indexing

The key mindset is:

> **A DML statement is not merely a command that changes rows. It is a state transition executed inside PostgreSQL's transactional and concurrency system.**

A senior engineer therefore asks:

```text
What rows are eligible?
        ↓
Which rows are actually modified?
        ↓
What constraints and policies apply?
        ↓
What locks are acquired?
        ↓
What happens under concurrency?
        ↓
What values are produced after triggers/defaults?
        ↓
How does the application know what changed?
        ↓
What happens if the request is retried?
```

# 3. The DML Mental Model

Think of a DML statement as a pipeline rather than a line of SQL.

```text
Client Request
      ↓
SQL Statement
      ↓
Parse / Analyze / Rewrite
      ↓
Plan
      ↓
Find Candidate Rows
      ↓
Lock / Visibility Checks
      ↓
Evaluate Expressions
      ↓
Apply Constraints / Policies
      ↓
Apply BEFORE Triggers
      ↓
Modify Row Version / Index Entries
      ↓
Apply AFTER Triggers / Deferred Work
      ↓
RETURNING Projection
      ↓
Command Result
      ↓
Commit / Rollback
```

The exact internals vary by statement and feature, but this model is extremely useful when debugging production behavior.

### The critical distinction

```text
Rows matching WHERE
        ≠
Rows successfully modified
        ≠
Rows returned by RETURNING
```

For example, an `UPDATE` may identify rows, but a trigger can suppress a modification, a policy can restrict visibility/eligibility, a constraint can reject the statement, or an `ON CONFLICT DO UPDATE ... WHERE` condition can prevent an update for a conflicting row.

# 4. INSERT — Creating State

## 4.1 Basic Form

```sql
INSERT INTO users (name, email)
VALUES ('Prasanta', 'prasanta@example.com');
```

The production-grade habit is to specify the target column list.

### Fragile form

```sql
INSERT INTO users
VALUES ('Prasanta', 'prasanta@example.com');
```

### Why fragile?

It couples application code to the table's declared column order.

Schema evolution can turn a previously valid statement into incorrect or failing behavior.

### Better

```sql
INSERT INTO users (name, email)
VALUES ('Prasanta', 'prasanta@example.com');
```

---

## 4.2 Multiple Rows

```sql
INSERT INTO products (sku, name, price)
VALUES
    ('SKU-100', 'Ring', 25000),
    ('SKU-101', 'Chain', 40000),
    ('SKU-102', 'Bracelet', 18000);
```

One statement can insert multiple rows.

This is generally preferable to issuing many independent insert statements from an application when the data can be safely batched.

But batch size is a workload decision, not an absolute rule.

Large batches can increase:

- transaction duration
- lock duration
- WAL generation
- memory use
- statement latency
- rollback cost
- replication lag

So:

> **Batch until the workload says stop, not until a generic rule says stop.**

# 5. INSERT ... SELECT

A powerful pattern for set-based writes is:

```sql
INSERT INTO archived_orders (order_id, customer_id, total, archived_at)
SELECT order_id, customer_id, total, now()
FROM orders
WHERE status = 'completed'
  AND completed_at < now() - interval '1 year';
```

The important conceptual shift is:

```text
Application loop:
    read row
    construct object
    send INSERT
    repeat

Database set operation:
    derive relation
    ↓
    insert relation
```

Set-based operations often reduce network round trips and allow PostgreSQL to optimize the operation as a whole.

# 6. Defaults, Identity, Generated Values, and Triggers

A newly inserted row can acquire values from multiple layers:

```text
Explicit application value
        ↓
Column DEFAULT
        ↓
Identity / sequence behavior
        ↓
Generated-column behavior
        ↓
BEFORE trigger modifications
        ↓
Constraint checks
        ↓
AFTER trigger effects
```

These mechanisms should not be mentally collapsed into one category.

### Example

```sql
CREATE TABLE invoices (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    subtotal numeric(18,2) NOT NULL,
    tax numeric(18,2) NOT NULL,
    total numeric(18,2) GENERATED ALWAYS AS (subtotal + tax) STORED
);
```

The database can own important invariants instead of relying entirely on application code.

# 7. RETURNING — The Atomic Write/Read Bridge

One of PostgreSQL's most valuable DML features is `RETURNING`.

```sql
INSERT INTO users (name, email)
VALUES ('A', 'a@example.com')
RETURNING id, created_at;
```

Instead of:

```text
INSERT
  ↓
SELECT generated ID
  ↓
SELECT current row again
```

we can do:

```text
INSERT
  ↓
RETURNING
```

PostgreSQL documents `RETURNING` for `INSERT`, `UPDATE`, `DELETE`, and `MERGE`; in PostgreSQL 18, `OLD` and `NEW` can also be referenced explicitly in the `RETURNING` list. citeturn146162search1turn146162search3

### Example — update audit information

```sql
UPDATE products
SET price = price * 1.10
WHERE category_id = 7
RETURNING
    id,
    old.price AS old_price,
    new.price AS new_price,
    new.price - old.price AS delta;
```

This is powerful because the values describe the modification performed by the statement itself.

### Trigger interaction

The data available to `RETURNING` reflects the row as modified by triggers, which makes `RETURNING` useful for retrieving database-computed results. citeturn146162search1

# 8. UPDATE — State Transition, Not Assignment

The naïve mental model is:

```text
UPDATE = change a column
```

A better model is:

```text
Find eligible rows
        ↓
Compute new row values
        ↓
Validate transition
        ↓
Create new row version
```

Example:

```sql
UPDATE products
SET price = price * 1.10
WHERE category_id = 7;
```

The right question is not merely:

> What value should this column have?

It is:

> Which rows are allowed to transition from the current state to the new state?

---

# 9. The Most Dangerous UPDATE Bug

This statement is syntactically valid:

```sql
UPDATE accounts
SET status = 'closed';
```

But if the intended predicate was:

```sql
WHERE id = $1;
```

then the missing predicate is a catastrophic correctness failure.

### Production write checklist

Before executing an `UPDATE`, be able to answer:

```text
How many rows should match?
How many rows should change?
What prevents accidental broad updates?
Can the same request execute twice?
What happens under concurrent updates?
```

A useful development technique is first running:

```sql
SELECT id
FROM accounts
WHERE ...;
```

and validating the candidate set before issuing the write.

# 10. UPDATE ... FROM

PostgreSQL supports joining additional tables into an `UPDATE`.

```sql
UPDATE products p
SET price = price * d.multiplier
FROM discounts d
WHERE p.category_id = d.category_id;
```

This is powerful but dangerous when the join is not one-to-one.

## 10.1 Cardinality Hazard

Suppose:

```text
products
product_id = 10

matched discount rows:
category_id = 5, multiplier = 1.10
category_id = 5, multiplier = 1.20
```

Then the join produces multiple source rows for the same target row.

PostgreSQL documents that, with `UPDATE ... FROM`, each join output row represents an update operation, and the join should be arranged so that at most one source row corresponds to each target row; otherwise which source row is used can be unpredictable. citeturn146162search2

### Dangerous assumption

> "The database will pick the correct matching row."

It should not be left to chance.

### Safer design

First produce exactly one source row per target key.

```sql
WITH chosen_discount AS (
    SELECT DISTINCT ON (category_id)
           category_id,
           multiplier
    FROM discounts
    ORDER BY category_id, priority DESC, id DESC
)
UPDATE products p
SET price = price * d.multiplier
FROM chosen_discount d
WHERE p.category_id = d.category_id;
```

The key invariant is:

```text
1 target row
    ↕
0 or 1 source row
```

---

# 11. Updating Based on Aggregates

Example:

```sql
UPDATE customers c
SET lifetime_value = x.total_value
FROM (
    SELECT customer_id, SUM(total) AS total_value
    FROM orders
    GROUP BY customer_id
) x
WHERE c.id = x.customer_id;
```

The derived relation establishes the correct grain before updating.

```text
orders: many rows/customer
        ↓
aggregate
        ↓
1 row/customer
        ↓
UPDATE customers
```

This is safer than joining a raw detail table directly into the update.

# 12. DELETE — Destructive State Transition

Basic:

```sql
DELETE FROM sessions
WHERE expires_at < now();
```

Without a predicate:

```sql
DELETE FROM sessions;
```

all rows qualify.

For safety-critical tables, destructive operations deserve explicit validation and operational controls.

---

# 13. DELETE Using Other Tables

PostgreSQL supports `USING`:

```sql
DELETE FROM orders o
USING customers c
WHERE o.customer_id = c.id
  AND c.status = 'blocked';
```

The same cardinality and correctness principles from joins apply.

PostgreSQL also supports subqueries for delete conditions. citeturn146162search4

---

# 14. DELETE vs TRUNCATE

Do not mentally equate them.

```text
DELETE
    row-oriented DML
    supports WHERE
    supports RETURNING
    interacts with row-level deletion semantics

TRUNCATE
    removes all rows from a table quickly
    different locking and operational semantics
    not a substitute for arbitrary DELETE logic
```

PostgreSQL explicitly notes `TRUNCATE` as the faster mechanism when the goal is to remove all rows. citeturn146162search4

Choosing between them is a data-lifecycle decision, not merely a syntax preference.

---

# 15. Foreign Keys Change the Meaning of DELETE

Suppose:

```text
customers
    ↓
orders
```

Deleting a customer may:

- fail because dependent rows exist
- cascade deletion
- set foreign-key columns to NULL
- trigger other behavior depending on the schema definition

Therefore:

> **DELETE correctness is partly a schema-design question.**

A developer should inspect foreign-key actions before assuming a delete affects one relation only.

# 16. Constraints Are Part of the Write Contract

Imagine:

```sql
CREATE TABLE inventory (
    quantity integer NOT NULL CHECK (quantity >= 0)
);
```

Then:

```sql
UPDATE inventory
SET quantity = quantity - 10
WHERE product_id = 42;
```

can fail if the resulting value violates the check.

The important model is:

```text
Application intent
      ↓
Proposed state transition
      ↓
Database invariants
      ↓
Accept OR reject
```

Database constraints are not merely documentation. They are executable correctness rules.

---

# 17. DML and MVCC

An `UPDATE` in PostgreSQL should not be imagined as simply overwriting bytes in place.

At a high level, PostgreSQL's MVCC model means an update creates a new row version and the old version remains relevant to visibility and cleanup.

Consequences include:

- dead tuples
- vacuum requirements
- index maintenance
- storage growth
- write amplification
- long-transaction interactions

Therefore:

```text
UPDATE frequency
×
row width
×
index count
×
transaction duration
```

can have substantial operational consequences.

This relationship becomes central later in the curriculum when studying HOT updates, VACUUM, bloat, WAL, and storage internals.

---

# 18. UPDATE Is Not Always Cheap

Consider:

```sql
UPDATE users
SET last_seen_at = now();
```

executed for every request.

Even if the logical value looks trivial, high-frequency updates can create substantial write traffic and row-version churn.

Ask:

```text
Does this value belong in the main row?
Does it need durability?
Is every update meaningful?
Can writes be sampled or batched?
Does it affect HOT eligibility?
How many indexes include this column?
```

---

# 19. Atomic Arithmetic Beats Read-Modify-Write

### Dangerous application workflow

```text
SELECT balance
↓
application adds 100
↓
UPDATE balance
```

Concurrent requests can interfere.

Prefer:

```sql
UPDATE accounts
SET balance = balance + 100
WHERE id = $1
RETURNING balance;
```

This expresses the state transition inside the database statement.

But even this is not universally sufficient for business invariants.

For example, withdrawing money requires a condition:

```sql
UPDATE accounts
SET balance = balance - $1
WHERE id = $2
  AND balance >= $1
RETURNING balance;
```

Now the transition is:

```text
old balance >= amount
        AND
same row gets decremented
```

A zero-row result can be interpreted by the application as "transition not permitted".

---

# 20. Optimistic Concurrency With Version Columns

A common pattern:

```sql
UPDATE orders
SET status = 'confirmed',
    version = version + 1
WHERE id = $1
  AND version = $2
RETURNING *;
```

Meaning:

```text
Update only if
current version == version client previously observed
```

If zero rows are returned:

```text
someone else changed the row
OR
row no longer qualifies
```

This gives the application a database-enforced conflict detector.

---

# 21. Pessimistic Concurrency

Another strategy is to lock first:

```sql
SELECT *
FROM inventory
WHERE product_id = $1
FOR UPDATE;
```

Then perform the state transition inside the same transaction.

This is useful when:

- a complex decision depends on the current state
- contention is expected
- the transition cannot be safely expressed as one conditional statement

But locks increase coordination cost, so they should be introduced deliberately.

---

# 22. Idempotency

HTTP requests can be retried because of:

- network failures
- client retries
- load balancer retries
- worker retries
- timeout ambiguity
- message delivery semantics

A request like:

```text
Create payment
```

must not necessarily create two payments because the client did not receive the first response.

A common database design is an idempotency key protected by a unique constraint:

```sql
CREATE TABLE payments (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    idempotency_key text NOT NULL UNIQUE,
    amount numeric(18,2) NOT NULL
);
```

Then an insert can be designed around the uniqueness boundary.

```sql
INSERT INTO payments (idempotency_key, amount)
VALUES ($1, $2)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING *;
```

The deeper lesson is:

> **Idempotency is a database/schema property as much as an application coding pattern.**

---

# 23. DML + Transactions

A statement can be atomic while a business operation contains multiple statements.

Example order placement:

```text
INSERT order
INSERT order_items
UPDATE inventory
INSERT payment record
INSERT outbox event
```

If these belong to one business transaction:

```sql
BEGIN;

-- statement 1
-- statement 2
-- statement 3
-- statement 4
-- statement 5

COMMIT;
```

The important distinction is:

```text
Statement atomicity
        ≠
Business transaction atomicity
```

Choosing the correct transaction boundary is an architecture decision.

---

# 24. CTEs and DML

DML can be combined with CTEs.

Example:

```sql
WITH expired AS (
    DELETE FROM sessions
    WHERE expires_at < now()
    RETURNING id, user_id
)
INSERT INTO expired_session_audit (session_id, user_id)
SELECT id, user_id
FROM expired;
```

This can express a multi-step data transformation in one statement.

It is particularly useful when one modification's output becomes another operation's input.

Remember that this chapter builds on the earlier CTE chapter; recursive CTEs and complex mutation workflows should still be evaluated for readability, performance, and transaction semantics.

# 25. Large-Scale UPDATE Strategy

This is dangerous on a large production table:

```sql
UPDATE events
SET archived = true
WHERE created_at < now() - interval '2 years';
```

Even when logically correct, one massive update can cause:

- long execution time
- large WAL volume
- many row versions
- lock pressure
- replication lag
- vacuum debt
- bloat
- operational blast radius

For very large datasets, chunking may be preferable.

Conceptually:

```text
identify bounded key range
        ↓
update bounded batch
        ↓
commit
        ↓
measure
        ↓
repeat
```

The exact chunking mechanism depends on workload and must account for concurrency and stable ordering.

---

# 26. Large-Scale DELETE Strategy

Mass deletion is similarly operationally expensive.

Possible strategies include:

```text
DELETE in bounded batches
        OR
partition and detach/drop old partitions
        OR
archive first, then remove
```

The best design often starts earlier with data lifecycle architecture rather than waiting until a huge `DELETE` becomes necessary.

# 27. RETURNING as an API Primitive

Node.js/NestJS example:

```ts
const result = await db.query(
  `
  UPDATE inventory
  SET quantity = quantity - $1
  WHERE product_id = $2
    AND quantity >= $1
  RETURNING product_id, quantity
  `,
  [requested, productId],
);
```

Now the application does not need:

```text
UPDATE
↓
SELECT current inventory
```

The database returns the authoritative post-transition state.

This is especially useful for:

- generated IDs
- timestamps
- counters
- balances
- status changes
- generated columns
- trigger-populated fields

# 28. DML and Permissions

Write permissions are not identical to read permissions.

For PostgreSQL DML, privileges can be required on the columns/tables being modified and on columns referenced by expressions or conditions.

`RETURNING` can additionally require `SELECT` privileges for returned columns. PostgreSQL documents these privilege requirements for `INSERT`, and analogous read privileges can be required for values inspected by `UPDATE`/`DELETE` expressions. citeturn146162search0turn146162search2

This matters in least-privilege designs.

---

# 29. DML and Row-Level Security

Row-Level Security can affect DML eligibility and checks.

For example, an update may involve both:

```text
Can I access the existing row?
        AND
Is the new row allowed?
```

PostgreSQL's policy model distinguishes row filtering and new-row checking for operations such as `UPDATE` and `INSERT ... ON CONFLICT`. citeturn146162search6

This is highly relevant for multi-tenant systems.

A tenant-safe update should not rely only on an application-provided tenant ID.

Schema-level enforcement can provide defense in depth.

---

# 30. Multi-Tenant DML Safety

Suppose:

```sql
UPDATE invoices
SET status = 'paid'
WHERE id = $1;
```

In a multi-tenant system, is invoice ID globally unique and sufficient?

If not, a safer logical boundary might be:

```sql
UPDATE invoices
SET status = 'paid'
WHERE tenant_id = $1
  AND id = $2
RETURNING *;
```

Or tenant separation may be enforced with RLS.

The general principle:

```text
Every write must prove ownership of the target row.
```

---

# 31. Financial DML

Financial systems require unusually strong write semantics.

Avoid vague workflows such as:

```text
read balance
calculate balance in Node.js
write balance
```

Instead, prefer explicit atomic state transitions, ledger entries, constraints, and transaction boundaries.

A ledger-oriented design often prefers:

```text
append immutable transaction
        ↓
derive current balance
```

rather than repeatedly overwriting historical truth.

This is an architectural decision, not merely an `UPDATE` trick.

---

# 32. Temporal DML

Suppose a pricing table stores validity periods.

An update that changes:

```text
valid_from
valid_to
price
```

may have temporal invariants such as:

```text
No overlapping periods
No invalid intervals
No missing required continuity
```

The write should therefore be designed around temporal constraints and transaction semantics, not only application validation.

Temporal correctness receives deeper treatment later in the curriculum.

# 33. The Difference Between "Matched" and "Changed"

Consider:

```sql
UPDATE products
SET status = 'active'
WHERE status = 'active';
```

Rows can match the predicate even if the resulting logical value is unchanged.

PostgreSQL's command tag reports rows updated; it is therefore important not to confuse:

```text
matched
changed in business meaning
RETURNING rows
```

The exact result must be interpreted according to the application's needs and any trigger behavior. PostgreSQL notes that an `UPDATE` count includes matched rows whose values did not change, subject to cases such as trigger suppression. citeturn146162search2

---

# 34. UPDATE and BEFORE Triggers

A trigger can modify or suppress a row before the write is completed.

That means application assumptions can be wrong if they assume:

```text
SET x = value
```

means the stored value must exactly equal `value`.

The real database pipeline may be:

```text
application value
    ↓
BEFORE trigger
    ↓
final row image
    ↓
constraints
    ↓
storage
```

Always inspect trigger behavior when debugging unexpected DML results.

---

# 35. DML and Locking

DML interacts with concurrency through row-level and other locks.

The actual lock behavior depends on the operation, indexes, foreign keys, triggers, isolation level, and concurrent activity.

When a write is unexpectedly slow, do not immediately assume:

> "The query is badly indexed."

Possible bottlenecks include:

```text
waiting for another transaction
waiting on a lock
index maintenance
I/O
WAL pressure
foreign-key checks
trigger execution
CPU
resource saturation
```

Later chapters will formalize this with `pg_stat_activity`, wait events, and lock inspection.

---

# 36. Deadlocks and Write Ordering

Two transactions can produce a deadlock when they acquire resources in conflicting orders.

Conceptual example:

```text
Transaction A: locks row 1 → wants row 2
Transaction B: locks row 2 → wants row 1
```

A principal-level solution is not simply:

> "Retry the error."

Instead ask:

```text
Why did the lock order differ?
Can all transactions use a consistent order?
What is the retry contract?
Is the operation idempotent?
```

Retry is a safety mechanism, not a substitute for understanding the concurrency design.

# 37. Prepared Statements and DML

Parameterized statements are important for:

- SQL injection prevention
- plan reuse considerations
- type correctness
- application/database boundary clarity

Good:

```ts
await db.query(
  `UPDATE users SET status = $1 WHERE id = $2`,
  [status, userId],
);
```

Bad:

```ts
await db.query(
  `UPDATE users SET status = '${status}' WHERE id = ${userId}`,
);
```

The second form mixes untrusted values into SQL text and creates injection risk.

# 38. ORM Reality Check

ORM code may look harmless:

```ts
await repository.update(id, { status: 'paid' });
```

But the actual production behavior depends on:

- generated SQL
- transaction boundaries
- predicates
- loaded relations
- optimistic locking configuration
- cascades
- hooks
- batching
- connection pooling

Therefore:

> **A database engineer reads generated SQL, not only ORM syntax.**

The ORM is an abstraction layer, not a replacement for database reasoning.

# 39. AI / Vibe-Coding Failure Patterns

AI-generated DML deserves hostile review.

## Failure 1 — Missing WHERE

```sql
UPDATE users
SET role = 'admin';
```

### Why it fails
It modifies every eligible row.

### Expert response
Require explicit target-set reasoning before executing destructive writes.

---

## Failure 2 — Read-Modify-Write Race

```text
SELECT inventory
↓
subtract in application
↓
UPDATE inventory
```

### Why it fails
Concurrent writers can overwrite one another's state transitions.

### Better
Use atomic SQL or explicit locking according to the invariant.

---

## Failure 3 — Duplicate UPDATE JOIN

```sql
UPDATE accounts a
SET tier = x.tier
FROM customer_events x
WHERE a.customer_id = x.customer_id;
```

### Why it fails
Multiple event rows can map to one account.

### Better
Produce a deterministic one-row-per-account relation first.

---

## Failure 4 — "INSERT then SELECT"

```text
INSERT
SELECT generated row
```

### Problem
Extra round trip and possible ambiguity about which row is retrieved under concurrency.

### Better
Use `RETURNING`.

---

## Failure 5 — Retry Without Idempotency

```text
request times out
↓
client retries
↓
duplicate INSERT
```

### Better
Define a uniqueness boundary and an idempotent command design.

---

## Failure 6 — Massive One-Shot Update

```sql
UPDATE events SET archived = true WHERE ...;
```

### Problem
Potential large transaction and operational blast radius.

### Better
Assess whether batching or partition lifecycle operations are more appropriate.

# 40. Production Debugging Framework for DML

When a write is wrong or slow, collect evidence in this order.

### Step 1 — Reproduce the exact statement

```sql
-- exact SQL
-- exact parameters
```

### Step 2 — Identify the intended target set

Run the equivalent `SELECT`.

### Step 3 — Establish expected cardinality

```text
expected rows
actual rows
returned rows
```

### Step 4 — Inspect constraints

Check:

- unique constraints
- foreign keys
- checks
- exclusion constraints

### Step 5 — Inspect triggers

A trigger may change or suppress the transition.

### Step 6 — Inspect policies

Especially with RLS.

### Step 7 — Inspect locks and active sessions

A slow write may simply be waiting.

### Step 8 — Inspect the plan

Use:

```sql
EXPLAIN
EXPLAIN (ANALYZE, BUFFERS)
```

with appropriate caution in production because `ANALYZE` executes the statement.

### Step 9 — Inspect transaction behavior

Ask:

```text
How long is the transaction open?
What else is inside it?
Is the application retrying?
```

# 42. Safe Change Pattern

A production write should often follow:

```text
1. Define invariant
2. Identify candidate rows
3. Verify cardinality
4. Verify ownership boundary
5. Check concurrency semantics
6. Perform bounded write
7. RETURNING authoritative result
8. Validate outcome
9. Commit
10. Observe production metrics
```

This pattern will recur throughout the curriculum.

# 43. Production Scenario — Inventory Reservation

Requirement:

> Reserve 5 units only when at least 5 are available.

Naïve:

```text
SELECT quantity
UPDATE quantity
```

Production-oriented:

```sql
UPDATE inventory
SET quantity = quantity - $1
WHERE product_id = $2
  AND quantity >= $1
RETURNING product_id, quantity;
```

If no row is returned:

```text
reservation was not performed
```

This single statement gives a compact concurrency boundary.

But a complete production system still needs to consider:

- transaction scope
- reservation expiry
- idempotency
- duplicate requests
- tenant isolation
- audit records
- failure recovery

# 44. Production Scenario — Soft Delete

Instead of:

```sql
DELETE FROM users
WHERE id = $1;
```

an application may use:

```sql
UPDATE users
SET deleted_at = now()
WHERE id = $1
  AND deleted_at IS NULL
RETURNING *;
```

Benefits can include:

- recoverability
- auditability
- historical references

Costs include:

- every query must exclude deleted rows
- indexes may need redesign
- uniqueness semantics become more complicated
- storage never disappears automatically

A partial unique index may later be useful:

```sql
CREATE UNIQUE INDEX users_email_active_uq
ON users (email)
WHERE deleted_at IS NULL;
```

Soft delete is not automatically superior to hard delete.

# 45. Production Scenario — Audit Trail

For sensitive updates:

```text
business row
    ↓
UPDATE
    ↓
audit mechanism
```

Audit can be implemented via:

- application code
- triggers
- append-only audit tables
- logical decoding / CDC
- event publishing

Each choice has different failure and consistency properties.

The central question is:

> **Must the audit record be guaranteed to commit with the business mutation?**

If yes, it belongs inside the same transactional design.

# 46. Common Developer Mistakes

## Mistake: treating DML as string manipulation

SQL is a declarative state-transition language operating under transaction and constraint semantics.

## Mistake: assuming one API call = one row

A statement may modify many rows.

## Mistake: ignoring row grain in `UPDATE ... FROM`

One target row can match multiple source rows.

## Mistake: putting business safety only in JavaScript/TypeScript

Application validation can race with concurrent writers.

## Mistake: assuming a timeout means rollback

A client-side timeout may create ambiguity about whether the database completed the statement or transaction.

The recovery strategy must account for that ambiguity.

## Mistake: using `RETURNING *` everywhere

Useful for debugging, but excessive payloads can increase network and application cost.

Prefer returning the minimal authoritative data needed.

# 47. Design Review Checklist

Before approving production DML, review:

### Correctness
- What exact rows can change?
- Can zero rows be valid?
- Can multiple rows be valid?
- What invariants must remain true?

### Concurrency
- What happens under simultaneous writers?
- Is the transition optimistic or pessimistic?
- Can deadlocks occur?
- What is the retry policy?

### Safety
- Is tenant ownership enforced?
- Is the predicate explicit?
- Are destructive operations bounded?

### Performance
- How are rows located?
- How many rows will be touched?
- How much WAL may be generated?
- How long can the transaction last?

### Integration
- Does the API need `RETURNING`?
- Is the command idempotent?
- Are ORM-generated SQL and transaction boundaries understood?

### Operations
- What happens under partial failure?
- How do we observe write latency and lock waits?
- What is the rollback/recovery plan?

# 54. Final Rules

1. **Never issue broad DML casually.**
2. **Know the target set before changing it.**
3. **Make the row grain explicit when using joins.**
4. **Prefer database-enforced invariants over application-only assumptions.**
5. **Use atomic state transitions when possible.**
6. **Use `RETURNING` when the authoritative write result is needed immediately.**
7. **Design retries together with idempotency.**
8. **Treat mass updates/deletes as operational events.**
9. **Measure locks and wait events before guessing at performance causes.**
10. **Read generated SQL from ORMs and AI tools.**
11. **A successful SQL execution does not prove business correctness.**
12. **A correct statement can still be the wrong production architecture.**
