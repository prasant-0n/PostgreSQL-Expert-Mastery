# 01.8 — Window Functions

> **Phase:** 01 — Advanced SQL  
> **Chapter:** 01.8  
> **Target Mastery:** L6–L7  
> **Primary Goal:** Understand window functions as a formal mechanism for computing values over a logically related set of rows while preserving row identity.

---

## 1. Why This Chapter Matters

Window functions are one of the most powerful and most frequently misunderstood parts of SQL.

The beginner mental model is:

```text
GROUP BY      → combines rows
Window        → calculates over rows
```

That is useful, but incomplete.

The engineering mental model is:

```text
FROM / JOIN
      ↓
WHERE
      ↓
GROUP BY / HAVING
      ↓
Logical result relation
      ↓
Window partitioning
      ↓
Window ordering
      ↓
Window frame
      ↓
Window function evaluation
      ↓
Final ORDER BY / LIMIT
```

A window function lets PostgreSQL compute a value using a **window of rows associated with the current row without collapsing those rows into one output row**.

That single property explains why window functions are ideal for:

- ranking
- running totals
- moving averages
- top-N-per-group
- previous/next row comparisons
- change detection
- cohort calculations
- percentages of group totals
- deduplication
- temporal analysis
- financial reconciliation
- inventory history
- analytical reporting

But window functions also have sharp edges. A query can be syntactically correct and still be semantically wrong because the **partition, ordering, or frame does not match the business question**.

# 3. Precise Definitions

## 3.1 Simple definition

A window function calculates something using a related set of rows while keeping the current row in the result.

## 3.2 Engineering definition

A window function applies an aggregate, ranking, navigation, or distribution operation over a **window definition** associated with each result row.

A window definition is fundamentally composed of:

```sql
OVER (
    [PARTITION BY ...]
    [ORDER BY ...]
    [frame_clause]
)
```

## 3.3 Expert definition

A window calculation is evaluated over the rows visible to the window stage, grouped into partitions, ordered into a sequence where applicable, and optionally restricted by a frame relative to the current row.

The distinction between:

```text
partition
peer group
frame
```

is central to expert-level reasoning.

# 4. The Foundational Mental Model

Suppose we have:

```text
sales
------------------------------------------------
id | tenant_id | customer_id | sale_date | amount
------------------------------------------------
1  | A         | C1          | Jan 01    | 100
2  | A         | C1          | Jan 02    | 150
3  | A         | C1          | Jan 03    | 200
4  | A         | C2          | Jan 01    | 80
5  | B         | C9          | Jan 01    | 500
```

For:

```sql
SUM(amount) OVER (
    PARTITION BY tenant_id, customer_id
)
```

PostgreSQL conceptually says:

```text
Build the result rows
        ↓
Group related rows into window partitions
        ↓
Calculate total for each partition
        ↓
Attach that total to every row in the partition
```

Output:

```text
C1 row 1 → 450
C1 row 2 → 450
C1 row 3 → 450
C2 row 4 → 80
C9 row 5 → 500
```

The three C1 rows remain three rows.

That is the fundamental difference from:

```sql
SELECT tenant_id, customer_id, SUM(amount)
FROM sales
GROUP BY tenant_id, customer_id;
```

which produces one row per group.

---

# 5. `GROUP BY` vs Window Functions

## `GROUP BY`

```text
many rows
   ↓
one row per group
```

## Window function

```text
many rows
   ↓
calculate across related rows
   ↓
keep original row identity
```

This leads to a powerful rule:

> **Use `GROUP BY` when the output grain should become the grouping grain. Use a window function when the original row grain must survive.**

---

# 6. Anatomy of `OVER()`

The syntax is:

```sql
function_name(...) OVER (
    PARTITION BY ...
    ORDER BY ...
    frame_clause
)
```

Each component answers a different question.

### `PARTITION BY`

**Which rows belong to the same analytical population?**

### `ORDER BY`

**In what logical sequence should rows be considered?**

### Frame

**Which portion of that ordered partition is visible to the current row?**

Do not treat these as interchangeable.

---

# 7. Partitioning

Consider:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
)
```

Each customer gets a separate partition.

For a multi-tenant system, this is dangerous:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
)
```

may be semantically wrong if `customer_id` is only unique inside a tenant.

Safer:

```sql
SUM(amount) OVER (
    PARTITION BY tenant_id, customer_id
)
```

## Production rule

> Every analytical partition key must be checked against the real uniqueness boundary of the domain.

This is especially important for:

- tenant-local customer IDs
- branch-local invoice IDs
- warehouse-local SKU IDs
- organization-local employee IDs
- company-local sequence numbers

---

# 8. Ordering

Ordering is what gives navigation and ranking functions meaning.

Example:

```sql
LAG(amount) OVER (
    PARTITION BY customer_id
    ORDER BY sale_date
)
```

This asks:

> What was the amount in the preceding ordered row for this customer?

But there is a hidden question:

**What happens when `sale_date` is tied?**

That is why production queries frequently need a deterministic tie-breaker:

```sql
ORDER BY sale_date, id
```

Without a total enough ordering key, peer rows can make row-position-based calculations semantically ambiguous.

---

# 9. Peer Groups

Rows that are indistinguishable under a window's `ORDER BY` are peers for window-function purposes.

Example:

```text
score
100
100
90
80
```

With:

```sql
RANK() OVER (ORDER BY score DESC)
```

results are:

```text
100 → 1
100 → 1
90  → 3
80  → 4
```

`DENSE_RANK()` gives:

```text
100 → 1
100 → 1
90  → 2
80  → 3
```

`ROW_NUMBER()` gives every row a unique sequence position:

```text
100 → 1
100 → 2
90  → 3
80  → 4
```

### Critical distinction

```text
ROW_NUMBER → row position
RANK       → rank with gaps after ties
DENSE_RANK → rank without gaps after ties
```

---

# 10. Core Ranking Functions

## 10.1 `ROW_NUMBER()`

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY created_at, id
)
```

Use for:

- deduplication
- top-N
- deterministic sequencing
- choosing latest/earliest row

Example:

```sql
SELECT *
FROM (
    SELECT
        c.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, id DESC
        ) AS rn
    FROM customer_events c
) x
WHERE rn = 1;
```

This is one of the most important patterns in practical SQL.

### Production warning

Do not use:

```sql
ORDER BY created_at DESC
```

alone when multiple rows can share the timestamp and your business logic requires a deterministic winner.

Prefer:

```sql
ORDER BY created_at DESC, id DESC
```

assuming `id` is a stable tie-breaker.

---

## 10.2 `RANK()`

Best when competition ranking semantics are intended.

Example:

```text
sales
1000
1000
900
```

Ranks:

```text
1
1
3
```

---

## 10.3 `DENSE_RANK()`

Ranks distinct values without gaps.

```text
1
1
2
```

Useful for:

- price bands
- score levels
- distinct performance tiers
- category ranking

---

## 10.4 Distribution functions

PostgreSQL also provides functions such as:

```sql
percent_rank()
cume_dist()
ntile(n)
```

These answer distribution questions rather than simple row-position questions.

---

# 11. Window Aggregates

Window functions can use ordinary aggregate functions.

Examples:

```sql
SUM(amount) OVER (...)
AVG(amount) OVER (...)
MIN(amount) OVER (...)
MAX(amount) OVER (...)
COUNT(*) OVER (...)
```

This is useful when you want both the original row and a group-level or running metric.

Example:

```sql
SELECT
    id,
    customer_id,
    amount,
    SUM(amount) OVER (
        PARTITION BY customer_id
    ) AS customer_total
FROM sales;
```

---

# 12. Running Totals

Classic form:

```sql
SUM(amount) OVER (
    PARTITION BY account_id
    ORDER BY transaction_time, id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Result:

```text
transaction | amount | running_total
------------+--------+--------------
T1          | 100    | 100
T2          | 50     | 150
T3          | 20     | 170
```

The important concept is the frame:

```text
start = first row in partition
end   = current row
```

---

# 13. Why the Frame Matters

This is one of the most important expert topics in the chapter.

Consider:

```sql
SUM(amount) OVER (
    ORDER BY transaction_time
)
```

Do not blindly assume this means:

```text
all rows from first row to current physical row
```

The exact result depends on the window frame and peer semantics associated with the ordered window.

For a strict row-by-row running total, make intent explicit:

```sql
SUM(amount) OVER (
    ORDER BY transaction_time, id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Explicit frames are often worth the additional text because they communicate the business intent and reduce ambiguity.

---

# 14. `ROWS` vs `RANGE` vs `GROUPS`

These frame units are not equivalent.

## `ROWS`

Frame based on physical row positions.

Conceptually:

```text
2 rows preceding
current row
1 row following
```

Useful for:

- row-by-row calculations
- fixed-row moving windows
- deterministic sequence analysis

Example:

```sql
AVG(amount) OVER (
    ORDER BY event_time, id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

## `RANGE`

Frame based on ordering values and peer/range semantics.

It can include multiple peer rows sharing the same ordering value.

Useful when the business question is value-oriented rather than strictly row-count-oriented.

## `GROUPS`

Frame based on peer groups rather than individual rows.

Useful when ties should move together as a logical unit.

### Expert rule

Before choosing a frame ask:

```text
Do I mean rows?
Do I mean ordering-value ranges?
Do I mean peer groups?
```

---

# 15. `LAG()` and `LEAD()`

## Previous row

```sql
LAG(amount) OVER (
    PARTITION BY account_id
    ORDER BY transaction_time, id
)
```

## Next row

```sql
LEAD(amount) OVER (
    PARTITION BY account_id
    ORDER BY transaction_time, id
)
```

Useful for:

- period-over-period change
- inventory movement
- price changes
- status transitions
- detecting gaps
- duration calculations

Example:

```sql
SELECT
    account_id,
    transaction_time,
    balance,
    balance - LAG(balance) OVER (
        PARTITION BY account_id
        ORDER BY transaction_time, id
    ) AS delta
FROM account_snapshots;
```

---

# 16. `FIRST_VALUE`, `LAST_VALUE`, `NTH_VALUE`

These require extra care because the concept of “first” and “last” is frame-dependent.

Example:

```sql
FIRST_VALUE(amount) OVER (
    PARTITION BY customer_id
    ORDER BY created_at, id
)
```

For `LAST_VALUE`, a common conceptual trap is assuming:

```sql
LAST_VALUE(x) OVER (ORDER BY t)
```

means the last row of the entire partition.

Depending on the frame, it may mean the last row **within the current frame**.

This is why expert SQL authors explicitly reason about the frame when using value-access functions.

---

# 17. Named Windows

When several calculations share the same window definition:

```sql
SELECT
    id,
    amount,
    ROW_NUMBER() OVER w AS rn,
    SUM(amount) OVER w AS running_sum,
    AVG(amount) OVER w AS running_avg
FROM sales
WINDOW w AS (
    PARTITION BY customer_id
    ORDER BY sale_date, id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
);
```

Benefits:

- reduces repetition
- makes semantics easier to audit
- centralizes the analytical definition
- lowers the risk of subtle differences between calculations

---

# 18. Window Functions and Query Grain

Always write down the grain first.

Suppose your input is:

```text
one row per invoice line
```

Then:

```sql
SUM(line_total) OVER (PARTITION BY customer_id)
```

computes over invoice-line rows.

If your business question is:

> total invoice amount per customer

and an invoice has many lines, that may be perfectly valid only if the input grain intentionally is invoice-line grain.

But if you already joined another one-to-many table, your line rows may have multiplied.

Example:

```text
invoice
  ↓
invoice_items
  ↓
payments
```

A careless join can turn:

```text
3 invoice items × 2 payments = 6 rows
```

Then a window aggregate sees 6 rows rather than 3.

### Critical rule

> A window function cannot repair incorrect cardinality introduced earlier in the query.

You must fix the row population before windowing.

---

# 19. Window Functions Do Not Magically Deduplicate

This is a common AI-generated SQL mistake:

```sql
SELECT DISTINCT
    customer_id,
    SUM(amount) OVER (PARTITION BY customer_id)
FROM sales;
```

The `DISTINCT` is not a substitute for defining the intended row grain.

If there are many distinct projected columns, duplicates may remain.

Correct reasoning is:

```text
Define the desired output grain
→ choose the representative row
→ use ROW_NUMBER or appropriate aggregation
```

---

# 20. Top-N per Group

Classic problem:

> Give me the three highest-value orders for every customer.

Use:

```sql
SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY total_amount DESC, id DESC
        ) AS rn
    FROM orders o
) x
WHERE rn <= 3;
```

For ties where you want all tied rows, consider `RANK()` or `DENSE_RANK()` depending on the business definition.

### Important question

Do you want:

```text
exactly 3 rows
```

or:

```text
all rows tied within the top 3 ranks
```

Those are different requirements.

---

# 21. Deduplication Pattern

Suppose duplicate customer events exist.

```sql
WITH ranked AS (
    SELECT
        e.*,
        ROW_NUMBER() OVER (
            PARTITION BY tenant_id, customer_id, event_type
            ORDER BY created_at DESC, id DESC
        ) AS rn
    FROM customer_events e
)
SELECT *
FROM ranked
WHERE rn = 1;
```

This pattern is powerful, but a production review should ask:

- Is the partition key actually the duplicate identity?
- Is the ordering the correct winner policy?
- Is `id` immutable?
- Can timestamps be equal?
- Should soft-deleted rows participate?
- Does tenant identity belong in the partition?
- Is deduplication occurring before or after joins?

# 22. Percentage of Total

Example:

```sql
SELECT
    product_id,
    revenue,
    revenue
      / NULLIF(SUM(revenue) OVER (), 0) AS revenue_share
FROM product_revenue;
```

For per-tenant percentages:

```sql
SELECT
    tenant_id,
    product_id,
    revenue,
    revenue
      / NULLIF(
            SUM(revenue) OVER (PARTITION BY tenant_id),
            0
        ) AS tenant_share
FROM product_revenue;
```

### Financial correctness

Be explicit about:

- numeric precision
- division by zero
- NULL semantics
- rounding policy
- currency boundaries
- tenant/currency partitioning

Do not casually apply floating-point assumptions to monetary calculations.

# 23. Change Detection

A powerful pattern:

```sql
SELECT
    entity_id,
    occurred_at,
    status,
    CASE
        WHEN status IS DISTINCT FROM
             LAG(status) OVER (
                 PARTITION BY entity_id
                 ORDER BY occurred_at, id
             )
        THEN 1
        ELSE 0
    END AS changed
FROM entity_events;
```

Then a running sum can create change groups.

This is useful for:

- state history
- machine status
- customer lifecycle
- price versions
- inventory state
- audit histories

---

# 24. Gap and Island Problems

Window functions are central to gaps-and-islands techniques.

Typical strategy:

```text
ordered rows
    ↓
LAG / LEAD
    ↓
identify boundaries
    ↓
running SUM or grouping key
    ↓
form islands
```

The exact solution depends on whether you want:

- contiguous dates
- consecutive sequence numbers
- state continuity
- session windows
- repeated business events

The key lesson is that a window function often creates the **metadata required for a later grouping step**.

---

# 25. Sessionization Mental Model

A simplified sessionization pattern:

```sql
WITH marked AS (
    SELECT
        user_id,
        event_time,
        CASE
            WHEN LAG(event_time) OVER (
                PARTITION BY user_id
                ORDER BY event_time, id
            ) IS NULL
              OR event_time - LAG(event_time) OVER (
                    PARTITION BY user_id
                    ORDER BY event_time, id
                ) > INTERVAL '30 minutes'
            THEN 1
            ELSE 0
        END AS new_session
    FROM events
),
numbered AS (
    SELECT
        *,
        SUM(new_session) OVER (
            PARTITION BY user_id
            ORDER BY event_time
            ROWS UNBOUNDED PRECEDING
        ) AS session_no
    FROM marked
)
SELECT *
FROM numbered;
```

In production, avoid repeating expensive expressions unnecessarily; compute the `LAG` once in a lower layer and reuse it.

---

# 26. Window Functions vs Correlated Subqueries

These can sometimes express similar business logic.

Example correlated approach:

```sql
SELECT
    s.*,
    (
        SELECT SUM(x.amount)
        FROM sales x
        WHERE x.customer_id = s.customer_id
    ) AS customer_total
FROM sales s;
```

Window approach:

```sql
SELECT
    s.*,
    SUM(amount) OVER (
        PARTITION BY customer_id
    ) AS customer_total
FROM sales s;
```

The window version more directly communicates the analytical operation and often gives the planner a better structure to work with, but one should still inspect the actual plan rather than assuming one syntax is always faster.

---

# 27. Window Functions vs Self-Joins

Previous-row comparison can be expressed through self-joins, but:

```sql
LAG(value) OVER (ORDER BY event_time)
```

is usually much clearer than manually finding the previous row through a join.

Use a window when the business operation is inherently positional or partition-relative.

---

# 28. WHERE, GROUP BY, HAVING and Window Placement

A common mistake is trying to use a window function directly in `WHERE`.

This is invalid conceptually because the filtering stage happens before the window result is available.

Instead:

```sql
SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY total_amount DESC, id DESC
        ) AS rn
    FROM orders o
) x
WHERE rn <= 3;
```

The query shape is:

```text
base rows
  ↓
window calculation
  ↓
outer filter
```

This staged thinking is more important than memorizing a syntax restriction.

---

# 29. `FILTER` + Window Aggregates

PostgreSQL supports aggregate `FILTER` syntax.

Example:

```sql
COUNT(*) FILTER (WHERE status = 'paid')
    OVER (PARTITION BY customer_id)
```

This can produce conditional window metrics without creating separate queries.

Example:

```sql
SELECT
    customer_id,
    order_id,
    COUNT(*) FILTER (WHERE status = 'paid')
        OVER (PARTITION BY customer_id) AS paid_orders,
    COUNT(*) OVER (PARTITION BY customer_id) AS total_orders
FROM orders;
```

---

# 30. NULL Semantics

Window functions interact with NULLs through:

- ordering rules
- aggregate NULL handling
- navigation-function defaults
- equality comparisons
- frame boundaries

Never say simply:

> “NULLs are ignored.”

Ask:

```text
Ignored by which aggregate?
At which stage?
Under which ordering?
Compared with what?
```

For change detection, use `IS DISTINCT FROM` when NULL-sensitive equality semantics are needed.

---

# 31. Determinism

A production analytical query should be deterministic when the business requirement demands reproducibility.

Risky:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY created_at DESC
)
```

Safer:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY created_at DESC, id DESC
)
```

The tie-breaker should be semantically justified, not merely added mechanically.

---

# 32. Pagination with Window Functions

A common pattern is:

```sql
ROW_NUMBER() OVER (ORDER BY created_at DESC, id DESC)
```

followed by a range filter.

This can be useful for analytical reports, but it is not automatically superior to keyset pagination.

For large API datasets, prefer a pagination design based on the indexed business ordering rather than ranking the entire dataset when the use case does not require ranking.

### Principle

> Do not use a window function to solve a problem that a bounded indexed seek can solve more cheaply.

---

# 33. Performance Model

Window queries can become expensive because PostgreSQL may need to:

```text
read candidate rows
    ↓
partition / order them
    ↓
sort or otherwise arrange rows
    ↓
compute window state
    ↓
produce output
```

The performance questions are:

1. How many rows reach the window stage?
2. How many partitions exist?
3. How large are the partitions?
4. What ordering is required?
5. Can existing ordering reduce work?
6. Are multiple different window orderings required?
7. Does sorting spill to temporary storage?
8. Is the input already reduced enough?

---

# 34. `EXPLAIN` Thinking

For a slow window query, inspect:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Look for:

- excessive rows entering `WindowAgg`
- expensive Sort nodes
- large actual-vs-estimated row differences
- external merge sorts / disk spill
- repeated sorting for different window specifications
- upstream joins multiplying rows
- filters applied too late

The operator name `WindowAgg` is important, but the real cause of a slow window query may be upstream.

---

# 35. Example: Hidden Performance Bug

Suppose:

```sql
SELECT
    o.*,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY created_at DESC, id DESC
    ) AS rn
FROM orders o
JOIN order_items oi
    ON oi.order_id = o.id;
```

If each order has 10 items, one order may enter the window stage 10 times.

The rank now applies to **joined rows**, not orders.

Correct approach may require:

```text
first restore order grain
→ then window over orders
```

This is one of the highest-value debugging habits in analytical SQL.

---

# 36. Multi-Window Queries

Example:

```sql
SELECT
    id,
    customer_id,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY created_at DESC, id DESC
    ) AS rn,
    SUM(amount) OVER (
        PARTITION BY customer_id
    ) AS customer_total,
    LAG(amount) OVER (
        PARTITION BY customer_id
        ORDER BY created_at, id
    ) AS previous_amount
FROM sales;
```

These windows do not necessarily share the same ordering requirements.

Therefore, do not assume one sort automatically satisfies every window expression.

A plan inspection is required for serious performance work.

---

# 37. Window Chaining / Staged Analytics

Some analytical questions need multiple stages.

Example:

```text
raw events
   ↓
LAG to calculate change
   ↓
derive boundary marker
   ↓
running SUM to create group ID
   ↓
GROUP BY session ID
```

Trying to force everything into a single giant expression often decreases readability and makes correctness harder to audit.

A good SQL engineer uses relational stages intentionally.

---

# 38. Common Wrong Approaches

## Wrong approach 1 — Using `ROW_NUMBER` without deterministic ordering

### Assumption

“The timestamp is enough.”

### Problem

Ties can exist.

### Why it fails

The selected row may not be reproducible.

### Better mental model

Ranking is only as deterministic as its ordering keys.

### Production consequence

Different executions or plans may choose different tied rows when business correctness requires one specific winner.

---

## Wrong approach 2 — Partitioning without tenant identity

### Assumption

`customer_id` is globally unique.

### Problem

It is only tenant-local.

### Consequence

One tenant's totals can contaminate another tenant's analytics.

---

## Wrong approach 3 — Using `LAST_VALUE` without understanding the frame

### Assumption

“It returns the last value in the partition.”

### Problem

The frame may end at the current row.

### Better approach

Explicitly reason about the desired frame and ordering.

---

## Wrong approach 4 — Window after accidental one-to-many multiplication

### Assumption

“The database knows I mean one order.”

### Problem

The window sees physical result rows, not business intent.

---

## Wrong approach 5 — Ranking the entire table when only one page is needed

### Assumption

“Window functions are the standard pagination solution.”

### Problem

You may process far more rows than necessary.

### Better approach

Use indexed keyset pagination when the requirement is ordinary ordered retrieval.

---

# 39. AI / Vibe-Coding Failure Patterns

AI-generated SQL frequently gets the syntax approximately right while missing the semantic grain.

Audit for:

```text
□ Is PARTITION BY complete?
□ Is the tenant key included?
□ Is the ORDER BY deterministic?
□ Is the frame appropriate?
□ Are peer semantics intentional?
□ Is the input grain correct?
□ Did an upstream JOIN multiply rows?
□ Does ROW_NUMBER answer an exact-row requirement?
□ Does RANK answer a tied-rank requirement?
□ Is LAST_VALUE frame-safe?
□ Is a window being used where keyset pagination is better?
□ Does the query sort unnecessarily large populations?
□ Is monetary arithmetic using appropriate numeric types?
```

### AI rule

> Never approve a window query because the SQL “looks correct.” Reconstruct the input grain, partition, ordering, frame, and expected output row-by-row.


Requirement:

> Show each customer's invoices with lifetime invoiced amount, most recent invoice, and previous invoice amount.

A strong design might calculate:

```sql
SELECT
    i.*,
    SUM(i.total_amount) OVER (
        PARTITION BY i.tenant_id, i.customer_id
    ) AS lifetime_invoice_amount,
    ROW_NUMBER() OVER (
        PARTITION BY i.tenant_id, i.customer_id
        ORDER BY i.invoice_date DESC, i.id DESC
    ) AS invoice_recency_rank,
    LAG(i.total_amount) OVER (
        PARTITION BY i.tenant_id, i.customer_id
        ORDER BY i.invoice_date, i.id
    ) AS previous_invoice_amount
FROM invoices i;
```

The important part is not memorizing this SQL.

The expert questions are:

- Is `customer_id` tenant-local?
- Is invoice grain really one row per invoice?
- Could cancelled invoices participate?
- Is invoice date the correct business ordering?
- Is `id` a valid tie-breaker?
- Should fiscal period boundaries reset the calculation?
- Should branch identity be included?
- Should currencies be partitioned separately?
- Is the report filtered before the window stage or after it?

# 41. Production Scenario — Inventory

Requirement:

> For every SKU, show each stock movement, previous quantity, delta, and running balance.

```sql
SELECT
    sku_id,
    occurred_at,
    quantity,
    LAG(quantity) OVER (
        PARTITION BY tenant_id, warehouse_id, sku_id
        ORDER BY occurred_at, id
    ) AS previous_quantity,
    SUM(quantity) OVER (
        PARTITION BY tenant_id, warehouse_id, sku_id
        ORDER BY occurred_at, id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_balance
FROM stock_movements;
```

Potential domain issues:

- corrections
- backdated movements
- reversals
- opening balance
- warehouse transfers
- duplicate event ingestion
- concurrent writes
- timezone normalization

The SQL is only correct if the data model and event ordering are correct.

# 51. When NOT to Use a Window Function

Do not use a window function merely because it can express the requirement.

Prefer a grouped aggregate when the output grain is already the grouped grain.

Prefer keyset pagination when you only need a page of ordered rows.

Prefer a direct indexed lookup when you need one row by a unique key.

Prefer pre-aggregation when upstream joins create a much larger intermediate relation than the analytical calculation requires.

Prefer a dedicated summary table/materialized view when the computation is expensive, repeated frequently, and the freshness requirements permit precomputation.

Expert engineering means choosing the correct abstraction, not the most sophisticated SQL feature.

---

# 52. Performance Optimization Framework

Use this order:

```text
1. Verify semantic correctness
2. Verify input/output grain
3. Reduce rows before windowing when valid
4. Remove unnecessary joins
5. Eliminate accidental row multiplication
6. Make ordering deterministic
7. Inspect EXPLAIN ANALYZE
8. Inspect sort behavior and spills
9. Check indexes and useful ordering opportunities
10. Consider staged computation
11. Consider pre-aggregation
12. Consider materialization if workload justifies it
```

Do not optimize a semantically wrong query.

# 56. Final Principle

> **A window function is not merely “an aggregate without GROUP BY.” It is a controlled analytical view of rows around the current row, defined by partition, order, peers, and frame.**

Mastering window functions means being able to predict the exact row population, the exact analytical neighborhood, the exact result, and the physical work PostgreSQL must perform.

That is the difference between knowing window-function syntax and being able to use window functions safely in production PostgreSQL systems.
