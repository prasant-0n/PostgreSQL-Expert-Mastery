# 01.17 — Arrays

## PostgreSQL Expert Mastery

> **Phase 01 — Advanced SQL**
>
> Arrays are a PostgreSQL-native collection type. They are powerful when the business meaning is genuinely "a bounded or naturally grouped collection of homogeneous values," but they are not a universal replacement for relational tables. Expert PostgreSQL engineering requires knowing the difference.

---

By the end of this chapter, you should be able to:

## 3. The Core Mental Model

A relational row is already a structured value. An array adds another level of structure inside a column:

```text
Table
└── Row
    └── Column
        └── Array value
            ├── element 1
            ├── element 2
            └── element 3
```

The key architectural question is therefore not:

> "Can PostgreSQL store these values in an array?"

It almost certainly can.

The real question is:

> **Does this collection need to behave like one atomic attribute, or like independently addressable relational facts?**

That single question prevents a large class of poor schemas.

---

## 4. Three Levels of Understanding

### 4.1 Simple definition

An array is a PostgreSQL value containing an ordered collection of elements of a compatible element type.

### 4.2 Engineering definition

An array is a typed column value with element-level access and array-aware operators/functions. It allows multiple values to travel with a row while remaining one column value from the relational perspective.

### 4.3 Expert definition

An array is a first-class PostgreSQL data value whose semantics include element type, dimensionality, bounds, ordering, `NULL` state, containment/overlap/equality behavior, and operator/function interactions. Whether those semantics align with the application's entity model determines whether the design is robust or an embedded-relational anti-pattern.

---

## 5. Why Arrays Exist

Arrays solve real problems:

- tags or labels attached to one entity;
- a compact set of feature flags;
- fixed or naturally grouped values such as coordinates or dimensions;
- PostgreSQL-native function inputs/outputs;
- intermediate query representations;
- denormalized search attributes;
- controlled lists whose lifecycle is owned by the parent row;
- mathematical or scientific data structures.

They become problematic when the elements have their own:

- identity;
- lifecycle;
- foreign keys;
- permissions;
- monetary values;
- audit requirements;
- history;
- ordering business rules;
- independent updates;
- uniqueness rules across rows.

In those cases, child rows are usually the stronger abstraction.

## 6. Creating Arrays

### 6.1 Literal syntax

```sql
SELECT ARRAY[1, 2, 3] AS values;

SELECT ARRAY['gold', 'silver', 'bronze'] AS priorities;
```

PostgreSQL infers an element type from the literals where possible.

### 6.2 Explicit casts

```sql
SELECT ARRAY[1, 2, 3]::bigint[];
SELECT ARRAY['a', 'b']::text[];
SELECT ARRAY['2026-01-01', '2026-02-01']::date[];
```

Explicit typing is preferable at boundaries where implicit type resolution could be surprising.

### 6.3 Array constructor from a query

```sql
SELECT ARRAY(
    SELECT id
    FROM products
    ORDER BY id
) AS product_ids;
```

This is useful when the application truly wants one collection value, not a rowset.

### 6.4 `ARRAY_AGG`

```sql
SELECT customer_id,
       array_agg(product_id ORDER BY product_id) AS product_ids
FROM orders
GROUP BY customer_id;
```

Ordering inside `array_agg` matters when the resulting order is meaningful.

---

## 7. Empty Array vs NULL Array vs Array Containing NULL

These are different states.

```sql
NULL
```

means there is no array value.

```sql
'{}'::text[]
```

means an array exists and contains zero elements.

```sql
ARRAY[NULL]::text[]
```

means an array exists and contains one element whose value is `NULL`.

This distinction is critical for APIs and business logic.

| State | Meaning |
|---|---|
| `NULL` | no array value / unknown / not provided depending on model |
| `{}` | known empty collection |
| `{NULL}` | one element, but the element value is null |

Do not collapse these three states without an explicit business decision.

## 8. Array Subscripts

PostgreSQL arrays support subscripting:

```sql
SELECT (ARRAY['A', 'B', 'C'])[1];
SELECT (ARRAY['A', 'B', 'C'])[3];
```

For a conventional one-dimensional array, the lower bound is normally `1`, but PostgreSQL arrays can have non-default lower bounds. Expert code should not assume every array starts at index 1 when working with externally constructed arrays or advanced database functions.

Useful introspection functions include:

```sql
array_ndims(...)
array_dims(...)
array_lower(...)
array_upper(...)
array_length(...)
cardinality(...)
```

Example:

```sql
SELECT
    array_ndims(ARRAY[[1,2],[3,4]]) AS dimensions,
    array_length(ARRAY[[1,2],[3,4]], 1) AS rows,
    array_length(ARRAY[[1,2],[3,4]], 2) AS cols,
    cardinality(ARRAY[[1,2],[3,4]]) AS total_elements;
```

---

## 9. One-Dimensional vs Multidimensional Arrays

### 9.1 One-dimensional

```sql
ARRAY[10, 20, 30]
```

### 9.2 Multidimensional

```sql
ARRAY[
    [1, 2],
    [3, 4]
]
```

Conceptually:

```text
[ [1,2],
  [3,4] ]
```

Multidimensional arrays are useful for mathematical/scientific or tightly structured data. They are usually a poor choice for business entities whose nested values need independent identity or relationships.

Do not confuse an array of composite values or JSON objects with a true relational hierarchy.

---

## 10. Rectangularity and Dimensions

PostgreSQL supports multidimensional arrays with dimensional metadata. Construction therefore has stronger structural requirements than "a random nested list" in application memory.

A developer should understand the distinction between:

```text
Nested JSON-like data
```

and

```text
Typed PostgreSQL array with dimensions
```

If your business object is heterogeneous, deeply nested, or schema-flexible, JSONB is usually the more natural type. If it is homogeneous and collection-oriented, arrays may be appropriate.

## 11. Querying Array Elements

### 11.1 Subscript access

```sql
SELECT tags[1]
FROM products;
```

### 11.2 Search using `ANY`

```sql
SELECT *
FROM products
WHERE 'gold' = ANY(tags);
```

This asks whether the scalar value compares equal to at least one element.

### 11.3 `ALL`

```sql
SELECT *
FROM products
WHERE 10 < ALL(prices);
```

This asks whether the comparison is true for every relevant element.

Be especially careful with empty arrays and `NULL` arrays. Their truth behavior is part of SQL's three-valued semantics and should be tested rather than guessed.

---

## 12. Core Array Operators

PostgreSQL provides array-aware operators such as:

```sql
array1 @> array2   -- contains
array1 <@ array2   -- is contained by
array1 && array2   -- overlaps
array1 || array2   -- concatenate
```

Example:

```sql
SELECT ARRAY['red', 'blue']::text[] @> ARRAY['red']::text[];
```

### Important semantic distinction

Containment is about element presence, not relational equality of multisets.

Do not automatically interpret:

```sql
ARRAY[1,2] @> ARRAY[2,2]
```

as requiring two distinct copies of `2`. Array containment semantics are not equivalent to frequency-count matching.

This distinction becomes very important when arrays are treated as sets.

---

## 13. Are Arrays Sets or Lists?

This is one of the most important architectural questions.

An array structurally behaves like an ordered collection, but many operators are about containment/overlap rather than preserving a business interpretation of order.

Your schema must define what the array means.

### Interpretation A — Ordered list

```text
preferred_categories = [electronics, jewelry, clothing]
```

Order matters.

### Interpretation B — Unordered set-like collection

```text
roles = [admin, auditor]
```

Order should not matter.

### Interpretation C — Multiset-like data

```text
scores = [10, 10, 20]
```

Duplicates matter.

These are different data contracts. Do not let the choice be accidental.

---

## 14. Equality, Duplicates, and Ordering

When arrays are compared for equality, element ordering and array structure can matter. Therefore:

```sql
ARRAY[1,2] <> ARRAY[2,1]
```

can be true even though a developer thinking in sets may incorrectly call them equivalent.

This is why a tag array should not be treated casually as a true mathematical set.

If order is irrelevant but duplicates are forbidden, you need an explicit invariant. That may be enforced in application code, with database logic, or—when the relationship is important enough—by using a normalized child table with a unique constraint.

## 15. Array Functions You Must Know

Core functions include:

```sql
array_append()
array_prepend()
array_cat()
array_position()
array_positions()
array_remove()
array_replace()
array_to_string()
string_to_array()
unnest()
cardinality()
trim_array()
```

Examples:

```sql
SELECT array_append(ARRAY[1,2], 3);
SELECT array_remove(ARRAY[1,2,2,3], 2);
SELECT array_position(ARRAY['a','b','c'], 'b');
SELECT cardinality(ARRAY[10,20,30]);
```

Always check whether the function's semantics match your intended business invariant. For example, removing a value from an array is not the same architectural operation as deleting a child entity from a relational table.

## 16. `unnest()` — Turning Elements Back Into Rows

`unnest()` expands array elements into rows.

```sql
SELECT unnest(ARRAY['gold', 'silver', 'bronze']);
```

Result conceptually:

```text
 gold
 silver
 bronze
```

This is extremely useful for analytics, validation, joins, and set-based processing.

Example:

```sql
SELECT p.id, tag
FROM products p
CROSS JOIN LATERAL unnest(p.tags) AS tag;
```

This connects arrays directly to the LATERAL chapter: the array value comes from the current row, and `unnest()` expands that value into a rowset.

---

## 17. `WITH ORDINALITY`

When position matters, preserve it explicitly.

```sql
SELECT *
FROM unnest(ARRAY['A','B','C']) WITH ORDINALITY AS t(value, position);
```

Result:

```text
value | position
------+---------
A     | 1
B     | 2
C     | 3
```

This is better than assuming row order survives an arbitrary query plan.

---

## 18. `generate_subscripts()`

For index-aware processing, `generate_subscripts()` exposes valid indexes.

```sql
SELECT i, arr[i]
FROM (VALUES (ARRAY['A','B','C'])) AS v(arr)
CROSS JOIN LATERAL generate_subscripts(v.arr, 1) AS g(i);
```

This is especially useful when you need both position and element and want explicit control over subscripting.

---

## 19. Array Aggregation

`array_agg` converts grouped rows into one array value.

```sql
SELECT customer_id,
       array_agg(product_id ORDER BY product_id) AS product_ids
FROM order_items
GROUP BY customer_id;
```

### The correctness questions

Before using `array_agg`, ask:

1. What is the input grain?
2. Can duplicates occur?
3. Should duplicates be retained?
4. Does order matter?
5. What should an empty group produce?
6. Is `NULL` an allowed element?
7. Could the resulting array become huge?

Do not use `array_agg` as a reflexive way to hide a many-to-many relationship.

---

## 20. Arrays and `NULL`

Array logic has multiple `NULL` dimensions:

```text
A. column is NULL
B. column contains an empty array
C. array contains NULL element(s)
D. comparison with array returns NULL
```

Example questions that must be tested:

```sql
SELECT NULL = ANY(ARRAY[1,2]);
SELECT 1 = ANY(NULL::int[]);
SELECT 1 = ANY(ARRAY[NULL]::int[]);
SELECT 1 = ANY('{}'::int[]);
```

The safe engineering practice is not memorization alone. Build truth-table tests for the predicates your production code depends on.

---

## 21. Searching Arrays Correctly

Different problem statements require different expressions.

### Any one value exists

```sql
WHERE 'admin' = ANY(roles)
```

### Array contains all requested values

```sql
WHERE roles @> ARRAY['admin','auditor']::text[]
```

### Arrays overlap

```sql
WHERE roles && ARRAY['admin','auditor']::text[]
```

These are not interchangeable.

---

## 22. Arrays vs JSONB

Choose arrays when:

- every element has one homogeneous type;
- the collection shape is simple;
- element-level relational identity is unnecessary;
- PostgreSQL array operators are a good semantic match.

Choose JSONB when:

- elements are heterogeneous;
- objects have named attributes;
- the shape is semi-structured;
- nested object structure is meaningful.

Choose relational rows when:

- elements have lifecycle or identity;
- there are foreign keys;
- permissions apply to elements;
- elements need independent joins and reporting;
- uniqueness must be enforced across parent/child rows;
- high-volume element-level updates are common.

Never choose based only on "the data looks like a list."

---

## 23. Arrays vs Normalized Child Tables

### Array model

```sql
CREATE TABLE users (
    id bigint PRIMARY KEY,
    roles text[] NOT NULL DEFAULT '{}'
);
```

### Relational model

```sql
CREATE TABLE users (
    id bigint PRIMARY KEY
);

CREATE TABLE user_roles (
    user_id bigint NOT NULL REFERENCES users(id),
    role text NOT NULL,
    PRIMARY KEY (user_id, role)
);
```

### The relational model wins when you need

- referential integrity;
- indexing on child facts;
- child-level auditability;
- role metadata;
- independent updates;
- joins to a roles table;
- uniqueness guaranteed by database structure.

### The array model wins when

- the collection is owned as one attribute;
- individual elements have little independent meaning;
- compact reads/writes matter;
- the workload is naturally collection-oriented.

## 24. Production ERP Example — Product Tags

Suppose a product has:

```text
['hallmark', 'featured', 'sale']
```

An array can be reasonable when these are lightweight labels.

But suppose the organization later requires:

```text
Tag
├── id
├── tenant_id
├── name
├── created_by
├── created_at
└── active
```

and product-tag relationships need auditing, permissions, and unique constraints.

That is no longer just an attribute. It is a relationship.

**Architectural lesson:** schemas evolve. A design that was reasonable for a small collection can become a migration target as business meaning grows.

---

## 25. Multi-Tenant Arrays

Arrays do not magically create tenant isolation.

Suppose:

```sql
users (
    tenant_id bigint,
    roles text[]
)
```

A query like:

```sql
SELECT *
FROM users
WHERE 'admin' = ANY(roles);
```

is still tenant-unsafe if the application is supposed to return only one tenant and the tenant boundary was omitted.

Correctness requires the tenant predicate or an equivalent enforced isolation mechanism:

```sql
WHERE tenant_id = $1
  AND 'admin' = ANY(roles)
```

Arrays are data representation, not authorization boundaries.

---

## 26. GIN Indexes for Arrays

PostgreSQL provides GIN indexing support useful for array containment/overlap-style predicates.

Example:

```sql
CREATE INDEX idx_users_roles_gin
ON users
USING gin (roles);
```

Potentially useful predicates include:

```sql
WHERE roles @> ARRAY['admin']::text[]
WHERE roles && ARRAY['admin','auditor']::text[]
```

But do not assume:

> "I have a GIN index, therefore every array query will become fast."

Planner choice depends on:

- query shape;
- selectivity;
- table size;
- statistics;
- cost estimates;
- visibility/cache state;
- operator support;
- workload.

Always verify with `EXPLAIN (ANALYZE, BUFFERS)`.

---

## 27. Why Element-Level Indexes Change the Architecture

An array GIN index can accelerate membership-like predicates, but it does not transform the array into a relational child table.

For example, if you frequently need:

```text
role
role_created_at
role_source
role_granted_by
role_expiration
```

an array is becoming structurally mismatched with the domain.

The correct optimization may be **schema normalization**, not a more sophisticated index.

---

## 28. Array Statistics and Planner Reasoning

The planner needs statistics to estimate predicate selectivity. Array-heavy workloads can become difficult when the planner's estimates do not reflect actual element distributions.

When a query suddenly changes plan:

```text
SQL
 ↓
Predicate
 ↓
Statistics
 ↓
Selectivity estimate
 ↓
Cost model
 ↓
Plan choice
```

Do not immediately rewrite the query. First inspect:

```sql
ANALYZE users;
```

and then:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

The correct diagnosis is evidence-driven.

---

## 29. Large Arrays — The Hidden Cost

A large array is one column syntactically, but that does not mean it is cheap.

Large values can create:

- larger tuples;
- more I/O;
- more memory pressure;
- more WAL activity on updates;
- more network transfer;
- more work when copying or reconstructing the value;
- more application serialization cost.

PostgreSQL may use TOAST storage for large variable-length values, but TOAST changes the storage path; it does not make a large mutable collection free.

---

## 30. The Mutation Problem

Consider:

```sql
UPDATE users
SET roles = array_append(roles, 'auditor')
WHERE id = $1;
```

This may look tiny at the SQL level.

But if `roles` is large, changing one logical element can require PostgreSQL to create a new row version containing the updated value. The physical consequences of updates matter.

That becomes especially important under:

- high write concurrency;
- large arrays;
- frequent element changes;
- replication;
- WAL-sensitive systems.

An array is not an independently mutable collection of tuples.

---

## 31. Concurrency and Duplicate Elements

Suppose two requests execute:

```sql
UPDATE users
SET roles = array_append(roles, 'auditor')
WHERE id = $1;
```

Concurrently.

The final semantics depend on transaction isolation, locking, row versions, and the exact statement behavior. More importantly, if duplicate membership is forbidden by the business, `array_append` alone does not encode the uniqueness invariant.

A safer semantic operation might check membership before insertion or use a normalized child table with a database-enforced unique key.

For example:

```sql
UPDATE users
SET roles = CASE
    WHEN 'auditor' = ANY(roles) THEN roles
    ELSE array_append(roles, 'auditor')
END
WHERE id = $1;
```

Even this must be evaluated against the concurrency and business requirements. A database-level unique relationship is often stronger than procedural array manipulation.

## 32. Arrays and API Contracts

Node.js/NestJS systems commonly map PostgreSQL arrays into JavaScript arrays.

That creates a semantic translation:

```text
PostgreSQL NULL   ↔ null
PostgreSQL {}     ↔ []
PostgreSQL {NULL} ↔ [null]
```

Do not accidentally convert `NULL` into `[]` everywhere.

The API contract must answer:

> Does `null` mean unknown/not supplied, while `[]` means explicitly empty?

That distinction often matters for PATCH semantics.

---

## 33. PATCH Semantics Example

Suppose:

```json
{
  "roles": null
}
```

could mean:

```text
Clear the roles
```

while omission means:

```text
Do not change roles
```

and:

```json
{
  "roles": []
}
```

could mean:

```text
Set the known collection to empty
```

The database schema and API semantics must agree. This is not a PostgreSQL-only issue; it is a cross-layer data-contract problem.

## 34. AI / Vibe-Coding Failure Patterns

### Failure 1 — "Use an array because the UI sends an array"

**Your assumption:** input shape determines storage model.

**Problem:** transport representation is not domain modeling.

**Why it fails:** a UI list may represent an independently meaningful relationship.

**Correct mental model:** API shape ≠ relational schema.

**Production consequence:** future reporting, permissions, and referential integrity become difficult.

**Better approach:** model the domain first, then choose the physical representation.

---

### Failure 2 — Treating arrays as sets

```sql
WHERE roles = ARRAY['admin','auditor']
```

**Problem:** ordering and duplicate semantics may make this more restrictive than intended.

**Better approach:** use the predicate that expresses the actual requirement, such as containment or overlap.

---

### Failure 3 — Using `NOT IN` with array extraction without NULL analysis

Array workflows often expand into rows:

```sql
NOT IN (SELECT unnest(...))
```

Now all the `NOT IN` / `NULL` pitfalls from the subquery chapter can return.

**Better approach:** reason about `NULL` explicitly and prefer `NOT EXISTS` when the requirement is existential exclusion.

---

### Failure 4 — Assuming GIN guarantees an index scan

**Problem:** indexes are physical alternatives, not commands.

**Better approach:** inspect the actual plan.

---

### Failure 5 — Storing foreign keys in arrays

```sql
member_ids bigint[]
```

This can be tempting, but it often throws away relational integrity.

Ask:

- Can every ID be verified against another table?
- Can deleted members leave stale IDs?
- Do members have independent permissions?
- Do we need metadata on the relationship?
- Do we need efficient joins and aggregation?

If yes, a join table is usually the stronger design.

---

## 35. Common Anti-Patterns

### Anti-pattern A — Delimited strings instead of arrays

```text
"admin,auditor,viewer"
```

This loses type safety, requires parsing, and makes querying/indexing awkward.

### Anti-pattern B — Massive business collections in one row

```text
customer.favorite_product_ids = [millions of IDs]
```

A collection that large generally has relational behavior.

### Anti-pattern C — Array as a foreign-key substitute

```sql
customer_ids bigint[]
```

This bypasses ordinary FK modeling.

### Anti-pattern D — Positional business meaning without explicit ordering

If the application says "element 1 is primary, element 2 is secondary," that is a business invariant. Consider whether a relational table with an explicit position column better expresses it.

---

## 36. Arrays and Constraints

PostgreSQL can enforce constraints on array-valued columns through normal expressions.

Examples:

```sql
CHECK (cardinality(tags) <= 20)
```

or:

```sql
CHECK (NOT ('forbidden' = ANY(tags)))
```

But remember the deeper principle:

> **A constraint should describe a domain invariant, not merely a storage trick.**

If the constraint becomes extremely complex, that is evidence the collection may need to be normalized.

---

## 37. Generated Arrays

Arrays can be produced from other relational data:

```sql
SELECT customer_id,
       array_agg(order_id ORDER BY order_id) AS order_ids
FROM orders
GROUP BY customer_id;
```

This is often excellent for read-model construction.

It is different from storing a mutable array as the authoritative source of truth.

A useful architecture pattern is:

```text
Normalized source of truth
        ↓
Aggregation / projection
        ↓
Array-valued read model
```

This often gives you both integrity and efficient read representation.

---

## 38. Arrays as Read Models

For example:

```text
orders
order_items
products
```

could remain fully normalized, while a reporting query generates:

```text
customer_id
product_ids[]
```

This is often safer than storing the array permanently unless there is a measured need for denormalization.

## 39. Array Query Performance Workflow

When a query involving arrays is slow:

### Step 1 — State the business predicate

Example:

> Return users whose role set overlaps the requested roles.

### Step 2 — Confirm the semantic expression

```sql
roles && $1::text[]
```

### Step 3 — Inspect the schema

Is this actually an array-shaped business concept?

### Step 4 — Inspect indexes

```sql
\d users
```

### Step 5 — Inspect the plan

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

### Step 6 — Compare actual vs estimated rows

Large estimation errors indicate a planning/statistics problem, not necessarily a SQL-writing problem.

### Step 7 — Benchmark realistic cardinalities

Test:

- small arrays;
- medium arrays;
- large arrays;
- common values;
- rare values;
- empty arrays;
- `NULL` arrays.

Create a table:

```sql
CREATE TABLE demo_users (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    roles text[] NOT NULL DEFAULT '{}'

```

Insert representative data:

```sql
INSERT INTO demo_users (tenant_id, roles)

    (1, ARRAY['admin','auditor']),
    (1, ARRAY['viewer']),

    (2, ARRAY['admin']);
```

Now intentionally run an unsafe tenant query:

```sql
SELECT *
FROM demo_users
WHERE 'admin' = ANY(roles);
```

Observe that a role predicate is not a tenant boundary.

Then correct it:

```sql
SELECT *
FROM demo_users
WHERE tenant_id = 1
  AND 'admin' = ANY(roles);
```

This lab ties array semantics to authorization architecture.

## 41. Lab — Membership vs Containment

Create rows such as:

```sql
INSERT INTO demo_users (tenant_id, roles)
VALUES
    (1, ARRAY['admin','auditor']),
    (1, ARRAY['auditor']),
    (1, ARRAY['admin','viewer']);
```

Compare:

```sql
SELECT *
FROM demo_users
WHERE 'admin' = ANY(roles);
```

with:

```sql
SELECT *
FROM demo_users
WHERE roles @> ARRAY['admin','auditor']::text[];
```

Then test overlap:

```sql
SELECT *
FROM demo_users
WHERE roles && ARRAY['viewer','auditor']::text[];
```

You should be able to explain the exact difference in one sentence for each query.

## 42. Lab — Unnest and Rebuild

Given:

```sql
SELECT id, roles
FROM demo_users;
```

Expand:

```sql
SELECT id, role
FROM demo_users
CROSS JOIN LATERAL unnest(roles) AS role;
```

Then rebuild:

```sql
SELECT id,
       array_agg(role ORDER BY role) AS roles
FROM (
    SELECT id, role
    FROM demo_users
    CROSS JOIN LATERAL unnest(roles) AS role
) s
GROUP BY id;
```

Think carefully about what information changed:

- ordering may have changed;
- duplicates may have been preserved or removed depending on transformations;
- `NULL` element handling matters;
- the rebuilt array is a new representation, not proof of identical physical/storage semantics.

## 43. Lab — GIN Benchmark

Create:

```sql
CREATE INDEX demo_users_roles_gin
ON demo_users
USING gin (roles);
```

Then run:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM demo_users
WHERE roles @> ARRAY['admin']::text[];
```

Scale the table substantially before drawing conclusions. A tiny test table may choose a sequential scan because that is cheaper.

The goal is not:

> "Make PostgreSQL use my index."

The goal is:

> **Understand why the planner chose the observed path and whether that path is appropriate for the real workload.**

## 44. Architecture Decision Matrix

| Requirement | Array | Child Table | JSONB |
|---|---:|---:|---:|
| Simple homogeneous values | Excellent | Good | Good |
| Element-level FK | Poor | Excellent | Poor |
| Child-level audit | Poor | Excellent | Possible but complex |
| Ordered list | Excellent | Excellent with position | Good |
| Semi-structured object | Poor | Good | Excellent |
| Frequent element updates | Can be costly | Excellent | Depends |
| GIN containment search | Excellent | Different indexing model | Excellent |
| Strong relational integrity | Limited | Excellent | Limited |
| Independent element lifecycle | Poor | Excellent | Poor |
| Compact parent-row representation | Excellent | Poorer | Excellent |

This is not a universal ranking. Workload and domain semantics determine the winner.

---

## 45. Decision Framework: Should This Be an Array?

Ask these questions in order:

```text
1. Is the collection homogeneous?
        ↓ yes
2. Does each element lack independent identity?
        ↓ yes
3. Does the parent own the whole collection lifecycle?
        ↓ yes
4. Do we mainly query membership/containment as one collection?
        ↓ yes
5. Is the collection bounded or operationally manageable?
        ↓ yes
6. Do ordering/duplicate/NULL semantics have a clear contract?
        ↓ yes

→ Array may be a strong design.
```

A "no" answer is not an automatic rejection, but it should trigger architecture review.

## 46. Array Safety Checklist

Before production use, verify:

### Semantics

- Is it a list, set-like collection, or multiset?
- Are duplicates meaningful?
- Is order meaningful?
- Is `NULL` meaningful?
- What does empty mean?

### Integrity

- Do elements need FKs?
- Do elements have independent lifecycle?
- Are there cross-row uniqueness rules?

### Performance

- How large can arrays become?
- How often are elements updated?
- What operators are queried?
- Is a GIN index justified?
- Have realistic plans been benchmarked?

### Application

- Does `null` differ from `[]`?
- Does the ORM map the type correctly?
- Are migrations safe?
- Are API PATCH semantics explicit?

### Operations

- What happens under replication?
- How large can WAL impact become?
- Are slow queries observable?
- Can the array be migrated to a child table later?

## 47. Expert Reasoning Questions

1. Why can an array be relationally convenient but architecturally non-relational?
2. Why does `@>` not mean multiset containment in the intuitive duplicate-count sense?
3. Why can a GIN index exist while PostgreSQL still chooses a sequential scan?
4. Why does updating one element of a large array have physical storage consequences?
5. When does an array stop being an attribute and start being a relationship?
6. Why can `NULL` array, empty array, and array containing `NULL` represent different API states?
7. Why is an array of foreign keys not equivalent to a join table?
8. Why can `array_agg` hide duplicate multiplication caused by joins?
9. Why can generated arrays be safer than stored arrays as a source of truth?
10. When would JSONB be superior to an array of composite-like information?
11. How would you migrate a large array column into a normalized child table with minimal downtime?
12. How would you prove an array query became faster rather than merely different?

## 50. Final Mental Model

Remember this:

> **An array is a powerful value type, not a miniature relational database.**

Use it when the collection belongs naturally to the row and benefits from collection-oriented operations.

Do not use it to avoid modeling relationships that PostgreSQL's relational system is specifically designed to represent.

The expert decision is not:

> "Can I put this into an array?"

It is:

> **"What invariants, access patterns, lifecycle rules, and operational costs follow from making this collection one column value?"**

---

## 51. Production Readiness Criteria

Before declaring an array-backed feature production-ready, prove that:

- the collection semantics are explicitly documented;
- tenant boundaries are enforced;
- `NULL` vs empty behavior is intentional;
- duplicate and ordering rules are explicit;
- maximum collection size is understood;
- query operators match the requirement;
- indexing strategy is workload-driven;
- realistic query plans have been inspected;
- write amplification is acceptable;
- API serialization preserves intended semantics;
- migration to normalized storage remains technically feasible if domain complexity grows.

---

## 52. Verification Standard

For PostgreSQL-version-sensitive behavior, verify against the PostgreSQL documentation for the deployed major version before relying on subtle array, operator, indexing, or planner details.

For production changes, validate with:

```text
Correctness tests
→ Integration tests
→ EXPLAIN / EXPLAIN ANALYZE
→ Representative dataset
→ Concurrency tests where relevant
→ Operational metrics
→ Rollback / migration plan
```
