# Chapter 01.4 — Subqueries

> **Phase:** 01 — Advanced SQL  
> **Chapter:** 01.4  
> **Level:** L2 → L7  
> **Primary goal:** Learn to reason about subqueries as relational expressions, understand their semantics before their syntax, predict NULL and cardinality behavior, recognize when PostgreSQL can transform them, and choose between subqueries, joins, aggregates, windows, and other formulations from evidence rather than folklore.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to:

- Define a subquery precisely and distinguish its semantic role from its textual location.
- Distinguish scalar, row, table/derived-table, correlated, and uncorrelated subqueries.
- Understand `EXISTS`, `IN`, `NOT IN`, `ANY`/`SOME`, `ALL`, and single-row comparisons.
- Predict behavior when a subquery returns zero, one, or many rows.
- Explain why `NOT IN` is dangerous when NULL can appear.
- Recognize when a correlated subquery expresses a per-row dependency.
- Understand that SQL formulation and physical execution are separate concerns.
- Reason about semijoin/antijoin behavior and duplicate preservation.
- Use subqueries safely in `SELECT`, `WHERE`, `FROM`, `HAVING`, `UPDATE`, `DELETE`, and other query contexts.
- Diagnose performance problems with `EXPLAIN (ANALYZE, BUFFERS)` rather than rewriting blindly.
- Decide when a subquery should remain a subquery and when a join, aggregate, window function, or `LATERAL` formulation is clearer or faster.
- Detect subquery mistakes in ORM-generated and AI-generated SQL.
- Defend a subquery design at a senior/staff/principal engineering interview.

## 2. The Core Mental Model

A subquery is not fundamentally “a query inside another query.” That description is syntactic.

The more useful engineering model is:

```text
Outer relation / expression
        ↓
Depends on another relation / result
        ↓
Evaluate relationship or derive value
        ↓
Compose the result into the outer query
```

A subquery can play several semantic roles:

```text
Scalar subquery     → produce one value
Row subquery        → produce one row for comparison/assignment
Table subquery      → produce a relation
EXISTS              → ask whether at least one row exists
IN                  → ask whether a value matches a set
NOT IN              → ask whether a value differs from every set member
ANY / SOME          → compare against at least one set member
ALL                 → compare against every set member
Correlated subquery→ outer row supplies values to inner evaluation
```

The first expert question is therefore not:

> “Should I use a subquery?”

It is:

> “What semantic question am I trying to express, and what cardinality should the inner result have?”

---

## 3. Three Layers of Understanding

### 3.1 Simple definition

A subquery is a query nested inside another SQL expression or query.

### 3.2 Engineering definition

A subquery is a nested relational computation whose output participates in an enclosing query as a value, boolean condition, row, or relation.

### 3.3 Expert definition

A subquery is a compositional query expression whose **scope, cardinality, correlation, NULL semantics, and relationship to the outer query** determine both correctness and potential execution strategies.

The expert definition matters because two SQL statements can look similar while having materially different semantics:

```sql
WHERE customer_id IN (...)
```

versus:

```sql
WHERE NOT EXISTS (...)
```

versus:

```sql
JOIN ...
```

These are not automatically interchangeable. Their row-preservation, duplicate, and NULL behavior must be reasoned about explicitly.

---

## 4. Subquery Taxonomy

## 4.1 Scalar subquery

A scalar subquery is used where one value is expected.

```sql
SELECT
    customer_id,
    (
        SELECT COUNT(*)
        FROM orders o
        WHERE o.customer_id = c.customer_id
    ) AS order_count
FROM customers c;
```

The semantic contract is:

```text
0 rows → NULL
1 row  → that row's single value
>1 row → error
```

The multi-row failure is a correctness signal, not something to “optimize away.”

Example:

```sql
SELECT
    (
        SELECT order_id
        FROM orders
        WHERE customer_id = 10
    );
```

This is valid only if the inner query produces at most one row at execution time.

If multiple rows are possible, you have not expressed a scalar fact.

---

## 4.2 Row subquery

A row subquery returns a single row that can be compared to another row value.

```sql
SELECT *
FROM customers c
WHERE (c.country, c.city) = (
    SELECT country, city
    FROM target_location
    WHERE id = 1
);
```

The number and types of columns must be compatible with the outer row expression.

---

## 4.3 Table / derived-table subquery

A subquery in `FROM` creates a derived relation.

```sql
SELECT x.customer_id, x.total_spent
FROM (
    SELECT customer_id, SUM(amount) AS total_spent
    FROM orders
    GROUP BY customer_id
) AS x
WHERE x.total_spent > 100000;
```

Think:

```text
inner SELECT
   ↓
virtual relation
   ↓
outer query consumes relation
```

This is particularly useful when the intermediate relation has a different grain from the base tables.

For example:

```text
orders
  grain = one row per order

aggregate subquery
  grain = one row per customer

outer query
  grain = one row per qualifying customer
```

A common source of bugs is failing to identify this grain transition.

---

## 4.4 Correlated subquery

A correlated subquery refers to columns from the outer query.

```sql
SELECT
    c.customer_id,
    c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'PAID'
);
```

The inner expression depends on the current outer row semantically.

Do **not** jump to the simplistic rule:

> “Correlated subqueries always execute once per outer row.”

That is a mental shortcut about one possible execution pattern, not a universal statement about PostgreSQL's physical plan. PostgreSQL can transform or execute semantically equivalent constructs using different plan strategies.

This distinction becomes critical in performance analysis.

---

## 4.5 Uncorrelated subquery

The inner query does not reference outer columns.

```sql
SELECT *
FROM products
WHERE price > (
    SELECT AVG(price)
    FROM products
);
```

The inner result is independent of individual outer rows at the logical level.

That does not mean the database must literally execute the textual subquery separately for every row. SQL describes semantics; the planner chooses an execution strategy.

---

# 5. Scope: The Boundary Between Queries

Consider:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

Inside the subquery:

- `o.customer_id` belongs to the inner query scope.
- `c.customer_id` is resolved from the outer query scope.

A reliable debugging technique is to qualify every column explicitly:

```sql
c.customer_id
```

rather than relying on ambiguous names.

This is especially important in generated SQL and large ORM queries.

---

# 6. Cardinality Is the Contract

For subqueries, always ask:

```text
Can the inner query return:
0 rows?
1 row?
Many rows?
```

And then:

```text
Does the outer operator accept:
scalar?
row?
set?
boolean existence?
```

## Cardinality matrix

| Construct | Inner result expectation | Zero rows | Many rows |
|---|---|---|---|
| Scalar subquery | ≤ 1 row, 1 column | `NULL` | error |
| Row comparison | ≤ 1 row, matching columns | context-dependent / NULL | error |
| `EXISTS` | any number | `FALSE` | `TRUE` |
| `IN` | one column, set of values | `FALSE` unless NULL semantics intervene | valid |
| `NOT IN` | one column, set of values | `TRUE` unless NULL semantics intervene | valid, but NULL-sensitive |
| `ANY` / `SOME` | set | false/NULL depending on operator and set | valid |
| `ALL` | set | true/NULL depending on operator and set | valid |
| Derived table | relation | empty relation | valid |

Memorize the **shape of the contract**, not a collection of isolated rules.

# 7. EXISTS — Existence, Not Value

Syntax:

```sql
EXISTS (subquery)
```

The question is:

> “Does this subquery produce at least one row?”

Example:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

The specific projected value is normally irrelevant because existence is what matters. PostgreSQL documents that an `EXISTS` subquery is generally evaluated only far enough to determine whether a row exists, so it is unwise to depend on full evaluation or side effects. citeturn324988search6

### Why `EXISTS` often expresses intent better than a join

Suppose the business question is:

> Find customers who have at least one paid order.

A join can produce duplicate customer rows when multiple paid orders exist:

```sql
SELECT c.customer_id
FROM customers c
JOIN orders o
  ON o.customer_id = c.customer_id
WHERE o.status = 'PAID';
```

This may return:

```text
customer 10
customer 10
customer 10
customer 20
```

You might add:

```sql
SELECT DISTINCT c.customer_id ...
```

but now `DISTINCT` is repairing a multiplication problem created by choosing a row-producing operator for an existence question.

A more direct formulation is:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'PAID'
);
```

### Engineering rule

When the business question is **whether at least one related row exists**, start by considering `EXISTS`.

Do not convert it to a join merely because joins feel more familiar.

---

# 8. IN — Membership in a Set

Syntax:

```sql
expression IN (subquery)
```

Example:

```sql
SELECT *
FROM customers
WHERE customer_id IN (
    SELECT customer_id
    FROM orders
    WHERE status = 'PAID'
);
```

Semantically, this asks whether the left-hand value matches at least one value from the subquery result.

`IN` is therefore naturally read as a **membership** question.

---

## 8.1 `IN` with a list

```sql
WHERE status IN ('PAID', 'SHIPPED', 'DELIVERED')
```

This is conceptually a disjunction:

```sql
status = 'PAID'
OR status = 'SHIPPED'
OR status = 'DELIVERED'
```

For subqueries, think:

```text
left value ∈ result set
```

---

# 9. NOT IN — The NULL Trap

This is one of the most important correctness lessons in SQL.

Naive intuition:

```sql
x NOT IN (1, 2, 3)
```

sounds like:

> x is different from 1, 2, and 3.

But SQL uses three-valued logic.

For a subquery:

```sql
x NOT IN (
    SELECT y
    FROM t
)
```

if the subquery contains a NULL and there is no equal non-NULL value, the result can be `NULL`, not `TRUE`. PostgreSQL explicitly documents this behavior. citeturn324988search3

Example:

```text
x = 5
subquery values = {1, 2, NULL}
```

Conceptually:

```text
5 <> 1  → TRUE
5 <> 2  → TRUE
5 <> NULL → NULL

TRUE AND TRUE AND NULL → NULL
```

And `WHERE` keeps only rows for which the condition is `TRUE`.

So the row is filtered out.

---

## 9.1 Safer anti-membership pattern

When the real business question is:

> “There must not exist a related row satisfying this condition.”

Prefer considering:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM blocked_customers b
    WHERE b.customer_id = c.customer_id
)
```

This expresses the semantic question directly.

It is not a universal commandment that `NOT EXISTS` must replace every `NOT IN`. You should still understand the specific query, data constraints, indexes, and planner behavior.

The critical lesson is:

> Never use `NOT IN` without understanding the NULL contract of the right-hand side.

---

# 10. ANY / SOME

Syntax:

```sql
expression operator ANY (subquery)
```

or:

```sql
expression operator SOME (subquery)
```

`SOME` is a synonym for `ANY`.

Example:

```sql
SELECT *
FROM products p
WHERE p.price > ANY (
    SELECT price
    FROM competitor_prices
);
```

Interpretation:

> Is `p.price > competitor_price` true for at least one value in the set?

This can be understood as an existential comparison over a set.

For equality:

```sql
x = ANY (subquery)
```

is closely related to membership:

```sql
x IN (subquery)
```

but the more general operator form makes `ANY` useful for inequalities and custom operators.

---

# 11. ALL

Syntax:

```sql
expression operator ALL (subquery)
```

Example:

```sql
SELECT *
FROM products p
WHERE p.price > ALL (
    SELECT price
    FROM competitor_prices
);
```

Interpretation:

> Is the comparison true for every value produced by the subquery?

This is naturally universal quantification:

```text
∀ value in set: condition is true
```

The empty-set behavior matters. In SQL, `ALL` over an empty set follows its logical truth conditions rather than behaving like an ordinary missing value.

Never guess empty-set semantics; test or consult the PostgreSQL documentation for the specific operator.

---

# 12. Single-Row Comparison

You can compare a value to a scalar subquery:

```sql
SELECT *
FROM employees
WHERE salary > (
    SELECT AVG(salary)
    FROM employees
);
```

You can also compare rows:

```sql
WHERE (department_id, salary) = (
    SELECT department_id, salary
    FROM benchmark
    WHERE benchmark_id = 1
)
```

The crucial issue is still cardinality.

If the inner query can return two benchmark rows, the statement is semantically broken for a single-row comparison.

# 13. Subquery Placement

A subquery can appear in multiple logical positions.

## 13.1 WHERE

```sql
SELECT *
FROM customers c
WHERE c.customer_id IN (
    SELECT customer_id
    FROM orders
    WHERE status = 'PAID'
);
```

Use when the inner result determines filtering.

## 13.2 SELECT list

```sql
SELECT
    c.customer_id,
    (
        SELECT COUNT(*)
        FROM orders o
        WHERE o.customer_id = c.customer_id
    ) AS order_count
FROM customers c;
```

Use when the subquery derives a value for each output row.

## 13.3 FROM

```sql
SELECT x.customer_id
FROM (
    SELECT customer_id, SUM(amount) AS total
    FROM orders
    GROUP BY customer_id
) x
WHERE x.total > 10000;
```

Use when you need an intermediate relation.

## 13.4 HAVING

```sql
SELECT customer_id, SUM(amount) AS total
FROM orders
GROUP BY customer_id
HAVING SUM(amount) > (
    SELECT AVG(customer_total)
    FROM customer_totals
);
```

Here the subquery participates in a group-level predicate.

## 13.5 UPDATE / DELETE

Subqueries can participate in data-modifying commands too.

Example:

```sql
DELETE FROM sessions s
WHERE NOT EXISTS (
    SELECT 1
    FROM active_users u
    WHERE u.user_id = s.user_id
);
```

The correctness stakes are higher because the subquery now controls data modification.

# 14. Correlation in Detail

Consider:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.amount > 10000
);
```

The inner query is correlated because it references `c.customer_id`.

A useful conceptual representation is:

```text
for each outer customer row
    ask: does a qualifying order exist for this customer?
```

That is a semantic description.

It does **not** prove that PostgreSQL will literally run a separate complete scan of `orders` once for every customer. Planner transformations, indexes, join-like strategies, and other execution mechanisms may change the physical work.

This distinction is essential:

```text
SQL semantics ≠ textual execution procedure
```

---

# 15. The Famous “Correlated Subquery = Slow” Myth

Naive claim:

> “Correlated subqueries are always slow.”

Why this fails:

1. It confuses logical dependence with physical execution.
2. It ignores indexing.
3. It ignores row counts and selectivity.
4. It ignores alternative join algorithms.
5. It ignores planner transformations.
6. It assumes one execution model from the SQL text.

Correct approach:

```text
Identify semantics
      ↓
Measure actual plan
      ↓
Inspect row estimates vs actual rows
      ↓
Inspect loops
      ↓
Inspect buffer activity
      ↓
Determine bottleneck
      ↓
Then rewrite if justified
```

A correlated `EXISTS` with a highly selective index can be an excellent implementation.

A rewritten join can also become worse if it creates huge intermediate row sets.

So the real engineering question is:

> “Which formulation produces the required semantics with acceptable measured work under this workload?”

# 16. EXISTS vs JOIN: The Cardinality Question

Consider a parent table:

```text
customers
-----------
1 Alice
2 Bob
```

and child rows:

```text
orders
-----------
101 customer 1
102 customer 1
103 customer 1
```

Query A:

```sql
SELECT c.id
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

Result:

```text
1
1
1
```

Query B:

```sql
SELECT c.id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

Result:

```text
1
```

They answer different relational questions.

```text
JOIN
→ produce related row combinations

EXISTS
→ test whether a relationship exists
```

This is one of the most important distinctions in this chapter.

---

# 17. The DISTINCT Repair Smell

A common pattern:

```sql
SELECT DISTINCT c.id
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'PAID';
```

This may be perfectly valid.

But ask:

> “Did I actually want order rows, or did I only want to test existence?”

If existence is the real semantic requirement:

```sql
SELECT c.id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
      AND o.status = 'PAID'
);
```

A `DISTINCT` after a multiplying join can sometimes conceal an incorrect mental model.

It is not automatically bad. It is a signal to inspect grain.

# 18. Subquery vs Aggregate

Suppose the requirement is:

> Find customers whose total order value exceeds ₹100,000.

One formulation:

```sql
SELECT c.customer_id
FROM customers c
WHERE (
    SELECT COALESCE(SUM(o.amount), 0)
    FROM orders o
    WHERE o.customer_id = c.customer_id
) > 100000;
```

Another formulation:

```sql
SELECT o.customer_id
FROM orders o
GROUP BY o.customer_id
HAVING SUM(o.amount) > 100000;
```

Both can be correct.

But they make different intermediate-grain choices.

### Subquery formulation

```text
customers
  ↓ per-customer derived scalar
filter customer
```

### Aggregate formulation

```text
orders
  ↓ aggregate
one row per customer
  ↓ filter
```

The better choice depends on the surrounding query, required columns, selectivity, indexes, cardinality, and plan.

Do not use a universal “joins are faster” or “subqueries are cleaner” rule.

---

# 19. Subquery vs Window Function

Suppose you need each employee plus their department average salary.

Subquery style:

```sql
SELECT
    e.employee_id,
    e.salary,
    (
        SELECT AVG(e2.salary)
        FROM employees e2
        WHERE e2.department_id = e.department_id
    ) AS department_avg
FROM employees e;
```

Window style:

```sql
SELECT
    employee_id,
    salary,
    AVG(salary) OVER (
        PARTITION BY department_id
    ) AS department_avg
FROM employees;
```

The window formulation directly describes a relation where every employee row is preserved while a group-level statistic is attached.

The key semantic distinction is:

```text
Subquery
→ derive a nested value/relation

Window function
→ compute across related rows while retaining row identity
```

Later chapters will analyze window functions in much greater depth.

---

# 20. Subquery vs LATERAL

Some correlated table-producing queries are easier to express with `LATERAL`.

Conceptually:

```text
ordinary derived table
→ independent

LATERAL derived table
→ may reference preceding FROM items
```

Example shape:

```sql
SELECT c.customer_id, recent.order_id
FROM customers c
CROSS JOIN LATERAL (
    SELECT o.order_id
    FROM orders o
    WHERE o.customer_id = c.customer_id
    ORDER BY o.created_at DESC
    LIMIT 1
) recent;
```

This chapter only establishes the connection. `LATERAL` receives its own dedicated chapter later in Phase 01.

# 21. Nested Query Results Are Relations

A powerful relational mental model is:

```text
base table
   ↓
query expression
   ↓
relation
   ↓
another query consumes it
```

For example:

```sql
SELECT *
FROM (
    SELECT customer_id, COUNT(*) AS order_count
    FROM orders
    GROUP BY customer_id
) x
WHERE x.order_count >= 10;
```

Think of the subquery as producing a relation:

```text
customer_id | order_count
------------+------------
10          | 12
11          | 4
12          | 27
```

The outer query then consumes that relation.

This viewpoint makes nested query composition much easier to reason about than thinking in terms of “inside SQL syntax.”

---

# 22. Empty Results Matter

Never only test the happy path.

For every subquery, intentionally test:

```text
0 rows
1 row
2+ rows
NULL values
duplicate values
```

For example:

```sql
SELECT
    100 > (
        SELECT MAX(price)
        FROM products
        WHERE false
    );
```

The aggregate itself returns one row containing NULL.

Contrast with:

```sql
SELECT
    100 > (
        SELECT price
        FROM products
        WHERE false
    );
```

A scalar subquery that returns no rows yields NULL.

The point is not merely the answer. The point is to understand **why the inner shape produces that outer behavior**.

---

# 23. Duplicate Values Inside IN

Suppose:

```text
subquery result =
1
1
1
2
```

For membership testing:

```sql
x IN (subquery)
```

repeated values do not create repeated outer rows by themselves.

This is a fundamental difference from an ordinary join.

```text
JOIN
→ row combinations can multiply

IN / EXISTS
→ boolean qualification of the outer row
```

This is another reason semijoin-style reasoning matters.

---

# 24. Anti-Joins and NOT EXISTS

Business requirement:

> Find customers who have never placed an order.

Strong semantic expression:

```sql
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

This means:

```text
For this customer,
there does not exist a matching order.
```

That is an anti-relationship query.

A left join can also express this pattern:

```sql
SELECT c.customer_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
WHERE o.customer_id IS NULL;
```

But the join formulation deserves careful review because the chosen join key and NULLability must match the intended anti-join semantics.

Do not mechanically rewrite every `NOT EXISTS` into a `LEFT JOIN` or vice versa.

---

# 25. Multi-Tenant Systems

In a multi-tenant application, correlated subqueries must preserve tenant boundaries.

Potentially dangerous:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

This is safe only if `customer_id` is globally unique or otherwise guarantees the tenant boundary.

In systems where identifiers may overlap by tenant, the relationship should reflect the real key:

```sql
WHERE o.tenant_id = c.tenant_id
  AND o.customer_id = c.customer_id
```

### Critical production rule

Do not assume:

```text
ID equality = tenant-safe relationship
```

Verify the actual key design.

This lesson connects directly to later chapters on relational modeling, constraints, RLS, multi-tenancy, and security.

---

# 26. Financial Data Example

Suppose a business asks:

> “Find accounts whose unpaid exposure exceeds their credit limit.”

A scalar correlated formulation might be:

```sql
SELECT a.account_id
FROM accounts a
WHERE (
    SELECT COALESCE(SUM(i.amount_due), 0)
    FROM invoices i
    WHERE i.account_id = a.account_id
      AND i.status = 'OPEN'
) > a.credit_limit;
```

This raises several expert questions:

1. Can `amount_due` be NULL?
2. Is currency normalized?
3. Are credits represented separately?
4. Does `SUM()` need a `COALESCE`?
5. Is `account_id` tenant-scoped?
6. What is the isolation requirement?
7. What indexes support the predicate?
8. Is the result used for a report or for a financial decision?
9. Could the account balance change concurrently?
10. Is the query running inside a transaction whose snapshot semantics matter?

A query can be syntactically correct and still be operationally wrong.

---

# 27. Temporal Example

Requirement:

> Find employees who had at least one active assignment overlapping a requested date.

An existence query may be clearer than a multiplying join:

```sql
SELECT e.employee_id
FROM employees e
WHERE EXISTS (
    SELECT 1
    FROM assignments a
    WHERE a.employee_id = e.employee_id
      AND a.start_at < $2
      AND a.end_at   > $1
);
```

The actual boundary semantics matter:

```text
[start, end)
```

versus:

```text
inclusive start + inclusive end
```

Do not let a subquery discussion hide a temporal modeling problem.

# 28. Planner and Execution Reasoning

PostgreSQL separates the SQL statement's declarative semantics from the chosen execution strategy. The PostgreSQL documentation describes query processing as progressing through parsing/analyzing and planning before execution, and the planner may choose among different physical paths. citeturn897849search9turn897849search1

Therefore:

```text
SQL text
  ≠
physical execution algorithm
```

A subquery may be transformed, flattened, joined, hashed, or otherwise incorporated into an execution plan depending on its structure and planner rules.

The correct workflow is:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Then inspect:

- estimated rows vs actual rows
- loops
- scan types
- join types
- buffer hits/reads
- sort/hash behavior where relevant
- total execution time

A rewrite without a measured baseline is not optimization; it is speculation.

---

# 29. Query Planner Misestimation Can Change Everything

Suppose a subquery is estimated to return:

```text
10 rows
```

but actually returns:

```text
1,000,000 rows
```

Then a strategy selected on the assumption of a tiny relation can become disastrous.

This is why advanced subquery debugging eventually connects to PostgreSQL statistics and cardinality estimation.

PostgreSQL documentation notes that correlated/multicolumn data relationships can make ordinary independent-column assumptions inaccurate, and extended statistics can capture some cross-column relationships. citeturn897849search12

The chain is:

```text
data distribution
→ statistics
→ cardinality estimate
→ plan choice
→ actual work
→ latency
```

So a “slow subquery” can actually be a **statistics problem**.

# 30. The N+1 Shape in SQL

Subqueries can expose N+1-like patterns at the SQL level when a value is independently derived for many outer entities.

Example:

```sql
SELECT
    c.customer_id,
    (
        SELECT MAX(o.created_at)
        FROM orders o
        WHERE o.customer_id = c.customer_id
    ) AS last_order_at
FROM customers c;
```

This is semantically clear.

But if the result is expensive under the actual workload, investigate the plan before declaring it “N+1.”

The application-level N+1 problem is different:

```text
1 API request
→ 1 query for customers
→ N queries for orders
```

versus a SQL-level nested expression inside one statement.

They should not be conflated.

---

# 31. ORM / NestJS Considerations

Suppose a service method wants customers with paid orders.

A developer may write application logic that loads customers and then checks orders one customer at a time.

That creates:

```text
application loop
→ database round trip
→ application loop
→ database round trip
→ ...
```

A set-based SQL formulation can instead express the relationship in one statement:

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'PAID'
);
```

This is not merely a “database trick.” It changes where the work occurs and how many network round trips the system performs.

When reviewing ORM-generated SQL, inspect whether the generated statement:

- preserves the intended grain
- creates hidden joins
- introduces unnecessary `DISTINCT`
- uses correlated predicates correctly
- has tenant predicates
- generates scalar subqueries where a set-based strategy would be better
- causes parameter-sensitive plan issues

Always inspect generated SQL rather than trusting the ORM abstraction blindly.

# 32. AI / Vibe-Coding Failure Patterns

AI-generated SQL commonly makes subquery mistakes because it recognizes syntax patterns without reliably reasoning about data shape.

## Failure 1 — Blind `NOT IN`

```sql
WHERE id NOT IN (SELECT id FROM other_table)
```

Problem:

```text
other_table.id may contain NULL
```

Result:

unexpected filtering due to three-valued logic.

---

## Failure 2 — Scalar subquery without uniqueness proof

```sql
SELECT (
    SELECT email
    FROM users
    WHERE organization_id = 10
);
```

Problem:

multiple users may exist.

Better reasoning:

```text
What constraint guarantees ≤ 1 row?
```

If no constraint exists, the query is suspect.

---

## Failure 3 — Join instead of existence test

```sql
SELECT DISTINCT c.id
FROM customers c
JOIN orders o ON ...
```

Problem:

`DISTINCT` may be compensating for incorrect row multiplication.

---

## Failure 4 — Missing tenant predicate

```sql
WHERE o.customer_id = c.customer_id
```

Problem:

identifier may not be globally unique.

---

## Failure 5 — Rewrite by folklore

AI says:

> “Joins are always faster than subqueries.”

This is not an acceptable engineering justification.

Required evidence:

```text
EXPLAIN
statistics
cardinality
indexes
workload
actual timing
```

---

## Failure 6 — Accidental semantic change during optimization

Original:

```sql
WHERE EXISTS (...)
```

Generated rewrite:

```sql
JOIN ...
```

Potential change:

```text
one outer row
→ many output rows
```

A rewrite is correct only if the result semantics remain correct.

# 33. Common Developer Mistakes

### Mistake: “Subqueries are slower than joins.”

**Your assumption:** the syntax determines performance.

**Problem:** PostgreSQL chooses an execution plan.

**Why it fails:** the same semantics can be implemented using different physical strategies.

**Correct mental model:** inspect the plan and workload.

**Production consequence:** unnecessary rewrites can make a query worse.

**Better approach:** measure first.

---

### Mistake: Using `COUNT(*) > 0` for existence everywhere

Example:

```sql
WHERE (
    SELECT COUNT(*)
    FROM orders o
    WHERE o.customer_id = c.customer_id
) > 0
```

This asks the database to derive a count when the actual semantic question is existence.

Consider:

```sql
WHERE EXISTS (...)
```

because existence is the business predicate.

---

### Mistake: Ignoring NULL in `NOT IN`

This is one of the most dangerous correctness bugs because the query often looks perfectly reasonable in code review.

---

### Mistake: Ignoring cardinality guarantees

A scalar subquery should make you immediately ask:

> “What proves there is at most one row?”

The strongest proof is usually a schema-level uniqueness guarantee rather than a comment.

# 34. Production Debugging Framework

When a subquery query is wrong or slow:

## Step 1 — State the business question

Example:

> “Return one row per customer who has at least one paid order.”

## Step 2 — State the intended grain

```text
one row per customer
```

## Step 3 — Classify the subquery

```text
EXISTS?
IN?
scalar?
derived table?
correlated?
```

## Step 4 — Check cardinality

```text
0 / 1 / many?
```

## Step 5 — Check NULL behavior

Especially:

```text
IN
NOT IN
ANY
ALL
scalar comparison
```

## Step 6 — Check key correctness

```text
Does the predicate use the real relationship key?
```

## Step 7 — Check tenant/security boundaries

```text
tenant_id
RLS
authorization scope
```

## Step 8 — Run EXPLAIN ANALYZE

Do not speculate.

## Step 9 — Compare estimated vs actual rows

Large divergence may indicate a statistics or data-skew problem.

## Step 10 — Only then compare alternative formulations

```text
subquery
vs join
vs aggregate
vs window
vs lateral
```

## Step 11 — Re-test correctness

Performance is not success if semantics changed.

# 35. Subquery Decision Framework

Use this as a starting heuristic, not a law.

```text
What question am I asking?
        │
        ├── “Does a related row exist?”
        │       → EXISTS / NOT EXISTS
        │
        ├── “Is this value a member of a set?”
        │       → IN / = ANY
        │
        ├── “Must this comparison hold for every value?”
        │       → ALL
        │
        ├── “Do I need exactly one derived value?”
        │       → scalar subquery / aggregate / window
        │
        ├── “Do I need an intermediate relation?”
        │       → derived table / CTE / other relational expression
        │
        ├── “Do I need per-row top-N related data?”
        │       → consider LATERAL
        │
        └── “Do I need row combinations from both sides?”
                → JOIN
```

Then validate with actual workload data.

---

# 36. When a Subquery Is Better

Subqueries are often a good fit when the semantics are naturally nested:

```text
existence
membership
single derived scalar
anti-existence
intermediate aggregate relation
```

They can make the query communicate the business question directly.

Example:

```sql
WHERE EXISTS (...)
```

is often immediately understandable as:

> related record exists.

---

# 37. When a Join May Be Better

A join may be preferable when you genuinely need columns from both relations and want those row combinations to participate in the outer result.

Example:

```sql
SELECT
    c.id,
    o.order_id,
    o.amount
FROM customers c
JOIN orders o
  ON o.customer_id = c.id;
```

That is a row-combination question, not merely an existence question.

---

# 38. When an Aggregate May Be Better

If the requirement is fundamentally:

```text
summarize many rows into one group-level value
```

aggregation may better express the computation.

Example:

```sql
SELECT customer_id, SUM(amount)
FROM orders
GROUP BY customer_id;
```

The semantic grain is explicit.

---

# 39. When a Window Function May Be Better

When you need both:

```text
original row identity
+
calculation across a related partition
```

window functions are often the natural tool.

Example:

```sql
AVG(salary) OVER (PARTITION BY department_id)
```

---

# 40. Readability vs Optimization

Do not optimize away a subquery merely because another formulation is shorter.

A senior engineer evaluates:

```text
Correctness
Semantics
Maintainability
Execution plan
Operational behavior
Future data growth
Security
```

A one-line query that nobody can safely reason about is not necessarily superior to a slightly longer query with a clear semantic boundary.

# 41. Testing Strategy

For every important subquery, create tests around edge cardinalities.

## Dataset matrix

Test:

```text
parent with 0 children
parent with 1 child
parent with many children
child value NULL
duplicate child values
missing parent
multiple candidate scalar rows
empty subquery
```

## Example `NOT IN` regression test

Test both:

```text
right side = {1, 2, 3}
```

and:

```text
right side = {1, 2, NULL}
```

The second case is essential.

## Example scalar regression test

Test:

```text
0 rows
1 row
2 rows
```

The third case should expose an invalid scalar assumption.

# 44. Failure Lab: Scalar Cardinality

Run:

```sql

    SELECT x
    FROM (VALUES (10), (20)) AS t(x)

```

Observe the failure.

Then ask:

> “What schema or predicate guarantee would make this safe?”

Possible answer patterns include:

```text
PRIMARY KEY lookup
UNIQUE constraint
unique composite key
aggregation
LIMIT 1 — but only when arbitrary selection is actually correct
```

Do not use `LIMIT 1` as a universal repair.

If business semantics require a unique row, fix the data model or predicate.

# 45. Anti-Pattern Catalog

| Anti-pattern | Why dangerous | Better reasoning |
|---|---|---|
| `NOT IN` without NULL analysis | three-valued logic can filter unexpectedly | prove non-nullability or use existence semantics |
| scalar subquery without uniqueness | multi-row runtime failure | prove ≤1 row |
| join + `DISTINCT` for existence | hides row multiplication | consider `EXISTS` |
| “all correlated subqueries are slow” | confuses semantics and plan | inspect plan |
| rewriting every subquery as a join | can change grain | preserve semantics first |
| `COUNT(*) > 0` for existence | computes a count for a boolean question | consider `EXISTS` |
| omitting tenant predicate | cross-tenant leakage | use actual tenant-scoped key |
| adding `LIMIT 1` to silence multi-row error | may produce arbitrary/wrong data | establish real uniqueness |
| optimizing before baseline | no evidence | benchmark with realistic data |

# 48. Principal-Level Scenario

You are reviewing this query in a multi-tenant ERP:

```sql
SELECT c.id,
       (
           SELECT o.amount
           FROM orders o
           WHERE o.customer_id = c.id
           ORDER BY o.created_at DESC
           LIMIT 1
       ) AS latest_amount
FROM customers c
WHERE c.status = 'ACTIVE';
```

You are told:

> “It is slow in production. Rewrite it using a join.”

Do **not** immediately comply.

First ask:

```text
1. Is customer_id globally unique?
2. What is the tenant relationship?
3. What index exists on orders?
4. How many active customers exist?
5. How many orders per customer?
6. Is the latest row deterministic under ties?
7. Is NULL latest_amount acceptable?
8. What does EXPLAIN ANALYZE show?
9. What is the buffer profile?
10. Is the workload read-heavy or bursty?
```

Then compare alternatives, potentially including:

- correlated scalar subquery
- `LATERAL`
- `DISTINCT ON`
- window function
- aggregate + join-back

The correct solution is the one that preserves the exact business semantics and performs acceptably under measured production characteristics.
