# 01.11 — LATERAL Queries

> **Phase 01 — Advanced SQL**
>
> LATERAL is not merely another JOIN spelling. It changes the dependency model of a `FROM` item: a lateral subquery or table function may reference columns produced by preceding `FROM` items, making the right-hand operation parameterized by the current left-hand row.

---

## 1. Learning Objective

By the end of this chapter you should be able to:

- explain what `LATERAL` means semantically and operationally;
- distinguish a normal derived table from a lateral derived table;
- reason about the left-to-right dependency introduced by `LATERAL`;
- use `CROSS JOIN LATERAL` and `LEFT JOIN LATERAL` correctly;
- solve top-N-per-group and per-row lookup problems without accidental global limits;
- use `LATERAL` with table-valued functions and set-returning functions;
- understand when a correlated subquery and a lateral join express the same logical dependency;
- reason about parameterized execution and repeated inner work;
- identify when `LATERAL` is elegant and when it creates an expensive nested-loop-shaped workload;
- analyze its interaction with indexes, ordering, `LIMIT`, predicates, and row counts;
- use it safely in multi-tenant, temporal, inventory, ERP, and API-facing queries;
- review AI-generated SQL that uses `LATERAL` without understanding its cost model.

---

## 2. Precise Definition

### Simple definition

`LATERAL` allows a `FROM` item to reference columns from a preceding `FROM` item in the same `FROM` list.

### Engineering definition

A lateral relation is a relation whose evaluation may depend on the current row of an earlier relation. Instead of producing one relation independently, the inner expression is parameterized by values from the current outer row.

### Expert definition

`LATERAL` exposes a correlated relational dependency in the `FROM` clause. For each qualifying outer row or outer row-set according to the chosen join structure, PostgreSQL may evaluate the lateral item with outer-column values bound as parameters. This is especially powerful when the inner operation can exploit an index and stop early with `ORDER BY ... LIMIT`, but it can also multiply work by the number of outer rows.

---

## 3. The Core Mental Model

Without `LATERAL`:

```text
FROM A
JOIN (
  SELECT ...
  FROM B
) B2 ON ...
```

The derived table must be logically valid without depending on `A`.

With `LATERAL`:

```text
FROM A
CROSS JOIN LATERAL (
  SELECT ...
  FROM B
  WHERE B.a_id = A.id
) B2
```

The dependency is explicit:

```text
A row
  ↓ supplies values
LATERAL expression
  ↓ produces rows for that A row
Join result
```

The most useful mental model is:

> **`LATERAL` turns a `FROM` item into a parameterized relation.**

---

## 4. Why LATERAL Exists

Many real queries ask a question of this form:

> “For each row in A, run a different query against B using values from A.”

Examples:

- for each customer, fetch their latest order;
- for each product, fetch the three most recent price changes;
- for each branch, find today's latest inventory state;
- for each order, fetch its most recent payment attempt;
- for each event, locate the closest preceding event;
- for each API resource, expand a dependent collection;
- for each JSON/document row, invoke a row-dependent table function.

A normal derived table cannot directly reference an earlier sibling relation. `LATERAL` gives SQL an explicit mechanism for that dependency in the `FROM` clause.

---

## 5. Syntax Forms

### 5.1 `CROSS JOIN LATERAL`

```sql
SELECT ...
FROM parent p
CROSS JOIN LATERAL (
    SELECT ...
    FROM child c
    WHERE c.parent_id = p.id
) x;
```

Equivalent comma style:

```sql
SELECT ...
FROM parent p,
LATERAL (
    SELECT ...
    FROM child c
    WHERE c.parent_id = p.id
) x;
```

Use `CROSS JOIN LATERAL` when an outer row should survive only when the lateral expression yields at least one row.

### 5.2 `LEFT JOIN LATERAL`

```sql
SELECT ...
FROM parent p
LEFT JOIN LATERAL (
    SELECT ...
    FROM child c
    WHERE c.parent_id = p.id
) x ON true;
```

This preserves the parent row even when the lateral expression returns no rows.

This is one of the most useful patterns in production.

### 5.3 LATERAL table functions

PostgreSQL permits functions in the `FROM` list to reference columns from preceding `FROM` items. Writing `LATERAL` explicitly is useful for readability and for communicating the dependency to reviewers.

```sql
SELECT p.id, item
FROM payloads p
CROSS JOIN LATERAL jsonb_array_elements(p.payload -> 'items') AS item;
```

## 6. The Most Important Distinction: Global vs Per-Row LIMIT

Consider:

```sql
SELECT *
FROM customers c
JOIN (
    SELECT *
    FROM orders
    ORDER BY created_at DESC
    LIMIT 1
) o ON o.customer_id = c.id;
```

This asks for **one order globally**, not one order per customer.

The lateral form expresses the actual requirement:

```sql
SELECT c.id,
       c.name,
       o.id AS latest_order_id,
       o.created_at
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id, o.created_at
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 1
) o ON true;
```

Mental model:

```text
Customer 1 → query orders for customer 1 → latest 1
Customer 2 → query orders for customer 2 → latest 1
Customer 3 → query orders for customer 3 → latest 1
...
```

This is a canonical `LATERAL` workload.

---

## 7. LATERAL vs Correlated Scalar Subquery

Some problems can be written as a correlated scalar subquery:

```sql
SELECT
    c.id,
    (
        SELECT o.id
        FROM orders o
        WHERE o.customer_id = c.id
        ORDER BY o.created_at DESC, o.id DESC
        LIMIT 1
    ) AS latest_order_id
FROM customers c;
```

Or with `LATERAL`:

```sql
SELECT c.id, o.id AS latest_order_id
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 1
) o ON true;
```

The logical dependency is closely related, but the result shape differs.

A scalar subquery promises at most one scalar value.

A lateral relation may return zero, one, or many rows.

Therefore `LATERAL` is often the cleaner abstraction when the dependent operation naturally returns a relation rather than a scalar.

---

## 8. LATERAL vs Normal JOIN

### Normal JOIN

Use a normal join when both relations can be conceptually formed independently and connected through a join predicate.

```sql
SELECT ...
FROM customers c
JOIN orders o
  ON o.customer_id = c.id;
```

### LATERAL JOIN

Use lateral when the right side depends on the current left-side row and that dependency is central to the query.

```sql
SELECT ...
FROM customers c
LEFT JOIN LATERAL (
    SELECT ...
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC
    LIMIT 3
) o ON true;
```

The second query is not merely “a different way to join.” Its right-hand relation is parameterized by `c`.

---

## 9. The Join Type Matters

### `CROSS JOIN LATERAL`

For each outer row:

- evaluate the lateral expression;
- keep its produced rows;
- if it returns zero rows, the outer row contributes zero rows.

### `LEFT JOIN LATERAL ... ON true`

For each outer row:

- evaluate the lateral expression;
- emit matching lateral rows;
- if none exist, emit one null-extended result for the lateral columns.

This distinction is critical in APIs.

Suppose every customer should appear, whether or not they have orders. `LEFT JOIN LATERAL` is usually the correct semantic choice.

---

## 10. Top-N Per Group

This is one of the strongest reasons to learn `LATERAL`.

### Requirement

> Return the three newest orders for every customer.

```sql
SELECT
    c.id,
    c.name,
    o.id AS order_id,
    o.created_at,
    o.total_amount
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id,
           o.created_at,
           o.total_amount
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 3
) o ON true;
```

Result shape:

```text
customer 1 → order A
customer 1 → order B
customer 1 → order C
customer 2 → order D
customer 2 → order E
...
```

If the business grain is “customer + order”, this is correct.

If the API requires one row per customer with an array of the three orders, aggregate after the lateral operation:

```sql
SELECT
    c.id,
    c.name,
    COALESCE(
        jsonb_agg(
            jsonb_build_object(
                'id', o.id,
                'created_at', o.created_at,
                'total_amount', o.total_amount
            )
            ORDER BY o.created_at DESC, o.id DESC
        ) FILTER (WHERE o.id IS NOT NULL),
        '[]'::jsonb
    ) AS recent_orders
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id, o.created_at, o.total_amount
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 3
) o ON true
GROUP BY c.id, c.name;
```

---

## 11. The Index That Makes the Pattern Powerful

For the top-N query above, a useful index often looks like:

```sql
CREATE INDEX idx_orders_customer_created_id
ON orders (customer_id, created_at DESC, id DESC);
```

Conceptual execution:

```text
Outer customer row
    ↓
parameterized lookup on customer_id
    ↓
index already ordered by created_at DESC, id DESC
    ↓
read only first N rows
    ↓
stop
```

This can be dramatically cheaper than repeatedly sorting all orders for each customer.

The lesson is not “LATERAL is fast.”

The lesson is:

> **LATERAL + selective outer rows + matching index + small LIMIT can produce an excellent parameterized lookup pattern.**

---

## 12. Deterministic Top-N

Never rely on a non-unique ordering when business correctness requires stable results.

Bad:

```sql
ORDER BY created_at DESC
LIMIT 1
```

Better:

```sql
ORDER BY created_at DESC, id DESC
LIMIT 1
```

Why?

If multiple rows share the same timestamp, the business needs a deterministic tie-breaker.

This matters for:

- latest record selection;
- audit histories;
- inventory state;
- payment attempts;
- status snapshots;
- queue selection;
- API pagination.

---

## 13. Temporal “As-Of” Lookup

Suppose each transaction must use the most recent effective price at or before the transaction time.

```sql
SELECT
    t.id,
    t.product_id,
    t.occurred_at,
    p.price
FROM transactions t
LEFT JOIN LATERAL (
    SELECT ph.price
    FROM price_history ph
    WHERE ph.product_id = t.product_id
      AND ph.effective_at <= t.occurred_at
    ORDER BY ph.effective_at DESC, ph.id DESC
    LIMIT 1
) p ON true;
```

This is a powerful temporal lookup pattern.

The correctness invariant is:

```text
selected effective_at <= transaction occurred_at
AND
selected effective_at is maximal among eligible rows
```

Do not describe this merely as “latest price.” It is **latest price as of a specific business time**.

---

## 14. Multi-Tenant Safety

In a multi-tenant system, the tenant boundary must usually participate in the lateral lookup.

Dangerous:

```sql
FROM products p
LEFT JOIN LATERAL (
    SELECT *
    FROM prices pr
    WHERE pr.product_id = p.id
    ORDER BY pr.effective_at DESC
    LIMIT 1
) pr ON true
```

Safer when IDs are not globally unique or isolation is defense-in-depth:

```sql
FROM products p
LEFT JOIN LATERAL (
    SELECT *
    FROM prices pr
    WHERE pr.tenant_id = p.tenant_id
      AND pr.product_id = p.id
    ORDER BY pr.effective_at DESC, pr.id DESC
    LIMIT 1
) pr ON true
```

The index should reflect the access path:

```sql
CREATE INDEX idx_prices_tenant_product_effective
ON prices (tenant_id, product_id, effective_at DESC, id DESC);
```

Do not rely on application code to “remember” the tenant filter. Database query semantics should make the isolation boundary explicit wherever required by the data model.

## 15. Inventory Example

Requirement:

> For every branch and SKU, show the latest inventory snapshot.

```sql
SELECT
    b.id AS branch_id,
    s.id AS sku_id,
    inv.quantity,
    inv.recorded_at
FROM branches b
CROSS JOIN skus s
LEFT JOIN LATERAL (
    SELECT i.quantity, i.recorded_at
    FROM inventory_snapshots i
    WHERE i.branch_id = b.id
      AND i.sku_id = s.id
    ORDER BY i.recorded_at DESC, i.id DESC
    LIMIT 1
) inv ON true;
```

However, this query starts with `branches × skus`.

If that Cartesian base is huge, the problem is not “LATERAL performance.” The problem is the chosen population.

The correct review sequence is:

```text
Define required population
→ verify cardinality
→ identify dependent lookup
→ inspect index
→ measure execution
```

---

## 16. LATERAL with `VALUES`

LATERAL can make inline parameterized sets readable.

```sql
SELECT x.base_value,
       y.square_value,
       y.cube_value
FROM (VALUES (2), (3), (4)) AS x(base_value)
CROSS JOIN LATERAL (
    SELECT
        x.base_value * x.base_value AS square_value,
        x.base_value * x.base_value * x.base_value AS cube_value
) y;
```

This is useful for compact transformations, although it should not be used merely to make simple expressions look more complicated.

---

## 17. LATERAL with Set-Returning Functions

A dependent function invocation can be expressed naturally with LATERAL.

Example with JSON arrays:

```sql
SELECT
    p.id,
    elem
FROM products p
CROSS JOIN LATERAL jsonb_array_elements(p.attributes -> 'tags') AS elem;
```

Another example:

```sql
SELECT
    o.id,
    x.*
FROM orders o
CROSS JOIN LATERAL jsonb_to_recordset(o.payload -> 'lines')
    AS x(product_id bigint, quantity numeric, price numeric);
```

This lets one row supply input to a table-valued operation that returns zero, one, or many rows.

---

## 18. LATERAL and Functions: Important Safety Considerations

For production code, do not assume that a table-valued function is cheap merely because the SQL looks compact.

Investigate:

- how many times the function runs;
- whether it is SQL, PL/pgSQL, or another language;
- whether it performs additional SQL internally;
- whether it is volatile or stable;
- whether it can return many rows;
- whether each invocation allocates substantial memory or performs expensive work.

The query may be syntactically elegant while hiding a massive amount of repeated work.

---

## 19. LATERAL and N+1 Thinking

A common misconception is:

> “N+1 is only an application problem.”

It can also appear inside SQL.

Consider:

```text
100,000 outer rows
×
1 dependent lookup per row
=
100,000 parameterized inner executions or inner iterations
```

This may be entirely appropriate when each lookup is highly selective and index-backed.

It may be disastrous when the inner side scans thousands of rows or performs a sort for every outer row.

So the correct question is not:

> “Does this have a nested loop?”

The correct question is:

> “What is the total amount of work generated by the parameterization?”

---

## 20. LATERAL and Nested Loops

A lateral dependency naturally fits a parameterized nested-loop shape.

Conceptually:

```text
for each outer row:
    bind outer values
    execute / scan the lateral relation
    emit returned rows
```

This is excellent when:

```text
outer rows = relatively small
AND
inner lookup = highly selective
AND
inner lookup = index-supported
AND
inner result = small
```

It is dangerous when:

```text
outer rows = huge
OR
inner lookup = broad
OR
inner side sorts/aggregates repeatedly
OR
inner function is expensive
OR
result fan-out is large
```

---

## 21. Anti-Pattern: LATERAL Everywhere

Do not replace every correlated query with `LATERAL`.

A single set-based join may be better when the entire matching relation can be processed efficiently in bulk.

For example, if the requirement is:

> fetch all orders for all customers,

then:

```sql
SELECT ...
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

is usually more natural than a lateral subquery that retrieves all matching orders.

Use LATERAL because the dependency and access shape justify it—not because it is “advanced SQL.”

---

## 22. Top-1 Per Group: LATERAL vs Window Function

These can solve related problems.

### LATERAL

```sql
SELECT c.id, o.id
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 1
) o ON true;
```

### Window function

```sql
SELECT id, customer_id
FROM (
    SELECT
        o.id,
        o.customer_id,
        ROW_NUMBER() OVER (
            PARTITION BY o.customer_id
            ORDER BY o.created_at DESC, o.id DESC
        ) AS rn
    FROM orders o
) x
WHERE rn = 1;
```

Neither is universally better.

The architectural question is:

```text
How many outer groups exist?
How much data exists in the inner relation?
Can the inner lookup stop early?
Can a composite index satisfy the lookup and order?
Is bulk processing cheaper than repeated parameterized probes?
```

---

## 23. Top-N Per Group: A Cost Intuition

Suppose:

```text
customers = 10,000
orders = 50,000,000
N = 3
```

A lateral plan with an excellent index may conceptually perform:

```text
10,000 outer rows
×
very small index probe
×
up to 3 returned rows
```

A window approach may process a much larger portion of the 50 million order rows before ranking.

But the opposite can also happen. If the outer relation contains hundreds of thousands or millions of rows and the inner relation can be processed efficiently in one pass, repeated parameterized probes may lose.

Measure.

## 24. `LEFT JOIN LATERAL` and Optional Data

A very common API requirement is:

> “Return the parent even when there is no matching dependent resource.”

Example:

```sql
SELECT
    c.id,
    c.name,
    o.id AS latest_order_id
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 1
) o ON true;
```

Without the `LEFT`, you can unintentionally turn optional data into mandatory data.

This is a semantic bug, not merely a join-style preference.

---

## 25. `ON true` Is Not a Hack Here

You will often see:

```sql
LEFT JOIN LATERAL (...) x ON true
```

The actual correlation predicate is inside the lateral subquery:

```sql
WHERE x.key = outer.key
```

`ON true` means:

> once the lateral expression has produced its rows for this outer row, attach them; the dependency itself was already expressed inside the lateral expression.

For many readers, this is initially surprising. It becomes straightforward once the dependency model is understood.

---

## 26. Scope Rules

The lateral expression can reference preceding items in the `FROM` list.

Conceptually:

```sql
FROM A,
     B,
     LATERAL C(A, B)
```

means `C` can refer to columns from `A` and `B`.

But if you move the lateral expression before the required source, the reference is no longer available.

This makes `FROM` ordering semantically important when lateral dependencies exist.

---

## 27. Refactoring to LATERAL

A good refactoring sequence is:

```text
1. State the outer population.
2. State the dependent question.
3. Identify which outer columns parameterize the dependent question.
4. Decide whether the dependent result is scalar or relational.
5. Decide whether missing dependent rows should eliminate or preserve the outer row.
6. Add deterministic ordering if using LIMIT.
7. Add the supporting index.
8. Measure the plan.
```

Example requirement:

> For every account, return its most recent successful payment attempt.

Outer relation:

```text
accounts
```

Parameter:

```text
account_id
```

Dependent relation:

```text
payment_attempts
```

Eligibility:

```text
status = 'succeeded'
```

Ordering:

```text
created_at DESC, id DESC
```

Multiplicity:

```text
1 row per account
```

Missing-row behavior:

```text
preserve account
```

Query:

```sql
SELECT a.id,
       p.id AS payment_attempt_id,
       p.created_at
FROM accounts a
LEFT JOIN LATERAL (
    SELECT p.id, p.created_at
    FROM payment_attempts p
    WHERE p.account_id = a.id
      AND p.status = 'succeeded'
    ORDER BY p.created_at DESC, p.id DESC
    LIMIT 1
) p ON true;
```

---

## 28. Index Design for LATERAL

Index design must follow the actual dependent predicate and ordering.

For:

```sql
WHERE account_id = a.id
  AND status = 'succeeded'
ORDER BY created_at DESC, id DESC
LIMIT 1
```

a natural candidate is:

```sql
CREATE INDEX idx_payment_attempts_account_success_created
ON payment_attempts (account_id, created_at DESC, id DESC)
WHERE status = 'succeeded';
```

Why a partial index may be attractive:

- it stores only rows relevant to this workload;
- it can reduce index size;
- it can improve locality;
- it directly matches the predicate.

But index design must account for the broader workload. A specialized index should not be created solely because one query example looks good.

---

## 29. Filtering Inside vs Outside the LATERAL

Compare:

```sql
LEFT JOIN LATERAL (
    SELECT ...
    FROM orders o
    WHERE o.customer_id = c.id
      AND o.status = 'paid'
    ORDER BY ...
    LIMIT 3
) o ON true
```

with filtering after the join:

```sql
LEFT JOIN LATERAL (
    SELECT ...
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY ...
    LIMIT 3
) o ON true
WHERE o.status = 'paid'
```

These are not equivalent.

The first asks for the three newest **paid** orders.

The second asks for the three newest orders and then filters those rows for `paid`.

This can produce different results.

The dependency's eligibility rules usually belong inside the lateral expression when they define which rows qualify for the per-parent selection.

---

## 30. LIMIT Is Part of the Business Semantics

Do not treat `LIMIT` as a cosmetic optimization.

In:

```sql
ORDER BY effective_at DESC
LIMIT 1
```

`LIMIT 1` is part of the business rule:

> choose one record from the eligible set.

If the requirement changes to:

> choose all tied records sharing the latest effective timestamp,

then `LIMIT 1` may be wrong.

This is why deterministic ordering and explicit tie semantics matter.

---

## 31. LATERAL and “Latest Row” Semantics

“Latest” can mean different things:

- latest by insertion time;
- latest by business timestamp;
- latest successful state;
- latest non-cancelled event;
- latest row visible to the transaction;
- latest row as of another event's timestamp.

LATERAL does not define “latest.”

The query's predicate and `ORDER BY` define it.

Always specify the business semantics first.

---

## 32. Production Scenario: ERP Document State

Requirement:

> For every invoice, return the latest status transition and the user who performed it.

```sql
SELECT
    i.id AS invoice_id,
    s.status,
    s.changed_at,
    u.id AS changed_by_id,
    u.name AS changed_by_name
FROM invoices i
LEFT JOIN LATERAL (
    SELECT
        sh.status,
        sh.changed_at,
        sh.changed_by_user_id
    FROM invoice_status_history sh
    WHERE sh.invoice_id = i.id
    ORDER BY sh.changed_at DESC, sh.id DESC
    LIMIT 1
) s ON true
LEFT JOIN users u
    ON u.id = s.changed_by_user_id;
```

Potential correctness question:

> Is `changed_at` guaranteed unique?

If not, `id DESC` provides deterministic tie-breaking, assuming `id` represents a suitable stable ordering key.

Potential performance question:

> Is there an index on `(invoice_id, changed_at DESC, id DESC)`?

Potential security question:

> Does every tenant boundary need to be included in the history lookup?

Potential observability question:

> Can we identify whether the lateral inner scan is responsible for latency?

---

## 33. Production Scenario: “Current State” from Append-Only History

Append-only systems frequently store history rather than mutating current rows.

LATERAL can reconstruct current state per entity:

```sql
SELECT
    a.id,
    state.status,
    state.changed_at
FROM accounts a
LEFT JOIN LATERAL (
    SELECT h.status, h.changed_at
    FROM account_status_history h
    WHERE h.account_id = a.id
    ORDER BY h.changed_at DESC, h.id DESC
    LIMIT 1
) state ON true;
```

This is useful, but consider the scale.

If this becomes one of the highest-volume queries in production, alternatives may include:

- a maintained current-state table;
- materialized state projection;
- indexed current-state columns;
- event-sourced read models.

LATERAL solves the query problem; it does not automatically solve the architectural scaling problem.

---

## 34. LATERAL and JSON Expansion

A row may contain a JSON document with a variable-length array.

```sql
SELECT
    o.id AS order_id,
    line.product_id,
    line.quantity
FROM orders o
CROSS JOIN LATERAL jsonb_to_recordset(o.payload -> 'lines')
    AS line(product_id bigint, quantity numeric);
```

The cardinality of the result is now dependent on each order's JSON array length.

This means:

```text
orders rows × average array length
```

can become the real output volume.

Do not infer cost from outer-row count alone.

---

## 35. Cardinality Explosion

LATERAL can return many rows per outer row.

Suppose:

```text
outer rows = 100,000
average inner rows = 100
```

Potential result cardinality:

```text
10,000,000 rows
```

The query may be logically correct but operationally unsuitable.

Review:

- expected fan-out;
- network transfer;
- downstream aggregation cost;
- sort memory;
- application deserialization;
- API payload size;
- pagination strategy.

---

## 36. LATERAL with Pagination

For per-parent nested resources, avoid blindly using offset pagination inside a lateral query.

A pattern such as:

```sql
ORDER BY created_at DESC, id DESC
OFFSET 1000
LIMIT 50
```

may require walking over many earlier rows for each outer parent.

Keyset-style conditions are often better:

```sql
WHERE customer_id = c.id
  AND (created_at, id) < ($last_created_at, $last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50
```

The exact row-value predicate depends on the ordering direction and NULL semantics.

The broader principle is:

> **Dependent pagination must be designed around the inner relation's access path.**

---

## 37. LATERAL and `EXPLAIN`

Never judge a lateral query from SQL text alone.

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Questions to answer:

1. How many outer rows are actually produced?
2. How many times is the inner operation executed?
3. What is the actual rows-per-loop?
4. Is the inner path using the intended index?
5. Is a sort happening repeatedly?
6. How many buffers are hit or read?
7. Is the inner relation producing many more rows than expected?
8. Is the planner estimation badly wrong?
9. Is the total work dominated by repeated inner execution?

A useful pattern in plan reading is:

```text
Outer actual loops
×
Inner actual work per loop
=
Approximate repeated workload
```

The exact cost is more complicated, but this mental multiplication catches many performance problems quickly.

---

## 38. Example Plan Reasoning

Imagine a plan conceptually resembling:

```text
Nested Loop Left Join
  -> Seq Scan on customers        (actual rows=10000)
  -> Limit                         (actual rows=1 loops=10000)
       -> Index Scan on orders     (actual rows=1 loops=10000)
```

This can be excellent.

The inner operation is executed 10,000 times, but each execution returns one row quickly through an index.

Now imagine:

```text
Nested Loop Left Join
  -> Seq Scan on customers        (actual rows=1000000)
  -> Sort                          (actual rows=100 loops=1000000)
       -> Seq Scan on orders       (actual rows=5000 loops=1000000)
```

This is catastrophic.

The problem is not the word `LATERAL`.

The problem is repeated broad inner work.

## 39. Common Mistakes

### Mistake 1 — Thinking LATERAL Automatically Improves Performance

**Assumption:**

“LATERAL is a PostgreSQL optimization feature.”

**Problem:**

LATERAL is primarily a semantic capability. Performance depends on the resulting plan and workload.

**Correct mental model:**

LATERAL enables parameterized relations. The planner then chooses an execution strategy consistent with the query and statistics.

**Production consequence:**

You can turn one set-based operation into repeated work.

---

### Mistake 2 — Forgetting Deterministic Ordering

```sql
ORDER BY created_at DESC
LIMIT 1
```

**Problem:** ties may not have deterministic selection semantics.

**Better:**

```sql
ORDER BY created_at DESC, id DESC
LIMIT 1
```

---

### Mistake 3 — Using `CROSS JOIN LATERAL` for Optional Data

**Problem:** parents with no dependent rows disappear.

**Better:**

```sql
LEFT JOIN LATERAL (...) x ON true
```

when parent preservation is required.

---

### Mistake 4 — Filtering Too Late

The inner `LIMIT` may choose rows before an outer filter is applied.

Always inspect the required semantics:

```text
eligible rows
→ order eligible rows
→ limit
```

or:

```text
all rows
→ order
→ limit
→ filter
```

Those are different operations.

---

### Mistake 5 — Ignoring Fan-Out

One outer row can produce many inner rows.

This can multiply data volume unexpectedly.

---

### Mistake 6 — Ignoring Index Order

An index on:

```sql
(customer_id)
```

may still require sorting to satisfy:

```sql
ORDER BY created_at DESC
LIMIT 1
```

An index tailored to the full access path can avoid that repeated sort.

---

## 40. AI/Vibe-Coding Failure Patterns

AI-generated SQL frequently introduces LATERAL because it appears elegant, but without validating workload shape.

### Failure Pattern A — “LATERAL solves N+1”

False.

The application N+1 problem may move into SQL as repeated parameterized work.

### Failure Pattern B — Global LIMIT accidentally retained

An AI may generate a derived-table `LIMIT 1` where the requirement is one result per parent.

The correct question is:

> Is the limit global or correlated to each outer row?

### Failure Pattern C — Wrong JOIN type

AI may use `CROSS JOIN LATERAL` where optional data requires `LEFT JOIN LATERAL`.

### Failure Pattern D — Missing tie-breaker

AI may write:

```sql
ORDER BY created_at DESC
LIMIT 1
```

without considering duplicate timestamps.

### Failure Pattern E — Tenant filter omitted

The lateral subquery may correctly reference the parent ID but forget the tenant boundary.

### Failure Pattern F — Unbounded fan-out

AI may use a lateral table function that expands large JSON arrays and then return everything to an API.

### AI review rule

> **Never accept a lateral query because it is clever. Validate dependency, cardinality, indexability, and repeated work.**

---

## 41. Security Review

When reviewing LATERAL in production:

- confirm tenant/authorization predicates are inside the dependent lookup where required;
- avoid exposing unrestricted dependent rows through API projections;
- examine table functions for privilege behavior and security-definer implications;
- ensure user-supplied identifiers are parameterized;
- check whether row-level security changes what the lateral expression can see;
- consider whether a function invoked per row can expose data outside the intended security boundary.

The fact that the query is a single SQL statement does not make it automatically secure.

---

## 42. Reliability Review

LATERAL-heavy queries can become fragile under cardinality growth.

Track:

```text
outer rows
×
inner execution count
×
inner average work
×
inner result fan-out
```

A query that is excellent at 1,000 customers may become problematic at 1,000,000.

Load testing should vary both:

- outer row count;
- inner data distribution.

Skew matters.

When a lateral query becomes slow, collect:

```text

rows removed by filter

buffer reads

planning time
execution time
```

Correlate this with:

- concurrent workloads.

Do not diagnose a LATERAL query using duration alone.

## 45. Failure Lab 1 — Missing Index

Start with:

```sql
SELECT c.id, o.id
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.id
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC, o.id DESC
    LIMIT 1
) o ON true;
```

Run:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

Observe the inner access path.

Then add:

```sql
CREATE INDEX idx_orders_customer_created_id
ON orders (customer_id, created_at DESC, id DESC);
```

Run again.

Record:

- execution time;
- loop count;
- buffer reads/hits;
- scan type;
- sort presence.

The objective is not memorizing the expected plan. The objective is learning to measure the change.

## 50. Decision Framework

Ask these questions in order:

### Question 1
Does the right side depend on the current left-side row?

If no, prefer a normal relation/join.

### Question 2
Does the dependent operation return a relation rather than one scalar?

If yes, LATERAL may be an excellent fit.

### Question 3
Can the inner access path be highly selective?

If yes, LATERAL becomes especially attractive.

### Question 4
Can an index satisfy both filtering and ordering?

If yes, repeated probes may be cheap.

### Question 5
How many outer rows exist?

Large outer populations require more scrutiny.

### Question 6
How many rows can each inner execution return?

Fan-out can dominate cost.

### Question 7
Would a bulk set-based strategy process the same information more efficiently?

If yes, compare alternatives.

### Question 8
What does the measured plan actually do?

Use `EXPLAIN (ANALYZE, BUFFERS)`.

## 51. LATERAL vs Alternatives

| Problem | Possible approach | Typical strength |
|---|---|---|
| Simple relationship | JOIN | Set-based and direct |
| One scalar dependent value | Correlated scalar subquery | Compact |
| Multiple dependent rows | LATERAL | Natural relational dependency |
| Top-N per group | LATERAL or window function | Depends on workload |
| All rows for all groups | Normal JOIN | Often best bulk strategy |
| Large analytical ranking | Window function | Often natural |
| Precomputed current state | Current-state table | Often stronger at high read volume |
| Reusable complex logic | View/materialized view/function | Architecture dependent |

No single construct wins universally.

## 54. Expert “Why?” Drills

Do not answer these with syntax.

### Why can LATERAL be faster than a window function for top-1 lookup?

Expected reasoning:

```text
parameterized predicate
→ ordered index access
→ stop after first row
→ avoid processing unrelated rows
```

### Why can the same LATERAL query become much slower as outer-row count grows?

Expected reasoning:

```text
more outer rows
→ more parameterized executions
→ more total inner work
```

### Why is `LEFT JOIN LATERAL` often better for APIs?

Because parent resources often remain valid even when an optional dependent resource is absent.

### Why can adding an index change the practical value of LATERAL dramatically?

Because the inner operation may change from broad scanning/sorting to a tiny ordered index probe.

```text

   ↓
LATERAL dependency

   ↓
predicate
   ↓
ordering
   ↓
LIMIT / expansion / transformation
   ↓
```

```text

→ Repeated Work
```

The central lesson is:
