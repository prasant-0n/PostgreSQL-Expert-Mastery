# Chapter 01.2 — Expressions and Conditional Logic

> **Phase:** 01 — Advanced SQL  
> **Level:** Foundations → Expert  
> **Status:** Core Curriculum  
> **Primary Goal:** Build a precise mental model for PostgreSQL expressions, type resolution, NULL semantics, conditional logic, operators, casts, evaluation behavior, and safe production use.

---

## 1. Chapter Mission

A SQL query is not merely a list of clauses. Every value you write inside a query is an **expression**. Expressions determine what PostgreSQL computes, what types are produced, how comparisons behave, how NULL propagates, and whether seemingly correct business logic actually means what you intended.

This chapter develops the ability to reason about an expression before running it:

```text
SQL text
  ↓
Parsing
  ↓
Operator / function / type resolution
  ↓
Expression tree
  ↓
Logical meaning
  ↓
Runtime evaluation
  ↓
Result value + result type
```

The target is not memorizing `CASE`, `COALESCE`, or operators. The target is being able to answer:

- What is this expression's type?
- What happens when one operand is NULL?
- Which operator or function is actually selected?
- Where is an implicit cast happening?
- What is evaluated, and what is not guaranteed to be evaluated?
- Does the expression preserve business meaning?
- Does it remain correct under edge cases, scale, and schema evolution?

PostgreSQL's current documentation describes SQL as strongly typed and explains that functions and operators may be overloaded, requiring type resolution by the parser. `CASE` and related constructs also require compatible result types. citeturn363464search0turn363464search3turn363464search5

# 3. Precise Definitions

## 3.1 Simple definition

An **expression** is SQL code that PostgreSQL can evaluate to produce a value.

Examples:

```sql
price
price * quantity
NOW()
status = 'paid'
COALESCE(phone, email)
CASE WHEN amount > 10000 THEN 'high' ELSE 'normal' END
```

## 3.2 Engineering definition

An expression is a typed computation embedded inside a SQL statement whose inputs may include constants, columns, parameters, functions, operators, subexpressions, and conditional constructs.

## 3.3 Expert definition

An expression is a node or tree of typed operations that PostgreSQL parses and resolves according to SQL syntax, operator/function lookup rules, type conversion rules, collation and contextual typing, then evaluates according to the semantics and execution behavior applicable to that expression.

That definition is important because the visible text is not the whole story.

For example:

```sql
SELECT 1 + 2.0;
```

You did not explicitly specify a common result type, yet PostgreSQL resolves the mixed numeric types into a compatible result. PostgreSQL's type-conversion system exists specifically to resolve such mixed-type expressions. citeturn363464search0

---

# 4. The Expression Mental Model

Think of an expression as a typed tree:

```text
             +
           /   \
         price quantity
```

For:

```sql
price * quantity
```

PostgreSQL must determine:

1. What is `price`?
2. What is `quantity`?
3. What are their data types?
4. Which `*` operator applies to those types?
5. What type does the operator return?
6. What happens if either operand is NULL?
7. How is the resulting value used by the surrounding query?

This is why SQL is not merely textual substitution.

# 5. The Major Expression Families

PostgreSQL supports many forms of value expressions, including:

| Category | Example |
|---|---|
| Column reference | `customer_id` |
| Constant | `42`, `'paid'`, `true` |
| Positional parameter | `$1` |
| Arithmetic | `price * quantity` |
| Comparison | `price >= 100` |
| Boolean | `active AND verified` |
| Function call | `lower(email)` |
| Aggregate | `sum(amount)` |
| Window expression | `row_number() OVER (...)` |
| Cast | `price::numeric` |
| Conditional | `CASE ... END` |
| NULL handling | `COALESCE(...)` |
| Scalar subquery | `(SELECT ...)` |
| Array expression | `ARRAY[1,2,3]` |
| Row expression | `ROW(id, email)` |
| Collation expression | `name COLLATE ...` |

PostgreSQL documents these value-expression forms as part of its SQL syntax model. citeturn363464search4

# 6. Literals and Constants

## 6.1 Numeric literals

```sql
SELECT 10;
SELECT 10.5;
SELECT -20;
```

Do not casually assume every numeric literal behaves as the exact application type you had in mind. PostgreSQL has rules for classifying and resolving literals and mixed numeric expressions. citeturn363464search0

## 6.2 String literals

```sql
SELECT 'hello';
```

An untyped string literal starts as `unknown` and is resolved later using context and type-conversion rules. citeturn363464search0

This matters when writing overloaded functions or mixed-type expressions.

## 6.3 Boolean literals

```sql
SELECT true;
SELECT false;
```

Prefer proper boolean types instead of storing semantic booleans in strings such as `'yes'`, `'no'`, or `'active'`.

---

# 7. Column References Are Typed Inputs

Consider:

```sql
orders.total_amount * orders.quantity
```

Each column contributes both a value and a type to the expression.

If:

```text
 total_amount NUMERIC
 quantity     INTEGER
```

then PostgreSQL must resolve the multiplication using compatible numeric semantics.

This is one reason schema design and expression design cannot be separated completely.

A change such as:

```sql
quantity INTEGER
```

to:

```sql
quantity NUMERIC
```

can alter the type-resolution path of downstream expressions.

---

# 8. Operators Are Not Mere Symbols

A common beginner model is:

```text
+ means addition
* means multiplication
= means equality
```

The expert model is:

```text
operator token + operand types
          ↓
operator lookup
          ↓
selected operator implementation
          ↓
result type
```

PostgreSQL permits overloaded operators. The exact operator selected depends on the operand types and conversion rules. The official type-conversion documentation explicitly treats operator resolution as a distinct type-resolution problem. citeturn363464search0

Therefore:

```sql
SELECT 1 + 2;
```

and:

```sql
SELECT some_domain_value + some_other_value;
```

may involve different resolution behavior depending on the types involved.

---

# 9. Operator Precedence

Expression correctness can fail before NULL handling or business logic enters the picture.

Consider:

```sql
SELECT true OR false AND false;
```

`AND` has higher precedence than `OR`, so this is interpreted as:

```sql
true OR (false AND false)
```

not:

```sql
(true OR false) AND false
```

PostgreSQL documents a fixed precedence table for operators and recommends parentheses when you want a different grouping or want the intended grouping to be unmistakable. citeturn363464search22

## Engineering rule

When business logic is important, prefer:

```sql
WHERE is_active
  AND (role = 'admin' OR role = 'manager')
```

over relying on readers remembering precedence.

Parentheses are cheap. Production ambiguity is expensive.

---

# 10. Boolean Expressions and Three-Valued Logic

SQL boolean logic is not ordinary two-valued Boolean algebra because NULL introduces a third logical state:

```text
TRUE
FALSE
UNKNOWN
```

`UNKNOWN` commonly appears when a comparison involves NULL.

Example:

```sql
SELECT NULL = 10;
```

The result is NULL/unknown, not false.

Likewise:

```sql
SELECT NULL <> 10;
```

also produces unknown.

This is the foundation for understanding why:

```sql
WHERE amount = NULL
```

is wrong.

Use:

```sql
WHERE amount IS NULL
```

or:

```sql
WHERE amount IS NOT NULL
```

---

# 11. NULL Is Not a Normal Value

One of the most damaging mental models in SQL is treating NULL as if it were a regular value such as zero or an empty string.

NULL represents the absence of a known value or an SQL null marker. It participates in special logical and expression semantics.

Examples:

```sql
SELECT 10 + NULL;
SELECT 'abc' || NULL;
SELECT NULL = NULL;
SELECT NULL AND true;
```

You must learn the resulting semantics rather than guess from ordinary programming-language intuition.

---

# 12. CASE — SQL Conditional Logic

`CASE` is the central conditional expression in SQL.

## 12.1 Searched CASE

```sql
CASE
    WHEN amount >= 100000 THEN 'enterprise'
    WHEN amount >= 10000 THEN 'large'
    WHEN amount >= 1000 THEN 'medium'
    ELSE 'small'
END
```

This form evaluates Boolean conditions in order and returns the result associated with the first matching condition. PostgreSQL documents this behavior for `CASE`. citeturn363464search7

## 12.2 Simple CASE

```sql
CASE status
    WHEN 'paid' THEN 'complete'
    WHEN 'pending' THEN 'waiting'
    ELSE 'other'
END
```

It compares the search expression against the `WHEN` values.

## 12.3 Ordering matters

Bad:

```sql
CASE
    WHEN amount > 1000 THEN 'high'
    WHEN amount > 10000 THEN 'very-high'
    ELSE 'normal'
END
```

The second branch can never be reached because amounts above 10000 already satisfy `amount > 1000`.

Better:

```sql
CASE
    WHEN amount > 10000 THEN 'very-high'
    WHEN amount > 1000 THEN 'high'
    ELSE 'normal'
END
```

---

# 13. CASE Result Types

All possible `CASE` result expressions must resolve to a common compatible type.

Example:

```sql
CASE
    WHEN paid THEN 1
    ELSE 0
END
```

returns an integer-like result.

A mixed expression such as:

```sql
CASE
    WHEN paid THEN 1
    ELSE 'unpaid'
END
```

is not semantically valid merely because both branches are values. PostgreSQL must determine a common result type, using its type-resolution algorithm. citeturn363464search5

## Engineering lesson

A `CASE` branch is not free-form output. Its branches participate in the type system.

---

# 14. COALESCE

`COALESCE` returns the first non-NULL expression.

```sql
COALESCE(phone, email, 'no-contact')
```

Mental model:

```text
candidate 1 → NULL? skip
candidate 2 → NULL? skip
candidate 3 → first usable value
```

### Common API use

```sql
SELECT
    id,
    COALESCE(display_name, username, 'Unknown') AS label
FROM users;
```

### Common aggregation use

PostgreSQL documents that many aggregates, including `sum` and `array_agg`, return NULL when no input rows are selected; `COALESCE` can substitute a desired empty/zero value. citeturn363464search8

Example:

```sql
SELECT COALESCE(SUM(amount), 0)
FROM payments
WHERE order_id = $1;
```

This can be correct when the business meaning of “no rows” is zero.

It can be incorrect when “no rows” must remain distinguishable from an actual zero amount.

That distinction is business semantics, not syntax.

---

# 15. NULLIF

`NULLIF(a, b)` returns NULL when `a = b`; otherwise it returns `a`.

Classic divide-by-zero protection:

```sql
revenue / NULLIF(order_count, 0)
```

If `order_count = 0`, the denominator becomes NULL instead of zero.

This is often preferable to:

```sql
CASE
    WHEN order_count = 0 THEN NULL
    ELSE revenue / order_count
END
```

because the intent is direct and composable.

But do not use `NULLIF` merely to silence an error. Decide what division-by-zero means for the business metric.

---

# 16. GREATEST and LEAST

Examples:

```sql
GREATEST(price, minimum_price)
LEAST(discount, maximum_discount)
```

These constructs require their arguments to resolve to a common type. They are syntactically similar to functions but are special conditional expressions rather than ordinary functions. citeturn363464search7turn363464search0

## Critical NULL detail

Do not assume these behave exactly like mathematical max/min functions over ordinary programming-language values.

Always test the NULL behavior relevant to your PostgreSQL version and application contract before relying on it.

---

# 17. Explicit Casting

Explicit casts make your intent visible.

PostgreSQL syntax examples:

```sql
price::numeric
user_id::text
created_at::date
```

or:

```sql
CAST(price AS numeric)
```

### Why explicit casts matter

They can:

- remove ambiguity,
- document intent,
- stabilize overloaded function resolution,
- control result types,
- prevent accidental type inference from context.

PostgreSQL's type-conversion documentation recommends explicit casting where necessary to tailor conversion behavior. citeturn363464search1

---

# 18. Implicit vs Explicit Conversion

Implicit conversion can be convenient:

```sql
SELECT 1 + 2.5;
```

But convenience can hide assumptions.

A production-grade engineer asks:

```text
What type did this become?
Which cast was chosen?
Could a schema change alter the resolution?
Could the cast prevent an index strategy?
Could precision be lost?
```

Do not add explicit casts everywhere blindly. The objective is not “maximum casting.” The objective is **intentional typing**.

---

# 19. Function Resolution

PostgreSQL supports overloaded functions.

The name alone may not identify the exact implementation:

```sql
some_function(value)
```

The parser considers visible functions with matching names/argument counts, then resolves the best candidate using the argument types and conversion rules. The search path also matters for unqualified function names. citeturn363464search3

This creates an important security and correctness connection:

```text
function name
+ search_path
+ argument types
→ selected function
```

Therefore function qualification is sometimes an architectural/security decision, not mere style.

---

# 20. Short-Circuit Thinking: Useful but Dangerous

It is tempting to say:

> “CASE always evaluates only the branch I need.”

The documented semantics support conditional evaluation behavior for `CASE`, and subsequent `WHEN` conditions are not evaluated once a prior condition matches. citeturn363464search7

However, SQL is not a general-purpose imperative language where every textual expression can be reasoned about solely by left-to-right runtime intuition. Planner transformations and constant evaluation can matter, especially for errors involving constants or constructs that can be evaluated earlier than expected.

Therefore:

```text
Use documented semantics.
Do not build correctness around undocumented evaluation order.
```

---

# 21. Dangerous Example: Divide by Zero

A developer may write:

```sql
CASE
    WHEN denominator = 0 THEN 0
    ELSE numerator / denominator
END
```

Often this is reasonable.

But a stronger design question is:

```text
What does zero denominator mean?
```

Possible answers:

- zero rate,
- undefined rate,
- NULL / unavailable,
- invalid record,
- business error.

The correct SQL depends on the business invariant.

---

# 22. Boolean Expressions for Business Rules

Suppose a jewelry ERP permits an invoice discount only for authorized users when the invoice is still editable.

Weak thinking:

```sql
WHERE is_admin = true
```

Stronger thinking:

```sql
WHERE invoice_status IN ('draft', 'pending')
  AND user_role IN ('admin', 'manager')
  AND discount_amount <= approved_discount_limit
```

Best thinking:

```text
Which conditions are application hints?
Which conditions are database-enforced invariants?
What happens under concurrent modification?
Can a malicious or buggy client bypass the application?
```

The expression itself is only one part of correctness.

# 23. Common NULL Mistakes

## Mistake 1 — Equality against NULL

Wrong:

```sql
WHERE deleted_at = NULL
```

Correct:

```sql
WHERE deleted_at IS NULL
```

## Mistake 2 — Treating NULL as zero

Wrong:

```sql
COALESCE(balance, 0)
```

when NULL actually means “balance unavailable because account was never initialized.”

## Mistake 3 — Assuming NOT IN is safe with NULL

Expressions involving `NOT IN` and NULL can produce surprising unknown results because SQL uses three-valued logic.

Prefer carefully designed `NOT EXISTS` patterns when NULL semantics make membership exclusion ambiguous.

---

# 24. Common CASE Mistakes

### Mistake: Overlapping ranges

```sql
CASE
    WHEN score >= 50 THEN 'pass'
    WHEN score >= 80 THEN 'excellent'
END
```

`excellent` is unreachable.

### Mistake: Missing ELSE

Without an `ELSE`, an unmatched `CASE` yields NULL.

That may be correct or may silently leak NULL into downstream calculations.

### Mistake: Embedding duplicated business logic

```sql
CASE
    WHEN status = 'paid' AND total > 1000 THEN ...
    WHEN status = 'paid' AND total > 1000 THEN ...
END
```

If the same rule appears in multiple places, consider centralizing the rule at the appropriate architectural layer.

---

# 25. Expressions and Index Usage

Not every expression in a predicate is equally index-friendly.

Compare:

```sql
WHERE email = $1
```

with:

```sql
WHERE lower(email) = lower($1)
```

The second query may require an expression index such as:

```sql
CREATE INDEX idx_users_lower_email
ON users (lower(email));
```

The important engineering principle is:

```text
Expression design
     ↕
Access path design
```

Do not optimize an expression in isolation from the query planner and index strategy.

---

# 26. Casts Can Affect Performance and Semantics

Suppose:

```sql
WHERE user_id = $1
```

and the column is `BIGINT`.

Compare that with a query that forces the column through another expression or cast:

```sql
WHERE user_id::text = $1
```

You have changed the expression around the indexed column.

Sometimes PostgreSQL can still find a good plan; sometimes the expression changes the available strategy. The only safe engineering process is:

```text
Write query
→ EXPLAIN
→ inspect plan
→ measure under realistic data
```

Never assume a cast is “just formatting.”

---

# 27. CASE in SELECT vs CASE in WHERE

The same conditional logic can have very different roles.

### Projection

```sql
SELECT
    CASE WHEN amount >= 10000 THEN 'large' ELSE 'normal' END AS size
FROM orders;
```

This transforms output.

### Predicate

```sql
WHERE CASE
          WHEN customer_type = 'vip' THEN amount >= 5000
          ELSE amount >= 1000
      END
```

This controls which rows qualify.

The second is more consequential for query planning because the expression participates in row filtering.

Prefer direct Boolean predicates where they make intent clearer:

```sql
WHERE (customer_type = 'vip' AND amount >= 5000)
   OR (customer_type <> 'vip' AND amount >= 1000)
```

Then inspect the resulting plan rather than assuming one form is always faster.

---

# 28. Conditional Aggregation

One of the most useful advanced expression patterns is conditional aggregation.

```sql
SELECT
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (WHERE status = 'paid') AS paid_orders,
    SUM(amount) FILTER (WHERE status = 'paid') AS paid_revenue
FROM orders;
```

This is generally clearer than repeating large `CASE` expressions inside every aggregate.

Equivalent CASE-style patterns exist, but clarity and explicit semantics matter.

---

# 29. Financial Correctness

Expressions become high-risk when money is involved.

Avoid casually mixing:

```text
integer
numeric
real
double precision
text
```

without understanding the consequences.

Prefer a data model whose monetary precision is explicit and consistent.

Example:

```sql
unit_price NUMERIC(12,2)
quantity    INTEGER
```

Then:

```sql
unit_price * quantity
```

has a defined business-oriented precision model.

Do not assume floating-point arithmetic is equivalent to decimal financial arithmetic.

---

# 30. Temporal Expressions

Time expressions often combine:

```text
timestamp
interval
date
time zone
cast
comparison
```

For example:

```sql
created_at >= NOW() - INTERVAL '7 days'
```

The expression's correctness depends on the types and timezone semantics, not just the text.

Temporal correctness becomes especially important in:

- reports,
- settlement windows,
- SLA calculations,
- subscription renewals,
- inventory aging,
- audit timelines.

Temporal logic deserves explicit design rather than ad-hoc casting.

---

# 31. Expressions Inside Constraints

Expressions are not only for SELECT queries.

Example:

```sql
CHECK (quantity > 0)
```

or:

```sql
CHECK (discount_amount >= 0)
```

This is a powerful example of using expressions to encode invariants at the database boundary.

The more critical the invariant, the stronger the argument for enforcing it where bypassing the application would still be unacceptable.

---

# 32. Expressions Inside Generated Columns

A generated column can encapsulate a deterministic derived expression at the schema level.

Example conceptually:

```sql
line_total = unit_price * quantity
```

The architectural question is not only “can SQL calculate this?” but:

```text
Should this value be derived centrally?
Should it be independently stored?
Should it be indexed?
Is the expression stable?
What happens when the source columns change?
```

---

# 33. Expressions and Search Path Security

Unqualified function calls can interact with `search_path` and function resolution.

This matters especially for privileged functions and `SECURITY DEFINER` code.

Production security review should therefore consider:

```text
Expression
→ function/operator lookup
→ schema visibility
→ search_path
→ privileges
→ actual implementation selected
```

Do not review SQL expressions only for “does this output the right value?”

---

# 34. AI / Vibe-Coding Failure Patterns

AI-generated SQL frequently fails at expression semantics rather than syntax.

## Failure Pattern 1 — `= NULL`

AI writes:

```sql
WHERE deleted_at = NULL
```

Why it fails:

```text
NULL uses special SQL logic.
Equality is not the NULL test.
```

Correct reasoning:

```sql
WHERE deleted_at IS NULL
```

---

## Failure Pattern 2 — Blind COALESCE

AI writes:

```sql
COALESCE(total, 0)
```

for every nullable numeric column.

Problem:

It may erase the distinction between:

```text
unknown
not applicable
not calculated
zero
```

---

## Failure Pattern 3 — Unreachable CASE branches

AI often produces broad conditions before specific conditions.

Review every `CASE` as an ordered decision tree.

---

## Failure Pattern 4 — Unnecessary casting

AI may cast every value to `text` “to make comparison work.”

That can:

- hide schema problems,
- destroy type safety,
- alter semantics,
- complicate index usage,
- increase runtime work.

---

## Failure Pattern 5 — Missing parentheses

Generated predicates such as:

```sql
WHERE tenant_id = $1
  AND status = 'active'
  OR role = 'admin'
```

may mean:

```sql
(tenant_id = $1 AND status = 'active') OR role = 'admin'
```

which can accidentally cross tenant boundaries.

This is a **security-critical SQL expression bug**.

Correct when intended:

```sql
WHERE tenant_id = $1
  AND (status = 'active' OR role = 'admin')
```

---

# 35. Multi-Tenant Safety Example

Consider:

```sql
SELECT *
FROM invoices
WHERE tenant_id = $1
  AND status = 'open'
  OR status = 'pending';
```

The likely semantics are:

```text
(tenant_id = $1 AND status = 'open')
OR status = 'pending'
```

That can return pending invoices from other tenants.

Correct form:

```sql
SELECT *
FROM invoices
WHERE tenant_id = $1
  AND status IN ('open', 'pending');
```

This example demonstrates why expression knowledge is directly connected to application security and multi-tenancy.

# 36. Production Debugging Method

When an expression gives a surprising result, do not immediately rewrite it.

Use this diagnostic sequence:

```text
1. Isolate the smallest failing expression.
2. Inspect every operand's type.
3. Test NULL cases explicitly.
4. Check operator/function resolution.
5. Check parentheses / precedence.
6. Check implicit casts.
7. Check collation/timezone assumptions.
8. Check surrounding query semantics.
9. EXPLAIN if performance is involved.
10. Validate against business invariants.
```

Example:

```sql
SELECT
    pg_typeof(price),
    pg_typeof(quantity),
    pg_typeof(price * quantity)
FROM order_items
LIMIT 1;
```

`pg_typeof()` is a practical diagnostic tool for understanding expression typing.

# 37. Evidence-Driven Experiment Lab

Create a small sandbox:

```sql
CREATE TABLE expression_lab (
    id          BIGSERIAL PRIMARY KEY,
    price       NUMERIC(10,2),
    quantity    INTEGER,
    discount    NUMERIC(10,2),
    status      TEXT,
    note        TEXT
);
```

Insert deliberately difficult rows:

```sql
INSERT INTO expression_lab (price, quantity, discount, status, note)
VALUES
    (100.00, 2, 10.00, 'paid', NULL),
    (NULL, 3, 0.00, 'pending', 'missing price'),
    (250.00, NULL, NULL, NULL, NULL),
    (0.00, 0, NULL, 'cancelled', 'zero case');
```

Then investigate:

```sql
SELECT
    id,
    price * quantity AS gross,
    COALESCE(discount, 0) AS normalized_discount,
    NULLIF(quantity, 0) AS safe_quantity,
    CASE
        WHEN status = 'paid' THEN 'complete'
        WHEN status = 'pending' THEN 'waiting'
        ELSE 'other'
    END AS state_label
FROM expression_lab;
```

Add experiments for:

```text
NULL + number
NULL = NULL
NULL IS NULL
CASE without ELSE
CASE mixed result types
implicit numeric conversion
explicit casts
operator precedence
GREATEST / LEAST with NULL
```

Record not just the result, but your predicted result before running it.

That prediction step is essential for mastery.

# 41. Wrong Approach → Why It Fails → Better Approach

## Wrong approach

> Treat SQL expressions like JavaScript expressions.

### Why it fails

SQL has:

- NULL semantics,
- three-valued logic,
- strong typing,
- overloaded operators/functions,
- contextual type resolution,
- declarative query semantics.

### Better approach

Use this mental model:

```text
Value
+ type
+ operator/function
+ SQL semantics
+ context
→ result
```

# 42. Production Review Checklist

Before approving complex SQL expressions, check:

### Correctness

- Are NULL semantics intentional?
- Are all CASE branches reachable and ordered correctly?
- Is an ELSE clause required?
- Are result types compatible?
- Are comparisons using the correct operators?

### Security

- Could precedence broaden a tenant predicate?
- Could NULL bypass an authorization condition?
- Are privileged functions resolved safely?
- Is `search_path` behavior understood?

### Performance

- Are expressions applied to indexed columns?
- Are casts changing access paths?
- Is the expression repeated unnecessarily?
- Does the plan confirm the expected strategy?

### Maintainability

- Is the expression readable?
- Are parentheses used where intent matters?
- Is a business rule duplicated?
- Would a constraint provide stronger guarantees?

# 45. Final Takeaways

The most important lessons from this chapter are:

1. **An SQL expression is a typed computation, not just text.**
2. **NULL is not an ordinary value.**
3. **SQL uses three-valued logic.**
4. **Operator and function resolution depend on types.**
5. **Implicit casts are part of semantics, not invisible magic.**
6. **CASE is an ordered decision structure.**
7. **COALESCE changes meaning when NULL carries business information.**
8. **Parentheses can prevent security bugs.**
9. **Expression design and index design are connected.**
10. **Correctness must be proven with semantics, tests, and evidence—not because the query executes successfully.**
