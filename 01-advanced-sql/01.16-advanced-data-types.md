# 01.16 — Advanced PostgreSQL Data Types

> **Phase:** 01 — Advanced SQL  
> **Chapter:** 16  
> **Target Mastery:** L0 → L7  
> **Primary Goal:** Learn to choose, model, query, validate, index, migrate, and troubleshoot PostgreSQL data types based on semantics, invariants, workload, and operational consequences — not convenience alone.

---

## 1. Chapter Objective

The objective of this chapter is to move beyond the beginner question:

> “Which PostgreSQL data types are available?”

and replace it with the engineering question:

> “What meaning does this value have, what invariants must hold, how will it be queried, how will it change over time, and which PostgreSQL type best represents that meaning?”

A database type is not merely a container for bytes. It establishes a contract involving:

- value domain
- comparison semantics
- ordering semantics
- equality semantics
- operator behavior
- function behavior
- casting behavior
- storage representation
- indexing possibilities
- constraint design
- serialization behavior
- planner/statistics behavior
- application interoperability
- migration cost

This chapter therefore treats data types as **semantic engineering decisions**.

---

## 2. The Core Mental Model

Use this decision chain for every non-trivial column:

```text
Business Meaning
      ↓
Value Domain
      ↓
Allowed / Forbidden States
      ↓
Precision Requirements
      ↓
Comparison / Ordering Semantics
      ↓
Query Operators
      ↓
Indexing Strategy
      ↓
Storage Characteristics
      ↓
Application Representation
      ↓
Serialization / API Contract
      ↓
Migration & Lifecycle Cost
```

A type choice is good only when the entire chain remains coherent.

### 2.1 Example

Suppose an ERP stores the price of gold.

Weak thought:

```text
Use FLOAT because it stores numbers.
```

Engineering thought:

```text
Money / metal price
→ exact decimal semantics
→ predictable arithmetic
→ fixed precision/scale policy
→ safe aggregation
→ auditability
→ deterministic reconciliation
```

That points toward an exact numeric representation rather than a floating approximation.

# 3. Type Families

PostgreSQL provides a broad type system. The major families relevant to application engineering include:

| Family | Examples | Typical purpose |
|---|---|---|
| Boolean | `boolean` | true/false state |
| Integers | `smallint`, `integer`, `bigint` | exact whole numbers |
| Exact numeric | `numeric`, `decimal` | exact decimal arithmetic |
| Floating point | `real`, `double precision` | approximate scientific/measurement values |
| Monetary | `money` | locale-aware monetary display/arithmetic with specific semantics |
| Character | `char`, `varchar`, `text` | textual data |
| Binary | `bytea` | raw bytes |
| Date/time | `date`, `time`, `timestamp`, `timestamptz`, `interval` | temporal values |
| UUID | `uuid` | identifier values |
| Network | `inet`, `cidr`, `macaddr` | network addresses |
| Bit strings | `bit`, `varbit` | fixed/variable bit sequences |
| Enumerated | `enum` | finite named states |
| Arrays | `type[]` | homogeneous collections |
| JSON | `json`, `jsonb` | semi-structured documents |
| Range | `int4range`, `int8range`, `numrange`, `tsrange`, `tstzrange`, `daterange` | continuous/discrete spans |
| Geometric | `point`, `line`, `path`, `polygon`, `circle` | geometric primitives |
| Full-text | `tsvector`, `tsquery` | text-search representation/query |
| Composite | user-defined composite types | structured records |
| Domain | `CREATE DOMAIN` | reusable constrained scalar contracts |

The important lesson is not memorization. It is understanding the semantic contract of each family.

# 4. Integer Types

## 4.1 `smallint`

Usually appropriate when the valid domain is genuinely small.

Examples:

- rating 1–5
- month 1–12
- finite category counts
- small bounded sequence values

Do not choose it merely because the current values are small. Ask whether the domain can grow.

## 4.2 `integer`

A common exact whole-number type for application data.

Good candidates:

- ordinary identifiers where the domain is comfortably bounded
- counters
- quantities
- status codes
- foreign keys in appropriately sized systems

## 4.3 `bigint`

Useful when the domain, event volume, sequence growth, or distributed integration justifies a wider integer range.

Common uses:

- high-volume event IDs
- large surrogate keys
- transaction numbers
- monotonically increasing records
- externally interoperable integer identifiers

### Engineering rule

Do not blindly use `bigint` everywhere. Wider identifiers affect storage and index footprint, although the practical impact depends on row and index structure. Choose based on expected domain and lifecycle rather than fashion.

---

# 5. Exact Numeric vs Floating Point

This is one of the most important type decisions in production systems.

## 5.1 Exact numeric

`numeric` / `decimal` represents decimal values with exact arithmetic semantics appropriate for financial and many business calculations.

Example:

```sql
CREATE TABLE invoices (
    invoice_id bigint PRIMARY KEY,
    subtotal numeric(18,2) NOT NULL,
    tax numeric(18,2) NOT NULL,
    total numeric(18,2) NOT NULL
);
```

## 5.2 Floating point

`real` and `double precision` are approximate floating-point representations.

They are appropriate for workloads where approximation is acceptable, such as:

- scientific calculations
- sensor measurements
- numerical simulations
- physical calculations where the source itself is approximate

They are dangerous when application semantics require exact decimal equality or deterministic financial reconciliation.

## 5.3 Failure pattern

```sql
WHERE amount = 10.10
```

may not express the business notion of “exactly ten rupees and ten paise” when the stored representation is approximate floating point.

### Better question

Do not ask:

> “Can PostgreSQL store decimal numbers in this type?”

Ask:

> “Does the mathematical model of the business require exact decimal semantics?”

---

# 6. Precision and Scale

For `numeric(p, s)`:

- `p` is precision: total number of significant decimal digits allowed.
- `s` is scale: digits allowed to the right of the decimal point.

Example:

```sql
numeric(12,2)
```

permits a defined exact decimal domain suitable for many currency-style values.

But precision and scale should be derived from business invariants.

### Example: Jewellery ERP

Potential quantities may need different policies:

```text
weight       → numeric(18,3)
price        → numeric(18,2)
percentage   → numeric(8,4)
exchange_rate→ numeric(20,8)
```

Those values should not automatically share one arbitrary precision merely because they are all numeric.

---

# 7. `money`

PostgreSQL has a `money` type with locale-dependent output behavior and fixed-scale monetary semantics.

It can be appropriate in specific systems, but application architecture should carefully consider:

- localization
- presentation vs storage responsibilities
- interoperability
- conversion/casting behavior
- currency semantics
- multi-currency requirements

For many business systems, `numeric` plus an explicit currency code/type is easier to reason about and integrate.

### Important architectural distinction

```text
numeric amount
+
currency identity
=
financial value
```

A numeric amount without currency semantics is not automatically a complete monetary model.

---

# 8. Text Types

PostgreSQL provides `char(n)`, `varchar(n)`, and `text`.

## 8.1 `text`

Often the best default for unconstrained textual values when there is no business reason to impose a character length constraint in the type.

## 8.2 `varchar(n)`

Use when the maximum length is itself a meaningful domain constraint.

Example:

```sql
postal_code varchar(20)
```

if the domain contract truly has a maximum length that should be enforced by the database.

## 8.3 `char(n)`

Fixed-length semantics introduce padding behavior and should not be selected merely because the value “looks short.”

### Expert rule

If your real requirement is:

> “The value must be between 1 and 20 characters.”

then model that requirement explicitly and understand the behavior of the chosen text type.

---

# 9. Binary Data: `bytea`

`bytea` is PostgreSQL's binary byte-string type.

Common uses:

- hashes or binary digests
- cryptographic material when appropriate
- binary protocol payloads
- compact binary metadata
- application-generated blobs

However, storing very large application files directly in ordinary relational rows creates different operational characteristics than storing metadata plus external object-storage references.

For large assets, reason about:

```text
row size
→ TOAST behavior
→ vacuum / update cost
→ backup size
→ replication volume
→ application latency
→ object storage alternatives
```

Do not make “database or object storage” a universal rule. Make it a workload decision.

---

# 10. UUID

UUIDs provide a fixed-width identifier representation suited to globally generated identifiers and distributed systems.

Example:

```sql
CREATE TABLE users (
    user_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    email text NOT NULL
);
```

### Trade-offs

Compared with sequential integers, UUIDs can have:

- larger indexes
- different locality characteristics depending on generation strategy
- less human readability
- different insert/index behavior

Benefits include:

- reduced central coordination for ID generation
- safer cross-system merging
- better suitability for distributed generation

### Architecture question

Do not ask only:

> “UUID or bigint?”

Ask:

```text
Who generates IDs?
Where are records created?
Do datasets merge?
Do IDs cross service boundaries?
Does locality matter?
What is the expected scale?
```

---

# 11. Date and Time Types

Temporal types require semantic precision.

Relevant types include:

- `date`
- `time`
- `timestamp`
- `timestamp with time zone` (`timestamptz`)
- `interval`

## 11.1 `date`

Use when the business concept is a calendar date with no time-of-day meaning.

Examples:

- birth date
- invoice due date
- accounting date
- holiday date

Do not store a calendar-only concept as a timestamp merely because the application language uses a generic Date object.

## 11.2 `timestamp without time zone`

Represents a date and time without time-zone semantics.

Useful when the value is intentionally a “wall-clock” local date/time concept and timezone conversion is not part of the model.

## 11.3 `timestamptz`

Represents an instant in time. PostgreSQL stores an absolute temporal value and renders it according to session timezone.

This is often the correct choice for:

- event occurrence
- creation timestamp
- payment time
- job execution time
- audit event time

### Critical distinction

```text
Instant in the world
        ≠
Local wall-clock representation
```

A type decision must preserve the distinction.

---

# 12. Intervals

`interval` represents elapsed time / temporal duration semantics.

Examples:

```sql
SELECT now() + interval '7 days';
```

But interval arithmetic has calendar semantics that require careful reasoning around months, daylight-saving transitions, and timestamp behavior.

Do not assume:

```text
1 month = 30 days
```

They are different concepts.

---

# 13. Enum

PostgreSQL enums model a finite named set of states.

Example:

```sql
CREATE TYPE order_status AS ENUM (
    'pending',
    'confirmed',
    'cancelled',
    'completed'
);
```

Advantages:

- strong type-level representation
- compact domain vocabulary
- prevents arbitrary strings outside the declared values

Trade-offs:

- schema evolution is coupled to enum definition management
- dynamic business taxonomies may be better represented by reference data tables

### Decision rule

Use an enum when the set is genuinely a stable part of the database type system.

Use a lookup/reference table when the set is business data that changes independently.

---

# 14. Domains

A domain creates a reusable constrained type over an underlying scalar type.

Example:

```sql
CREATE DOMAIN positive_amount AS numeric(18,2)
CHECK (VALUE >= 0);
```

Now multiple tables can use the same semantic contract:

```sql
amount positive_amount NOT NULL
```

### Why domains matter

They allow a database-wide semantic vocabulary:

```text
email-like value
positive monetary amount
non-negative weight
country code
validated business code
```

This can reduce repeated constraints and centralize invariant definitions.

But domains should not be abused as a replacement for proper entity modeling.

---

# 15. Arrays

PostgreSQL supports arrays of many element types.

Example:

```sql
CREATE TABLE products (
    product_id bigint PRIMARY KEY,
    tags text[]
);
```

## Good uses

Arrays can be appropriate when:

- values are naturally a homogeneous collection
- the collection is usually consumed as a unit
- relational child-row behavior is unnecessary
- element-level querying has been considered

## Bad use

Avoid arrays as a shortcut for avoiding relational modeling:

```text
customer.product_ids = '{10,11,12,13}'
```

when those IDs actually represent an entity relationship that requires:

- referential integrity
- independent lifecycle
- joins
- uniqueness
- attributes per relationship

In that case a junction table is usually semantically stronger.

---

# 16. JSON vs JSONB

PostgreSQL supports both `json` and `jsonb`.

## `json`

Preserves the textual JSON representation.

## `jsonb`

Stores a decomposed binary representation designed for efficient processing and supports indexing strategies not available in the same way for plain `json`.

For most application workloads that query JSON content, `jsonb` is the more useful choice.

### But JSONB is not a relational replacement

Bad modeling pattern:

```json
{
  "customer_id": 10,
  "status": "paid",
  "amount": 5000,
  "branch_id": 4
}
```

stored as the only source of truth for fields that are:

- frequently filtered
- joined
- constrained
- audited
- aggregated
- referenced by many parts of the system

A better hybrid model may be:

```text
stable relational attributes
+
JSONB for flexible extension fields
```

---

# 17. JSONB Operator Families

Advanced JSONB engineering requires understanding different operators and their intended semantics.

Examples:

```sql
payload -> 'customer'
payload ->> 'customer'
payload @> '{"status":"paid"}'
payload ? 'status'
```

The distinction between returning JSON and text matters:

```sql
payload -> 'amount'
```

versus:

```sql
payload ->> 'amount'
```

Once values become text, further comparisons may involve casts and different planner/index behavior.

---

# 18. JSONB Indexing

GIN indexes are commonly important for JSONB containment/operator-heavy workloads.

Example:

```sql
CREATE INDEX idx_orders_payload_gin
ON orders
USING gin (payload);
```

But “JSONB column + GIN index” is not automatically optimal.

The actual workload determines whether to use:

- a general-purpose GIN index
- an expression index
- a focused relational column
- a generated column
- a partial index

### Expert rule

Start from the query predicate.

```text
Query operator
→ operator class
→ index structure
→ selectivity
→ maintenance cost
```

---

# 19. Range Types

Range types model spans rather than single points.

Built-in range families include examples such as:

- `int4range`
- `int8range`
- `numrange`
- `daterange`
- `tsrange`
- `tstzrange`

Example:

```sql
SELECT daterange('2026-01-01', '2026-02-01', '[)');
```

The canonical half-open representation:

```text
[start, end)
```

is particularly useful for temporal reasoning because adjacent ranges can meet without overlapping.

---

# 20. Range Operators

Range semantics become powerful when business concepts are naturally intervals.

Common conceptual operations include:

```text
contains
contained by
overlaps
adjacent to
strictly left
strictly right
```

This is useful for:

- room bookings
- employee assignments
- pricing validity
- inventory reservation windows
- maintenance windows
- subscription periods
- effective-dated configuration

### Example

```sql
WHERE active_period @> now()
```

asks whether the current instant is contained by the stored period.

---

# 21. Exclusion Constraints + Range Types

One of the strongest PostgreSQL-specific modeling patterns is:

```text
Range type
+
Exclusion constraint
=
Declarative non-overlap invariant
```

Conceptually:

```sql
EXCLUDE USING gist (
    resource_id WITH =,
    active_period WITH &&
)
```

This can enforce that two reservations for the same resource may not overlap.

This is far stronger than relying only on application checks such as:

```text
SELECT existing reservation
→ if none
→ INSERT
```

because the database constraint protects the invariant under concurrency.

---

# 22. Network Address Types

PostgreSQL network types include `inet` and `cidr`.

These are preferable to arbitrary text for actual IP/network semantics because the database can understand:

- address family
- network containment
- subnet relationships
- comparisons
- network operators

Example:

```sql
SELECT inet '192.168.1.10' <<= cidr '192.168.1.0/24';
```

The general principle is:

> Use semantic domain types when the database can enforce and operate on the domain directly.

---

# 23. Bit Strings

`bit(n)` and `varbit(n)` represent sequences of bits.

Potential uses include:

- compact feature flags
- protocol fields
- binary masks
- fixed-format low-level representations

Do not use them for ordinary application booleans merely because they appear compact. Optimize semantics and maintainability before micro-optimizing storage.

---

# 24. Full-Text Search Types

PostgreSQL provides `tsvector` and `tsquery` for full-text search.

The semantic separation is important:

```text
Document text
   ↓
Tokenization / normalization
   ↓
tsvector

Search intent
   ↓
tsquery
```

These types are often paired with a GIN or GiST index depending on workload and configuration.

Full-text types are a good example of PostgreSQL encoding a higher-level semantic domain instead of forcing everything into `text`.

---

# 25. Composite Types

Composite types represent structured records.

Example conceptually:

```text
address = (street, city, postal_code)
```

They can be useful in specialized PostgreSQL-heavy designs, functions, or shared structured contracts.

However, for ordinary application domain modeling, normalize carefully before introducing complex composite structures.

A composite type is not automatically a substitute for a relational entity.

---

# 26. Type Modifiers and Constraints

A common misconception is that “the type enforces the complete business rule.”

Usually the real contract is distributed across:

```text
Type
+
NOT NULL
+
CHECK
+
UNIQUE
+
FOREIGN KEY
+
DOMAIN
+
EXCLUSION
+
TRIGGER / FUNCTION when justified
```

Example:

```sql
CREATE TABLE payments (
    payment_id bigint PRIMARY KEY,
    amount numeric(18,2) NOT NULL,
    currency_code text NOT NULL,
    CONSTRAINT payments_amount_positive
        CHECK (amount > 0),
    CONSTRAINT payments_currency_format
        CHECK (length(currency_code) = 3)
);
```

The type controls representation; constraints control additional invariants.

---

# 27. Type Casting

Casting is where type semantics become operational.

Explicit cast:

```sql
SELECT '123'::integer;
```

or:

```sql
SELECT CAST('123' AS integer);
```

Implicit conversion can sometimes occur, but relying on implicit behavior in critical SQL can create ambiguity and planner surprises.

### Engineering rule

Use explicit casts when the intended type boundary is important to correctness, readability, or index usage.

---

# 28. Type Resolution

When PostgreSQL sees overloaded operators/functions or expressions with multiple types, it performs type resolution.

This affects queries such as:

```sql
SELECT some_column = '123';
```

versus:

```sql
SELECT some_column = 123;
```

These may resolve differently depending on column type and available casts/operators.

Expert SQL writing therefore includes awareness of:

- unknown literals
- preferred types
- implicit casts
- assignment casts
- operator overloads
- function overloads

---

# 29. Collation Is Part of Type Semantics

Text comparison is not merely byte comparison.

Collation can influence:

- ordering
- equality-related operations in some contexts
- index behavior
- locale-sensitive behavior
- case/linguistic ordering

Therefore:

```text
text value
+
collation
+
operator
```

collectively define important comparison semantics.

This becomes especially important in multilingual systems.

---

# 30. Generated Columns and Type Design

A generated column can derive one value from another using a stored expression.

Example concept:

```sql
CREATE TABLE products (
    price numeric(18,2) NOT NULL,
    tax_rate numeric(8,4) NOT NULL,
    total numeric(18,2)
        GENERATED ALWAYS AS (price + price * tax_rate) STORED
);
```

Generated columns are useful when derived values should be represented consistently at the database layer.

But financial semantics require careful rounding and scale decisions; blindly copying arithmetic from an application language is unsafe.

# 31. Domain-Specific Type Selection Framework

For every new column, answer these questions.

## Question 1 — What does it mean?

Not “what value does it contain?” but:

> What business concept does it represent?

## Question 2 — What values are legal?

Define the domain explicitly.

## Question 3 — What values are impossible?

These should become constraints whenever practical.

## Question 4 — Is precision exact?

This determines integer vs numeric vs floating point, among others.

## Question 5 — Is timezone part of the meaning?

This is critical for temporal types.

## Question 6 — Is the value scalar or relational?

A list stored in an array or JSON field may actually be a relationship that deserves rows.

## Question 7 — How is it queried?

The query operators influence index strategy.

## Question 8 — How does it evolve?

Consider enum evolution, domain changes, precision changes, and migrations.

## Question 9 — What will the application serialize?

The database representation and API representation need not be identical, but the conversion must be explicit and lossless where required.

## Question 10 — What happens under scale?

A type that is convenient at 100 rows may be expensive at 1 billion rows.

# 32. Production Case Study — Multi-Tenant ERP

Suppose a jewellery ERP has:

```text
Tenant
Branch
Product
Metal Weight
Price
Discount
```

A poor schema may use:

```text

```


But the final choice still depends on:

- workload
- tenant scale
- migration requirements
- reporting
- integration contracts
- search patterns
- retention policies

# 33. Anti-Pattern Catalog

## Anti-pattern 1 — Everything is `text`

### Assumption
Text is flexible.

### Problem
The database loses domain semantics and must trust application code.

### Consequence
Invalid states become easier to store and harder to detect.

### Better approach
Use the narrowest semantic type that fits the real business contract.

---

## Anti-pattern 2 — Everything is `jsonb`

### Assumption
JSONB avoids migrations.

### Problem
You replace schema evolution with application-level uncertainty.

### Better approach
Use relational columns for stable, highly queried, highly constrained concepts and JSONB for genuinely flexible structures.

---

## Anti-pattern 3 — FLOAT for money

### Assumption
It is numeric, so it is sufficient.

### Problem
Approximate arithmetic can violate exact business expectations.

### Better approach
Use exact numeric semantics for exact decimal business values.

---

## Anti-pattern 4 — Local timestamp without thinking

### Assumption
The server runs in one timezone.

### Problem
Distributed deployments, daylight-saving behavior, integrations, and audits expose ambiguity.

### Better approach
Model instants as instants and local wall-clock values as local values.

---

## Anti-pattern 5 — Array as a hidden join table

### Assumption
It is simpler.

### Problem
Referential integrity and relationship attributes disappear.

### Better approach
Use a normalized relationship table when the relationship itself has lifecycle or attributes.

# 34. AI / Vibe-Coding Failure Patterns

AI-generated database code commonly produces type mistakes such as:

```text
amount DOUBLE PRECISION
createdAt TIMESTAMP
metadata TEXT
status VARCHAR(255)
ids TEXT[]
```

The SQL may compile perfectly while the model is wrong.

### Audit every AI-generated schema with this checklist

```text
1. What business concept does the column represent?
2. Is the precision exact?
3. Is timezone meaningful?
4. Is the field really scalar?
5. Should the database enforce a domain constraint?
6. Does the chosen type support required operators?
7. What indexes become possible or impossible?
8. How will it be serialized?
9. How will it migrate?
10. What happens at 10x / 100x scale?
```

The goal is not to distrust AI. It is to prevent syntactically valid but semantically weak schemas from reaching production.

# 35. Performance Reasoning

Type choice can influence performance through:

```text
row width
→ page density
→ cache residency
→ index size
→ WAL volume
→ sort memory
→ aggregation memory
→ network payloads
→ replication bandwidth
```

A wider type is not automatically slow. A narrow type is not automatically fast.

Always connect type choice to workload characteristics.

---

# 36. Index Interaction

Different types unlock different index/operator combinations.

Examples:

```text
scalar equality/range
→ B-tree

JSONB containment/key operators
→ GIN commonly relevant

range overlap/containment
→ GiST/SP-GiST depending on use case

full-text search
→ GIN/GiST with tsvector

large naturally ordered data
→ BRIN may be useful
```

Do not choose the type independently from how the column must be searched.

---

# 37. Storage and TOAST Awareness

Large variable-length values such as long text, JSONB, arrays, and binary data can interact with PostgreSQL's TOAST storage mechanism.

The engineering implications include:

- large-row updates
- out-of-line storage
- extra I/O
- vacuum behavior
- WAL generation
- backup size

An advanced schema review therefore asks:

> “How big can this value become, and how frequently is it updated?”

# 40. Debugging Framework

When a query behaves unexpectedly, inspect the type boundary first.

```text
Unexpected result
      ↓
Check column types
      ↓
Check literal types
      ↓
Check casts
      ↓
Check operator resolution
      ↓
Check collation/timezone context
      ↓
Check index/operator compatibility
      ↓
EXPLAIN
      ↓
Validate business semantics
```

Common symptoms:

| Symptom | Possible type issue |
|---|---|
| Index not used | cast or operator mismatch |
| wrong ordering | text/collation/type semantics |
| time shifts | timezone interpretation |
| precision mismatch | floating-point approximation |
| JSON query slow | wrong operator/index strategy |
| overlap checks fail | poor temporal representation |
| invalid state stored | insufficient domain constraints |

# 41. Design Review Questions

Before approving a schema, ask:

1. Why is this type correct semantically?
2. Why is a different type worse?
3. Which invariants does the type enforce?
4. Which invariants still require constraints?
5. What operators are required?
6. Which index structures become available?
7. What is the largest realistic value?
8. What happens under malformed input?
9. How will the application serialize it?
10. How will it migrate in production?
11. Does the type preserve financial/temporal correctness?
12. Does this choice become problematic at large scale?

# 47. Key Principles to Retain

> **A PostgreSQL type is a semantic contract, not merely a storage bucket.**

> **Choose types from business meaning outward, not from application-language convenience inward.**

> **Exact business values require exact mathematical semantics.**

> **An instant in time is not the same thing as a local wall-clock timestamp.**

> **Flexible data does not automatically justify JSONB.**

> **A collection in a column may actually be a relational relationship.**

> **Range types become especially powerful when paired with declarative exclusion constraints.**

> **Type choice and index strategy should be designed together.**

> **The strongest schemas use types plus constraints to make invalid states difficult or impossible to represent.**

> **AI can generate valid SQL while still generating an invalid data model.**

1. infer why each important type was selected,

3. predict correctness failures,
