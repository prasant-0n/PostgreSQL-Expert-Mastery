# 01.13 — RETURNING

> **Phase 01 — Advanced SQL**  
> **Chapter 01.13**  
> **Target mastery:** L5 → L7

---

## 1. Chapter Mission

`RETURNING` is not merely syntactic sugar for "give me the row I just changed." It is a database-to-application dataflow primitive: a data-modification statement can produce a result set describing the rows actually inserted, updated, deleted, or merged.

This chapter develops the ability to reason about `RETURNING` as part of:

- correctness
- atomic state transitions
- generated-value retrieval
- concurrency-safe workflows
- audit/event pipelines
- bulk DML
- PostgreSQL-specific trigger behavior
- application/database boundaries
- observability and debugging
- API response design

The core principle is:

> **When the database is the authority that performs a state transition, prefer obtaining authoritative post-write state from the same statement rather than reconstructing it with a second query.**

PostgreSQL documents `RETURNING` for `INSERT`, `UPDATE`, `DELETE`, and `MERGE`. The returned expressions follow the output-list rules of `SELECT`. PostgreSQL 18 additionally supports explicit `OLD` and `NEW` references in `RETURNING`. [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/dml-returning.html)

---

## 2. Precise Definitions

### 2.1 Simple definition

`RETURNING` tells PostgreSQL to send information about rows affected by a data-modification statement back to the client.

### 2.2 Engineering definition

`RETURNING` turns DML into a **producer of relational output**. Instead of:

```text
write → commit → query again
```

you can often do:

```text
write → produce authoritative result
```

### 2.3 Expert definition

`RETURNING` exposes the result relation associated with rows actually modified by a DML operation, after PostgreSQL has applied the relevant row changes and, where applicable, trigger effects. PostgreSQL 18 also permits explicit access to old and new row images through `OLD` and `NEW` aliases. [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/dml-returning.html)

---

# 3. The Fundamental Mental Model

Do not think of `RETURNING` as:

> "a SELECT attached to UPDATE."

Think of it as:

```text
DML Statement
     │
     ├── identify target rows
     │
     ├── perform mutation
     │
     ├── enforce constraints / triggers
     │
     └── construct RETURNING output
                  │
                  ▼
              result rows
```

The returned relation describes the rows affected by the statement—not an independent re-read of the table.

That distinction becomes critical for concurrency, generated values, trigger-modified data, and bulk operations.

---

# 4. Why RETURNING Exists

Without `RETURNING`, application code often falls into this pattern:

```sql
INSERT INTO users (email, name)
VALUES ('a@example.com', 'A');

SELECT id, created_at
FROM users
WHERE email = 'a@example.com';
```

The application is now reconstructing information that the write operation itself already knows.

Problems include:

- another transaction may alter matching state
- the lookup condition may not uniquely identify the row
- generated values may be difficult to reproduce
- two round trips increase latency
- write/read logic becomes duplicated
- bulk writes become awkward

With `RETURNING`:

```sql
INSERT INTO users (email, name)
VALUES ('a@example.com', 'A')
RETURNING id, created_at;
```

The database returns the values associated with the actual inserted row.

---

# 5. RETURNING Is a Result Relation

The conceptual model is important.

A statement such as:

```sql
UPDATE products
SET price = price * 1.10
WHERE price <= 100
RETURNING id, price;
```

does not conceptually return one scalar. It returns zero or more rows:

```text
(id, price)
(id, price)
(id, price)
...
```

Therefore all normal output-list reasoning matters:

- expressions
- aliases
- computed columns
- functions
- table qualification
- `*`

PostgreSQL explicitly states that the contents of `RETURNING` use the same output-list rules as `SELECT`. citeturn805769search1

# 6. INSERT + RETURNING

## 6.1 Basic identity retrieval

```sql
CREATE TABLE users (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    name text NOT NULL
);

INSERT INTO users (email, name)
VALUES ('alice@example.com', 'Alice')
RETURNING id;
```

The application should consume the returned generated key rather than attempt to predict it.

## 6.2 Returning multiple generated values

```sql
INSERT INTO users (email, name)
VALUES ('alice@example.com', 'Alice')
RETURNING id, email, name, created_at;
```

Useful when defaults or generated expressions populate fields.

## 6.3 Returning computed expressions

```sql
INSERT INTO products (sku, price)
VALUES ('SKU-100', 100)
RETURNING sku, price, price * 1.18 AS price_with_tax;
```

The result does not need to be limited to physical columns.

---

# 7. INSERT ... SELECT + RETURNING

This becomes especially powerful for bulk ingestion.

```sql
INSERT INTO order_items (order_id, product_id, quantity)
SELECT order_id, product_id, quantity
FROM staging_order_items
RETURNING order_item_id, order_id, product_id;
```

Now the application can receive the identities of all rows created by the statement.

### Important distinction

For large batches, `RETURNING *` may itself become expensive because the database must send every returned column for every affected row.

Prefer a deliberately designed output contract:

```sql
RETURNING order_item_id, order_id;
```

rather than blindly using:

```sql
RETURNING *;
```

---

# 8. UPDATE + RETURNING

For `UPDATE`, unqualified target-table columns in the `RETURNING` list represent the **new/post-update values** by default. PostgreSQL also permits explicit old/new references in PostgreSQL 18. citeturn805769search1turn805769search4

```sql
UPDATE products
SET price = price * 1.10
WHERE category_id = 10
RETURNING id, price;
```

This is often the cleanest way to return exactly what the write changed.

---

# 9. PostgreSQL 18: OLD and NEW

PostgreSQL 18 adds explicit `OLD` and `NEW` support to `RETURNING` for DML. citeturn805769search0turn805769search1

Example:

```sql
UPDATE products
SET price = price * 1.10
WHERE id = 42
RETURNING
    id,
    OLD.price AS old_price,
    NEW.price AS new_price,
    NEW.price - OLD.price AS price_change;
```

This is considerably clearer than forcing application code to infer the previous value.

### Why this matters

The database owns the transition:

```text
old state
   ↓
mutation
   ↓
new state
```

`RETURNING` can now expose both ends of that transition.

---

# 10. DELETE + RETURNING

For a delete, returned target-table values describe the row being deleted.

```sql
DELETE FROM sessions
WHERE expires_at < now()
RETURNING id, user_id, expires_at;
```

This is useful for:

- cleanup reporting
- downstream job construction
- deletion auditing
- cache invalidation inputs
- observability

PostgreSQL documents that `DELETE ... RETURNING` computes output from each row actually deleted. citeturn805769search3

---

# 11. MERGE + RETURNING

PostgreSQL 18 supports `RETURNING` for `MERGE` as well. The returned data can include source and target information, and `merge_action()` can identify which action occurred. citeturn805769search7

Example shape:

```sql
MERGE INTO products AS p
USING incoming_products AS n
ON p.sku = n.sku
WHEN MATCHED THEN
    UPDATE SET price = n.price
WHEN NOT MATCHED THEN
    INSERT (sku, price)
    VALUES (n.sku, n.price)
RETURNING p.sku, p.price, merge_action();
```

This is useful for synchronization pipelines because the write statement can emit what happened.

---

# 12. RETURNING vs SELECT-after-write

Consider:

```sql
UPDATE accounts
SET status = 'active'
WHERE id = 100;

SELECT status
FROM accounts
WHERE id = 100;
```

versus:

```sql
UPDATE accounts
SET status = 'active'
WHERE id = 100
RETURNING status;
```

The second form is generally preferable when all you need is the state resulting from that mutation.

It avoids the architectural mistake of treating the database write and database read as unrelated operations.

---

# 13. Generated Defaults

A common pattern:

```sql
CREATE TABLE invoices (
    invoice_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    invoice_no text DEFAULT gen_random_uuid()::text,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Then:

```sql
INSERT INTO invoices DEFAULT VALUES
RETURNING invoice_id, invoice_no, created_at;
```

The application does not need to duplicate database default logic.

That is a major design principle:

> **Do not copy authoritative database-generated behavior into application code merely to predict what the database will generate.**

---

# 14. Triggers and RETURNING

PostgreSQL documents that when triggers are present, the data available to `RETURNING` reflects the row as modified by the triggers. This makes `RETURNING` useful for observing trigger-computed fields. citeturn805769search1

Example conceptual flow:

```text
UPDATE request
    ↓
BEFORE trigger
    ↓
row mutation
    ↓
AFTER trigger effects
    ↓
RETURNING result
```

Therefore:

```sql
UPDATE customers
SET name = 'Alice Smith'
WHERE customer_id = 10
RETURNING *;
```

can return values that the application did not explicitly set, depending on database-side behavior.

---

# 15. RETURNING and Upsert

`RETURNING` becomes especially useful with `INSERT ... ON CONFLICT`.

```sql
INSERT INTO users (email, name)
VALUES ('a@example.com', 'Alice')
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name
RETURNING id, email, name;
```

PostgreSQL 18 also exposes old/new row images in this context. PostgreSQL documents that old values can be non-NULL for conflicting rows in an `INSERT ... ON CONFLICT DO UPDATE`. citeturn805769search1turn805769search5

Example:

```sql
INSERT INTO users (email, name)
VALUES ('a@example.com', 'Alice Updated')
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name
RETURNING
    id,
    OLD.name AS previous_name,
    NEW.name AS current_name;
```

This is a powerful state-transition primitive.

---

# 16. Concurrency: Why RETURNING Matters

Suppose the application executes:

```text
1. UPDATE row
2. SELECT row
```

That second statement is a separate statement with its own visibility semantics and can be affected by intervening work.

`RETURNING` instead attaches the result directly to the mutation.

That does **not** mean all concurrency problems disappear. It means the application is not unnecessarily reconstructing the mutation result using a separate query.

Always distinguish:

```text
atomic mutation result
```

from:

```text
post-write follow-up observation
```

They are not automatically equivalent.

---

# 17. Row Count vs Returned Rows

Do not confuse:

```text
number of rows affected
```

with:

```text
number of rows returned by RETURNING
```

For successful ordinary DML, the `RETURNING` result corresponds to the rows actually affected by that DML action.

Application code should therefore define whether its contract needs:

- only an affected-row count
- one generated identifier
- one complete row
- many changed rows
- before/after state

Returning huge result sets just because the feature is available is poor API/database design.

---

# 18. RETURNING and Bulk DML

Example:

```sql
UPDATE inventory
SET available = available - 1
WHERE warehouse_id = 7
  AND sku IN ('A', 'B', 'C')
RETURNING sku, available;
```

This is better than issuing one statement per SKU merely to discover the resulting values.

### Bulk engineering question

Always ask:

> What is the output cardinality of my mutation?

If 500,000 rows are changed and you return 20 columns per row, the database may correctly produce 500,000 rows—but the application may be unable to consume them efficiently.

Database correctness and application transport capacity are different concerns.

---

# 19. The `RETURNING *` Trap

`RETURNING *` is convenient:

```sql
DELETE FROM temp_events
WHERE processed = true
RETURNING *;
```

But production code should ask whether all columns are genuinely needed.

Problems:

- wider network payload
- more serialization
- more memory in the client/driver
- accidental exposure of sensitive columns
- unstable API coupling to schema changes

Prefer:

```sql
RETURNING event_id, event_type, occurred_at;
```

when those are the actual downstream requirements.

---

# 20. RETURNING and API Contracts

A NestJS service might expose:

```ts
const result = await this.pool.query(
  `
  UPDATE orders
  SET status = $1
  WHERE order_id = $2
  RETURNING order_id, status, updated_at
  `,
  [status, orderId],
);
```

The service can then construct a response directly from the returned database state.

This reduces the temptation to:

```text
update()
→ fetchById()
→ map()
```

for every mutation.

The database already returned the authoritative values.

---

# 21. RETURNING Does Not Replace Validation

Bad reasoning:

> "Because I use RETURNING, my update is safe."

Incorrect.

`RETURNING` tells you what was changed.

It does not automatically ensure:

- the correct target row was selected
- the tenant was correct
- authorization was correct
- invariants are enforced
- business transitions are valid
- the transaction boundary is correct

Example:

```sql
UPDATE invoices
SET status = 'paid'
WHERE invoice_id = $1
RETURNING invoice_id, status;
```

This may be perfectly valid SQL and still be a multi-tenant security bug if the target predicate does not constrain tenant ownership.

---

# 22. Multi-Tenant Safety

Bad:

```sql
UPDATE orders
SET status = 'cancelled'
WHERE order_id = $1
RETURNING order_id, status;
```

Safer when the architecture requires tenant scoping:

```sql
UPDATE orders
SET status = 'cancelled'
WHERE order_id = $1
  AND tenant_id = $2
RETURNING order_id, status;
```

The returned row should itself be part of the authorization/correctness boundary—not an excuse to perform an unscoped write.

---

# 23. Conditional Mutation + RETURNING

A highly valuable pattern is to encode the business predicate into the mutation itself.

```sql
UPDATE inventory
SET available = available - 1
WHERE tenant_id = $1
  AND sku = $2
  AND available > 0
RETURNING sku, available;
```

Now:

```text
returned row exists  → decrement succeeded
returned row absent  → no row satisfied the condition
```

This is much stronger than:

```text
SELECT available
UPDATE inventory
```

because the condition participates directly in the mutation.

---

# 24. RETURNING as an Atomic Decision Signal

For a mutation with a narrow predicate:

```sql
UPDATE jobs
SET claimed_at = now(),
    worker_id = $1
WHERE job_id = $2
  AND claimed_at IS NULL
RETURNING job_id, claimed_at, worker_id;
```

Application semantics can become:

```text
row returned    → claim won
zero rows       → someone else already claimed it / target unavailable
```

This is a database-backed coordination pattern.

It is not magic: correctness still depends on the predicate, transaction semantics, schema constraints, and workload.

---

# 25. RETURNING with CTEs

`WITH` can be combined with DML and `RETURNING`, enabling more complex dataflows.

Conceptual example:

```sql
WITH moved AS (
    DELETE FROM source_orders
    WHERE order_id = $1
    RETURNING order_id, customer_id, total
)
INSERT INTO archived_orders (order_id, customer_id, total)
SELECT order_id, customer_id, total
FROM moved;
```

The important idea is not the syntax alone:

```text
DML output becomes relational input
```

This creates powerful database-local workflows.

---

# 26. RETURNING as a Pipeline Primitive

Think in terms of:

```text
DML
 ↓
RETURNING relation
 ↓
CTE / query consumer
 ↓
next relational operation
```

This makes PostgreSQL capable of expressing some workflows without pulling intermediate state into application memory.

Benefits can include:

- fewer round trips
- reduced serialization/deserialization
- stronger atomicity
- simpler state transitions

But complexity should remain proportional to the business logic.

---

# 27. BEFORE vs AFTER State

PostgreSQL 18's explicit `OLD`/`NEW` syntax makes transition-oriented reporting clearer.

Example:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE account_id = 7
RETURNING
    account_id,
    OLD.balance AS old_balance,
    NEW.balance AS new_balance;
```

The returned result can directly support:

- audit records
- change events
- reconciliation
- debugging
- application response construction

However, do not assume the presence of old/new values means the operation is automatically a complete audit architecture. Audit durability, actor identity, transaction correlation, and tamper resistance are separate design concerns.

---

# 28. Financial Systems

For financial state transitions, explicit before/after reporting can make correctness easier to reason about.

Example:

```sql
UPDATE ledger_accounts
SET balance = balance + $2
WHERE tenant_id = $1
  AND account_id = $3
RETURNING
    account_id,
    OLD.balance AS balance_before,
    NEW.balance AS balance_after,
    NEW.balance - OLD.balance AS delta;
```

Then validate the invariant:

```text
balance_after = balance_before + delta
```

Do not use this pattern as a substitute for a proper ledger model when append-only financial history is required. Mutable balances and immutable transaction history solve different problems.

---

# 29. Temporal Data

Example:

```sql
UPDATE subscriptions
SET status = 'cancelled',
    cancelled_at = now()
WHERE tenant_id = $1
  AND subscription_id = $2
RETURNING
    subscription_id,
    OLD.status AS previous_status,
    NEW.status AS current_status,
    NEW.cancelled_at;
```

This produces a useful transition record without a follow-up lookup.

But temporal correctness still depends on:

- timezone semantics
- clock source
- allowed state transitions
- transaction boundaries
- uniqueness/exclusion rules where applicable

---

# 30. Common Mistake: Re-querying by a Non-Unique Attribute

Bad:

```sql
INSERT INTO users (email)
VALUES ($1);

SELECT id
FROM users
WHERE email = $1;
```

Even when `email` is currently unique, the design duplicates identity-resolution logic.

Correct:

```sql
INSERT INTO users (email)
VALUES ($1)
RETURNING id;
```

Better yet, make the uniqueness invariant explicit in the schema:

```sql
UNIQUE (email)
```

Then let the database enforce it.

---

# 31. Common Mistake: Assuming Zero Returned Rows Means an Error

Example:

```sql
UPDATE jobs
SET status = 'done'
WHERE job_id = $1
  AND status = 'running'
RETURNING job_id;
```

Zero rows may be a legitimate business outcome:

- job does not exist
- job is already done
- job is not currently running

Application code must define the semantics deliberately.

Do not convert every zero-row mutation into a generic 500 response.

---

# 32. Common Mistake: Returning Sensitive Data

Bad:

```sql
UPDATE users
SET password_hash = $2
WHERE id = $1
RETURNING *;
```

The SQL may be correct, but the result contract may expose sensitive fields unnecessarily.

Prefer explicit columns:

```sql
RETURNING id, email, updated_at;
```

---

# 33. Common Mistake: Using RETURNING as an Audit Log

`RETURNING` produces a result relation.

An audit log requires durable storage.

Therefore:

```text
RETURNING output
≠
audit trail
```

A proper audit design may include:

- immutable records
- actor identity
- request/correlation ID
- old/new state
- timestamp
- tenant
- reason
- transaction context
- retention policy

`RETURNING` can be an input to such a design, but it is not the design itself.

# 34. AI / Vibe-Coding Failure Patterns

### Failure A — UPDATE then SELECT every time

AI-generated pattern:

```text
UPDATE
SELECT same row
```

Question to ask:

> Why are we reconstructing the state the DML already produced?

### Failure B — `RETURNING *` everywhere

Question:

> What is the output contract, and why do we need every column?

### Failure C — Missing tenant predicate

Question:

> Does the returned row prove authorization, or did the write itself fail to constrain the target?

### Failure D — Treating zero rows as exceptional

Question:

> Is zero-row output a business state or an actual database failure?

### Failure E — Returning secrets

Question:

> Could this result leak hashes, tokens, private metadata, or internal columns?

### Failure F — Confusing returned state with committed side effects

Question:

> What other systems must observe this change, and what guarantees do they require?

# 35. Performance Engineering

`RETURNING` changes the output side of a DML statement.

The write itself may be cheap compared with transmitting a large returned relation.

Think about:

```text
Rows changed × columns returned × row width
```

A mutation affecting one row:

```sql
RETURNING id;
```

is very different from a bulk update returning 30 wide columns for 5 million rows.

### Measure

For production systems, inspect:

- execution time
- rows affected
- rows returned
- network bytes
- client deserialization cost
- application memory
- downstream serialization cost

The correct optimization may be to return **less**, not to optimize the write.

---

# 36. EXPLAIN and RETURNING

`EXPLAIN` can be used to inspect the DML plan.

For example:

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders
SET status = 'cancelled'
WHERE tenant_id = 7
  AND order_id = 1001
RETURNING order_id, status;
```

The main performance questions remain:

- how many rows were scanned?
- how many rows were actually updated?
- was the target predicate selective?
- were buffers hit or read from storage?
- did the statement touch far more rows than expected?

`RETURNING` does not make a bad mutation plan good.

# 37. RETURNING and Triggers: Debugging Strategy

Suppose the application says:

> "I updated `status` to `paid`, but the returned row says `settled`."

Do not immediately blame the driver.

Investigate:

```text
Application input
→ DML target predicate
→ BEFORE triggers
→ row mutation
→ constraints/rules
→ trigger side effects
→ RETURNING output
```

PostgreSQL documents that trigger-modified values can be visible through `RETURNING`. citeturn805769search1

# 38. Node.js / NestJS Integration

A low-level driver pattern:

```ts
const result = await pool.query<{
  order_id: bigint;
  status: string;
  updated_at: string;
}>(
  `
  UPDATE orders
  SET status = $1
  WHERE tenant_id = $2
    AND order_id = $3

  `,
  [status, tenantId, orderId],

if (result.rowCount === 0) {
  // Interpret according to business semantics.
}

const order = result.rows[0];
```

Production considerations:

- define the returned DTO intentionally
- avoid returning internal-only columns
- treat zero rows deliberately
- use parameterized SQL
- preserve transaction boundaries
- avoid unnecessary follow-up reads

# 39. ORM Considerations

ORMs differ in how naturally they expose database-returned rows.

Before using an ORM abstraction, ask:

1. Does it actually issue `RETURNING`?
2. Does it retrieve generated values in one statement?
3. What happens for bulk writes?
4. Does it return old/new values where PostgreSQL supports them?
5. Does it silently perform a second query?

Never assume that a convenient ORM API implies an efficient database round-trip pattern.

Inspect generated SQL when performance or correctness matters.

---

# 40. RETURNING and Event Publication

A tempting architecture is:

```text
UPDATE
RETURNING
→ publish event
```

This can be useful, but it introduces a reliability question:

```text
What happens if the database transaction commits
but event publication fails?
```

Therefore `RETURNING` alone does not solve dual-write consistency.

For reliable event publication, consider a transactional outbox architecture where the database transaction persists both the state change and the event record atomically.

`RETURNING` can still help capture the authoritative state needed to construct the event payload.

---

# 41. Idempotency

Example:

```sql
INSERT INTO payments (idempotency_key, amount)
VALUES ($1, $2)
ON CONFLICT (idempotency_key)
DO UPDATE SET amount = payments.amount
RETURNING payment_id, amount;
```

Whether this is actually a correct idempotency implementation depends on the intended semantics.

Ask:

- should mismatched amounts be rejected?
- should the original result be replayed?
- should the record be immutable?
- who owns the idempotency invariant?

`RETURNING` provides output. It does not define the business contract.

---

# 42. State Machines

A robust transition pattern:

```sql
UPDATE orders
SET status = 'shipped'
WHERE order_id = $1
  AND status = 'paid'
RETURNING
    order_id,
    OLD.status AS old_status,
    NEW.status AS new_status;
```

The mutation itself encodes:

```text
paid → shipped
```

A returned row indicates that the transition matched and was executed.

This is often more reliable than:

```text
SELECT current state
if valid:
    UPDATE
```

because the validity predicate can be part of the state transition itself.

---

# 43. When NOT to Use RETURNING

Do not automatically use it everywhere.

Avoid or minimize it when:

- the caller needs no resulting data
- the affected set is enormous
- only a count is required
- returning wide rows causes transport pressure
- the result would duplicate an already sufficient application contract

Example:

```sql
UPDATE analytics_events
SET processed = true
WHERE batch_id = $1;
```

If the application only needs "how many rows changed," fetching every changed row is unnecessary.

---

# 44. Decision Framework

Use this sequence:

```text
1. What state transition occurred?
2. Does the caller need database-authoritative output from that transition?
3. Is one statement sufficient?
4. What is the expected returned cardinality?
5. What is the output width?
6. Are any values generated or trigger-modified?
7. Does authorization depend on the mutation predicate?
8. Is zero-row output a valid business outcome?
9. Are OLD/NEW values useful?
10. Does the result feed another database operation?
11. Does transport cost justify the returned columns?
12. Does downstream event publication require stronger durability guarantees?
```

# 46. Production Failure Scenarios

## Failure 1 — Wrong-row update

Symptom:

```text
API says user updated
but wrong tenant's user changed
```

Investigation:

- inspect target predicate
- inspect tenant constraints/RLS
- inspect authorization path
- verify returned row

`RETURNING` may help detect the outcome, but it cannot repair the bad predicate.

## Failure 2 — Missing generated ID

Symptom:

```text
insert succeeded
but application performs another lookup to discover ID
```

Fix:

```sql
INSERT ... RETURNING id;
```

## Failure 3 — Huge API payload

Symptom:

```text
bulk UPDATE became slow after adding RETURNING *
```

Likely cause:

```text
database write + result serialization + network transport + client decode
```

Fix:

- return only necessary columns
- consider count-only semantics
- batch if required

## Failure 4 — Unexpected values returned

Symptom:

# 49. Expert Review Checklist

Before approving production code containing `RETURNING`, ask:

### Correctness

- Does the DML predicate identify exactly the intended rows?
- Is tenant scope enforced?
- Are invariants enforced by the database where appropriate?
- Is zero-row output interpreted correctly?

### Output design

- Which columns are actually required?
- Is `RETURNING *` justified?
- What is the expected output cardinality?
- Could the response expose secrets or internal metadata?

### Concurrency

- Is the returned result tied directly to the mutation?
- Does a conditional predicate encode the concurrency invariant?
- Is a retry safe?

### Performance

- How many rows can be returned?
- How wide are the rows?
- Can network/client serialization dominate cost?

### Architecture

- Is the result becoming an API response, an audit input, or an event payload?
- If it feeds an event, what guarantees are required?
- Should the workflow use an outbox or another durable mechanism?

# 51. Final Mental Model

```text
A database mutation has two outputs:

1. The changed state
2. Information about that state transition

DML changes the state.
RETURNING exposes a relational description of the affected rows.

Therefore:

WRITE
  ↓
AUTHORITATIVE STATE TRANSITION
  ↓
RETURNING RESULT
  ↓
APPLICATION / NEXT SQL OPERATION
```

The expert question is not:

> "Can I use RETURNING here?"

It is:

> **"What authoritative information does this state transition need to produce, at what cardinality and width, and what guarantees must the consumer derive from it?"**

That is the difference between knowing PostgreSQL syntax and engineering with PostgreSQL.
