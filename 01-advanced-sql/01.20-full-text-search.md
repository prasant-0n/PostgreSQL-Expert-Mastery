# 01.20 — Full-Text Search

> **Phase 01 — Advanced SQL**
>
> Full-text search (FTS) is PostgreSQL's native system for turning natural-language text into searchable lexemes, expressing search intent as `tsquery`, matching with `@@`, ranking matches, highlighting results, and accelerating searches with specialized indexes.

---

## 1. Learning Objective

By the end of this chapter, you should be able to design, implement, debug, optimize, and productionize PostgreSQL full-text search without confusing it with substring search, regular expressions, trigram similarity, or an external search engine.

You should understand not only **what query to write**, but **why PostgreSQL represents text as a `tsvector`, why a query is a `tsquery`, how configurations and dictionaries change semantics, why GIN is normally preferred, when GiST or `pg_trgm` is better, how ranking works, and where database FTS stops being the right architecture**.

### Mastery target

A strong engineer can take a product requirement such as:

> “Search jewellery products by title, SKU, description, category and material; understand English word variants; support phrases, OR and exclusions; rank title matches higher; return highlighted snippets; remain tenant-safe and fast under high concurrency.”

and translate it into:

```text
business semantics
    ↓
search document design
    ↓
text-search configuration
    ↓
tsvector representation
    ↓
user-query parsing
    ↓
tsquery
    ↓
index strategy
    ↓
ranking + pagination
    ↓
observability + tests
    ↓
production operating model
```

# 2. What Full-Text Search Actually Is

## 2.1 Simple definition

Full-text search lets PostgreSQL search text by **words and normalized lexemes**, rather than requiring an exact character sequence.

For example:

```sql
SELECT to_tsvector('english', 'The customers purchased beautiful rings');
```

produces a normalized representation roughly like:

```text
'beautiful' 'custom' 'purchas' 'ring'
```

The exact result depends on the selected configuration and dictionaries.

Searching for `rings` can therefore match the normalized lexeme associated with `ring`.

## 2.2 Engineering definition

FTS is a pipeline:

```text
raw document
   ↓
parser
   ↓
tokens
   ↓
dictionaries
   ↓
lexemes
   ↓
tsvector
```

and:

```text
raw search input
   ↓
query parser
   ↓
normalized terms/operators
   ↓
tsquery
```

Then:

```text
tsvector @@ tsquery
```

answers the matching question.

PostgreSQL documents `tsvector` as a text-search document type and `tsquery` as a text-search query type. PostgreSQL's text-search chapter covers configurations, parsers, dictionaries, indexes, ranking, highlighting, debugging, and limitations. citeturn305741search1

## 2.3 Expert definition

PostgreSQL FTS is an **in-database inverted lexical search system** whose semantics are determined by a text-search configuration and whose searchable representation can preserve lexeme positions and weights.

This matters because search correctness is not merely an indexing problem.

A bad configuration produces a bad `tsvector`.

A bad query parser produces a bad `tsquery`.

A good vector and bad ranking can still produce a bad search experience.

A correct search expression without the right index can become a latency problem.

# 3. FTS Mental Model

Think of a document as a book.

A normal B-tree on a text column can efficiently answer ordered/equality-style questions. It is not an inverted word index.

FTS instead builds something conceptually like:

```text
lexeme                matching rows
------------------------------------------------
ring                  12, 31, 40, 51
silver                2, 31, 88
necklace              7, 11, 31
handmade              31, 72
```

The database can then begin with search terms and identify candidate rows.

GIN is designed around this kind of composite-value search. Conceptually it stores keys and the row references associated with those keys. citeturn366847search4

This is fundamentally different from:

```sql
WHERE description ILIKE '%silver ring%'
```

which asks PostgreSQL to find a character sequence.

---

# 4. The Core Types

PostgreSQL's main FTS types are:

| Type | Purpose |
|---|---|
| `tsvector` | normalized searchable document |
| `tsquery` | normalized search condition |
| `regconfig` | identifier of a text-search configuration |
| `regdictionary` | identifier of a dictionary |

The basic operation is:

```sql
vector @@ query
```

Example:

```sql
SELECT
  to_tsvector('english', 'silver diamond ring')
  @@
  to_tsquery('english', 'silver & ring');
```

The `@@` operator tests whether a `tsvector` matches a `tsquery`. citeturn305741search12

---

# 5. `to_tsvector`: Turning Documents into Searchable Data

```sql
SELECT to_tsvector('english', 'Silver rings are beautiful products');
```

The function parses the document, normalizes words according to the selected configuration, and produces lexemes with positions.

PostgreSQL describes `to_tsvector` as parsing textual input into tokens, reducing them to lexemes, and returning lexemes with positions. citeturn366847search0

## Why positions matter

Positions support phrase/proximity-aware operations and ranking algorithms such as `ts_rank_cd`.

Conceptually:

```text
'silver':1
'ring':2
'beautiful':4
```

is richer than merely:

```text
'silver' 'ring' 'beautiful'
```

because the vector can carry structural information about where lexemes occurred.

---

# 6. `to_tsquery`: Expressing Search Intent

`to_tsquery` accepts PostgreSQL text-search query syntax.

Example:

```sql
SELECT to_tsquery('english', 'silver & ring');
```

Common operators include:

```text
&       AND
|       OR
!       NOT
<->     FOLLOWED BY / phrase proximity
:*      prefix matching
```

Example:

```sql
SELECT to_tsvector('english', 'silver ring')
       @@
       to_tsquery('english', 'silver & ring');
```

## Important security lesson

Never blindly concatenate arbitrary user text into a `to_tsquery` expression.

Bad:

```js
const query = `to_tsquery('english', '${userInput}')`;
```

A user can supply syntax that changes the query or produces parser errors.

For ordinary web-search style input, PostgreSQL provides `websearch_to_tsquery`, which accepts user-oriented syntax and does not raise syntax errors for malformed input. citeturn305741search13

---

# 7. Query Construction Functions

## 7.1 `plainto_tsquery`

Use when the input is ordinary text and you want words interpreted as an AND-style search rather than exposing raw query syntax.

```sql
SELECT plainto_tsquery('english', 'silver diamond ring');
```

Conceptually:

```text
'silver' & 'diamond' & 'ring'
```

## 7.2 `phraseto_tsquery`

Useful when word order/proximity matters.

```sql
SELECT phraseto_tsquery('english', 'silver diamond ring');
```

PostgreSQL represents the phrase using FOLLOWED-BY semantics between normalized lexemes. citeturn305741search13

## 7.3 `websearch_to_tsquery`

This is especially valuable for application search boxes.

Example input:

```text
"silver ring" or necklace -gold
```

can become a structured `tsquery` using phrase, OR, and NOT semantics.

PostgreSQL explicitly documents `websearch_to_tsquery` as web-search-style input and notes that it never raises syntax errors, making it suitable for raw user-supplied search text. citeturn305741search13

### Production rule

For a public search box:

```text
user input
   ↓
websearch_to_tsquery / controlled parser
   ↓
tsquery
```

not:

```text
user input
   ↓
string concatenation
   ↓
raw to_tsquery syntax
```

# 8. `json`/`JSONB` vs FTS

JSONB stores structured data.

FTS represents searchable lexical information.

These can work together.

Example:

```sql
products (
  id,
  name,
  description,
  attributes jsonb,
  search_vector tsvector
)
```

A search vector can combine relational and JSON-derived text without making the JSON document itself the search index.

The architecture is:

```text
source fields
   ↓
search-document projection
   ↓
tsvector
   ↓
GIN
```

Do not confuse:

```text
JSONB containment
```

with:

```text
lexical full-text search
```

A JSONB query can answer:

```text
attribute color = silver
```

FTS can answer:

```text
document contains lexemes related to “silver ring”
```

# 9. Text Search Configurations

A configuration defines how text is transformed into `tsvector`/`tsquery` data.

It coordinates:

```text
parser
  ↓
dictionaries
  ↓
lexemes
```

PostgreSQL states that each `to_tsvector` or `to_tsquery` call needs a text-search configuration; the default comes from `default_text_search_config` when none is supplied. PostgreSQL also supports predefined and custom configurations. citeturn305741search0

## Explicit configuration is usually safer

Prefer:

```sql
to_tsvector('english', body)
```

over relying everywhere on:

```sql
to_tsvector(body)
```

because implicit defaults can differ between environments or sessions.

For production search semantics, make the configuration part of the application contract.

---

# 10. Parsers

The parser determines token boundaries and token categories.

PostgreSQL's built-in parser is `pg_catalog.default`. It recognizes many token types and identifies plausible word boundaries; parser behavior is separate from dictionary normalization. citeturn305741search8

This distinction is critical:

```text
parser
= “what kind of token did I see?”

dictionary
= “what lexeme should represent it?”
```

Do not try to solve language-specific linguistic behavior entirely inside the parser.

---

# 11. Dictionaries

Dictionaries normalize tokens into lexemes and can remove stop words.

Common ideas include:

```text
simple
english
snowball / stemming
synonym
thesaurus
ispell
```

A dictionary can:

```text
accept a token
↓
normalize it
↓
return lexeme(s)
```

or identify it as a stop word / otherwise suppress it depending on configuration.

### Example mental model

```text
“rings”
   ↓
parser
   ↓
dictionary
   ↓
“ring”
```

This is why FTS is not simple string matching.

---

# 12. Stop Words

Stop words are common words that may contribute little to search selectivity.

Examples can include language-specific words such as:

```text
and
or
the
of
```

But whether a word should be a stop word is a product decision.

A legal document search system, conversational search system, and product catalog may have very different requirements.

### Failure mode

You search:

```text
“bank of america”
```

but your configuration removes terms that your domain considers meaningful.

The issue is not your index.

It is your search semantics.

# 13. Testing the Configuration Before Building the Application

Use diagnostic functions early.

Useful tooling includes:

```sql
SELECT ts_debug('english', 'Silver diamond rings');
```

This exposes how PostgreSQL parses and transforms the input.

The official documentation provides configuration, parser, and dictionary testing facilities under the text-search debugging section. citeturn305741search1

### Engineering habit

Before saying:

> “PostgreSQL search is not finding this term.”

inspect:

```text
ts_debug()
→ to_tsvector()
→ query parser
→ tsquery
→ index
→ ranking
```

# 14. The Basic Table Pattern

Start with a document table:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    name text NOT NULL,
    description text,
    search_vector tsvector
);
```

Populate a vector:

```sql
UPDATE products
SET search_vector =
    to_tsvector(
        'english',
        coalesce(name, '') || ' ' || coalesce(description, '')
    );
```

Search:

```sql
SELECT id, name
FROM products
WHERE search_vector
      @@ websearch_to_tsquery('english', 'silver ring');
```

---

# 15. Why `coalesce` Matters

Consider:

```sql
name || ' ' || description
```

If `description` is NULL, concatenation can produce NULL.

Safer:

```sql
coalesce(name, '') || ' ' || coalesce(description, '')
```

The rule is broader than FTS:

> Understand SQL NULL propagation before composing search documents.

---

# 16. Weighted Search Documents

Not all fields have equal business importance.

A product title should often rank higher than an internal description.

PostgreSQL supports weighting lexemes.

The four weights are commonly represented as:

```text
A
B
C
D
```

You can construct a weighted vector:

```sql
setweight(to_tsvector('english', coalesce(name, '')), 'A')
|| setweight(to_tsvector('english', coalesce(description, '')), 'B')
```

Conceptually:

```text
name        → A
summary     → B
body        → C
metadata    → D
```

The weights can then influence ranking.

---

# 17. Ranking

Matching is binary:

```text
match / no match
```

Ranking answers:

```text
Which matching result should appear first?
```

PostgreSQL provides `ts_rank` and `ts_rank_cd`. The former ranks based on matching lexeme frequency, while cover-density ranking considers proximity as well. Weights can influence these functions. citeturn366847search0

Example:

```sql
SELECT
    id,
    name,
    ts_rank(search_vector, query) AS rank
FROM products,
     websearch_to_tsquery('english', 'silver ring') AS query
WHERE search_vector @@ query
ORDER BY rank DESC, id DESC;
```

## Ranking is application-specific

A useful production score might be:

```text
FTS relevance
+ title boost
+ exact SKU boost
+ popularity
+ freshness
+ inventory availability
+ tenant-specific business rules
```

PostgreSQL's built-in ranking functions are starting points, not a universal relevance model. citeturn366847search0

---

# 18. Phrase and Proximity Search

A user may search:

```text
“silver diamond ring”
```

and expect those terms to occur together or in close sequence.

`phraseto_tsquery` and phrase operators can represent this intent.

Example:

```sql
SELECT *
FROM products
WHERE search_vector @@
      phraseto_tsquery('english', 'silver diamond ring');
```

This is different from:

```sql
silver & diamond & ring
```

The first expresses a proximity relationship.

The second expresses co-occurrence.

---

# 19. Prefix Search

FTS supports prefix-style query construction.

Example:

```sql
'term:*'::tsquery
```

More safely through controlled query generation:

```sql
to_tsquery('english', 'ring:*')
```

This can be useful for partial word endings such as:

```text
ring
rings
ringlet
```

But prefix search is not the same as arbitrary substring search.

It does not mean:

```text
contains these letters anywhere
```

---

# 20. FTS vs `LIKE` / `ILIKE`

| Requirement | Typical tool |
|---|---|
| exact equality | B-tree / `=` |
| prefix `abc%` | B-tree under appropriate conditions |
| arbitrary substring `%abc%` | `pg_trgm` often appropriate |
| lexical word search | FTS |
| stemming | FTS |
| phrase/proximity semantics | FTS |
| typo similarity | `pg_trgm` / other search approach |
| structured attribute lookup | relational columns / JSONB |

A common mistake is:

> “Full-text search is just a faster `ILIKE`.”

It is not.

It implements a different semantic model.

---

# 21. When `pg_trgm` Is Better

Trigram matching is useful for similarity and substring-oriented behavior, particularly spelling mistakes or user-entered names that do not normalize into useful FTS lexemes.

PostgreSQL documents combining `pg_trgm` with FTS to recognize misspelled words that would not match directly through lexical search. citeturn366847search8

A powerful production architecture can therefore be:

```text
query
 ├── lexical FTS
 └── fuzzy/trigram candidate expansion
            ↓
        combined ranking
```

Do not use FTS to solve every search problem.

---

# 22. Indexing Strategy

There are two traditional native index families for PostgreSQL FTS:

```text
GIN
GiST
```

PostgreSQL documents both for text search, with GIN generally preferred for regular text-search workloads. citeturn366847search6turn366847search4

## GIN

```sql
CREATE INDEX products_search_idx
ON products
USING gin (search_vector);
```

GIN is an inverted index and is designed for cases where composite values contain searchable elements. citeturn366847search4

## GiST

GiST can also index `tsvector`/`tsquery` and may offer different build/update/storage trade-offs.

GiST is a generalized, extensible balanced tree framework rather than a single fixed indexing algorithm. citeturn366847search2

### Practical default

For a heavily searched `tsvector` column:

```text
start with GIN
measure
only choose otherwise with workload evidence
```

---

# 23. Why an Index on the Raw Text Column Usually Does Not Solve FTS

This does not normally make FTS fast:

```sql
CREATE INDEX products_description_idx
ON products(description);
```

because your query is semantically operating on:

```sql
to_tsvector('english', description)
```

The useful index is aligned with the searchable representation:

```sql
CREATE INDEX products_fts_idx
ON products
USING gin (
    to_tsvector('english', coalesce(description, ''))
);
```

or preferably a materialized `tsvector` column when the search document becomes an important first-class projection.

---

# 24. Generated Column Pattern

For a deterministic search projection, a stored generated column can be attractive:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    description text,
    search_vector tsvector
      GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(name, '')), 'A')
        ||
        setweight(to_tsvector('english', coalesce(description, '')), 'B')
      ) STORED
);
```

Then:

```sql
CREATE INDEX products_search_idx
ON products
USING gin(search_vector);
```

This makes the search document part of the database's derived state.

### Architectural question

Would changing the search document require changing the table definition?

If yes, a generated column is schema-level policy.

If search composition changes often or depends on more complex orchestration, a maintained application/database projection may be more flexible.

---

# 25. Trigger-Maintained Search Vectors

Another approach is to maintain a `tsvector` column through a trigger.

Conceptually:

```text
INSERT/UPDATE source columns
          ↓
trigger
          ↓
rebuild search_vector
```

PostgreSQL provides trigger support for automatically updating text-search vectors. citeturn305741search1

### Trade-off

Advantages:

```text
centralized consistency
works for many writers
search vector persists
```

Costs:

```text
write overhead
trigger debugging complexity
hidden side effects
bulk-load implications
migration considerations
```

For teams that prioritize explicit dataflow, a visible derived-column strategy can be easier to reason about than complicated triggers.

---

# 26. Search Across Multiple Fields

A production search document commonly combines fields:

```sql
setweight(to_tsvector('english', coalesce(name, '')), 'A')
|| setweight(to_tsvector('english', coalesce(category, '')), 'B')
|| setweight(to_tsvector('english', coalesce(description, '')), 'C')
```

The key question is not:

> “Can we concatenate all text?”

It is:

> “What business concept does one searchable document represent?”

For a product table:

```text
product search document
```

For a support-ticket system:

```text
ticket search document
```

For a knowledge base:

```text
article search document
```

Do not accidentally combine unrelated tenant or security domains into one vector without preserving authorization boundaries.

---

# 27. Multi-Tenant Search Safety

Suppose your table contains:

```text
tenant_id
product_id
name
description
search_vector
```

Every search should preserve the tenant predicate:

```sql
SELECT id, name
FROM products
WHERE tenant_id = $1
  AND search_vector @@ $2::tsquery
ORDER BY id;
```

FTS must not become a side door around tenant isolation.

## Important lesson

An index can accelerate a query.

It does not replace authorization.

The database still needs correct predicates, RLS policies where applicable, and application-level authorization design.

---

# 28. Pagination

This is dangerous:

```sql
ORDER BY ts_rank(search_vector, query) DESC
OFFSET 50000
LIMIT 50;
```

Large offsets can become increasingly expensive because the system must still deal with rows before the requested page.

For high-scale search, investigate cursor/keyset-style pagination with a stable tie-breaker.

Example conceptual ordering:

```text
rank DESC,
id DESC
```

A stable cursor may encode the previous:

```text
rank + id
```

but ranking values need careful handling because floating-point score equality and changes in source data can complicate cursor semantics.

For search-heavy products, benchmark actual pagination behavior rather than assuming generic keyset patterns transfer perfectly.

---

# 29. Ranking Stability

This is unstable as a sole order:

```sql
ORDER BY ts_rank(search_vector, query) DESC
```

Two rows may have the same score.

Prefer:

```sql
ORDER BY
    ts_rank(search_vector, query) DESC,
    id DESC
```

The secondary key gives deterministic tie-breaking.

This matters for:

```text
pagination
caching
repeatable API output
test assertions
user experience
```

---

# 30. Highlighting with `ts_headline`

PostgreSQL provides `ts_headline` for producing document fragments with query terms highlighted. citeturn366847search0

Example:

```sql
SELECT ts_headline(
    'english',
    description,
    websearch_to_tsquery('english', 'silver ring')
)
FROM products
WHERE search_vector @@ websearch_to_tsquery('english', 'silver ring');
```

## Security warning

Do not treat `ts_headline` output as automatically safe HTML.

PostgreSQL explicitly warns that `ts_headline` output is not guaranteed to be safe for direct web inclusion and should not be used as an XSS defense. Sanitize untrusted content or sanitize the rendered result appropriately. citeturn366847search0

This is a real production security boundary:

```text
database highlighting
≠
HTML sanitization
```

---

# 31. `ts_headline` Performance

`ts_headline` operates on the original document to create the excerpt, not merely the compact `tsvector` summary, and can therefore be expensive. PostgreSQL recommends care in its use. citeturn366847search0

A high-volume search API should consider:

```text
first page
↓
small result set
↓
highlight only returned rows
```

rather than generating headlines for a giant candidate set.

# 32. Search Query Reuse

This pattern avoids repeated expression generation conceptually:

```sql
WITH q AS (
    SELECT websearch_to_tsquery('english', $1) AS query
)
SELECT
    p.id,
    p.name,
    ts_rank(p.search_vector, q.query) AS rank
FROM products p
CROSS JOIN q
WHERE p.tenant_id = $2
  AND p.search_vector @@ q.query
ORDER BY rank DESC, p.id DESC;
```

However, do not add a CTE merely for aesthetics. Query shape should remain planner-friendly and measurable.

# 33. Empty Queries

A search box can receive:

```text
""
```

or:

```text
"   "
```

Do not blindly issue a broad query.

Application behavior should explicitly define:

```text
empty input
malformed input
stop-word-only input
very long input
```

A safe product contract might be:

```text
empty → no search request / browse mode
stop-word-only → no-op or validation error
valid → FTS query
```

---

# 34. Stop-Word-Only Queries

A query may normalize into little or no useful searchable content.

For example, a language configuration can discard common terms.

Therefore, a search service should inspect query behavior and not assume:

```text
user typed 3 words
→ query contains 3 searchable lexemes
```

A robust API can detect an unusable query before executing an expensive search.

---

# 35. `querytree()` for Indexability Reasoning

PostgreSQL provides `querytree` for inspecting the indexable portion of a `tsquery`.

This is especially useful when debugging why a query behaves unexpectedly with an index.

The documentation notes that an empty result or just `T` indicates a non-indexable query representation. citeturn305741search9

Expert debugging asks:

```text
What is my tsquery?
What part is indexable?
What candidate set can the index identify?
What work remains after candidate generation?
```

# 36. EXPLAIN and Planner Analysis

Never assume:

> “I created a GIN index, therefore the query is fast.”

Run:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM products
WHERE search_vector @@ websearch_to_tsquery('english', 'silver ring');
```

Inspect:

```text
actual rows
planning time
execution time
buffer hits
buffer reads
index scan behavior
filter/recheck work
sort behavior
```

The question is not merely:

```text
“Did PostgreSQL use the index?”
```

It is:

```text
“Did the selected plan efficiently solve the actual workload?”
```

# 37. Why Search Can Still Be Slow with GIN

Possible causes:

```text
query matches huge portions of the table
ranking requires many candidates
highlighting touches large documents
sorting dominates
tenant predicate changes selectivity
returned page is too large
very common lexeme produces massive candidate sets
I/O/cache behavior is poor
```

The GIN lookup itself can be fast while the overall request remains slow.

Search latency is an end-to-end property.

---

# 38. Ranking Cost

Suppose:

```text
10 million documents
```

and the query matches:

```text
4 million documents
```

Even a highly effective inverted index cannot make ranking four million candidates free.

Therefore:

```text
index selectivity
×
candidate count
×
ranking cost
×
sort cost
```

becomes important.

### Production implication

Very common terms can be expensive.

You may need:

```text
query validation
minimum term length
business filters
category filters
availability filters
result caps
external search architecture
```

---

# 39. GIN Write Amplification

GIN indexes are powerful but write-heavy systems must account for index maintenance.

The GIN implementation includes concepts such as pending-list behavior and maintenance thresholds. PostgreSQL exposes tuning controls such as `gin_pending_list_limit`. citeturn366847search4

Therefore, when search columns are updated constantly:

```text
more writes
→ more index maintenance
→ more WAL / I/O pressure
→ possible impact on write latency
```

Do not treat the FTS index as free.

---

# 40. Large Documents

A giant document produces a giant search representation.

You should ask:

```text
How large can one searchable document become?
How many lexemes does it create?
How often does it change?
What is the update frequency?
How large is the GIN index?
```

PostgreSQL also documents hard limitations on text search structures, including a maximum `tsvector` length of less than 1 MB and limits on lexeme size, positions, and query-node counts. citeturn305741search4

These are not theoretical curiosities for systems that attempt to make entire huge records searchable as one vector.

---

# 41. Search Document Granularity

One of the most important architecture decisions is:

> What is one document?

Possible choices:

```text
one product
one product variant
one article
one support ticket
one comment
one order note
one customer profile
```

If an enormous parent object contains thousands of child objects, creating one giant vector can become inefficient and semantically ambiguous.

Often the better model is:

```text
one searchable entity
→ one search vector
```

Then join back to related entities when presenting results.

---

# 42. Search and Authorization

Search results must be filtered by authorization.

Bad architecture:

```text
FTS gets IDs
↓
application checks authorization after fetching everything
```

Safer architecture:

```text
FTS candidate generation
+
authorization/tenant predicates
+
visibility rules
↓
final results
```

The exact planner/index strategy may differ, but the security invariant must hold regardless of plan.

---

# 43. Search and Soft Deletes

A soft-deleted row should not magically become searchable just because its text remains indexed.

Example:

```sql
WHERE tenant_id = $1
  AND deleted_at IS NULL
  AND search_vector @@ $2
```

The derived representation should not be treated as a substitute for lifecycle state.

---

# 44. Search and Status Filters

Product search often requires:

```text
published
active
in stock
tenant visible
region allowed
```

Therefore the actual query is closer to:

```sql
SELECT ...
FROM products
WHERE tenant_id = $1
  AND status = 'active'
  AND search_vector @@ $2
ORDER BY ...;
```

A search index optimizes lexical candidate generation; it does not replace the rest of your relational model.

# 45. Search API Design for Node.js / NestJS

A clean API boundary might be:

```http
GET /products/search?q=silver%20ring&page=1&pageSize=20
```

Application pipeline:

```text
HTTP query
  ↓
validation
  ↓
normalization
  ↓
empty-query policy
  ↓
search query parser
  ↓
parameterized SQL
  ↓
authorization / tenant filter
  ↓
FTS
  ↓

  ↓
```

The application should not construct raw SQL by string interpolation.

Example with parameters conceptually:

```ts
const sql = `

  FROM products

    AND search_vector @@ websearch_to_tsquery('english', $2)

  LIMIT $3

```

The input value remains a parameter.

# 46. Search Query Normalization


# 47. Unicode and Language Strategy

Questions to answer:

Consider a jewellery platform:

# 49. SKU / Identifier Search

FTS is often a poor sole mechanism for identifiers.

Examples:

```text
SKU-AX-2049
```

Users may expect exact or prefix behavior.

A better design can use:

```text
exact B-tree lookup

+
trigram for fuzzy identifier/name matching where justified
```

# 50. Common Wrong Implementation #1 — `ILIKE` Everywhere

Naive:

```sql
WHERE name ILIKE '%' || $1 || '%'
   OR description ILIKE '%' || $1 || '%'
```

### Why it fails

```text
character semantics ≠ lexical semantics
no stemming
no phrase model
ranking is poor
can become expensive at scale
```

### Improved

```sql
search_vector @@ websearch_to_tsquery('english', $1)
```

with a suitable index.

---

# 51. Common Wrong Implementation #2 — Raw `to_tsquery(userInput)`

Naive:

```sql
to_tsquery('english', $1)
```

This is not inherently unsafe when parameterized, but it exposes PostgreSQL's query syntax to the user input and can reject malformed syntax.

For public web-style search:

```sql
websearch_to_tsquery('english', $1)
```

is often a better semantic boundary. PostgreSQL explicitly documents it as safe for raw web-search-style input and notes that it does not raise syntax errors. citeturn305741search13

---

# 52. Common Wrong Implementation #3 — Indexing Raw Text Only

Naive:

```sql
CREATE INDEX products_name_idx
ON products(name);
```

and expecting it to accelerate:

```sql
WHERE to_tsvector('english', name) @@ ...
```

The searchable expression and index representation are mismatched.

Build the appropriate expression index or materialized search-vector index.

---

# 53. Common Wrong Implementation #4 — One Giant Search Vector

Naive:

```text
customer + orders + invoices + notes + audit logs + products
```

all concatenated into one giant document.

### Why it fails

```text
unclear ranking
huge vectors
poor document boundaries
authorization complexity
unbounded growth
hard updates
ambiguous search semantics
```

The searchable document should correspond to a coherent business entity.

---

# 54. Common Wrong Implementation #5 — Ranking Everything After Returning Everything

Naive:

```sql
SELECT ...
FROM products
WHERE search_vector @@ $1
ORDER BY ts_rank(search_vector, $1) DESC;
```

This may be fine for moderate candidate sets.

But when the query is broad, ranking and sorting a huge candidate set can dominate.

The real optimization question becomes:

```text
How do we reduce candidate count before expensive scoring?
```

Potential filters include:

```text
tenant
status
category
availability
date range
region
price range
```

---

# 55. Common Wrong Implementation #6 — Highlighting Every Candidate

Naive:

```text
every matching row
→ ts_headline
→ huge result set
```

`ts_headline` can be expensive and is designed for presentation snippets, not candidate generation. PostgreSQL explicitly warns about its document-processing cost. citeturn366847search0

Generate snippets only for the rows you intend to return.

---

# 56. Common Wrong Implementation #7 — Treating FTS as an Authorization Layer

Wrong:

```text
search all rows
→ filter sensitive rows in application memory
```

Correct:

```text
search
+
visibility predicate
+
tenant predicate
+
authorization model
```

Security must survive plan changes and future clients.

# 57. Common AI/Vibe-Coding Failure Patterns

AI-generated PostgreSQL search code often looks syntactically plausible but fails architecturally.

### Failure A — `ILIKE` presented as “full-text search”

Symptom:

```sql
ILIKE '%query%'
```

Claim:

> “This provides full-text search.”

Reality:

It is substring matching, not PostgreSQL FTS semantics.

### Failure B — Creating a GIN index on a column that is not the search representation

Symptom:

```sql
CREATE INDEX ... USING GIN(description);
```

without verifying the operator class and actual query expression.

### Failure C — Raw user query syntax

Symptom:

```sql
to_tsquery('english', userInput)
```

without deciding whether raw PostgreSQL search syntax is actually part of the product contract.

### Failure D — No query-length limits

A search endpoint can become a resource-amplification endpoint when extremely large queries are accepted.

### Failure E — Ranking without deterministic tie-breaking

This produces unstable pages and flaky tests.

### Failure F — Highlighting untrusted content directly into HTML

This can create XSS exposure. PostgreSQL explicitly warns about `ts_headline` output safety. citeturn366847search0

### Failure G — “GIN makes it O(1)”

No.

Candidate generation, rechecks, ranking, sorting, visibility filters, and I/O still matter.

# 60. When to Leave PostgreSQL FTS

PostgreSQL FTS is powerful, but an external search engine may become appropriate when requirements demand capabilities such as:

```text
complex distributed relevance
massive multi-node search clusters
advanced typo/fuzzy behavior
semantic/vector retrieval pipelines
specialized autocomplete
complex faceting at very large scale
search-specific horizontal scaling
rich ranking experimentation
```

The key decision is workload-driven.

Do not introduce Elasticsearch/OpenSearch/Solr merely because:

> “Real companies use search engines.”

Likewise, do not force PostgreSQL FTS to become a distributed search platform when your workload does not justify it.

# 67. Slow Search Diagnosis Workflow

When search latency rises:

```text
1. Reproduce exact query
2. Capture normalized tsquery
3. Run EXPLAIN (ANALYZE, BUFFERS)
4. Inspect candidate count
5. Separate index lookup from ranking/sort cost
6. Check filters and selectivity
7. Check highlight cost
8. Check cache/I/O
9. Check GIN size and maintenance
10. Compare with workload history
```

Do not immediately:

```text
add random index
increase memory
rewrite SQL
move to Elasticsearch
```

Measure first.

Symptom:


```text

ranking dominates
sort dominates
```

The root cause is not:

```text
“GIN is slow.”
```

It is:

```text
query selectivity is low
→ huge candidate set
→ expensive ranking/sort
```

Potential responses:

```text
require/encourage additional filters
adjust product ranking architecture
use business constraints
consider autocomplete/facet design
cache popular searches where valid
evaluate external search if scale requires it
```

# 69. Performance Decision Matrix

| Situation | Likely direction |
|---|---|
| simple lexical search, moderate data | PostgreSQL FTS + GIN |
| highly write-heavy searchable table | benchmark GIN maintenance carefully |
| fuzzy names | FTS + `pg_trgm` |
| exact SKU lookup | B-tree |
| complex JSON attribute filter | JSONB indexes / relational columns |
| enormous documents | reconsider document granularity |
| multilingual advanced search | specialized configurations or external engine |
| huge distributed search workload | evaluate dedicated search system |
| very common terms | candidate-reduction strategy |

# 76. Final Engineering Principles

### Principle 1

**FTS is a semantic system, not a faster `LIKE`.**

### Principle 2

**Search correctness begins with the text-search configuration and document model.**

### Principle 3

**The search vector is a derived representation; treat its construction as an explicit data contract.**

### Principle 4

**Use `websearch_to_tsquery` or another controlled parser at a public search boundary rather than blindly exposing raw `tsquery` syntax.** citeturn305741search13

### Principle 5

**GIN is normally the starting point for regular PostgreSQL FTS workloads, but the workload determines whether it is sufficient.** citeturn366847search6turn366847search4

### Principle 6

**A fast index lookup does not guarantee a fast search request. Candidate count, ranking, sorting, filtering, I/O, and presentation all matter.**

### Principle 7

**FTS must remain inside the same authorization and tenant-isolation model as the rest of the application.**

### Principle 8

**`ts_headline` is presentation functionality, not an HTML security mechanism.** citeturn366847search0

### Principle 9

**Measure search quality and latency independently.**

### Principle 10

**Do not introduce a dedicated search engine because it sounds more scalable; introduce it when the workload and product requirements justify the architectural cost.**
