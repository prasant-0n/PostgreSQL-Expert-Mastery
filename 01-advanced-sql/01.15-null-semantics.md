# Chapter 01.15 — NULL Semantics

> **Phase 01 — Advanced SQL**  
> **Level:** L0–L7 progression  
> **Primary theme:** Missingness, unknown truth, three-valued logic, predicate semantics, aggregates, constraints, joins, indexes, uniqueness, ordering, application APIs, and production correctness.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to reason about `NULL` without relying on memorized exceptions.

You should be able to:

- explain what `NULL` represents and what it does **not** represent;
- distinguish SQL's `TRUE`, `FALSE`, and `UNKNOWN` outcomes;
- predict the result of boolean expressions involving `NULL`;
- correctly use `IS NULL`, `IS NOT NULL`, `IS DISTINCT FROM`, and `IS NOT DISTINCT FROM`;
- understand why `= NULL` and `<> NULL` do not test missingness;
- predict `WHERE`, `JOIN`, `HAVING`, `CASE`, `CHECK`, and aggregate behavior in the presence of `NULL`;
- reason about `NOT IN` and why `NULL` can invalidate an apparently obvious predicate;
- understand how `NULL` interacts with `UNIQUE`, composite keys, partial indexes, ordering, and constraints;
- choose between `COALESCE`, explicit predicates, `NULLIF`, sentinel values, and schema redesign;
- diagnose bugs caused by accidental conversion of “unknown” into a business value;
- review SQL and ORM-generated SQL for `NULL` correctness;
- design APIs, reports, financial calculations, and multi-tenant queries that preserve the meaning of absence.

The expert target is not “knowing that `NULL` is special.” The target is being able to derive the correct behavior from first principles.

---

## 2. The Core Mental Model

The most important rule is:

> **`NULL` is not a value that means “nothing.” It represents the absence of a known value in a SQL expression context.**

That distinction matters because SQL comparisons normally answer whether two known values relate in a particular way. When one operand is unknown, SQL cannot generally establish `TRUE` or `FALSE`; the predicate can become `UNKNOWN`.

Think in terms of:

```text
Known value ──comparison── Known value
      │
      └──────────────► TRUE or FALSE

Unknown / NULL ──comparison── anything
      │
      └──────────────► usually UNKNOWN
```

The key is that `UNKNOWN` is a logical result, not a third stored value sitting inside the row.

---

## 3. Three Levels of Definition

### 3.1 Simple Definition

`NULL` represents a missing, unavailable, inapplicable, or otherwise unknown value.

### 3.2 Engineering Definition

`NULL` is SQL's marker for the absence of a known scalar value. Expressions that depend on that unknown value often evaluate to `NULL` or predicates evaluate to `UNKNOWN`.

### 3.3 Expert Definition

`NULL` introduces non-classical semantics into SQL expressions and predicates. Query correctness therefore depends on the distinction among:

- value existence;
- value equality;
- truth of a predicate;
- applicability of a condition;
- and whether a business rule treats missingness as an allowed state.

A strong database design makes these meanings explicit rather than hiding them behind sentinels.

---

## 4. First Principles: Why SQL Needs NULL

Suppose a customer has a `date_of_birth` column.

These are not necessarily equivalent:

```text
1978-04-12      → known date
NULL            → date is not known / not supplied / not applicable
'1900-01-01'    → a real date value
```

Using a fake date would collapse two different concepts:

```text
unknown
vs.
known and equal to sentinel
```

That creates downstream ambiguity in filtering, reporting, averages, ranges, sorting, and constraints.

`NULL` exists partly so that the database can preserve the distinction.

---

## 5. NULL Is Not the Same as These Concepts

Do not casually treat `NULL` as interchangeable with:

| Concept | Meaning | Same as NULL? |
|---|---|---|
| `0` | numeric zero | No |
| `''` | empty string | No |
| `'unknown'` | literal text | No |
| `'N/A'` | literal marker | No |
| `false` | known boolean false | No |
| empty array | known array with zero elements | No |
| missing JSON key | structural absence inside JSON | No, not automatically |
| database row not found | no row exists | No |

The distinction between **no row** and **row exists with a NULL attribute** is especially important in joins and APIs.

---

## 6. SQL's Three-Valued Logic

SQL predicates can produce three logical outcomes:

```text
TRUE
FALSE
UNKNOWN
```

In a `WHERE` clause, only rows whose predicate evaluates to `TRUE` are retained. Both `FALSE` and `UNKNOWN` are filtered out.

This is the source of many subtle bugs.

### Example

```sql
SELECT *
FROM customers
WHERE phone <> '9999999999';
```

For a row with:

```text
phone = '8888888888'  → TRUE
phone = '9999999999'  → FALSE
phone = NULL          → UNKNOWN
```

The `NULL` phone row is not returned.

The expression did **not** prove that the phone was different. It failed to establish the comparison.

---

## 7. Truth Tables

### 7.1 NOT

```text
NOT TRUE     = FALSE
NOT FALSE    = TRUE
NOT UNKNOWN  = UNKNOWN
```

### 7.2 AND

| A | B | A AND B |
|---|---|---|
| TRUE | TRUE | TRUE |
| TRUE | FALSE | FALSE |
| TRUE | UNKNOWN | UNKNOWN |
| FALSE | TRUE | FALSE |
| FALSE | FALSE | FALSE |
| FALSE | UNKNOWN | FALSE |
| UNKNOWN | TRUE | UNKNOWN |
| UNKNOWN | FALSE | FALSE |
| UNKNOWN | UNKNOWN | UNKNOWN |

A useful expert shortcut:

```text
AND sees a FALSE → result can be FALSE immediately.
AND with no FALSE but an UNKNOWN → UNKNOWN.
AND of all TRUE → TRUE.
```

### 7.3 OR

| A | B | A OR B |
|---|---|---|
| TRUE | TRUE | TRUE |
| TRUE | FALSE | TRUE |
| TRUE | UNKNOWN | TRUE |
| FALSE | TRUE | TRUE |
| FALSE | FALSE | FALSE |
| FALSE | UNKNOWN | UNKNOWN |
| UNKNOWN | TRUE | TRUE |
| UNKNOWN | FALSE | UNKNOWN |
| UNKNOWN | UNKNOWN | UNKNOWN |

Useful shortcut:

```text
OR sees a TRUE → result can be TRUE immediately.
OR with no TRUE but an UNKNOWN → UNKNOWN.
OR of all FALSE → FALSE.
```

## 8. Why `= NULL` Is Wrong

This is one of the most important rules in SQL:

```sql
WHERE email = NULL
```

is not a valid test for missingness.

Conceptually:

```text
email = NULL
```

asks SQL to compare a known-or-unknown expression to an unknown value. The result is not `TRUE` when `email` is null; it is `UNKNOWN`.

Use:

```sql
WHERE email IS NULL
```

or:

```sql
WHERE email IS NOT NULL
```

### The rule

> **Comparison operators answer questions about values. `IS NULL` answers a question about nullness.**

---

## 9. `IS NULL` and `IS NOT NULL`

Correct:

```sql
SELECT *
FROM users
WHERE deleted_at IS NULL;
```

Incorrect:

```sql
SELECT *
FROM users
WHERE deleted_at = NULL;
```

This distinction appears everywhere:

- soft deletes;
- optional foreign keys;
- nullable dates;
- customer profile fields;
- partial workflows;
- audit fields;
- nullable configuration;
- optional tenant relationships.

---

## 10. `IS DISTINCT FROM`

Normal equality is null-sensitive:

```sql
NULL = NULL
```

does not produce `TRUE`.

PostgreSQL provides:

```sql
IS DISTINCT FROM
```

which treats `NULL` as a comparable state.

Conceptually:

```text
value A        value B        IS DISTINCT FROM
------------------------------------------------
10             10             FALSE
10             20             TRUE
10             NULL           TRUE
NULL           10             TRUE
NULL           NULL           FALSE
```

This is extremely useful when business semantics are:

> “Treat two missing values as equal for comparison purposes.”

Example:

```sql
UPDATE customer_profile p
SET phone = s.phone
FROM staging_profile s
WHERE p.customer_id = s.customer_id
  AND p.phone IS DISTINCT FROM s.phone;
```

This avoids both:

- unnecessary updates when both are `NULL`;
- missed updates when one side is `NULL`.

The opposite operator is:

```sql
IS NOT DISTINCT FROM
```

which behaves like null-safe equality.

---

## 11. Why This Matters for UPDATEs

Naive:

```sql
UPDATE users
SET phone = $1
WHERE user_id = $2
  AND phone <> $1;
```

Suppose:

```text
current phone = NULL
new phone     = '123'
```

Then:

```text
NULL <> '123' → UNKNOWN
```

The update does not happen.

Correct null-aware comparison:

```sql
UPDATE users
SET phone = $1
WHERE user_id = $2
  AND phone IS DISTINCT FROM $1;
```

This pattern is particularly valuable in synchronization and change-detection pipelines.

---

## 12. NULL and CASE

### Simple CASE

```sql
CASE status
    WHEN 'paid' THEN 1
    WHEN 'pending' THEN 2
    ELSE 3
END
```

Do not assume a `NULL` status magically matches another `NULL` branch by equality semantics.

When explicit null testing matters, use searched `CASE`:

```sql
CASE
    WHEN status IS NULL THEN 'missing'
    WHEN status = 'paid' THEN 'paid'
    ELSE 'other'
END
```

### Expert rule

When null behavior is business-critical, prefer explicit predicates over relying on implicit equality semantics.

---

## 13. NULL and COALESCE

`COALESCE` returns the first non-null argument:

```sql
SELECT COALESCE(nickname, display_name, email)
FROM users;
```

Conceptually:

```text
nickname known?    yes → nickname
                    no
                       ↓
display_name known? yes → display_name
                    no
                       ↓
email
```

### The dangerous mistake

`COALESCE` is not a universal “fix NULL” operator.

Bad:

```sql
COALESCE(balance, 0)
```

may be correct in one report and incorrect in another.

You must first ask:

> Does `NULL` mean “zero,” “unknown,” “not applicable,” or “data missing” in this business domain?

Replacing unknown with zero is a semantic transformation, not a formatting operation.

---

## 14. NULL and NULLIF

`NULLIF(a, b)` returns `NULL` when `a = b`; otherwise it returns `a`.

Classic example:

```sql
SELECT revenue / NULLIF(order_count, 0)
FROM metrics;
```

This prevents division by zero by converting a zero denominator into `NULL`.

But again, the resulting `NULL` has meaning:

```text
average unavailable / undefined
```

It does not mean the average is actually zero.

---

## 15. NULL Propagation in Expressions

Many ordinary scalar expressions propagate `NULL`.

Example:

```sql
SELECT 10 + NULL;
```

returns `NULL`.

Likewise:

```sql
SELECT 'hello' || NULL;
```

produces a null result under normal PostgreSQL concatenation semantics.

Mental model:

```text
unknown input
     ↓
dependent expression
     ↓
often unknown result
```

This is why one nullable column can silently propagate through an entire computed expression.

---

## 16. NULL in WHERE

These are not equivalent:

```sql
WHERE amount = 100
```

```sql
WHERE amount <> 100
```

The second does **not** mean “every row whose amount is not 100.” It means rows where the comparison can be established as true.

For:

```text
amount = NULL
```

we get:

```text
amount = 100  → UNKNOWN
amount <> 100 → UNKNOWN
```

Therefore both predicates exclude the row.

---

## 17. The Classic `NOT IN` Trap

Consider:

```sql
SELECT *
FROM customers
WHERE customer_id NOT IN (
    SELECT customer_id
    FROM blocked_customers
);
```

This can become surprising if the subquery contains `NULL`.

Suppose the set is:

```text
{10, 20, NULL}
```

For a customer `30`, the predicate conceptually requires checking:

```text
30 <> 10
AND 30 <> 20
AND 30 <> NULL
```

The final comparison is `UNKNOWN`.

So the whole `AND` expression becomes `UNKNOWN`, and the row is not returned.

### Safer anti-membership pattern

When the intent is relational anti-existence, prefer:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM blocked_customers b
    WHERE b.customer_id = c.customer_id
)
```

The exact choice depends on constraints and data model, but `NOT EXISTS` often communicates the intended semantics more directly and avoids the `NULL` trap.

---

## 18. `IN` Is Also About Three-Valued Logic

`IN` is not merely a convenient list syntax.

Conceptually:

```sql
x IN (a, b, c)
```

behaves like a sequence of equality comparisons combined with `OR`-style semantics.

Therefore a list containing `NULL` can make results become `UNKNOWN` when no definite match exists.

Do not reason about `IN` only as a set-membership operation. Reason about its null semantics too.

---

## 19. NULL in JOINs

Consider:

```sql
SELECT *
FROM orders o
JOIN customers c
  ON o.referrer_id = c.id;
```

If:

```text
referrer_id = NULL
```

then:

```text
NULL = c.id → UNKNOWN
```

The row does not satisfy the inner join predicate.

In a `LEFT JOIN`, the order survives because the left row is preserved, but the right-side customer columns become `NULL`.

This gives two different meanings that must not be confused:

```text
customer row exists, but attribute is NULL
vs.
no matching customer row was found
```

A later transformation can easily collapse these states and create a reporting bug.

---

## 20. ON vs WHERE with NULL

Consider:

```sql
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
WHERE o.status = 'paid';
```

The `WHERE` condition eliminates rows where `o.status` is `NULL`, effectively removing customers without matching paid orders from the result.

Compare with:

```sql
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.status = 'paid';
```

Now the left customer row can remain even when there is no paid order.

The difference is not merely stylistic. It changes the result relation.

---

## 21. NULL in Aggregates

Most ordinary aggregates ignore `NULL` inputs.

For example:

```sql
SELECT AVG(amount)
FROM payments;
```

does not average `NULL` amounts as zeros.

Likewise:

```sql
COUNT(amount)
```

counts non-null values, whereas:

```sql
COUNT(*)
```

counts rows.

Therefore:

```text
COUNT(*)
vs.
COUNT(column)
```

ask different questions.

### Important consequence

If five rows exist and only three have a known amount:

```text
COUNT(*)      = 5
COUNT(amount) = 3
```

Do not substitute one for the other without knowing the business question.

---

## 22. SUM and Empty Input

An empty aggregate input is not always equivalent to zero.

For business calculations, this distinction matters:

```text
no rows
vs.
rows whose amounts sum to zero
```

For example, an invoice report might need to distinguish:

```text
No payments recorded
vs.
Payments recorded and net amount is 0
```

Blindly writing:

```sql
COALESCE(SUM(amount), 0)
```

can erase that distinction.

Use it when the business semantics explicitly require “no aggregate input means zero.”

---

## 23. NULL and COUNT

These are common interview and production questions:

```sql
COUNT(*)
COUNT(column)
COUNT(DISTINCT column)
```

For:

```text
10
10
NULL
20
```

we have conceptually:

```text
COUNT(*)              = 4
COUNT(column)         = 3
COUNT(DISTINCT column)= 2
```

The null marker participates in neither the ordinary non-null count nor ordinary distinct-value count in the same way as actual values.

---

## 24. NULL and DISTINCT

`NULL` has special treatment in SQL operations such as `DISTINCT` and grouping.

You should distinguish:

```text
comparison equality
```

from:

```text
deduplication / grouping identity
```

Two rows with `NULL` in the same grouped column can belong to the same grouping bucket even though:

```sql
NULL = NULL
```

does not evaluate to `TRUE`.

This is a crucial expert principle:

> **Equality for predicates and identity for grouping/deduplication are not the same semantic operation.**

---

## 25. NULL in GROUP BY

Example:

```sql
SELECT region, COUNT(*)
FROM customers
GROUP BY region;
```

All rows with `region IS NULL` can form the same group.

This often surprises developers who learned only the simple rule “NULL never equals NULL.”

The deeper model is:

```text
Predicate equality semantics
≠
Grouping equivalence semantics
```

---

## 26. NULL and HAVING

Because `HAVING` is a predicate, `UNKNOWN` behaves like a filtered-out result.

Example:

```sql
HAVING SUM(amount) > 1000
```

If the aggregate result is `NULL`, the comparison produces `UNKNOWN`, so that group is removed.

This can become relevant for groups containing only `NULL` values.

---

## 27. NULL in CHECK Constraints

A common misconception is:

> “A CHECK expression must always be TRUE for the row to be accepted.”

PostgreSQL follows SQL semantics where a `CHECK` condition passes when it is not `FALSE`; this means `UNKNOWN` can permit a row.

Example:

```sql
CHECK (price > 0)
```

If `price` is nullable:

```text
price = 10   → TRUE  → passes
price = -5   → FALSE → rejected
price = NULL  → UNKNOWN → passes
```

Therefore:

```sql
CHECK (price > 0)
```

does **not** mean:

> price must be a positive number.

It means:

> price, when known, must be positive.

If the domain requires a value, combine with `NOT NULL`:

```sql
price numeric NOT NULL,
CHECK (price > 0)
```

---

## 28. NULL and UNIQUE Constraints

A nullable unique column is not the same as a non-null unique column.

PostgreSQL's unique semantics allow multiple nulls under its default behavior because nulls are not treated as ordinary equal values for uniqueness enforcement.

Example conceptually:

```text
email
----------------
a@example.com
b@example.com
NULL
NULL
```

can satisfy a normal unique constraint.

This is often correct for optional attributes.

But sometimes the business requirement is:

> “At most one row may have a missing value.”

That is a different constraint and should be designed explicitly.

---

## 29. NULLS NOT DISTINCT in PostgreSQL

PostgreSQL supports a way to make unique enforcement treat nulls as not distinct.

Example:

```sql
CREATE TABLE settings (
    tenant_id bigint,
    external_key text,
    UNIQUE NULLS NOT DISTINCT (tenant_id, external_key)
);
```

Now two rows with the same `tenant_id` and both `external_key = NULL` conflict.

This is powerful, but the decision should be driven by the business identity model.

---

## 30. Composite UNIQUE Constraints

For composite uniqueness:

```sql
UNIQUE (tenant_id, email)
```

you must reason about null behavior across the full key.

Questions to ask:

1. Is every key component required?
2. Is “unknown email” a legitimate state?
3. Can multiple rows exist with the same tenant and unknown email?
4. Does a null-safe identity rule better represent the business?
5. Would a partial unique index communicate the business rule more precisely?

Never choose the constraint from syntax alone.

---

## 31. NULL and Partial Indexes

Partial indexes often encode semantic predicates such as:

```sql
CREATE UNIQUE INDEX users_active_email_uq
ON users (tenant_id, email)
WHERE deleted_at IS NULL;
```

This means uniqueness is enforced only for rows satisfying the predicate.

A nullable email and a soft-delete condition can therefore combine into nuanced behavior.

The important point is:

> **A partial index is a constraint/index over a selected population, not over the entire table.**

---

## 32. NULL Ordering

Ordering with nullable values requires explicit thought.

PostgreSQL supports:

```sql
ORDER BY score NULLS FIRST;
```

and:

```sql
ORDER BY score NULLS LAST;
```

Do not assume that application-level sorting and database sorting naturally agree when nulls are present.

This matters for:

- pagination;
- ranking;
- top-N queries;
- user-visible lists;
- indexes and ordered scans.

For deterministic APIs, include explicit null ordering when it affects the contract.

---

## 33. NULL and Pagination

Suppose an API uses:

```sql
ORDER BY priority DESC, created_at DESC, id DESC
```

If `priority` or `created_at` can be `NULL`, keyset pagination must define precisely where nulls belong.

Otherwise:

- page boundaries can become difficult to reason about;
- cursor predicates can omit or duplicate rows;
- the API's “next page” behavior can be unstable.

A production cursor contract should encode ordering semantics explicitly.

---

## 34. NULL and Keyset Pagination

Consider a cursor built from:

```text
(priority, created_at, id)
```

If `priority` is nullable, a simple predicate such as:

```sql
WHERE (priority, created_at, id) < ($1, $2, $3)
```

requires careful validation of null semantics.

A robust design may instead:

- make the sort key non-null;
- materialize a deterministic sort expression;
- split nullable and non-null populations explicitly;
- or define a cursor encoding that captures the null state.

Pagination bugs caused by nulls are often mistaken for frontend bugs when the real problem is an underspecified database ordering contract.

---

## 35. NULL and Boolean Columns

A nullable boolean is a three-state domain:

```text
TRUE
FALSE
NULL
```

That may be exactly what the business requires:

```text
approved
rejected
not yet reviewed
```

But it can also be accidental schema ambiguity.

Ask:

> Is this really a 3-state domain, or should the column simply be `NOT NULL DEFAULT false`?

Do not make every boolean nullable by default.

---

## 36. NULL as a State Machine Signal

Nullable timestamps are often used intentionally:

```text
approved_at IS NULL
approved_at IS NOT NULL
```

This can be a valid state transition representation.

But if a workflow requires multiple explicit states, relying on a single nullable column can become ambiguous.

Compare:

```text
status = 'pending'|'approved'|'rejected'
```

with:

```text
approved_at NULL/non-NULL
rejected_at NULL/non-NULL
```

The second can create impossible combinations unless constrained.

---

## 37. NULL in Financial Systems

Financial systems are particularly sensitive to null semantics.

Consider:

```text
amount = NULL
amount = 0
```

They may mean:

```text
unknown amount
vs.
known zero amount
```

Those are economically different.

Similarly:

```text
SUM(transactions) = NULL
```

may mean no qualifying transactions, whereas:

```text
SUM(transactions) = 0
```

may mean known net zero.

Before using `COALESCE`, define the accounting meaning.

---

## 38. NULL in Temporal Data

A nullable timestamp can mean:

- event has not happened;
- timestamp was not recorded;
- event is not applicable;
- data is incomplete.

These meanings have very different operational consequences.

For example:

```sql
WHERE shipped_at IS NULL
```

might mean “not shipped yet,” but only if the domain guarantees that `NULL` is not also used for “shipping data missing.”

A production design should prevent one marker from carrying multiple incompatible meanings.

---

## 39. NULL and Multi-Tenant Systems

Consider:

```sql
SELECT *
FROM invoices
WHERE tenant_id = $1
  AND deleted_at IS NULL;
```

Now add a nullable business column:

```sql
AND external_ref <> $2
```

Rows where `external_ref IS NULL` silently disappear.

In a shared database, this can become a tenant-visible correctness bug even though there is no SQL error.

Expert tenant review therefore includes:

```text
tenant predicate
+ null semantics
+ soft-delete semantics
+ join semantics
+ cursor semantics
```

---

## 40. Sentinel Values vs NULL

A sentinel value is a real stored value chosen to mean something special:

```text
-1
1900-01-01
'UNKNOWN'
999999
```

This can be attractive because ordinary comparisons still work, but the cost is semantic pollution.

### Sentinels create risks

- validation ambiguity;
- accidental aggregation;
- incorrect ordering;
- incorrect range predicates;
- accidental display to users;
- impossible combinations hidden as “valid” values;
- migration complexity.

Use a sentinel only when the domain genuinely treats it as a first-class value.

---

## 41. JSON NULL vs SQL NULL

With JSON/JSONB, you can encounter multiple notions of absence.

For example:

```json
{}
```

has a missing key, while:

```json
{"phone": null}
```

has an explicit JSON `null` value.

Those are not necessarily equivalent to SQL:

```sql
phone IS NULL
```

When working with JSONB, distinguish:

```text
SQL NULL
JSON null
missing JSON key
empty string
empty object
```

An API PATCH operation often needs to distinguish:

```text
field omitted → leave unchanged
field present with null → clear field
field present with value → replace field
```

That is a domain-level distinction, not merely a serialization detail.

---

## 42. NULL and Outer Joins: Provenance Matters

Suppose:

```sql
SELECT c.id, o.status
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id;
```

A result row with:

```text
status = NULL
```

could mean either:

1. customer has an order whose status itself is `NULL`;
2. customer has no matching order and the outer join synthesized the null-extended columns.

If the query later needs to distinguish them, select a non-nullable key from the right side:

```sql
SELECT
    c.id,
    o.id AS order_id,
    o.status
```

Then:

```text
order_id IS NULL → no joined order
order_id IS NOT NULL + status IS NULL → order exists, status missing
```

This is an extremely important production reasoning technique.

---

## 43. Nullability as Information

A nullable column adds information to a schema.

Instead of:

```text
Known domain D
```

you effectively have:

```text
D + absence/unknown state
```

Therefore making a column nullable is not free.

Every nullable attribute creates additional states that queries, application code, APIs, tests, and constraints must reason about.

This is why unnecessary nullability increases cognitive and operational complexity.

---

## 44. Normalization of Missingness

Before adding `NULL`, decide why the value can be absent.

A useful classification is:

```text
Unknown
Not applicable
Not yet occurred
Not collected
Intentionally withheld
```

If the domain needs to distinguish these states, one nullable column may be insufficient.

Possible alternatives include:

- explicit status columns;
- state machines;
- separate event tables;
- availability flags;
- typed status codes;
- normalized child entities.

`NULL` is a mechanism, not a complete business-state model.

---

## 45. Wrong Implementations

### Mistake 1

```sql
WHERE deleted_at = NULL
```

**Your assumption:** equality works for nulls.  
**Problem:** result is `UNKNOWN`.  
**Why it fails:** null is not a known value.  
**Correct mental model:** use `IS NULL`.  
**Production consequence:** soft-deleted or active rows can be misclassified.  
**Better approach:** `WHERE deleted_at IS NULL`.

### Mistake 2

```sql
WHERE status <> 'cancelled'
```

**Your assumption:** this means every status except cancelled.  
**Problem:** rows with `status IS NULL` disappear.  
**Correct mental model:** “not cancelled” and “status is known and not cancelled” may be different requirements.  
**Better approach:** make the requirement explicit.

### Mistake 3

```sql
WHERE id NOT IN (SELECT id FROM blacklist)
```

**Your assumption:** simple anti-membership.  
**Problem:** a null in the subquery can produce `UNKNOWN`.  
**Better approach:** prefer `NOT EXISTS` when that matches the intended relational semantics.

### Mistake 4

```sql
COALESCE(amount, 0)
```

**Your assumption:** null is harmlessly replaced.  
**Problem:** unknown becomes known zero.  
**Better approach:** only coalesce when business semantics justify it.

### Mistake 5

```sql
CHECK (quantity > 0)
```

**Your assumption:** quantity must be positive.  
**Problem:** null quantity can satisfy the check because the predicate is not `FALSE`.  
**Better approach:** pair with `NOT NULL` when required.

---

## 46. AI / Vibe-Coding Failure Patterns

AI-generated SQL frequently makes these mistakes:

```sql
WHERE column = NULL
```

or:

```sql
COALESCE(value, 0)
```

without understanding the domain.

Another common generated pattern is:

```sql
WHERE x NOT IN (...)
```

without checking whether the inner column is nullable.

Generated SQL also commonly moves conditions between `ON` and `WHERE` without recognizing that this changes outer-join semantics.

### AI code-review checklist

Ask:

1. Is the column nullable?
2. What exactly does NULL mean in this domain?
3. Is the predicate trying to test missingness, equality, or inequality?
4. Could `UNKNOWN` eliminate rows?
5. Could `NOT IN` be null-sensitive?
6. Does `COALESCE` change business meaning?
7. Does an outer join synthesize nulls here?
8. Does the API distinguish missing from explicit null?

## 47. PostgreSQL-Specific Engineering Considerations

PostgreSQL supports null-aware comparison operators and explicit null ordering, giving you stronger tools than simply writing `IS NULL` everywhere.

Important tools to know:

```sql
IS NULL
IS NOT NULL
IS DISTINCT FROM
IS NOT DISTINCT FROM
ORDER BY ... NULLS FIRST
ORDER BY ... NULLS LAST
UNIQUE NULLS NOT DISTINCT (...)
```

These features allow the schema and query to express business semantics more precisely.

Use the feature that matches the invariant rather than forcing every problem into ordinary equality.

## 48. Debugging Framework for NULL Bugs

When a query unexpectedly loses rows, use this sequence:

```text
1. Identify nullable columns.
2. Identify every predicate involving them.
3. Evaluate each predicate for NULL explicitly.
4. Check AND / OR propagation.
5. Check OUTER JOIN null-extension.
6. Check NOT IN / IN.
7. Check aggregate input semantics.
8. Check COALESCE / NULLIF transformations.
9. Check GROUP BY / DISTINCT behavior.
10. Compare business requirement with SQL semantics.
```

Do not debug only from sample rows. Construct a minimal matrix containing:

```text
known value
matching value
non-matching value
NULL
```

and evaluate the query against each case.

## 49. A NULL Test Matrix

For a nullable column `x` and target `10`:

| x | `x = 10` | `x <> 10` | `x IS NULL` | `x IS DISTINCT FROM 10` |
|---|---|---|---|---|
| 10 | TRUE | FALSE | FALSE | FALSE |
| 20 | FALSE | TRUE | FALSE | TRUE |
| NULL | UNKNOWN | UNKNOWN | TRUE | TRUE |

This table is worth memorizing conceptually, not mechanically.

## 50. Production Pattern: Null-Safe Synchronization

Suppose an external system feeds customer data.

Naive:

```sql
UPDATE customers c
SET phone = s.phone,
    name = s.name
FROM staging_customers s
WHERE c.external_id = s.external_id
  AND (c.phone <> s.phone OR c.name <> s.name);
```

This can miss changes involving nulls.

Better:

```sql
UPDATE customers c
SET phone = s.phone,
    name = s.name
FROM staging_customers s
WHERE c.external_id = s.external_id
  AND (
      c.phone IS DISTINCT FROM s.phone
      OR c.name IS DISTINCT FROM s.name
  );
```

Now the comparison expresses the actual requirement:

> update when the stored state differs from the incoming state, including null transitions.

---

## 51. Production Pattern: Optional Filter Parameters

Application code often generates optional filters.

Bad mental model:

```sql
WHERE status = $1
```

and then passing `NULL` to mean “don't filter.”

That does **not** work as intended because:

```text
status = NULL → UNKNOWN
```

You might see generated patterns like:

```sql
WHERE ($1 IS NULL OR status = $1)
```

which can be semantically correct for an optional filter, but introduces planner/performance considerations that should be evaluated against actual workload and parameter behavior.

The key lesson is:

> **SQL parameter nullability is part of the query contract.**

---

## 52. Production Pattern: Soft Deletes

Common pattern:

```sql
WHERE deleted_at IS NULL
```

Potential failure:

```sql
WHERE deleted_at = NULL
```

Another failure is assuming:

```text
NULL = active
```

when historical rows or archival jobs use null differently.

The semantics of the lifecycle column should be documented and constrained.

---

## 53. Production Pattern: “Missing” vs “Zero” in Dashboards

Suppose:

```sql
SELECT COALESCE(SUM(refund_amount), 0)
```

A dashboard might display zero even when there were:

```text
no refund rows at all
```

This can be acceptable for a KPI but misleading for an audit report.

Therefore reporting layers should classify outputs:

```text
Operational metric
Financial statement
Audit/reconciliation
User-facing summary
```

The acceptable null-to-zero transformation may differ by layer.

## 54. Performance Considerations

`NULL` itself is not automatically a performance problem.

The important issues are semantic transformations and predicates that affect selectivity, index use, statistics, and plan choice.

Examples to investigate with `EXPLAIN (ANALYZE, BUFFERS)` include:

- `IS NULL` / `IS NOT NULL` filters;
- expressions wrapped in `COALESCE`;
- nullable composite keys;
- partial indexes over null-sensitive populations;
- optional-parameter predicates;
- null-heavy distributions affecting selectivity estimation.

Never rewrite a correct null predicate merely because it “looks slower.” Measure it.

---

## 55. Index Design with NULL Predicates

If a workload repeatedly asks:

```sql
WHERE deleted_at IS NULL
```

and only a subset of rows are active, a partial index can be highly effective:

```sql
CREATE INDEX CONCURRENTLY idx_orders_active_customer
ON orders (customer_id, created_at DESC)
WHERE deleted_at IS NULL;
```

The exact usefulness depends on workload, cardinality, and query shape.

The engineering sequence is:

```text
Business filter
→ population
→ selectivity
→ workload
→ index candidate
→ EXPLAIN
→ benchmark
```

## 56. NULL and Functional Dependencies

When designing grouped queries and constraints, remember that nullability can affect how confidently you reason about uniqueness and dependencies.

For example, a nullable business key may not represent a globally unique identity because multiple rows can legitimately have no known key.

A strong model asks:

```text
What identifies this entity?
What does absence mean?
Can absence occur more than once?
Should absence itself be unique?
```

These are data-model questions before they are SQL questions.

## 57. Testing Strategy

A mature test suite should deliberately include:

```text
NULL
empty string
zero
false
known value
missing row
```

For nullable fields, test transitions too:

```text
NULL → value
value → NULL
NULL → NULL
value → same value
value → different value
```

For joins:

```text
match
no match
right row contains NULL attribute
multiple matches
```

For aggregates:

```text
no rows
all NULL
mixed NULL/non-NULL
all zero
```

These tests reveal semantic bugs that ordinary happy-path fixtures hide.

## 60. Principal-Level Design Questions

A principal engineer should be able to answer:

1. Which nullable columns are intentional, and what exact business state does each represent?
2. Which invariants are encoded through `NOT NULL`, `CHECK`, `UNIQUE`, partial indexes, and state machines?
3. Where does application code intentionally convert `NULL` into a value?
4. Are those conversions audited and tested?
5. Does API serialization preserve “missing” vs “explicit null” semantics?
6. Do synchronization pipelines detect `NULL ↔ value` changes correctly?
7. Are reports distinguishing no data from zero data where required?
8. Do pagination and ordering define null placement explicitly?
9. Are anti-joins expressed using semantics that remain correct with nullable keys?
10. Does the schema have accidental nullable states that should be eliminated?

## 62. Final Mental Model

Carry this forward into every later PostgreSQL chapter:

```text
NULL
 │
 ├── represents absence of a known value
 │
 ├── influences expression results
 │
 ├── influences predicate truth
 │       ├── TRUE
 │       ├── FALSE
 │       └── UNKNOWN
 │
 ├── changes JOIN behavior
 ├── changes aggregate interpretation
 ├── changes constraint behavior
 ├── changes uniqueness semantics
 ├── changes ordering semantics
 ├── changes pagination semantics
 ├── changes API serialization semantics
 └── can change business meaning
```

The most important rule to retain is:

> **Never ask “How does PostgreSQL handle NULL here?” as a memorization question. Ask “What proposition am I trying to prove, what does absence mean, and what should happen when the required value is unknown?”**

Once that becomes your default reasoning pattern, the seemingly strange parts of SQL `NULL` behavior become predictable.
