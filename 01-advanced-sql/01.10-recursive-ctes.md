# 01.10 — Recursive CTEs

> **Phase 01 — Advanced SQL**  
> **Level:** Advanced → Expert  
> **Primary goal:** Build a precise mental model for recursive query evaluation, graph/tree traversal, termination, ordering, cycle handling, performance, correctness, and production-safe use of PostgreSQL recursive CTEs.

---

## 1. Chapter Mission

A recursive CTE is not simply “a query that calls itself.” It is a declarative way to repeatedly apply a recursive transformation to a working relation until no more rows are produced.

This chapter teaches you to reason about a recursive query as:

```text
Anchor relation
      ↓
Working relation
      ↓
Recursive transformation
      ↓
Next working relation
      ↓
Repeat
      ↓
Termination
      ↓
Final result
```

The target is not memorizing `WITH RECURSIVE` syntax. The target is being able to answer:

- What is the anchor set?
- What is the recursive step?
- What constitutes progress?
- Why must termination occur?
- What is the row identity and grain at every iteration?
- Can cycles exist?
- Can one input generate many paths?
- What is the maximum depth?
- What is the expected cardinality?
- Does the output represent nodes, paths, levels, or states?
- Can the query explode exponentially?
- What does PostgreSQL materialize internally during recursive evaluation?
- What evidence would prove that the recursive query is the bottleneck or is returning incorrect data?

By the end of this chapter you should be able to:

1. Explain recursive CTE evaluation from first principles.

# 3. Precise Definitions

## 3.1 Simple definition

A recursive CTE is a CTE whose query refers to the CTE itself.

## 3.2 Engineering definition

A recursive CTE consists of an initial relation called the **non-recursive term** or **anchor term**, followed by one or more recursive terms that derive additional rows from the rows generated so far.

## 3.3 Expert definition

A recursive CTE is an iterative relational computation represented declaratively as a fixpoint-style evaluation over a working relation. Each iteration transforms the current working set into an intermediate result; termination occurs when the recursive term produces no new rows under the query's semantics.

The important abstraction is therefore not “self-reference,” but:

```text
Seed → Transition Function → Next State → ... → Fixpoint
```

---

# 4. Why Recursive SQL Exists

Ordinary SQL is naturally strong at finite relational transformations:

```text
rows → filter → join → group → project
```

But hierarchical and graph-shaped data naturally asks repeated questions:

```text
employee
  → manager
    → manager's manager
      → ...
```

or:

```text
category
  → child category
    → child category
      → ...
```

or:

```text
node A
  → edge
    → node B
      → edge
        → node C
```

A recursive CTE lets the database express that repeated traversal close to the data.

# 5. The Core Mental Model

Consider:

```sql
WITH RECURSIVE org AS (
    SELECT id, manager_id, name, 1 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.id, e.manager_id, e.name, org.depth + 1
    FROM employees e
    JOIN org
      ON e.manager_id = org.id
)
SELECT *
FROM org;
```

Think of it as:

### Step 1 — Anchor

```text
All root employees
```

### Step 2 — Working set

```text
roots
```

### Step 3 — Recursive expansion

```text
Find employees whose manager is in the current working set
```

### Step 4 — New working set

```text
children of roots
```

### Step 5 — Repeat

```text
children → grandchildren → great-grandchildren → ...
```

### Step 6 — Terminate

Eventually no additional matching rows exist.

The exact output ordering should not be inferred merely from this conceptual expansion. Explicit ordering should be designed when output order is part of the contract.

---

# 6. Recursive CTE Anatomy

The canonical structure is:

```sql
WITH RECURSIVE cte_name AS (
    -- anchor term
    SELECT ...

    UNION ALL

    -- recursive term
    SELECT ...
    FROM ...
    JOIN cte_name ...
)
SELECT ...
FROM cte_name;
```

The important pieces are:

| Component | Responsibility |
|---|---|
| Anchor | Seeds recursion |
| Recursive term | Produces the next generation |
| Recursive reference | Connects current generation to next generation |
| Union operator | Defines how generations are combined |
| Termination condition | Makes progress stop safely |
| Final SELECT | Consumes the recursive result |

---

# 7. Anchor Term

The anchor defines the initial population.

Example:

```sql
SELECT id, parent_id, name, 0 AS depth
FROM categories
WHERE parent_id IS NULL;
```

This says:

> Start with root categories.

A poor anchor produces a poor recursive computation.

If the anchor accidentally includes every row:

```sql
SELECT id, parent_id, name, 0
FROM categories;
```

then the recursive term may traverse an enormous amount of data unnecessarily.

## Engineering rule

Always be able to state the anchor population in one sentence.

Bad understanding:

> “It starts from the CTE.”

Good understanding:

> “It starts from active root categories belonging to tenant 42.”

---

# 8. Recursive Term

The recursive term consumes the rows produced so far.

Example:

```sql
SELECT c.id,
       c.parent_id,
       c.name,
       tree.depth + 1
FROM categories c
JOIN tree
  ON c.parent_id = tree.id;
```

This is the transition function:

```text
current node → matching children
```

The recursive term must preserve the CTE's declared column structure.

---

# 9. Iterative Evaluation Model

A useful reasoning model is:

```text
Result R₀ = Anchor

W₀ = Anchor

W₁ = Recursive(W₀)

W₂ = Recursive(W₁)

W₃ = Recursive(W₂)

...

Wₙ = ∅
```

The complete result conceptually accumulates the generated rows according to the recursive query's set/bag semantics.

You should mentally simulate small examples before optimizing large recursive queries.

# 10. Example: Employee Hierarchy

Schema:

```sql
CREATE TABLE employees (
    id         bigint PRIMARY KEY,
    name       text NOT NULL,
    manager_id bigint REFERENCES employees(id)
);
```

Data:

```text
1  CEO       NULL
2  Alice     1
3  Bob       1
4  Carol     2
5  David     2
6  Eve       3
```

Query:

```sql
WITH RECURSIVE org AS (
    SELECT
        id,
        name,
        manager_id,
        0 AS depth
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT
        e.id,
        e.name,
        e.manager_id,
        org.depth + 1
    FROM employees e
    JOIN org
      ON e.manager_id = org.id
)
SELECT *
FROM org
ORDER BY depth, id;
```

Result conceptually:

```text
CEO      0
Alice    1
Bob      1
Carol    2
David    2
Eve      2
```

Notice that **depth is business information**, while the physical execution strategy and final presentation ordering are different concerns.

# 11. The Most Important Question: What Is a Row?

Recursive SQL becomes dangerous when row meaning is unclear.

Possible recursive row grains include:

```text
one row = one node
one row = one path
one row = one node at one depth
one row = one traversal state
one row = one ancestor-descendant pair
```

These are not interchangeable.

## Node grain

```text
node_id
```

## Path grain

```text
root → A → B → C
```

## Ancestor-descendant grain

```text
ancestor_id + descendant_id
```

## State grain

```text
node_id + visited_path + depth + accumulated_cost
```

A recursive query can be logically correct but still return duplicate business entities because the actual grain is “path,” not “node.”

---

# 12. `UNION ALL` vs `UNION`

Recursive CTEs commonly use:

```sql
UNION ALL
```

because every generated row is retained.

`UNION` introduces duplicate elimination semantics.

This distinction is critical in recursive graphs.

Suppose:

```text
A → B
A → C
B → D
C → D
```

There are two paths to D:

```text
A → B → D
A → C → D
```

If the recursive row contains only `node_id`, duplicate-elimination semantics can collapse repeated nodes.

If the recursive row contains the full path, those two rows are distinct:

```text
(D, [A,B,D])
(D, [A,C,D])
```

So changing `UNION ALL` to `UNION` is not a generic “fix duplicates” operation. It changes the semantics of the recursive relation.

---

# 13. Recursive CTE and Cycles

A hierarchy is often assumed to be a tree.

But production data can violate that assumption.

Example:

```text
A → B
B → C
C → A
```

Then:

```text
A → B → C → A → B → C → ...
```

The query can fail to terminate.

## The deeper lesson

A foreign key may guarantee that a referenced row exists.

It does **not**, by itself, guarantee that the relationship forms an acyclic hierarchy.

Acyclicity is a separate invariant.

---

# 14. Cycle Prevention by Tracking Visited Nodes

A common defensive pattern is to carry a path of visited identifiers.

Example:

```sql
WITH RECURSIVE graph AS (
    SELECT
        id,
        ARRAY[id] AS path,
        false AS cycle
    FROM nodes
    WHERE id = 1

    UNION ALL

    SELECT
        e.to_id,
        graph.path || e.to_id,
        e.to_id = ANY(graph.path)
    FROM graph
    JOIN edges e
      ON e.from_id = graph.id
    WHERE NOT graph.cycle
)
SELECT *
FROM graph;
```

The exact implementation should be chosen with awareness of data types, path size, cycle semantics, and PostgreSQL's native recursive search/cycle features.

---

# 15. Native Cycle Detection

Modern PostgreSQL supports SQL-standard recursive query syntax for cycle detection:

```sql
WITH RECURSIVE search_tree(id, link, data) AS (
    SELECT t.id, t.link, t.data
    FROM tree t
    UNION ALL
    SELECT t.id, t.link, t.data
    FROM tree t, search_tree st
    WHERE t.id = st.link
)
CYCLE id SET is_cycle USING path
SELECT *
FROM search_tree;
```

The database can automatically maintain cycle state and a path representation.

This is generally easier to reason about than repeatedly hand-building custom path logic once the native feature fits the problem.

---

# 16. Search Order: Breadth-First vs Depth-First

A common misconception is:

> “Because recursive SQL expands recursively, the rows will automatically come out in the order I visually imagine.”

Do not rely on incidental row production order.

If business output requires hierarchy order, encode that order explicitly.

PostgreSQL supports SQL-standard `SEARCH` syntax for describing depth-first or breadth-first traversal ordering.

Conceptually:

```sql
SEARCH DEPTH FIRST BY id SET ordercol
```

or:

```sql
SEARCH BREADTH FIRST BY id SET ordercol
```

The generated ordering column can then be used by an outer `ORDER BY`.

---

# 17. `SEARCH` Is Not the Same as Recursion

Separate these ideas:

```text
RECURSIVE
= enables recursive evaluation

SEARCH
= defines a traversal ordering representation

CYCLE
= detects repeated traversal keys
```

They solve different problems.

---

# 18. Maximum Depth as a Safety Control

A production recursive query may intentionally cap traversal:

```sql
WHERE tree.depth < 100
```

This is not a substitute for correct cycle handling.

It is a safety boundary.

Useful controls include:

```text
cycle detection
+ maximum depth
+ selective anchor
+ selective recursive join
+ statement timeout
+ API result limits
```

# 20. Organizational Hierarchy Example

Question:

> Find every employee under manager `42`, including depth and full reporting path.

Pattern:

```sql
WITH RECURSIVE org AS (
    SELECT
        e.id,
        e.manager_id,
        e.name,
        0 AS depth,
        ARRAY[e.id] AS path
    FROM employees e
    WHERE e.id = 42

    UNION ALL

    SELECT
        e.id,
        e.manager_id,
        e.name,
        org.depth + 1,
        org.path || e.id
    FROM employees e
    JOIN org
      ON e.manager_id = org.id
)
SELECT *
FROM org
WHERE id <> 42
ORDER BY path;
```

This is a path-grain representation.

# 21. Bill of Materials

Consider:

```text
Assembly A
 ├── Component B × 2
 │    └── Component D × 4
 └── Component C × 3
```

A recursive BOM query may carry cumulative quantity.

For each recursive edge:

```text
new_quantity = parent_quantity × edge_quantity
```

This makes recursive queries powerful for manufacturing and ERP systems.

But it also introduces a major correctness issue:

> The result grain is now part hierarchy path × quantity state, not merely component id.

Two distinct paths to the same component can legitimately contribute different quantities.

Do not blindly `DISTINCT component_id` at the end.

---

# 22. Financial / Ledger Trees

Examples include:

```text
Assets
 ├── Current Assets
 │    ├── Cash
 │    └── Receivables
 └── Fixed Assets
```

Recursive traversal can construct account hierarchies.

But financial aggregation needs special care:

```text
hierarchy traversal
≠
account balance aggregation
```

You must distinguish:

```text
stored balance
transaction movement
parent account rollup
presentation hierarchy
```

Never assume the recursive traversal itself defines accounting semantics.

---

# 23. Graph Traversal

A graph differs from a tree because nodes may have multiple parents and cycles may exist.

Example:

```text
A → B
A → C
B → D
C → D
D → A
```

Now recursion is a graph walk.

Important state often includes:

```text
current node
visited nodes
path
hop count
accumulated cost
edge metadata
```

The more state you carry, the larger each recursive row becomes.

That can materially affect performance.

---

# 24. Shortest-Path Thinking

Recursive SQL can generate candidate paths, but “generate every path and sort later” can become computationally explosive.

Suppose a graph branches by factor `b` for `d` levels.

The number of possible paths can grow approximately like:

```text
O(b^d)
```

This is why recursive graph queries require workload and cardinality analysis before being placed behind a high-QPS API.

For large graph workloads, specialized graph-processing approaches may be more appropriate.

---

# 25. Recursive CTE + Aggregation

You can aggregate after recursive traversal:

```sql
WITH RECURSIVE tree AS (...)
SELECT parent_id, count(*)
FROM tree
GROUP BY parent_id;
```

Or aggregate values carried through recursion.

But carefully identify whether aggregation occurs:

```text
per generation
per node
per path
after full traversal
```

These produce different answers.

---

# 26. Recursive CTE + Window Functions

Window functions can be applied after recursion:

```sql
WITH RECURSIVE tree AS (...)
SELECT *,
       row_number() OVER (
           PARTITION BY parent_id
           ORDER BY id
       ) AS sibling_position
FROM tree;
```

This is useful for presentation and ranking.

Be careful about applying window logic inside recursive transitions: the semantic population available to a recursive step is not necessarily the same as the final complete relation.

---

# 27. Recursive CTE + `LATERAL`

Recursive rows can feed parameterized subqueries through `LATERAL`.

This can be powerful, but also expensive.

Mental model:

```text
for every recursive row
    execute a parameterized relation-producing operation
```

Therefore assess:

```text
recursive row count × lateral work per row
```

before using this pattern at scale.

---

# 28. Recursive Queries and Multi-Tenancy

A critical production rule:

> **Tenant isolation must exist at the anchor and recursive transition.**

Dangerous:

```sql
WITH RECURSIVE tree AS (
    SELECT id, parent_id
    FROM categories
    WHERE id = $1

    UNION ALL

    SELECT c.id, c.parent_id
    FROM categories c
    JOIN tree t
      ON c.parent_id = t.id
)
```

If tenant boundaries are represented in the table, the recursive relationship must not accidentally cross them.

Safer:

```sql
WITH RECURSIVE tree AS (
    SELECT id, parent_id, tenant_id
    FROM categories
    WHERE id = $1
      AND tenant_id = $2

    UNION ALL

    SELECT c.id, c.parent_id, c.tenant_id
    FROM categories c
    JOIN tree t
      ON c.parent_id = t.id
     AND c.tenant_id = t.tenant_id
)
...
```

Tenant isolation should also be backed by database constraints and/or RLS where appropriate.

---

# 29. The Cross-Tenant Parent Problem

Suppose:

```text
tenant 1: A
tenant 2: B

B.parent_id = A.id
```

A simple foreign key on `parent_id` permits this unless tenant identity is part of the referenced key design or another constraint prevents it.

The query may be written correctly yet the data model may permit illegal hierarchy edges.

This is a modeling problem, not merely a SQL problem.

---

# 30. Recursive Query and Data Integrity

A recursive hierarchy requires at least three classes of integrity:

```text
Existence integrity
→ referenced parent exists

Ownership integrity
→ parent and child belong to the same logical scope

Acyclic integrity
→ hierarchy does not contain forbidden cycles
```

A database schema may enforce the first two relatively naturally.

Acyclicity can require additional mechanisms depending on the model.

---

# 31. Common Wrong Implementation #1

```sql
WITH RECURSIVE tree AS (
    SELECT * FROM categories
    UNION ALL
    SELECT c.*
    FROM categories c
    JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;
```

### Your assumption

> PostgreSQL will stop when it reaches a previously visited node.

### Problem

`UNION ALL` does not automatically imply cycle detection.

### Why it fails

Cycles can continually produce rows.

### Correct mental model

You must explicitly reason about termination and cycle behavior.

### Production consequence

A malformed hierarchy can cause runaway CPU, memory pressure, excessive temp activity, long-running statements, or application timeouts.

### Better approach

Use appropriate cycle detection, integrity controls, depth bounds, and workload limits.

---

# 32. Common Wrong Implementation #2

```sql
SELECT DISTINCT id
FROM recursive_result;
```

### Assumption

> Duplicate IDs mean the recursive query is wrong.

### Problem

The recursive relation may be path-grain.

### Why it fails

Multiple paths to the same node can be meaningful.

### Better approach

Define the required grain first.

---

# 33. Common Wrong Implementation #3

Put an expensive filter only in the outer query:

```sql
WITH RECURSIVE tree AS (... entire hierarchy ...)
SELECT *
FROM tree
WHERE status = 'active';
```

### Problem

The recursive engine may still traverse inactive branches before the outer query removes the output.

### Better approach

Push logically valid predicates into the anchor and recursive term.

Always verify the actual plan and semantics rather than assuming pushdown.

---

# 34. Common Wrong Implementation #4 — Depth Limit as Cycle Handling

```sql
WHERE depth < 100
```

### Assumption

> The hierarchy is now safe.

### Problem

A 100-level cycle is still a cycle.

### Better approach

Treat depth limit as a safety guard, not proof of acyclicity.

---

# 35. Common Wrong Implementation #5 — Ordering by Depth Only

```sql
ORDER BY depth;
```

This provides a level grouping, but not necessarily the desired sibling/tree traversal order.

For a hierarchical UI, users often expect:

```text
CEO
  Alice
    Carol
    David
  Bob
    Eve
```

A simple depth sort cannot produce this alone.

Carry an explicit ordering path or use recursive `SEARCH` facilities.

# 36. AI / Vibe-Coding Failure Patterns

AI-generated recursive SQL commonly fails in the following ways.

## Failure A — No termination analysis

The generated query looks elegant but cannot explain why it stops.

## Failure B — `UNION` used as a magical cycle fix

The model removes duplicates without understanding row grain.

## Failure C — Tenant predicate omitted from recursive step

This can create cross-tenant traversal.

## Failure D — `DISTINCT` added after recursion

This can destroy legitimate paths or hide data-model problems.

## Failure E — Path arrays grow without consideration

Long paths increase row width and memory pressure.

## Failure F — Recursive graph query exposed directly through a public API

The query can become an accidental resource-exhaustion endpoint.

## AI audit questions

Before accepting generated recursive SQL, ask:

```text
1. What is the anchor?
2. What is the transition?
3. What guarantees termination?
4. Can cycles exist?
5. What is the row grain?
6. What prevents tenant leakage?
7. What is the maximum depth?
8. What is the maximum result size?
9. What is the expected branching factor?
10. What happens under adversarial data?
```

# 37. Performance Model

Recursive performance is driven by more than row count.

Think in terms of:

```text
Total work
≈
Σ(work per generation)
```

And each generation can be influenced by:

```text
working-set size
× join cost
× branching factor
× row width
× number of generations
```

A recursive query can therefore become expensive even when the base table is not enormous.

---

# 38. Cardinality Explosion

Suppose each node has an average of 5 children.

Approximate generation sizes:

```text
depth 0:       1

depth 1:       5

depth 2:      25

depth 3:     125

depth 4:     625

depth 5:   3,125
```

This is why:

```text
branching factor
× depth
```

is a first-class design consideration.

Real graphs with merging and cycles can behave even more subtly.

---

# 39. Row Width Matters

Carrying this:

```text
id
parent_id
depth
```

is cheap compared with carrying:

```text
id
parent_id
depth
full text description
large JSONB payload
array of every visited node
array of timestamps
accumulated metadata
```

Every recursive generation carries these values forward.

Therefore:

> Carry the minimum state required to correctly compute the next generation.

Add rich presentation columns after recursion when practical.

---

# 40. Indexing Recursive Queries

A common recursive join is:

```sql
child.parent_id = parent.id
```

That often makes an index on the child-side parent key useful:

```sql
CREATE INDEX ON categories (parent_id);
```

But indexing is workload-dependent.

You still need to consider:

```text
selectivity
branching factor
table size
visibility/cache behavior
additional filters
tenant_id
composite-key design
```

For multi-tenant hierarchy tables, a composite index such as:

```sql
CREATE INDEX ON categories (tenant_id, parent_id);
```

may better match the recursive join when tenant is part of the relationship predicate.

---

# 41. EXPLAINing Recursive Queries

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
WITH RECURSIVE ...
SELECT ...;
```

Look for:

```text
recursive working-table behavior
actual row counts
loop counts
unexpected cardinality
join strategy
buffer reads
sorts
spill indicators
```

The most important debugging question is:

> Which operator is doing disproportionate work relative to the number of useful output rows?

---

# 42. Evidence-Driven Debugging

When a recursive query is slow, do not immediately:

```text
add an index
rewrite everything
replace recursive SQL with application recursion
```

Instead capture:

```text
1. Query text
2. Parameters
3. Anchor row count
4. Rows per generation if measurable
5. Maximum observed depth
6. Branching factor
7. EXPLAIN ANALYZE BUFFERS
8. Index definitions
9. Table statistics
10. Concurrent workload
```

Then identify the dominant cost.

# 43. Statement Timeouts as a Production Safety Layer

Recursive queries should be treated as potentially unbounded work.

For user-facing workloads, timeouts are important.

Example at session/transaction/application policy level:

```sql
SET LOCAL statement_timeout = '2s';
```

A timeout is not a correctness mechanism.

It is a resource protection mechanism.

# 44. API Architecture for Recursive Queries

A dangerous endpoint:

```http
GET /categories/tree?id=<arbitrary-root>
```

backed by an unconstrained recursive query.

Safer design includes:

```text
authorization
+ tenant binding
+ maximum depth
+ bounded page/result size
+ statement timeout
+ indexed relationship
+ observability
+ rate limiting
```

The database query is one part of the system.

# 45. NestJS / Node.js Example

A repository method might accept:

```ts
getDescendants(tenantId: string, rootId: string, maxDepth: number)
```

The application should bind parameters, not interpolate them into SQL.

Conceptually:

```ts
await pool.query(
  sql,
  [tenantId, rootId, maxDepth]
);
```

The application should also enforce appropriate authorization before returning a subtree.

# 46. Recursive SQL vs Application-Side Recursion

Use SQL recursion when:

```text
relationship is stored relationally
traversal is naturally data-local
result set is moderate
transactional consistency matters
```

Application-side recursion may be preferable when:

```text
workflow requires external service calls
business logic dominates traversal
graph spans independent systems
per-node processing is heavy
caching/memoization is central
```

Neither side is universally superior.

The correct choice depends on workload, consistency, operational cost, and system boundaries.

---

# 47. Recursive SQL vs Materialized Hierarchy Models

For highly repeated hierarchy reads, consider alternatives:

```text
adjacency list
closure table
materialized path
ltree-based modeling
nested-set style models
cached/materialized hierarchy
```

Recursive CTEs are often excellent for adjacency-list traversal.

But if every request repeatedly computes the same deep hierarchy, precomputed representations may be more appropriate.

That decision belongs to the modeling and workload chapters later in the curriculum.

# 48. Recursive CTE and Transaction Consistency

Recursive queries are ordinary SQL statements from the transaction's perspective.

Therefore their observed data is governed by the transaction's visibility semantics.

For application behavior, ask:

```text
Is the hierarchy changing concurrently?
Can parent links change during a workflow?
Do we need a stable snapshot for the entire operation?
```

Recursive correctness is not separate from MVCC and transaction semantics.

Those topics will be studied deeply in Phase 04.

# 49. Temporal Hierarchies

Some hierarchies are valid only during time ranges.

Example:

```text
employee reports to manager
from 2025-01-01 to 2025-12-31
```

A recursive query must then answer:

> Traverse relationships valid at time T.

This means the recursive transition needs temporal predicates.

Do not traverse today's hierarchy when the business question asks for last year's hierarchy.

Temporal correctness will be revisited in the modeling and advanced-feature phases.

# 50. Soft Deletes and Status Filters

Suppose categories can be archived.

You must decide whether traversal should:

```text
default to active only
traverse through archived parents
exclude archived descendants
return archived structure for audit
```

There is no universally correct filter.

The business rule determines recursive semantics.

# 51. Security

Recursive queries create security risks beyond SQL injection.

Important controls:

```text

```

A perfectly parameterized recursive query can still be a security problem if an attacker can force huge traversals.

# 55. Property-Based / Invariant Testing

For a tree traversal, useful properties include:

```text
Every returned node is reachable from the root.
No returned node crosses tenant boundaries.
Depth increases consistently.
Cycle policy is respected.
Returned parent-child relationships are valid.
Maximum depth is never exceeded.
```

These are stronger than asserting only a fixed output example.
