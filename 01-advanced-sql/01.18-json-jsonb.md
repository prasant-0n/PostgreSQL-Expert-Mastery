# 01.18 — JSON / JSONB

> **Phase 01 — Advanced SQL**  
> JSON is a data representation. `jsonb` is a PostgreSQL data type with storage, comparison, containment, indexing, and query semantics. Treating it as “just a blob” is one of the fastest ways to build an unqueryable database.

---

## 1. Chapter Objective

This chapter develops production-grade mastery of PostgreSQL `json` and `jsonb`.

By the end, you should be able to:

- explain the difference between `json` and `jsonb` from first principles
- distinguish SQL `NULL` from JSON `null`
- understand object, array, scalar, and nested JSON structure
- extract values safely with `->`, `->>`, `#>`, `#>>`, and subscripting
- construct JSON with `json_build_object`, `jsonb_build_object`, `json_agg`, and related functions
- query nested structures with containment, existence operators, and SQL/JSON path
- understand why JSON containment is not ordinary equality and not ordinary relational membership
- design effective GIN indexes for `jsonb`
- distinguish `jsonb_ops` from `jsonb_path_ops`
- recognize when an expression index is better than an entire-column GIN index
- update nested JSON safely and understand write amplification
- design relational + JSON hybrid schemas
- decide when JSONB is appropriate and when it is masking a relational modeling problem
- reason about constraints, validation, security, observability, migrations, API contracts, and testing
- diagnose slow JSON queries using evidence and `EXPLAIN (ANALYZE, BUFFERS)`

The goal is not “knowing JSON operators.” The goal is knowing **when JSON should be a value, when it should be a document, and when the document should actually be rows and columns.**

## 2. Three Levels of Definition

### Simple definition

JSON is a structured text/data format containing objects, arrays, strings, numbers, booleans, and `null`.

### Engineering definition

PostgreSQL provides two JSON storage types:

- `json`: stores the original JSON text representation
- `jsonb`: stores a decomposed binary representation designed for database processing and indexing

PostgreSQL's current documentation recommends `jsonb` for most applications unless preserving the exact original textual representation has a specific purpose. `jsonb` does not preserve insignificant whitespace or object-key order and removes duplicate object keys, keeping the last value. citeturn959566view0

### Expert definition

`jsonb` is a typed PostgreSQL value with recursive document structure, defined extraction and containment semantics, comparison behavior, mutation operators, planner-visible operators, and specialized index support. The correct engineering question is therefore not “Can PostgreSQL store this JSON?” but **“What invariants, access patterns, update patterns, and relational dependencies does this value have?”**

---

# 3. First Principles: What Problem Does JSON Solve?

Traditional relational modeling starts with known attributes:

```text
customer
-------
id
name
email
phone
created_at
```

But real systems often encounter data whose structure changes by source, tenant, integration, version, or product configuration:

```json
{
  "provider": "external-marketplace",
  "campaign": "summer-sale",
  "attributes": {
    "seller_score": 4.8,
    "warehouse": "HYD-02"
  }
}
```

A rigid table can represent this, but every structural variation may force schema changes.

JSON is attractive when:

- the shape is genuinely variable
- the structure is naturally document-like
- the application receives or emits JSON
- some fields are optional or provider-specific
- the complete object has value as one atomic payload
- relational decomposition would create excessive schema churn

JSON becomes dangerous when developers use it as an escape hatch for every difficult modeling problem.

Consider:

```json
{
  "customer_ids": [12, 45, 91, 108]
}
```

This might be acceptable for a configuration snapshot. But if the real requirement is “customers assigned to an account,” the relationship probably belongs in a junction table.

**JSON provides flexibility. Relational design provides explicit structure. Production systems frequently need both.**

# 4. `json` vs `jsonb`

## 4.1 `json`

`json` stores an exact copy of the input text. Processing functions need to parse it when they operate on it.

Consequences:

- preserves input whitespace
- preserves object-key order
- preserves duplicate object keys in stored text
- useful when exact textual representation matters
- poor default for heavily queried JSON data

## 4.2 `jsonb`

`jsonb` stores a decomposed binary representation.

Consequences:

- input has conversion overhead
- querying is generally more efficient
- supports JSON-oriented indexing
- does not preserve whitespace
- does not preserve object-key order
- duplicate object keys are discarded except for the last value

These semantics are documented for PostgreSQL 18. citeturn959566view0

### Example

```sql
SELECT
  '{"a":1,"b":2}'::json  AS as_json,
  '{"a":1,"b":2}'::jsonb AS as_jsonb;
```

`jsonb` may print keys in a different order.

That is not data corruption. It is a consequence of its normalized internal representation.

### Practical default

Use:

```sql
payload jsonb
```

unless you have a demonstrated requirement for preserving the original textual representation.

# 5. JSON Data Model

A JSON value can be:

1. object
2. array
3. string
4. number
5. boolean
6. JSON `null`

Examples:

```sql
SELECT '{}'::jsonb;
SELECT '[]'::jsonb;
SELECT '"hello"'::jsonb;
SELECT '42'::jsonb;
SELECT 'true'::jsonb;
SELECT 'null'::jsonb;
```

Nested structures are arbitrary:

```sql
SELECT '{
  "customer": {
    "name": "Milan",
    "tags": ["gold", "priority"],
    "preferences": {
      "language": "en",
      "notifications": true
    }
  }
}'::jsonb;
```

Do not confuse JSON structure with SQL schema. PostgreSQL knows that the value is valid JSON, but arbitrary business rules are not automatically enforced.

---

# 6. SQL `NULL` vs JSON `null`

This distinction is critical.

SQL `NULL` means:

> the SQL value is absent/unknown.

JSON `null` means:

> the JSON document explicitly contains the JSON null literal.

Example:

```sql
SELECT
  NULL::jsonb AS sql_null,
  'null'::jsonb AS json_null;
```

These are different states.

Inside a JSON object:

```sql
SELECT '{"middle_name": null}'::jsonb;
```

The key exists and its JSON value is `null`.

But:

```sql
SELECT NULL::jsonb;
```

means the SQL column itself is NULL.

This becomes important for APIs, partial updates, filters, indexes, and business rules.

# 7. Extracting JSON Values

## 7.1 `->`

Returns a JSON/JSONB value.

```sql
SELECT payload -> 'customer'
FROM orders;
```

Array element:

```sql
SELECT payload -> 0
FROM events;
```

For JSON arrays, element indexing is zero-based. Negative indexes count from the end. citeturn959566view1

## 7.2 `->>`

Returns text.

```sql
SELECT payload ->> 'status'
FROM orders;
```

This distinction matters:

```sql
payload -> 'amount'
```

returns a JSONB value, while:

```sql
payload ->> 'amount'
```

returns text.

Do not blindly compare a text extraction with numeric values:

```sql
(payload ->> 'amount')::numeric > 1000
```

is a different operation from a native typed column comparison.

## 7.3 `#>` and `#>>`

Path extraction uses a text array describing the path.

```sql
SELECT payload #> '{customer,address,city}'
FROM orders;
```

Text form:

```sql
SELECT payload #>> '{customer,address,city}'
FROM orders;
```

Example source:

```json
{
  "customer": {
    "address": {
      "city": "Hyderabad"
    }
  }
}
```

Result:

```text
Hyderabad
```

---

# 8. JSONB Subscripting

PostgreSQL also supports subscripting syntax for `jsonb`.

```sql
SELECT payload['customer']['address']['city']
FROM orders;
```

For mutation, subscripting can assign values in supported contexts:

```sql
UPDATE orders
SET payload['status'] = '"paid"'::jsonb
WHERE id = 10;
```

Do not use nested mutation syntax merely because it looks cleaner. First verify the exact target type, semantics, null behavior, and expression produced by the query.

Use explicit operators/functions when they communicate intent more clearly.

---

# 9. Existence Operators

`jsonb` provides existence-oriented operators such as:

```text
?
?| 
?&
```

Examples:

```sql
SELECT '{"status":"paid","priority":true}'::jsonb ? 'status';
```

Checks top-level existence of a key or array string.

```sql
SELECT '{"status":"paid","priority":true}'::jsonb ?| ARRAY['status', 'missing'];
```

Any of the requested strings exists.

```sql
SELECT '{"status":"paid","priority":true}'::jsonb ?& ARRAY['status', 'priority'];
```

All requested strings exist.

Important: these existence checks are **top-level** operations. They do not recursively search arbitrary nested objects. citeturn959566view0

---

# 10. JSONB Containment: `@>` and `<@`

Containment is one of the most important JSONB concepts.

```sql
left @> right
```

means that the left JSONB value contains the right JSONB structure according to JSONB containment rules.

Example:

```sql
SELECT
  '{"status":"paid","priority":true}'::jsonb
  @> '{"status":"paid"}'::jsonb;
```

Result:

```text
true
```

## 10.1 Object containment

```sql
SELECT '{"a":1,"b":2}'::jsonb @> '{"b":2}'::jsonb;
```

`true`.

But:

```sql
SELECT '{"foo":{"bar":"baz"}}'::jsonb @> '{"bar":"baz"}'::jsonb;
```

is false because the structure does not match at that level.

## 10.2 Array containment

For JSONB containment, array order is not significant and duplicate array elements do not increase containment requirements. PostgreSQL documents examples such as `[1,2,3] @> [3,1]` being true. citeturn959566view0

This is a major source of bugs for developers who assume JSON arrays behave exactly like ordered SQL arrays.

### This:

```sql
'[1,2,3]'::jsonb @> '[3,1]'::jsonb
```

can be true.

Therefore `@>` must not be mentally reduced to “left array starts with/right array appears in this order.”

---

# 11. Equality Is Not Containment

These are different questions:

```sql
payload = '{"a":1}'::jsonb
```

asks whether the complete JSONB values compare equal.

Whereas:

```sql
payload @> '{"a":1}'::jsonb
```

asks whether the structure contains the specified content.

Example:

```sql
SELECT '{"a":1,"b":2}'::jsonb = '{"b":2,"a":1}'::jsonb;
```

JSONB object-key ordering is not semantic identity in the same way as textual JSON. `jsonb` comparisons operate on the normalized representation.

Use equality for complete-value identity. Use containment for structural predicates.

# 13. Row-to-JSON Mapping

PostgreSQL can convert rows and records into JSON.

Typical patterns:

```sql
SELECT row_to_json(o)
FROM orders o;
```

or explicit construction:

```sql
SELECT jsonb_build_object(
  'id', o.id,
  'status', o.status,
  'total', o.total
)
FROM orders o;
```

Explicit construction is usually preferable for stable API contracts because it makes the output shape intentional rather than accidentally exposing future columns.

---

# 14. Aggregating Rows into JSON

A common API response requires nested output.

Example:

```sql
SELECT jsonb_agg(
  jsonb_build_object(
    'id', id,
    'name', name
  )
)
FROM customers;
```

Grouped aggregation:

```sql
SELECT
  customer_id,
  jsonb_agg(
    jsonb_build_object(
      'id', id,
      'amount', amount
    )
    ORDER BY created_at
  ) AS orders
FROM orders
GROUP BY customer_id;
```

The `ORDER BY` inside an aggregate is important when output order is part of the API contract.

Never assume row order is naturally stable just because tests happened to return the same order.

---

# 15. Expanding JSON into Rows

A database often needs to turn a document back into relational rows.

For JSON arrays, functions such as `jsonb_array_elements` are fundamental.

Example:

```sql
SELECT jsonb_array_elements('["gold","priority","vip"]'::jsonb);
```

For JSON objects, functions such as `jsonb_each` expose key/value pairs.

```sql
SELECT *
FROM jsonb_each('{"a":1,"b":2}'::jsonb);
```

This is a critical mental model:

```text
JSON document
      ↓
JSON expansion function
      ↓
relational rows
      ↓
JOIN / WHERE / GROUP BY / window functions
```

JSON is therefore not outside SQL. PostgreSQL provides a bridge between document representation and relational execution.

---

# 16. LATERAL + JSON Expansion

One of the most useful production patterns is combining each row with its own JSON expansion.

```sql
SELECT
  o.id,
  item
FROM orders o
CROSS JOIN LATERAL jsonb_array_elements(o.payload -> 'items') AS item;
```

This transforms:

```json
{
  "items": [
    {"sku":"A100","qty":2},
    {"sku":"B200","qty":1}
  ]
}
```

into relational rows associated with the original order.

This is powerful, but remember the cost: expansion multiplies rows. A JSON array of 500 elements can turn one base row into hundreds of executor rows.

---

# 17. Extracting Typed Values from JSON

JSON extraction generally gives JSONB or text. Business logic often needs native PostgreSQL types.

Example:

```sql
SELECT
  (payload ->> 'amount')::numeric AS amount,
  (payload ->> 'active')::boolean AS active,
  (payload ->> 'created_at')::timestamptz AS created_at
FROM events;
```

This is useful at integration boundaries, but repeated casts throughout the workload can be a sign that frequently queried fields should become real columns.

A common architectural progression is:

```text
JSON-only field
    ↓
field becomes operationally important
    ↓
generated/functional extraction
    ↓
indexed query path
    ↓
validated native column
```

The correct endpoint depends on workload and business semantics.

# 18. SQL/JSON Path

PostgreSQL includes the `jsonpath` type and JSON path operators including `@?` and `@@`. citeturn959566view0turn959566view1

Example:

```sql
SELECT
  '{"items":[{"price":120},{"price":80}]}'::jsonb
  @? '$.items[*] ? (@.price > 100)';
```

This asks whether the JSON path finds a matching item.

`@@` is used for JSON path predicate checks:

```sql
SELECT
  '{"items":[{"price":120},{"price":80}]}'::jsonb
  @@ '$.items[*].price > 100';
```

Treat JSON path as a query language, not a magic string.

Complex path expressions deserve the same discipline as SQL:

- test them independently
- validate edge cases
- benchmark representative data
- inspect index support
- document expected semantics

# 19. JSONB Indexing: First Principles

A normal B-tree index answers questions naturally expressed as ordered scalar lookup:

```text
WHERE customer_id = 42
WHERE created_at >= ...
WHERE amount BETWEEN ...
```

JSONB often asks a different question:

> Which documents contain this key/value or structural fragment?

This is an inverted-index problem.

PostgreSQL's GIN is designed for composite values in which queries search for elements appearing within those values. GIN stores keys and posting lists rather than treating the whole composite value as one scalar. citeturn298839search0

For JSONB, this makes GIN a natural indexing mechanism for many containment/existence workloads.

---

# 20. Basic JSONB GIN Index

```sql
CREATE INDEX idx_orders_payload_gin
ON orders
USING GIN (payload);
```

This can support operators such as JSONB existence and containment, plus supported JSON path operators depending on operator class. PostgreSQL documents the default `jsonb_ops` operator class as supporting `?`, `?|`, `?&`, `@>`, `@?`, and `@@`. citeturn959566view0

But:

> **Adding a GIN index does not mean every JSON query becomes fast.**

The expression and operator used by the query must line up with what the index can accelerate.

---

# 21. `jsonb_ops` vs `jsonb_path_ops`

PostgreSQL provides two important GIN operator classes for JSONB.

## `jsonb_ops`

Default operator class.

Supports a broader operator set, including existence operators.

Conceptually it indexes keys and values separately.

Advantages:

- flexible
- broad operator support
- useful for mixed query patterns

Costs:

- generally larger index
- potentially less selective for some containment workloads

## `jsonb_path_ops`

Supports `@>`, `@?`, and `@@`, but not the top-level existence operators.

Its index representation is more specific to structural value paths and can be substantially smaller for suitable workloads. PostgreSQL documents that `jsonb_path_ops` often produces smaller indexes and more specific searches, while sacrificing operator flexibility. citeturn959566view0

### Decision rule

Choose based on the actual workload:

```text
Need ? / ?| / ?& frequently
        ↓
jsonb_ops is often appropriate

Mostly @> / JSON path containment predicates
        ↓
benchmark jsonb_path_ops
```

Never choose the operator class from a blog post without measuring your workload.

# 22. Why an Expression Index Can Be Better

Suppose documents look like:

```json
{
  "customer": {...},
  "metadata": {...},
  "tags": ["vip", "priority"],
  "audit": {...}
}
```

and the dominant query is:

```sql
WHERE payload -> 'tags' ? 'vip'
```

A full-document GIN index indexes everything.

A targeted expression index can focus on the relevant subdocument:

```sql
CREATE INDEX idx_orders_tags_gin
ON orders
USING GIN ((payload -> 'tags'));
```

Then the query:

```sql
SELECT *
FROM orders
WHERE payload -> 'tags' ? 'vip';
```

has an indexable operator directly applied to the indexed expression.

PostgreSQL explicitly documents this pattern and notes that expression indexes can be smaller and faster when a particular nested path is queried frequently. citeturn959566view0

This leads to a broader engineering principle:

> **Index the access pattern, not the data type.**

# 23. Generated Columns and JSONB

A frequent production design is:

```sql
CREATE TABLE orders (
  id bigint PRIMARY KEY,
  payload jsonb NOT NULL,
  status text GENERATED ALWAYS AS (payload ->> 'status') STORED
);
```

Now operational queries can use:

```sql
CREATE INDEX idx_orders_status
ON orders (status);
```

This is often easier to reason about than repeatedly extracting a heavily used value from JSONB.

But generated columns should not be introduced merely to hide poor modeling. Ask:

- Is this field queried frequently?
- Does it participate in joins?
- Does it have strong type requirements?
- Does it need foreign keys?
- Does it need uniqueness?
- Is it part of business identity?

If yes, a native relational column may be the better final design.

---

# 24. JSONB Update Semantics

A frequent misconception is:

> “Updating one JSON key should only modify that small key.”

At the SQL and MVCC level, an UPDATE creates a new row version. PostgreSQL's documentation specifically warns that large JSON documents can create row-level lock contention because updating a JSON document locks the whole row. citeturn959566view0

Example:

```sql
UPDATE orders
SET payload = jsonb_set(
  payload,
  '{status}',
  '"paid"'::jsonb
)
WHERE id = 42;
```

The syntax targets one field, but the database still updates the row version.

For frequently changing independent fields, this can be worse than separate columns.

---

# 25. `jsonb_set`

A common mutation primitive is:

```sql
jsonb_set(target, path, new_value)
```

Example:

```sql
UPDATE profiles
SET settings = jsonb_set(
  settings,
  '{notifications,email}',
  'false'::jsonb
)
WHERE id = 7;
```

Be explicit about whether intermediate objects should be created and verify behavior for missing paths.

Do not build complex JSON updates through fragile string concatenation.

Bad:

```sql
SET settings = (settings::text || '...')::jsonb
```

Good:

```sql
SET settings = jsonb_set(...)
```

Use typed constructors and JSON functions so the database understands the structure.

---

# 26. JSONB Merge / Concatenation

The `||` operator combines JSONB values.

Example:

```sql
SELECT '{"a":1}'::jsonb || '{"b":2}'::jsonb;
```

For objects with duplicate keys, merge semantics matter. Test conflict cases explicitly before using `||` as an application “deep merge.”

A critical trap:

> `||` is not a universal recursive deep-merge algorithm for arbitrarily nested objects.

Do not assume:

```text
nested object A
+
nested object B
=
recursive field-by-field merge
```

without verifying the exact operator semantics for the structures involved.

---

# 27. Deleting JSONB Fields

JSONB provides operators for removing fields/elements.

Examples include:

```sql
payload - 'temporary_field'
```

and path-oriented removal:

```sql
payload #- '{customer,internal_code}'
```

Use these operations rather than fetching the entire document into application memory, mutating it, and writing it back, unless application-level transformation is genuinely required.

Database-side mutation reduces unnecessary network transfer and race windows around read-modify-write logic.

---

# 28. JSON Validation Is Not Business Validation

A column declaration:

```sql
payload jsonb NOT NULL
```

proves that every non-null value is valid JSONB.

It does **not** prove:

```text
status is one of: pending, paid, failed
customer_id references customers(id)
amount >= 0
currency is 3-character ISO code
items is non-empty
sku is unique inside the document
```

Those are business invariants.

You may enforce some invariants with:

- CHECK constraints
- generated columns
- domains
- triggers, where justified
- native relational columns
- application schema validation

The closer an invariant is to data integrity, the more valuable database-level enforcement becomes.

---

# 29. JSON Schema at the API Boundary

Application frameworks frequently validate incoming JSON with a schema library.

That is valuable.

For example:

```text
HTTP request
   ↓
DTO/schema validation
   ↓
service logic
   ↓
PostgreSQL
```

But API validation is not a substitute for database integrity.

Another code path may write directly to the database.

A migration may introduce malformed data.

A background worker may bypass the normal API.

Therefore use layers intentionally:

```text
API schema
= request contract

Database constraint
= persistence invariant

Business logic
= workflow/rule enforcement
```

# 30. Hybrid Relational + JSONB Modeling

One of the strongest PostgreSQL patterns is:

```sql
CREATE TABLE products (
  id bigint PRIMARY KEY,
  tenant_id bigint NOT NULL,
  sku text NOT NULL,
  price numeric(18,2) NOT NULL,
  attributes jsonb NOT NULL DEFAULT '{}'::jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

Here:

- `tenant_id` is relational
- `sku` is relational
- `price` is relational
- `created_at` is relational
- variable integration/product attributes are JSONB

This is often superior to storing everything in one document because the high-value relational fields retain:

- indexes
- foreign keys
- type safety
- constraints
- efficient joins
- predictable query plans

JSONB becomes the extension surface rather than the entire data model.

---

# 31. The “Everything in JSONB” Anti-Pattern

Bad design:

```sql
CREATE TABLE users (
  id bigint PRIMARY KEY,
  data jsonb
);
```

with:

```json
{
  "name": "Milan",
  "email": "milan@example.com",
  "department_id": 12,
  "role": "manager",
  "salary": 85000,
  "active": true
}
```

This looks flexible.

But the database has lost obvious relational semantics for critical fields.

Questions become harder:

- How do you enforce email uniqueness?
- How do you foreign-key department_id?
- How do you efficiently report salary ranges?
- How do you index common predicates?
- How do you evolve the data safely?
- How do you guarantee every record has the same essential shape?

JSONB should reduce unnecessary rigidity, not eliminate data modeling.

---

# 32. Foreign Keys Inside JSONB

Dangerous pattern:

```json
{
  "customer_id": 123
}
```

where `123` refers to `customers.id`.

The database cannot treat that JSON scalar as a normal foreign-key column.

You have created an application-level convention instead of a relational constraint.

If referential integrity is important:

```sql
customer_id bigint REFERENCES customers(id)
```

is normally superior.

A JSON snapshot of an external object may still be valid:

```json
{
  "customer_snapshot": {
    "name": "ABC Jewellers",
    "code": "C-1002"
  }
}
```

because the snapshot is intentionally historical rather than relational identity.

---

# 33. Many-to-Many Relationships Inside JSON

Bad:

```json
{
  "role_ids": [2, 4, 8, 13]
}
```

when the application needs to answer:

- which users have role 4?
- when was the role assigned?
- who assigned it?
- what is the relationship status?
- can the relationship carry attributes?

A junction table wins:

```text
user_roles
----------
user_id
role_id
assigned_at
assigned_by
```

JSON arrays are appropriate when the list is truly an attribute and relational operations over individual members are not central.

---

# 34. Ordering Semantics: JSON Arrays vs JSONB Containment

Two separate concepts must not be conflated:

### Document representation

JSON arrays are ordered sequences.

```json
["a","b","c"]
```

### JSONB containment

Containment does not treat array order as significant in the same way as sequence equality. PostgreSQL documents this explicitly. citeturn959566view0

Therefore:

```text
“display this list in this order”
```

and:

```text
“does the document contain these values?”
```

are different questions requiring different operators and data models.

---

# 35. Numeric Precision Inside JSONB

JSON numbers are mapped to PostgreSQL numeric semantics for JSONB processing, and PostgreSQL rejects JSONB numbers outside the range representable by `numeric`. citeturn959566view0

For financial systems, do not assume that a JSON number automatically gives you your desired financial contract.

Prefer explicit extraction and validation:

```sql
(payload ->> 'amount')::numeric
```

and, for important persisted monetary values, a native:

```sql
amount numeric(18,2)
```

The representation contract should be deliberate across:

```text
JavaScript number
        ↓
JSON serialization
        ↓
PostgreSQL JSONB
        ↓
numeric extraction
        ↓
financial invariant
```

Do not allow implicit numeric assumptions to cross system boundaries unnoticed.

---

# 36. JSONB and Duplicate Object Keys

This is a classic `json` vs `jsonb` trap.

Input:

```json
{"role":"user","role":"admin"}
```

Textual `json` preserves the original representation.

`jsonb` does not preserve duplicate object keys; the last value is retained. PostgreSQL documents this explicitly. citeturn959566view0

Therefore, if duplicate-key preservation is semantically meaningful, `jsonb` may be the wrong storage type.

In normal application data, duplicate keys are typically a data-quality bug rather than a feature.

# 37. JSON vs JSONB Decision Matrix

| Requirement | Prefer |
|---|---|
| Preserve exact source text | `json` |
| Frequently query document structure | `jsonb` |
| Need GIN JSON indexing | `jsonb` |
| Preserve key order | `json` |
| Preserve duplicate object keys | `json` |
| Typical application document storage | `jsonb` |
| Stable identity / joins / FK | native relational columns |
| Variable provider attributes | `jsonb` |
| High-frequency scalar filtering | native column or generated/indexed extraction |
| Relationship-heavy data | normalized relational tables |

This is a workload-driven decision, not a style preference.

---

# 38. Performance Model

A JSON query has several possible costs:

```text
row retrieval
   + JSON navigation
   + casts
   + document expansion
   + predicate evaluation
   + index maintenance
   + TOAST/storage effects
   + row-version/write cost
```

A query that looks short can still be expensive.

Example:

```sql
WHERE (payload ->> 'customer_id')::bigint = 100
```

Potential issues:

- text extraction
- cast per row
- poor selectivity estimates
- sequential scan if no suitable index exists

A native column:

```sql
WHERE customer_id = 100
```

is often simpler for the planner and executor.

---

# 39. Measure, Do Not Guess

For production performance analysis:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Ask:

- Did PostgreSQL choose Seq Scan, Index Scan, or Bitmap Heap Scan?
- How many rows were examined?
- How many rows survived the filter?
- How much heap/index I/O occurred?
- Is the JSON predicate using the expected index?
- Are estimates close to actual rows?
- Did expansion multiply rows unexpectedly?

Do not begin with:

> “JSONB is slow.”

That is not a diagnosis.

The useful statement is:

> “The query scans 14 million rows because the expression in the WHERE clause is not covered by the available index, and the filter has low selectivity.”

# 40. Reading a JSONB Plan

A suspicious query:

```sql
SELECT id
FROM orders
WHERE payload @> '{"status":"paid"}'::jsonb;
```

Run:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM orders
WHERE payload @> '{"status":"paid"}'::jsonb;
```

Then inspect:

```text
Bitmap Index Scan
    ↓
Bitmap Heap Scan
    ↓
Rows Removed by Filter
```

or a sequential scan.

The presence of a GIN index is not proof that it will be selected. Cost, selectivity, table size, cache state, statistics, and workload all matter.

# 41. Indexing Strategy: Whole Document vs Targeted Paths

### Whole-document GIN

```sql
CREATE INDEX idx_payload_gin
ON documents USING GIN (payload);
```

Use when queries vary across many keys.

### Targeted expression GIN

```sql
CREATE INDEX idx_payload_tags_gin
ON documents USING GIN ((payload -> 'tags'));
```

Use when a specific nested path dominates the workload.

### Native extracted column

```sql
ALTER TABLE documents
ADD COLUMN status text
GENERATED ALWAYS AS (payload ->> 'status') STORED;

CREATE INDEX idx_documents_status
ON documents(status);
```

Use when the field has become an important relational attribute.

The progression is often:

```text
JSONB
 → JSONB + GIN
 → expression index
 → generated/native column
 → fully relational model
```

This is not a mandatory migration path, but it is a valuable design evolution pattern.

---

# 42. TOAST and Large JSON Documents

Large PostgreSQL values may be stored using TOAST mechanisms rather than entirely inline in the main heap tuple.

This matters because large JSON documents can affect:

- I/O
- cache efficiency
- write cost
- update cost
- vacuum workload
- replication traffic
- lock duration and contention

The rule is not “large JSON is forbidden.”

The rule is:

> **Large mutable JSON documents deserve explicit workload analysis.**

If one 200 KB document contains ten logically independent sections updated by separate transactions, a relational split may dramatically improve concurrency.

---

# 43. Concurrency: Whole-Row Updates Matter

Suppose:

```json
{
  "billing": {...},
  "shipping": {...},
  "preferences": {...}
}
```

Transaction A updates billing.

Transaction B updates preferences.

Even though the logical fields are independent, both transactions may update the same row. PostgreSQL's documentation warns that JSON updates acquire a row-level lock on the whole row. citeturn959566view0

This can create contention that a document-oriented schema may hide from the developer.

A relational decomposition can allow the independently mutable units to become independently lockable rows.

---

# 44. Multi-Tenant JSONB Design

For multi-tenant systems, tenant identity should normally remain a first-class relational field:

```sql
CREATE TABLE tenant_documents (
  id bigint PRIMARY KEY,
  tenant_id bigint NOT NULL,
  payload jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

Prefer:

```sql
WHERE tenant_id = $1
  AND payload @> $2::jsonb
```

over putting tenant identity only inside JSON:

```json
{
  "tenant_id": 17
}
```

Why?

Because tenant isolation is an architectural invariant, not merely document metadata.

A database can index and constrain `tenant_id`. It becomes much harder to guarantee isolation when tenant identity is buried in a document and every query must remember to extract it.

---

# 45. Security: JSONB Does Not Eliminate Injection Risk

Parameterize JSON values.

Bad:

```ts
const sql = `SELECT * FROM orders WHERE payload @> '${JSON.stringify(filter)}'::jsonb`;
```

Better:

```ts
const sql = `
  SELECT *
  FROM orders
  WHERE payload @> $1::jsonb
`;
```

and bind the serialized JSON as a query parameter.

The same security rule applies to JSON path expressions and dynamic SQL fragments:

> **Data belongs in parameters. SQL syntax belongs in the query.**

Do not concatenate untrusted values into JSON path expressions or SQL strings without deliberate validation and parameterization.

---

# 46. Security: Sensitive Data in JSONB

JSONB is still database data.

Putting a secret into JSON does not make it safer:

```json
{
  "password": "...",
  "api_key": "..."
}
```

Risks remain:

- backups
- replicas
- logs
- debugging tools
- exports
- accidental API serialization
- admin access

A flexible document is not a security boundary.

Minimize sensitive payload storage and explicitly control what is returned to clients.

- Which keys are queried most often?

## Structure tests

# 49. Common Developer Mistakes

## Mistake 1: Using `->>` everywhere

Everything becomes text.

Then every numeric/date/boolean comparison requires conversion.

### Better

Use JSON values when structural operations are needed; extract and cast deliberately when native semantics are required.

---

## Mistake 2: Assuming `@>` means sequence containment

JSONB containment has its own semantics, including order-insensitive array containment. citeturn959566view0

### Better

Learn containment as a structural predicate, not as string matching or ordered-list membership.

---

## Mistake 3: Putting foreign keys inside JSON

### Better

Keep referential identity relational.

---

## Mistake 4: Adding a GIN index without measuring

### Better

Validate the actual operator and query shape with `EXPLAIN (ANALYZE, BUFFERS)`.

---

## Mistake 5: Assuming a GIN index is always smaller/faster

GIN can be large and expensive to maintain.

### Better

Measure index size, build time, write workload, and query benefit.

---

## Mistake 6: Storing large frequently changing documents

### Better

Separate independently mutable domains.

---

## Mistake 7: Treating JSONB as schema-free

The database schema is not absent. You have simply moved part of the schema into conventions and application code.

### Better

Make important document structure explicit and validated.

# 50. AI / Vibe-Coding Failure Patterns

AI-generated PostgreSQL code frequently produces believable but weak JSONB designs.

### Failure: “Just use JSONB for flexibility.”

Missing question:

> Which fields require relational guarantees?

### Failure: “Add a GIN index; JSONB will be fast.”

Missing questions:

- Which operator?
- Which expression?
- Which operator class?
- What cardinality?
- What selectivity?
- What write rate?

### Failure: “Store IDs in a JSON array.”

Missing question:

> Do we need relationship queries or foreign-key enforcement?

### Failure: “Use `->>` and cast.”

Repeated extraction/casting may hide a field that should be native.

### Failure: “Merge objects with `||`.”

Missing understanding of shallow/structural merge semantics.

### Failure: “Patch one JSON property cheaply.”

Missing understanding of row-versioning, locking, storage, and write amplification.

Suppose a jewellery ERP has a product catalog.

Stable fields:

```text

created_at
```

Variable fields by category:

```json
{

    "source_grade":"A"
  },
  "channel_attributes": {
    "marketplace_x": {
      "listing_group":"premium"
    }

```


# 54. Naive → Improved → Production

## Problem

Frequently query customer status stored in JSONB.

### Naive Approach

```sql
SELECT *
FROM orders
WHERE payload ->> 'status' = 'paid';
```

### Why It Can Fail

- repeated extraction
- no appropriate index
- potentially large sequential scan
- status may actually be a stable relational attribute

### Improved Approach A: expression index

```sql
CREATE INDEX idx_orders_payload_status
ON orders ((payload ->> 'status'));
```

Useful when the field remains intentionally inside JSONB.

### Improved Approach B: native column

```sql
status text NOT NULL
```

Best when status is central to the business model.

### Production Considerations

Measure:

- query frequency
- cardinality
- selectivity
- write frequency
- migration effort
- API compatibility

### Trade-Off

Expression index preserves document flexibility.

Native column improves relational semantics.

Neither is universally correct.

# 55. Naive → Improved → Production: JSON Search

### Naive

```sql
WHERE payload::text ILIKE '%paid%'
```

### Why It Fails

This treats structured JSON as arbitrary text.

It can match:

- keys
- unrelated values
- nested content you did not intend
- formatting-dependent representations

and generally does not express JSON structure.

### Improved

```sql
WHERE payload @> '{"status":"paid"}'::jsonb
```

### Production

Create a suitable GIN index if workload evidence supports it.

# 56. Naive → Improved → Production: Relationship Storage

### Naive

```json
{
  "employee_ids": [10,11,12,15]
}
```

### Why It Fails

Relationship queries become awkward.

### Improved

```text
employee_department
-------------------
employee_id

department_id
```

### Production Consideration

Normalize relationships when they have independent identity, lifecycle, constraints, or queryability.

# 57. Decision Framework: Should This Be JSONB?

Ask these questions in order:

### Question 1
Is the structure genuinely variable?

If no, use relational columns.

### Question 2
Is the data naturally document-shaped?

If no, reconsider JSONB.

### Question 3
Does individual field identity matter?

If yes, native columns become more attractive.

### Question 4
Does the field need a foreign key or uniqueness constraint?

If yes, prefer relational storage unless there is a compelling architecture.

### Question 5
Will individual nested values be frequently filtered, joined, grouped, or ordered?

If yes, consider promotion to native columns or carefully designed indexes.

### Question 6
Are different subparts updated independently at high frequency?

If yes, JSONB may create unnecessary row-level contention.

### Question 7
Do queries need broad document containment?

If yes, JSONB + GIN may be strong.

### Question 8
Do you need the original textual JSON representation exactly?

If yes, consider `json`.

# 58. Architecture Pattern: JSON as the Edge, Relational Core

A strong default for enterprise systems is:

```text
                External / Variable World
                          │
                          ▼
                    JSONB boundary
                          │
                  validation/mapping
                          │
                          ▼
                 relational core
                          │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       entities       relations      invariants
```

This architecture contains change where change is expected while preserving relational guarantees where they matter most.

# 59. Advanced Expert Questions

## Why can `jsonb` be faster to query than `json`?

Because `json` stores the original textual representation and processing functions must parse it, while `jsonb` stores a decomposed binary representation designed for processing. citeturn959566view0

## Why does JSONB generally make a better default?

Because applications commonly query, manipulate, and index JSON rather than merely archive exact input text. PostgreSQL explicitly recommends `jsonb` for most applications. citeturn959566view0

## Why is GIN a natural JSONB index?

Because JSONB queries frequently search for keys, values, or structural elements within a composite document, matching GIN's inverted-index model. citeturn298839search0

## Why can an expression index beat a full JSONB GIN index?

Because it can index only the nested expression actually queried, reducing indexed data and improving search focus for a stable access path. PostgreSQL documents this targeted-expression pattern. citeturn959566view0

## Why isn't JSONB schema-free?

Because the business still depends on fields, types, paths, invariants, and semantics; those rules simply move from table definitions into application and document conventions unless explicitly enforced elsewhere.

## Why can large JSONB documents hurt concurrency?

Because updates are row updates, and PostgreSQL documentation warns that large JSON documents can increase row-level lock contention. citeturn959566view0
