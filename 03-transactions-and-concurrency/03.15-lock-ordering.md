# 03.15 — Lock Ordering

> **Phase 03 — Transactions & Concurrency**  
> Lock ordering is the primary design technique for preventing a large class of database deadlocks. This chapter develops the idea from first principles, turns it into enforceable engineering rules, and applies it to PostgreSQL row locks, table locks, advisory locks, foreign keys, batches, queues, money movement, and Node.js/NestJS services.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- explain why deadlocks emerge from acquisition order rather than merely from “too many locks”;
- model concurrent transactions as a wait-for graph;
- define a deterministic global ordering over rows, tables, tenants, accounts, resources, or advisory-lock keys;
- distinguish lock acquisition order from SQL text order;
- recognize ordering hazards introduced by joins, scans, `IN (...)`, sorting, triggers, foreign keys, cascades, and ORM-generated SQL;
- choose between row locks, table locks, advisory locks, constraints, and atomic statements;
- use a canonical ordering strategy for multi-row updates;
- understand why acquiring the strongest required lock first can reduce self-induced deadlock cycles;
- diagnose production deadlocks from PostgreSQL logs and lock views;
- design deterministic concurrency tests that reproduce ordering bugs;
- implement safe retry behavior for `40P01` deadlocks without retrying every database error;
- prevent retry storms, duplicate side effects, and transaction leaks in Node.js/NestJS;
- apply lock-ordering principles to jewellery ERP inventory, transfers, payments, ledger entries, and multi-tenant workloads;
- review AI-generated database code for hidden lock-ordering violations;
- explain the difference between preventing deadlocks and merely recovering from them.

PostgreSQL automatically detects deadlocks and aborts one of the transactions involved. The PostgreSQL documentation identifies consistent acquisition order for multiple objects as the best general defense; if that cannot be guaranteed, deadlocks can be handled by retrying aborted transactions. citeturn407940search2

# 2. The Central Mental Model

The core idea is simple:

```text
Deadlock risk
     |
     v
Transactions acquire overlapping resources
     |
     v
Different acquisition orders
     |
     v
Circular wait
     |
     v
Deadlock
```

The preventive transformation is:

```text
Many possible acquisition orders

A -> B
B -> A
A -> C
C -> A
B -> C
C -> B

          |
          v

One canonical order

A < B < C

Every transaction:

A -> B -> C
```

This is more powerful than “be careful with locks.” It turns an informal concurrency problem into an ordering invariant.

> **If multiple transactions can need the same set of lockable resources, make them acquire those resources in one globally consistent order.**

---

# 3. What Lock Ordering Means

## 3.1 Simple definition

Lock ordering means that concurrent transactions acquire multiple locks in the same predetermined order.

## 3.2 Engineering definition

A system defines a total or otherwise conflict-safe ordering over resources, and every code path that can lock more than one resource follows that ordering.

Examples:

```text
account 10 before account 20
warehouse 2 before warehouse 7
parent row before child row
table A before table B
advisory key 100 before advisory key 200
```

## 3.3 Expert definition

Lock ordering is a concurrency-control design invariant intended to make the wait-for graph acyclic for a defined class of transactions. It does not eliminate contention, does not guarantee that all deadlocks disappear, and does not replace correct transaction boundaries, timeout design, or observability. Its value is that it systematically removes circular-wait patterns caused by inconsistent multi-resource acquisition.

# 4. First Principles: Why Deadlocks Exist

Suppose two transactions need the same two rows:

```text
Rows: A and B
```

Transaction T1:

```text
lock A
lock B
```

Transaction T2:

```text
lock B
lock A
```

Execution can become:

```text
T1                        T2
--                        --
lock A                    lock B
   |                         |
   v                         v
wait for B                wait for A
```

The dependency graph is:

```text
T1 -> T2
T2 -> T1
```

A cycle exists.

No amount of waiting can resolve a cycle because neither participant can reach the point where it releases the resource the other needs.

PostgreSQL therefore detects the cycle and aborts one transaction. citeturn407940search2

Now impose:

```text
A < B
```

and require every transaction to acquire resources in ascending order:

```text
T1: A -> B
T2: A -> B
```

T2 may wait for A, but it never holds B while waiting for A.

Therefore:

```text
T1 holds A
T2 waits for A

T1 acquires B
T1 commits

T2 gets A
T2 then gets B
```

The cycle disappears.

---

# 5. Wait-for Graphs

A wait-for graph is the most useful formal model.

Vertices:

```text
transactions
```

Edges:

```text
T1 -> T2
```

meaning:

> T1 is waiting for T2 to release a conflicting resource.

Deadlock condition:

```text
There exists a cycle.
```

Example:

```text
T1 -> T2 -> T3 -> T1
```

Canonical ordering tries to prevent the application from constructing the cycle in the first place.

Think of the design constraint as:

```text
resource order induces a direction

R1 < R2 < R3

valid acquisition:

R1 -> R2 -> R3
```

A transaction that always moves forward in the order cannot wait on a resource earlier in the same order after already holding a later resource.

That is the conceptual proof behind canonical ordering.

---

# 6. Total Ordering vs Partial Ordering

A total order assigns every relevant resource a position:

```text
A < B < C < D
```

A partial order defines only the relationships that actually matter:

```text
A < C
B < C
```

Transactions must respect every declared dependency.

For application development, a total order is often easier to reason about because engineers can answer:

> “Which lock comes first?”

without needing to reconstruct a dependency graph for every pair.

However, a total order can unnecessarily serialize unrelated resources when implemented too broadly. Therefore:

```text
simple global order
        vs
minimal conflict order
```

is an architectural trade-off.

---

# 7. Lock Ordering Does Not Mean SQL Text Ordering

This distinction is critical.

Developers often assume:

```sql
UPDATE accounts
SET balance = balance - 10
WHERE id IN (10, 20);
```

means:

```text
lock row 10
then lock row 20
```

That is not a safe assumption.

The optimizer and executor determine how rows are located and processed. Query plans, index scans, bitmap scans, join order, parallelism, and executor behavior can change the physical order in which rows are encountered.

The correct engineering rule is:

> **Do not infer a concurrency-critical lock acquisition order merely from the textual order of values in SQL. Make the intended ordering explicit where correctness depends on it.**

For multi-row locking patterns, a common deliberate shape is:

```sql
SELECT id
FROM accounts
WHERE id = ANY($1)
ORDER BY id
FOR UPDATE;
```

The goal is not to claim that every internal lock event can be reconstructed from the `ORDER BY` clause. The goal is to make the application-level lock acquisition sequence explicit and easier to reason about.

When exact concurrency behavior matters, verify the actual plan and test under contention rather than relying on intuition.

# 8. Canonical Ordering for Rows

Suppose a transfer moves value from account 10 to account 20.

Naive implementation:

```text
Transfer(10,20): lock 10 -> lock 20
Transfer(20,10): lock 20 -> lock 10
```

This creates a classic cycle.

Canonical implementation:

```text
first  = min(accountA, accountB)
second = max(accountA, accountB)

lock first
lock second
```

Therefore both directions become:

```text
10 -> 20
```

Even when business direction is:

```text
20 -> 10
```

the lock order is still:

```text
10 -> 20
```

Separate these concepts:

```text
business direction
!=
lock acquisition order
```

That separation is one of the most important concurrency-design techniques in this chapter.

# 9. Production Example — Money Transfer

## 9.1 Naive implementation

```ts
async function transfer(fromId: number, toId: number, amount: string) {
  await client.query('BEGIN');

  await client.query(
    'SELECT id FROM accounts WHERE id = $1 FOR UPDATE',
    [fromId],
  );

  await client.query(
    'SELECT id FROM accounts WHERE id = $1 FOR UPDATE',
    [toId],
  );

  // debit + credit

  await client.query('COMMIT');
}
```

Two concurrent calls can deadlock when one transfers A → B while another transfers B → A.

## 9.2 Improved approach

```ts
const [firstId, secondId] = [fromId, toId].sort((a, b) => a - b);

await client.query(
  `
  SELECT id
  FROM accounts
  WHERE id IN ($1, $2)
  ORDER BY id
  FOR UPDATE
  `,
  [firstId, secondId],
);
```

Then perform the business operation in its original direction.

The key design is:

```text
business operation
      +
canonical synchronization order
```

## 9.3 Validation

After locking:

```text
verify both accounts
verify active status
verify currency
verify sufficient balance
apply debit/credit
insert immutable ledger entries
commit
```

The validation must happen after the correct locks are established when the validation depends on mutable state protected by those locks.

# 10. Strongest Required Lock First

PostgreSQL's documentation recommends that the first lock acquired on an object be the most restrictive mode that will be needed for that object when the mode can be known in advance. This reduces deadlock opportunities created by lock upgrades. citeturn407940search2

Conceptually:

```text
Bad:

acquire weak lock
      |
      v
later request stronger lock
      |
      v
possible conflict/upgrade interaction
```

Better:

```text
know required mode
      |
      v
acquire sufficient mode immediately
```

This is especially important when several transactions may need stronger modes on the same objects.

The general rule is:

> **Do not acquire a weaker lock merely because it is sufficient for the first line of code if the transaction already knows it will later require a stronger incompatible lock.**

This does not mean “always use the strongest possible lock.” Stronger locks increase contention.

It means:

```text
use the strongest lock actually required
at the first acquisition point
```

---

# 11. Parent-Child Ordering

Suppose a transaction updates:

```text
customers
orders
order_items
```

Another path updates:

```text
order_items
orders
customers
```

Even if each individual operation is valid, the mixed ordering creates a deadlock risk.

Choose one canonical hierarchy:

```text
customer
   -> order
       -> order_item
```

and enforce it across every transaction path that may touch these resources.

This becomes especially important with:

- triggers;
- cascading updates/deletes;
- foreign-key maintenance;
- audit writes;
- inventory reservation workflows;
- reconciliation jobs;
- administrative scripts.

A transaction's true lock set is often larger than what appears in its application service method.

---

# 12. Ordering Across Tables

Example:

```text
Transaction A
lock inventory
lock orders

Transaction B
lock orders
lock inventory
```

Canonical system rule:

```text
inventory < orders
```

Then every transaction must follow:

```text
inventory -> orders
```

Do not let different teams independently invent local ordering conventions.

The ordering invariant is cross-cutting architecture.

A practical pattern is to document resource precedence:

```text
1. tenant
2. customer
3. warehouse
4. inventory item
5. order
6. payment
7. ledger
```

Only include resources that actually participate in shared transactions. Overly broad hierarchies can create unnecessary serialization.

---

# 13. Ordering Advisory Locks

Advisory locks are especially susceptible to ordering mistakes because the database does not know the business meaning of the key.

Suppose:

```sql
SELECT pg_advisory_xact_lock(100);
SELECT pg_advisory_xact_lock(200);
```

and another request does:

```sql
SELECT pg_advisory_xact_lock(200);
SELECT pg_advisory_xact_lock(100);
```

The same classic cycle appears.

PostgreSQL supports application-defined advisory-lock keys and both session-level and transaction-level variants. These locks are stored in the shared lock-management machinery, and the application is responsible for using the keys consistently. citeturn407940search1turn407940search6

Therefore define:

```text
canonical key order
```

before introducing multi-key advisory locking.

For example:

```ts
const keys = resourceIds.sort((a, b) => a - b);

for (const key of keys) {
  await client.query(
    'SELECT pg_advisory_xact_lock($1)',
    [key],
  );
}
```

Avoid session-level advisory locks for ordinary request-scoped transactional coordination unless their longer lifetime is explicitly intended. A session-level advisory lock survives transaction rollback and remains until explicitly released or the session ends. citeturn407940search1

---

# 14. `FOR UPDATE` and Ordering Multiple Rows

A common pattern is:

```sql
SELECT id
FROM inventory
WHERE warehouse_id = $1
  AND product_id = ANY($2)
ORDER BY product_id
FOR UPDATE;
```

This is far easier to reason about than issuing many unrelated lock statements from application code.

But do not conclude:

> “`ORDER BY` is a magical guarantee that PostgreSQL always locks rows in exactly that visible order under every plan.”

The safe design process is:

```text
Define desired resource order
        |
Make query semantics align with the order
        |
Inspect plan when necessary
        |
Run concurrency tests
        |
Verify production assumptions
```

The database is the concurrency authority; your application code must not depend on undocumented execution accidents.

---

# 15. Batch Operations and `IN` Lists

Consider:

```sql
SELECT id
FROM inventory
WHERE id = ANY($1)
FOR UPDATE;
```

The array may arrive in arbitrary order:

```text
[100, 30, 50]
```

If different requests build lists differently, you have created an ambiguous application-level ordering convention.

A stronger pattern is:

```text
normalize input
     |
     v
sort resource identifiers
     |
     v
acquire all locks according to the canonical order
```

For example:

```ts
const ids = [...new Set(inputIds)]
  .sort((a, b) => a - b);
```

Then use those IDs consistently through the transaction.

Deduplication also matters because duplicate logical resources can otherwise make reasoning about the lock set harder.

---

# 16. The Hidden Problem: Different Query Paths

Imagine two code paths:

```text
API endpoint
    -> direct primary-key lookup

background worker
    -> indexed predicate scan
```

The endpoint may lock:

```text
A then B
```

while the worker's plan may encounter:

```text
B then A
```

Even if both SQL statements look equivalent at a business level, they may create different lock acquisition behavior.

This is why lock ordering is an **application + database + plan** concern.

For concurrency-critical paths, ask:

```text
What resources are locked?
In what logical order should they be locked?
Which SQL statement obtains them?
What access path may PostgreSQL choose?
Can another code path obtain the same resources differently?
Do triggers or constraints add hidden dependencies?
```

---

# 17. Triggers Can Break Your Intended Order

Application code may explicitly do:

```text
lock A
lock B
```

but an update on B can invoke a trigger that touches C.

Another path may explicitly lock C before A.

The true graph becomes:

```text
T1
A -> B -> C

T2
C -> A
```

Now the application developer's visible sequence is incomplete.

Therefore lock-order reviews must include:

- triggers;
- foreign-key checks;
- cascades;
- deferred constraints;
- stored procedures;
- row-level security-related functions where relevant;
- extension behavior;
- ORM callbacks;
- database-side audit mechanisms.

The rule is:

> **Review the effective lock set, not just the lines that explicitly say `FOR UPDATE`.**

---

# 18. Foreign Keys and Ordering

Foreign-key enforcement can introduce locking interactions that are not obvious from application code.

Suppose:

```text
parent
child
```

and multiple transactions update or insert related rows.

One workflow might acquire a parent lock first, while another operation's path is dominated by child-row work before it reaches the parent dependency.

The exact conflict depends on the statement type, key changes, constraint configuration, and transaction timing, so do not memorize a universal “foreign keys always deadlock” rule.

Instead:

```text
schema relationship
+
statement semantics
+
lock mode
+
transaction order
=
actual dependency
```

When a deadlock report involves foreign-key activity, inspect the complete server log detail rather than assuming the application code tells the whole story.

---

# 19. Ordering by Immutable Resource Identity

Good ordering keys are usually:

- stable;
- comparable;
- available before locking;
- unique enough to identify the resource;
- independent of business direction.

Examples:

```text
BIGINT primary key
UUID with a deterministic comparison
warehouse_id + product_id tuple
canonicalized composite key
advisory-lock bigint key
```

For composite resources, define an unambiguous tuple order:

```text
(tenant_id, warehouse_id, product_id)
```

and compare lexicographically or map it to a canonical scalar key when appropriate.

Avoid business rules such as:

```text
“lock the source account first”
```

when the source can be either 10 or 20.

That is not a globally stable ordering rule.

---

# 20. Ordering and Tenant Isolation

In a shared multi-tenant database, resource identity often includes tenant scope:

```text
(tenant_id, resource_id)
```

A canonical order can therefore be:

```text
tenant_id ASC
resource_id ASC
```

But be careful.

Tenant-first ordering does **not** automatically solve contention if a transaction spans many tenants or uses global resources.

Example:

```text
T1: tenant 1 -> global ledger
T2: global ledger -> tenant 1
```

The global resource must still be included in the canonical hierarchy.

A better model may be:

```text
global settlement resource
    < tenant resource
```

or the reverse, depending on the actual dependency structure.

The ordering must represent the real shared-resource graph.

---

# 21. When Canonical Ordering Is Not Enough

Lock ordering cannot solve every deadlock.

It does not automatically cover:

```text
unanticipated resources
trigger-created dependencies
external distributed locks
advisory keys not included in the hierarchy
application mutexes
cross-service dependencies
multiple database connections used in one logical workflow
```

Example:

```text
Service A
DB lock X
then HTTP call to Service B

Service B
DB lock Y
then HTTP call to Service A
```

The deadlock is now distributed across system boundaries.

PostgreSQL lock ordering cannot see the full graph.

For distributed workflows, the architecture must define ownership, sequencing, timeouts, and idempotency at the system level.

# 22. Naive Approach → Why It Fails → Improved Approach

## Naive Approach

```ts
await lock(fromId);
await lock(toId);
```

## Why It Fails

The order depends on business direction.

```text
A -> B
B -> A
```

creates a cycle.

## Improved Approach

```ts
const [a, b] = [fromId, toId].sort((x, y) => x - y);
await lock(a);
await lock(b);
```

## Why It Works

All requests converge on the same resource order.

## Production Considerations

You must apply the same policy to every path that can touch those resources, including jobs, scripts, admin tools, triggers, and related APIs.

## Alternative

Use a single atomic SQL statement that updates the required rows without an application-level multi-step locking sequence.

## Trade-Off

Explicit ordering is easier to reason about for complex workflows, while a single atomic statement may be simpler and faster for narrow invariants. Overusing explicit locks can increase contention.

# 23. Deadlock Prevention vs Deadlock Recovery

These are different layers.

## Prevention

```text
canonical order
minimal lock scope
short transaction
strongest required lock first
consistent resource hierarchy
```

## Recovery

```text
detect SQLSTATE 40P01
rollback failed transaction
re-run entire logical transaction
backoff + jitter
limit retry attempts
```

A robust system uses both.

Do not say:

> “We retry deadlocks, so we do not need lock ordering.”

Retries are a safety net.

Ordering is a design control.

---

# 24. Retrying Deadlock Failures Safely

The PostgreSQL error for a deadlock is SQLSTATE:

```text
40P01
```

A retry should be applied to the whole transaction attempt.

Conceptually:

```text
attempt 1
   |
   +-- BEGIN
   +-- acquire locks
   +-- read
   +-- validate
   +-- write
   +-- COMMIT
          |
          +-- 40P01
                |
                v
             rollback/cleanup
                |
                v
             backoff
                |
                v
             attempt 2
```

Do not retry:

```text
syntax errors
permission errors
invalid input
foreign-key violations
unique violations caused by a business bug
serialization-independent logic errors
```

A generic “retry any database error” handler can make production failure much worse.

---

# 25. Backoff and Jitter

Suppose 200 requests deadlock during a hot workflow.

If all 200 retry immediately:

```text
deadlock
  |
  +--> 200 immediate retries
          |
          +--> contention spike
                 |
                 +--> more deadlocks
                        |
                        +--> retry storm
```

Use bounded exponential backoff with jitter.

Conceptually:

```text
baseDelay * 2^attempt + randomJitter
```

with a maximum delay and a maximum retry count.

The exact values should come from workload measurement rather than a universal constant.

---

# 26. Node.js / NestJS Transaction Boundary

A common application bug is splitting one logical transaction across different pooled connections.

Wrong:

```ts
await this.pool.query('BEGIN');
await this.pool.query('SELECT ... FOR UPDATE');
await this.pool.query('UPDATE ...');
await this.pool.query('COMMIT');
```

Each pool operation may use a different session.

Then the intended lock ownership model collapses.

Correct:

```ts
const client = await this.pool.connect();

try {
  await client.query('BEGIN');

  // all reads and writes using the same client

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

For NestJS/ORM layers, the equivalent rule is:

> **The entire concurrency-critical unit must execute through one transaction context that maps to one database session/connection.**

---

# 27. Transaction Context Is Part of Lock Ordering

Suppose:

```text
Service A
transaction T1
locks account 10
calls Service B

Service B
starts another DB transaction
locks account 20
```

The logical workflow now has multiple transaction contexts.

The original canonical order may no longer be enforceable.

For synchronous request handling:

```text
HTTP request
    |
    v
one logical DB transaction
    |
    +--> repository 1
    +--> repository 2
    +--> repository 3
```

The transaction context must be passed intentionally through the call chain.

Do not let a repository silently obtain its own pool connection for a portion of a transaction.

# 28. Concurrency Pattern — Inventory Transfer

Suppose inventory moves between locations:

```text
warehouse A -> warehouse B
```

A naive workflow may lock according to movement direction:

```text
A -> B
B -> A
```

Canonical resource order:

```text
min(warehouseA, warehouseB)
max(warehouseA, warehouseB)
```

Then:

```text
lock lower warehouse inventory row
lock higher warehouse inventory row
validate quantity
subtract from source
add to destination
insert movement record
commit
```

Business semantics still distinguish source and destination; synchronization order is independent.

This pattern is useful for jewellery ERP workflows where stock can move between branches, showcases, warehouses, or repair locations.

# 29. Concurrency Pattern — Payment and Ledger

Consider:

```text
payment
ledger_account
```

Workflow 1:

```text
lock payment
lock ledger account
```

Workflow 2:

```text
lock ledger account
lock payment
```

Define:

```text
payment < ledger_account
```

and enforce:

```text
payment -> ledger_account
```

For financial systems, also prefer immutable ledger entries and database constraints for accounting invariants. Lock ordering is one layer, not the entire correctness model.

---

# 30. Concurrency Pattern — Job Queue

Workers often use:

```sql
SELECT id
FROM jobs
WHERE status = 'READY'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

The queue itself may have deterministic row selection semantics, but additional resources can still introduce deadlocks.

Example:

```text
Worker 1
lock job 10
lock customer 50

Worker 2
lock job 20
lock customer 50
```

Now the main contention is customer-level ordering rather than queue-row ordering.

Therefore:

```text
queue selection order
!=
complete lock hierarchy
```

Every additional shared resource must be incorporated into the design.

---

# 31. Ordering With Multiple Resource Types

Suppose a transaction can lock:

```text
tenant
customer
inventory
order
payment
ledger
```

Define a hierarchy:

```text
1 tenant
2 customer
3 inventory
4 order
5 payment
6 ledger
```

Now a transfer involving customer + inventory + order must use:

```text
customer -> inventory -> order
```

A payment workflow involving order + payment + ledger must use:

```text
order -> payment -> ledger
```

A workflow touching customer + payment + ledger must use:

```text
customer -> payment -> ledger
```

The same global hierarchy makes pairwise composition easier.

However, do not automatically force unrelated read-only work into that sequence. Only lock resources that are actually needed.

# 32. Lock Ordering and Isolation Levels

Lock ordering is useful under all PostgreSQL isolation levels, but its interaction differs.

At `READ COMMITTED`:

```text
lock ordering
+
statement-level snapshots
```

At `REPEATABLE READ`:

```text
lock ordering
+
transaction-level snapshot
+
possible serialization failures
```

At `SERIALIZABLE`:

```text
lock ordering
+
SSI dependency detection
+
possible serialization failures
```

Therefore:

> **Avoiding deadlocks does not make the transaction serializable, and serializable isolation does not eliminate ordinary lock-ordering problems.**

These are separate concurrency mechanisms.

---

# 33. Lock Ordering and `SERIALIZABLE`

This distinction is especially important.

A transaction can be perfectly ordered with respect to explicit row locks and still fail under `SERIALIZABLE` because SSI detects a dangerous dependency structure.

Example:

```text
No explicit lock cycle
        |
        v
rw dependencies
        |
        v
serialization failure
```

Conversely, a transaction can run under `READ COMMITTED` and deadlock because explicit row locks are acquired in opposite order.

Therefore classify incidents correctly:

```text
40P01
= deadlock

40001
= serialization failure
```

A good production taxonomy prevents the wrong mitigation from being applied.

# 34. Monitoring Lock Ordering in Production

When investigating deadlocks, collect:

```sql
SELECT
  pid,
  usename,
  state,
  wait_event_type,
  wait_event,
  xact_start,
  query_start,
  query
FROM pg_stat_activity
WHERE datname = current_database();
```

Lock state:

```sql
SELECT
  pid,
  locktype,
  mode,
  granted,
  relation::regclass,
  transactionid,
  virtualxid,
  tuple,
  page
FROM pg_locks;
```

Blocking relationship:

```sql
SELECT
  pid,
  pg_blocking_pids(pid) AS blockers,
  query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

For deadlock diagnosis, PostgreSQL's server log is particularly important because the deadlock detector can report the involved processes and the lock relationships that formed the cycle. PostgreSQL's lock management documentation also explains that `deadlock_timeout` controls when the server checks for deadlock; lowering it can make real deadlocks surface faster but increases checking overhead. citeturn407940search12

# 35. Reading a Deadlock as an Ordering Bug

Imagine a PostgreSQL deadlock report effectively tells you:

```text
Process 101 waits for row R2 held by process 202
Process 202 waits for row R1 held by process 101
```

Do not stop at:

> “PostgreSQL had a deadlock.”

Translate it into an application invariant:

```text
Transaction A acquired R1 before R2
Transaction B acquired R2 before R1
```

Then ask:

```text
Why are these transactions allowed to choose different orderings?
```

That question usually leads to the durable fix.

# 37. Concurrency Test — Two-Row Reversal

Create:

```text
row A
row B
```

Transaction T1:

```sql
BEGIN;
SELECT id FROM accounts WHERE id = 1 FOR UPDATE;
SELECT pg_sleep(1);
SELECT id FROM accounts WHERE id = 2 FOR UPDATE;
COMMIT;
```

Transaction T2:

```sql
BEGIN;
SELECT id FROM accounts WHERE id = 2 FOR UPDATE;
SELECT pg_sleep(1);
SELECT id FROM accounts WHERE id = 1 FOR UPDATE;
COMMIT;
```

The deliberate sleep widens the race window.

Expected result:

```text
one transaction eventually receives 40P01
```

Now change both transactions to:

```text
1 -> 2
```

Repeat.

Expected result:

```text
one waits
one completes
then the other completes
```

This is a minimal laboratory for lock-ordering reasoning.

# 38. Concurrency Test — Randomized Resource Sets

For stronger testing:

```text
Generate many pairs of overlapping resource sets
Normalize each set into canonical order
Run concurrently
Measure:
- deadlock count
- serialization failures
- lock wait time
- transaction latency
```

Use application-level stress tests instead of relying solely on unit tests.

# 39. AI / Vibe-Coding Mistake #1 — “The Array Order Is the Lock Order”

Generated code:

```ts
for (const id of ids) {
  await lock(id);
}
```

Why it looks reasonable:

```text
Input already contains IDs.
Loop is deterministic for one request.
```

Why it is unsafe:

```text
Request A gets [1,2]
Request B gets [2,1]
```

Fix:

```ts
const orderedIds = [...new Set(ids)].sort((a, b) => a - b);
```

The important lesson:

> **Deterministic per request is not enough; the order must be deterministic across all competing requests.**

---

# 40. AI / Vibe-Coding Mistake #2 — “Use the Business Direction”

Generated rule:

```text
lock source
then destination
```

This is exactly the rule that creates:

```text
A -> B
B -> A
```

Correct rule:

```text
lock canonical smaller resource first
```

Business direction remains in the update semantics, not in synchronization order.

---

# 41. AI / Vibe-Coding Mistake #3 — “Retry Everything”

Generated handler:

```ts
for (let i = 0; i < 5; i++) {
  try {
    await runTransaction();
    break;
  } catch {
    // retry
  }
}
```

Why it is dangerous:

- invalid SQL gets retried;
- permission failures get retried;
- business rule failures get retried;
- unique violations can amplify load;
- repeated external side effects may occur;
- root-cause defects remain hidden.

Fix:

```text
retry only explicitly retryable classes
```

For deadlocks, identify `40P01` and retry the whole database transaction after cleanup.

# 42. AI / Vibe-Coding Mistake #4 — “More Locking Means More Safety”

Generated workflow:

```text
lock tenant
lock customer
lock warehouse
lock product
lock order
lock payment
lock ledger
```

even though the operation touches only one order.

Why it is wrong:

```text
larger lock set
    |
    v
more contention
    |
    v
more latency
    |
    v
more opportunities for cycles
```

The correct question is:

> “What is the smallest set of resources whose lock protection is necessary for this invariant?”

Then order that set canonically.

# 43. Performance Analysis

Lock ordering has two competing effects.

## Benefit

Fewer deadlocks means:

```text
fewer aborts
fewer retries
lower wasted work
better tail latency
```

## Cost

Strict canonical ordering can increase:

```text
lock wait time
serialization of competing workflows
critical-section duration
```

Therefore optimize:

```text
correct lock set
+
correct order
+
short transaction
```

not merely:

```text
more aggressive locking
```

# 44. Measuring Lock-Wait Impact

Use transaction and statement timing together with lock observability.

Useful dimensions:

```text
p50 latency
p95 latency
p99 latency
lock wait time
deadlocks/sec
retry rate
transaction duration
active connection count
```

A deadlock-free design can still be operationally poor if every request waits behind a hot resource.

The engineering target is:

```text
deadlocks ↓
lock wait ↓
retry rate ↓
throughput ↑
tail latency ↓
```

without weakening correctness.

# 45. Migration and DDL Ordering

Lock ordering is not only about row locks.

Migration tooling may execute:

```text
ALTER TABLE A
ALTER TABLE B
```

while another maintenance process touches:

```text
B
then A
```

The conflict graph exists at the table-lock level too.

PostgreSQL documents that explicit table locking increases deadlock risk and recommends consistent order when locking multiple objects. citeturn407940search2

Production migrations should therefore consider:

- relation lock order;
- transaction duration;
- concurrent DML;
- deployment overlap;
- `lock_timeout`;
- rollback behavior;
- retry policy.

# 46. `lock_timeout` Is Not a Deadlock-Prevention Strategy

`lock_timeout` aborts a statement that waits longer than the configured limit for a lock. PostgreSQL documents that this timeout applies separately to each lock acquisition attempt. citeturn407940search0

It can be useful as an operational guardrail.

But:

```text
lock_timeout
!=
canonical ordering
```

A timeout can reduce the amount of time a blocked transaction consumes, but it does not remove the underlying cycle-producing design.

Use:

```text
ordering for prevention
+
timeouts for bounded waiting
+
retry for transient failure
```

---

# 47. Session-Level vs Transaction-Level Advisory Locks

When using advisory locks for a request-scoped workflow, transaction-level advisory locks are often easier to compose:

```sql
SELECT pg_advisory_xact_lock($1);
```

They release when the transaction ends.

Session-level locks:

```sql
SELECT pg_advisory_lock($1);
```

are held until explicit unlock or session termination. PostgreSQL documents that session-level advisory locks do not follow transaction rollback semantics. citeturn407940search1

This creates an ordering concern plus a lifetime concern.

A lock-order design is incomplete if the team does not also define:

```text
key space
acquisition order
lock scope
release semantics
connection ownership
```

---

# 48. Operational Capacity and Lock Memory

PostgreSQL's lock-management structures are shared resources. Advisory locks and regular locks consume lock-related shared memory governed by configuration such as `max_locks_per_transaction` and `max_connections`. citeturn407940search2turn407940search6

A design that locks thousands of resources per transaction may therefore create a different production problem even if it never deadlocks.

Canonical ordering should not become an excuse to lock an unnecessarily huge resource set.

Use:

```text
small correct conflict set
```

not:

```text
lock everything “just to be safe”
```

# 49. Production Incident Example

### Symptom

```text
checkout API p99 rises
```

### Evidence

```text
deadlock errors increase
retry rate rises
transaction duration increases
```

### Investigation

Deadlock logs reveal:

```text
order row <-> inventory row
```

Two code paths differ:

```text
Checkout
order -> inventory

Stock correction job
inventory -> order
```

### Root cause

Inconsistent lock hierarchy.

### Fix

Define:

```text
inventory < order
```

and update both paths to use that sequence.

### Additional hardening

- add deterministic concurrency test;
- instrument transaction duration;
- monitor `40P01` rate;
- verify worker and admin scripts;
- inspect triggers and foreign-key interactions;
- retain bounded retry handling.

### Result

The durable fix is not “increase the retry count.”

It is:

```text
eliminate the cycle-producing ordering divergence
```

# 53. Interview Questions

## Junior

**Q1. What is lock ordering?**

Weak answer: “Locks should be taken carefully.”

Acceptable answer: “Transactions should acquire multiple locks in the same order.”

Strong answer: “A canonical order prevents circular waits for overlapping multi-resource transactions.”

Expert answer: “The ordering creates an invariant that constrains the wait-for graph so that valid transactions cannot construct cycles for the covered resource set.”

**Q2. Why can A → B and B → A deadlock?**

Because each transaction can hold one resource while waiting for the other, producing a cycle.

## Mid-Level

**Q3. Should business direction determine lock order?**

No. Business direction and synchronization order should be separated.

**Q4. Why is SQL text order insufficient?**

Because executor behavior and access paths determine how rows are encountered; application code must not rely on textual value order as an undocumented lock-order guarantee.

## Senior

**Q5. How would you design a safe money-transfer transaction?**

Canonicalize the two account IDs, lock them in deterministic order, then perform validation and the debit/credit in business direction.

**Q6. How do triggers change lock-order reasoning?**

They can introduce hidden resource dependencies not visible in the application service method.

## Staff

**Q7. Can canonical ordering still leave deadlocks?**

Yes, when the true resource set contains dependencies that are omitted from the hierarchy, or when synchronization occurs outside the database transaction model.

## Principal

**Q8. Prove your ordering policy is sufficient.**

Define the resource graph, identify every lockable shared resource relevant to the workflow, establish a consistent order for every edge, and demonstrate that no valid transaction can acquire a later resource and subsequently request an earlier conflicting resource.

## Trick Question

**Q9. “We use `SERIALIZABLE`, so we do not need lock ordering.” Is that correct?**

No. Serializable isolation addresses serialization anomalies; explicit locking can still deadlock through circular waits.

# 55. Rolling Deployment Hazard

Changing ordering rules is itself a concurrency migration.

Suppose version A uses:

```text
A -> B
```

and version B uses:

```text
B -> A
```

During a rolling deployment both versions can execute concurrently.

You have reintroduced the exact deadlock pattern you were trying to eliminate.

Therefore lock-order changes require deployment planning.

Safer migration pattern:

```text
Phase 1
Introduce code that can understand canonical order
without immediately creating conflicting behavior.

Phase 2
Deploy canonical-order behavior consistently across workers.

Phase 3
Remove legacy ordering path.
```

For large systems, compatibility windows must be designed so that old and new binaries still follow a mutually safe order.

# 56. Ordering Contracts in Shared Libraries

If many services use the same database, define ordering conventions in a shared engineering contract.

Example:

```text
DATABASE LOCK HIERARCHY

inventory < order < payment < ledger
```

Then encode utilities:

```ts
function canonicalPair(a: number, b: number) {
  return a < b ? [a, b] : [b, a];
}
```

For heterogeneous resources:

```ts
const rank = {
  inventory: 10,
  order: 20,
  payment: 30,
  ledger: 40,
};
```

But do not treat a utility function as proof of correctness. The database schema, SQL, triggers, migrations, workers, and operational tooling must follow the same contract.

# 57. Ordering and Query Planning

When lock ordering is part of correctness, query plans are evidence, not implementation trivia.

Use:

```sql
EXPLAIN
```

- join order;
- scan method;
- sort placement;
- estimated vs actual rows;
- loops;
- parallel execution;
- filters;
- whether a statement is likely to touch a much larger set than expected.

The real objective is:

```text
correct resource set
+
predictable contention
+
acceptable latency
```

# 58. Why Short Transactions Matter to Ordering

Canonical ordering prevents cycles, but long lock lifetimes still increase queueing.

Bad:

```text
BEGIN
lock A
lock B
call HTTP API
wait 2 seconds
write audit record
COMMIT
```

Better:

```text
perform external API preparation first
BEGIN
lock A
lock B
validate
write
COMMIT
perform non-transactional follow-up if safe
```

Never move externally visible side effects inside a transaction merely to “keep the order.” Use an outbox or other durable messaging pattern when the database commit and external publication must be coordinated.

# 59. Security Considerations

Lock ordering is also relevant to denial-of-service resistance.

An attacker who can cause many requests to acquire a common sequence of locks can amplify queueing.

Therefore inspect:

```text
hot resource selection
request fan-out
transaction duration
maximum lock set size
retry count
advisory key cardinality
```

Do not expose arbitrary advisory-lock keys directly to untrusted users without a controlled mapping.

Authorization must also happen before expensive transactional work whenever possible.
