# 03.5 — Transaction Isolation Levels

> **Phase 03 — Transactions & Concurrency**  
> **Chapter:** 03.5  
> **Focus:** How PostgreSQL controls what concurrent transactions can observe, what anomalies remain possible, and how to choose the weakest isolation level that still preserves the required business invariants.

---

## 1. Chapter Objective

Transaction isolation is the bridge between **MVCC internals** and **application-level concurrency correctness**.

A database can provide atomic transactions and still allow an application to produce an incorrect business result if concurrent transactions are allowed to observe and act on data in ways the business rule does not tolerate.

This chapter builds the reasoning required to answer:

- What exactly does an isolation level control?
- Why are isolation levels a concurrency contract rather than a performance toggle?
- What does PostgreSQL actually mean by `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, and `SERIALIZABLE`?
- Why does PostgreSQL's `READ UNCOMMITTED` behave like `READ COMMITTED`?
- Why is `READ COMMITTED` the default?
- Why can `REPEATABLE READ` still permit outcomes that are not equivalent to a serial execution in the SQL-standard sense?
- What does PostgreSQL's `SERIALIZABLE` isolation actually prevent?
- What anomalies can still happen at each level?
- When should an application use row locking instead of a stronger isolation level?
- Why can a transaction succeed at the database level yet still violate a business invariant?
- Why do stronger guarantees often require retries?

The target outcome is not memorizing four names. The target outcome is being able to start with a concurrency invariant, identify the anomaly that could violate it, and select an isolation strategy based on evidence.

---

## 2. The Core Mental Model

Think of isolation as answering one question:

> **When multiple transactions execute concurrently, what observations and outcomes are permitted?**

A useful hierarchy is:

```text
Transaction boundary
        ↓
MVCC / tuple versions
        ↓
Snapshot / visibility
        ↓
Isolation level
        ↓
Permitted concurrent observations
        ↓
Permitted anomalies
        ↓
Application correctness
```

Isolation does **not** mean:

- every transaction gets a private copy of the database,
- no transaction can ever wait,
- no lock can ever be acquired,
- every business rule automatically becomes safe,
- higher isolation is always better,
- `SERIALIZABLE` means "the database executes one request at a time."

PostgreSQL uses MVCC as the core concurrency mechanism. SQL statements see snapshots, and PostgreSQL provides explicit locking facilities in addition to MVCC. citeturn403423search3

---

## 3. Precise Definitions

### 3.1 Simple definition

An **isolation level** specifies how one transaction is allowed to interact, from a visibility and conflict perspective, with concurrent transactions.

### 3.2 Engineering definition

An isolation level defines a set of guarantees about:

- which committed row versions a transaction may observe,
- whether later statements use new or stable snapshots,
- whether conflicting concurrent operations can proceed,
- whether certain anomalies can occur,
- whether a transaction may be aborted because its result cannot be serialized safely.

### 3.3 Expert definition

Isolation is a contract over the set of histories admitted by the concurrency-control protocol. Choosing an isolation level therefore means choosing which concurrent histories PostgreSQL must exclude and which histories it is allowed to admit.

The important shift is:

```text
"Which isolation level is fastest?"
            ↓
"Which histories does my invariant forbid?"
            ↓
"Which isolation mechanism excludes those histories?"
```

## 4. PostgreSQL's Four SQL Isolation Names

PostgreSQL exposes the four SQL isolation names:

| Level | PostgreSQL behavior |
|---|---|
| `READ UNCOMMITTED` | Behaves as `READ COMMITTED` |
| `READ COMMITTED` | Default; each statement obtains its own snapshot |
| `REPEATABLE READ` | Transaction-level stable snapshot semantics |
| `SERIALIZABLE` | Strongest level; committed transactions behave as though executed serially |

`default_transaction_isolation` defaults to `read committed`. The session-level `transaction_isolation` setting reflects the active transaction's isolation level. citeturn403423search0

The PostgreSQL 18 documentation distinguishes the behavior of these levels explicitly, including the fact that `READ UNCOMMITTED` is implemented as `READ COMMITTED` and that `SERIALIZABLE` provides the strictest guarantee. citeturn403423search12turn403423search5

## 5. Why `READ UNCOMMITTED` Is Not Actually Dirty Read in PostgreSQL

The SQL standard exposes `READ UNCOMMITTED`, but PostgreSQL does not expose dirty-read behavior through that setting.

In PostgreSQL:

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

produces `READ COMMITTED` semantics.

That means an application should **not** reason about PostgreSQL as though uncommitted row versions become visible merely because this isolation name was requested.

### Why this matters

A developer who knows only the ANSI names might assume:

```text
READ UNCOMMITTED
    ↓
dirty reads
```

That inference is incorrect for PostgreSQL.

The safe mental model is:

```text
PostgreSQL READ UNCOMMITTED
    ≈
PostgreSQL READ COMMITTED
```

The PostgreSQL documentation explicitly states this implementation behavior. citeturn403423search0turn403423search5

## 6. `READ COMMITTED` — The PostgreSQL Default

`READ COMMITTED` is the default isolation level. citeturn403423search0

The defining mental model is:

> **Each statement sees a snapshot established for that statement.**

This is very different from:

> "The whole transaction sees one snapshot."

Consider:

```sql
BEGIN;

SELECT stock FROM inventory WHERE product_id = 10;

-- another transaction commits an update here

SELECT stock FROM inventory WHERE product_id = 10;

COMMIT;
```

At `READ COMMITTED`, the two `SELECT` statements can observe different committed states because the statements establish visibility independently.

### Example

Initial state:

```text
stock = 10
```

Transaction A:

```sql
BEGIN;
SELECT stock FROM inventory WHERE product_id = 10;
-- sees 10
```

Transaction B:

```sql
BEGIN;
UPDATE inventory
SET stock = 7
WHERE product_id = 10;
COMMIT;
```

Transaction A then executes:

```sql
SELECT stock FROM inventory WHERE product_id = 10;
```

and may now see:

```text
7
```

The transaction itself did not become a single frozen historical universe. Its statements can see newly committed data that became visible after the earlier statement.

---

## 7. What `READ COMMITTED` Prevents

`READ COMMITTED` does provide important guarantees.

Another transaction's uncommitted changes are not treated as committed visible data.

A statement also operates on a consistent statement snapshot rather than seeing arbitrary mixtures of tuple versions within that statement.

This is enough for a very large class of ordinary CRUD workloads.

Examples that often fit naturally at `READ COMMITTED`:

- inserting a normal record,
- updating a row based on its current value,
- standard request-scoped transactions with row-level locks where needed,
- ordinary order creation when the scarce resource is locked explicitly,
- workflows whose correctness comes from unique constraints and atomic statements rather than cross-statement snapshot stability.

But `READ COMMITTED` does **not** make multi-step business decisions automatically serial.

---

## 8. The Classic `READ COMMITTED` Mistake

A common pattern is:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;

-- application logic

UPDATE accounts
SET balance = ...
WHERE id = 1;

COMMIT;
```

Two concurrent transactions can both read the same initial value and then derive decisions from stale observations.

This is not because PostgreSQL is broken. It is because the transaction's correctness requirement may span multiple statements, while `READ COMMITTED` provides statement-level snapshots rather than a single transaction-wide snapshot.

### Better question

Do not ask:

> "Should I increase the isolation level?"

First ask:

> "What exact invariant can be violated between the read and the write?"

That often reveals that an atomic update or row lock is sufficient.

## 9. `REPEATABLE READ`

At `REPEATABLE READ`, a transaction receives a stable snapshot for the transaction rather than obtaining a fresh snapshot for every statement.

This means a transaction has a much stronger view-stability guarantee:

```text
Transaction starts
       ↓
Snapshot established
       ↓
Statement 1 ─┐
Statement 2  │ same transaction snapshot
Statement 3  │
Statement 4 ─┘
       ↓
COMMIT / ROLLBACK
```

This is valuable for:

- consistent multi-query reporting,
- workflows that perform several reads against one logical database state,
- repeatable analytical decisions,
- avoiding statement-to-statement visibility changes.

PostgreSQL documents `REPEATABLE READ` as providing a stable view of the database for the transaction, while also explaining that this view is not necessarily equivalent to a serial execution of concurrent transactions. citeturn403423search12

---

## 10. Stable Snapshot Does Not Mean "All Business Rules Are Safe"

This distinction is critical.

Suppose two doctors may take leave only if at least one doctor remains on duty.

Initial state:

```text
Alice on duty
Bob   on duty
```

Transaction A:

```text
reads Alice = on duty
reads Bob   = on duty
puts Alice = off duty
```

Transaction B:

```text
reads Alice = on duty
reads Bob   = on duty
puts Bob = off duty
```

Both transactions can reason from a stable snapshot and still produce a final state in which **neither doctor is on duty**.

The problem is not that the snapshot was unstable.

The problem is that the invariant depends on the combination of facts:

```text
Alice_on_duty OR Bob_on_duty
```

and each transaction independently changed one part of that predicate.

This family of errors is commonly discussed as **write skew**.

The lesson is:

> Snapshot stability and serializability are different guarantees.

---

## 11. `SERIALIZABLE`

`SERIALIZABLE` is PostgreSQL's strongest isolation level.

The goal is to ensure that successful committed transactions behave as though they were executed one at a time in some serial order. PostgreSQL implements serializability using Serializable Snapshot Isolation (SSI), rather than simply executing every transaction under a giant global lock. citeturn403423search3turn403423search12

This distinction is extremely important.

### Naive mental model

```text
SERIALIZABLE
    ↓
Only one transaction runs at a time
```

### Better mental model

```text
Transactions may execute concurrently
             ↓
PostgreSQL tracks dangerous conflict patterns
             ↓
If concurrency cannot be represented safely
             ↓
one transaction may be aborted
             ↓
application retries
```

This allows concurrency while preserving serializable outcomes for committed transactions.

---

## 12. Serialization Failure Is Part of the Contract

At `SERIALIZABLE`, an application must be prepared for transaction aborts caused by serialization conflicts.

That means this pattern is incomplete:

```text
BEGIN
business logic
COMMIT
```

A production design must also answer:

```text
What happens when COMMIT or a statement fails because the transaction
cannot be serialized safely?
```

The retry strategy should be:

```text
start transaction
     ↓
perform complete business operation
     ↓
commit
     ↓
success? ───── yes → return
     │
     no: serialization failure
     ↓
rollback / discard transaction state
     ↓
retry whole transaction
```

Do not retry only the failed SQL statement while continuing with a partially completed transaction. The transaction itself is the unit of retry.

PostgreSQL provides explicit documentation for serialization failure handling and recommends designing applications to retry transactions when such failures occur. citeturn403423search5

---

## 13. Isolation Level Is Not the Same as Locking

Isolation level and explicit locking solve related but distinct problems.

### MVCC / isolation

Controls what transactions can observe and whether certain conflicting histories are permitted.

### Explicit locks

Create specific points of coordination.

For example:

```sql
SELECT *
FROM inventory
WHERE product_id = 10
FOR UPDATE;
```

may be exactly what is required when one physical row represents the scarce resource.

A common production decision is:

```text
One known row is the contention point?
        ↓
Explicit row lock may be simpler.

Invariant spans many rows / predicate?
        ↓
Stronger isolation may be appropriate.
```

PostgreSQL explicitly supports both MVCC-based concurrency and explicit table/row locking. citeturn403423search3

## 14. Choosing Isolation by Invariant

Use this reasoning process.

### Step 1 — State the invariant

Example:

```text
Inventory.available_qty >= 0
```

### Step 2 — Identify the race

Can two transactions independently consume the same quantity?

### Step 3 — Identify the representation

Is the scarce resource represented by:

- one row,
- several rows,
- a predicate over many rows,
- a range,
- a unique constraint,
- a derived aggregate?

### Step 4 — Choose the narrowest effective mechanism

Possibilities:

```text
Atomic UPDATE
UNIQUE constraint
Row lock
Advisory lock
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

### Step 5 — Define failure behavior

Ask:

```text
What happens on lock timeout?
What happens on serialization failure?
What happens on deadlock?
What happens on client retry?
```

The isolation level is one component of a larger concurrency design.

## 15. Isolation-Level Comparison

| Concern | Read Uncommitted | Read Committed | Repeatable Read | Serializable |
|---|---|---|---|---|
| PostgreSQL dirty reads | No | No | No | No |
| Statement snapshot stability | Equivalent to RC | Per statement | Transaction snapshot | Transaction snapshot + SSI |
| Sees later commits in same transaction | Yes, on later statements | Yes | No | No, subject to serializable snapshot semantics |
| Protects against all serialization anomalies | No | No | No | Yes for committed transactions |
| Possible serialization aborts | No | No | Possible transaction aborts from conflicts | Yes |
| Default | No | **Yes** | No | No |

This table is a reasoning aid, not a substitute for understanding PostgreSQL's actual implementation semantics. PostgreSQL documents the default as `READ COMMITTED`, stable snapshots for `REPEATABLE READ`, and serial execution equivalence for committed `SERIALIZABLE` transactions. citeturn403423search0turn403423search12

## 16. Isolation vs Application Logic

Consider:

```sql
SELECT COUNT(*)
FROM reservations
WHERE resource_id = 42
  AND status = 'active';
```

Then:

```text
if count = 0:
    INSERT reservation
```

The application may intend:

> "At most one active reservation exists."

Isolation alone may not be the best solution.

A better design could be a structural invariant such as a unique partial index:

```sql
CREATE UNIQUE INDEX one_active_reservation
ON reservations (resource_id)
WHERE status = 'active';
```

The larger principle is:

> If an invariant can be represented as a database constraint, prefer an explicit constraint over relying entirely on application timing.

Isolation protects histories; constraints directly represent certain states as illegal.

---

## 17. When `READ COMMITTED` Is Enough

`READ COMMITTED` is often enough when:

- each statement is independently correct,
- uniqueness is enforced structurally,
- updates use atomic predicates,
- conflicts are coordinated with row locks,
- cross-row invariants are not vulnerable to write skew,
- stale reads do not alter correctness,
- the transaction is short and request-scoped.

Example:

```sql
UPDATE inventory
SET available_qty = available_qty - 1
WHERE product_id = $1
  AND available_qty > 0
RETURNING available_qty;
```

This is often safer than:

```sql
SELECT available_qty ...;
-- application subtracts 1
UPDATE inventory SET available_qty = $new_value;
```

The first design turns the correctness condition into one atomic database operation.

---

## 18. When `REPEATABLE READ` Is Useful

`REPEATABLE READ` is valuable when one transaction needs a stable database view for multiple reads.

Typical scenarios include:

- generating a consistent report from several queries,
- comparing multiple tables against one historical snapshot,
- performing multi-step read/validate logic where later reads should not drift,
- long analytical workflows where snapshot consistency matters.

However, long-running repeatable-read transactions have operational consequences because they can preserve old row versions that vacuum cannot yet remove.

This connects directly back to MVCC from Chapter 03.3 and transaction visibility from Chapter 03.4.

---

## 19. When `SERIALIZABLE` Is a Strong Candidate

Consider `SERIALIZABLE` when:

- correctness depends on a predicate over multiple rows,
- the invariant is difficult to encode as constraints or locks,
- write skew would be catastrophic,
- correctness is more important than maximizing concurrency,
- retry semantics are acceptable,
- the workload is compatible with serialization-conflict retries.

A serializable transaction should be designed as a retryable operation:

```text
transaction function
       ↓
BEGIN ISOLATION LEVEL SERIALIZABLE
       ↓
business reads + writes
       ↓
COMMIT
       ↓
serialization failure?
       ↓
retry complete transaction
```

## 20. `SET TRANSACTION` Syntax

Isolation can be specified at transaction start.

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- work

COMMIT;
```

or:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

-- work

COMMIT;
```

You can inspect the active setting with:

```sql
SHOW transaction_isolation;
```

and inspect the configured default with:

```sql
SHOW default_transaction_isolation;
```

PostgreSQL exposes `transaction_isolation` and `default_transaction_isolation` as transaction configuration parameters. citeturn403423search0

## 21. Transaction Characteristics Are a Separate Axis

Isolation is not the only transaction characteristic.

PostgreSQL also has:

```text
READ WRITE / READ ONLY
DEFERRABLE / NOT DEFERRABLE
```

For example:

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
```

A serializable, read-only, deferrable transaction can wait before beginning execution so that it can obtain a safe snapshot without the serialization overhead that would otherwise require aborting it due to concurrent updates. PostgreSQL documents that `default_transaction_deferrable` currently affects serializable read-only transactions and not read-write transactions or lower isolation levels. citeturn403423search0

This is useful for certain long-running, consistent reporting workloads.

## 22. Node.js / NestJS Production Pattern

The application should make isolation explicit when a particular use case needs stronger semantics.

Conceptually:

```ts
await dataSource.transaction(
  'SERIALIZABLE',
  async (manager) => {
    // complete business operation
  },
);
```

The exact API depends on the database library/ORM, but the architectural rule remains:

> The transaction and its isolation level belong to the business operation, not to an arbitrary helper function that might be called outside its intended boundary.

### Strong rule

Do not do this:

```ts
await beginTransaction();
await callExternalApi();
await doDatabaseWork();
await commit();
```

unless the external call is deliberately part of a controlled transaction strategy.

Long-lived transactions hold snapshots and can increase contention and vacuum pressure.

---

## 23. Retry Architecture for Serializable Workloads

A robust retry wrapper should conceptually look like:

```ts
async function runSerializable<T>(work: () => Promise<T>): Promise<T> {
  for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
    try {
      return await runTransaction('SERIALIZABLE', work);
    } catch (error) {
      if (!isSerializationFailure(error) || attempt === MAX_RETRIES) {
        throw error;
      }

      await backoff(attempt);
    }
  }

  throw new Error('unreachable');
}
```

Production considerations:

- retry only known transient serialization failures,
- retry the entire transaction,
- keep retry counts bounded,
- use jittered backoff where appropriate,
- ensure external side effects are not duplicated,
- make commands idempotent,
- emit telemetry for retry counts.

A database retry without idempotency design can simply transform a correctness problem into a duplicate-side-effect problem.

## 24. Serialization Failure vs Deadlock vs Lock Timeout

These are different signals.

### Serialization failure

The concurrent history cannot safely be committed under serializable semantics.

Expected response:

```text
rollback → retry complete transaction
```

### Deadlock

Two or more transactions form a cycle of waits.

Expected response:

```text
transaction abort → retry complete transaction when safe
```

### Lock timeout

The configured wait duration expires before a lock is acquired.

Expected response depends on the operation. It may be retryable, but it could also indicate an architectural problem such as oversized transaction scope.

Do not collapse all concurrency failures into a generic "database retry" category.

## 25. Isolation and Connection Pooling

With a pooled Node.js application, isolation is attached to a database transaction/session context.

A common production mistake is leaking transaction state across requests.

For example:

```text
Request A
  connection acquired
  SET transaction characteristics
  transaction incomplete
  connection returned incorrectly

Request B
  receives same physical connection
  observes unexpected session state
```

The application must ensure:

```text
acquire connection
      ↓
BEGIN
      ↓
set transaction characteristics as required
      ↓
perform all work
      ↓
COMMIT / ROLLBACK
      ↓
release connection
```

The exact pool/driver mechanics differ, but the invariant does not: **transaction state must never escape its intended ownership boundary.**

## 26. Multi-Tenant Systems

Isolation level does not replace tenant isolation.

These are different dimensions:

```text
Transaction isolation
        ≠
Tenant authorization isolation
```

A transaction can be perfectly serializable and still access another tenant's data if the application or RLS policy is wrong.

Likewise, a multi-tenant query can be correctly scoped while still suffering a concurrency anomaly.

A production architecture should independently reason about:

- tenant visibility,
- authorization,
- relational constraints,
- transaction isolation,
- explicit locks,
- auditability.

---

## 27. Financial Systems

For financial or ledger workloads, stronger isolation may be appropriate around operations that depend on multiple concurrent predicates, such as:

- period closing,
- allocation limits,
- risk thresholds,
- account-level business rules,
- settlement state transitions.

But serializable isolation is not a substitute for ledger immutability, double-entry invariants, unique transaction identifiers, or reconciliation.

Use the layers together:

```text
Ledger model
   ↓
Constraints
   ↓
Immutable facts
   ↓
Transaction boundary
   ↓
Isolation / locks
   ↓
Retry strategy
   ↓
Reconciliation
```

## 28. Production Jewellery ERP Example

Consider a jewellery order allocating one unique inventory item.

A naive design is:

```text
SELECT item WHERE status = 'available'

application decides item is available

UPDATE item SET status = 'allocated'
```

Two concurrent orders can race depending on the exact workflow.

A stronger design might use:

```sql
UPDATE inventory_items
SET status = 'allocated',
    order_id = $1
WHERE id = $2
  AND status = 'available'
RETURNING id;
```

Now the scarce transition is an atomic database operation.

For a different invariant such as:

> "Across all branches, at least one particular reserve quantity must remain available while several rows may change concurrently."

the correct solution might require coordinated locking or serializable semantics, depending on how the invariant is modeled.

The important point is that **isolation is selected from the invariant's conflict geometry**, not from a generic application preference.

## 29. Evidence-Driven Isolation Debugging

When a concurrency bug appears, collect evidence before raising isolation globally.

Useful observations include:

```sql
SHOW transaction_isolation;
SHOW default_transaction_isolation;
```

Inspect active sessions:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
WHERE datname = current_database();
```

Inspect locks:

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    relation::regclass,
    transactionid,
    virtualxid
FROM pg_locks;
```

PostgreSQL documents transaction and lock identity information in `pg_locks`, including `virtualxid` and `transactionid`. citeturn403423search9

Then reproduce the race using two or more sessions.

```text
Session A                 Session B
---------                 ---------
BEGIN                     BEGIN
read                      read
pause                     write
write                     pause
commit                    commit
```

Change one variable at a time:

```text
READ COMMITTED
    ↓
REPEATABLE READ
    ↓
SERIALIZABLE
```

The goal is to identify the smallest mechanism that eliminates the observed anomaly.

## 30. Performance Considerations

Isolation has a cost, but the cost is workload-dependent.

### `READ COMMITTED`

Usually offers high concurrency for ordinary transactional workloads because readers and writers can make efficient use of MVCC.

### `REPEATABLE READ`

Can retain older row versions for longer due to transaction snapshot lifetime.

### `SERIALIZABLE`

Can introduce serialization conflicts and application retries. High-conflict workloads can therefore spend significant work repeating transactions.

Do not optimize isolation in the abstract.

Measure:

- transaction duration,
- conflict rate,
- retry count,
- lock wait time,
- throughput,
- tail latency,
- vacuum health,
- workload skew.

The PostgreSQL concurrency documentation emphasizes MVCC as a way to reduce read/write lock contention, while explicit locks remain available for targeted conflict management. citeturn403423search3

## 31. Isolation Level Anti-Patterns

### Anti-pattern 1 — "Always use SERIALIZABLE"

Why it fails:

- may cause unnecessary aborts,
- increases retry requirements,
- can hide poor data modeling,
- may reduce throughput under conflict-heavy workloads.

Better:

```text
Invariant → anomaly → mechanism → measured result
```

### Anti-pattern 2 — "READ COMMITTED is unsafe"

Why it fails:

It ignores the fact that many correct systems use `READ COMMITTED` plus constraints, atomic updates, and explicit row locking.

### Anti-pattern 3 — "REPEATABLE READ means serializable"

Why it fails:

A stable transaction snapshot does not automatically guarantee serial execution equivalence. PostgreSQL explicitly distinguishes these semantics. citeturn403423search12

### Anti-pattern 4 — Raising isolation instead of modeling the invariant

Why it fails:

A uniqueness or state-transition rule may be much easier to encode as a constraint or atomic update.

### Anti-pattern 5 — Retrying a statement instead of the transaction

Why it fails:

A serialization failure invalidates the transaction's serialization attempt. The retry should restart the transaction as one logical operation.

### Anti-pattern 6 — Keeping serializable transactions open across network calls

Why it fails:

Long transaction scope increases the opportunity for conflicts, resource retention, and retry amplification.

## 32. AI / Vibe-Coding Failure Modes

AI-generated backend code commonly gets isolation wrong in predictable ways.

### Failure: hard-coding SERIALIZABLE everywhere

```text
"Make all transactions SERIALIZABLE because it's safest."
```

Problem:

Correctness was treated as a configuration flag rather than an invariant-design problem.

### Failure: using SELECT + application arithmetic

```text
SELECT quantity
UPDATE quantity = calculated_value
```

Problem:

The code may introduce a race that an atomic SQL update would eliminate.

### Failure: missing retries

```text
SERIALIZABLE transaction
COMMIT
catch error
return 500
```

Problem:

Expected transient serialization failures are presented as permanent application errors.

### Failure: retrying external side effects

```text
transaction fails
retry
send email again
charge provider again
```

Problem:

Database retry semantics and external side effects are not automatically atomic.

### Failure: assuming ORM transaction wrappers imply correct isolation

Problem:

The ORM may create a transaction correctly while the business operation still contains an unsafe concurrency pattern.

The deeper rule is:

> AI can generate valid SQL while still generating an invalid concurrency protocol.

## 33. Testing Strategy

Isolation behavior should be tested with **concurrent schedules**, not only sequential unit tests.

### L1 — Basic

Verify the active isolation level.

### L2 — Statement visibility

Demonstrate different observations under `READ COMMITTED`.

### L3 — Snapshot stability

Demonstrate stable visibility under `REPEATABLE READ`.

### L4 — Anomaly reproduction

Construct a write-skew scenario.

### L5 — Serialization handling

Run conflicting serializable transactions and verify retry behavior.

### L6 — Production simulation

Run realistic concurrent workload with:

- multiple application workers,
- connection pooling,
- retries,
- timeouts,
- realistic transaction durations.

### L7 — Adversarial concurrency

Intentionally inject:

- delays between reads and writes,
- retries,
- lock waits,
- failures before commit,
- process termination,
- duplicate commands.

A concurrency test that never overlaps transactions is not a concurrency test.

```sql
INSERT INTO accounts(id, balance)
VALUES (1, 1000.00), (2, 1000.00);
```

### Lab A — Read committed

Session A:

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 1;
```

Session B:

```sql
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
COMMIT;
```

Back in Session A:

```sql
SELECT balance FROM accounts WHERE id = 1;
COMMIT;
```

Observe the statement-level snapshot behavior.

### Lab B — Repeatable read

Repeat the experiment with:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

Observe that the transaction snapshot remains stable.

### Lab C — Serializable conflict

Design two concurrent transactions that each validate a shared business predicate and then update different rows.

Run them under:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

Observe that PostgreSQL may abort one transaction rather than allow a non-serializable committed outcome.

The purpose of this experiment is to make the abstract guarantee visible through an actual schedule.

## 35. Decision Framework

Use this hierarchy:

```text
1. Can the invariant be represented by a constraint?
             ↓ yes
        use a constraint

             ↓ no
2. Can the operation be one atomic statement?
             ↓ yes
        use atomic SQL

             ↓ no
3. Is one row the conflict point?
             ↓ yes
        consider row locking

             ↓ no
4. Is stable transaction-wide visibility required?
             ↓ yes
        consider REPEATABLE READ

             ↓ no
5. Does correctness require serializable outcomes?
             ↓ yes
        use SERIALIZABLE + retry

             ↓ no
        READ COMMITTED may be sufficient
```

This is not a rigid rulebook. It is a reasoning framework.

## 36. Production Checklist

Before selecting or changing an isolation level, verify:

- [ ] The business invariant is written explicitly.
- [ ] The concurrency anomaly is understood.
- [ ] The conflicting rows/predicate are identified.
- [ ] Constraints are being used where possible.
- [ ] Atomic SQL has been considered.
- [ ] Explicit row locking has been considered.
- [ ] Transaction scope is minimal.
- [ ] External network calls are outside critical transaction paths unless deliberately designed otherwise.
- [ ] Retry behavior is defined for transient failures.
- [ ] Retries restart the whole transaction.
- [ ] Side effects are idempotent.
- [ ] Serialization failures are observable.
- [ ] Lock waits are observable.
- [ ] Transaction duration is monitored.
- [ ] Connection pooling does not leak transaction state.
- [ ] Concurrency tests reproduce the targeted race.
- [ ] Load testing measures conflict behavior, not just raw throughput.
- [ ] Long-running snapshots are monitored.

## 39. Final Mental Model

Do not memorize:

```text
RC < RR < Serializable
```

as though stronger were always better.

Memorize this instead:

```text
Business invariant
      ↓
Possible concurrent schedule
      ↓
Potential anomaly
      ↓
Required guarantee
      ↓
Constraint / atomic SQL / lock / isolation
      ↓
Failure & retry strategy
      ↓
Measured production behavior
```

The strongest isolation level that you can configure is not automatically the best architecture.

The best architecture is the one that **proves the invariant**, minimizes unnecessary coordination, and has explicit behavior for conflicts and retries.

## 40. Chapter Summary

PostgreSQL provides four SQL isolation names, with `READ COMMITTED` as the default and `READ UNCOMMITTED` mapped to `READ COMMITTED`. `READ COMMITTED` establishes snapshots at the statement level; `REPEATABLE READ` gives a stable transaction snapshot; `SERIALIZABLE` provides the strongest guarantee that committed concurrent transactions behave as though run serially. citeturn403423search0turn403423search12

But isolation is only one layer of concurrency correctness.

A strong PostgreSQL engineer thinks in this order:

```text
What must never happen?
        ↓
What concurrent schedule could cause it?
        ↓
What mechanism excludes that schedule?
        ↓
What happens when the mechanism rejects a transaction?
        ↓
How do we measure and prove the behavior in production?
```

That is the real purpose of transaction isolation: **not merely controlling visibility, but controlling which concurrent histories your system is willing to accept.**
