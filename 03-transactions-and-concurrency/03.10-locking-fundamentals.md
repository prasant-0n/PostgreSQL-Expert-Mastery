# 03.10 — Locking Fundamentals

> **Phase 03 — Transactions & Concurrency**  
> This chapter builds the foundation for understanding PostgreSQL locks: why they exist in an MVCC system, what is actually locked, how conflicts create waiting, how automatic and explicit locks differ, how to observe contention, and how to design locking safely in production.

# 2. The Central Mental Model

The first correction to make is:

> **MVCC and locking solve different problems.**

MVCC answers:

> “Which row version may this statement see?”

Locking answers:

> “Which concurrent operations are allowed to proceed together?”

A useful model is:

```text
                   PostgreSQL concurrency
                           |
              +------------+------------+
              |                         |
             MVCC                     Locks
              |                         |
       visibility rules          conflict / ordering
              |                         |
       Which version can I see?  Who must wait?
```

Therefore:

```text
No lock
!=
no concurrency control
```

and:

```text
MVCC
!=
mutual exclusion
```

A normal `SELECT` can often read a row without blocking a concurrent writer because MVCC can provide an older visible version. A writer still needs concurrency-control mechanisms to prevent conflicting physical/logical modifications from occurring incorrectly.

---

# 3. Three Definitions

## 3.1 Simple definition

A lock is a database coordination mechanism that can prevent incompatible operations from proceeding at the same time.

## 3.2 Engineering definition

A PostgreSQL lock represents a claim on some lockable database resource under a particular mode. Two transactions can proceed concurrently when their requested lock modes are compatible; otherwise one may wait until the conflicting lock is released or the operation fails.

## 3.3 Expert definition

PostgreSQL's locking system is a set of lock modes and lockable-object mechanisms integrated with transaction processing, MVCC, command execution, and deadlock detection. Locks can concern whole relations, tuples, pages, transaction IDs, advisory resources, and other database objects. Some lock state is represented in `pg_locks`; row-level locking details may also live in tuple state, and row-lock inspection can involve `pgrowlocks`. citeturn989323search0turn989323search2turn989323search4

The expert mental model is therefore not:

> “PostgreSQL has one lock per row.”

It is:

> **“PostgreSQL has multiple lock mechanisms operating at different granularities and for different purposes.”**

---

# 4. Why Locks Are Needed in an MVCC Database

A common beginner question is:

> “If MVCC lets readers see old versions, why do we need locks?”

Because MVCC primarily solves visibility and versioning. It does not eliminate all forms of conflict.

Consider two transactions:

```text
T1 wants to modify account 7
T2 wants to modify account 7
```

Both cannot blindly replace the physical/logical state without coordination.

Or consider DDL:

```sql
ALTER TABLE orders ...;
```

PostgreSQL must coordinate a schema-changing operation with concurrent users of that relation.

Or consider a business operation:

```text
read resource
check condition
reserve resource
```

The application may explicitly lock the resource while performing that critical section.

So the broader model is:

```text
MVCC
  -> nonblocking visibility where possible

Locks
  -> ordering and mutual exclusion where required
```

This is why “PostgreSQL is MVCC, so reads never block” and “all database operations use row locks” are both oversimplifications.

---

# 5. What Is a Lockable Object?

PostgreSQL's lock subsystem deals with more than tables.

Official documentation lists lockable objects including:

- whole relations such as tables;
- individual pages of relations;
- individual tuples of relations;
- virtual and permanent transaction IDs;
- database objects identified through object/class identifiers;
- relation-extension resources;
- other internal resources required for transaction processing.

`pg_locks` exposes one row per active lockable object, requested mode, and relevant process; the same object can therefore appear many times when several sessions hold or wait for locks. Objects with no active locks do not appear. citeturn989323search0

The implication is important:

```text
“lock”
```

is a family of mechanisms, not one physical thing.

---

# 6. Lock Granularity

A useful hierarchy is:

```text
Database-level / transaction coordination
            |
        Relation/table
            |
          Page
            |
         Tuple/row
```

There are also locks that do not map neatly to that hierarchy, such as transaction-ID waits and advisory locks.

Granularity creates a classic trade-off.

### Coarser lock

Advantages:

- simpler coordination;
- fewer lock objects;
- can protect a broad invariant.

Costs:

- larger contention domain;
- more unrelated work waits;
- lower concurrency.

### Finer lock

Advantages:

- less unrelated blocking;
- higher potential concurrency.

Costs:

- more complex coordination;
- more lock operations;
- larger deadlock surface when several resources are acquired independently.

There is no universal rule saying “row-level is always better.” The correct granularity follows the invariant being protected.

---

# 7. Lock Modes Are Compatibility Rules

A lock mode does not primarily mean:

```text
READ
WRITE
```

Instead, a mode defines which other modes it conflicts with.

For table locks, PostgreSQL provides several modes ranging from relatively permissive modes to `ACCESS EXCLUSIVE`, the most restrictive. Every lock mode has a defined conflict set. citeturn989323search33

The mental model should be:

```text
Transaction T1 holds mode A
Transaction T2 requests mode B

             |
             v
      Are A and B compatible?
          /          \
        YES           NO
         |             |
      proceed        wait
```

This is substantially more accurate than memorizing names without understanding the conflict matrix.

---

# 8. Table-Level Locks

PostgreSQL automatically acquires table-level locks for many commands. The lock protects the relation from incompatible structural or data-changing operations while the command runs.

Examples include:

```sql
SELECT ...;
INSERT ...;
UPDATE ...;
DELETE ...;
TRUNCATE ...;
ALTER TABLE ...;
```

The exact mode depends on the command.

This is why a simple query is not literally “lock free.” It may hold an automatically acquired relation lock even when the query does not lock individual rows for application-level mutual exclusion.

The important distinction is:

```text
table lock
!=
row lock
```

A table-level `ROW EXCLUSIVE` lock, for example, is still a table lock. The word `ROW` in the historical mode name does not make it a per-row lock. PostgreSQL explicitly documents this distinction. citeturn989323search33

---

# 9. The Table Lock Conflict Matrix as a Mental Tool

When reasoning about table locks, do not memorize the whole matrix first. Learn the pattern.

The key principle is:

```text
shared-compatible operations
        can coexist

structurally conflicting operations
        force waiting
```

`ACCESS EXCLUSIVE` conflicts with all other table-level lock modes, making it the classic broad blocker.

A production debugging question should therefore be:

> “Which session is holding which mode on which relation, and which requested mode conflicts with it?”

not:

> “Why is PostgreSQL randomly slow?”

---

# 10. `LOCK TABLE`

PostgreSQL lets applications explicitly acquire a table-level lock:

```sql
BEGIN;

LOCK TABLE orders IN SHARE MODE;

-- consistency-sensitive work

COMMIT;
```

General form:

```sql
LOCK [ TABLE ] [ ONLY ] table_name
    IN lock_mode
    [ NOWAIT ];
```

A transaction can lock multiple tables:

```sql
LOCK TABLE orders, order_items IN SHARE MODE;
```

The locks are acquired one by one in the order listed. PostgreSQL documents that `LOCK TABLE` is transaction-oriented and is ineffective outside a transaction block because there would be no useful transaction lifetime for the lock to span. citeturn989323search33

This creates an important rule:

> **An explicit table lock only protects a critical section if the critical section and the lock share the same transaction boundary.**

---

# 11. Naive Explicit Locking

Suppose an application wants to prevent two workflows from changing a group of related rows while it calculates a consistency-sensitive result.

A naive implementation might be:

```sql
LOCK TABLE orders IN SHARE MODE;

SELECT ...;
```

but execute the two commands in separate transactions or different pooled connections.

That fails to provide the intended protection.

## Why It Fails

The lock belongs to the transaction/session context that acquired it. Connection pooling does not make two different connections one transaction.

## Improved Approach

```text
checkout one connection
        |
BEGIN
        |
LOCK
        |
read/validate/change
        |
COMMIT
        |
release connection
```

The transaction boundary is part of the locking design, not an implementation detail.

---

# 12. Automatic Locks vs Explicit Locks

There are two broad categories to understand.

## Automatic locking

PostgreSQL obtains locks as part of normal command execution.

Examples:

```sql
SELECT ...
INSERT ...
UPDATE ...
ALTER TABLE ...
TRUNCATE ...
```

These locks exist because PostgreSQL needs to preserve database correctness and coordinate concurrent operations.

## Explicit locking

The application asks for a stronger or more specific lock.

Examples:

```sql
LOCK TABLE ...;
SELECT ... FOR UPDATE;
SELECT ... FOR SHARE;
pg_advisory_lock(...);
```

These should be introduced because the application has a concrete concurrency requirement, not because “locks are safer.”

---

# 13. Locks and Transactions

The most useful lifetime model is:

```text
BEGIN
  |
  +-- lock acquired
  |
  +-- critical section
  |
  +-- more SQL
  |
COMMIT / ROLLBACK
  |
  +-- transaction-scoped locks released
```

This has major consequences.

If a transaction stays open because the Node.js service calls an external API:

```text
BEGIN
  |
update row
  |
HTTP request to payment gateway  <--- 2.5 seconds
  |
more SQL
  |
COMMIT
```

the row/table locks remain relevant for that transaction lifetime.

The database did not become slow because HTTP is inherently slow. The application expanded the transaction's critical section to include the HTTP request.

This is a common production architecture error.

---

# 14. Granted vs Waiting Locks

Every useful lock investigation begins by separating:

```text
granted = true
```

from:

```text
granted = false
```

A granted lock means the backend currently holds the requested lock.

A waiting lock means the request cannot yet be granted because of conflict.

A typical blocking chain looks like:

```text
T1: holds lock A
 |
 +---- T2 waits for A
          |
          +---- T3 waits behind T2 / related resource
```

The first blocker is often more important than the largest wait count.

A production investigation should reconstruct the chain rather than merely count locks.

---

# 15. Observing Locks with `pg_locks`

Basic inspection:

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    relation,
    page,
    tuple,
    transactionid,
    virtualxid,
    virtualtransaction
FROM pg_locks
ORDER BY pid;
```

`pg_locks` exposes both granted and awaited locks and supports investigation of relations, tuples, transaction IDs, and other lockable resources. citeturn989323search0turn989323search1

Join with `pg_stat_activity`:

```sql
SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.client_addr,
    a.state,
    a.wait_event_type,
    a.wait_event,
    a.xact_start,
    a.query_start,
    a.query,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation
FROM pg_stat_activity a
JOIN pg_locks l
  ON l.pid = a.pid
ORDER BY a.xact_start NULLS LAST;
```

This combines:

```text
who is running
+
what they are running
+
what they are waiting on
+
what locks they hold/request
```

That is vastly more useful than looking at query latency alone.

---

# 16. Finding Waiting Sessions

A first-pass query is:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    now() - query_start AS query_age,
    query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
ORDER BY query_start;
```

Then identify the blocker.

Modern PostgreSQL provides useful waiting/blocking relationships through activity information and lock inspection; the exact investigation should use both views rather than assuming every `Lock` wait has the same cause.

The diagnostic mindset is:

```text
Observed latency
      |
      v
Is backend waiting?
      |
      +-- CPU
      +-- I/O
      +-- Lock
      +-- Client
      +-- Other wait event
```

Only after establishing `Lock` contention should you optimize the locking path.

---

# 17. Transaction IDs as Lock Coordination

Not all lock waits look like a simple table conflict.

PostgreSQL transaction processing also uses transaction IDs and virtual transaction IDs as lockable resources. `pg_locks` exposes `virtualxid` and `transactionid` columns for relevant locks. PostgreSQL's internals documentation notes that read-only transactions have a virtual transaction ID but no permanent transaction ID, while read-write transactions have both. citeturn989323search2

This matters because a wait can mean:

```text
“I am waiting for another transaction's outcome”
```

rather than simply:

```text
“I am waiting for a table lock.”
```

At expert level, always identify the **lock object type** before interpreting a wait.

---

# 18. Row Locks Are Not Just Table Locks With Smaller Names

Row-level locking is a different mechanism from ordinary relation-level locking.

PostgreSQL's transaction internals documentation explains that row-level read and write locks are recorded directly in locked rows; `pgrowlocks` can inspect row-lock information for a table. citeturn989323search2turn989323search4

This distinction is important for debugging.

A query may show a relation-level lock in `pg_locks` while the actual application conflict is between row-level modifications.

In later chapters we will study:

```text
FOR UPDATE
FOR NO KEY UPDATE
FOR SHARE
FOR KEY SHARE
```

in detail.

For now, understand the architecture:

```text
Table-level lock
    -> protects/coordinates relation-level operations

Row-level lock
    -> coordinates access to specific tuples
```

---

# 19. Page-Level Locks

PostgreSQL can also represent page-level lock state in the locking subsystem. These are generally internal coordination mechanisms rather than the application-level primitive developers reach for.

The key lesson is:

> **Do not design application concurrency by assuming every internal lock is an API-level row lock.**

Internal locking may exist to coordinate storage or execution details even when the application never requested it explicitly.

---

# 20. Advisory Locks: Different Philosophy

Advisory locks are application-defined coordination primitives.

Conceptually:

```sql
SELECT pg_advisory_lock(12345);
```

The integer is an application-defined namespace/key.

Unlike row/table locks, advisory locks do not automatically correspond to a specific table tuple.

That can be powerful:

```text
“Only one job for customer 42 may run.”
```

or:

```text
“Only one settlement process for branch 7 may run.”
```

But advisory locks are dangerous when the application has no clear ownership protocol.

A later chapter covers advisory-lock design in depth. Here the core distinction is:

```text
Database object lock
vs
application protocol lock
```

# 21. Waiting Is Often Correct

A lock wait is not automatically an incident.

Example:

```text
T1 starts updating order 100
T2 also needs order 100
T2 waits briefly
T1 commits
T2 continues
```

That is normal serialization of conflicting work.

The engineering problem begins when waiting becomes excessive:

```text
milliseconds -> normal
hundreds of ms -> workload dependent
seconds -> investigate
minutes -> usually serious
```

There is no universal threshold because the acceptable wait depends on the workload and latency objective.

Measure the actual service-level impact.

---

# 22. Blocking vs Deadlock

These concepts must be separated.

## Blocking

```text
T2 waits for T1
```

T1 can eventually commit and unblock T2.

## Deadlock

```text
T1 waits for T2
T2 waits for T1
```

Neither can proceed without intervention. PostgreSQL detects deadlock cycles and aborts a transaction.

Therefore:

```text
not every lock wait is a deadlock
```

and:

```text
a deadlock is a graph-cycle problem, not merely “a long lock wait.”
```

Deadlocks are covered deeply in chapter 03.14, but lock-order discipline begins here.

---

# 23. Blocking vs Lock Timeout

A lock wait can terminate because a timeout is configured.

For example:

```sql
SET lock_timeout = '2s';
```

Then a conflicting acquisition that cannot complete in time can fail instead of waiting indefinitely.

This is a workload-control mechanism, not a correctness mechanism.

Do not think:

> “A timeout means the concurrency problem is solved.”

The timeout only changes what happens when contention persists.

The application still needs to decide:

```text
retry?
return conflict?
fail operation?
queue work?
alert?
```

# 24. `NOWAIT` as an Immediate-Failure Policy

Some locking commands support:

```sql
NOWAIT
```

The idea is:

```text
Can I acquire this lock now?
    |
    +-- yes -> proceed
    |
    +-- no  -> fail immediately
```

This is different from:

```sql
lock_timeout = '0'
```

because command-level `NOWAIT` communicates the intent at the SQL operation itself.

We will study `SELECT ... FOR UPDATE NOWAIT` and related forms in chapter 03.18.

# 25. Why Long Transactions Are Dangerous

Consider:

```text
BEGIN
 |
 +-- lock order row
 |
 +-- compute pricing
 |
 +-- call external service
 |
 +-- generate report
 |
 +-- wait for another service
 |
 +-- UPDATE
 |
 +-- COMMIT
```

Even if each individual SQL statement is fast, the transaction lifetime may be very long.

Consequences can include:

- longer lock ownership;
- larger blocking windows;
- more lock queues;
- stale application state;
- longer-lived snapshots;
- vacuum cleanup constraints from old transactions;
- larger rollback cost;
- higher probability of conflict and timeout.

The fix is generally not “increase timeout.” The fix is to reduce the critical section and transaction lifetime where correctness permits.

---

# 26. Lock Amplification

One of the most important production concepts is **lock amplification**.

Suppose one slow transaction holds a lock required by 20 requests.

```text
one slow transaction
        |
        +---- 20 waiting requests
                    |
                    +---- connection pool fills
                              |
                              +---- unrelated requests wait
                                        |
                                        +---- API latency spikes
```

The original database action may consume only one backend session, but the resulting wait queue can consume a large part of the service's connection pool.

This creates a chain:

```text
slow critical section
 -> lock contention
 -> connection retention
 -> pool exhaustion
 -> request queueing
 -> latency amplification
```

This is why database locks are also an application-capacity problem.

---

# 27. Node.js / NestJS: The Connection-Pool Trap

A transaction must use the same database connection for all statements in the transaction.

Bad pattern:

```ts
await dataSource.query('BEGIN');
await repository.update(...);
await repository.query(...);
await dataSource.query('COMMIT');
```

Depending on the abstraction, these calls may not all use the same physical connection.

Then the application thinks it has:

```text
one transaction
```

while PostgreSQL actually sees:

```text
connection A: BEGIN
connection B: UPDATE
connection C: COMMIT
```

That is not one transaction.

Good pattern:

```text
checkout one client
      |
BEGIN
      |
all SQL through same client
      |
COMMIT / ROLLBACK
      |
release client
```

With `node-postgres`, this normally means acquiring a `PoolClient` and using that client throughout the transaction.

With NestJS/ORM abstractions, use the transaction manager/query runner/session supplied by that abstraction and verify that every operation participates in the same physical transaction.

---

# 28. Connection Pool Exhaustion From Lock Contention

Imagine:

```text
pool size = 20
```

A transaction holds a hot-row lock for 4 seconds.

Twenty requests can become blocked while consuming or waiting on pool clients.

Now:

```text
DB lock contention
       ↓
clients occupied
       ↓
pool has no free connections
       ↓
new requests queue before reaching PostgreSQL
```

The symptom can therefore appear as:

```text
“Database connection problem”
```

when the root cause is actually:

```text
lock contention
```

Evidence should distinguish these stages.

# 29. Atomic SQL vs Explicit Locking

Many applications reach for:

```text
SELECT row
check condition in JavaScript
UPDATE row
```

then add locks after discovering race conditions.

Sometimes the better design is to make the operation atomic in one SQL statement.

Example:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0
RETURNING quantity;
```

This can be much simpler than:

```sql
SELECT quantity ... FOR UPDATE;
-- application check
UPDATE ...;
```

The right question is not:

> “Where should I add a lock?”

It is:

> **“What is the smallest database operation that makes the invariant atomic?”**

Explicit locks are often valuable, but they should not compensate for avoidable multi-step logic.

# 30. Wrong Implementation — Lock Everything

A novice “safe” strategy:

```sql
BEGIN;
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
-- do work
COMMIT;
```

## Why It Looks Reasonable

Nothing else can interfere.

## Why It Fails

The application has converted concurrency into serialization across the entire table.

Consequences:

- unrelated requests block;
- throughput collapses;
- latency becomes workload-wide;
- the lock becomes a single bottleneck;
- operational risk increases.

## Improved Approach

Protect only the resource needed by the invariant, using the weakest appropriate mechanism.

Possible choices include:

```text
single atomic UPDATE
row-level lock
unique constraint
advisory lock
SERIALIZABLE transaction
explicit table lock
```

Each solves a different problem.

---

# 31. Wrong Implementation — Assume `SELECT` Locks Rows

This pattern is also wrong as a general statement:

```sql
SELECT * FROM inventory WHERE id = 7;
```

followed by:

> “The row is now locked because I selected it.”

A normal `SELECT` is not an application-level row lock.

When row locking is actually required, later chapters will use:

```sql
SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE;
```

The distinction is fundamental.

---

# 32. Wrong Implementation — Hold Locks During Business Logic

Bad architecture:

```text
BEGIN
SELECT ... FOR UPDATE
  |
  +-- calculate pricing
  +-- call API
  +-- generate PDF
  +-- send email
  +-- wait 1.8s
UPDATE
COMMIT
```

Why it fails:

```text
lock lifetime ≈ transaction lifetime
```

You have made unrelated application work part of the database critical section.

Better:

```text
prepare data
perform external work when safe
BEGIN
small critical section
atomic database change
COMMIT
```

The exact sequence depends on the business invariant and whether the external operation itself must be transactional.

---

# 33. Wrong Implementation — Retry Every Lock Error

A common AI-generated pattern is:

```ts
for (;;) {
  try {
    await doTransaction();
    break;
  } catch {
    continue;
  }
}
```

This is dangerous.

Not every lock-related failure is safely retryable.

Distinguish:

```text
serialization failure
lock timeout
deadlock
statement timeout
permission failure
constraint violation
business conflict
```

Retry policy must be based on error semantics.

An infinite retry loop can turn a transient contention problem into a self-sustaining production incident.

# 34. Lock Ordering

Deadlock resistance starts with deterministic resource ordering.

Suppose:

```text
Transaction A:
lock customer
lock order

Transaction B:
lock order
lock customer
```

Potential cycle:

```text
A holds customer -> waits for order
B holds order    -> waits for customer
```

A strong rule is:

```text
Always acquire resources in the same global order.
```

For example:

```text
tenant
→ customer
→ order
→ order_item
```

Then both transactions follow:

```text
customer first
then order
```

This does not eliminate every deadlock, but it removes an important class of lock-order cycles.

Chapter 03.15 is dedicated to lock ordering.

# 35. `pgrowlocks` for Row-Locking Investigation

When row-level lock information itself must be inspected, PostgreSQL provides the `pgrowlocks` extension.

Example:

```sql
CREATE EXTENSION pgrowlocks;

SELECT *
FROM pgrowlocks('orders');
```

Its output can expose tuple identifiers, locker IDs, row-lock modes, and backend PIDs. PostgreSQL documents that `pgrowlocks` scans rows and can be expensive on large tables; it is therefore a diagnostic tool, not a normal application query. citeturn989323search4

Operational principle:

> **Use heavyweight diagnostic tooling selectively and understand its own observation cost.**

# 36. Lock Monitoring Query — Human-Friendly View

A useful operational query is:

```sql
SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.state,
    a.wait_event_type,
    a.wait_event,
    now() - a.xact_start AS xact_age,
    now() - a.query_start AS query_age,
    l.locktype,
    l.mode,
    l.granted,
    CASE
        WHEN l.relation IS NOT NULL THEN l.relation::regclass::text
        ELSE NULL
    END AS relation,
    a.query
FROM pg_stat_activity a
JOIN pg_locks l
  ON l.pid = a.pid
WHERE l.granted = false
ORDER BY a.query_start;
```

Use it to answer:

```text
Who is waiting?
What mode?
On what object?
For how long?
Which transaction owns the session?
What query is running?
```

Then reconstruct the blocking chain.

# 37. Production Incident Pattern

### Symptom

```text
API p95: 120 ms -> 4.2 s
DB CPU: 28%
Pool utilization: 100%
```

A bad response is:

> “Database CPU is low, so the database is fine.”

Correct next step:

```text
inspect wait events
        ↓
find lock waits
        ↓
identify blockers
        ↓
inspect xact_start
        ↓
inspect blocking query
        ↓
measure lock duration
```

Suppose the blocker is:

```text
BEGIN
UPDATE settlement_jobs ...
-- waits on external service
-- 6.3 seconds
COMMIT
```

Root cause:

```text
external latency
→ extended transaction
→ long lock ownership
→ queued requests
→ pool saturation
→ API latency
```

The correct fix is architectural, not merely increasing the connection pool.

# 38. Security Implications

Locks are also a security boundary in multi-tenant systems when they protect tenant-scoped invariants.

A dangerous design can allow one tenant's workflow to hold a broad shared-table lock for a long time.

Consequences:

- cross-tenant availability impact;
- noisy-neighbor amplification;
- denial-of-service through contention;
- operational starvation.

For shared multi-tenant tables, ask:

```text
What resource is actually shared?
Can the critical section be tenant-scoped?
Can an atomic statement replace a broad lock?
Can partitioning reduce contention?
Could one tenant monopolize the hot resource?
```

Locks do not automatically provide tenant isolation. Authorization, RLS, constraints, and correct predicates still matter.

# 39. Performance Model

A simplified transaction latency model is:

```text
transaction latency
=
CPU
+
I/O
+
lock wait
+
other wait events
+
network/client delays
```

For a lock-heavy workload, an especially useful decomposition is:

```text
service time
+
queueing time
```

A database can have low CPU and still be slow because sessions are spending most of their time waiting.

Therefore measure:

```text
lock-wait duration
blocked-session count
transaction duration
query duration
pool utilization
throughput
p95/p99 latency
```

Do not optimize lock contention by guessing.

# 40. EXPLAIN and Locking

`EXPLAIN` does not itself answer all locking questions, but it helps identify why the locked critical section is expensive.

Example:

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders
SET status = 'PAID'
WHERE tenant_id = 42
  AND id = 9001;
```

If the update scans a huge relation to find a single target row, the time spent holding relevant locks may increase.

Therefore the chain can be:

```text
poor predicate/indexing
→ longer statement
→ longer lock acquisition/ownership window
→ more contention
```

The lock problem may therefore be partly a query-plan problem.

Lock tuning and query tuning cannot always be separated.

---

# 41. Indexes and Lock Contention

An index can reduce the work needed to find the target rows of an update or delete.

For a hot-row workload:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE tenant_id = $1
  AND sku = $2;
```

the indexing strategy can affect how quickly PostgreSQL locates the target rows and completes the statement.

However:

> **Adding an index does not automatically eliminate lock contention.**

If 500 requests all need the same row, they still logically contend for that resource.

The index can make the critical section shorter without making the shared invariant disappear.

# 42. Locking Decision Framework

Before adding a lock, ask in order:

```text
1. What invariant am I protecting?
2. Can one atomic SQL statement protect it?
3. Can a constraint protect it?
4. Can MVCC + current isolation level protect it?
5. Do I need a row lock?
6. Do I need a table lock?
7. Would SERIALIZABLE better express the invariant?
8. Is an advisory lock appropriate?
9. What is the maximum lock lifetime?
10. What is the retry/failure behavior?
11. How will I observe contention?
12. Can one tenant/workload monopolize the resource?
```

This prevents “add `FOR UPDATE` everywhere” architecture.

# 43. Example — Inventory Reservation

Requirement:

```text
Never sell more stock than is available.
```

Naive approach:

```text
SELECT quantity
if quantity > 0:
    UPDATE quantity = quantity - 1
```

Why it fails:

```text
T1 reads 1
T2 reads 1
T1 decrements
T2 decrements
```

Possible improved design:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0
RETURNING quantity;
```

Now the state transition and condition are evaluated together.

An explicit row lock may still be appropriate when the business workflow requires multiple dependent operations.

Solution pattern:

```text
Naive Approach
→ check then act

Why It Fails
→ race window

Improved Approach
→ atomic UPDATE

Why It Works
→ database performs conditional state transition as one operation

Production Considerations
→ inspect affected-row count, indexes, transaction scope, retries

Alternative
→ SELECT ... FOR UPDATE

Trade-Off
→ explicit locking gives more procedural control but increases lock-management complexity
```

# 44. Example — Order State Transition

Requirement:

```text
Only one worker may finalize an order at a time.
```

Possible atomic approach:

```sql
UPDATE orders
SET status = 'PROCESSING',
    worker_id = $2
WHERE id = $1
  AND status = 'READY'
RETURNING *;
```

If zero rows are returned:

```text
another worker already transitioned it
or
it was never ready
or
it no longer exists
```

No explicit lock is necessarily required for the state claim itself.

For a larger workflow where the worker must inspect related rows and keep them stable, a row-locking transaction may be appropriate.

The invariant determines the mechanism.

# 45. Example — Financial Reconciliation

Suppose the application wants to compare balances across multiple tables while concurrent changes are occurring.

The problem may be larger than a single row.

A repeatable-read snapshot can provide a stable historical view, but a business process asking:

> “What is the current indisputable state of these tables right now?”

may require explicit locking of all relevant tables in a carefully designed order.

PostgreSQL's documentation specifically discusses this class of global consistency checks and notes that explicit table locks can be appropriate when current reality must be protected from concurrent changes; in repeatable-read mode, lock acquisition should occur before the snapshot is frozen when relying on that technique. citeturn989323search8

This is an excellent example of why:

```text
isolation level
+
lock timing
+
transaction timing
```

must be reasoned about together.

Question:

# 48. Testing Lock Behavior

Concurrency bugs should be reproduced with at least two sessions.

### Laboratory setup

Session A:


# 53. Interview Questions

## Junior

### Q1. Why do databases use locks?

Weak answer:
> To stop multiple users accessing the same data.

Acceptable answer:
> To coordinate incompatible concurrent operations.

Strong answer:
> Locks enforce ordering or mutual exclusion where MVCC alone does not provide the required coordination.

Expert answer:
> PostgreSQL combines MVCC visibility with multiple locking mechanisms. Locks are compatibility rules over different lockable resources and are essential for coordinating write conflicts, schema changes, transaction dependencies, and explicit application-level critical sections.

### Q2. Does PostgreSQL use locks even with MVCC?

Yes. MVCC and locks solve different concurrency problems.

---

## Mid-Level

### Q3. What is the difference between a table lock and a row lock?

A table lock coordinates access at relation scope; a row lock coordinates access to specific tuples.

### Q4. What does `pg_locks` show?

It exposes currently held and requested locks over PostgreSQL's lockable resources, including whether a lock is granted. citeturn989323search0

### Q5. Why might a low-CPU database still have high latency?

Because sessions may be waiting on locks or other resources rather than consuming CPU.

---

## Senior

### Q6. Why can a short update create a large API outage?

Because a blocked hot resource can create a queue that consumes connection-pool capacity and amplifies latency across requests.

### Q7. Why is `FOR UPDATE` not always the best fix for a race condition?

Because an atomic state transition, constraint, or stronger isolation strategy may solve the invariant more simply and with less lock management.

---

## Staff / Principal

### Q8. When would you prefer a unique constraint over a lock?

When the invariant is fundamentally uniqueness and can be enforced declaratively. The constraint provides a durable database-level guarantee without requiring application-managed critical sections.

### Q9. How would you prove a lock is causing the incident?

Correlate request latency with database wait events, identify waiting sessions, reconstruct blockers from `pg_locks` and `pg_stat_activity`, measure lock duration, and reproduce the contention under controlled load.

### Q10. Why is “use stronger locks” a poor architectural rule?

Because stronger locks expand the contention domain. They may eliminate one race while reducing system throughput, increasing queueing, and creating new failure modes.

---

# 54. Trick Questions

### “MVCC means readers never block.”

Too broad. Ordinary MVCC reads often avoid waiting for row writers, but relation-level locks, explicit locking clauses, transaction dependencies, DDL, and other mechanisms can create waits.

### “`ROW EXCLUSIVE` is a row-level table lock.”

Incorrect. The mode is a table-level lock; its name reflects typical usage and intent, not lock granularity. citeturn989323search33

### “A waiting lock means the database is deadlocked.”

Incorrect. Waiting is ordinary blocking. Deadlock requires a cycle of dependencies.

### “More connections increase throughput.”

Not necessarily. More connections can increase the number of sessions competing for the same locked resource and can amplify queueing.

# 57. Final Mental Model

Remember this hierarchy:

```text
PostgreSQL concurrency
        |
        +-- MVCC
        |     |
        |     +-- visibility
        |     +-- row versions
        |     +-- snapshots
        |
        +-- Locks
              |
              +-- table / relation locks
              +-- row-level locking
              +-- transaction-ID coordination
              +-- other internal resources
              +-- advisory locks
```

And this workflow:

```text
Need correctness
      |
      v
Identify invariant
      |
      v

      |
      +-- yes --> prefer atomic database operation
      |
      +-- no
           |
           v
Can a constraint enforce it?
      |
      +-- yes --> use declarative constraint
      |
      +-- no
           |
           v
Choose appropriate concurrency mechanism
      |
      +-- row lock
      +-- table lock
      +-- SERIALIZABLE
      +-- advisory lock
      |
      v
Bound transaction / lock lifetime
      |
      v
Observe contention
      |
      v
Load test
      |
      v
Measure and refine
```

The deepest lesson is:

> **A lock is not a synonym for safety. A lock is a concurrency-control mechanism whose value depends entirely on what resource it protects, which conflicting operations it excludes, how long it is held, and whether that matches the business invariant.**

PostgreSQL's current documentation supports this broader view: explicit locks supplement MVCC where needed, table-level modes are defined by conflict relationships, `pg_locks` exposes active and waiting locks, and transaction processing also coordinates through transaction IDs and row-level state. citeturn989323search10turn989323search0turn989323search2
