# 03.1 — Transaction Fundamentals

> **Phase 03 — Transactions & Concurrency**
>
> A production PostgreSQL system is not correct merely because each individual SQL statement is correct. Correctness often depends on a group of statements behaving as one atomic unit. This chapter establishes the foundation for reasoning about that unit: the transaction.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to:

- define a database transaction precisely at multiple levels;
- distinguish a statement from a transaction and a transaction block;
- explain why atomicity matters to application correctness;
- use `BEGIN`, `COMMIT`, `ROLLBACK`, and savepoints correctly;
- reason about partial failure inside a transaction;
- understand PostgreSQL's implicit single-statement transactions;
- recognize the effect of autocommit in clients and drivers;
- design transaction boundaries around business invariants rather than arbitrary method boundaries;
- understand what a transaction does **not** guarantee yet, especially under concurrency;
- build safe transaction wrappers in Node.js/NestJS applications;
- debug transaction-state errors instead of treating them as generic database failures;
- understand transaction identity at a high level and why transaction lifetime matters;
- distinguish database atomicity from distributed-system atomicity;
- prepare the mental model required for ACID, MVCC, isolation, locks, deadlocks, and serialization in later chapters.

This chapter is intentionally foundational. It does not attempt to fully teach MVCC, isolation levels, row locking, deadlocks, or serialization anomalies. Those topics build on the transaction model established here.

# 2. Transaction — Three Definitions

## 2.1 Simple definition

A **transaction** is a group of database operations treated as one unit of work.

Either the intended unit succeeds and is committed, or its changes are rolled back rather than leaving a partially completed unit behind.

---

## 2.2 Engineering definition

A transaction is a database execution context that gives a defined set of statements a common atomic outcome and transaction-level semantics.

For a transaction block such as:

```sql
BEGIN;

statement_a;
statement_b;
statement_c;

COMMIT;
```

PostgreSQL treats the three operations as belonging to the same transaction. If the transaction is rolled back, the transaction's database changes are discarded.

PostgreSQL's documentation describes the essential property as bundling multiple steps into an all-or-nothing operation and notes that intermediate states are not visible as committed states to other concurrent transactions. citeturn661594search0

---

## 2.3 Expert definition

A transaction is a boundary within PostgreSQL's transaction-processing system that associates database work with transaction identity, visibility rules, failure semantics, commit/abort semantics, and resource/lifetime consequences.

That definition matters because a transaction is more than:

> "some SQL I put between `BEGIN` and `COMMIT`."

It is also a unit that interacts with:

- transaction identifiers;
- snapshots and visibility;
- locks;
- constraints;
- WAL and durability;
- vacuum horizons;
- replication behavior;
- connection/session state;
- application error handling;
- transaction retries;
- transaction duration.

We will progressively expose those layers through the rest of Phase 03.

# 3. The Fundamental Problem Transactions Solve

Consider a money transfer.

We have:

```text
Alice:  ₹10,000
Bob:    ₹5,000
```

A transfer of ₹2,000 consists conceptually of:

1. subtract ₹2,000 from Alice;
2. add ₹2,000 to Bob.

Without a transaction, these are two separate database operations.

Suppose operation 1 succeeds:

```text
Alice:  ₹8,000
Bob:    ₹5,000
```

Then the process crashes before operation 2.

The database now contains an invalid business state.

With a transaction:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 2000
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 2000
WHERE account_id = 2;

COMMIT;
```

If a failure occurs before commit and the transaction is rolled back, the transfer does not partially persist.

This is the first major mental model:

> **A transaction groups state changes that must succeed or fail together.**

---

# 4. Transaction as an Invariant Boundary

A stronger way to think about transactions is:

> **A transaction protects the transition between valid database states.**

Suppose the invariant is:

```text
Total money across accounts is conserved.
```

State A:

```text
Alice = 10,000
Bob   = 5,000
Total = 15,000
```

State B:

```text
Alice = 8,000
Bob   = 7,000
Total = 15,000
```

The intermediate state:

```text
Alice = 8,000
Bob   = 5,000
Total = 13,000
```

should not become a durable application state.

The transaction therefore represents:

```text
Valid State A
     ↓
[ transaction work ]
     ↓
Valid State B
```

rather than:

```text
Valid State A
     ↓
Partial State
     ↓
Potential crash
     ↓
Invalid State
```

This is one of the most important transaction mental models for backend engineering.

---

# 5. PostgreSQL's Transaction Model

PostgreSQL treats every SQL statement as executing within a transaction.

When you do not explicitly start a multi-statement transaction, a single statement effectively forms its own transaction and is committed if successful. PostgreSQL documentation explicitly describes this as the implicit single-statement behavior. citeturn661594search0turn249139search5

Therefore:

```sql
INSERT INTO users(name) VALUES ('A');
```

is not "outside a transaction."

It is effectively:

```text
BEGIN
  INSERT
COMMIT
```

as one statement transaction, from the application's conceptual perspective.

This distinction is crucial.

## Explicit transaction

```sql
BEGIN;

INSERT ...;
UPDATE ...;
DELETE ...;

COMMIT;
```

## Implicit single-statement transaction

```sql
INSERT ...;
```

Both execute transactionally, but only the explicit transaction groups multiple statements into one atomic unit.

---

# 6. `BEGIN`

`BEGIN` starts an explicit transaction block.

```sql
BEGIN;
```

Equivalent SQL spelling:

```sql
START TRANSACTION;
```

PostgreSQL documents these as starting a transaction block. Transaction characteristics such as isolation level, read/write mode, and deferrable mode can also be supplied when the transaction begins. citeturn661594search28

Example:

```sql
BEGIN;

INSERT INTO orders(customer_id, total)
VALUES (101, 2500);

INSERT INTO order_items(order_id, product_id, quantity)
VALUES (5001, 55, 2);

COMMIT;
```

Until the transaction commits, the transaction's changes are not committed as durable database state visible to other transactions.

---

# 7. `COMMIT`

`COMMIT` successfully ends the current transaction and makes its changes durable according to PostgreSQL's durability configuration and commit semantics.

```sql
COMMIT;
```

Engineering meaning:

```text
"The work inside this transaction is accepted as the new committed database state."
```

Do not interpret `COMMIT` as merely:

> "save the last SQL statement."

It commits the whole current transaction.

Example:

```sql
BEGIN;

INSERT INTO orders (...);
INSERT INTO order_items (...);
UPDATE inventory ...;
INSERT INTO audit_log (...);

COMMIT;
```

All of those changes belong to the same transaction.

---

# 8. `ROLLBACK`

`ROLLBACK` aborts the current transaction.

```sql
ROLLBACK;
```

Conceptually:

```text
Transaction started
      ↓
Several changes performed
      ↓
Something fails / business rule rejects work
      ↓
ROLLBACK
      ↓
Transaction changes discarded
```

PostgreSQL's transaction tutorial explicitly describes rollback as cancelling the updates performed so far in the transaction. citeturn661594search0

Example:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE account_id = 2;

ROLLBACK;
```

After rollback, neither update is part of the committed database state.

---

# 9. The All-or-Nothing Model

A useful abstraction is:

```text
             Transaction
                  │
       ┌──────────┴──────────┐
       │                     │
    SUCCESS                FAILURE
       │                     │
    COMMIT                ROLLBACK
       │                     │
Changes persist       Changes discarded
```

That is the beginner model.

The expert model is slightly stronger:

```text
Application intent
      ↓
Transaction begins
      ↓
Database operations
      ↓
Constraints / triggers / business checks
      ↓
Commit decision
      ↓
Committed state OR aborted state
```

Later we will add concurrency semantics to this graph.

# 10. Statement vs Transaction

This distinction should become automatic.

## Statement

One SQL command:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 10;
```

## Transaction

A collection of statements treated as one atomic unit:

```sql
BEGIN;

UPDATE inventory ...;
INSERT INTO sales ...;
INSERT INTO audit_log ...;

COMMIT;
```

## Transaction block

The SQL-visible sequence between transaction start and transaction end.

In practical backend discussion, people often use "transaction" and "transaction block" almost interchangeably. At advanced levels, keep the distinction available because the database internals, client behavior, and application framework may expose slightly different abstractions.

---

# 11. Why "One Request = One Transaction" Is Not a Law

A common backend rule of thumb is:

> one HTTP request = one database transaction.

This is often useful, but it is not a database law.

Consider:

```text
HTTP request
 ├─ validate input
 ├─ call external payment API
 ├─ update database
 └─ send email
```

A database transaction should generally not remain open while waiting for an external HTTP request.

Poor design:

```text
BEGIN
  database operation
  ↓
  call external API for 8 seconds
  ↓
  database operation
COMMIT
```

This can create unnecessarily long transaction lifetimes and may hold resources while the application waits on something outside PostgreSQL.

Better design depends on the business workflow, for example:

```text
Validate
   ↓
Persist intent / pending state
   ↓
Commit
   ↓
External operation
   ↓
Persist result in a later transaction
```

Or use an outbox/workflow architecture.

The transaction boundary should represent **database atomicity requirements**, not blindly mirror the HTTP lifecycle.

---

# 12. Designing the Correct Transaction Boundary

Ask these questions:

### Question 1
Which changes must succeed together?

### Question 2
Which database invariants must hold after the operation?

### Question 3
Can the operation be safely split into multiple committed states?

### Question 4
Does the unit call an external system?

### Question 5
Could the transaction be held open for user interaction, network I/O, file processing, or queue waits?

### Question 6
What should happen if step 7 fails after steps 1–6 succeed?

### Question 7
Can a retry safely repeat this transaction?

Those questions produce a much better boundary than:

```text
"Put the whole service method inside a transaction because that's best practice."
```

# 13. Example — Order Creation

Suppose an order creation workflow is:

1. create order header;
2. create order items;
3. reserve inventory;
4. calculate/store totals;
5. record audit event.

A plausible transaction is:

```sql
BEGIN;

INSERT INTO orders (...)
VALUES (...)
RETURNING order_id;

INSERT INTO order_items (...)
VALUES (...);

UPDATE inventory
SET available_qty = available_qty - 2
WHERE product_id = 100
  AND available_qty >= 2;

INSERT INTO audit_log (...)
VALUES (...);

COMMIT;
```

But there is a hidden issue.

If the inventory update affects zero rows, the transaction may still commit unless the application explicitly treats that as failure or the database design creates a constraint that rejects the invalid state.

This demonstrates a key lesson:

> **A transaction gives atomicity to the work you perform. It does not automatically understand your business intent.**

You must define what constitutes success.

For example:

```sql
UPDATE inventory
SET available_qty = available_qty - 2
WHERE product_id = 100
  AND available_qty >= 2
RETURNING product_id, available_qty;
```

Then the application verifies that exactly one expected row was updated.

Later, concurrency chapters will show why this pattern can be stronger than a separate read-then-write sequence.

# 14. Transaction Errors and the Aborted Transaction State

One of the most important PostgreSQL behaviors for application developers:

> Once a statement causes an error inside an explicit transaction, the transaction enters an aborted state and cannot normally continue with ordinary SQL until it is rolled back or recovered through a savepoint.

Example:

```sql
BEGIN;

INSERT INTO users(id, email)
VALUES (1, 'a@example.com');

-- duplicate key error
INSERT INTO users(id, email)
VALUES (1, 'b@example.com');

SELECT * FROM users;
```

The `SELECT` does not simply continue as though the failed `INSERT` were an isolated error.

The transaction is failed.

The usual recovery is:

```sql
ROLLBACK;
```

or, for a localized failure, a savepoint pattern discussed below.

This behavior is foundational for driver-level transaction handling.

---

# 15. Savepoints

A savepoint creates a recovery point inside a transaction.

```sql
BEGIN;

INSERT INTO orders (...);

SAVEPOINT before_optional_step;

INSERT INTO optional_table (...);

ROLLBACK TO SAVEPOINT before_optional_step;

INSERT INTO another_table (...);

COMMIT;
```

PostgreSQL documents savepoints as allowing selective rollback of a portion of a transaction while preserving earlier work. citeturn249139search1turn249139search0

Mental model:

```text
BEGIN
 │
 ├─ Step A
 ├─ Step B
 │
 ├─ SAVEPOINT S
 │
 ├─ Step C
 ├─ Step D
 │
 └─ ROLLBACK TO S
      ↓
   Step C/D undone
   A/B retained
      ↓
   continue
      ↓
   COMMIT
```

---

# 16. `RELEASE SAVEPOINT`

Once you no longer need a savepoint, you can release it.

```sql
RELEASE SAVEPOINT before_optional_step;
```

This does **not** commit the outer transaction.

It simply removes that savepoint marker.

The distinction is critical:

```text
RELEASE SAVEPOINT
    ≠
COMMIT
```

PostgreSQL also notes that rolling back to or releasing a savepoint destroys later savepoints. citeturn249139search0

---

# 17. Savepoint Example — Optional Work

Suppose the core order must succeed, but an optional metadata enrichment should not invalidate the core transaction.

```sql
BEGIN;

INSERT INTO orders (...);
INSERT INTO order_items (...);

SAVEPOINT optional_metadata;

INSERT INTO order_metadata (...);

-- optional operation fails
ROLLBACK TO SAVEPOINT optional_metadata;

COMMIT;
```

This can be valid architecture when the optional part genuinely belongs to the same overall atomic workflow but is independently discardable.

However, do not use savepoints to hide serious invariant violations.

Bad design:

```text
Core database invariant fails
↓
Rollback to savepoint
↓
Commit anyway
```

A savepoint is not a mechanism for pretending a failed business requirement did not happen.

---

# 18. Nested Transactions — The Important Reality

Many application frameworks expose APIs that look like:

```ts
transaction(() => {
  transaction(() => {
    ...
  });
});
```

Do not assume this means PostgreSQL has independent nested transactions.

PostgreSQL uses transactions and subtransactions/savepoints rather than arbitrary independently committing nested transactions.

At the application level, an ORM may emulate nested transaction semantics through savepoints.

Therefore always ask:

```text
Does the framework's "nested transaction" mean:
    a real independent transaction?
    or
    a savepoint/subtransaction inside the same transaction?
```

This distinction becomes important when reasoning about commit, rollback, locks, and visibility.

---

# 19. Autocommit

Autocommit describes client behavior around transaction boundaries.

In common PostgreSQL client usage, when autocommit is enabled, individual statements commit independently unless you explicitly begin a transaction.

Conceptually:

```text
Autocommit ON

INSERT → COMMIT
UPDATE → COMMIT
DELETE → COMMIT
```

Versus:

```text
BEGIN
INSERT
UPDATE
DELETE
COMMIT
```

All three changes belong to one transaction in the second case.

`psql` documents its default `AUTOCOMMIT` behavior and explains that turning it off causes it to issue an implicit `BEGIN` before commands that are not already in a transaction block, subject to exceptions. citeturn661594search8

Do not project `psql`'s client behavior directly onto every application driver. Client libraries may automatically issue transaction commands or expose their own transaction APIs. PostgreSQL's documentation explicitly warns that client libraries may issue `BEGIN` and `COMMIT` automatically. citeturn661594search0

---

# 20. The Connection Matters

A transaction is associated with a database session/connection.

This creates a critical backend rule:

> **All statements that belong to one transaction must execute on the same database connection.**

Conceptually:

```text
Connection A
BEGIN
UPDATE
INSERT
COMMIT
```

works.

But:

```text
Connection A
BEGIN

Connection B
UPDATE

Connection A
COMMIT
```

is not the same transaction.

A common application bug is to create a transaction using one connection and accidentally execute some operations through a normal/global repository that obtains another pooled connection.

The application then believes:

```text
"Everything is inside one transaction."
```

while PostgreSQL sees:

```text
Transaction A
Transaction B
```

This is one of the most important Node.js/NestJS transaction bugs to learn to recognize.

---

# 21. Connection Pooling and Transaction Leakage

Connection pools reuse database sessions.

A dangerous sequence is:

```text
Request A
  ↓
borrow connection
  ↓
BEGIN
  ↓
error
  ↓
connection accidentally returned without ROLLBACK
  ↓
Request B borrows same connection
```

Now Request B may inherit unexpected transaction/session state depending on what the client and driver did.

Therefore a robust transaction wrapper must guarantee:

```text
BEGIN
  work
COMMIT
```

or:

```text
BEGIN
  work fails
ROLLBACK
```

before the connection returns to the pool.

This is not optional cleanup. It is correctness infrastructure.

---

# 22. Node.js/NestJS Transaction Pattern

Frameworks differ, but the conceptual structure should look like:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  await client.query(/* statement 1 */);
  await client.query(/* statement 2 */);
  await client.query(/* statement 3 */);

  await client.query('COMMIT');
} catch (error) {
  try {
    await client.query('ROLLBACK');
  } catch (rollbackError) {
    // Log rollback failure with transaction/request context.
  }

  throw error;
} finally {
  client.release();
}
```

The important properties are:

```text
same client
      ↓
BEGIN
      ↓
all transactional statements
      ↓
COMMIT or ROLLBACK
      ↓
release connection
```

Do not substitute:

```ts
await pool.query('BEGIN');
await pool.query('UPDATE ...');
await pool.query('COMMIT');
```

for a transaction wrapper unless the pool API specifically guarantees all three calls use the same session. With a general connection pool, separate calls may use different connections.

The safe primitive is usually an explicitly checked-out client/connection.

# 23. Transaction Helper Design

A reusable abstraction is valuable:

```ts
async function withTransaction<T>(
  pool: Pool,
  work: (client: PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();

  try {
    await client.query('BEGIN');

    const result = await work(client);

    await client.query('COMMIT');

    return result;
  } catch (error) {
    try {
      await client.query('ROLLBACK');
    } catch (rollbackError) {
      // Log rollback error without hiding original failure.
    }

    throw error;
  } finally {
    client.release();
  }
}
```

Usage:

```ts
await withTransaction(pool, async (client) => {
  const order = await client.query(/* create order */);
  await client.query(/* create items */);
  await client.query(/* reserve inventory */);
});
```

The exact implementation will differ by library, but the invariant should remain:

> **One transaction = one connection/session context for the whole transaction.**

---

# 24. Transaction Scope and External Calls

A common anti-pattern:

```ts
await withTransaction(pool, async (client) => {
  await client.query('INSERT INTO payments ...');

  await fetch('https://payment-provider.example/charge');

  await client.query('UPDATE payments ...');
});
```

Why dangerous?

Because the transaction may remain open while the application waits for network I/O.

This can increase:

- transaction lifetime;
- lock duration where locks exist;
- resource retention;
- contention;
- MVCC cleanup pressure;
- exposure to client disconnects/timeouts.

Later chapters will make the MVCC and lock implications precise.

A safer architecture often persists an intent first:

```text
Transaction 1
  create payment_attempt = pending
  commit

External provider call

Transaction 2
  record success/failure
  commit
```

Or use a reliable outbox/workflow mechanism.

But do not blindly split transactions either. Splitting changes atomicity semantics and can create new consistency states. Architecture must match the business invariant.

# 25. Transactions Do Not Automatically Make Business Logic Safe Under Concurrency

This is one of the biggest misconceptions.

Suppose two requests both execute:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE account_id = 1;

-- application checks balance

UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

COMMIT;
```

Two transactions can still interact in ways that produce anomalies depending on isolation and locking semantics.

The existence of `BEGIN` alone does **not** mean:

- no race conditions;
- no lost updates;
- no write skew;
- no deadlocks;
- serial execution;
- no stale reads.

Those topics belong to later chapters in Phase 03.

The right progression is:

```text
Transaction
   ↓
ACID
   ↓
MVCC
   ↓
Isolation
   ↓
Locks
   ↓
Concurrency anomalies
```

# 26. Transaction Identity — First-Principles View

At the PostgreSQL internals level, every executing transaction has transaction identity information.

PostgreSQL documents both virtual transaction identifiers and regular transaction IDs. A virtual transaction ID is associated with a backend and local transaction sequence; a non-virtual `TransactionId` is assigned when a transaction first writes to the database. citeturn661594search3

You do not need to memorize implementation details yet, but remember:

```text
transaction ≠ abstract application idea only
```

It is represented in PostgreSQL's transaction machinery.

This later explains why transaction IDs, snapshots, vacuum, and old transactions matter operationally.

---

# 27. Transaction Lifetime Is a Production Concern

A short transaction:

```text
BEGIN
  several quick statements
COMMIT
```

is generally easier to reason about and less disruptive to concurrency than a transaction left open for a long time.

Long transactions can be created accidentally by:

- slow external API calls;
- debugging sessions;
- idle application code;
- interactive SQL clients;
- failed request cleanup;
- connection leaks;
- background jobs processing too much work in one transaction;
- waiting for user input.

Later we will connect long-running transactions to MVCC cleanup, transaction ID horizons, locking, and bloat.

For now, remember:

> **A transaction's lifetime is an operational resource, not just a logical boundary.**

# 28. What Commit Actually Means

A beginner may think:

```text
COMMIT = data is now permanently on disk
```

The more precise model is:

```text
COMMIT
  ↓
transaction accepted as committed
  ↓
PostgreSQL durability machinery applies
  ↓
WAL / flush / synchronous-commit settings determine durability behavior
```

PostgreSQL's documentation distinguishes durability from transaction semantics and notes that settings such as `synchronous_commit` can trade commit durability guarantees for performance. citeturn661594search11

Therefore do not reduce commit to a simple filesystem metaphor.

Later chapters will examine WAL and durability in more depth.

# 29. Transaction Boundary vs Validation Boundary

These are related but not identical.

Example:

```text
BEGIN
create order
create item
update inventory
COMMIT
```

The transaction boundary says all these changes commit together.

But suppose the application validates inventory **before** the transaction:

```text
Check inventory = 5
↓
BEGIN
↓
reserve 5
↓
COMMIT
```

Another request could change the inventory between the check and the transaction.

Therefore:

> **A pre-transaction validation is not automatically a transactional invariant check.**

Later we will solve this class of problem with atomic updates, locking, isolation, and serialization techniques.

---

# 30. Transaction Boundary vs Authorization Boundary

Authorization often happens in the application:

```text
User requests transfer
↓
Application checks permission
↓
Transaction updates data
```

But the database transaction still needs to preserve data invariants independently of the authorization check.

A transaction is not an authorization mechanism.

Similarly:

```text
transaction ≠ authentication
transaction ≠ authorization
transaction ≠ audit trail
transaction ≠ workflow engine
```

Transactions are one foundational mechanism within a larger correctness architecture.

# 31. Production Pattern — Inventory Reservation

Suppose a product has:

```text
available_qty = 10
```

A sale requires 3 units.

The transaction may be:

```sql
BEGIN;

UPDATE inventory
SET available_qty = available_qty - 3
WHERE product_id = 42
  AND available_qty >= 3;

-- verify affected row count

INSERT INTO order_items (...);

COMMIT;
```

The important design choice is that the state transition and its precondition are coupled in one database operation.

Naive pattern:

```text
SELECT available_qty
↓
application compares qty
↓
UPDATE available_qty
```

Improved pattern:

```text
UPDATE ...
WHERE available_qty >= requested_qty
```

The latter reduces the gap between checking the condition and modifying the state.

It still needs careful concurrency reasoning, which later chapters will cover.

# 32. Production Pattern — Ledger Entry

Financial workflows typically require several related writes:

```text
journal
  ↓
journal_lines
  ↓
accounting metadata
  ↓
audit/evidence
```

The posting operation often needs a transaction so that a partially written journal does not become committed accounting truth.

Conceptually:

```sql
BEGIN;

INSERT INTO journals (...);
INSERT INTO journal_lines (...);
INSERT INTO journal_lines (...);
INSERT INTO posting_audit (...);

COMMIT;
```

But there are additional invariants:

```text
debits = credits
period is open
currency rules valid
source document valid
idempotency satisfied
```

A transaction provides the boundary for enforcing these conditions, but you must still implement the conditions through constraints, SQL predicates, locking, or application/database logic.

# 33. Wrong Implementation — Transaction Around Each Statement

Bad:

```text
BEGIN
insert order
COMMIT

BEGIN
insert item
COMMIT

BEGIN
update inventory
COMMIT
```

This is not one atomic order creation.

Failure after the first commit leaves partial state.

Improved:

```text
BEGIN
insert order
insert item
update inventory
insert audit
COMMIT
```

This demonstrates the difference between:

```text
multiple transactional operations
```

and:

```text
one transaction containing multiple operations
```

---

# 34. Wrong Implementation — Swallowing Errors

Bad:

```ts
try {
  await client.query('BEGIN');
  await client.query('INSERT ...');
  await client.query('UPDATE ...');
  await client.query('COMMIT');
} catch (error) {
  console.error(error);
  return null;
}
```

Problems:

- rollback may be skipped;
- connection may return to pool in an unsafe state;
- the caller may believe the business operation succeeded or was simply ignored;
- the original error can disappear from the API contract.

Improved:

```ts
try {
  await client.query('BEGIN');
  ...
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

Production code should also handle rollback failure without hiding the original failure.

---

# 35. Wrong Implementation — Mixing Transactional and Non-Transactional Clients

Bad:

```ts
await transactionClient.query('BEGIN');

await transactionClient.query('INSERT INTO orders ...');

await repository.save(orderItem); // may use another connection

await transactionClient.query('COMMIT');
```

The code visually suggests one transaction.

The actual database behavior may be:

```text
Connection A
  BEGIN
  INSERT order
  COMMIT

Connection B
  INSERT item
```

or another sequence depending on ORM behavior.

The correct pattern is to ensure every transactional operation receives the transaction-scoped client/entity manager/query runner provided by the framework.

---

# 36. Wrong Implementation — Holding a Transaction Across User Input

Never design:

```text
BEGIN
↓
Show form to user
↓
Wait 20 seconds
↓
User confirms
↓
UPDATE
↓
COMMIT
```

The transaction should almost always be completed within a controlled service operation rather than waiting for human interaction.

Instead:

```text
User interaction
     ↓
request
     ↓
short transaction
     ↓
commit
```

---

# 37. Wrong Implementation — Assuming Rollback Undoes External Side Effects

This is a critical distributed-systems boundary.

Suppose:

```text
BEGIN
INSERT payment
CALL external provider → $100 charged
UPDATE payment status
error
ROLLBACK
```

The database rollback can undo the database changes.

It does **not** automatically reverse an already completed external payment charge.

This means:

```text
Database transaction
        ≠
Universal transaction across the internet
```

External effects require separate compensation/idempotency/workflow strategies.

---

# 38. Transaction and Idempotency

Retries become important whenever a transaction fails or the client loses the response.

Consider:

```text
Client sends request
↓
DB transaction commits
↓
network response is lost
↓
client retries
```

The second execution must not blindly create duplicate business effects.

This is why serious transaction design often combines:

```text
transaction
+
unique business/idempotency key
+
constraint
+
retry-safe logic
```

Example:

```sql
CREATE UNIQUE INDEX uq_payment_idempotency
ON payments (idempotency_key);
```

The exact design depends on the business operation, but the transaction should be part of an idempotency strategy rather than considered a substitute for it.

---

# 39. Savepoints in Application Frameworks

Some drivers/ORMs expose nested transaction helpers or callback APIs.

A framework may implement:

```ts
transaction(async manager => {
  ...
});
```

and internally issue:

```sql
BEGIN;
...
COMMIT;
```

A nested transaction may become:

```sql
SAVEPOINT sp_1;
...
ROLLBACK TO SAVEPOINT sp_1;
```

rather than a separately committing transaction.

Never infer SQL behavior from an API name.

Inspect the driver's/ORM's transaction implementation and logs when the distinction matters.

# 40. Debugging Transaction Problems

When a production transaction behaves unexpectedly, collect evidence rather than guessing.

At minimum identify:

```text
request ID
transaction scope
connection/session identity
transaction begin time
transaction end time
commit/rollback outcome
SQL error code
SQLSTATE
application operation
```

For difficult cases inspect PostgreSQL transaction and lock state using server-side monitoring views.

PostgreSQL exposes transaction and lock information through its transaction-processing and locking facilities, including `pg_locks`. citeturn661594search13turn661594search6

A useful debugging question is:

> Did the failure happen before transaction start, inside the transaction, during commit, or after commit while processing the application response?

Those are different failure classes.

---

# 41. Failure Classification

## Class A — Validation failure before transaction

```text
No transaction state changed.
```

## Class B — Statement failure inside transaction

```text
Transaction may enter aborted state.
```

## Class C — Explicit rollback

```text
Transaction aborted intentionally.
```

## Class D — Commit failure

```text
Application must treat commit as unsuccessful unless confirmed otherwise.
```

## Class E — Commit succeeded, response failed

```text
Database may contain the change even though the client saw an error.
```

Class E is why idempotency and reconciliation matter.

---

# 42. Commit Ambiguity

Consider:

```text
Client → COMMIT
PostgreSQL commits
Network breaks
Client receives no response
```

From the application's viewpoint:

```text
"Did commit succeed?"
```

A timeout does not automatically mean rollback occurred.

The database may already have committed the transaction.

Therefore robust APIs should not assume:

```text
request timeout = transaction rollback
```

This is another reason why idempotency keys, unique constraints, status records, and reconciliation are essential in production systems.

---

# 43. Transactional Work vs Non-Transactional Work

A useful design table:

| Work | Usually inside DB transaction? | Reason |
|---|---:|---|
| create order row | yes | domain state |
| create order items | yes | order consistency |
| update inventory | often yes | atomic business invariant |
| write audit record | often yes | evidence for same DB event |
| send email via SMTP | no | external side effect |
| HTTP API call | usually no | unpredictable latency/external system |
| publish reliable domain event | often via outbox | coordinate DB state + messaging intent |
| expensive report generation | usually no | avoid long transaction |
| user interaction | no | transaction lifetime risk |

"Usually" is important. There is no universal rule.

---

# 44. Transaction Size

Transaction size is not merely the number of SQL statements.

Relevant dimensions include:

```text
rows touched
locks acquired
WAL generated
execution time
memory usage
index work
foreign-key checks
trigger work
external waits
replication effects
```

Example:

```text
1 SQL statement
UPDATE 50 million rows
```

is still a very large transaction if executed under one transaction.

Conversely:

```text
20 small statements
```

may be a modest transaction.

Therefore avoid simplistic statements such as:

> "Few queries means small transaction."

Measure the actual workload.

---

# 45. Batch Processing and Transactions

Suppose a background worker must process 1,000,000 records.

One giant transaction:

```text
BEGIN
process 1,000,000
COMMIT
```

can have undesirable operational consequences.

A batched approach may be:

```text
batch 1 → transaction
batch 2 → transaction
batch 3 → transaction
...
```

But batching changes semantics.

You now have multiple commit points.

If batch 7 fails:

```text
batches 1–6 are already committed
```

That may be correct for a queue/ETL workload but unacceptable for a business operation requiring all-or-nothing semantics.

The transaction boundary is therefore inseparable from business correctness.

---

# 46. Transactional DDL — Important PostgreSQL Characteristic

PostgreSQL supports transactional behavior for many schema changes, meaning many DDL commands can participate in transactions.

However, not every command is freely usable inside a normal transaction block, and some operations have special restrictions.

Never infer:

```text
"PostgreSQL has transactional DDL"
```

as:

```text
"Every DDL command can be wrapped in BEGIN/COMMIT without restrictions."
```

Migration tooling must respect command-specific transactional rules.

This is particularly important when designing schema deployment systems.

---

# 47. Transaction Characteristics

A transaction can also have properties such as:

```sql
BEGIN;

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION READ ONLY;

...

COMMIT;
```

PostgreSQL supports transaction isolation levels including:

- `READ UNCOMMITTED`;
- `READ COMMITTED`;
- `REPEATABLE READ`;
- `SERIALIZABLE`.

Its documented default is `READ COMMITTED`. citeturn661594search4

However, isolation is intentionally not taught in depth here. Chapter `03.5` and the subsequent isolation chapters will build the full model.

For now remember:

> **A transaction defines a unit of work; the isolation level defines how that transaction interacts with concurrent work.**

---

# 48. Read-Only Transactions

A transaction may be explicitly read-only:

```sql
BEGIN READ ONLY;

SELECT ...;
SELECT ...;

COMMIT;
```

Read-only mode can be useful for operations that should not modify persistent database state.

Do not confuse:

```text
read-only
```

with:

```text
no locks
```

or:

```text
no concurrency interaction
```

Those are separate concepts.

---

# 49. Transactional Settings and Scope

Some PostgreSQL settings can be changed transaction-locally.

For example:

```sql
BEGIN;
SET LOCAL statement_timeout = '2s';
...
COMMIT;
```

The transaction-local setting does not become a permanent session setting.

This is useful when a specific transactional operation requires tighter operational limits than the default session configuration.

Use `SET LOCAL` deliberately; configuration scope is part of transaction design.

---

# 50. Transaction vs Session

Do not confuse:

```text
session / connection
```

with:

```text
transaction
```

One connection can execute many transactions:

```text
Connection A
  Transaction 1
  COMMIT
  Transaction 2
  ROLLBACK
  Transaction 3
  COMMIT
```

The connection/session is longer-lived.

This distinction matters enormously in connection pools.

A session can outlive an individual transaction and carry session state that needs cleanup or deliberate management.

---

# 51. Transaction vs Request

A request is an application-level concept.

A transaction is a database-level concept.

You may have:

```text
One request → one transaction
```

or:

```text
One request → several transactions
```

or:

```text
One background job → many transactions
```

or:

```text
One business workflow → transactions across multiple services
```

Do not conflate application and database boundaries.

---

# 52. Transaction vs Business Operation

These are also not guaranteed to be identical.

Example:

```text
Business operation: "Ship order"
```

could involve:

```text
Transaction A
  change order status
  record shipment intent

External carrier call

Transaction B
  record tracking number
```

One business operation can span multiple transactions because external systems introduce independent commit boundaries.

This is where distributed workflow architecture begins.

---

# 53. Naive Approach → Why It Fails → Improved Approach

## Naive Approach

```text
Every SQL statement committed independently.
```

### Why It Fails
Related changes can become partially committed.

### Improved Approach
Group the statements required for one atomic invariant transition into a transaction.

### Why It Works
The database can commit or abort the grouped changes as one transactional unit.

### Production Considerations
Keep the transaction short enough for the workload; avoid unnecessary external waits and enforce business-success conditions explicitly.

### Alternative
Use a staged state machine or outbox workflow when the operation spans external systems.

### Trade-Off
Multiple transactions can improve operational flexibility but introduce intermediate committed states and require compensation/idempotency/reconciliation.

# 54. ACID Preview

Transactions are commonly discussed through ACID:

```text
A — Atomicity
C — Consistency
I — Isolation
D — Durability
```

At this chapter's level:

### Atomicity
The transaction's changes are accepted or aborted as a unit.

### Consistency
A successful transaction should preserve the database's defined invariants and constraints.

### Isolation
Concurrent transactions must interact according to the selected isolation semantics.

### Durability
Committed changes are protected according to PostgreSQL's durability configuration.

The next chapter, `03.2 — ACID Deep Dive`, will take these from definitions to internal and operational reasoning.

# 55. Common Developer Mistakes

## Mistake 1: Treating each query as independent when the business operation is not

Result: partial state.

## Mistake 2: Calling `BEGIN` but using unrelated repository methods

Result: statements may execute on different connections.

## Mistake 3: Forgetting rollback on exceptions

Result: failed transaction state leaks into connection-pool usage.

## Mistake 4: Holding a transaction while waiting for an external API

Result: unnecessarily long transaction lifetime.

## Mistake 5: Assuming rollback reverses external effects

Result: distributed inconsistency.

## Mistake 6: Assuming `BEGIN` eliminates races

Result: incorrect concurrency design.

## Mistake 7: Treating timeout as proof of rollback

Result: duplicate writes on retry or inconsistent client state.

## Mistake 8: Using one giant transaction for an enormous batch without measuring workload

Result: operational pressure and difficult recovery.

## Mistake 9: Assuming nested ORM transactions are independent commits

Result: incorrect rollback/commit expectations.

## Mistake 10: Swallowing transaction errors

Result: impossible-to-debug business outcomes.

# 56. AI / Vibe-Coding Failure Modes

AI-generated backend code often produces transaction-looking code that is structurally plausible but semantically wrong.

### Failure Pattern 1 — Pool instead of transaction client

```ts
await pool.query('BEGIN');
await serviceA();
await serviceB();
await pool.query('COMMIT');
```

This may fail to guarantee a single session.

### Failure Pattern 2 — External API inside transaction

```ts
await tx(...);
await axios.post(...);
await tx(...);
```

No reasoning about transaction lifetime.

### Failure Pattern 3 — Transaction without business success validation

```ts
await tx.query('UPDATE inventory ...');
await tx.query('COMMIT');
```

No check whether the update actually reserved inventory.

### Failure Pattern 4 — Catch and continue after transaction error

```ts
try {
  await query();
} catch {}
await queryAgain();
```

Inside a failed PostgreSQL transaction, this is usually invalid until rollback/savepoint recovery.

### Failure Pattern 5 — Retry without idempotency

```text
transaction timeout
↓
retry entire operation
```

The original transaction may have committed.

The AI-generated code needs explicit idempotency design.

# 57. Production Observability

At minimum, transaction-aware services should expose:

```text
transaction duration
transaction outcome
rollback count
commit latency
SQLSTATE/error class
connection acquisition time
connection pool saturation
long-running transaction count
request/transaction correlation ID
```

For deep PostgreSQL investigation, inspect server-side transaction/lock views rather than relying only on application logs. PostgreSQL's transaction-processing documentation identifies `pg_locks` and transaction identifiers as core observability surfaces. citeturn661594search13

A high-level latency decomposition is:

```text
request time
= connection acquisition
+ transaction execution
+ commit/rollback
+ response processing
```

Do not assume all latency is SQL execution time.

# 58. Testing Strategy

A transaction design should be tested at multiple levels.

## L1 — Basic commit

Verify committed changes persist.

## L2 — Rollback

Force a failure and verify no partial state remains.

## L3 — Savepoint

Verify rollback to a savepoint preserves earlier work.

## L4 — Connection correctness

Verify all operations in the transaction use the same connection/context.

## L5 — Failure injection

Inject errors:

```text
before statement 1
between statements
before commit
after commit but before response
```

## L6 — Retry behavior

Simulate lost responses and repeated requests.

## L7 — Concurrency

Later chapters should test simultaneous transactions against shared rows and invariants.

# 59. Practical Lab — Money Transfer

Create:

```sql
CREATE TABLE accounts (
    account_id bigint PRIMARY KEY,
    owner_name text NOT NULL,
    balance numeric(20,2) NOT NULL CHECK (balance >= 0)
);
```

Seed data:

```sql
INSERT INTO accounts(account_id, owner_name, balance)
VALUES
    (1, 'Alice', 10000.00),
    (2, 'Bob', 5000.00);
```

Transaction:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000.00
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 1000.00
WHERE account_id = 2;

COMMIT;
```

Verify:

```sql
SELECT *
FROM accounts
ORDER BY account_id;
```

Then intentionally fail:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000.00
WHERE account_id = 1;

INSERT INTO accounts(account_id, owner_name, balance)
VALUES (1, 'Duplicate', 100.00);

COMMIT;
```

Observe that after the duplicate-key error, the transaction is aborted and cannot simply continue with arbitrary commands. Roll it back:

```sql
ROLLBACK;
```

# 60. Practical Lab — Savepoint

```sql
BEGIN;

INSERT INTO accounts(account_id, owner_name, balance)
VALUES (3, 'Carol', 3000.00);

SAVEPOINT before_second_insert;

INSERT INTO accounts(account_id, owner_name, balance)
VALUES (1, 'Duplicate', 100.00);

ROLLBACK TO SAVEPOINT before_second_insert;

INSERT INTO accounts(account_id, owner_name, balance)
VALUES (4, 'David', 4000.00);

COMMIT;
```

Expected conceptual result:

```text
Carol  → persisted
failed duplicate insert → discarded
David → persisted
```

# 62. Expert Mental Model

A useful hierarchy:

```text
SQL statement
     ↓
Transaction
     ↓
Transaction identity
     ↓
Visibility / snapshot semantics
     ↓
Locks / conflicts
     ↓
Commit / abort
     ↓
WAL / durability
     ↓
Vacuum / cleanup / replication implications
```

Do not jump directly to locks before understanding transactions.

Do not jump to serializable isolation before understanding snapshots.

Do not jump to distributed transactions before understanding local transaction atomicity.

The hierarchy matters.

# 63. When to Use a Transaction

A transaction is strongly indicated when multiple writes represent one atomic business state transition.

Examples:

```text
order creation + order items
inventory reservation + sale record
journal + journal lines
wallet debit + wallet credit
state transition + transition history
user creation + required dependent rows
allocation + allocation metadata
```

The more tightly coupled the invariant, the stronger the case for one transaction.

---

# 64. When Not to Force One Transaction

Avoid forcing unrelated operations into one transaction merely because they happen during the same request.

Example:

```text
Create order
and
send marketing email
```

The email generally does not belong in the same database transaction because SMTP or another external provider cannot participate in the PostgreSQL commit.

A better architecture may be:

```text
Transaction
  create order
  create outbox event
  commit

Worker
  read outbox
  send email
  record delivery state
```

That becomes a later Phase 03/production-architecture topic.

# 65. Transaction Decision Framework

Before adding `BEGIN`, answer:

```text
1. What invariant am I protecting?
2. Which writes must succeed together?
3. What is the success condition?
4. What happens if statement N fails?
5. Which operations require the same connection?
6. Could any operation wait on external I/O?
7. How long can the transaction remain open?
8. What happens if the client retries?
9. What happens if commit succeeds but the response is lost?
10. How will I observe and debug the transaction?
```

If those answers are unclear, the transaction design is not finished.

# 70. Production Readiness Checklist

Before shipping transactional backend logic, verify:

- [ ] The transaction protects a clearly defined invariant.
- [ ] The transaction boundary is intentional rather than accidental.
- [ ] All participating statements use the same transaction-scoped connection/context.
- [ ] Successful work commits exactly once.
- [ ] Failed work rolls back reliably.
- [ ] Rollback failure is logged without hiding the original error.
- [ ] Connections are always released back to the pool.
- [ ] No unnecessary external I/O occurs while the transaction is open.
- [ ] The expected success condition is explicitly verified.
- [ ] Retries are safe or protected by idempotency mechanisms.
- [ ] Commit/response ambiguity is considered.
- [ ] Long-running transactions are observable.
- [ ] Transaction duration is measurable.
- [ ] SQLSTATE/database errors are preserved for correct classification.
- [ ] The transaction design has failure-injection tests.
- [ ] Batch size and transaction size are based on workload measurements.
- [ ] The team understands which guarantees come from transactions and which require concurrency controls.

# 71. Core Principles to Remember

1. **A transaction is an atomic database work unit.**
2. **Every PostgreSQL statement executes within a transaction context; explicit `BEGIN` groups multiple statements.**
3. **A transaction protects a transition between database states, but it does not define business success automatically.**
4. **All statements intended to share a transaction must use the same database session/connection.**
5. **An error inside a transaction is not just an ordinary statement failure; PostgreSQL may place the transaction into an aborted state requiring rollback or savepoint recovery.**
6. **Savepoints provide partial rollback without committing the outer transaction.**
7. **Transactions do not eliminate concurrency anomalies by themselves. Isolation and locking determine concurrency behavior.**
8. **Transactions do not roll back external side effects.**
9. **Transaction lifetime is an operational concern.**
10. **Retry design must account for the possibility that a commit succeeded even when the client did not receive confirmation.**
11. **A good transaction boundary follows business invariants rather than arbitrary code structure.**
12. **Correctness comes first; transaction scope should then be optimized using evidence.**
