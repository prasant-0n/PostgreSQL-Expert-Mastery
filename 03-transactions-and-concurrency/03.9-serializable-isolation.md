# 03.9 — Serializable Isolation

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains PostgreSQL `SERIALIZABLE` isolation from first principles through production architecture: serializability, SSI, dangerous read/write dependencies, predicate locking, serialization failures, retries, performance, observability, Node.js/NestJS integration, testing, and expert decision-making.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- define serializability precisely;
- distinguish `SERIALIZABLE` from `READ COMMITTED` and `REPEATABLE READ`;
- explain why a stable snapshot alone does not prevent every anomaly;
- explain PostgreSQL's Serializable Snapshot Isolation (SSI) model;
- reason about read/write dependencies and serialization anomalies;
- understand predicate-lock participation in serializability;
- recognize SQLSTATE `40001` and design a safe retry policy;
- explain why retries restart the entire transaction;
- keep external side effects outside retryable transaction boundaries;
- use constraints, atomic SQL, locks, and serializability together rather than treating isolation as a universal hammer;
- debug conflict-heavy production workloads;
- design safe Node.js/NestJS transaction handling;
- understand `SERIALIZABLE READ ONLY DEFERRABLE`;
- test concurrency and retry behavior under realistic interleavings;
- select serializability based on the business invariant and workload.

PostgreSQL's current documentation describes `SERIALIZABLE` as its strictest isolation level. PostgreSQL implements it by taking the repeatable-read snapshot model and adding nonblocking monitoring for dangerous read/write conflict patterns; when a pattern could produce a serialization anomaly, one transaction is rolled back. PostgreSQL 18.6 is the current PostgreSQL 18 minor release as of August 13, 2026.

# 2. The Central Mental Model

The most important idea is:

> **`SERIALIZABLE` permits concurrent execution, but requires successful committed transactions to be equivalent to some serial execution order. When PostgreSQL cannot safely establish that property, it aborts one transaction.**

```text
                 CONCURRENT EXECUTION

       T1 ----------------------------+
        |                             |
        | read A                      | write B
        v                             v
      snapshot                  dependency

       T2 ----------------------------+
        |                             |
        | read B                      | write A
        v                             v
      snapshot                  dependency

                 conflicting cycle
                        |
                        v
              serialization failure
                        |
                        v
                 rollback + retry
```

Therefore:

```text
SERIALIZABLE != no concurrency
SERIALIZABLE != every query blocks
SERIALIZABLE != pessimistic locking
SERIALIZABLE != zero failures

SERIALIZABLE = serializable outcomes + possible abort/retry
```

---

# 3. What “Serializable” Means

## 3.1 Simple definition

The committed result should be equivalent to one produced by running the transactions one at a time in some order.

## 3.2 Engineering definition

A concurrent history is serializable when its externally visible outcome is equivalent to a serial ordering of the participating transactions.

The important point is that the **outcome** is constrained, not that the server must physically execute transactions sequentially.

## 3.3 Expert definition

PostgreSQL uses MVCC snapshots together with Serializable Snapshot Isolation (SSI). A serializable transaction can proceed concurrently with others, while PostgreSQL tracks relevant read/write conflict relationships. If those dependencies form a dangerous pattern that could permit a result with no equivalent serial ordering, PostgreSQL forces a transaction to abort with a serialization failure.

---

# 4. The Isolation Ladder

| Level | Main visibility model | Nonrepeatable reads | Serialization anomalies | Retry implication |
|---|---|---:|---:|---|
| `READ COMMITTED` | fresh statement snapshot | possible | possible | normally not isolation-driven |
| `REPEATABLE READ` | stable transaction snapshot | prevented | possible | some concurrent updates can fail |
| `SERIALIZABLE` | stable snapshot + SSI | prevented | prevented for participating serializable transactions | whole transaction may need retry |

A useful progression is:

```text
READ COMMITTED
statement consistency
      ↓
REPEATABLE READ
transaction snapshot consistency
      ↓
SERIALIZABLE
serial execution equivalence
```

Do not confuse “stronger guarantee” with “always better production performance.” A stronger isolation level can produce more aborts under contention and therefore more application work.

---

# 5. Why Repeatable Read Is Not Enough

Consider the classic on-call invariant:

> At least one doctor must remain on call.

Initial state:

```text
Alice = on_call
Bob   = on_call
```

Two concurrent repeatable-read transactions each do:

```sql
SELECT count(*)
FROM doctors
WHERE on_call = true;
```

Both see:

```text
2
```

T1 then turns Alice off. T2 turns Bob off.

Final state:

```text
Alice = false
Bob   = false
```

Both transactions had a stable, internally consistent snapshot. Yet the combined result does not correspond to a valid serial execution of the two decisions. This is the classic **write skew** pattern.

The important lesson is:

> **Snapshot consistency and serializability are related, but they are not the same guarantee.**

---

# 6. SSI: Serializable Snapshot Isolation

A naïve way to provide serializable behavior is to lock almost everything:

```text
read -> lock
scan range -> lock
write -> lock
```

That can create excessive blocking and deadlock opportunities.

SSI instead follows this conceptual model:

```text
MVCC snapshot
    +
read/write conflict tracking
    +
concurrent execution
    +
danger detection
    +
abort when required
```

The trade-off is:

```text
less broad blocking
      versus
possible serialization failures
```

PostgreSQL documents serializable transactions as repeatable-read behavior plus nonblocking monitoring of dangerous read/write conflict patterns.

---

# 7. Dependency Graph Mental Model

Think of transactions as nodes and data dependencies as edges.

Example:

```text
T1 reads X
T2 writes X
```

Conceptually:

```text
T1 ----rw----> T2
```

Another dependency:

```text
T2 reads Y
T3 writes Y
```

Now:

```text
T1 ----rw----> T2 ----rw----> T3
```

A dangerous structure arises when dependencies combine in a way that can create a serialization cycle.

You do not need to memorize an implementation algorithm to use this professionally. You need to recognize the shape:

> A transaction's reads influence its writes, another transaction has overlapping dependencies, and the resulting dependency graph cannot be given a valid serial ordering without rejecting some transaction.

---

# 8. What Is a Serialization Anomaly?

A serialization anomaly is a committed outcome that is inconsistent with every possible serial ordering of the concurrent transactions.

Practical test:

> **Could these committed transactions have produced exactly this result if they had run one after another in some order?**

If no serial ordering can explain the committed result, the history is not serializable.

`SERIALIZABLE` exists to prevent that class of committed outcome for the transactions participating in the serializable protocol.

---

# 9. Serialization Failure Is a Correctness Mechanism

A common beginner reaction is:

```text
"The database failed."
```

A better interpretation is:

```text
The database detected a concurrency pattern
that cannot be safely committed under SERIALIZABLE.
```

Therefore:

```text
serialization conflict
        ↓
rollback one transaction
        ↓
retry whole logical operation
        ↓
new snapshot / new execution
        ↓
commit if safe
```

The abort is part of the guarantee.

It is often better to have:

```text
one transaction aborted + retried
```

than:

```text
both transactions commit corrupted business state
```

---

# 10. Predicate Reads and Predicate Locks

Row locks protect existing rows. But a business rule may depend on the absence or presence of rows matching a predicate.

Example:

```sql
SELECT 1
FROM reservations
WHERE resource_id = 42
  AND starts_at < $2
  AND ends_at > $1;
```

Suppose it returns zero rows.

The transaction is still making a decision based on:

```text
"No conflicting reservation exists."
```

Another transaction can attempt to insert a matching reservation.

A normal row lock cannot lock a row that does not exist.

This is where predicate-lock participation matters to serializability. PostgreSQL's SSI machinery tracks dependencies created by predicate reads so that a concurrent write can be recognized as relevant to the serializability decision.

Do not mentally equate a predicate lock with a simple blocking row lock. In SSI the important concept is **conflict detection for a read dependency**, not “every matching row is permanently locked.”

---

# 11. Why Indexes Matter

Query shape can change the size of the data region a transaction touches.

Suppose the invariant is branch + SKU specific:

```sql
SELECT available_qty
FROM inventory
WHERE tenant_id = $1
  AND branch_id = $2
  AND sku = $3;
```

A useful index might be:

```sql
CREATE INDEX idx_inventory_tenant_branch_sku
ON inventory (tenant_id, branch_id, sku);
```

Do not claim that “indexes fix serializable conflicts.” The correct engineering statement is narrower:

> A query plan that accesses a more targeted data set can reduce unnecessary work and may reduce the scope of predicate conflict tracking compared with a broad scan.

Verify with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

The process is:

```text
observe conflicts
↓
inspect query plan
↓
understand read set
↓
improve access path where justified
↓
retest concurrency
```

---

# 12. `FOR UPDATE` Still Has a Place

Serializable isolation does not make explicit locking useless.

If one hot row represents a physical business resource, an explicit row lock may communicate the intended ordering better:

```sql
SELECT balance
FROM accounts
WHERE id = $1
FOR UPDATE;
```

Potential benefits:

- explicit serialization of a hot resource;
- reduced wasted concurrent work;
- simpler reasoning for a row-centric invariant;
- deliberate ordering of critical operations.

Choose based on the invariant:

```text
single hot row
    -> often row lock / atomic SQL

multi-row predicate invariant
    -> serializable may be more natural
```

They can also be combined when there is a concrete reason.

---

# 13. Declarative Constraints First

Before choosing serializable isolation, ask whether the invariant can be represented directly in the schema.

Example:

```sql
CREATE UNIQUE INDEX uq_active_membership
ON memberships(user_id)
WHERE status = 'active';
```

That is often better than:

```text
SELECT active membership
IF none
  INSERT
```

with application hope layered on top.

General rule:

> **Use the narrowest mechanism that completely expresses the invariant.**

Possible mechanisms include:

```text
CHECK constraint
UNIQUE constraint/index
EXCLUDE constraint
foreign key
atomic UPDATE
row lock
advisory lock
SERIALIZABLE transaction
workflow/state-machine design
```

Serializable is general, but generality is not a reason to use it when a simpler mechanism proves the same invariant.

---

# 14. SQL Syntax

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

-- transactional work

COMMIT;
```

Equivalent form:

```sql
START TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

Session default:

```sql
SET SESSION CHARACTERISTICS AS TRANSACTION
  ISOLATION LEVEL SERIALIZABLE;
```

Database configuration can also change the default, but the default PostgreSQL isolation level remains `READ COMMITTED` unless configured otherwise.

Inspect the active level:

```sql
SHOW transaction_isolation;
```

or:

```sql
SELECT current_setting('transaction_isolation');
```

A transaction isolation decision belongs at the transaction boundary. Do not assume a single ORM query is automatically equivalent to a serializable transaction.

---

# 15. The Non-Negotiable Rule: Retry the Entire Transaction

Wrong:

```ts
try {
  await client.query(updateSql);
} catch (error) {
  await client.query(updateSql);
}
```

Correct conceptual model:

```text
ATTEMPT 1
BEGIN
  read
  validate
  compute
  write
COMMIT
  |
  +-- 40001
       |
       v
ROLLBACK

ATTEMPT 2
BEGIN
  read again
  validate again
  compute again
  write again
COMMIT
```

Why?

Because the decision made in attempt 1 was based on a specific transaction snapshot and dependency history. A serialization failure means that execution cannot safely be completed as attempted.

Retrying only the final statement would reuse stale reasoning.

Therefore:

> **A serialization retry is a retry of the complete transactional unit, not the failed SQL statement.**

---

# 16. SQLSTATE `40001`

Applications should classify PostgreSQL errors by SQLSTATE rather than parsing human-readable error strings.

Example:

```ts
function isSerializationFailure(error: unknown): boolean {
  return (
    typeof error === 'object' &&
    error !== null &&
    'code' in error &&
    (error as { code?: string }).code === '40001'
  );
}
```

Do not use:

```ts
error.message.includes('could not serialize access')
```

Machine-readable SQLSTATE is the correct integration boundary.

---

# 17. `40P01` Is a Different Failure

PostgreSQL also exposes:

```text
40P01 = deadlock_detected
```

A deadlock is a lock-wait cycle. A serialization failure is a serializability conflict.

Both may justify a bounded retry in some applications, but they should remain different diagnostic categories.

Avoid:

```ts
catch {
  retry();
}
```

Prefer explicit classification:

```text
40001 -> serialization retry
40P01 -> deadlock retry policy
23xxx -> integrity/business handling
other -> case-by-case failure policy
```

---

# 18. A Production Retry Skeleton

```ts
async function withSerializableRetry<T>(
  operation: (client: PoolClient) => Promise<T>,
  maxAttempts = 5,
): Promise<T> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const client = await pool.connect();

    try {
      await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');

      const result = await operation(client);

      await client.query('COMMIT');
      return result;
    } catch (error) {
      try {
        await client.query('ROLLBACK');
      } catch {
        // Preserve the original error.
      }

      if (!isSerializationFailure(error) || attempt === maxAttempts) {
        throw error;
      }

      await sleep(withJitter(attempt));
    } finally {
      client.release();
    }
  }

  throw new Error('Serializable retry budget exhausted');
}
```

Production concerns include:

```text
bounded attempts
backoff
jitter
metrics
structured logs
request correlation
idempotency
connection cleanup
```

The exact values should come from workload measurements and latency SLOs rather than copied defaults.

---

# 19. Never Retry Inside the Same Aborted Transaction

After a transaction has failed and is no longer usable for the attempted unit of work, do not try to continue performing business work inside that same failed transaction boundary.

The clean model is:

```text
failed attempt
    ↓
rollback
    ↓
release/clean connection
    ↓
backoff
    ↓
new transaction
```

A retry is a new transaction identity and a new snapshot.

---

# 20. External Side Effects Must Not Be Inside the Retry Boundary

Bad:

```text
BEGIN SERIALIZABLE
  ↓
update order
  ↓
charge payment provider
  ↓
serialization failure
  ↓
rollback
  ↓
retry
  ↓
charge payment provider again
```

The database rollback cannot undo the third-party payment.

The same problem applies to:

- email;
- SMS;
- webhooks;
- Kafka publishes;
- shipping APIs;
- WhatsApp messages;
- external inventory providers;
- irreversible hardware/API actions.

Preferred:

```text
SERIALIZABLE DB transaction
   |
   +-- state change
   +-- outbox event
   |
   +-- COMMIT
           |
           v
       worker
           |
           +-- external effect
```

This creates a clean boundary between database atomicity and external effect delivery.

---

# 21. Idempotency Is a Separate Layer

A logical request may have multiple physical transaction attempts:

```text
request req_123
  |
  +-- attempt 1 -> 40001
  |
  +-- attempt 2 -> success
```

Therefore distinguish:

```text
logical operation
        !=
transaction attempt
```

For user-visible commands, an idempotency key can be persisted:

```sql
CREATE TABLE request_dedup (
  request_id uuid PRIMARY KEY,
  status text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

Retries and repeated client requests can then be handled as the same logical operation where the business contract requires it.

# 22. Serializable and Long Transactions

A 30-second serializable transaction has a much larger overlap window than a 30-millisecond one.

Long transactions can increase:

```text
conflict opportunity
retry probability
snapshot lifetime
resource retention
vacuum pressure
latency
```

Avoid:

```text
BEGIN SERIALIZABLE
call remote API
sleep
generate PDF
wait for user input
run huge computation
write
COMMIT
```

Prefer:

```text
prepare outside transaction
      ↓
BEGIN SERIALIZABLE
      ↓
minimal reads/writes
      ↓
outbox
      ↓
COMMIT
      ↓
external work
```

Transaction duration is therefore both a performance and concurrency-control variable.

---

# 23. Never Use Infinite Retries

This is dangerous:

```ts
while (true) {
  try {
    return await transaction();
  } catch (error) {
    if (isSerializationFailure(error)) continue;
    throw error;
  }
}
```

Under a hot invariant:

```text
contention
 ↓
40001
 ↓
retry
 ↓
more contention
 ↓
40001
 ↓
retry
```

This can become a retry storm.

Use:

```text
bounded attempts
exponential backoff
jitter
observability
terminal failure handling
```

---

# 24. Retry Backoff

Without jitter, many requests can synchronize:

```text
100 requests fail
↓
all sleep 100ms
↓
all wake together
↓
all conflict again
```

With jitter:

```text
base delay + random component
```

The exact algorithm is workload-specific. What matters is avoiding synchronized retry waves and respecting the API latency budget.

---

# 25. Node.js / `pg` Transaction Discipline

A transaction belongs to one PostgreSQL connection.

Correct:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE');
  await client.query('SELECT ...');
  await client.query('UPDATE ...');
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

Do not do this:

```ts
await pool.query('BEGIN');
await pool.query('SELECT ...');
await pool.query('UPDATE ...');
await pool.query('COMMIT');
```

A pool manages multiple connections. Multi-statement transaction ownership must stay on the same checked-out client.

# 26. NestJS Transaction Architecture

A clean production arrangement is:

```text
Controller
   ↓
Application Service
   ↓
Transaction Runner
   ↓
Serializable Retry Policy
   ↓
pg Client
   ↓
Repositories
```

Repositories should receive the transaction context explicitly rather than silently acquiring unrelated connections.

Example:

```ts
await transactionRunner.serializable(async (tx) => {
  const state = await orderRepository.read(tx, orderId);
  const decision = decide(state, input);

  await orderRepository.apply(tx, decision);
  await outboxRepository.insert(tx, decision.event);
});
```

The transaction runner owns:

```text
BEGIN
ROLLBACK
COMMIT
retry classification
backoff
connection lifecycle
```

The service owns:

```text
business invariants and decisions
```

# 27. ORM / AI-Generated Code Trap

Looks clean:

```ts
await db.transaction(async (tx) => {
  await tx.order.update(...);
  await paymentApi.charge(...);
});
```

But if the transaction is retried, the external payment can execute more than once.

Another bad pattern is:

```ts
const state = await loadState();

return retry(() => updateUsing(state));
```

If `state` was captured from an aborted attempt, the retry is not actually re-reading the database.

A correct retry re-executes the entire read/decide/write path inside the new transaction.

# 28. Serializable Does Not Correct Bad Business Logic

Suppose the requirement is:

> Customer can create at most 10 orders per calendar day.

But the code checks:

```sql
WHERE created_at >= now() - interval '24 hours'
```

The transaction can be perfectly serializable while enforcing the wrong business rule.

Therefore:

```text
SERIALIZABLE
   ↓
correct concurrent execution of
   ↓
correctly expressed invariant
```

not:

```text
SERIALIZABLE
   ↓
automatic business correctness
```

---

# 29. Mixed Isolation Levels

Suppose:

```text
T1 = SERIALIZABLE
T2 = READ COMMITTED
```

If your correctness argument assumes all transactions that can invalidate an invariant participate in serializable conflict detection, a transaction that bypasses that discipline can invalidate the argument.

The correct question is:

> **Which transactions can change the state on which this invariant depends?**

Those transactions must participate in the chosen correctness strategy.

Do not say “one critical query uses serializable, therefore the invariant is protected.”

---

# 30. Serializable Read-Only Deferrable

For large, consistent, read-only transactions, PostgreSQL supports:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
```

The important behavior is:

```text
may wait for a safe snapshot
        ↓
once acquired
        ↓
read-only transaction proceeds
        ↓
without normal serializable conflict overhead
        ↓
and without being aborted by concurrent updates
```

This is particularly valuable for:

- financial reports;
- reconciliation;
- regulatory exports;
- end-of-day reports;
- large consistency-sensitive reads.

The trade-off is startup delay in exchange for a safe snapshot execution mode.

---

# 31. Replica Caveat

Serializable protection is a primary-side transaction property. Do not assume that a query served from a hot standby or logical replica automatically has the same serializability guarantee as the primary transaction that produced the data.

For consistency-sensitive workflows, explicitly reason about:

```text
primary vs replica
replication lag
read-after-write expectations
transaction boundary
staleness tolerance
```

Do not put a replica read into a correctness argument without analyzing replica semantics.

---

# 32. `postgres_fdw` Is a Special Case

PostgreSQL's `postgres_fdw` can map a remote PostgreSQL transaction to a corresponding local transaction. When the local transaction is serializable, the remote transaction uses serializable isolation as well; otherwise the remote transaction uses repeatable read so successive queries within the remote transaction remain snapshot-consistent.

This is PostgreSQL-specific integration behavior. It is not a general solution for arbitrary distributed service transactions.

At minimum track:

```text
operation name
attempt number
SQLSTATE
transaction duration
retry count
commit/rollback outcome
request/correlation ID
```

Database evidence:

```sql
SELECT pid,
       usename,

       wait_event_type,
       wait_event,
       xact_start,
       query_start,
       query
```

```sql
SELECT pid,
       locktype,
       mode,
       granted,
       relation::regclass,
       transactionid,
       virtualxid
FROM pg_locks
WHERE pid <> pg_backend_pid();
```

For serializable incidents, combine:

```text
application retry metrics
+
transaction duration
+
query plans
+
workload/concurrency shape
+
server evidence
```

No single system view explains the full dependency history by itself.

# 34. Diagnosing a High `40001` Rate

A disciplined workflow is:

```text
1. Confirm SQLSTATE = 40001
2. Group by operation
3. Measure transaction duration
4. Identify overlapping reads/writes
5. Inspect query plans
6. Find broad predicates or unnecessary reads
7. Reduce critical-section size
8. Consider a narrower invariant mechanism
9. Retest under concurrency
10. Measure p95/p99 and retry rate
```

Do not begin with:

```text
"Increase connection pool size."
```

More concurrent attempts can increase contention on the same logical invariant.

# 35. Retry Amplification

Suppose:

```text
100 logical requests
20% fail first attempt
```

The database may process:

```text
100 initial attempts
+ 20 retry attempts
= 120 transaction attempts
```

If conflicts rise during the retry wave, the amplification can become larger.

Therefore watch:

```text
first-attempt success rate
average attempts/request
final failure rate
retry contribution to DB load
```

Retries are not free.

---

# 36. Pool Capacity and Contention

A pool size of 100 does not imply 100 useful concurrent serializable operations.

If one invariant is hot, 100 attempts may simply create:

```text
more overlap
more conflicts
more retries
more CPU
more latency
```

Sometimes reducing application-level concurrency is the better optimization.

The goal is not maximum parallelism. It is maximum **useful throughput while preserving correctness and SLOs**.

# 37. Performance Engineering

Use this sequence:

```text
measure
↓
locate conflict hotspot
↓
measure transaction duration
↓
inspect read/write set
↓
inspect query plans
↓
reduce unnecessary work
↓
reduce conflict surface
↓

```

# 38. Single-Row Counter: Often a Better Mechanism Exists

Suppose the only invariant is:

```text
counter must never become negative
```

Prefer an atomic statement where possible:

```sql
UPDATE quotas
SET remaining = remaining - 1
WHERE id = $1
  AND remaining > 0;
```

Then:

```text
rows affected = 1 -> reservation accepted
rows affected = 0 -> quota unavailable
```

This can be simpler and more targeted than a broad serializable transaction.

The correct question is not:

> “Can serializable solve it?”

It is:

> “What is the smallest mechanism that solves it correctly?”

---

# 39. Multi-Row Invariant: Serializable Becomes More Attractive

Suppose a tenant can allocate at most 100 units across several inventory rows and the decision depends on an aggregate across those rows.

The invariant spans multiple records:

```text
total reserved <= tenant budget
```

Possible solutions:

```text
aggregate/budget row + row lock
SERIALIZABLE transaction
schema redesign
constraint-oriented design where possible
```

This is a better candidate for serializable reasoning than a simple counter on one row.

# 40. Jewellery ERP Example — Gold Allocation

Suppose:

```text
Tenant: Makkah Jewellers
Branch: HYD-01
SKU: GOLD-CHAIN-22K-001
available_qty = 10
```

Two orders arrive concurrently.

A naïve flow is:

```text
SELECT available_qty
IF >= requested
  UPDATE available_qty
```

Two concurrent requests can both observe 10.

For a single-row invariant, an atomic update is often the narrowest solution:

```sql
UPDATE inventory
SET available_qty = available_qty - $4
WHERE tenant_id = $1
  AND branch_id = $2
  AND sku = $3
  AND available_qty >= $4;
```

For a more complex rule:

```text
branch gold budget
+
multiple inventory rows
+
existing reservations
+
order state
```

serializable isolation becomes more compelling because the invariant is no longer naturally local to one row.

# 41. Jewellery ERP Example — Daily Reconciliation

Suppose branch close must verify:

```text
ledger debits = ledger credits
inventory movement totals reconcile
cash balances reconcile
all required documents are posted
```

A sequence of independent `READ COMMITTED` queries can observe different committed worlds.

A consistent transaction boundary is stronger.

For a large read-only reconciliation:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
```

can be considered when the workload can tolerate snapshot acquisition delay.

For a state-changing close workflow:

```text
SERIALIZABLE
+
short transaction
+
bounded retries
+
explicit invariant
+
outbox/event architecture
```

may be appropriate.

# 42. Multi-Tenant Security and Serializable Transactions

Serializable isolation does not replace tenant isolation.

A query missing tenant scope:

```sql
SELECT *
FROM inventory
WHERE sku = $1;
```

can still read another tenant's data if the schema permits it.

Correct transaction design should include the actual scope:

```sql
SELECT *
FROM inventory
WHERE tenant_id = $1
  AND branch_id = $2
  AND sku = $3;
```

For security-sensitive invariants, ensure retries re-run authorization and tenant scoping from the new transaction attempt rather than reusing stale decisions from an aborted attempt.

# 43. Failure Boundary: Commit Timeout

Serialization failure is not the only difficult retry case.

Consider:

```text
client sends COMMIT
↓
server commits
↓
network breaks
↓
client sees timeout
```

The client may not know whether the commit succeeded.

This is not the same as a confirmed serialization failure.

For externally observable commands, use:

```text
idempotency key
business request record
outbox/workflow state
reconciliation
```

to distinguish:

```text
retry because transaction definitely aborted
```

from:

```text
request outcome is uncertain
```

# 44. Error-Handling Matrix

| Error | Typical retry? | Main concern |
|---|---:|---|
| `40001` | Yes | restart entire transaction |
| `40P01` | Often | deadlock root cause + bounded retry |
| `23505` | Usually no | business-specific duplicate handling |
| `23503` | Usually no | ordering/data correctness |
| `23514` | No | violated invariant/input |
| network failure | depends | transaction outcome may be ambiguous |
| timeout | depends | determine whether work committed |

The safe architecture is never “retry everything.”

---

# 45. Why `SERIALIZABLE` Does Not Mean No Deadlocks

Deadlocks arise from incompatible locks and wait cycles.

Serializable isolation does not remove every possible lock interaction.

If your workflow uses:

```text
row locks
advisory locks
DDL
explicit table locks
```

you must still understand lock ordering and deadlock handling.

Therefore a system can legitimately experience both:

```text
40001 serialization failures
```

and:

```text
40P01 deadlocks
```

# 46. Testing Strategy

Concurrency needs concurrency tests.

Build a harness that:

```text
1. creates a known invariant
2. launches N concurrent transactions
3. executes the same business operation
4. records SQLSTATE failures
5. retries safe operations
6. checks the final invariant
7. records latency and attempt counts
```

Compare:

```text
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

The meaningful assertion is not that every request succeeds on the first attempt.

It is:

```text
final invariant holds
+
logical requests complete correctly
+
external effects are not duplicated
```

# 48. Production Checklist

Before adopting serializable for a critical workflow:

- [ ] Business invariant is explicitly documented.
- [ ] All transactions that can invalidate the invariant participate in the correctness strategy.
- [ ] Transaction boundary is minimal but complete.
- [ ] Entire transaction can be safely retried.
- [ ] Retry count is bounded.
- [ ] Backoff and jitter are appropriate.
- [ ] External side effects are not duplicated by retries.
- [ ] Idempotency semantics exist for logical requests.
- [ ] SQLSTATE `40001` is handled explicitly.
- [ ] Deadlock handling is separate.
- [ ] Connection ownership is correct.
- [ ] Transaction client is not mixed with unrelated pool queries.
- [ ] Transaction duration is measured.
- [ ] Serialization failure rate is observable.
- [ ] Query plans for critical reads are known.
- [ ] Retry storms have been load-tested.
- [ ] Replica semantics are understood.
- [ ] The team can explain why serializable is better than a narrower mechanism.

# 49. AI / Vibe-Coding Audit

Reject these patterns during review:

### “Retry the last statement.”
Wrong: retry the entire transaction.

### “Serializable means we don't need constraints.”
Wrong: declarative constraints remain valuable and often superior for local invariants.

### “Serializable means no deadlocks.”
Wrong: locking and deadlock behavior still exist.

### “Retry every PostgreSQL error.”
Wrong: classify by SQLSTATE and business semantics.

### “Increase pool size to fix serialization failures.”
Wrong: higher concurrency can increase contention.

### “Put the payment call inside the transaction.”
Wrong: rollback cannot undo the external call.

### “Cache the read outside the retry.”
Wrong: retries must re-read state in a new transaction when that state participates in the decision.

### “Use serializable everywhere.”
Wrong: stronger isolation is not a substitute for correct mechanism selection.

# 51. Weak vs Strong Interview Answers

### Question: “Does serializable mean transactions run one at a time?”

**Weak:** “Yes.”

**Acceptable:** “It makes concurrent results safe.”

**Strong:** “It allows concurrent execution but prevents committed outcomes that are inconsistent with serial execution.”

**Expert:** “PostgreSQL uses SSI: transactions retain snapshot-based execution while the system tracks relevant read/write dependencies and aborts a transaction when a dangerous structure could otherwise lead to a non-serializable committed outcome.”

```text
                  SERIALIZABLE
                       |

                 MVCC snapshot
                       |
                       v

                       |

                       |

                               |
                               v
                       new transaction
                               |
                               v
                        re-read + decide
                               |
                               v
                             commit
```

The deepest lesson is:

> **Serializable isolation converts certain concurrency bugs that could otherwise become silent data corruption into explicit transaction failures that the application can safely retry.**

The database is not failing when it aborts such work. The abort is one of the mechanisms by which the stronger correctness guarantee is maintained.

# 54. Production Decision Rule

Use this sequence:

```text
What invariant are we protecting?
        ↓
Can a constraint express it?
        ↓
Can one atomic SQL statement express it?
        ↓
Can a row/advisory lock express the required ordering?
        ↓
If not, does a serializable transaction naturally capture it?
        ↓
Can we retry the whole transaction safely?
        ↓
Can external effects be decoupled?
        ↓
Can we observe and load-test conflict behavior?
```

The objective is not maximum isolation.

The objective is:

> **the strongest correctness guarantee justified by the invariant, implemented with bounded contention, safe retries, explicit failure handling, and measurable production behavior.**
