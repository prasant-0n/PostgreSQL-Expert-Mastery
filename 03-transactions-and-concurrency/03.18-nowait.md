# 03.18 — NOWAIT

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains PostgreSQL's `NOWAIT` locking option from first principles: fail-fast concurrency control, lock conflicts, transaction semantics, error handling, production design, observability, and the trade-offs against waiting and `SKIP LOCKED`.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- explain exactly what `NOWAIT` changes about PostgreSQL lock acquisition;
- distinguish `NOWAIT` from ordinary blocking, `lock_timeout`, and `SKIP LOCKED`;
- understand that `NOWAIT` applies to lock acquisition rather than magically making a query nonblocking in every respect;
- identify the locking clauses and explicit table-lock statements that support `NOWAIT`;
- reason about row-level and table-level conflict behavior;
- design fail-fast business workflows around resource ownership;
- classify and handle lock-not-available failures correctly;
- avoid retrying `NOWAIT` failures blindly;
- use transactions, savepoints, and application-level control flow safely;
- debug NOWAIT failures using PostgreSQL observability tools;
- evaluate contention, latency, throughput, fairness, and user experience;
- integrate NOWAIT correctly with Node.js, `pg`, NestJS, workers, and ORMs;
- recognize cases where `NOWAIT` is appropriate and cases where it is the wrong abstraction;
- explain the difference between **resource unavailable** and **database failure**;
- build production-safe APIs whose behavior under contention is explicit and deterministic.

PostgreSQL 18 documentation describes `NOWAIT` as causing a locking clause to report an error immediately rather than wait if the selected row cannot be locked. Table-lock statements also support `NOWAIT`. `NOWAIT` therefore changes the waiting policy of lock acquisition; it does not remove the underlying lock conflict. citeturn226736search12turn226736search8

# 2. The Central Mental Model

Without `NOWAIT`, a conflicting lock commonly behaves like:

```text
Transaction T1
      |
      | request lock on resource R
      v
   R is locked
      |
      v
   WAIT / QUEUE
      |
      v
   lock released
      |
      v
   continue
```

With `NOWAIT`:

```text
Transaction T1
      |
      | request lock on resource R
      v
   R is locked
      |
      v
   FAIL IMMEDIATELY
      |
      v
   application decides what to do
```

This produces a deliberately different contract:

> **“Do not wait for this resource; tell me immediately whether I can acquire the requested lock.”**

That contract is extremely useful when waiting is itself unacceptable.

---

# 3. What `NOWAIT` Means

## 3.1 Simple definition

`NOWAIT` tells PostgreSQL to return an error immediately when a required lock conflicts with another transaction instead of waiting for that lock to become available.

## 3.2 Engineering definition

`NOWAIT` converts lock acquisition from a potentially blocking operation into a fail-fast operation. The caller receives a lock-conflict error and can explicitly choose to abort, return a business response, retry later, or use another resource.

## 3.3 Expert definition

`NOWAIT` is a lock-acquisition policy layered on top of PostgreSQL's normal lock manager and concurrency semantics. If a requested lock conflicts with a lock held by another transaction, PostgreSQL does not enqueue the request behind the conflicting lock. It reports the conflict immediately. The database still enforces the underlying locking rules; `NOWAIT` merely changes the behavior of the waiter.

---

# 4. `NOWAIT` Does Not Mean “The Query Cannot Block”

This distinction is critical.

Consider:

```sql
SELECT *
FROM orders
WHERE id = 42
FOR UPDATE NOWAIT;
```

The **row-lock acquisition** is fail-fast.

That does not mean the entire statement is immune to every possible wait or resource delay. Query execution can still involve ordinary CPU work, I/O, buffer contention, catalog activity, network delay, or other mechanisms unrelated to the requested row lock.

Therefore:

```text
NOWAIT
    !=
zero execution latency
```

Instead:

```text
NOWAIT
    =
no waiting for the conflicting requested lock
```

This is one of the most important corrections to shallow explanations of `NOWAIT`.

---

# 5. Basic Syntax

The most common usage is with a row-locking clause:

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR UPDATE NOWAIT;
```

You can also use:

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR NO KEY UPDATE NOWAIT;
```

or:

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR SHARE NOWAIT;
```

or:

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR KEY SHARE NOWAIT;
```

For explicit table locks:

```sql
LOCK TABLE inventory IN SHARE MODE NOWAIT;
```

The supported syntax and conflict behavior should always be checked against the PostgreSQL version deployed in production.

# 6. `NOWAIT` vs Ordinary Waiting

Suppose T1 currently owns the row lock:

```text
T1
 |
 +--> row 42 locked
```

T2 asks for the same lock.

## Ordinary behavior

```text
T2 -> request lock
      |
      +--> incompatible
              |
              +--> wait
```

The latency of T2 is now partly determined by T1's transaction duration.

## NOWAIT behavior

```text
T2 -> request lock NOWAIT
      |
      +--> incompatible
              |
              +--> error immediately
```

This creates an important architectural difference:

```text
Ordinary waiting

Resource contention
        |
        v
Database absorbs delay
        |
        v
Application request remains open


NOWAIT

Resource contention
        |
        v
Database rejects immediately
        |
        v
Application owns the policy
```

---

# 7. Why Fail-Fast Concurrency Is Useful

Waiting is not always a useful form of progress.

Consider a hotel-style reservation, warehouse workstation, or financial approval workflow:

```text
User A owns the resource

User B requests the same resource
```

There are two possible UX contracts.

### Contract A — Wait

> “Please wait while another operation finishes.”

### Contract B — Fail fast

> “This resource is currently busy. Try again or choose another one.”

For some workloads, Contract B is dramatically better because the application can immediately redirect the user or select an alternative resource.

Examples:

- editing a document already being processed;
- claiming a scarce workstation;
- changing a record under exclusive operational ownership;
- selecting one pending job from a small set of candidates;
- obtaining a short-lived business lock where waiting would create poor UX;
- preventing duplicate operator actions.

---

# 8. `NOWAIT` Is a Concurrency Decision, Not an Optimization Trick

A common bad explanation is:

> “Use `NOWAIT` because it is faster.”

That is incomplete.

`NOWAIT` can make a request complete faster **when contention exists**, but the system has not eliminated the conflict. It has transformed:

```text
wait and eventually succeed
```

into:

```text
fail immediately
```

Whether that is better depends on the application's policy.

The actual design question is:

> **When the resource is busy, should this operation wait, skip the resource, retry later, or fail as a business-level conflict?**

That is a correctness and product-semantics question first.

---

# 9. `NOWAIT` vs `SKIP LOCKED`

These are related but fundamentally different.

| Behavior | `NOWAIT` | `SKIP LOCKED` |
|---|---|---|
| Conflicting row | Error | Skip it |
| Query returns immediately | Yes, for the requested conflicting lock | Yes, for skipped locked rows |
| Result completeness | Preserved until conflict | Intentionally incomplete |
| Typical use | Fail-fast ownership check | Work distribution / queues |
| Caller sees conflict directly | Yes | No; locked rows simply disappear from result |
| Suitable for “must own this exact resource” | Yes | Usually no |
| Suitable for worker queues | Usually no | Yes |

Example:

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE NOWAIT;
```

means:

> “I need order `$1`. If someone owns it, tell me immediately.”

Whereas:

```sql
SELECT *
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

means:

> “Give me work that is immediately claimable; do not make me wait for locked work.”

This distinction is central to choosing the correct primitive.

---

# 10. `NOWAIT` vs `lock_timeout`

Another frequent confusion:

```sql
SET LOCAL lock_timeout = '2s';
```

is not identical to:

```sql
FOR UPDATE NOWAIT
```

Conceptually:

```text
NOWAIT
    wait budget = 0
```

while:

```text
lock_timeout = 2s
    wait budget = up to 2 seconds
```

The policies are different:

```text
NOWAIT
    conflict -> immediate error

lock_timeout = '2s'
    conflict -> possibly wait
    if still blocked after deadline -> timeout error
```

Therefore `NOWAIT` is deterministic with respect to waiting for that lock, whereas `lock_timeout` introduces a bounded waiting window.

PostgreSQL's documentation describes `lock_timeout` as the maximum amount of time a statement waits to acquire a lock before canceling; `0` disables the timeout. citeturn226736search8

# 11. Why `NOWAIT` Often Produces Better Latency Under Contention

Suppose:

```text
T1 holds lock for 4 seconds.
```

T2 arrives at t=1 second.

Without `NOWAIT`:

```text
T2 latency ≈ 3 seconds of lock waiting
```

With `NOWAIT`:

```text
T2 receives conflict almost immediately
```

From a latency perspective:

```text
Tail latency
     |
     +-- blocking wait increases with transaction duration
     |
     +-- NOWAIT caps lock waiting at effectively zero
```

However, application-level retries can reintroduce load:

```text
NOWAIT failure
      |
      v
retry immediately
      |
      v
NOWAIT failure
      |
      v
retry immediately
```

So:

> **NOWAIT prevents database-side waiting, but a badly designed retry loop can recreate the same contention at the application layer.**

# 12. A Classic Production Anti-Pattern: Immediate Retry Storm

Bad:

```ts
while (true) {
  try {
    await claimOrder(id);
    break;
  } catch (err) {
    if (isLockNotAvailable(err)) {
      continue;
    }
    throw err;
  }
}
```

This can produce:

```text
lock unavailable
     |
     v
retry immediately
     |
     v
lock unavailable
     |
     v
retry immediately
     |
     v
CPU/network amplification
```

The database is no longer waiting, but the application is effectively busy-spinning.

Better strategies may include:

```text
fail request

or

bounded retry
+
backoff
+
jitter
+
maximum attempts

or

switch to another resource

or

enqueue work for later
```

The correct choice depends on the business semantics.

# 13. Exact Resource vs Any Available Resource

This provides a useful architectural decision rule.

## Exact resource

Use `NOWAIT` when the operation means:

> “I specifically need resource R.”

Example:

```sql
SELECT *
FROM inventory_lots
WHERE lot_id = $1
FOR UPDATE NOWAIT;
```

If another transaction owns the row, failing is meaningful.

## Any available resource

Use `SKIP LOCKED` when the operation means:

> “I need some resource from this pool.”

Example:

```sql
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY priority DESC, id
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

A locked item is not a failure; another available item may be equally useful.

This distinction prevents many incorrect locking designs.

# 14. Fundamental Example — Protecting a Single Inventory Item

Suppose:

```text
inventory
---------
id | quantity
7  | 20
```

Transaction T1 begins:

```sql
BEGIN;

SELECT id, quantity
FROM inventory
WHERE id = 7
FOR UPDATE;
```

T1 now owns a conflicting row lock until transaction completion.

T2 executes:

```sql
BEGIN;

SELECT id, quantity
FROM inventory
WHERE id = 7
FOR UPDATE NOWAIT;
```

Instead of waiting for T1, T2 receives a lock-not-available error.

This enables the application to return something like:

```text
Inventory item is currently being modified.
Please retry shortly.
```

The important thing is that the application response is now a deliberate business policy rather than an accidental database wait.

---

# 15. Production Example — Order Editing

Suppose an operations dashboard allows users to edit order `ORD-10042`.

A naive endpoint might do:

```text
GET order
      |
user edits
      |
UPDATE order
```

This can create stale-edit problems.

A stronger workflow can acquire an explicit lock during the critical transaction:

```sql
BEGIN;

SELECT id, status, version
FROM orders
WHERE id = $1
FOR UPDATE NOWAIT;

-- validate state
-- apply change
-- commit
```

If another transaction is already performing a protected operation, the caller gets an immediate conflict.

However, this does **not** mean the HTTP request should hold the lock while the user thinks for 30 seconds. That would be a severe design error.

Instead:

```text
HTTP request
    |
short DB transaction
    |
claim/update/commit
    |
response
```

Keep the database lock lifetime short.

---

# 16. Production Example — Jewellery ERP Inventory Adjustment

Imagine two branch operators attempt to adjust the same jewellery stock record:

```text
Stock item:
branch_id = 12
item_id   = 8401
quantity  = 17
```

Operator A starts an adjustment and locks the row.

Operator B attempts:

```sql
BEGIN;

SELECT quantity
FROM stock
WHERE branch_id = $1
  AND item_id = $2
FOR UPDATE NOWAIT;
```

The database can fail immediately.

This can be turned into a domain-level response:

```text
RESOURCE_BUSY
```

That is often superior to allowing API latency to become dependent on another transaction's duration.

But the business rule must decide whether “busy” means:

```text
reject
retry
queue
select another record
ask operator to refresh
```

The database should not be expected to invent that product policy.

---

# 17. Production Example — Preventing Duplicate Operational Commands

Consider a system where a device or workstation can execute only one maintenance command at a time.

A coordination row can represent ownership:

```text
resource_locks
--------------
resource_id
state
```

A transaction may attempt:

```sql
SELECT resource_id
FROM resource_locks
WHERE resource_id = $1
FOR UPDATE NOWAIT;
```

If another transaction holds the row lock, the second operation fails immediately.

This is a database-backed mutual-exclusion protocol.

It is often simpler and more observable than inventing an application-only mutex that cannot coordinate processes, pods, or workers.

---

# 18. `NOWAIT` With Joins

PostgreSQL allows a locking clause to specify which table in a join should be locked.

For example:

```sql
SELECT o.id, c.id
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.id = $1
FOR UPDATE OF o NOWAIT;
```

The semantic question should always be:

> Which rows are actually part of the ownership boundary?

A common mistake is to lock every joined table simply because the query joins them.

Prefer the smallest lock footprint that protects the invariant.

---

# 19. `NOWAIT` and Multi-Row Locking

Consider:

```sql
SELECT id
FROM inventory
WHERE warehouse_id = $1
ORDER BY id
FOR UPDATE NOWAIT;
```

If the query encounters a conflicting row that it needs to lock, the command can fail instead of waiting.

This leads to a design question:

> What does the application want if only some rows can be locked?

With `NOWAIT`, partial success is usually not the desired semantic for an all-or-nothing operation.

For example, a stock transfer involving five rows may need all five rows.

A safer transactional model can be:

```text
attempt to establish the required lock set
       |
       +--> conflict
              |
              v
           abort
```

rather than:

```text
lock first four rows
skip the fifth
continue transfer
```

This is one reason `NOWAIT` and `SKIP LOCKED` should not be treated as interchangeable.

---

# 20. `NOWAIT` and Atomic SQL

Before introducing explicit locking, ask whether the operation can be expressed atomically.

Suppose inventory decrementation is simply:

```sql
UPDATE inventory
SET quantity = quantity - $1
WHERE id = $2
  AND quantity >= $1
RETURNING quantity;
```

This may be preferable to:

```text
SELECT ... FOR UPDATE NOWAIT
UPDATE ...
```

Why?

Because the business rule is already encoded in one DML statement.

The best design is often:

```text
one atomic SQL statement
```

rather than:

```text
read + lock + application logic + write
```

Use `NOWAIT` when the application genuinely needs explicit ownership semantics, not simply because locking looks safer.

---

# 21. `NOWAIT` and Optimistic Concurrency

`NOWAIT` is pessimistic concurrency control.

It says:

> “Before proceeding, try to acquire exclusive/shared ownership. If another transaction already owns an incompatible lock, fail.”

Optimistic concurrency says:

> “Proceed without taking that ownership lock, then detect whether the state changed when I write.”

Typical optimistic pattern:

```sql
UPDATE orders
SET status = $new_status,
    version = version + 1
WHERE id = $id
  AND version = $expected_version
RETURNING *;
```

Typical pessimistic pattern:

```sql
SELECT *
FROM orders
WHERE id = $id
FOR UPDATE NOWAIT;
```

Neither is universally better.

Choose based on:

- contention frequency;
- critical-section duration;
- business cost of conflicts;
- acceptable retries;
- user experience;
- number of participants;
- resource ownership semantics.

# 22. `NOWAIT` and Transaction Abort Behavior

This is an application-critical detail.

A `NOWAIT` conflict is a SQL error.

In PostgreSQL, once a statement inside a transaction raises an error, the transaction is generally left in an aborted state until it is rolled back or otherwise reset through the appropriate transaction-control mechanism.

For example:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE NOWAIT;

-- lock-not-available error

SELECT 1;
```

The second statement cannot simply proceed as though nothing happened; the transaction must be handled correctly.

In application code:

```text
BEGIN
  |
  v
statement
  |
  +--> NOWAIT conflict
          |
          v
      transaction enters error state
          |
          v
        ROLLBACK
```

This is why retrying only the failed SQL command on the same failed transaction is incorrect.

---

# 23. Savepoints and Recovering From a NOWAIT Conflict

A savepoint can isolate an expected failure within a larger transaction.

For example:

```sql
BEGIN;

SAVEPOINT try_resource;

SELECT *
FROM resources
WHERE id = $1
FOR UPDATE NOWAIT;

-- protected work

RELEASE SAVEPOINT try_resource;
COMMIT;
```

If the operation can legitimately fail and the surrounding transaction should continue, an application can roll back to a savepoint:

```sql
ROLLBACK TO SAVEPOINT try_resource;
```

The correct use depends on transaction semantics.

Do not use savepoints as a way to hide a fundamentally incorrect transaction architecture.

The deeper principle is:

> **Use a savepoint when the conflict is locally recoverable; use a full rollback when the failed operation invalidates the transaction's larger unit of work.**

# 24. Node.js / `pg` Transaction Pattern

A safe pattern is:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  const result = await client.query(
    `
      SELECT id, quantity
      FROM inventory
      WHERE id = $1
      FOR UPDATE NOWAIT
    `,
    [inventoryId],
  );

  // Perform only short, database-local work here.

  await client.query(
    `
      UPDATE inventory
      SET quantity = quantity - $1
      WHERE id = $2
    `,
    [amount, inventoryId],
  );

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

Important properties:

```text
BEGIN
  ↓
NOWAIT lock attempt
  ↓
short critical section
  ↓
COMMIT
  ↓
release connection
```

Never hold the lock while waiting for:

- HTTP APIs;
- user input;
- file uploads;
- slow network requests;
- remote service calls;
- unnecessary application computation.

# 25. NestJS Service Boundary

A clean service can make the business meaning explicit:

```ts
async adjustStock(id: number, amount: number) {
  return this.db.transaction(async (tx) => {
    try {
      const stock = await tx.query(
        `
          SELECT quantity
          FROM stock
          WHERE id = $1
          FOR UPDATE NOWAIT
        `,
        [id],
      );

      if (stock.rowCount === 0) {
        throw new NotFoundError('Stock item not found');
      }

      // Validate and update quickly.

      return await tx.query(
        `
          UPDATE stock
          SET quantity = quantity + $1
          WHERE id = $2
          RETURNING *
        `,
        [amount, id],
      );
    } catch (error) {
      // Translate lock-not-available at the service boundary.
      throw error;
    }
  });
}
```

The exact API varies by ORM/framework, but the invariant is constant:

> **The connection performing the `NOWAIT` lock and the subsequent writes must belong to the same database transaction.**

# 26. Connection-Pool Hazard

This is a severe Node.js mistake:

```ts
await pool.query('BEGIN');
await pool.query('SELECT ... FOR UPDATE NOWAIT');
await pool.query('UPDATE ...');
await pool.query('COMMIT');
```

A pool does not mean “one logical transaction magically follows the same physical PostgreSQL session.” Each call may be assigned to a different connection.

The transaction must be pinned to one checked-out client:

```ts
const client = await pool.connect();
```

Then every statement uses:

```ts
client.query(...)
```

This matters especially for locks because the lock belongs to the PostgreSQL transaction/session state, not to the JavaScript function conceptually.

---

# 27. ORM Hazard — Hiding the Locking Clause

A developer may write a repository helper that appears to perform:

```ts
findById(id)
```

and assume it provides ownership.

It does not unless the generated SQL actually contains the required locking clause and executes inside the intended transaction.

Production review should ask:

```text
What SQL was generated?
Which connection executed it?
Which transaction owns the lock?
Which rows are actually locked?
When is the lock released?
```

Abstraction is useful only when its concurrency semantics remain visible and correct.

---

# 28. Wrong Implementation — Catch and Continue on the Same Transaction

Bad:

```ts
try {
  await client.query(`
    SELECT *
    FROM orders
    WHERE id = $1
    FOR UPDATE NOWAIT
  `, [id]);
} catch (error) {
  return fallback();
}

await client.query('UPDATE orders SET ...');
```

Why it fails:

1. the `NOWAIT` statement raised an error;
2. the current transaction may now be aborted;
3. later SQL on that transaction cannot be treated as normal execution;
4. the fallback must be designed around transaction state.

Corrected shape:

```text
NOWAIT conflict
      |
      +--> local fallback via savepoint
      |
      or
      +--> rollback transaction
             |
             +--> return conflict
```

---

# 29. Wrong Implementation — Use `NOWAIT` Everywhere

AI-generated code sometimes applies:

```sql
FOR UPDATE NOWAIT
```

to every mutation.

Why it looks attractive:

> “Never block production traffic.”

Why it fails:

- expected contention becomes user-visible errors;
- normal workloads may become artificially fragile;
- successful operations require more retries;
- contention may move from database waits to application retry loops;
- the system can become fail-fast but not resilient.

Better rule:

> Use `NOWAIT` when immediate conflict detection is part of the application's semantics.

---

# 30. Wrong Implementation — Replace `NOWAIT` With a Random Sleep

Bad:

```ts
tryLock();
await sleep(200);
tryLock();
```

This is an application-level approximation of a concurrency policy without a clear correctness model.

Problems:

- arbitrary timing assumptions;
- herd behavior;
- unpredictable latency;
- poor utilization;
- no guarantee that the resource is free afterward;
- difficult testing.

Prefer a database-defined locking policy plus explicit application retry rules.

---

# 31. Wrong Implementation — Hold the Lock Across External I/O

Bad:

```text
BEGIN
  |
FOR UPDATE NOWAIT
  |
HTTP call to payment provider
  |
HTTP call to tax service
  |
HTTP call to inventory service
  |
UPDATE
  |
COMMIT
```

Now the lock duration depends on network behavior.

A slow dependency can create:

```text
long transaction
     |
     +--> prolonged lock ownership
     |
     +--> more NOWAIT failures
     |
     +--> more retries
     |
     +--> more contention
```

Better:

```text
short transaction
  |
claim durable state
  |
commit
  |
external processing
  |
short transaction
  |
finalize state
```

When true atomicity with an external system is required, use an explicit distributed workflow rather than silently extending a database lock across network calls.

---

# 32. `NOWAIT` and `ORDER BY`

When using locking reads with ordering, application developers often assume ordering alone creates a perfect reservation policy.

It does not.

The query plan, visibility rules, joins, and locking behavior all matter.

For deterministic application behavior:

```sql
SELECT id
FROM tasks
WHERE status = 'READY'
ORDER BY priority DESC, id
FOR UPDATE NOWAIT;
```

should be evaluated as a concurrency design, not just a SQL formatting choice.

The key question is:

> What happens when one of the selected rows is already locked?

With `NOWAIT`, that is a conflict rather than an instruction to silently move to another row. If the desired semantics are “find any free row,” `SKIP LOCKED` may be more appropriate.

---

# 33. `NOWAIT` and Table Locks

`NOWAIT` also applies to explicit table locking:

```sql
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE NOWAIT;
```

This is useful in controlled administrative or migration workflows where waiting behind an existing relation-level lock is unacceptable.

However, table-level `NOWAIT` can have a large blast radius.

```text
row-level NOWAIT
    -> potentially one row unavailable

relation-level NOWAIT
    -> potentially a whole workload unavailable
```

Therefore the same syntax can have radically different operational consequences depending on lock scope.

---

# 34. Lock Scope Is More Important Than the Keyword

Consider these three designs:

```text
A. FOR UPDATE NOWAIT on one row
B. FOR UPDATE NOWAIT on 10,000 rows
C. ACCESS EXCLUSIVE NOWAIT on a table
```

All contain the word `NOWAIT`.

Their operational meaning is completely different.

A useful review framework is:

```text
What is locked?
How many resources?
Which lock mode?
How long?
How many requests contend?
What happens on conflict?
```

The keyword alone tells you almost nothing about system-level risk.

# 35. Observability — Detecting NOWAIT Failures

Monitor application-level counts of lock-not-available failures.

For PostgreSQL diagnosis, useful views include:

```sql
SELECT
  pid,
  usename,
  state,
  wait_event_type,
  wait_event,
  xact_start,
  query_start,
  query
FROM pg_stat_activity;
```

and:

```sql
SELECT
  pid,
  locktype,
  relation::regclass,
  mode,
  granted,
  transactionid,
  virtualxid
FROM pg_locks;
```

`pg_stat_activity` helps answer:

> What sessions are active, idle in transaction, or waiting?

`pg_locks` helps answer:

> What lock requests are granted or waiting, and what resources are involved?

A pure `NOWAIT` failure may be so fast that it does not remain visible as a long-lived waiting session. That is expected.

Therefore application error metrics become particularly important.

# 36. Observability — Measure the Conflict, Not Just the Error

A useful dashboard may track:

```text
nowait_conflicts_total
nowait_conflict_rate
conflicts_by_endpoint
conflicts_by_resource_type
conflicts_by_tenant
retry_attempts
retry_success_rate
retry_exhaustion_rate
transaction_duration
```

For example:

```text
endpoint = /inventory/adjust
nowait_conflict_rate = 8.2%
```

That can reveal a hot business resource much earlier than generic database CPU metrics.

This is an important systems lesson:

> **A lock conflict can be a business-capacity signal rather than merely a database error.**

---

# 37. Performance Model

Think about three quantities:

```text
Contention rate
Critical-section duration
Arrival rate
```

If critical sections are long, the probability of `NOWAIT` conflicts rises.

Conceptually:

```text
more transaction duration
        |
        v
more lock occupancy
        |
        v
more overlap with competitors
        |
        v
more NOWAIT failures
```

This means reducing transaction duration can improve success rate even if query execution time is otherwise unchanged.

---

# 38. `NOWAIT` Is Not a Substitute for Short Transactions

Suppose a transaction holds a row lock for 500 ms.

Another request using `NOWAIT` will often fail during that window.

If the transaction is reduced to 20 ms:

```text
lock occupancy ↓
conflict window ↓
NOWAIT failure probability ↓
```

Therefore the optimization hierarchy should be:

```text
correct resource
      ↓
correct lock mode
      ↓
correct transaction scope
      ↓
short critical section
      ↓
then measure contention
```

Adding `NOWAIT` does not fix an oversized critical section.

---

# 39. Fairness and Starvation

`NOWAIT` itself does not implement fairness.

Imagine:

```text
worker A repeatedly acquires resource R
worker B repeatedly receives NOWAIT failures
```

If B always retries immediately, starvation can result.

Solutions can include:

- backoff;
- jitter;
- queueing;
- explicit ownership state;
- fair scheduling in the application;
- alternative resource selection;
- reducing critical-section duration.

The important distinction is:

```text
NOWAIT = fail-fast

fairness = separate scheduling problem
```

Do not assume the former provides the latter.

---

# 40. Retry Taxonomy

A production system should classify errors rather than simply retry all failures.

```text
lock not available
      |
      +--> expected contention?
      |       |
      |       +--> yes: bounded business retry / alternate resource
      |
      +--> structural hotspot?
              |
              +--> investigate architecture
```

Compare:

```text
unique_violation
serialization_failure
deadlock_detected
lock_not_available
lock_timeout
statement_timeout
connection_failure
network_failure
```

Each means something different.

A single generic:

```ts
retryOnDatabaseError(error)
```

is dangerous production code.

---

# 41. Error Translation at the API Boundary

A database-level failure should usually be mapped deliberately to a domain-level outcome.

Conceptually:

```text
PostgreSQL error
      |
      v
error classifier
      |
      v
RESOURCE_BUSY
      |
      v
HTTP / RPC / domain response
```

For example, an HTTP API might return a conflict-oriented response rather than a generic 500.

The exact status code depends on API semantics and organizational conventions, but the architectural principle is stable:

> **Expected contention should not be masqueraded as an unknown infrastructure failure.**

# 42. Security Considerations

`NOWAIT` does not grant permissions.

A caller still needs appropriate privileges for the underlying query/lock operation.

Security review should additionally consider whether exposing “resource busy” information leaks sensitive state.

Example:

```text
request for record X
  |
NOWAIT failure
  |
resource exists and is currently owned
```

If record identifiers are sensitive, conflict responses can become an information channel.

For multi-tenant systems:

```text
tenant authorization
      ↓
resource visibility
      ↓
row selection
      ↓
locking
```

Authorization must remain correct independently of the lock policy.

---

# 43. Multi-Tenant Contention

A shared PostgreSQL database may contain:

```text
tenant A
  |
  +-- hot resource

tenant B
  |
  +-- normal traffic
```

A poorly designed coordination row can accidentally create cross-tenant contention.

For example:

```sql
SELECT *
FROM locks
WHERE resource_type = 'inventory'
FOR UPDATE NOWAIT;
```

could lock more than intended if tenant scoping is missing.

Prefer precise predicates:

```sql
SELECT *
FROM inventory_locks
WHERE tenant_id = $1
  AND resource_id = $2
FOR UPDATE NOWAIT;
```

Tenant boundaries should be reflected in the locking model, not only in application filtering.

---

# 44. `NOWAIT` and Idempotency

A fail-fast request can be retried by the client.

Therefore the operation itself must be safe under retry semantics.

For example:

```text
client
  |
request
  |
NOWAIT conflict
  |
retry
```

A retry-safe command should have a clear idempotency model, such as:

- unique operation ID;
- version check;
- business command key;
- durable state transition.

Otherwise `NOWAIT` failures plus naive retries can turn a concurrency control mechanism into duplicate business actions.

---

# 45. When `NOWAIT` Is a Good Choice

Good candidates include:

### Exact-resource operational ownership

```text
“This record must be exclusively owned right now.”
```

### Low-latency APIs

```text
“Do not let a lock wait dominate p99 latency.”
```

### User-facing conflict semantics

```text
“Someone else is editing this resource.”
```

### Short critical sections

```text
Claim → validate → update → commit
```

### Controlled administrative operations

```text
Acquire table lock or fail rather than block production indefinitely.
```

---

# 46. When `NOWAIT` Is Usually the Wrong Choice

Avoid treating it as the default for:

- ordinary CRUD with naturally low contention;
- long workflows where waiting is a meaningful part of the product contract;
- queue workers where another available item is acceptable;
- broad table locking in a busy production database;
- workloads where failures are immediately retried in a tight loop;
- cases where optimistic concurrency is simpler;
- operations that need a consistent all-or-nothing lock set but use partial fallback logic.

For queues, `SKIP LOCKED` is often the more natural primitive.

For optimistic updates, version predicates may be preferable.

For critical cross-row invariants, stronger transaction-level techniques may be needed.

---

# 47. Decision Matrix

| Business meaning | Typical approach |
|---|---|
| “Wait until this exact resource becomes free” | Ordinary lock / bounded wait |
| “Fail immediately if this exact resource is busy” | `NOWAIT` |
| “Take any available resource” | `SKIP LOCKED` |
| “Detect stale state without locking first” | Optimistic concurrency |
| “Protect complex serializable invariant” | `SERIALIZABLE` / appropriate locking |
| “Do not block longer than N ms” | `lock_timeout` |

This matrix is more useful than memorizing individual SQL keywords.

# 48. Testing `NOWAIT` Deterministically

Concurrency tests should create a real lock conflict rather than hoping two requests overlap.

Session A:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE;
```

Keep the transaction open.

Session B:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE NOWAIT;
```

Expected outcome:

```text
lock-not-available
```

Then clean up Session A:

```sql
ROLLBACK;
```

A strong automated test should assert:

```text
T1 holds lock
T2 attempts NOWAIT
T2 fails immediately
T1 commits/rolls back
resource becomes available
subsequent attempt succeeds
```

# 49. Testing With a Node.js Harness

A useful integration test uses two dedicated clients:

```ts

    FROM inventory
```

# 52. AI / Vibe-Coding Failure Patterns

## “NOWAIT makes the query nonblocking.”

Incomplete.

It makes conflicting lock acquisition fail immediately, not every part of query execution nonblocking.

## “NOWAIT is always faster.”

False as a system-level rule.

It can reduce lock-wait latency while increasing application-level failures and retries.

## “Catch the error and continue.”

Unsafe inside a failed transaction unless the error is isolated using a suitable savepoint/transaction strategy.

## “Retry immediately until it works.”

Creates contention amplification and CPU/network waste.

## “Use NOWAIT instead of fixing long transactions.”

Treats a symptom instead of the root cause.

## “Use NOWAIT for queue workers.”

Often the wrong semantic. Workers generally want available work, making `SKIP LOCKED` a more natural fit.

## “NOWAIT replaces optimistic concurrency.”

It does not. They solve related but different problems.

# 54. Expert Distinction — Failure vs Wait vs Skip

Three operations can all observe the same underlying fact:

```text
resource is locked by another transaction
```

but produce different semantics:

```text
ORDINARY
    -> wait

NOWAIT
    -> fail

SKIP LOCKED
    -> skip
```

That is a powerful abstraction.

The database resource state is the same.

The caller's **coordination policy** is different.

# 55. Architecture Pattern — Resource Claim API

For a controlled resource, expose a domain-level operation:

```text
POST /resources/:id/claim
```

Transaction:

```sql
BEGIN;

SELECT id, state
FROM resources
WHERE id = $1
FOR UPDATE NOWAIT;

UPDATE resources
SET state = 'CLAIMED'
WHERE id = $1;

COMMIT;
```

API behavior:

```text
available -> claim succeeds
busy      -> conflict response
missing   -> not found
invalid   -> business validation error
```

This turns database concurrency semantics into an explicit application contract.

---

# 56. Architecture Pattern — Combining NOWAIT With State

Locks should usually not be the only record of ownership.

Prefer durable state such as:

```text
state
owner_id
claimed_at
version
```

Then:

```text
row lock
  = short-lived synchronization

state columns
  = durable business state
```

This is much more robust than treating an open database transaction itself as the business ownership record.

---

# 57. Architecture Pattern — Retry Outside the Failed Transaction

A safe retry shape is:

```text
attempt 1
    |
    +-- BEGIN
    +-- NOWAIT
    +-- conflict
    +-- ROLLBACK

backoff / alternate resource
    |
    v
attempt 2
    |
    +-- BEGIN
    +-- NOWAIT
    +-- success
    +-- COMMIT
```

Not:

```text
same failed transaction
      |
      +-- retry query
```

The transaction boundary is part of the retry unit.

# 58. Trade-Off Analysis

## `NOWAIT`

Advantages:

- immediate conflict detection;
- predictable lock-wait latency;
- useful user-facing conflict semantics;
- easy to reason about for exact-resource ownership.

Costs:

- more explicit failure handling;
- retry policy moves into application code;
- possible starvation;
- application-level retry storms;
- may expose contention as user-visible errors.

## Ordinary blocking

Advantages:

- many operations eventually succeed without application retry;
- simple semantics for low-contention workloads.

Costs:

- tail latency can grow;
- connection pool slots remain occupied;
- lock chains can amplify incidents.

## `SKIP LOCKED`

Advantages:

- excellent for queues and worker pools;
- avoids waiting behind busy rows;
- supports parallel work distribution.

Costs:

- incomplete result sets;
- fairness/starvation concerns;
- unsuitable when a specific resource is mandatory.

# 59. Senior Interview Questions

### Q1. What does `NOWAIT` do?

**Weak:**
> It makes the query nonblocking.

**Acceptable:**
> It prevents waiting for a conflicting lock and returns an error.

**Strong:**
> `NOWAIT` changes lock acquisition semantics so an incompatible requested lock fails immediately rather than waiting.

**Expert:**
> `NOWAIT` is a fail-fast coordination policy layered over PostgreSQL's lock manager. It eliminates lock waiting for the requested conflicting resource but does not eliminate other execution latency, and application retry behavior can reintroduce contention.

### Q2. `NOWAIT` vs `SKIP LOCKED`?

**Expert:**
> `NOWAIT` says a specific resource is required and conflict is an error. `SKIP LOCKED` says locked resources are not required because another available resource is acceptable.

### Q3. Why not retry immediately?

**Expert:**
> Because the retry itself can create a hot-loop that amplifies lock pressure. Retry must be bounded and usually include backoff/jitter or alternate-resource selection.

### Q4. Does `NOWAIT` mean zero blocking anywhere in the statement?

**Expert:**
> No. It governs waiting for the requested lock conflict, not all possible execution delays.

### Q5. Can you continue using the same transaction after a NOWAIT error?

**Expert:**
> Not as though nothing happened. A statement error normally places the transaction into an aborted state; the application must roll back or recover through an appropriate savepoint boundary.

# 60. Principal-Level Reasoning Questions

# 65. Key Takeaways

1. `NOWAIT` makes conflicting lock acquisition fail immediately rather than wait.
2. It does not mean the entire SQL statement is incapable of all forms of waiting or delay.
3. `NOWAIT` is primarily a coordination policy, not an optimization trick.
4. Use it when an exact resource is required and immediate conflict detection is meaningful.
5. Use `SKIP LOCKED` when another available resource is acceptable.
6. Use `lock_timeout` when bounded waiting is part of the desired policy.
7. Treat NOWAIT failures as distinct errors, not as generic database failures.
8. Do not retry immediately in a tight loop.
9. After a statement error, handle PostgreSQL transaction state correctly.
10. Keep locks short-lived and never hold them across avoidable external I/O.
11. Verify ORM-generated SQL and connection affinity.
12. Measure conflict rates as capacity and architecture signals.
13. `NOWAIT` does not replace optimistic concurrency, good data modeling, or proper transaction design.
14. The right concurrency primitive follows the business invariant and workload.

> **The expert skill is not knowing that `NOWAIT` exists. It is knowing exactly when waiting is the wrong behavior, expressing that policy explicitly in PostgreSQL, and designing the surrounding application so fast failure leads to controlled progress rather than retry storms.**
