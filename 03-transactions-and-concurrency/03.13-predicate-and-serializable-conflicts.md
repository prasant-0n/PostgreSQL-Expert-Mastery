# 03.13 — Predicate / Serializable Conflicts

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains the conflict-detection machinery behind PostgreSQL `SERIALIZABLE`: predicate semantics, `SIREAD` predicate locks, read/write dependencies, dangerous structures, serialization failures, observability, and production design.

# 2. The Core Problem: A Read Can Matter to a Future Write

The easiest way to misunderstand serializable conflicts is to think only in terms of two transactions trying to update the same row.

Consider a business rule:

> A doctor may be on call only when at least one other doctor remains on call.

Suppose two doctors are currently on call:

```text
on_call
-------
Alice  yes
Bob    yes
```

Transaction T1 checks:

```sql
SELECT count(*)
FROM doctors
WHERE on_call = true;
```

T1 sees `2`.

At roughly the same time T2 performs the same check and also sees `2`.

Then:

```text
T1 -> Alice off call
T2 -> Bob off call
```

Each transaction saw a valid starting state.

Each individual row update is valid.

Both transactions can nevertheless produce an invalid final state:

```text
Alice no
Bob   no

COUNT(on_call = true) = 0
```

There is no simple same-row lock conflict between the two updates.

The actual relationship is:

```text
T1 reads predicate P
T2 writes data affecting predicate P

T2 reads predicate P
T1 writes data affecting predicate P
```

That is the class of problem serializable conflict detection exists to catch.

# 3. What Is a Predicate?

## 3.1 Simple definition

A predicate is the condition that determines which rows a query is interested in.

Examples:

```sql
WHERE tenant_id = 7
WHERE status = 'PENDING'
WHERE quantity > 0
WHERE price BETWEEN 1000 AND 5000
WHERE account_id = 42
```

## 3.2 Engineering definition

For concurrency control, the predicate represents the logical set of rows whose presence, absence, or values influence the transaction's decision.

For example:

```sql
SELECT *
FROM inventory
WHERE branch_id = 10
  AND status = 'AVAILABLE';
```

The important logical question is not simply:

> “Which rows did I read?”

It is also:

> “What future writes would change the truth of the condition I relied on?”

That second question is where predicate-based conflict reasoning begins.

## 3.3 Expert definition

A predicate represents a logical read-set boundary. To preserve serializability, a concurrent transaction that creates or changes data which would have affected that earlier read must participate in dependency tracking. PostgreSQL's SSI records such read dependencies using `SIREAD` predicate locks rather than ordinary blocking locks. citeturn195076search1turn195076search2

---

# 4. Ordinary Locks vs Predicate Locks

These mechanisms solve different problems.

| Mechanism | Main purpose | Blocks? | Typical scope |
|---|---|---:|---|
| Row lock | Coordinate conflicting row operations | Yes | Tuple/row |
| Table lock | Coordinate relation-wide operations | Yes | Table |
| Advisory lock | Application-defined coordination | Yes | Arbitrary key |
| Predicate/SIREAD lock | Detect serializable read/write dependencies | Normally no | Tuple/page/relation/index depending on access path |

The crucial word is **detect**.

A `SIREAD` lock generally does not mean:

> “Other sessions are forbidden from writing this row.”

Instead it means something closer to:

> “This serializable transaction has read this logical region; later writes that overlap it may create an `rw` conflict that must be considered when deciding whether the concurrent execution remains serializable.”

PostgreSQL explicitly describes predicate locks as nonblocking and uses them to detect read/write conflicts. citeturn195076search2

---

# 5. Why Nonblocking Predicate Locks Exist

A naïve implementation of serializable predicate locking would simply block writes.

Imagine:

```sql
T1:
SELECT * FROM orders WHERE status = 'PENDING';
```

A strict blocking predicate lock would tell every concurrent transaction:

> “You cannot insert a new `PENDING` order until T1 commits.”

That would preserve correctness, but it could destroy concurrency for workloads where conflicts are rare.

PostgreSQL instead uses SSI:

```text
T1 reads predicate P
       |
       v
Record SIREAD coverage
       |
       +------------------------------+
                                      |
T2 writes row affecting P -----------+
                                      |
                                      v
                           Record rw dependency
                                      |
                                      v
                         Check dangerous patterns
                                      |
                    +-----------------+----------------+
                    |                                  |
               safe structure                    dangerous structure
                    |                                  |
                 continue                        abort one transaction
```

The database therefore pays conflict-tracking cost without forcing every potential conflict to block immediately.

PostgreSQL's documentation describes serializable transactions as repeatable-read transactions augmented with nonblocking monitoring of dangerous read/write patterns. citeturn195076search4

# 6. The Three Dependency Types You Must Recognize

A useful graph model is:

```text
Transaction A ----dependency----> Transaction B
```

Three dependency shapes matter in serialization reasoning.

## 6.1 Write → Read dependency (`wr`)

A transaction reads a value written by another transaction.

Conceptually:

```text
T1 writes X
   |
   v
T2 reads X
```

This is normally consistent with an ordering where T1 occurs before T2.

## 6.2 Write → Write dependency (`ww`)

Two transactions modify the same logical data.

```text
T1 writes X
   |
   v
T2 writes X later
```

This establishes an ordering between the writes.

## 6.3 Read → Write dependency (`rw`)

The subtle one.

```text
T1 reads condition P
        |
        | concurrent write changes P
        v
T2 writes data affecting P
```

The writer may have changed data that was not visible to T1 but would have affected the result of T1's read if it had existed or been committed at the relevant time.

SSI focuses heavily on `rw` dependencies because cycles involving them are what allow snapshot-based execution to become nonserializable. PostgreSQL's SSI description explicitly identifies `rw` conflicts between concurrent transactions and uses conflict graphs to reason about anomalies. citeturn195076search1

---

# 7. Serialization Graphs

Imagine every transaction as a node:

```text
      +-------+
      |  T1   |
      +-------+
        |   ^
       rw   rw
        |   |
        v   |
      +-------+
      |  T2   |
      +-------+
```

If the graph can be ordered consistently, the execution can be explained as a serial order.

If the dependencies form a cycle:

```text
T1 -> T2 -> T3 -> T1
```

then there is no equivalent serial order for those dependencies.

That is the key correctness boundary:

```text
No cycle
   -> serializable explanation exists

Dangerous cycle / dangerous structure
   -> PostgreSQL may abort a transaction
```

The goal is not to prevent concurrency.

The goal is to prevent an **unexplainable concurrent result** from committing as though it were serial execution.

---

# 8. The Classic Write-Skew Pattern

Write skew is the canonical example.

Initial state:

```text
shift_staff
-----------
id | on_call
---+--------
1  | true
2  | true
```

Rule:

```text
At least one person must remain on call.
```

T1:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT count(*)
FROM shift_staff
WHERE on_call = true;

UPDATE shift_staff
SET on_call = false
WHERE id = 1;
```

T2 concurrently does:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT count(*)
FROM shift_staff
WHERE on_call = true;

UPDATE shift_staff
SET on_call = false
WHERE id = 2;
```

Both reads initially return `2`.

At least one transaction must eventually fail because allowing both commits would violate serializable execution.

One possible outcome is:

```text
T1 COMMIT
T2 -> ERROR 40001
```

The exact victim is implementation-dependent; applications must not build correctness around which transaction is selected.

PostgreSQL's application-level consistency documentation uses this general principle: serializable transactions can protect multi-query integrity rules without requiring application programmers to manually construct all the blocking locks. citeturn195076search4

---

# 9. “But I Did Not Read the New Row”

This is one of the deepest questions in predicate conflict reasoning.

Suppose:

```sql
SELECT *
FROM reservations
WHERE room_id = 10
  AND start_at < '2026-10-10'
  AND end_at > '2026-10-09';
```

No conflicting reservation exists.

The query returns zero rows.

Another transaction inserts a reservation satisfying the condition.

The second transaction has changed the truth of the predicate even though it did not update a row that the first transaction returned.

That is why serializable conflict detection must reason about **absence and potential future membership**, not only about rows that were physically returned.

A normal row lock cannot protect a row that does not yet exist.

A predicate conflict can.

---

# 10. Predicate Locks Do Not Mean “Lock the WHERE Clause”

Do not imagine PostgreSQL storing:

```text
WHERE room_id = 10 AND date = '2026-10-09'
```

as a literal expression-level lock.

Predicate locking is implemented using physical/logical lock targets associated with the data access path.

Depending on how PostgreSQL accesses the data, predicate locks can be associated with:

```text
tuple
page
relation
index structures
```

The exact coverage can therefore differ from the text of the SQL predicate.

PostgreSQL documents that table scans can lead to relation-level predicate locks, while index access methods can provide finer-grained predicate locking when supported. citeturn195076search1turn195076search2

This leads to an important production concept:

> **Predicate conflict precision is influenced by the chosen access path.**

---

# 11. Heap-Level Predicate Locking

PostgreSQL's SSI implementation tracks predicate coverage in the heap as well as through indexes.

Conceptually:

```text
Table scan
   |
   +--> relation-level SIREAD coverage

Visible tuple access
   |
   +--> tuple/page/relation predicate coverage
```

The implementation documentation states that for a table scan the predicate lock can cover the entire relation, while visible tuples can acquire more specific heap-level coverage depending on the access pattern and lock aggregation. citeturn195076search1

The engineering consequence is important:

```text
Broad predicate coverage
        |
        v
More transactions may appear to conflict
        |
        v
More serialization cancellations
```

False positives can be safe from a correctness perspective but expensive from a throughput perspective.

---

# 12. Indexes and Predicate Conflict Precision

Indexes matter because serializable conflict tracking must know which future writes could affect a previous indexed search.

For example:

```sql
SELECT *
FROM products
WHERE sku >= 'A100'
  AND sku <  'A200';
```

An index-aware serializable access path can track a narrower logical region than a full-table scan.

PostgreSQL's index-locking documentation explains that index access methods can provide predicate locking internally. When an access method does not provide finer-grained predicate locks, PostgreSQL can fall back to predicate-locking the whole index, increasing the range of inserts that may conflict. citeturn195076search2

Conceptually:

```text
Fine-grained index predicate coverage
        |
        +--> fewer unrelated rw conflicts

Coarse relation/index coverage
        |
        +--> more false-positive conflicts
```

This does **not** mean:

> “Add an index so SERIALIZABLE never fails.”

Indexes affect access paths and may reduce conflict scope, but serializability is a correctness mechanism, not an indexing optimization problem.

---

# 13. `SIREAD` Locks Are Special

A `SIREAD` predicate lock behaves differently from a normal blocking lock.

Important characteristics:

- it exists for serializable conflict detection;
- it is normally nonblocking;
- it represents a prior read that may matter to future writes;
- its coverage can be promoted or aggregated to coarser granularity;
- it can survive beyond the instant the original read physically executes because the conflict information may still be needed;
- it is observable through PostgreSQL's lock infrastructure.

Do not interpret this as a normal exclusive lock.

The right mental model is:

```text
Normal lock:
    “You cannot proceed until I release this.”

SIREAD:
    “Remember that I read this region so later writes can be checked for conflicts.”
```

PostgreSQL's current documentation explicitly distinguishes predicate locking from blocking locks and discusses predicate lock granularity. citeturn195076search1turn195076search2

---

# 14. Why Predicate Locks Can Be Aggregated

Tracking every tuple separately forever would be expensive.

Suppose a serializable transaction reads 500,000 rows.

A naïve model would create:

```text
500,000 independent predicate lock records
```

PostgreSQL can instead aggregate coverage.

Conceptually:

```text
Tuple locks
   |
   | too many / same page
   v
Page-level coverage
   |
   | broader aggregation
   v
Relation-level coverage
```

This reduces metadata pressure but broadens the conflict region.

That is a classic systems trade-off:

```text
metadata efficiency <-> conflict precision
```

The more coarse-grained the tracking becomes, the more unrelated future writes can intersect the tracked region.

---

# 15. A Crucial Distinction: Detection vs Blocking

Consider two transactions:

```text
T1: serializable read
T2: write
```

A normal blocking lock says:

```text
T2 WAIT
```

A serializable predicate conflict may instead say:

```text
T2 CONTINUE
        |
        v
record dependency
        |
        v
T1/T2 relationship analyzed
        |
        v
possibly abort later
```

Therefore this can happen:

```text
No visible lock wait
        |
        v
Transaction still gets
serialization failure
```

This is why searching only for blocked sessions is insufficient when debugging `SERIALIZABLE` failures.

# 16. Serialization Failure vs Deadlock

## Deadlock

```text
T1 waits for T2
T2 waits for T1
```

The lock manager detects a wait cycle.

Typical error:

```text
ERROR: deadlock detected
SQLSTATE: 40P01
```

## Serialization failure

The database detects that the concurrent dependency pattern cannot safely commit while preserving serializable semantics.

Typical SQLSTATE:

```text
40001
```

The transaction may have experienced no conventional blocking cycle at all.

Therefore:

```text
40P01 != 40001
```

The retry architecture may overlap, but the operational diagnosis is different.

PostgreSQL's application-level guidance identifies `40001` as the standard serialization-failure code and recommends retrying the whole transaction. citeturn195076search1turn195076search4

---

# 17. The Dangerous Structure Intuition

You do not need to memorize internal implementation code to reason correctly.

Use this mental model:

```text
T1 reads something
   |
   | rw conflict
   v
T2 reads/writes
   |
   | rw conflict
   v
T3
```

If dependencies can create a cycle that cannot be serialized safely, PostgreSQL must break the structure by aborting a transaction.

A practical expert question is:

> “Which transaction read something that another concurrent transaction later changed, and what other dependency links connect the transactions?”

That question is much more useful than:

> “Which row was locked?”

# 18. Predicate Conflicts and Empty Results

Empty result sets are especially important.

Suppose:

```sql
SELECT count(*)
FROM inventory
WHERE branch_id = 4
  AND status = 'AVAILABLE';
```

returns:

```text
0
```

The application may now decide:

> “No available item exists, therefore create one.”

Another transaction makes the same decision concurrently.

Both can read zero.

Both can insert.

Whether the invariant is preserved depends on the data model and the concurrency mechanism.

A unique constraint might solve a uniqueness invariant:

```sql
CREATE UNIQUE INDEX ...;
```

A serializable transaction might solve a more complex cross-row invariant.

An explicit locking strategy might solve a narrow known resource conflict.

The important engineering rule is:

> **Do not use `SERIALIZABLE` as a substitute for a constraint that can directly encode the invariant.**

When a rule is naturally representable as a constraint, the constraint usually provides a simpler and stronger boundary.

---

# 19. Constraint vs Predicate Conflict Detection

Consider the requirement:

> A customer may have only one active subscription.

Bad solution:

```text
SELECT active subscription
IF none:
    INSERT
```

Concurrent requests can race.

Better database design:

```sql
CREATE UNIQUE INDEX one_active_subscription
ON subscriptions(customer_id)
WHERE status = 'ACTIVE';
```

Now the invariant is encoded directly.

The database can reject the conflicting write deterministically.

Use serializable isolation when the rule is more complex, such as:

```text
No more than three active resources across a group
unless another qualifying record exists
and a separate aggregate remains below a threshold.
```

The hierarchy is often:

```text
Simple invariant
    -> CHECK / UNIQUE / EXCLUDE / FK

Known row conflict
    -> row lock / atomic update

Complex multi-row dependency
    -> SERIALIZABLE or carefully designed explicit locking
```

# 20. Explicit Locking Can Replace Some Predicate Problems

PostgreSQL documentation notes that applications using nonserializable writes can enforce consistency with explicit blocking locks such as `SELECT FOR UPDATE`, `SELECT FOR SHARE`, or `LOCK TABLE`. citeturn195076search4

Example:

```sql
SELECT *
FROM branch_state
WHERE branch_id = 10
FOR UPDATE;
```

Then all transactions that need to change the branch-wide invariant coordinate through the same row.

This is a powerful design technique:

```text
Complex distributed invariant
          |
          v
Introduce stable coordination row
          |
          v
Serialize modifications through that row
```

This can outperform broad serializable conflict tracking in a high-contention hotspot.

But it also creates a hotspot.

Again:

```text
Correctness first
then measure contention
then optimize coordination
```

# 21. Production Example: Jewellery ERP Stock Allocation

Suppose a branch has a limited pool of sellable items.

A naïve implementation:

```text
1. SELECT available inventory
2. If available, mark item reserved
3. Create invoice line
4. Commit
```

Under concurrency, two operators can reason from overlapping state.

Potential designs:

### Design A — Atomic row update

```sql
UPDATE inventory
SET reserved = true,
    reserved_by = $2
WHERE id = $1
  AND reserved = false
RETURNING *;
```

Best when a single row is the coordination object.

### Design B — `FOR UPDATE`

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR UPDATE;
```

Then validate and update.

Best when the workflow needs a controlled read-modify-write sequence.

### Design C — Serializable

Use when the decision depends on a more complicated multi-row invariant and encoding the rule as a simpler lock/constraint would be awkward or unsafe.

The correct decision depends on the actual invariant, conflict rate, latency requirements, and retry tolerance.

# 22. Multi-Tenant Conflict Amplification

Predicate conflicts can be dramatically affected by tenant scoping.

Suppose every query includes:

```sql
WHERE tenant_id = $1
```

A properly indexed access path can help keep reads physically focused on the tenant's portion of the data.

But a broad scan such as:

```sql
SELECT count(*)
FROM orders
WHERE status = 'PENDING';
```

may logically cross tenants even when the application only cares about one tenant's business rule.

This creates a critical architectural question:

> “Is the transaction's invariant tenant-local or global?”

If tenant-local:

```text
tenant-scoped predicates
+ tenant-aware indexes
+ tenant-local coordination
```

may substantially reduce unnecessary conflict overlap.

If the invariant is global:

```text
Do not accidentally weaken it by assuming tenant isolation that the business rule does not actually permit.
```

# 23. Node.js / NestJS Transaction Boundary

A serializable transaction must execute on a single database session/connection for its entire logical attempt.

Correct conceptual structure:

```ts
const result = await withTransaction(async (client) => {
  await client.query(
    'SET TRANSACTION ISOLATION LEVEL SERIALIZABLE',
  );

  const state = await client.query(/* read */);
  // business decision
  await client.query(/* write */);
  return result;
});
```

The exact framework API varies, but these invariants do not:

```text
BEGIN
  |
  +-- all reads
  +-- all validations
  +-- all writes
  +-- COMMIT / ROLLBACK
       |
       +--> same physical connection
```

Do not let one ORM call use transaction client A and another call silently use pooled client B.

That destroys the intended transaction boundary.

---

# 24. Retry the Whole Serializable Transaction

Serialization failure is not a signal to repeat only the failed query.

Use:

```text
logical operation
      |
      +-- attempt 1
      |      read
      |      decide
      |      write
      |      commit
      |
      +-- 40001
             |
             v
          rollback/cleanup
             |
             v
          attempt 2
             read again
             decide again
             write again
             commit
```

A robust Node.js policy should generally include:

- bounded retries;
- exponential backoff;
- jitter;
- a clear retryable-error classifier;
- transaction re-execution from the beginning;
- idempotent external side effects;
- metrics for retry frequency;
- logging of transaction attempt number and reason.

Never write:

```ts
catch {
  retryEverythingForAnyError();
}
```

That can turn one database problem into an uncontrolled retry storm.

---

# 25. External Side Effects Are Outside SSI

Suppose the transaction does this:

```text
SERIALIZABLE transaction
    |
    +-- update database
    +-- call payment provider
    +-- commit
```

If the database aborts with `40001`, the payment provider may already have processed the charge.

Retrying the database transaction could charge the customer twice.

The correct architecture is generally:

```text
Database transaction
    |
    +-- persist durable intent/outbox event
                 |
                 v
           commit transaction
                 |
                 v
       asynchronous side effect
```

or use a provider-supported idempotency key.

Serializable isolation protects the database transaction.

It does not magically make external systems transactional.

---

# 26. Long-Running Serializable Transactions

Long-running transactions are dangerous because their conflict footprint remains relevant for longer.

As transaction duration increases:

```text
longer lifetime
      |
      +--> more concurrent transactions overlap
      |
      +--> more possible rw dependencies
      |
      +--> more predicate-lock metadata retained
      |
      +--> greater chance of serialization cancellation
      |
      +--> greater resource and vacuum pressure
```

This is one reason PostgreSQL's documentation warns that SSI performance can degrade more rapidly with a large number of active transactions and that controlling concurrency with a connection pool may be necessary. citeturn195076search1

Therefore:

```text
Do not keep a serializable transaction open while waiting for:
- HTTP APIs
- user input
- slow queues
- file uploads
- external services
- expensive application computation
```

---

# 27. Connection Pool Size Is a Concurrency Control Tool

Developers often think:

> “More connections = more throughput.”

With serializable workloads, this can be wrong.

Suppose:

```text
Pool size = 100
Active serializable transactions = 100
```

If the workload generates dense overlap:

```text
100 active transactions
        |
        v
many dependency relationships
        |
        v
more conflict tracking
        |
        v
more retries
        |
        v
more work
```

Then increasing the pool can decrease useful throughput.

The right question is:

> “What concurrency level maximizes committed useful work while keeping retry rate and latency acceptable?”

Measure it.

# 28. Observability: What to Measure

Use multiple evidence sources.

## 28.1 Current activity

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL
   OR state = 'active';
```

## 28.2 Locks

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    relation,
    page,
    tuple,
    virtualxid,
    transactionid
FROM pg_locks;
```

PostgreSQL 18 documents that current transaction IDs are represented through `virtualxid` and `transactionid` in `pg_locks`, while row-level locks can be inspected at the row layer with `pgrowlocks`. citeturn195076search6

## 28.3 Blocking graph

For conventional waits:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blockers,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE wait_event IS NOT NULL;
```

But remember:

```text
serialization failure
!= necessarily blocked session
```

You may need application logs and transaction-level metrics to correlate `40001` with specific code paths and workloads.

# 29. What to Log in a Serializable Application

At minimum, capture:

```text
request_id
transaction_id / trace_id
attempt number
isolation level
logical operation name
start time
commit/rollback outcome
SQLSTATE
retry count
tenant/business key
latency
```

Avoid logging sensitive row contents unnecessarily.

A useful metric is:

```text
serializable_retry_rate
    = serialization_failures / serializable_attempts
```

Also track:

```text
p50/p95/p99 transaction latency
average retries per successful operation
max retries
40001 rate by endpoint
40001 rate by SQL fingerprint
```

A low average retry count can hide a pathological hot endpoint.

# 30. `pg_locks` Does Not Give the Entire SSI Story

This deserves emphasis.

`pg_locks` is invaluable, but it is not a complete visualization of the application-level serialization graph.

You should combine:

```text
pg_stat_activity
+
pg_locks
+
application retry logs
+
SQL fingerprints
+
transaction duration
+
workload/business key
```

Think in terms of evidence layers:

```text
Database waits
      |
      +--> pg_stat_activity / pg_locks

Database aborts
      |
      +--> SQLSTATE / server logs

Application retries
      |
      +--> metrics/logs/traces

Business hotspot
      |
      +--> endpoint / tenant / entity correlation
```

This prevents the classic mistake of concluding:

> “There are no blocked locks, so the database has no concurrency problem.”

# 31. Performance Trade-Offs

Serializable isolation adds bookkeeping and can cause aborted work.

Cost dimensions include:

```text
CPU
memory
predicate-lock metadata
transaction overlap
retry work
latency variance
connection utilization
application complexity
```

The right comparison is not:

```text
SERIALIZABLE = slow
```

The right comparison is:

```text
Cost of stronger conflict detection
        vs
Cost of preventing the anomaly another way
```

For one invariant:

```text
SERIALIZABLE
```

may be the simplest correct design.

For another:

```text
UNIQUE constraint + atomic INSERT
```

may be substantially cheaper.

For another:

```text
single coordination row + FOR UPDATE
```

may outperform generalized serializable coordination.

# 32. Wrong Implementation: “Retry Every Database Error”

## Naive approach

```ts
try {
  await runTransaction();
} catch {
  await runTransaction();
}
```

## Why it fails

It may retry:

```text
syntax error
permission error
unique violation
foreign-key violation
invalid input
out-of-memory conditions
connection failures
business-rule errors
```

Some are not transient.

## Improved approach

Classify database failures.

```text
40001  -> serialization retry candidate
40P01  -> deadlock retry candidate
23505  -> usually business/data conflict, not generic retry
23503  -> integrity problem
57014  -> cancellation/timeout class
```

Then apply bounded retry policy according to the operation semantics.

# 33. Wrong Implementation: “Serializable Means No Locks”

False.

Serializable transactions still involve ordinary database mechanisms such as:

```text
row locks
relation locks
transaction visibility
index concurrency
WAL
MVCC
```

SSI adds another layer:

```text
predicate conflict detection
```

So:

```text
SERIALIZABLE
!=
lock-free
```

The actual system is a combination of snapshot visibility, write coordination, and dependency tracking.

---

# 34. Wrong Implementation: “Predicate Locks Block Inserts”

Not necessarily.

`SIREAD` predicate locks are primarily nonblocking conflict records.

The write may proceed.

PostgreSQL then evaluates the resulting dependency structure and may cancel a transaction to prevent a nonserializable outcome. citeturn195076search2turn195076search4

This is a major conceptual difference from traditional two-phase blocking predicate-lock schemes.

---

# 35. Wrong Implementation: “SERIALIZABLE Eliminates the Need for Constraints”

It does not.

Suppose the invariant is:

```text
SKU must be globally unique.
```

Use:

```sql
UNIQUE (sku)
```

Do not replace a direct structural constraint with a generalized concurrency policy simply because serializable exists.

Constraints are:

```text
local
explicit
declarative
persistent
easy to test
```

Use the simplest database mechanism that directly expresses the invariant.

# 36. AI / Vibe-Coding Mistakes

## Mistake 1 — “Use SERIALIZABLE everywhere”

Why it looks good:

```text
maximum consistency = maximum safety
```

Why it fails:

- more aborted transactions;
- more retries;
- higher latency variance;
- more contention sensitivity;
- operational complexity.

Better:

```text
Choose isolation per invariant/workload.
```

## Mistake 2 — “Retry the failed UPDATE”

Why it fails:

The transaction's entire dependency context may be invalid.

Retry the logical transaction, not just one query.

## Mistake 3 — “Add an index to eliminate serialization failures”

An index can improve access-path precision but cannot make logically conflicting business operations independent.

## Mistake 4 — “Check in Node, enforce later”

This reintroduces race conditions.

## Mistake 5 — “Lock the row returned by the query”

What if the query returns zero rows?

The invariant may be about the absence of a row or the entire matching set.

## Mistake 6 — “No lock wait means no conflict”

SSI conflicts can produce an abort without a traditional blocking wait.

# 43. Security Considerations

Serializable transactions can help prevent integrity violations, but they are not an authorization mechanism.

Do not confuse:

```text
SERIALIZABLE
```

with:

```text
tenant isolation
authorization
RLS
privilege control
```

A perfectly serializable transaction can still execute an unauthorized update.

Use the correct security boundary:

```text
Authentication
    +
Authorization
    +
RLS / tenant controls
    +
Constraints
    +
Concurrency control
```

These solve different problems.

# 44. Reliability Considerations

A serializable application must treat transaction aborts as a normal operating condition under contention.

This implies:

```text
retry-safe code
idempotent side effects
bounded retry count
backoff
observability
capacity planning
```

Failure is not an implementation accident.

At this isolation level, transaction cancellation is part of the mechanism that preserves correctness.

PostgreSQL documents this directly: applications should be prepared to retry transactions that are rolled back with serialization failures. citeturn195076search1turn195076search4

# 45. Advanced Insight — Serializable Is a Contract With the Application

The database can guarantee:

> Successful committed serializable transactions have an execution equivalent to some serial order.

The application still must provide:

```text
correct transaction boundaries
complete reads/writes
proper isolation selection
retry handling
side-effect discipline
```

If critical business logic runs outside the transaction:

```text
read DB
call external API
new transaction
write DB
```

the database cannot make the whole workflow serializable.

Therefore:

```text
Database serializability
!=
whole-system serializability
```

This distinction becomes increasingly important in distributed architectures.

# 46. Advanced Insight — A Retry Is a New Logical Attempt

The cleanest mental model is:

```text
Attempt 1
   |
   +--> aborted

Attempt 2
   |
   +--> fresh snapshot
   +--> fresh dependency graph
   +--> fresh reads
   +--> fresh decision
   +--> commit
```

Do not carry stale values from attempt 1 into attempt 2 unless they are immutable inputs.

For example, this is suspicious:

```ts
const available = await readInAttempt1();

retry(async (tx) => {
  await tx.update(...available...);
});
```

The retry should normally re-read the authoritative state inside the new transaction.

# 47. Expert Mental Model

When a serializable transaction fails, reason backward:

```text
40001
  |
  v
What logical operation failed?
  |
  v
What did the transaction read?
  |
  v
What concurrent transaction wrote into that read set?
  |
  v
What other dependency linked those transactions?
  |
  v
Could the successful result be ordered serially?
  |
  +--> yes: why did access-path / dependency tracking produce pressure?
  |
  +--> no: which transaction must be retried?
```

This is much stronger than:

> “Postgres randomly failed my query.”

Nothing random is required.

A serialization failure is evidence that the concurrency protocol found a combination of operations that cannot all safely commit under the requested isolation semantics.

# 49. Trick Questions

### “Does a predicate lock stop all inserts matching the predicate?”

**Weak:** Yes.  
**Strong:** No; `SIREAD` predicate locks are normally nonblocking conflict-tracking mechanisms.

### “If no rows were returned, no lock exists.”

**Weak:** Correct.  
**Strong:** Incorrect; serializable reads can track predicate coverage even for conditions whose current result is empty.

### “If a transaction never waits, it cannot have a serialization failure.”

**Weak:** Correct.  
**Strong:** Incorrect; SSI conflict detection can abort a transaction without a conventional lock wait cycle.

### “An index guarantees fewer serialization failures.”

**Weak:** Yes.  
**Strong:** No; an index can change the access path and potentially improve predicate-lock precision, but actual failure rates depend on workload and dependency structure.

# 51. Production Readiness Checklist

Before shipping serializable business logic, verify:

### Correctness

- [ ] The invariant is explicitly defined.
- [ ] Constraints are used where they can encode the rule directly.
- [ ] All required reads occur inside the transaction.
- [ ] All required writes occur inside the transaction.
- [ ] The transaction uses the intended isolation level.

### Retry

- [ ] SQLSTATE `40001` is classified as retryable where appropriate.
- [ ] The whole transaction is retried.
- [ ] Retry count is bounded.
- [ ] Backoff includes jitter.
- [ ] Retry metrics exist.

### Application boundary

- [ ] All transaction statements use the same connection.
- [ ] External side effects are not duplicated by retries.
- [ ] Idempotency is defined for retried operations.
- [ ] Time spent inside the transaction is minimized.

### Observability

- [ ] `40001` is measurable by endpoint/operation.
- [ ] Transaction duration is visible.
- [ ] Hot keys/tenants can be identified.
- [ ] `pg_stat_activity` and `pg_locks` are available during incidents.
- [ ] Logs preserve attempt number and correlation ID.

### Performance

- [ ] Connection pool size is load-tested.
- [ ] Retry rate is benchmarked under expected concurrency.
- [ ] p95/p99 latency is measured.
- [ ] Access paths are understood with `EXPLAIN`.
- [ ] Long-running transaction patterns are eliminated.

The deepest lesson is:
