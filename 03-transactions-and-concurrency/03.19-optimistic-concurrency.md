# 03.19 — Optimistic Concurrency

> **Phase 03 — Transactions & Concurrency**  
> Optimistic concurrency is a conflict-detection strategy: allow independent actors to work without holding a long-lived database lock, then make the write succeed only when the data is still at the version the caller originally observed.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- define optimistic concurrency precisely;
- distinguish optimistic concurrency from optimistic locking as a database implementation technique;
- explain why MVCC does not automatically prevent lost updates;
- implement compare-and-set (`WHERE version = ?`) updates safely;
- understand affected-row counts as a concurrency signal;
- use integer versions, timestamps, and stronger tokens correctly;
- design optimistic concurrency across HTTP APIs and database transactions;
- distinguish stale-data conflicts from validation failures and serialization failures;
- reason about retries without accidentally overwriting newer state;
- compare optimistic and pessimistic approaches;
- understand the interaction with `READ COMMITTED`, `REPEATABLE READ`, and `SERIALIZABLE`;
- identify ORM and AI-generated concurrency mistakes;
- debug production conflicts using logs, SQL, row counts, and transaction evidence;
- design conflict responses and user-facing merge/retry workflows;
- apply optimistic concurrency to inventory, orders, pricing, documents, settings, and other mutable business records.

# 2. Central Principle

> **Optimistic concurrency does not prevent another transaction from changing a row; it makes your write conditional on the row still representing the version of reality you originally read.**

The fundamental pattern is:

```text
READ version N
     |
     | another actor may modify the row
     |
WRITE only WHERE version = N
     |
     +--> 1 row changed -> success
     |
     +--> 0 rows changed -> stale write detected
```

The database is being asked to perform an atomic compare-and-set operation:

```text
if current_version == expected_version:
    apply mutation
    version = version + 1
else:
    reject
```

The comparison and mutation must happen inside the same SQL statement or otherwise inside a database-enforced concurrency boundary. Doing the comparison only in application code is not enough.

---

# 3. What Optimistic Concurrency Means

## 3.1 Simple definition

Optimistic concurrency assumes conflicts are relatively uncommon, so transactions do not hold a lock merely to reserve a row while application logic runs. Instead, the write checks whether the row changed since it was read.

## 3.2 Engineering definition

A mutable record carries a concurrency token such as an integer version. A client reads the record and token, performs work using that representation, and later issues an update whose predicate includes the expected token. If no row is updated, the caller knows the record changed meanwhile.

## 3.3 Expert definition

Optimistic concurrency is an application-level compare-and-set protocol layered on top of PostgreSQL's atomic statement execution and MVCC. Its correctness depends on the database enforcing the expected-state predicate at write time, interpreting the affected-row count correctly, and ensuring every competing writer participates in the same protocol. It is a coordination strategy, not merely a schema column.

---

# 4. Why MVCC Alone Does Not Solve Lost Updates

PostgreSQL MVCC provides multiple tuple versions and snapshot-based visibility. That does not mean the application automatically gets a conflict whenever two users edit the same logical object.

Consider:

```text
balance = 1000
```

Two requests read it:

```text
T1 reads 1000
T2 reads 1000
```

Then both compute a new value independently:

```text
T1 -> 1100
T2 -> 900
```

With naive application code:

```sql
UPDATE accounts
SET balance = $1
WHERE id = $2;
```

both updates can succeed sequentially, producing one final value and silently replacing the other actor's work.

The database correctly serialized the physical writes, but the application failed to preserve the logical intent.

This distinction is crucial:

```text
Physical write serialization
        !=
Logical write conflict detection
```

Optimistic concurrency addresses the second problem.

# 5. The Canonical Version-Column Pattern

Schema:

```sql
CREATE TABLE products (
    id           bigint PRIMARY KEY,
    name         text NOT NULL,
    price        numeric(12,2) NOT NULL,
    version      bigint NOT NULL DEFAULT 1,
    updated_at   timestamptz NOT NULL DEFAULT now()
);
```

Client reads:

```sql
SELECT id, name, price, version
FROM products
WHERE id = $1;
```

Suppose the result is:

```text
id      = 42
price   = 1250.00
version = 7
```

Client proposes a new price:

```sql
UPDATE products
SET price = $1,
    version = version + 1,
    updated_at = now()
WHERE id = $2
  AND version = $3
RETURNING id, price, version, updated_at;
```

Parameters:

```text
$1 = 1300.00
$2 = 42
$3 = 7
```

If the row is still version `7`, the update succeeds and version becomes `8`.

If another transaction already changed it to version `8`, the predicate fails and the statement affects zero rows.

That zero-row result is not “no data.” It is a **concurrency signal**.

---

# 6. Compare-and-Set as the Mental Model

Think of the SQL as:

```text
COMPARE
current version == expected version?

        |
        +-- yes --> SET new state + increment version
        |
        +-- no  --> do nothing
```

This is analogous to a compare-and-swap primitive in concurrent systems.

The important property is atomicity:

```text
CHECK + WRITE
```

must be one indivisible database operation with respect to competing writers.

Bad:

```ts
const row = await db.query(
  'SELECT version, price FROM products WHERE id = $1',
  [id],
);

if (row.version === expectedVersion) {
  await db.query(
    'UPDATE products SET price = $1 WHERE id = $2',
    [price, id],
  );
}
```

The check and update are separated. Another writer can modify the row between them.

Better:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE id = $2
  AND version = $3;
```

Now the database evaluates the predicate and mutation as one statement.

---

# 7. Why Affected-Row Count Matters

Suppose the application executes:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE id = $2
  AND version = $3;
```

There are three important outcomes:

```text
rowCount = 1
    -> expected version matched
    -> write accepted

rowCount = 0
    -> row does not exist, or
    -> version did not match

execution error
    -> SQL/database failure
```

In many APIs the query must distinguish:

```text
NOT_FOUND
```

from:

```text
CONFLICT / STALE_WRITE
```

A robust implementation can first know whether the resource exists, or design the statement to return enough information to distinguish the cases.

Do not blindly map every zero-row update to HTTP `404`.

---

# 8. Version Numbers Are Usually Better Than `updated_at`

A tempting pattern is:

```sql
UPDATE products
SET price = $1,
    updated_at = now()
WHERE id = $2
  AND updated_at = $3;
```

This can work, but timestamp equality is a weaker concurrency token design.

Potential concerns include:

- timestamp precision and representation across layers;
- serialization and formatting differences;
- application/database clock assumptions when timestamps originate outside PostgreSQL;
- accidental updates that change `updated_at` without participating in the intended semantic version;
- difficulty communicating the token as a simple monotonically advancing revision.

A dedicated integer revision makes the contract explicit:

```text
version 41
version 42
version 43
```

The number itself does not have to represent time. Its job is to represent a new logical version.

---

# 9. Stronger Concurrency Tokens

Not every system needs an integer.

Possible tokens include:

```text
BIGINT revision
UUID revision token
cryptographic hash of canonical state
ETag-style opaque token
xmin-derived mechanisms in specialized designs
```

Each has trade-offs.

An integer version is simple and efficient but must be updated consistently.

An opaque token can hide implementation details and integrate naturally with API `ETag` / `If-Match` semantics, but the application still needs a reliable database-side equality check.

A content hash can detect any change to the canonical representation but introduces more computation and a much stronger dependency on canonicalization rules.

Do not use PostgreSQL's internal tuple metadata as an application API contract merely because it is available. Internal MVCC metadata has different lifecycle and portability characteristics than an explicit application version.

---

# 10. HTTP APIs: Carry the Version Across the Boundary

Optimistic concurrency becomes especially useful when business logic spans multiple requests.

Example response:

```json
{
  "id": 42,
  "name": "Gold Ring",
  "price": "1250.00",
  "version": 7
}
```

Client later sends:

```http
PATCH /products/42
If-Match: "7"
Content-Type: application/json
```

or a body such as:

```json
{
  "price": "1300.00",
  "version": 7
}
```

Server translates the contract into:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE id = $2
  AND version = $3
RETURNING *;
```

The server should not trust the client's new version as the version to write.

Instead:

```text
client supplies expected version
        |
        v
server checks current DB version
        |
        v
server advances version itself
```

---

# 11. ETag / If-Match Semantics

HTTP already has a useful conceptual model for optimistic concurrency:

```text
GET resource
        |
        v
receive representation + validator
        |
        v
client edits
        |
        v
PUT/PATCH with If-Match validator
        |
        +--> validator matches -> update
        |
        +--> validator differs -> conflict
```

This maps cleanly onto PostgreSQL version columns.

For example:

```text
ETag: "product-42-v7"
```

and:

```text
If-Match: "product-42-v7"
```

The server can parse the validator into the expected revision used by the SQL predicate.

The important architectural boundary is:

```text
HTTP conditional request
        ↓
application concurrency token
        ↓
SQL compare-and-set predicate
        ↓
database commit
```

---

# 12. Partial Updates and Field-Level Intent

Optimistic concurrency alone does not tell you how to merge edits.

Suppose two users edit:

```text
User A changes price
User B changes description
```

The second update may fail because the whole product revision changed.

That can be correct, even though the field changes do not semantically conflict.

There are several strategies.

## Whole-record conflict

```text
Any change increments version.
Any stale writer conflicts.
```

Simple and safe.

## Field-aware merge

The application loads current state and attempts to merge non-overlapping changes.

More complex, but useful for collaborative editing.

## Field-level versions

Separate revision domains exist for different independent aggregates or sections.

This reduces false conflicts but increases schema and reasoning complexity.

## Domain-specific commands

Instead of sending a whole desired state:

```text
set price to 1300
```

use a semantic command:

```text
increase price by 50
```

or:

```text
reserve quantity 2
```

This can sometimes reduce conflict rates, but only when the business semantics make the command safe and deterministic.

---

# 13. Optimistic Concurrency Does Not Mean “Never Lock”

The word optimistic is about how conflicts are handled, not a universal prohibition on locks.

A transaction can still use:

```sql
SELECT ... FOR UPDATE;
```

when a short critical section genuinely requires pessimistic coordination.

A design may combine techniques:

```text
Long user interaction
    |
    +-- optimistic version token
            |
            v
Short server transaction
    |
    +-- atomic update
```

or:

```text
Optimistic check
        |
        +-- conflict-heavy hot path
                  |
                  v
          short pessimistic lock
```

The correct question is not:

> “Which pattern is universally better?”

It is:

> “How expensive is waiting compared with detecting and resolving a conflict?”

---

# 14. Optimistic vs Pessimistic Concurrency

| Dimension | Optimistic | Pessimistic |
|---|---|---|
| Basic strategy | Detect conflict at write | Prevent/intercept conflict earlier |
| Typical mechanism | Version predicate | Row lock |
| Waiting | Usually minimized | Can be significant |
| Conflict cost | Application resolution/retry | Queueing/blocking |
| Best when | Conflicts relatively uncommon | Conflicts frequent or critical section is short |
| User-facing edits | Excellent fit | Usually awkward for long interactions |
| Hot rows | Can produce many conflicts | Can serialize access efficiently if designed carefully |
| Long application work | Good, because no lock held | Dangerous if lock held across work |
| Complexity | Conflict handling | Lock ordering and blocking |

Neither model eliminates concurrency complexity.

They move the complexity to different places.

# 15. Production Pattern: Lost-Update Prevention

Naive implementation:

```sql
SELECT quantity
FROM inventory
WHERE id = $1;
```

Application computes:

```text
new_quantity = old_quantity - requested_quantity
```

Then:

```sql
UPDATE inventory
SET quantity = $2
WHERE id = $1;
```

The value can become stale before the write.

A versioned approach:

```sql
SELECT id, quantity, version
FROM inventory
WHERE id = $1;
```

Then:

```sql
UPDATE inventory
SET quantity = $2,
    version = version + 1
WHERE id = $1
  AND version = $3
RETURNING id, quantity, version;
```

If `0` rows are returned:

```text
someone changed inventory since you read it
```

The application can reload the latest state and decide whether to retry, reject, or reconcile.

For pure decrements, however, optimistic read-modify-write may be inferior to a database-side atomic update:

```sql
UPDATE inventory
SET quantity = quantity - $2,
    version = version + 1
WHERE id = $1
  AND quantity >= $2;
```

This illustrates a critical engineering rule:

> **Do not use an optimistic read-modify-write workflow merely because optimistic locking is available. When the business operation is naturally expressible as one atomic SQL mutation, that can be simpler and stronger.**

---

# 16. Production Pattern: Preventing Lost Edits in an ERP

Imagine an ERP product record:

```text
product_id = 7001
price      = 625000
weight     = 18.42
version    = 12
```

Two branch users open the same record.

```text
User A -> version 12
User B -> version 12
```

A changes price:

```sql
UPDATE products
SET price = 630000,
    version = version + 1
WHERE product_id = 7001
  AND version = 12;
```

Success:

```text
version = 13
```

B submits an old form:

```sql
UPDATE products
SET weight = 18.55,
    version = version + 1
WHERE product_id = 7001
  AND version = 12;
```

It updates zero rows.

The server should not silently overwrite the newer price.

Instead it can return a concurrency conflict containing:

```text
Your form was based on revision 12.
The record is now revision 13.
Reload and review the newer price before saving.
```

For sensitive financial or inventory fields, this is usually safer than accepting stale writes.

# 17. Optimistic Concurrency Inside a Transaction

It is common to think that adding a version check inside a transaction automatically solves everything.

Example:

```sql
BEGIN;

SELECT version, state
FROM orders
WHERE id = $1;

-- application logic

UPDATE orders
SET state = $2,
    version = version + 1
WHERE id = $1
  AND version = $3;

COMMIT;
```

This can correctly protect the specific row mutation.

But the transaction may also read or depend on other rows:

```text
order
customer credit
inventory
pricing
approval status
```

A single row version does not automatically protect invariants spanning those resources.

For multi-row invariants consider:

```text
atomic SQL
constraints
row locks
SERIALIZABLE
coordination rows
or combinations
```

Optimistic concurrency is a protocol for detecting stale state; it is not a substitute for choosing an adequate transaction isolation model.

---

# 18. Interaction With Isolation Levels

Optimistic concurrency and isolation levels solve different layers of the problem.

## READ COMMITTED

The version predicate is checked against the database state relevant to the executing statement. This is a common fit for short compare-and-set updates.

## REPEATABLE READ

A transaction can have a stable snapshot while its versioned write still encounters a concurrent-update conflict. A failed attempt must be treated as a failed transaction and usually retried from a fresh transaction.

## SERIALIZABLE

Serializable isolation may reject the transaction because of a broader serialization dependency even when the version predicate itself matched.

Therefore:

```text
version conflict
    !=
serialization failure
```

Both may be retryable, but they mean different things.

---

# 19. Version Conflict vs Serialization Failure vs Deadlock

A mature application should classify these separately.

### Optimistic conflict

The SQL predicate matched zero rows.

Typical meaning:

```text
expected version is stale
```

Often maps to a domain/application conflict response.

### Serialization failure

PostgreSQL rejects the transaction because its execution cannot safely complete under the requested isolation semantics.

Typical SQLSTATE:

```text
40001
```

Retrying the whole transaction is commonly appropriate when the operation is safe to replay.

### Deadlock

PostgreSQL detects circular lock waiting.

Typical SQLSTATE:

```text
40P01
```

Usually indicates a locking-design problem plus a retry requirement for the aborted attempt.

These are fundamentally different signals.

---

# 20. Retry Semantics

A naive retry is dangerous:

```ts
catch (error) {
  return updateAgain();
}
```

Suppose the server returns a stale-write conflict.

Retrying the exact same stale token will predictably fail again.

Correct optimistic recovery is often:

```text
stale write detected
        |
        v
reload current state
        |
        v
re-evaluate business intent
        |
        +--> safely merge -> retry with new version
        |
        +--> cannot merge -> return conflict
```

By contrast, serialization failure recovery is usually:

```text
serialization failure
        |
        v
abort failed attempt
        |
        v
start a completely new transaction
        |
        v
reread all required state
        |
        v
re-execute logic
```

The two retry loops should not be conflated.

---

# 21. Backoff and Retry Storms

Even correct optimistic retry can become harmful under high contention.

Suppose 100 requests all update the same row.

A conflict wave may look like:

```text
100 readers
  |
  +-- 1 succeeds
  +-- 99 conflict
          |
          +-- all retry immediately
                  |
                  +-- contention repeats
```

This can create a feedback loop:

```text
contention
   ↓
conflicts
   ↓
retries
   ↓
more writes
   ↓
more contention
```

Mitigations include:

- bounded retry counts;
- exponential backoff;
- jitter;
- prioritization;
- reducing hot-row access;
- aggregating writes;
- moving to a domain-specific command model;
- switching selected paths to pessimistic coordination.

Retry rate should be observable as a first-class metric.

---

# 22. Hot-Row Problem

Optimistic concurrency is attractive when conflicts are rare.

It can become inefficient when everyone updates one row.

Example:

```text
organization_id = 1
quota_used      = ...
version         = ...
```

Hundreds of requests repeatedly compete on the same record.

If almost every attempt loses and retries, the protocol becomes a contention amplifier.

Ask:

```text
What does this row represent?
Why is all mutable state concentrated here?
Can the state be partitioned?
Can updates be expressed as atomic deltas?
Can events be appended rather than rewriting a shared aggregate?
Would a queue serialize the work more efficiently?
Would row-level locking outperform repeated conflicts?
```

Optimistic concurrency should be measured by conflict rate, not selected by ideology.

---

# 23. Version Increment Discipline

The version column is only useful if every logical writer updates it correctly.

Dangerous:

```sql
UPDATE products
SET price = $1
WHERE id = $2;
```

Some writer bypassed the version contract.

Then another writer may think:

```text
version = 7
```

still represents the state, even though important data changed.

Every update path that participates in the protocol must have a clear rule:

```text
logical mutation
      ↓
version increment
```

This includes:

- REST handlers;
- GraphQL mutations;
- background jobs;
- admin tools;
- SQL scripts;
- database functions;
- migration/data-fix scripts;
- imports;
- integration workers.

A protocol is only as strong as its least disciplined writer.

---

# 24. Enforcing Version Discipline

Possible strategies include:

## Application convention

Every mutation repository method increments the version.

Simple, but bypassable.

## Database trigger

A trigger increments the version for relevant updates.

Useful when many writers exist, but hidden behavior can complicate debugging and bulk operations.

## Stored procedure boundary

Only approved database procedures mutate the aggregate.

Strong boundary, but more database-centric architecture.

## Direct SQL with explicit predicate

Every write statement contains:

```sql
AND version = $expected_version
```

and increments the version.

Transparent and easy to reason about.

There is no universally correct enforcement mechanism. The important question is whether unauthorized or legacy writers can bypass the protocol.

---

# 25. What Happens If Someone Updates the Row Without the Version Predicate?

Suppose current state is:

```text
version = 8
price = 100
```

A stale request expects `7`.

A separate privileged process executes:

```sql
UPDATE products
SET price = 120
WHERE id = 42;
```

but does not increment the version.

Now:

```text
price changed
version stayed 8
```

The concurrency token no longer means what the system thinks it means.

This is a semantic integrity failure, not merely a coding style issue.

---

# 26. Concurrency Token as a Domain Revision

A useful design question is:

> “What exactly does version N mean?”

Possible answers:

```text
Every row mutation
Every business-relevant mutation
Every externally visible state change
Every aggregate revision
```

The broader the version semantics, the more conflicts may be produced.

The narrower the semantics, the more easily unrelated changes can slip past a check.

Therefore define the revision contract explicitly.

Example:

> `version` increments whenever the mutable commercial state of a product changes.

Then decide whether changes such as:

```text
last_viewed_at
search_counter
internal_metric
```

belong to that revision domain.

---

# 27. Bulk Updates

Optimistic concurrency is easiest with one row per logical aggregate.

Bulk operations require a more careful contract.

Example:

```sql
UPDATE products
SET status = 'ARCHIVED',
    version = version + 1
WHERE tenant_id = $1
  AND status = 'DISCONTINUED'
  AND version = $2;
```

A single scalar expected version may not make sense across many rows.

Possible designs:

- select and record row-level revisions first;
- use a transaction and stronger locking;
- use a predicate that captures the intended state rather than a shared version;
- use a batch job with explicit ownership;
- use `SERIALIZABLE` when the invariant demands it.

Do not force single-row optimistic locking onto a multi-row state transition problem.

---

# 28. Multi-Tenant Systems

Tenant isolation must remain independent of optimistic concurrency.

Bad:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE id = $2
  AND version = $3;
```

if IDs are not globally unique and tenant context is part of the security boundary.

Safer shape:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE tenant_id = $2
  AND id = $3
  AND version = $4;
```

The concurrency predicate must not accidentally become a tenant-isolation omission.

For security-sensitive systems, tenant identity should come from the authenticated request context and not merely from a mutable client-supplied field.

---

# 29. Security Considerations

Optimistic concurrency has security implications.

A conflict response may reveal that a record exists or has changed.

Consider whether the API distinguishes:

```text
404 not found
403 forbidden
409 conflict
```

in a way that leaks resource existence to unauthorized callers.

Authorization should be enforced in the same logical update scope:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE tenant_id = $2
  AND id = $3
  AND version = $4;
```

or through a properly enforced authorization layer such as RLS where appropriate.

Do not treat the version token as an authorization credential.

It is a concurrency validator, not permission proof.

# 30. Node.js / NestJS Implementation Pattern

A repository method might expose:

```ts
async updateProduct(
  id: bigint,
  expectedVersion: bigint,
  patch: { price?: string; name?: string },
) {
  const result = await this.pool.query(
    `
      UPDATE products
      SET price = COALESCE($1, price),
          name = COALESCE($2, name),
          version = version + 1,
          updated_at = now()
      WHERE id = $3
        AND version = $4
      RETURNING id, name, price, version, updated_at
    `,
    [patch.price ?? null, patch.name ?? null, id, expectedVersion],
  );

  if (result.rowCount === 0) {
    throw new Error('OPTIMISTIC_CONCURRENCY_CONFLICT');
  }

  return result.rows[0];
}
```

The important boundaries are:

```text
controller
   ↓
application service
   ↓
repository
   ↓
atomic SQL compare-and-set
```

Do not first load a record in the repository merely to compare versions in TypeScript unless the additional read is needed for a conflict-resolution workflow.

---

# 31. ORM Pitfall: `save()` After a Stale Read

An ORM pattern can look harmless:

```ts
const product = await repo.findOneBy({ id });
product.price = newPrice;
await repo.save(product);
```

Depending on ORM behavior and mapping configuration, this may not implement optimistic concurrency at all.

An explicit concurrency mechanism should be visible in the generated SQL or ORM configuration:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE id = $2
  AND version = $3;
```

Do not infer concurrency safety from the presence of a `version` property in an entity class.

Verify the actual SQL behavior.

# 32. AI / Vibe-Coding Mistakes

AI-generated code frequently produces superficially reasonable but unsafe concurrency patterns.

## Mistake 1 — Check then update

```ts
const row = await getProduct(id);
if (row.version === version) {
  await updateProduct(id, data);
}
```

**Why it fails:** another writer can change the row between the two statements.

**Correct:** put the expected version in the `UPDATE` predicate.

---

## Mistake 2 — Ignore `rowCount`

```ts
await db.query(updateSql, params);
return 'success';
```

**Why it fails:** a stale write that updates zero rows is silently reported as successful.

**Correct:** interpret affected-row count as a protocol result.

---

## Mistake 3 — Retry the same stale version

```text
expected version 7
conflict
retry expected version 7
```

**Why it fails:** the request still carries stale state.

**Correct:** reload/reconcile and obtain a new revision, or reject the operation.

---

## Mistake 4 — Retry every database error

```text
ANY ERROR -> retry
```

**Why it fails:** unique violations, permission errors, malformed SQL, constraint errors, and application conflicts are not interchangeable.

**Correct:** classify errors before retrying.

---

## Mistake 5 — Use timestamp equality without a reason

**Why it fails:** timestamps are harder to treat as explicit revision semantics.

**Correct:** prefer a dedicated revision token unless timestamp-based semantics are intentionally designed and verified.

---

## Mistake 6 — Assume versioning protects cross-row invariants

**Why it fails:** one row's version does not protect other rows the business rule depends on.

**Correct:** select atomic SQL, constraints, locks, serializable isolation, or other coordination appropriate to the invariant.

---

## Mistake 7 — Increment version in application code

Bad:

```ts
nextVersion = currentVersion + 1;
```

**Why it fails:** concurrent writers can derive conflicting versions.

**Correct:** let PostgreSQL perform:

```sql
version = version + 1
```

inside the atomic mutation.

---

# 33. Transactions and External Side Effects

Suppose an optimistic transaction updates a payment record and then calls an external API before commit.

Potential sequence:

```text
DB update succeeds
      ↓
external API succeeds
      ↓
DB commit fails because of concurrency
```

Now the external side effect exists, but the database transaction did not commit.

Optimistic concurrency does not solve distributed atomicity.

Use patterns such as:

```text
transactional outbox
idempotency keys
post-commit dispatch
reconciliation
```

The key rule is:

> **A retryable database transaction must not blindly replay an irreversible external side effect.**

---

# 34. Event-Sourced and Append-Only Alternatives

Some domains do not need repeated mutable-row overwrites.

Instead of:

```text
UPDATE account_state
SET balance = ...
```

one might append:

```text
ledger event
payment event
adjustment event
```

and derive state.

Optimistic concurrency can still be useful:

```text
expected aggregate revision N
        |
append event only if revision N
        |
aggregate revision becomes N+1
```

This is conceptually the same compare-and-set idea applied to an append-only stream.

The trade-off is substantial: event-driven models shift complexity toward reconstruction, projections, idempotency, and event evolution.

# 36. Detecting Hot Keys

If conflicts concentrate on a small set of records, aggregate by logical key:

```text
product:42 -> 28% of conflicts
branch:7   -> 19%
quota:1    -> 34%
```

This can reveal an architectural problem hidden by average conflict rates.

A 1% global conflict rate may look fine while one critical record has a 90% conflict rate.

Always analyze the distribution, not merely the mean.

# 38. Evidence-Driven Debugging

When users report:

> “My update succeeded but my changes disappeared.”

Do not immediately blame PostgreSQL.

Collect:

```text

resource id

rowCount

```

Then reconstruct the timeline:

```text

T1 wrote without version predicate
T1 overwrote T2
```

or:

```text

T2 wrote v8
T1 conditional update rowCount=0
API incorrectly returned 200
```

Both are concurrency bugs, but they are different bugs.

# 39. Query-Plan Considerations

A version predicate should be supported by an appropriate access path.

For a primary-key update:

```sql
WHERE id = $1
  AND version = $2
```

an index on the primary key is typically sufficient to locate the row, then PostgreSQL checks the version.

Do not automatically create an index on `(id, version)` without evidence.

For tenant-scoped keys such as:

```sql
WHERE tenant_id = $1
  AND id = $2
  AND version = $3
```

the useful index depends on actual key design and workload.

Measure with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE ...;
```

Remember that an `UPDATE` also has write-side costs:

```text
heap tuple version
index maintenance
WAL
visibility effects
vacuum work later
```

Optimistic concurrency is not free simply because it avoids waiting.

# 40. Performance Trade-Offs

Optimistic concurrency tends to trade waiting for failed work.

A rough conceptual model is:

```text
Expected cost
≈ base successful work
 + conflict probability × discarded work
 + retry cost
 + conflict-resolution cost
```

Pessimistic locking instead trends toward:

```text
Expected cost
≈ base work
 + queueing / wait time
 + lock-management cost
 + deadlock risk
```

Neither formula is exact, but the comparison is useful.

At low conflict rates:

```text
optimistic -> often attractive
```

At very high conflict rates:

```text
repeated retries -> potentially wasteful
```

Use measurements rather than ideology.

---

# 41. Decision Framework

Ask these questions.

### 1. How long does the user or service hold the logical state before writing?

Long human interaction favors optimistic concurrency.

### 2. How frequently do writers collide?

High collision rates may favor different coordination.

### 3. Can the operation be expressed as one atomic SQL mutation?

If yes, that may beat both explicit optimistic and pessimistic workflows.

### 4. Does the invariant span multiple rows?

If yes, a single version column may be insufficient.

### 5. Is conflict resolution meaningful?

If two edits can be merged, optimistic concurrency is often attractive.

### 6. Is the mutation irreversible?

Retry and side-effect handling become more difficult.

### 7. Are there many uncontrolled writers?

Version discipline becomes harder to enforce.

# 42. Solution Pattern

## Naive Approach

```text
read row
modify in application
save row
```

## Why It Fails

The save is not tied to the state that was originally read.

## Improved Approach

```text
read row + version
        ↓
process
        ↓
UPDATE ... WHERE id = ? AND version = ?
        ↓
inspect rowCount
```

## Why It Works

The database atomically checks the expected revision while applying the mutation.

## Production Considerations

Add:

- bounded retries where appropriate;
- conflict metrics;
- explicit HTTP/API semantics;
- authorization checks;
- idempotency for side effects;
- tests with real concurrency;
- clear version semantics.

## Alternative

Use:

```text
SELECT ... FOR UPDATE
```

or an atomic domain-specific SQL command.

## Trade-Off

Optimistic concurrency minimizes waiting but can waste work under heavy contention. Pessimistic locking minimizes conflicting simultaneous work but introduces blocking and lock-management complexity.

# 43. Production Failure Scenario

Imagine an order approval screen.

User A opens order `9001`:

```text
version = 14
status = PENDING
```

User B also opens it at version `14`.

User A approves:

```sql
UPDATE orders
SET status = 'APPROVED',
    version = version + 1
WHERE id = 9001
  AND version = 14;
```

Success:

```text
version = 15
```

User B tries to cancel from the stale screen:

```sql
UPDATE orders
SET status = 'CANCELLED',
    version = version + 1
WHERE id = 9001
  AND version = 14;
```

Affected rows:

```text
0
```

A weak application might respond:

```text
200 OK
```

and display the stale local state.

A robust application responds with a conflict and forces reconciliation.

This is the key user-visible benefit of optimistic concurrency: **stale intent becomes explicit instead of silently overwriting newer state.**

# 44. Expert Boundary: Intent vs State

The deepest optimistic-concurrency question is:

> “What exactly are we protecting: the entire state representation, or the business intent expressed by the command?”

A whole-row version protects representation freshness.

A domain command can protect intent more precisely.

For example:

```text
set balance to 900
```

is sensitive to stale state.

But:

```text
withdraw 100
```

may be represented as an atomic conditional mutation:

```sql
UPDATE accounts
SET balance = balance - $1,
    version = version + 1
WHERE id = $2
  AND balance >= $1;
```

Now the operation is expressed relative to current state, avoiding a client-held stale absolute value.

This is often the next step beyond basic optimistic locking:

```text
stale state prevention
        ↓
intent-preserving commands
        ↓
atomic database operations
```

# 46. Interview Questions

## Junior

### Q1. What is optimistic concurrency?

**Weak Answer**  
“It uses a version field.”

**Acceptable Answer**  
“It detects conflicts at update time instead of locking the row early.”

**Strong Answer**  
“It reads a concurrency token and performs a conditional update using that expected token, treating a zero-row update as a stale-write conflict.”

**Expert Answer**  
“It is a compare-and-set protocol layered on database atomicity and MVCC. The database enforces that the mutation applies only if the row still matches the expected revision; conflict classification, retry semantics, and writer discipline are part of the protocol.”

# 50. Production Readiness Checklist

Before declaring an optimistic-concurrency design production-ready, verify:

- [ ] The concurrency invariant is explicitly documented.
- [ ] A dedicated revision/token exists where appropriate.
- [ ] The expected revision is checked in the write statement.
- [ ] The database advances the revision atomically.
- [ ] `rowCount` or `RETURNING` is inspected.
- [ ] Missing resource and stale resource are distinguished where required.
- [ ] All important writers participate in the protocol.
- [ ] ORM-generated SQL has been verified rather than assumed.
- [ ] Multi-row invariants use stronger or broader coordination where needed.
- [ ] Retry logic distinguishes stale conflicts from database retryable errors.
- [ ] Retries are bounded.
- [ ] Backoff/jitter is used for high-contention paths where appropriate.
- [ ] External side effects are idempotent or coordinated through an outbox.
- [ ] Conflict metrics exist.
- [ ] Hot-key distribution is observable.
- [ ] Concurrency tests reproduce conflicts deterministically.
- [ ] Authorization is enforced independently of the version token.
- [ ] Tenant scope is present wherever it is part of the security boundary.
- [ ] Version semantics are documented.
- [ ] Operators know when to switch from optimistic to another coordination strategy.

# 51. Final Mental Model

Keep this model:

```text
                OPTIMISTIC CONCURRENCY
                         |
          +--------------+--------------+
          |                             |
       READ                         WRITE
          |                             |
          v                             v
  capture version N          UPDATE ... WHERE version = N
                                      |
                              +-------+-------+
                              |               |
                           match           mismatch
                              |               |
                              v               v
                           commit          conflict
                              |               |
                              v               v
                         version N+1     reload/reconcile
```

And remember the deeper distinction:

```text
MVCC
= multiple versions + visibility

Locks
= coordination / waiting

Optimistic concurrency
= stale-state detection

SERIALIZABLE
= prevention of non-serializable outcomes

Atomic SQL
= express business mutation directly in the database
```

These mechanisms overlap, but they are not interchangeable.

The production engineer's job is to combine the smallest set of mechanisms that correctly protects the actual business invariant.

---

# 52. Final Takeaway

The durable lesson is not:

> “Add a version column.”

The durable lesson is:

> **Make the database reject stale intent atomically, make the application recognize and resolve that rejection correctly, and choose a stronger coordination mechanism whenever the protected invariant extends beyond the state represented by one revision token.**

That is optimistic concurrency engineering.
