# 2. The Central Mental Model

The key difference is:

```text
Ordinary SELECT

read row
   |
   +--> obtain a consistent MVCC view
   |
   +--> other transactions may still modify the row
```

versus:

```text
SELECT ... FOR UPDATE

find row
   |
   +--> obtain the row version visible to the statement
   |
   +--> acquire UPDATE-strength row lock
   |
   +--> keep lock until transaction ends
   |
   +--> other conflicting lockers/writers must wait
```

The most important sentence in this chapter is:

> **`SELECT ... FOR UPDATE` is a coordination primitive: it turns a read of selected rows into ownership of those rows for subsequent transactional work.**

It is not merely a faster `SELECT`, and it is not a substitute for every database invariant.

---

# 3. What `SELECT ... FOR UPDATE` Means

## 3.1 Simple definition

`SELECT ... FOR UPDATE` reads rows and locks those rows so competing transactions cannot update, delete, or acquire conflicting row locks on them until the locking transaction ends.

## 3.2 Engineering definition

It is a locking read used inside a transaction when application logic needs to inspect a row and then safely make a decision or perform related work against that same row without another transaction concurrently changing the row during the protected interval.

## 3.3 Expert definition

A `SELECT ... FOR UPDATE` statement performs an MVCC-aware row selection and requests an `FOR UPDATE` row-level lock on each selected target row. The lock participates in PostgreSQL's row-lock conflict matrix and is retained until transaction end unless transaction control rolls it back to an earlier savepoint state. The statement also acquires a `ROW SHARE` table-level lock on explicitly row-locked relations. In `READ COMMITTED`, a row changed by a concurrent transaction can cause the locking read to wait and then return the updated version if the row still satisfies the query condition; in `REPEATABLE READ` or `SERIALIZABLE`, a row changed since the transaction snapshot can instead cause a serialization failure. citeturn253508search2turn237530search20

# 4. Why Ordinary SELECT Is Not Enough

Consider inventory:

```text
inventory
---------
id | available
7  | 1
```

Application code:

```sql
BEGIN;

SELECT available
FROM inventory
WHERE id = 7;

-- application checks available > 0

UPDATE inventory
SET available = available - 1
WHERE id = 7;

COMMIT;
```

At first glance, this may look transactional.

But the `SELECT` did not coordinate ownership of the row.

Two transactions can both perform the read before either performs the update.

Conceptually:

```text
T1                          T2
---------------------------------------
SELECT available = 1
                            SELECT available = 1
check: 1 > 0
                            check: 1 > 0
UPDATE - 1
                            UPDATE - 1
COMMIT
                            COMMIT
```

Whether the final arithmetic itself is safe depends on the exact SQL, but the application decision based on the earlier read is not automatically protected.

A locking read changes the coordination model:

```sql
BEGIN;

SELECT available
FROM inventory
WHERE id = 7
FOR UPDATE;

-- inspect + decide

UPDATE inventory
SET available = available - 1
WHERE id = 7;

COMMIT;
```

Now another transaction trying to acquire a conflicting lock or update that row must wait for T1's transaction to finish. PostgreSQL documents that `FOR UPDATE` conflicts with `UPDATE`, `DELETE`, and all four row-lock modes. citeturn253508search2

---

# 5. `FOR UPDATE` Is a Row-Level Lock, Not a Table Lock

This distinction matters.

```sql
SELECT *
FROM orders
WHERE id = 100
FOR UPDATE;
```

The selected row receives the `FOR UPDATE` row lock.

The whole table is **not** exclusively locked.

Other transactions can still:

```text
read other rows
update other rows
insert other rows
perform unrelated work
```

subject to their own constraints and lock conflicts.

However, the statement does also acquire a table-level `ROW SHARE` lock on the relation named in the locking clause. That table lock is much weaker than `ACCESS EXCLUSIVE`; its presence should not be mistaken for relation-wide serialization. citeturn253508search2

Think in layers:

```text
Statement
   |
   +-- table-level ROW SHARE lock
   |
   +-- row-level FOR UPDATE locks on selected rows
```

The row-level locks provide the primary coordination semantics of `FOR UPDATE`.

---

# 6. Which Operations Conflict With `FOR UPDATE`?

PostgreSQL's row-lock matrix makes `FOR UPDATE` the strongest of the four row-level locking clauses.

Conceptually:

```text
                 Existing
Requested        KEY SHARE  SHARE  NO KEY UPDATE  UPDATE
----------------------------------------------------------
FOR KEY SHARE       -         -          -            X
FOR SHARE           -         -          X            X
FOR NO KEY UPDATE   -         X          X            X
FOR UPDATE          X         X          X            X
```

Therefore `FOR UPDATE` blocks another transaction from acquiring any conflicting row lock on that row, including another `FOR UPDATE`, and it blocks `UPDATE` and `DELETE`. PostgreSQL documents this compatibility matrix explicitly. citeturn253508search2

A subtle but important point:

> **Not every operation that touches a row is blocked by every row lock.**

For example, plain `SELECT` generally does not wait for a row-level lock because ordinary MVCC reads do not conflict with row-level locks. Row locks primarily block writers and other locking reads on the same rows. citeturn253508search2

# 7. `FOR UPDATE` and MVCC Work Together

It is tempting to model locking and MVCC as competing mechanisms:

```text
MVCC OR Locks
```

A better model is:

```text
MVCC
  = visibility / version selection

Locks
  = coordination between concurrent operations
```

A `SELECT ... FOR UPDATE` still performs a visibility-aware read.

Then it adds a coordination requirement:

```text
Which row version can I see?
        |
        v
Which physical/logical row do I need to lock?
        |
        v
Can I acquire the required row lock now?
        |
        +--> yes -> continue
        |
        +--> no  -> wait / NOWAIT error / SKIP LOCKED
```

This is why understanding the previous chapters on MVCC and row locks is essential before using `FOR UPDATE` safely.

# 8. Basic Transaction Pattern

The canonical pattern is:

```sql
BEGIN;

SELECT *
FROM orders
WHERE id = 100
FOR UPDATE;

-- validate state
-- perform dependent changes
-- update related data

UPDATE orders
SET status = 'PAID'
WHERE id = 100;

COMMIT;
```

The transaction protects the interval between:

```text
read current authoritative state
        |
        v
make decision
        |
        v
apply dependent writes
```

Without the lock, another transaction could change the row between the read and write.

With the lock, the database becomes the coordinator for that interval.

---

# 9. Example — Order State Transition

Assume:

```text
orders
------
id | status
50 | PENDING
```

You want to pay the order only if it is still pending.

A robust locking workflow is:

```sql
BEGIN;

SELECT id, status
FROM orders
WHERE id = 50
FOR UPDATE;

-- application logic / validation

UPDATE orders
SET status = 'PAID'
WHERE id = 50
  AND status = 'PENDING';

COMMIT;
```

Why keep the status predicate in the final update?

Because redundant defensive conditions can make the business invariant visible in more than one place, and because it makes the intended transition explicit.

In many designs, however, the stronger approach is a single atomic conditional update:

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 50
  AND status = 'PENDING'
RETURNING *;
```

This leads to a critical design rule:

> **Use `FOR UPDATE` when you genuinely need a protected read before subsequent work. Use one atomic statement when the entire decision can be represented in one statement.**

# 10. Naive Approach → Improved Approach

## Naive Approach

```sql
SELECT status
FROM orders
WHERE id = $1;

-- application checks status

UPDATE orders
SET status = 'PAID'
WHERE id = $1;
```

### Why It Fails

The read does not establish ownership of the row.

Another transaction can change the state between the two commands.

### Improved Approach

```sql
BEGIN;

SELECT status
FROM orders
WHERE id = $1
FOR UPDATE;

-- check allowed transition

UPDATE orders
SET status = 'PAID'
WHERE id = $1;

COMMIT;
```

### Why It Works

The row remains locked for the rest of the transaction, so competing writers or lockers cannot concurrently modify the same row without waiting.

### Production Considerations

The transaction must be short. Do not hold the lock while waiting for external services, user input, long CPU work, or unrelated queries.

### Alternative

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = $1
  AND status = 'PENDING'
RETURNING *;
```

### Trade-Off

The atomic statement is usually simpler and faster when the invariant fits entirely inside one SQL statement. `FOR UPDATE` becomes useful when several reads and writes must share the same protected state transition.

# 11. Blocking Behavior

Suppose T1 executes:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE;
```

T2 tries:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE;
```

If T1 still holds the row lock, T2 waits.

The state is conceptually:

```text
T1
|
+-- owns row lock on inventory(7)
|
+-- transaction still open

T2
|
+-- requests row lock on inventory(7)
|
+-- waits
```

When T1 commits:

```text
T1 COMMIT
    |
    v
row lock released
    |
    v
T2 wakes
    |
    v
T2 acquires lock
    |
    v
T2 continues
```

PostgreSQL's documentation describes this waiting behavior explicitly for row-level locks. citeturn253508search2

---

# 12. What If the First Transaction Rolls Back?

Suppose T1 locks the row and then rolls back:

```sql
ROLLBACK;
```

The lock disappears with the transaction.

T2 can then acquire the row lock and continue.

This is why a blocked session can appear to “suddenly” continue without the application doing anything visible in T2: the transaction holding the conflicting lock finished, allowing the wait queue to progress.

The critical operational consequence is:

> **Transaction lifetime is lock lifetime.**

A forgotten transaction is therefore not only a data-integrity concern; it can become a concurrency incident.

---

# 13. `SELECT ... FOR UPDATE` Under READ COMMITTED

PostgreSQL's `READ COMMITTED` behavior has an important special case.

A locking read initially searches using the statement snapshot. If it reaches a row that has been concurrently updated, it can wait for the other transaction. Once the other transaction commits, PostgreSQL can lock and return the updated row if it still satisfies the query's condition; if the row was deleted, no row is returned. citeturn253508search2

Conceptually:

```text
T1: SELECT ... FOR UPDATE
        |
        v
find row R
        |
        v
R is concurrently locked
        |
        v
wait
        |
        v
other transaction commits
        |
        v
re-check visibility / qualification
        |
        +--> still matches -> lock updated version + return
        |
        +--> no longer matches / deleted -> no row
```

This behavior is one reason `READ COMMITTED` locking queries can produce results that are newer than the original statement snapshot in this specific conflict-handling path.

That is different from an ordinary non-locking `SELECT`.

---

# 14. `FOR UPDATE` Under REPEATABLE READ and SERIALIZABLE

At stronger isolation levels, a transaction cannot simply move its snapshot forward to accommodate a conflicting row change.

PostgreSQL documents that within `REPEATABLE READ` or `SERIALIZABLE`, an error is thrown if the row to be locked has changed since the transaction started. citeturn253508search2

Conceptually:

```text
Transaction snapshot S
        |
        v
SELECT ... FOR UPDATE
        |
        v
row was changed after S
        |
        v
serialization failure
```

This usually means the application must discard the failed transaction attempt and retry the logical operation from a fresh transaction.

Do not “retry just the `SELECT`” while pretending the rest of the transaction remains valid. The failed attempt no longer represents a transaction that can safely continue.

---

# 15. Lock Lifetime

`FOR UPDATE` locks last until transaction end under normal transaction control.

Therefore:

```sql
BEGIN;

SELECT ... FOR UPDATE;

-- row stays protected here

COMMIT;
```

The lock is released at commit.

Likewise:

```sql
ROLLBACK;
```

releases the lock.

This has a major architectural implication:

```text
Long transaction
      |
      +--> long-lived row locks
      |
      +--> more contention
      |
      +--> more waiting
      |
      +--> higher deadlock opportunity
      |
      +--> connection-pool pressure
```

A lock that is technically correct can still be operationally harmful if the transaction scope is too broad.

---

# 16. `FOR UPDATE OF table_name` in Joins

Consider:

```sql
SELECT o.id, o.status, c.id AS customer_id
FROM orders AS o
JOIN customers AS c
  ON c.id = o.customer_id
WHERE o.id = $1
FOR UPDATE;
```

Without an `OF` list, the locking clause can apply to rows selected from all eligible tables in the query according to PostgreSQL's locking-clause semantics.

When you only need to lock the order row:

```sql
SELECT o.id, o.status, c.id AS customer_id
FROM orders AS o
JOIN customers AS c
  ON c.id = o.customer_id
WHERE o.id = $1
FOR UPDATE OF o;
```

This is often preferable because it narrows the coordination scope.

The mental model should be:

```text
Query reads:
orders + customers

Business invariant requires lock on:
orders only

Therefore:
FOR UPDATE OF orders
```

Use the smallest correct lock set.

---

# 17. Locking Only the Necessary Relation

Over-locking can create unrelated contention.

Suppose you have:

```text
orders
customers
payments
```

and your logic only needs exclusive ownership of the order row.

This:

```sql
SELECT ...
FROM orders o
JOIN customers c ON ...
JOIN payments p ON ...
WHERE o.id = $1
FOR UPDATE;
```

may coordinate more rows than your invariant requires.

A narrower design can be:

```sql
SELECT ...
FROM orders o
JOIN customers c ON ...
JOIN payments p ON ...
WHERE o.id = $1
FOR UPDATE OF o;
```

Then lock customer or payment rows separately only when they are actually part of the invariant.

The goal is not “minimum number of locks at all costs.”

The goal is:

> **minimum conflict set that fully protects the invariant.**

# 18. `ORDER BY` and Locking Reads

Ordering matters in concurrent systems.

For example:

```sql
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY id
FOR UPDATE;
```

If competing workers use a consistent order, they are more likely to acquire overlapping locks in the same sequence, reducing deadlock risk.

PostgreSQL's current `UPDATE` documentation explicitly notes that ordering can be used to prioritize rows and can help prevent deadlocks when other update operations use the same ordering. citeturn253508search0

However, there is an important nuance with `ORDER BY` and blocking locking reads: a row can be ordered according to values visible when sorting occurs, then waiting can allow another transaction to modify an ordering column before the row lock is acquired. At lower isolation this can produce an output order that does not reflect the final values of the ordering column. PostgreSQL documents this behavior and recommends restructuring the query only when strict final ordering is required. citeturn253508search6

Do not treat `ORDER BY` as merely a presentation concern in lock-heavy workflows. It can affect concurrency behavior.

---

# 19. `LIMIT` + `FOR UPDATE`

A common queue pattern is:

```sql
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY id
LIMIT 10
FOR UPDATE;
```

The locking clause works as part of row selection, so blocked rows can affect how many rows are ultimately returned.

For queue consumption, a common variant is:

```sql
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED` can allow workers to bypass rows currently locked by another transaction. PostgreSQL documents that this produces an inconsistent view and is intended for queue-like workloads rather than general-purpose reads. citeturn604714search12

This is powerful but should be treated as a workload-specific coordination pattern, not a universal optimization.

---

# 20. `NOWAIT`

A blocking lock request can be changed to fail immediately:

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR UPDATE NOWAIT;
```

If another transaction already holds a conflicting lock, the statement reports an error instead of waiting. PostgreSQL documents `NOWAIT` as an option for locking clauses. citeturn604714search12

Use this when waiting itself is unacceptable, for example:

```text
interactive command
short SLA
best-effort reservation
fail-fast administrative action
```

Do not use `NOWAIT` merely because lock waiting feels uncomfortable. Converting expected contention into errors may create a worse user experience or a noisy retry storm.

---

# 21. `SKIP LOCKED`

The alternative is:

```sql
SELECT *
FROM work_items
WHERE status = 'READY'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

The worker says:

> “Give me rows I can lock now; I do not need the currently locked rows.”

This is ideal for many queue patterns:

```text
Worker A -> row 1
Worker B -> row 2
Worker C -> row 3
```

rather than:

```text
Worker A -> row 1
Worker B -> waits on row 1
Worker C -> waits on row 1
```

But `SKIP LOCKED` changes the semantics:

```text
not all matching rows
        |
        v
only currently lockable rows
```

That is why PostgreSQL explicitly warns that skipped rows yield an inconsistent view and that this behavior is not appropriate for general-purpose querying. citeturn604714search12

---

# 22. `FOR UPDATE` in a Queue

A robust queue claim often looks like:

```sql
BEGIN;

WITH next_jobs AS (
  SELECT id
  FROM jobs
  WHERE status = 'READY'
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 10
)
UPDATE jobs
SET status = 'RUNNING',
    claimed_at = clock_timestamp()
WHERE id IN (SELECT id FROM next_jobs)
RETURNING *;

COMMIT;
```

The important design choices are:

```text
ORDER BY
    -> deterministic work preference

FOR UPDATE
    -> ownership of selected rows

SKIP LOCKED
    -> do not wait behind other workers

LIMIT
    -> bounded transaction work

UPDATE ... RETURNING
    -> transition + retrieval
```

For a serious job queue, also reason about retry state, visibility timeouts, crashes, poison jobs, idempotency, and worker leases. `FOR UPDATE` solves only the row-claim synchronization portion.

# 23. `FOR UPDATE` vs Atomic UPDATE

This is one of the most important design comparisons.

## Locking Read

```sql
BEGIN;

SELECT quantity
FROM inventory
WHERE sku = $1
FOR UPDATE;

-- complex application decision

UPDATE inventory
SET quantity = quantity - $2
WHERE sku = $1;

COMMIT;
```

## Atomic SQL

```sql
UPDATE inventory
SET quantity = quantity - $2
WHERE sku = $1
  AND quantity >= $2
RETURNING *;
```

When the whole invariant can be represented as an atomic predicate, the second pattern is frequently preferable:

```text
less network round trips
less lock-holding time
a smaller application critical section
simpler retry behavior
```

`FOR UPDATE` is stronger as a coordination primitive but more expensive in transaction complexity.

Use it when the business logic truly requires a read-modify-write workflow that cannot be expressed cleanly in one atomic statement.

# 24. Example — Jewellery ERP Stock Reservation

Imagine:

```text
stock_items
-----------
id | branch_id | sku | available_qty
42 | 7         | G-100 | 3
```

A sale attempts to reserve two units.

A locking workflow:

```sql
BEGIN;

SELECT id, available_qty
FROM stock_items
WHERE id = $1
FOR UPDATE;

-- business checks
-- branch authorization
-- reservation rules

UPDATE stock_items
SET available_qty = available_qty - 2
WHERE id = $1;

INSERT INTO stock_reservations (...)
VALUES (...);

COMMIT;
```

The lock prevents two competing transactions from simultaneously taking ownership of the same stock row.

But this is not automatically sufficient if the real invariant spans multiple rows, for example:

```text
sum(stock across multiple bins)
<= physical stock
```

In that case, row-locking one stock row may protect the wrong object.

The correct lock set may instead include all rows participating in the invariant, or the design may need an aggregate/coordination row, exclusion constraint, serializable isolation, or another architecture.

This is why:

> **Lock the invariant, not the code path.**

---

# 25. Example — Payment Claim

Suppose a payment must only be processed once.

```sql
BEGIN;

SELECT id, status
FROM payments
WHERE id = $1
FOR UPDATE;

-- if status = PENDING, process

UPDATE payments
SET status = 'PROCESSING'
WHERE id = $1;

COMMIT;
```

This protects concurrent database transactions from both claiming the same payment row.

But it does **not** guarantee exactly-once behavior with an external payment gateway.

The architecture still needs:

```text
DB transaction
    |
    +-- durable state transition
    |
    +-- outbox / idempotency key
    |
    v
external provider
```

Holding a database lock while calling the payment provider is usually a poor design because network latency becomes lock duration.

# 26. Never Hold the Lock Across External I/O

A dangerous pattern is:

```text
BEGIN
SELECT ... FOR UPDATE
call payment API
call shipping API
call email API
COMMIT
```

Potential result:

```text
external API latency
       |
       v
long transaction
       |
       v
long row lock
       |
       v
blocked requests
       |
       v
pool saturation
```

A better architecture is:

```text
BEGIN
lock + validate + transition state
write outbox event
COMMIT

asynchronous worker
        |
        +--> external API
        +--> idempotent retry
        +--> state update
```

This decouples row-lock duration from unpredictable network latency.

# 27. Connection Pool Hazard in Node.js / NestJS

The transaction belongs to the PostgreSQL connection/session.

Therefore this is dangerous conceptually:

```ts
await dataSource.query('BEGIN');
await repository.query('SELECT ... FOR UPDATE');
await repository.query('UPDATE ...');
await dataSource.query('COMMIT');
```

when those calls are not guaranteed to use the same dedicated connection.

The correct transaction architecture is:

```text
acquire one connection / query runner
        |
        +-- BEGIN
        +-- SELECT ... FOR UPDATE
        +-- dependent work
        +-- COMMIT / ROLLBACK
        |
release same connection
```

With `node-postgres`:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  const result = await client.query(
    `SELECT id, status
     FROM orders
     WHERE id = $1
     FOR UPDATE`,
    [orderId],
  );

  // dependent work must use this same client

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

The critical rule is:

> **A transaction-scoped lock is useful only when every operation that relies on that lock executes in the same transaction on the same PostgreSQL session.**

# 28. ORM Failure Pattern

AI-generated or ORM-generated code often looks like:

```ts
const order = await repo.findOne({ where: { id } });

// application checks order.status

await repo.update(id, { status: 'PAID' });
```

A developer may say:

> “Both calls happen inside my service method, so it is transactional.”

They do not automatically become one transactional operation merely because they are in one function.

The engineering questions are:

```text
Same connection?
Same transaction?
Correct isolation level?
Correct lock clause?
Commit guaranteed?
Rollback guaranteed?
External work outside transaction?
```

A robust code review should verify these explicitly.

# 29. Common Mistake: Locking Without a Transaction

Consider:

```sql
SELECT *
FROM inventory
WHERE id = 7
FOR UPDATE;
```

If executed outside an explicit multi-statement transaction, the lock is not useful as a durable coordination boundary for later application work, because the surrounding transaction scope is what determines how long the lock remains held.

The effective pattern is:

```sql
BEGIN;
SELECT ... FOR UPDATE;
-- dependent work
COMMIT;
```

The important unit is not “a locking SELECT.”

It is:

```text
transaction + lock + protected decision + commit
```

---

# 30. Common Mistake: Locking Everything

A common AI/vibe-coding response to any concurrency problem is:

```sql
SELECT *
FROM table
FOR UPDATE;
```

This is usually cargo-cult locking.

Why it looks attractive:

```text
more locking
   -> feels safer
```

Why it can be wrong:

```text
more rows locked
      |
      v
more contention
      |
      v
longer queues
      |
      v
lower throughput
      |
      v
more deadlocks
```

The correct question is:

> Which rows actually participate in the invariant?

Then lock those rows, and only those rows, unless a broader lock is deliberately required.

---

# 31. Common Mistake: Locking Reads Instead of Constraints

Suppose the rule is:

```text
email must be unique
```

Do not implement that primarily as:

```sql
SELECT ... FOR UPDATE;
```

A unique constraint is a declarative database invariant:

```sql
CREATE UNIQUE INDEX users_email_uq
ON users(email);
```

Likewise, if the rule is:

```text
quantity >= 0
```

use a `CHECK` constraint when possible:

```sql
CHECK (quantity >= 0)
```

`FOR UPDATE` is for coordination. Constraints are often better for invariants that can be declared directly.

---

# 32. Common Mistake: Checking Then Acting Without Rechecking Business State

Even with `FOR UPDATE`, business state can be misunderstood if the application has fetched stale assumptions from elsewhere.

For example:

```text
read order
lock order
use customer object loaded 5 minutes ago
make decision
```

The lock only protects the rows actually locked.

A transaction must reason about the authoritative state required for the invariant.

The design question is always:

```text
What facts must be mutually consistent?
```

Then lock/read the relevant facts within the transaction.

# 33. Row Locking and Foreign Keys

`FOR UPDATE` interacts with the broader row-lock hierarchy.

PostgreSQL's weaker `FOR KEY SHARE`, `FOR SHARE`, and `FOR NO KEY UPDATE` modes exist partly to allow more precise concurrency around key relationships and foreign keys. For example, `FOR NO KEY UPDATE` is weaker than `FOR UPDATE` and does not block `SELECT FOR KEY SHARE` on the same row. citeturn604714search0turn253508search2

Therefore a strong lock should not be selected merely because it is familiar.

When the actual invariant is:

```text
non-key field changes
```

`FOR NO KEY UPDATE` may be sufficient.

When the invariant requires stronger protection:

```text
row must not be deleted
key must not change
row must not be concurrently modified
```

the appropriate row-lock strength depends on the precise operation.

This chapter focuses on `FOR UPDATE`; the weaker modes are the subject of deliberate lock-strength selection rather than aliases.

# 34. `FOR UPDATE` and Query Planning

A locking clause is a semantic requirement, not merely an optimizer hint.

The planner still chooses an execution plan based on the query's predicates, indexes, cardinality, join strategy, and costs.

Useful diagnostic command:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM inventory
WHERE branch_id = 7
  AND status = 'AVAILABLE'
FOR UPDATE;
```

Important questions:

```text
How many rows were estimated?
How many were actually visited?
How many rows are ultimately locked?
Was the filter selective?
Was an index used?
How much heap access occurred?
How many buffers were touched?
Did the query scan far more rows than expected?
```

A locking query can be correct but still expensive if it selects too broad a set.

Correctness comes first, but lock footprint is part of performance engineering.

# 35. Row Locking Can Cause Disk I/O

PostgreSQL documents that locking rows can cause a disk write because row-locking information is associated with the tuple state. Consequently, `SELECT FOR UPDATE` is not always a “read-only” operation from a storage/I/O perspective. citeturn253508search2

That matters when benchmarking.

Do not assume:

```text
SELECT -> read-only
```

for a locking read.

A more accurate mental model is:

```text
SELECT
+
row-lock state change
+
transaction coordination
```

Therefore compare:

```text
ordinary SELECT latency
vs
SELECT FOR UPDATE latency
```

under realistic concurrency and storage conditions.

# 36. Lock Footprint and Result Cardinality

One of the easiest ways to create a concurrency problem is to accidentally return and lock more rows than intended.

Compare:

```sql
SELECT *
FROM inventory
WHERE branch_id = $1
FOR UPDATE;
```

with:

```sql
SELECT *
FROM inventory
WHERE branch_id = $1
  AND sku = $2
FOR UPDATE;
```

The first statement may lock a large set.

The second expresses a much narrower ownership request.

Measure the cardinality:

```sql
SELECT count(*)
FROM inventory
WHERE branch_id = $1
  AND sku = $2;
```

Then inspect the actual execution plan.

A production code review should ask:

> How many rows can this locking statement lock at peak, not just in today's test database?

# 37. Long-Lived Locks and Pool Exhaustion

Suppose a service has 50 database connections.

A request executes:

```text
BEGIN
SELECT ... FOR UPDATE
wait 5 seconds for external service
COMMIT
```

Under load, many requests can occupy connections while waiting.

The database may still be healthy in terms of CPU:

```text
CPU = 30%
```

while the application is failing because:

```text
pool utilization = 100%
```

This is a classic queueing failure.

Lock duration therefore belongs in application performance analysis.

Measure:

```text
transaction duration
lock wait duration
query duration
pool acquisition duration
external I/O duration
```

Do not optimize only query execution time.

# 40. Deadlocks with `FOR UPDATE`

Imagine:

```text
T1: FOR UPDATE row A
T1: FOR UPDATE row B

T2: FOR UPDATE row B
T2: FOR UPDATE row A
```

Now:

```text
T1 waits for B
T2 waits for A
```

A cycle exists.

PostgreSQL can detect the deadlock and abort one participant.

The prevention pattern from chapter 03.15 applies directly:

```text
Choose canonical order
        |
        v
Every transaction locks in that order
```

Example:

```sql
SELECT id
FROM stock_items
WHERE id IN ($1, $2)
ORDER BY id
FOR UPDATE;
```

But do not assume the presence of `ORDER BY` automatically solves every deadlock. Triggers, foreign-key interactions, other SQL statements, advisory locks, and application-level resource ordering can introduce hidden dependencies.

Lock ordering must be a system-level rule.

---

# 41. `FOR UPDATE` Does Not Prevent Every Race

Suppose the invariant is:

```text
no more than one active booking per time interval
```

A transaction locks an existing row:

```sql
SELECT *
FROM bookings
WHERE id = $1
FOR UPDATE;
```

That does not automatically protect the **absence** of another conflicting booking.

The invariant concerns a set or range:

```text
existing row(s) + possible new rows
```

Potential solutions may include:

```text
exclusion constraint
SERIALIZABLE isolation
coordination row
range locking strategy
application-specific allocation model
```

The lesson is:

> **A row lock protects rows you locked. It does not automatically protect every future row that could make the business rule false.**

This is exactly where the concepts from predicate/serializable conflicts become important.

# 42. Savepoints and Locking

Locks normally survive until transaction end, but transaction rollback semantics around savepoints matter.

For advanced code, avoid designing critical locking behavior around obscure savepoint side effects. Keep the locking sequence simple:

```text
BEGIN
  |
  +-- SELECT ... FOR UPDATE
  +-- validate
  +-- write
COMMIT
```

When using savepoints or PL/pgSQL exception blocks, explicitly test the lock state you rely on. PostgreSQL's locking documentation discusses lock behavior around savepoint rollback and transaction-level lock lifetime. citeturn253508search2

The general engineering principle remains:

> **Do not make a concurrency design depend on subtle rollback-to-savepoint semantics unless the behavior has been demonstrated in the target PostgreSQL version.**

# 43. Security Review

`FOR UPDATE` is not an authorization mechanism.

It solves concurrency, not permissions.

A malicious or buggy client with permission to execute the query can still lock rows.

For multi-tenant systems:

```text
tenant isolation
+
authorization
+
RLS / application policy
+
row locking
```

must be designed separately.

A particularly dangerous pattern is:

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;
```

when the application should have restricted the row to the caller's tenant.

The correct query may need:

```sql
SELECT *
FROM orders
WHERE tenant_id = $1
  AND id = $2
FOR UPDATE;
```

and the authorization boundary should still be enforced independently.

The lock should never become a substitute for tenant authorization.

```text

statement timeout
deadlock

serialization retry
```

# 45. Retry Strategy

`FOR UPDATE` itself does not mean every error is retryable.

A retry layer should classify errors.

For example:

```text
deadlock detected              -> often retryable
serialization failure          -> often retryable
lock timeout                   -> workload-dependent
unique violation               -> usually business/conflict handling
invalid input                   -> no retry
permission denied              -> no retry
syntax error                    -> no retry
```

When retrying a deadlock or serialization failure:

```text
rollback failed attempt
        |
        v
start a fresh transaction
        |
        v
re-read authoritative state
        |
        v
repeat business decision
        |
        v
commit
```

Do not reuse stale objects read by the failed transaction unless they are explicitly safe and authoritative for the new attempt.

# 47. Concurrency Test — Competing Updates

Session A:

```sql
BEGIN;

SELECT quantity
FROM inventory
WHERE id = 7
FOR UPDATE;

UPDATE inventory
SET quantity = quantity - 1
WHERE id = 7;
```

Session B:

```sql
BEGIN;

UPDATE inventory
SET quantity = quantity - 1
WHERE id = 7;
```

Session B will wait for the conflicting row update/lock while Session A's transaction remains open.

Commit Session A:

```sql
COMMIT;
```

Then observe Session B continue.

This experiment is useful because it shows that `FOR UPDATE` coordinates with ordinary writes, not only with another `FOR UPDATE` statement.

# 48. Concurrency Test — NOWAIT

Session A:

```sql
BEGIN;

FROM inventory
WHERE id = 7
FOR UPDATE;
```

Session B:

```sql
SELECT *
FROM inventory
WHERE id = 7
```

Expected outcome:


There is no waiting interval equivalent to ordinary `FOR UPDATE`.

# 49. Concurrency Test — SKIP LOCKED

Session A:

```sql
BEGIN;

SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY id
LIMIT 1
FOR UPDATE;
```

Session B:

```sql
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

If another eligible row exists, Session B can skip the locked row and select another one.

# 50. Example — Batch Processing Without Deadlock Amplification

Suppose a reconciliation worker updates thousands of rows.

Naive approach:

```sql
SELECT id
FROM reconciliation_items
WHERE status = 'OPEN'
FOR UPDATE;
```

Potential problems:

```text
huge lock footprint
long transaction
high contention
large rollback cost
pool pressure
replication impact from subsequent writes
```

Better batch pattern:

```sql
WITH batch AS (
  SELECT id
  FROM reconciliation_items
  WHERE status = 'OPEN'
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 500
)
UPDATE reconciliation_items r
SET status = 'PROCESSING'
FROM batch b
WHERE r.id = b.id
RETURNING r.*;
```

Then process a bounded amount of work per transaction.

The exact batch size should be measured, not chosen by folklore.

# 54. Production Decision Framework

Ask these questions in order:

### Question 1
Can the invariant be enforced with a constraint?

```text
UNIQUE
CHECK
FOREIGN KEY
EXCLUSION
```

Prefer declarative enforcement where appropriate.

### Question 2
Can the operation be expressed as one atomic SQL statement?

Example:

```sql
UPDATE ...
WHERE condition
RETURNING ...;
```

Prefer it when it fully captures the invariant.

### Question 3
Does the application need to read authoritative state and then perform multiple dependent operations?

If yes, consider:

```text
SELECT ... FOR UPDATE
```

### Question 4
Can concurrent callers safely skip locked work?

If yes, evaluate:

```text
SKIP LOCKED
```

### Question 5
Must failure happen immediately rather than waiting?

Evaluate:

```text
NOWAIT
```

### Question 6
Does the invariant concern rows that may not yet exist?

A plain row lock may be insufficient. Consider:

```text
SERIALIZABLE
predicate conflict handling
exclusion constraints
coordination rows
```

# 55. Comparison Matrix

| Technique | Best for | Main strength | Main risk |
|---|---|---|---|
| Plain `SELECT` | ordinary reads | low coordination cost | no ownership of row |
| Atomic `UPDATE` | simple state transitions | compact + race-resistant | limited for complex workflows |
| `SELECT FOR UPDATE` | read-modify-write | explicit row ownership | lock contention |
| `FOR UPDATE NOWAIT` | fail-fast workflows | avoids waiting | errors under contention |
| `FOR UPDATE SKIP LOCKED` | queues/work stealing | high concurrency | intentionally incomplete view |
| `REPEATABLE READ` | stable transaction snapshot | consistent view | serialization failures on conflicts |
| `SERIALIZABLE` | cross-row invariants | serial execution semantics | more abort/retry pressure |
| Constraint | declarative invariant | centralized correctness | not every invariant is declarable |

There is no universal winner.

The correct choice follows the invariant and workload.

# 57. Interview Questions

## Junior

### Q1. What does `SELECT ... FOR UPDATE` do?

**Weak Answer:**

> It locks the database.

**Acceptable Answer:**

> It locks selected rows for update so concurrent transactions cannot modify or acquire conflicting row locks on them until the transaction ends.

**Strong Answer:**

> It is a locking read that selects rows using MVCC semantics and acquires `FOR UPDATE` row locks, coordinating future writers and lockers on those rows.

**Expert Answer:**

> It combines snapshot-aware row selection with update-strength row locking. In `READ COMMITTED`, a concurrent modification can cause the statement to wait and then return the updated version if it still qualifies; at `REPEATABLE READ` or `SERIALIZABLE`, a conflicting row change since the snapshot can produce a serialization failure. citeturn253508search2

---

### Q2. Does `FOR UPDATE` lock the whole table?

**Answer:**

No. It locks selected rows, while the statement also acquires the weaker table-level `ROW SHARE` lock on explicitly locked relations. citeturn253508search2

---

## Mid-Level

### Q3. Why use `FOR UPDATE` instead of a plain `SELECT`?

Because a plain `SELECT` gives visibility but not ownership. `FOR UPDATE` is useful when the application must read authoritative state and then perform dependent work while preventing competing writers/lockers from changing those rows during the transaction.

### Q4. Why might an atomic `UPDATE` be better?

Because when the entire invariant can be expressed in one statement, it avoids an unnecessary read-modify-write round trip and often reduces the duration and complexity of the critical section.

---

## Senior

### Q5. Why can `SELECT ... FOR UPDATE` still be insufficient?

Because the invariant may concern multiple rows, ranges, or the absence of rows. Locking one returned row does not automatically protect future inserts or every row that contributes to the business rule.

### Q6. Why can lock contention exist even when CPU is low?

Because sessions may be waiting on other transactions instead of executing CPU work. Queueing can dominate request latency while database CPU remains modest.

---

## Staff / Principal

### Q7. How do you decide between `FOR UPDATE`, atomic SQL, constraints, and `SERIALIZABLE`?

Start from the invariant:

```text
constraint if declarative
atomic SQL if single-statement
row lock if explicit read-modify-write coordination
SERIALIZABLE if the invariant spans concurrent predicate/range reasoning
```

Then evaluate workload, contention, retry cost, failure semantics, and observability.

# 60. Production Incident Scenario

### Incident

A jewellery ERP API normally responds in 120 ms.

During a high-traffic sale:

The lesson is not:

The lesson is:

> **Use row locks for short, explicit coordination boundaries, and keep unpredictable work outside those boundaries.**

- [ ] A constraint or atomic statement was considered first.
- [ ] The lock strength is justified.
- [ ] `FOR UPDATE OF` is used when joins do not require locking every target relation.
- [ ] Transaction scope is explicit.
- [ ] One dedicated PostgreSQL connection owns the entire transaction.
- [ ] No external API or unpredictable I/O occurs while critical rows are locked unless deliberately justified.
- [ ] Lock ordering is compatible with other code paths.
- [ ] Result cardinality is bounded where feasible.
- [ ] `NOWAIT` and `SKIP LOCKED` semantics are understood by the caller.
- [ ] Deadlock handling is implemented where relevant.
- [ ] Serialization failure handling is implemented where relevant.
- [ ] Retry attempts restart the logical transaction.
- [ ] Retry count and backoff are bounded.
- [ ] Idempotency is established for retried business operations.
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` has been reviewed for the locking query.
- [ ] Lock wait and transaction duration are observable.
- [ ] Production query logging identifies unexpectedly long transactions.
- [ ] Concurrency tests reproduce the critical race.
- [ ] Multi-tenant authorization is enforced independently of locking.
- [ ] The team understands that row locks do not protect nonexistent rows or arbitrary predicates.
