# 03.8 — Repeatable Read

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains PostgreSQL's `REPEATABLE READ` isolation level from first principles: snapshot stability, visibility, concurrent updates, serialization failures, application design, debugging, testing, and production trade-offs.

## 1. Chapter Objective

By the end of this chapter you should be able to:

- explain exactly what PostgreSQL guarantees with `REPEATABLE READ`;
- distinguish transaction-level snapshot consistency from statement-level `READ COMMITTED` behavior;
- explain when the repeatable-read snapshot is established;
- reason about what rows a transaction can and cannot see after concurrent commits;
- explain why PostgreSQL's `REPEATABLE READ` prevents nonrepeatable reads;

# 2. The Central Mental Model

The simplest useful model is:

```text
READ COMMITTED

Transaction
    |
    +-- Statement 1 -> Snapshot S1
    |
    +-- Statement 2 -> Snapshot S2
    |
    +-- Statement 3 -> Snapshot S3

Each statement can observe a newer committed world.
```

Versus:

```text
REPEATABLE READ

Transaction
    |
    +-- First query/write -> Snapshot S
    |
    +-- Statement 2 -------> Snapshot S
    |
    +-- Statement 3 -------> Snapshot S
    |
    +-- Statement 4 -------> Snapshot S

All ordinary statements use the same transaction snapshot.
```

The most important sentence in this chapter is:

> **`REPEATABLE READ` gives one stable MVCC view for the transaction, but that view is not necessarily the latest state of the database.**

That distinction is critical. A stable snapshot is not the same thing as real-time truth.

PostgreSQL's documentation states that a `REPEATABLE READ` transaction sees the data committed before the first query or data-modification command began, and successive reads see the same snapshot. It also documents a stronger behavior than the SQL minimum: phantom reads are not possible in PostgreSQL's implementation. citeturn237530search20turn237530search0

# 3. What `REPEATABLE READ` Means

## 3.1 Simple definition

`REPEATABLE READ` means that a transaction works from a stable snapshot of the database, so the same row cannot appear to change underneath ordinary repeated reads during that transaction.

## 3.2 Engineering definition

A `REPEATABLE READ` transaction uses a single transaction snapshot for visibility. Other transactions may commit changes while the transaction is running, but those newly committed row versions are not automatically added to the transaction's ordinary visibility view.

## 3.3 Expert definition

PostgreSQL implements `REPEATABLE READ` with MVCC snapshot isolation semantics. Once the transaction snapshot is established, all subsequent ordinary reads use that snapshot. If a write operation conflicts with a row version that changed after the snapshot was taken, PostgreSQL may be unable to safely apply the operation within that fixed snapshot and will raise a serialization failure rather than silently moving the transaction's view forward. citeturn237530search20

# 4. `REPEATABLE READ` Is Snapshot Isolation, Not “Time Travel”

It is tempting to think:

> “The transaction is frozen in time.”

That is useful as an intuition, but incomplete.

The database is not globally frozen.

```text
Transaction T1                    Database
--------------                   --------
Snapshot S                       Current state keeps changing
     |                                  |
     |       T2 commits UPDATE          |
     |<---------------------------------|
     |
     +-- T1 still sees S for ordinary reads
```

T2 can keep committing. T1 simply does not incorporate those new versions into its ordinary snapshot visibility.

This gives an essential distinction:

```text
Database state at time T
        !=
Snapshot visible to transaction T1
```

A snapshot answers:

> “Which row versions belong to the consistent world this transaction is allowed to observe?”

It does **not** answer:

> “What is the latest committed value right now?”

# 5. Why `REPEATABLE READ` Exists

`READ COMMITTED` is often excellent for short independent operations, but multi-step reasoning can become difficult because each statement can observe a newer committed world.

Example:

```sql
BEGIN;

SELECT total FROM accounts WHERE customer_id = 42;

-- another transaction commits changes

SELECT balance FROM accounts WHERE customer_id = 42;

COMMIT;
```

Under `READ COMMITTED`, those two statements can see different committed states.

Under `REPEATABLE READ`, both statements use the same snapshot.

This matters when application logic depends on reading a consistent set of facts:

```text
Read A
Read B
Read C
Compare A + B against C
Make a decision
```

Without a stable snapshot, the application can end up reasoning over a mixture of different committed worlds.

PostgreSQL explicitly notes that `REPEATABLE READ` provides a stable view throughout the transaction, while `READ COMMITTED` has a shifting view with each statement. citeturn237530search0

# 6. Starting a Repeatable-Read Transaction

You can request the isolation level when starting the transaction:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

or:

```sql
START TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

You can also use:

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

The transaction-level setting must be established before statements whose behavior depends on the transaction snapshot are executed.

Check the active isolation level with:

```sql
SHOW transaction_isolation;
```

or:

```sql
SELECT current_setting('transaction_isolation');
```

The default in PostgreSQL remains `READ COMMITTED`, so `REPEATABLE READ` must be requested explicitly unless a different default has been configured. citeturn237530search3

# 7. When Is the Snapshot Actually Established?

This detail is easy to misunderstand.

A repeatable-read snapshot is not best thought of as “created at the exact moment the TCP connection receives `BEGIN`.” PostgreSQL documents that the snapshot is frozen at the start of the transaction's **first query or data-modification command** — `SELECT`, `INSERT`, `UPDATE`, `DELETE`, or `MERGE`. citeturn237530search0

For reasoning purposes:

```text
BEGIN
  |
  |  no visibility-dependent command yet
  |
  +-- first SELECT / INSERT / UPDATE / DELETE / MERGE
          |
          +--> transaction snapshot becomes fixed
```

This has a surprising production implication:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

LOCK TABLE orders IN SHARE MODE;

SELECT ...;
```

A transaction can explicitly acquire some locks before its repeatable-read snapshot is frozen. PostgreSQL's documentation specifically warns that when explicit locking is used for consistency checks, lock acquisition order relative to snapshot creation matters. citeturn237530search0

This is not a trivia detail. It can affect correctness in advanced consistency-checking designs.

# 8. Visibility Example: The Same Row, Twice

Assume:

```text
accounts
--------
id | balance
1  | 1000
```

T1 begins repeatable read and reads the row:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM accounts
WHERE id = 1;
```

Result:

```text
1000
```

Now T2 runs:

```sql
BEGIN;

UPDATE accounts
SET balance = 900
WHERE id = 1;

COMMIT;
```

T2 has committed.

T1 now executes:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

T1 still sees the version belonging to its snapshot.

Conceptually:

```text
Time ------------------------------------------------>

Initial committed version
balance = 1000
        |
        | T1 snapshot established
        v
        S
        |
        | T2 updates and commits
        v
balance = 900

T1 ordinary reads --> still based on S --> 1000
```

That is the essence of repeatability.

# 9. Nonrepeatable Reads: What `REPEATABLE READ` Prevents

A nonrepeatable read occurs when a transaction reads a row, another transaction changes and commits that row, and the first transaction reads it again but gets a different value.

Under `READ COMMITTED`:

```text
T1: SELECT balance -> 1000
T2: UPDATE balance -> 900 COMMIT
T1: SELECT balance -> 900
```

Under PostgreSQL `REPEATABLE READ`:

```text
T1: SELECT balance -> 1000
T2: UPDATE balance -> 900 COMMIT
T1: SELECT balance -> 1000
```

The second read is stable because T1's visibility snapshot has not changed.

The PostgreSQL isolation-level table explicitly marks nonrepeatable reads as not possible at `REPEATABLE READ`. citeturn237530search20

---

# 10. Phantom Reads in PostgreSQL

The SQL standard permits phantom reads at `REPEATABLE READ`, but PostgreSQL's implementation does not expose ordinary phantom reads at this level.

Suppose:

```sql
SELECT count(*)
FROM orders
WHERE status = 'PENDING';
```

returns:

```text
10
```

Another transaction inserts a new matching order and commits:

```sql
INSERT INTO orders(status) VALUES ('PENDING');
COMMIT;
```

The original repeatable-read transaction performs the same query again.

It continues to see the same snapshot-defined set of committed rows rather than suddenly acquiring the new row.

PostgreSQL's official isolation documentation explicitly notes this stronger behavior: its `REPEATABLE READ` implementation does not allow phantom reads even though the standard allows them at that isolation level. citeturn237530search20

Do not turn this fact into the wrong rule:

> “Repeatable read guarantees every possible business invariant.”

It does not.

A stable snapshot can still allow **serialization anomalies** — situations where concurrently committed transactions cannot be explained as some serial ordering. PostgreSQL's documentation lists serialization anomalies as possible at `REPEATABLE READ` and impossible at `SERIALIZABLE`. citeturn237530search20

---

# 11. `REPEATABLE READ` vs `READ COMMITTED`

| Property | READ COMMITTED | REPEATABLE READ |
|---|---|---|
| Default in PostgreSQL | Yes | No |
| Snapshot scope | Per statement | Per transaction |
| Dirty reads | No | No |
| Nonrepeatable reads | Possible | Not possible |
| Ordinary phantom reads | Possible | Not possible in PostgreSQL |
| Serialization anomalies | Possible | Possible |
| Concurrent update behavior | May wait and continue with updated row version | Conflict can raise serialization failure |
| Best mental model | Fresh committed view per command | Stable committed snapshot per transaction |

The important transition is:

```text
READ COMMITTED
statement consistency

        -> stronger snapshot stability ->

REPEATABLE READ
transaction snapshot consistency

        -> stronger anomaly prevention ->

SERIALIZABLE
serial execution equivalence
```

Do not select an isolation level by “higher is always better.” The stronger the concurrency guarantee, the more carefully the application must handle blocking, aborts, retries, and workload trade-offs.

---

# 12. The Most Important Surprise: Concurrent Updates Can Fail

Consider:

```text
T1: BEGIN ISOLATION LEVEL REPEATABLE READ
T1: SELECT * FROM inventory WHERE id = 7;
```

Now T2 changes the same row and commits:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE id = 7;
COMMIT;
```

T1 then attempts to update that same row:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE id = 7;
```

T1 cannot simply say:

> “The latest version is now the correct target. I will transparently move my snapshot forward.”

That would violate repeatable-read semantics.

PostgreSQL can instead abort the command/transaction with a serialization failure such as:

```text
ERROR: could not serialize access due to concurrent update
```

PostgreSQL's documentation explicitly describes concurrent update conflicts at higher isolation levels as a reason the transaction may need to retry rather than silently follow a newer committed row version. citeturn237530search20turn237530search11

The core idea is:

```text
READ COMMITTED

snapshot S
   |
concurrent update
   |
wait
   |
use newer committed row version


REPEATABLE READ

snapshot S
   |
concurrent update conflicts with S
   |
cannot advance ordinary snapshot
   |
serialization failure
```

---

# 13. Why Does PostgreSQL Abort Instead of Updating the New Version?

Because otherwise the transaction would no longer behave as a repeatable-read transaction.

Suppose T1's logic is based on:

```text
World W1
```

Then another transaction commits and creates:

```text
World W2
```

If T1 suddenly incorporates part of W2 into its write operation while retaining W1 for other reads, it could reason over a hybrid state.

That would weaken the very guarantee the isolation level is supposed to provide.

Therefore PostgreSQL chooses the safer outcome:

```text
Detect conflict
      |
      v
Abort transaction
      |
      v
Application may retry the whole logical unit
```

This is a fundamental concurrency design pattern:

> **At stronger isolation levels, correctness can require aborting work rather than silently producing a result from a mixed view.**

---

# 14. Serialization Failure Is Not the Same as Deadlock

These are frequently confused.

## 14.1 Deadlock

Two transactions wait on each other:

```text
T1 waits for T2
T2 waits for T1
```

PostgreSQL detects the cycle and aborts one transaction.

## 14.2 Serialization failure

The database determines that letting the transaction commit would violate the requested isolation semantics, so it aborts it rather than allowing a result that cannot be reconciled with the isolation guarantee.

Typical application-level categories should therefore distinguish:

```text
lock timeout
statement timeout
deadlock detected
serialization failure
unique violation
foreign-key violation
business-rule rejection
```

These failures have different causes and often different retry strategies.

# 15. Retry the Whole Transaction, Not the Failed Statement

A common mistake is:

```ts
try {
  await client.query(updateSql);
} catch (error) {
  await client.query(updateSql);
}
```

That is usually the wrong recovery model for a serialization failure.

A retryable serialization failure invalidates the logical transaction attempt. The correct shape is generally:

```text
Begin attempt 1
    |
    +-- read
    +-- validate
    +-- write
    +-- commit
          |
          +-- serialization failure
                    |
                    v
              rollback/connection cleanup
                    |
                    v
               retry attempt 2
                    |
                    +-- read again
                    +-- validate again
                    +-- write again
                    +-- commit
```

Why repeat the entire transaction?

Because the failed attempt was based on a snapshot and execution history that cannot safely be completed. A statement-level retry may reuse assumptions that are now invalid.

A robust transaction retry loop should:

- start a fresh transaction;
- re-read data inside the new snapshot;
- recompute decisions;
- reapply writes;
- cap the number of attempts;
- use bounded backoff where appropriate;
- avoid retrying non-retryable application errors;
- preserve idempotency at external boundaries.

PostgreSQL's documentation explicitly recommends application-level retry handling for serialization failures when stronger isolation is used. citeturn237530search0

# 16. A Production-Grade Retry Skeleton

Node.js / `pg`-style pseudocode:

```ts
async function withRetry<T>(
  operation: (client: PoolClient) => Promise<T>,
  maxAttempts = 3,
): Promise<T> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const client = await pool.connect();

    try {
      await client.query('BEGIN ISOLATION LEVEL REPEATABLE READ');

      const result = await operation(client);

      await client.query('COMMIT');
      return result;
    } catch (error: any) {
      try {
        await client.query('ROLLBACK');
      } catch {
        // Preserve the original failure.
      }

      const retryable =
        error?.code === '40001';

      if (!retryable || attempt === maxAttempts) {
        throw error;
      }

      const delayMs = 25 * 2 ** (attempt - 1);
      await sleep(delayMs);
    } finally {
      client.release();
    }
  }

  throw new Error('Unreachable');
}
```

Important engineering details:

```text
Do:
- retry the complete logical transaction
- obtain a fresh connection/transaction attempt
- rollback on error
- release the connection
- cap retries
- classify errors

Do not:
- retry forever
- retry every database error
- reuse stale application decisions
- keep external side effects inside the retried block without an idempotency strategy
```

The PostgreSQL SQLSTATE for serialization failure is commonly handled as `40001`. Always verify driver/framework mappings before hard-coding error handling behavior in a reusable library.

# 17. The Snapshot Can Be Consistent and Still Be Stale

This is one of the most important production truths.

Consider a reporting transaction:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT ... many tables ...;
SELECT ... many tables ...;
SELECT ... aggregates ...;

COMMIT;
```

The report can be internally consistent with respect to the transaction's snapshot while being minutes or hours behind the latest committed state, depending on how long the transaction has been open.

Thus:

```text
Consistency != freshness
```

A long-running transaction can be perfectly consistent and operationally useless if the product requirement is “current status.”

Ask two separate questions:

1. Is the view internally consistent?
2. How fresh must the view be?

Those are different requirements.

# 18. Multi-Statement Consistency Checks

A classic use case for repeatable read is a multi-query consistency check.

Suppose a system tracks:

```text
credits
-----------
debit_id | amount

and

ledger
-----------
entry_id | amount | type
```

A validation process may need several queries to inspect the same logical world.

Under `READ COMMITTED`, each query can observe a later state:

```text
Q1 -> snapshot S1
Q2 -> snapshot S2
Q3 -> snapshot S3
```

Under `REPEATABLE READ`:

```text
Q1 -> snapshot S
Q2 -> snapshot S
Q3 -> snapshot S
```

This avoids a simple but dangerous class of false inconsistencies caused by comparing results from different snapshots.

PostgreSQL's consistency-checking documentation specifically contrasts `READ COMMITTED`'s shifting view with repeatable read's stable view. citeturn237530search0

---

# 19. But a Stable Snapshot Does Not Prove Current Truth

Suppose the check returns:

```text
credits = 1,000,000
ledger  = 1,000,000
```

That proves those values agree **in the snapshot**.

It does not prove:

```text
credits = 1,000,000
ledger  = 1,000,000
right now
```

There may be newer commits that occurred after the snapshot.

This distinction becomes critical for:

- settlement systems;
- financial close processes;
- reconciliation jobs;
- regulatory reports;
- inventory reconciliation;
- fraud analysis;
- operational dashboards.

For a current-state invariant, you may need explicit locking, a stronger isolation level, a controlled maintenance window, or an architecture where the invariant is enforced at write time rather than inferred by a later read.

PostgreSQL explicitly warns that a repeatable-read consistency check only describes transactions committed before that transaction's snapshot. citeturn237530search0

# 20. Repeatable Read and Explicit Locks

Locks and snapshots solve different problems.

```text
MVCC snapshot
    -> what row versions I can see

Lock
    -> what concurrent operations I can block or coordinate with
```

This distinction is fundamental.

Consider:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

LOCK TABLE orders IN SHARE MODE;

SELECT ...;
```

A lock may prevent other conflicting operations, but the snapshot may still be older than some changes already committed before the lock was acquired.

PostgreSQL's documentation gives an important advanced rule: when using explicit locking in repeatable-read consistency checks, be careful about **when** the lock is taken relative to snapshot creation. A lock obtained before the snapshot is frozen can provide a different picture from one acquired afterward. citeturn237530search0

Think in two timelines:

```text
Timeline A: snapshot creation
Timeline B: lock acquisition
```

Correctness may depend on their order.

---

# 21. Locking a Row Does Not Make the Snapshot Current

A common misunderstanding is:

```sql
SELECT *
FROM orders
WHERE id = 42
FOR UPDATE;
```

and the assumption:

> “Because I locked the row, I now see the latest committed value.”

That conclusion is not generally valid at `REPEATABLE READ`.

A lock is a concurrency-control operation. Snapshot visibility is an MVCC visibility rule.

Always ask two independent questions:

```text
1. What version does my snapshot allow me to see?
2. What concurrent actions does my lock prevent?
```

Mixing those concepts causes many subtle concurrency bugs.

---

# 22. Repeatable Read and `SELECT ... FOR UPDATE`

At `READ COMMITTED`, a locking read can encounter a row changed by another transaction, wait for the concurrent updater, and then work with the updated row version.

At `REPEATABLE READ`, PostgreSQL cannot simply move the transaction's visibility forward. A conflicting update against a row that changed after the transaction snapshot can therefore produce a serialization failure. PostgreSQL documents this stronger conflict behavior as part of its higher isolation guarantees. citeturn237530search20turn237530search11

This gives a practical rule:

> **Do not assume that changing `READ COMMITTED` to `REPEATABLE READ` is a transparent configuration change. Existing application code may start seeing retryable transaction aborts.**

---

# 23. Repeatable Read and Atomic Updates

Suppose your inventory operation is:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0;
```

This remains an excellent pattern because the database performs the check and change atomically.

However, the isolation level changes how the transaction behaves when multiple logical operations interact.

Compare:

```text
Single atomic statement
        |
        +--> small concurrency window

vs.

Read -> business logic -> read -> write
        |
        +--> larger reasoning surface
```

`REPEATABLE READ` can make the multi-step read side more coherent, but it does not eliminate the need for atomic predicates and correct update conditions.

Do not use higher isolation as a substitute for writing correct SQL.

# 24. Naive Approach → Why It Fails → Improved Approach

## 24.1 Naive approach

> “Use `REPEATABLE READ` everywhere because stronger isolation is always safer.”

### Why it fails

You can introduce:

- more serialization failures;
- more application retries;
- longer transaction lifetimes;
- stale reads;
- unnecessary contention;
- poorer throughput under write-heavy workloads;
- retry storms if many workers fail and immediately restart.

### Improved approach

Choose the isolation level from the invariant:

```text
What must be true if this transaction commits?
```

Then choose the minimum mechanism that safely enforces that invariant.

---

## 24.2 Naive approach

> “A repeatable snapshot means my data is current.”

### Why it fails

Snapshot stability says nothing about freshness.

### Improved approach

Model freshness explicitly:

```text
Consistency requirement = one thing
Freshness requirement   = another thing
```

---

## 24.3 Naive approach

> “If a serialization failure happens, retry the failed SQL statement.”

### Why it fails

The rest of the transaction was based on the failed snapshot and assumptions.

### Improved approach

Retry the entire transaction from the beginning using a fresh snapshot.

---

## 24.4 Naive approach

> “Retry immediately forever.”

### Why it fails

Two or more hot transactions can repeatedly collide:

```text
T1 fails -> retry
T2 fails -> retry
T1 fails -> retry
T2 fails -> retry
...
```

This can amplify load instead of reducing it.

### Improved approach

Use bounded retries and, where appropriate, exponential backoff with jitter.

# 25. Repeatable Read in a Jewellery ERP

Consider a multi-branch jewellery ERP.

A stock reconciliation operation might need to read:

```text
branch inventory
+ tagged pieces
+ repair items
+ transfer records
+ reservation state
+ transaction history
```

Suppose the reconciliation consists of ten SQL statements.

Under `READ COMMITTED`:

```text
Q1 -> state S1
Q2 -> state S2
Q3 -> state S3
...
Q10 -> state S10
```

A concurrent stock transfer may commit between these queries.

Under `REPEATABLE READ`:

```text
Q1 -> S
Q2 -> S
Q3 -> S
...
Q10 -> S
```

The reconciliation now reasons over one snapshot.

But there is a crucial business question:

> Is the reconciliation supposed to represent a historically consistent snapshot, or the most current branch inventory at the instant the check finishes?

If it is historical consistency, repeatable read may be appropriate.

If it is “current reality,” a stable but older snapshot may be the wrong semantic model.

This is how isolation decisions should be made in real systems: from business semantics, not from the name of the isolation level.

# 26. Multi-Tenant Applications

For a tenant-scoped transaction:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT ...
FROM inventory
WHERE tenant_id = $1;

SELECT ...
FROM orders
WHERE tenant_id = $1;

SELECT ...
FROM transfers
WHERE tenant_id = $1;

COMMIT;
```

The snapshot applies to the transaction as a whole, not merely to one tenant filter.

That means the isolation boundary is:

```text
Database transaction
        |
        +--> tenant A rows
        +--> tenant B rows
        +--> system tables / shared data
```

Even when application logic is tenant-scoped, MVCC semantics remain database-transaction scoped.

Security implication:

> **Repeatable read is not a tenant-isolation mechanism.**

Tenant boundaries still require correct predicates, authorization, RLS where appropriate, and safe query construction.

# 27. Repeatable Read and Connection Pools

In Node.js, transaction state lives on a database connection/session.

This is dangerous:

```ts
await pool.query('BEGIN ISOLATION LEVEL REPEATABLE READ');
await pool.query('SELECT ...');
```

followed later by:

```ts
await pool.query('SELECT ...');
```

There is no guarantee those calls use the same pooled connection.

Correct pattern:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN ISOLATION LEVEL REPEATABLE READ');

  await client.query('SELECT ...');
  await client.query('SELECT ...');
  await client.query('UPDATE ...');

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

The transaction's snapshot is connection/session state. Losing the connection between statements means losing the transaction.

This is one of the highest-impact mistakes for Node.js developers moving from simple CRUD to advanced transactional code.

# 28. NestJS Transaction Boundaries

A production NestJS application should make the transaction boundary obvious.

Good conceptual structure:

```text
Controller
   |
   v
Application Service
   |
   v
Transaction boundary
   |
   +--> repository A
   +--> repository B
   +--> repository C
```

All repositories participating in that logical transaction must use the same database session.

A common anti-pattern is:

```text
service starts transaction on client X
repository creates new pool query on client Y
repository B uses client Z
```

That is not one transaction.

For repeatable read, this mistake is especially harmful because the application may believe several queries share one snapshot when they do not.

# 29. Do Not Call External Services Inside the Retry Loop Without a Strategy

Consider:

```text
BEGIN REPEATABLE READ

update database
call payment provider
call shipping provider
commit
```

Now suppose the database transaction gets a serialization failure after the external payment provider has already succeeded.

The retry executes:

```text
call payment provider again
```

You can create a duplicate external effect.

Therefore:

```text
Database retry
    !=
External API retry
```

Use patterns such as:

- idempotency keys;
- transactional outbox;
- durable workflow state;
- state-machine orchestration;
- post-commit event processing.

This is one reason PostgreSQL transaction design cannot be treated independently from distributed systems design.

# 30. Repeatable Read and the Outbox Pattern

Suppose a transaction creates an order and an event record:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

INSERT INTO orders (...);

INSERT INTO outbox_events (...);

COMMIT;
```

If serialization failure occurs, the **whole transaction** can be retried.

The outbox row is recreated as part of the new successful transaction attempt.

An event dispatcher can later publish it outside the database transaction.

This sharply separates:

```text
Database atomicity
        |
        +--> order + outbox row

from

External delivery
        |
        +--> event broker / API / worker
```

That architecture is much safer than directly calling external systems from inside a transaction that may be retried.

---

# 31. Long-Running Repeatable-Read Transactions

Long-lived transactions deserve special attention.

Conceptually:

```text
BEGIN RR
   |
   | snapshot remains relevant
   |
   | many queries
   |
   | user waits
   |
   | more queries
   |
   COMMIT
```

The longer the transaction lives, the older its snapshot can become.

Operational consequences can include:

- stale application views;
- increased vacuum pressure from old snapshots;
- transaction ID aging concerns;
- longer-held locks if the transaction also locks objects;
- more difficult failure recovery;
- greater probability of conflicts;
- increased resource usage across the workload.

A snapshot is cheap conceptually but not free operationally when retained for a long time.

Never design a transaction that spans human think time.

Avoid:

```text
BEGIN
show form to user
wait 30 seconds
wait for payment UI
wait for confirmation
UPDATE
COMMIT
```

Transactions should usually be short-lived units of database work.

---

# 32. Snapshot Age and Vacuum Interaction

MVCC keeps multiple row versions because active transactions may still need older versions for visibility.

Therefore a long-running transaction can contribute to preventing old row versions from being removable.

At a conceptual level:

```text
old transaction snapshot
        |
        +--> old tuple versions may remain relevant
        |
        +--> vacuum cannot freely remove everything visible to nobody
```

The exact cleanup rules are more nuanced than “one old transaction blocks all vacuum,” but long-lived snapshots are a real operational concern.

The practical principle is:

> **Short transactions reduce the lifetime of historical visibility requirements.**

Monitor transaction age in production, especially when applications use long-running reporting, ETL, or maintenance transactions.

# 33. Monitoring Long Transactions

Useful starting point:

```sql
SELECT
  pid,
  usename,
  application_name,
  client_addr,
  state,
  xact_start,
  query_start,
  now() - xact_start AS transaction_age,
  wait_event_type,
  wait_event,
  query
```

Look for:

```text
transaction_age
wait_event_type
wait_event
state
query
application_name
```

A session that is `idle in transaction` is especially worth investigating.

For a repeatable-read workload, also correlate transaction age with:

- autovacuum behavior;
- table bloat;
- application latency;
- conflict rates;
- connection-pool saturation.

# 34. Monitoring Locks and Conflicts

```text
blocked on a lock
vs.
serialization failure
vs.
slow query
vs.
application inactivity
```

# 35. Error Handling in the Application Layer

A mature database abstraction should classify transaction failures.

Example conceptual mapping:

```text
40001 -> serialization failure -> retry whole transaction
40P01 -> deadlock detected      -> retry whole transaction if safe
23505 -> unique violation       -> usually business/application handling
23503 -> FK violation           -> data integrity/application handling
55P03 -> lock not available     -> depends on operation
57014 -> statement timeout      -> usually investigate/possibly retry
```

Do not blindly retry everything.

For example:

```text
unique violation
```

may mean:

```text
request is duplicate
```

rather than:

```text
transaction encountered transient concurrency
```

A universal retry handler is dangerous.

# 36. Idempotency and Repeatable-Read Retries

Suppose a client sends:

```text
POST /orders
```

The server starts a repeatable-read transaction.

The transaction fails once and is retried internally.

From the client's perspective, there was still only one request.

The database layer must ensure the logical operation is safe to retry.

This is where an idempotency key can help:

```text
client request
    |
    +--> idempotency_key = abc123
    |
    +--> transaction attempt 1
    |       failure
    |
    +--> transaction attempt 2
    |       success
```

The system should ensure the externally observable result is one logical operation, not two.

Repeatable-read retries therefore belong to a larger reliability architecture that includes API idempotency.

# 37. A Concrete Concurrency Lab

Use a simple table:

```sql
CREATE TABLE accounts (
  id bigint PRIMARY KEY,
  balance numeric(12, 2) NOT NULL
);

INSERT INTO accounts(id, balance)
VALUES (1, 1000.00);
```

## Session A

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM accounts
WHERE id = 1;
```

Expected:

```text
1000.00
```

Do not commit yet.

## Session B

```sql
BEGIN;

UPDATE accounts
SET balance = 900.00
WHERE id = 1;

COMMIT;
```

## Back to Session A

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

The result should remain consistent with A's snapshot.

Then attempt:

```sql
UPDATE accounts
SET balance = 800.00
WHERE id = 1;
```

Observe the concurrency error behavior.

The point of the lab is not to memorize the error string. The point is to answer:

> “Which version does my transaction believe exists, and what happens when I try to modify a row whose current version changed after my snapshot?”

# 38. Second Concurrency Lab: Phantom Prevention

Create:

```sql
CREATE TABLE jobs (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status text NOT NULL
);

INSERT INTO jobs(status)
VALUES ('pending'), ('pending'), ('done');
```

## Session A

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT count(*)
FROM jobs
WHERE status = 'pending';
```

Record the count.

## Session B

```sql
INSERT INTO jobs(status)
VALUES ('pending');
COMMIT;
```

## Session A

Repeat the same query:

```sql
SELECT count(*)
FROM jobs
WHERE status = 'pending';
```

The repeatable-read transaction continues to use its snapshot-defined world.

Then compare the same experiment under `READ COMMITTED`.

This is one of the easiest demonstrations of the difference between statement-level and transaction-level snapshots.

```text
consistent snapshot
```

# 41. Performance Considerations

`REPEATABLE READ` is not simply “faster” or “slower” than `READ COMMITTED`.

Performance depends on workload shape.

Potential costs include:

```text
more aborted transactions
more retries
longer-lived snapshots
more application work per successful operation
contention amplification under hot rows
```

Potential benefits include:

```text
consistent multi-query reads
simpler reasoning for snapshot-based workflows
fewer anomalies caused by shifting statement snapshots
```

The correct engineering question is:

> “What is the end-to-end cost of the chosen consistency model under our actual contention profile?”

Measure:

```text
transaction throughput
p50/p95/p99 latency
serialization failure rate
retry rate
average attempts
lock wait time
transaction age
CPU/WAL impact
application queue depth
```

# 42. `EXPLAIN` and Repeatable Read

`EXPLAIN` still helps answer query-planning questions:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

But remember:

> **`EXPLAIN` explains query execution; it does not by itself prove concurrency correctness.**

A beautifully indexed query can still participate in a broken transaction design.

Use two dimensions of evidence:

```text
Performance evidence
    -> EXPLAIN / BUFFERS / I/O / timing

Concurrency evidence
    -> pg_stat_activity / pg_locks / transaction state / controlled race tests
```

Do not use a query plan as a substitute for a transaction model.

# 43. AI / Vibe-Coding Failure Modes

## Failure mode 1: “Upgrade everything to repeatable read”

AI-generated code often treats stronger isolation as a generic fix for race conditions.

Why this fails:

- some bugs require an atomic SQL predicate;
- some require a row lock;
- some require a unique constraint;
- some require `SERIALIZABLE`;
- some are caused by incorrect transaction boundaries;
- some are distributed-system failures outside PostgreSQL.

Isolation level is one tool, not a universal concurrency patch.

---

## Failure mode 2: Retry only the failed statement

AI-generated retry wrappers commonly catch an error around one query and rerun that query.

Why this fails:

```text
transaction state before failure
!=
transaction state after fresh retry
```

The entire logical unit generally needs replay.

---

## Failure mode 3: Forgetting connection affinity

Code appears transactional:

```ts
await db.query('BEGIN ...');
await db.query('SELECT ...');
await db.query('UPDATE ...');
await db.query('COMMIT');
```

but `db.query()` pulls arbitrary pooled sessions.

The transaction model is then wrong at the infrastructure level.

---

## Failure mode 4: Long transaction around business workflow

Generated code may keep a transaction open while it:

- calls HTTP services;
- processes large files;
- waits for user confirmation;
- performs network retries;
- invokes slow third-party APIs.

This expands snapshot lifetime and failure surface.

---

## Failure mode 5: Calling current data from a historical snapshot

An AI-generated report may run under repeatable read and then describe its output as “current inventory.”

That is a semantic bug, not a SQL syntax bug.

---

# 44. Security Considerations

Isolation level does not replace authorization.

For a multi-tenant service:

```text
transaction isolation
        !=
row-level authorization
        !=
tenant isolation
```

A repeatable-read transaction can consistently expose the wrong tenant's rows if the application query is wrong.

Continue to enforce:

- tenant predicates;
- authorization checks;
- row-level security where appropriate;
- least-privilege database roles;
- parameterized SQL;
- safe dynamic SQL construction.

Consistency and confidentiality are separate properties.

---

# 45. Reliability Considerations

A production repeatable-read implementation should define:

```text
retry policy
transaction timeout
statement timeout
maximum attempts
backoff policy
idempotency behavior
observability
failure classification
```

A robust architecture treats transaction aborts as expected control-flow events under contention, while still keeping their rate low enough to meet latency and capacity targets.

Do not build a system whose correctness depends on infinite retries.

# 47. Production Scenario: Inventory Reservation

Suppose two shoppers try to reserve the final item.

A naive design:

```text
SELECT quantity
UPDATE later
```

under concurrency can fail because the decision and write are separated.

A stronger design may combine:

```text
atomic conditional update
+
appropriate isolation
+
transaction boundary
+
unique constraints where needed
+
retry handling
```

For example:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE sku = $1
  AND quantity > 0
RETURNING quantity;
```

The statement itself expresses the invariant.

`REPEATABLE READ` should not be used to compensate for poor SQL design.

# 48. Production Scenario: Financial Reconciliation

Suppose a nightly process wants a coherent view of related financial tables.

A repeatable-read transaction can provide a stable snapshot for the analysis.

But if the requirement is:

> “Prove that no invalid write can commit concurrently with this validation.”

then a passive snapshot may not be enough.

You may need:

```text
write-time constraints
or
explicit locking
or
SERIALIZABLE
or
architectural coordination
```

PostgreSQL's official consistency-checking guidance discusses this exact distinction between a consistent snapshot and a guarantee about concurrent writes. citeturn237530search0

# 49. Production Scenario: Reporting

A business dashboard may need:

```text
orders
customers
payments
inventory
```

One coherent snapshot can be valuable so numbers do not come from multiple moments.

But a read-only report may be better served by:

- a reporting replica;
- precomputed aggregates;
- materialized views;
- a warehouse;
- CDC-fed analytics infrastructure;
- a controlled historical snapshot.

Do not assume “use repeatable read” is automatically the best analytics architecture.

The correct solution depends on freshness, latency, isolation, and workload requirements.

# 50. `postgres_fdw` and Snapshot Semantics

When PostgreSQL accesses remote PostgreSQL tables through `postgres_fdw`, the remote transaction has its own transaction-management semantics. PostgreSQL 18 documents that the remote transaction uses `SERIALIZABLE` when the local transaction uses `SERIALIZABLE`; otherwise it uses `REPEATABLE READ`. This supports snapshot-consistent remote scans. citeturn237530search1

This matters because distributed-looking SQL can hide multiple transactional systems.

Do not assume:

```text
one SQL statement
=
one physical database engine's local snapshot
```

When foreign data wrappers, external systems, or distributed transaction patterns are involved, reason explicitly about each transaction boundary.

---

# 51. Repeatable Read vs Serializable

A useful mental ladder is:

```text
READ COMMITTED

“I see a current-enough committed view for each statement.”

REPEATABLE READ

“I reason over one stable snapshot for the whole transaction.”

SERIALIZABLE

“The committed result must be equivalent to some serial execution.”
```

PostgreSQL's documentation describes `SERIALIZABLE` as adding protection against dangerous read/write conflict patterns that can still occur under repeatable read. When such a dangerous pattern is detected, PostgreSQL aborts one transaction to break the cycle. citeturn237530search0

Therefore:

```text
Repeatable Read
    solves snapshot instability

Serializable
    solves broader serialization anomalies
```

The two are related but not interchangeable.

---

# 52. When `REPEATABLE READ` Is a Good Fit

Good candidates include workloads that benefit from one stable snapshot across multiple statements, such as:

- complex read-only analysis;
- reconciliation based on a coherent point-in-time view;
- consistency-sensitive batch logic where snapshot semantics are sufficient;
- workflows where nonrepeatable reads would complicate correctness;
- controlled transactional processing where serialization failures can be retried.

But always verify actual workload behavior.

---

# 53. When `REPEATABLE READ` Is a Poor Fit

It can be a poor choice when:

- the transaction must always see the latest committed state;
- the transaction is long-running;
- the workload has very high contention and retries are expensive;
- the application is not prepared to retry serialization failures;
- external side effects cannot be made idempotent;
- a stronger serializability guarantee is required;
- a reporting architecture should be isolated from the OLTP primary.

There is no universal “best” isolation level.

# 54. Common Developer Mistakes

## Mistake 1 — Assuming `BEGIN` means snapshot instantly freezes

More precise model: for repeatable read, snapshot visibility is frozen at the first query or data-modification command. citeturn237530search0

## Mistake 2 — Assuming repeatable read sees the latest committed data

It deliberately does not incorporate later commits into its ordinary snapshot.

## Mistake 3 — Assuming no phantom reads means no anomalies

Serialization anomalies can still occur at repeatable read. citeturn237530search20

## Mistake 4 — Treating serialization failure as a database bug

It is often the database correctly enforcing the requested isolation behavior.

## Mistake 5 — Retrying only one SQL statement

Retry the complete logical transaction.

## Mistake 6 — Opening transactions through a pool without connection pinning

All transactional statements must use the same client/session.

## Mistake 7 — Keeping the transaction open while waiting on network calls

This increases snapshot lifetime and can worsen contention and maintenance pressure.

## Mistake 8 — Using isolation level instead of a constraint

Use unique, foreign-key, check, exclusion, or other schema guarantees where the invariant belongs in the database.

## Mistake 9 — Assuming locks automatically refresh snapshot visibility

Locks and MVCC snapshots have separate semantics.

## Mistake 10 — Ignoring retry observability

A system can appear healthy while silently burning a large fraction of CPU and latency on repeated failed attempts.

# 55. Expert Reasoning Questions

When reviewing a repeatable-read design, ask:

### Q1. What exact invariant requires transaction-level snapshot stability?

Do not accept “because concurrency.” Identify the actual invariant.

### Q2. Does the transaction require consistency or freshness?

These are different dimensions.

### Q3. What happens when the target row changes after the snapshot?

Can the application tolerate a serialization failure?

### Q4. Is the logical operation retry-safe?

Can all database effects be replayed safely?

### Q5. Are there external side effects inside the retryable region?

If yes, how is idempotency guaranteed?

### Q6. How often do serialization failures occur in production?

A theoretical guarantee without operational measurement is incomplete.

### Q7. Could a unique constraint or atomic statement replace the higher isolation level?

Often the best optimization is reducing unnecessary coordination.

### Q8. Is the snapshot created before or after required explicit locks?

This can materially change consistency-check semantics. citeturn237530search0

### Q9. What happens if the transaction lasts 10 seconds instead of 100 ms?

Concurrency design must be evaluated under realistic latency distributions, not only the happy path.

### Q10. What happens during a retry storm?

A correct retry algorithm must also be a stable load-control mechanism.

# 58. Testing Strategy

A correct concurrency test should have deterministic coordination points.

Weak test:

```text
start two threads
hope they race
assert something
```

Strong test:

```text
T1 BEGIN RR
T1 SELECT

signal T2

T2 UPDATE
T2 COMMIT

signal T1

T1 SELECT
T1 UPDATE
T1 COMMIT
```

Use barriers/latches to control ordering.

Test at least:

- repeated reads;
- concurrent inserts matching predicates;
- concurrent updates to the same row;
- concurrent deletes;
- retry behavior;
- rollback behavior;
- connection release after failure;
- duplicate external-effect protection;
- transaction timeout behavior;
- retry exhaustion.

Your test suite should verify semantics, not merely code coverage.

# 59. Evidence-Driven Debugging Workflow

When production reports:

> “The application read inconsistent data.”

Do not immediately change the isolation level.

Investigate:

```text
1. What isolation level was actually active?
2. Did all statements use the same connection?
3. When did the transaction start?
4. When was the first query executed?
5. Were there concurrent writers?
6. Was the transaction blocked?
7. Was there a serialization failure?
8. Were retries happening?
9. Did the transaction call external services?
10. What was the exact business invariant?
```

Then reproduce the timeline.

Use:

```sql
SHOW transaction_isolation;
```

and inspect:

```sql
pg_stat_activity
pg_locks
```

plus application logs with transaction attempt identifiers.

Root cause first. Isolation-level change second.

# 62. Final Mental Model

Memorize this:

```text
REPEATABLE READ
        |
        v
one stable transaction snapshot
        |
        +--> repeated reads see the same snapshot-defined world
        |
        +--> later commits are not automatically visible
        |
        +--> PostgreSQL prevents ordinary phantom reads here
        |
        +--> serialization anomalies can still exist
        |
        +--> conflicting updates may cause serialization failure
        |
        +--> retries must replay the whole transaction
        |
        +--> long transactions can create operational pressure
        |
        +--> consistency does not imply freshness
```

The deepest principle is:

> **`REPEATABLE READ` trades a shifting statement view for a stable transaction snapshot. When concurrent writes cannot be reconciled with that snapshot, PostgreSQL prefers a transaction failure over silently producing a result from a mixed world.**

That is the foundation for understanding why `REPEATABLE READ` is both powerful and operationally demanding.
