# 2. The Central Mental Model

Pessimistic concurrency begins with one assumption:

> **Another transaction may touch the same logical resource while I am making my decision.**

Instead of detecting the collision after the fact, the transaction establishes ownership before performing the critical read-modify-write sequence.

```text
Without explicit pessimistic coordination

Read state
   |
   v
Think / decide
   |
   v
Write
   |
   v
Maybe discover conflict
```

Versus:

```text
Pessimistic concurrency

Acquire lock
   |
   v
Read protected state
   |
   v
Validate invariant
   |
   v
Write
   |
   v
Commit / release
```

The lock is therefore not the business operation. It is a **coordination boundary around the business operation**.

---

# 3. What Pessimistic Concurrency Means

## 3.1 Simple definition

Pessimistic concurrency assumes conflicts are sufficiently likely or sufficiently expensive that a transaction should acquire a lock before changing or depending on a shared resource.

## 3.2 Engineering definition

A pessimistic design makes a concurrent transaction wait, fail, or skip when it encounters ownership of a protected resource, so that one transaction can execute a critical section under controlled concurrency.

## 3.3 Expert definition

Pessimistic concurrency in PostgreSQL combines MVCC visibility with explicit or automatically acquired locks. The design is correct only when the locked resource, lock mode, lock duration, and isolation semantics jointly cover the invariant being protected. PostgreSQL's row locks coordinate writers and lockers rather than turning MVCC reads into a globally serial execution model. citeturn393051search0

---

# 4. Pessimistic Does Not Mean “No MVCC”

This is one of the most important distinctions in PostgreSQL.

PostgreSQL uses MVCC for visibility and locking for coordination.

```text
                    PostgreSQL concurrency

                +----------------------+
                |        MVCC          |
                | Who can see what?    |
                +----------------------+
                           +
                +----------------------+
                |       Locks          |
                | Who may modify /    |
                | lock the resource?  |
                +----------------------+
```

A transaction can read a row through MVCC without acquiring an exclusive row lock.

A locking read adds a coordination mechanism:

```sql
SELECT *
FROM inventory
WHERE id = $1
FOR UPDATE;
```

The statement both retrieves rows and requests row locks on the rows it returns. PostgreSQL documents that `FOR UPDATE` prevents other transactions from locking, modifying, or deleting the locked rows until the current transaction ends. citeturn393051search0

Therefore:

```text
MVCC -> visibility
Locking -> coordination
```

Keeping these concepts separate prevents many incorrect explanations of PostgreSQL concurrency.

# 5. Why Pessimistic Concurrency Exists

Consider an inventory reservation:

```text
available_quantity = 5
```

Two requests arrive at nearly the same time:

```text
Request A: reserve 4
Request B: reserve 4
```

Naive application logic:

```ts
const item = await db.query(
  'SELECT available_quantity FROM inventory WHERE id = $1',
  [id]
);

if (item.available_quantity >= quantity) {
  await db.query(
    'UPDATE inventory SET available_quantity = available_quantity - $1 WHERE id = $2',
    [quantity, id]
  );
}
```

Both requests may read `5` before either write completes.

That creates a classic race.

A pessimistic version is:

```sql
BEGIN;

SELECT available_quantity
FROM inventory
WHERE id = $1
FOR UPDATE;

-- validate availability

UPDATE inventory
SET available_quantity = available_quantity - $2
WHERE id = $1;

COMMIT;
```

Now one transaction owns the row while it performs the critical decision.

PostgreSQL's row-lock mechanism is explicitly designed for this type of application-controlled coordination when MVCC alone does not provide the desired behavior. citeturn393051search0

# 6. The Real Question: What Is the Critical Resource?

A common beginner question is:

> “Which row should I lock?”

The better question is:

> **“What shared resource represents the invariant I need to protect?”**

Examples:

```text
Inventory quantity
    -> inventory row

Single order state transition
    -> order row

Customer credit limit
    -> customer/account row or an explicitly designed coordination row

Unique business allocation
    -> allocation row / unique constraint / serializable predicate

Work queue item
    -> work-item row

Bank-like balance mutation
    -> account row + appropriate ledger design
```

A lock is only correct when it covers the resource whose concurrent modification could invalidate the decision.

# 7. Pessimistic Concurrency vs Optimistic Concurrency

These approaches solve the same broad class of concurrency problems differently.

## 7.1 Optimistic

Assume conflicts are uncommon.

```text
Read version 17
      |
      v
Perform work
      |
      v
UPDATE ... WHERE id = ? AND version = 17
      |
      +--> row_count = 1 -> success
      |
      +--> row_count = 0 -> conflict
```

## 7.2 Pessimistic

Assume conflicts must be coordinated before work proceeds.

```text
SELECT ... FOR UPDATE
      |
      +--> lock acquired -> continue
      |
      +--> lock held -> wait/fail/skip
```

## 7.3 Practical comparison

| Dimension | Optimistic | Pessimistic |
|---|---|---|
| Conflict assumption | Rare | Material / expensive |
| Normal behavior | No waiting for ownership | May wait for ownership |
| Conflict discovery | At write/commit check | Before critical section proceeds |
| Typical primitive | Version predicate | Row/table/advisory lock |
| Throughput with low contention | Often excellent | Often also good, but adds coordination |
| Behavior under hot-row contention | Many failed attempts possible | Queueing/waiting possible |
| User-visible conflict | Natural | Often hidden behind wait unless `NOWAIT`/timeout used |
| Main failure risk | Stale writes | Blocking/deadlock/lock amplification |

Neither is universally superior.

# 8. The Four Row-Level Lock Modes

PostgreSQL provides four row-level lock modes. Their practical strength order is:

```text
FOR KEY SHARE
       |
FOR SHARE
       |
FOR NO KEY UPDATE
       |
FOR UPDATE
```

But “strongest is best” is the wrong design rule.

PostgreSQL documents these semantics: `FOR UPDATE` conflicts with all four row-lock modes; `FOR NO KEY UPDATE` is weaker and does not block `FOR KEY SHARE`; `FOR SHARE` is shared; `FOR KEY SHARE` is the weakest and mainly protects key identity from deletion or key-changing updates. citeturn393051search0

Use the least restrictive lock that actually protects the invariant.

---

# 9. `FOR UPDATE`

Typical form:

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;
```

It means, conceptually:

> “Lock the selected rows as though they are about to be updated, and keep that protection through the transaction.”

PostgreSQL states that another transaction attempting `UPDATE`, `DELETE`, or a conflicting locking read on the same row will be blocked until the current transaction ends. citeturn393051search0

This is appropriate for workflows like:

```text
read current order
check state
transition state
record side effects
commit
```

---

# 10. `FOR NO KEY UPDATE`

```sql
SELECT *
FROM customers
WHERE id = $1
FOR NO KEY UPDATE;
```

This is weaker than `FOR UPDATE`.

PostgreSQL uses this mode automatically for many ordinary updates that do not modify key columns considered relevant to foreign-key enforcement. It does not conflict with `FOR KEY SHARE`. citeturn393051search0

This matters when designing concurrent parent/child operations. Overusing `FOR UPDATE` can create unnecessary blocking.

---

# 11. `FOR SHARE`

```sql
SELECT *
FROM products
WHERE id = $1
FOR SHARE;
```

A shared row lock protects a row from writers that require incompatible row locks while allowing other shared/key-share readers.

It is useful when the transaction needs to assert that a row remains structurally available during a coordinated operation but does not intend to take exclusive modification ownership.

Do not reach for it merely because “read” sounds like a shared lock. Ordinary MVCC reads do not need explicit row locking.

---

# 12. `FOR KEY SHARE`

`FOR KEY SHARE` is specialized for protecting key relationships.

```sql
SELECT id
FROM customers
WHERE id = $1
FOR KEY SHARE;
```

It blocks deletion and updates that change key values, but is weaker than `FOR SHARE` and does not conflict with normal non-key updates. PostgreSQL documents this distinction specifically because foreign-key relationships depend on key stability. citeturn393051search0

---

# 13. Lock Lifetime Is Part of Correctness

A row lock is normally held until transaction end.

```text
BEGIN
  |
  +-- acquire lock
  |
  +-- application work
  |
  +-- UPDATE
  |
  +-- COMMIT
          |
          +--> lock released
```

PostgreSQL also releases locks acquired after a savepoint when rolling back to that savepoint. citeturn393051search0

This makes transaction duration a concurrency design parameter.

A five-line SQL transaction that takes 100 ms is very different from a transaction that holds the same lock while waiting 10 seconds for an external API.

# 14. The Most Dangerous Pessimistic Pattern

```ts
await client.query('BEGIN');
await client.query(
  'SELECT * FROM orders WHERE id = $1 FOR UPDATE',
  [orderId]
);

await callPaymentProvider();
await callShippingProvider();
await callSomeOtherService();

await client.query('UPDATE orders SET status = $1 WHERE id = $2', [status, orderId]);
await client.query('COMMIT');
```

The row remains locked during remote network calls.

Consequences can include:

```text
Long lock lifetime
      ↓
More waiters
      ↓
More application connections blocked
      ↓
Higher tail latency
      ↓
Pool pressure
      ↓
Timeouts
      ↓
Retry amplification
```

The usual design improvement is to keep the critical section database-local whenever possible:

```text
Phase A
Acquire + validate + mutate durable DB state

        ↓

Commit

        ↓

Phase B
Perform external action using durable intent/outbox
```

Pessimistic locking should coordinate the database invariant, not turn PostgreSQL into a mutex around an unreliable network.

# 15. Pessimistic Concurrency and Atomic SQL

A crucial design question is:

> “Do I actually need a lock, or can the invariant be encoded in one atomic statement?”

Example:

```sql
UPDATE inventory
SET available_quantity = available_quantity - $1
WHERE id = $2
  AND available_quantity >= $1
RETURNING id, available_quantity;
```

This can be superior to:

```text
SELECT ... FOR UPDATE
check in application
UPDATE ...
```

because the predicate and mutation are fused into one statement.

The result itself becomes the concurrency signal:

```text
1 row returned -> reservation succeeded
0 rows -> invariant condition failed
```

This reduces lock duration and application round trips.

Therefore:

```text
Explicit lock
    is not
    automatically better than
atomic SQL
```

The correct primitive depends on the invariant.

---

# 16. Naive Approach → Improved Approach

## Naive Approach

```text
SELECT row
↓
check status
↓
UPDATE row
```

### Why It Fails

The gap between the read and the write permits another transaction to change the protected state.

### Improved Approach A — Lock

```sql
BEGIN;

SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;

-- validate in transaction

UPDATE orders
SET status = 'CONFIRMED'
WHERE id = $1;

COMMIT;
```

### Improved Approach B — Atomic transition

```sql
UPDATE orders
SET status = 'CONFIRMED'
WHERE id = $1
  AND status = 'PENDING'
RETURNING id;
```

### Improved Approach C — Serializable

Use `SERIALIZABLE` when the invariant spans a read/write dependency pattern that is not safely protected by a narrower lock or atomic statement.

### Production Decision

```text
Single-row state transition?
    -> atomic conditional UPDATE may be best

Read several attributes, calculate decision, then mutate same row?
    -> FOR UPDATE may be appropriate

Cross-row invariant?
    -> atomic constraint / lock design / SERIALIZABLE depending on invariant
```

# 17. `FOR UPDATE` Does Not Magically Protect a Business Rule

Suppose the rule is:

> “Only one active reservation may exist for each product and customer.”

Locking one existing reservation row does not protect against another transaction inserting a new reservation row.

You must lock or constrain the **actual conflict set**.

Possible solutions include:

```text
UNIQUE constraint
partial unique index
coordination row
advisory lock
SERIALIZABLE transaction
```

A lock is not a substitute for a schema constraint when a uniqueness invariant can be directly represented in the schema.

# 18. Pessimistic Concurrency at Different Isolation Levels

## `READ COMMITTED`

A locking read can wait for a concurrent transaction and then lock the current version after the conflict resolves. PostgreSQL documents that `FOR UPDATE` under `READ COMMITTED` can wait and then return the updated row if the row still matches the query condition. citeturn393051search0

## `REPEATABLE READ`

The snapshot is fixed. If a row targeted by a locking read has changed since the transaction started, PostgreSQL can raise a serialization failure rather than moving the snapshot forward. citeturn393051search0turn393051search1

## `SERIALIZABLE`

Locking is still useful for explicit coordination, but serializable conflict detection also tracks dependencies that explicit row locks alone cannot fully model.

Therefore:

```text
Pessimistic locking != isolation level

Locking is a coordination primitive.
Isolation is a transaction-wide visibility/conflict guarantee.
```

---

# 19. `NOWAIT`

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE NOWAIT;
```

Instead of waiting for a conflicting lock, the statement fails immediately.

This is useful when waiting itself is undesirable:

```text
Interactive command
Administrative operation
Fast-fail API
Short lease acquisition
Explicit ownership check
```

The caller can convert lock contention into an application-level response such as:

```text
409 Conflict
423 Locked
retry later
show current state
```

Do not silently classify every `NOWAIT` failure as a server error. Contention can be an expected domain outcome.

---

# 20. `SKIP LOCKED`

```sql
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

Instead of waiting for locked rows, PostgreSQL skips them.

This is especially useful for concurrent queue consumers.

But the semantics are deliberately weaker:

> The result is not a complete statement-level view of all eligible rows.

Therefore:

```text
NOWAIT
-> fail if resource unavailable

SKIP LOCKED
-> choose another resource

ordinary locking read
-> wait
```

PostgreSQL explicitly documents `SKIP LOCKED` as useful for multiple consumers accessing a queue-like table. citeturn393051search6

# 21. Pessimistic Queue Design

A robust PostgreSQL queue often uses a claim transaction:

```sql
BEGIN;

WITH next_jobs AS (
  SELECT id
  FROM work_items
  WHERE status = 'READY'
    AND available_at <= now()
  ORDER BY priority DESC, id
  FOR UPDATE SKIP LOCKED
  LIMIT 20
)
UPDATE work_items w
SET status = 'CLAIMED',
    claimed_at = now(),
    claimed_by = $1
FROM next_jobs j
WHERE w.id = j.id
RETURNING w.*;

COMMIT;
```

The critical idea is that the transaction claims ownership quickly and commits.

Actual work can then happen outside the lock.

```text
claim
  ↓
commit
  ↓
process
  ↓
ack / complete
```

Crash recovery should be explicit through leases, retry counts, visibility timeouts, or durable state transitions.

# 22. Pessimistic Locking and Deadlocks

Suppose:

```text
Transaction A:
lock row 1
lock row 2

Transaction B:
lock row 2
lock row 1
```

This is a circular wait.

The solution is not “use stronger locks.”

The solution is:

```text
Canonical order:
row 1 -> row 2
```

Both transactions follow the same order.

PostgreSQL automatically detects deadlocks and aborts one transaction. The PostgreSQL documentation recommends consistent acquisition order when multiple objects are involved. citeturn393051search0

---

# 23. Multi-Row Pessimistic Locking

Suppose an inventory transfer moves quantity from A to B.

Incorrect:

```sql
SELECT * FROM inventory WHERE id = $1 FOR UPDATE;
SELECT * FROM inventory WHERE id = $2 FOR UPDATE;
```

if another code path does the inverse order.

Safer:

```sql
SELECT id, available_quantity
FROM inventory
WHERE id IN ($1, $2)
ORDER BY id
FOR UPDATE;
```

The application can then process both rows in deterministic order.

However, do not assume `ORDER BY` alone is a universal proof of lock acquisition order for every query plan and every hidden dependency. The design must be validated against the full workload, joins, triggers, foreign keys, and other code paths.

---

# 24. Lock Scope with Joins

When joining tables, specify which relation should be locked when necessary.

Example:

```sql
SELECT o.id,
       c.id AS customer_id
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.id = $1
FOR UPDATE OF o;
```

This communicates an important intent:

```text
Lock order row
Do not unnecessarily lock customer row
```

A broad locking clause can enlarge the contention set and increase the probability of deadlocks.

Design locking scope explicitly.

# 25. Pessimistic Locking and Foreign Keys

Foreign-key enforcement can involve key-share semantics and transaction-ID waits.

This means a transaction may block even when your application code did not explicitly call `FOR UPDATE`.

Example mental model:

```text
Parent key
   ↑
Foreign-key relationship
   ↑
Child insert/update
```

PostgreSQL documents `FOR KEY SHARE` specifically around protection of key values relevant to referential integrity. citeturn393051search0

Therefore production lock analysis must include database-generated lock dependencies, not only explicit application locks.

---

# 26. Pessimistic Concurrency and `UPDATE`

Remember that ordinary updates already participate in row locking.

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = $1;
```

PostgreSQL acquires appropriate row-level locking during the update. citeturn393051search0

This is why many concurrency bugs are not solved by simply adding `FOR UPDATE` everywhere.

Often the actual problem is the separation of:

```text
read
+
application decision
+
write
```

rather than the absence of low-level row locking itself.

---

# 27. Pessimistic Concurrency and Long Transactions

Long transactions create a multiplicative problem:

```text
transaction duration
        ×
lock conflict rate
        ×
number of concurrent workers
```

As the transaction remains open, more transactions may queue behind it.

PostgreSQL explicitly warns that applications should avoid keeping transactions open for long periods, because lock requests can wait indefinitely absent a deadlock. citeturn393051search0

A common production anti-pattern is:

```text
BEGIN
FOR UPDATE
wait for user input
wait for HTTP request
wait for message
wait for file
COMMIT
```

Never use an open database transaction as a human-scale session lock.

---

# 28. Connection Pool Amplification

Suppose the application has 100 connections.

One transaction holds a hot row for 5 seconds.

Soon many other requests are waiting.

Even if PostgreSQL itself is healthy, application-visible capacity can collapse:

```text
1 hot lock
  ↓
20 waiting transactions
  ↓
20 occupied pool connections
  ↓
new requests cannot acquire connections
  ↓
request queue grows
```

This is why database lock incidents can look like:

```text
API latency problem
connection pool problem
CPU problem
```

when the root cause is actually lock contention.

# 29. Node.js / NestJS Transaction Affinity

A transaction belongs to one PostgreSQL session/connection.

Therefore this is conceptually dangerous:

```ts
await dataSource.transaction(async () => {
  await repository.findOne(...); // transaction connection
  await repository.findOne(...); // accidentally another connection
});
```

depending on the ORM and configuration.

The safe requirement is:

```text
BEGIN
  ↓
Every statement in critical section
  ↓
uses the same transaction-bound client
  ↓
COMMIT / ROLLBACK
```

With node-postgres:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  await client.query(
    'SELECT * FROM inventory WHERE id = $1 FOR UPDATE',
    [inventoryId],
  );

  await client.query(
    `UPDATE inventory
     SET available_quantity = available_quantity - $1
     WHERE id = $2`,
    [quantity, inventoryId],
  );

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

Never release the transaction connection midway and then assume a new connection is still inside the transaction.

# 30. External Side Effects

A pessimistic transaction creates an important boundary:

```text
Database lock
      |
      v
Database mutation
      |
      v
COMMIT
```

An external service cannot participate in the same PostgreSQL transaction merely because you called it inside the callback.

Therefore this is unsafe:

```text
BEGIN
lock order
call payment API
payment succeeds
DB transaction rolls back
```

Now the payment may exist without the intended database state.

A safer architecture is:

```text
Transaction
    |
    +-- lock/validate/mutate durable state
    +-- create outbox event
    +-- COMMIT
             |
             v
        worker processes outbox
             |
             v
        external API
```

Pessimistic locking protects the local database invariant. The outbox protects the local-to-external handoff.

# 31. Security Considerations

Locks can become an availability attack surface.

If an attacker can trigger expensive transactions that lock hot rows, they may intentionally increase:

```text
lock hold time
waiting transactions
connection utilization
CPU spent scheduling/waking waiters
request latency
```

Security controls should therefore include:

- authenticated and authorized mutation paths;
- bounded transaction sizes;
- statement and lock timeouts where appropriate;
- rate limits on highly contended operations;
- protection against unbounded batch sizes;
- observability for repeated lock contention;
- careful handling of multi-tenant hot resources.

A lock is a concurrency tool, but in production it is also part of the availability boundary.

# 32. Observability

Start with:

```sql
SELECT
  pid,
  usename,
  application_name,
  state,
  wait_event_type,
  wait_event,
  xact_start,
  query_start,
  query
FROM pg_stat_activity
WHERE datname = current_database();
```

Then inspect locks:

```sql
SELECT
  pid,
  locktype,
  mode,
  granted,
  relation::regclass AS relation,
  page,
  tuple,
  virtualxid,
  transactionid
FROM pg_locks
ORDER BY granted, pid;
```

Find blockers:

```sql
SELECT
  pid,
  pg_blocking_pids(pid) AS blocking_pids,
  wait_event_type,
  wait_event,
  query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

PostgreSQL documents `pg_locks` as the system view for outstanding locks and explains that some row-level waits are represented through transaction-level mechanisms rather than as a simple row-lock entry. citeturn393051search0turn393051search4

# 33. Lock Forensics Workflow

Use evidence, not intuition.

```text
Symptom
  ↓
Which requests are slow?
  ↓
Which sessions are waiting?
  ↓
What are they waiting on?
  ↓
Who is blocking them?
  ↓
What transaction owns the blocking resource?
  ↓
How long has it been open?
  ↓
What SQL acquired the lock?
  ↓
Why is that SQL holding it this long?
  ↓
Why does the business workflow require the critical section?
```

Never stop at:

> “There is a lock.”

The real diagnosis is:

> “Transaction A holds resource X because workflow Y entered a critical section at time T, transaction B has been waiting since time U, and the lock lifetime is longer than intended because of Z.”

# 34. Lock Timeouts Are Different from `NOWAIT`

`NOWAIT` means:

```text
Attempt lock
  ↓
If unavailable -> fail immediately
```

`lock_timeout` means:

```text
Attempt lock
  ↓
Wait up to configured duration
  ↓
If still blocked -> error
```

This difference is useful when an application can tolerate a small amount of waiting but must never become indefinitely blocked.

Example:

```sql
SET LOCAL lock_timeout = '750ms';

SELECT *
FROM inventory
WHERE id = $1
FOR UPDATE;
```

Use `SET LOCAL` when the policy should apply only within the current transaction.

---

# 35. Deadlocks Are a Separate Failure Class

A blocked transaction may simply be waiting.

A deadlock means:

```text
T1 -> waits for T2
T2 -> waits for T1
```

PostgreSQL automatically detects deadlocks and aborts one transaction. citeturn393051search0

Application behavior should distinguish:

```text
lock timeout
NOWAIT failure
statement timeout
deadlock detected
serialization failure
business conflict
```

Do not retry every database error using one generic catch block.

---

# 36. Retry Strategy for Pessimistic Workflows

Some pessimistic operations should retry; others should fail fast.

## Good retry candidates

Transient:

```text
deadlock
serialization failure
short-lived lock timeout
```

when the operation is safe to repeat.

## Poor retry candidates

Permanent:

```text
permission denied
foreign-key violation
invalid state transition
validation failure
unique violation caused by an expected business conflict
```

The correct retry unit is the whole logical transaction attempt.

```text
attempt 1
  ↓
BEGIN
  ↓
lock
  ↓
validate
  ↓
mutate
  ↓
COMMIT
  ↓
failure
  ↓
ROLLBACK / connection cleanup
  ↓
attempt 2
```

Never retry only the final `UPDATE` if the decision depended on an earlier snapshot and lock acquisition.

---

# 37. Idempotency

Retries become safe only when the business operation is idempotent or otherwise protected from duplication.

Example:

```text
POST /orders/123/confirm
```

If the operation is retried after a deadlock, the application must not accidentally create two payments or two external shipments.

Use an idempotency key or durable operation identifier:

```text
request_id
operation_id
payment_attempt_id
```

Pessimistic locking does not solve distributed duplicate side effects.

---

# 38. Hot Rows

A row that many requests must lock becomes a serialization point.

Example:

```text
customers
id = 42
balance = ...
```

If every operation for customer 42 requires:

```sql
SELECT *
FROM customers
WHERE id = 42
FOR UPDATE;
```

then concurrency on that customer is intentionally serialized.

That may be correct.

But if a “global settings” row is locked by every request, the same design can destroy throughput.

Ask:

```text
Is the serialization point required by the business invariant?
```

If not, redesign it.

# 39. Lock Amplification

One business operation can accidentally lock many database resources.

Example:

```sql
SELECT o.*, c.*, p.*
FROM orders o
JOIN customers c ON ...
JOIN payments p ON ...
WHERE o.id = $1
FOR UPDATE;
```

Without deliberate scope, the critical section may be broader than intended.

Better:

```sql
SELECT o.*
FROM orders o
WHERE o.id = $1
FOR UPDATE;
```

Then fetch immutable/reference data separately when safe.

The goal is:

```text
minimum lock footprint
+
minimum lock duration
```

subject to correctness.

# 40. Pessimistic Concurrency for Order State Machines

Suppose an order can move:

```text
PENDING
  -> CONFIRMED
  -> PACKED
  -> SHIPPED
  -> DELIVERED
```

Two workers both see `CONFIRMED` and try to pack it.

A pessimistic design:

```sql
BEGIN;

SELECT status
FROM orders
WHERE id = $1
FOR UPDATE;

-- validate status = CONFIRMED

UPDATE orders
SET status = 'PACKED'
WHERE id = $1;

COMMIT;
```

An atomic design may be simpler:

```sql
UPDATE orders
SET status = 'PACKED'
WHERE id = $1
  AND status = 'CONFIRMED'
RETURNING id;
```

The second version may eliminate an explicit lock completely for a simple one-row transition.

This is a recurring architectural principle:

> **Use pessimistic locking when the critical section genuinely requires reading protected state before deciding; use a single atomic state transition when the invariant can be encoded directly in the write predicate.**

# 41. Pessimistic Inventory Reservation

Suppose:

```text
Inventory SKU-X = 12
```

Request A reserves 8.
Request B reserves 7.

Pessimistic implementation:

```sql
BEGIN;

SELECT available_quantity
FROM inventory
WHERE sku = $1
FOR UPDATE;

-- if quantity >= requested

UPDATE inventory
SET available_quantity = available_quantity - $2
WHERE sku = $1;

INSERT INTO reservations (...);

COMMIT;
```

Now only one transaction at a time can make the decision for that inventory row.

But the best design may instead be:

```sql
UPDATE inventory
SET available_quantity = available_quantity - $2
WHERE sku = $1
  AND available_quantity >= $2
RETURNING available_quantity;
```

Then insert the reservation in the same transaction.

This is often more compact and reduces one read round trip.

# 42. Pessimistic Financial Mutation

For a balance-like resource:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = $1
FOR UPDATE;

-- validate funds

UPDATE accounts
SET balance = balance - $2
WHERE id = $1;

INSERT INTO ledger_entries (...);

COMMIT;
```

But a production financial system should not rely on a mutable balance alone as its complete source of truth.

A robust model often separates:

```text
immutable ledger
+
transactional balance/cache
+
constraints
+
reconciliation
+
audit trail
```

The pessimistic lock protects the atomic business operation; it does not replace ledger correctness.

# 43. Pessimistic Multi-Tenant Design

Consider a shared database with:

```text
tenant_id
```

If all tenants update one global row, they contend unnecessarily.

Better coordination often scopes the resource to the tenant:

```text
Tenant A counter row
Tenant B counter row
Tenant C counter row
```

Now unrelated tenants can proceed independently.

This is a concurrency form of partitioning the critical resource.

The objective is not merely:

> “Use row locks.”

It is:

> **Make unrelated workloads contend on unrelated coordination objects.**

# 44. Node.js Anti-Pattern: Transaction Helper Hides the Lock

An ORM helper may expose:

```ts
await repository.findOne(...);
```

and another API:

```ts
await repository.findOne(..., { lock: ... });
```

The dangerous mistake is assuming the lock is present because the code is inside a transaction.

Being inside a transaction does not imply that a read acquired the exact row lock your invariant requires.

Always verify the generated SQL or ORM documentation.

AI-generated code frequently makes this mistake because it treats:

```text
transaction != lock
```

as though they were equivalent.

They are not.

# 45. Vibe-Coding Mistakes

## Mistake 1 — Add `FOR UPDATE` everywhere

Why it looks safe:

> “Locks prevent races.”

Why it fails:

- broad contention;
- unnecessary waits;
- deadlock risk;
- poor throughput;
- hidden coupling.

Better:

```text
identify invariant
→ identify conflict set
→ choose narrowest correct primitive
```

## Mistake 2 — Hold locks across HTTP calls

Why it looks reasonable:

> “I need the database state to remain unchanged until the API call finishes.”

Why it fails:

- long lock lifetime;
- pool exhaustion;
- external dependency becomes DB bottleneck.

Better:

Persist durable intent, commit, then perform external work.

## Mistake 3 — Retry every lock error

Why it looks resilient:

> “Transient database error means retry.”

Why it fails:

Some lock failures are expected business conflicts, permanent failures, or symptoms of architectural contention.

## Mistake 4 — Lock one row to protect an insert race

Why it looks intuitive:

> “I locked the existing row.”

Why it fails:

There may be no existing row representing the conflicting state.

Better:

constraint, coordination row, predicate protection, or serializable design.

## Mistake 5 — Use the strongest lock by default

Why it looks safe:

```text
FOR UPDATE
```

Why it fails:

Stronger locks increase the conflict set.

# 46. Performance Analysis

Pessimistic concurrency changes performance characteristics in a distinctive way.

## Low contention

```text
lock acquisition
≈ inexpensive coordination
```

## Moderate contention

```text
short waits
→ manageable queueing
```

## High contention

```text
queue depth ↑
latency ↑
connection usage ↑
tail latency ↑
timeouts ↑
retries ↑
```

The important metric is often not CPU.

A database can show:

```text
CPU = 30%
IO = moderate
```

while application latency is enormous because sessions are waiting on locks.

Analyze wait events and blocked duration.

# 47. Throughput vs Serialization

A pessimistic hot row effectively creates:

```text
N concurrent requests
        |
        v
one serialized resource
        |
        v
roughly one critical section at a time
```

If each critical section takes 100 ms, the resource cannot magically process hundreds of successful serialized mutations per second just because the server has many CPU cores.

This is why high-contention systems sometimes need architectural decomposition:

```text
one global counter
   ↓
sharded counters
   ↓
periodic reconciliation
```

but only when the business semantics allow that change.

Correctness still comes first.

# 48. `EXPLAIN` and Locking Queries

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
FOR UPDATE;
```

when diagnosing how many rows are scanned before the locking operation reaches its targets.

A poorly selective predicate can expand the number of rows that must be considered and potentially locked.

For a queue:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM work_items
WHERE status = 'READY'
ORDER BY priority DESC, id
FOR UPDATE SKIP LOCKED
LIMIT 20;
```

The query plan still matters.

A locking clause does not make an inefficient access path efficient.

PostgreSQL documentation also notes that large updates can increase lock contention, bloat, and replica lag, so batching can be useful in high-impact workloads. citeturn393051search6

# 49. Locking and Disk Writes

A surprising detail is that locking rows can itself involve disk writes.

PostgreSQL documents that `SELECT FOR UPDATE` modifies selected rows to mark them locked and therefore can result in disk writes. citeturn393051search0

This means a locking read is not necessarily equivalent in cost to a normal read.

Consequences:

```text
locking reads
   ↓
possible tuple/page changes
   ↓
WAL / buffer activity
   ↓
additional I/O
```

Do not benchmark pessimistic locking using only logical query time in an unloaded environment.

Measure the workload under realistic concurrency.

# 50. Production Failure Scenario — Jewellery ERP Stock Reservation

Imagine a jewellery ERP with:

```text
branch_id
product_id
available_weight
available_pieces
```

Two sales terminals reserve the same stock.

The dangerous approach is:

```text
SELECT available stock
→ calculate remaining stock in Node.js
→ call pricing service
→ UPDATE
```

A better database boundary is:

```text
BEGIN
  ↓
lock exact inventory row
  ↓
validate quantity/weight
  ↓
create reservation + mutation
  ↓
append audit/outbox record
  ↓
COMMIT
```

Even better, where the rule fits, use an atomic conditional mutation:

```sql
UPDATE inventory
SET available_weight = available_weight - $1,
    available_pieces = available_pieces - $2
WHERE branch_id = $3
  AND product_id = $4
  AND available_weight >= $1
  AND available_pieces >= $2
RETURNING *;
```

This design makes the database itself the arbiter of the mutation condition.

# 51. Production Failure Scenario — Order Double Processing

Suppose two workers receive the same order-processing message.

Naive:

```text
SELECT order WHERE status = PENDING
process
UPDATE status = COMPLETE
```

Both workers can process it.

Pessimistic claim:

```sql
BEGIN;

SELECT id
FROM orders
WHERE id = $1
  AND status = 'PENDING'
FOR UPDATE;

UPDATE orders
SET status = 'PROCESSING'
WHERE id = $1;

COMMIT;
```

Then processing happens outside the lock.

Completion is a second durable state transition.

This is safer than holding a row lock throughout the entire business workflow.

# 52. Pessimistic Concurrency and State Leases

For long-running work, use a lease instead of a long transaction.

Example fields:

```text
status
claimed_by
claimed_at
lease_until
attempt_count
```

Claim transaction:

```sql
UPDATE work_items
SET status = 'CLAIMED',
    claimed_by = $1,
    claimed_at = now(),
    lease_until = now() + interval '2 minutes'
WHERE id = $2
  AND status = 'READY'
RETURNING *;
```

Recovery:

```sql
UPDATE work_items
SET status = 'READY',
    claimed_by = NULL,
    lease_until = NULL
WHERE status = 'CLAIMED'
  AND lease_until < now();
```

The database lock protects the short claim operation; the lease protects work ownership across long-running processing.

# 53. Pessimistic Concurrency vs Advisory Locks

Row locks:

```text
attached to database row state
```

Advisory locks:

```text
application-defined logical key
```

Use row locks when the protected resource is naturally represented by a row.

Use advisory locks when the resource exists logically but has no suitable row representation.

Example:

```text
branch closing process
tenant-wide settlement job
one-time migration coordinator
external-resource synchronization
```

But advisory locks introduce their own design and observability considerations. They should not replace a real constraint or row-level lock when the actual invariant already belongs to schema data.

---

# 54. Pessimistic Concurrency vs `SERIALIZABLE`

These are complementary, not competing categories.

Pessimistic locking says:

> “I know the resource I need to coordinate; lock it.”

`SERIALIZABLE` says:

> “Preserve a result equivalent to some serial execution, and abort transactions when concurrent dependencies cannot safely be serialized.”

Use explicit locks when the conflict set is narrow and known.

Use serializable isolation when the invariant is broader or dynamic and explicit locking would be brittle or incomplete.

Example:

```text
Known account row
→ FOR UPDATE

Unknown set of rows satisfying a dynamic predicate
→ consider SERIALIZABLE
```

The exact architecture depends on the invariant.

# 55. Pessimistic Concurrency Decision Framework

Use this sequence:

```text
1. What invariant is being protected?
        |
        v
2. Can a schema constraint express it?
        |
        +--> yes -> prefer constraint
        |
        v
3. Can one atomic SQL statement express it?
        |
        +--> yes -> prefer atomic statement
        |
        v
4. Is there a small, explicit resource to serialize?
        |
        +--> yes -> consider row/table/advisory lock
        |
        v
5. Is the resource frequently contested?
        |
        +--> yes -> analyze wait cost / optimistic alternative
        |
        v
6. Is the invariant a broader read/write dependency?
        |
        +--> yes -> consider SERIALIZABLE
        |
        v
7. Can the critical section remain short and DB-local?
        |
        +--> no -> redesign workflow
```

This is much more reliable than:

> “Use `FOR UPDATE` because concurrency is dangerous.”

Do not merely increase timeouts.

# 58. Common Developer Mistakes

## Mistake — Transaction without lock

A transaction gives atomic commit/rollback but does not automatically serialize every read-modify-write operation.

## Mistake — Lock without transaction boundary

Locks are normally released at transaction end. A lock without an appropriately scoped transaction may not protect the intended workflow.

## Mistake — Wrong row

Locking an unrelated row provides no protection for the actual invariant.

## Mistake — Broad lock

Locking an entire table when one row is sufficient increases contention.

## Mistake — Long transaction

External I/O while holding a hot lock turns a database lock into a system-wide latency amplifier.

## Mistake — No retry classification

Deadlocks, serialization failures, lock timeouts, and domain conflicts are different events.

# 59. Interview Questions

## Junior

### Q1. What is pessimistic concurrency?

**Weak answer:** It uses locks.

**Acceptable answer:** It assumes conflicts may happen and coordinates them by acquiring locks before the critical operation.

**Strong answer:** It is a concurrency-control strategy where transactions explicitly establish ownership or exclusion before performing a critical read-modify-write sequence, trading some parallelism for deterministic conflict coordination.

**Expert answer:** It combines PostgreSQL's MVCC visibility model with a deliberately chosen lock boundary; correctness depends on identifying the true conflict set, choosing the correct lock mode, controlling lifetime, and handling waits/deadlocks without confusing locking with transaction isolation.

### Q2. Does PostgreSQL locking disable MVCC?

No. Visibility and locking are separate mechanisms.

---

## Mid-Level

### Q3. When would you prefer an atomic `UPDATE` over `SELECT FOR UPDATE`?

When the business condition and mutation can be safely expressed in one SQL statement, especially for one-row counters, state transitions, or conditional inventory changes.

### Q4. What is the difference between `FOR UPDATE`, `NOWAIT`, and `SKIP LOCKED`?

```text
FOR UPDATE -> wait for conflicting lock
NOWAIT     -> fail immediately
SKIP LOCKED -> ignore locked candidates
```

---

## Senior

### Q5. Why can `FOR UPDATE` reduce throughput dramatically?

Because it serializes access to the locked resource and can create queues. Under high contention, those queues consume connection capacity and increase tail latency.

### Q6. Why can adding `FOR UPDATE` still fail to protect an invariant?

Because the wrong resource may be locked, the conflicting state may not yet have a row, the invariant may span multiple rows, or another code path may not follow the same coordination protocol.

---

## Staff / Principal

### Q7. How do you choose between optimistic and pessimistic concurrency for a hot resource?

Analyze:

```text
conflict frequency
critical-section duration
retry cost
user-visible conflict cost
hot-key distribution
throughput requirement
fairness requirement
failure semantics
```

There is no universal winner.

### Q8. How would you redesign a transaction that holds a row lock while calling a payment provider?

Split durable local state transition from external side effect using an outbox/idempotency architecture.

# 63. Production Readiness Checklist

Before shipping a pessimistic concurrency workflow, verify:

### Correctness

- [ ] The invariant is explicitly documented.
- [ ] The true conflict set has been identified.
- [ ] The chosen lock mode is sufficient but not unnecessarily strong.
- [ ] Every code path that can mutate the resource follows the coordination protocol.
- [ ] Schema constraints exist where they can express the invariant directly.
- [ ] Multi-row resources use canonical ordering.

### Transaction design

- [ ] One transaction-bound connection is used throughout.
- [ ] The transaction is short.
- [ ] No human input occurs inside the transaction.
- [ ] External HTTP/RPC calls are not performed while holding hot locks.
- [ ] Commit/rollback behavior is explicit.

### Failure handling

- [ ] Deadlocks are classified separately.
- [ ] Serialization failures are classified separately.
- [ ] Lock timeouts have bounded retry policy.
- [ ] Retries repeat the whole logical transaction attempt.
- [ ] Operations are idempotent where retries can occur.

### Performance

- [ ] Lock footprint has been measured.
- [ ] Lock wait time is observable.
- [ ] Hot rows have been identified.
- [ ] Query plans are appropriate.
- [ ] Batch sizes are bounded.
- [ ] Connection-pool impact has been tested.

### Observability

- [ ] `pg_stat_activity` is available.
- [ ] `pg_locks` is queryable by operators.
- [ ] Blocking sessions can be identified.
- [ ] Transaction age is monitored.
- [ ] Application traces correlate database operations with business requests.

### Operational resilience

- [ ] Crash recovery has been tested.
- [ ] Stale work/leases have recovery logic where needed.
- [ ] Deployment behavior has been tested.
- [ ] Load tests include hot-key contention.
- [ ] Failure tests include deadlocks and lock timeouts.

# 64. The Pessimistic Concurrency Decision Matrix

| Situation | Preferred starting point |
|---|---|
| Simple unique invariant | Constraint / unique index |
| Single-row conditional mutation | Atomic `UPDATE ... WHERE ...` |
| Read protected row, calculate, then mutate | `FOR UPDATE` or appropriate row lock |
| Need fail-fast ownership | `NOWAIT` |
| Need concurrent queue consumers | `SKIP LOCKED` |
| Logical resource without a row | Advisory lock |
| Broad read/write dependency | `SERIALIZABLE` |
| Low-conflict stale-write detection | Optimistic versioning |
| Long-running work | Durable claim/lease, not long DB lock |

This table is a starting point, not a substitute for invariant analysis.

# 65. Final Mental Model

A production-grade pessimistic concurrency design can be reduced to:

```text
Business invariant
       |
       v
Identify shared resource
       |
       v
Choose smallest correct synchronization primitive
       |
       +--> constraint
       +--> atomic SQL
       +--> row lock
       +--> table lock
       +--> advisory lock
       +--> SERIALIZABLE
       |
       v
Acquire at the correct time
       |
       v
Keep critical section short
       |
       v
Commit durable state
       |
       v
Release coordination boundary
       |
       v
Handle retry/failure/idempotency
       |
       v
Measure contention in production
```

The expert habit is not:

> “Use locks.”

It is:

> **“Identify the invariant, identify the conflict set, choose the smallest correct coordination mechanism, keep its lifetime bounded, and verify the behavior under realistic concurrency.”**

# 66. Key Takeaways

1. Pessimistic concurrency assumes collisions are important enough to coordinate before the critical operation proceeds.
2. PostgreSQL's pessimistic locking works alongside MVCC; it does not replace MVCC.
3. `FOR UPDATE` is a coordination primitive, not a general-purpose consistency guarantee.
4. The correct lock is the one that protects the actual invariant with the smallest practical conflict set.
5. Atomic SQL can often eliminate the need for an explicit locking read.
6. `NOWAIT` converts contention into an immediate application decision.
7. `SKIP LOCKED` converts contention into work selection and intentionally sacrifices completeness.
8. Locks are normally held until transaction end, so transaction duration is a concurrency parameter. citeturn393051search0
9. Long-held locks can exhaust application connection pools even when database CPU is low.
10. Deadlocks require global ordering discipline, not just stronger locks.
11. External side effects should not be held under hot database locks.
12. Retry the whole transaction attempt when the failure invalidates its coordination assumptions.
13. Constraints, atomic SQL, optimistic concurrency, pessimistic locking, and `SERIALIZABLE` are complementary tools.
14. Production diagnosis requires evidence from waits, blockers, lock state, transaction age, and application traces.
15. A hot row is an intentional serialization point; ensure the business semantics truly require it.

> **Central Principle:**  
> **Pessimistic concurrency is controlled serialization around a deliberately chosen resource. The expert goal is not to maximize locking; it is to serialize exactly what must be serialized, for exactly as long as necessary, while preserving correctness and system throughput.**
