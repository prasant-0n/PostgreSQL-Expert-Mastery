# 03.21 — Lost Updates

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains lost updates from first principles: why they happen, how MVCC can still allow application-level overwrites, how PostgreSQL prevents some races, and how to design atomic, optimistic, pessimistic, and serializable solutions.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- define a lost update precisely;
- distinguish a lost update from every other write-write conflict;
- explain why MVCC does not automatically mean application logic is protected;
- reproduce lost updates with concurrent transactions;
- identify the classic read-modify-write race;
- recognize when an SQL expression is already atomic;
- design atomic `UPDATE` statements correctly;
- use version predicates for optimistic concurrency control;
- use row locks for pessimistic coordination;
- understand how `READ COMMITTED`, `REPEATABLE READ`, and `SERIALIZABLE` change the outcome;
- distinguish stale overwrites from serialization failures and deadlocks;
- design correct API semantics for stale writes;
- handle retries without duplicating external effects;
- identify ORM-generated lost-update patterns;
- diagnose production incidents with database evidence;
- choose the smallest concurrency mechanism that protects the business invariant.

# 2. The Central Mental Model

A lost update is fundamentally a race between **reading state** and **writing a replacement based on that stale state**.

```text
Initial state
value = 100

T1 reads 100                  T2 reads 100
     |                             |
     | computes 110                | computes 90
     |                             |
     v                             v
UPDATE value = 110          UPDATE value = 90
     |                             |
     +---------- commit -----------+

Final value = 90

T1's logical change is lost.
```

The dangerous sequence is:

```text
READ
↓
COMPUTE IN APPLICATION
↓
WRITE ENTIRE VALUE
```

The safer alternatives are usually:

```text
ATOMIC DATABASE OPERATION

UPDATE accounts
SET balance = balance + 10
WHERE id = 1;
```

or:

```text
OPTIMISTIC CONCURRENCY

UPDATE accounts
SET balance = 110,
    version = version + 1
WHERE id = 1
  AND version = 7;
```

or:

```text
PESSIMISTIC CONCURRENCY

SELECT ... FOR UPDATE;
-- compute from the locked current row
UPDATE ...;
```

or, for broader invariants:

```text
SERIALIZABLE
+
transaction retry
```

---

# 3. Precise Definition

## 3.1 Simple definition

A **lost update** occurs when two concurrent actors make changes based on overlapping or stale state and one committed change overwrites the other so that the earlier logical modification is no longer represented in the final state.

## 3.2 Engineering definition

A lost update usually occurs when an application performs a read-modify-write cycle outside a single atomic database operation or without a concurrency check. Both requests can read the same old value, compute different replacements, and then write those replacements sequentially.

## 3.3 Expert definition

A lost update is a correctness failure in which a later write is based on a stale observation and replaces a state component containing another transaction's logically independent modification. It is not synonymous with every concurrent update. PostgreSQL's MVCC, row-update locking, isolation levels, and application SQL shape determine whether the race is prevented, serialized, rejected, or silently converted into a stale overwrite.

---

# 4. Lost Update vs Related Problems

Do not use “race condition,” “deadlock,” and “lost update” interchangeably.

| Problem | Core failure |
|---|---|
| Lost update | One logical change disappears because stale data overwrites newer data |
| Write skew | Two transactions update different rows and jointly violate an invariant |
| Nonrepeatable read | Same row is observed differently across statements |
| Dirty read | Uncommitted state is observed |
| Phantom | A repeated predicate sees a different set |
| Deadlock | Transactions form circular waiting |
| Serialization failure | Database rejects a transaction because the requested isolation cannot safely preserve its semantics |

A transaction can have a race condition without having a lost update.

---

# 5. Why MVCC Does Not Automatically Prevent Lost Updates

MVCC solves a different problem.

MVCC provides multiple row versions and snapshot-based visibility so readers and writers can often proceed concurrently.

That does **not** mean PostgreSQL understands the business meaning of:

> “I read 100, changed it to 110, therefore nobody else's modification should disappear.”

The database knows:

```text
Tuple version A
        ↓
Tuple version B
```

The application may know:

```text
B contains a business transformation derived from A
```

Those are not equivalent levels of meaning.

Therefore the crucial rule is:

> **MVCC protects visibility semantics; it does not automatically protect application-level read-modify-write intent.**

# 6. The Classic Lost-Update Race

Assume:

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    stock integer NOT NULL
);

INSERT INTO products(id, stock)
VALUES (1, 100);
```

Two API requests arrive.

Request A wants to add 10.

Request B wants to subtract 20.

The naive application does this:

```ts
const row = await db.query(
  'SELECT stock FROM products WHERE id = $1',
  [1],
);

const newStock = row.rows[0].stock + delta;

await db.query(
  'UPDATE products SET stock = $1 WHERE id = $2',
  [newStock, 1],
);
```

Possible execution:

```text
Initial stock = 100

Request A: SELECT -> 100
Request B: SELECT -> 100

A computes -> 110
B computes -> 80

A UPDATE -> 110
B UPDATE -> 80

Final -> 80
```

The mathematically intended result was:

```text
100 + 10 - 20 = 90
```

But the database ends at 80.

The `+10` logical change disappeared.

---

# 7. Naive Approach → Why It Fails

## Naive approach

```sql
SELECT stock
FROM products
WHERE id = 1;
```

then in application code:

```ts
const next = stock - 1;
```

then:

```sql
UPDATE products
SET stock = $1
WHERE id = 1;
```

## Why it fails

The update is based on a value that may no longer be current.

```text
Read version V1
     |
     +---- another transaction creates V2
     |
     +---- application still writes based on V1
```

The SQL engine sees a valid update predicate:

```sql
WHERE id = 1
```

It does not know that the caller's intended precondition was:

```text
I am allowed to write only if the row still has the state I originally observed.
```

---

# 8. Improved Approach: Atomic SQL

For arithmetic updates, push the transformation into the database:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = $1;
```

For increments:

```sql
UPDATE counters
SET value = value + 1
WHERE id = $1;
```

Two concurrent statements become conceptually:

```text
T1: value = value + 10
T2: value = value - 20

Database serializes the conflicting row modifications.

Final value = old + 10 - 20
```

The crucial improvement is that no stale replacement value crosses the application/database boundary.

---

# 9. Why Atomic SQL Works

The application sends an operation:

```text
“Apply this transformation to the row.”
```

instead of:

```text
“Here is the result I calculated from a value I read earlier.”
```

That distinction is enormous.

Compare:

```sql
-- stale replacement
UPDATE products
SET stock = 99
WHERE id = 1;
```

with:

```sql
-- relative transformation
UPDATE products
SET stock = stock - 1
WHERE id = 1;
```

The second formulation allows PostgreSQL to evaluate the expression against the row version being updated rather than receiving a potentially stale absolute value from the application.

---

# 10. Atomic SQL Is Not a Universal Concurrency Solution

An atomic expression solves some races, not all invariants.

For example:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

may atomically subtract money, but the business rule might be:

```text
balance must never become negative
```

Then the predicate should express the invariant:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1
  AND balance >= 100;
```

Then inspect affected rows:

```text
rowCount = 1 -> debit applied
rowCount = 0 -> debit rejected / insufficient funds / row missing
```

A database operation can therefore be both:

```text
atomic
+
conditional
```

That is often stronger than a separate `SELECT` followed by `UPDATE`.

---

# 11. Conditional Atomic Updates

Example: reserve one inventory unit only if stock exists.

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND branch_id = $2
  AND quantity > 0
RETURNING quantity;
```

This single statement can represent:

```text
check availability
+
change quantity
+
return result
```

without exposing the application to a stale intermediate state.

For a production API:

```text
RETURNING row present
    -> reservation succeeded

no row returned
    -> reservation failed
```

This pattern reduces the race window dramatically.

---

# 12. A More Subtle Lost Update: Full-Row Replacement

Suppose a product has:

```text
name
price
status
stock
```

The frontend sends the entire object.

User A changes `price`.

User B changes `status`.

Both loaded the same version.

A sends:

```json
{
  "name": "Gold Ring",
  "price": 55000,
  "status": "ACTIVE",
  "stock": 10
}
```

B sends:

```json
{
  "name": "Gold Ring",
  "price": 50000,
  "status": "DISCONTINUED",
  "stock": 10
}
```

If B writes the entire row after A, A's new price is lost.

This is often called a **stale full-row overwrite**.

It is a lost-update class problem even when the database itself is behaving correctly according to the issued `UPDATE` statements.

---

# 13. Optimistic Concurrency Control

A standard solution is a version column.

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    price numeric(18,2) NOT NULL,
    status text NOT NULL,
    version bigint NOT NULL DEFAULT 1
);
```

Read:

```sql
SELECT price, status, version
FROM products
WHERE id = $1;
```

Suppose the caller observed:

```text
version = 7
```

Then write:

```sql
UPDATE products
SET price = $1,
    status = $2,
    version = version + 1
WHERE id = $3
  AND version = $4;
```

Parameters include:

```text
$4 = 7
```

If the row count is 1:

```text
update accepted
```

If the row count is 0:

```text
stale write detected
```

The application can return a conflict such as HTTP 409.

---

# 14. Why the Version Predicate Works

The original caller says:

```text
“I am modifying version 7.”
```

The database checks:

```text
Is the row still version 7?
```

If another transaction already changed it:

```text
current version = 8
```

then:

```sql
WHERE version = 7
```

matches nothing.

The stale write therefore cannot overwrite the newer state.

The important property is not the integer itself.

It is the **compare-and-set precondition**.

---

# 15. Version Columns vs Timestamps

Many systems use:

```text
updated_at
```

as a concurrency token.

This can work, but a dedicated revision/token is often conceptually cleaner.

Potential issues with timestamps include:

- precision assumptions;
- clock-related assumptions at the application layer;
- multiple writes occurring within an assumed precision window;
- ambiguity over whether the timestamp is business data or concurrency metadata;
- update paths that accidentally fail to maintain the timestamp.

A dedicated:

```sql
version bigint NOT NULL
```

makes the contract explicit.

For APIs, opaque ETags can provide the same conceptual compare-and-set boundary without exposing implementation details.

---

# 16. HTTP-Level Optimistic Concurrency

A resource can expose:

```http
ETag: "product-42-v7"
```

The client updates with:

```http
If-Match: "product-42-v7"
```

The server translates that into a database condition:

```sql
UPDATE products
SET ...,
    version = version + 1
WHERE id = 42
  AND version = 7;
```

If the row count is zero:

```text
412 Precondition Failed
```

or an application-specific conflict response can be used depending on the API contract.

The important architecture is:

```text
HTTP precondition
        ↓
application concurrency token
        ↓
SQL compare-and-set predicate
        ↓
rowCount
        ↓
success or conflict
```

Concurrency protection should therefore cross the full stack rather than living only in one layer.

---

# 17. Pessimistic Solution: Lock Then Modify

When the operation requires several pieces of state to be examined together, a row lock may be appropriate.

```sql
BEGIN;

SELECT quantity
FROM inventory
WHERE product_id = $1
FOR UPDATE;

-- application or SQL determines the new quantity

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1;

COMMIT;
```

The lock makes competing transactions wait rather than both freely reading and replacing the same row state.

This is useful when:

- the transaction is short;
- contention is expected;
- the calculation requires current locked state;
- the invariant spans multiple operations.

---

# 18. But Do Not Lock Automatically

A common cargo-cult fix is:

```sql
SELECT ... FOR UPDATE;
```

for every update workflow.

That may increase:

- lock waits;
- latency;
- deadlock risk;
- connection occupancy;
- transaction duration;
- throughput collapse under contention.

For a simple counter, this:

```sql
UPDATE counters
SET value = value + 1
WHERE id = $1;
```

is usually simpler than:

```text
SELECT FOR UPDATE
↓
application computes
↓
UPDATE
```

Use a lock because the invariant needs it, not because “concurrency is scary.”

---

# 19. What Happens Under `READ COMMITTED`?

Under PostgreSQL's default `READ COMMITTED`, an `UPDATE` encountering a row changed by another transaction can wait for the first updater. After the concurrent transaction commits, PostgreSQL may work with the updated row version and re-evaluate the search condition.

This behavior is useful for atomic updates because the database is coordinating the row modification rather than simply accepting an application-computed stale value.

But a full-row replacement like:

```sql
UPDATE products
SET stock = 80
WHERE id = 1;
```

still means exactly that:

```text
set stock to 80
```

No isolation-level setting can infer that the caller intended:

```text
subtract 20 from the value I originally observed
```

The SQL statement itself must encode the intended transformation or precondition.

---

# 20. What Happens Under `REPEATABLE READ`?

Under PostgreSQL `REPEATABLE READ`, a transaction keeps a stable snapshot.

If the transaction tries to update a row that has been concurrently modified after its snapshot was established, PostgreSQL may raise a serialization failure rather than silently moving the transaction to the newer row version.

Therefore a stale full-row replacement may be rejected rather than silently applied.

The application must then treat the failed transaction as an aborted attempt and retry the **logical transaction**, not merely repeat the single statement blindly.

---

# 21. What Happens Under `SERIALIZABLE`?

`SERIALIZABLE` adds protection against broader serialization anomalies, including cases where no single row update looks obviously conflicting but the combined transaction logic cannot be represented as a serial execution.

The database may therefore abort a transaction with a serialization failure.

This is stronger than merely preventing a stale replacement.

Think in layers:

```text
Version predicate
    protects one logical write against stale state

Row lock
    coordinates ownership of selected rows

SERIALIZABLE
    protects transaction-level serializability
```

These mechanisms solve overlapping but different classes of problems.

---

# 22. A Critical Distinction: Lost Update vs Atomic Increment

Consider two requests:

```text
A: +10
B: -20
```

This is vulnerable:

```text
SELECT value
application computes replacement
UPDATE value = replacement
```

This is usually safe from the lost-update pattern:

```sql
UPDATE accounts
SET balance = balance + 10
WHERE id = $1;
```

and:

```sql
UPDATE accounts
SET balance = balance - 20
WHERE id = $1;
```

The database is processing operations on the row rather than receiving stale absolute replacements.

This leads to a valuable design heuristic:

> **Prefer expressing state transitions as database operations when the transition can be represented atomically.**

---

# 23. Lost Update in an Inventory System

Suppose:

```text
stock = 5
```

Request A:

```text
reserve 2
```

Request B:

```text
reserve 3
```

A naive implementation:

```text
T1 SELECT stock -> 5
T2 SELECT stock -> 5

T1 computes 3
T2 computes 2

T1 UPDATE stock = 3
T2 UPDATE stock = 2
```

Final:

```text
2
```

But the intended result after reserving 5 units was:

```text
0
```

A better atomic command is:

```sql
UPDATE inventory
SET stock = stock - $reservation_quantity
WHERE product_id = $1
  AND stock >= $reservation_quantity
RETURNING stock;
```

Each request either consumes stock or fails the predicate.

This is a classic example where the database can simultaneously enforce:

```text
atomicity
+
conditional validity
```

---

# 24. Lost Update in a Jewellery ERP Price Edit

Consider a product record:

```text
product_id = 501
metal_rate = 7200
making_charge = 1400
version = 12
```

Two operators edit the same item.

Operator A changes:

```text
metal_rate = 7300
```

Operator B changes:

```text
making_charge = 1500
```

Both loaded version 12.

Without optimistic concurrency, B can accidentally send back the stale `metal_rate = 7200` and overwrite A's approved rate.

With:

```sql
UPDATE product_pricing
SET metal_rate = $1,
    making_charge = $2,
    version = version + 1
WHERE product_id = $3
  AND version = $4;
```

B's update fails once A has already advanced the row to version 13.

The system can then present:

```text
“This price record was modified by another operator. Refresh and review the latest values before saving.”
```

This is not merely a technical concurrency feature.

It is an operator-safety feature.

---

# 25. Field-Level Merge vs Reject-on-Conflict

A version check does not force you to reject every conflict permanently.

Suppose:

```text
A changes price
B changes description
```

The application might safely merge them if the product's business rules permit field-wise merging.

But:

```text
A changes price
B changes price
```

may require human resolution.

Therefore conflict handling can be:

```text
Detect conflict
      |
      +--> non-overlapping fields -> merge
      |
      +--> overlapping business field -> reject
      |
      +--> critical invariant -> escalate / retry / serialize
```

This is where application semantics go beyond basic SQL concurrency.

---

# 26. Wrong Implementation: “Read Then Update by ID”

```ts
const product = await repo.findOne({ where: { id } });
product.price = requestedPrice;
await repo.save(product);
```

Why it looks reasonable:

- easy to read;
- ORM hides SQL;
- works during manual testing;
- single-user tests pass.

Why it can fail:

- `findOne` and `save` are separate database operations;
- another request may modify the row between them;
- the ORM may issue a full-row or stale-field update;
- no version predicate may exist;
- tests without real concurrency will not expose it.

Improvement:

```text
load version
↓
update WHERE id + version
↓
inspect affected rows
```

or use a domain-specific atomic SQL operation.

---

# 27. Wrong Implementation: “Last Write Wins Is Fine”

Some systems intentionally use last-write-wins.

That is not automatically wrong.

It becomes wrong when the business requires:

```text
all operator changes preserved
```

or:

```text
no stale approval may overwrite a newer approval
```

The key question is:

> **Is last-write-wins an explicit business policy or an accidental consequence of a missing concurrency design?**

Those are completely different architectures.

---

# 28. Wrong Implementation: “Serializable Solves Everything”

Replacing every transaction with:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

is not a substitute for proper SQL design.

A bad statement such as:

```sql
UPDATE products
SET stock = $1
WHERE id = $2;
```

still carries stale application semantics.

Serializable can cause the database to reject problematic interleavings, but it does not magically infer the intended delta, merge semantics, or domain ownership model.

Correctness still starts with expressing the business operation correctly.

---

# 29. Wrong Implementation: “Retry Every Failed Update”

This is dangerous:

```ts
for (let i = 0; i < 5; i++) {
  try {
    await update();
    break;
  } catch {
    // retry everything
  }
}
```

Not every error is retryable.

Distinguish:

```text
serialization failure       -> often retry
lock timeout                -> maybe retry
 deadlock                   -> often retry, after diagnosis
unique violation            -> usually no blind retry
foreign-key violation       -> usually no blind retry
validation/business error   -> no retry
authorization error         -> no retry
stale version               -> conflict workflow, not blind retry
```

And even for retryable failures, the transaction should usually be reconstructed from fresh state.

---

# 30. Lost Updates and External Side Effects

A transaction can safely update the database and still duplicate an external effect during retry.

Example:

```text
DB transaction
↓
charge payment provider
↓
serialization failure
↓
retry
↓
charge payment provider again
```

That is a distributed correctness failure.

Use:

```text
idempotency key
+
outbox / durable intent
+
external API idempotency support
```

The database transaction boundary must not be confused with a transaction boundary in an external service.

---

# 31. Lost Updates and Transaction Scope in Node.js/NestJS

A classic bug is accidentally using different pooled connections:

```ts
await dataSource.query('BEGIN');
await dataSource.query('SELECT ...');
await dataSource.query('UPDATE ...');
await dataSource.query('COMMIT');
```

Depending on the abstraction and pool behavior, commands may not all run on the same physical session.

Production transaction code should use an explicit transaction-scoped client/manager:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');
  await client.query('...');
  await client.query('...');
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

For ORM-based systems, use the framework's transaction-bound entity manager/query runner rather than mixing global repositories with a transaction-scoped manager.

The database can only enforce the transaction semantics if the application actually keeps the operations inside the same transaction/session context.

# 32. Observability: How Do You Prove a Lost Update?

Do not begin with:

> “PostgreSQL lost my data.”

Collect evidence.

Useful evidence includes:

```text
application request IDs
transaction IDs where available
query logs
statement timestamps
row versions
optimistic version values
rows affected
pg_stat_activity
pg_locks
application traces
```

For optimistic concurrency, a particularly valuable metric is:

```text
stale-write conflict count
```

For example:

```sql
UPDATE products
SET price = $1,
    version = version + 1
WHERE id = $2
  AND version = $3;
```

Then:

```text
rowCount = 0
```

is not merely “nothing updated.”

It can be an explicit concurrency signal.

# 33. Forensic Timeline

When investigating a suspected lost update, reconstruct the timeline:

```text
Request A received
Request A reads version 12

Request B received
Request B reads version 12

Request A writes
version becomes 13

Request B writes stale state
```

Then ask:

```text
Was the B write conditional on version 12?
Was the UPDATE atomic?
Was a row lock held?
What isolation level was used?
Did the ORM issue a full-row UPDATE?
Were both statements in the same transaction?
Did a trigger modify the row?
Was there an external cache involved?
```

The goal is to prove the causal chain, not simply observe the final bad value.

# 34. Concurrency Test Lab

A proper test needs at least two concurrent sessions.

### Session A

```sql

FROM products
WHERE id = 1;

-- pause
```

### Session B

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 1;

```

Both sessions now hold the same observed value.

Continue each application-style workflow:

```sql
UPDATE products
SET stock = 110
WHERE id = 1;
```

and:

```sql
UPDATE products
SET stock = 80
WHERE id = 1;
```

Observe the final state.

Then repeat with:

```sql
UPDATE products
SET stock = stock + 10
WHERE id = 1;
```

and:

```sql
UPDATE products
SET stock = stock - 20
WHERE id = 1;
```

The difference demonstrates why expressing the intended transition in SQL matters.

# 35. Optimistic-Concurrency Test Lab

Create:

```sql
CREATE TABLE document (
    id bigint PRIMARY KEY,
    body text NOT NULL,
    version bigint NOT NULL DEFAULT 1
);
```

Insert:

```sql
INSERT INTO document(id, body)
VALUES (1, 'initial');
```

Two sessions both read:

```text
version = 1
```

Session A:

```sql
UPDATE document
SET body = 'A',
    version = version + 1
WHERE id = 1
  AND version = 1;
```

Session B:

```sql
UPDATE document
SET body = 'B',
    version = version + 1
WHERE id = 1
  AND version = 1;
```

One statement should affect one row.

The other should affect zero rows.

That zero-row result is the concurrency conflict.

# 36. Performance Considerations

Lost-update prevention has a performance dimension.

Compare:

```text
naive read
+
application computation
+
write
```

with:

```text
atomic UPDATE
```

The atomic form often reduces:

- network round trips;
- transaction duration;
- lock-holding time;
- application complexity.

But optimistic version checks may increase conflict rates under heavy contention.

Pessimistic locking may reduce write conflicts at the cost of waiting.

Serializable may increase retries under workloads with strong dependency overlap.

Therefore measure:

```text
request latency
rows affected
conflict rate
lock wait time
serialization failure rate
retry count
throughput
```

# 37. Hot Rows

A single logical record can become a scalability bottleneck.

Example:

```text
counter id = 1
```

10,000 requests per second all execute:

```sql
UPDATE counters
SET value = value + 1
WHERE id = 1;
```

The operation may be logically correct but still create a hot-row bottleneck because all writers target the same row.

Correctness and scalability are different questions:

```text
Is it correct?
        |
        +--> yes

Is it scalable?
        |
        +--> depends on contention
```

Possible architectural alternatives include sharded counters, append-only event records, batching, or aggregation, depending on the workload.

---

# 38. Multi-Tenant Systems

In a shared multi-tenant database, the same concurrency pattern may be amplified by tenant-level hotspots.

For example:

```text
tenant A -> one extremely popular product
```

may create far more contention than:

```text
tenant B -> 1,000 less-active products
```

Useful metrics include:

```text
conflicts per tenant
lock waits per tenant
hot-row frequency
retry rates
```

This can expose noisy-neighbor behavior that global averages hide.

---

# 39. Security Implications

Lost updates can become security issues when authorization state is involved.

Example:

```text
A approves user
B revokes user
```

A stale full-record update might accidentally restore the older permission state.

Concurrency control therefore matters to:

- approvals;
- role changes;
- access-control policy;
- financial approvals;
- inventory ownership;
- workflow state.

Do not treat concurrency as merely a performance topic.

---

# 40. AI / Vibe-Coding Failure Patterns

AI-generated code frequently produces this shape:

```ts
const record = await repo.findOne(id);
record.counter += 1;
await repo.save(record);
```

It looks correct in sequential tests.

Under concurrency it may be a lost-update candidate.

Another common pattern is:

```ts
const current = await getBalance();
const next = current - amount;
await updateBalance(next);
```

A database-aware design asks:

```text
Can this be an atomic UPDATE?
Can the invariant be encoded in the WHERE clause?
Do I need a version predicate?
Do I need a row lock?
Do I need SERIALIZABLE?
```

The lesson is:

> **AI-generated code often optimizes for local readability, while concurrency correctness lives in the interaction between requests.**

# 41. Decision Framework

Use this sequence.

```text
1. Can the invariant be expressed as one atomic SQL statement?
        |
       yes -> prefer atomic SQL
        |
       no
        v
2. Can a compare-and-set/version predicate protect the write?
        |
       yes -> optimistic concurrency
        |
       no
        v
3. Do I need current locked state across multiple operations?
        |
       yes -> pessimistic locking
        |
       no
        v
4. Does correctness depend on transaction-level serializability?
        |
       yes -> SERIALIZABLE + retry
```

This avoids jumping immediately to the strongest mechanism.

# 42. Trade-Off Matrix

| Technique | Prevents stale overwrite | Handles hot rows | Blocks | Can abort | Complexity |
|---|---:|---:|---:|---:|---:|
| Atomic SQL | Yes for represented operation | Can contend | Briefly during row update | Normally no | Low |
| Version predicate | Yes | Conflicts become explicit | Usually little | No, returns conflict | Low–medium |
| Row lock | Yes when used correctly | Can increase waiting | Yes | Deadlock possible | Medium |
| `REPEATABLE READ` | Can reject concurrent row update | Can increase aborts | Some waits possible | Yes | Medium |
| `SERIALIZABLE` | Stronger transaction guarantee | May increase retries | Some waits possible | Yes | High |

No row in this table means “best.”

The correct technique depends on the invariant and workload.

# 43. Production Pattern — Versioned Update Helper

A reusable service-layer abstraction can make stale writes explicit:

```ts
type UpdateResult =
  | { ok: true; version: number }
  | { ok: false; reason: 'STALE_VERSION' | 'NOT_FOUND' };

async function updateProduct(
  client: PoolClient,
  id: number,
  version: number,
  price: number,
): Promise<UpdateResult> {
  const result = await client.query(
    `
      UPDATE products
      SET price = $1,
          version = version + 1
      WHERE id = $2
        AND version = $3
      RETURNING version
    `,
    [price, id, version],
  );

  if (result.rowCount === 1) {
    return { ok: true, version: result.rows[0].version };
  }

  const exists = await client.query(
    'SELECT 1 FROM products WHERE id = $1',
    [id],
  );

  if (exists.rowCount === 0) {
    return { ok: false, reason: 'NOT_FOUND' };
  }

  return { ok: false, reason: 'STALE_VERSION' };
}
```

Production implementations may optimize the final existence check or use a domain-specific API response, but the concurrency contract remains explicit.

# 48. Interview Questions

## Junior

### Q1. What is a lost update?

**Weak answer:** “Two users update at the same time.”

**Acceptable answer:** “One user's update overwrites another user's concurrent update.”

**Strong answer:** “It usually happens when two actors read the same old state, compute separate replacements, and later writes erase one logical change.”

**Expert answer:** “It is a stale read-modify-write correctness failure whose outcome depends on SQL shape, MVCC/update conflict handling, isolation level, and whether the write encodes a concurrency precondition or atomic transformation.”

## Mid-Level

### Q2. Why is `UPDATE value = value + 1` safer than `SELECT value` followed by `UPDATE value = calculated_value`?

Because the former expresses the transformation at the database layer while the latter sends an application-computed replacement based on potentially stale state.

### Q3. What does `rowCount = 0` mean in an optimistic update?

It can mean the row does not exist, or that the expected version no longer matches. The API should distinguish those outcomes when necessary.

## Senior

### Q4. Does `READ COMMITTED` prevent lost updates?

Not generically. Atomic database-side transformations can avoid the classic stale replacement pattern, but `READ COMMITTED` alone does not understand application intent.

### Q5. What is the difference between optimistic and pessimistic concurrency?

Optimistic concurrency detects conflicts at write time using a precondition such as a version. Pessimistic concurrency coordinates access by locking the resource before making dependent decisions.

## Staff / Principal

### Q6. When would you choose atomic SQL over optimistic concurrency?

When the operation itself can be expressed as a correct atomic transformation and there is no need to surface a caller-specific stale-write conflict.

### Q7. When is a version predicate superior to `SELECT FOR UPDATE`?

When user think-time or long application processing exists between read and write and holding a lock for that entire period would be expensive or inappropriate.

### Q8. Can `SERIALIZABLE` replace optimistic concurrency everywhere?

No. It is stronger and more expensive operationally, and it still does not encode domain-specific merge semantics or the intended transformation of stale state.

# 49. Trick Questions

### “PostgreSQL uses MVCC, so lost updates cannot happen.”

False.

MVCC provides visibility and versioning semantics. Application-level stale overwrites can still occur.

### “A transaction means no other transaction can modify the row.”

False.

A transaction is not automatically an exclusive lock over every row it reads.

### “Adding `FOR UPDATE` always fixes a lost update.”

False.

The lock must be acquired at the correct point, on the correct rows, within the correct transaction scope, and the application must actually use the locked state correctly.

### “If two requests update different fields, there is no conflict.”

Not necessarily. A full-row ORM save can still overwrite unchanged fields with stale values.

# 53. Final Takeaway

The deepest lesson is not:

> “Use locks to prevent lost updates.”

It is:

> **Make the database operation represent the business transition and its preconditions as directly as possible.**

When a change is naturally atomic:

```sql
UPDATE ...
SET value = value + delta
WHERE ...;
```

When caller freshness matters:

```sql
UPDATE ...
SET ...,
    version = version + 1
WHERE id = $id
  AND version = $expected_version;
```

When several reads and writes require coordinated ownership:

```sql
SELECT ...
FOR UPDATE;
```

When the invariant requires transaction-level serializability:

```sql
SERIALIZABLE
+
whole-transaction retry
```

The engineering progression is therefore:

```text
Naive read-modify-write
        ↓
Atomic SQL when possible
        ↓
Optimistic compare-and-set when freshness matters
        ↓
Pessimistic locking when coordinated ownership is required
        ↓
Serializable isolation when broader transaction serializability is the invariant
```

> **Correct concurrency is not “more locking.” It is expressing exactly what must remain true when multiple actors act at the same time.**
