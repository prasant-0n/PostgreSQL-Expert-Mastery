# 2. The Central Mental Model

There are two mechanisms that developers frequently collapse into one concept:

```text
MVCC visibility
    answers:
    "Which row version can I see?"

Row locking
    answers:
    "Which concurrent operation is allowed to modify or lock this row now?"
```

They cooperate, but they are not interchangeable.

A useful model is:

```text
                 PostgreSQL concurrency
                         |
             +-----------+-----------+
             |                       |
           MVCC                    Locks
             |                       |
      version visibility       coordination
             |                       |
      what can I see?         who can change/lock?
```

A plain `SELECT` normally does not wait merely because another transaction holds a row lock. PostgreSQL's row locks primarily block other writers and explicit lockers of the same row. The official documentation explicitly states that row-level locks do not affect data querying; they block writers and lockers targeting the same row. citeturn681731search5

That gives the central principle:

> **MVCC determines visibility; row locks coordinate conflicting changes and lock requests.**

---

# 3. What Is a Row-Level Lock?

## 3.1 Simple definition

A row-level lock is a concurrency-control state associated with an individual table row that restricts which other transactions may update, delete, or explicitly lock that row until the relevant lock is released.

## 3.2 Engineering definition

A row lock is a transaction-scoped coordination mechanism used to serialize incompatible operations on a specific tuple while allowing unrelated rows to remain concurrently accessible.

## 3.3 Expert definition

PostgreSQL represents row-locking information in tuple state and coordinates conflicts through transaction ownership and MVCC machinery. Four row-lock strengths define different conflict sets: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, and `FOR KEY SHARE`. Unlike relation locks, the row-level lock itself is not normally represented as one persistent per-row entry in `pg_locks`; a waiter commonly appears as waiting on the transaction ID of the transaction holding the relevant row lock. PostgreSQL can use multixact IDs when multiple transactions simultaneously hold row-level share locks. citeturn681731search1turn681731search0turn681731search8

# 4. Why Row Locks Exist

Without row-level coordination, consider:

```text
Inventory item 42 = quantity 10

T1 reads 10
T2 reads 10
T1 decides to sell 7
T2 decides to sell 6
```

The application now needs a way to coordinate access to the same business object.

Row-level locking allows a design such as:

```text
T1 locks item 42
        |
        +-- T2 tries same row
                |
                +-- waits

T1 validates and updates
        |
        +-- commit
                |
                +-- T2 continues
```

The lock does not by itself express the entire business rule. It gives the application a serialization point on the chosen row.

The business invariant still has to be correct.

# 5. Row Locks vs Table Locks

A common mistake is thinking PostgreSQL has one generalized lock system with only different names.

Conceptually:

```text
TABLE-LEVEL LOCK
    protects a relation-level operation or compatibility condition

ROW-LEVEL LOCK
    coordinates a specific tuple
```

For example:

```sql
SELECT *
FROM inventory
WHERE id = 42
FOR UPDATE;
```

This does not mean:

> “The entire `inventory` table is locked for exclusive use.”

The query also acquires a table-level `ROW SHARE` lock because `SELECT ... FOR UPDATE` needs it, but the important data-level protection is on the qualifying rows. PostgreSQL documents the `ROW SHARE` table lock acquired by `SELECT` statements using `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, or `FOR KEY SHARE`. citeturn681731search5

This distinction matters operationally because a developer may observe a relation lock in `pg_locks` and incorrectly conclude that every row has been exclusively locked in the same way.

---

# 6. The Four PostgreSQL Row Lock Modes

PostgreSQL provides four explicit row-lock strengths:

| Row lock | Strength | Main idea |
|---|---|---|
| `FOR UPDATE` | strongest | reserve row for update/delete-like ownership |
| `FOR NO KEY UPDATE` | strong | reserve row for non-key updates |
| `FOR SHARE` | shared | protect row from writers while allowing compatible readers/lockers |
| `FOR KEY SHARE` | weakest | protect key identity / referenced-row relationship |

The exact conflict matrix matters more than the labels.

From strongest to weakest, a useful intuition is:

```text
FOR UPDATE
    |
    v
FOR NO KEY UPDATE
    |
    v
FOR SHARE
    |
    v
FOR KEY SHARE
```

But do not interpret this as a universal numerical ordering where every stronger lock conflicts with every weaker lock in a simple chain. The actual compatibility table is the source of truth. PostgreSQL documents the complete matrix explicitly. citeturn681731search5

---

# 7. The Row-Lock Conflict Matrix

The conflict relationship is:

| Requested ↓ / Existing → | `KEY SHARE` | `SHARE` | `NO KEY UPDATE` | `UPDATE` |
|---|---:|---:|---:|---:|
| `KEY SHARE` | — | — | — | X |
| `SHARE` | — | — | X | X |
| `NO KEY UPDATE` | — | X | X | X |
| `UPDATE` | X | X | X | X |

Therefore:

```text
KEY SHARE
    compatible with KEY SHARE, SHARE, NO KEY UPDATE
    conflicts with UPDATE

SHARE
    compatible with KEY SHARE, SHARE
    conflicts with NO KEY UPDATE, UPDATE

NO KEY UPDATE
    compatible with KEY SHARE
    conflicts with SHARE, NO KEY UPDATE, UPDATE

UPDATE
    conflicts with every row-lock mode
```

The official documentation states this matrix directly. citeturn681731search5

The practical lesson is:

> **Choose the weakest row lock that is sufficient to protect the invariant.**

Using `FOR UPDATE` everywhere can create unnecessary contention.

---

# 8. `FOR UPDATE`

Syntax:

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;
```

Conceptually:

```text
Find row
   |
   v
Lock row with UPDATE strength
   |
   v
Return row
   |
   v
Transaction performs protected work
```

While the lock is held, other transactions attempting incompatible updates, deletes, or row-locking operations on that row must wait, or fail immediately if a `NOWAIT` strategy is used later in this curriculum.

PostgreSQL documents that `FOR UPDATE` prevents other transactions from locking, modifying, or deleting the row until the current transaction ends. `UPDATE` itself also acquires a `FOR UPDATE` lock when it modifies the key columns relevant to foreign-key enforcement. citeturn681731search5

Typical use cases:

```text
inventory reservation
order state transition
claiming a payment attempt
editing a mutable business aggregate
protecting a row before conditional mutation
```

---

# 9. `FOR NO KEY UPDATE`

Syntax:

```sql
SELECT *
FROM products
WHERE id = $1
FOR NO KEY UPDATE;
```

This lock behaves similarly to `FOR UPDATE`, but it is weaker because it does not block `SELECT FOR KEY SHARE`.

PostgreSQL also automatically takes this lock for an `UPDATE` that does not modify the relevant key columns that can participate in a foreign key. citeturn681731search5

This distinction exists because changing a non-key attribute and changing a referenced key have different concurrency implications.

Think:

```text
UPDATE product
SET price = 125
WHERE id = 42;
```

This changes product data but not the identity referenced by foreign keys.

Contrast with an update that changes a referenced unique key. PostgreSQL uses stronger row-lock behavior for that case. citeturn681731search5

---

# 10. `FOR SHARE`

Syntax:

```sql
SELECT *
FROM documents
WHERE id = $1
FOR SHARE;
```

A share lock protects the row against stronger write locks while allowing compatible share/key-share readers.

This is useful when a transaction needs to establish:

> “This row must not be changed by an incompatible operation while I rely on it.”

But it does not provide the same exclusivity as `FOR UPDATE`.

A conceptual scenario:

```text
T1: FOR SHARE on row 10
T2: FOR SHARE on row 10     -> allowed
T3: UPDATE row 10           -> waits
```

PostgreSQL's documented conflict table gives exactly this relationship. citeturn681731search5

---

# 11. `FOR KEY SHARE`

Syntax:

```sql
SELECT *
FROM parent
WHERE id = $1
FOR KEY SHARE;
```

This is the weakest row-lock mode and is specifically designed to protect key identity relationships.

It blocks:

```text
DELETE
and
UPDATEs that change the referenced key
```

but it does not block ordinary non-key updates or other compatible row locks.

This matters for foreign-key concurrency. PostgreSQL's feature documentation describes `FOR NO KEY UPDATE` / `FOR KEY SHARE` as modes that let non-key-field updates avoid unnecessarily locking foreign-key rows. citeturn681731search4

A useful intuition:

```text
KEY SHARE says:

"I depend on this row's key identity remaining valid."
```

That is different from:

```text
FOR UPDATE says:

"I need exclusive row-level mutation rights."
```

---

# 12. Automatic Row Locks from `UPDATE`

Developers often think row locks matter only when they write `FOR UPDATE`.

They do not.

`UPDATE` automatically acquires row-level locking appropriate to what it changes.

PostgreSQL documents that an `UPDATE` acquires `FOR NO KEY UPDATE` when it does not modify columns forming relevant foreign-key keys, and can acquire `FOR UPDATE` when it does. `DELETE` takes `FOR UPDATE` on the affected row. citeturn681731search5

Therefore:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE id = 42;
```

is already a locking operation.

This leads to an important rule:

> **Do not add `SELECT ... FOR UPDATE` merely because an `UPDATE` is present. Add it when the transaction needs to lock the row before later decision-making or multiple statements.**

---

# 13. Atomic UPDATE vs SELECT-Then-UPDATE

Compare two approaches.

## Naive approach

```sql
SELECT quantity
FROM inventory
WHERE id = $1;

-- application logic

UPDATE inventory
SET quantity = quantity - $2
WHERE id = $1;
```

There is a concurrency gap between the read and the write.

## Better approach for simple arithmetic

```sql
UPDATE inventory
SET quantity = quantity - $2
WHERE id = $1
  AND quantity >= $2
RETURNING quantity;
```

The decision and mutation happen in one statement.

## Alternative: explicit lock

Use an explicit lock when the business decision truly requires multiple operations:

```sql
BEGIN;

SELECT quantity, reserved
FROM inventory
WHERE id = $1
FOR UPDATE;

-- validate multiple fields / related state

UPDATE inventory
SET quantity = quantity - $2,
    reserved = reserved + $2
WHERE id = $1;

COMMIT;
```

The design question is not:

> “Should I always use a row lock?”

It is:

> “Does the correctness proof require a protected sequence of observations and writes?”

---

# 14. Row Locks Do Not Replace Constraints

Suppose the invariant is:

```text
email must be unique
```

A row lock on the existing matching user row is not sufficient because the row may not exist yet.

A unique constraint is the correct database-level enforcement:

```sql
ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);
```

Similarly:

```text
quantity >= 0
```

should usually be enforced with:

```sql
CHECK (quantity >= 0)
```

Row locks are useful for coordination, not as a universal substitute for declarative integrity.

Production design commonly combines:

```text
Constraints
+
Atomic SQL
+
Row locks where needed
+
Appropriate isolation level
```

# 15. Row Lock Lifetime

A critical rule:

> **Row locks are normally held until the transaction ends, or are released earlier by savepoint/subtransaction rollback according to PostgreSQL's lock-lifetime rules.**

This means:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE id = 42
FOR UPDATE;

-- 20 seconds of application work

COMMIT;
```

The row can remain locked for the entire 20 seconds.

If the application calls an external API while holding the lock:

```text
DB lock acquired
      |
      v
HTTP request
      |
      v
remote service waits 8 sec
      |
      v
DB update
      |
      v
COMMIT
```

every incompatible waiter may be delayed for those 8 seconds.

This is one of the most common production lock-amplification patterns.

---

# 16. Why “Short Code” Does Not Mean “Short Lock”

Application source may look compact:

```ts
await db.transaction(async (tx) => {
  const item = await tx.inventory.findById(id, { lock: 'update' });
  await service.reserveExternalCapacity(item);
  await tx.inventory.update(id, ...);
});
```

The transaction may still be open across:

- network calls;
- retries;
- JSON processing;
- file I/O;
- CPU-heavy calculations;
- event publication;
- logging transports;
- user-facing waits.

The lock lifetime follows the transaction, not the number of SQL lines.

Production rule:

```text
Acquire lock
↓
Do bounded local work
↓
Mutate
↓
Commit quickly
```

# 17. Row Locks Under `READ COMMITTED`

At `READ COMMITTED`, an ordinary `SELECT` gets statement-level visibility while row-locking commands participate in conflict coordination.

Consider:

```text
T1: SELECT ... FOR UPDATE row 42
T2: UPDATE row 42
```

T2 must wait for the conflicting row lock.

Conversely:

```text
T1: UPDATE row 42
T2: SELECT ... FOR UPDATE row 42
```

T2 waits for T1's conflicting update transaction to resolve.

After the wait, PostgreSQL applies the command's isolation semantics. Under `READ COMMITTED`, a locking read can return the updated version; at higher isolation levels the behavior can instead result in an error when the row changed after the transaction snapshot. PostgreSQL documents these distinctions in its locking and isolation sections. citeturn681731search5turn237530search20

The important mental model is:

```text
Row lock conflict
    |
    +-- wait or fail
    |
    +-- transaction resolves
    |
    +-- isolation level determines what the waiter may then observe/do
```

---

# 18. Row Locks Under `REPEATABLE READ`

Under `REPEATABLE READ`, a lock request cannot simply make the transaction's snapshot become newer.

Suppose:

```text
T1: begins REPEATABLE READ
T1: snapshot established

T2: updates row 42 and commits

T1: SELECT ... FOR UPDATE row 42
```

PostgreSQL documents that within `REPEATABLE READ` or `SERIALIZABLE`, an error is thrown if a row to be locked has changed since the transaction started. citeturn681731search5

This is why row-locking semantics must always be taught together with isolation level.

The statement:

> “`FOR UPDATE` waits and then gives me the newest row.”

is not universally correct.

It depends on the transaction's isolation semantics.

---

# 19. Row Locks Under `SERIALIZABLE`

`SERIALIZABLE` adds broader protection against serialization anomalies, including dependency tracking beyond simple row-to-row blocking.

A row lock can still be useful, but it is not synonymous with serializability.

For example:

```text
T1 locks row A
T2 locks row B

Both independently read another predicate range
```

A business invariant involving the relationship between A and B may require stronger coordination than one row lock.

Therefore:

```text
Row lock
    !=
Serializable isolation
```

One is local coordination on a row.

The other is a transaction-wide consistency guarantee.

# 20. Foreign Keys and Row Locks

Foreign-key enforcement is one reason PostgreSQL has nuanced row-lock modes.

Suppose:

```sql
CREATE TABLE customers (
    id bigint PRIMARY KEY
);

CREATE TABLE orders (
    id bigint PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(id)
);
```

An operation that depends on the parent key remaining valid does not necessarily need to block ordinary non-key updates of the parent row.

That is why `FOR KEY SHARE` exists and why `FOR NO KEY UPDATE` is weaker than `FOR UPDATE`.

The design objective is concurrency without sacrificing referential integrity:

```text
Parent key identity
        |
        +-- protect with KEY SHARE semantics
        |
        +-- allow unrelated non-key field updates
```

PostgreSQL explicitly notes that `FOR NO KEY UPDATE` and `FOR KEY SHARE` prevent unnecessary conflicts with non-key-field updates while coordinating key-changing operations. citeturn681731search4turn681731search5

---

# 21. Multiple Row Lockers and Multixacts

One of PostgreSQL's more subtle internals appears when multiple transactions hold compatible row locks on the same tuple.

Example:

```text
T1: FOR SHARE row 42
T2: FOR SHARE row 42
```

Neither conflicts with the other.

But the tuple header has limited space for transaction-lock metadata.

PostgreSQL uses a **multixact ID** to represent multiple transactions associated with row-lock state. The official vacuum documentation explains that multixacts are used to support row locking by multiple transactions, and that tuple-header space is encoded through a multixact ID when more than one transaction concurrently locks a row. citeturn681731search8

This is an important bridge between:

```text
SQL syntax
    ↓
row locks
    ↓
tuple header metadata
    ↓
multixact
    ↓
MVCC cleanup / vacuum / wraparound considerations
```

You do not need to manipulate multixacts directly to use row locks correctly, but an expert PostgreSQL engineer should understand why they exist and why pathological locking workloads can have storage-maintenance consequences.

---

# 22. Why Row Locks Usually Do Not Appear as Ordinary `tuple` Rows in `pg_locks`

This surprises many developers.

They run:

```sql
SELECT *
FROM pg_locks
WHERE locktype = 'tuple';
```

and do not see the row they expected.

The reason is architectural.

PostgreSQL stores row-lock information in the locked tuple rather than maintaining one ordinary in-memory lock-manager object for every locked row. The `pg_locks` documentation explicitly states that row-level lock information is stored on disk and therefore row-level locks normally do not appear in that view. A session waiting on a row lock will usually appear as waiting for the permanent transaction ID of the transaction holding the row lock. citeturn681731search1

This gives a debugging pattern:

```text
Application says:
"UPDATE is waiting on a row"

        ↓

pg_stat_activity:
wait event / blocked PID

        ↓

pg_locks:
waiting on transactionid

        ↓

identify holder transaction

        ↓

inspect transaction SQL + age
```

This is why reading only `locktype = 'tuple'` is an incomplete diagnostic strategy.

---

# 23. `pgrowlocks` for Direct Row-Lock Inspection

PostgreSQL provides the `pgrowlocks` extension for row-lock inspection.

After enabling it:

```sql
CREATE EXTENSION pgrowlocks;
```

you can inspect a table:

```sql
SELECT *
FROM pgrowlocks('inventory');
```

The extension exposes information including:

- locked row TID;
- locker transaction ID or multixact ID;
- whether the locker is a multitransaction;
- transaction IDs of the lockers.

The official PostgreSQL 18 documentation describes `pgrowlocks(text)` and its output structure. Access is restricted according to the documented privileges, including superusers, members of `pg_stat_scan_tables`, and users with `SELECT` on the target table. citeturn681731search3

Use this as a forensic tool, not as a replacement for ordinary production monitoring.

# 24. Debugging a Blocked Row Update

Assume an API request is stuck.

Start with:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

Then inspect locks:

```sql
SELECT
    pid,
    locktype,
    relation::regclass AS relation_name,
    page,
    tuple,
    transactionid,
    mode,
    granted,
    waitstart
FROM pg_locks
WHERE pid = $1;
```

For relationship-oriented diagnosis:

```sql
SELECT
    blocked.pid AS blocked_pid,
    blocker.pid AS blocker_pid,
    blocked.query AS blocked_query,
    blocker.query AS blocker_query,
    blocked.wait_event_type,
    blocked.wait_event,
    blocker.xact_start AS blocker_xact_start
FROM pg_stat_activity blocked
JOIN pg_locks blocked_lock
  ON blocked_lock.pid = blocked.pid
 AND NOT blocked_lock.granted
JOIN pg_locks blocker_lock
  ON blocker_lock.locktype = blocked_lock.locktype
 AND blocker_lock.database IS NOT DISTINCT FROM blocked_lock.database
 AND blocker_lock.relation IS NOT DISTINCT FROM blocked_lock.relation
 AND blocker_lock.page IS NOT DISTINCT FROM blocked_lock.page
 AND blocker_lock.tuple IS NOT DISTINCT FROM blocked_lock.tuple
 AND blocker_lock.transactionid IS NOT DISTINCT FROM blocked_lock.transactionid
 AND blocker_lock.virtualxid IS NOT DISTINCT FROM blocked_lock.virtualxid
 AND blocker_lock.classid IS NOT DISTINCT FROM blocked_lock.classid
 AND blocker_lock.objid IS NOT DISTINCT FROM blocked_lock.objid
 AND blocker_lock.objsubid IS NOT DISTINCT FROM blocked_lock.objsubid
 AND blocker_lock.pid <> blocked_lock.pid
JOIN pg_stat_activity blocker
  ON blocker.pid = blocker_lock.pid
WHERE blocked.datname = current_database();
```

In production, prefer PostgreSQL's built-in blocking relationships where available and supplement them with lock inspection rather than attempting to reason from a single column.

PostgreSQL 18 explicitly documents `pg_locks` as a tool for identifying outstanding locks, ungranted locks, and contention. citeturn681731search7turn681731search1

# 25. Evidence-Driven Lock Diagnosis

Do not start with:

> “The database is slow because row locks are bad.”

Start with:

```text
Symptom
↓
Which requests are slow?
↓
Are sessions waiting?
↓
What wait event?
↓
Which resource?
↓
Which transaction owns the conflicting lock?
↓
How old is that transaction?
↓
What SQL kept it open?
↓
Why was that transaction long-lived?
↓
What design created the contention?
```

This distinguishes:

```text
row-lock contention
vs
CPU saturation
vs
I/O latency
vs
connection-pool starvation
vs
planner regression
vs
application backpressure
```

A blocked request does not automatically mean PostgreSQL is “slow.” PostgreSQL may be doing exactly what the concurrency design asked it to do: wait for another transaction to finish.

# 26. Production Failure: Long Transaction Holds Inventory Row

Scenario:

```text
T1
BEGIN
FOR UPDATE inventory row 42
call payment gateway
wait 4s
update
commit
```

Meanwhile:

```text
T2 -> waits 4s
T3 -> waits 4s
T4 -> waits 4s
T5 -> waits 4s
```

If traffic increases:

```text
One slow transaction
       ↓
lock wait queue
       ↓
more request latency
       ↓
more active connections
       ↓
connection pool exhaustion
       ↓
request timeouts
       ↓
retries
       ↓
more contention
```

This is a feedback loop.

Correct architecture usually moves external work outside the database transaction or changes the protocol so the database state machine can represent an intermediate state.

For example:

```text
Transaction 1:
reserve
commit

External payment call

Transaction 2:
record payment result
commit
```

The exact workflow depends on the business invariant, but the principle is stable:

> **Do not hold a contested database row lock while waiting on an external system unless the lock duration is deliberately bounded and the trade-off is understood.**

# 27. Production Pattern: Inventory Reservation

A robust pattern is:

```sql
BEGIN;

SELECT quantity, reserved
FROM inventory
WHERE product_id = $1
FOR UPDATE;
```

Then validate:

```text
available = quantity - reserved
requested <= available
```

Then mutate:

```sql
UPDATE inventory
SET reserved = reserved + $2
WHERE product_id = $1;
```

Then record the reservation:

```sql
INSERT INTO inventory_reservations (...)
VALUES (...);
```

Then:

```sql
COMMIT;
```

Why this works:

```text
T1 locks inventory aggregate
      |
T2 attempts same aggregate
      |
      +-- waits

T1 checks + mutates atomically
      |
      +-- commit

T2 continues and sees a serialized state
```

The exact isolation level and constraint design still matter.

# 28. Production Pattern: Order State Transition

Suppose an order may move:

```text
PENDING -> CONFIRMED
PENDING -> CANCELLED
```

Two requests arrive concurrently.

Naive application code:

```ts
const order = await repo.find(id);

if (order.status === 'PENDING') {
  await repo.update(id, { status: 'CONFIRMED' });
}
```

Both requests can observe `PENDING`.

A protected workflow:

```sql
BEGIN;

SELECT status
FROM orders
WHERE id = $1
FOR UPDATE;

-- validate current state

UPDATE orders
SET status = 'CONFIRMED'
WHERE id = $1
  AND status = 'PENDING';

COMMIT;
```

An even simpler atomic transition may be:

```sql
UPDATE orders
SET status = 'CONFIRMED'
WHERE id = $1
  AND status = 'PENDING'
RETURNING *;
```

Again:

```text
Use a row lock when the transaction needs the row protected across multiple statements.

Use an atomic UPDATE when one SQL statement can express the invariant.
```

# 29. Production Pattern: Queue Claiming Preview

A worker queue commonly uses:

```sql
SELECT id
FROM jobs
WHERE status = 'READY'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

The purpose is not merely “get a row lock.” It is:

```text
Worker A locks jobs 1-10
Worker B skips those rows
Worker B claims other ready rows
```

This reduces workers waiting behind each other.

The complete `SKIP LOCKED` design is covered later in Phase 03, but the row-level-lock foundation is essential.

The critical production question is:

> “What happens if a worker crashes while holding the transaction?”

The answer depends on whether the job claim and status transition are committed, whether the work is performed inside or outside the transaction, and whether the queue is designed for retries/idempotency.

# 30. Lock Ordering and Deadlock Foundations

Consider:

```text
T1:
lock row A
lock row B

T2:
lock row B
lock row A
```

Possible outcome:

```text
T1 waits for B
T2 waits for A

      cycle
        ↓
     deadlock
```

Row locks therefore participate directly in deadlock behavior.

A robust strategy is deterministic ordering:

```sql
SELECT id
FROM accounts
WHERE id IN ($1, $2)
ORDER BY id
FOR UPDATE;
```

Both transactions then attempt locks in the same order.

This does not mathematically eliminate every deadlock in a complex system, but it removes a major class of circular waits.

---

# 31. Wrong Implementation #1 — Locking After the Business Decision

Bad:

```text
SELECT row
↓
check condition
↓
SELECT ... FOR UPDATE
↓
UPDATE
```

The decision was made before the row was protected.

Why it fails:

```text
T1 reads condition = true
T2 changes row
T1 locks later
T1's decision may no longer match the protected state
```

Correct:

```text
SELECT ... FOR UPDATE
↓
read protected state
↓
validate
↓
mutate
```

Or better yet, collapse the invariant into one atomic DML statement when possible.

---

# 32. Wrong Implementation #2 — Locking the Wrong Row

Suppose the invariant is:

```text
Only one pending reservation per product.
```

Locking an unrelated user row does not protect the invariant:

```sql
SELECT *
FROM users
WHERE id = $1
FOR UPDATE;
```

The correct synchronization object must be part of the invariant's conflict set.

Examples:

```text
inventory invariant -> inventory aggregate row
order transition -> order row
account transfer -> all involved account rows
quota -> quota-owner or quota bucket row
```

A lock is only meaningful relative to what it protects.

---

# 33. Wrong Implementation #3 — Locking Every Row “For Safety”

Bad:

```sql
SELECT *
FROM inventory
FOR UPDATE;
```

Why it fails:

- huge lock footprint;
- long execution time;
- unnecessary contention;
- application scalability collapse;
- more difficult deadlock reasoning;
- more disk work for row-locking operations;
- potential queueing across unrelated business objects.

PostgreSQL explicitly notes that locking a row can cause a disk write, for example `SELECT FOR UPDATE` modifies selected rows to mark them locked. citeturn681731search5

Lock the minimum necessary conflict set.

---

# 34. Wrong Implementation #4 — Holding the Lock Across HTTP

Bad:

```text
BEGIN
SELECT ... FOR UPDATE
HTTP API call
parse response
send event
UPDATE
COMMIT
```

Why it fails:

```text
DB contention
+
network variability
+
external timeout
+
retry behavior
=
unpredictable lock duration
```

A payment provider taking 1 second today and 15 seconds tomorrow becomes a database concurrency problem.

---

# 35. Wrong Implementation #5 — Assuming Row Locks Guarantee Business Exclusivity Everywhere

Consider a business invariant spanning many rows:

```text
No more than 5 active reservations for a branch.
```

Locking one arbitrary reservation row does not protect the count.

You need an appropriate design such as:

```text
counter row + row lock
or
atomic aggregate update
or
constraint-based strategy
or
serializable transaction
or
other coordination object
```

The lock target must correspond to the invariant.

---

# 36. Wrong Implementation #6 — Retrying All Errors

Bad Node.js pattern:

```ts
catch (error) {
  return retry(() => runTransaction());
}
```

Why it fails:

```text
unique violation
foreign key violation
invalid input
permission error
syntax error
business-rule error
```

may all be permanent failures.

Retry only errors whose semantics justify retry.

Lock waits, deadlocks, serialization failures, and transaction aborts each require distinct handling.

# 37. Developer Mistakes

## Mistake 1 — Confusing `FOR UPDATE` with table locking

It does not mean every row or the entire relation becomes unavailable.

## Mistake 2 — Forgetting transaction scope

A row lock acquired in one transaction is not automatically held by a second pooled connection.

## Mistake 3 — Doing work after acquiring the lock but before the next SQL statement

Application code between SQL statements still consumes lock lifetime.

## Mistake 4 — Locking before defining the invariant

A lock is not a goal. Correctness is.

## Mistake 5 — Using the strongest lock unnecessarily

`FOR UPDATE` everywhere increases contention.

## Mistake 6 — Ignoring multi-row ordering

This creates avoidable deadlocks.

## Mistake 7 — Observing only relation locks in `pg_locks`

Row-lock waiters may show transaction-ID waits instead. citeturn681731search1

# 38. Vibe-Coding / AI-Generated Row-Locking Mistakes

AI-generated backend code often contains patterns like:

```ts
await db.transaction(async (tx) => {
  const user = await tx.user.findUnique({ where: { id } });
  const wallet = await tx.wallet.findUnique({ where: { userId: user.id } });

  // business logic

  await tx.wallet.update(...);
});
```

The code may look transactional but still be race-prone.

Common AI mistakes:

```text
"Add FOR UPDATE everywhere."

"All transactions should use row locks."

"Lock the user row because it is convenient."

"Use UPDATE after SELECT because transactions prevent races."

"Retry every lock-related error indefinitely."

"Keep the transaction open while calling another API."

"Select many rows FOR UPDATE just to be safe."

"Assume the ORM's transaction wrapper automatically locks records."

"Inspect pg_locks and look only for tuple locks."
```

Why these are dangerous:

```text
transaction != automatic correctness
row lock != universal serialization
ORM transaction != database invariant
stronger lock != better architecture
```

An expert reviews the invariant and conflict set first.

# 39. Node.js / NestJS Transaction Discipline

For PostgreSQL-backed NestJS services, a row-locking workflow should look conceptually like:

```ts
await dataSource.transaction(
  'READ COMMITTED',
  async (manager) => {
    const order = await manager.query(
      `
      SELECT id, status
      FROM orders
      WHERE id = $1
      FOR UPDATE
      `,
      [orderId],
    );

    // bounded local decision

    await manager.query(
      `
      UPDATE orders
      SET status = $1
      WHERE id = $2
      `,
      ['CONFIRMED', orderId],
    );
  },
);
```

The most important architectural rules are:

```text
same connection/session
same transaction
same transaction-scoped EntityManager / client
no pool checkout changes mid-transaction
no external network call while holding contested locks
short transaction duration
explicit error classification
```

A particularly dangerous bug is mixing clients:

```ts
const txClient = await pool.connect();
await txClient.query('BEGIN');

await repositoryUsingGlobalPool.save(entity); // wrong connection

await txClient.query('COMMIT');
```

The repository operation may run outside the locking transaction entirely.

# 40. Performance: Row Locks Are Not Free

Row-level locking can improve correctness but has costs.

Possible costs include:

```text
waiting
↓
longer transaction duration
↓
connection occupancy
↓
throughput reduction
```

And row-locking operations such as `SELECT FOR UPDATE` may modify tuple metadata, which can require disk writes. PostgreSQL explicitly documents this behavior. citeturn681731search5

Therefore compare:

```text
plain SELECT
vs
SELECT FOR UPDATE
```

not only by logical correctness but also by workload impact.

# 41. Throughput Thinking

Suppose one row represents a hot business object:

```text
branch inventory aggregate
```

and 1,000 requests per second need that same row.

A row lock correctly serializes conflicting access, but that row may become a throughput bottleneck.

Conceptually:

```text
1 hot row
    ↓
1 serialization point
    ↓
high contention
    ↓
queueing
```

At that point the architectural question becomes:

```text
Can the conflict set be reduced?
Can the aggregate be partitioned?
Can updates become commutative/atomic?
Can work be queued?
Can inventory be bucketed by branch/product?
Can a different data model avoid a single hot row?
```

The answer is workload-specific.

Do not “solve” hot-row contention by arbitrarily increasing connection pool size. That can increase the number of sessions waiting behind the same serialization point.

# 42. Connection Pools and Row-Lock Contention

Suppose:

```text
pool size = 100

1 transaction holds a hot row
80 transactions wait for it
```

Those waiting transactions can consume pool slots.

Now unrelated queries may wait for available connections even though they do not need the hot row.

Thus:

```text
row contention
→ connection pool occupancy
→ request latency
→ apparent database-wide slowness
```

This is why lock diagnosis should correlate:

```text
wait events
+
transaction age
+
pool usage
+
request latency
```

# 43. Timeouts and Lock Safety

A production system should consider:

```sql
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '5s';
```

Use carefully and according to the service's latency contract.

`lock_timeout` can prevent a request from waiting indefinitely for a contested lock.

But a timeout is not a correctness strategy by itself.

It simply converts:

```text
unbounded wait
```

into:

```text
controlled failure
```

The application still needs to classify and respond appropriately.

---

# 44. Lock Wait vs CPU Wait

Suppose an API goes from 100 ms to 2 seconds.

Do not immediately inspect query plans.

First ask:

```text
Is the backend waiting?
```

Look at:

```sql
SELECT
    pid,
    wait_event_type,
    wait_event,
    state,
    query
FROM pg_stat_activity
WHERE state <> 'idle';
```

A session waiting on a lock is a very different problem from a CPU-bound sequential scan.

This is a core production-debugging discipline:

> **Always identify what the server is waiting for before optimizing what it is executing.**

# 45. Security Considerations

Row locks are not authorization.

A user who can execute:

```sql
SELECT * FROM orders FOR UPDATE;
```

can potentially create denial-of-service through long-lived transactions even if they cannot modify the data.

Security review therefore includes:

```text
who can start transactions?
who can lock rows?
what rows are visible?
what rows can be mutated?
how long can requests keep transactions open?
what statement timeouts exist?
what tenant filtering is guaranteed?
```

For multi-tenant applications, row locks cannot compensate for a missing tenant predicate:

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;
```

If IDs are not globally unique or authorization is incomplete, the locking query can protect and mutate a row belonging to the wrong tenant.

The authorization boundary must remain explicit:

```sql
SELECT *
FROM orders
WHERE tenant_id = $tenant
  AND id = $id
FOR UPDATE;
```

---

# 46. Multi-Tenant Hot Rows

In a shared database, tenants can unintentionally contend on the same synchronization object.

For example:

```text
platform-wide counter row
```

Every tenant competes for one lock.

A better design may be:

```text
counter per tenant
```

or:

```text
counter per tenant + branch
```

This illustrates a broader architecture principle:

> **Concurrency partitioning should often follow the same dimensions as workload isolation.**

If tenants operate independently, a shared lock target can destroy that independence.

---

# 47. Financial / Ledger Use Case

Consider an account balance row:

```text
account_id = 1001
balance = 500000
```

A naive transfer service might:

```text
read balance
check sufficient funds
call downstream service
write balance
```

A production-grade ledger should usually make the financial invariant explicit through immutable entries and database constraints, while using row locks where a mutable balance or reservation state must be coordinated.

For example:

```text
Transaction
    |
    +-- lock account aggregate rows in deterministic order
    |
    +-- validate state
    |
    +-- insert immutable ledger entries
    |
    +-- update derived balance if the design uses one
    |
    +-- commit
```

The row lock protects concurrency during the transaction; it does not replace the ledger model.

---

# 48. Two-Row Operations: Deterministic Lock Ordering

For a transfer:

```text
Account A -> Account B
```

two concurrent transfers can deadlock:

```text
T1: lock A -> waits for B
T2: lock B -> waits for A
```

Instead order by immutable identity:

```sql
SELECT id, balance
FROM accounts
WHERE id IN ($1, $2)
ORDER BY id
FOR UPDATE;
```

Then process the result in that order.

The source business direction:

```text
A -> B
```

must not determine lock order.

The lock order should be deterministic:

```text
min(id) first
max(id) second
```

This pattern is broadly useful for any multi-row operation.

# 51. Query-Plan Interaction

`FOR UPDATE` can affect execution because the executor must identify and lock qualifying tuples.

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM inventory
WHERE product_id = 42
FOR UPDATE;
```

Inspect:

- number of rows examined;
- actual rows locked;
- join strategy if multiple tables are involved;
- buffer activity;
- execution time;
- whether the query scans substantially more rows than it locks.

Do not assume:

> “The filter is indexed, therefore the lock operation is cheap.”

An inefficient predicate can still inspect many tuples, and locking a large result set can create substantial contention.

# 52. Locking Joined Queries

Consider:

```sql
SELECT o.id, i.quantity
FROM orders o
JOIN inventory i ON i.product_id = o.product_id
WHERE o.id = $1
FOR UPDATE;
```

In multi-table queries, be precise about which relation should be row-locked and use PostgreSQL's relation-specific locking syntax where appropriate.

For example:

```sql
SELECT o.id, i.quantity
FROM orders o
JOIN inventory i ON i.product_id = o.product_id
WHERE o.id = $1
FOR UPDATE OF o;
```

This is an important production technique when you need to lock one side of a join without unnecessarily locking rows from every referenced relation.

The rule is:

> **Lock exactly the rows and relations that belong to the transaction's conflict set.**

# 53. Row Locking and Cascading Business Workflows

Suppose confirming an order changes:

```text
order
inventory
payment_attempt
shipment
```

A naive design may lock all four rows immediately.

A better design starts from the invariant:

```text
What must be mutually exclusive?
```

Maybe only:

```text
order state
+
inventory reservation
```

need pessimistic coordination.

Payment provider state may instead require:

```text
idempotency key
outbox
state machine
```

and shipment may be asynchronous.

Thus concurrency architecture should not expand lock scope merely because the workflow touches many entities.

# 54. Savepoints and Lock Lifetime

PostgreSQL's lock documentation notes that locks acquired after a savepoint can be released when rolling back to that savepoint, consistent with PostgreSQL's lock behavior. citeturn681731search5

Conceptually:

```sql
BEGIN;

SAVEPOINT s1;

SELECT *
FROM inventory
WHERE id = 42
FOR UPDATE;

ROLLBACK TO SAVEPOINT s1;
```

A lock acquired after the savepoint can be released by the rollback.

This matters in advanced workflows using nested transactional abstractions.

It does not mean application-level “nested transactions” are equivalent to independent top-level transactions.

# 55. Transaction Pooling and Session Boundaries

A row lock belongs to a PostgreSQL transaction/session context.

Therefore a transaction like:

```text
connection A
BEGIN
lock row 42
```

cannot be continued by arbitrarily sending the next SQL statement through:

```text
connection B
```

Connection pool abstractions have to preserve the transaction's physical session until commit/rollback.

This becomes especially important with transaction-pooling proxies or abstractions that multiplex connections.

The engineering requirement is:

```text
BEGIN
  ↓
all lock-dependent statements
  ↓
COMMIT / ROLLBACK
```

must execute in the same server-side transaction context.

# 58. Trade-Off Matrix

| Strategy | Strength | Contention | Complexity | Best fit |
|---|---|---:|---:|---|
| Atomic `UPDATE` | high for simple invariant | low | low | counters, state flags |
| `FOR UPDATE` | high local coordination | potentially high | medium | multi-step row decision |
| `FOR NO KEY UPDATE` | targeted | lower than strongest | medium | non-key mutation |
| `FOR SHARE` | protected read | medium | medium | shared consistency |
| `FOR KEY SHARE` | narrow key protection | low | high conceptually | FK/key identity |
| `SERIALIZABLE` | broad correctness | workload-dependent | high | cross-row invariants |
| Constraint | declarative | minimal at runtime | low | integrity rules |
| Application-only lock | unreliable across instances | unknown | high | generally avoid as sole DB guarantee |

The correct choice depends on the invariant and workload.

# 59. Row Locks vs Application Mutexes

An in-process mutex:

```ts
const mutex = new Mutex();
```

only coordinates requests sharing the same process and mutex instance.

In a horizontally scaled service:

```text
Node instance A
Node instance B
Node instance C
```

three mutexes exist unless the coordination is externalized.

A PostgreSQL row lock can coordinate across application instances because all of them interact with the same database transaction system.

But that does not mean PostgreSQL row locks should become a universal distributed mutex. The database still has a workload-specific contention limit.

# 60. Expert Reasoning Example

Question:

> Two requests update the same order. One should confirm it; another should cancel it. Should we use `FOR UPDATE`?

Weak answer:

> “Yes, because concurrent updates are dangerous.”

Acceptable answer:

> “A row lock can serialize the state transition, but an atomic conditional update may be simpler.”

Strong answer:

> “First define the state-machine invariant. If only `PENDING` may transition and the transition must be mutually exclusive, `UPDATE ... WHERE status = 'PENDING' RETURNING ...` may eliminate the explicit lock. Use `FOR UPDATE` when subsequent logic requires a protected multi-statement read/validate/write sequence.”

Expert answer:

> “Choose the minimal mechanism that proves the invariant. Compare atomic conditional DML, row locking, constraints, and isolation level. Then test the design under concurrent requests, measure lock waits and transaction duration, and verify retry behavior.”

# 61. Interview Questions

## Junior

### Q1. What does `SELECT ... FOR UPDATE` do?

It locks qualifying rows with `FOR UPDATE` row-lock strength until the transaction ends, preventing conflicting row operations from proceeding concurrently.

### Q2. Does `FOR UPDATE` lock the whole table?

No. It locks qualifying rows, while the statement also acquires the appropriate table-level lock.

### Q3. Does a row lock stop a normal `SELECT`?

Not in the ordinary sense. PostgreSQL's row locks block writers and incompatible lockers; MVCC allows ordinary readers to access visible row versions. citeturn681731search5

## Mid-Level

### Q4. When should you prefer an atomic `UPDATE` to `SELECT ... FOR UPDATE`?

When the invariant can be expressed completely in one DML statement.

### Q5. Why can a row lock appear as a transaction-ID wait in `pg_locks`?

Because row-lock state is stored in the tuple and a waiter commonly waits on the transaction ID of the transaction holding the row lock. citeturn681731search1

### Q6. Why does PostgreSQL have `FOR NO KEY UPDATE`?

To distinguish non-key updates from stronger operations and avoid unnecessarily blocking `FOR KEY SHARE` relationships. citeturn681731search4turn681731search5

## Senior

### Q7. Why is a long-lived row lock dangerous even if only one row is locked?

Because a hot row can become a serialization point, creating wait chains, increasing transaction duration, occupying pool connections, and amplifying latency.

### Q8. Why might `SELECT ... FOR UPDATE` generate more I/O than a plain `SELECT`?

Because PostgreSQL may need to modify tuple metadata to mark rows locked, which can cause disk writes. citeturn681731search5

## Staff

### Q9. How do you choose a lock target for a business invariant?

Identify the smallest synchronization object whose ownership fully covers the invariant's conflict set.

### Q10. How would you diagnose a 3-second API latency increase caused by row locking?

Correlate endpoint latency with `pg_stat_activity` wait events, identify blocked PIDs and blocker transactions, measure transaction ages and SQL, then reduce lock scope/duration or redesign the synchronization point.

## Principal

### Q11. When does row locking stop being the right architecture?

When a single synchronization object becomes a sustained hot spot, when the invariant spans broad predicate ranges, or when business throughput requires a model that avoids serializing every operation on one aggregate.

# 62. Trick Questions

### “`FOR UPDATE` makes the query serializable.”

False. It serializes conflicting operations on selected rows. It does not provide transaction-wide serializability.

### “If a row is locked, no one can read it.”

False. Ordinary MVCC reads generally do not wait merely because a row lock exists.

### “All row locks appear in `pg_locks` as tuple locks.”

False. Row-lock state is normally stored on the tuple, and waiters commonly appear as transaction-ID waits. citeturn681731search1

### “`FOR UPDATE` is always safer than `FOR NO KEY UPDATE`.”

Not as a general architecture rule. Stronger locking can create unnecessary contention.

### “More database connections reduce row-lock contention.”

Usually not. More connections can increase the number of sessions waiting behind the same hot row.

- Have concurrent-session tests been written?
- Have deadlock scenarios been exercised?
- Have long-running transaction scenarios been tested?
- Have retry and timeout paths been tested?

# 66. Final Mental Model

Remember this hierarchy:

```text
Business invariant
        ↓
Conflict set
        ↓
Synchronization object
        ↓
Atomic SQL / constraint / row lock / isolation level
        ↓
Transaction boundary
        ↓
Lock lifetime
        ↓
Wait behavior
        ↓
Operational impact
```

For row locks specifically:

```text
Plain SELECT
    ↓
MVCC visibility

SELECT ... FOR UPDATE / SHARE variants
    ↓
explicit row coordination

UPDATE / DELETE
    ↓
automatic row locking

Conflict
    ↓
wait / fail according to lock + isolation semantics

Transaction ends
    ↓
locks are released according to PostgreSQL lock-lifetime rules
```

The expert does not ask:

> “Where should I add `FOR UPDATE`?”

The expert asks:

> **“What concurrent actions must be mutually constrained, what is the smallest synchronization object that enforces that invariant, and what is the operational cost of holding that lock under real workload?”**

# 67. Chapter Summary

Row-level locks are one of PostgreSQL's most powerful concurrency primitives, but they work best when treated as precise synchronization mechanisms rather than generic “thread safety.”

The core ideas are:

1. MVCC and row locks solve different problems.
2. PostgreSQL has four row-lock strengths with a precise compatibility matrix.
3. `FOR UPDATE` is not the only row-lock mode.
4. `UPDATE` and `DELETE` automatically acquire row-level locks.
5. A normal `SELECT` is not equivalent to a lock-taking read.
6. Row locks are generally held until transaction end.
7. Locking the wrong row does not protect the right invariant.
8. Atomic SQL is often better than explicit locking for simple state changes.
9. Stronger locks create stronger contention and are not automatically better.
10. Row locks can become hot serialization points.
11. `pg_locks` does not provide a simple per-row lock list; row-lock waiters commonly appear as transaction-ID waits.
12. `pgrowlocks` is a useful forensic tool for direct row-lock inspection.
13. Multiple compatible row lockers can involve multixacts.
14. Long transactions turn local row locks into system-wide latency problems.
15. Node.js/NestJS applications must preserve the same physical transaction connection.
16. Multi-row operations should use deterministic lock ordering.
17. Row locks do not replace constraints, idempotency, or correct data modeling.
18. The right locking strategy is determined by the business invariant and workload, not by a generic rule such as “always use `FOR UPDATE`.”

> **Final principle:** A row lock is valuable only when it protects the correct synchronization object for the invariant you are trying to preserve. The strongest lock is not the safest design; the smallest correct conflict set usually produces the best combination of correctness, concurrency, and operability.
