# 03.6 — Read Phenomena

> **Phase 03 — Transactions & Concurrency**
>
> Read phenomena are the observable anomalies that can appear when concurrent transactions read and write data under different isolation semantics. Understanding them is the bridge between knowing isolation-level names and being able to prove whether a concurrent history is correct.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to:

- Define dirty reads, non-repeatable reads, phantom reads, and serialization anomalies precisely.
- Distinguish SQL-standard terminology from PostgreSQL's actual behavior.
- Build two-session timelines that reproduce concurrency phenomena.
- Explain why PostgreSQL's MVCC implementation prevents some phenomena without preventing every business-level race.
- Identify when `READ COMMITTED`, `REPEATABLE READ`, or `SERIALIZABLE` changes the result.
- Distinguish a read phenomenon from a lost update, write skew, deadlock, timeout, or serialization failure.
- Turn an observed anomaly into an evidence-driven diagnosis rather than a guess.
- Design application logic around the invariant actually being protected.

---

## 2. Core Definition

### Simple definition

A **read phenomenon** is an unexpected difference in what a transaction can observe because another concurrent transaction is modifying data.

### Engineering definition

A read phenomenon is a class of concurrent execution behavior in which the result of one or more reads depends on the interleaving and visibility rules of concurrent transactions.

### Expert definition

A phenomenon is best understood as a property of a concurrent history: which versions were visible to each statement, which writes conflicted, and whether the resulting committed history can be interpreted as a valid serial execution.

The important shift is:

```text
"What did this SELECT return?"
            ↓
"Which transaction versions were visible?"
            ↓
"What concurrent history produced that visibility?"
            ↓
"Was that history legal under the selected isolation level?"
            ↓
"Was the business invariant actually preserved?"
```

---

## 3. Mental Model

A transaction does not read an abstract timeless database.

It reads a **visibility-controlled version of the database**.

Think in terms of:

```text
Concurrent transactions
        │
        ├── Transaction A
        │      └── reads/writes
        │
        └── Transaction B
               └── reads/writes

                 ↓

        MVCC visibility rules
                 ↓

        statement / transaction snapshots
                 ↓

        observable history
                 ↓

      allowed / forbidden phenomenon
```

This is why simply memorizing anomaly names is insufficient. The same application code can behave differently under different isolation levels.

# 4. The Classic Phenomena

The commonly discussed phenomena include:

| Phenomenon | Core idea | PostgreSQL consequence |
|---|---|---|
| Dirty read | See uncommitted data | Not possible under PostgreSQL's implemented isolation behavior |
| Non-repeatable read | Same row can produce a different committed value on a later read | Possible at `READ COMMITTED`; prevented by `REPEATABLE READ` |
| Phantom read | A predicate can match a different set of rows later | PostgreSQL `READ COMMITTED` can see changes between statements; `REPEATABLE READ` uses a stable snapshot |
| Serialization anomaly | Concurrent execution produces a result that cannot be explained by a serial order | Must be prevented by stronger coordination, constraints, locks, or `SERIALIZABLE` |
| Lost update | One write unintentionally overwrites another | Depends on statement design and concurrency control; not reducible to the four classic phenomena |
| Write skew | Transactions update different rows after reading a shared condition | Important under snapshot-based isolation; `SERIALIZABLE` is designed to reject dangerous patterns |

Do not assume that the classic SQL anomaly table completely describes PostgreSQL concurrency. PostgreSQL uses MVCC and has implementation-specific behavior that matters to real systems. The PostgreSQL documentation explicitly explains that `READ COMMITTED` uses a fresh snapshot per command while `REPEATABLE READ` provides a stable transaction view, and that serializable transactions detect dangerous read/write patterns. citehttps://www.postgresql.org/docs/18/transaction-iso.html

# 5. Dirty Reads

## 5.1 What is a dirty read?

A dirty read occurs when Transaction B reads data written by Transaction A **before A has committed**.

Timeline:

```text
Transaction A              Transaction B
-------------              -------------
BEGIN
UPDATE balance = 900
                           SELECT balance
                           --> 900   ❌ dirty read
ROLLBACK
```

If B had observed `900`, it would have observed a value that never became committed reality.

## 5.2 PostgreSQL behavior

PostgreSQL does not expose another transaction's uncommitted row versions to ordinary SQL reads. PostgreSQL's `READ UNCOMMITTED` level behaves as `READ COMMITTED`; PostgreSQL therefore does not permit dirty reads in the SQL sense used by systems that allow them. citehttps://www.postgresql.org/docs/18/transaction-iso.html

This is a useful example of why a standard label and an implementation's actual semantics are not always identical.

## 5.3 Developer mistake

A developer may see:

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

and assume:

> "Now my reads can see uncommitted writes."

That inference is wrong for PostgreSQL.

Always verify the database's documented semantics instead of transferring mental models from another database engine.

# 6. Non-Repeatable Reads

## 6.1 Definition

A non-repeatable read occurs when a transaction reads the **same logical row** twice and observes different committed values because another transaction committed an update between those reads.

Example under `READ COMMITTED`:

```text
Transaction A              Transaction B
-------------              -------------
BEGIN
SELECT stock
--> 10
                           BEGIN
                           UPDATE stock SET stock = 7
                           COMMIT
SELECT stock
--> 7
```

The first statement and second statement can use different snapshots in `READ COMMITTED`.

PostgreSQL documents `READ COMMITTED` as the default isolation level and states that each command begins with a new snapshot reflecting transactions committed before that command began. citehttps://www.postgresql.org/docs/18/transaction-iso.html

## 6.2 Why this matters

Consider:

```sql
SELECT balance FROM accounts WHERE id = $1;

-- business decision in application

SELECT balance FROM accounts WHERE id = $1;
```

The application may accidentally assume that the second result is a re-check of the exact same database state.

It is not necessarily so under `READ COMMITTED`.

## 6.3 When it is acceptable

Many request/response workloads do not need a transaction-wide frozen view.

For example:

```text
GET dashboard
```

does not always require every statement to observe the exact same instant in time.

The correct question is not:

> "Can non-repeatable reads happen?"

It is:

> "Would a changing view violate my application's invariant?"

# 7. Phantom Reads

## 7.1 Definition

A phantom read traditionally describes a transaction executing the same predicate twice and observing a different **set of matching rows** because another transaction inserted, deleted, or otherwise changed rows relevant to the predicate.

Example:

```text
Transaction A              Transaction B
-------------              -------------
BEGIN
SELECT count(*)
FROM orders
WHERE status = 'pending';
--> 10
                           INSERT INTO orders(status)
                           VALUES ('pending');
                           COMMIT
SELECT count(*)
FROM orders
WHERE status = 'pending';
--> 11
```

## 7.2 PostgreSQL nuance

The simple textbook statement "REPEATABLE READ prevents phantom reads" needs context.

PostgreSQL's `REPEATABLE READ` provides a transaction-level snapshot, so successive ordinary queries use the same snapshot and therefore do not suddenly see newly committed rows from transactions that committed after that snapshot. PostgreSQL documents this as a stable view of the database for the transaction. citehttps://www.postgresql.org/docs/18/transaction-iso.html

However, the deeper issue is not the anomaly label. The important question is whether the transaction's **business decision remains valid in the presence of concurrent writes**.

A stable snapshot alone does not guarantee that the transaction's business rule is safe.

That leads directly to write skew and serialization anomalies.

# 8. Read Skew / Inconsistent Multi-Object View

A particularly useful engineering pattern is **read skew**: a transaction reads related pieces of information at different times and obtains a combination that may not correspond to a single coherent committed state.

Suppose a transfer should maintain:

```text
Alice balance + Bob balance = 10,000
```

Under a shifting statement-by-statement view, two independent reads can observe different committed states.

Bad conceptual pattern:

```sql
SELECT balance FROM accounts WHERE id = $alice;
-- concurrent transaction commits transfer
SELECT balance FROM accounts WHERE id = $bob;
```

The two answers may come from different visibility points.

The PostgreSQL documentation specifically warns that consistency checks can be difficult under `READ COMMITTED` because the view of the data shifts with each statement. citeturn285603search0

This matters far beyond banking:

- inventory + reservation counts
- order header + order lines
- branch stock + warehouse stock
- account + ledger summary
- workflow state + approval record
- tenant configuration + tenant feature state

# 9. Lost Update

## 9.1 Why it deserves separate treatment

A lost update is often grouped informally with read anomalies, but it has a distinct mechanism.

Example:

```text
Initial quantity = 10

Transaction A              Transaction B
-------------              -------------
SELECT quantity = 10       SELECT quantity = 10
calculate 9                 calculate 8
UPDATE quantity = 9        UPDATE quantity = 8
COMMIT                      COMMIT

Final quantity = 8
```

A's logical change was overwritten by B.

## 9.2 Better pattern: atomic update

Instead of:

```sql
SELECT quantity FROM stock WHERE product_id = $1;

-- calculate in application

UPDATE stock
SET quantity = $new_quantity
WHERE product_id = $1;
```

prefer an operation that expresses the invariant atomically:

```sql
UPDATE stock
SET quantity = quantity - $requested
WHERE product_id = $1
  AND quantity >= $requested
RETURNING quantity;
```

Now the database performs the condition and mutation as one statement.

The application can distinguish:

```text
row returned     → reservation succeeded
zero rows        → invariant was not satisfied
```

This is often stronger and simpler than increasing isolation indiscriminately.

# 10. Write Skew

## 10.1 Definition

Write skew is a concurrency anomaly in which two transactions read a shared condition, each concludes that its own write is safe, and then each writes a different row so that their combined committed result violates a multi-row invariant.

Classic example:

```text
Rule:
At least one doctor must remain on call.

Dr A is on call.
Dr B is on call.

Transaction A              Transaction B
-------------              -------------
read A = on                read A = on
read B = on                read B = on
"B is still on"             "A is still on"
UPDATE A = off              UPDATE B = off
COMMIT                      COMMIT

Result:
A = off
B = off                    ❌ invariant violated
```

No single row update necessarily violates a row-level constraint.

The problem exists across the set.

## 10.2 Why this is important in PostgreSQL

Snapshot-based isolation can allow transactions to make decisions from the same historical view while updating different rows.

This is exactly the type of business consistency problem for which PostgreSQL's serializable isolation uses dangerous-structure detection and can abort one transaction to prevent an invalid committed history. citeturn285603search0turn285603search12

## 10.3 Alternatives to `SERIALIZABLE`

Depending on the invariant, you may instead use:

- a stronger database constraint
- a unique/exclusion constraint
- explicit row locks
- a canonical aggregate row as a synchronization point
- an atomic statement
- application-level optimistic version checks

The right solution depends on the invariant and access pattern.

---

# 11. Serialization Anomaly

A **serialization anomaly** occurs when the committed outcome of concurrent transactions cannot be explained by executing those transactions one at a time in some order.

This is the deepest level of reasoning in this chapter.

Suppose two transactions each perform a consistency check and each produces a write that is individually valid but collectively impossible under every serial ordering.

Then the execution is not serializable.

PostgreSQL's `SERIALIZABLE` isolation level is designed to ensure that committed transactions have behavior equivalent to some serial execution by detecting dangerous read/write dependency patterns and rolling back a transaction when needed. citeturn285603search0turn285603search12

This leads to an essential production rule:

> **A serialization failure is not necessarily a system bug. It can be the database correctly rejecting a dangerous concurrent history.**

The application must be prepared to retry the entire transaction where appropriate.

---

# 12. Phenomenon vs Failure

Do not collapse every concurrency error into "a race condition."

| Symptom | Likely concept |
|---|---|
| Reads another transaction's uncommitted value | Dirty read |
| Same row changes between two statements | Non-repeatable read |
| Predicate's visible set changes | Phantom / shifting visibility |
| One logical write overwrites another | Lost update |
| Independent writes jointly violate a rule | Write skew |
| Committed outcome cannot map to a serial order | Serialization anomaly |
| Transaction waits forever until deadlock detector intervenes | Deadlock |
| Statement exceeds configured wait | Lock timeout / statement timeout |
| Serializable transaction is aborted | Serialization failure |
| Transaction sees older snapshot and cannot continue after conflict | Snapshot/update conflict |

Diagnosis starts by identifying the mechanism, not the error message alone.

---

# 13. PostgreSQL Isolation Comparison

A practical mental table:

| Behavior | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|---|---|---|---|
| Dirty reads | No | No | No |
| Snapshot per statement | Yes | No; transaction-level snapshot | Transaction-level serializable snapshot behavior |
| Stable ordinary read view | No | Yes | Yes |
| Concurrent business conflicts automatically serialized | No | No | Dangerous patterns can trigger serialization failure |
| Retry strategy may be needed | Sometimes | Yes for certain conflicts | Yes, explicitly expected |

PostgreSQL documents `READ COMMITTED` as the default and explains that `REPEATABLE READ` uses a stable snapshot, while `SERIALIZABLE` adds protection against dangerous concurrent patterns. citehttps://www.postgresql.org/docs/18/transaction-iso.html

Do not read the table as:

```text
SERIALIZABLE = magically correct application
```

You still need correctly designed transactions, constraints, authorization, and side-effect handling.

# 14. Phenomena and Business Invariants

The strongest design process starts from the invariant.

## Example: inventory cannot go negative

Naive:

```sql
SELECT quantity FROM inventory WHERE id = $1;
```

Application checks:

```text
if quantity >= requested
```

Then:

```sql
UPDATE inventory ...
```

This splits the invariant across multiple operations.

Better:

```sql
UPDATE inventory
SET quantity = quantity - $requested
WHERE id = $1
  AND quantity >= $requested
RETURNING quantity;
```

The invariant is now represented atomically.

---

# 15. Phenomena and Constraints

A business rule may be expressible as a database constraint.

For example, "two active reservations may not overlap" can often be expressed using an exclusion constraint rather than:

```text
SELECT whether conflict exists
        ↓
application decision
        ↓
INSERT
```

The second approach has a race window.

The first pushes the invariant into the database's concurrency-controlled integrity machinery.

This is one of the most important lessons from Phase 02:

> **Good schema design reduces the number of concurrency problems that the application has to solve manually.**

# 16. Two-Session Lab: Non-Repeatable Read

Use two `psql` sessions.

### Setup

```sql
CREATE TABLE demo_balance (
    id bigint PRIMARY KEY,
    balance integer NOT NULL
);

INSERT INTO demo_balance VALUES (1, 1000);
```

### Session A

```sql
BEGIN;

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT balance
FROM demo_balance
WHERE id = 1;
```

Observe:

```text
1000
```

### Session B

```sql
BEGIN;

UPDATE demo_balance
SET balance = 700
WHERE id = 1;

COMMIT;
```

### Session A again

```sql
SELECT balance
FROM demo_balance
WHERE id = 1;
```

Under `READ COMMITTED`, the second statement can see the newly committed value:

```text
700
```

Now repeat the experiment under `REPEATABLE READ`.

The transaction's ordinary snapshot remains stable, so the second read continues to use the earlier transaction snapshot. The exact behavior of a concurrent write conflict must still be understood separately from simple visibility. citeturn285603search12

# 17. Two-Session Lab: Predicate Change

### Session A

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT count(*)
FROM demo_balance
WHERE balance >= 1000;
```

### Session B

Insert or update a qualifying row and commit.

### Session A

Run the same predicate again.

The result may differ because the statement can acquire a newer snapshot in `READ COMMITTED`.

Repeat under `REPEATABLE READ` and compare the result.

The purpose of this exercise is not memorization. It is to train your ability to associate:

```text
statement
→ snapshot
→ visible versions
→ result
```

# 18. Read Phenomena in Node.js / NestJS

Consider this anti-pattern:

```ts
const inventory = await repo.findOne({ where: { id } });

if (inventory.quantity >= requested) {
  inventory.quantity -= requested;
  await repo.save(inventory);
}
```

Problems may include:

- stale reads
- lost updates
- concurrent overselling
- incorrect retry behavior
- inconsistent transaction scope

A stronger repository method can express the invariant directly:

```sql
UPDATE inventory
SET quantity = quantity - $1
WHERE id = $2
  AND quantity >= $1
RETURNING id, quantity;
```

The service then interprets the result rather than reconstructing concurrency control in JavaScript.

# 19. External Side Effects

A transaction can correctly reject a dangerous history while the application still produces an incorrect external side effect.

Bad:

```text
BEGIN
reserve stock
call payment provider
commit
```

What happens if:

```text
payment succeeds
transaction aborts
```

or:

```text
transaction commits
external call fails
```

The phenomenon is no longer only a database isolation problem.

You now have a distributed consistency problem.

The correct architecture often involves:

```text
DB transaction
  ├── durable state change
  └── outbox event
          ↓
      async worker
          ↓
   external side effect
```

Isolation levels cannot make an external HTTP call transactional with PostgreSQL.

# 20. Evidence-Driven Debugging

When a concurrency bug is reported, collect evidence.

Useful signals include:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    backend_xid,
    backend_xmin,
    query
FROM pg_stat_activity
WHERE state <> 'idle';
```

And:

```sql
SELECT
    pid,
    locktype,
    relation::regclass,
    page,
    tuple,
    virtualxid,
    transactionid,
    mode,
    granted
FROM pg_locks;
```

PostgreSQL documents transaction and lock identifiers in `pg_locks`, including `virtualxid` and `transactionid` for currently executing transactions. citeturn285603search8

Reconstruct the timeline:

```text
T0: A BEGIN
T1: A SELECT
T2: B BEGIN
T3: B UPDATE
T4: B COMMIT
T5: A SELECT
T6: A COMMIT
```

Then ask:

1. Which isolation level?
2. Which snapshot did each statement use?
3. Which rows/versions were visible?
4. Which transaction committed first?
5. Did the transaction wait?
6. Did a constraint enforce an invariant?
7. Could the history be serialized?
8. Was the observed result actually forbidden?

# 21. Common Developer Mistakes

## Mistake 1 — "Transactions automatically prevent races"

False.

Transactions provide atomicity and visibility boundaries, but the correctness of concurrent decisions depends on isolation, locking, constraints, and statement design.

## Mistake 2 — "A transaction gives one stable snapshot"

Not necessarily.

At PostgreSQL `READ COMMITTED`, each command can use a fresh snapshot. citeturn285603search0turn285603search1

## Mistake 3 — "Repeatable Read means fully serializable"

False.

PostgreSQL's `REPEATABLE READ` provides a stable snapshot but does not provide the same guarantee as `SERIALIZABLE`. citeturn285603search12

## Mistake 4 — "Locking one row fixes a multi-row invariant"

Only when the chosen lock actually covers every conflicting execution.

## Mistake 5 — "Add more isolation"

Isolation is not a substitute for schema design.

Sometimes the best solution is:

```text
constraint
```

rather than:

```text
SERIALIZABLE everywhere
```

## Mistake 6 — "The ORM transaction decorator is enough"

Not unless you understand:

- actual transaction boundaries
- connection ownership
- isolation level
- generated SQL
- lock behavior
- retry semantics

# 22. AI / Vibe-Coding Failure Modes

AI-generated code frequently produces patterns like:

```ts
const row = await getRow();
if (row.available) {
  await updateRow();
}
```

The code looks reasonable sequentially.

Under concurrency:

```text
request A reads available
request B reads available
A updates
B updates
```

The missing reasoning is not syntax. It is the missing concurrent history.

### Red flags in generated code

- separate `SELECT` + `UPDATE` for a conditional invariant
- no explicit transaction around multi-step mutation
- no isolation strategy
- no retry for serialization failures
- transaction held across external HTTP calls
- generic catch-and-retry without idempotency
- lock acquisition in inconsistent order
- assuming ORM `save()` is atomic business logic
- checking a predicate and then writing a different row

### Expert response to AI-generated concurrency code

Ask:

> What happens if two requests execute these statements at the same time?

Then write the timeline.

# 23. Production Scenario — Jewellery ERP

Suppose a jewellery ERP has:

```text
item
inventory_balance
reservation
invoice
payment
```

A salesperson reserves a unique jewellery item while another branch attempts to reserve the same item.

Naive flow:

```text
SELECT item available
        ↓
application decides available
        ↓
INSERT reservation
```

Two requests can both pass the check.

Better design combines:

```text
transaction
+ appropriate row/constraint protection
+ unique business key
+ conflict handling
+ idempotency
```

For a unique physical item, the strongest invariant may be expressible directly as a constraint rather than a pre-check.

For aggregate stock:

```sql
UPDATE inventory_balance
SET available_qty = available_qty - $qty
WHERE branch_id = $branch_id
  AND item_id = $item_id
  AND available_qty >= $qty
RETURNING available_qty;
```

The key is that the database performs the eligibility check and mutation atomically.

# 24. Decision Framework

When you see a concurrency anomaly:

```text
1. Identify the invariant
        ↓
2. Identify the conflicting transactions
        ↓
3. Draw the exact timeline
        ↓
4. Identify snapshots / visibility
        ↓
5. Determine the observed phenomenon
        ↓
6. Ask whether the result is actually forbidden
        ↓
7. Prefer the narrowest correctness mechanism
```

Candidate mechanisms:

```text
constraint
atomic SQL
row lock
optimistic version
transaction isolation
SERIALIZABLE + retry
architectural redesign
```

Do not jump straight to the strongest tool.

# 25. Testing Strategy

Concurrency tests should deliberately create overlap.

Do not rely only on sequential unit tests.

Useful techniques:

### Barrier synchronization

Pause both transactions at a controlled point:

```text
A reaches barrier
B reaches barrier
release both
observe outcome
```

### Failure injection

Inject delays between:

```text
SELECT
→ decision
→ UPDATE
```

### Repeated stress

Run the same history many times.

### Property-based reasoning

Instead of asserting only a particular final number, assert the invariant:

```text
quantity >= 0
```

or:

```text
sum(debits) = sum(credits)
```

### Production-like connection behavior

Use real pooled connections, not a single mock transaction object.

# 26. Performance Considerations

Preventing anomalies has a cost.

Potential costs include:

- waiting for locks
- transaction aborts
- retries
- increased application latency
- reduced throughput
- longer transaction lifetime
- contention on hot rows

But the correct comparison is:

```text
cost of correctness mechanism
vs
cost of corrupted business state
```

A false optimization that increases throughput while allowing overselling, duplicate reservations, or financial inconsistency is not an optimization.

Measure:

- transaction latency
- lock wait time
- rollback rate
- serialization failure rate
- retry rate
- deadlocks
- hot-row contention
- throughput

# 28. Security Considerations

Concurrency correctness and security overlap.

A race condition can become an authorization bug.

Example:

```text
check user may approve invoice
        ↓
concurrent change of invoice owner/tenant
        ↓
approval mutation
```

Authorization conditions that matter to the mutation should be enforced within the same transaction and, where practical, represented in the actual SQL predicate or database constraints.

For multi-tenant systems, every concurrency-sensitive query must preserve tenant boundaries.

The worst possible outcome is:

```text
correct concurrency
+ wrong tenant scope
= consistently wrong security
```

You can choose between constraints, atomic updates, locks, and isolation without unnecessary serialization.

### L6 — Architecture

You can design concurrency-safe workflows across transactions, queues, retries, and external systems.

### L7 — Internal Mastery

You can reason from snapshots, dependencies, invariants, and transaction histories without relying on memorized anomaly tables.

---

# 33. The Central Principle

> **Concurrency correctness is about histories, not individual statements.**
>
> A statement can be perfectly correct in isolation and still participate in an invalid concurrent history. The engineer's job is to identify the invariant, model the competing transactions, understand visibility, and choose the narrowest mechanism that prevents the forbidden history.
