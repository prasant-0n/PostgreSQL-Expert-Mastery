# 2. The Central Mental Model

The most important model is not “two queries are waiting.” It is:

```text
A waits for B
B waits for C
C waits for A

        ↓

     CYCLE
        ↓

    DEADLOCK
```

A normal wait is a chain:

```text
T1 → T2 → T3
```

There is progress potential because T3 can eventually release its lock.

A deadlock is different:

```text
T1 → T2
↑     ↓
└─────┘
```

No participant can make progress without another participant first giving up a lock.

The central principle is:

> **Contention is waiting; deadlock is circular waiting.**

---

# 3. Precise Definition

## 3.1 Simple definition

A deadlock occurs when transactions are waiting for one another in a cycle, so none of them can continue on its own.

## 3.2 Engineering definition

A database deadlock exists when the current lock dependency graph contains a directed cycle: transaction A waits for a resource held by B, B waits for another resource held by A, or the dependency extends through additional transactions and eventually returns to A.

## 3.3 Expert definition

A PostgreSQL deadlock is a cycle in the effective wait-for relationships created by lockable objects and transaction dependencies. PostgreSQL does not permit the system to remain indefinitely in such a cycle; after a deadlock check determines that the dependency graph contains a cycle, the server aborts a transaction to break the cycle. The selected victim cannot be predicted safely by application logic and must not be relied upon. citeturn348494search5turn348494search12

---

# 4. Deadlock vs Lock Contention

These concepts must remain separate.

## Ordinary contention

```text
T1 owns row A
T2 requests row A

T2 waits

T1 commits
T2 continues
```

This is not a deadlock.

## Deadlock

```text
T1 owns A
T2 owns B

T1 requests B
T2 requests A

T1 waits for T2
T2 waits for T1
```

Both are blocked.

PostgreSQL's deadlock handling exists precisely because waiting alone is not the problem; the cycle is. citeturn348494search5

---

# 5. First Principles: Why Deadlocks Exist

Deadlocks emerge from a combination of three facts:

1. transactions can hold locks while requesting additional locks;
2. locks can conflict;
3. different transactions can acquire resources in different orders.

The classic pattern is:

```text
Resource A
Resource B

T1: lock A → request B
T2: lock B → request A
```

Neither transaction is inherently “wrong” in isolation.

The problem exists in the interaction:

```text
T1 ordering: A → B
T2 ordering: B → A
```

Therefore deadlock prevention is frequently an architectural ordering problem rather than a SQL-syntax problem.

---

# 6. A Canonical Two-Row Deadlock

Create a simple table:

```sql
CREATE TABLE accounts (
    id bigint PRIMARY KEY,
    balance numeric(18,2) NOT NULL
);

INSERT INTO accounts(id, balance)
VALUES
    (1, 1000),
    (2, 1000);
```

Session T1:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

T1 now owns the relevant row lock.

Session T2:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 50
WHERE id = 2;
```

T2 now owns the relevant row lock.

T1 continues:

```sql
UPDATE accounts
SET balance = balance + 100
WHERE id = 2;
```

T1 waits for T2.

T2 continues:

```sql
UPDATE accounts
SET balance = balance + 50
WHERE id = 1;
```

T2 waits for T1.

Graph:

```text
T1 --waits--> T2
 ^            |
 |            |
 +------------+
```

PostgreSQL detects the cycle and aborts one transaction. The other may then proceed. citeturn348494search5

---

# 7. Why “Both Transactions Need Both Rows” Is Not the Problem

This is subtle.

The following can be safe:

```text
T1: lock 1, then 2
T2: lock 1, then 2
```

because T2 may wait for T1 on row 1, but there is no cycle:

```text
T2 → T1
```

Once T1 commits:

```text
T2 continues
```

The dangerous pattern is inconsistent ordering:

```text
T1: 1 → 2
T2: 2 → 1
```

Therefore:

> **Multiple locks are not inherently dangerous. Inconsistent acquisition order is dangerous.**

---

# 8. Lock Ordering: The Most Powerful Prevention Technique

Choose a canonical order.

For numeric identifiers:

```text
always lock smaller id first

1 → 2
```

Then both transactions converge on the same order:

```sql
SELECT id
FROM accounts
WHERE id IN (1, 2)
ORDER BY id
FOR UPDATE;
```

Now competing transactions both attempt:

```text
1 → 2
```

One may wait, but they do not form the classic cycle.

This pattern generalizes:

```text
tenant_id ascending
resource_id ascending
account_id ascending
inventory_location ascending
```

The ordering key must be deterministic and shared by all code paths that can participate in the same conflict domain.

---

# 9. Why `ORDER BY` Alone Is Not a Magical Guarantee

This is a common AI-generated oversimplification:

> “Add `ORDER BY id` and deadlocks are impossible.”

That is false.

The actual requirement is stronger:

```text
Every conflicting transaction
        |
        +--> acquires the same resources
        |
        +--> in the same canonical order
```

You can still create deadlocks if another code path:

- locks a different table first;
- acquires an advisory lock before row locks;
- updates rows through a different access path;
- invokes a trigger that acquires another lock;
- touches a parent row after locking a child row;
- uses a different resource ordering rule.

Therefore review the **whole lock footprint**, not one visible SQL clause.

---

# 10. Deadlocks Across Tables

Rows are not the only source.

Example:

```text
orders
inventory
```

T1:

```text
lock order 101
lock inventory item 7
```

T2:

```text
lock inventory item 7
lock order 101
```

The same cycle appears:

```text
T1 owns order
T1 waits for inventory

T2 owns inventory
T2 waits for order
```

This is why service methods with apparently unrelated SQL statements can deadlock.

A transaction is a **sequence of resource acquisitions**, not merely a list of statements.

---

# 11. Triggers Can Create Invisible Lock Dependencies

Suppose:

```sql
UPDATE orders ...;
```

looks like it only changes `orders`.

A trigger may also:

```text
UPDATE customer_totals
UPDATE audit_rows
UPDATE inventory
```

Now the real lock footprint is larger than the application code immediately suggests.

A deadlock investigation must therefore consider:

```text
SQL
+ triggers
+ foreign-key enforcement
+ indexes
+ generated behavior
+ advisory locks
+ application-level coordination
```

The database's effective dependency graph matters more than the surface syntax.

---

# 12. Foreign Keys and Deadlock Reasoning

Referential integrity can participate in locking behavior.

For example:

```text
parent
child
```

Operations affecting referenced keys may require stronger coordination than a developer expects from the visible `UPDATE` or `DELETE` statement.

A production diagnosis therefore should not assume:

> “Only the row in the table named in my SQL can be involved.”

The lock graph can include related resources created by referential-integrity enforcement.

This is especially important for workflows that update parent and child entities in different orders across different endpoints.

---

# 13. Advisory Locks Can Deadlock Too

Application-defined advisory locks are still locks.

Suppose:

```sql
SELECT pg_advisory_xact_lock(100);
```

T1 holds key 100 and requests 200.

T2 holds key 200 and requests 100.

Then:

```text
T1 → T2
T2 → T1
```

A common mistake is to think advisory locks are exempt because PostgreSQL cannot interpret their business meaning.

It cannot interpret your meaning, but it still tracks the lock dependency.

Canonical ordering applies here too:

```text
lock advisory key 100 before 200
```

for every participating transaction.

---

# 14. Self-Deadlocks and Recursive Application Flows

Application logic can accidentally re-enter a resource acquisition path.

For example:

```text
service A
  ↓
transaction
  ↓
lock resource X
  ↓
call service B
  ↓
service B tries to coordinate X/Y differently
```

Depending on the locking mechanism and transaction structure, re-entry can produce unexpected conflicts or, more commonly, lock retention that creates cycles with another transaction.

This is why transaction boundaries should be explicit and service-layer lock ownership should be documented.

---

# 15. The Wait-For Graph

A powerful diagnostic abstraction is:

```text
Transaction nodes
        |
        +--> edge A → B means A waits for something held by B
```

Example:

```text
T1 → T2
T2 → T3
T3 → T4
```

This is a wait chain.

Add:

```text
T4 → T1
```

and the graph becomes cyclic.

That cycle is the deadlock.

A production engineer should be able to look at a lock incident and mentally transform:

```text
pg_locks rows
+
pg_stat_activity
+
blocking relationships
```

into:

```text
who owns what?
who waits for what?
what cycle exists?
what transaction can be safely sacrificed?
why did the acquisition order diverge?
```

---

# 16. How PostgreSQL Detects Deadlocks

PostgreSQL does not need to perform an expensive global deadlock search for every instantaneous lock wait.

The server waits for a configured amount of time before running a deadlock check.

That interval is controlled by:

```sql
SHOW deadlock_timeout;
```

The current PostgreSQL documentation describes `deadlock_timeout` as the amount of time to wait on a lock before checking for a deadlock. The default is one second in PostgreSQL 18 documentation. The check is relatively expensive, so PostgreSQL does not run it on every wait. citeturn348494search12

Conceptually:

```text
lock requested
     |
     v
wait starts
     |
     +---- lock released quickly? ----> continue
     |
     +---- still waiting after deadlock_timeout
                         |
                         v
                  run deadlock check
                         |
              +----------+----------+
              |                     |
          no cycle                cycle
              |                     |
              v                     v
           keep waiting        abort one txn
```

This explains why a deadlock does not necessarily produce an error the instant the second conflicting request appears.

---

# 17. `deadlock_timeout` Is Not a Deadlock Deadline

This misconception is extremely common.

`deadlock_timeout = 1s` does **not** mean:

> “PostgreSQL kills any transaction waiting for one second.”

It means:

> “After waiting this long on a lock, PostgreSQL performs a deadlock check.”

A normal lock wait can last longer than `deadlock_timeout` if no cycle exists.

For example:

```text
T1 owns row
T2 waits
T1 does expensive work
T1 commits after 4 seconds
```

No deadlock exists.

T2 may simply wait.

---

# 18. Why PostgreSQL Does Not Check for Deadlocks Continuously

Deadlock detection is more expensive than merely sleeping on a lock.

Most waits in a healthy application are not deadlocks:

```text
short lock wait
```

If the server performed a full deadlock analysis for every short-lived wait, the overhead could be wasteful.

The intended optimization is therefore:

```text
assume most waits are benign
        ↓
wait briefly
        ↓
check when the wait becomes suspicious
```

The PostgreSQL documentation explicitly describes this trade-off. Increasing `deadlock_timeout` reduces unnecessary deadlock checks but delays detection of real deadlocks. citeturn348494search12

---

# 19. `deadlock_timeout` and `log_lock_waits`

PostgreSQL also uses `deadlock_timeout` as the threshold associated with `log_lock_waits`.

When:

```sql
SET log_lock_waits = on;
```

PostgreSQL can emit log messages when a session has waited longer than `deadlock_timeout` for a lock. The current documentation explicitly notes this relationship and recommends shorter values during locking investigations when appropriate. citeturn348494search1turn348494search12

This makes `deadlock_timeout` operationally important even when no deadlock occurs.

---

# 20. `lock_timeout` vs `statement_timeout` vs `deadlock_timeout`

These settings solve different problems.

| Setting | Meaning |
|---|---|
| `deadlock_timeout` | How long to wait before checking whether a deadlock exists |
| `lock_timeout` | Maximum time a statement may wait for an individual lock acquisition |
| `statement_timeout` | Maximum execution time allowed for the statement as a whole |

`lock_timeout` applies to explicit and implicit lock acquisition waits, and the current PostgreSQL documentation warns that it is distinct from `statement_timeout`. citeturn348494search0

Do not use them interchangeably.

A useful mental model is:

```text
waiting on lock
     |
     +--> deadlock_timeout --> inspect for cycle
     |
     +--> lock_timeout ------> abort lock wait if exceeded

entire statement
     |
     +--> statement_timeout -> abort statement if total execution exceeds limit
```

---

# 21. PostgreSQL Chooses a Victim

When PostgreSQL finds a deadlock cycle, one transaction must be aborted to break it.

Do not write application logic assuming:

```text
“the younger transaction always loses”
```

or:

```text
“the transaction that requested the last lock loses”
```

The exact victim-selection behavior is not an application contract. PostgreSQL documentation explicitly warns that which transaction is aborted is difficult to predict and should not be relied upon. citeturn348494search5

Therefore application code should be prepared for **any participating transaction attempt** to fail with a deadlock error.

---

# 22. SQLSTATE `40P01`

PostgreSQL reports deadlock detection with SQLSTATE:

```text
40P01
```

This is different from serialization failure:

```text
40001
```

That distinction matters for application behavior and observability.

A useful failure taxonomy is:

```text
40P01  deadlock detected
40001  serialization failure
55P03  lock_not_available / lock timeout style conditions
57014  statement timeout / query cancellation class
```

Exact handling should still inspect the database driver error code rather than relying only on free-form error text.

---

# 23. Deadlock vs Serialization Failure

The two can both look like “Postgres aborted my transaction,” but the mechanism is different.

## Deadlock

```text
actual lock dependency cycle
        ↓
server must break cycle
        ↓
victim transaction aborted
```

## Serialization failure

```text
requested isolation semantics cannot safely permit this execution
        ↓
transaction aborted
```

You therefore need to ask:

```text
Was there a lock cycle?
OR
Was there a serializability conflict?
```

Do not build one generic “retry anything” handler.

---

# 24. Correct Deadlock Retry Pattern

At the application boundary:

```text
start transaction
     |
     +--> perform all reads/writes
     |
     +--> COMMIT
             |
       +-----+------+
       |            |
    success      40P01
       |            |
       v            v
     return     rollback/cleanup
                    |
                    v
                retry whole unit
```

The retry unit should encompass the full logical transaction.

Do not merely repeat the failed SQL statement while keeping the rest of the previous transaction state.

Why?

Because the original attempt's lock graph and intermediate state are no longer valid after the transaction is aborted.

---

# 25. Retry Budget

Never implement:

```ts
while (true) {
  try {
    await runTransaction();
    break;
  } catch (err) {
    // retry
  }
}
```

That can convert a concurrency incident into a retry storm.

Use bounded retries:

```text
attempt 1
attempt 2
attempt 3
then fail
```

Also use backoff and jitter:

```text
delay = base * 2^attempt + random_jitter
```

The purpose is to reduce synchronized re-entry into the same conflict pattern.

---

# 26. Why Retrying Can Reproduce the Same Deadlock

Suppose 100 requests all execute:

```text
lock A
lock B
```

while another code path executes:

```text
lock B
lock A
```

If every failed request retries immediately, the system can repeatedly recreate the same interleaving.

Therefore:

```text
retry without redesign
        ↓
may improve availability temporarily
        ↓
but does not remove structural deadlock risk
```

The right goal is:

```text
retry transient collision
+
remove recurring lock-order inversion
```

---

# 27. External Side Effects Make Deadlock Retry Dangerous

Consider:

```text
BEGIN
UPDATE order
CALL payment provider
UPDATE ledger
COMMIT
```

Suppose a deadlock occurs after the external payment call.

The database transaction may roll back, but the payment provider may already have accepted the charge.

A naive retry can charge again.

Therefore:

```text
Database transaction
        |
        +--> durable state transition
        |
        +--> outbox / idempotency boundary
        |
        +--> external side effect
```

Deadlock retry must be designed together with idempotency and transactional messaging.

This becomes even more important in payment, inventory reservation, fulfillment, and ledger systems.

# 28. Node.js / `pg` Transaction Pattern

A robust application shape is:

```ts
async function withTransaction<T>(
  pool: Pool,
  fn: (client: PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();

  try {
    await client.query('BEGIN');

    const result = await fn(client);

    await client.query('COMMIT');
    return result;
  } catch (error) {
    try {
      await client.query('ROLLBACK');
    } finally {
      client.release();
    }

    throw error;
  }
}
```

For retryable deadlocks, the retry loop should surround the **whole call** to `withTransaction`, not merely one SQL query.

Conceptually:

```ts
for (let attempt = 0; attempt < maxAttempts; attempt++) {
  try {
    return await withTransaction(pool, businessOperation);
  } catch (error) {
    if (!isDeadlock(error) || attempt === maxAttempts - 1) {
      throw error;
    }

    await backoffWithJitter(attempt);
  }
}
```

Always release the connection even when rollback itself fails.

# 29. Connection Pool Amplification

A deadlock involves a small number of transactions directly, but the impact can spread through the pool.

Example:

```text
20 pooled connections
        |
4 transactions become blocked
        |
requests keep arriving
        |
application creates more waiting work
        |
latency rises
        |
connection utilization rises
```

Deadlocks can therefore manifest at the API layer as:

```text
high p95 latency
connection-pool saturation
request timeouts
queue growth
CPU not necessarily high
```

The visible symptom may be much larger than the original lock cycle.

---

# 30. Long Transactions Increase the Cost of Deadlocks

Long transaction lifetime means:

```text
locks held longer
        +
more resources accumulated
        +
more opportunities for dependency inversion
        =
larger deadlock surface
```

Common causes:

- external API calls inside transactions;
- unnecessary application computation;
- slow network calls;
- user interaction accidentally inside a transaction;
- large batch updates;
- excessive ORM entity traversal;
- waiting for unrelated resources.

A deadlock prevention strategy should therefore also minimize transaction scope.

---

# 31. The Hidden Risk of “Convenient” ORM Transactions

ORM code may hide SQL order.

Example:

```ts
await manager.save(order);
await manager.save(inventory);
```

Another service may do:

```ts
await manager.save(inventory);
await manager.save(order);
```

The source code looks innocent.

The database sees:

```text
resource O → resource I
resource I → resource O
```

The correct review question is not:

> “Does this function use a transaction?”

It is:

> **“What resources can this transaction acquire, and in what order?”**

---

# 32. Deadlocks from Batch Processing

Suppose a worker processes IDs:

```text
[10, 11, 12]
```

another worker processes:

```text
[12, 11, 10]
```

Both lock rows as encountered.

This creates an ordering inversion.

Canonicalize the batch:

```sql
SELECT id
FROM inventory
WHERE id = ANY($1)
ORDER BY id
FOR UPDATE;
```

Then process in the same order.

The principle applies to:

- queue workers;
- bulk price updates;
- reconciliation jobs;
- stock adjustments;
- order fulfillment;
- ledger postings.

---

# 33. Deadlocks in Jewellery ERP Workflows

Consider a jewellery ERP transfer:

```text
Branch A
  ↓
stock item / lot
  ↓
transfer order
  ↓
ledger entry
```

One workflow may lock:

```text
transfer → source stock → destination stock
```

while another locks:

```text
source stock → destination stock → transfer
```

A third workflow may lock ledger state first.

The problem is not a single SQL query.

It is the **global resource ordering across workflows**.

A production-grade design should define canonical ordering rules such as:

```text
tenant
→ transfer
→ stock locations ascending
→ item/lot IDs ascending
→ ledger
```

The exact order must be chosen from the application's real dependency graph and then applied consistently across all code paths.

---

# 34. Multi-Tenant Deadlocks

Multi-tenant systems add another dimension:

```text
tenant A resources
+
tenant B resources
+
shared catalog/configuration resources
```

A transaction that normally stays inside one tenant may touch a shared table such as:

```text
tenant_settings
pricing_rules
sequence/control rows
auditing tables
```

This can produce cross-tenant lock interactions.

Canonical ordering should include shared resources explicitly rather than assuming tenant isolation eliminates deadlocks.

# 35. `pg_locks`: Start With Evidence

PostgreSQL's `pg_locks` view exposes current lock information, including lockable object identity, requested mode, process ownership, and whether a lock is granted. A waiting lock has `granted = false`. The current documentation notes that lockable objects include relations, pages, tuples, transaction IDs, and other database objects. citeturn348494search4

A useful investigation query is:

```sql
SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.state,
    a.wait_event_type,
    a.wait_event,
    a.xact_start,
    a.query_start,
    l.locktype,
    l.mode,
    l.granted,
    l.relation,
    l.page,
    l.tuple,
    l.transactionid,
    l.virtualxid
FROM pg_stat_activity AS a
JOIN pg_locks AS l
  ON l.pid = a.pid
WHERE a.datname = current_database()
ORDER BY a.xact_start NULLS LAST, a.pid;
```

This is not yet the full deadlock graph, but it gives the raw evidence needed to build one.

---

# 36. `pg_blocking_pids()` for Immediate Blocking Relationships

A useful helper is:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    query,
    wait_event_type,
    wait_event,
    xact_start
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

Interpretation:

```text
pid 101 waits for [102]
pid 102 waits for [103]
pid 103 waits for [101]
```

You have found a cycle.

The essential skill is not memorizing this query. It is understanding why the cycle exists and which application code path created each edge.

# 37. Transaction-ID Waiting

A subtle but important detail is that a session can wait on another transaction's ID rather than simply appearing to wait on a visible tuple lock.

PostgreSQL documentation explains that current transactions expose `virtualxid` and, for read-write transactions, usually permanent `transactionid` entries in `pg_locks`; processes may wait on transaction IDs when they need another transaction to end. citeturn348494search6turn348494search4

Therefore:

> **“I don't see the row lock I expected” does not prove there is no blocking dependency.**

Inspect transaction IDs and wait events as part of forensic analysis.

---

# 38. PostgreSQL Logs Are Often the Best Deadlock Evidence

For actual deadlocks, logs can preserve information that disappears after the transaction aborts.

Enable suitable logging/monitoring and inspect:

```text
time
pid
user
transaction context
application name
relation/object
lock mode
wait relationship
SQL statements
```

For lock investigation, `log_lock_waits` is particularly useful because PostgreSQL can log waits that exceed `deadlock_timeout`. The documentation explicitly describes it as useful for determining whether lock waits are causing poor performance. citeturn348494search1

A production incident should capture logs before the evidence is gone.

# 39. Evidence-Driven Deadlock Investigation

Use this sequence:

```text
1. Confirm the error code
        ↓
2. Identify affected endpoints/jobs
        ↓
3. Correlate application request IDs
        ↓
4. Inspect PostgreSQL logs
        ↓
5. Reconstruct transaction timelines
        ↓
6. Identify held resources
        ↓
7. Identify requested resources
        ↓
8. Draw the wait-for graph
        ↓
9. Find the ordering inversion
        ↓
10. Fix the resource ordering / scope
        ↓
11. Keep bounded retry as resilience
        ↓
12. Measure recurrence
```

Do not stop at:

> “We saw `deadlock detected`, so PostgreSQL is slow.”

The deadlock error is evidence of a concurrency cycle, not a generic performance diagnosis.

# 40. Reproducing a Deadlock Deterministically

Use two database sessions.

### Session A

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 10
WHERE id = 1;

-- pause here
```

### Session B

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 20
WHERE id = 2;

-- pause here
```

### Session A

```sql
UPDATE accounts
SET balance = balance + 10
WHERE id = 2;
```

A now waits.

### Session B

```sql
UPDATE accounts
SET balance = balance + 20
WHERE id = 1;
```

B creates the reverse dependency.

Wait for PostgreSQL to detect the cycle.

This should be part of your concurrency test toolkit.

# 41. Production Concurrency Testing

A serious test should control interleavings explicitly.

Useful techniques include:

```text
barriers
latches
advisory-lock pauses
pg_sleep for demonstrations
multiple database clients
controlled transaction phases
```

For example:

```text
Worker A
  lock A
  signal barrier 1
  wait barrier 2
  request B

Worker B
  lock B
  signal barrier 2
  wait barrier 1
  request A
```

This is far more reliable than hoping a load test randomly reproduces the race.

# 42. Wrong Implementation — Opposite Lock Order

### Naive approach

```ts
async function transfer(a: number, b: number) {
  await lock(a);
  await lock(b);
  // mutate
}
```

Elsewhere:

```ts
async function reverseTransfer(a: number, b: number) {
  await lock(b);
  await lock(a);
  // mutate
}
```

### Why it fails

The lock acquisition order depends on the call path.

### Improved approach

```ts
const [first, second] = a < b ? [a, b] : [b, a];

await lock(first);
await lock(second);
```

### Why it works

Both code paths converge on the same ordering relation.

### Production consideration

The canonical ordering rule must apply to every participant, including batch workers, triggers, background jobs, and administrative operations where relevant.

### Alternative

Use a single coordination resource or an atomic SQL operation that removes the need for multi-resource locking.

### Trade-off

Canonical ordering preserves concurrency better than a coarse global lock, but it requires strict architectural discipline.

---

# 43. Wrong Implementation — Infinite Retry

### Naive approach

```ts
while (true) {
  try {
    await runTransaction();
    return;
  } catch (error) {
    if (error.code !== '40P01') throw error;
  }
}
```

### Why it fails

A structural deadlock can recur forever.

### Improved approach

```ts
for (let attempt = 0; attempt < 3; attempt++) {
  try {
    return await runTransaction();
  } catch (error) {
    if (error.code !== '40P01') throw error;
    if (attempt === 2) throw error;
    await sleep(withJitter(attempt));
  }
}
```

### Production consideration

Track retry counts as metrics and alert on sustained increases.

---

# 44. Wrong Implementation — Retry Every Database Error

### Naive approach

```ts
catch (error) {
  return runTransactionAgain();
}
```

### Why it fails

You may retry:

- validation errors;
- unique violations;
- foreign-key violations;
- permission errors;
- malformed SQL;
- business-rule rejections.

This wastes resources and can amplify load.

### Improved approach

Retry only errors explicitly classified as transient and safe to retry, such as a known deadlock or appropriately handled serialization failure.

---

# 45. Wrong Implementation — Increase `deadlock_timeout` and Hope

### Naive approach

```text
deadlocks happening
        ↓
raise deadlock_timeout
```

### Why it fails

The setting controls when PostgreSQL checks for deadlocks; it does not fix the lock-order inversion.

Increasing the setting can actually delay deadlock reporting and, separately, can delay logging of waits when `log_lock_waits` is enabled. citeturn348494search12turn348494search1

### Improved approach

```text
identify cycle
→ identify lock-order inversion
→ redesign ordering
→ reduce transaction scope
→ retain bounded retries
```

---

# 46. Wrong Implementation — Solve Everything With `NOWAIT`

A developer may write:

```sql
SELECT *
FROM accounts
WHERE id = $1
FOR UPDATE NOWAIT;
```

and conclude that deadlocks are solved.

Not necessarily.

`NOWAIT` avoids waiting for a conflicting lock acquisition, but it changes the application semantics from:

```text
wait for resource
```

to:

```text
fail immediately if unavailable
```

It can be an excellent design for some workloads, but it is not a universal deadlock-prevention mechanism.

---

# 47. Wrong Implementation — Coarse Global Lock

Another response to deadlocks is:

```sql
LOCK TABLE everything;
```

This can eliminate some concurrency cycles simply by eliminating concurrency.

But it may produce:

```text
low throughput
high latency
queueing
poor tenant isolation
maintenance pain
```

The better engineering goal is:

> **Remove cyclic dependencies without destroying useful concurrency.**

# 48. Performance Implications

Deadlock frequency itself is often not the only cost.

Consider:

```text
transaction starts
↓
work performed
↓
locks accumulated
↓
deadlock detected
↓
all work rolled back
↓
application retries
↓
work performed again
```

The wasted CPU, I/O, WAL, network, and application work can exceed the raw number of deadlock errors.

Therefore important metrics include:

```text
deadlock count
transaction retries
retry success rate
retry exhaustion rate
lock wait duration
transaction duration
rollback volume
API latency impact
connection pool utilization
```

---

# 49. Deadlocks and WAL / Rollback Cost

A deadlock victim may have already performed significant work before PostgreSQL aborts it.

The database must undo the transaction's effects logically through transactional visibility/rollback processing, while generated WAL and resource consumption are not magically erased from the system's total work budget.

Therefore preventing deadlocks can be materially valuable even when clients successfully retry and eventually succeed.

---

# 50. Deadlocks and Throughput

Suppose each request takes:

```text
normal transaction = 20 ms
```

but deadlocked attempts consume:

```text
20 ms + wait + rollback + retry
```

At scale:

```text
deadlock rate × wasted work
```

becomes a throughput tax.

That is why concurrency correctness and performance engineering are deeply connected.

---

# 51. `EXPLAIN` and Deadlocks

`EXPLAIN` does not directly say:

> “This query will deadlock.”

But plans can influence the order and number of rows touched.

Relevant considerations include:

- join order;
- index scan vs sequential scan;
- number of rows modified;
- filtering selectivity;
- row visitation order;
- nested-loop behavior;
- batch size.

For update-heavy workflows, a plan change can alter the practical lock footprint even when the SQL text is unchanged.

Therefore when a deadlock appears after a deployment, compare:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

before and after the change, while separately reconstructing the lock graph.

Do not assume the plan is the root cause merely because it changed.

---

# 52. Deadlocks and Isolation Levels

Deadlocks can occur at multiple isolation levels.

Changing from:

```text
READ COMMITTED
```

to:

```text
REPEATABLE READ
```

or:

```text
SERIALIZABLE
```

does not automatically eliminate lock-order deadlocks.

In fact, stronger isolation can introduce additional conflict behavior and more aborts for different reasons.

Therefore:

> **Isolation level and deadlock prevention solve related but distinct concurrency problems.**

---

# 53. Deadlocks in `SELECT ... FOR UPDATE`

Locking reads can participate directly.

Example:

```sql
SELECT id
FROM inventory
WHERE id IN (1, 2)
ORDER BY id
FOR UPDATE;
```

If every workflow uses the same ordering, the risk is reduced.

But another workflow may execute:

```sql
SELECT id
FROM inventory
WHERE id IN (2, 1)
FOR UPDATE;
```

without deterministic ordering.

The code review target is not the literal order of the `IN` list. It is the actual row acquisition strategy and global resource ordering.

---

# 54. Deadlocks and `SKIP LOCKED`

`SKIP LOCKED` changes waiting behavior:

```sql
SELECT id
FROM jobs
WHERE status = 'ready'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

Instead of waiting on locked rows, eligible locked rows can be skipped.

This can reduce blocking in queue-worker systems.

But it does not automatically solve deadlocks in the rest of the transaction.

For example, after claiming jobs, workers may still acquire other resources in inconsistent orders.

Thus:

```text
SKIP LOCKED
≠
deadlock-proof architecture
```

---

# 55. Deadlocks and `NOWAIT`

Likewise:

```sql
FOR UPDATE NOWAIT
```

converts some waits into immediate lock errors.

This may be ideal when:

```text
freshness is more valuable than waiting
```

or:

```text
caller should choose an alternative resource
```

But application semantics become more failure-oriented.

Use `NOWAIT` intentionally, not as a panic button after seeing a deadlock error.

---

# 56. Security Considerations

Deadlock prevention is also a security concern.

An attacker who can cause many long transactions to contend on predictable resources may create:

```text
lock amplification
↓
connection exhaustion
↓
request queue growth
↓
availability degradation
```

Controls include:

- transaction duration limits;
- statement/lock timeouts where appropriate;
- bounded retries;
- rate limits on expensive workflows;
- resource ownership checks;
- appropriate least-privilege access;
- monitoring for unusual wait patterns.

Never expose internal lock diagnostics to untrusted clients merely because they are useful to operators.

# 58. Production Incident Example

### Symptom

A stock-transfer API suddenly reaches:

```text
p95 = 2.8 s
p99 = 7.4 s
```

Database CPU is only 30%.

### Evidence

Logs show:

```text
deadlock detected
SQLSTATE 40P01
```

### Investigation

Two workflows exist:

```text
transfer creation:
transfer → source stock → destination stock

stock adjustment:
source stock → destination stock → transfer
```

### Root cause

Global lock-order inversion.

### Mitigation

Bounded retry reduced immediate user-visible failures.

### Permanent fix

Canonicalized the resource order across all workflows:

```text
transfer
→ stock locations ordered by stable identifier
→ dependent ledger state
```

### Prevention

Added deterministic concurrency tests and retry/deadlock metrics.

This is the desired incident pattern:

```text
symptom
→ evidence
→ wait graph
→ ordering inversion
→ mitigation
→ structural fix
→ regression test
```

# 59. Architecture Pattern: Canonical Resource Ordering

For any workflow touching resources:

```text
R1, R2, R3, ...
```

define a total or sufficiently deterministic order:

```text
R1 < R2 < R3
```

Every transaction that can overlap must acquire resources in that order.

This converts a potentially cyclic graph into an acyclic ordering discipline.

Conceptually:

```text
arbitrary
A → B
B → A

        ↓

canonical
A → B
A → B
```

A single queue may still exist, but the cycle is removed.

---

# 60. Architecture Pattern: Reduce the Lock Footprint

Use:

```text
read outside transaction where safe
↓
compute outside transaction where safe
↓
open transaction
↓
lock only required resources
↓
perform atomic changes
↓
commit quickly
```

But do not move a read outside the transaction when doing so breaks correctness.

The principle is:

> **Short transactions reduce deadlock opportunities, but correctness still determines the transaction boundary.**

---

# 61. Architecture Pattern: Replace Multi-Resource Coordination

Sometimes the best way to prevent a deadlock is to avoid needing several independent locks.

Possible approaches:

```text
atomic UPDATE
single coordination row
queue serialization
pre-allocated ownership
append-only event
advisory lock with canonical key
```

Example:

Instead of locking two inventory rows and comparing them in application code, a carefully designed atomic statement may encode the invariant directly.

Use this only when the statement genuinely protects the business rule.

---

# 62. Architecture Pattern: Serialize Hot Work Intentionally

Not every workload benefits from maximum concurrency.

A heavily contended resource may be better modeled as:

```text
many callers
    ↓
work queue
    ↓
ordered workers
    ↓
single resource mutation stream
```

This can trade some concurrency for predictable contention behavior.

Examples:

- per-account ledger posting;
- per-stock-location sequencing;
- per-order state machine transitions.

The decision must be driven by measured contention and business requirements.

---

# 63. AI / Vibe-Coding Deadlock Mistakes

### Mistake 1 — “Transactions prevent race conditions.”

False.

Transactions provide atomicity and isolation semantics, but poorly ordered multi-resource locking can still deadlock.

### Mistake 2 — “Add `FOR UPDATE` everywhere.”

This often increases lock footprint and contention without proving the invariant.

### Mistake 3 — “Retry every Postgres error.”

This can retry permanent failures and amplify load.

### Mistake 4 — “Increase `deadlock_timeout`.”

That changes detection timing, not the dependency structure.

### Mistake 5 — “Use `SKIP LOCKED` to fix deadlocks.”

It changes waiting behavior for eligible locks; other resource dependencies can still cycle.

### Mistake 6 — “The ORM handles locking for us.”

The database still sees actual resource acquisition. Hidden SQL can hide ordering problems from code review.

### Mistake 7 — “One endpoint cannot deadlock because it only runs one SQL statement.”

Triggers, foreign keys, implicit locking, and concurrent dependencies can make the effective interaction more complex.

# 64. Code Review Checklist for Deadlock Risk

For every transaction touching multiple resources, ask:

```text
1. What resources can it lock?
2. In what order are they acquired?
3. Do all competing code paths use the same order?
4. Can triggers acquire additional resources?
5. Can foreign-key checks add dependencies?
6. Are advisory locks involved?
7. How long are locks held?
8. Can external calls occur while locks are held?
9. What happens after 40P01?
10. Is retry bounded and idempotent?
11. Are retry metrics visible?
12. Can the workflow be simplified to one atomic operation?
```

This is much stronger than reviewing individual SQL statements independently.

# 67. Interview Questions

## Junior

### Q1. What is a deadlock?

**Weak answer:** “Two queries are slow.”

**Acceptable answer:** “Transactions wait for each other's locks.”

**Strong answer:** “A deadlock is circular waiting between transactions.”

**Expert answer:** “A deadlock is a cycle in the effective wait-for graph created by conflicting resource dependencies; PostgreSQL detects the cycle and aborts one participant so progress can resume.”

### Q2. Is every lock wait a deadlock?

**Weak:** Yes.

**Strong:** No. A wait can be a simple chain with eventual progress; a deadlock requires a cycle.

---

## Mid-Level

### Q3. How do you prevent deadlocks?

**Strong answer:** Keep transactions short, acquire multiple resources in a canonical global order, reduce unnecessary lock footprints, and use bounded retries for transient conflicts.

### Q4. What does `deadlock_timeout` do?

**Strong answer:** It controls how long PostgreSQL waits on a lock before checking for a deadlock; it is not a maximum lock-wait duration. citeturn348494search12

---

## Senior

### Q5. Why can adding `ORDER BY` fail to eliminate deadlocks?

Because deadlock freedom requires a globally consistent acquisition order across all participating workflows and hidden dependencies, not merely one query's visible ordering.

### Q6. Deadlock or serialization failure?

A deadlock is a lock dependency cycle; a serialization failure is an isolation/serializability conflict. Their SQLSTATEs and retry diagnosis differ.

Memorize the structure, not the symptom:

```text
TRANSACTIONS
     ↓
ACQUIRE RESOURCES
     ↓
CONFLICTING LOCKS
     ↓
WAIT-FOR EDGES
     ↓
      ?
     / \
   NO   YES
   |      |
   v      v
 WAIT   CYCLE
   |      |
   v      v
PROGRESS ABORT ONE
          |
          v
       RETRY
          |
          v
   REDESIGN ORDER
```

And the architectural rule:

> **Do not design for “never wait.” Design so that waits are bounded, cycles are structurally avoided, retries are safe, and the system can explain exactly why a transaction failed.**

# 72. Chapter Summary

Deadlocks are not random database failures. They are graph-theoretic consequences of conflicting resource acquisition.

The durable engineering approach is:

```text
understand the lock footprint
        ↓
identify the resource order
        ↓
make ordering deterministic
        ↓
shorten transaction lifetime
        ↓
reduce unnecessary coordination
        ↓
observe actual wait graphs
        ↓
retry only safe transient failures
        ↓
make retries idempotent
        ↓
regression-test the interleaving
```

PostgreSQL is doing something valuable when it reports a deadlock: it is refusing to let a circular wait remain unresolved indefinitely. The engineering task is to remove the conditions that repeatedly create the cycle.
