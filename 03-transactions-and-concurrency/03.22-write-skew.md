# 03.22 — Write Skew

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains **write skew** from first principles: how individually valid transactions can together violate a cross-row invariant, why ordinary row locks and snapshot isolation may not be enough, how PostgreSQL's `SERIALIZABLE` isolation detects dangerous structures, and how to choose between constraints, atomic SQL, explicit locking, and serializable execution.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- define write skew precisely and distinguish it from a lost update;
- explain why MVCC can permit write skew even when every transaction sees a consistent snapshot;
- identify the business invariants that create write-skew risk;
- construct a deterministic two-transaction write-skew reproduction;
- explain why row-level locks on different rows do not necessarily coordinate a shared invariant;
- understand why `REPEATABLE READ` can still allow serialization anomalies;
- explain how PostgreSQL `SERIALIZABLE` / SSI detects dangerous read-write dependency structures and aborts unsafe transactions;
- determine when a declarative constraint is stronger and simpler than transactional coordination;
- compare atomic SQL, explicit locks, coordination rows, and `SERIALIZABLE` isolation;
- design retries correctly after SQLSTATE `40001`;
- recognize retry loops that make a write-skew problem operationally worse;
- debug suspected write skew using transaction timelines, SQL statements, lock state, and reproducible concurrency tests;
- avoid Node.js/NestJS/ORM transaction-boundary mistakes;
- reason about multi-tenant, inventory, scheduling, approval, credit, and jewellery-ERP invariants;
- defend an isolation/concurrency design in a senior, staff, or principal-level architecture review.

Current PostgreSQL 18 documentation describes `REPEATABLE READ` as providing a stable transaction snapshot while allowing serialization anomalies, and `SERIALIZABLE` as preventing anomalies that cannot be reconciled with some serial order by aborting transactions when necessary. The PostgreSQL documentation also describes predicate-lock/SSI conflict tracking and serialization failures. These semantics are the foundation for the patterns in this chapter.

# 2. The Central Problem

The most useful mental model is:

```text
Two transactions
        |
        +-- read overlapping business state
        |
        +-- each makes a locally valid decision
        |
        +-- each writes a different row
        |
        +-- no direct write-write conflict
        |
        v
Shared invariant becomes false
```

That is write skew.

The essential property is:

> **The transactions do not have to update the same row. They only have to make decisions whose correctness depends on a shared invariant.**

Compare:

```text
LOST UPDATE

T1 reads row A
T2 reads row A
T1 writes row A
T2 writes row A
              ^
       same-row conflict
```

with:

```text
WRITE SKEW

T1 reads A and B
T2 reads A and B
T1 writes A
T2 writes B

        ^
 writes are different rows,
 but decisions depend on A + B
```

This distinction is fundamental.

---

# 3. Precise Definitions

## 3.1 Simple definition

Write skew happens when two concurrent transactions each make a decision based on the same condition, then modify different rows, causing the combined result to violate a business rule.

## 3.2 Engineering definition

A write-skew anomaly occurs when concurrent transactions read a common logical predicate or set of rows, observe a state satisfying an invariant, and then perform non-conflicting writes whose combination invalidates that invariant.

## 3.3 Expert definition

Write skew is a serialization anomaly produced when two concurrent transactions establish read dependencies over a shared logical fact but write to disjoint physical rows. Snapshot-based isolation can permit both transactions to commit because neither write directly conflicts with the other, even though no serial ordering can explain the resulting state while preserving the transactions' decision predicates.

Under PostgreSQL `SERIALIZABLE`, SSI tracks relevant read/write dependencies and can abort a transaction with SQLSTATE `40001` rather than allow the unsafe outcome.

# 4. First Principles: Why Write Skew Exists

Suppose an invariant is:

```text
At least one doctor must remain on call.
```

Database state:

```text
Alice  on_call = true
Bob    on_call = true
```

Invariant:

```text
COUNT(on_call = true) >= 1
```

Now:

```text
T1 checks: Alice or Bob is on call -> true
T2 checks: Alice or Bob is on call -> true

T1 decides: Alice can go off call
T2 decides: Bob can go off call
```

Each transaction individually sees a valid starting condition.

The problem is that their decisions interact:

```text
Initial
Alice = ON
Bob   = ON

T1 -> Alice OFF
T2 -> Bob OFF

Final
Alice = OFF
Bob   = OFF

Invariant violated
```

There was no lost update.

No transaction overwrote the other's value.

Every write may have passed its local checks.

The bug is the **decision dependency**.

---

# 5. Canonical Write-Skew Example

Create a small table:

```sql
CREATE TABLE doctor_schedule (
    doctor_id bigint PRIMARY KEY,
    on_call boolean NOT NULL
);

INSERT INTO doctor_schedule (doctor_id, on_call)
VALUES
    (1, true),
    (2, true);
```

Business rule:

```text
At least one doctor must remain on call.
```

Transaction T1:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT count(*)
FROM doctor_schedule
WHERE on_call = true;

-- sees 2

UPDATE doctor_schedule
SET on_call = false
WHERE doctor_id = 1;

COMMIT;
```

Transaction T2, concurrently:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT count(*)
FROM doctor_schedule
WHERE on_call = true;

-- sees 2

UPDATE doctor_schedule
SET on_call = false
WHERE doctor_id = 2;

COMMIT;
```

Possible final state:

```text
doctor 1 -> false
doctor 2 -> false
```

The invariant is broken.

---

# 6. Why This Is Not a Lost Update

A lost update normally has this shape:

```text
initial balance = 100

T1 reads 100
T2 reads 100

T1 writes 80
T2 writes 70

one write effectively destroys the other decision
```

Write skew looks different:

```text
initial
A = valid
B = valid

T1 reads A+B
T2 reads A+B

T1 writes A
T2 writes B

A + B becomes invalid
```

The writes do not collide.

That is why solutions based only on detecting same-row modification can miss write skew.

---

# 7. The Invariant Is Usually the Real Synchronization Object

Developers often ask:

> “Which row should I lock?”

That may be the wrong first question.

Ask:

> **“What logical fact must remain true?”**

Examples:

```text
At least one active approver exists.
At most N reservations can be active.
Available stock cannot become negative.
A credit limit cannot be exceeded.
Only one primary address exists.
At least one payment method remains active.
Two staff members cannot occupy the same exclusive shift.
A workflow must not have two simultaneous terminal owners.
A tenant cannot exceed its concurrency quota.
```

The logical invariant may span:

- one row;
- many rows;
- one table;
- multiple tables;
- a predicate-defined set;
- or an entire transactional workflow.

The synchronization mechanism must protect **that invariant**, not merely whichever row happened to be written.

---

# 8. Why MVCC Does Not Automatically Prevent It

MVCC answers a question like:

> “Which committed row versions may this transaction see?”

It does not automatically answer:

> “Can two independent decisions made from this snapshot safely commit together?”

Under snapshot isolation semantics, both transactions can read the same committed world:

```text
Snapshot S

A = ON
B = ON

T1 sees S
T2 sees S
```

Then:

```text
T1 writes A
T2 writes B
```

Because:

```text
write(T1) != write(T2)
```

there may be no ordinary row-level write-write conflict.

But:

```text
read(T1) --> influences write(A)
read(T2) --> influences write(B)
```

and both decisions were based on the shared predicate:

```text
A OR B must remain true
```

That is the hidden dependency.

---

# 9. The Key Difference Between Physical and Logical Conflicts

Think in two layers:

```text
PHYSICAL CONFLICT

same row
same tuple
same lockable resource

        vs

LOGICAL CONFLICT

same business invariant
same predicate
same capacity
same rule
```

Write skew occurs when:

```text
logical conflict exists
physical write conflict does not
```

This explains why simple row locking can be insufficient.

---

# 10. Why `REPEATABLE READ` Is Not Enough

PostgreSQL `REPEATABLE READ` provides a stable transaction snapshot, which prevents nonrepeatable reads and, in PostgreSQL, ordinary phantom reads.

But stable visibility is not equivalent to serial execution.

Two transactions may still reason from the same valid snapshot and make disjoint writes that jointly violate an invariant.

Conceptually:

```text
REPEATABLE READ

Stable snapshot
      |
      +-- prevents changing read view
      |
      +-- does NOT guarantee every business invariant
      |
      +-- serialization anomalies can remain
```

Therefore:

> **“The reads are repeatable” does not imply “the business decision is serializable.”**

---

# 11. The Serialization Question

For two transactions T1 and T2, ask:

> Could the final result be explained as if T1 ran entirely before T2, or T2 entirely before T1?

If neither order can explain the successful outcome while preserving each transaction's assumptions, the execution is non-serializable.

Write skew often has exactly this property.

Example:

```text
Invariant: at least one doctor is on call

Serial order T1 then T2:

T1 turns Alice OFF.
T2 now checks the state and should see Bob ON,
so T2 cannot also turn Bob OFF.

Therefore T1 -> T2 cannot produce both OFF.

Serial order T2 then T1:

same reasoning.

Therefore both committed OFF cannot be explained by
any serial execution.
```

That is the crucial reasoning step.

---

# 12. Why `SERIALIZABLE` Exists

PostgreSQL's `SERIALIZABLE` isolation level is designed to prevent successful transactions from producing serialization anomalies.

The database may therefore reject one transaction:

```text
T1 -----------\
               > unsafe dependency structure
T2 -----------/

             |
             v
        serialization failure
             |
             v
       retry one transaction
```

The application must treat SQLSTATE `40001` as a possible normal concurrency outcome of a serializable workload.

This is fundamentally different from saying:

> “Serializable means transactions literally execute one at a time.”

They do not need to execute sequentially in wall-clock time.

The guarantee is about the **committed result being equivalent to some serial order**.

---

# 13. Predicate Reads Matter

Consider:

```sql
SELECT count(*)
FROM reservations
WHERE tenant_id = $1
  AND status = 'ACTIVE';
```

The query is logically reading a set, not one predetermined row.

Suppose two transactions both conclude:

```text
ACTIVE reservations = 9
limit = 10
```

and each inserts one:

```text
T1 -> insert reservation 10
T2 -> insert reservation 10
```

If the business rule is about the **count**, the dangerous fact is the predicate:

```text
tenant_id = X AND status = ACTIVE
```

The concurrency problem is not reducible to a single existing row.

This is exactly the class of situation where predicate-aware serializable conflict detection becomes important.

---

# 14. Empty-Result Predicates Can Also Be Dangerous

Suppose:

```sql
SELECT 1
FROM approvals
WHERE request_id = $1
  AND active = true;
```

returns no rows.

The application may interpret that as:

> “No active approval exists, so I may create one.”

Two concurrent transactions can both observe the absence and then create different rows.

The critical dependency is therefore:

```text
read absence
      |
      v
make decision
      |
      v
insert something that makes the read predicate false
```

This is why reasoning only about existing row locks is insufficient for predicate-based invariants.

A unique constraint may be the stronger design when the invariant can be represented declaratively.

---

# 15. First Defense: Declarative Constraints

Before reaching for locks or `SERIALIZABLE`, ask whether PostgreSQL can represent the rule as a constraint.

Examples:

```text
One active primary address per customer
One unique invoice number per tenant
One active workflow owner per job
No duplicate business identifier
```

Potential mechanisms include:

- `UNIQUE` constraints;
- composite unique constraints;
- partial unique indexes;
- `EXCLUDE` constraints for range overlap;
- foreign keys;
- `CHECK` constraints when the rule is row-local.

Example:

```sql
CREATE UNIQUE INDEX one_active_primary_address
ON customer_addresses (customer_id)
WHERE is_primary = true;
```

This is often stronger than application-side coordination because the invariant becomes a database-enforced property.

However, constraints cannot directly encode every cross-row business rule.

---

# 16. Second Defense: Atomic SQL

Sometimes the business rule can be reformulated as one atomic modification.

Instead of:

```text
SELECT availability
if availability > 0:
    UPDATE
```

prefer:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE id = $1
  AND quantity > 0
RETURNING quantity;
```

Now the predicate and state transition are performed as one database operation.

This can remove an entire class of application-level races.

The important question is:

> Can the invariant be transformed into an atomic state transition over one well-defined row or resource?

If yes, that is frequently simpler than broad locking.

---

# 17. Third Defense: Explicit Coordination Row

If the logical invariant spans many rows but has a natural coordinator, introduce one deliberately.

Example:

```text
tenant_limits
-------------
tenant_id
active_count
limit
```

Then coordinate through one tenant row:

```sql
SELECT active_count, limit
FROM tenant_limits
WHERE tenant_id = $1
FOR UPDATE;
```

Then modify the underlying records while holding the lock.

The system turns:

```text
many-row logical invariant
```

into:

```text
one-row synchronization object
```

This can make concurrency reasoning much easier.

Trade-off:

```text
Pros
- simple reasoning
- explicit owner of the invariant
- easy observability
- predictable lock target

Cons
- hot-row contention
- reduced concurrency for one tenant/resource
- coordinator row must remain correct
```

---

# 18. Fourth Defense: Explicit Predicate-Narrowing Locks

Sometimes you can deliberately lock a set of rows that collectively represent the invariant.

Example:

```sql
SELECT doctor_id
FROM doctor_schedule
WHERE on_call = true
ORDER BY doctor_id
FOR UPDATE;
```

Then decide whether one can safely be removed from on-call duty.

The lock protects the currently represented set.

But there is a critical caveat:

> **Locking only currently existing rows does not automatically protect future inserts into the predicate.**

For insert-sensitive invariants, use a design that actually synchronizes creation as well: a coordinator row, a suitable constraint, serializable execution, or another explicit serialization mechanism.

---

# 19. Fifth Defense: `SERIALIZABLE`

When the invariant is genuinely predicate-level and difficult to encode declaratively or through a simple coordinator, `SERIALIZABLE` can be the cleanest correctness mechanism.

Typical shape:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT ... predicate ...;

-- validate invariant

UPDATE ...;

COMMIT;
```

Possible outcome:

```text
COMMIT
```

or:

```text
ERROR: could not serialize access due to read/write dependencies among transactions
```

Application response:

```text
rollback
↓
retry whole logical transaction
```

Serializable is particularly powerful when the invariant is difficult to enumerate as lockable rows.

The trade-off is operational complexity: retry handling, abort rates, telemetry, and workload analysis become part of the design.

---

# 20. Write Skew Under Different Strategies

Consider:

```text
Invariant: at least one active approver
```

### Strategy A — No coordination

```text
T1 reads two approvers
T2 reads two approvers
T1 disables approver A
T2 disables approver B
```

Result:

```text
invalid
```

### Strategy B — Lock only the row being changed

```text
T1 locks A
T2 locks B
```

Result:

```text
still potentially invalid
```

### Strategy C — Lock a coordinator row

```text
T1 locks workflow row
T2 waits
```

Result:

```text
serialized decision
```

### Strategy D — `SERIALIZABLE`

```text
T1 and T2 execute concurrently
SSI identifies dangerous dependency structure
one transaction may abort
```

Result:

```text
serializable outcome after retry
```

# 21. Why “Lock Every Row” Is Not a Universal Fix

A naive response is:

```sql
SELECT *
FROM large_table
WHERE tenant_id = $1
FOR UPDATE;
```

This may prevent some anomalies, but it creates serious costs:

- broad contention;
- longer lock hold times;
- increased latency;
- lower throughput;
- larger deadlock surfaces;
- more connection waiting;
- operational complexity;
- possible starvation or queue buildup.

And it may still fail to protect a predicate if new matching rows can be inserted outside the chosen synchronization path.

Correctness requires the right conflict set, not the maximum conflict set.

---

# 22. Common Write-Skew Pattern: “At Least One”

Examples:

```text
at least one doctor on call
at least one approver active
at least one payment method enabled
at least one warehouse operator assigned
at least one tenant quota slot available
at least one recovery contact configured
```

These are dangerous because a transaction often asks:

```text
How many satisfy P?
```

and then modifies one member of P.

The invariant is about the whole set.

---

# 23. Common Pattern: “At Most N”

Example:

```text
tenant can have at most 5 active jobs
```

Two transactions:

```text
T1 sees 4 active jobs
T2 sees 4 active jobs

T1 creates job #5
T2 creates job #5

final count = 6
```

This resembles a capacity race.

A naive design:

```sql
SELECT count(*) ...;
INSERT ...;
```

is not enough under concurrent execution.

Possible solutions:

- atomic counter/coordination row;
- unique constraint where appropriate;
- serializable transaction;
- queue-based allocation;
- explicit row locking around the capacity owner.

Choose according to workload and invariant shape.

---

# 24. Common Pattern: Scheduling

Suppose a worker must ensure:

```text
No two exclusive appointments overlap.
```

A transaction checks for an overlap:

```sql
SELECT 1
FROM appointments
WHERE resource_id = $1
  AND tstzrange(start_at, end_at, '[)')
      && tstzrange($2, $3, '[)');
```

Then inserts the appointment.

Two transactions can both see no overlap.

For temporal exclusion rules, a PostgreSQL `EXCLUDE` constraint may be dramatically better than transactional application logic.

Example:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE appointments
ADD CONSTRAINT no_overlapping_appointments
EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
);
```

This turns the invariant into a declarative database property rather than a race-prone check-then-insert sequence.

---

# 25. Common Pattern: Financial Credit

Suppose:

```text
credit_limit = 100000
```

Current outstanding balances:

```text
A = 60000
B = 30000
```

Two concurrent requests each attempt another `10000`.

Both may independently see:

```text
90000 + 10000 <= 100000
```

and both succeed.

Final exposure:

```text
110000
```

The problem is not simply the account row.

It is the aggregate financial invariant.

Possible design choices:

```text
single account counter row + atomic update
OR
serializable transaction
OR
ledger + materialized/maintained exposure model
OR
explicit credit-reservation coordinator
```

Financial systems usually need stronger modeling than an application-side count followed by separate writes.

---

# 26. Jewellery ERP Example: Branch Stock Allocation

Imagine a jewellery ERP where a branch-level inventory policy says:

```text
For a specific high-value item class,
at least one eligible piece must remain available
for immediate branch sale.
```

Two concurrent workflows could be:

```text
T1 -> reads available eligible pieces
     reserves piece A

T2 -> reads same available set
     reserves piece B
```

If the invariant is simply total quantity, an atomic counter may be enough.

If the invariant depends on multiple attributes:

```text
branch
+
item category
+
certification state
+
quality grade
+
reservation status
```

then the logical predicate becomes more complex.

A production design should first ask:

```text
Can this be expressed as a constraint?
Can this be represented by one coordinator row?
Can this become an atomic UPDATE?
Would SERIALIZABLE be simpler and safer?
```

The correct answer should be driven by the actual invariant and contention profile.

# 27. Node.js / NestJS Failure Mode

A typical unsafe service looks like:

```ts
const rows = await repo.query(`
  SELECT id
  FROM approvals
  WHERE workflow_id = $1
    AND active = true
`, [workflowId]);

if (rows.length >= 1) {
  // decide whether current approval may be disabled
}

await repo.query(`
  UPDATE approvals
  SET active = false
  WHERE id = $1
`, [approvalId]);
```

Problems:

1. the read and write may not be in one transaction;
2. the database connection may change between operations when a transaction is not pinned;
3. the invariant is cross-row;
4. the update may lock only one row;
5. the service may assume ORM abstractions imply serialization.

A safer architecture starts by defining the invariant and then choosing the synchronization mechanism explicitly.

---

# 28. ORM Danger: “Transaction = Safe”

A transaction alone does not prevent write skew.

This is not enough:

```ts
await manager.transaction(async (tx) => {
  const rows = await tx.find(...);

  if (rows.length > 0) {
    await tx.save(...);
  }
});
```

The isolation level and concurrency design still matter.

A transaction gives atomicity of the work it encloses.

It does not automatically make concurrent transactions serializable.

Therefore:

```text
transaction != serializability
transaction != lock
transaction != invariant protection
```

---

# 29. Retry Semantics for Serializable Write Skew

Suppose PostgreSQL aborts one transaction:

```text
SQLSTATE = 40001
```

The correct pattern is generally:

```text
attempt
  |
  +-- begin serializable
  +-- read predicate
  +-- make decision
  +-- write
  +-- commit
       |
       +-- 40001
             |
             v
         discard attempt
             |
             v
         retry whole unit
```

Do not retry only the failing statement.

The decision made by the failed attempt was based on a transaction execution that the database rejected.

A new attempt must re-read the state and make the decision again.

---

# 30. Retry Budget

Retries should be bounded.

Example conceptual policy:

```text
max_attempts = 3

attempt 1 -> immediate
attempt 2 -> small jittered delay
attempt 3 -> larger jittered delay

then fail explicitly
```

Why?

Because high contention can create a feedback loop:

```text
high contention
   ↓
40001 failures
   ↓
retries
   ↓
more transactions
   ↓
more contention
   ↓
more 40001 failures
```

This is a retry storm.

Observability should include:

- serialization failure rate;
- retry count per operation;
- final retry exhaustion;
- latency by attempt number;
- hot tenants/resources;
- transaction duration.

---

# 31. Idempotency and External Side Effects

A database retry must not duplicate external effects.

Bad sequence:

```text
DB transaction
   ↓
charge payment provider
   ↓
DB commit
```

If the DB attempt fails with `40001`, retrying can charge twice.

Safer architecture:

```text
DB transaction
   ↓
record durable intent / outbox event
   ↓
commit
   ↓
external worker performs side effect
   ↓
idempotency key protects repeat delivery
```

This is especially important when serializable transactions are used in high-contention business workflows.

---

# 32. Write Skew vs Deadlock

They are different failure classes.

Write skew:

```text
transactions commit
business invariant violated
```

or, under `SERIALIZABLE`:

```text
transaction aborts with 40001
```

Deadlock:

```text
T1 waits for T2
T2 waits for T1
```

and PostgreSQL aborts one transaction with a deadlock error, typically SQLSTATE `40P01`.

Do not classify every concurrency failure as a deadlock.

---

# 33. Write Skew vs Unique Constraint Violation

Some apparent write-skew scenarios are better solved by a uniqueness rule.

Example:

```text
Only one active primary address per customer
```

Rather than:

```text
SELECT count(primary=true)
IF zero
  UPDATE/INSERT
```

use a partial unique index:

```sql
CREATE UNIQUE INDEX one_primary_address
ON customer_addresses (customer_id)
WHERE is_primary = true;
```

This converts a complicated concurrency protocol into a direct database invariant.

The constraint is then the authority.

---

# 34. Write Skew vs Atomic Counter

Capacity rules often benefit from an explicit counter.

Example:

```sql
UPDATE tenant_limits
SET active_count = active_count + 1
WHERE tenant_id = $1
  AND active_count < limit
RETURNING active_count;
```

The important property is that the capacity check and increment are one atomic write.

Compare with:

```sql
SELECT active_count, limit ...;

-- application checks

UPDATE tenant_limits
SET active_count = active_count + 1 ...;
```

The latter has a race unless the synchronization is otherwise provided.

---

# 35. Why a Version Column Is Not a General Write-Skew Solution

Optimistic concurrency with:

```sql
UPDATE table
SET value = $new_value,
    version = version + 1
WHERE id = $id
  AND version = $expected_version;
```

is excellent for detecting stale updates to the **same logical object**.

But consider:

```text
T1 updates row A
T2 updates row B
```

Their version checks can both succeed because neither row's version changed.

If the invariant spans A+B, optimistic row versioning alone does not prove that the invariant remains true.

Therefore:

> **Version checks protect freshness of a resource; they do not automatically protect arbitrary cross-resource invariants.**

---

# 36. Wrong Implementation #1 — “It Is in a Transaction”

```text
BEGIN
SELECT count(*)
UPDATE row A
COMMIT
```

Why it fails:

```text
atomicity exists
but concurrent invariant protection may not
```

Improvement:

```text
constraint
OR
atomic state transition
OR
coordination lock
OR
SERIALIZABLE
```

based on the invariant.

---

# 37. Wrong Implementation #2 — “Lock the Row We Update”

```sql
SELECT *
FROM doctors
WHERE doctor_id = $doctor_id
FOR UPDATE;
```

Why it fails:

The business decision depends on the entire on-call set, not just the selected doctor.

T1 can lock Alice.

T2 can lock Bob.

The invariant can still break.

Improvement:

Protect the actual coordination object.

---

# 38. Wrong Implementation #3 — “Use `SELECT ... FOR UPDATE` on the Predicate”

Even:

```sql
SELECT *
FROM doctors
WHERE on_call = true
FOR UPDATE;
```

must be analyzed carefully.

It locks rows returned at that point.

It does not magically convert every possible future row insert into a protected member of the predicate under all workflows.

For insert-sensitive predicates, use a constraint, coordination row, serializable transaction, or another design that explicitly covers creation as well as modification.

---

# 39. Wrong Implementation #4 — “Retry Every Error”

```ts
while (true) {
  try {
    await doTransaction();
    break;
  } catch {
    // retry
  }
}
```

Why it fails:

- non-retryable errors are hidden;
- programming bugs loop forever;
- constraint violations become storms;
- lock failures may have different semantics;
- latency becomes unbounded;
- incidents become harder to diagnose.

Improvement:

```text
retry only known transient concurrency failures
with bounded attempts and backoff
```

# 40. AI / Vibe-Coding Mistakes

AI-generated implementations frequently produce patterns such as:

### Mistake: “Use a transaction.”

Problem:

```text
transaction scope is confused with isolation guarantee
```

### Mistake: “Lock the object being updated.”

Problem:

```text
object != invariant
```

### Mistake: “Add a version column everywhere.”

Problem:

```text
row freshness != cross-row serialization
```

### Mistake: “Use SERIALIZABLE everywhere.”

Problem:

```text
higher correctness guarantee
but potentially higher abort/retry cost
and unnecessary complexity for simple operations
```

### Mistake: “Retry the failed query.”

Problem:

```text
failed transaction decision may already be invalid
```

### Mistake: “COUNT then INSERT is safe inside a transaction.”

Problem:

```text
predicate invariant may still admit write skew
```

The fix is always the same first step:

> Identify the invariant before selecting the concurrency mechanism.

---

# 41. Performance Considerations

Write-skew prevention has a real concurrency cost.

## Declarative constraint

Often efficient because enforcement is targeted and integrated with indexes/constraint machinery.

## Atomic update

Usually excellent for localized counters/state transitions.

## Coordination row

Can become a hot row:

```text
many workers
    |
    v
same tenant row
    |
    v
queue
```

## Explicit broad locks

Can reduce concurrency substantially.

## SERIALIZABLE

Allows concurrent execution but may abort transactions that conflict logically.

The relevant metric is therefore not only query latency.

Measure:

```text
throughput
+
lock wait time
+
serialization failures
+
retry attempts
+
transaction duration
+
CPU
+
I/O
```

# 42. Observability

When investigating suspected write skew, capture a timeline.

Useful sources include:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state <> 'idle';
```

Lock information:

```sql
SELECT
    pid,
    locktype,
    relation::regclass,
    page,
    tuple,
    virtualxid,
    transactionid,
    mode,
    granted
FROM pg_locks
WHERE pid <> pg_backend_pid();
```

For blocking relationships:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

But remember:

> **A write-skew incident may involve little or no ordinary lock blocking.**

The primary evidence may instead be:

- transaction SQL;
- timestamps;
- isolation level;
- committed values;
- serialization failures;
- application request IDs;
- trace correlation;
- invariant checks;
- deterministic reproduction.

# 43. Forensic Workflow

Use:

```text
1. Define invariant
       ↓
2. Capture actual SQL sequence
       ↓
3. Identify transaction boundaries
       ↓
4. Identify isolation level
       ↓
5. Identify rows/predicates read
       ↓
6. Identify rows written
       ↓
7. Build dependency graph
       ↓
8. Determine whether a serial order exists
       ↓
9. Reproduce with controlled interleaving
       ↓
10. Choose smallest correct prevention mechanism
       ↓
11. Load-test contention behavior
```

This is much stronger than:

> “It happened under high traffic, so add a lock.”

# 44. Deterministic Concurrency Test

A reliable test should force the interleaving.

Conceptual flow:

```text
T1: BEGIN RR
T1: read invariant

T2: BEGIN RR
T2: read invariant

T1: write A
T1: pause

T2: write B
T2: commit

T1: commit
```

Then assert the invariant.

For serializable mode, the expected result may instead be:

```text
one commit
one 40001 retryable failure
```

The test should assert the database's actual concurrency contract, not merely that “no exception occurred.”

---

# 45. Production Testing Matrix

Test at minimum:

| Scenario | Expected question |
|---|---|
| Two concurrent writers | Can invariant be broken? |
| Ten concurrent writers | Does abort rate explode? |
| Hot tenant | Does one tenant monopolize coordination? |
| Slow transaction | Does contention become queueing? |
| Retry after 40001 | Is the full unit recomputed? |
| External side effect | Can retry duplicate it? |
| Process crash | Is the state recoverable? |
| New-row insertion | Is predicate creation protected? |
| Migration/deployment | Does code change concurrency semantics? |
| Replica read | Could stale data influence a write decision? |

---

# 46. Replica Warning

Never use stale replica reads as authoritative input for a cross-row write decision unless the architecture explicitly accounts for that staleness.

Example:

```text
read capacity from replica
       ↓
see available slot
       ↓
write to primary
```

A lagging replica can cause the application to act on an obsolete snapshot.

For invariants requiring current authoritative state, perform the critical decision on the primary inside the appropriate transactional boundary.

---

# 47. Distributed Systems Boundary

`SERIALIZABLE` protects a PostgreSQL transaction.

It does not automatically serialize:

```text
PostgreSQL
+
Redis
+
Kafka
+
HTTP service
+
external payment provider
```

If the invariant spans multiple systems, the database transaction cannot alone make the entire distributed workflow serializable.

Use appropriate patterns:

- transactional outbox;
- idempotency keys;
- durable state machines;
- compensating actions;
- workflow orchestration;
- explicit ownership of the authoritative invariant.

---

# 48. Choosing the Smallest Correct Mechanism

Use this decision tree:

```text
Can the invariant be declared?
    |
    +-- YES --> constraint/index/exclusion
    |
    +-- NO -->

Can it be expressed as one atomic state transition?
    |
    +-- YES --> atomic SQL
    |
    +-- NO -->

Is there a natural coordination resource?
    |
    +-- YES --> explicit lock / coordinator row
    |
    +-- NO -->

Is the invariant predicate-level or difficult to enumerate?
    |
    +-- YES --> SERIALIZABLE may be appropriate
```

This avoids both extremes:

```text
under-coordinated
```

and:

```text
over-locked
```

---

# 49. Trade-Off Matrix

| Mechanism | Best for | Main strength | Main cost/risk |
|---|---|---|---|
| `CHECK` | Row-local rules | Declarative correctness | Cannot span arbitrary rows |
| `UNIQUE` / partial unique | Identity/cardinality rules | Strong DB enforcement | Rule must fit uniqueness model |
| `EXCLUDE` | Range overlap | Declarative temporal correctness | More specialized/index cost |
| Atomic SQL | Local state/counters | High concurrency + simple reasoning | Requires reformulatable invariant |
| Coordinator row | Cross-row resource | Explicit serialization point | Hot-row contention |
| `FOR UPDATE` | Known row set | Predictable ownership | Must lock complete conflict set |
| `SERIALIZABLE` | Complex predicate invariants | Strong correctness semantics | `40001`, retries, contention management |
| Optimistic versioning | Same-resource freshness | Minimal locking | Weak for arbitrary cross-row invariants |
| Queue ownership | Work allocation | Explicit single-worker ownership | Throughput/fairness design |

# 50. Production Checklist

Before shipping a workflow that reads one set of rows and modifies another, verify:

```text
[ ] The business invariant is written down explicitly.
[ ] We know whether it is row-local or cross-row.
[ ] We know whether inserts can affect the predicate.
[ ] We checked whether a constraint can represent it.
[ ] We checked whether atomic SQL can represent it.
[ ] We identified the actual synchronization object.
[ ] We did not assume updating different rows means no conflict.
[ ] We selected the isolation level intentionally.
[ ] SERIALIZABLE transactions handle SQLSTATE 40001.
[ ] Retries rerun the whole logical transaction.
[ ] Retries are bounded and jittered.
[ ] External side effects are idempotent or decoupled.
[ ] Transaction connections remain correctly scoped.
[ ] Replica reads are not used for authoritative decisions.
[ ] Concurrency tests force the dangerous interleaving.
[ ] Serialization failures and retry rates are observable.
[ ] Hot tenants/resources are measurable.
[ ] Long transactions are detectable.
[ ] We have verified behavior under production-like concurrency.
```

# 52. Interview Questions

## Junior

### What is write skew?

**Weak Answer**  
Two transactions update data at the same time.

**Acceptable Answer**  
Two transactions make conflicting decisions based on shared data.

**Strong Answer**  
Two concurrent transactions read a shared invariant but write different rows, allowing both writes to commit while the combined state violates the invariant.

**Expert Answer**  
Write skew is a serialization anomaly where transactions have overlapping logical read dependencies but disjoint physical writes. Snapshot isolation can allow both because there is no direct write-write conflict; serializable execution detects the unsafe dependency structure and may abort one transaction.

---

## Mid-Level

### Why does `SELECT ... FOR UPDATE` on the row being changed not always prevent write skew?

Because the invariant may span multiple rows. Locking one row does not necessarily coordinate another transaction modifying a different member of the logical conflict set.

---

## Senior

### How would you diagnose write skew in production?

Look at:

```text
invariant
transaction timelines
SQL statements
isolation level
rows/predicates read
rows written
commit ordering
serialization failures
application traces
```

Then reproduce the exact interleaving and prove whether a serial ordering can explain the result.

---

## Staff

### When would you prefer a coordinator row over `SERIALIZABLE`?

Prefer the coordinator when the invariant has a natural stable ownership point, the conflict set is easy to identify, contention is acceptable, and explicit serialization provides simpler operational behavior.

---

## Principal

### What is the architectural question behind write skew?

Not:

> “Which lock should I add?”

but:

> **“Where is the authoritative representation of the invariant, and what mechanism makes competing decisions over that invariant mutually consistent?”**

# 55. Final Mental Model

Remember the progression:

```text
LOST UPDATE
same resource
same write target
        |
        v
optimistic version / row lock / atomic update
```

```text
WRITE SKEW
shared invariant
+ disjoint writes
        |
        v
constraint
or atomic transition
or coordination resource
or SERIALIZABLE
```

The deepest lesson is:

> **Concurrency correctness is about preserving invariants, not merely preventing two transactions from touching the same row at the same time.**

A strong database engineer therefore reasons in this order:

```text
Business invariant
        ↓
Logical conflict set
        ↓
Physical representation
        ↓
Concurrency mechanism
        ↓
Failure/retry behavior
        ↓
Observability
        ↓
Load-test evidence
```
