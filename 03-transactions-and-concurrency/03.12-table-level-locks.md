# 03.12 — Table-Level Locks

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains PostgreSQL table-level locking from first principles: why relation locks exist, how lock modes conflict, which SQL commands acquire them automatically, how explicit `LOCK TABLE` works, why DDL can block production traffic, how lock escalation misconceptions arise, how to diagnose blocking, and how to design safe operational and application behavior.

## 2. Why Table-Level Locks Exist

A common beginner question is:

> “PostgreSQL uses MVCC. Why does it still need locks?”

Because MVCC solves a different problem.

MVCC is primarily about **which row versions a transaction can see**.

Locks are primarily about **which concurrent operations are allowed to proceed together**.

A useful decomposition is:

```text
MVCC
  ↓
Which version can I see?

Locks
  ↓
Can this operation proceed concurrently with that operation?

Constraints
  ↓
Is the resulting state allowed?

Serializable / SSI
  ↓
Can these concurrent actions be allowed to commit while preserving serializable behavior?
```

These mechanisms complement one another.

### Example

A normal query:

```sql
SELECT *
FROM orders
WHERE customer_id = 42;
```

can use MVCC to read a consistent version without waiting for many concurrent writers.

But PostgreSQL still needs a relation-level lock to protect the table's structural semantics while the query executes. The normal read obtains `ACCESS SHARE`, which conflicts only with `ACCESS EXCLUSIVE`. citeturn314600search18

That means PostgreSQL can support high concurrency such as:

```text
SELECT + INSERT + UPDATE + DELETE
            ↓
mostly coexist
```

while still preventing an incompatible structural operation such as:

```text
DROP TABLE
TRUNCATE
certain ALTER TABLE operations
            ↓
block incompatible activity
```

The lock is therefore not saying:

> “Nobody may touch this table.”

It is saying:

> “This transaction requires a particular concurrency relationship with other operations touching this relation.”

# 3. Three Definitions

## 3.1 Simple definition

A table-level lock is a PostgreSQL concurrency-control lock associated with an entire table/relation rather than an individual row.

## 3.2 Engineering definition

A table-level lock is a relation-level lock mode whose compatibility with other relation-level lock modes determines whether a session can proceed immediately or must wait.

## 3.3 Expert definition

PostgreSQL's relation lock manager tracks lock requests against relations using one of several table-level lock modes. Commands acquire appropriate modes automatically, while applications can request modes explicitly with `LOCK TABLE`. The semantics are determined by the conflict matrix, not by the word “read”, “write”, or “exclusive” in isolation. Lock acquisition can block, queue, or contribute to deadlock formation, and locks generally persist until transaction end unless released earlier by savepoint rollback. citeturn314600search18turn314600search1

# 4. The Mental Model

Think of a table lock as a permission state over an entire relation.

```text
                    orders table
                         │
          ┌──────────────┴──────────────┐
          │                             │
       Session A                     Session B
          │                             │
   wants ACCESS SHARE              wants ROW EXCLUSIVE
          │                             │
          └──────── compatible ─────────┘
                    │
                    ▼
              both can proceed
```

Now change Session B:

```text
Session A                         Session B
---------                         ---------
SELECT                            ALTER TABLE ...
  │                                  │
  ▼                                  ▼
ACCESS SHARE                   ACCESS EXCLUSIVE
  │                                  │
  └──────── conflict ────────────────┘
                    │
                    ▼
             one session waits
```

The lock manager is effectively enforcing the question:

```text
Does requested mode R conflict with any granted mode G
on the same lockable relation?
```

If no:

```text
grant
```

If yes:

```text
wait
```

If a deadlock cycle forms:

```text
abort one participant
```

# 5. PostgreSQL Table-Level Lock Modes

PostgreSQL defines eight table-level lock modes:

```text
ACCESS SHARE
ROW SHARE
ROW EXCLUSIVE
SHARE UPDATE EXCLUSIVE
SHARE
SHARE ROW EXCLUSIVE
EXCLUSIVE
ACCESS EXCLUSIVE
```

Important warning:

> **These are all table-level lock modes even though some names contain the word `ROW`.**

`ROW SHARE` and `ROW EXCLUSIVE` are historical names; they do not mean row-level locks. PostgreSQL's documentation explicitly calls this out. citeturn314600search18

---

# 6. The Conflict Matrix

A useful simplified view is:

| Requested / Held | Access Share | Row Share | Row Exclusive | Share Update Exclusive | Share | Share Row Exclusive | Exclusive | Access Exclusive |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **Access Share** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ |
| **Row Share** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ |
| **Row Exclusive** | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Share Update Exclusive** | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Share** | ✓ | ✓ | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ |
| **Share Row Exclusive** | ✓ | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Exclusive** | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **Access Exclusive** | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

The exact matrix is the authoritative definition of compatibility. PostgreSQL's documentation notes that some modes are self-conflicting while others are not: multiple sessions can hold `ACCESS SHARE`, while `ACCESS EXCLUSIVE` permits only one holder and conflicts with every other table-level mode. citeturn314600search18

Do not memorize this matrix as a random table. Learn its structural meaning:

```text
ACCESS SHARE
    ↓
very permissive; ordinary SELECT

...

ACCESS EXCLUSIVE
    ↓
strongest relation-level exclusion
```

But “strongest” does not mean “best”. A stronger lock means a larger blocked conflict set.

---

# 7. `ACCESS SHARE`

## 7.1 What it means

`ACCESS SHARE` is the normal relation lock acquired by a plain read-only query.

Example:

```sql
SELECT *
FROM customers
WHERE id = 10;
```

The referenced table receives an `ACCESS SHARE` lock. PostgreSQL documents that this mode conflicts only with `ACCESS EXCLUSIVE`. citeturn314600search18

## 7.2 Why it is permissive

This design allows:

```text
many readers
+
many writers
```

without relation-level blocking between ordinary DML operations.

For example:

```text
SELECT          -> ACCESS SHARE
INSERT          -> ROW EXCLUSIVE
UPDATE          -> ROW EXCLUSIVE
DELETE          -> ROW EXCLUSIVE
```

These can coexist because the modes are compatible.

That is an important part of PostgreSQL's concurrency model.

---

# 8. `ROW SHARE`

Despite its name, this is a **table-level** lock.

It is acquired by `SELECT` statements using row-locking clauses such as:

```sql
SELECT *
FROM inventory
WHERE id = 10
FOR UPDATE;
```

or:

```sql
SELECT *
FROM inventory
WHERE id = 10
FOR SHARE;
```

PostgreSQL documents that `ROW SHARE` conflicts with `EXCLUSIVE` and `ACCESS EXCLUSIVE`. citeturn314600search18

This relation-level lock accompanies the actual row-level locking behavior.

Therefore:

```text
SELECT ... FOR UPDATE
        │
        ├── table-level: ROW SHARE
        │
        └── row-level: row lock(s)
```

This is a perfect example of why one SQL statement can participate in multiple locking mechanisms simultaneously.

---

# 9. `ROW EXCLUSIVE`

`INSERT`, `UPDATE`, `DELETE`, and `MERGE` acquire `ROW EXCLUSIVE` on the target table. PostgreSQL documents this mode as conflicting with `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, and `ACCESS EXCLUSIVE`. citeturn314600search18

Conceptually:

```text
INSERT ─┐
UPDATE ─┼──> ROW EXCLUSIVE
DELETE ─┤
MERGE  ─┘
```

The name again does not mean:

> “Lock one row exclusively.”

It means:

> “Acquire the table-level lock mode historically named `ROW EXCLUSIVE`.”

The actual row-level effects of DML are separate.

---

# 10. `SHARE UPDATE EXCLUSIVE`

This mode occupies an important middle ground.

It is relevant to operations that need stronger coordination with concurrent table changes, including certain maintenance operations. The important engineering point is not simply memorizing every command but recognizing that PostgreSQL deliberately provides intermediate relation-level modes so that maintenance and metadata operations can coordinate without immediately blocking every ordinary reader.

Examples of operations that can use this mode include certain `VACUUM` and `ANALYZE` paths and some `ALTER TABLE` forms. Exact behavior depends on the command and PostgreSQL version, so command-specific documentation should be consulted before assuming a migration is non-blocking.

The mode conflicts with `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, and `ACCESS EXCLUSIVE`. citeturn314600search18

Production lesson:

> **“Maintenance” does not mean “lock-free.”**

A maintenance operation can be safe in terms of data correctness and still create meaningful lock contention.

---

# 11. `SHARE`

`SHARE` coordinates operations that need a stable table-level relationship while still permitting multiple compatible shareholders.

It conflicts with DML's `ROW EXCLUSIVE`, as well as stronger modes.

A classic conceptual example is an operation that requires a table to be stable enough for a shared property to be established or checked.

The crucial point is that `SHARE` is not simply:

> “read lock.”

`ACCESS SHARE` is the usual lock for ordinary reads.

`SHARE` is a stronger relation-level requirement and therefore conflicts with ordinary DML.

---

# 12. `SHARE ROW EXCLUSIVE`

This mode is stronger than `SHARE` and is self-conflicting.

It is useful when an operation needs a stronger coordination point than ordinary shared access but does not require full `ACCESS EXCLUSIVE` isolation.

The conflict behavior is the key engineering property:

```text
ordinary readers
    ↓
can usually continue

ordinary writers
    ↓
may conflict

other strong DDL / schema operations
    ↓
may conflict
```

Do not choose this mode by name alone. Choose it only when the PostgreSQL command semantics or a carefully designed consistency protocol justify it.

---

# 13. `EXCLUSIVE`

`EXCLUSIVE` is a very strong table-level lock.

It conflicts with `ROW SHARE`, `ROW EXCLUSIVE`, `SHARE UPDATE EXCLUSIVE`, `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, and `ACCESS EXCLUSIVE`, but not with `ACCESS SHARE`. citeturn314600search18

That means plain readers can still coexist with it:

```text
EXCLUSIVE
   +
ACCESS SHARE
   = compatible
```

while row-locking reads and writes may be blocked.

This distinction matters when analyzing a blocked system. Seeing an `EXCLUSIVE` lock does not automatically imply that **all** readers are blocked.

---

# 14. `ACCESS EXCLUSIVE`

This is the strongest table-level lock mode.

It conflicts with every other table-level mode, including `ACCESS SHARE`. PostgreSQL documents it as the mode associated with operations such as `TRUNCATE` and many forms of schema-changing activity that must exclude concurrent access. citeturn314600search18

Conceptually:

```text
ACCESS EXCLUSIVE
        │
        ├── SELECT blocked
        ├── INSERT blocked
        ├── UPDATE blocked
        ├── DELETE blocked
        ├── row-locking SELECT blocked
        └── many other relation operations blocked
```

This is why a schema operation can appear to “freeze the application.”

It might not be consuming CPU.

It may simply be waiting for an incompatible lock to be granted, and then causing other sessions to queue behind it.

---

# 15. Which Commands Automatically Acquire Table Locks?

PostgreSQL acquires relation-level locks automatically as part of command execution.

A simplified map is:

| Command category | Typical table lock |
|---|---|
| Ordinary `SELECT` | `ACCESS SHARE` |
| `SELECT ... FOR UPDATE/SHARE/...` | `ROW SHARE` on locking target(s) plus row locks |
| `INSERT` | `ROW EXCLUSIVE` |
| `UPDATE` | `ROW EXCLUSIVE` |
| `DELETE` | `ROW EXCLUSIVE` |
| `MERGE` | `ROW EXCLUSIVE` |
| Some maintenance | often `SHARE UPDATE EXCLUSIVE` |
| Strong schema/structural operations | may require `ACCESS EXCLUSIVE` |

The exact lock mode is command- and version-specific. Never design a deployment solely from a remembered blog post stating that “ALTER TABLE is always blocking” or “this operation is always online.” PostgreSQL has many command-specific lock requirements and they change over versions. Current PostgreSQL documentation should be treated as the authority. citeturn314600search18

---

# 16. `LOCK TABLE`: Explicit Table-Level Locking

PostgreSQL allows an application to explicitly request a table lock:

```sql
BEGIN;

LOCK TABLE inventory IN SHARE MODE;

-- consistency-sensitive work

COMMIT;
```

Syntax:

```sql
LOCK [ TABLE ] [ ONLY ] name [ * ] [ , ... ]
    [ IN lockmode MODE ] [ NOWAIT ]
```

Common examples:

```sql
LOCK TABLE orders IN SHARE MODE;
```

```sql
LOCK TABLE inventory IN ACCESS EXCLUSIVE MODE;
```

```sql
LOCK TABLE orders, order_items IN SHARE MODE;
```

```sql
LOCK TABLE inventory IN EXCLUSIVE MODE NOWAIT;
```

Explicit locks should be viewed as deliberate synchronization mechanisms, not as a generic “make this transaction safe” switch.

---

# 17. Why `LOCK TABLE` Can Be Dangerous

Consider:

```sql
BEGIN;

LOCK TABLE customers IN ACCESS EXCLUSIVE MODE;

SELECT ...;

CALL_EXTERNAL_SERVICE();

UPDATE ...;

COMMIT;
```

Suppose the external service takes 4 seconds.

For 4 seconds the table may be protected by the strongest relation lock.

Now imagine:

```text
Application traffic = 2,000 req/s
```

Even if each blocked request is only waiting, the system may accumulate:

```text
2,000
4,000
6,000
...
```

requests behind the lock boundary depending on the workload and connection pool.

This can cause:

```text
lock held
  ↓
DB waiters
  ↓
connection pool occupancy
  ↓
application queueing
  ↓
request timeout
  ↓
retry traffic
  ↓
more DB pressure
```

The lock becomes the root cause of an apparently unrelated API outage.

---

# 18. Table Locks and MVCC Are Different Axes

Suppose T1 executes:

```sql
BEGIN;
SELECT * FROM orders WHERE id = 10;
```

T1 receives a row version according to its MVCC snapshot.

Now T2 executes:

```sql
UPDATE orders
SET status = 'SHIPPED'
WHERE id = 10;
COMMIT;
```

The ordinary table-level relation locks acquired by these commands are not the thing determining which historical row version T1 sees.

That is MVCC visibility.

The relation locks instead govern whether relation-level operations are compatible.

Therefore:

```text
MVCC visibility
      ≠
relation lock compatibility
      ≠
row lock conflict
      ≠
serializable dependency tracking
```

An expert must know which mechanism is responsible for the observed behavior.

---

# 19. A Single Statement Can Have Multiple Locks

Consider:

```sql
SELECT *
FROM orders
WHERE customer_id = 42
FOR UPDATE;
```

This can involve:

```text
1. relation-level locks
2. row-level locks
3. MVCC visibility rules
4. transaction ownership
5. possible waits on another transaction
```

Now consider:

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 10;
```

The statement participates in:

```text
relation-level: ROW EXCLUSIVE
row-level: target row locking/update behavior
MVCC: tuple visibility/version creation
WAL: durable representation of the change
```

This layered model is much more powerful than saying:

> “The query has a lock.”

The right question is:

> **Which lock, on which resource, owned by which transaction, conflicting with which other operation?**

# 20. Lock Lifetime

Explicit table locks are normally held until the end of the transaction.

Example:

```sql
BEGIN;

LOCK TABLE orders IN SHARE MODE;

SELECT ...;

-- lock remains held

UPDATE ...;

-- lock remains held

COMMIT;
```

A critical production rule follows:

> **Transaction lifetime is lock lifetime for many transaction-level locks.**

Therefore long transactions are not just an MVCC/vacuum problem.

They can also be a lock-retention problem.

```text
Long transaction
      ↓
longer lock lifetime
      ↓
more opportunity for contention
      ↓
more waiting sessions
```

PostgreSQL also documents a savepoint nuance: if a lock is acquired after a savepoint and the savepoint is rolled back, the lock can be released as part of that rollback. citeturn314600search18

---

# 21. Lock Upgrades and Multiple Requests

A transaction may acquire multiple lock modes on the same table during its lifetime.

For example, a transaction may first execute a normal read and later issue an explicit stronger lock.

The important engineering question is not merely:

> “Does the session have a lock?”

but:

> “What strongest effective lock requirement does the transaction now have, and what other lock requests must wait?”

Locking designs that gradually acquire stronger resources can increase contention and deadlock risk.

A robust design usually decides the required synchronization boundary early and acquires resources in a deterministic order.

This connects directly to the upcoming chapter on deadlocks and lock ordering.

---

# 22. Explicit Lock Ordering

Suppose one transaction does:

```sql
LOCK TABLE accounts IN SHARE MODE;
LOCK TABLE orders IN SHARE MODE;
```

while another does:

```sql
LOCK TABLE orders IN SHARE MODE;
LOCK TABLE accounts IN SHARE MODE;
```

If the requested modes conflict with existing holders, an ordering inversion can create a wait cycle.

General rule:

```text
Choose an order
     ↓
Document it
     ↓
Use it everywhere
     ↓
Acquire locks in that order
```

For multiple relations, deterministic ordering is one of the most effective deadlock-prevention strategies.

Do not rely on:

> “The operations are usually fast.”

Deadlocks are about interleaving, not average duration.

---

# 23. Lock Waits Are Not CPU Work

One of the most useful production observations is:

> **A blocked backend can consume little CPU while still causing a major outage.**

Imagine:

```text
CPU = 20%
Memory = normal
Disk = normal

API latency = 8 seconds
```

A superficial diagnosis may conclude:

> “The database is healthy because CPU is low.”

But the actual picture may be:

```text
1 session holds ACCESS EXCLUSIVE
      ↓
400 sessions waiting
      ↓
application pool exhausted
      ↓
requests queue
      ↓
latency explodes
```

Lock contention is therefore a **wait problem**, not necessarily a compute problem.

# 24. Observability: `pg_locks`

PostgreSQL's `pg_locks` system view exposes currently outstanding locks. It can represent locks on:

- relations
- pages
- tuples
- transaction IDs
- virtual transaction IDs
- advisory/user-defined lock objects
- other database objects.

The view contains information about whether a lock is granted and which lock mode is involved. PostgreSQL 18 documents `pg_locks` as a principal mechanism for examining lock manager state. citeturn314600search0turn314600search1

Start with:

```sql
SELECT
    pid,
    locktype,
    relation::regclass AS relation,
    mode,
    granted
FROM pg_locks
WHERE relation IS NOT NULL
ORDER BY relation::regclass::text, pid;
```

The exact query should be adapted to the incident. Avoid turning every production investigation into an enormous cross join that itself becomes expensive.

---

# 25. Join `pg_locks` with `pg_stat_activity`

A more useful operational view is:

```sql
SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.client_addr,
    a.state,
    a.wait_event_type,
    a.wait_event,
    a.xact_start,
    a.query_start,
    a.query,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation
FROM pg_stat_activity a
JOIN pg_locks l
  ON l.pid = a.pid
WHERE l.relation IS NOT NULL
ORDER BY a.xact_start NULLS LAST;
```

Now you can ask:

```text
Who holds the lock?
Who is waiting?
What relation is involved?
What mode is requested?
How long has the transaction existed?
What query is running?
Is the session active or idle in transaction?
```

That turns a vague incident into an evidence-driven diagnosis.

PostgreSQL's monitoring documentation explicitly recommends `pg_locks` for examining outstanding locks and identifying relations with many ungranted locks. citeturn314600search1

---

# 26. Find Blocking Relationships

A useful diagnostic pattern is to identify blocked sessions and their blockers.

Modern PostgreSQL provides helper functions such as:

```sql
pg_blocking_pids(pid)
```

Example:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Then inspect the blocker directly.

For production analysis, combine:

```text
pg_stat_activity
+
pg_locks
+
pg_blocking_pids()
+
PostgreSQL logs
+
application traces
```

Do not terminate sessions before understanding the ownership and business impact of the blocker.

---

# 27. `lock_timeout`

PostgreSQL supports:

```sql
SET lock_timeout = '2s';
```

This limits how long a statement can wait for a lock acquisition attempt.

PostgreSQL 18 documents that `lock_timeout` applies to waits for table, index, row, or other database-object locks, including both explicit and implicitly acquired locks. The timeout is applied separately to each lock acquisition attempt. citeturn314600search7

This can be useful for risky application operations or migrations.

However:

```text
lock_timeout
    ≠
fix for bad locking architecture
```

A timeout converts an unbounded wait into a controlled failure.

It does not eliminate the contention source.

---

# 28. `statement_timeout` vs `lock_timeout`

These are different.

```text
statement_timeout
    ↓
limits total statement execution duration

lock_timeout
    ↓
limits time spent waiting to acquire locks
```

Example:

A query may run for 10 seconds doing CPU work and never wait on a lock.

`lock_timeout` does not solve that.

Conversely, a query can be computationally trivial but spend 10 seconds waiting for `ACCESS EXCLUSIVE`.

`lock_timeout` directly addresses that wait.

Production diagnosis should therefore capture both:

```text
execution time
+
wait time
```

not just the final latency number.

# 29. The Classic Migration Incident

Imagine production traffic is normal:

```text
API latency = 100ms
```

A deployment runs:

```sql
ALTER TABLE orders
ADD COLUMN warehouse_id bigint;
```

Depending on the exact operation and PostgreSQL version, the DDL may require a strong relation lock during some portion of the command.

Suppose a transaction currently holds a conflicting lock for an unexpectedly long time.

Then:

```text
DDL waits
   ↓
DDL requests strong lock remain queued
   ↓
new traffic encounters interactions with queued lock requests
   ↓
latency rises
   ↓
connection pool fills
```

The dangerous mental model is:

> “The migration is one SQL statement, so it should be fast.”

The correct model is:

```text
SQL statement duration
        +
lock acquisition delay
        +
work performed by DDL
        +
dependency on existing transactions
        =
operational impact
```

Migration safety must therefore be evaluated under concurrent production traffic, not just in an empty development database.

---

# 30. Why Idle Transactions Are Dangerous

Consider:

```text
BEGIN;
UPDATE orders SET status = 'PACKED' WHERE id = 100;
-- application waits for another service
-- transaction remains open
```

The session may become:

```text
idle in transaction
```

Yet the transaction can still retain locks.

This creates a dangerous contradiction:

```text
Application thinks:
“I'm not doing database work.”

Database sees:
“The transaction is still open and still owns transactional state.”
```

Always treat `idle in transaction` as an operational state worth investigating when transaction age is high.

---

# 31. Connection Pool Amplification

Suppose your Node.js application has a pool of 100 connections.

One migration-related lock blocks many application statements.

Now:

```text
100 connections
↓
waiting on database locks
↓
new application work has no free connection
↓
requests queue outside PostgreSQL
```

This can make an otherwise moderate lock problem look like a complete application outage.

The database may report:

```text
many sessions waiting
```

while the application reports:

```text
pool exhausted
```

These are the same incident observed from different layers.

# 32. Node.js / NestJS Transaction Hazard

Bad pattern:

```ts
await dataSource.transaction(async (manager) => {
  await manager.query(`LOCK TABLE orders IN ACCESS EXCLUSIVE MODE`);

  await externalPaymentApi.charge();

  await manager.query(`UPDATE orders SET status = 'PAID' WHERE id = $1`, [id]);
});
```

Why it is dangerous:

```text
strong lock
   ↓
external network call
   ↓
unbounded external latency
   ↓
lock remains held
```

Improved architecture:

```text
1. Validate request
2. Perform preconditions that do not require the lock
3. Acquire the minimum necessary lock
4. Do database work
5. Commit quickly
6. Perform external side effects through an outbox/workflow boundary
```

The exact design depends on business requirements, but the principle is stable:

> **Do not hold a strong relation lock across slow or failure-prone external work unless that blocking behavior is explicitly part of the design.**

# 33. Table Lock ≠ Table Serialization

A common mistake is:

```sql
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
```

because:

> “I want no concurrent changes.”

That may technically produce the desired exclusion, but it may also destroy throughput.

For a single-row inventory invariant, a row-level lock can be the correct tool:

```sql
SELECT quantity
FROM inventory
WHERE product_id = $1
FOR UPDATE;
```

For a cross-row business invariant, perhaps:

```text
constraint
or
atomic SQL
or
row locks
or
SERIALIZABLE
```

is sufficient.

The principle is:

```text
smallest correct synchronization boundary
        ↓
prefer it
```

Do not serialize an entire table to protect one row.

---

# 34. Wrong Implementation #1 — “Just Lock the Whole Table”

### Naive approach

```sql
BEGIN;

LOCK TABLE inventory IN ACCESS EXCLUSIVE MODE;

UPDATE inventory
SET quantity = quantity - 1
WHERE id = 42;

COMMIT;
```

### Why it fails operationally

The transaction may only need to protect one inventory item, but the table lock conflicts with a huge set of unrelated operations.

Consequences:

```text
unrelated product requests blocked
read traffic blocked
write traffic blocked
migration interaction risk
latency spikes
throughput collapse
```

### Improved approach

```sql
BEGIN;

SELECT quantity
FROM inventory
WHERE id = 42
FOR UPDATE;

UPDATE inventory
SET quantity = quantity - 1
WHERE id = 42;

COMMIT;
```

Or, when appropriate, use a single atomic update:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE id = 42
  AND quantity > 0
RETURNING quantity;
```

### Production consideration

The second design protects the actual business resource rather than the whole relation.

---

# 35. Wrong Implementation #2 — Treating `ROW EXCLUSIVE` as a Row Lock

### Naive reasoning

> “UPDATE gets ROW EXCLUSIVE, so it only locks the updated rows.”

This is wrong.

`ROW EXCLUSIVE` is a table-level lock mode.

The update also participates in row-level locking and MVCC behavior.

The corrected mental model is:

```text
UPDATE
  │
  ├── relation-level: ROW EXCLUSIVE
  │
  ├── tuple-level effects
  │
  └── MVCC / new row version
```

That distinction becomes extremely important when reading `pg_locks`.

---

# 36. Wrong Implementation #3 — Assuming MVCC Means DDL Cannot Block Reads

### Naive reasoning

> “Readers don't block writers in MVCC, so reads will never be blocked by schema changes.”

Wrong.

A normal `SELECT` holds `ACCESS SHARE`, and `ACCESS EXCLUSIVE` conflicts with `ACCESS SHARE`.

Therefore:

```text
SELECT
  ↓
ACCESS SHARE

DDL/strong structural operation
  ↓
ACCESS EXCLUSIVE

conflict
```

MVCC does not make structural locks disappear.

---

# 37. Wrong Implementation #4 — “The Migration Ran in Staging”

A migration that works in staging may still block production because staging has:

```text
fewer connections
fewer long transactions
less concurrency
smaller data
fewer background workers
fewer replicas
less traffic
```

Production lock safety is workload-dependent.

At minimum, evaluate:

```text
lock mode
lock duration
existing transaction age
concurrent DML
concurrent reads
connection pool size
application timeout policy
rollback strategy
```

---

# 38. Wrong Implementation #5 — Ignoring Lock Queue Effects

A naive engineer sees:

```text
DDL waiting for lock
```

and thinks:

> “Only this DDL is affected.”

But a strong lock request can become part of a queue whose ordering affects later requests.

The operational effect can be much larger than the one blocked command.

Therefore investigate:

```text
blocker
↓
blocked strong request
↓
other sessions behind it
↓
application impact
```

Do not stop at the first waiting PID.

---

# 39. Explicit Table Locks for Consistency Checks

There are situations where a transaction needs to reason about a set of rows while preventing certain concurrent structural or data changes.

For example, a consistency-checking workflow may intentionally use:

```sql
BEGIN;

LOCK TABLE balances IN SHARE MODE;

-- perform consistency-sensitive reads

COMMIT;
```

But this is an advanced technique.

It should be justified by a specific invariant.

The key design questions are:

```text
What anomaly are we preventing?
Which concurrent operations must be excluded?
Why is MVCC insufficient?
Why are row locks insufficient?
Could SERIALIZABLE solve this more safely?
How long will the table lock be held?
What is the expected contention?
```

A correct answer to these questions is more valuable than knowing the `LOCK TABLE` syntax.

---

# 40. `LOCK TABLE` and Snapshot Timing

Advanced transaction designs can be sensitive to the order in which locks and snapshots are acquired.

For example:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

LOCK TABLE orders IN SHARE MODE;

SELECT ...;
```

A relation lock can be acquired before the transaction's first snapshot-dependent command establishes the repeatable-read snapshot.

This can matter in carefully constructed consistency checks.

The broader principle is:

> **Lock timing and snapshot timing are separate dimensions of transaction behavior.**

Experts should not mentally collapse them into one event called “the transaction started.”

---

# 41. Table-Level Locks and Foreign Keys

Foreign-key enforcement introduces concurrency relationships beyond simple application code.

For example, changes to referenced keys can involve stronger row-level protection and transaction-ID waits.

The important takeaway for this chapter is:

```text
schema relation lock
        ≠
foreign-key enforcement lock
```

A production lock graph may therefore contain multiple resource types at once.

If a blocker is not explained by a visible relation conflict, inspect:

```text
transactionid
virtualxid
tuple
relation
```

PostgreSQL 18 explicitly documents that `pg_locks` includes relation, tuple, transaction-ID, and virtual-transaction lock targets, and that row-level locks can be represented through tuple state rather than appearing as a simple relation-level lock. citeturn314600search0turn314600search2

---

# 42. Why `pg_locks` Can Surprise You

Developers often expect:

```text
UPDATE row A
→ pg_locks shows row A
```

But PostgreSQL's lock manager representation is layered.

Relation locks are visible directly through `locktype = 'relation'`.

Tuple-level locking can involve waits on transaction IDs, and PostgreSQL documents row-level lock information as being stored in locked rows and inspectable using `pgrowlocks`. citeturn314600search2turn314600search5

Therefore absence of an obvious tuple lock row in one `pg_locks` query does not prove absence of row-level contention.

This is why lock forensics requires understanding the implementation rather than relying on one simplified query.

# 44. Safe Termination Decision

Before terminating a blocker ask:

```text
Is this session actually the blocker?

Who owns it?

Is it an application request?

Is it a migration?

Is it a maintenance operation?

What will rollback do?

How many sessions are waiting?

Will terminating it trigger automatic application retries?

Could retries create another thundering herd?
```

The fastest way to make a lock incident worse is to remove the blocker without understanding the resulting retry behavior.

# 45. Security Perspective

Table-level locks are not an authorization mechanism.

This is wrong thinking:

> “Only one service gets the table lock, so tenant data is safe.”

Locks control concurrency, not access policy.

Use authorization mechanisms for access control:

```text
roles
GRANT / REVOKE
RLS
application authorization
schema ownership
```

Use locks for concurrency control:

```text
lock modes
row locks
advisory locks
serialization mechanisms
```

Conflating these responsibilities produces weak security designs.

# 46. Multi-Tenant Systems

Consider a shared `orders` table containing:

```text
tenant_id
branch_id
order_id
status
amount
```

An application action affecting one tenant rarely needs a table-wide lock.

Bad:

```sql
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
```

Better candidates may include:

```text
row locks for specific orders
advisory locks keyed to a tenant workflow
constraints
atomic updates
SERIALIZABLE for suitable cross-row invariants
```

The key question is:

> “What exact business resource must be mutually coordinated?”

If the answer is:

```text
tenant T + workflow W
```

then a table-wide lock is usually an overly broad synchronization boundary.

# 47. Jewellery ERP Example: Stock Adjustment

Suppose two branches concurrently adjust stock for the same product.

A dangerous implementation is:

```sql
BEGIN;
LOCK TABLE stock IN ACCESS EXCLUSIVE MODE;

-- adjust one SKU for one branch

COMMIT;
```

This blocks unrelated branch operations.

A narrower design might be:

```sql
BEGIN;

SELECT quantity
FROM stock
WHERE branch_id = $1
  AND product_id = $2
FOR UPDATE;

UPDATE stock
SET quantity = quantity + $3
WHERE branch_id = $1
  AND product_id = $2;

COMMIT;
```

Or a carefully designed atomic update may eliminate the need for an explicit lock.

The database should serialize the **conflicting resource**, not the entire ERP.

# 48. Deployment and Migration Design

Before running a migration in production, ask:

```text
What lock mode does this statement acquire?

Does it need a table scan?

Can existing transactions delay its lock acquisition?

How long might the operation hold its lock?

What traffic is blocked while it runs?

Can it be decomposed into safer steps?

Can the operation be performed asynchronously?

What is the rollback / forward-fix strategy?

What happens if the deploy is interrupted?
```

A safer pattern for many schema changes is staged evolution:

```text
1. Add compatible schema
2. Deploy code that understands old + new shape
3. Backfill in controlled batches
4. Add validation / constraints carefully
5. Switch reads/writes
6. Remove old schema later
```

This is not universally required. The exact migration depends on the feature and PostgreSQL version.

The principle is:

> **Separate compatibility changes from destructive or strongly blocking changes.**

# 49. Online Migration Is a Workload Property

A migration is not “online” merely because documentation says the SQL command is designed to minimize blocking.

Operational reality depends on:

```text
existing transactions
lock queue
relation size
data distribution
I/O throughput
DDL duration
replication topology
application timeouts
connection pool behavior
```

An operation can be logically online while still creating a serious transient lock wait.

Measure the actual workload.

# 50. Performance Analysis

Table locks can affect performance through waiting rather than computation.

Model the impact as:

```text
Lock contention
    ↓
Wait time
    ↓
Connection occupancy
    ↓
Queue depth
    ↓
Tail latency
    ↓
Timeouts
    ↓
Retries
    ↓
Additional load
```

This can create nonlinear behavior.

For example:

```text
baseline = 100 ms

lock wait = 2 s

application timeout = 3 s

retry = 1 extra attempt
```

The retry load can increase concurrency precisely when the database is already blocked.

Therefore lock incidents are often **queueing-system incidents**, not merely SQL incidents.

# 51. Why `EXPLAIN ANALYZE` Does Not Explain Every Lock Problem

`EXPLAIN ANALYZE` tells you about query execution.

It does not, by itself, provide a complete explanation of lock waiting outside the query plan.

A query can have an excellent plan:

```text
Index Scan
estimated rows = 1
actual rows = 1
execution = 2 ms
```

and still experience:

```text
lock wait = 4 seconds
```

The total user-visible latency is then:

```text
4s wait + 2ms execution
```

The plan was not the problem.

This is why production latency investigations must distinguish:

```text
planning
execution
I/O
lock wait
network
application queueing
```

# 52. AI / Vibe-Coding Mistakes

## Mistake 1 — “Use `ACCESS EXCLUSIVE` for safety”

Why it looks reasonable:

```text
strongest lock = maximum protection
```

Why it fails:

```text
maximum exclusion = maximum contention
```

## Mistake 2 — “MVCC means DDL cannot block reads”

Wrong because strong relation locks can conflict with `ACCESS SHARE`.

## Mistake 3 — “ROW EXCLUSIVE is a row lock”

Wrong because it is table-level.

## Mistake 4 — “Retry every lock timeout automatically”

This can create:

```text
contention
↓
timeout
↓
retry
↓
more contention
```

Retry policy must be workload-aware.

## Mistake 5 — “Run migrations during deploy with default settings”

A deployment system may have:

```text
no lock timeout
long statement timeout
no preflight
no active blocker detection
```

That is an operational risk.

## Mistake 6 — “The query is only one line”

SQL length has no relationship to lock impact.

```text
one-line DDL
```

can block thousands of requests.

## Mistake 7 — “Kill the blocker immediately”

Sometimes necessary, but unsafe without understanding rollback and retry effects.

# 54. Testing Table-Level Lock Behavior

You should be able to reproduce lock behavior with two sessions.

## Session A

```sql
BEGIN;

LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;

SELECT pg_sleep(30);

COMMIT;
```

## Session B

```sql
SELECT *
FROM orders
LIMIT 1;
```

Observe that Session B can block because its `SELECT` requires `ACCESS SHARE` and `ACCESS SHARE` conflicts with `ACCESS EXCLUSIVE`. citeturn314600search18

Now inspect:

```sql
SELECT
    pid,
    relation::regclass,
    mode,
    granted
FROM pg_locks
WHERE relation = 'orders'::regclass;
```

This lab should become muscle memory.

---

# 55. Testing Compatible Locks

Session A:

```sql
BEGIN;
LOCK TABLE orders IN SHARE MODE;
SELECT pg_sleep(30);
```

Session B:

```sql
BEGIN;
LOCK TABLE orders IN SHARE MODE;
```

Because `SHARE` is compatible with another `SHARE` lock, Session B can acquire it concurrently. The compatibility matrix, not the intuitive meaning of “share”, determines the result. citeturn314600search18

Now test:

```sql
BEGIN;
INSERT INTO orders(status) VALUES ('PENDING');
```

A `ROW EXCLUSIVE` request conflicts with the existing `SHARE` lock and can wait.

This is a good exercise because it teaches you to predict waits before running the test.

# 56. Lock Forensics with `pgrowlocks`

For row-level questions, PostgreSQL provides the optional `pgrowlocks` module.

```sql
CREATE EXTENSION IF NOT EXISTS pgrowlocks;

SELECT *
FROM pgrowlocks('orders');
```

PostgreSQL 18 documents `pgrowlocks` as showing row-locking information including tuple IDs and locker transaction IDs. Access is privilege-controlled. citeturn314600search5

Use this tool when relation-level information is insufficient and row-level forensic detail is necessary.

Do not install it just because “more observability is always better.” Use it when its diagnostic value justifies the operational and privilege considerations.

# 57. Table Locks and Savepoints

Consider:

```sql
BEGIN;

SAVEPOINT before_lock;

LOCK TABLE orders IN SHARE MODE;

ROLLBACK TO SAVEPOINT before_lock;
```

The transaction-level consequences of the lock acquisition can be affected by savepoint rollback. PostgreSQL documents that locks acquired after a savepoint can be released when rolling back to that savepoint. citeturn314600search18

This is an advanced mechanism.

Do not use savepoints merely as an ad hoc lock-management layer without understanding transaction semantics.

---

# 58. Table Locking and Retry Design

Suppose an explicit lock uses:

```sql
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE NOWAIT;
```

If another session holds a conflicting lock, the statement fails immediately instead of waiting.

This can be useful for:

```text
leader-only maintenance
exclusive administrative jobs
migration coordination
short operational probes
```

But an immediate failure is not automatically a reason to retry in a tight loop.

Bad:

```text
NOWAIT failure
↓
retry immediately
↓
NOWAIT failure
↓
retry immediately
```

Better:

```text
NOWAIT failure
↓
record contention
↓
backoff / reschedule
↓
retry through controlled orchestration
```

# 59. Decision Framework

Before introducing a table-level lock ask:

```text
1. What invariant am I protecting?
2. What exact resources conflict?
3. Is MVCC already sufficient?
4. Can a constraint enforce it?
5. Can one atomic statement enforce it?
6. Can row-level locking enforce it?
7. Would SERIALIZABLE be more appropriate?
8. Why is table-level locking required?
9. Which lock mode is sufficient?
10. How many operations will it block?
11. How long will it be held?
12. How will production contention be observed?
13. What happens on timeout?
14. What happens on retry?
15. What happens during deployment failure?
```

If you cannot answer these questions, the locking design is not ready for production.

# 60. Trade-Off Matrix

| Technique | Conflict scope | Concurrency | Complexity | Typical use |
|---|---|---:|---:|---|
| Atomic SQL | statement-defined | High | Low–Medium | counters, conditional writes |
| Row lock | row(s) | High | Medium | workflows on specific records |
| Table lock | whole relation | Low–Medium | Medium | structural/consistency coordination |
| Advisory lock | application-defined key | Depends | Medium–High | distributed workflow coordination |
| Serializable | transaction dependency graph | Depends | High | strong cross-row invariants |
| Constraint | schema-defined invariant | High | Low–Medium | uniqueness, references, checks |

The point is not to declare one technique superior.

The point is to map the invariant to the narrowest mechanism that actually guarantees it.

# 63. Interview Questions

## Junior

**Q: What is a table-level lock?**

Weak answer:
> A lock on a table.

Strong answer:
> A relation-level concurrency-control lock whose mode determines which other table-level operations can proceed concurrently.

## Mid-Level

**Q: Does `ROW EXCLUSIVE` lock individual rows?**

Weak answer:
> Yes.

Strong answer:
> No. `ROW EXCLUSIVE` is a table-level lock mode. DML also performs row-level locking/versioning separately.

## Senior

**Q: Why can a simple `SELECT` be blocked by a migration?**

Strong answer:
> A plain `SELECT` acquires `ACCESS SHARE`, and `ACCESS EXCLUSIVE` conflicts with `ACCESS SHARE`, so an incompatible schema operation can block readers even though PostgreSQL uses MVCC for data visibility.

## Staff

**Q: Why can lock contention cause an API outage when database CPU is low?**

Strong answer:
> Blocked sessions consume connection-pool capacity and increase queueing latency even when they are not doing CPU-intensive work. The resulting pool exhaustion can propagate into request timeouts and retries.

## Principal

**Q: When should a table lock be replaced with row locking, atomic SQL, a constraint, or SERIALIZABLE?**

Expert answer:
> Choose based on the invariant and conflict set. Use the narrowest mechanism that actually guarantees correctness, then quantify contention and failure behavior under the target workload. A table lock is justified only when the invariant genuinely spans the relation-level resource or when PostgreSQL command semantics require that scope.

# 64. Trick Questions

### “ACCESS SHARE means readers block writers.”

False.

`ACCESS SHARE` conflicts only with `ACCESS EXCLUSIVE`. Ordinary DML uses `ROW EXCLUSIVE`, which is compatible with `ACCESS SHARE`. citeturn314600search18

### “MVCC means PostgreSQL never waits.”

False.

MVCC reduces many read/write conflicts, but locking, transaction dependencies, row updates, DDL, and other operations can wait.

### “More restrictive lock means more correctness.”

False.

It may prevent more concurrency without protecting the actual invariant better.

### “A lock timeout means the transaction is safe to retry.”

False.

The application must understand transaction state, side effects, idempotency, and the specific failure.

# 68. Chapter Summary

The central model is:

```text
PostgreSQL concurrency
        │
        ├── MVCC
        │     └── visibility / row versions
        │
        ├── Row-level locks
        │     └── specific row conflicts
        │
        ├── Table-level locks
        │     └── relation-wide compatibility
        │
        ├── Constraints
        │     └── valid database states
        │
        └── Serializable machinery
              └── transaction-level anomaly prevention
```

The most important lesson is:

> **Table-level locking is a relation-wide concurrency boundary, not a generic safety switch. Use the narrowest mechanism that protects the actual invariant, keep strong locks short-lived, understand the conflict matrix, and diagnose lock waits as queueing problems rather than merely SQL problems.**
