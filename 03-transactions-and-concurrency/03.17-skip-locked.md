# 03.17 — SKIP LOCKED

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains PostgreSQL's `SKIP LOCKED` behavior from first principles and shows how to use it safely for queue-like workloads, worker pools, batch processing, inventory workflows, and other high-concurrency systems without confusing work distribution with general-purpose consistency.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- explain exactly what `SKIP LOCKED` changes in a locking read;
- distinguish `SKIP LOCKED` from `NOWAIT` and ordinary blocking behavior;
- understand why skipping a locked row intentionally produces an inconsistent view;
- design concurrent consumers around a PostgreSQL-backed work queue;
- reason about transaction and lock lifetime;
- understand how `ORDER BY`, `LIMIT`, joins, and locking clauses affect work selection;
- identify starvation, fairness, hot-partition, and retry hazards;
- choose between `SKIP LOCKED`, blocking locks, `NOWAIT`, advisory locks, and external queue systems;
- build safe Node.js/NestJS worker transactions using a single checked-out connection;
- diagnose contention using `pg_locks`, `pg_stat_activity`, and application telemetry;
- understand failure, crash, rollback, retry, and idempotency behavior;
- distinguish queue-oriented semantics from ordinary business-consistency semantics;
- design production-grade batching, backoff, visibility, and recovery strategies.

PostgreSQL 18 documentation states that `SKIP LOCKED` skips rows that cannot be immediately locked, that this produces an inconsistent view unsuitable for general-purpose work, and that it can be useful for avoiding lock contention among multiple consumers of a queue-like table. `NOWAIT` instead raises an error when the row cannot be locked immediately. citeturn916313search18turn916313search0

# 2. The Central Mental Model

A normal locking read behaves approximately like:

```text
Find candidate row
      |
      v
Try to lock row
      |
      +---- lock available ----> acquire ----> return row
      |
      +---- lock held ----------> WAIT
```

With `NOWAIT`:

```text
Find candidate row
      |
      v
Try to lock row
      |
      +---- available ---------> acquire ----> return row
      |
      +---- locked ------------> ERROR
```

With `SKIP LOCKED`:

```text
Find candidate row
      |
      v
Try to lock row
      |
      +---- available ---------> acquire ----> return row
      |
      +---- locked ------------> SKIP ----> inspect next candidate
```

The key is that `SKIP LOCKED` changes **conflict handling**, not transaction isolation in general.

It does not mean:

> "Read the latest data without locks."

It means:

> "When this locking read encounters a row that cannot be locked immediately, do not wait for it; move on."

---

# 3. Precise Definitions

## 3.1 Simple Definition

`SKIP LOCKED` tells PostgreSQL not to wait for rows that are already locked when executing a row-locking clause such as `FOR UPDATE`; those rows are skipped.

## 3.2 Engineering Definition

A locking query using `SKIP LOCKED` attempts to acquire row-level locks as it identifies candidate tuples. Rows whose required row lock cannot be immediately obtained are omitted from the result rather than becoming blocking points. This allows independent workers to consume different rows concurrently.

## 3.3 Expert Definition

`SKIP LOCKED` is a lock-avoidance strategy for row-locking clauses. It deliberately weakens the completeness/consistency properties of the selected row set in exchange for concurrency and progress. It is therefore appropriate when the application treats rows as independently claimable work items and can tolerate a worker seeing a subset of currently eligible rows. PostgreSQL also notes that `SKIP LOCKED` applies to row-level locks; the required `ROW SHARE` table-level lock is still acquired normally. citeturn916313search18

# 4. Why `SKIP LOCKED` Exists

Imagine a queue table:

```text
work_items
----------
id | status   | priority
1  | pending  | 100
2  | pending  | 90
3  | pending  | 80
4  | pending  | 70
```

Suppose Worker A claims row 1 and keeps its transaction open briefly.

Without `SKIP LOCKED`:

```text
Worker A -> locks row 1
Worker B -> reaches row 1 -> WAITS
```

Worker B may be perfectly capable of processing row 2, 3, or 4, but it is blocked behind a resource it does not actually need.

With `SKIP LOCKED`:

```text
Worker A -> locks row 1
Worker B -> row 1 locked -> skip
         -> row 2 available -> claim row 2
```

This converts:

```text
contention through waiting
```

into:

```text
contention avoidance through work redistribution
```

That is why PostgreSQL documents queue-like consumption as a principal use case. citeturn916313search18

---

# 5. `SKIP LOCKED` Is Not a General-Purpose Consistency Feature

This is the most important warning in the chapter.

PostgreSQL explicitly says that skipping locked rows provides an inconsistent view and is not suitable for general-purpose work. citeturn916313search18

That means this pattern can be excellent:

```sql
SELECT id
FROM work_items
WHERE status = 'pending'
ORDER BY priority DESC, id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

but dangerous for a business rule like:

> "Select all rows satisfying condition X and prove there are none others before taking an action."

Why?

Because rows hidden by the lock are still real candidates. They are simply temporarily unavailable to this worker.

Conceptually:

```text
Logical candidate set:

[A] [B] [C] [D] [E]

Locked:
    [C]

SKIP LOCKED sees:
[A] [B] [D] [E]

But C did not cease to exist.
```

Therefore:

```text
SKIP LOCKED
= work allocation optimization

NOT

SKIP LOCKED
= stronger correctness guarantee
```

# 6. Canonical Queue Pattern

A common queue schema is:

```sql
CREATE TABLE work_items (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id    bigint NOT NULL,
    payload      jsonb NOT NULL,
    status       text NOT NULL CHECK (status IN ('pending', 'processing', 'done', 'failed')),
    priority     integer NOT NULL DEFAULT 0,
    available_at timestamptz NOT NULL DEFAULT now(),
    attempts     integer NOT NULL DEFAULT 0,
    locked_at    timestamptz,
    completed_at timestamptz,
    created_at   timestamptz NOT NULL DEFAULT now()
);
```

A worker can claim a batch with:

```sql
BEGIN;

SELECT id, tenant_id, payload
FROM work_items
WHERE status = 'pending'
  AND available_at <= now()
ORDER BY priority DESC, id
FOR UPDATE SKIP LOCKED
LIMIT 20;
```

Then claim the rows in the same transaction:

```sql
UPDATE work_items
SET status = 'processing',
    attempts = attempts + 1,
    locked_at = now()
WHERE id IN (...);

COMMIT;
```

The exact implementation can be optimized into a single statement or CTE, for example:

```sql
WITH claimed AS (
    SELECT id
    FROM work_items
    WHERE status = 'pending'
      AND available_at <= now()
    ORDER BY priority DESC, id
    FOR UPDATE SKIP LOCKED
    LIMIT 20
)
UPDATE work_items AS w
SET status = 'processing',
    attempts = w.attempts + 1,
    locked_at = now()
FROM claimed
WHERE w.id = claimed.id
RETURNING w.*;
```

This is often preferable because selection and state transition occur within one database statement/transaction boundary.

# 7. Claiming vs Processing

One of the most important architectural decisions is whether the row lock is held during actual work.

## 7.1 Anti-Pattern: Hold the Row Lock During External Work

```text
BEGIN
  SELECT ... FOR UPDATE SKIP LOCKED
  call payment provider
  call API
  resize image
  publish message
  update row
COMMIT
```

This can be disastrous because the lock lifetime now includes network latency, retries, remote outages, and arbitrary application execution time.

The lock should generally protect a **short claim transition**, not surround the entire work duration.

## 7.2 Better Pattern: Claim Quickly, Work Outside Transaction

```text
Transaction
    |
    +-- select pending rows + lock
    +-- transition to processing
    +-- commit quickly

Then outside transaction:

worker
  |
  +-- perform external work
  +-- update result
```

The row is now reserved through durable state rather than a database lock.

This creates a critical distinction:

```text
Database lock
= temporary coordination

Processing status
= durable ownership state
```

A production queue often needs both.

---

# 8. Exactly Why the Claim Must Be Durable

A row lock disappears when the transaction ends.

That is useful for queue claiming, but not enough for long-running jobs.

Consider:

```text
Worker A
BEGIN
  lock job 42
COMMIT

Worker A crashes 3 seconds later.
```

If there is no durable state change, the system has no memory that A had claimed the work.

A safer flow is:

```text
pending
   |
   | atomic claim
   v
processing
   |
   +---- success ----> done
   |
   +---- retry ------> pending + next_attempt_at
   |
   +---- terminal ---> failed
```

That is a state-machine problem, not merely a locking problem.

This connects directly to the earlier data-modeling principles: lock state is ephemeral; durable workflow state belongs in data.

---

# 9. `SKIP LOCKED` and Multiple Workers

Suppose 100 jobs are pending and 10 workers each request 10 rows.

With an appropriate query:

```sql
SELECT id
FROM work_items
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

workers can naturally divide the available rows:

```text
Worker A -> 1..10
Worker B -> 11..20
Worker C -> 21..30
...
```

The exact allocation is an execution-time outcome, not a contractual partitioning scheme.

Workers should therefore not assume:

> "Worker B always gets the next numerical range."

The safe assumption is:

> "Each worker receives some currently lockable subset of eligible work."

---

# 10. Ordering: Priority and Fairness

A queue usually needs an ordering policy:

```sql
ORDER BY priority DESC, available_at ASC, id ASC
```

Ordering provides a preference, not a global reservation guarantee.

Concurrent workers can affect which rows each worker actually locks.

Consider:

```text
priority
--------
A = 100
B = 99
C = 98
```

Worker 1 obtains A.

Worker 2 reaches A and skips it, then may claim B.

This is desirable for concurrency, but it means the highest-priority item is not globally guaranteed to be processed before lower-priority items in all concurrent circumstances.

Therefore:

```text
ORDER BY
= selection preference

SKIP LOCKED
= lock contention avoidance

Together
= approximately priority-oriented concurrent scheduling
```

not strict serial priority execution.

# 11. Starvation

`SKIP LOCKED` introduces a real possibility of starvation.

Suppose a particular row is repeatedly locked by another long-running or high-throughput worker before every worker that searches for it can acquire it.

Then:

```text
Worker attempts
   |
   +--> row locked -> skip
   |
   +--> row locked -> skip
   |
   +--> row locked -> skip
   |
   +--> row locked -> skip
   |
   +--> ...
```

The row may remain eligible but repeatedly overlooked.

Potential causes include:

- extremely hot jobs;
- unfair scheduling;
- transactions that hold locks too long;
- a permanently failing item that keeps being selected and locked;
- ordering that keeps returning other rows first;
- a small candidate window combined with high concurrency;
- tenant-level concentration of work.

Mitigations include:

```text
short claim transactions
+
retry timestamps
+
attempt counters
+
lease/visibility timeouts
+
backoff
+
aging priority
+
periodic reconciliation
+
monitoring oldest pending age
```

Do not assume that `SKIP LOCKED` automatically provides fairness.

---

# 12. The Queue's Real Metric Is Often Age, Not Throughput

A worker pool can report excellent throughput while a subset of jobs silently waits for hours.

Suppose:

```text
10,000 jobs completed/minute
```

but:

```text
oldest pending job = 4 hours
```

The system is not healthy for every workload.

Useful metrics include:

```text
queue depth
oldest pending age
oldest processing age
claim latency
processing latency
retry count
failure count
jobs/sec
worker utilization
per-tenant backlog
```

For `SKIP LOCKED` systems, **oldest age** is especially important because skipped rows may temporarily disappear from a worker's immediate result set.

# 13. Transaction Lifetime and Lock Lifetime

Consider:

```sql
BEGIN;

SELECT ...
FOR UPDATE SKIP LOCKED
LIMIT 10;

-- process for 30 seconds

COMMIT;
```

Those rows remain locked for the duration of the transaction.

That can defeat the purpose of `SKIP LOCKED`.

A better pattern is:

```text
T1
BEGIN
  claim rows
  UPDATE status='processing'
COMMIT

--- long work outside transaction ---

T2
BEGIN
  mark done
COMMIT
```

The transaction should generally be proportional to the state transition, not the job execution time.

This also reduces:

- lock waits;
- tuple contention;
- idle-in-transaction exposure;
- pool occupancy;
- deadlock surface;
- vacuum interference from long transactions.

---

# 14. `SKIP LOCKED` Does Not Avoid All Locks

A common misconception is:

> "With `SKIP LOCKED`, the query never waits."

That is too broad.

PostgreSQL documents that `NOWAIT` and `SKIP LOCKED` apply to row-level locks, while the required `ROW SHARE` table-level lock is still acquired in the normal way. citeturn916313search18

Therefore:

```text
SKIP LOCKED
       |
       +-- row conflict -> skip
       |
       +-- required table-level lock -> normal locking behavior
```

This matters during DDL, maintenance, migrations, and unusual table-level contention.

At scale, the queue may therefore still experience blocking unrelated to the row locks being skipped.

---

# 15. Joins and Lock Scope

Consider:

```sql
SELECT w.id, t.name
FROM work_items AS w
JOIN tenants AS t ON t.id = w.tenant_id
WHERE w.status = 'pending'
FOR UPDATE SKIP LOCKED;
```

Without careful locking scope, the query can involve rows from more than one table in the locking clause's semantics.

When only the work item should be locked:

```sql
SELECT w.id, t.name
FROM work_items AS w
JOIN tenants AS t ON t.id = w.tenant_id
WHERE w.status = 'pending'
FOR UPDATE OF w SKIP LOCKED;
```

This is usually the correct mental model for queue workers:

```text
work_items -> ownership boundary

tenants -> reference data
```

The worker should not accidentally serialize on unrelated tenant rows.

PostgreSQL documents that a locking clause without a table list affects all tables used in the statement, while a clause naming a specific table restricts locking to that table. citeturn916313search18

---

# 16. `LIMIT` Is Central to Batch Consumption

A typical worker pattern is:

```sql
SELECT id
FROM work_items
WHERE status = 'pending'
ORDER BY priority DESC, id
FOR UPDATE SKIP LOCKED
LIMIT 100;
```

The limit bounds the claim set.

This is important for:

- memory use;
- lock footprint;
- transaction duration;
- application payload size;
- failure blast radius;
- fairness among workers.

A worker that claims 100,000 jobs in one transaction is not necessarily better than a worker that claims 100.

Larger batches can improve amortization but increase:

```text
lock footprint
+
rollback cost
+
transaction size
+
contention concentration
+
recovery work
```

Tune batch size from measurements.

---

# 17. `ORDER BY` and Locking Interaction

PostgreSQL has documented behavior where ordering and locking can interact unexpectedly under `READ COMMITTED` when concurrent updates change ordering columns after rows are initially identified and before they are locked. The query can return rows out of order in such circumstances. PostgreSQL notes that a subquery pattern can enforce locking before sorting, but it may lock more rows and have substantial performance cost. At `REPEATABLE READ` or `SERIALIZABLE`, the corresponding conflict can instead result in a serialization failure. citeturn916313search20

Therefore do not assume:

```sql
ORDER BY priority
FOR UPDATE SKIP LOCKED
```

means:

> "I have a mathematically strict global priority queue."

It means the executor uses the query's plan and concurrent locking rules to produce a best-effort ordered batch under concurrency.

For queue systems, define what level of ordering is actually required:

```text
strict global order
vs
priority preference
vs
FIFO approximation
vs
fair work distribution
```

Then design accordingly.

# 18. Efficient Claiming With a Partial Index

A queue frequently filters on a small active subset:

```sql
WHERE status = 'pending'
  AND available_at <= now()
```

A partial index can reduce the candidate search space:

```sql
CREATE INDEX work_items_pending_idx
ON work_items (priority DESC, available_at, id)
WHERE status = 'pending';
```

Whether this is actually beneficial must be verified with the workload and `EXPLAIN`.

Inspect the plan:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM work_items
WHERE status = 'pending'
  AND available_at <= now()
ORDER BY priority DESC, available_at, id
FOR UPDATE SKIP LOCKED
LIMIT 100;
```

Look for:

- estimated vs actual rows;
- index scan vs sequential scan;
- rows filtered;
- buffer hits and reads;
- loop counts;
- time spent locating candidates;
- whether the executor scans many locked/unusable rows before finding the batch.

`SKIP LOCKED` correctness does not depend on a specific index, but queue performance often does.

# 19. Naive Approach → Why It Fails → Improved Approach

## Naive Approach

```sql
SELECT *
FROM work_items
WHERE status = 'pending'
LIMIT 10;
```

Then:

```ts
for (const item of rows) {
  await claim(item.id);
}
```

### Why It Fails

Two workers can select the same rows before either claims them.

The workflow becomes:

```text
SELECT
   |
   v
application delay
   |
   v
UPDATE
```

That gap is a race condition.

## Improved Approach

Claim atomically through a locking transaction:

```sql
WITH claimed AS (
    SELECT id
    FROM work_items
    WHERE status = 'pending'
    ORDER BY priority DESC, id
    FOR UPDATE SKIP LOCKED
    LIMIT 10
)
UPDATE work_items w
SET status = 'processing',
    attempts = attempts + 1,
    locked_at = now()
FROM claimed c
WHERE w.id = c.id
RETURNING w.*;
```

### Why It Works

The candidate selection and ownership transition share one transactional synchronization boundary.

### Production Considerations

Still define:

- stale processing recovery;
- idempotency;
- retry policy;
- failure transitions;
- tenant fairness;
- observability;
- batch size;
- transaction timeout.

### Alternative

Use an external durable queue when the workload requires advanced delivery guarantees, scheduling, fan-out, delayed delivery, or cross-service semantics that exceed a relational queue's strengths.

### Trade-Off

A PostgreSQL queue keeps transactional state and work metadata together, but it makes queue throughput, vacuum, indexing, lock contention, and retention part of database operations.

# 20. Claiming and Idempotency

A worker must assume this can happen:

```text
claim succeeds
   |
work executes
   |
worker crashes before completion update
```

The system may later retry the job.

Therefore a queue using `SKIP LOCKED` should normally be **at-least-once**, unless stronger external machinery changes the guarantees.

Design handlers so repeated execution is safe:

```sql
INSERT INTO payments_external_results (provider_id, result)
VALUES ($1, $2)
ON CONFLICT (provider_id) DO NOTHING;
```

or use a durable business idempotency key.

Do not build correctness around:

> "The worker should only run once."

Crashes, timeouts, retries, network ambiguity, and process restarts make exactly-once application behavior much harder than row claiming itself.

# 21. Failure and Recovery State Machine

A production queue should define explicit transitions:

```text
             +----------------+
             |     pending    |
             +----------------+
                      |
                claim / lock
                      v
             +----------------+
             |   processing   |
             +----------------+
                |          |
             success      failure
                |          |
                v          v
             +------+   retryable?
             | done |       |
             +------+   yes | no
                          |    |
                          v    v
                       pending failed
```

A crash detector might use:

```sql
WHERE status = 'processing'
  AND locked_at < now() - interval '15 minutes'
```

but this threshold must be workload-specific.

Recovery is not just:

```sql
UPDATE ... SET status='pending'
```

You also need to reason about:

- whether work may still be executing elsewhere;
- whether an external side effect already happened;
- whether retry is safe;
- whether attempts should increment;
- whether a poisoned item needs quarantine.

# 22. Tenant Fairness

In a multi-tenant system, `SKIP LOCKED` can unintentionally favor the tenant with the largest backlog.

Suppose:

```text
Tenant A -> 1,000,000 pending jobs
Tenant B -> 100 jobs
Tenant C -> 50 jobs
```

If workers always select globally:

```sql
ORDER BY priority DESC, id
```

Tenant A may dominate execution.

Possible designs include:

```text
per-tenant queues
weighted scheduling
tenant-aware ordering
quota-based claiming
separate worker pools
partitioned queue tables
```

The right solution depends on fairness requirements and workload shape.

Do not confuse:

```text
database-level concurrency
```

with:

```text
scheduler-level fairness
```

`SKIP LOCKED` solves the first problem; it does not automatically solve the second.

# 23. `SKIP LOCKED` vs `NOWAIT` vs Blocking

| Behavior | Blocking Lock | `NOWAIT` | `SKIP LOCKED` |
|---|---|---|---|
| Locked row encountered | Wait | Error | Skip |
| Result completeness | More complete | Fails fast | Intentionally incomplete |
| Good for work queues | Sometimes | Sometimes | Excellent fit |
| Good for strict consistency checks | Possible | Possible | Usually unsuitable |
| Main benefit | Coordination | Immediate failure | Parallel work distribution |
| Main hazard | Wait chains | Retry/error handling | Starvation/incomplete view |

A useful decision rule:

```text
Need the exact row?
    -> blocking or NOWAIT

Need any available row?
    -> SKIP LOCKED
```

But even this should be refined by the business invariant.

---

# 24. `SKIP LOCKED` vs Advisory Locks

Advisory locks protect application-defined keys:

```sql
SELECT pg_try_advisory_xact_lock(12345);
```

`SKIP LOCKED` is attached to actual row locks on table data.

Use row locking when:

```text
ownership corresponds to a real row
```

Use advisory locking when:

```text
ownership corresponds to a logical key
that may not map naturally to one row
```

Example:

```text
customer:42
warehouse:7
external-account:ABC123
```

Advisory locks can be useful, but they create a separate coordination namespace that the application must document and consistently follow.

# 25. Connection Pooling: A Critical Node.js Hazard

With `node-postgres`, transaction state belongs to the checked-out PostgreSQL connection.

Correct:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  const result = await client.query(claimSql);

  // process claim transition

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

Incorrect:

```ts
await pool.query('BEGIN');
await pool.query(claimSql);
await pool.query('COMMIT');
```

for a transaction that requires connection affinity.

The queue may appear correct in low load while failing under pool concurrency because separate calls can execute on different sessions.

This is one of the most common application-level mistakes in PostgreSQL concurrency code.

# 26. ORM Hazards

Be especially skeptical of ORM APIs that hide:

- the transaction connection;
- locking clauses;
- isolation level;
- batch scope;
- transaction lifetime.

A query such as:

```ts
repository.find({ where: { status: 'pending' } });
```

does not imply row locking.

Likewise, an ORM option named something like `lock: 'pessimistic_write'` is not enough to prove correct queue semantics.

Verify the generated SQL and transaction boundaries.

For high-value concurrency code:

```text
ORM abstraction
      ↓
Generated SQL
      ↓
PostgreSQL semantics
      ↓
Observed behavior
```

The database behavior, not the ORM method name, is the source of truth.

---

# 27. External API Calls: Never Confuse Lock Ownership With Job Ownership

Bad:

```text
BEGIN
  SELECT ... FOR UPDATE SKIP LOCKED
  charge card
  call courier
  publish event
COMMIT
```

Problems:

```text
remote API slow
        ↓
transaction stays open
        ↓
row remains locked
        ↓
other workers skip it
        ↓
throughput falls
        ↓
worker pool fills
```

Better:

```text
TX 1:
claim + durable state transition
        ↓
COMMIT
        ↓
external work
        ↓
TX 2:
record result
```

Then pair it with an outbox/idempotency architecture where side effects require transactional guarantees.

# 28. Queue Tables and Vacuum

Queue workloads frequently churn rows:

```text
pending
  -> processing
  -> done
```

If rows are updated repeatedly, dead tuples accumulate.

Large queue tables can therefore interact with:

- autovacuum;
- index growth;
- bloat;
- WAL volume;
- replication lag;
- buffer churn.

PostgreSQL's current documentation notes that large update operations can increase bloat, replica lag, and lock contention, and recommends smaller batches in applicable cases. citeturn916313search1

Queue design should therefore consider lifecycle and retention early:

```text
active queue
    ↓
completed history
    ↓
archive / delete / partition lifecycle
```

A queue that keeps every completed item forever is a storage design, not merely a queue design.

---

# 29. Partitioning and Queue Hotspots

At very high scale, one queue table can become a hotspot because all workers repeatedly inspect the same active region.

Potential approaches:

```text
partition by tenant
partition by time
partition by queue type
partition by status/lifecycle strategy
```

But partitioning is not automatically a performance win.

Measure:

- rows scanned per claim;
- index size;
- buffer churn;
- autovacuum behavior;
- lock contention;
- insert/update distribution;
- replication impact.

A single well-indexed table can outperform an unnecessarily complex partitioned design at moderate scale.

---

# 30. Security Considerations

A queue often contains sensitive payloads.

Avoid allowing workers to bypass tenant authorization merely because `SKIP LOCKED` makes claiming convenient.

Always include the security boundary in the eligibility predicate where required:

```sql
WHERE tenant_id = $1
  AND status = 'pending'
```

For centralized workers operating across tenants, authorization must be explicit and auditable.

If Row-Level Security is involved, validate what rows the worker can see and claim. A queue design is only correct if the worker's visible candidate set is the intended candidate set.

Do not treat queue worker role privileges as an implementation detail; they define the blast radius of worker compromise.

# 31. Observability

Useful database queries include:

```sql
SELECT
    pid,
    application_name,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

Inspect locks:

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    relation::regclass,
    page,
    tuple,
    transactionid,
    virtualxid
FROM pg_locks
WHERE pid <> pg_backend_pid();
```

Find blocking relationships:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

# 35. AI / Vibe-Coding Failure Modes

## Mistake 1 — `SKIP LOCKED` Everywhere

AI sees concurrency and generates:

```sql
FOR UPDATE SKIP LOCKED
```

for ordinary business queries.

### Why It Looks Plausible

It sounds concurrency-safe.

### Why It Is Wrong

It intentionally skips rows and creates an inconsistent view.

### Rule

Use it primarily for claimable work where incomplete immediate visibility is acceptable. citeturn916313search18

---

## Mistake 2 — Hold Locks During Work

```text
FOR UPDATE SKIP LOCKED
↓
HTTP call
↓
Commit
```

This turns row locks into long-lived distributed coordination.

---

## Mistake 3 — Assume Exactly Once

```text
claim succeeded
=> job will only execute once
```

False under crash/retry ambiguity.

Use idempotency.

---

## Mistake 4 — Ignore Starvation

A query may always process newer/other rows while a hot row remains skipped.

Monitor age, not only throughput.

---

## Mistake 5 — Use `SELECT` Then `UPDATE`

This creates a race window.

Claim atomically.

---

## Mistake 6 — Add Workers Without Measuring

More workers can increase database contention without increasing useful throughput.

---

## Mistake 7 — Assume ORM Lock Options Are Correct

Inspect generated SQL.

---

## Mistake 8 — Forget Table-Level Locking

`SKIP LOCKED` does not make all locks nonblocking. PostgreSQL still acquires the required table-level `ROW SHARE` lock normally. citeturn916313search18

# 36. Performance Engineering

The main cost dimensions are:

```text
candidate search cost
+
rows skipped
+
rows claimed
+
index maintenance
+
transaction overhead
+
WAL volume
+
vacuum cost
+
application work
```

A useful approximation is:

```text
Queue throughput
≈
min(
  claim throughput,
  worker processing throughput,
  external dependency throughput,
  database write throughput
)
```

Increasing workers only helps when another resource is not already the bottleneck.

## Batch Size Trade-Off

Small batch:

```text
+ shorter transactions
+ smaller lock footprint
+ better fairness
- more transaction overhead
```

Large batch:

```text
+ fewer round trips
+ better amortization
- larger lock footprint
- longer transaction
- larger failure blast radius
```

Benchmark the actual workload.

# 37. Query Plan Reasoning

For queue queries, inspect:

```sql
EXPLAIN (ANALYZE, BUFFERS)
WITH claimed AS (
    SELECT id
    FROM work_items
    WHERE status = 'pending'
      AND available_at <= now()
    ORDER BY priority DESC, available_at, id
    FOR UPDATE SKIP LOCKED
    LIMIT 100
)
UPDATE work_items w
SET status = 'processing',
    attempts = attempts + 1,
    locked_at = now()
FROM claimed c
WHERE w.id = c.id
RETURNING w.id;
```

Ask:

- Is the active queue subset selective?
- Is the ordering supported efficiently?
- How many rows are visited before 100 usable rows are found?
- Are stale/locked rows causing excessive scanning?
- Is the update touching too many indexes?
- Does the query spend more time locating work or modifying it?

A plan that looks cheap when the queue is 100 rows may become pathological at 100 million rows.

# 39. Concurrency Lab: Observe the Skip

### Session A

```sql
BEGIN;

SELECT id
FROM work_items
WHERE id = 1
FOR UPDATE;
```

Do not commit yet.

### Session B

```sql
BEGIN;

SELECT id
FROM work_items
WHERE id IN (1, 2, 3)
ORDER BY id
FOR UPDATE SKIP LOCKED;
```

Expected conceptual outcome:

```text
1 -> skipped
2 -> returned
3 -> returned if limit allows
```

Session B is not being told:

> "Row 1 does not exist."

It is being told:

> "Row 1 could not be locked now, so continue."

This distinction is the foundation of the feature.

# 40. Concurrency Lab: Compare the Three Behaviors

Use identical candidates and compare:

```sql
FOR UPDATE;
```

```sql
FOR UPDATE NOWAIT;
```

```sql
FOR UPDATE SKIP LOCKED;
```

Observe:

| Clause | Locked row | Application result |
|---|---|---|
| `FOR UPDATE` | waits | eventually returns/errors according to transaction outcome |
| `FOR UPDATE NOWAIT` | immediate conflict | error |
| `FOR UPDATE SKIP LOCKED` | immediate conflict | row omitted |

This lab should be repeated under different isolation levels and with concurrent updates/deletes.

# 42. Queue Schema Evolution

Changing queue states is a migration problem as well as a concurrency problem.

For example:

```text
pending
processing
completed
```

becomes:

```text
pending
claimed
processing
retry_wait
completed
failed
```

Use an additive migration strategy where possible:

```text

↓
deploy readers accepting both
↓
deploy writers using new state
↓
backfill
↓
remove legacy behavior
```

Do not deploy a worker that assumes a new state before every producer/consumer is compatible with it.

# 43. When PostgreSQL Is a Good Queue

PostgreSQL-backed queues are attractive when:

- the work item is already transactional data;
- the queue volume is moderate;
- strong SQL filtering is valuable;
- operational simplicity matters;
- the team already operates PostgreSQL;
- claims and business-state changes should occur atomically;
- queue and domain data need the same transaction boundary.

Examples:

```text
invoice generation
statement generation
notification dispatch
report generation
ERP background jobs
inventory reconciliation
payment reconciliation
webhook retry scheduling
```

---

# 44. When an External Queue May Be Better

A dedicated queue/broker may be preferable when requirements include:

```text
very high message throughput
large fan-out
partitioned streaming
specialized delivery semantics
cross-service messaging as the primary architecture
long retention as a message log
consumer groups with broker-managed offsets
complex replay semantics
```

The decision is architectural, not ideological.

A PostgreSQL queue can be excellent, but it turns the database into both:

```text
system of record
+
work scheduler
```

That is powerful and also creates shared-resource coupling.

## Trick Questions

### Q: Does `SKIP LOCKED` guarantee no duplicate processing?

**Weak Answer:** Yes.

**Acceptable Answer:** It prevents concurrent workers from obtaining the same row lock at the same time, but crashes can lead to retries.

**Strong Answer:** It is a claim-coordination mechanism, not an exactly-once execution guarantee; durable state transitions and idempotency are still required.

**Expert Answer:** Row locking serializes the claim transition, while process failure can occur after the claim and before completion, so application-level execution semantics remain at-least-once unless a larger protocol establishes stronger guarantees.

### Q: Does `SKIP LOCKED` mean the query never blocks?

**Weak Answer:** Yes.

**Strong Answer:** No. It skips conflicting row locks, but the statement still acquires its required table-level lock normally. citeturn916313search18

### Q: Is `SKIP LOCKED` a stronger isolation level?

**Answer:** No. It is a locking-clause option that changes what happens when a row lock cannot be obtained immediately.

# 50. Final Mental Model

Carry this model forward:

```text
SKIP LOCKED
     |
     +--> try to lock candidate row
              |
              +--> available --> claim
              |
              +--> locked ----> skip

Purpose
-------
Reduce waiting among concurrent consumers.

Guarantee
---------
No waiting on conflicting row lock for that locking clause.

Non-guarantee
-------------
Not a complete, globally ordered, or exactly-once view.

Best fit
--------
Independent, claimable work items.

Required companion designs
--------------------------
Durable state
Idempotency
Retry
Lease/recovery
Fairness
Observability
Retention
```

The deepest lesson is:

> **`SKIP LOCKED` does not make a database queue correct by itself. It supplies one concurrency primitive: avoid waiting on currently locked rows. Production correctness comes from combining that primitive with a durable ownership state machine, idempotent work, bounded transactions, recovery semantics, fairness, and evidence-driven operations.**
