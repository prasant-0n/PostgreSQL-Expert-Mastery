# 03.4 — Transaction IDs & Snapshots

> **Phase 03 — Transactions & Concurrency**
>
> This chapter explains the identity and visibility machinery underneath PostgreSQL concurrency: virtual transaction IDs, persistent transaction IDs, snapshots, `xmin`, `xmax`, in-progress XIDs, visibility decisions, subtransactions, multixacts, transaction age, wraparound, and how to diagnose transaction state in production.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to:

- distinguish a session, virtual transaction, transaction ID, snapshot, command, and row version;
- explain when PostgreSQL assigns a permanent transaction ID;
- interpret `xmin`, `xmax`, and snapshot `xmin/xmax/xip_list` correctly;
- reason about whether a tuple version is visible to a transaction;
- understand why read-only transactions can have a virtual XID but no permanent XID;
- inspect transaction state with `pg_current_xact_id_if_assigned()`, `pg_current_snapshot()`, `pg_stat_activity`, and `pg_locks`;
- explain transaction-ID wraparound and why long-running transactions can become operationally dangerous;
- distinguish top-level XIDs, subtransactions, prepared transactions, and multixacts;
- diagnose stale snapshots, vacuum starvation, and long-running transaction incidents;
- design Node.js/NestJS transaction handling that does not accidentally hold snapshots open;
- reason about concurrency from evidence rather than intuition.

# 2. The Core Mental Model

A useful hierarchy is:

```text
Database Session / Connection
          |
          v
Virtual Transaction (vxid)
          |
          v
Permanent Transaction ID (xid)
          |
          v
MVCC Row Versions
          |
          v
Visibility to a Snapshot
```

This is not a single identifier chain. They solve different problems.

- A **session** is a client/backend connection context.
- A **virtual transaction ID** identifies an executing transaction at the backend level.
- A **permanent transaction ID (XID)** participates in MVCC visibility and is assigned when a transaction first needs one, notably when it writes.
- A **row version** carries transaction metadata used to determine visibility.
- A **snapshot** records which transactions were active at a point in time and therefore controls what a statement can see.

The critical idea is:

> PostgreSQL does not ask only “what is the latest row?” It asks “which row version is visible under this transaction's snapshot?”

---

# 3. Transaction Identity: Why More Than One ID Exists

PostgreSQL has multiple kinds of transaction identifiers because identity and visibility have different operational requirements.

## 3.1 Virtual Transaction ID

Every executing transaction gets a unique **VirtualTransactionId**, commonly displayed as `virtualxid` or `vxid`.

It is local to a backend and is useful for tracking the currently executing transaction, especially for lock waits and transaction coordination.

Conceptually:

```text
backend process + local sequence

4/12532
^^^^ ^^^^^
 |     |
 |     local transaction number
 backend/proc number
```

A virtual XID exists even when a transaction has not been assigned a permanent XID.

## 3.2 Permanent Transaction ID

The regular PostgreSQL transaction ID, or **XID**, comes from a cluster-wide transaction counter and is relevant to MVCC. PostgreSQL's current documentation notes that the internal `xid` representation is 32 bits and wraps, while `xid8` exposes a 64-bit representation that includes the epoch. citehttps://www.postgresql.org/docs/18/transaction-id.html

A key operational fact is:

> A transaction does not necessarily consume a permanent XID merely because it began.

A read-only transaction can remain without a permanent XID. PostgreSQL assigns one when the transaction needs it, typically when it first modifies database state.

Useful inspection functions:

```sql
SELECT pg_current_xact_id_if_assigned();
SELECT pg_current_xact_id();
```

`pg_current_xact_id()` can force assignment when one is not already present. `pg_current_xact_id_if_assigned()` avoids that side effect and is generally preferable for diagnostics where the transaction may be read-only. citeturn745823view1

---

# 4. XID Assignment Is Not Start Time

A subtle but extremely important point:

```text
Transaction A starts at 10:00
Transaction B starts at 10:01

A performs only reads
B performs a write

B may receive an XID before A.
```

Therefore:

```text
lower XID != necessarily earlier transaction start time
```

The PostgreSQL documentation explicitly notes that XIDs are assigned from the global counter when a transaction first writes, so the order of first writes can differ from transaction-start order. citeturn745823view0

This matters when reasoning about:

- tuple visibility;
- transaction-age calculations;
- vacuum horizons;
- incident timelines;
- replication and recovery diagnostics.

Do not use XID ordering as a substitute for wall-clock timestamps.

---

# 5. Snapshot: The Visibility Contract

A PostgreSQL snapshot is a representation of transaction visibility at a point in time.

Inspect one with:

```sql
SELECT pg_current_snapshot();
```

The textual form is conceptually:

```text
xmin:xmax:xip_list
```

For example:

```text
10:20:10,14,15
```

means:

```text
snapshot xmin = 10
snapshot xmax = 20
in-progress XIDs = 10, 14, 15
```

PostgreSQL 18 documents these components precisely: `xmin` is the lowest still-active transaction ID, `xmax` is one past the highest completed transaction ID as of the snapshot, and `xip_list` contains top-level XIDs that were in progress when the snapshot was taken. citeturn745823view1

---

# 6. Snapshot Components in Depth

## 6.1 Snapshot `xmin`

Snapshot `xmin` establishes the lower boundary of uncertainty.

Transaction IDs below this boundary are no longer active at the snapshot point. They are either:

- committed and potentially visible, or
- aborted and therefore not visible.

## 6.2 Snapshot `xmax`

Snapshot `xmax` is **one past** the highest completed XID at snapshot time.

Therefore:

```text
XID >= snapshot.xmax
```

was not completed yet and cannot be visible through that snapshot.

This “one past” detail matters constantly in exact reasoning.

## 6.3 `xip_list`

For XIDs in the interval:

```text
snapshot.xmin <= xid < snapshot.xmax
```

an XID that appears in `xip_list` was still in progress when the snapshot was captured.

An XID in that interval but **not** in `xip_list` had already completed, so its commit/abort status determines visibility.

Subtransaction IDs are not listed directly in this top-level snapshot representation. citeturn745823view1

---

# 7. Tuple Metadata: `xmin` and `xmax`

Earlier we used the same words for both snapshot fields and tuple fields. Context matters.

A physical tuple version contains transaction metadata that includes:

- tuple `xmin`: the transaction that created that row version;
- tuple `xmax`: the transaction that deleted or superseded that row version, where applicable.

This is foundational to MVCC.

Conceptually:

```text
Row version V1
created by XID 100
xmax = 105

Row version V2
created by XID 105
xmax = 0 / not deleted
```

An update generally creates a new version rather than mutating an existing version in place from the perspective of MVCC visibility.

This is why a single logical row can correspond to multiple physical tuple versions over time.

> Tuple `xmin/xmax` and snapshot `xmin/xmax` are different things. Never mix them when diagnosing visibility.

---

# 8. Visibility Reasoning: A Practical Model

A simplified reasoning model is:

### Version created by transaction T

For a snapshot S, ask:

1. Was T committed before the snapshot?
2. Was T still in progress when the snapshot was created?
3. Was T after the snapshot boundary?
4. If T is the current transaction, does the visibility rule permit seeing its own work?

### Version invalidated by transaction D

Ask:

1. Did D commit before the snapshot?
2. Was D still in progress?
3. Was D after the snapshot?
4. Is the current transaction the deleting/updating transaction?

The exact visibility algorithm has additional subtleties around command IDs, subtransactions, hint bits, multixacts, and transaction status, but this model is enough to build the right mental structure before studying the implementation details.

---

# 9. Snapshot Timeline Example

Consider:

```text
T10 starts
T10 writes
T11 starts
T11 writes
T10 takes snapshot S
T11 commits
T12 starts
```

At the instant S is captured:

```text
T10 = current transaction
T11 = in progress
T12 = not yet started
```

So a conceptual snapshot may look like:

```text
xmin = 10
xmax = 12
xip_list = {11}
```

Then reason about an XID:

| XID | Snapshot classification |
|---|---|
| 9 | before `xmin`; status determines visible/dead |
| 10 | current transaction |
| 11 | explicitly in progress → not visible as committed work |
| 12 | `>= xmax` → not visible |

The exact behavior for self-visible current-transaction changes follows transaction visibility rules rather than a simplistic “XID is always visible” statement.

---

# 10. Why Snapshot Timing Matters

The same `SELECT` text can produce different results because its snapshot was created at a different time.

Conceptually:

```text
Statement 1 -> Snapshot S1
--- concurrent commit ---
Statement 2 -> Snapshot S2
```

Even inside one transaction, the snapshot policy depends on the isolation level. That is why later chapters will distinguish:

- statement-level snapshots;
- transaction-level snapshots;
- repeatable-read behavior;
- serializable behavior.

This chapter intentionally stops before fully deriving isolation semantics, because the transaction ID/snapshot model must come first.

---

# 11. Read Committed vs Snapshot Lifetime

Under PostgreSQL's default `READ COMMITTED` behavior, snapshots are statement-oriented.

Conceptually:

```text
BEGIN
  SELECT -> S1
  UPDATE another session commits
  SELECT -> S2
COMMIT
```

`S1` and `S2` can differ.

Under stronger isolation, the snapshot lifecycle changes. That is why a long-running transaction can pin an old visibility horizon and interfere with maintenance even when it is not actively doing work.

---

# 12. Long-Running Transactions: The Operational Trap

One of PostgreSQL's most important production relationships is:

```text
Long transaction
      ↓
Old snapshot
      ↓
Old row versions remain potentially relevant
      ↓
VACUUM has less freedom to remove them
      ↓
Bloat / storage pressure / cleanup lag
```

The transaction may appear “idle” from the application's perspective while still being dangerous to the database.

This is why inspecting only CPU utilization or active query count is insufficient.

Inspect:

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    backend_xid,
    backend_xmin,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

The exact meaning of `backend_xid` and `backend_xmin` should be understood from PostgreSQL's transaction and MVCC internals rather than treated as generic timestamps.

---

# 13. `backend_xmin` and the Vacuum Horizon

For operational diagnostics, `backend_xmin` is especially important because it can represent a transaction horizon that other maintenance work must respect.

A session that holds an old snapshot can effectively communicate:

> “Some tuples newer than this boundary may still be visible to me.”

This is one reason a connection that is technically idle can still be operationally expensive.

Production symptom pattern:

```text
Application looks quiet
        ↓
Open transaction remains
        ↓
Old snapshot remains
        ↓
Dead tuples accumulate
        ↓
Table/index growth
        ↓
Autovacuum struggles to keep up
```

---

# 14. Transaction IDs and Wraparound

The internal `xid` representation is 32 bits and therefore wraps around. PostgreSQL uses an epoch to extend the logical transaction sequence, and the 64-bit `xid8` representation does not wrap during the life of an installation. citeturn745823view0

The dangerous issue is not that wrapping exists; PostgreSQL is designed to handle it.

The danger is allowing sufficiently old transaction references to survive so long that the system can no longer safely treat old XIDs as old.

This is why transaction-ID age is a production health metric.

Useful inspection:

```sql
SELECT
    datname,
    age(datfrozenxid)
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

Also inspect table-level age and vacuum state when diagnosing wraparound pressure.

---

# 15. Freeze: The Related Maintenance Concept

PostgreSQL can replace the need to retain the original semantics of very old transaction IDs by **freezing** tuples when they are old enough that they are known to be visible to all relevant transactions.

The operational chain is:

```text
Old tuple
  ↓
VACUUM evaluates age / horizon
  ↓
Tuple can become frozen
  ↓
Old XID dependency is reduced
  ↓
Wraparound protection remains possible
```

Do not interpret freezing as “rewriting the business record.” It is storage-level transaction metadata maintenance.

---

# 16. XID Allocation and Read-Only Work

This subtlety matters in high-throughput systems.

A transaction that only performs reads may have:

```text
virtualxid = present
transactionid = NULL
```

PostgreSQL explicitly documents this distinction in its transaction-locking documentation. citeturn995402search2

A write transaction can have both:

```text
virtualxid = present
transactionid = present
```

This distinction is useful when interpreting `pg_locks` and activity views.

---

# 17. `pg_locks`: Transaction IDs as Waitable Objects

Inspect transaction-related locks with:

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    virtualxid,
    transactionid
FROM pg_locks
WHERE locktype IN ('virtualxid', 'transactionid');
```

PostgreSQL 18 documents that transaction IDs currently executing are represented in `pg_locks` through `virtualxid` and `transactionid`; read-only transactions can have a virtual XID without a permanent transaction ID. citeturn995402search2

This helps explain waits that appear mysterious if you only look for ordinary table locks.

---

# 18. Subtransactions

Savepoints introduce subtransactions.

Conceptually:

```text
Top-level transaction
    |
    +-- subtransaction A
    |
    +-- subtransaction B
```

Subtransactions have their own internal identity and visibility implications, but snapshot displays contain only top-level XIDs. PostgreSQL explicitly states that subtransaction IDs do not appear in the snapshot's `xip_list`. citeturn745823view1

Why this matters:

- deep savepoint usage can increase transaction bookkeeping;
- error-handling frameworks can unintentionally create many subtransactions;
- diagnostics can be misleading if you expect every internal subtransaction to appear as an independent top-level snapshot entry.

Later, when we discuss deadlocks and lock behavior, this distinction becomes even more useful.

---

# 19. Multixacts: Shared Row-Level Lock Metadata

PostgreSQL also has **multixact IDs** for cases where multiple transactions hold row-level lock relationships that cannot be represented by one ordinary transaction ID alone.

This is distinct from ordinary XID allocation.

Operationally, multixact age can also matter:

```sql
SELECT age(datminmxid)
FROM pg_database;
```

The existence of multixacts is one reason advanced PostgreSQL operations cannot be reduced to “every row has one XID.”

---

# 20. Prepared Transactions

Two-phase commit introduces prepared transactions.

Prepared transactions remain visible to transaction-management infrastructure even though the application has not yet completed the final commit phase.

Relevant metadata includes:

```sql
SELECT * FROM pg_prepared_xacts;
```

The current PostgreSQL documentation notes that prepared transactions have Global Transaction Identifiers (GIDs), with their XID mapping visible through `pg_prepared_xacts`. citeturn745823view0

A forgotten prepared transaction can therefore become an operational hazard.

---

# 21. Transaction Status Inspection

PostgreSQL 18 provides:

```sql
SELECT pg_xact_status(<xid8>);
```

For sufficiently recent transactions, this can report:

```text
in progress
committed
aborted
```

or `NULL` when the relevant status information is no longer retained. PostgreSQL documents this function as useful in commit-ambiguity scenarios, such as when an application disconnects while `COMMIT` is in progress. citeturn745823view1

This is an important bridge between database internals and reliable application retry design.

---

# 22. Commit Order Is Not the Same as Transaction Start Order

Consider:

```text
T1 starts
T2 starts

T2 writes -> gets XID 200
T1 reads for 30 seconds
T2 commits
T1 later writes -> gets XID 201
```

The XID ordering reflects assignment order, not the fact that T1 began first.

Similarly:

```text
commit timestamp
!=
XID assignment timestamp
!=
transaction start timestamp
```

Each represents a different event.

For causal reconstruction, retain appropriate application and database timestamps rather than inferring chronology from XIDs.

---

# 23. Commit Timestamp Is Optional Metadata

PostgreSQL can retain commit timestamps when `track_commit_timestamp` is enabled for transactions committed after the setting takes effect.

This can support forensic and temporal analysis, but it should not be treated as a replacement for a well-designed business audit model.

A production audit architecture should usually record its own business semantics:

```text
who
what
when
why
from state
 to state
request / command identity
```

XID metadata is database-internal evidence, not a complete business audit trail.

---

# 24. Snapshot Export

PostgreSQL supports exporting a snapshot so another transaction can reuse the same visibility point.

Conceptually:

```sql
SELECT pg_export_snapshot();
```

A cooperating transaction can then import the exported snapshot where the transaction protocol and isolation requirements allow it.

This can be useful for:

- coordinated analytical work;
- consistent multi-session reads;
- advanced data-processing workflows.

But snapshot export is an advanced mechanism and should not be introduced merely because “consistent reads sound useful.” It expands coordination complexity.

# 25. Diagnostic Lab

Run these experiments against a disposable PostgreSQL instance.

## Experiment A — Observe XID Assignment

Session A:

```sql
BEGIN;
SELECT pg_current_xact_id_if_assigned();
```

Observe that a permanent XID may not yet be assigned.

Then:

```sql
CREATE TEMP TABLE xid_demo(id int);
INSERT INTO xid_demo VALUES (1);
SELECT pg_current_xact_id_if_assigned();
```

The write causes XID assignment behavior to become observable.

## Experiment B — Inspect Snapshot

```sql
BEGIN;
SELECT pg_current_snapshot();
```

Then create concurrent transactions in another session and compare snapshots at different moments.

## Experiment C — Observe Activity

```sql
SELECT
    pid,
    state,
    xact_start,
    backend_xid,
    backend_xmin,
    query
FROM pg_stat_activity

```

## Experiment D — Observe Lock Metadata

```sql
SELECT
    pid,

    granted

WHERE virtualxid IS NOT NULL
   OR transactionid IS NOT NULL;
```

The objective is not to memorize output. The objective is to connect each line to the underlying transaction state.

# 26. Production Incident Pattern: “The Database Is Quiet but Vacuum Is Not Catching Up”

A common investigation path is:

```text
Symptom:
Table keeps growing

↓
Check autovacuum activity

↓
Check dead tuples / table statistics

↓
Find old transactions in pg_stat_activity

↓
Inspect xact_start / backend_xmin

↓
Identify application connection holding an old snapshot

↓
Trace request / pool behavior
```

The root cause may be:

- transaction opened before an HTTP request and left open during business logic;
- streaming response that holds a transaction for minutes;
- forgotten cursor lifecycle;
- ORM transaction wrapper not released on an exception;
- connection pool misuse;
- background worker stalled inside a transaction.

The key is to prove the snapshot/transaction horizon is old before declaring vacuum “broken.”

# 27. Node.js / NestJS Engineering Rules

A safe transaction wrapper should make transaction lifetime explicit.

Conceptually:

```ts
await dataSource.transaction(async (manager) => {
  await manager.query(...);
  await manager.query(...);
});
```

The important property is not the framework syntax. It is:

```text
BEGIN
  do database work
  do database work
COMMIT / ROLLBACK
```

with guaranteed cleanup.

Avoid:

```ts
BEGIN
await slowExternalHttpCall(); // dangerous
UPDATE ...
COMMIT
```

Prefer:

```text
Validate external work / prepare decision
        ↓
Open short transaction
        ↓
Perform required DB mutations
        ↓
Commit
        ↓
Publish via transactional outbox / async mechanism
```

Long transactions are not automatically wrong. The problem is unbounded or accidental transaction lifetime.

---

# 28. Common ORM Mistakes

### Mistake 1 — “One request = one transaction”

This can be valid for carefully bounded operations, but is dangerous when a request includes external calls, user interaction, or streaming.

### Mistake 2 — Hiding transactions in decorators

An abstraction that silently opens a transaction can make snapshot lifetime invisible.

### Mistake 3 — Returning lazy data after the transaction closes

Streaming/lazy-loading behavior can accidentally extend database access or fail outside the intended transaction boundary.

### Mistake 4 — Connection reuse assumptions

A transaction must remain on the same backend connection. Pooling is not a magic distributed transaction mechanism.

---

# 29. AI / Vibe-Coding Failure Modes

AI-generated PostgreSQL code often makes these mistakes:

### Failure: Using XID as a business sequence

Wrong:

```text
XID = order number
```

Why it fails:

- XID allocation is an internal implementation mechanism;
- read-only transactions may not receive one;
- XID ordering is not business ordering;
- semantics are cluster-wide and storage-oriented.

### Failure: Treating snapshot `xmax` as “largest visible row XID”

Wrong mental model.

It is one past the highest completed transaction ID known at snapshot creation.

### Failure: Assuming every open transaction has a permanent XID

False.

### Failure: Assuming “idle” means harmless

An idle session can still retain a transaction/snapshot horizon.

### Failure: Killing random sessions to fix vacuum

Never use a blind kill strategy. Identify the offending transaction and confirm the business impact first.

# 30. Performance Considerations

Transaction-ID and snapshot machinery is optimized by PostgreSQL, but application behavior can still create pathological workloads.

Watch for:

- long transaction lifetimes;
- huge transaction batches;
- deep savepoint/subtransaction usage;
- prepared transactions left open;
- lock-heavy workloads creating large multixacts;
- excessive connection pool sizes that hide transaction leaks.

The correct response is measurement, not automatically changing vacuum settings.

# 32. Security Considerations

Transaction metadata can expose operational information:

- session identities;
- query text;
- database activity timing;
- client addresses;
- transaction states.

Restrict diagnostic access appropriately.

For multi-tenant systems, never expose raw internal transaction information to tenant users as though it were business state.

Use an internal diagnostic role and controlled observability pipeline.

# 37. Final Mental Model

Keep this model:

```text
Session
  ↓
Virtual Transaction
  ↓
Permanent XID (when assigned)
  ↓
Row versions carry transaction metadata
  ↓
Snapshot defines the transaction's visibility horizon
  ↓
Visibility determines which row version is readable
  ↓
Long-lived snapshots constrain cleanup
  ↓
VACUUM / FREEZE / transaction-age health become operational concerns
```

And remember the most important distinction:

```text
XID = transaction-management identity
Snapshot = visibility state at a point in time
Tuple xmin/xmax = row-version transaction metadata
Business timestamp = application/domain time
```

Confusing these four concepts creates some of the hardest PostgreSQL concurrency bugs to diagnose.

# 38. Central Principle

> **Transaction IDs identify transactional state; snapshots define visibility; neither is a substitute for business time, business ordering, or application-level identity.**

The path to PostgreSQL concurrency mastery is to stop thinking of a transaction as merely `BEGIN ... COMMIT` and start reasoning about the transaction's identity, snapshot, visibility horizon, and lifetime.
