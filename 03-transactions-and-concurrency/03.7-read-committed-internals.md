# 03.7 — Read Committed Internals

> **Phase 03 — Transactions & Concurrency**  
> This chapter explains what PostgreSQL's default `READ COMMITTED` isolation level actually does at statement execution time, especially when rows are concurrently modified.

---

## 1. Chapter Objective

By the end of this chapter you should be able to:

- explain precisely when a `READ COMMITTED` snapshot is created;
- distinguish statement visibility from row-lock/update behavior;
- explain why two statements in one transaction can see different committed states;
- reason about what happens when an `UPDATE`, `DELETE`, or locking read encounters a concurrently modified row;
- understand why PostgreSQL may re-check a row after waiting for another transaction;
- identify cases where `READ COMMITTED` is a good fit and cases where it is not;
- distinguish a database guarantee from an application-level business invariant;
- debug surprising results using evidence rather than intuition;
- design Node.js/NestJS transaction code that correctly handles these semantics.

PostgreSQL 18.6 is the current documented PostgreSQL 18 minor release as of August 13, 2026. The current PostgreSQL documentation states that `READ COMMITTED` is the default isolation level and that each command begins with a snapshot of data committed before that command started. citeturn226736search1turn226736search0

---

## 2. The Central Mental Model

The most useful mental model is:

```text
Transaction
    |
    +-- Statement 1 -> Snapshot S1
    |                  |
    |                  +-- sees commits visible at statement start
    |
    +-- Statement 2 -> Snapshot S2
                       |
                       +-- may see commits that happened after S1
```

Therefore:

```text
READ COMMITTED != one fixed snapshot per transaction

READ COMMITTED = one fresh visibility snapshot per command
```

That does **not** mean an `UPDATE` always operates only on the exact row version visible when its statement began. When it reaches a row that another transaction has changed concurrently, PostgreSQL may wait and then continue against the updated version, subject to re-evaluating the command's search condition. This special write behavior is one of the most important details in this chapter. citeturn226736search12

---

# 3. What `READ COMMITTED` Means

## 3.1 Simple definition

A statement sees data committed before that statement began, plus changes made earlier by the current transaction.

It does not see uncommitted changes from other transactions.

## 3.2 Engineering definition

At the start of each command, PostgreSQL establishes visibility based on the transaction state that is committed and visible at that point. A later command in the same transaction can therefore establish a different snapshot.

## 3.3 Expert definition

`READ COMMITTED` is statement-level MVCC visibility combined with special row-update conflict handling. For ordinary reads, visibility follows the command snapshot. For modifying commands, if a candidate row has been concurrently updated or deleted after the command snapshot was established, PostgreSQL waits for the first updater, then may operate on the updated version and re-evaluate the search condition. citeturn226736search12

---

# 4. The First Principle: Statement Boundaries Matter

Consider:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;

SELECT balance
FROM accounts
WHERE id = 1;

COMMIT;
```

Under `READ COMMITTED`, these are two separate commands.

If another transaction commits an update between them:

```text
T1                         T2
--                         --
SELECT balance = 100
                           UPDATE balance = 150
                           COMMIT
SELECT balance = 150
```

The transaction did not become internally inconsistent merely because it saw two values. The two statements used different statement snapshots.

This is why application code must never assume that `BEGIN` means “everything I read from now on is frozen.” That is a `REPEATABLE READ`-style assumption, not the default PostgreSQL `READ COMMITTED` behavior.

---

# 5. Read Operations

For a normal query:

```sql
SELECT * FROM products WHERE id = 10;
```

PostgreSQL searches according to the command snapshot.

The query does not expose another transaction's uncommitted write.

If another transaction commits while the query is already running, the ordinary `SELECT` does not suddenly switch to the newly committed state halfway through the query. The command has a snapshot associated with its execution.

This distinction becomes critical when comparing a normal `SELECT` with a locking read such as:

```sql
SELECT *
FROM products
WHERE id = 10
FOR UPDATE;
```

A locking read can wait for a concurrent updater and then return the updated version that it is locking. PostgreSQL's documentation explicitly calls out this behavior for `SELECT FOR UPDATE` and `SELECT FOR SHARE`. citeturn226736search12

---

# 6. Why Writes Are More Complicated

A naive mental model says:

```text
UPDATE finds row in snapshot
        ↓
UPDATE writes exactly that version
```

That is incomplete.

Suppose:

```text
initial quantity = 10
```

Transaction A starts:

```sql
BEGIN;
UPDATE inventory
SET quantity = quantity - 3
WHERE product_id = 1;
```

Meanwhile Transaction B tries to update the same row.

PostgreSQL cannot simply allow both transactions to overwrite the same physical state blindly. It must coordinate concurrent updates.

The high-level behavior is:

```text
T1 identifies candidate row
T2 concurrently updates row
T1 reaches conflicting row
        ↓
T1 waits for T2
        ↓
T2 commits or rolls back
        ↓
If T2 rolled back -> T1 can continue using the original row
If T2 committed -> T1 considers the new row version
        ↓
T1 re-evaluates its WHERE condition
        ↓
If predicate still matches -> update continues
Otherwise -> row is skipped
```

This behavior is documented for `UPDATE`, `DELETE`, `SELECT FOR UPDATE`, and `SELECT FOR SHARE` in `READ COMMITTED`. citeturn226736search12

---

# 7. The WHERE Clause Can Be Re-Evaluated

This is one of the most important expert-level behaviors in `READ COMMITTED`.

Consider:

```sql
UPDATE jobs
SET status = 'processing'
WHERE status = 'queued'
  AND id = 42;
```

Suppose another transaction changes job 42 from `queued` to `done` while this statement is competing for the row.

The waiting transaction does not blindly modify the row merely because the original snapshot had matched it.

Conceptually:

```text
snapshot says:
job 42 = queued

concurrent transaction changes:
job 42 = done

waiting UPDATE resumes
        ↓
fetch updated version
        ↓
re-check WHERE status = 'queued'
        ↓
false
        ↓
no update
```

This protects the semantics of predicates in many straightforward row-update cases. citeturn226736search12

---

# 8. Why PostgreSQL Can Appear to See a Future Row

This surprises developers:

```text
My snapshot says the row has value A.

Why did my UPDATE use value B?
```

The answer is that visibility rules for locating candidate rows and conflict resolution for updating a concurrently changed row are not identical operations.

A modifying command can wait for the concurrent updater, then continue using the newest relevant row version once the conflict is resolved. PostgreSQL documents this as a deliberate part of `READ COMMITTED` behavior. citeturn226736search12

This means an updating statement can, in a specific conflict path, observe effects on the row it is trying to modify that were not visible in its original command snapshot.

That is not an implementation accident. It is part of the documented concurrency behavior.

---

# 9. Example: Atomic Increment Works Well

This pattern is strong:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 1001
  AND quantity > 0;
```

Why?

The business action is represented directly in the SQL statement.

Two concurrent transactions might both attempt the operation, but row-level conflict handling plus the predicate determines whether each update can proceed.

The application does **not** need to do:

```text
SELECT quantity
if quantity > 0
    UPDATE quantity = quantity - 1
```

That split introduces an unnecessary race window.

Prefer:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0;
```

Then inspect:

```text
rowCount === 1 -> reservation/decrement succeeded
rowCount === 0 -> condition was not satisfied
```

This is a fundamental concurrency design pattern.

---

# 10. Naive Check-Then-Act

## Naive approach

```sql
SELECT quantity
FROM inventory
WHERE product_id = $1;
```

Application:

```ts
if (quantity > 0) {
  await db.query(
    `UPDATE inventory
     SET quantity = quantity - 1
     WHERE product_id = $1`,
    [productId],
  );
}
```

### Why it fails

The read and write are separate commands.

Between them, another transaction can modify the same row.

```text
T1                         T2
--                         --
SELECT quantity = 1
                           SELECT quantity = 1
UPDATE -1
                           UPDATE -1
```

Depending on the exact business operation, the application may make a decision using stale information.

## Improved approach

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0
RETURNING quantity;
```

Now the eligibility test and state change are part of one SQL command.

---

# 11. `READ COMMITTED` and Multiple Statements

Consider:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

SELECT balance
FROM accounts
WHERE id = 1;

COMMIT;
```

The `SELECT` sees the transaction's own prior update because a transaction sees its own changes.

It also sees other transactions that committed before the `SELECT` statement's snapshot was established.

So the effective model is:

```text
Statement snapshot
       +
Current transaction's own writes
       ↓
visible state for statement
```

That is very different from a simple database-wide “snapshot from BEGIN.”

---

# 12. A Subtle Consequence: Multi-Statement Business Checks

Suppose code does:

```sql
BEGIN;

SELECT SUM(amount) FROM credits;

SELECT SUM(amount) FROM debits;

COMMIT;
```

A concurrent transaction can commit between the two statements.

Therefore:

```text
credits = state at S1

debits  = state at S2
```

The comparison may not represent one coherent global instant.

PostgreSQL explicitly warns that Read Committed is difficult to use for complex consistency checks where the visible state shifts from command to command. citeturn226736search3

Better options depend on the invariant:

- one statement, when possible;
- explicit locks;
- stronger isolation;
- constraints;
- atomic update logic;
- a purpose-built consistency model.

Do not automatically “solve” every problem by switching everything to `SERIALIZABLE`.

First identify the invariant.

---

# 13. `UPDATE` With a Complex Predicate

This is where `READ COMMITTED` becomes easier to misuse.

Example:

```sql
UPDATE invoices
SET state = 'expired'
WHERE state = 'pending'
  AND due_at < now();
```

Another transaction might simultaneously modify `state` or `due_at`.

A row can be found based on the command's initial visibility state and then encounter a concurrent update before PostgreSQL can finish modifying it.

The updated row is then considered again against the search condition.

This means you must reason about:

```text
candidate discovery
        +
concurrency wait
        +
new row version
        +
predicate re-evaluation
```

rather than treating `UPDATE` as a simple scan followed by unconditional assignment.

---

# 14. `DELETE` Has the Same Problem Class

Suppose:

```sql
DELETE FROM sessions
WHERE state = 'expired';
```

A concurrently updated row may no longer match when the deleting transaction obtains the row after waiting.

The row can therefore be skipped after predicate re-evaluation.

This matters for cleanup jobs, queue workers, archival tasks, and state transitions.

A cleanup query's correctness depends on the exact predicate and business semantics, not merely on the fact that the command runs inside a transaction.

---

# 15. `SELECT FOR UPDATE`

A normal query:

```sql
SELECT *
FROM jobs
WHERE id = 42;
```

and a locking query:

```sql
SELECT *
FROM jobs
WHERE id = 42
FOR UPDATE;
```

serve different purposes.

The second says, in effect:

> locate the row and establish a row-level lock suitable for a subsequent modification, while coordinating with concurrent changes.

Under `READ COMMITTED`, a locking read can wait for a concurrent updater and then return the updated version. citeturn226736search12

That makes this pattern useful:

```sql
BEGIN;

SELECT *
FROM inventory
WHERE product_id = $1
FOR UPDATE;

-- perform dependent reads/writes

COMMIT;
```

But locking is not magic. It must be acquired on the right rows at the right time and kept for a reasonable transaction duration.

---

# 16. `READ COMMITTED` + `FOR UPDATE` and Security

PostgreSQL's documentation contains a particularly subtle RLS example showing that a `READ COMMITTED` transaction using `SELECT ... FOR UPDATE` can observe an updated version of a row while a related non-locking lookup still uses the original statement snapshot. citeturn170327search0

The lesson is broader than RLS:

> Different parts of a complex command can have different visibility/locking behavior.

Therefore security-sensitive logic should not depend on an intuitive “everything is the same snapshot” assumption.

For tenant isolation and authorization:

- enforce ownership in the database where practical;
- use RLS deliberately;
- understand which expressions are ordinary reads and which are locking operations;
- test concurrent authorization-sensitive workflows.

---

# 17. `READ COMMITTED` and `ON CONFLICT`

PostgreSQL's `INSERT ... ON CONFLICT DO UPDATE` also has concurrency behavior that is easy to underestimate.

In `READ COMMITTED`, for each proposed row, the command can either insert or update, and PostgreSQL documents that one of those outcomes is guaranteed unless there is another unrelated error. citeturn226736search12

Example:

```sql
INSERT INTO idempotency_keys(key, response_hash)
VALUES ($1, $2)
ON CONFLICT (key)
DO UPDATE
SET response_hash = EXCLUDED.response_hash;
```

The correct design still requires a clear business invariant.

An upsert is not automatically equivalent to a conflict-free business transaction.

---

# 18. The Classic “Two Successive Reads” Trap

This code looks safe:

```sql
BEGIN;

SELECT status FROM orders WHERE id = 100;

-- application logic

SELECT status FROM orders WHERE id = 100;

COMMIT;
```

But under `READ COMMITTED`:

```text
SELECT #1 -> snapshot S1
other transaction commits
SELECT #2 -> snapshot S2
```

Therefore:

```text
status #1 != status #2
```

is completely legal.

When the application requires a stable view:

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

may be appropriate.

When the application requires an invariant to survive concurrent writes, stronger isolation or explicit locking may be required.

---

# 19. `READ COMMITTED` Is Often Exactly Right

Do not treat the previous sections as a statement that `READ COMMITTED` is unsafe.

It is the default isolation level for a reason.

It works particularly well for operations such as:

```sql
UPDATE accounts
SET balance = balance + 100
WHERE account_id = $1;
```

where the business operation is inherently row-local and can be represented as an atomic modification.

PostgreSQL explicitly gives a bank-account transfer example where concurrent modifications to predetermined account rows can be handled appropriately under `READ COMMITTED`. citeturn226736search12

Good candidates include:

- atomic counters;
- row-local state changes;
- idempotency-key inserts;
- predetermined-record updates;
- simple queue state transitions;
- CRUD operations with database constraints.

---

# 20. Where `READ COMMITTED` Becomes Risky

Be cautious when the transaction performs:

```text
read many rows
   ↓
derive global conclusion
   ↓
write something based on conclusion
```

Examples:

- “if no active reservation exists, create one”;
- “if total balance is below limit, approve withdrawal”;
- “if no worker is processing this item, claim a batch”;
- “if all child records are complete, close the parent”;
- “if combined inventory across warehouses is sufficient, approve order.”

The issue is not that `READ COMMITTED` is “bad.”

The issue is that the business invariant spans a concurrency history that simple statement-level snapshots may not protect.

---

# 21. Better Decision Order

Use this order of reasoning:

```text
1. State the business invariant.
2. Identify the concurrent history that can violate it.
3. Ask whether one atomic SQL statement can enforce it.
4. If not, ask whether constraints can enforce it.
5. If not, determine which rows must be locked.
6. If lock-based coordination is insufficient, evaluate stronger isolation.
7. Design retries for serialization/deadlock outcomes where necessary.
```

This prevents cargo-cult use of isolation levels.

---

# 22. `READ COMMITTED` vs Atomic SQL

A very important engineering distinction:

```text
BAD:
SELECT eligibility
UPDATE state
```

versus:

```sql
UPDATE table
SET state = 'claimed'
WHERE id = $1
  AND state = 'available'
RETURNING *;
```

The second can often eliminate the need for an explicit `SELECT` + lock because the predicate and state transition are performed together.

This is frequently the simplest and fastest concurrency control technique.

---

# 23. `READ COMMITTED` vs Explicit Locking

### Atomic statement

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity >= 1;
```

Best when the operation is naturally expressible as one row-local mutation.

### Explicit lock

```sql
SELECT *
FROM inventory
WHERE product_id = $1
FOR UPDATE;
```

Useful when several dependent operations must coordinate around the same row.

### Stronger isolation

Useful when the correctness rule cannot be safely implemented using a narrower lock/constraint design.

The goal is the smallest mechanism that actually protects the invariant.

Create a test table:

```sql
DROP TABLE IF EXISTS demo_accounts;

CREATE TABLE demo_accounts (
    id bigint PRIMARY KEY,
    balance numeric(12,2) NOT NULL
);

INSERT INTO demo_accounts(id, balance)
VALUES (1, 100.00);
```

### Session A

```sql
BEGIN;

SELECT balance
FROM demo_accounts
WHERE id = 1;
```

Expected:

```text
100.00
```

### Session B

```sql
BEGIN;

UPDATE demo_accounts
SET balance = 150.00
WHERE id = 1;

COMMIT;
```

### Session A again

```sql
SELECT balance
FROM demo_accounts
WHERE id = 1;
```

Under `READ COMMITTED`, the second statement can see:

```text
150.00
```

because it gets a new statement snapshot.

This experiment should become muscle memory.

# 25. Update Conflict Laboratory

Reset:

```sql
UPDATE demo_accounts
SET balance = 100.00
WHERE id = 1;
```

### Session A

```sql
BEGIN;

UPDATE demo_accounts
SET balance = balance + 10
WHERE id = 1;
```

Do not commit yet.

### Session B

```sql
BEGIN;

UPDATE demo_accounts
SET balance = balance + 20
WHERE id = 1;
```

Session B may wait for Session A because both contend for the same row.

After Session A commits:

```sql
COMMIT;
```

Session B can continue and apply its operation to the relevant current row version.

This demonstrates why:

```sql
SET balance = balance + 20
```

is much safer than:

```text
SELECT balance
client-side addition
UPDATE balance = old + 20
```

for concurrent row-local increments.

# 26. Predicate Re-Evaluation Laboratory

```sql
DROP TABLE IF EXISTS demo_jobs;

CREATE TABLE demo_jobs (
    id bigint PRIMARY KEY,
    status text NOT NULL
);

INSERT INTO demo_jobs VALUES (1, 'queued');
```

### Session A

```sql
BEGIN;

UPDATE demo_jobs
SET status = 'processing'
WHERE id = 1
  AND status = 'queued';
```

Leave the transaction open.

### Session B

```sql
BEGIN;

UPDATE demo_jobs
SET status = 'done'
WHERE id = 1
  AND status = 'queued';
```

This blocks until Session A resolves.

After Session A commits:

```sql
COMMIT;
```

Session B must reason about the updated row version and whether its original predicate still holds. It should not blindly rewrite the row merely because it once matched in the initial snapshot. citeturn226736search12

# 27. Why “Transaction = Lock” Is Wrong

A transaction does not automatically lock every row it reads.

This is a common beginner misconception:

```text
BEGIN
SELECT row
```

does **not** mean:

```text
Nobody else can modify row
```

A normal MVCC read can coexist with concurrent writers.

Explicit locking clauses communicate a different requirement:

```sql
FOR UPDATE
FOR NO KEY UPDATE
FOR SHARE
FOR KEY SHARE
```

The exact lock mode matters and will be covered in depth in the locking chapters.

---

# 28. Why “READ COMMITTED = Read Current Value” Is Also Wrong

Another common misconception:

> “READ COMMITTED always reads the latest value at the moment the row is physically touched.”

A normal statement has a visibility snapshot established for that command.

A concurrent update can commit during execution without becoming visible as an ordinary read midway through that same command.

However, a modifying or locking command that reaches a concurrently changed row has special conflict-resolution behavior.

Therefore there are two questions:

```text
What did the command's snapshot contain?

AND

What happens if the target row changed concurrently?
```

They are not identical questions.

# 29. Application-Level Design Pattern

For Node.js/NestJS:

```ts
await dataSource.transaction(async (manager) => {
  const result = await manager.query(
    `
      UPDATE inventory
      SET quantity = quantity - $1
      WHERE product_id = $2
        AND quantity >= $1
      RETURNING product_id, quantity
    `,
    [requestedQuantity, productId],
  );

  if (result.length !== 1) {
    throw new Error('Insufficient inventory');
  }
});
```

The important part is not NestJS syntax.

The important part is:

```text
invariant
   ↓
SQL predicate
   ↓
atomic state transition
   ↓
result inspection
```

This is much stronger than building a decision from stale application variables.

---

# 30. Connection Pooling Hazard

In Node.js applications, a transaction belongs to a database session/connection.

Therefore this is dangerous conceptually:

```text
BEGIN on connection A
query on connection B
COMMIT on connection A
```

The application transaction wrapper must guarantee that all statements in the transaction use the same acquired connection/session.

A repository abstraction that silently checks out different pooled connections between calls can destroy the intended transactional boundary.

This is one reason production transaction APIs usually expose a transaction-scoped entity manager/query runner.

---

# 31. External APIs Inside `READ COMMITTED` Transactions

This is dangerous:

```text
BEGIN
UPDATE database
CALL Stripe
CALL external service
CALL another service
COMMIT
```

The database cannot atomically control the external side effects just because the SQL transaction is open.

Problems include:

- long transaction lifetime;
- locks held while waiting on network calls;
- retries that repeat external side effects;
- ambiguous commit outcomes;
- increased MVCC retention pressure.

Prefer:

```text
short database transaction
        ↓
record intent/outbox
        ↓
commit
        ↓
external worker performs side effect
```

The transactional outbox pattern belongs to the later distributed-transactions material, but the transaction-boundary principle starts here.

# 32. Debugging Surprising `READ COMMITTED` Behavior

Never start with:

> “PostgreSQL is inconsistent.”

Start by capturing evidence.

Useful sources:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
WHERE datname = current_database();
```

Also inspect locks:

```sql
SELECT
    pid,
    locktype,
    mode,
    granted,
    relation::regclass AS relation,
    virtualxid,
    transactionid
FROM pg_locks
WHERE pid <> pg_backend_pid();
```

PostgreSQL documents that transaction and virtual transaction identifiers appear in `pg_locks` and that lock waits can be associated with transaction IDs or virtual transaction IDs. citeturn226736search8

Record:

```text
Session ID
Transaction start
Statement start
SQL text
Isolation level
Locks held
Locks waited on
Commit/rollback order
```

Then reconstruct the history.

# 33. Common Failure Patterns

## Failure 1 — Two reads treated as one snapshot

```sql
SELECT ...;
SELECT ...;
```

### Root cause
Fresh statement snapshots.

### Fix
Choose the required isolation/locking semantics or redesign the operation.

---

## Failure 2 — Check-then-act

```text
SELECT eligibility
UPDATE
```

### Root cause
The eligibility decision can become stale.

### Fix
Use an atomic conditional mutation where possible.

---

## Failure 3 — Client-side arithmetic

```text
SELECT balance = 100
client computes 110
UPDATE balance = 110
```

### Root cause
Lost-update style race.

### Fix
Prefer:

```sql
UPDATE accounts
SET balance = balance + 10
WHERE id = $1;
```

---

## Failure 4 — Long transaction

```text
BEGIN
SELECT
HTTP request
wait 5 seconds
UPDATE
COMMIT
```

### Root cause
Transaction scope is much larger than database work.

### Consequences
- longer lock retention;
- longer snapshot lifetime;
- increased vacuum pressure;
- more contention.

---

## Failure 5 — Wrong abstraction in ORM

```text
Repository A uses connection X
Repository B uses connection Y
```

### Root cause
Transaction context is not propagated.

### Fix
Use a transaction-scoped context/manager and make transaction boundaries explicit.

# 34. Performance Considerations

`READ COMMITTED` is often a strong default because it avoids the stronger serialization machinery required by the strictest isolation semantics.

But performance is workload-dependent.

Do not optimize isolation level in isolation from:

```text
query shape
row contention
transaction duration
index quality
hotspot frequency
retry rate
lock wait time
```

A poorly designed atomic operation can still perform badly under heavy contention.

A very short `READ COMMITTED` transaction may be dramatically healthier than a long `SERIALIZABLE` transaction with frequent retries for a workload whose invariant could have been expressed as one guarded `UPDATE`.

---

# 35. Observability Signals

For production systems, monitor:

- transaction duration;
- active transaction age;
- lock waits;
- blocked sessions;
- deadlocks;
- rollback rate;
- serialization failures;
- queue claim latency;
- hot-row contention;
- idle-in-transaction sessions.

A useful operational rule is:

> A transaction that is waiting on application I/O is usually a transaction whose scope should be examined.

---

# 36. Security Considerations

Isolation is not authorization.

`READ COMMITTED` does not decide:

```text
Who is allowed to see this row?
Who is allowed to change it?
Which tenant owns it?
```

Those are authorization and row-security concerns.

However, security properties can still depend on concurrency behavior. PostgreSQL's RLS documentation includes a concrete example where a `READ COMMITTED` locking read can observe an updated row in a way that differs from a related non-locking lookup. citeturn170327search0

Security-sensitive workflows therefore need concurrency tests, not merely unit tests of policy predicates.

---

# 37. Testing Strategy

## Unit tests

Test:

```text
predicate satisfied
predicate not satisfied
zero-row update
single-row update
```

## Integration tests

Use a real PostgreSQL instance.

Simulate:

```text
T1 begins
T2 begins
T1 updates
T2 updates
T1 commits
T2 resumes
```

## Concurrency tests

Run many workers against the same hot key.

Verify:

```text
final state
number of successful transitions
number of rejected transitions
invariant preservation
```

## Failure-injection tests

Force:

- rollback;
- connection termination;
- statement timeout;
- lock timeout;
- retry after transient error.

# 38. AI / Vibe-Coding Failure Modes

AI-generated backend code frequently produces patterns such as:

```ts
const row = await repo.findOne(...);

if (row.status === 'pending') {
  row.status = 'approved';
  await repo.save(row);
}
```

This code may look perfectly reasonable in sequential testing.

Under concurrency:

```text
Request A reads pending
Request B reads pending
A writes approved
B writes approved
```

The real invariant may be violated even though every statement succeeds.

Another common generated pattern is:

```ts
const quantity = await getQuantity();
if (quantity >= requested) {
  await decrement(requested);
}
```

The model may recommend a transaction around both calls without noticing that the actual best solution is often an atomic conditional `UPDATE`.

The right engineering question is:

> What concurrent history can invalidate this decision?

# 39. Production Pattern — Inventory Reservation

Requirement:

> Reserve `N` units only when at least `N` units are currently available.

### Naive Approach

```text
SELECT available
if available >= N
UPDATE available = available - N
```

### Why It Fails

The check can become stale.

### Improved Approach

```sql
UPDATE inventory
SET available = available - $1
WHERE product_id = $2
  AND available >= $1
RETURNING product_id, available;
```

### Why It Works

The eligibility predicate and mutation are one database operation, reducing the race window and allowing PostgreSQL to coordinate concurrent row updates.

### Production Considerations

Also consider:

- idempotency key;
- reservation record;
- expiration policy;
- audit/event history;
- multi-warehouse allocation;
- deadlock avoidance when multiple inventory rows are involved.

### Alternative

Use `SELECT ... FOR UPDATE` when the decision requires multiple dependent operations that cannot be expressed as one statement.

### Trade-Off

Atomic SQL is usually simpler and narrower; explicit locks provide a larger coordination boundary but increase lock duration and contention risk.

# 40. Production Pattern — Job Claiming

Instead of:

```text
SELECT id FROM jobs WHERE status = 'queued';
UPDATE job SET status = 'processing';
```

use the queue-specific locking/claiming pattern introduced in later chapters, commonly involving:

```sql
SELECT ...
FOR UPDATE SKIP LOCKED;
```

or an atomic conditional update depending on the queue architecture.

The key principle remains the same:

> claim ownership in the database, not in application memory.

# 41. Production Pattern — Jewellery ERP Stock Movement

Imagine a jewellery ERP where two branches attempt to reserve the same inventory item.

A weak design is:

```text
read stock
calculate availability
write reservation
```

A stronger design is:

```text
transaction
  ↓
conditional inventory mutation
  ↓
reservation row
  ↓
outbox/event if required
  ↓
commit
```

For stronger correctness, the reservation model should also enforce:

- tenant/branch ownership;
- product/location identity;
- quantity non-negativity;
- reservation state transitions;
- idempotency;
- audit history.

The concurrency mechanism should match the exact invariant rather than blindly defaulting to a stronger isolation level.

# 42. Read Committed vs Repeatable Read vs Serializable

| Property | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|---|---|---|---|
| Default in PostgreSQL | Yes | No | No |
| Snapshot | Per statement | Stable for transaction | Stable/serializable execution model |
| Two reads can differ | Yes | No | No |
| Concurrent write conflict can wait/recheck | Yes | Stronger conflict behavior | Serialization detection |
| Business invariant protection | Limited | Stronger but not universally enough | Strongest |
| Retry needed | Usually not because of serialization alone | Can be required for some conflicts | Yes, application must handle serialization failures |
| Typical use | General OLTP | Stable analytical/transactional view | Cross-row/global invariants |

Isolation semantics are version-sensitive and should be verified against the PostgreSQL documentation for the running major version. Current PostgreSQL 18 documentation describes `READ COMMITTED` as the default and documents its statement-level snapshots and concurrent-update behavior. citeturn226736search0turn226736search12

# 43. Expert Reasoning Framework

When given a concurrency problem, write:

```text
Actors:
  T1, T2, ...

Invariant:
  What must remain true?

Reads:
  Which rows/predicates are inspected?

Writes:
  Which rows are modified?

Snapshot:
  At what statement does visibility get established?

Conflict:
  Which rows can another transaction modify?

Wait:
  Can this operation block?

Re-check:
  Could the row change before the write completes?

History:
  Which interleavings are legal?

Protection:
  statement / constraint / lock / isolation / architecture

Failure:
  what happens on rollback, deadlock, timeout, or retry?
```

This framework is more valuable than memorizing isolation-level slogans.

# 47. Production Readiness Checklist

Before shipping a `READ COMMITTED` workflow, verify:

- [ ] The business invariant is explicitly documented.
- [ ] All concurrency-sensitive reads and writes are identified.
- [ ] Check-then-act races have been removed or deliberately protected.
- [ ] Atomic SQL is used where appropriate.
- [ ] Constraints protect data invariants where possible.
- [ ] Required rows are explicitly locked when multi-step coordination needs them.
- [ ] Transaction scope is short and contains no unnecessary network waits.
- [ ] Transaction-scoped database connections/managers are propagated correctly.
- [ ] Idempotency exists where retries are possible.
- [ ] Zero-row updates are treated as meaningful outcomes where applicable.
- [ ] Concurrency tests reproduce the expected race scenarios.
- [ ] Lock waits and transaction duration are observable.
- [ ] Deadlock/serialization/timeout behavior has a deliberate retry policy.
- [ ] Multi-tenant and authorization semantics are tested under concurrency.
- [ ] External side effects are not assumed to roll back with PostgreSQL.

# 48. Key Takeaways

```text
READ COMMITTED
    ↓
new visibility snapshot per command
    ↓
not one frozen snapshot per transaction
    ↓
ordinary SELECT follows its command snapshot
    ↓
modifying/locking commands have special conflict handling
    ↓
concurrent row updates can cause waiting
    ↓
updated row version may then be considered
    ↓
WHERE predicate can be re-evaluated
    ↓
atomic SQL is often the simplest concurrency control
    ↓
complex cross-row invariants may need locks or stronger isolation
```

The central lesson is not “avoid `READ COMMITTED`.”

It is:

> **Understand exactly what your statement guarantees, then design the invariant so that concurrency cannot silently invalidate the decision.**

That is the bridge from SQL correctness to real transactional engineering.
