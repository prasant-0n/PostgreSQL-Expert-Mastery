# 03.2 — ACID Deep Dive

> **Phase 03 — Transactions & Concurrency**  
> **Level:** Beginner → Expert  
> **Primary Goal:** Understand ACID as a set of observable guarantees and engineering trade-offs—not as four memorized words.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to:

- define Atomicity, Consistency, Isolation, and Durability precisely;
- explain what each property does and does **not** guarantee;
- distinguish database guarantees from application/business invariants;
- reason about ACID across multiple SQL statements;
- explain how PostgreSQL's transaction manager, MVCC, locks, and WAL participate in ACID behavior;
- identify where ACID can be weakened intentionally and what risk that creates;
- recognize false ACID claims made by application code, ORMs, queues, caches, and distributed systems;
- design transactions around business invariants rather than arbitrary API boundaries;
- diagnose failures using evidence rather than relying on the label "transactional";
- understand why ACID alone does not solve race conditions, retries, duplicate messages, or external side effects.

# 2. The Four Properties — Precise Definition

| Property | Core question | PostgreSQL interpretation |
|---|---|---|
| **Atomicity** | Does the transaction's effect happen completely or not at all? | A transaction's database changes are committed together or rolled back together. |
| **Consistency** | Does a successful transaction preserve required valid states? | PostgreSQL preserves database-enforced invariants; application-defined invariants still require suitable design. |
| **Isolation** | What can concurrent transactions observe and how do conflicting operations interact? | PostgreSQL uses MVCC plus locking and isolation-level semantics. |
| **Durability** | After commit is acknowledged, will the committed result survive failures? | WAL and durable commit processing provide the foundation, subject to configured durability settings. |

The PostgreSQL documentation describes transactions as all-or-nothing operations, explains that committed changes are recorded durably, and describes MVCC as the basis for concurrent transaction isolation. citeturn673144search2turn673144search1

The most important correction to the usual textbook definition is this:

> **ACID is not a promise that your business logic is correct.**

A transaction can be fully ACID and still perform the wrong business operation.

For example:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

This can be atomic, isolated, and durable while still being a bad business operation if account `1` was not authorized to spend the money or the account was already over its permitted limit.

ACID protects the transactional mechanism. Your schema, constraints, transaction design, and application logic must define the business invariants.

---

# 3. A Better Mental Model

Think of a transaction as a transition:

```text
Valid State S0
      |
      | transaction T
      v
Valid State S1
```

ACID asks four different questions about that transition:

```text
Atomicity  -> Is the transition indivisible?
Consistency -> Is the resulting state valid?
Isolation   -> What can concurrent transactions observe?
Durability  -> Does the committed transition survive failure?
```

This makes it easier to avoid the common mistake of treating ACID as a single feature.

---

# 4. Atomicity

## 4.1 Simple definition

Atomicity means a transaction is treated as one unit of work:

```text
all changes succeed
        OR
no transaction changes become committed
```

PostgreSQL's transaction tutorial explicitly describes transactions as all-or-nothing and notes that intermediate states are not visible to other concurrent transactions in the ordinary transactional model. citeturn673144search2

## 4.2 Example: money transfer

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 10;

UPDATE accounts
SET balance = balance + 100
WHERE id = 20;

COMMIT;
```

A failure before `COMMIT` causes the transaction to roll back rather than leave only one side permanently applied.

## 4.3 Atomicity is larger than one SQL statement

A single SQL statement is already transactional. The practical reason to create an explicit transaction is to bind **multiple statements into one unit**.

```text
Statement A
Statement B
Statement C

        ↓

One transaction boundary
```

Without the transaction boundary:

```text
A commits
B commits
C fails

=> partial business operation
```

With it:

```text
A
B
C fails

=> rollback of the transaction's uncommitted work
```

## 4.4 Atomicity and savepoints

Atomicity does not mean you can only choose between "everything in the entire session" and "nothing".

Savepoints create a smaller rollback boundary inside the transaction:

```sql
BEGIN;

INSERT INTO orders (...);

SAVEPOINT before_optional_step;

INSERT INTO optional_order_metadata (...);

ROLLBACK TO SAVEPOINT before_optional_step;

COMMIT;
```

The outer transaction can still commit while work after the savepoint is discarded. PostgreSQL documents savepoints as a more granular form of transaction control. citeturn673144search2

### Engineering lesson

Use savepoints for controlled partial recovery, not as a substitute for designing correct transaction boundaries.

---

# 5. Atomicity Does Not Mean "Undo Everything Everywhere"

This is one of the most important production distinctions.

Suppose a request performs:

```text
1. PostgreSQL INSERT
2. Stripe/API call
3. Send email
4. Publish Kafka message
```

A PostgreSQL rollback can undo step 1, but it cannot magically reverse the external side effects of steps 2–4.

So this code is **not globally atomic**:

```text
BEGIN
  INSERT payment
COMMIT

call external-payment-provider
send-email
```

The database transaction gives you atomicity only over the resources participating in that transaction protocol.

This leads to the transactional-outbox pattern later in the curriculum.

---

# 6. Consistency

## 6.1 The most misunderstood ACID property

"Consistency" does **not** simply mean:

> PostgreSQL never has bad data.

A better interpretation is:

> A transaction that commits must leave the database satisfying the integrity rules that apply to it.

Examples include:

```text
PRIMARY KEY uniqueness
FOREIGN KEY validity
CHECK constraints
NOT NULL requirements
EXCLUSION rules
application-enforced invariants when implemented correctly
```

PostgreSQL provides database-level consistency mechanisms through constraints and transaction semantics. But it cannot infer arbitrary business rules from an application's intention.

## 6.2 Database consistency vs business consistency

Suppose:

```text
orders.total >= 0
```

is enforced by a constraint.

But your business rule is:

```text
order cannot be shipped unless payment is captured
```

That rule is not automatically enforced just because a transaction exists.

You need something such as:

```text
state-machine constraint/design
conditional update
stored procedure
trigger
explicit lock/isolation strategy
serializable transaction
application orchestration
```

The correct mechanism depends on the invariant.

## 6.3 Consistency is not automatic correctness

Consider:

```sql
BEGIN;

UPDATE inventory
SET quantity = quantity - 5
WHERE product_id = 100;

COMMIT;
```

This can satisfy every database constraint while still being semantically wrong if there were only three sellable units.

The schema may need:

```sql
UPDATE inventory
SET quantity = quantity - 5
WHERE product_id = 100
  AND quantity >= 5;
```

followed by checking the affected row count.

Or it may require a stronger concurrency strategy.

**Consistency is a system-design responsibility, not a keyword.**

---

# 7. Isolation

Isolation answers:

> **When transactions execute concurrently, what interactions are allowed and what results may each transaction observe?**

PostgreSQL's concurrency system uses MVCC so statements can read appropriate row versions without relying exclusively on blocking readers with locks. The documentation notes that reading normally does not block writing and writing normally does not block reading under MVCC, while explicit locks are available for targeted conflicts. citeturn673144search1

Isolation is therefore not equivalent to:

```text
"only one transaction can run at a time"
```

That would be serial execution, which is much more restrictive than most database workloads require.

---

# 8. Durability

Durability means:

> Once a commit is acknowledged as successful, the committed transaction is intended to survive relevant failures according to the configured durability guarantees.

PostgreSQL's WAL architecture is central to this. The documentation explains that durability is a database feature guaranteeing the recording of committed transactions even after server crashes or power loss, and describes configuration options that can deliberately weaken those guarantees. citeturn673144search0turn673144search7

## 8.1 WAL mental model

A simplified model is:

```text
SQL change
   ↓
transaction changes
   ↓
WAL records
   ↓
commit record / durability processing
   ↓
COMMIT acknowledged
```

Later, recovery can use WAL to reconstruct database state.

This is why PostgreSQL can acknowledge committed transactions without requiring every modified data page to be synchronously written at the exact moment of commit.

---

# 9. Durability Is Configurable

PostgreSQL provides settings that intentionally trade durability for performance.

For example, the PostgreSQL 18 documentation notes that `synchronous_commit` can allow commit acknowledgment before the transaction's WAL is forced to disk, introducing a risk of losing recently committed transactions after a crash. It also documents `fsync`, `full_page_writes`, and unlogged tables as durability-related settings. citeturn673144search0

This leads to an important production principle:

> **"PostgreSQL is ACID" is incomplete unless you know the durability configuration and workload assumptions.**

Do not casually change durability settings in production because a benchmark became faster.

---

# 10. ACID Properties Interact

The four letters are conceptually separate, but implementation choices connect them.

For example:

```text
MVCC      -> isolation
WAL       -> durability
constraints + transaction boundaries -> consistency
COMMIT / rollback -> atomicity
```

But these are not four completely independent modules.

A stronger isolation strategy may increase abort/retry pressure.

More indexes may increase the amount of WAL generated by writes.

Long transactions can retain old row versions and interfere with cleanup.

A durable commit can require waiting for WAL-related processing.

Therefore ACID must be reasoned about as a system of trade-offs.

# 11. A Concrete End-to-End Example

Consider an order checkout:

```text
1. Verify customer
2. Create order
3. Create order items
4. Reserve inventory
5. Record payment intent
6. Update order state
7. Commit
8. Notify downstream services
```

A robust architecture separates the database transaction boundary from external side effects.

### Database transaction

```text
BEGIN
  create order
  create order items
  reserve inventory
  create payment record
  set order state
  create outbox event
COMMIT
```

### After commit

```text
outbox worker
   ↓
message broker / external systems
   ↓
email / search / analytics / integrations
```

This provides a stronger consistency boundary than:

```text
BEGIN
  create order
COMMIT

call broker
call payment provider
call email service
```

because the transactional outbox makes the intent to publish part of the database transaction itself.

# 12. ACID and MVCC

PostgreSQL's MVCC model means rows can have multiple physical versions associated with transactions. A transaction does not simply ask:

> "What is the latest value on disk?"

It evaluates visibility according to transaction/snapshot rules.

The PostgreSQL documentation describes MVCC as a multiversion model where statements see a snapshot of database data and notes that this reduces read/write blocking. citeturn673144search1

This matters because:

```text
Isolation
   ↓
visibility rules
   ↓
MVCC snapshots
   ↓
row versions + transaction state
```

A later chapter will go deeply into the internal mechanics. Here, the key ACID insight is that isolation is implemented through more than simple mutex-style locking.

---

# 13. ACID and Constraints

Constraints are one of the major mechanisms by which database consistency is expressed.

Example:

```sql
CREATE TABLE order_items (
    id bigint PRIMARY KEY,
    order_id bigint NOT NULL,
    quantity integer NOT NULL CHECK (quantity > 0),
    CONSTRAINT fk_order
      FOREIGN KEY (order_id)
      REFERENCES orders(id)
);
```

A transaction that violates an enforced constraint cannot successfully commit.

This is much stronger than relying on code like:

```ts
if (!orderId) {
  throw new Error("invalid order");
}
```

because another application process, SQL client, migration, job, or service could bypass that application check.

---

# 14. ACID and Concurrency

A transaction can be ACID and still produce an unexpected business result if its isolation level is too weak for the invariant.

Example:

```text
Transaction A                    Transaction B
--------------                   --------------
Read available = 1              Read available = 1
Decide to allocate               Decide to allocate
Write allocation                 Write allocation
Commit                           Commit
```

The question is not merely:

> "Were both transactions atomic?"

The real question is:

> "Was the invariant protected under concurrent execution?"

This is why the curriculum progresses from ACID to MVCC, isolation levels, locking, and concurrency anomalies.

---

# 15. ACID Does Not Equal Serializable Execution

A common misconception is:

```text
ACID = transactions behave as if they ran one at a time
```

That is false.

Isolation has levels. PostgreSQL supports multiple isolation semantics, and the strongest commonly discussed mode is `Serializable`, which aims to prevent serialization anomalies rather than simply allowing arbitrary concurrent outcomes. PostgreSQL documentation explains that serializable transactions use nonblocking monitoring of dangerous read/write conflict patterns and may roll back a transaction to break a cycle. citeturn673144search6

The trade-off is important:

```text
More concurrency
       ↕
Stronger isolation
       ↕
Abort/retry cost
```

There is no universal "best" isolation level.

---

# 16. ACID and Retries

This is one of the most important production consequences.

At stronger isolation levels, PostgreSQL may reject a transaction to preserve correctness. PostgreSQL documents SQLSTATE `40001` (`serialization_failure`) for retryable serialization failures and recommends that applications using Repeatable Read or Serializable be prepared to retry failed transactions. It also documents `40P01` for deadlocks. citeturn673144search8

Therefore a transaction wrapper should conceptually be capable of:

```text
BEGIN
  perform complete transactional unit
COMMIT

if retryable failure:
  rollback
  retry whole transaction
```

Not:

```text
retry only the final UPDATE
```

because the entire transactional unit may need to be re-evaluated against a new snapshot.

---

# 17. Why Retry Design Is Part of ACID Engineering

Imagine:

```text
Transaction T1
charge customer
insert payment
commit
```

The client times out immediately after the server commits.

The application sees:

```text
"I do not know whether it committed."
```

A naive retry can cause a duplicate payment.

Thus:

```text
Atomicity alone
      ↓
not enough
      ↓
Idempotency + transaction design
      ↓
correct retry behavior
```

This is why transaction correctness must include failure scenarios outside the SQL text itself.

---

# 18. ACID vs BASE

You will often see:

```text
ACID
vs
BASE
```

This comparison can be misleading.

ACID primarily describes transactional guarantees.

BASE is a broad architecture style emphasizing availability and eventual consistency in certain distributed systems.

Modern systems frequently combine them:

```text
PostgreSQL core state      -> ACID
message propagation        -> eventual consistency
cache                      -> eventual consistency
analytics                  -> asynchronous
search index               -> eventually consistent
```

A production architecture does not need to choose one slogan for everything.

---

# 19. ACID vs Distributed Transactions

A PostgreSQL transaction is not automatically a distributed transaction.

This is a crucial boundary:

```text
PostgreSQL transaction
        ≠
PostgreSQL + Kafka + Redis + Stripe all atomically commit together
```

PostgreSQL does support two-phase commit, using `PREPARE TRANSACTION`, `COMMIT PREPARED`, and `ROLLBACK PREPARED`, for external transaction-management systems. But prepared transactions introduce operational complexity and are intended for specialized distributed transaction coordination rather than being a default application pattern. citeturn673144search13turn673144search12

For most Node/NestJS systems, transactional outbox/inbox patterns are often simpler and more operationally robust than attempting global two-phase coordination.

---

# 20. ACID and Long-Running Transactions

A transaction that remains open for a long time is not "more ACID".

It can instead create operational pressure:

```text
long transaction
      ↓
old snapshots remain relevant
      ↓
cleanup becomes harder
      ↓
bloat can increase
      ↓
WAL / replication pressure can increase
```

Later chapters will study this through MVCC and vacuum internals.

The design principle is simple:

> **Keep transaction scope large enough to protect the invariant, but no larger than necessary.**

---

# 21. ACID and Connection Pooling

A transaction is associated with a database session/connection context.

This creates a serious application-level risk in pooled environments.

Bad conceptual pattern:

```ts
const tx = beginTransaction();
await doWork();
returnConnectionToPool();
```

The transaction must be committed or rolled back before that connection is returned to the pool.

Otherwise application requests can inherit unintended session state or transaction state.

Correct architecture:

```text
acquire connection
    ↓
BEGIN
    ↓
transaction work
    ↓
COMMIT / ROLLBACK
    ↓
release connection
```

This is especially important for Node.js/NestJS applications using connection pools and ORM transaction managers.

# 22. Common ACID Myths

## Myth 1: "A transaction prevents race conditions."

False.

A transaction provides a boundary, not necessarily the isolation strength or locking needed for a specific race.

## Myth 2: "ACID means no bad data is possible."

False.

A transaction can faithfully commit a logically incorrect operation.

## Myth 3: "COMMIT means everything in the whole system is durable."

False.

It means the database transaction committed according to database durability semantics. External systems may have separate durability guarantees.

## Myth 4: "READ COMMITTED is basically serialized."

False.

It permits concurrent behaviors that stronger isolation modes reject.

## Myth 5: "WAL means every data page is immediately on disk."

False.

WAL separates logging/recovery from data-page flushing.

## Myth 6: "Retries are safe because transactions are atomic."

False.

Retrying a committed operation can duplicate side effects unless operations are idempotent.

## Myth 7: "Using an ORM transaction automatically gives correct business consistency."

False.

The ORM controls transaction mechanics; it does not infer your concurrency invariants.

# 23. Naive → Improved → Production

## Scenario: prevent overselling

### Naive

```ts
const stock = await repo.findOne(productId);
if (stock.quantity > 0) {
  stock.quantity -= 1;
  await repo.save(stock);
}
```

### Why it fails

Two requests can read the same logical state before either update becomes effective.

### Improved

Use an atomic conditional update:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0
RETURNING quantity;
```

Then treat a zero-row result as "not available".

### Why it works

The invariant is expressed at the write boundary instead of being separated into a vulnerable read/check/write sequence.

### Production considerations

Depending on the broader business rule, you may still need:

```text
transaction boundary
order reservation record
idempotency key
state machine
timeout/release policy
outbox event
reconciliation
```

The exact solution depends on the domain.

# 24. Testing ACID Properties

Do not test ACID only with one successful unit test.

Test failure paths.

## Atomicity tests

```text
statement 1 succeeds
statement 2 fails
=> verify none of the transaction changes committed
```

## Consistency tests

```text
attempt illegal state
=> constraint/business invariant rejects it
```

## Isolation tests

Run two concurrent sessions and deliberately interleave statements.

Example harness:

```text
Session A                Session B
---------                ---------
BEGIN                    BEGIN
READ x                   READ x
WRITE x                  WRITE x
COMMIT                   COMMIT
```

Observe the actual result rather than relying on expected textbook diagrams.

## Durability tests

For infrastructure-level testing, validate the configured durability assumptions, crash-recovery procedures, backups, WAL archiving, and replica recovery behavior.

# 25. Evidence-Driven Debugging

When someone reports:

> "The transaction committed, but the data disappeared."

Do not immediately conclude PostgreSQL violated durability.

Investigate systematically:

```text
Was COMMIT actually reached?
        ↓
Was an error hidden by application code?
        ↓
Was the transaction rolled back later?
        ↓
Was a retry executed?
        ↓
Was the observation made from a replica?
        ↓
Was replication lag involved?
        ↓
Was synchronous_commit changed?
        ↓
Was the table UNLOGGED?
        ↓
Was there crash/recovery evidence?
```

Similarly, for an isolation anomaly:

```text
identify transaction IDs/sessions
identify timing
identify statements
identify isolation level
identify locks
identify snapshots
reproduce the interleaving
```

The PostgreSQL documentation provides dedicated sections for transaction processing, MVCC, isolation, locking, consistency checks, and serialization failure handling. citeturn673144search5turn673144search1turn673144search6turn673144search8

# 26. Security Implications of ACID

Transactions do not replace authorization.

Consider:

```sql
BEGIN;
UPDATE users SET role = 'admin' WHERE id = 20;
COMMIT;
```

This can be perfectly ACID and still be a severe security failure.

Security requires:

```text
authorization
least privilege
RLS where appropriate
validated actor/context
safe stored procedures/functions when used
protected audit history
```

In other words:

> **ACID protects state transitions; authorization determines whether the actor should be allowed to request that transition.**

# 27. ACID in a Jewellery ERP

Consider a stock transfer:

```text
Branch A
  ↓
transfer 10 grams
  ↓
Branch B
```

A correct transactional unit may need to update:

```text
transfer header
transfer lines
source inventory
destination inventory
movement ledger
financial impact
audit record
outbox event
```

The transaction boundary should protect the invariants that must move together.

But external notifications should normally not determine whether the inventory mutation commits.

A strong architecture is:

```text
BEGIN
  validate transfer
  reserve source inventory
  create transfer
  create movement/ledger records
  create audit record
  create outbox event
COMMIT

        ↓

async consumers
  ├── notifications
  ├── reporting projection
  ├── search
  └── integrations
```

This creates a clear boundary between authoritative transactional state and downstream eventual-consistency work.

# 28. Production Decision Framework

When designing a transactional operation, ask in this order:

```text
1. What business invariant must remain true?
2. Which records must change together?
3. What is the smallest safe transaction boundary?
4. What concurrent operations can interfere?
5. Which isolation semantics are required?
6. Is an atomic statement enough?
7. Do we need row/table/advisory locking?
8. Could serialization/deadlock failure occur?
9. Is the transaction retryable?
10. Are all side effects idempotent?
11. What happens if the client times out after COMMIT?
12. What happens if the process crashes before COMMIT?
13. What happens after commit but before event publication?
14. How will we observe and diagnose failures?
15. What is the recovery/reconciliation path?
```

This checklist is substantially more useful than asking:

> "Is this operation inside a transaction?"

# 29. AI / Vibe-Coding Failure Modes

AI-generated code frequently gets transaction mechanics superficially right while missing the system invariant.

## Failure 1: Transaction around every service method

```ts
await transaction(async () => {
  callExternalAPI();
});
```

Problem: external I/O may hold locks and prolong the transaction unnecessarily.

## Failure 2: Read-check-write without concurrency reasoning

```text
SELECT quantity
if quantity > 0
UPDATE quantity
```

Problem: atomicity does not eliminate the race.

## Failure 3: Blind retries

```ts
for (let i = 0; i < 3; i++) {
  try {
    return await performPayment();
  } catch {
    continue;
  }
}
```

Problem: retries can duplicate committed effects.

## Failure 4: Treating ORM transactions as magic

Problem: the ORM cannot automatically choose the correct isolation, locking strategy, invariant, or retry semantics.

## Failure 5: External side effects inside the transaction

Problem: long lock duration, timeout complexity, and no true global atomicity.

## Failure 6: Changing durability settings for benchmark results

Problem: performance gains may represent weakened failure guarantees. PostgreSQL explicitly documents these durability trade-offs. citeturn673144search0

# 34. Key Distinctions to Memorize

```text
ACID
├── Atomicity    -> transaction effect is all-or-nothing
├── Consistency  -> committed state preserves enforced invariants
├── Isolation    -> concurrent execution has defined visibility/conflict semantics
└── Durability   -> committed data survives failures according to configured guarantees
```

But also remember:

```text
ACID ≠ business correctness
ACID ≠ authorization
ACID ≠ idempotency
ACID ≠ distributed atomicity
ACID ≠ serialization
ACID ≠ zero conflicts
ACID ≠ zero retries
ACID ≠ zero operational failure
```

---

# 35. Central Principle

> **ACID is the foundation for reliable transactional state transitions, not a substitute for invariant design, concurrency control, authorization, idempotency, or distributed-systems engineering.**

A strong PostgreSQL engineer does not merely ask:

> "Is this inside a transaction?"

They ask:

> **"What invariant are we protecting, which concurrent executions can violate it, what transactional guarantees are required, and what happens when the transaction succeeds, fails, retries, times out, or commits just before the process crashes?"**
