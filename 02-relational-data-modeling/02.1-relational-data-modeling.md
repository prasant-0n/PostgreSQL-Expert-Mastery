# 02.1 — Relational Data Modeling

> **Phase 02 — Relational Data Modeling**  
> **Level:** Foundation → Advanced → Production Architecture  
> **Goal:** Learn to translate business reality into relational structures that preserve correctness, clarity, evolvability, and operational safety.

---

## 1. Chapter Objective

Relational modeling is not the act of drawing tables. It is the disciplined process of deciding:

- what facts the system must store,
- what each fact means,
- which facts belong together,
- which facts depend on other facts,
- which business rules must be impossible to violate,
- how identity is represented,
- how relationships are represented,
- how historical change is represented,
- and which assumptions should be enforced by PostgreSQL rather than merely trusted in application code.

By the end of this chapter, you should be able to take a vague requirement such as:

> “Customers can place orders containing products, products belong to categories, prices can change, branches operate independently, and managers need historical reporting.”

and systematically turn it into a relational design with explicit entities, attributes, keys, relationships, constraints, temporal rules, ownership boundaries, and known trade-offs.

The target is not merely a schema that **can store the data**.

The target is a schema that makes **invalid states difficult or impossible to represent**.

---

# 2. What Is Relational Data Modeling?

## 2.1 Simple definition

Relational data modeling is deciding how real-world information is represented using relations (tables), attributes (columns), keys, relationships, and constraints.

## 2.2 Engineering definition

A relational model is a structured representation in which facts are decomposed into relations and connected through keys, while integrity rules constrain the legal states of the database.

## 2.3 Expert definition

A production relational model is a **formalized information contract** between business rules, application behavior, queries, concurrency, and storage. The schema should encode stable invariants in a way that remains correct across API endpoints, background jobs, migrations, scripts, multiple services, retries, failures, and future application versions.

This distinction is critical:

```text
Application validation
        ↓
helps users avoid mistakes

Database constraints
        ↓
protect the data regardless of caller
```

An API may be the primary writer today. Tomorrow there may be:

- an admin script,
- an import job,
- a reporting process,
- a queue consumer,
- a migration,
- another service,
- or an AI-generated maintenance script.

The relational model must survive all of them.

# 3. First Principles

## 3.1 Data is facts

Start by separating **facts** from **computed views of facts**.

Example:

```text
Fact:
Customer 42 has email alice@example.com

Fact:
Order 9001 was created on 2026-09-13

Fact:
Order 9001 contains product 17 with quantity 3

Derived value:
Order total = sum(line quantities × effective prices)
```

Do not automatically store derived values just because they appear on screens.

Ask:

> Is this an independent business fact, or can it be derived from other facts?

Sometimes a derived value **should** be stored because it represents historical truth, a snapshot, or an intentional denormalization. The decision must be explicit.

---

## 3.2 Every attribute needs an owner

Suppose a system has:

```text
customer_id
customer_name
customer_phone
order_id
order_date
order_total
```

Do not ask only:

> “Can these columns fit in one table?”

Ask:

> “Which business object owns each fact?”

Possible ownership:

```text
Customer
 ├── customer_id
 ├── customer_name
 └── customer_phone

Order
 ├── order_id
 └── order_date

Order total
 └── derived from order lines
```

Ownership is one of the strongest tools for preventing duplicated facts.

---

## 3.3 Relationships are facts too

A relationship is often a business fact that deserves explicit representation.

Examples:

```text
Customer places Order
Order contains Product
Employee works at Branch
Product belongs to Category
User has Role
Role grants Permission
```

Do not assume relationships are always just foreign-key columns. Many relationships have their own attributes:

```text
Student enrolls in Course

Enrollment:
- enrolled_at
- status
- grade
- dropped_at
```

Once a relationship has its own facts, it commonly becomes an associative entity/table.

---

# 4. Entity, Attribute, Relationship

## 4.1 Entity

An entity represents a distinct class of business object that can be identified and discussed independently.

Examples:

- customer,
- order,
- invoice,
- product,
- branch,
- employee,
- payment.

A database table often—but not always—represents an entity.

---

## 4.2 Attribute

An attribute describes an entity.

```text
Customer
--------
id
name
email
created_at
```

The important question is whether an attribute is **atomic at the level required by the model**.

---

## 4.3 Relationship

A relationship describes how entities are connected.

```text
Customer ─── places ─── Order
```

In a relational schema this commonly becomes:

```sql
orders.customer_id REFERENCES customers(id)
```

or, for many-to-many:

```sql
course_students(
    course_id,
    student_id
)
```

---

# 5. Business Requirements → Relational Model

A strong modeling workflow starts **before SQL**.

## Step 1 — Extract nouns

From a requirement, list candidate nouns.

Example:

> A customer can place multiple orders. Each order belongs to one branch and contains one or more products. Product prices change over time.

Candidate nouns:

```text
customer
order
branch
product
price
```

## Step 2 — Extract verbs

Candidate relationships:

```text
customer places order
order belongs to branch
order contains product
product has price history
```

## Step 3 — Extract business rules

Rules include:

```text
A customer can have many orders.
An order belongs to exactly one customer.
An order belongs to exactly one branch.
An order contains one or more lines.
A quantity must be positive.
A historical price has an effective period.
```

## Step 4 — Identify identity

For every entity ask:

> How do we know that two records represent the same business object?

## Step 5 — Identify cardinality

Examples:

```text
1 : 1
1 : N
N : 1
N : M
```

## Step 6 — Identify optionality

```text
Customer may have a middle name.
Order must have a customer.
Invoice may not yet have a payment.
```

This is where nullable foreign keys become meaningful rather than arbitrary.

## Step 7 — Identify invariants

Ask:

> What must never become true?

Examples:

```text
email must be unique per tenant
quantity must be > 0
invoice total must not be negative
an active subscription cannot overlap another active subscription
```

These become candidates for database constraints.

## Step 8 — Model time

Ask whether facts are:

- current-state only,
- historical,
- effective-dated,
- append-only,
- versioned,
- or event-oriented.

## Step 9 — Validate against real queries

A theoretically elegant model can still fail operationally if common access patterns become unnecessarily complicated or expensive.

# 6. Grain: The Most Important Modeling Question

**Grain** means what exactly one row represents.

This is one of the most important concepts in relational design.

Consider:

```text
order_lines
```

Its grain should be something like:

> One row represents one product line on one order.

Not:

> One row represents some order information and perhaps several products.

A clear grain prevents ambiguity in:

- aggregation,
- uniqueness,
- updates,
- joins,
- constraints,
- auditing,
- and reporting.

## Example

```text
order_id | product_id | quantity
---------+------------+---------
1001     | 10         | 2
1001     | 11         | 1
1001     | 15         | 4
```

Grain:

```text
one row = one product occurrence/line in one order
```

If the business permits the same product on an order only once, that creates another invariant:

```sql
UNIQUE (order_id, product_id)
```

But do not add this constraint blindly. Discounts, batches, serial numbers, tax categories, or fulfillment splits may legitimately require multiple lines for the same product. **Business grain comes first.**

---

# 7. Entity Identity

Identity is not merely “pick an ID column.”

There are several different identity concepts.

## 7.1 Technical identity

A surrogate identifier exists primarily to identify a database row.

Examples:

```sql
bigint
uuid
```

## 7.2 Natural/business identity

A value that has meaning outside the database.

Examples:

```text
GST registration number
SKU
ISBN
passport number
external customer number
```

## 7.3 External identity

An identifier assigned by another system.

Examples:

```text
Stripe customer ID
ERP legacy ID
CRM contact ID
supplier product code
```

A mature schema can have more than one identity:

```text
internal_id        → PostgreSQL identity
external_id        → integration identity
sku                → business identity
```

---

# 8. Surrogate Keys vs Natural Keys

## Surrogate key

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL
);
```

Advantages:

- stable technical identity,
- compact joins in many designs,
- decouples database identity from business policy,
- allows natural attributes to change.

Disadvantages:

- does not itself prevent duplicates in business identifiers,
- can hide missing domain-level uniqueness.

## Natural key

```sql
CREATE TABLE countries (
    country_code text PRIMARY KEY,
    name text NOT NULL
);
```

Advantages:

- directly represents business identity,
- can simplify certain domains.

Risks:

- business identifiers may change,
- large natural keys can propagate into foreign keys,
- humans may assume a value is immutable when it is not.

## Production rule

Do not ask:

> “Are surrogate keys better?”

Ask:

> “What is the stable identity of this entity, and which business identities must also be enforced?”

Often the answer is:

```text
Surrogate PK
+
UNIQUE natural/business key
```

---

# 9. Composite Keys

Composite keys identify a row through multiple attributes.

Example:

```sql
PRIMARY KEY (order_id, line_number)
```

Useful when the combination is genuinely the entity's identity.

### Example

```sql
CREATE TABLE order_lines (
    order_id bigint NOT NULL,
    line_number integer NOT NULL,
    product_id bigint NOT NULL,
    quantity numeric(12,3) NOT NULL,
    PRIMARY KEY (order_id, line_number)
);
```

This means:

> line number is unique **within an order**, not globally.

Avoid automatically introducing an `id` column when a meaningful composite identity already expresses the grain clearly.

But also recognize downstream implications:

- foreign keys become wider,
- joins may become more verbose,
- ORM mappings can become more complex,
- APIs may prefer a stable external identifier.

Modeling is a trade-off, not a slogan.

---

# 10. One-to-One Relationships

One-to-one is frequently modeled incorrectly.

Suppose:

```text
users
user_profiles
```

A true one-to-one relationship requires uniqueness.

```sql
CREATE TABLE user_profiles (
    user_id bigint PRIMARY KEY
        REFERENCES users(id),
    bio text
);
```

The primary key on `user_id` makes it impossible for one user to have multiple profiles.

A foreign key alone does **not** imply one-to-one:

```sql
user_profiles.user_id REFERENCES users(id)
```

Without `PRIMARY KEY` or `UNIQUE`, that is one-to-many.

## Question to ask

> Is this really a separate entity, or just optional attributes of the parent?

Use a separate table when there is a meaningful boundary such as:

- different lifecycle,
- sparse/optional data,
- security separation,
- ownership boundary,
- independent growth,
- different access patterns.

Do not split tables merely because a diagram looks cleaner.

---

# 11. One-to-Many Relationships

Example:

```text
Customer 1 ─── N Orders
```

Relational representation:

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(id),
    created_at timestamptz NOT NULL DEFAULT now()
);
```

The foreign key lives on the **many side**.

Mental rule:

```text
1 ───────── N
            ↑
       foreign key here
```

Optionality determines whether the foreign key is nullable.

```text
Every order must belong to a customer
→ customer_id NOT NULL

An order may exist before assignment
→ customer_id nullable
```

Do not use nullable foreign keys merely because application code sometimes creates objects in multiple steps.

If the relationship is mandatory in the business domain, model it as mandatory unless the workflow genuinely requires an intermediate state.

---

# 12. Many-to-Many Relationships

Relational databases model many-to-many relationships through an associative relation.

Example:

```text
students      courses
   \          /
    \        /
     enrollment
```

```sql
CREATE TABLE enrollments (
    student_id bigint NOT NULL REFERENCES students(id),
    course_id bigint NOT NULL REFERENCES courses(id),
    enrolled_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (student_id, course_id)
);
```

Now the relationship itself can carry attributes:

```text
enrolled_at
status
grade
completed_at
```

This is more than a technical bridge table. It represents a real business fact:

> Student X is enrolled in Course Y under these conditions.

---

# 13. Optionality and NULL

Model optionality deliberately.

```text
NOT NULL
```

means:

> The fact must exist for this row.

A nullable column means more than “sometimes empty.” It means the domain admits absence/unknownness represented by SQL NULL.

Consider:

```text
middle_name
```

Nullable may be reasonable.

But:

```text
customer_id
```

being nullable should require a business reason.

### Important distinction

These are not always equivalent:

```text
NULL
''
'unknown'
'not_provided'
```

Choose the representation based on semantics, not convenience.

---

# 14. Normalization: Why It Exists

Normalization reduces problematic redundancy and dependency anomalies.

The purpose is not:

> “Make every table tiny.”

The purpose is:

> **Store each fact in a location that matches its dependency and ownership.**

Common anomalies:

## Insert anomaly

You cannot insert a fact without inventing unrelated data.

## Update anomaly

The same fact appears in multiple rows and must be updated everywhere.

## Delete anomaly

Deleting one row accidentally deletes the only stored copy of another fact.

---

# 15. Functional Dependencies

A powerful modeling concept is:

> Attribute B is functionally dependent on A when a given A value determines exactly one B value.

Example:

```text
customer_id → customer_name
```

But in an order-line table:

```text
(order_id, product_id) → quantity
```

may be true if each product appears once per order.

Functional dependency reasoning helps identify:

- repeated facts,
- incorrect grains,
- candidate keys,
- normalization opportunities.

You do not need to perform formal relational algebra every time, but you should develop the habit of asking:

> “What determines this column?”

That question exposes many schema defects.

---

# 16. First Normal Form (1NF)

1NF is commonly explained as requiring atomic values and avoiding repeating groups.

The more useful engineering interpretation is:

> A column should represent one value at the row's declared grain rather than a hidden collection of unrelated records.

Bad relational design:

```text
order_id | product_ids
---------+------------
1001     | {10,11,15}
```

This may be a valid PostgreSQL array, but it is not automatically a good representation of order lines.

Better:

```text
order_id | product_id | quantity
---------+------------+---------
1001     | 10         | 2
1001     | 11         | 1
1001     | 15         | 4
```

Important nuance:

**1NF does not mean “PostgreSQL must never use arrays or JSON.”**

Specialized types can be correct when the value is genuinely one attribute at the declared grain. The question is semantic, not ideological.

---

# 17. Second Normal Form (2NF)

2NF concerns attributes depending on the whole candidate key rather than only part of a composite key.

Example:

```text
(order_id, product_id)
```

Suppose a table stores:

```text
order_id
product_id
order_date
product_name
quantity
```

Dependencies might be:

```text
order_id → order_date
product_id → product_name
(order_id, product_id) → quantity
```

This indicates the table mixes multiple entities/facts.

A decomposition might become:

```text
orders(order_id, order_date)
products(product_id, product_name)
order_lines(order_id, product_id, quantity)
```

---

# 18. Third Normal Form (3NF)

3NF focuses on removing non-key attributes that depend transitively on other non-key attributes.

Example:

```text
employee_id
branch_id
branch_name
```

If:

```text
employee_id → branch_id
branch_id → branch_name
```

then storing `branch_name` in the employee row duplicates the branch fact.

Better:

```text
employees(employee_id, branch_id)
branches(branch_id, branch_name)
```

Again, normalization is not a religion. Intentional denormalization may be justified when the duplicated value represents a snapshot or when a measured workload benefits significantly.

---

# 19. BCNF and Stronger Normalization Reasoning

Boyce-Codd Normal Form is stricter than 3NF and focuses on determinants being candidate keys.

You should know BCNF conceptually even when production work rarely starts with a formal BCNF checklist.

The practical lesson is:

> Every determinant that controls another fact should be represented honestly in the model.

This becomes especially important with:

- scheduling,
- pricing rules,
- organizational hierarchies,
- room/resource allocation,
- permission systems,
- academic enrollment,
- temporal data.

---

# 20. Denormalization

Denormalization means intentionally introducing redundancy or precomputed structure for a reason.

Valid reasons can include:

- measured query latency,
- high read amplification,
- expensive repeated aggregation,
- historical snapshots,
- reporting workloads,
- materialized representations,
- integration boundaries.

Invalid reason:

> “Joining is slow.”

before measuring the actual query.

A join is a relational operation, not a defect.

## Denormalization checklist

Before denormalizing, record:

```text
What query is slow?
What is the measured latency?
What is the workload frequency?
What causes the cost?
Can indexing solve it?
Can query shape solve it?
Can aggregation strategy solve it?
What new consistency obligation will duplication create?
Who owns synchronization?
How is drift detected?
```

---

# 21. Constraints Are Part of the Model

A schema without constraints often represents intentions rather than enforceable rules.

Core constraints:

```sql
PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
EXCLUDE
```

Example:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE,
    price numeric(12,2) NOT NULL CHECK (price >= 0)
);
```

The application may also validate price.

That is good.

But the database constraint remains valuable because other writers cannot bypass it.

---

# 22. Business Rules vs Database Rules

Not every rule belongs in a `CHECK` constraint.

## Strong database candidates

```text
column required
value must be >= 0
identifier must be unique
foreign row must exist
range must not overlap
status must be one of a controlled set
```

## Often application/service-level

```text
send an email after approval
call a payment provider
choose a recommendation strategy
format UI text
```

## Sometimes transaction-level/database-level

```text
cannot oversell stock
only one active subscription may exist
two bookings cannot overlap
balance must not become negative
```

These may require:

- locking,
- unique constraints,
- exclusion constraints,
- serializable transactions,
- triggers,
- or carefully designed transaction workflows.

The key is to identify the invariant before choosing the mechanism.

---

# 23. Referential Integrity

Foreign keys express existence dependencies.

```sql
customer_id bigint NOT NULL
    REFERENCES customers(id)
```

This means the referenced customer must exist when the relationship is enforced.

## Delete behavior

Possible semantics include:

```sql
ON DELETE RESTRICT
ON DELETE NO ACTION
ON DELETE CASCADE
ON DELETE SET NULL
ON DELETE SET DEFAULT
```

Choose based on business meaning.

### Example: order → customer

Automatically cascading from a customer to financial orders is usually dangerous because historical records commonly outlive the customer account.

### Example: order → order_lines

Cascading deletion of dependent line rows may be reasonable for drafts or child records where independent existence has no business meaning.

Do not choose `CASCADE` merely because migrations become convenient.

---

# 24. Lifecycle Modeling

A mature schema models entity lifecycle explicitly.

Example:

```text
pending
confirmed
fulfilled
cancelled
closed
```

Questions:

- Can states be skipped?
- Can transitions reverse?
- Which timestamps are required?
- Is cancellation permanent?
- Can a cancelled order be reopened?
- Does state represent current status only or a full history?

A single `status` column represents current state.

It does **not** automatically represent transition history.

If history matters, model it:

```text
order_status_history
--------------------
order_id
from_status
to_status
changed_at
changed_by
reason
```

---

# 25. Current State vs History

One of the biggest modeling decisions is whether a table represents:

```text
current truth
```

or

```text
historical truth
```

Example product price:

### Current-state model

```text
products.price
```

Good when only today's price matters.

### Historical model

```text
product_prices
--------------
product_id
price
valid_during
```

Required when the question is:

> “What was the price when the order happened?”

In financial or audit-heavy domains, historical snapshots are often more important than elegant normalization.

---

# 26. Snapshot Facts

An important subtlety:

A value may be copied intentionally because the copied value is **a new historical fact**.

Example:

```text
products.name = "Gold Chain"
```

At order time:

```text
order_lines.product_name = "Gold Chain"
```

This is not necessarily a normalization failure.

The order line may mean:

> The product was sold under this displayed name at the time of sale.

Similarly:

```text
unit_price
currency
customer_address
sales_tax_rate
```

may need to be snapshotted because later source changes must not rewrite historical meaning.

### Key distinction

```text
Duplication because we failed to model ownership
        ≠
Intentional snapshot because history requires immutability
```

---

# 27. Monetary and Quantity Modeling

Model financial quantities according to domain semantics.

Avoid:

```sql
price double precision
```

for ordinary currency accounting.

Prefer exact numeric representations appropriate to the domain:

```sql
numeric(19,4)
```

or a carefully selected scale.

For quantities in manufacturing or jewelry:

```text
weight
purity
stone_count
metal_quantity
```

may require different scales.

Do not force every numeric quantity into `integer` or a generic decimal without examining real domain precision.

---

# 28. Units Must Be Modeled

A number without a unit may be ambiguous.

Bad:

```text
weight = 12.5
```

What is it?

```text
gram
kilogram
ounce
milligram
```

Better models can include:

```text
weight_grams numeric(...)
```

where the unit is encoded by the column contract.

This is often safer than storing:

```text
weight = 12.5
unit = 'g'
```

when every row is expected to use a standard unit.

The right choice depends on integration needs and domain variability.

---

# 29. Multi-Tenant Modeling

For SaaS and ERP systems, tenant ownership becomes a first-class modeling concern.

Example:

```text
tenants
branches
customers
orders
```

One strategy:

```text
orders.tenant_id
orders.branch_id
```

and enforce relationships so that a branch cannot be accidentally associated with a different tenant.

A basic foreign key:

```sql
FOREIGN KEY (branch_id) REFERENCES branches(id)
```

may prove insufficient when tenant isolation requires the pair:

```text
(tenant_id, branch_id)
```

to correspond to one exact branch.

Composite foreign keys can encode this:

```sql
FOREIGN KEY (tenant_id, branch_id)
    REFERENCES branches (tenant_id, id)
```

This is a powerful pattern because it moves ownership assumptions into relational integrity.

Then add row-level security or application authorization as appropriate.

---

# 30. Modeling Organizational Hierarchies

Common patterns:

```text
Company
 └── Region
     └── Branch
         └── Department
             └── Employee
```

Do not blindly flatten the hierarchy:

```text
employee.company_name
employee.region_name
employee.branch_name
```

Store references to authoritative entities.

If hierarchy queries are frequent, later chapters can introduce:

- recursive CTEs,
- materialized paths,
- `ltree`,
- closure tables,
- nested sets,
- or specialized hierarchy strategies.

Modeling begins with business semantics before selecting an optimization structure.

---

# 31. Polymorphism: A Dangerous Shortcut

A common anti-pattern is:

```text
owner_type
owner_id
```

where `owner_id` can reference several unrelated tables.

Example:

```text
comments
--------
commentable_type
commentable_id
```

This cannot be represented by one normal foreign key because PostgreSQL cannot enforce:

```text
if type = 'post' → post_id exists
if type = 'video' → video_id exists
```

without additional mechanisms.

Alternatives include:

- separate association tables,
- a common parent table,
- subtype modeling,
- JSONB for truly flexible metadata,
- trigger-based enforcement when justified.

Never use polymorphic IDs merely because they are easy to serialize from application code.

---

# 32. Inheritance and Subtypes

Suppose a system has:

```text
party
customer
supplier
employee
```

Ask whether they are:

```text
independent entities
```

or

```text
subtypes of a shared entity
```

A common approach:

```text
parties
-------
id
name

customers
---------
party_id PK/FK
credit_limit

suppliers
---------
party_id PK/FK
payment_terms
```

This can reduce duplication when common identity truly belongs to a shared parent.

But subtype hierarchies introduce joins and complexity. Do not create a universal `entity` table for everything without a strong domain reason.

---

# 33. PostgreSQL-Specific Modeling Power

PostgreSQL offers more expressive modeling than a lowest-common-denominator SQL design.

Useful tools include:

```text
domains
enums
ranges
multiranges
arrays
JSONB
composite types
generated columns
identity columns
exclusion constraints
partial indexes
expression indexes
row-level security
```

The existence of a feature does not mean every schema should use it.

A disciplined engineer asks:

> Does this type express domain semantics better than ordinary columns and tables?

Use specialized PostgreSQL types when they create a clear contract, not merely to demonstrate database features.

---

# 34. Relational Modeling vs JSON/Document Modeling

A document structure can look convenient:

```json
{
  "customer": {
    "name": "Alice"
  },
  "orders": [
    {"id": 1},
    {"id": 2}
  ]
}
```

But ask what must be:

- uniquely identified,
- joined,
- filtered,
- aggregated,
- referenced,
- independently updated,
- constrained,
- audited,
- or shared across transactions.

Those needs often point toward relational structures.

JSONB is excellent for some flexible or semi-structured data.

It should not become a hiding place for an undocumented relational model.

---

# 35. Index Design Begins With Access Paths

Indexes are not part of conceptual modeling, but physical design must reflect the model's relationships and workloads.

Every important foreign key and uniqueness decision should later be evaluated against:

```text
join patterns
filter patterns
sort patterns
cardinality
write rate
```

A foreign key does not automatically mean the database needs a separate index on the referencing column in every situation, but many parent/child access patterns benefit from one.

Do not blindly create an index on every column.

---

# 36. Production Schema Example — Multi-Branch ERP

Consider an ERP with:

```text
Tenant
Branch
Customer
Product
Order
Order Line
Payment
Employee
```

A conceptual structure could be:

```text
Tenant
  │
  ├── Branch
  │     │
  │     ├── Employee
  │     └── Order
  │            │
  │            ├── Customer
  │            ├── Order Line ─── Product
  │            └── Payment
```

Key questions:

```text
Does customer belong to tenant?
Can customer exist across branches?
Can one order contain products owned by another tenant?
Can a product be shared across branches?
Can payment belong to an order only once?
Can an order be deleted after payment?
Does the order preserve historical product price?
```

These are modeling questions—not implementation details.

A production schema should make the permitted answers explicit.

---

# 37. Naive vs Improved Modeling

## Problem

Store orders like this:

```text
orders
------
id
customer_name
product_ids
product_names
quantities
```

### Why it fails

- product count becomes implicit,
- parallel arrays can become misaligned,
- product identity is duplicated,
- quantity has unclear grain,
- referential integrity is weak,
- line-level pricing becomes difficult,
- querying individual products becomes awkward,
- updates can produce inconsistent state.

### Improved approach

```text
customers
products
orders
order_lines
```

with explicit foreign keys and line-level attributes.

### Why it works

The data now mirrors the business grain:

```text
order
order line
product
customer
```

and PostgreSQL can enforce relationships.

### Production consideration

If order history needs immutable product information, intentionally snapshot the relevant fields on `order_lines` rather than rebuilding history from today's product record.

# 38. Wrong Implementation Patterns

## 38.1 “One huge table”

```text
customer_name
customer_phone
branch_name
product_name
supplier_name
order_date
payment_status
...
```

Problem:

- duplicated facts,
- null-heavy structure,
- update anomalies,
- unclear grain.

## 38.2 “Everything gets an ID”

An `id` column does not replace business identity.

You can have:

```text
id = 123
sku = ABC-100
```

and still need:

```sql
UNIQUE (sku)
```

## 38.3 “Application validates everything”

Application checks do not protect against every writer or race condition.

## 38.4 “Use JSON because the schema changes”

Schema evolution alone is not enough justification. Core relational facts often deserve relational structure even when requirements evolve.

## 38.5 “Use CASCADE everywhere”

Cascade semantics must reflect lifecycle semantics.

## 38.6 “Normalize until joins disappear”

The opposite goal is not better either.

A relational schema intentionally uses relationships.

---

# 39. AI / Vibe-Coding Failure Modes

AI-generated schemas frequently exhibit recognizable problems.

## Failure 1 — Tables derived from UI screens

A UI page is not automatically an entity.

```text
Dashboard table
Checkout page
Profile card
```

These are views/workflows, not necessarily business objects.

## Failure 2 — Blind `id` columns everywhere

The model loses business uniqueness.

## Failure 3 — Arrays for relationships

```sql
product_ids bigint[]
```

is often used instead of a join table.

## Failure 4 — JSONB for every optional field

This hides important constraints and makes core querying harder.

## Failure 5 — Missing foreign keys

AI-generated migration scripts often assume application code will maintain relationships.

## Failure 6 — Wrong NULL behavior

Everything is nullable because the generator wants to avoid insert errors.

## Failure 7 — Missing temporal reasoning

The schema stores current price/status but cannot reconstruct historical truth.

## Failure 8 — Tenant leakage

`tenant_id` exists on rows but relationships do not ensure that referenced entities belong to the same tenant.

## Failure 9 — Premature denormalization

AI often duplicates names, totals, or status fields before demonstrating a workload need.

### AI-review question

For every generated table ask:

> “What exact business fact does one row represent?”

Then ask:

> “Which rule prevents an invalid duplicate or invalid relationship?”

If the answer is unclear, the schema is not ready.

# 40. Production Modeling Heuristics

These are heuristics, not laws.

### Prefer explicit relationships over hidden structure

If an entity must be independently queried, constrained, referenced, or updated, consider modeling it explicitly.

### Prefer database-enforced invariants

Especially for:

- uniqueness,
- referential integrity,
- valid ranges,
- required values,
- non-overlap.

### Separate current state from historical state

Do not make a single mutable row pretend to be an audit trail.

### Encode units

Avoid ambiguous numbers.

### Treat tenant ownership as a relational concern

Do not merely filter by tenant in application queries and assume that is sufficient.

### Model cardinality explicitly

A foreign key without the right uniqueness/`NOT NULL` characteristics may encode the wrong relationship.

# 41. Evidence-Driven Schema Review

When reviewing a real schema, do not begin by criticizing naming.

Begin with evidence.

## Step 1 — Identify business invariants

Write them in plain language.

## Step 2 — Map each invariant to enforcement

```text
Invariant
   ↓
PK / FK / UNIQUE / CHECK / EXCLUDE / transaction / application
```

## Step 3 — Validate row grain

For each table complete:

> One row represents __________.

If the sentence cannot be completed precisely, investigate.

## Step 4 — Trace dependencies

For each important column:

> What determines this value?

## Step 5 — Inspect duplicate facts

Search for columns repeated across related entities.

## Step 6 — Test race conditions

Ask whether two concurrent transactions can both believe they satisfied an invariant.

## Step 7 — Validate historical questions

Ask:

> Can the database answer what the business will inevitably ask six months later?

---

# 42. Testing a Data Model

Schema tests should verify more than “migration succeeded.”

## Structural tests

Verify:

```text
PK exists
FK exists
UNIQUE exists
NOT NULL exists
CHECK exists
indexes exist where required
```

## Behavioral tests

Attempt invalid states:

```text
duplicate business identifier
orphan child
negative quantity
cross-tenant relationship
invalid lifecycle transition
```

The test should prove the database rejects the state.

## Concurrency tests

For important invariants:

```text
Transaction A → attempt state
Transaction B → attempt same state
```

Verify the invariant remains true.

# 43. Observability Implications

A good model helps debugging.

Include appropriate metadata where the domain benefits:

```text
created_at
updated_at
created_by
updated_by
source_system
external_id
version
```

But do not mechanically add every audit column to every table.

Ask:

> Which facts are operationally necessary to explain this record?

For integration-heavy systems, `external_id` plus `source_system` can become extremely valuable.

---

# 44. Security Implications

Model security boundaries explicitly.

Questions:

```text
Who owns this row?
Which tenant owns it?
Can users cross branches?
Can employees access records outside their organization?
Which relationships must never cross security boundaries?
```

Security bugs are often data-model bugs disguised as authorization bugs.

Example:

```text
request contains order_id only
```

Application fetches:

```sql
SELECT * FROM orders WHERE id = $1;
```

If authorization is later applied only in application code and one path forgets it, data may leak.

A stronger design can make ownership explicit and combine it with authorization mechanisms such as row-level security where appropriate.

---

# 45. Reliability and Migration Thinking

A production model must be evolvable.

Before adding a column ask:

```text
Is it nullable during rollout?
Can old application versions handle it?
Can new application versions handle old rows?
Will backfill lock or overload the table?
Does the column eventually become NOT NULL?
```

Schema design and migration design cannot be completely separated.

A theoretically perfect final schema can still be operationally dangerous if there is no safe path from the current schema to the new one.

---

# 46. Schema Naming Principles

Naming is not merely style. It affects long-term comprehension.

Prefer:

```text
customers
order_lines
created_at
customer_id
```

over ambiguous names like:

```text
cust
orderItems
created
customer
```

Be consistent about:

- singular/plural table names,
- `_id` for references,
- `_at` for timestamps,
- `_date` for dates,
- boolean naming,
- status conventions.

Consistency reduces cognitive load, but domain clarity beats aesthetic uniformity.

# 54. Final Mental Model

A strong relational schema is not a collection of tables.

It is a set of **legal states**.

Think of it as:

```text
Business reality
      ↓
Facts
      ↓
Entities + Relationships
      ↓
Row Grain
      ↓
Keys + Dependencies
      ↓
Constraints
      ↓
Legal Database States
      ↓
Queries + Transactions + Applications
```

The deepest lesson is this:

> **Good relational modeling does not merely describe valid data. It makes invalid data structurally difficult to create.**

The database should not be a passive storage container behind the application. It should be an active integrity boundary.

When you can look at a requirement and immediately reason about:

```text
facts
ownership
grain
identity
cardinality
optionality
dependencies
history
invariants
concurrency
security
migration
```

you have moved from “creating tables” to **database engineering**.
