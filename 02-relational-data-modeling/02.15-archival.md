# 02.15 — Archival

> **Phase 02 — Relational Data Modeling**  
> **Chapter 02.15 — Archival**

---

## 1. Why This Chapter Exists

A production database does not merely need to store data correctly. It needs a deliberate answer to a harder question:

> **What should happen to data that is no longer operationally hot, but still has business, legal, analytical, or historical value?**

That question is archival.

Archival is often confused with deletion, backups, partitioning, cold storage, or simply moving rows into an `archive_*` table. Those mechanisms can participate in an archival system, but none of them, by itself, defines an archival architecture.

A serious archival design answers all of these questions:

- What qualifies as archive-eligible?
- When does eligibility begin?
- Can the record still change after eligibility?
- What relationships must remain valid?
- Where does archived data live?
- How is the archive addressed and queried?
- How is completeness proven?
- How is corruption or accidental omission detected?
- Can archived data be restored to the operational model?
- What happens when schema changes after archival?
- Which users are allowed to read or restore it?
- How are tenant isolation and privacy preserved?
- How are retention and legal holds applied?
- How do we archive billions of rows without creating a production incident?

This chapter treats archival as a **data-placement, integrity, lifecycle, and recoverability architecture**.

PostgreSQL's partitioning documentation explicitly identifies migration of seldom-used data to cheaper or slower storage as a major use case, and documents `DETACH PARTITION` as a fast way to remove old data from an active partition tree while retaining the detached table for further processing or backup. citeturn870616search0

# 3. Precise Definition

## 3.1 Simple Definition

**Archival is the controlled movement or representation of data outside the primary operational access path while preserving its required meaning, integrity, and retrievability.**

## 3.2 Engineering Definition

An archive is a managed storage state for data that is no longer part of the normal hot workload but must remain available for one or more defined purposes.

Examples:

- historical reporting
- regulatory retention
- customer history
- dispute investigation
- accounting reconciliation
- fraud investigation
- audit evidence
- recovery from operational mistakes
- historical pricing reconstruction

## 3.3 Expert Definition

Archival is a **state transition in data placement** governed by explicit eligibility, immutability/change rules, retention requirements, integrity contracts, security policies, and restoration semantics.

This definition matters because the same row may simultaneously be:

- operationally cold,
- legally retained,
- analytically useful,
- security-sensitive,
- and impossible to delete.

Therefore:

> **Cold does not mean disposable.**

---

# 4. Archival vs Related Concepts

These concepts are related but not interchangeable.

| Concept | Primary Goal | Typical Location | Can it replace production data? |
|---|---|---|---|
| Backup | Recover from failure | Backup storage | No |
| Replication | Keep copies synchronized | Another database/system | No |
| Retention | Define how long data remains | Policy | No |
| Archive | Move cold data out of hot operational path | Cold/warm storage | Sometimes |
| Snapshot | Preserve point-in-time state | Snapshot/backup system | Usually no |
| Deletion | Remove data | None | Yes |
| Materialized view | Precompute query result | Database | No |
| Data warehouse | Analytical workload | Separate analytical system | No |

A backup protects against loss of the database.

An archive optimizes the lifecycle and placement of data.

A backup can contain the active database and therefore be unsuitable for operational historical queries. An archive is intentionally organized for long-term access, lifecycle management, and often lower-cost storage.

PostgreSQL's current backup documentation distinguishes SQL dumps, file-system-level backups, and continuous archiving/PITR as backup mechanisms. These solve recovery problems and should not be treated as a substitute for an archival model. citeturn870616search1

# 5. First Principles

Archival can be derived from five fundamental properties.

## 5.1 Data Temperature

Data has different access frequencies.

```text
Hot       → frequent reads/writes
Warm      → occasional reads
Cold      → rare reads
Frozen    → exceptional retrieval only
```

The database should not force every record to pay the same operational cost forever.

## 5.2 Business Value

A row may be cold but still valuable.

For example:

```text
Invoice from yesterday       → hot
Invoice from last year       → warm
Invoice from 8 years ago     → cold
Ledger evidence for audit    → potentially frozen
```

## 5.3 Mutability

Archive candidates become much easier to manage when they are immutable.

A key question is:

> **Can an archive-eligible record legally or operationally change?**

If yes, moving it introduces synchronization complexity.

If no, archival becomes substantially safer.

## 5.4 Integrity

Moving a row changes its physical location, but must not silently change its meaning.

If an invoice references a customer, product, tax rule, and payment history, moving the invoice requires understanding those relationships.

## 5.5 Recoverability

A successful archive is not merely data that disappeared from the hot database.

A successful archive is data that can still be:

- located,
- interpreted,
- validated,
- authorized,
- and retrieved.

# 6. The Mental Model: Archive as a State Transition

Think of archival as:

```text
        ACTIVE
           |
           | eligibility satisfied
           v
       ARCHIVE-READY
           |
           | validated transfer
           v
        ARCHIVED
           |
           | exceptional retrieval
           v
        RESTORED
```

A robust implementation may have additional states:

```text
ACTIVE
  ↓
CANDIDATE
  ↓
SNAPSHOT_CAPTURED
  ↓
TRANSFERRED
  ↓
VALIDATED
  ↓
SOURCE_REMOVAL_APPROVED
  ↓
ARCHIVED
```

The important insight is that **archiving is a workflow, not a `DELETE ... WHERE created_at < ...` statement**.

---

# 7. Archive Eligibility

Never start with the physical mechanism.

Start with the rule that makes a row eligible.

Examples:

```sql
WHERE closed_at < now() - interval '2 years'
```

But that may be incomplete.

A stronger rule might be:

```text
Order is archive eligible when:

- order status = 'completed'
- no refund is pending
- no dispute is open
- no legal hold applies
- all settlement events are finalized
- minimum operational retention period has elapsed
```

This is a **domain invariant**, not a storage optimization.

## 7.1 Eligibility Must Be Deterministic

Prefer rules that can be recomputed.

Bad:

```text
archive_candidate = true
```

without documenting how it became true.

Better:

```text
eligible because:
status = completed
AND completed_at < retention_cutoff
AND legal_hold = false
```

A deterministic rule enables reconciliation.

---

# 8. Retention Cutoff Design

Do not assume that `created_at` defines retention.

Different record types require different anchors:

```text
Customer data           → account closure date
Invoice                 → settlement completion date
Dispute                 → dispute resolution date
Audit record            → event occurrence date
Employment record       → employment termination date
Session/log             → event timestamp
```

For temporal correctness, explicitly identify:

```text
retention_anchor
retention_duration
retention_policy_version
archive_eligible_at
```

This makes archival decisions explainable.

---

# 9. Archive Architecture Patterns

There is no universally correct archive design.

## 9.1 Same Table, Partition by Time

```text
orders
├── orders_2026_09
├── orders_2026_08
├── orders_2026_07
└── orders_2024_01
```

Old partitions can be detached and moved through an archive workflow.

### Advantages

- same logical table
- partition pruning
- simple historical SQL
- efficient removal of whole time ranges

### Disadvantages

- partition-management complexity
- careful uniqueness design required
- still tied to PostgreSQL operational infrastructure

PostgreSQL documents `DETACH PARTITION` as a way to remove an old partition while keeping it as a standalone table for operations such as backup or aggregation; the concurrent detach variant reduces the parent-table lock level but has additional restrictions. citeturn870616search0

---

# 10. Separate Archive Tables

Example:

```sql
CREATE TABLE orders_archive (
    LIKE orders INCLUDING ALL
);
```

Then move rows explicitly.

```sql
INSERT INTO orders_archive
SELECT *
FROM orders
WHERE ...;
```

After successful validation:

```sql
DELETE FROM orders
WHERE ...;
```

### Advantage

Simple conceptual model.

### Major risk

The two statements are not automatically an archival protocol.

If validation is weak, you can create:

```text
source rows     → lost
archive rows    → incomplete
```

or:

```text
source rows     → duplicated
archive rows    → duplicated
```

---

# 11. Separate Database

```text
Operational PostgreSQL
        |
        | archive pipeline
        v
Archive PostgreSQL
```

Useful when:

- archive volume is large
- operational database should remain small
- archive queries are infrequent
- separate scaling is beneficial
- retention policy differs

But now you introduce distributed integrity concerns.

A foreign key cannot usually enforce integrity across two independent PostgreSQL databases.

Therefore the architecture must replace automatic database constraints with explicit transfer and validation protocols.

---

# 12. Object Storage Archive

For very cold data:

```text
PostgreSQL
   |
   | export
   v
Object Storage
   |
   +── manifest
   +── checksum
   +── schema version
   +── tenant metadata
   +── archive metadata
```

This can reduce database storage cost substantially.

But querying becomes more difficult.

Object storage may be appropriate when:

- reads are very rare
- bulk retrieval is acceptable
- regulatory evidence must be retained
- structured query requirements are low

It is usually a poor replacement for operational SQL access.

---

# 13. Hybrid Architecture

Production systems frequently benefit from multiple tiers.

```text
                   ┌─────────────────┐
                   │ Hot PostgreSQL  │
                   └────────┬────────┘
                            │
                       archive pipeline
                            │
             ┌──────────────┴──────────────┐
             │                             │
     Warm archive DB                Cold object storage
             │                             │
        occasional SQL               rare retrieval
```

The key is to define a **canonical representation** and clear ownership.

---

# 14. Source of Truth

This is one of the most important architectural decisions.

For each field, answer:

> **Where is the authoritative value stored?**

Possible answers:

```text
Operational DB
Archive DB
Ledger
Event log
External system
Object storage
```

Avoid this:

```text
orders.status        ← maybe source of truth
orders_archive.status ← maybe source of truth
analytics.status     ← maybe source of truth
```

After archival, the archive should generally become the authoritative historical representation for the archived domain—not a random copy that nobody trusts.

---

# 15. Referential Integrity During Archival

This is where naive archive scripts fail.

Suppose:

```text
customer
   |
   +── order
          |
          +── order_item
          +── payment
          +── shipment
```

If you archive `order`, can you safely remove its `order_item` and `payment` rows from the operational database?

Only if the archival boundary includes all required dependencies or if the remaining references are intentionally preserved.

## 15.1 Archive Closure

Define an archive set:

```text
A = orders eligible for archival

closure(A) = all records required to interpret A
```

A robust archive pipeline either:

1. archives the full closure, or
2. explicitly preserves dependencies in hot storage.

---

# 16. Parent/Child Archival Strategies

## Strategy A — Archive Children First

```text
order_items
payments
shipments
→ orders
```

Useful when foreign keys prevent parent removal.

## Strategy B — Archive Whole Aggregate

Move an entire business aggregate atomically from the perspective of the archival protocol.

Example:

```text
Order
├── items
├── payments
├── shipments
├── adjustments
└── audit/history
```

This is usually easier to reason about.

## Strategy C — Keep Reference Data Hot

Customer, product, branch, currency, and other relatively small reference tables may remain operational while transactional facts are archived.

This can be valid when the archive retains stable foreign-key identifiers and immutable historical attributes where needed.

---

# 17. Snapshotting Historical Context

A major archival problem is that reference data changes.

Suppose an invoice originally used:

```text
Tax rate = 18%
Product description = "Gold Necklace"
Customer name = "ABC Jewellers"
```

Five years later:

```text
Tax rate = 12%
Product renamed
Customer renamed
```

A historical report must not reconstruct the past using today's mutable reference rows unless that is explicitly intended.

Therefore archival may require **historical snapshots**.

Example:

```sql
CREATE TABLE invoice_archive (
    invoice_id bigint PRIMARY KEY,
    customer_id bigint NOT NULL,
    customer_name_at_issue text NOT NULL,
    tax_rate_at_issue numeric(6,3) NOT NULL,
    total_amount numeric(18,2) NOT NULL,
    issued_at timestamptz NOT NULL,
    archived_at timestamptz NOT NULL
);
```

This is denormalization with a semantic purpose: preserving historical truth.

---

# 18. Archive Manifest

Never rely solely on “the job finished successfully.”

Create an archive manifest.

Example:

```sql
CREATE TABLE archive_manifest (
    archive_batch_id uuid PRIMARY KEY,
    entity_name text NOT NULL,
    source_partition text,
    source_min_id bigint,
    source_max_id bigint,
    candidate_count bigint NOT NULL,
    archived_count bigint NOT NULL,
    validation_status text NOT NULL,
    checksum text,
    schema_version text NOT NULL,
    policy_version text NOT NULL,
    started_at timestamptz NOT NULL,
    completed_at timestamptz,
    created_by text NOT NULL
);
```

The manifest provides evidence that a specific batch was processed.

---

# 19. Why Counts Are Not Enough

A common mistake:

```text
source count = 1,000,000
archive count = 1,000,000
therefore success
```

Not necessarily.

The archive could contain 1,000,000 wrong rows.

Better validation can include:

- count
- minimum/maximum identifiers
- aggregate sums
- partition boundaries
- checksums
- business totals
- foreign-key closure checks
- sampled row comparisons

Example:

```sql
SELECT
    count(*) AS row_count,
    min(order_id) AS min_id,
    max(order_id) AS max_id,
    sum(total_amount) AS total_amount
FROM orders_archive
WHERE archive_batch_id = $1;
```

Compare with the source snapshot.

---

# 20. Checksums and Fingerprints

For higher assurance, derive deterministic fingerprints.

Conceptually:

```text
fingerprint = hash(canonical(row representation))
```

At scale, full cryptographic row-by-row hashing can be expensive. A layered strategy is often better:

```text
Layer 1 → count
Layer 2 → range
Layer 3 → aggregate business totals
Layer 4 → deterministic batch fingerprint
Layer 5 → sampled exact comparison
```

The correct level depends on risk.

---

# 21. Idempotency

An archival job will eventually be interrupted.

Possible failure points:

```text
export starts
export partially succeeds
worker crashes
network breaks
transaction aborts
process restarts
```

The job must be safe to retry.

Bad:

```text
INSERT rows
DELETE source rows
```

without identifying the archive batch.

Better:

```text
1. Assign batch ID
2. Identify immutable candidate set
3. Transfer with batch ID
4. Validate
5. Record completion
6. Remove source only after successful validation
7. Retry using the same deterministic identity
```

---

# 22. Exactly-Once Is Usually an Application Protocol

Do not casually claim that a distributed archival workflow is “exactly once.”

Across systems, you usually need:

```text
idempotent destination writes
+ deterministic batch identity
+ source removal guard
+ reconciliation
```

For example:

```sql
INSERT INTO orders_archive (...)
SELECT ...
FROM orders
WHERE order_id = ANY($1)
ON CONFLICT (order_id) DO NOTHING;
```

Then separately validate the archive before source removal.

The database can provide atomicity within its transaction boundary. It cannot magically make an external object store write and a database delete one atomic transaction.

---

# 23. Transaction Boundaries

A useful local transaction may be:

```text
BEGIN
  identify small candidate set
  lock or otherwise stabilize eligibility
  copy
  validate
  mark archive state
  delete source
COMMIT
```

But large archive batches can create undesirable:

- long-running transactions
- lock duration
- WAL pressure
- replication lag
- vacuum delay
- bloat
- transaction ID pressure

Therefore archive jobs should generally use controlled batches unless a partition-level operation is available and appropriate.

---

# 24. Batch Size

There is no universal “best” batch size.

Start with workload measurement.

Example progression:

```text
1,000 rows
5,000 rows
10,000 rows
50,000 rows
```

Measure:

- transaction duration
- WAL generated
- replication lag
- lock waits
- CPU
- I/O
- autovacuum activity
- application latency

Then tune.

> **Batch size is a workload parameter, not a constant of nature.**

---

# 25. `FOR UPDATE SKIP LOCKED`

For worker-based archival, a common pattern is:

```sql
SELECT order_id
FROM orders
WHERE archive_eligible_at <= now()
  AND archived_at IS NULL
ORDER BY order_id
FOR UPDATE SKIP LOCKED
LIMIT 1000;
```

This allows multiple workers to avoid waiting on rows already claimed by another worker.

But do not blindly use `SKIP LOCKED` everywhere.

It changes scheduling behavior and can allow starvation for persistently locked rows.

You still need:

- stable ordering
- retry handling
- observability
- stuck-row detection

---

# 26. Partition-Based Archival

When data naturally aligns with partitions, the cleanest architecture can be:

```text
hot parent
   |
   +── current partitions
   +── recent partitions
   +── old partition
          |
          | DETACH
          v
      standalone table
          |
          +── validate
          +── backup/export
          +── relocate
          +── retain
```

PostgreSQL specifically documents partition detach/drop as substantially faster than deleting millions of rows individually and notes that dropping or detaching avoids the `VACUUM` overhead associated with a bulk `DELETE`. citeturn870616search0

This is a critical reason to design partitioning with future lifecycle operations in mind.

---

# 27. `DETACH PARTITION` as an Archival Primitive

Conceptually:

```sql
ALTER TABLE events
DETACH PARTITION events_2024;
```

Now:

```text
events_2024
```

is a standalone table.

That is powerful because the table can then be:

- validated
- exported
- backed up
- copied elsewhere
- aggregated
- transformed
- dropped later

PostgreSQL also documents `DETACH PARTITION ... CONCURRENTLY` for reducing the parent-table lock strength, subject to its restrictions. citeturn870616search0

---

# 28. Archive and `VACUUM`

A huge `DELETE` is usually not equivalent to physically shrinking the table immediately.

A large row-by-row delete can create dead tuples and subsequent maintenance work.

Therefore:

```text
DELETE millions of rows
```

is often much more operationally expensive than:

```text
DETACH PARTITION
DROP/relocate partition
```

when the data model permits it.

This does not mean partitioning is always better. It means the data lifecycle should influence physical design.

---

# 29. Archive and WAL

Archival operations are writes.

A copy into another PostgreSQL table generates WAL.

A huge delete also generates WAL.

Therefore a naive archive cycle can produce:

```text
Archive copy
   ↓
large WAL volume
   ↓
replication pressure
   ↓
standby lag
   ↓
slower replicas
   ↓
application impact
```

This is why measuring WAL and replication behavior is essential.

Partition detach/drop changes the economics considerably because the operation can avoid rewriting millions of individual rows. citeturn870616search0

---

# 30. Archive and Replication

Ask which systems receive the archived writes.

Example:

```text
Primary
  |
  +── read replica
  +── reporting replica
  +── CDC pipeline
```

Copying millions of rows into an archive table may propagate through replication and CDC.

If the archive is outside the hot workload, this may be undesirable.

A mature design explicitly chooses whether archival should:

- replicate normally,
- bypass a particular analytical path,
- happen on a separate source,
- or use a dedicated export pipeline.

---

# 31. Archive and CDC

Change Data Capture systems introduce another concern.

Suppose:

```text
orders row inserted
→ CDC event
→ archived later
→ archive insert
→ another CDC event
→ archive consumer sees it as a business creation
```

That can be misleading.

Consumers should distinguish:

```text
business event
```

from:

```text
storage movement event
```

For example:

```json
{
  "event_type": "entity.archived",
  "entity": "order",
  "entity_id": 1234,
  "archive_batch_id": "..."
}
```

---

# 32. Schema Evolution

An archive can live for many years.

The operational schema may evolve:

```text
v1 → v2 → v3 → v4 → v5
```

Do not assume:

```text
archive schema = current schema
```

It may be useful to retain:

```text
source_schema_version
archive_schema_version
transformation_version
policy_version
```

---

# 33. Two Major Archive Strategies for Schema Evolution

## Strategy A — Preserve Original Shape

```text
orders_archive_v1
orders_archive_v2
orders_archive_v3
```

Advantages:

- high fidelity
- easier forensic reconstruction

Disadvantages:

- query complexity
- many versions

## Strategy B — Canonical Archive Model

Transform old records into a stable archival schema.

Advantages:

- easier historical querying
- fewer physical versions

Disadvantages:

- transformation risk
- possible information loss

The correct answer depends on whether the archive is a **forensic record** or a **normalized historical query model**.

---

# 34. Never Silently Destroy Information During Transformation

Suppose the old schema contains:

```text
customer_name
customer_email
customer_phone
```

and the canonical archive stores only:

```text
customer_id
```

You may have accidentally made historical reconstruction impossible.

Before transforming, identify:

```text
preserve
transform
derive
discard
```

Every discard should be explicit and justified.

---

# 35. Archive and Security

Archived data is often more sensitive than active data because it can contain years of history.

Security controls should cover:

- authentication
- authorization
- tenant isolation
- encryption
- object-storage access controls
- key management
- audit logging
- privileged restore operations
- export permissions

A common mistake is:

```text
production DB protected heavily
archive bucket broadly accessible
```

This defeats the architecture.

---

# 36. Multi-Tenant Archival

Tenant boundaries must remain explicit.

Example:

```sql
CREATE TABLE orders_archive (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    ...,
    PRIMARY KEY (tenant_id, order_id)
);
```

Archive jobs should be tenant-aware.

Avoid:

```sql
SELECT * FROM orders
WHERE created_at < cutoff;
```

when the operational model requires additional tenant or authorization invariants.

A safer conceptual model is:

```text
tenant scope
+ lifecycle scope
+ entity eligibility
```

---

# 37. Cross-Tenant Archive Queries

Operational staff may need global archive access.

But a global administrative query must not become a normal tenant user capability.

Separate:

```text
tenant reader
tenant admin
platform archive operator
compliance auditor
```

This also improves observability because privileged archive access becomes explicit.

---

# 38. Privacy and Data Subject Requests

Archival does not exempt data from privacy obligations.

You may need to answer:

```text
Is this person's data archived?
Where?
Which copies exist?
Can it be deleted?
Can it be anonymized?
Does legal retention override ordinary deletion?
```

Therefore maintain an inventory of archive locations.

For object storage, this may mean an archive manifest keyed by:

```text
entity_id
subject_id
tenant_id
archive_batch_id
object_uri
retention_until
legal_hold
```

---

# 39. Legal Hold

A legal hold should block destructive archival lifecycle steps when required.

Example:

```text
eligible for archive
        ↓
legal_hold = true
        ↓
archive allowed
source deletion blocked
```

This distinction matters:

> **Archive eligibility and deletion eligibility are not the same rule.**

---

# 40. Archive Restore

Every archive should answer:

> **How do we get the record back?**

Possible restore modes:

### Logical Restore

Copy selected rows back into the operational model.

### Temporary Access

Query archive directly without restoring.

### Full Dataset Restore

Rebuild a historical database or environment.

Different use cases require different restore paths.

---

# 41. Restore Is a First-Class Feature

A dangerous archive has this property:

```text
write archive = easy
read archive = difficult
restore archive = unknown
```

A production archive should have documented procedures for:

```text
locate
authorize
validate
restore
verify
record
```

---

# 42. Restore Into Current Schema

Historical data may not fit the latest operational schema.

For example:

```text
archive v2
     ↓ transform
current schema v8
```

This transformation may be lossy or ambiguous.

Therefore a restore pipeline should identify:

- original schema version
- transformation path
- defaults introduced
- fields removed
- fields renamed
- validation rules that did not exist historically

---

# 43. Archive and Generated Columns

If the current operational schema adds generated columns, the archive may store the source columns and recompute the generated representation during restore.

Do not blindly copy computed values unless their historical semantics are preserved.

The same reasoning applies to:

- materialized summaries
- denormalized counters
- derived status fields
- cached classifications

---

# 44. Archive and Constraints

An archive table often has different constraint requirements from the live model.

Example:

```text
live table
  strict current relationships

archive table
  historical representation
```

But “archive” should never mean “remove all integrity constraints.”

Retain the constraints that are meaningful for archived truth.

For example:

```text
PRIMARY KEY             → usually retain
NOT NULL                → usually retain
CHECK                   → retain where historical invariant remains valid
FOREIGN KEY             → depends on archive topology
UNIQUE                  → retain where semantically valid
```

A historical record that cannot satisfy current business rules may still be valid historically.

---

# 45. Historical Validity vs Current Validity

This is a subtle expert distinction.

Suppose an old invoice had a tax classification that is no longer accepted.

Current validation might reject it.

That does not mean the historical record is invalid.

Therefore restoration may require:

```text
historical validation
```

rather than:

```text
current business-rule validation
```

A mature archive distinguishes **historical truth** from **current admissibility**.

---

# 46. Archival in a Jewellery ERP

Consider a multi-branch jewellery ERP.

Entities may include:

```text
Tenant
Branch
Customer
Product
Inventory Movement
Sales Invoice
Purchase Invoice
Payment
Return
Repair Order
Stock Transfer
Pricing History
Ledger Entry
Audit Event
```

A plausible lifecycle:

```text
Current operational transactions
          ↓
completed + settled
          ↓
retention period elapsed
          ↓
archive candidate
          ↓
aggregate closure validated
          ↓
archive batch
          ↓
verification
          ↓
operational removal
```

But product master data may stay hot while historical transaction snapshots preserve:

- item description
- purity
- weight
- rate
- tax basis
- discount basis
- branch
- customer display information

This avoids trying to reconstruct 2019 business truth entirely from 2026 mutable reference data.

---

# 47. Naive Approach → Failure → Improved Approach

## Naive Approach

```sql
DELETE FROM orders
WHERE created_at < now() - interval '5 years';
```

### Why It Fails

- no archival copy
- no validation
- no legal-hold check
- may break dependencies
- creates dead tuples
- generates substantial WAL
- difficult to recover

## Improved Approach

```text
1. define eligibility
2. freeze/stabilize candidate set
3. transfer
4. validate
5. record manifest
6. confirm retention/legal rules
7. remove source safely
8. reconcile
```

### Why It Works

Each stage produces evidence.

### Production Considerations

Monitor:

- batch duration
- rows moved
- rows removed
- WAL
- replication lag
- lock wait
- failures
- retry count
- archive lag

### Alternative

Use time-based partitions and detach whole old partitions.

### Trade-Off

Higher upfront modeling complexity can produce much safer and cheaper long-term lifecycle operations.

# 49. State Tracking

One approach is to add lifecycle metadata:


But do not add lifecycle fields casually to every table.

# 51. Archive Lag

Define:

```text
archive_lag = now - oldest eligible record not yet archived
```

Track:

- row lag
- time lag
- byte lag
- tenant lag
- partition lag

A system may process millions of rows but still have one tenant whose archive is months behind.

# 52. Tenant Fairness

In multi-tenant systems, do not allow a giant tenant to monopolize archive workers.

```text

partition queue
per-tenant concurrency limit
```

# 53. Backpressure

Possible signals:


This gives the archive system an explicit relationship with operational health.

# 59. Why Indexes Matter for Archive Workers

Without a usable access path:

```text
archive worker
     ↓
full table scan
     ↓
repeat frequently
     ↓
high I/O
```

With a selective index:

```text
archive worker
     ↓
index range scan
     ↓
small candidate set
```

But an archival index itself has a write and storage cost.

Evaluate:

```text
query savings
vs
index maintenance cost
```

# 60. Partitioning as Lifecycle-Aware Modeling

Partitioning should not be chosen solely for query performance.

Also ask:

```text
Can one partition represent one retention boundary?
Can it be detached safely?
Can it be exported independently?
Can it be restored independently?
Can it map cleanly to archive batches?
```

PostgreSQL's documentation explicitly recommends considering data-removal patterns when designing partitioning so that data to be removed at once is located in a manageable partition. citeturn870616search0

# 61. Backup vs Archive One More Time

A strong mental model:

```text
BACKUP
  └── "Can I recover the system?"

ARCHIVE
  └── "Can I intentionally move cold data out of the operational path while preserving access and meaning?"
```

You often need both.

PostgreSQL's `pg_dump` can create archive-format dumps and `pg_restore` can selectively restore objects, making the tools useful for controlled export/transfer scenarios. The official documentation also cautions that `pg_dump` is generally not the right choice for routine production backups except in simple cases. citeturn870616search2

# 65. AI / Vibe-Coding Failure Modes

AI-generated archive implementations often fail in predictable ways.

## Failure 1 — “Just Delete Old Data”

No archive semantics.

## Failure 2 — `INSERT ... SELECT` Then `DELETE`

No verification barrier.

## Failure 3 — One Giant Transaction

Potential operational instability.

## Failure 4 — Counts Equal Success

Does not prove semantic equality.

## Failure 5 — Current Schema Assumed for Historical Data

Can silently misrepresent history.

## Failure 6 — No Idempotency

Retry can duplicate or delete the wrong rows.

## Failure 7 — Ignore Legal Hold

Can create irreversible policy violations.

## Failure 8 — Archive Has Weaker Tenant Security

Creates cross-tenant exposure.

## Failure 9 — No Restore Procedure

Archive becomes a write-only graveyard.

## Failure 10 — No Monitoring

The system can fail silently for months.

The remedy is always the same:

> **Define invariants first, then implement the archive mechanism.**

# 70. Expert Interview Questions

### Q1. Why is archival not the same thing as backup?

A backup optimizes for recovery from loss or corruption. Archival optimizes long-term controlled placement and access to cold historical data.

### Q2. Why can partitioning simplify archival?

Because lifecycle boundaries can align with physical partitions, allowing detach/drop operations instead of rewriting millions of individual rows. citeturn870616search0

### Q3. Why is `COUNT(*)` insufficient to validate an archive?

Equal counts do not prove that the same rows, values, relationships, or semantics were transferred.

### Q4. What is archive closure?

The complete set of records and historical context required to interpret the archived records correctly.

### Q5. Why is a giant archive transaction dangerous?

It can amplify lock duration, WAL, replication lag, vacuum pressure, resource consumption, and failure scope.

### Q6. Why should archive jobs be idempotent?

Because interruptions and retries are inevitable. Idempotency prevents retries from producing duplicate or ambiguous effects.

### Q7. What is the hardest archival problem?

Usually not moving bytes. It is preserving **historical meaning under changing schemas, relationships, policies, and security boundaries**.

# 73. Central Principle

> ## Archive for lifecycle efficiency without sacrificing historical truth.

A strong archival architecture is **policy-driven, integrity-aware, idempotent, observable, secure, schema-conscious, and restoreable**.

The best archive is not the one that moves the most rows.

It is the one that can confidently say:

> **This data no longer needs to burden the hot operational system, yet its historical meaning, integrity, security, and recoverability remain provable.**
