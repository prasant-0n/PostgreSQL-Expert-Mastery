# 02.6 — Denormalization

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to introducing intentional redundancy without losing correctness, explainability, rebuildability, or operational control.

---

## 1. Chapter Objective

Normalization gives us a strong default: store each fact at the correct grain, avoid unnecessary duplication, and represent dependencies explicitly.

But production systems are not evaluated only by how elegantly facts are decomposed. They are evaluated by:

- latency
- throughput
- write amplification
- read amplification
- operational complexity
- consistency guarantees
- availability
- reporting requirements
- workload shape
- storage cost
- migration cost
- failure behavior

Denormalization is the deliberate introduction of redundancy or precomputed state to optimize a known workload or satisfy a known architectural requirement.

The goal is **not** to make schemas less normalized merely because joins exist.

The goal is:

> **Start from a correct normalized model, identify a measured bottleneck or explicit workload requirement, introduce the smallest useful redundancy, define its consistency contract, and make the redundant state observable and rebuildable.**

---

# 2. Three Levels of Definition

## 2.1 Simple definition

Denormalization means storing information in more than one place when a fully normalized design would derive it through joins or computation.

Example:

```text
orders
------
id
customer_id
customer_name_snapshot
```

The customer's name may already exist in `customers`, so `customer_name_snapshot` is redundant by design.

## 2.2 Engineering definition

Denormalization is a schema or data-flow decision that intentionally duplicates, precomputes, materializes, or restructures facts to reduce read work, support a specific access pattern, or isolate workload characteristics.

## 2.3 Expert definition

Denormalization creates multiple representations of related information. Those representations form a consistency contract.

The engineering problem therefore changes from:

```text
How do we store this fact?
```

to:

```text
What is authoritative?
How is derived state produced?
When may it lag?
How is divergence detected?
How is it repaired?
How is it rebuilt from source truth?
```

A useful model is:

```text
Normalized Source of Truth
        ↓
Derived / Redundant Representation
        ↓
Read Optimization
        ↓
Consistency Contract
        ↓
Reconciliation + Rebuildability
        ↓
Operational Safety
```

---

# 3. First Principle: Redundancy Is Not Automatically Bad

Consider:

```text
orders
------
id
customer_id
```

and:

```text
customers
---------
id
name
```

The normalized query is:

```sql
SELECT o.id, c.name
FROM orders AS o
JOIN customers AS c
  ON c.id = o.customer_id;
```

That join is not evidence of a schema problem.

Relational systems exist partly so that facts can be stored once and combined logically when needed.

The right question is:

> **Does the workload justify maintaining another representation?**

Examples where redundancy may be justified:

- a high-volume dashboard repeatedly calculates the same aggregate
- a historical document must preserve the value shown at transaction time
- a service requires a read model shaped differently from the write model
- an aggregate is computationally expensive and changes infrequently
- an external integration needs a stable snapshot
- a search or reporting workload should not repeatedly traverse a transactional graph

---

# 4. The Core Rule: Name the Source of Truth

Every denormalized attribute should have an explicit authority.

Suppose:

```text
products
--------
id
current_price
```

and:

```text
order_items
-----------
order_id
product_id
unit_price
```

`unit_price` is a duplicate-looking value.

But it may not be denormalization in the problematic sense.

Why?

Because the business fact is different:

```text
products.current_price
= current price now

order_items.unit_price
= price agreed for this historical transaction
```

The two values have different meanings and different temporal grain.

Therefore:

> **Repeated values are not automatically redundant. A value is redundant only relative to an intended fact and grain.**

---

# 5. Types of Denormalization

Common forms include:

| Technique | Typical purpose |
|---|---|
| Duplicate scalar | Avoid repeated joins |
| Snapshot column | Preserve historical meaning |
| Cached counter | Avoid repeated `COUNT(*)` |
| Summary table | Accelerate reporting |
| Materialized view | Precompute complex query |
| Read model | Serve a specific application workload |
| Aggregate cache | Reduce expensive computation |
| Precomputed search document | Optimize search |
| Array / JSON embedding | Collapse frequently-read subordinate data |
| Partition-aligned representation | Improve workload isolation |
| External projection | Feed another system efficiently |

Each has a different consistency model.

---

# 6. Duplicate Scalar Values

Example:

```text
orders
------
customer_id
customer_name
```

This appears simple but creates a synchronization problem.

If:

```text
customers.name = 'Asha Sharma'
```

and:

```text
orders.customer_name = 'Asha Sharma'
```

then changing the customer's current name creates multiple possible states.

Possible designs:

### Source of truth only

```text
orders.customer_id
customers.name
```

### Intentional snapshot

```text
orders.customer_id
orders.customer_name_snapshot
```

The second is correct only when the business meaning is:

> “What customer name was recorded on this order?”

That is a temporal or transactional snapshot, not simply a performance optimization.

---

# 7. Cached Counters

Suppose:

```text
customers
---------
id
order_count
```

instead of:

```sql
SELECT count(*)
FROM orders
WHERE customer_id = $1;
```

This can make reads cheap, but the counter becomes derived state.

The invariant is:

```text
customers.order_count
= count(orders WHERE customer_id = customers.id)
```

Now every order insertion/deletion that affects the customer must preserve the invariant.

This is a concurrency problem as much as a performance problem.

Naive implementation:

```text
READ count
ADD 1
WRITE count
```

Two concurrent transactions can both observe the same value and lose an increment.

Safer atomic update:

```sql
UPDATE customers
SET order_count = order_count + 1
WHERE id = $1;
```

But even this requires the operation and related order mutation to have a clearly defined transaction contract.

---

# 8. Cached Counters Are Not Free

A cached aggregate introduces:

```text
Write Cost
+ Consistency Cost
+ Recovery Cost
+ Reconciliation Cost
+ Operational Complexity
```

Therefore compare:

```text
Option A
COUNT / aggregate on demand

vs

Option B
Maintain redundant state on every write
```

The better design depends on actual:

- read frequency
- row count
- index support
- write frequency
- contention
- latency SLO
- acceptable staleness

---

# 9. Summary Tables

A summary table is useful when a complex query is repeatedly executed.

Example:

```text
sales_daily_summary
-------------------
business_date
branch_id
gross_sales
net_sales
order_count
```

The source tables might contain millions of transaction rows.

Instead of scanning and aggregating the raw fact tables for every dashboard request, a summary can be queried directly.

But the summary now has a contract:

```text
summary = deterministic transformation(source facts)
```

Define:

- source relations
- aggregation grain
- refresh frequency
- correction strategy
- late-arriving data policy
- rebuild mechanism
- reconciliation query

---

# 10. Materialized Views

PostgreSQL supports materialized views for persisted query results.

Conceptually:

```sql
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT
    date_trunc('month', created_at) AS month,
    branch_id,
    sum(total) AS revenue
FROM orders
GROUP BY 1, 2;
```

The important distinction is:

```text
VIEW
→ stores query definition
→ computes on read

MATERIALIZED VIEW
→ stores query result
→ must be refreshed
```

A materialized view is therefore cached derived state.

It is not magically “always correct.” Its freshness is part of the design.

---

# 11. Read Models

A read model is a representation designed for a particular query workload.

Example transactional model:

```text
customers
orders
order_items
payments
shipments
```

Read model:

```text
customer_order_dashboard
------------------------
customer_id
customer_name
last_order_at
lifetime_order_count
lifetime_value
open_balance
last_payment_at
```

This is often useful for:

- dashboards
- operational search
- API response optimization
- reporting
- CQRS architectures

The read model should not become a second uncontrolled source of truth.

---

# 12. CQRS and Denormalization

Command Query Responsibility Segregation often permits different write and read models.

Conceptually:

```text
Commands
   ↓
Normalized transactional model
   ↓
Events / projection process
   ↓
Denormalized read model
   ↓
Queries
```

The advantage is not merely fewer joins.

It is the ability to shape data specifically around query requirements.

The cost is eventual consistency and operational complexity.

Therefore CQRS is not a synonym for:

```text
“joins are slow.”
```

It is an architectural choice with substantial trade-offs.

---

# 13. Naive Approach → Failure → Improved Approach

## Scenario: Dashboard customer totals

### Naive approach

Every request executes:

```sql
SELECT
    c.id,
    c.name,
    count(o.id),
    coalesce(sum(o.total), 0)
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.id
GROUP BY c.id, c.name;
```

At small scale this may be perfectly acceptable.

### Why it fails

Only after measurement might you discover:

- huge order volume
- high request frequency
- repeated aggregation
- dashboard SLO violations
- CPU pressure

### Improved approach

Maintain or periodically build:

```text
customer_sales_summary
```

### Why it works

The expensive aggregation is moved from request-time to controlled refresh/update work.

### Production considerations

Define:

- freshness SLA
- rebuild procedure
- reconciliation query
- correction process
- monitoring
- failure semantics

### Alternative

Use a materialized view.

### Trade-off

Choose among:

```text
On-demand aggregate
vs
Materialized view
vs
Incrementally maintained summary
vs
Dedicated analytical system
```

based on workload evidence.

# 14. Denormalization and Historical Snapshots

One of the safest forms of “duplication” is preserving historical meaning.

Example:

```text
order_items
-----------
product_id
product_name_snapshot
unit_price
```

Why preserve these?

Because the transaction may need to answer:

> What did the customer purchase and at what displayed price at the time of the transaction?

The current product record may later change.

This is not an optimization for joins.

It is a business-history requirement.

The distinction matters because history should not be accidentally overwritten by synchronization jobs.

---

# 15. Denormalized State Must Have a Consistency Contract

Common contracts:

## Strongly consistent

The redundant representation must be updated in the same transaction.

Example:

```text
order + customer.cached_order_count
```

## Transactionally consistent within one transaction

Multiple rows are modified atomically, but readers outside the transaction see the previous or new state.

## Eventually consistent

The source changes first; projection updates later.

Examples:

```text
source event
   ↓
queue
   ↓
projection worker
   ↓
read model
```

## Best-effort cache

The derived representation may be wrong or absent temporarily and can simply be rebuilt.

The system must document which category applies.

---

# 16. Do Not Confuse Cache With Source of Truth

Bad architecture:

```text
orders
cached_orders
maybe authoritative?
```

and developers are unsure which one wins.

Good architecture:

```text
orders = authoritative
cached_orders = rebuildable projection
```

This gives a clear recovery path.

Expert principle:

> **A redundant representation is safe only when its authority and repair path are explicit.**

---

# 17. Rebuildability

For every derived table ask:

> Can we delete it and recreate it from authoritative data?

Ideal:

```text
DELETE projection
REBUILD projection FROM source
```

If the answer is “no,” the system may have accidentally made the denormalized copy part of the source of truth.

That can make corruption much harder to repair.

---

# 18. Reconciliation

Every important derived structure should have an invariant query.

Example:

```sql
SELECT
    c.id,
    c.order_count,
    actual.order_count AS expected_order_count
FROM customers c
JOIN (
    SELECT customer_id, count(*) AS order_count
    FROM orders
    GROUP BY customer_id
) actual
  ON actual.customer_id = c.id
WHERE c.order_count <> actual.order_count;
```

The exact query depends on the model.

What matters is that divergence is detectable.

Observability should answer:

```text
Is the projection current?
Is it complete?
Is it internally consistent?
How far behind is it?
Can it be rebuilt?
```

---

# 19. Denormalization and Concurrency

Suppose:

```text
customer.order_count
```

is derived from orders.

Two transactions concurrently create orders.

A design based on:

```text
SELECT order_count
→ increment in application memory
→ UPDATE absolute value
```

can lose updates.

Prefer database-side atomic operations where appropriate:

```sql
UPDATE customers
SET order_count = order_count + 1
WHERE id = $1;
```

Then define the transaction boundary carefully.

Do not assume that an atomic counter update alone guarantees perfect synchronization if related write paths can bypass it.

---

# 20. Write Path Discipline

A denormalized model is most reliable when there is one controlled write path.

Bad:

```text
HTTP API
→ updates summary

Admin script
→ updates source only

ETL
→ updates source differently

Background worker
→ updates summary again
```

This creates multiple invariant-maintenance paths.

Better:

```text
Authoritative mutation
        ↓
One defined projection mechanism
        ↓
Derived state
```

Alternative architectures may use:

- database triggers
- transactional application code
- outbox events
- logical replication
- CDC
- scheduled refresh

Each has distinct guarantees.

---

# 21. Database Trigger vs Application Maintenance

## Trigger

Pros:

- mutation cannot easily forget the projection
- database sees every qualifying write path
- strong transaction coupling is possible

Cons:

- hidden write behavior
- harder application reasoning
- debugging complexity
- bulk operation surprises

## Application code

Pros:

- explicit
- easier domain visibility
- easier testing at service level

Cons:

- alternative write paths may bypass logic
- migrations/scripts can accidentally violate invariants

## Choice

Choose based on where the invariant belongs.

> If correctness depends on every SQL write path, database enforcement may be safer. If the derived state is an architectural projection, explicit application/event processing may be clearer.

---

# 22. Arrays and JSONB as Denormalization

Arrays and JSONB can collapse related information into a single row.

Example:

```text
products
--------
id
category_ids bigint[]
```

or:

```text
products
--------
attributes jsonb
```

This can reduce joins for specific read patterns.

But it can also remove relational guarantees:

- foreign-key enforcement becomes harder
- updates become less granular
- indexing choices change
- cardinality becomes hidden
- concurrent updates can become more complicated

Use collection-valued columns because their semantics fit the domain—not merely to avoid a join.

---

# 23. Denormalization vs Indexing

A common mistake is to denormalize before testing whether an index solves the problem.

Suppose:

```sql
SELECT *
FROM orders
WHERE customer_id = $1
ORDER BY created_at DESC
LIMIT 20;
```

Before duplicating customer information or creating a summary, investigate an appropriate index such as:

```sql
CREATE INDEX ON orders (customer_id, created_at DESC);
```

The broader decision tree is:

```text
Slow query
   ↓
Check correctness
   ↓
EXPLAIN (ANALYZE, BUFFERS)
   ↓
Statistics / selectivity
   ↓
Index opportunity?
   ↓
Query rewrite?
   ↓
Only then consider denormalization
```

Denormalization is an architectural tool, not the first response to every slow query.

---

# 24. Query Shape Matters

Two schemas with the same logical facts can have very different read costs because workloads differ.

Example:

```text
Workload A
small result set
highly selective lookups
```

may favor normalized tables and indexes.

Whereas:

```text
Workload B
large repeated reporting aggregates
high query concurrency
```

may benefit from summaries.

Therefore:

> **Optimize for the actual access pattern, not the abstract existence of a join.**

---

# 25. Denormalization and Storage Cost

Every duplicate value costs storage.

But storage cost is not limited to table bytes.

Consider:

```text
extra column
→ larger heap tuple
→ more WAL
→ larger indexes if indexed
→ more vacuum work
→ more replication traffic
→ more backup volume
→ more cache pressure
```

The total system cost may therefore be much larger than the raw duplicated bytes.

---

# 26. Denormalization and Write Amplification

Suppose one source mutation updates:

```text
orders
customer_summary
branch_summary
dashboard_projection
search_document
```

One logical business event can now create many physical writes.

This is write amplification.

The optimization may still be worthwhile, but the workload must justify it.

A useful conceptual equation is:

```text
Total Cost
≈ Read Cost Saved
− Write Cost Added
− Consistency Cost
− Operational Cost
```

This is not a literal database formula. It is a design discipline.

---

# 27. Denormalization and Lock Contention

A popular counter can become a hotspot.

Example:

```text
global_stats.total_orders
```

If thousands of concurrent transactions update the same row:

```sql
UPDATE global_stats
SET total_orders = total_orders + 1;
```

the atomicity is correct, but contention can increase.

Possible alternatives:

- shard counters
- batch aggregation
- asynchronous aggregation
- periodic summary rebuild
- analytical storage

Therefore:

> Correctness does not imply scalability.

---

# 28. Sharded / Bucketed Counters

Instead of one hot counter:

```text
stats
-----
total_orders
```

use buckets:

```text
stats_buckets
-------------
bucket_id
total_orders
```

Writers update a chosen bucket.

Reads sum the buckets.

The model trades:

```text
more read aggregation
for
less write contention
```

The appropriate bucket count depends on workload.

---

# 29. Soft Deletes and Denormalization

Suppose:

```text
users.deleted_at
```

and a cached summary counts active users.

Now every deletion state transition changes derived data.

The invariant becomes:

```text
active_count
= count(users WHERE deleted_at IS NULL)
```

Soft deletes can therefore increase synchronization complexity across the entire schema.

Do not treat soft deletion as a harmless boolean-style flag.

---

# 30. Multi-Tenant Denormalization

In a SaaS system:

```text
tenant_id
```

must remain part of the derived-state model where tenant scope matters.

Bad:

```text
global_customer_summary
```

when business logic is tenant-specific.

Better:

```text
customer_summary
----------------
tenant_id
customer_id
order_count
revenue
```

Then uniqueness and indexing should reflect tenant scope.

For example:

```sql
PRIMARY KEY (tenant_id, customer_id)
```

The projection must preserve the same security boundary as the source data.

---

# 31. Security Considerations

Denormalized data can accidentally bypass security boundaries.

Example:

```text
source tables
→ tenant-filtered by RLS

projection table
→ missing RLS
```

A read model can become a data-leak path even if the source schema is secure.

Every derived relation should answer:

- Does it contain sensitive data?
- Is tenant scope preserved?
- Does it require RLS?
- Can users query it directly?
- Does it expose values that source-level authorization would have hidden?

Security must be designed across the entire representation graph.

---

# 32. Privacy and Data Erasure

Denormalization makes deletion harder.

Suppose customer PII exists in:

```text
customers
orders snapshots
customer_summary
search_documents
analytics tables
materialized views
exports
```

Deleting the source row does not automatically erase every copy.

Therefore denormalized systems must model:

```text
Data Lineage
→ Replication / Projection Paths
→ Retention
→ Erasure
→ Rebuild
→ Backup Expiration
```

Privacy requirements can make some denormalization choices unacceptable.

---

# 33. Search Documents as Denormalized State

A search document may combine:

```text
product
brand
category
attributes
availability
```

into one indexed representation.

This is a deliberate projection.

The correct architecture is usually:

```text
normalized source
       ↓
search projection
       ↓
search index
```

The search representation should be disposable and rebuildable.

Do not make the search index the only copy of business truth.

---

# 34. Eventual Consistency and User Experience

Suppose:

```text
Order created
   ↓
source transaction committed
   ↓
projection worker pending
```

A dashboard may temporarily show:

```text
Orders: 100
```

while the source already contains:

```text
Orders: 101
```

This is acceptable only when the product contract allows it.

Therefore define explicit UX semantics:

```text
“Updated within 30 seconds”
```

is much safer than silently presenting stale data as authoritative.

---

# 35. Backfill Strategy

Introducing denormalization to an existing table usually requires a backfill.

Example:

```text
orders.customer_name_snapshot
```

Potential rollout:

```text
1. Add nullable column
2. Deploy code that understands both states
3. Backfill existing rows
4. Verify consistency
5. Start enforcing new invariant where appropriate
```

Never assume a huge backfill is a harmless one-shot UPDATE.

Consider:

- lock duration
- WAL volume
- replication lag
- vacuum pressure
- transaction size
- failure recovery
- resumability

---

# 36. Chunked Backfills

Instead of one enormous transaction:

```sql
UPDATE orders
SET customer_name_snapshot = ...;
```

consider controlled batches.

A batch-oriented design should be:

- resumable
- observable
- bounded
- idempotent
- safe under concurrent writes

The exact batching mechanism should respect the table's primary-key distribution and workload.

---

# 37. Concurrent Writes During Backfill

Suppose the backfill reads:

```text
customer.name
```

while the application concurrently changes the customer name.

Which value should the snapshot contain?

The answer depends on semantics.

For a transaction-history snapshot:

```text
existing orders = original transactional value
```

For a current-state cache:

```text
projection should eventually converge to current value
```

Therefore backfill logic must follow the business meaning of the derived value.

---

# 38. Migration Safety Pattern

A production migration often follows:

```text
Expand
  ↓
Deploy compatibility code
  ↓
Backfill
  ↓
Validate
  ↓
Switch reads
  ↓
Observe
  ↓
Remove legacy path later
```

Do not combine schema change, massive backfill, application rollout, and legacy deletion into one irreversible operation unless the workload is tiny and controlled.

---

# 39. AI / Vibe-Coding Failure Modes

AI-generated schema advice commonly produces patterns such as:

### Failure 1 — “Joins are slow, denormalize everything.”

Why it fails:

- ignores indexes
- ignores selectivity
- ignores planner behavior
- creates synchronization problems

### Failure 2 — Cached count without concurrency reasoning

The model proposes:

```text
count = count + 1
```

inside application memory.

Why it fails:

Concurrent writers can lose updates.

### Failure 3 — No source of truth

Generated systems sometimes duplicate fields without defining which copy wins.

### Failure 4 — No rebuild path

A projection is treated as permanent business data.

### Failure 5 — Security boundary omission

A tenant-filtered source becomes a global projection.

### Failure 6 — Historical snapshots synchronized incorrectly

A job “fixes” old transaction data by replacing historical values with current master data.

Expert review question:

> **What invariant is this duplicate preserving, and what happens when the two copies diverge?**

# 40. Performance Investigation Workflow

Never begin with:

```text
“Let's denormalize.”
```

Begin with evidence.

```text
1. Identify the slow workload
2. Define latency / throughput target
3. Capture representative query
4. EXPLAIN (ANALYZE, BUFFERS)
5. Check indexes
6. Check cardinality / statistics
7. Check join order and row estimates
8. Check I/O vs CPU
9. Check cache behavior
10. Check concurrency / contention
11. Test query rewrite
12. Prototype denormalization only if justified
13. Benchmark both designs
14. Compare operational costs
```

### Question 6

### Question 7
What is the source of truth?

### Question 8

What happens on missed updates?

### Question 10

### Question 11

### Question 12

# 44. Testing Strategy

A mature denormalized system tests more than successful writes.

Test:

### Invariant correctness

```text
projection == expected(source)
```

### Concurrent mutation

Multiple transactions modify source data simultaneously.

### Failure injection

Projection update fails after source commit.

### Retry

Projection processing executes twice.

### Reordering

Events arrive out of order.

### Backfill

Old data is migrated without corrupting new writes.

### Rebuild

Projection is deleted and recreated.

### Security

One tenant cannot observe another tenant's projection.

### Erasure

Sensitive source data is removed according to retention/privacy requirements.

---

# 45. Idempotency

Projection operations should often be idempotent.

Suppose an event says:

```text
order 100 updated
```

Processing it twice should not produce:

```text
revenue += total
revenue += total
```

unless the event itself represents two distinct business facts.

Prefer projection logic that can safely converge to a target state when possible.

For example:

```sql
INSERT INTO customer_summary (...)
VALUES (...)
ON CONFLICT (...) DO UPDATE
SET order_count = EXCLUDED.order_count,
    lifetime_value = EXCLUDED.lifetime_value;
```

This can be safer than blindly incrementing counters when the projection event represents a state rather than an increment.

---

# 46. Incremental vs Full Rebuild

Two major strategies exist.

## Incremental

```text
source change
→ update projection
```

Pros:

- low read-time cost
- low rebuild latency

Cons:

- complex consistency logic
- harder failure recovery

## Full rebuild

```text
source
→ recompute entire projection
```

Pros:

- conceptually simple
- strong recovery model

Cons:

- expensive for large datasets
- can create operational load

## Hybrid

Common production pattern:

```text
incremental maintenance
+
periodic reconciliation
+
full rebuild capability
```

---

# 47. Source-Driven vs Event-Driven Projection

### Source-driven refresh

```text
SELECT from authoritative tables
→ recompute projection
```

Strong rebuildability.

### Event-driven

```text
business event
→ projection update
```

Lower incremental work but requires reliable event delivery and idempotency.

### Outbox pattern

A transactional outbox can bridge source mutation and event publication:

```text
business transaction
    ↓
source row
outbox row
    ↓ commit
worker publishes / processes
    ↓
projection
```

The important principle is not the pattern name.

It is:

> **Do not let source state and projection-triggering intent diverge without a recovery mechanism.**

---

# 48. When NOT to Denormalize

Do not denormalize merely because:

- joins look complicated
- the ORM emits joins
- another developer says “NoSQL is faster”
- the schema has several foreign keys
- a tutorial recommends duplication
- AI generated duplicate fields
- a query feels verbose

Avoid it when:

```text
workload is small
OR
query is already fast
OR
indexing solves the issue
OR
freshness requirements are strict
OR
redundancy would create unacceptable write complexity
OR
rebuildability is unclear
OR
security/privacy becomes harder than the benefit justifies
```

---

# 49. Expert Mental Model

Think of denormalization as a second-order design problem.

Normalization asks:

```text
Where does the fact belong?
```

Denormalization asks:

```text
Where should an additional representation live?
Why?
Who owns it?
How fresh must it be?
What happens when it fails?
How do we prove it is correct?
How do we rebuild it?
```

That is why denormalization is fundamentally about **consistency architecture**, not merely schema shape.

# 54. Final Principle

The most important lesson is simple:

> **Denormalization is not permission to duplicate facts casually. It is a deliberate decision to maintain another representation because the total system benefit justifies the additional consistency and operational complexity.**

A strong PostgreSQL engineer does not ask:

> “Should databases be normalized?”

They ask:

> **“What workload are we optimizing, what invariant are we preserving, what state is authoritative, what can become stale, how will we detect divergence, and how will we recover?”**

That is production-grade denormalization.
