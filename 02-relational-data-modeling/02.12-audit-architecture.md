# 02.12 — Audit Architecture

> Auditability is the ability to reconstruct what changed, when it changed, who or what initiated it, what the previous state was, what the resulting state was, and why the change was allowed. A production audit system is not merely a pair of `created_at` / `updated_at` columns; it is an evidence architecture.

---

## 1. Chapter Objective

This chapter develops a production-grade mental model for database auditing in PostgreSQL.

By the end, you should be able to design an audit system that can answer:

- What record changed?
- Which fields changed?
- What was the old value?
- What is the new value?
- When did the database observe the change?
- Which authenticated human or service initiated it?
- Which application request, job, or workflow caused it?
- Which tenant, branch, or business context was active?
- Was the change committed or rolled back?
- Can the history be reconstructed after many changes?
- Can the audit trail itself be altered by an ordinary application role?
- Can compliance, security, support, and debugging teams query it efficiently?
- Can the audit volume scale without making the OLTP workload unusable?

The central design question is:

> **What evidence must exist so that a future investigator can reconstruct a business-important state transition without trusting the application's memory of what happened?**

---

# 2. Three Levels of Understanding

## 2.1 Simple definition

An audit trail records important changes to data so that the system can later explain what happened.

## 2.2 Engineering definition

An audit architecture records data mutations together with sufficient actor, time, context, and change information to reconstruct relevant state transitions and support operational, security, and compliance investigations.

## 2.3 Expert definition

An audit architecture is a set of database, application, identity, transaction, storage, access-control, retention, and observability mechanisms that establish a trustworthy evidence boundary around state transitions.

That last definition matters because an audit row without trustworthy identity, transaction semantics, retention guarantees, or access controls can create the appearance of accountability without providing reliable evidence.

---

# 3. Why Auditing Is Harder Than `created_at` and `updated_at`

Consider:

```sql
CREATE TABLE orders (
  id bigint PRIMARY KEY,
  status text NOT NULL,
  total numeric(18,2) NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

This tells you roughly when the row was last updated.

It does **not** tell you:

- who changed it,
- what it was before,
- which fields changed,
- why it changed,
- which request caused it,
- whether the caller was a human or automated process,
- whether a previous value was overwritten multiple times,
- what happened during the transaction before commit,
- whether the update came from SQL, a scheduled job, a migration, or an administrative action.

A timestamp answers only one small part of the audit question.

---

# 4. The Audit Information Model

A strong audit event commonly contains some combination of these dimensions:

| Dimension | Question |
|---|---|
| Subject | What business object changed? |
| Operation | INSERT, UPDATE, DELETE, or domain event? |
| Before | What state existed before? |
| After | What state exists after? |
| Changed fields | Which attributes actually changed? |
| Database time | When did PostgreSQL observe the mutation? |
| Application time | When did the application initiate the operation? |
| Actor | Which authenticated identity initiated it? |
| DB principal | Which PostgreSQL role executed it? |
| Request | Which HTTP/RPC/job request caused it? |
| Correlation | Which distributed trace/workflow does it belong to? |
| Tenant | Which tenant or organization owns the change? |
| Source | API, worker, migration, admin SQL, import, etc. |
| Reason | Business justification, command, or change reason |
| Transaction | Which transaction context contains it? |
| Outcome | Was the transaction committed or rolled back? |
| Integrity | Can the evidence be trusted and protected? |

Do not blindly store every field everywhere. Model the evidence that supports actual investigations.

---

# 5. Audit Is Not One Problem

There are several different requirements commonly called “audit”. They should not automatically be implemented using one mechanism.

## 5.1 Row history

Question:

> What versions did this row have over time?

Example:

```text
price = 6800
price = 6950
price = 7100
```

This is data history.

## 5.2 User accountability

Question:

> Which authenticated user initiated the change?

This requires identity propagation.

## 5.3 Security audit

Question:

> Which privileged operation was performed, and by whom?

This may require broader database/server logging than row-level history.

## 5.4 Compliance audit

Question:

> Can the organization demonstrate a controlled and reviewable history over a required retention period?

This introduces retention, access control, evidence integrity, and operational process.

## 5.5 Debugging/auditability

Question:

> Why did this value unexpectedly become X?

This often needs request IDs, application context, row history, and logs together.

## 5.6 Domain event history

Question:

> What business facts occurred?

For example:

```text
ORDER_CREATED
ORDER_APPROVED
PAYMENT_CAPTURED
ORDER_CANCELLED
```

Domain events and row-level audit records overlap but are not identical.

---

# 6. First Principle: Define the Evidence Contract

Before writing a trigger, define what a future investigation must reconstruct.

Example:

```text
For every manual order-status change:

1. order ID
2. old status
3. new status
4. user identity
5. tenant
6. timestamp
7. request ID
8. reason
9. database transaction outcome
```

Now the schema follows the evidence contract instead of becoming an arbitrary dump of row data.

---

# 7. Snapshot Audit vs Diff Audit

There are two major representations.

## 7.1 Full snapshot

Store the entire previous and/or next row.

```json
{
  "id": 1001,
  "status": "approved",
  "total": 125000,
  "customer_id": 88
}
```

### Advantages

- easy reconstruction,
- easy forensic inspection,
- schema is conceptually straightforward,
- captures context that may otherwise disappear.

### Costs

- more storage,
- repeated unchanged fields,
- sensitive data gets duplicated,
- schema changes become more complicated,
- large JSON snapshots may become expensive.

## 7.2 Diff audit

Store only changed attributes.

```json
{
  "status": {
    "old": "pending",
    "new": "approved"
  }
}
```

### Advantages

- smaller for sparse updates,
- directly answers “what changed?”.

### Costs

- harder complete reconstruction,
- complicated data-type representation,
- schema evolution must be handled carefully,
- diff semantics can become application-specific.

Neither approach is universally correct.

# 8. A Practical Audit Table

A generic baseline:

```sql
CREATE TABLE audit_log (
  audit_id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  occurred_at     timestamptz NOT NULL DEFAULT clock_timestamp(),
  operation       text NOT NULL,
  table_schema    text NOT NULL,
  table_name      text NOT NULL,
  row_id          text,
  actor_id        text,
  db_role         name NOT NULL DEFAULT current_user,
  session_role    name NOT NULL DEFAULT session_user,
  request_id      text,
  trace_id        text,
  tenant_id       text,
  source          text,
  reason          text,
  old_row         jsonb,
  new_row         jsonb,
  changed_fields  jsonb
);
```

This is a teaching model, not a universal production schema.

The most important architectural lesson is that **audit identity and business identity are separate concerns**.

---

# 9. `current_user` vs `session_user`

PostgreSQL distinguishes the authenticated session identity from the effective execution identity.

`session_user` normally represents the user who initiated the database connection.

`current_user` represents the role currently applicable for permission checking and can change through role switching or `SECURITY DEFINER` execution. PostgreSQL documents this distinction explicitly. citeturn181864search0

Therefore an audit design should consciously decide whether it wants:

```sql
session_user
```

or

```sql
current_user
```

or **both**.

For privileged functions, storing only `current_user` can obscure which session identity initiated an operation.

A useful baseline is:

```sql
SELECT
  session_user,
  current_user;
```

---

# 10. Application Identity Is Different From Database Identity

A common production stack is:

```text
Human User
   ↓
JWT / Session
   ↓
NestJS API
   ↓
Connection Pool
   ↓
PostgreSQL Role
```

Suppose every request uses the same database role:

```text
app_user
```

Then PostgreSQL sees:

```text
current_user = app_user
```

That is not enough to identify the business user.

You therefore need explicit request context.

Typical options include transaction-local settings:

```sql
SET LOCAL app.user_id = 'user-123';
SET LOCAL app.request_id = 'req-456';
SET LOCAL app.tenant_id = 'tenant-9';
```

Then an audit trigger can read the values.

The important design requirement is **transaction scoping**. Session-level mutable context on pooled connections can leak between requests if connection lifecycle is mishandled.

---

# 11. Safe Context Propagation With `SET LOCAL`

Example transaction:

```sql
BEGIN;

SET LOCAL app.user_id = 'u-42';
SET LOCAL app.request_id = 'req-8f9c';
SET LOCAL app.tenant_id = 'tenant-7';

UPDATE orders
SET status = 'approved'
WHERE id = 1001;

COMMIT;
```

`SET LOCAL` limits the setting to the current transaction.

This is generally safer with connection pools than ordinary session-level mutation because the context naturally ends with the transaction.

Still, the application must ensure the transaction boundaries are correct.

---

# 12. Application Context Is Metadata, Not Authentication

Never confuse:

```sql
SET LOCAL app.user_id = 'u-42';
```

with cryptographic proof that the caller really is user 42.

The database receives whatever the trusted application connection tells it.

Therefore the trust chain is:

```text
Authentication system
        ↓
Application authorization
        ↓
Trusted DB context
        ↓
Audit record
```

For stronger isolation, use distinct database roles, carefully controlled functions, or additional infrastructure so untrusted callers cannot arbitrarily impersonate audit identities.

---

# 13. Trigger-Based Row Auditing

PostgreSQL triggers can automatically execute functions in response to table operations. Row-level triggers receive `NEW` and/or `OLD` records, making them suitable for generic change capture. PostgreSQL also supports statement-level triggers and transition tables. citeturn181864search2

Basic pattern:

```sql
CREATE OR REPLACE FUNCTION audit_row_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    INSERT INTO audit_log (
      operation,
      table_schema,
      table_name,
      row_id,
      new_row
    )
    VALUES (
      TG_OP,
      TG_TABLE_SCHEMA,
      TG_TABLE_NAME,
      NEW.id::text,
      to_jsonb(NEW)
    );

    RETURN NEW;

  ELSIF TG_OP = 'UPDATE' THEN
    INSERT INTO audit_log (
      operation,
      table_schema,
      table_name,
      row_id,
      old_row,
      new_row
    )
    VALUES (
      TG_OP,
      TG_TABLE_SCHEMA,
      TG_TABLE_NAME,
      NEW.id::text,
      to_jsonb(OLD),
      to_jsonb(NEW)
    );

    RETURN NEW;

  ELSIF TG_OP = 'DELETE' THEN
    INSERT INTO audit_log (
      operation,
      table_schema,
      table_name,
      row_id,
      old_row
    )
    VALUES (
      TG_OP,
      TG_TABLE_SCHEMA,
      TG_TABLE_NAME,
      OLD.id::text,
      to_jsonb(OLD)
    );

    RETURN OLD;
  END IF;

  RETURN NULL;
END;
$$;
```

Then:

```sql
CREATE TRIGGER orders_audit
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
EXECUTE FUNCTION audit_row_change();
```

---

# 14. Why `AFTER` Often Makes Sense

For an audit record intended to represent the resulting mutation, an `AFTER` trigger is often conceptually easier:

```text
SQL statement
   ↓
row mutation
   ↓
AFTER trigger
   ↓
audit record
```

PostgreSQL documents that an `AFTER` row-level trigger sees the outer statement's completed data changes. citeturn181864search8

However, `AFTER` does **not** mean “permanently committed”. The trigger runs inside the transaction.

That distinction is fundamental.

---

# 15. Audit Rows Roll Back With the Transaction

Consider:

```sql
BEGIN;

UPDATE orders
SET status = 'approved'
WHERE id = 1001;

ROLLBACK;
```

The row change disappears.

The audit row written by the trigger also disappears because it was part of the same transaction.

Therefore a row-level trigger provides:

> **transactionally consistent audit history**

not necessarily:

> **independently durable evidence of every attempted mutation**.

This is usually exactly what business history needs.

For security investigations that must record attempted actions even when the transaction fails, database row auditing alone may be insufficient; server/database logging or an external logging mechanism can be required.

---

# 16. Business History vs Attempt Logging

These should be modeled separately.

## 16.1 Committed business history

```text
Only successfully committed state changes
```

Great for:

- record history,
- financial history,
- order lifecycle,
- customer profile history.

## 16.2 Attempt/security log

```text
Successful and failed operations
```

Useful for:

- authentication attempts,
- privileged access,
- suspicious operations,
- security investigation.

PostgreSQL server logs can capture request/session information and configurable error/log output, but server logging is conceptually different from a business audit table. citeturn181864search4

Do not force one mechanism to satisfy both requirements.

---

# 17. Transition Tables for Statement-Level Auditing

A statement can change thousands of rows.

This matters:

```sql
UPDATE products
SET status = 'inactive'
WHERE discontinued_at IS NOT NULL;
```

A row trigger runs once per affected row.

For bulk operations, statement-level triggers with transition tables can make set-oriented processing possible. PostgreSQL supports transition tables for `AFTER` triggers. citeturn181864search2

This can be architecturally superior when the audit operation itself is naturally set-oriented.

---

# 18. Row Trigger vs Statement Trigger

| Requirement | Row trigger | Statement trigger |
|---|---:|---:|
| Individual old/new row | Excellent | Requires transition table |
| One event per row | Excellent | Manual expansion |
| Large batch efficiency | Potentially expensive | Often better |
| Aggregate event | Awkward | Natural |
| Fine-grained field diff | Natural | Set processing needed |
| Generic history table | Common | More complex |

Do not choose based only on familiarity. Choose based on workload and evidence requirements.

---

# 19. Avoid Auditing Every Column Blindly

Suppose a table has:

```text
password_hash
refresh_token_hash
internal_flags
large_json_document
PII
billing_data
```

Blindly storing `to_jsonb(OLD)` and `to_jsonb(NEW)` may create a second sensitive-data repository.

Now you have:

```text
primary data → sensitive
        ↓
audit copy → also sensitive
```

This can increase:

- breach impact,
- retention obligations,
- deletion complexity,
- backup exposure,
- access-control surface,
- storage cost.

Audit design must include data minimization.

---

# 20. Sensitive-Column Redaction

Instead of:

```sql
new_row = to_jsonb(NEW)
```

consider an explicit projection:

```sql
jsonb_build_object(
  'id', NEW.id,
  'status', NEW.status,
  'total', NEW.total,
  'customer_id', NEW.customer_id
)
```

Or strip sensitive keys:

```sql
to_jsonb(NEW) - 'password_hash' - 'refresh_token_hash'
```

But redaction should be intentional and reviewed.

A dangerous anti-pattern is silently removing a field that investigators actually need.

---

# 21. Audit the Audit Table

An audit table should not casually be mutable by application code.

At minimum, think about:

```text
Application role
   ├── INSERT audit? usually no direct access
   ├── UPDATE audit? no
   ├── DELETE audit? no
   └── SELECT audit? restricted

Audit writer
   └── append according to controlled mechanism

Auditor / security role
   └── SELECT
```

The exact PostgreSQL privileges depend on whether triggers are `SECURITY DEFINER`, which role owns the audit function/table, and how the application connects.

The principle is:

> **An audit trail should have a narrower mutation surface than the data it protects.**

---

# 22. `SECURITY DEFINER` Requires Care

A privileged trigger function can make auditing reliable even when ordinary application roles cannot directly insert into the audit table.

But `SECURITY DEFINER` expands authority.

A careless function can become a privilege-escalation path.

Security design should address:

- ownership,
- `search_path`,
- schema qualification,
- executable privileges,
- dynamic SQL,
- SQL injection,
- attacker-controlled identifiers,
- function replacement,
- role ownership.

The goal is to create a tightly scoped privileged writer, not a general-purpose superuser function.

---

# 23. Search Path Hazards

A security-sensitive function should avoid relying on an attacker-influenced `search_path`.

Prefer explicit qualification:

```sql
INSERT INTO audit.audit_log (...)
VALUES (...);
```

rather than:

```sql
INSERT INTO audit_log (...)
```

The more privilege a function has, the more carefully its name resolution should be designed.

---

# 24. Audit Function Recursion

Suppose:

```text
orders trigger
   ↓
audit_log INSERT
   ↓
audit trigger on audit_log
   ↓
insert into audit_log
   ↓
...
```

This can create recursion or explosive audit noise.

The audit subsystem should have an explicit boundary.

Possible strategies:

- do not audit the audit table,
- isolate the audit schema,
- distinguish business tables from audit tables,
- guard against recursion where appropriate.

PostgreSQL exposes `pg_trigger_depth()` for trigger nesting inspection, but using depth as a blanket suppression mechanism can hide legitimate nested behavior. citeturn181864search0

Architectural isolation is usually clearer.

---

# 25. `UPDATE` Does Not Necessarily Mean “Business Change”

A SQL update can happen even when business values are effectively unchanged:

```sql
UPDATE orders
SET updated_at = now()
WHERE id = 1001;
```

or:

```sql
UPDATE orders
SET status = status
WHERE id = 1001;
```

A naive audit system will generate noise.

Use meaningful change detection where appropriate:

```sql
IF OLD IS DISTINCT FROM NEW THEN
  -- audit
END IF;
```

For column-specific logic:

```sql
IF OLD.status IS DISTINCT FROM NEW.status THEN
  -- state transition occurred
END IF;
```

`IS DISTINCT FROM` is especially useful because ordinary equality has SQL NULL semantics.

---

# 26. Audit Business Transitions, Not Just SQL Operations

Suppose an order changes:

```text
pending → approved
```

That is a business event.

SQL may additionally update:

```text
updated_at
version
search_vector
last_modified_by
```

Auditing every physical mutation may create several technical records for one business action.

Therefore mature systems often use two layers:

```text
Layer 1 — Row audit
    Exact persisted mutation

Layer 2 — Domain audit/event
    Business meaning of the operation
```

Example:

```text
ROW_UPDATE
status: pending → approved

ORDER_APPROVED
approver: u-42
reason: credit verified
```

Both can be valuable, but they answer different questions.

---

# 27. Audit Event Schema Design

A domain audit event might look like:

```sql
CREATE TABLE order_audit_events (
  event_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id      bigint NOT NULL,
  event_type    text NOT NULL,
  occurred_at   timestamptz NOT NULL DEFAULT clock_timestamp(),
  actor_id      text,
  tenant_id     text NOT NULL,
  request_id    text,
  reason        text,
  metadata      jsonb NOT NULL DEFAULT '{}'::jsonb
);
```

This is often easier for product/business queries than a generic table containing every possible table name.

Generic row auditing and domain audit events should coexist when the requirements differ.

---

# 28. Audit Log Ordering

Do not automatically assume:

```text
audit_id 100
```

means:

```text
business event happened before audit_id 101
```

Identity values provide identifiers, not universal causal ordering.

For precise reasoning, use explicit timestamps and transaction/request identifiers as needed.

Even `occurred_at` itself needs a semantic definition:

- application event time,
- transaction start time,
- statement time,
- trigger execution time,
- commit time.

Name the field according to what it actually means.

---

# 29. `now()` vs `clock_timestamp()`

PostgreSQL's `now()` represents the start time of the current transaction.

`clock_timestamp()` returns the actual current time and can advance during a transaction.

This distinction matters in long transactions.

For example:

```sql
BEGIN;

SELECT now();
-- work
SELECT now();

SELECT clock_timestamp();
-- work
SELECT clock_timestamp();

COMMIT;
```

For audit semantics, choose deliberately.

If the field means:

> transaction start time

`now()` is meaningful.

If it means:

> wall-clock moment at trigger execution

`clock_timestamp()` is closer to the intended meaning.

---

# 30. Commit Time Is Different

A row trigger does not directly give you a universally available “commit timestamp” field in every audit design.

That means a trigger-generated `occurred_at` should not be mislabeled as `committed_at`.

For many business histories, trigger execution time is enough.

For strict transaction chronology across concurrent transactions, commit-order semantics may require a different design using database-level mechanisms or external event capture.

Never put a stronger semantic meaning in a column name than your implementation can guarantee.

---

# 31. Old/New Row Storage and Schema Evolution

Suppose audit history stores:

```json
{
  "status": "approved",
  "total": 1000
}
```

Later the live table changes:

```text
currency
price_source
approval_level
```

Historical JSON remains an old schema representation.

This can be good: it preserves historical evidence.

It can also be inconvenient for strongly typed reporting.

Therefore decide whether audit snapshots are:

- forensic documents,
- queryable analytical records,
- reconstructable state versions,
- event payloads.

The storage representation should follow the usage contract.

---

# 32. Audit and Data Retention

Audit retention is a lifecycle problem.

```text
Hot audit
   ↓
Warm audit
   ↓
Cold archive
   ↓
Deletion according to policy
```

Do not let audit tables grow indefinitely by accident.

A table that receives every update can become one of the largest tables in the system.

Retention must consider:

- legal obligations,
- security requirements,
- business requirements,
- storage cost,
- backup impact,
- query performance,
- privacy/deletion obligations.

This topic will connect directly with the later `02.14 Data Lifecycle` and `02.15 Archival` chapters.

---

# 33. Partitioning Large Audit Tables

Large append-heavy audit tables are often candidates for time-based partitioning.

Example:

```sql
CREATE TABLE audit_log (
  audit_id bigint NOT NULL,
  occurred_at timestamptz NOT NULL,
  operation text NOT NULL,
  payload jsonb
) PARTITION BY RANGE (occurred_at);
```

Then:

```text
2026-01 partition
2026-02 partition
2026-03 partition
...
```

Benefits can include:

- easier retention,
- partition-local maintenance,
- partition pruning for time-bounded investigations,
- operational isolation.

But partitioning does not magically solve audit write amplification or indexing cost.

It is a workload tool, not a default requirement.

---

# 34. Indexing Audit Tables

Common query patterns:

```sql
WHERE tenant_id = ?
```

```sql
WHERE table_name = ? AND row_id = ?
```

```sql
WHERE actor_id = ? AND occurred_at >= ?
```

```sql
WHERE request_id = ?
```

Potential indexes:

```sql
CREATE INDEX audit_row_lookup_idx
ON audit_log (table_name, row_id, occurred_at DESC);

CREATE INDEX audit_actor_time_idx
ON audit_log (actor_id, occurred_at DESC);

CREATE INDEX audit_request_idx
ON audit_log (request_id);
```

Do not index every metadata field.

Every additional index increases write cost.

Measure real investigative query patterns.

---

# 35. JSONB Indexing: Powerful but Easy to Abuse

Suppose:

```sql
metadata jsonb NOT NULL
```

A generic GIN index might look attractive:

```sql
CREATE INDEX audit_metadata_gin
ON audit_log
USING gin (metadata);
```

But a large GIN index can materially increase storage and write overhead.

For stable query paths, a dedicated relational column may be better:

```text
request_id
actor_id
tenant_id
order_id
```

Use JSONB for flexible metadata, not as an excuse to avoid modeling important query dimensions.

---

# 36. Audit Throughput and Write Amplification

A normal update may already create:

```text
heap change
index changes
WAL
vacuum work
replication traffic
```

Adding audit insertion creates another write path:

```text
business update
      ↓
 audit row
      ↓
 audit indexes
      ↓
 extra WAL
      ↓
 replication
      ↓
 vacuum / maintenance
```

Audit architecture therefore directly affects OLTP performance.

The right question is not:

> “Are audit triggers slow?”

It is:

> **“What is the additional write amplification of the audit evidence required by the workload?”**

---

# 37. The Hot Path Problem

Suppose:

```text
orders: 5,000 updates/sec
```

and every row update writes:

```text
1 audit row
+ 4 audit indexes
```

The effective write workload can be far larger than “5,000 updates/sec”.

This can create:

- WAL growth,
- replication lag,
- I/O pressure,
- autovacuum activity,
- index bloat,
- CPU overhead.

Audit requirements need capacity planning.

---

# 38. Trigger Audit vs CDC

Another architectural choice is change data capture (CDC).

Conceptually:

```text
Database mutation
       ↓
transaction log / WAL
       ↓
CDC pipeline
       ↓
Kafka / stream / warehouse / audit store
```

Compared with trigger auditing:

| Dimension | Trigger | CDC/log-based |
|---|---|---|
| Same transaction | Excellent | Depends on pipeline semantics |
| Local audit table | Excellent | Not required |
| OLTP write amplification | Higher | Often lower on source rows |
| Operational complexity | Lower initially | Higher |
| External consumers | Limited | Excellent |
| Exact application actor | Needs context | Requires propagated metadata |
| Business-domain meaning | Easy in trigger/app | Usually transformed downstream |

CDC is not automatically a replacement for compliance audit.

It may be an excellent transport mechanism, but actor/context/evidence requirements still need design.

---

# 39. Audit Table vs Event Store

Do not conflate:

```text
audit history
```

with:

```text
event sourcing
```

Event sourcing stores business events as the authoritative state history and derives current state from them.

Audit history usually records changes to an otherwise authoritative current-state model.

These architectures have fundamentally different operational consequences.

---

# 40. Audit + Transactions

The strongest simple property of in-database row auditing is transaction atomicity:

```text
BEGIN
  business change
  audit change
COMMIT
```

Either both commit or both roll back.

This means the audit trail does not normally diverge from committed business state because of a network failure between the database and a separate audit API.

That is a major reason database-native auditing remains valuable.

---

# 41. Why “Call Audit API After Update” Is Weaker

Naive application flow:

```text
UPDATE business row
   ↓
HTTP call to audit service
```

Potential failure:

```text
UPDATE succeeds
   ↓
network failure
   ↓
audit call fails
```

Now:

```text
business state = changed
 audit state    = missing
```

A transaction-local trigger avoids that gap for committed row history.

The trade-off is write amplification and coupling to the transaction path.

---

# 42. Naive Approach → Why It Fails → Improved Approach

## Naive Approach

```sql
updated_by text
updated_at timestamptz
```

### Why It Fails

Only current state survives; previous values disappear.

### Improved Approach

Append-only audit history with actor and old/new values.

### Why It Works

Each committed mutation leaves durable historical evidence.

### Production Considerations

Add access control, retention, indexing, redaction, and capacity planning.

### Alternative

Domain event history or CDC.

### Trade-Off

More operational complexity in exchange for reconstructable history.

# 43. A Better Hybrid Architecture

For many enterprise systems:

```text
                    ┌─────────────────────┐
                    │   PostgreSQL OLTP    │
                    │                     │
Request ───────────►│ business tables    │
                    │        │            │
                    │        ▼            │
                    │ row audit/history   │
                    └────────┬────────────┘
                             │
                             ▼
                         WAL / CDC
                             │
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼
         analytics       security       long-term archive
```

This separates:

- transactionally consistent local history,
- downstream integration,
- analytics,
- long-term retention.

Not every system needs all layers.

# 44. Audit and Multi-Tenancy

An audit system in a multi-tenant application must never lose tenant identity.

Bad:

```text
row_id = 1001
```

Better:

```text
tenant_id = T7
row_id    = 1001
```

because IDs may repeat across tenant-local namespaces or investigations may be tenant-scoped.

Useful invariant:

> Every tenant-scoped audit record must be attributable to exactly one tenant unless the operation is explicitly system-wide.

This will connect directly to `02.13 Multi-Tenant Modeling`.

---

# 45. Audit and Branch/Organization Context

Enterprise systems often have nested business context:

```text
organization
   ↓
tenant
   ↓
branch
   ↓
warehouse
   ↓
user
```

The relevant audit context may be:

```text
tenant_id
branch_id
actor_id
```

Do not assume the actor's home branch is necessarily the context of the operation.

A user may operate across branches.

Audit the **transactional context**, not merely profile attributes.

---

# 46. Audit and Impersonation

Support and administrator workflows can involve:

```text
Admin A
   ↓
impersonates User B
   ↓
changes order
```

A single `actor_id` can be ambiguous.

Consider separating:

```text
authenticated_actor_id
acting_as_user_id
session_user
current_user
```

Then an investigation can distinguish:

```text
who authenticated
```

from:

```text
on whose behalf the action occurred
```

This is especially important for privileged support tooling.

---

# 47. Audit Reasons Are Not Decorative

A generic field:

```text
reason = "manual"
```

has low forensic value.

Prefer structured reasons when business workflows require them:

```json
{
  "reason_code": "PRICE_OVERRIDE",
  "reason_text": "Customer loyalty adjustment",
  "approved_by": "u-88"
}
```

Machine-readable reason codes support reporting and policy enforcement.

Free-text can supplement, not replace, structured meaning.

---

# 48. Audit and State Machines

For lifecycle-heavy entities:

```text
DRAFT
  ↓
SUBMITTED
  ↓
APPROVED
  ↓
FULFILLED
```

Audit should capture state transitions explicitly:

```text
from_state
 to_state
 actor
 reason
 occurred_at
```

This pairs naturally with the later `02.16 State Machines` chapter.

A generic UPDATE audit tells you that a row changed.

A domain state-transition record tells you why the state machine moved.

---

# 49. Financial and Ledger Systems

For financial data, audit architecture should generally complement—rather than replace—immutable business records.

Bad model:

```sql
UPDATE ledger_entry
SET amount = 950;
```

Better financial modeling usually records compensating or correcting entries rather than silently mutating historical facts.

The audit trail then documents the correction workflow.

This connects directly to `02.17 Immutable / Append-Only Data` and `02.18 Financial / Ledger Modeling`.

Audit is not a substitute for immutability.

---

# 50. Delete Auditing

Delete is where audit architecture becomes especially important.

If:

```sql
DELETE FROM customers WHERE id = 42;
```

and no history exists, the current row is gone.

A trigger can preserve:

```text
OLD customer state
```

before it disappears.

However, legal/privacy deletion creates an important tension:

```text
Need history
      vs
Need data minimization/deletion
```

This must be resolved through explicit retention and redaction policy rather than ad-hoc exceptions.

---

# 51. Soft Delete Is Not Auditing

A column:

```sql
deleted_at timestamptz
```

provides current-state knowledge that the entity was marked deleted.

It does not tell you:

- what other fields changed,
- who changed them,
- why the deletion occurred,
- what happened before deletion,
- whether the record changed repeatedly.

Soft delete and audit solve different problems.

---

# 52. Audit and Privacy

Audit copies can become a hidden privacy sink.

Suppose a customer asks to remove personal information.

You might have copies in:

```text
live table
audit table
backup
CDC stream
warehouse
cache
search index
object archive
```

Therefore an audit architecture must participate in the data lifecycle.

Possible patterns include:

- field-level redaction,
- cryptographic tokenization,
- deletion of directly identifying fields while preserving operational metadata,
- separate highly restricted archive,
- retention windows.

The correct solution depends on legal and business requirements.

---

# 53. Audit and Security Boundaries

Do not allow every developer to query every audit record.

Audit data may expose:

- private customer details,
- administrative actions,
- internal operational metadata,
- previous sensitive values,
- security investigation clues.

Use least privilege.

Create clear roles such as:

```text
app_role
support_read_role
audit_read_role
security_audit_role
```

Then grant only the minimum operations needed.

# 54. Auditing Privileged Database Changes

Row triggers only fire for the tables/triggers configured.

They do not automatically provide a complete history of every database-level administrative action.

Examples of separate concerns:

```text
GRANT / REVOKE
ALTER ROLE
DDL
login activity
configuration changes
```

These can require PostgreSQL server logging, event triggers, deployment logs, or external security tooling.

PostgreSQL provides event triggers for database-level event classes, but their scope differs from ordinary row triggers. citeturn181864search5

Think in layers:

```text
row audit
statement logging
DDL/event logging
authentication logging
infrastructure audit
```

# 55. Audit Trigger Discoverability

Production debugging must be able to answer:

```text
Which triggers exist on this table?
Which function do they execute?
When do they fire?
```

The information schema exposes trigger metadata, while PostgreSQL catalogs provide deeper internal metadata. citeturn181864search1

Example:

```sql
SELECT
  trigger_schema,
  trigger_name,
  event_object_schema,
  event_object_table,
  event_manipulation,
  action_timing,
  action_statement
FROM information_schema.triggers
WHERE event_object_table = 'orders';
```

Do not debug invisible database behavior by guessing.

Inspect it.

# 56. Audit and Observability Correlation

A powerful audit record can link:

```text
actor_id
request_id
trace_id
job_id
transaction context
```

Then an investigation can follow:

```text
Audit event
   ↓
request
   ↓
application log
   ↓
service trace
   ↓
database change
```

That makes the audit system part of the broader observability architecture rather than an isolated table.

# 57. What Audit Should Not Do

An audit trigger should generally not:

- call external HTTP services,
- perform slow analytics,
- make nonessential network calls,
- perform unbounded recursion,
- mutate unrelated business state without strong reason,
- depend on unstable application behavior.

A trigger lives on the transaction path.

Every extra operation becomes part of the database write latency and failure surface.

Keep the critical audit action local, deterministic, and bounded.

# 58. AI / Vibe-Coding Failure Modes

## Failure 1: “Just add `updated_by`.”

**Problem:** loses historical state.

## Failure 2: “Log the API request.”

**Problem:** database writes can occur outside that API path.

## Failure 3: “Call an audit microservice after every mutation.”

**Problem:** can diverge from the committed transaction.

## Failure 4: “Store every row as JSONB.”

**Problem:** sensitive-data duplication and uncontrolled storage growth.

## Failure 5: “Use `current_user` as the human user.”

**Problem:** pooled applications commonly share database roles.

## Failure 6: “`audit_id` tells exact event order.”

**Problem:** identifiers do not automatically represent commit causality.

## Failure 7: “Audit trigger means committed audit.”

**Problem:** the audit row rolls back with the transaction.

## Failure 8: “Use `SECURITY DEFINER` everywhere.”

**Problem:** unnecessary privilege amplification.

## Failure 9: “Audit tables never need indexes.”

**Problem:** investigations become full-table scans.

## Failure 10: “Put a GIN index on every JSONB audit payload.”

**Problem:** unnecessary write/storage overhead.

## Failure 11: “Audit history solves financial immutability.”

**Problem:** mutable financial state remains mutable; audit is only evidence of the mutation.

## Failure 12: “Never delete audit data.”

**Problem:** retention, privacy, and storage obligations still apply.

# 60. Production Example — Approval History

Suppose an invoice moves:

```text
PENDING
→ APPROVED
→ PAID
```

Do not rely only on:

```sql
invoice.status = 'PAID'
```

Use explicit history:

```sql
CREATE TABLE invoice_status_history (
  history_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  invoice_id  bigint NOT NULL,
  from_status text,
  to_status   text NOT NULL,
  actor_id    text,
  reason      text,
  changed_at  timestamptz NOT NULL DEFAULT clock_timestamp()
);
```

Now you can reconstruct lifecycle progression.

This is a domain-specific audit model and often more useful than generic JSON row snapshots for workflow reporting.

# 61. Testing Strategy

Audit systems require more than unit tests.

## 61.1 Insert test

Verify one business insert creates exactly one intended audit record.

## 61.2 Update test

Verify:

```text
old values
new values
changed fields
actor
context
```

## 61.3 Delete test

Verify the deleted state is retained according to policy.

## 61.4 Rollback test

```sql
BEGIN;
UPDATE ...;
ROLLBACK;
```

Confirm no committed business audit row remains.

## 61.5 Nested transaction/savepoint test

Verify expected behavior with savepoints.

## 61.6 Context leakage test

With connection pooling:

```text
Request A → user A
Request B → user B
```

Confirm user A's context never appears on B's audit rows.

## 61.7 Privilege test

Confirm the application cannot:

```sql
UPDATE audit.audit_log ...
DELETE FROM audit.audit_log ...
```

unless explicitly authorized.

## 61.8 Tampering test

Attempt unauthorized modifications and verify they fail.

## 61.9 Bulk-update test

Measure performance for:

```sql
UPDATE products ...
```

affecting thousands or millions of rows.

## 61.10 Schema migration test

Verify audit triggers continue working across column additions, removals, and renames.

> Does the failure preserve, lose, or corrupt audit guarantees?

# 63. Audit Error Policy

A critical decision:

> What happens if the audit write itself fails?

Option A:

```text
Audit failure → business transaction fails
```

This maximizes audit completeness but makes auditing part of business availability.

Option B:

```text
Audit failure → business transaction continues
```

This maximizes business availability but can create audit gaps.

For high-integrity domains, making audit writes mandatory is often appropriate.

For noncritical observability records, fail-open behavior may be reasonable.

There is no universal answer; the requirement must drive it.

---

# 64. Audit Completeness vs Availability

This is a real trade-off:

```text
             Audit completeness
                    ↑
                    │
                    │
Availability ───────┼───────
```

Ask:

- Is missing one audit row acceptable?
- Is a business transaction allowed to fail because audit storage is unavailable?
- Can audit be reconstructed later?
- Is the audit legally or financially material?

These answers determine architecture.

# 65. Reconciliation

A production system should have ways to detect audit gaps.

For example:

```text
business rows changed during period
          vs
expected audit records during period
```

Reconciliation can detect:

- missing triggers,
- disabled triggers,
- bulk operations that bypassed intended mechanisms,
- migration mistakes,
- accidental audit schema changes.

The exact reconciliation strategy depends on the model.

# 66. Audit Trigger Deployment Safety

A deployment adding an audit trigger should consider:

```text
lock acquisition
existing writes
backfill strategy
rollback
permissions
trigger ordering
function deployment order
```

Recommended sequence often resembles:

```text
1. create audit schema/table
2. create writer function
3. grant required privileges
4. deploy trigger
5. validate writes
6. monitor overhead
```

For very large systems, operational rollout may require more careful staged deployment.

# 67. Trigger Ordering Matters

A table can have multiple triggers.

Possible pipeline:

```text
BEFORE validation
   ↓
BEFORE mutation
   ↓
row mutation
   ↓
AFTER history
   ↓
AFTER derived logic
```

Do not assume all triggers are independent.

Inspect trigger definitions and understand their ordering and visibility semantics. PostgreSQL documents trigger firing behavior and visibility rules; these details matter when audit code depends on other trigger-generated changes. citeturn181864search2turn181864search8

# 68. Audit and ORM Hooks

Application ORM hooks are useful but are not a complete database audit boundary.

Why?

Data may change through:

```text
ORM
raw SQL
migration
admin SQL
background worker
ETL/import
stored function
another service
```

Database triggers can provide a broader mutation boundary for row changes.

The trade-off is more logic inside PostgreSQL and potentially more operational coupling.

# 69. Audit and Migrations

Schema migration is itself a source of change.

Example:

```sql
UPDATE orders
SET status = 'approved'
WHERE status = 'pending';
```

Should this produce 10 million audit records?

Maybe.

Maybe not.

The answer depends on whether the migration represents:

- business history,
- technical backfill,
- data repair,
- derived-state recomputation.

A mature system defines how migrations identify themselves:

```sql
SET LOCAL app.source = 'migration';
SET LOCAL app.migration_id = '2026_09_14_status_backfill';
```

That keeps technical changes distinguishable from human actions.

# 70. Audit Source Classification

Useful source values:

```text
api
worker
scheduled_job
migration
import
admin_sql
system
integration
```

This enables investigations such as:

```sql
SELECT source, count(*)
FROM audit_log
WHERE occurred_at >= now() - interval '1 day'
GROUP BY source;
```

Source metadata becomes especially valuable when automated processes modify the same tables as humans.

# 71. Idempotency and Audit

Suppose a client retries:

```text
request R123
```

and accidentally sends the same command twice.

You may get:

```text
AUDIT 1 — approve order
AUDIT 2 — approve order
```

But perhaps only one business state transition occurred.

Therefore audit semantics should align with command idempotency.

Possible fields:

```text
request_id
idempotency_key
command_id
```

Then investigations can distinguish:

```text
same command retried
```

from:

```text
two independent business actions
```

# 72. Audit Diff Representation

A structured field diff can look like:

```json
{
  "status": {
    "old": "pending",
    "new": "approved"
  },
  "credit_limit": {
    "old": 500000,
    "new": 750000
  }
}
```

This is easy to display in admin interfaces.

But generating diffs for arbitrary schemas can become expensive and complex.

Do not build a universal diff engine unless the product actually requires it.

# 73. When Full Snapshots Are Better

Use snapshots when investigators commonly ask:

> “Show me exactly what the record looked like at that point.”

Examples:

- customer profile history,
- pricing configuration,
- approval configuration,
- inventory master configuration.

Snapshots make point-in-time reconstruction straightforward.

---

# 74. When Domain History Is Better

Use dedicated history tables when the business asks:

> “How did this entity move through its workflow?”

Examples:

```text
order_status_history
invoice_status_history
approval_history
price_history
assignment_history
```

These tables are often cleaner and more queryable than generic JSONB audit records.

---

# 75. When Generic Audit Is Better

Generic row-level auditing is useful when:

- many tables require baseline history,
- exact old/new row evidence is valuable,
- schema changes happen frequently,
- investigations need broad coverage,
- domain-specific history would be too expensive to implement everywhere.

A mature architecture often uses generic audit as the floor and domain histories for important workflows.

### Question 1

### Question 2

### Question 3

# 77. Production Architecture Patterns

## Pattern A — Simple Row Audit

```text
business table
   ↓
AFTER trigger
   ↓
audit table
```

Use for baseline change history.

## Pattern B — Domain History

```text
business table
   ↓
application/domain command
   ↓
history table
```

Use for workflow semantics.

## Pattern C — Row Audit + Domain Events

```text
business table
   ├── row history
   └── business event
```

Use when both forensic and domain semantics matter.

## Pattern D — Database Audit + CDC

```text
PostgreSQL
 ├── local audit
 └── WAL/CDC → downstream systems
```

Use at larger integration scale.

## Pattern E — Security Evidence Stack

```text
DB row audit
+ DB/server logs
+ identity provider logs
+ application logs
+ infrastructure audit
```

Use when investigations must cover the full execution chain.

# 78. Anti-Patterns Summary

| Anti-pattern | Failure |
|---|---|
| `updated_by` only | No history |
| Audit only in controller | Misses non-HTTP mutations |
| External audit call after commit | Possible audit gap |
| Full JSON snapshot everywhere | Data duplication |
| No tenant ID | Weak attribution |
| Only DB role identity | Not actual business actor |
| Audit rows editable by app | Evidence can be tampered with |
| Unbounded audit retention | Storage and privacy problems |
| Every JSON field indexed | Excess write cost |
| Treat audit as ledger | History ≠ immutable accounting |
| Assume trigger = commit timestamp | Wrong temporal semantics |
| Ignore rollback | False expectation of persisted attempts |
| Ignore migration source | Hard-to-interpret history |
| Audit every technical update | Noise |

> “This order changed unexpectedly.”

Do not immediately inspect application code.

2. Query audit history
3. Find timestamp/window
4. Identify actor/context
5. Identify request ID
6. Trace request/application logs
7. Check worker/job activity

FROM audit_log
WHERE table_name = 'orders'
  AND row_id = '1001'

SELECT date_trunc('hour', occurred_at), count(*)

# 86. Expert “Why?” Questions

### Why not put `updated_by` everywhere and stop there?

Because that stores only the latest actor, not the sequence of state transitions.

### Why not audit entirely in the application?

Because multiple mutation paths may bypass that application layer.

### Why not make the audit service asynchronous?

Because asynchronous transport can separate audit persistence from the transaction unless the consistency contract explicitly accepts that gap.

### Why not store every old row forever?

Because storage, privacy, retention, query cost, and backup impact grow with every mutation.

### Why not use only CDC?

Because transport of database changes does not automatically provide the business actor, reason, authorization context, or desired domain semantics.

### Why not use audit rows as a ledger?

Because an audit record describes mutation; it does not necessarily prohibit mutation of the underlying fact.

                    ┌───────────────────────┐

                                │
                ┌───────────────┼────────────────┐

             └──────────────────┼──────────────────┘
                                ▼

                                │
                                ▼

A trustworthy audit architecture answers four fundamental questions:

```text
WHO changed it?
WHAT changed?
WHEN did it change?
WHY did it change?
```

A stronger enterprise audit system adds:

```text
under which tenant/context?
through which request/workflow?
was it committed?
can the evidence be trusted?
can it be retained and protected?
```

# 89. Final Principle

> **Audit architecture is not about recording everything. It is about preserving the right evidence, at the right trust boundary, with the right transaction semantics, for the right retention period, while keeping the system secure, queryable, and operationally sustainable.**

A production-grade PostgreSQL audit system therefore combines database-native atomicity with explicit identity propagation, deliberate evidence modeling, strict access control, controlled retention, performance measurement, and observability.

The objective is not merely to produce logs.

The objective is to make important state transitions **explainable and defensible**.
