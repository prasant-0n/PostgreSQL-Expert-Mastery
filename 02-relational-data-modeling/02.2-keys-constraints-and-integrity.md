# 02.2 — Keys, Constraints & Integrity

> **Phase:** 02 — Relational Data Modeling  
> **Chapter:** 02.2  
> **Level:** Foundation → Production → Expert  
> **Primary goal:** Design relational schemas in which invalid states are difficult or impossible to represent, while preserving clear ownership of business invariants, useful diagnostics, maintainability, and operational safety.

---

## 1. Chapter Objective

A production PostgreSQL schema is not merely a set of tables and columns. It is an executable model of the rules that determine which database states are legal.

This chapter develops the ability to answer:

- What makes a row identifiable?
- Which values must be unique?
- Which relationships must exist?
- Which values are allowed together?
- Which rules belong in `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `EXCLUDE`, or application code?
- What happens under concurrent writes?
- What changes when data is soft-deleted, tenant-scoped, versioned, or historical?
- How do constraint design, indexing, locking, and error handling interact?
- How should constraints be introduced safely into an existing production system?

The central engineering objective is **state-space reduction**.

Without constraints, the database accepts a large set of possible states and the application attempts to keep them valid.

With well-designed constraints, PostgreSQL itself rejects a large class of invalid states.

> **The database should enforce invariants at the strongest layer that has enough information to enforce them correctly.**

---

# 2. Three Definitions

## 2.1 Simple Definition

A key identifies rows. A constraint restricts what data is allowed. Integrity means the stored data remains valid and consistent.

## 2.2 Engineering Definition

Keys establish identity and uniqueness. Referential constraints protect relationships between tables. Domain constraints restrict individual values or combinations of values. Integrity is maintained by making illegal states fail close to their point of creation.

## 2.3 Expert Definition

Constraint design is the formalization of invariants over a database state space. A good relational design converts business predicates into declarative, transactionally enforced rules whose correctness remains valid across API boundaries, concurrent sessions, retries, scripts, background jobs, migrations, and future application implementations.

---

# 3. The Core Mental Model

Think of a database as a state machine.

```text
Current State
     |
     | INSERT / UPDATE / DELETE
     v
Candidate State
     |
     | Constraint validation
     v
+---------------------------+
| Is candidate state legal? |
+---------------------------+
       |              |
      YES             NO
       |              |
       v              v
Persist          Reject transaction
```

The important point is that constraints operate on **state**, not intentions.

An API may intend:

> "There should never be two active subscriptions for the same customer."

The database only sees rows and transactions.

The engineering problem is to translate that sentence into an enforceable invariant such as:

```sql
CREATE UNIQUE INDEX uq_active_subscription
ON subscriptions (customer_id)
WHERE cancelled_at IS NULL;
```

Now the rule survives:

- REST requests
- GraphQL
- admin scripts
- cron jobs
- queues
- migrations
- multiple application instances
- retries
- concurrent transactions

That is the power of declarative integrity.

---

# 4. Constraint Hierarchy

A useful design hierarchy is:

```text
NOT NULL
   ↓
CHECK
   ↓
UNIQUE
   ↓
PRIMARY KEY
   ↓
FOREIGN KEY
   ↓
Partial / expression uniqueness
   ↓
EXCLUSION / temporal constraints
   ↓
Cross-row or cross-table business invariants
```

This is not a strict statement about implementation complexity. It is a reasoning aid.

The further down the hierarchy a rule goes, the more carefully you should determine:

- who owns it,
- how it is enforced,
- what concurrency means,
- what failure looks like,
- how it is tested,
- whether the database can actually express it declaratively.

---

# 5. Keys

## 5.1 What Is a Key?

A key is a set of attributes whose values identify a relation instance according to a uniqueness rule.

In practical PostgreSQL engineering, distinguish:

- superkey
- candidate key
- primary key
- alternate key
- surrogate key
- natural key
- composite key
- foreign key

These terms are related but not interchangeable.

---

# 6. Superkeys

A **superkey** is any attribute set that uniquely identifies rows.

Example:

```text
users
-----
id
email
name
```

Suppose both `id` and `email` are unique.

Then all of these may technically be superkeys:

```text
(id)
(email)
(id, email)
(id, name)
(email, name)
(id, email, name)
```

The last combinations contain unnecessary attributes but remain unique.

---

# 7. Candidate Keys

A **candidate key** is a minimal superkey.

If both are independently unique:

```text
id
email
```

then both can be candidate keys.

One candidate key is normally selected as the primary key. The others remain alternate keys and should usually receive explicit uniqueness enforcement.

---

# 8. Primary Keys

## 8.1 Definition

A primary key is the chosen row identity for a table.

```sql
CREATE TABLE customers (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL
);
```

A primary key provides:

- uniqueness
- non-nullability
- a named identity contract
- a natural target for foreign keys

## 8.2 What a Primary Key Is Not

A primary key is not automatically:

- the business identifier shown to users
- the only unique value
- immutable by magic
- sufficient for every access pattern
- proof that the rest of the schema is correct

---

# 9. Surrogate vs Natural Keys

## 9.1 Surrogate Key

A surrogate key has no business meaning.

```sql
customer_id bigint GENERATED ALWAYS AS IDENTITY
```

Advantages:

- stable internal identity
- compact relationships
- avoids coupling row identity to mutable business data
- simplifies many references

Disadvantages:

- another identifier exists alongside business identifiers
- uniqueness of business fields still needs explicit constraints

## 9.2 Natural Key

A natural key derives from domain data.

Examples:

```text
country_code
SKU
invoice_number within a tenant
email address under a specific policy
```

Natural keys can be excellent alternate keys but are dangerous as sole identity when the business meaning may change.

## 9.3 Practical Pattern

A common production pattern is:

```text
Surrogate primary key
        +
One or more explicit business UNIQUE constraints
```

Example:

```sql
CREATE TABLE products (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL,
    name text NOT NULL,
    UNIQUE (sku)
);
```

In a multi-tenant system:

```sql
UNIQUE (tenant_id, sku)
```

The tenant boundary is part of the business key.

---

# 10. Composite Keys

A composite key uses more than one column.

Example:

```sql
CREATE TABLE order_items (
    order_id bigint NOT NULL,
    line_no integer NOT NULL,
    product_id bigint NOT NULL,
    quantity numeric(12,3) NOT NULL,
    PRIMARY KEY (order_id, line_no)
);
```

This expresses:

> A line number only needs to be unique inside an order.

This is often better than pretending `line_no` is globally unique.

---

# 11. Foreign Keys

A foreign key is a referential integrity constraint between a child key and a referenced key.

```sql
CREATE TABLE orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers(customer_id)
);
```

The relationship now means:

```text
orders.customer_id
        ↓
customers.customer_id
```

A child row cannot reference a nonexistent parent when the foreign key is enforced and immediate.

---

# 12. Foreign Keys Encode Relationships, Not Merely Joins

A common shallow understanding is:

> "Foreign keys are for joining tables."

No.

A SQL join can be performed without a foreign key.

The foreign key is a **validity rule**.

It says:

> Values in this column are references into a permitted set of parent keys.

That distinction matters.

```text
JOIN = query relationship
FK   = integrity relationship
```

---

# 13. `NOT NULL`

`NOT NULL` states that the column must have a value.

```sql
CREATE TABLE invoices (
    invoice_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL,
    status text NOT NULL
);
```

Without it, this is valid:

```sql
INSERT INTO invoices (customer_id, status)
VALUES (NULL, NULL);
```

With `NOT NULL`, the database rejects it.

## 13.1 `NOT NULL` Is More Important Than It Looks

A nullable column has an additional state:

```text
unknown / absent
```

Therefore:

```text
NOT NULL reduces the state space.
```

That improves:

- query reasoning
- indexing behavior
- constraint design
- application typing
- API semantics
- data quality

Use nullability deliberately.

---

# 14. `CHECK` Constraints

A `CHECK` constraint evaluates a Boolean condition.

```sql
CREATE TABLE products (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    price numeric(14,2) NOT NULL,
    CHECK (price >= 0)
);
```

Invalid:

```sql
INSERT INTO products (price) VALUES (-10);
```

## 14.1 Column-Level vs Table-Level Checks

Column-level style:

```sql
price numeric(14,2) CHECK (price >= 0)
```

Table-level style:

```sql
CHECK (start_at < end_at)
```

Use table-level checks when the invariant relates multiple columns.

---

# 15. Three-Valued Logic and `CHECK`

One of the most important constraint subtleties is that a `CHECK` constraint does not simply require the expression to evaluate to `TRUE` in every ordinary sense.

A `CHECK` expression that evaluates to `FALSE` rejects the row. An expression that evaluates to `TRUE` or `NULL` does not reject it.

Therefore:

```sql
CHECK (discount <= 100)
```

does not reject `discount = NULL`.

If null must also be forbidden:

```sql
CHECK (discount IS NOT NULL AND discount <= 100)
```

or more cleanly:

```sql
discount numeric NOT NULL CHECK (discount BETWEEN 0 AND 100)
```

This is why **`NOT NULL` and `CHECK` solve different problems**.

---

# 16. Designing `CHECK` Constraints

Good checks are:

- deterministic
- local to the row where possible
- understandable
- stable across migrations
- aligned with business language

Examples:

```sql
CHECK (quantity > 0)
```

```sql
CHECK (status IN ('draft', 'posted', 'cancelled'))
```

```sql
CHECK (
    (status = 'cancelled' AND cancelled_at IS NOT NULL)
    OR
    (status <> 'cancelled' AND cancelled_at IS NULL)
)
```

The last example encodes a relationship between status and timestamp.

---

# 17. `UNIQUE`

A unique constraint prevents duplicate non-null key combinations according to PostgreSQL's unique semantics.

```sql
CREATE TABLE users (
    user_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE
);
```

## 17.1 Why `UNIQUE` Is Not the Same as `DISTINCT`

`DISTINCT` transforms a result set.

`UNIQUE` restricts a database state.

```text
DISTINCT = query operation
UNIQUE   = integrity rule
```

---

# 18. Composite `UNIQUE`

Suppose SKU is unique per tenant:

```sql
CREATE TABLE products (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    sku text NOT NULL,
    UNIQUE (tenant_id, sku)
);
```

This allows:

```text
Tenant A / SKU-100
Tenant B / SKU-100
```

but rejects:

```text
Tenant A / SKU-100
Tenant A / SKU-100
```

This is a classic multi-tenant invariant.

---

# 19. `PRIMARY KEY` vs `UNIQUE`

| Property | PRIMARY KEY | UNIQUE |
|---|---|---|
| Chooses table identity | Yes | No |
| Allows null | No | PostgreSQL unique semantics apply; nulls are not equal under ordinary uniqueness |
| Multiple constraints | One primary key | Multiple unique constraints/indexes |
| FK target | Yes | Yes, when referenced key satisfies required uniqueness |
| Creates backing unique index | Yes | Yes |

Do not choose `PRIMARY KEY` simply because you want uniqueness.

Use it for the chosen identity.

---

# 20. Unique Constraints and NULL

Consider:

```sql
CREATE TABLE users (
    email text UNIQUE
);
```

Multiple rows with `NULL` can be allowed because `NULL` does not compare equal to another `NULL` under ordinary unique semantics.

This frequently surprises developers coming from application-level uniqueness checks.

If an email is mandatory:

```sql
email text NOT NULL UNIQUE
```

For more advanced semantics, PostgreSQL also supports explicit `NULLS NOT DISTINCT` behavior for unique constraints/indexes.

Example:

```sql
CREATE UNIQUE INDEX uq_example
ON example_table (code) NULLS NOT DISTINCT;
```

Use this only when the domain actually treats missing values as mutually exclusive.

---

# 21. Expression and Partial Uniqueness

Real business rules are rarely just:

```text
UNIQUE(column)
```

They often look like:

> usernames must be unique case-insensitively

or:

> only one active record may exist per customer

## 21.1 Expression Index

```sql
CREATE UNIQUE INDEX uq_users_email_ci
ON users (lower(email));
```

## 21.2 Partial Unique Index

```sql
CREATE UNIQUE INDEX uq_active_customer_address
ON customer_addresses (customer_id)
WHERE archived_at IS NULL;
```

The rule applies only to rows satisfying the predicate.

This is one of the strongest practical tools for modeling conditional business uniqueness.

---

# 22. Functional Dependencies and Constraint Design

Suppose:

```text
customer_id → email
```

means a customer determines one email under your business rule.

You may encode that identity through:

```sql
UNIQUE (customer_id)
```

But if email itself identifies a customer, then:

```sql
UNIQUE (email)
```

may also be required.

Constraint design should begin from **functional dependencies**, not from whichever ORM decorator happens to be convenient.

---

# 23. Referential Actions

Foreign keys can define what happens when the referenced row changes.

Common actions include:

- `NO ACTION`
- `RESTRICT`
- `CASCADE`
- `SET NULL`
- `SET DEFAULT`

Example:

```sql
CREATE TABLE order_items (
    order_id bigint NOT NULL
        REFERENCES orders(order_id)
        ON DELETE CASCADE
);
```

This means deleting an order deletes its child items.

---

# 24. `CASCADE` Is Not Automatically Good

A common AI-generated mistake is:

> "Use `ON DELETE CASCADE` everywhere to avoid orphan rows."

That is dangerous.

Ask:

1. Is the child lifecycle truly owned by the parent?
2. Should historical records disappear?
3. Could an administrative delete destroy financial evidence?
4. Could deleting one row recursively delete millions of descendants?
5. Is the relationship optional, archival, or legally significant?

For an invoice and its immutable ledger entries, automatic cascade deletion may be completely wrong.

---

# 25. Referential Actions as Ownership Semantics

Use the action to express lifecycle ownership.

```text
Parent owns child strongly
→ CASCADE may be appropriate

Child must survive independently
→ NO ACTION / RESTRICT

Reference may disappear but row survives
→ SET NULL

Reference replacement has meaningful default
→ SET DEFAULT (rare; use deliberately)
```

This is a domain decision, not merely a database preference.

---

# 26. Deferrable Constraints

Some constraints can be checked at transaction end instead of immediately.

Example:

```sql
CREATE TABLE accounts (
    account_id bigint PRIMARY KEY,
    parent_id bigint,
    CONSTRAINT fk_parent
        FOREIGN KEY (parent_id)
        REFERENCES accounts(account_id)
        DEFERRABLE INITIALLY DEFERRED
);
```

Deferrability matters when a valid final state temporarily passes through an invalid intermediate state within one transaction.

Conceptually:

```text
Immediate constraint
statement 1 → must be valid
statement 2 → must be valid

Deferred constraint
statement 1 → temporary state allowed
statement 2 → temporary state allowed
COMMIT      → final state must be valid
```

Use this only where the transactional workflow genuinely requires it.

---

# 27. Constraint Timing Is Part of Semantics

Ask:

> Does the invariant have to hold after every statement or only at transaction completion?

This is important for:

- cyclic references
- bulk reordering
- batch graph updates
- certain migration operations
- swapping unique values

Do not introduce deferred constraints as a generic performance trick. Their purpose is semantic correctness for transactional workflows.

---

# 28. Foreign Key Indexing

A foreign key column on the child side should usually have an index when it participates in meaningful parent-related operations.

Example:

```sql
CREATE INDEX idx_orders_customer_id
ON orders(customer_id);
```

Why?

Because a common workload is:

```sql
SELECT *
FROM orders
WHERE customer_id = $1;
```

and parent updates/deletes may also need to inspect referencing rows.

A foreign key declaration does not mean your desired child-side query index strategy has been designed.

---

# 29. `ON DELETE` Performance and Concurrency

When deleting a parent row, PostgreSQL must ensure referential integrity.

If a parent has many children and the child foreign-key column is not efficiently searchable, referential checks can become expensive.

For high-volume parent-child relationships, treat FK indexing as part of both:

```text
Correctness + Operational performance
```

---

# 30. Cross-Column Integrity

Consider an order line:

```text
quantity > 0
unit_price >= 0
line_total = quantity * unit_price
```

The first two are straightforward row-level checks.

```sql
CHECK (quantity > 0)
CHECK (unit_price >= 0)
```

The third may be modeled as a generated column:

```sql
line_total numeric(14,2)
GENERATED ALWAYS AS (quantity * unit_price) STORED
```

This is preferable to trusting application code to keep redundant derived values synchronized.

---

# 31. Generated Values and Integrity

When a value is deterministically derived from other stored values, ask:

> Should the application write it, or should the database derive it?

Application-written derived data creates synchronization risk.

Database-derived values reduce one class of invalid states.

Examples:

```text
normalized search key
computed totals
canonicalized identifiers
status-independent derived metrics
```

Not every derived value belongs in a generated column; choose based on volatility, indexing needs, write cost, and semantics.

---

# 32. Constraints vs Application Validation

This distinction is foundational.

### Application validation

Good for:

- user-friendly messages
- expensive policy checks
- external service decisions
- request-shape validation
- authorization

### Database constraints

Good for:

- uniqueness
- references
- domain bounds
- local invariants
- transactional integrity
- concurrent race protection

The strongest architecture is usually:

```text
Client validation
        ↓
Application validation
        ↓
Database constraints
```

Each layer has a different job.

---

# 33. Why “Check Then Insert” Is Not Enough

Naive code:

```sql
SELECT 1
FROM users
WHERE email = $1;
```

Then:

```sql
INSERT INTO users(email)
VALUES ($1);
```

This has a race condition.

Two transactions can execute:

```text
T1: SELECT → no row
T2: SELECT → no row
T1: INSERT
T2: INSERT
```

Without a database uniqueness constraint, duplicates are possible.

Correct architecture:

```sql
ALTER TABLE users
ADD CONSTRAINT uq_users_email UNIQUE (email);
```

Then application code handles the possible uniqueness violation.

---

# 34. Constraints and Concurrency

A constraint is especially valuable because it operates inside the database's concurrency model.

Do not attempt to rebuild unique enforcement with:

- application mutexes
- in-memory flags
- Redis locks without a carefully justified design
- request serialization assumptions
- "we checked first"

These may be useful for other purposes, but they are poor substitutes for the database invariant itself.

---

# 35. Exclusion Constraints

Some integrity rules are about **conflicts**, not equality.

Example:

> Two reservations for the same room must not overlap.

Equality-based `UNIQUE` cannot express this directly.

PostgreSQL exclusion constraints can.

Conceptually:

```text
same room
AND overlapping time range
→ forbidden
```

Example shape:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_reservations (
    reservation_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL,
    occupied tstzrange NOT NULL,
    EXCLUDE USING gist (
        room_id WITH =,
        occupied WITH &&
    )
);
```

This is a direct expression of a business invariant that would otherwise require race-prone application logic.

---

# 36. Constraint Taxonomy by Question

Use this mental mapping:

| Business question | Typical mechanism |
|---|---|
| Must a value exist? | `NOT NULL` |
| Must value obey local rule? | `CHECK` |
| Must row identity be stable and unique? | `PRIMARY KEY` |
| Must business identifier be unique? | `UNIQUE` |
| Must another row exist? | `FOREIGN KEY` |
| Must only active rows be unique? | Partial unique index |
| Must normalized expression be unique? | Expression unique index |
| Must time ranges not overlap? | `EXCLUDE USING GIST` |
| Must invariant survive concurrent writes? | Database constraint / transactional design |
| Must user have permission? | Privileges / RLS / application authorization |

---

# 37. Integrity and Multi-Tenancy

Suppose:

```sql
CREATE TABLE products (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    sku text NOT NULL
);
```

A common mistake is:

```sql
UNIQUE (sku)
```

when the business rule is actually:

```text
SKU unique within tenant
```

The correct constraint is usually:

```sql
UNIQUE (tenant_id, sku)
```

The tenant dimension belongs in the invariant when the business meaning is tenant-local.

---

# 38. Composite Foreign Keys for Tenant Safety

A particularly important pattern is preventing cross-tenant references.

Bad:

```text
orders.tenant_id
orders.customer_id → customers.customer_id
```

The schema may still permit:

```text
Order tenant A
→ Customer tenant B
```

unless additional integrity rules prevent it.

A robust relational pattern is to make the tenant part of the referenced identity:

```sql
CREATE TABLE customers (
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    PRIMARY KEY (tenant_id, customer_id)
);
```

Then:

```sql
CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customers (tenant_id, customer_id)
);
```

Now the database itself rejects cross-tenant references.

This is a powerful example of schema design enforcing isolation rather than merely documenting it.

---

# 39. Constraint Naming

Always prefer explicit, stable names for important production constraints.

Instead of relying on generated names:

```sql
CONSTRAINT uq_products_tenant_sku
UNIQUE (tenant_id, sku)
```

```sql
CONSTRAINT fk_orders_customer
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, customer_id)
```

```sql
CONSTRAINT ck_order_total_nonnegative
CHECK (total_amount >= 0)
```

Benefits:

- better errors
- easier migration work
- easier observability
- easier debugging
- easier documentation
- stable references in tooling

---

# 40. Constraint Naming Strategy

A practical convention:

```text
pk_<table>
fk_<child>_<parent>
uq_<table>_<business-key>
ck_<table>_<rule>
ex_<table>_<conflict-rule>
```

Examples:

```text
pk_customers
fk_orders_customers
uq_products_tenant_sku
ck_order_items_quantity_positive
ex_room_reservations_no_overlap
```

The exact naming standard is a team decision. Consistency matters more than this particular prefix scheme.

---

# 41. Wrong Implementation: App-Only Uniqueness

```ts
const existing = await userRepo.findOne({ email });
if (!existing) {
  await userRepo.insert({ email });
}
```

Why it fails:

```text
request A ── check ── insert
request B ── check ── insert
```

Both requests can observe the same state.

Improved:

```sql
CREATE UNIQUE INDEX uq_users_email
ON users (email);
```

Then:

```ts
try {
  await userRepo.insert(...);
} catch (error) {
  // translate unique_violation into domain-level conflict
}
```

---

# 42. Wrong Implementation: `COUNT(*)` Before Delete

A developer may do:

```sql
SELECT COUNT(*)
FROM order_items
WHERE order_id = $1;
```

then decide whether to delete the order.

That check is not atomic with another concurrent transaction changing child rows unless the transaction design explicitly provides the required serialization.

Prefer expressing the actual invariant with foreign keys and appropriate transaction semantics.

---

# 43. Wrong Implementation: Soft Delete Without Revisiting Uniqueness

Suppose:

```sql
UNIQUE (tenant_id, email)
```

and rows are soft-deleted:

```text
deleted_at IS NOT NULL
```

Now a deleted account may block reuse of the email.

If the business rule is:

> Active accounts must have unique email addresses.

then model exactly that:

```sql
CREATE UNIQUE INDEX uq_active_account_email
ON accounts (tenant_id, lower(email))
WHERE deleted_at IS NULL;
```

Do not encode historical records into active-state uniqueness accidentally.

---

# 44. Wrong Implementation: Using `CHECK` for Cross-Row Rules

This is a common misconception:

```sql
CHECK (
    NOT EXISTS (
        SELECT 1 FROM other_table ...
    )
)
```

Ordinary PostgreSQL `CHECK` constraints are intended to validate row-level conditions and are not a general mechanism for arbitrary cross-row or cross-table integrity.

For cross-row invariants, consider:

- unique indexes
- exclusion constraints
- foreign keys
- triggers where justified
- transactional locking/design
- redesigning the model

The right answer is not always "add a trigger."

---

# 45. Wrong Implementation: Nullable Foreign Keys Without Intent

```sql
customer_id bigint REFERENCES customers(customer_id)
```

This permits `NULL`.

That may be correct for:

> customer is optional

or incorrect if the domain really requires:

> every order must belong to a customer

Then use:

```sql
customer_id bigint NOT NULL REFERENCES customers(customer_id)
```

Nullability is part of the relationship's cardinality semantics.

---

# 46. Wrong Implementation: Free-Text Status Without Constraint

```sql
status text NOT NULL
```

Then application code gradually produces:

```text
pending
Pending
PENDING
in-progress
processing
procressing
```

Possible alternatives include:

```sql
CHECK (status IN ('pending', 'processing', 'completed'))
```

or a suitable enum/domain/reference-table strategy depending on lifecycle and change frequency.

The important point is not "always use ENUM." The important point is:

> constrain finite domains according to their lifecycle and ownership.

---

# 47. Wrong Implementation: Duplicate Business Identifiers

Schema:

```text
id PK
invoice_number text
```

No uniqueness on `invoice_number`.

Application logic says:

> "We generate unique invoice numbers."

That is not enough under concurrency.

If the business says invoice number is unique within a tenant:

```sql
UNIQUE (tenant_id, invoice_number)
```

The database should own that invariant.

---

# 48. Constraint Errors Are Part of the API Contract

Production applications should not treat every database exception as HTTP 500.

Example database state conflict:

```text
duplicate key value violates unique constraint
```

The API may correctly translate that to:

```http
409 Conflict
```

depending on the business/API contract.

Likewise:

```text
foreign key violation
```

may map to a domain-level "referenced resource does not exist" error.

The exact HTTP mapping is application-specific, but the principle is universal:

> database integrity failures are often expected domain conflicts, not programmer catastrophes.

---

# 49. PostgreSQL SQLSTATE Codes

For robust error handling, applications should prefer machine-readable error metadata such as SQLSTATE instead of parsing human-readable error strings.

Important categories include:

```text
23505 = unique_violation
23503 = foreign_key_violation
23514 = check_violation
23502 = not_null_violation
23P01 = exclusion_violation
```

These codes provide stable categories for translating database failures into domain behavior.

---

# 50. Constraint Failure Diagnostics

When a write fails, capture enough information to diagnose it without logging sensitive values.

Useful fields include:

- SQLSTATE
- constraint name
- relation/table
- operation type
- request correlation ID
- transaction or job context
- application entity identifiers when safe

Avoid logging raw credentials, tokens, payment data, or complete sensitive payloads.

---

# 51. Constraint Design and Security

Constraints are not authorization.

For example:

```sql
CHECK (tenant_id IS NOT NULL)
```

does not prevent one tenant from reading another tenant's rows.

That requires appropriate:

- role privileges
- row-level security where used
- query scoping
- application authorization
- trusted execution paths

However, constraints can strengthen security architecture by making forbidden relationships impossible.

Example:

```text
cross-tenant FK → rejected by schema
```

This is defense in depth.

---

# 52. Constraints and RLS

Row-Level Security answers:

> Who may access or modify a row?

Constraints answer:

> What states may exist?

These are complementary.

```text
Authorization boundary
        +
Integrity boundary
        =
Stronger system safety
```

Do not confuse them.

---

# 53. Constraints and Transactions

Constraints are evaluated as part of database operations and transaction semantics.

This means integrity is not a separate afterthought.

It participates in:

- statement execution
- transaction abort behavior
- locking
- concurrent writes
- commit-time validation for deferred constraints

A failed integrity check can abort the current statement or transaction depending on context and error handling.

---

# 54. Transaction Savepoints and Constraint Recovery

If an application wants to attempt a write that may violate a constraint and continue within a larger transaction, savepoints can sometimes isolate the failure.

Conceptually:

```sql
SAVEPOINT try_insert;

-- potentially conflicting operation

ROLLBACK TO SAVEPOINT try_insert;
```

Use this intentionally. Frequent exception-driven control flow inside hot paths can have cost and complexity.

For expected conflict-heavy workflows, patterns such as `INSERT ... ON CONFLICT` are often cleaner.

---

# 55. Constraints and UPSERT

Unique constraints provide the conflict target for many upsert workflows.

```sql
INSERT INTO products (tenant_id, sku, name)
VALUES ($1, $2, $3)
ON CONFLICT (tenant_id, sku)
DO UPDATE SET name = EXCLUDED.name;
```

The uniqueness rule is declared by the schema; the statement uses it atomically.

This is dramatically stronger than:

```text
SELECT → if absent INSERT → else UPDATE
```

---

# 56. Constraint-Driven API Design

Suppose an endpoint creates a product.

The API contract can state:

```text
201 Created
409 Conflict → SKU already exists in tenant
422 Unprocessable Entity → invalid field combination
```

The database can enforce:

```text
NOT NULL
CHECK
UNIQUE
FK
```

The application translates the resulting state conflict into the API contract.

This gives the system a clean boundary:

```text
Database = authoritative integrity
Application = domain behavior + presentation
```

# 57. Schema Review Technique: Translate Sentences Into Invariants

Take a business sentence:

> An order must belong to exactly one tenant and one customer from that tenant.

Translate:

```text
order.tenant_id       NOT NULL
order.customer_id     NOT NULL
customer PK           (tenant_id, customer_id)
order FK              (tenant_id, customer_id)
```

Another sentence:

> A tenant can have only one active default warehouse.

Translate:

```sql
CREATE UNIQUE INDEX uq_tenant_active_default_warehouse
ON warehouses (tenant_id)
WHERE is_default;
```

Another:

> Reservations for the same room cannot overlap.

Translate:

```text
EXCLUDE USING GIST
```

This translation skill is more important than memorizing syntax.

# 59. Production Example — Jewellery ERP

Consider a multi-branch jewellery ERP.

### Business requirements

```text
1. SKU is unique within a tenant.
2. Every stock ledger entry belongs to an existing product in the same tenant.
3. Quantity must be greater than zero for movement rows.
4. A posted transaction cannot be silently changed.
5. One active stock reservation cannot overlap another reservation for the same item.
6. Branch-scoped users cannot accidentally reference another tenant's product.
```

### Possible integrity model

```sql
CREATE TABLE products (
    tenant_id bigint NOT NULL,
    product_id bigint NOT NULL,
    sku text NOT NULL,
    PRIMARY KEY (tenant_id, product_id),
    UNIQUE (tenant_id, lower(sku))
);
```

```sql
CREATE TABLE stock_movements (
    tenant_id bigint NOT NULL,
    movement_id bigint NOT NULL,
    product_id bigint NOT NULL,
    quantity numeric(14,3) NOT NULL,
    PRIMARY KEY (tenant_id, movement_id),
    FOREIGN KEY (tenant_id, product_id)
        REFERENCES products (tenant_id, product_id),
    CHECK (quantity > 0)
);
```

This is substantially safer than merely storing:

```text
product_id
sku
tenant_id
```

and trusting the application to keep them consistent.

# 60. Posted Records and Mutability

A constraint cannot express every lifecycle rule.

Suppose:

> A posted financial transaction must never be modified.

That is not simply:

```sql
CHECK (status = 'posted')
```

because the rule concerns **future transitions**, not only a static row predicate.

Possible approaches include:

- permissions separating posting from ordinary users
- append-only ledger design
- carefully designed triggers
- immutable event/transaction tables
- controlled stored procedures

The lesson:

> Not every business invariant maps directly to a static row constraint.

For each invariant classify it.

### Class A — Row-local

Examples:

```text
quantity > 0
end_at > start_at
status in allowed values
```

Typical mechanism:

```text
NOT NULL / CHECK
```

### Class B — Key uniqueness

Examples:

```text
SKU unique per tenant
email unique among active users
```

Typical mechanism:

```text
UNIQUE / unique index / partial unique index
```

### Class C — Referential

Examples:

```text
order must belong to customer
```

Typical mechanism:

```text
FOREIGN KEY
```

### Class D — Conflict / temporal

Examples:

```text
reservations may not overlap
```

Typical mechanism:

```text
EXCLUDE
```

### Class E — Workflow / transition

Examples:

```text
posted → immutable

```

Typical mechanism:

```text
permissions / transactions / triggers / domain architecture
```

# 62. Migrations: Adding Constraints to Existing Data

Adding a constraint to a production table is a data-quality operation.

Suppose you want:

```sql
ALTER TABLE orders
ADD CONSTRAINT ck_orders_total_nonnegative
CHECK (total_amount >= 0);
```

But existing rows may violate it.

A safe workflow is:

```text
1. Discover violations
2. Quantify them
3. Repair or explicitly classify exceptions
4. Verify clean state
5. Add constraint using an operationally appropriate strategy
6. Monitor failures
```

Do not assume a syntactically correct migration is operationally safe.

---

# 63. Constraint Backfill Strategy

For a large production table:

```text
Naive
ALTER TABLE → validate millions of rows during critical deployment window
```

Potential problem:

- long validation work
- deployment coupling
- lock implications
- unexpected impact

A more controlled process can use PostgreSQL mechanisms such as creating an initially unvalidated constraint and validating later where supported and appropriate.

The exact strategy depends on constraint type and PostgreSQL behavior, but the architectural principle is:

> Separate data cleanup from production enforcement when the migration size requires it.

---

# 64. Constraint Validation Is Evidence

Before enabling an invariant, measure violations.

Example:

```sql
SELECT COUNT(*)
FROM orders
WHERE total_amount < 0;
```

Then identify examples:

```sql
SELECT order_id, total_amount
FROM orders
WHERE total_amount < 0
ORDER BY order_id
LIMIT 100;
```

This makes migration decisions evidence-driven rather than optimistic.

# 65. Monitoring Constraint Failures

A sudden increase in:

```text
23505 unique_violation
```

could mean:

- normal race handling
- a client bug
- a duplicate replay storm
- a broken import
- a changed uniqueness policy
- a missing tenant scope

Do not merely count failures.

Add dimensions such as:

```text
constraint_name
route / job
operation
tenant or safe tenant category
application version
```

This helps distinguish healthy conflict behavior from regressions.

---

# 66. Testing Constraints

Constraint tests should prove that invalid states fail.

### Example

```sql
INSERT INTO products (tenant_id, sku)
VALUES (1, 'SKU-100');
```

Then:

```sql
INSERT INTO products (tenant_id, sku)
VALUES (1, 'SKU-100');
```

Expected:

```text
unique_violation
```

And test the scope boundary:

```sql
INSERT INTO products (tenant_id, sku)
VALUES (2, 'SKU-100');
```

Expected:

```text
success
```

Testing only the happy path proves almost nothing about integrity.

---

# 67. Concurrency Testing

For uniqueness and conflict constraints, test concurrent actors.

Conceptual test:

```text
T1 ───────── insert tenant=1, sku=X ───────── COMMIT
T2 ───────── insert tenant=1, sku=X ───────── COMMIT
```

Expected:

```text
exactly one succeeds
```

Do not settle for:

```text
"The unit test inserts duplicate rows sequentially and it failed."
```

The race is the important part.

---

# 68. Property-Based Integrity Testing

For sophisticated systems, test invariants rather than only examples.

Examples:

```text
For every order:
order tenant = customer tenant
```

```text
For every active product:
no duplicate (tenant, normalized_sku)
```

```text
For every reservation set:
no prohibited overlap exists
```

Generate many operations and assert that the database never reaches an illegal state.

# 69. AI / Vibe-Coding Failure Patterns

## Failure 1 — "Unique Check in Service"

AI generates:

```ts
if (!(await exists(email))) {
  await create(email);
}
```

Problem: race condition.

Repair:

```text
database UNIQUE + conflict-aware application behavior
```

## Failure 2 — "CASCADE Everything"

AI assumes cascades simplify cleanup.

Problem:

```text
one delete → uncontrolled data loss
```

Repair:

```text
model lifecycle ownership explicitly
```

## Failure 3 — "Nullable by Default"

AI leaves most columns nullable.

Problem:

```text
NULL creates additional state combinations
```

Repair:

```text
make required domain facts NOT NULL
```

## Failure 4 — "Tenant Filtering in Every Query"

AI adds:

```sql
WHERE tenant_id = $1
```

everywhere but leaves FK relationships tenant-unsafe.

Problem:

```text
cross-tenant references can still exist
```

Repair:

```text
composite scoped keys / foreign keys where domain semantics require them
```

## Failure 5 — "CHECK for Everything"

AI tries to encode cross-table invariants in `CHECK` constraints.

Problem:

```text
CHECK is not a generic relational assertion mechanism
```

Repair:

```text
choose FK, unique, exclusion, trigger, transaction design, or schema redesign
```

## Failure 6 — Error String Parsing

AI checks whether an exception message contains:

```text
"duplicate key"
```

Problem: brittle text parsing.

Repair:

```text
SQLSTATE + constraint name
```

# 70. Performance Considerations

Constraints are not free.

Typical costs include:

- indexes required for uniqueness
- parent/child lookups for foreign-key validation
- write amplification
- additional WAL
- index page maintenance
- conflict detection
- exclusion index maintenance

But the cost must be compared with the cost of invalid data.

A good question is not:

> "Does this constraint slow writes?"

It is:

> "What business failure does this constraint prevent, and what is the measured cost of enforcing it?"

---

# 71. Indexes Created by Constraints

Primary keys and unique constraints require supporting uniqueness structures.

This has several consequences:

```text
INSERT
UPDATE of indexed key
DELETE
```

may all carry additional index maintenance cost.

Therefore avoid unnecessary unique constraints that duplicate the same rule and index.

Review existing indexes before adding another one.

---

# 72. Duplicate Integrity Structures

Bad example:

```sql
UNIQUE (email)
```

plus

```sql
CREATE UNIQUE INDEX uq_users_email ON users(email);
```

if both enforce the same exact rule.

This duplicates storage and maintenance for little or no benefit.

Understand whether you need:

- a constraint,
- an index,
- or a special-purpose index expression.

---

# 73. Unique Constraint vs Unique Index

A unique constraint expresses a **schema invariant**.

A unique index is an index object with uniqueness semantics.

For straightforward business integrity, prefer a unique constraint because it communicates intent clearly and participates naturally in schema metadata.

Use a unique index when you need features such as:

- partial uniqueness
- expression-based uniqueness
- specialized indexing behavior not represented directly by a plain constraint

This distinction improves schema communication.

---

# 74. Foreign Keys and Delete Storms

A parent deletion can fan out into many child checks or cascades.

Imagine:

```text
customer
  ↓
10 million orders
  ↓
30 million order_items
```

A seemingly simple delete can become a massive operational event.

For high-volume systems, model deletion carefully:

- archival
- soft deletion
- partitioning strategies
- retention policies
- controlled batch cleanup
- explicit administrative workflows

Do not treat cascades as an operational garbage collector.

---

# 75. Constraint Trade-Off Matrix

| Mechanism | Best for | Major strength | Main limitation |
|---|---|---|---|
| `NOT NULL` | Required values | Simple, fast, universal | Cannot express relationships |
| `CHECK` | Row-local rules | Declarative | Limited for cross-row semantics |
| `UNIQUE` | Equality uniqueness | Strong concurrency-safe invariant | Equality-oriented |
| `PRIMARY KEY` | Identity | Identity + reference target | One per table |
| `FOREIGN KEY` | Referential integrity | Prevents dangling references | Adds validation/work on writes |
| Partial unique index | Conditional uniqueness | Encodes real business rules | Index-specific semantics |
| Expression unique index | Normalized uniqueness | Flexible | Expression must be appropriate and stable |
| `EXCLUDE` | Conflict/overlap rules | Powerful temporal semantics | More specialized, index-dependent |
| Trigger | Complex transitions | Highly expressive | More hidden behavior and maintenance |
| Application code | UX/external policy | Flexible | Race-prone if used for core integrity |

---

# 76. Production Decision Framework

When you discover a rule, use this decision sequence.

### Step 1 — Is the rule row-local?

Yes → `NOT NULL` / `CHECK`

### Step 2 — Is it uniqueness?

Yes → `UNIQUE` / partial or expression unique index

### Step 3 — Is it existence/reference integrity?

Yes → `FOREIGN KEY`

### Step 4 — Is it an overlap/conflict rule?

Yes → `EXCLUDE` or an equivalent transactionally safe design

### Step 5 — Is it about a state transition?

Consider:

- permissions
- triggers
- procedures
- append-only modeling
- workflow architecture

### Step 6 — Does application code know more than the database?

Use the application for policies that depend on:

- external APIs
- authorization context
- feature flags
- user/session state
- expensive algorithms

But do not move core integrity into the application merely because it is convenient.

# 78. Expert Questions

### Q1. Why does a unique constraint solve a race condition that `SELECT then INSERT` cannot?

Because uniqueness enforcement participates in the database's concurrency-control machinery rather than depending on a stale application observation.

### Q2. Why is `(tenant_id, id)` sometimes a better relational identity than globally unique `id` plus application checks?

Because the tenant boundary becomes part of referential integrity and can be propagated through composite foreign keys.

### Q3. Why is `CHECK` insufficient for arbitrary cross-row constraints?

Because row-level check constraints are not a general transactional assertion mechanism for inspecting and synchronizing arbitrary external rows.

### Q4. When is a trigger justified?

When the invariant genuinely requires procedural behavior that cannot be expressed cleanly through stronger declarative mechanisms, and the trigger's transactional semantics, observability, and maintenance cost are understood.

### Q5. Why are constraints architecture, not merely database syntax?

Because they determine which states can exist under every code path and therefore shape concurrency safety, API behavior, migrations, operational recovery, and data trust.

When an unexpected integrity error appears:

```text

2. Capture constraint name
3. Identify table
4. Identify exact operation
5. Identify transaction context
```

```text

3. Is the rule modeled correctly?
4. Is scope missing, especially tenant scope?
5. Is soft-delete semantics missing?
6. Is the rule about a transition rather than a state?
7. Can concurrent writes bypass the application's check?
8. Is the invariant actually external to the database?
```

# 83. Final Principles

## Principle 1 — Model the invariant, not the implementation shortcut

Do not start with:

> "Which ORM annotation should I use?"

Start with:

> "What database states are legal?"

## Principle 2 — Uniqueness belongs in the database

Application checks can improve UX. They cannot replace transactional uniqueness enforcement.

## Principle 3 — Nullability is semantics

Every nullable column introduces additional possible states. Make null meaningful, not automatic.

## Principle 4 — Foreign keys are integrity contracts

A join can work without a foreign key. Referential integrity cannot.

## Principle 5 — Scope the invariant correctly

For multi-tenant systems, ask whether the business key is global or tenant-local.

## Principle 6 — Lifecycle determines delete behavior

`CASCADE` is a domain decision, not a cleanup convenience.

## Principle 7 — Static state rules and transition rules are different

Use row constraints for row state. Use workflow architecture, permissions, transactions, or carefully justified triggers for transitions.

## Principle 8 — Constraints are concurrency protection

The strongest invariant is one that remains correct when many processes write at the same time.

## Principle 9 — Measure before changing constraint architecture

Constraint behavior has real performance and operational consequences. Use evidence.

## Principle 10 — A trustworthy database rejects invalid states early

The goal is not to make the application less important.

The goal is to make the system safer when the application is imperfect.
