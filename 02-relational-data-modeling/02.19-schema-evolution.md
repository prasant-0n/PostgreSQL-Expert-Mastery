# 02.19 — Schema Evolution

> **Phase 02 — Relational Data Modeling**
>
> Schema evolution is the discipline of changing a live database model without silently breaking data, application behavior, performance, availability, integrations, or historical guarantees.

---

## 1. Objective

By the end of this chapter, you should be able to:

- distinguish a schema change from a data migration and a PostgreSQL major-version upgrade;
- reason about compatibility across application versions, workers, replicas, ETL, reports, and external consumers;
- design additive, transitional, and contract-breaking changes deliberately;
- evolve tables, columns, constraints, indexes, generated columns, enums, functions, views, and relationships safely;
- migrate large production datasets incrementally;
- understand locking, rewrite risk, WAL amplification, replication lag, and deployment hazards;
- use expand/contract migrations and dual-read/dual-write strategies when necessary;
- validate new invariants before enforcing them;
- preserve rollback safety and understand why database rollback is often different from application rollback;
- test migrations under production-like concurrency and scale;
- build migration observability and operational runbooks;
- reason about schema compatibility as an architecture problem rather than a file-editing task.

---

## 2. Three Definitions

### 2.1 Simple definition

**Schema evolution means changing the structure or rules of a database while the system continues to operate.**

Examples:

- adding a column;
- renaming a column;
- changing a data type;
- adding a foreign key;
- creating an index;
- splitting one table into two;
- replacing a free-form status with a constrained workflow;
- introducing tenant scoping;
- retiring an old column.

### 2.2 Engineering definition

Schema evolution is the controlled transformation of a database contract while preserving specified compatibility and correctness guarantees.

The important word is **contract**.

A database schema is not only DDL. It is also:

- what queries expect;
- what writes are allowed;
- what values mean;
- what constraints guarantee;
- what indexes make affordable;
- what APIs expose;
- what background jobs consume;
- what reports assume;
- what CDC/replication streams carry;
- what historical data means.

### 2.3 Expert definition

A production schema change is a distributed-system change whose compatibility surface spans time, transactions, processes, deployments, and independent consumers.

A useful model is:

```text
Schema evolution
    = data-shape evolution
    + invariant evolution
    + application-contract evolution
    + operational migration
    + compatibility management
    + rollback strategy
```

# 3. First Principles

A live database is never isolated.

Suppose today you have:

```text
orders(id, customer_name)
```

and you want:

```text
orders(id, customer_id)
customers(id, name)
```

This is not one change. It is a sequence of state transitions:

```text
Old schema
   ↓
New nullable structure
   ↓
Backfill
   ↓
Dual-read / transitional application
   ↓
Dual-write or authoritative-write transition
   ↓
Validation
   ↓
Enforce invariant
   ↓
Cut over readers
   ↓
Remove legacy path later
```

The core idea is:

> **Do not treat a production schema migration as a single instant unless the workload genuinely allows an atomic instant.**

Many migrations are better understood as a **temporal protocol**.

# 4. The Compatibility Surface

Before changing a schema, identify every consumer.

```text
                    ┌──────────────┐
                    │   Database   │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
       API pods         Workers           Reports
          │                │                │
       old/new          old/new          scheduled
          │                │                │
          └────────────────┼────────────────┘
                           │
                  external consumers
```

Also include:

- migrations;
- BI queries;
- admin tools;
- stored procedures;
- triggers;
- views;
- materialized views;
- logical replication;
- CDC pipelines;
- search indexing;
- cache builders;
- data exports;
- scripts and operational tooling.

A migration is unsafe when any unknown consumer can still depend on the old contract.

# 5. Schema Version Is Not Just a Number

There are multiple relevant versions:

```text
database physical major version
application release
schema state
migration version
API contract version
data interpretation version
projection version
```

Do not confuse:

```text
PostgreSQL 17 → PostgreSQL 18
```

with:

```text
migration 104 → migration 105
```

A PostgreSQL major-version upgrade changes the database engine and system catalogs. PostgreSQL documents `pg_upgrade` and dump/restore/logical-replication approaches separately from ordinary DDL changes. citeturn503708search0turn503708search2

# 6. Migration Taxonomy

## 6.1 Additive change

Examples:

```sql
ALTER TABLE orders
ADD COLUMN notes text;
```

Usually the easiest class because old application versions can continue ignoring the new field.

But “additive” does not automatically mean “safe.” A new `NOT NULL`, default behavior, generated expression, trigger, or index can introduce locking or runtime cost.

## 6.2 Relaxing change

Examples:

- removing a constraint;
- allowing a previously forbidden value;
- making a field nullable.

These are often compatibility-friendly but can weaken invariants.

The danger is semantic rather than syntactic:

```text
old guarantee > new guarantee
```

The application may rely on the stronger old guarantee.

## 6.3 Transformative change

Examples:

- integer → bigint;
- text → structured type;
- one column → two columns;
- table normalization;
- changing ownership semantics.

Transformative changes usually need staged migration.

## 6.4 Contract-breaking change

Examples:

```sql
ALTER TABLE orders
DROP COLUMN legacy_code;
```

or changing meaning so old application code becomes incorrect.

These need explicit coordination or a compatibility window.

---

# 7. Expand / Migrate / Contract

The canonical production pattern is:

```text
EXPAND
  ↓
MIGRATE
  ↓
CONTRACT
```

## 7.1 Expand

Add the new structure while preserving the old one.

Example:

```sql
ALTER TABLE customer_profiles
ADD COLUMN normalized_name text;
```

Do not immediately remove `name`.

## 7.2 Migrate

Populate and adopt the new structure.

```text
old data → transform → new data
```

The application may temporarily read both or write both.

## 7.3 Contract

After all consumers have migrated:

- make the new invariant strict;
- remove compatibility code;
- drop old indexes;
- remove old columns;
- remove temporary triggers/functions.

Contract is a separate deployment phase, not an afterthought.

---

# 8. Why “Just Rename the Column” Is Dangerous

Suppose:

```sql
ALTER TABLE users
RENAME COLUMN full_name TO display_name;
```

The database change can be simple while the system change is not.

Potential breakage:

- old API binaries still issue `full_name` queries;
- reporting scripts still select `full_name`;
- ORM-generated SQL references old property mapping;
- CDC consumers expect old field names;
- views/functions depend on the old identifier;
- blue/green deployment creates old/new application overlap.

The problem is **temporal compatibility**.

A safer approach is often:

1. add `display_name`;
2. populate it;
3. temporarily maintain both representations;
4. migrate all readers;
5. verify no old readers remain;
6. remove `full_name` later.

---

# 9. Additive Column Strategy

## 9.1 Safe baseline

```sql
ALTER TABLE orders
ADD COLUMN internal_reference text;
```

Old code can generally ignore it.

## 9.2 Adding `NOT NULL`

Do not assume this can be added safely without considering existing rows and validation work.

A common staged pattern is:

```sql
ALTER TABLE orders
ADD COLUMN internal_reference text;

-- backfill in controlled batches

ALTER TABLE orders
ADD CONSTRAINT orders_internal_reference_nn
CHECK (internal_reference IS NOT NULL) NOT VALID;

ALTER TABLE orders
VALIDATE CONSTRAINT orders_internal_reference_nn;
```

Then, depending on the desired PostgreSQL representation and release strategy, transition to an actual `NOT NULL` constraint when operationally appropriate.

The important concept is separating **data cleanup** from **enforcement**.

# 10. Defaults and Rewrite Risk

A migration author must ask:

> Does this DDL merely change metadata, or can it force expensive physical work?

Potential consequences include:

- table scans;
- heap rewrites;
- index builds;
- WAL generation;
- long-running transactions;
- replication lag;
- lock acquisition delays.

Never judge a migration only by the number of SQL lines.

Judge it by:

```text
lock duration
+ rows affected
+ bytes rewritten
+ WAL generated
+ replica impact
+ concurrent workload
```

PostgreSQL's DDL documentation separates adding/removing/modifying table structures, and current PostgreSQL releases contain specific improvements and semantics around generated columns, constraints, and migration behavior. citeturn503708search9

---

# 11. Column Type Changes

Consider:

```sql
ALTER TABLE payments
ALTER COLUMN amount TYPE numeric(20,4);
```

Questions:

1. Is the conversion lossless?
2. Is a `USING` clause required?
3. Does the table need to be rewritten?
4. What lock is acquired?
5. How long can it run?
6. What happens to replication?
7. Can old application binaries still interpret the values?
8. Are indexes/constraints/functions affected?

Never assume:

```text
same-looking values = safe type migration
```

A type change is a data transformation plus a contract change.

---

# 12. Large-Table Type Migration

For a huge production table, prefer a staged conversion when direct alteration is operationally unsafe.

Example:

```text
old_amount numeric(12,2)
new_amount numeric(20,4)
```

Pattern:

```text
1. add new_amount
2. backfill batches
3. dual-write
4. validate equivalence
5. switch readers
6. stop writing old column
7. remove old column later
```

Batching limits transaction size and reduces lock duration per unit of work.

A robust backfill is:

- bounded;
- resumable;
- idempotent;
- observable;
- throttled;
- safe under concurrent writes.

---

# 13. Data Backfills

A backfill is an operational workload, not merely a SQL statement.

Naive:

```sql
UPDATE orders
SET normalized_status = normalize_status(status);
```

Why it fails at scale:

- large transaction;
- huge WAL burst;
- long locks/row-version churn;
- vacuum pressure;
- replica lag;
- rollback becomes expensive.

Better:

```sql
UPDATE orders
SET normalized_status = normalize_status(status)
WHERE id > :last_id
  AND id <= :next_id
  AND normalized_status IS NULL;
```

Repeat with measured batch sizes.

Track:

```text
rows processed
rows remaining
throughput
error count
lag
WAL rate
transaction duration
```

---

# 14. Cursor-Based vs Keyset Backfill

Prefer stable keyset traversal over pagination based on an ever-changing offset.

Good:

```sql
WHERE id > :last_id
ORDER BY id
LIMIT :batch_size
```

Potentially poor for large mutable tables:

```sql
OFFSET 500000 LIMIT 1000
```

The second pattern can require increasingly expensive work and becomes fragile when rows change during execution.

---

# 15. Idempotent Migrations

A production migration should be designed so interrupted execution has a safe recovery path.

Backfill example:

```sql
UPDATE customers
SET normalized_email = lower(trim(email))
WHERE normalized_email IS NULL;
```

This is naturally resumable.

Idempotency does **not** mean every DDL statement should blindly use `IF NOT EXISTS`.

Bad:

```sql
CREATE INDEX IF NOT EXISTS some_index ...;
```

without verifying whether an existing index is actually equivalent.

“Exists” is not the same as “correct.”

---

# 16. `CREATE INDEX CONCURRENTLY`

For large live tables, concurrent index creation can reduce writer blocking compared with a regular index build, but it has different operational characteristics and cannot simply be treated as a drop-in replacement.

PostgreSQL documents that `CREATE INDEX` normally acquires stronger table-level effects during the build, while concurrent approaches perform multiple scans and wait for relevant transactions. `REINDEX CONCURRENTLY` also has restrictions, including exclusion-constraint indexes. citeturn503708search6

Remember:

```text
concurrent ≠ free
```

It can still:

- take significant time;
- consume I/O;
- hold resources for a long time;
- be affected by long-running transactions;
- create operational complexity.

---

# 17. Index Migration

Treat indexes as part of the schema contract.

A migration may need to:

```text
add new index
→ observe planner behavior
→ switch queries
→ verify utilization
→ remove obsolete index
```

Do not immediately drop the old index just because the new index exists.

A supposedly unused index may still serve:

- rare queries;
- emergency diagnostics;
- foreign-key checks;
- reporting jobs.

Use production evidence before removal.

---

# 18. Constraint Evolution

Constraints are executable business rules.

Therefore constraint migration should often follow:

```text
discover violations
→ remediate data
→ add constraint in validation-safe form
→ validate
→ enforce
```

Example:

```sql
ALTER TABLE invoices
ADD CONSTRAINT invoices_total_nonnegative
CHECK (total_amount >= 0) NOT VALID;

ALTER TABLE invoices
VALIDATE CONSTRAINT invoices_total_nonnegative;
```

The migration must explicitly answer:

> What happens to rows that violate the new invariant?

Do not discover this only at deployment time.

PostgreSQL 18 also supports `NOT ENFORCED` for `CHECK` and foreign-key constraints, which can be useful in selected migration and metadata scenarios but should not be mistaken for actual runtime enforcement. citeturn503708search2

---

# 19. Constraint Tightening Is a Semantic Migration

Example:

```text
Before:
status ∈ any text value

After:
status ∈ {draft, posted, cancelled}
```

This is not just DDL.

It changes the legal state space.

The migration sequence should include:

```text
inventory invalid states
→ decide remediation policy
→ normalize existing values
→ validate
→ enforce
→ update producers
```

This is why database engineering is domain engineering.

---

# 20. Unique Constraint Evolution

Suppose current uniqueness is:

```text
UNIQUE(email)
```

but future semantics are:

```text
UNIQUE(tenant_id, email)
```

The migration must consider existing duplicates under the new scope.

Correct sequence:

```text
1. identify collisions
2. resolve them
3. add new uniqueness mechanism
4. migrate readers/writers
5. remove old global uniqueness
```

Do not reverse the order.

Otherwise the new invariant can reject legitimate data before the application has been prepared.

---

# 21. Foreign-Key Evolution

Adding a foreign key to a large existing table is not just:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id)
REFERENCES customers(id);
```

First investigate:

```sql
SELECT customer_id, count(*)
FROM orders
WHERE customer_id IS NOT NULL
GROUP BY customer_id
HAVING NOT EXISTS (
  SELECT 1
  FROM customers c
  WHERE c.id = orders.customer_id
);
```

Then choose a validation strategy appropriate to the workload.

Also inspect the child-side index.

A referential constraint without appropriate indexing can turn otherwise safe operations into expensive checks.

---

# 22. Renaming: Compatibility-Aware Alternatives

## Option A — Atomic rename

Use when all consumers can be stopped or upgraded together.

## Option B — Add + dual path

Use when old and new application versions coexist.

## Option C — Compatibility view

Sometimes a view can preserve an old read contract:

```sql
CREATE VIEW legacy_customers AS
SELECT id,
       display_name AS full_name
FROM customers;
```

Views can provide compatibility, but they do not magically preserve write semantics.

---

# 23. Splitting a Table

Before:

```text
users
------------------------------------------------
id
name
phone
address
preferences
billing_data
```

After:

```text
users
user_profiles
user_billing
```

Migration plan:

```text
add child tables
→ copy data
→ establish FKs
→ dual-write or transactional write to new tables
→ switch reads
→ reconcile
→ remove old columns
```

The key question is:

> Is there ever a period where old and new representations can disagree?

If yes, define the consistency mechanism explicitly.

---

# 24. Merging Tables

Merging has the opposite risk: collisions and semantic ambiguity.

Suppose:

```text
local_customers
crm_customers
```

become:

```text
customers
```

You must determine:

- identity matching rules;
- conflict resolution;
- surviving primary keys;
- foreign-key remapping;
- duplicate elimination;
- audit preservation;
- historical references.

The data mapping should be deterministic and documented.

---

# 25. Enum Evolution

Enums can be useful when the state space is intentionally constrained, but operational evolution must be understood.

Ask:

- can new values be introduced without changing application assumptions?
- are clients using string literals?
- are values externally serialized?
- are values ordered or compared in application code?
- can a value ever be removed?

Do not use an enum when the business requirement is actually a configurable workflow or tenant-specific taxonomy.

---

# 26. Domain Types and Semantic Stability

PostgreSQL domains, custom types, functions, and operators can centralize semantic rules.

But they increase the schema dependency graph.

Changing a domain can affect many columns at once.

Use them when central semantic reuse is valuable and ownership is clear.

Avoid creating custom types merely because they appear sophisticated.

---

# 27. Generated Columns

Generated columns are useful when derived values belong to the relational model.

Before changing one, ask:

- is the generation expression stable?
- are indexes built on it?
- can old application code coexist?
- does the generated value participate in constraints?
- is it stored or virtual according to the version and design?

PostgreSQL 18 changed generated-column defaults by introducing virtual generated columns as the default, so migration documentation should state the target PostgreSQL major version explicitly rather than assuming old behavior. citeturn503708search2

---

# 28. Functions, Triggers, and Views Are Schema Dependencies

A migration can break behavior without breaking table DDL.

Dependency examples:

```text
column
  ↓
view
  ↓
report

column
  ↓
trigger function
  ↓
audit table

column
  ↓
CDC consumer
```

Before dropping or changing an object, inspect dependencies and operational consumers.

Never assume an ORM migration file contains the whole schema contract.

---

# 29. Compatibility Matrix

For zero-downtime deployments, think in versions.

Example:

| Database | App v1 | App v2 | Safe? |
|---|---|---|---|
| Old | yes | no | yes |
| Expanded | yes | yes | yes |
| Expanded + dual-write | yes | yes | yes |
| New contract only | no | yes | yes |
| Contract dropped | old | no | no |

A migration should explicitly identify which cells are allowed.

This makes blue/green and rolling deployments much easier to reason about.

---

# 30. Dual-Write: Powerful but Dangerous

Dual-writing means:

```text
application write
   ├── old representation
   └── new representation
```

Naive dual-write code can diverge:

```text
write old succeeds
write new fails
```

Possible approaches:

### Transactional dual-write

Both writes occur in one transaction in the same database.

Strongest consistency when practical.

### Trigger-maintained dual-write

The database keeps the representations synchronized.

Useful when many writers exist, but triggers add hidden coupling.

### Asynchronous dual-write

One side eventually follows another through events/queues.

More operational complexity and eventual consistency.

Choose based on the required consistency contract.

---

# 31. Dual-Read

During migration:

```text
read new
if absent:
    read old
```

But this creates ambiguous truth.

A better approach is to define an authority rule:

```text
new value exists → new is authoritative
new absent       → old is temporary fallback
```

Then remove the fallback after the cutover window.

Never leave fallback logic indefinitely. Transitional logic becomes permanent complexity surprisingly often.

---

# 32. Backfill + Concurrent Writes

Suppose:

```text
T1 backfills row 100
T2 updates row 100 concurrently
```

You must define whether T2 can overwrite the backfill or vice versa.

Patterns include:

- write-through application logic;
- trigger synchronization;
- compare-and-swap conditions;
- row locking for targeted transformations;
- backfill predicates that only update missing values;
- replay/reconciliation passes.

A migration without concurrency reasoning is incomplete.

---

# 33. The Two-Phase Backfill Problem

For some transformations, one pass is not enough.

Example:

```text
old_code → new_code
```

A robust flow may be:

```text
pass 1: historical backfill
pass 2: reconcile rows changed during migration
pass 3: verify equivalence
```

This is similar to synchronization protocols: initial copy plus convergence.

---

# 34. Migration Invariants

Every significant migration should define invariants.

Examples:

```text
old.amount = new.amount
```

or:

```text
old.customer_id = new.customer_id
```

or:

```text
COUNT(old rows) = COUNT(new rows)
```

or, for a decomposition:

```text
sum(child balances) = parent balance
```

Measure invariants before and after.

Do not rely on:

```text
migration finished with exit code 0
```

That only proves the process ended.

---

# 35. Reconciliation Queries

Example:

```sql
SELECT count(*)
FROM orders
WHERE customer_id IS NOT NULL
  AND customer_id <> legacy_customer_id;
```

Better reconciliation often includes:

- counts;
- distinct counts;
- null distributions;
- aggregate sums;
- checksums/hashes where appropriate;
- orphan detection;
- duplicate detection;
- sampled row comparisons.

For financial data, aggregate reconciliation must be stronger than row-count reconciliation.

---

# 36. Migration State Tracking

Serious migration systems often maintain explicit operational state.

Example conceptual record:

```text
migration_id
started_at
last_key
rows_processed
status
error_count
finished_at
```

This helps resumability and observability.

Do not confuse migration bookkeeping with the canonical business schema.

Keep operational metadata isolated and well documented.

---

# 37. PostgreSQL Transaction Boundaries

Some schema operations can run transactionally; others have restrictions.

A migration author must know the command's transaction behavior rather than assuming:

```text
BEGIN
DDL
COMMIT
```

is universally sufficient.

`CREATE INDEX CONCURRENTLY`, for example, has transaction-block restrictions. PostgreSQL documents its specialized locking and concurrency behavior. citeturn503708search6

Therefore migrations should be classified into:

```text
transactional DDL
non-transactional / specially constrained DDL
long-running data migration
background operational work
```

---

# 38. Locking Is Part of Migration Design

For each DDL statement, ask:

```text
What lock?
How long?
Who conflicts?
What happens if a transaction is already holding a conflicting lock?
```

The most dangerous migration may be a tiny statement waiting behind a forgotten long-running transaction.

Operational readiness should include:

```sql
SELECT pid,
       usename,
       state,
       xact_start,
       query_start,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_start NULLS LAST;
```

Use evidence rather than assumptions.

---

# 39. `lock_timeout` and `statement_timeout`

Production migrations should often use bounded failure rather than waiting indefinitely.

Example:

```sql
SET lock_timeout = '3s';
SET statement_timeout = '5min';
```

The exact limits depend on workload.

The principle is:

> **A migration should fail safely rather than silently turning into an availability incident.**

Be careful: a timeout is not a recovery plan. The migration still needs a retry and diagnosis procedure.

---

# 40. Long-Running Transactions Are Migration Enemies

Long transactions can:

- hold locks;
- prevent vacuum cleanup;
- keep old snapshots alive;
- extend index-build waits;
- increase bloat;
- delay schema-change completion.

A successful staging test with no long-running transactions does not prove production safety.

Include representative transaction durations in load testing.

---

# 41. Replication Considerations

Schema evolution can affect replication in multiple ways.

### Physical replication

DDL and data changes flow through WAL as part of the physical stream.

### Logical replication

The publisher and subscriber have schema contracts that must remain compatible with the replicated change stream.

PostgreSQL logical replication is based on logical changes and replication identity, and PostgreSQL documents dedicated upgrade procedures for logical-replication clusters. citeturn503708search4turn503708search1

Never assume:

```text
primary migration success = replica ecosystem success
```

Check:

- apply lag;
- publication/subscription behavior;
- generated columns;
- schema compatibility;
- replication identity;
- downstream consumers.

---

# 42. Schema Changes and CDC

CDC consumers may break when:

- column names change;
- types change;
- columns become nullable/non-nullable;
- fields disappear;
- event payload shape changes.

Therefore the database schema may have a larger effective API surface than the application API.

Treat CDC payload compatibility as a versioned contract.

---

# 43. Schema Evolution with Event-Driven Systems

An event payload may outlive the current relational schema.

Example:

```json
{
  "customerId": 123,
  "name": "Asha"
}
```

Later relational schema:

```text
customers
profiles
identity
```

The event's historical contract does not automatically change.

This reinforces a crucial distinction:

```text
current database schema
≠
historical event schema
```

Preserve event compatibility explicitly.

---

# 44. Schema Evolution and Historical Data

Changing semantics can be more dangerous than changing structure.

Example:

```text
price = “current selling price”
```

versus:

```text
price = “price at transaction time”
```

A migration must never silently reinterpret historical data.

This is especially important for:

- invoices;
- payments;
- inventory movements;
- taxation;
- accounting entries;
- audit history;
- regulatory exports.

---

# 45. Database Major-Version Upgrades

Do not mix these concepts:

```text
schema migration
```

with:

```text
PostgreSQL major-version upgrade
```

For major-version upgrades, PostgreSQL documents approaches including `pg_upgrade`, dump/restore, and logical-replication-based strategies depending on the architecture. PostgreSQL 18 also documents changes specific to that major release and its migration considerations. citeturn503708search0turn503708search2

A major-version upgrade plan should include:

- extension compatibility;
- application compatibility;
- query behavior changes;
- planner/statistics behavior;
- replication topology;
- rollback strategy;
- extension upgrade steps;
- test-cluster rehearsal.

---

# 46. Versioned Migration Files

A common migration repository pattern is:

```text
001_create_users.sql
002_add_email.sql
003_add_customer_id.sql
004_backfill_customer_id.sql
005_enforce_customer_fk.sql
```

Good migration naming communicates ordering and intent.

Avoid giant opaque migration files containing unrelated changes.

Prefer:

```text
one logical transformation
+ explicit preconditions
+ verification
```

---

# 47. Schema Drift

Schema drift occurs when environments no longer represent the same intended schema.

Examples:

```text
production ≠ staging
staging ≠ migration source
tenant A ≠ tenant B
replica schema ≠ publisher schema
```

Prevent drift with:

- migration-based deployment;
- schema diff tooling;
- migration checksums/versioning;
- CI validation;
- deployment gates;
- periodic catalog inspection.

Never manually patch production and forget to encode the change.

---

# 48. ORM Migrations vs Database Reality

ORMs can generate migrations, but they cannot infer every operational requirement.

An ORM may see:

```text
rename field
```

while production reality is:

```text
rolling deployment
+ 2 application versions
+ CDC
+ 2 billion rows
+ strict availability SLO
```

Therefore:

> **Use ORM migrations as implementation tools, not as substitutes for database engineering.**

Review generated SQL.

Ask:

- what lock?
- what scan?
- what rewrite?
- what data loss?
- what rollback?

# 49. Naive Approach → Why It Fails → Improved Approach

## Example: rename

### Naive Approach

```sql
ALTER TABLE users
RENAME COLUMN name TO display_name;
```

### Why It Fails

Old application instances may still execute `name` queries.

### Improved Approach

```text
expand
→ dual compatibility
→ migrate readers
→ verify
→ contract
```

### Why It Works

It supports a transition period where old and new consumers coexist.

### Production Considerations

Measure remaining old consumers before deleting the legacy path.

### Alternative

Atomic deployment where no old consumer can exist.

### Trade-Off

More deployment complexity, but lower compatibility risk.

# 50. Production Pattern: Column Split

Suppose:

```text
customer.full_address
```

must become:

```text
customer.address_line_1
customer.address_line_2
customer.city
customer.postal_code
```

Recommended sequence:

```text
1. ADD new columns
2. deploy writers that populate new + old
3. backfill historical rows
4. reconcile old/new
5. switch readers to new fields
6. stop writing old field
7. enforce new constraints
8. keep old field during safety window
9. drop old field in later release
```

This is schema evolution as a protocol.

---

# 51. Production Pattern: Table Decomposition

Example:

```text
orders
  ├─ shipping_address
  ├─ billing_address
  └─ customer_snapshot
```

becomes:

```text
orders
order_addresses
order_customer_snapshots
```

The migration must preserve historical semantics.

Do not replace an invoice's historical customer snapshot with a mutable current customer record merely because normalization looks cleaner.

**Normalization is not permission to destroy historical meaning.**

---

# 52. Jewellery ERP Scenario

Consider a multi-branch jewellery ERP.

Existing stock table:

```text
stock_items
------------
id
branch_id
product_code
weight
status
```

New architecture requires:

```text
products
inventory_items
inventory_movements
```

A production migration could be:

```text
Phase A — Expand
products + inventory_items + inventory_movements

Phase B — Backfill
existing stock → inventory_items
existing stock history → inventory_movements where available

Phase C — Dual-write
new transactions update both old and new structures

Phase D — Reconcile
counts, weights, status totals, branch totals

Phase E — Cutover
reads use new model

Phase F — Contract
legacy columns/tables retired after verification
```

For financial and inventory data, reconciliation should include quantitative totals, not only row counts.

---

# 53. Multi-Tenant Migration

A multi-tenant schema adds another dimension:

```text
global migration state
per-tenant migration state
```

For a very large system, tenant-by-tenant migration may reduce blast radius.

Example:

```text
tenant 1 → complete
tenant 2 → complete
tenant 3 → failed/retry
tenant 4 → pending
```

This requires:

- idempotent scripts;
- tenant isolation;
- tenant-scoped reconciliation;
- rollback or compensation strategy;
- per-tenant observability.

Do not assume all tenants have equivalent data quality.

---

# 54. Feature Flags and Schema Migration

Feature flags are not schema-versioning substitutes, but they can coordinate application behavior around a migration.

Example:

```text
flag = use_new_customer_identity
```

Migration phases:

```text
schema expanded
→ flag off
→ backfill
→ verify
→ enable for internal users
→ enable for subset
→ enable globally
→ contract legacy path
```

This separates:

```text
deployment
```

from:

```text
activation
```

which can reduce blast radius.

---

# 55. Rollback Is Not Always “Down Migration”

A dangerous misconception is:

```text
up migration
→ failure
→ down migration
```

For destructive or partially applied data transformations, reverse DDL may not restore original information.

Example:

```text
old text → normalized structure
```

Once information is transformed or merged, a reverse migration may be lossy.

Therefore rollback strategies include:

- backward-compatible application rollout;
- retained legacy columns;
- snapshots/backups;
- compensating transformations;
- forward-fix migrations;
- feature-flag rollback.

The safest rollback may be a **forward fix**, not an inverse DDL script.

---

# 56. Backup Before High-Risk Migration

For high-risk transformations, confirm:

- backup recency;
- restore test status;
- recovery point objectives;
- recovery time objectives;
- exact migration version;
- affected objects;
- rollback/forward-fix procedure.

A backup that has never been restored is only an assumption.

# 57. Migration Observability

Minimum useful metrics:

```text
migration status
elapsed time
rows processed
rows remaining
throughput

error count
replication lag
```

For backfills also record:

```text
last processed key
```

Log structured migration events.

# 58. Migration Alerting

Alert on conditions rather than merely duration.

Examples:

```text
lock wait > threshold
replica lag > threshold
backfill throughput drops sharply
error rate > 0
migration has not advanced for N intervals
unexpected row mismatch
```

“Migration still running” is not necessarily a failure.

“No progress” is a stronger signal.

# 59. Testing Strategy

A serious migration should be tested at several levels.

## L1 — SQL correctness

Does the script execute on representative schema/data?

## L2 — Data correctness

Do invariants hold?

## L3 — Concurrency

What happens with simultaneous application writes?

## L4 — Scale

Does performance remain acceptable at realistic row counts?

## L5 — Deployment compatibility

Can old and new application versions coexist?

## L6 — Failure recovery

What happens if the migration stops halfway?

## L7 — Rehearsal

Can the entire migration be run against production-like data and topology?

# 60. Failure Injection Exercises

Test deliberately:

1. kill the backfill worker halfway;
2. terminate a migration connection while a batch is active;
3. introduce a conflicting application update;
4. hold a lock with a long-running transaction;
5. introduce a violating row before validation;
6. pause a replica;
7. restart the application during dual-write;
8. make one representation intentionally diverge;
9. run the migration twice;
10. deploy an old application binary against the expanded schema.

The migration is production-ready only if failure behavior is understood.

# 61. Security Considerations

Schema changes can create security bugs.

Examples:

- a new column exposed through an API automatically;
- RLS policies not updated;
- a new table missing grants;
- a view accidentally exposing tenant data;
- a generated/derived field revealing sensitive information;
- migration roles having excessive privileges.

Check:

```text
ownership
privileges
RLS
views
functions
security definer behavior
search_path assumptions
```

PostgreSQL's schema documentation emphasizes deliberate schema ownership, privileges, search-path behavior, and the security implications of object placement and access configuration. citeturn503708search5

# 62. Schema Evolution and RLS

Suppose a new tenant-owned table is introduced.

Do not stop after:

```sql
CREATE TABLE tenant_reports (...);
```

Also define:

- tenant identity source;
- RLS policy;
- privileged-role behavior;
- indexes supporting tenant access;
- foreign-key ownership boundaries;
- audit requirements.

A schema migration is incomplete when it changes the isolation boundary but not the security model.

# 63. Performance Engineering During Migration

Track at least:

```text
query latency
lock waits
CPU
I/O
WAL
replica lag
vacuum activity
cache hit behavior
```

For changed query patterns, run:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Compare before and after.

Do not declare a migration successful merely because all rows were transformed.

It must preserve or intentionally change runtime performance characteristics.

# 64. Planner Statistics After Large Backfills

Large data changes can alter distributions.

After substantial migrations, verify statistics and planner behavior.

Potential actions depend on the migration, but the key question is:

> Does the planner understand the new data distribution?

Do not guess.

Measure representative queries before and after.

PostgreSQL 18 also improves major-upgrade behavior by preserving optimizer statistics during `pg_upgrade`, while extended statistics have separate considerations documented by PostgreSQL. citeturn503708search0

# 65. Migration Anti-Pattern: Giant One-Shot Update

```sql
UPDATE huge_table
SET new_value = complex_transform(old_value);
```

### Why it fails

- unbounded transaction;
- operationally large rollback;
- WAL spike;
- replica impact;
- vacuum pressure;
- poor progress visibility.

### Better

```text
chunk
→ commit
→ measure
→ adapt
→ continue
```

Chunk size should be evidence-driven.

---

# 66. Migration Anti-Pattern: `IF NOT EXISTS` Everywhere

This can hide incorrect state.

Example:

```sql
CREATE TABLE IF NOT EXISTS customers (...);
```

The table may exist with a different definition.

Therefore:

```text
idempotent migration
≠
blindly suppress every error
```

A robust migration verifies the intended state.

---

# 67. Migration Anti-Pattern: Manual Production Fix

Engineer runs:

```sql
ALTER TABLE production ...;
```

but forgets to encode the change in version control.

Now:

```text
production ≠ repository
```

This creates schema drift and makes future automation dangerous.

All persistent schema changes should have a durable, reviewed representation.

---

# 68. AI/Vibe-Coding Failure Modes

AI-generated migration SQL is especially risky because it often optimizes for syntactic validity rather than operational safety.

### Failure 1 — Rename without compatibility analysis

AI sees a clean rename and misses rolling deployments.

### Failure 2 — Giant backfill

AI produces one elegant `UPDATE` that is operationally disastrous at scale.

### Failure 3 — Unsafe constraint enforcement

AI adds a foreign key or `NOT NULL` without checking existing violations.

### Failure 4 — Incorrect rollback assumption

AI writes `down.sql` that cannot restore transformed information.

### Failure 5 — Blind index duplication

AI creates an index without checking equivalent existing indexes.

### Failure 6 — Ignoring replicas

AI tests only the primary.

### Failure 7 — Ignoring old application versions

AI assumes deployment is instantaneous.

### Failure 8 — Semantic loss

AI “normalizes” a historical snapshot into a mutable reference and silently destroys historical truth.

### Failure 9 — `IF NOT EXISTS` as error suppression

The script succeeds while leaving the wrong schema in place.

### Failure 10 — Missing observability

The migration runs but nobody knows whether it is progressing safely.

# 69. Evidence-Driven Migration Review

Before approval, require answers backed by evidence:

```text
row count?
index size?
longest transaction?
expected lock?
backfill duration?
WAL rate?
replica lag budget?
violation count?
rollback path?
old-version compatibility window?
```

Strong migration review sounds like:

> “The table contains 280 million rows, the backfill processes 10k rows per batch, observed p95 batch duration is 420 ms, replica lag remains below 3 seconds, and validation found zero violations.”

Weak review sounds like:

> “It should be fine.”

---

# 70. Migration Decision Framework

Use this sequence:

```text
1. What invariant or capability is changing?
2. Which consumers depend on the old contract?
3. Can the change be additive?
4. Can expand/contract reduce compatibility risk?
5. How much data must move?
6. Can the transformation be incremental?
7. What locks are required?
8. What happens under concurrent writes?
9. What is the replication impact?
10. What are the reconciliation invariants?
11. What is the rollback/forward-fix strategy?
12. What evidence proves completion?
```

If you cannot answer these questions, the migration is not fully designed.

## L1 — Recognition

Classify each as additive, relaxing, transformative, or breaking:

1. add nullable column;
2. rename column;
3. add FK;
4. drop index;
5. split table;
6. widen numeric precision;

is not equivalent operationally to:

```sql
ALTER TABLE orders
```

Design an expand/contract migration for:

```text
users.email → users.normalized_email
```

with rolling deployment support.

## L4 — Diagnosis

A migration is “stuck.” Diagnose:

- lock waits;
- long-running transactions;
- replica lag;
- stalled backfill;
- unexpected data violations.

## L5 — Optimization

Design a 500-million-row backfill that maintains a strict replica-lag budget.

## L6 — Architecture

Design a zero-downtime table decomposition for an ERP inventory aggregate consumed by API servers, reporting jobs, and CDC.

## L7 — Internal Mastery

Prove why a migration can be logically correct yet operationally unsafe.

# 75. Expert Mental Model

Think of every significant migration as a state machine:

```text
S0 = old schema
S1 = expanded schema
S2 = partially migrated data
S3 = dual-compatible runtime
S4 = fully migrated data
S5 = new runtime authoritative
S6 = legacy path removable
S7 = contract completed
```

Transitions have preconditions.

For example:

```text
S3 → S4
requires:
    backfill complete
    reconciliation passes
    no unacceptable drift
```

And:

```text
S5 → S6
requires:
    no remaining legacy consumers
```

This model is far more reliable than thinking:

> “Run migration 42 and deploy.”

---

# 76. The Deep Principle

Schema evolution is not about changing columns.

It is about changing **invariants and contracts over time without losing control of truth**.

A high-quality migration preserves five things:

```text
Correctness
Availability
Compatibility
Recoverability
Observability
```

Optimizing only for migration speed is dangerous.

A one-minute migration that corrupts semantics is worse than a one-hour migration that preserves them.

---

# 77. Production Readiness Criteria

You have mastered schema evolution when you can take a change request such as:

> “Replace this legacy customer field with a normalized tenant-aware model.”

and immediately reason about:

```text
entities
→ invariants
→ compatibility
→ migration phases
→ backfill
→ concurrency
→ locks
→ indexes
→ constraints
→ replication
→ security
→ observability
→ rollback/forward-fix
→ cutover
→ cleanup
```

You should be able to explain:

- why the obvious migration is unsafe;
- why the staged design is safer;
- what evidence proves each phase;
- how failure is recovered;
- what temporary complexity is introduced;
- when and how that complexity is removed.

---

# 78. Final Takeaway

> **A production schema is a living contract. Evolving it safely requires sequencing structural change, data transformation, invariant enforcement, application compatibility, and operational verification across time.**

The strongest database engineers do not ask only:

> “What SQL changes the schema?”

They ask:

> “What must be true before this change, what can be true during the transition, what must be true after cutover, and what evidence proves that those states are safe?”

That is the difference between writing migrations and engineering schema evolution.
