# 02.8 — Referential Integrity

> **Phase 02 — Relational Data Modeling**  
> Referential integrity is the discipline of ensuring that relationships between rows remain valid throughout the lifetime of the data.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to design, implement, inspect, troubleshoot, and operate PostgreSQL foreign-key relationships as **database invariants**, not merely application conventions.

You should be able to answer questions such as:

- What exactly does a foreign key guarantee?
- What is the difference between the **referenced** and **referencing** side?
- Why does a foreign key not automatically create an index on the child table?
- Why can an apparently harmless parent `DELETE` become an expensive operation?
- When should `ON DELETE CASCADE` be used, and when is it dangerous?
- What is the difference between `NO ACTION` and `RESTRICT`?
- Why is `ON UPDATE CASCADE` uncommon in mature systems?
- How do nullable foreign keys change relationship semantics?
- What do `MATCH SIMPLE` and `MATCH FULL` mean for composite foreign keys?
- How can concurrent transactions interact with referential-integrity checks?
- What happens when a foreign key is deferred?
- How do cascading actions interact with triggers?
- How do you diagnose a foreign-key failure from an error message back to the violated invariant?
- How should referential integrity be designed in a multi-tenant, financial, or high-volume system?

The target is not syntax memorization. The target is the ability to treat relationships as enforceable contracts between sets of rows.

## 2. The Core Definition

### 2.1 Simple definition

Referential integrity means:

> A row that points to another row must point to a valid row according to the relationship's declared rules.

Example:

```sql
CREATE TABLE customers (
    customer_id bigint PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(customer_id)
);
```

The database now guarantees that every non-null `orders.customer_id` corresponds to an existing `customers.customer_id` at the appropriate constraint-checking point.

### 2.2 Engineering definition

A foreign key creates a database-enforced invariant between:

- a **referencing relation**: the child/dependent table;
- a **referenced relation**: the parent/target table;
- a set of referencing columns;
- a target key made from a primary key, unique constraint, or other supported unique structure;
- and a set of referential actions governing parent updates/deletes.

### 2.3 Expert definition

Referential integrity is a constrained state transition system.

For a foreign key `F = child(a) -> parent(b)`, valid database states are those in which every referencing key that participates in the relationship has a corresponding target key, subject to the foreign key's null and match semantics.

The important architectural consequence is:

```text
Application correctness
        ↓
Database invariant
        ↓
Valid state space
```

An application may *attempt* to maintain the relationship.

The database constraint defines what states are actually legal.

# 3. First Principles

## 3.1 Why a relationship needs enforcement

Consider an application-level relationship:

```text
orders.customer_id → customers.customer_id
```

Without a foreign key, this can happen:

```text
customers
---------
1  Alice
2  Bob

orders
------
101  customer_id=1
102  customer_id=999   ← no such customer
```

The application may have intended `999` to be invalid.

The database, however, cannot infer that intention from a similarly named column.

Unless an invariant is declared, the database is allowed to store the value.

That produces **orphaned references**.

---

## 3.2 The database should protect invariants at the lowest reliable boundary

Suppose your system has:

```text
REST API
   ↓
Service
   ↓
ORM
   ↓
PostgreSQL
```

An application-only rule can be bypassed by:

- a background worker;
- an admin SQL session;
- a migration;
- a second service;
- a data-import script;
- a reporting pipeline with write access;
- a failed deployment that runs an old code path;
- an ORM bug;
- a race condition.

A PostgreSQL foreign key remains part of the database contract regardless of which legitimate client performs the write.

This does **not** mean every business rule belongs in the database. It means that a rule whose definition is fundamentally relational should normally have relational enforcement.

# 4. The Mental Model: Parent, Child, Reference

Terminology must be precise.

```text
                     REFERENCED TABLE
                +-----------------------+
                | customers             |
                |-----------------------|
                | customer_id   PK      |
                | name                  |
                +-----------+-----------+
                            ^
                            |
                            | referenced key
                            |
                +-----------+-----------+
                | orders                |
                |-----------------------|
                | order_id      PK      |
                | customer_id   FK      |
                +-----------------------+
                     REFERENCING TABLE
```

The terminology is from the foreign-key perspective:

| Concept | Meaning |
|---|---|
| Referenced table | The table whose key is being referenced |
| Referenced columns | The target key columns |
| Referencing table | The table containing the foreign key |
| Referencing columns | The columns holding the reference |
| Parent | Common application terminology for referenced row/table |
| Child | Common application terminology for referencing row/table |

Do not reason only with “parent” and “child.”

For diagnostics, metadata, and documentation, **referenced** and **referencing** are clearer.

# 5. Basic Foreign Key Syntax

## 5.1 Column-level form

```sql
CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    customer_id bigint REFERENCES customers(customer_id)
);
```

## 5.2 Table-level form

```sql
CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    customer_id bigint,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);
```

For production systems, explicit table-level constraints with meaningful names are often easier to inspect and operate.

Example naming convention:

```text
fk_<referencing_table>_<referenced_table>[_<purpose>]
```

Example:

```text
fk_orders_customer
fk_order_items_orders
fk_invoices_customer
fk_payments_invoice
```

# 6. The Referenced Side: What Can Be Referenced?

A foreign key does not simply point at any arbitrary column.

The target must provide an appropriate uniqueness guarantee. PostgreSQL documents foreign keys as referencing columns that are a primary key, a suitable unique constraint, or supported non-partial unique index structure. citeturn428092search0turn428092search1

Valid pattern:

```sql
CREATE TABLE customers (
    customer_id bigint PRIMARY KEY
);

CREATE TABLE orders (
    customer_id bigint
        REFERENCES customers(customer_id)
);
```

Also valid:

```sql
CREATE TABLE customers (
    customer_id bigint PRIMARY KEY,
    external_code text UNIQUE
);

CREATE TABLE orders (
    external_customer_code text
        REFERENCES customers(external_code)
);
```

The referenced value must identify a target row unambiguously under the target key semantics.

## 6.1 Why uniqueness matters

Suppose PostgreSQL allowed this:

```text
customers
---------
external_code = 'ACME'
external_code = 'ACME'
```

What would this mean?

```text
orders.external_code = 'ACME'
```

There is no unique target.

The relationship would be ambiguous.

Therefore a referential relationship needs a key-like target.

---

# 7. The Referencing Side Does Not Automatically Get an Index

This is one of the most important production facts.

Given:

```sql
CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(customer_id)
);
```

PostgreSQL does **not** automatically create an index on:

```sql
orders(customer_id)
```

The referenced side needs a unique lookup structure for the target key, but PostgreSQL does not automatically create the most appropriate index for the referencing side. citeturn428092search0turn428092search1

That distinction matters because parent-side deletes and updates may need to find referencing rows.

Recommended in many workloads:

```sql
CREATE INDEX idx_orders_customer_id
    ON orders(customer_id);
```

But this is not a universal rule. The correct index depends on the workload.

For example, if queries already use:

```sql
CREATE INDEX idx_orders_customer_status
    ON orders(customer_id, status);
```

that index may already support the necessary lookup for the foreign-key column because `customer_id` is the leading column.

---

# 8. Referential Integrity as an Invariant

Let:

```text
P = set of valid parent keys
C = set of child foreign-key values
```

With a non-null foreign key and a standard match condition:

```text
C ⊆ P
```

That is the core mental model.

Every child key must belong to the valid parent-key set.

When the parent changes, the invariant must remain valid.

When the child changes, the new reference must be valid.

Therefore these operations are linked:

```text
INSERT child
UPDATE child FK
DELETE parent
UPDATE parent key
```

Each can affect referential integrity.

---

# 9. Child INSERT Semantics

Suppose:

```sql
INSERT INTO orders(order_id, customer_id)
VALUES (1001, 42);
```

The database needs to determine whether `42` is a valid target key, subject to the foreign key's semantics.

If no corresponding customer exists and the constraint is active at that point, the statement fails.

Typical error class:

```text
ERROR: insert or update on table "orders" violates foreign key constraint "fk_orders_customer"
DETAIL: Key (customer_id)=(42) is not present in table "customers".
```

This is good information.

The database has converted an invalid state transition into a deterministic failure.

---

# 10. Child UPDATE Semantics

A child row can become invalid through an update even when it was valid before.

Example:

```sql
UPDATE orders
SET customer_id = 999
WHERE order_id = 1001;
```

If `999` does not exist, the foreign key rejects the transition.

Therefore referential integrity protects both:

```text
INSERT
UPDATE
```

on the referencing side.

---

# 11. Parent DELETE: The Hard Part

The interesting operation is:

```sql
DELETE FROM customers
WHERE customer_id = 42;
```

What should happen if orders still reference `42`?

There are multiple valid business semantics.

PostgreSQL therefore does not assume one universal behavior. The foreign key declaration defines the action.

The major actions are:

```text
NO ACTION
RESTRICT
CASCADE
SET NULL
SET DEFAULT
```

PostgreSQL documents `NO ACTION` as the default and distinguishes it from `RESTRICT`, especially with respect to deferral. citeturn428092search0turn428092search1

---

# 12. `ON DELETE NO ACTION`

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE NO ACTION
```

This means:

> Do not permit the database to finish in a state where the foreign-key relationship is violated.

For an immediate constraint, an attempted parent deletion that would leave referencing rows causes an error.

For a deferred constraint, PostgreSQL can postpone the final check until the constraint-checking point. citeturn428092search0turn428092search1

`NO ACTION` is the default.

A useful mental model is:

```text
Parent delete
     ↓
Would child references become invalid?
     ↓ yes
Constraint must fail unless the transaction repairs the relationship
```

---

# 13. `ON DELETE RESTRICT`

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE RESTRICT
```

`RESTRICT` is stricter operationally.

It prevents the parent modification immediately when referencing rows exist and does not allow the constraint itself to be deferred in the way `NO ACTION` can. PostgreSQL explicitly documents this distinction. citeturn428092search0turn428092search1

### 13.1 Practical distinction

```text
NO ACTION
    “The final state must be valid.”

RESTRICT
    “This parent operation is not allowed while references exist.”
```

This distinction becomes relevant in complex transactions where rows can temporarily move through intermediate states.

---

# 14. `ON DELETE CASCADE`

```sql
FOREIGN KEY (order_id)
REFERENCES orders(order_id)
ON DELETE CASCADE
```

The semantic meaning is:

> Deleting the referenced row automatically deletes rows that reference it.

Classic example:

```sql
CREATE TABLE orders (
    order_id bigint PRIMARY KEY
);

CREATE TABLE order_items (
    order_item_id bigint PRIMARY KEY,
    order_id bigint NOT NULL
        REFERENCES orders(order_id)
        ON DELETE CASCADE
);
```

Now:

```sql
DELETE FROM orders
WHERE order_id = 500;
```

causes associated `order_items` rows to be deleted as part of the referential action. PostgreSQL documents cascading actions as changes on the referencing table, and those resulting changes can fire triggers defined on that table. citeturn428092search0turn428092search3

---

# 15. When CASCADE Is Appropriate

A strong rule:

> Use `CASCADE` when the child is genuinely part of the parent's lifecycle and does not have an independent business identity that should survive independently.

Good examples:

```text
order → order_items
invoice → invoice_lines
workflow → workflow_nodes
cart → cart_items
```

Potentially dangerous examples:

```text
customer → invoices
customer → legal_documents
product → historical_sales
user → audit_events
```

Why?

Because those child rows may represent:

- historical facts;
- compliance evidence;
- financial records;
- audit information;
- independent business entities.

Deleting the parent should not necessarily erase history.

---

# 16. The CASCADE Trap

Imagine:

```text
tenant
  ↓ CASCADE
users
  ↓ CASCADE
orders
  ↓ CASCADE
order_items
  ↓ CASCADE
payments
```

One command:

```sql
DELETE FROM tenants
WHERE tenant_id = 10;
```

could cause a large cascade.

This is not inherently wrong.

But the operational cost can be enormous.

Potential consequences include:

- many row deletes;
- index updates;
- WAL generation;
- trigger execution;
- locking;
- replication lag;
- vacuum/dead-row cleanup work;
- long transactions;
- large rollback cost if something fails;
- application surprises.

Therefore:

```text
CASCADE = semantic convenience + operational responsibility
```

Never interpret `CASCADE` as “free cleanup.”

---

# 17. `ON DELETE SET NULL`

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE SET NULL
```

When the parent disappears, the child reference is cleared.

This represents an optional relationship.

Example:

```sql
CREATE TABLE support_tickets (
    ticket_id bigint PRIMARY KEY,
    assigned_agent_id bigint,
    CONSTRAINT fk_ticket_agent
        FOREIGN KEY (assigned_agent_id)
        REFERENCES agents(agent_id)
        ON DELETE SET NULL
);
```

If an agent record is deleted, the ticket remains, but the assignment disappears.

This is appropriate when:

```text
child can exist without that parent reference
```

It is inappropriate when the foreign-key column is part of an invariant requiring a value.

For example:

```sql
assigned_agent_id bigint NOT NULL
    REFERENCES agents(agent_id)
    ON DELETE SET NULL
```

would be contradictory because the resulting `NULL` would violate `NOT NULL`.

---

# 18. `SET DEFAULT`

Example:

```sql
CREATE TABLE documents (
    document_id bigint PRIMARY KEY,
    owner_id bigint DEFAULT 0,
    FOREIGN KEY (owner_id)
        REFERENCES users(user_id)
        ON DELETE SET DEFAULT
);
```

The default value must itself satisfy the foreign-key rule when it is non-null. PostgreSQL documents that a `SET DEFAULT` action does not bypass the foreign-key requirement. citeturn428092search0turn428092search1

A practical pattern is a sentinel row:

```text
user_id = 0
name = 'System / Deleted User'
```

Then deleting an account could reassign references to that row.

However, this should be a deliberate domain decision, not a generic trick.

Often an explicit archival/deactivation model is clearer than physically deleting the referenced entity.

---

# 19. The Decision Matrix for ON DELETE

| Business meaning | Typical action |
|---|---|
| Child cannot exist independently | `CASCADE` |
| Parent should not be deleted while referenced | `RESTRICT` or `NO ACTION` |
| Child survives, relationship becomes absent | `SET NULL` |
| Child should move to a defined fallback | `SET DEFAULT` |
| Final validity matters and transaction may repair state | `NO ACTION` |

Never choose the action first and invent a justification later.

Start from lifecycle semantics.

---

# 20. `ON UPDATE`

Foreign keys can also define actions when referenced columns change.

Example:

```sql
FOREIGN KEY (customer_code)
REFERENCES customers(customer_code)
ON UPDATE CASCADE
```

The available referential actions are analogous to `ON DELETE`, with PostgreSQL documenting the corresponding semantics. citeturn428092search0turn428092search1

---

# 21. Why ON UPDATE CASCADE Is Less Common

Modern schemas usually avoid changing primary identifiers.

Example:

```text
customer_id = immutable surrogate identifier
```

A natural identifier such as:

```text
customer_code
email
phone_number
sku
```

may change for legitimate reasons, but it often should not be used as a mutable relational identity if a stable surrogate or immutable business identifier exists.

That leads to:

```text
Stable PK
    ↓
References remain stable
    ↓
Fewer cascading updates
```

So the architectural preference is often:

> Make relational identifiers stable rather than designing a system that frequently has to update them transitively.

---

# 22. `NO ACTION` vs `RESTRICT`: The Expert Distinction

This distinction is frequently misunderstood.

Consider:

```sql
CREATE TABLE parent (
    id bigint PRIMARY KEY
);

CREATE TABLE child (
    id bigint PRIMARY KEY,
    parent_id bigint,
    CONSTRAINT fk_child_parent
        FOREIGN KEY (parent_id)
        REFERENCES parent(id)
        ON DELETE NO ACTION
        DEFERRABLE INITIALLY DEFERRED
);
```

A transaction can potentially perform a sequence such as:

```sql
BEGIN;

DELETE FROM parent WHERE id = 10;

-- temporarily no child may reference the row
DELETE FROM child WHERE parent_id = 10;

COMMIT;
```

The final state can be valid.

By contrast, `RESTRICT` disallows the parent deletion when referencing rows already exist and cannot be postponed through constraint deferral. PostgreSQL explicitly documents this difference. citeturn428092search0turn428092search1

This is why `NO ACTION` is not simply a synonym for `RESTRICT`.

---

# 23. Nullable Foreign Keys

This is another major source of production confusion.

Consider:

```sql
customer_id bigint
    REFERENCES customers(customer_id)
```

Because the column is nullable, a row can contain:

```text
customer_id = NULL
```

Under the default `MATCH SIMPLE` semantics, a foreign-key row with a null referencing component can escape the matching requirement. PostgreSQL documents this explicitly. citeturn428092search0turn428092search1

Therefore:

```text
FOREIGN KEY
```

does **not** automatically mean:

```text
must always point to a parent
```

It means the relationship applies under the FK's null/match semantics.

If a relationship is mandatory:

```sql
customer_id bigint NOT NULL
    REFERENCES customers(customer_id)
```

Use both constraints.

---

# 24. Optional vs Mandatory Relationships

Think in domain terms.

### Mandatory

```text
Every order belongs to a customer.
```

Model:

```sql
customer_id bigint NOT NULL
    REFERENCES customers(customer_id)
```

### Optional

```text
A support ticket may have an assigned agent.
```

Model:

```sql
assigned_agent_id bigint
    REFERENCES agents(agent_id)
```

The difference is not cosmetic.

It defines the allowed state space.

---

# 25. Composite Foreign Keys

Relationships may involve multiple columns.

Example:

```sql
CREATE TABLE stores (
    tenant_id bigint,
    store_id bigint,
    PRIMARY KEY (tenant_id, store_id)
);

CREATE TABLE products (
    tenant_id bigint,
    store_id bigint,
    product_id bigint,
    PRIMARY KEY (tenant_id, product_id),
    FOREIGN KEY (tenant_id, store_id)
        REFERENCES stores(tenant_id, store_id)
);
```

The relationship is now defined by a tuple:

```text
(tenant_id, store_id)
```

not by either column independently.

---

# 26. Why Composite FKs Are Powerful for Multi-Tenant Data

Suppose:

```text
Tenant A → Store 1
Tenant B → Store 1
```

A global `store_id` alone is insufficient to guarantee tenant-local identity.

A composite key can encode:

```text
(tenant_id, store_id)
```

Then a child row cannot accidentally reference:

```text
tenant A + store 1
```

while claiming:

```text
tenant B
```

This is an important defense against **cross-tenant referential leaks**.

The invariant becomes:

```text
child.tenant_id = parent.tenant_id
AND
child.store_id = parent.store_id
```

rather than:

```text
child.store_id = parent.store_id
```

alone.

---

# 27. Composite FK Null Semantics: MATCH SIMPLE

PostgreSQL's default is:

```sql
MATCH SIMPLE
```

For a composite foreign key, if a referencing component is null, the row can avoid the normal matching requirement. PostgreSQL documents this behavior. citeturn428092search0turn428092search1

Example:

```text
tenant_id = 10
store_id  = NULL
```

can bypass the foreign-key match under `MATCH SIMPLE`.

That may or may not be what your domain allows.

---

# 28. MATCH FULL

With:

```sql
FOREIGN KEY (tenant_id, store_id)
REFERENCES stores(tenant_id, store_id)
MATCH FULL
```

the composite reference escapes the matching requirement only when **all** referencing columns are null. A mixture of null and non-null values is not allowed to evade the relationship. citeturn428092search0turn428092search1

So:

```text
(10, NULL)   → invalid under MATCH FULL
(NULL, 1)    → invalid under MATCH FULL
(NULL, NULL) → allowed to mean no relationship
```

This is useful when the relationship is semantically all-or-nothing.

---

# 29. MATCH PARTIAL

The SQL grammar exposes `MATCH PARTIAL`, but PostgreSQL 18 documents it as not implemented. citeturn428092search1

Do not design a PostgreSQL schema assuming partial matching exists simply because it appears in SQL terminology.

Version-sensitive features should always be verified against the PostgreSQL version you deploy.

---

# 30. Referential Actions Are Database Operations

A crucial internal-behavior insight is that cascading referential actions affect the referencing rows as actual data modifications.

PostgreSQL documents that foreign-key referential actions are performed as ordinary SQL `UPDATE` or `DELETE` operations on the referencing table, and triggers on that table can therefore fire. citeturn428092search3

This means a cascade can trigger additional application/database behavior such as:

```text
DELETE parent
   ↓
CASCADE child DELETE
   ↓
child DELETE triggers
   ↓
additional writes
   ↓
more triggers / side effects
```

Therefore a cascade can have a larger operational footprint than the DDL statement visually suggests.

---

# 31. Referential Integrity and Triggers

Suppose:

```sql
CREATE TRIGGER trg_order_item_delete
AFTER DELETE ON order_items
FOR EACH ROW
EXECUTE FUNCTION audit_order_item_delete();
```

When an `orders` row is deleted with:

```text
ON DELETE CASCADE
```

the resulting deletion of `order_items` can fire this trigger. PostgreSQL explicitly documents this behavior for cascading referential actions. citeturn428092search3

This creates a production design question:

> Is the trigger behavior expected for both explicit child deletes and FK-generated child deletes?

Usually the answer should be yes and the trigger should be designed accordingly.

# 32. Application Deletion vs Database Cascade

There are two broad strategies.

## Strategy A — Explicit application orchestration

```text
DELETE child rows
DELETE parent row
```

Advantages:

- explicit control;
- easier to reason about business workflow;
- can emit domain events intentionally;
- can batch work.

Disadvantages:

- every writer must remember the ordering;
- race conditions are easier to introduce;
- another writer can bypass the workflow;
- database state can become inconsistent unless constraints still protect it.

## Strategy B — Database cascade

```sql
ON DELETE CASCADE
```

Advantages:

- invariant is centralized;
- one transaction controls the relationship;
- no application path can accidentally forget dependent cleanup;
- multiple clients share the same rule.

Disadvantages:

- potentially surprising implicit work;
- large cascades can be expensive;
- business workflows can be too complex for automatic deletion;
- trigger interactions require care.

The correct decision depends on lifecycle semantics and workload.

---

# 33. A Common Wrong Implementation

### Naive approach

```text
“Whenever a customer is deleted, the API first deletes orders, then deletes customer.”
```

### Why it fails

Another code path may do:

```sql
DELETE FROM customers WHERE customer_id = 42;
```

Now the relationship rule exists only in application code.

### Improved approach

Use the database constraint to encode the relational invariant.

Then decide separately whether the lifecycle action should be:

```text
RESTRICT
CASCADE
SET NULL
```

### Why it works

The database remains the authoritative enforcement boundary.

---

# 34. Another Wrong Implementation: CASCADE Everything

### Naive approach

```sql
ON DELETE CASCADE
```

on every foreign key.

### Why it fails

Not all relationships represent ownership.

Consider:

```text
customer → invoice
```

A customer deletion should not necessarily destroy invoices.

The child may represent historical business truth.

### Improved approach

Classify the relationship:

```text
composition      → often CASCADE
association      → often RESTRICT/NO ACTION
optional link    → often SET NULL
retained history → often prevent parent deletion
```

### Production rule

A foreign-key action must reflect lifecycle semantics, not developer convenience.

---

# 35. Referential Integrity and Soft Deletes

Suppose you use:

```sql
deleted_at timestamptz
```

instead of physical deletion.

Then:

```sql
UPDATE customers
SET deleted_at = now()
WHERE customer_id = 42;
```

does not trigger `ON DELETE` because the row is not being physically deleted.

This is a very important distinction.

```text
Soft delete
    ≠
DELETE
```

A foreign key enforces physical row existence, not necessarily your application-level notion of “active.”

Therefore this row is still a valid FK target:

```text
customers
---------
customer_id=42
status='deleted'
```

unless you implement an additional constraint/modeling mechanism.

---

# 36. Foreign Keys Do Not Encode Arbitrary Business Eligibility

This is a common design error.

Suppose an order may reference only an **active** customer.

A normal FK:

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
```

guarantees existence, not:

```text
customers.status = 'ACTIVE'
```

Why?

Because referential integrity answers:

> Does a matching target key exist?

It does not automatically answer:

> Is that target currently business-eligible?

That second requirement may need:

- application logic;
- additional schema design;
- a separate status invariant;
- controlled state transitions;
- views or service policy.

Do not overestimate what a foreign key guarantees.

---

# 37. Referential Integrity and Historical Records

A mature system frequently distinguishes:

```text
current relational dependency
```

from:

```text
historical identity
```

Example:

```text
invoice.customer_id → customers.customer_id
```

If a customer is legally merged or deactivated, destroying the target row may be inappropriate because invoices need an auditable customer association.

Better domain models may use:

```text
status = MERGED
merged_into_customer_id = ...
```

or an archival strategy.

The lesson is:

> Referential integrity often tells you that a row must remain referentially addressable; it does not require physical deletion as the primary lifecycle mechanism.

---

# 38. Self-Referential Foreign Keys

A table can reference itself.

Example:

```sql
CREATE TABLE employees (
    employee_id bigint PRIMARY KEY,
    manager_id bigint,
    CONSTRAINT fk_employee_manager
        FOREIGN KEY (manager_id)
        REFERENCES employees(employee_id)
);
```

This models:

```text
employee → manager
```

A manager is itself an employee.

The same relational concepts apply:

- nullability means whether a manager is optional;
- FK enforcement guarantees the referenced employee exists;
- delete actions define what happens when a manager row is deleted.

But business constraints such as:

```text
employee cannot manage itself
```

may require an additional constraint or application rule.

---

# 39. Cyclic Relationships

More difficult models contain cycles.

Example:

```text
A → B
B → C
C → A
```

Cycles can complicate:

- insertion ordering;
- deletion ordering;
- migration;
- constraint timing;
- data import;
- bootstrapping.

This is where deferrable foreign keys become highly relevant, which will be covered explicitly in **02.9 — Deferrable Constraints**.

Do not treat a cyclic graph as merely a syntax problem.

It is a transaction-ordering problem.

---

# 40. Referential Integrity and Transactions

The database must reason about relationships inside transactions.

Example:

```sql
BEGIN;

INSERT INTO orders(order_id, customer_id)
VALUES (1001, 42);

INSERT INTO customers(customer_id, name)
VALUES (42, 'Alice');

COMMIT;
```

Whether this is permitted at statement time depends on the constraint's timing configuration.

With the usual immediate constraint, the first insert cannot rely on a parent row that has not yet been created.

With a suitable deferred FK, the transaction can temporarily move through an intermediate state and become valid before commit.

This distinction is foundational:

```text
statement validity
        vs
transaction validity
```

---

# 41. Concurrency: The Hidden Dimension

Referential integrity exists in a concurrent system, not an isolated script.

Imagine two transactions:

```text
T1                         T2
---------------------      ---------------------
read parent 42             delete parent 42
insert child -> 42
```

A correct database implementation cannot simply perform a naive application-level “check then insert” and assume the result is safe.

The important principle is:

> A referential constraint must remain correct under concurrent state transitions, not merely under sequential examples.

This is one reason database-enforced constraints are stronger than code such as:

```ts
const parent = await repo.findById(id);
if (parent) {
  await childRepo.insert({ parentId: id });
}
```

That application sequence is vulnerable to races unless the database transaction/locking/constraint semantics make the operation safe.

---

# 42. The Check-Then-Insert Race

### Incorrect pattern

```text
1. SELECT customer WHERE id = 42
2. If found, INSERT order(customer_id=42)
```

Possible interleaving:

```text
T1: SELECT customer 42 → exists
T2: DELETE customer 42
T1: INSERT order(customer_id=42)
```

Without database enforcement, the child can become orphaned.

With the FK, the database handles the relationship's correctness according to transactional rules.

The correct architectural principle is:

```text
pre-check may improve UX
constraint guarantees correctness
```

---

# 43. Foreign-Key Index Design

Because parent deletes/updates may need to identify referencing rows, indexing the FK columns is often important. PostgreSQL's documentation explicitly recommends considering an index on referencing columns, while noting that the FK declaration itself does not create one. citeturn428092search0turn428092search1

Example:

```sql
CREATE INDEX idx_order_items_order_id
    ON order_items(order_id);
```

This can improve operations such as:

```sql
DELETE FROM orders
WHERE order_id = 500;
```

when PostgreSQL must locate dependent `order_items` rows.

---

# 44. Why Missing FK Indexes Can Become a Production Incident

Suppose:

```text
orders          = 10 million rows
order_items     = 80 million rows
```

and:

```sql
DELETE FROM orders
WHERE order_id = 12345;
```

Without a suitable child-side index, finding referencing rows can become much more expensive than expected.

A schema may perform fine under development data and fail dramatically at production scale.

This leads to an important review question:

> For every high-volume foreign key, what access path supports parent-side update/delete checks?

---

# 45. Do Not Blindly Index Every Foreign Key

The previous section does not mean:

```text
Every FK → CREATE INDEX
```

without thought.

Consider:

```text
existing composite index:
(tenant_id, customer_id, created_at)
```

A new index on:

```text
(customer_id)
```

may be redundant or less useful.

You must consider:

- query workload;
- column order;
- parent-delete/update frequency;
- selectivity;
- index size;
- write amplification;
- existing indexes;
- partitioning.

This is why production indexing remains workload-driven.

---

# 46. Foreign Keys and Partitioning

Partitioned systems introduce additional design considerations.

Before adopting a complex partitioning strategy, verify the exact PostgreSQL version's supported foreign-key behavior and operational characteristics for your model.

The principles remain:

```text
relationship correctness
+
partition routing
+
index strategy
+
maintenance behavior
```

Do not assume that a foreign key behaves operationally like a foreign key between two small heap tables simply because the SQL declaration looks identical.

Version-specific behavior should be tested on the exact PostgreSQL release used in production.

---

# 47. Multi-Tenant Referential Integrity

Consider this bad model:

```sql
CREATE TABLE products (
    product_id bigint PRIMARY KEY,
    tenant_id bigint NOT NULL
);

CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    tenant_id bigint NOT NULL,
    product_id bigint NOT NULL REFERENCES products(product_id)
);
```

The FK guarantees:

```text
orders.product_id → some products.product_id
```

But it does **not** guarantee:

```text
orders.tenant_id = products.tenant_id
```

That means a child from tenant A could potentially reference a product belonging to tenant B, if the application supplies matching IDs.

This is a serious multi-tenant integrity flaw.

---

# 48. Composite Tenant-Aware Foreign Keys

A stronger model is:

```sql
CREATE TABLE products (
    tenant_id bigint NOT NULL,
    product_id bigint NOT NULL,
    PRIMARY KEY (tenant_id, product_id)
);

CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    product_id bigint NOT NULL,
    PRIMARY KEY (tenant_id, order_id),
    CONSTRAINT fk_order_product
        FOREIGN KEY (tenant_id, product_id)
        REFERENCES products(tenant_id, product_id)
);
```

Now the database-level invariant includes tenant identity.

This is often much stronger than relying on every service to remember:

```text
WHERE tenant_id = currentTenant
```

for every relationship.

---

# 49. Referential Integrity vs Row-Level Security

These solve different problems.

```text
Foreign key
    → Is the referenced row structurally valid?

RLS / authorization policy
    → Is this role/session allowed to access or modify the row?
```

A valid foreign-key relationship does not imply that the current user is authorized to operate on either row.

Conversely, an authorization policy does not replace a structural foreign key.

Keep these concerns separate.

---

# 50. Referential Integrity in Financial Systems

Financial data deserves stricter lifecycle design.

Consider:

```text
invoice
invoice_line
payment
ledger_entry
```

Potential relationships:

```text
invoice → invoice_lines
invoice → payments
invoice → ledger_entries
```

An `invoice → invoice_lines` relationship may reasonably use `CASCADE` in a system where invoices are draft-only and physically deletable.

But once an invoice becomes a legally significant historical record, physical deletion may be prohibited by business policy.

Then the model may evolve toward:

```text
immutable invoice
      ↓
status transitions
      ↓
void / cancel / reverse
```

rather than deletion.

Referential integrity and data lifecycle architecture therefore need to be designed together.

---

# 51. Referential Integrity and Immutable Data

Suppose:

```text
ledger_entries
```

are append-only.

Then a parent entity may never be physically deleted.

The FK can remain strict:

```sql
FOREIGN KEY (...)
REFERENCES accounts(...)
ON DELETE RESTRICT
```

This aligns physical storage behavior with financial semantics.

The relationship itself becomes a historical guarantee:

```text
Every ledger entry points to an existing account identity.
```

---

# 52. Referential Integrity and Data Import

Large imports often reveal hidden relationship problems.

Suppose you import:

```text
orders.csv
products.csv
customers.csv
```

If you load child rows first with immediate FKs, inserts may fail because parents are not yet present.

Possible strategies include:

- load referenced data first;
- stage data before enforcing production constraints;
- use deferrable constraints where appropriate;
- use controlled migration sequencing.

Do not disable all constraints casually just to make an import succeed.

That can convert a loading-order problem into permanent integrity debt.

---

# 53. Referential Integrity During Schema Migration

Suppose you introduce:

```sql
customer_id bigint NOT NULL
    REFERENCES customers(customer_id)
```

to a large existing table.

You must solve two distinct problems:

```text
1. Existing rows are valid.
2. Future rows cannot become invalid.
```

A migration may need to:

```text
backfill existing data
→ remove bad references
→ enforce the relationship
→ make nullability stricter
```

Large production migrations should consider locks, transaction duration, validation cost, and deployment sequencing.

Referential integrity is not just a DDL concern; it is a migration concern.

# 54. Diagnostic Workflow for FK Failures

When PostgreSQL reports:

```text
violates foreign key constraint
```

do not immediately edit the application.

Use an evidence-first workflow.

### Step 1 — Identify the exact constraint

Example:

```text
fk_orders_customer
```

### Step 2 — Identify the referencing table/column

```text
orders.customer_id
```

### Step 3 — Identify the referenced target

```text
customers.customer_id
```

### Step 4 — Inspect the actual value

```sql
SELECT customer_id
FROM orders
WHERE order_id = 1001;
```

### Step 5 — Inspect the target

```sql
SELECT customer_id
FROM customers
WHERE customer_id = 42;
```

### Step 6 — Determine the violated transition

Was it:

```text
INSERT child?
UPDATE child?
DELETE parent?
UPDATE parent key?
```

### Step 7 — Determine whether the data or the workflow is wrong

A failed constraint may expose:

- a genuine bug;
- an ordering issue;
- a race;
- an incorrect delete policy;
- stale external data;
- bad migration ordering.

The error is evidence, not merely an obstacle.

# 55. Inspecting Foreign Keys in PostgreSQL

## 55.1 Information schema

A convenient metadata view is:

```sql
SELECT
    constraint_name,
    unique_constraint_name,
    match_option,
    update_rule,
    delete_rule
FROM information_schema.referential_constraints
WHERE constraint_schema = 'public';
```

PostgreSQL documents `referential_constraints` as a view containing referential constraints visible to the current user, including match and update/delete rules. citeturn428092search2

## 55.2 Catalog-level inspection

For deeper PostgreSQL-specific diagnostics, inspect:

```sql
SELECT
    conname,
    contype,
    conrelid::regclass AS referencing_table,
    confrelid::regclass AS referenced_table,
    convalidated,
    condeferrable,
    condeferred
FROM pg_constraint
WHERE contype = 'f';
```

This is particularly useful when investigating migrations and constraint state.

# 56. Naming Constraints for Operations

Avoid:

```sql
CONSTRAINT fk1
```

Prefer:

```sql
CONSTRAINT fk_order_items_order
```

Why?

Because production errors, migration logs, and schema inspection frequently identify constraints by name.

A good name can answer:

```text
what table?
what relationship?
what direction?
```

A bad name forces unnecessary catalog exploration during incidents.

# 57. Referential Integrity Error Handling in Node.js

In Node/NestJS applications, map database errors intentionally.

Conceptually:

```text
PostgreSQL constraint violation
          ↓
Database driver error
          ↓
Repository/data-access layer
          ↓
Domain/application error
          ↓
HTTP/API response
```

Do not expose raw PostgreSQL internals directly to clients.

Instead, translate them into domain-meaningful outcomes such as:

```text
CUSTOMER_NOT_FOUND
ORDER_REFERENCED
ENTITY_HAS_DEPENDENCIES
INVALID_RELATIONSHIP
```

But preserve the original database evidence in internal logs.

# 58. Do Not Replace FK Errors with Silent Success

Bad pattern:

```ts
try {
  await repo.deleteCustomer(id);
} catch {
  return { success: true };
}
```

This is dangerous because the database may have correctly rejected a destructive operation.

A foreign-key error is often a valuable domain signal:

```text
This customer still has protected dependent records.
```

The API should communicate the business outcome rather than pretending the operation succeeded.

# 59. Referential Integrity and Idempotency

Suppose an API creates an order:

```text
POST /orders
```

with:

```text
customer_id = 42
```

The FK guarantees structural validity, but not idempotency.

You still may need:

```text
idempotency_key UNIQUE
```

This illustrates a broader lesson:

> One constraint should solve one invariant well. Do not expect foreign keys to solve unrelated consistency problems.

# 60. Referential Integrity and Unique Constraints

Consider:

```sql
customers.customer_id PRIMARY KEY
```

and:

```sql
orders.customer_id REFERENCES customers(customer_id)
```

The relationship depends on the uniqueness semantics of the target.

Therefore referential integrity is deeply connected to Phase 02 topics already covered:

```text
Keys
↓
Uniqueness
↓
Foreign-key target
↓
Referential integrity
```

This is why data modeling should be learned as a system rather than as isolated DDL keywords.

# 61. Referential Integrity and Normalization

Normalization reduces duplication.

Foreign keys preserve the relationships between normalized entities.

For example:

```text
customers
    ↓
orders
    ↓
order_items
```

Without foreign keys, normalized tables can still contain invalid relationships.

So:

```text
Normalization
    = structure

Referential integrity
    = relationship validity
```

They solve different problems and work together.

---

# 62. Referential Integrity and Denormalization

Denormalized systems often add copies of values.

Example:

```text
order.customer_name_snapshot
```

alongside:

```text
order.customer_id → customers.customer_id
```

The FK protects the identity relationship.

The snapshot is a separate representation with separate consistency semantics.

This distinction matters:

```text
FK = structural relationship invariant
snapshot = representation consistency contract
```

Do not remove a foreign key merely because a denormalized display field exists.

# 63. Production Scenario: Jewellery ERP

Consider a multi-branch jewellery ERP:

```text
tenant
  ↓
branches
  ↓
users
  ↓
orders
  ↓
order_items
  ↓
payments
```

A naive model might use only IDs:

```text
order.branch_id
order.user_id
order.customer_id
```

but not enforce tenant consistency.

A stronger design asks:

```text
Does the order's branch belong to the same tenant?
Does the order's user belong to the same tenant?
Does the customer belong to the same tenant?
```

Where tenant identity is part of the relational key, composite FKs can encode the cross-entity tenant invariant directly.

For financially sensitive records, deletion should usually be treated as a domain lifecycle decision rather than automatically cascading through every historical record.

The key architectural principle is:

```text
Tenant boundary
    ↓
Relational key design
    ↓
Foreign-key enforcement
    ↓
Reduced cross-tenant integrity risk
```

# 64. Production Scenario: Order → Order Items

Model:

```sql
CREATE TABLE orders (
    order_id bigint PRIMARY KEY
);

CREATE TABLE order_items (
    order_item_id bigint PRIMARY KEY,
    order_id bigint NOT NULL,
    quantity integer NOT NULL,
    CONSTRAINT fk_order_items_order
        FOREIGN KEY (order_id)
        REFERENCES orders(order_id)
        ON DELETE CASCADE
);

CREATE INDEX idx_order_items_order_id
    ON order_items(order_id);
```

Why this design is strong:

- an item cannot exist without an order;
- deleting an order removes owned items;
- child-side lookup can be efficient;
- the constraint is named;
- the lifecycle semantics are explicit.

But this assumes historical order deletion is genuinely permitted.

For finalized financial orders, a different lifecycle may be more appropriate.

---

# 65. Production Scenario: Customer → Invoice

A safer default in many business systems is:

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(customer_id)
ON DELETE RESTRICT
```

Why?

Because deleting a customer while invoices still reference that customer can be a business and compliance problem.

A common architecture is:

```text
customer status → INACTIVE / ARCHIVED
```

rather than:

```text
DELETE customer
```

This preserves referential identity while changing lifecycle state.

---

# 66. Production Scenario: User → Audit Events

Audit data is often intended to outlive the user account.

Bad design:

```sql
user_id REFERENCES users(user_id)
ON DELETE CASCADE
```

If the user is deleted, audit events disappear.

That may destroy accountability.

Potential alternatives include:

```text
prevent user deletion
```

or:

```text
retain a tombstone identity
```

or:

```text
store an immutable actor snapshot plus carefully designed identity relationship
```

The correct solution depends on legal, privacy, and operational requirements.

# 67. Referential Integrity and Privacy / Erasure

Privacy-driven deletion creates a difficult tension:

```text
Need to remove personal data
          vs
Historical records need stable relational identity
```

A robust system may separate:

```text
personally identifying attributes
```

from:

```text
business identity / historical key
```

Then erasure can target personal attributes without destroying the structural history required by the system.

Referential integrity therefore needs to participate in privacy architecture, not be designed independently from it.

# 68. Referential Integrity and Large Deletes

A command such as:

```sql
DELETE FROM tenants
WHERE tenant_id = 10;
```

can be deceptively small in SQL text while representing a large amount of work because of cascades.

Before executing a large deletion in production, understand:

```text
dependency graph
row counts
indexes
triggers
locks
WAL volume
replicas
rollback impact
```

A safe operational workflow may be:

```text
identify dependencies
→ estimate cardinalities
→ archive if required
→ delete in controlled batches where appropriate
→ monitor locks/WAL/replication
→ validate postconditions
```

Do not confuse a one-line SQL command with a one-row operation.

# 69. Referential Graph Thinking

Treat the schema as a directed graph:

```text
A ← B ← C ← D
```

where arrows represent foreign-key dependency direction.

Now ask:

```text
Which tables depend on this table?
How deep is the graph?
Where do cascades stop?
Which edges are optional?
Which edges are historical?
Where are cycles?
```

This graph model is extremely useful for:

- deletes;
- migrations;
- archival;
- tenant removal;
- data exports;
- backups;
- GDPR-style erasure analysis;
- incident response.

# 70. Delete Dependency Discovery

When analyzing a table, do not look only at its direct FKs.

A production deletion can have transitive effects:

```text
customer
 ↓
orders
 ↓
order_items
 ↓
item_allocations
 ↓
stock_movements
```

The safe question is:

> What is the transitive dependency closure of this row?

This is much more powerful than asking:

> Which tables directly reference this one?

# 71. Foreign Keys and Performance: Measure, Don't Guess

When a parent delete is slow, investigate.

Use evidence such as:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

for representative queries and inspect:

- index usage;
- row counts;
- scans;
- execution time;
- buffer activity;
- locking behavior.

For the relationship itself, inspect the actual indexes available on the referencing table.

Do not add five indexes because “foreign keys should always be indexed.”

Do not remove an index because “the query planner usually handles it.”

Measure the workload.

# 72. Locking and Referential Actions

Foreign-key operations can interact with locks on referenced and referencing rows/tables.

In a high-concurrency system, a seemingly small operation such as:

```sql
DELETE FROM parent WHERE id = 42;
```

can contend with concurrent child inserts or updates.

Potential symptoms:

```text
slow deletes
blocked inserts
waiting transactions
long lock chains
unexpected latency spikes
```

The debugging principle is:

```text
application latency
     ↓
SQL statement latency
     ↓
lock wait vs execution time
     ↓
constraint/index/dependency behavior
```

Do not label every slow FK-related operation “a database performance issue” without identifying the actual wait or execution mechanism.

---

# 73. Foreign Keys and Trigger Side Effects

Because referential actions can fire triggers, a schema review should ask:

```text
What triggers exist on the child?
What does each trigger write?
Can a cascade trigger further work?
Can the trigger fail?
Can it create recursive behavior?
```

PostgreSQL warns that cascading trigger activity can recurse and that trigger programmers are responsible for avoiding harmful recursion. citeturn428092search3

This is particularly important when combining:

```text
FK cascades
+
soft-delete triggers
+
Audit triggers
+
outbox/event triggers
```

The combined system can be much more complex than the FK definition alone suggests.

# 74. Event-Driven Architecture and Cascades

Suppose your system emits an event whenever an order item is deleted.

Now an order deletion with `ON DELETE CASCADE` can implicitly emit item-deletion events.

This may be exactly what you want.

But if your event semantics are:

```text
“business user intentionally deleted order item”
```

then a cascade may produce an unexpected event meaning.

The solution is not automatically “never use cascades.”

The solution is to define event semantics explicitly:

```text
row-level storage event
vs
business-domain event
```

These are not always the same thing.

# 75. Referential Integrity and Auditability

A production audit system should answer:

```text
What changed?
Why?
Who caused it?
What related rows were affected?
```

A cascade can make one root operation produce many dependent changes.

Therefore audit design should retain enough context to distinguish:

```text
explicit child mutation
```

from:

```text
child mutation caused by parent referential action
```

When necessary, carry operation context through application-level transactions or carefully designed audit mechanisms.

# 76. A Better Relationship Design Process

Use this sequence for every important FK.

### Step 1 — Identify the domain relationship

Example:

```text
Order belongs to Customer
```

### Step 2 — Identify cardinality

```text
Customer 1 → N Orders
```

### Step 3 — Decide optionality

```text
Every order must have a customer
```

### Step 4 — Identify identity

```text
customer_id
```

### Step 5 — Define database invariant

```text
orders.customer_id must reference customers.customer_id
```

### Step 6 — Define parent lifecycle

```text
Can customer ever be deleted physically?
```

### Step 7 — Choose referential action

```text
RESTRICT / NO ACTION / CASCADE / SET NULL / SET DEFAULT
```

### Step 8 — Design supporting indexes

Especially on high-volume referencing columns.

### Step 9 — Test concurrency and failure paths

### Step 10 — Document the lifecycle contract

This process is much safer than starting from:

```text
“Which FK option should I copy?”
```

# 77. A Complete Production Example

```sql
CREATE TABLE tenants (
    tenant_id bigint PRIMARY KEY
);

CREATE TABLE customers (
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    name text NOT NULL,
    PRIMARY KEY (tenant_id, customer_id)
);

CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, order_id),
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customers(tenant_id, customer_id)
        ON DELETE RESTRICT
);

CREATE INDEX idx_orders_customer
    ON orders(tenant_id, customer_id);
```

This design demonstrates several principles:

- tenant identity participates in the relationship;
- customer identity is unique within tenant scope;
- orders require customers;
- customer deletion is blocked while orders remain;
- the child-side relationship has a useful index;
- constraints have explicit names.

This is far stronger than merely having:

```sql
customer_id bigint REFERENCES customers(customer_id)
```

in a multi-tenant system.

# 78. Common Developer Mistakes

## Mistake 1 — Treating a FK as a validation hint

A foreign key is an integrity rule, not UI validation.

## Mistake 2 — Assuming FK creates a child-side index

It does not automatically do so. citeturn428092search0turn428092search1

## Mistake 3 — Using CASCADE everywhere

Lifecycle semantics must justify it.

## Mistake 4 — Forgetting nullability

A nullable FK is not the same as a mandatory relationship.

## Mistake 5 — Ignoring tenant scope

A global FK can allow cross-tenant references when IDs are only tenant-unique.

## Mistake 6 — Deleting historical parents

Invoices, ledger records, audits, and other historical data may need identity retention.

## Mistake 7 — Assuming soft-delete activates ON DELETE

It does not.

## Mistake 8 — Using a pre-check as the guarantee

`SELECT then INSERT` is not a replacement for a database constraint.

## Mistake 9 — Ignoring trigger side effects

Cascades can fire child-table triggers. citeturn428092search3

## Mistake 10 — Debugging only at the API layer

The database error often already identifies the violated invariant.

# 79. AI / Vibe-Coding Failure Modes

AI-generated schema suggestions frequently produce patterns such as:

```sql
customer_id UUID REFERENCES customers(id) ON DELETE CASCADE
```

without understanding the business lifecycle.

Typical failures:

### 79.1 “Add CASCADE to prevent delete errors”

This optimizes for convenience rather than data safety.

### 79.2 “Add FK everywhere” without modeling identity

A wrong target key can produce a structurally valid but semantically weak model.

### 79.3 “Foreign keys are slow, remove them”

This replaces a correctness mechanism with application discipline and can create irreversible integrity debt.

### 79.4 “Check the parent before insert”

This ignores concurrency races.

### 79.5 “Create an index on every FK”

Potentially unnecessary write and storage overhead.

### 79.6 Tenant ID omitted from composite identity

This can undermine isolation even while the FK technically passes.

### 79.7 Soft-delete treated as referential deletion

The parent still exists physically, so FK semantics have not changed.

The cure for AI-generated schema code is the same as for human-generated code:

```text
ask what invariant exists
→ ask what state transitions are legal
→ inspect generated DDL
→ test failure paths
→ measure production behavior
```

# 80. Testing Referential Integrity

A serious test suite should test both happy paths and invalid transitions.

## L1 — Basic validity

```text
Insert parent
Insert valid child
```

Expected: success.

## L2 — Invalid child

```text
Insert child referencing missing parent
```

Expected: failure.

## L3 — Parent delete semantics

Test each configured action.

```text
NO ACTION
RESTRICT
CASCADE
SET NULL
SET DEFAULT
```

## L4 — Composite FK semantics

Test:

```text
valid tuple
invalid tenant tuple
NULL combinations
MATCH FULL
```

## L5 — Concurrency

Run concurrent parent/child operations and verify the final state never violates the invariant.

## L6 — Trigger interaction

Verify cascade-driven child modifications trigger the intended auditing/events and do not recursively explode.

## L7 — Production-scale behavior

Test representative row counts and measure:

```text
execution time
lock waits
WAL generation
replication effects
vacuum impact
```

---

# 81. Failure-Injection Tests

A production-grade schema should deliberately test failure cases.

Examples:

```text
delete parent with protected children
insert orphan child
update FK to missing target
remove target during concurrent child creation
execute large cascade
fire cascade with child trigger failure
```

The goal is not simply:

```text
“Does valid data work?”
```

It is:

```text
“Does invalid state remain impossible under realistic failure modes?”
```

# 82. Migration Review Checklist for Foreign Keys

Before adding a FK to a populated table, review:

```text
[ ] Existing orphan rows identified
[ ] Referenced key is unique
[ ] Data types align correctly
[ ] Null semantics are intentional
[ ] Existing duplicate values are resolved
[ ] Child-side index strategy reviewed
[ ] Delete/update semantics defined
[ ] Lock impact understood
[ ] Validation strategy defined
[ ] Rollback/recovery strategy tested
```

A migration that merely “runs successfully” is not enough.

The resulting invariant must be correct and operationally safe.

# 83. Production Observability

Monitor systems where FK-related work is operationally significant.

Useful signals include:

```text
constraint violation rate
transaction latency
lock waits
deadlocks
large DELETE duration
replication lag
WAL volume
error rates by constraint name
```

A particularly useful application metric is:

```text
foreign_key_violation_total{constraint="fk_orders_customer"}
```

This can reveal upstream bugs without requiring you to inspect individual logs manually.

Avoid high-cardinality labels such as raw customer IDs.

---

# 84. Error Classification

A useful operational classification is:

```text
Expected domain rejection
    ≠
Application bug
    ≠
Data corruption
    ≠
Migration failure
    ≠
Concurrency defect
```

For example:

```text
DELETE customer
with existing protected invoice
```

may be an expected domain rejection.

Whereas:

```text
create order
with missing customer
```

may indicate an application bug.

Treating every FK violation as the same error class destroys useful operational information.

---

# 85. Security Perspective

Referential integrity can provide meaningful security support, especially in multi-tenant architectures, but it is not an authorization boundary by itself.

A tenant-aware composite FK can prevent structurally invalid cross-tenant references.

However, it does not decide whether a given application role is allowed to modify either row.

Therefore:

```text
FK
+
RLS / authorization
+
application/domain policy
```

may collectively form the protection model.

Never treat the FK alone as access control.

---

# 86. Architecture Trade-Offs

## Strong database enforcement

Advantages:

- centralized correctness;
- race-resistant relational invariants;
- consistent behavior across clients;
- easier long-term integrity.

Costs:

- more careful migrations;
- write-time checks;
- index considerations;
- more explicit lifecycle design.

## Application-only enforcement

Advantages:

- flexible business workflows;
- easy conditional logic.

Costs:

- duplicate rules;
- race conditions;
- bypass paths;
- data corruption risk.

For relational invariants, strong database enforcement is usually the safer foundation.

# 87. Decision Framework

Use this framework for every foreign key.

### Question 1
Is the relationship structurally real?

```text
No → do not invent an FK.
Yes → continue.
```

### Question 2
Must the relationship always exist?

```text
Yes → NOT NULL + FK
No  → nullable FK may be appropriate
```

### Question 3
Can the parent be physically deleted?

```text
No → avoid deletion or use restricted lifecycle
Yes → choose action intentionally
```

### Question 4
What should happen to children?

```text
CASCADE
RESTRICT / NO ACTION
SET NULL
SET DEFAULT
```

### Question 5
Is tenant identity part of the relationship?

```text
Yes → consider composite tenant-aware FK
```

### Question 6
What is the workload impact?

```text
child-side index?
large cascade?
locks?
triggers?
replication?
```

### Question 7
What must remain historical?

```text
invoices?
audit?
ledger?
orders?
```

Then design the FK accordingly.

# 88. Expert Review Questions

Before approving a schema, ask:

### Relationship semantics

- What exact invariant does this FK guarantee?
- What states are intentionally allowed to be null?
- Is the target key immutable?
- Is the relationship tenant-scoped?

### Lifecycle

- What happens when the parent is archived?
- What happens when it is physically deleted?
- Should historical children survive?
- Is CASCADE semantically correct?

### Performance

- Is the referencing column appropriately indexed?
- What is the expected child cardinality?
- What happens during parent deletion at production scale?
- Are there existing composite indexes that already cover the FK lookup?

### Concurrency

- What happens during concurrent parent delete and child insert?
- Is an application pre-check being mistaken for the actual guarantee?

### Operations

- How will a foreign-key failure map to API behavior?
- Can a cascade cause a large lock/WAL event?
- What triggers fire as part of the relationship action?

### Architecture

- Does the FK enforce identity or business eligibility?
- Should the relationship be physical or logical?
- Is soft-delete being confused with physical deletion?

# 92. The Core Invariant to Remember

For a typical non-null foreign key:

```text
Every referencing key
must resolve to a valid referenced key.
```

For a lifecycle-aware relationship:

```text
Parent state transition
        ↓
must preserve or intentionally transform
        ↓
all dependent relationships
```

That is the real meaning of referential integrity.

# 94. Final Principle

> **A foreign key is not a convenience link between two tables. It is a database-enforced statement about which states of the data are legal.**

The strongest relational designs do not begin with:

```text
“Which `ON DELETE` option should I use?”
```

They begin with:

```text
What is the relationship?
↓
What states are legal?
↓
Is the relationship mandatory?
↓
What is the lifecycle of the parent?
↓
What must happen to dependents?
↓
What must remain historical?
↓
What happens under concurrency?
↓
What is the production workload?
```

Then the schema expresses those decisions.

The goal is not to maximize the number of foreign keys.

The goal is to make **invalid relational states structurally difficult or impossible to persist**, while preserving the lifecycle, performance, and operational behavior the business actually requires.
