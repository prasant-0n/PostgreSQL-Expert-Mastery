# 02.4 — UUID / BIGINT / Distributed IDs

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to choosing, generating, indexing, exposing, migrating, and operating identifiers in PostgreSQL systems.

---

## 1. Chapter Objective

Identifiers are deceptively foundational.

An `id` column looks like a small implementation detail, but it influences:

- identity semantics
- primary-key design
- foreign-key width
- index size
- cache locality
- insert patterns
- distributed writes
- replication and merge strategies
- API design
- enumeration resistance
- event ordering assumptions
- data migration
- interoperability with external systems
- sharding or partitioning strategies
- operational debugging
- long-term schema evolution

The goal of this chapter is **not** to declare that UUIDs are better than integers or that integers are better than UUIDs.

The goal is to learn how to select an identifier strategy from first principles.

The central question is:

> **What guarantees does this identifier need to provide, who generates it, where must it be unique, how will it behave in indexes, and which other identifiers must remain distinct from it?**

---

# 2. Three Levels of Definition

## 2.1 Simple definition

An identifier is a value used to distinguish one entity or row from another.

Examples:

```text
customer 42
order 90128
product 7
```

## 2.2 Engineering definition

An identifier is a stable key value used to establish identity and construct references between records, APIs, events, services, and external systems.

## 2.3 Expert definition

An identifier is a system-level identity contract whose properties include:

- uniqueness scope
- generation authority
- lifetime
- mutability
- ordering characteristics
- predictability
- representation
- storage cost
- replication behavior
- collision model
- interoperability

A good design separates these concerns instead of forcing one field to satisfy every use case.

---

# 3. The Identity Stack

A production system may have several identifiers for the same business entity.

For example:

```text
                    Customer
                       │
       ┌───────────────┼────────────────┐
       │               │                │
    DB PK         Business key       Public ID
    bigint        email+tenant       UUID
       │                                │
       │                                │
    internal                         external
    identity                         identity
```

An external partner may add another identifier:

```text
partner_customer_id
```

This leads to a critical rule:

> **Do not make a single identifier carry unrelated semantic responsibilities merely because doing so is convenient.**

---

# 4. BIGINT: What It Really Means

PostgreSQL `bigint` is a signed 8-byte integer type.

That means its storage footprint is fixed and compact compared with a UUID, and its domain is finite. PostgreSQL documents `bigint` as an 8-byte signed integer. citeturn185047search2

A common schema is:

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);
```

An identity column is backed by an implicit sequence. PostgreSQL documents identity columns as automatically generated from such a sequence; the identity property also implies `NOT NULL`, but it does **not** itself guarantee uniqueness, so a primary key or unique constraint is still required. citeturn185047search1

This distinction matters:

```text
IDENTITY
    ↓
generation mechanism

PRIMARY KEY / UNIQUE
    ↓
uniqueness invariant
```

They are related, but not equivalent.

---

# 5. Identity Columns vs SERIAL

Modern PostgreSQL schema design should generally understand identity columns rather than treating `serial` as the conceptual model.

Example:

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
```

There are two important identity modes:

```sql
GENERATED ALWAYS AS IDENTITY
```

and:

```sql
GENERATED BY DEFAULT AS IDENTITY
```

The choice determines how explicit inserted values interact with automatic generation.

The key mental model is:

> **Identity is column-generation behavior; sequence-backed generation is not a uniqueness constraint.**

---

# 6. Sequence Semantics

PostgreSQL sequences are database objects designed for multi-user-safe generation of successive values. `nextval` is atomic and concurrent callers receive distinct sequence values from that sequence. citeturn185047search5

Example:

```sql
CREATE SEQUENCE invoice_number_seq;

SELECT nextval('invoice_number_seq');
```

But a sequence is not a gapless business-number allocator.

Suppose:

```text
nextval -> 100
INSERT fails
nextval -> 101
```

The database is allowed to have:

```text
99
101
```

with 100 never represented by a committed row.

Therefore:

> **Sequence values are suitable for identity generation; they are not inherently suitable for legal-document numbering requirements that demand gaplessness.**

Gaplessness, when legally or financially required, is a separate design problem involving transaction timing, locking, failure handling, and often a dedicated allocation model.

---

# 7. The `MAX(id) + 1` Anti-Pattern

Never use:

```sql
SELECT COALESCE(MAX(id), 0) + 1
FROM orders;
```

followed by:

```sql
INSERT INTO orders (id, ...)
VALUES ($computed_id, ...);
```

Under concurrency:

```text
Transaction A → MAX = 100
Transaction B → MAX = 100

A chooses 101
B chooses 101
```

You now have a race.

A unique constraint may detect the collision, but that does not turn the algorithm into a valid ID generator. It merely converts a race into an error.

Correct approaches include:

```text
IDENTITY
SEQUENCE
UUID generation
Distributed ID algorithm
```

depending on the actual requirements.

---

# 8. UUID Fundamentals

PostgreSQL has a native `uuid` type storing a 128-bit UUID. PostgreSQL 18 documents UUID support according to RFC 9562 and notes that UUIDs provide uniqueness properties suitable for distributed systems beyond a single sequence generator. PostgreSQL 18 also provides native `uuidv4()` and `uuidv7()` generation. citeturn185047search0

Example:

```sql
CREATE TABLE customers (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    name text NOT NULL
);
```

For PostgreSQL 18 specifically, `uuidv7()` is timestamp-ordered in the UUID scheme, making it materially different from purely random UUID generation. PostgreSQL 18 release notes explicitly identify `uuidv7()` support. citeturn185047search3

---

# 9. UUIDv4 vs UUIDv7

These should not be treated as interchangeable merely because both are UUIDs.

## UUIDv4

Conceptually:

```text
random UUID
```

Strengths:

- excellent distributed generation
- no central allocator
- hard to guess
- simple conceptual model

Costs:

- effectively random insertion order
- poor locality compared with time-ordered identifiers
- can increase index churn relative to ordered keys in write-heavy workloads

## UUIDv7

Conceptually:

```text
        time component
              ↓
[ timestamp ][ random / sequence-related bits ]
```

Strengths:

- globally useful identity
- naturally carries ordering information
- better insertion locality than random UUIDs in common B-tree workloads
- suitable for distributed generation

But the ordering is not the same thing as an exact event-time guarantee.

Do not infer:

```text
UUIDv7 order == business event order
```

They serve different semantics.

---

# 10. Identifier Order Is Not Business Time

Suppose:

```text
request A created UUID at 10:00:00.100
request B created UUID at 10:00:00.050
```

Network delays may cause B to commit later.

Therefore:

```text
ID ordering
≠
commit ordering
≠
business event ordering
≠
causal ordering
```

This distinction is critical in event-driven systems.

If the application needs:

```text
created_at
occurred_at
effective_at
sequence_no
```

store those concepts explicitly.

Do not overload an identifier with temporal semantics.

---

# 11. Distributed IDs: The Problem

A single PostgreSQL sequence gives a strong local allocator, but distributed writers introduce a different problem.

Suppose two databases independently allocate:

```text
DB-A → 1, 2, 3
DB-B → 1, 2, 3
```

Merge them and collisions occur.

Therefore a distributed ID strategy needs uniqueness across the required scope.

Possible strategies include:

```text
UUID
Snowflake-like IDs
ULID-like schemes
Hi/Lo allocation
Node-prefixed sequences
Range allocation
Application-generated random IDs
```

The correct strategy depends on the system's topology.

---

# 12. Distributed ID Requirements Checklist

Before selecting an algorithm, answer:

```text
Unique where?

Within one table?
Within one database?
Across regions?
Across all environments?
Across offline clients?
Across merged databases?
Forever?
For a bounded retention period?

Who generates?

Database?
Application?
Edge device?
Service?
Client?

Does ordering matter?

No?
Approximate time order?
Strict sequence?
Per-tenant sequence?
Global sequence?
```

Only after answering those questions should you choose the identifier.

---

# 13. Snowflake-Like IDs

A common distributed-ID family uses a structured integer composed from fields such as:

```text
┌────────────┬──────────┬───────────────┐
│ timestamp  │ node ID  │ sequence      │
└────────────┴──────────┴───────────────┘
```

This provides:

- approximate chronological ordering
- distributed generation
- compact integer representation
- no central database sequence on every write

But it introduces operational assumptions:

- clock correctness
- node identity management
- sequence rollover
- epoch management
- clock rollback behavior
- serialization format

A distributed ID algorithm is therefore an operational system, not merely a function.

---

# 14. Clock Rollback Is a Real Failure Mode

Consider a time-based ID generator:

```text
T1 = 12:00:10
T2 = 12:00:11
T3 = 12:00:09   ← clock moved backward
```

If the algorithm assumes monotonic time, it may:

- reject generation
- wait
- reuse state incorrectly
- produce duplicate or misordered IDs

Therefore distributed ID designs need an explicit policy for clock anomalies.

Possible policies include:

```text
wait until clock catches up
use last timestamp
advance a logical timestamp
fail generation
```

The correct choice depends on availability and correctness requirements.

---

# 15. BIGINT Capacity Planning

`bigint` provides a very large finite numeric domain, but “very large” is not the same as “infinite.”

For a high-volume system, estimate:

```text
rows per second
× seconds per year
× retention years
```

For example:

```text
50,000 rows/sec
× 31,536,000 sec/year
≈ 1.5768e12 rows/year
```

This is comfortably inside the positive range of a PostgreSQL `bigint`, but the exercise reveals an important engineering habit:

> **Capacity should be derived from workload, not from intuition.**

Also remember that separate tables may use separate sequences, so “global row count” is usually not the correct utilization metric unless a global sequence is intentionally used.

---

# 16. UUID Storage and Index Cost

A UUID is 128 bits / 16 bytes of raw value, while a `bigint` is 64 bits / 8 bytes.

The difference is not merely the column width.

Every index containing the identifier also carries associated key and tuple metadata, so wider keys can increase:

- index size
- cache pressure
- memory consumption
- I/O
- replication volume indirectly through larger index structures

This becomes significant when a primary key is referenced by many secondary indexes or foreign-key indexes.

Therefore:

> **Key width should be evaluated across the entire schema, not just in the table definition.**

---

# 17. Primary Key Width Multiplies

Suppose:

```text
parent(id)
```

has 10 million rows.

And there are eight child tables containing the parent ID.

A wider parent identifier appears repeatedly across:

```text
child rows
child indexes
join paths
foreign-key indexes
materialized views
cache keys
serialized events
```

Therefore the storage difference between `bigint` and `uuid` compounds across the schema.

This does not mean UUID is wrong.

It means UUID has a real system-level cost that must be weighed against its distributed-system benefits.

---

# 18. UUID and B-tree Locality

B-tree indexes perform well when inserts have useful locality.

A random UUID workload approximately distributes new keys across the keyspace.

A time-ordered identifier such as UUIDv7 tends to create more append-like behavior because newly generated values are generally near recent values.

The exact performance depends on:

- insertion rate
- index size
- cache residency
- fillfactor
- workload shape
- update behavior
- number of indexes
- hardware

Therefore:

```text
UUID = slow
BIGINT = fast
```

is not a valid engineering conclusion.

The right statement is:

> **Identifier distribution affects index behavior, and its impact must be measured under the target workload.**

---

# 19. Random UUID vs UUIDv7: A Practical Comparison

| Property | BIGINT identity | UUIDv4 | UUIDv7 |
|---|---|---|---|
| Size | 8 bytes | 16 bytes | 16 bytes |
| Native PostgreSQL type | integer | uuid | uuid |
| Local generation | excellent | excellent | excellent |
| Cross-database generation | requires coordination | strong | strong |
| Predictability | often sequential | low | low in practice, but time-structured |
| Approx. chronological order | no | no | yes |
| B-tree locality | strong | weaker | generally better than v4 |
| Central allocator required | typically sequence | no | no |
| Easy human inspection | yes-ish | no | no |

The table is a decision aid, not a benchmark.

---

# 20. Public IDs vs Internal IDs

An internal database primary key and a public resource identifier can be different.

Example:

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id uuid NOT NULL UNIQUE DEFAULT uuidv7(),
    name text NOT NULL
);
```

Now:

```text
id       → internal joins / storage-oriented identity
public_id → API / external references
```

Advantages:

- internal representation can remain compact
- public identifiers need not reveal row count
- APIs can avoid exposing predictable database IDs
- external identity can remain stable even if internal strategies change

But this introduces another column and another uniqueness invariant.

That complexity is justified only when the separation has a real architectural benefit.

---

# 21. Does a Sequential ID Automatically Create a Security Problem?

Not necessarily.

But exposing:

```text
/orders/1001
/orders/1002
/orders/1003
```

can make enumeration easier.

However, replacing IDs with UUIDs does **not** fix authorization.

Broken authorization:

```text
GET /orders/<some-id>
```

that returns another tenant's order remains broken whether `<some-id>` is:

```text
42
```

or:

```text
2c3b...
```

Therefore:

> **Unpredictable identifiers can reduce accidental enumeration, but authorization must enforce access independently.**

For multi-tenant systems, tenant-scoped authorization and row-level controls remain necessary.

---

# 22. Enumeration Resistance Is Not Confidentiality

A UUID that is difficult to guess does not encrypt information.

An attacker who obtains the identifier directly may still retrieve the resource if authorization is weak.

Therefore never describe UUIDs as:

```text
secure IDs
```

as though they were access-control tokens.

Think instead:

```text
UUID
   ↓
identity representation

Authorization
   ↓
access decision

Encryption
   ↓
confidentiality
```

Different mechanisms, different guarantees.

---

# 23. Business Keys Still Matter With Surrogate IDs

Suppose:

```sql
CREATE TABLE users (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL
);
```

The surrogate ID answers:

> Which physical entity is this?

But the business may require:

> Can two active users in this tenant share the same email?

That requires a business uniqueness rule such as:

```sql
CREATE UNIQUE INDEX users_tenant_email_uq
ON users (tenant_id, lower(email));
```

The surrogate key does not replace business uniqueness.

This produces a useful separation:

```text
Surrogate key
→ row identity

Natural/business key
→ domain uniqueness
```

---

# 24. Never Confuse Key Generation With Business Numbering

Consider an ERP invoice.

There may be several identifiers:

```text
internal_id
public_id
invoice_number
external_reference
```

They may have very different requirements.

### Internal ID

Needs stable database identity.

### Public ID

May need globally unique externally safe representation.

### Invoice number

May need:

- tenant scope
- fiscal-year scope
- branch scope
- human readability
- regulatory continuity
- controlled allocation

### External reference

Comes from an external system.

Trying to collapse all four into one column creates unnecessary coupling.

---

# 25. Composite Identity and Distributed IDs

Sometimes the logical identity includes scope.

Example:

```text
tenant_id + sequence_number
```

The business may say:

> Invoice 1000 in Tenant A is different from Invoice 1000 in Tenant B.

That is not a global identity requirement.

The database representation may therefore be:

```sql
PRIMARY KEY (tenant_id, invoice_number)
```

while a separate surrogate UUID or BIGINT provides internal identity.

This is often cleaner than inventing a complicated globally unique invoice number when the domain itself is scoped.

---

# 26. Multi-Tenant ID Design

For shared-table SaaS systems, common choices include:

```sql
id bigint GENERATED ALWAYS AS IDENTITY
```

plus:

```sql
tenant_id bigint NOT NULL
```

with business uniqueness represented as:

```sql
UNIQUE (tenant_id, external_code)
```

Alternatively:

```sql
id uuid PRIMARY KEY DEFAULT uuidv7()
```

may be used when distributed generation or externally exposed identity is valuable.

But neither choice automatically creates tenant isolation.

Tenant isolation still requires:

- tenant-aware foreign keys where needed
- tenant-scoped uniqueness
- application authorization
- RLS where appropriate
- correct query predicates
- controlled database roles

---

# 27. Tenant-Safe Foreign Keys

Suppose:

```text
orders(tenant_id, customer_id)
customers(tenant_id, id)
```

A foreign key only on:

```text
customer_id → customers.id
```

can allow a logically cross-tenant reference if customer IDs are only unique globally by accident or if later architecture changes weaken that assumption.

A stronger tenant-aware relationship can use a composite parent key:

```sql
UNIQUE (tenant_id, id)
```

and reference:

```sql
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, id)
```

This makes tenant scope part of the database invariant.

---

# 28. Distributed IDs and Offline Clients

Suppose mobile clients must create entities while disconnected.

A database sequence cannot naturally allocate the final identifier offline.

A client-generated UUID can.

Example:

```text
phone creates customer UUID
       ↓
offline storage
       ↓
sync
       ↓
PostgreSQL accepts same identity
```

This can simplify synchronization because the entity can have a stable identity before central persistence.

But offline IDs create new requirements around:

- collision probability
- malicious client input
- deduplication
- conflict resolution
- ownership
- retry behavior
- idempotency

UUID generation solves identity allocation.

It does not solve synchronization semantics.

---

# 29. Client-Generated IDs and Trust Boundaries

Do not assume that a client-generated UUID is trustworthy simply because it is globally unique.

A malicious client can submit:

```text
another customer's UUID
```

The authorization boundary still needs to validate ownership.

Therefore:

```text
UUID uniqueness
≠
authorization
```

and:

```text
client generated
≠
server trusted
```

---

# 30. Idempotency Keys Are Not Entity IDs

This distinction is crucial in APIs.

An API may receive:

```http
Idempotency-Key: 8b1e...
```

That value identifies an attempted operation.

The resulting order may have:

```text
order.id = UUID
```

These are different concepts.

Model them separately:

```text
request identity
→ operation deduplication

entity identity
→ persistent business object
```

Conflating them makes retries and recovery harder to reason about.

---

# 31. External IDs Need Provenance

Suppose a system stores:

```text
external_id = "12345"
```

This is incomplete information.

Ask:

```text
12345 from which system?

Which environment?
Which tenant?
Which resource type?
What happens when the external system reuses the number?
```

A safer model is often:

```text
provider
external_id
resource_type
tenant_id
```

with an explicit uniqueness rule.

Example:

```sql
UNIQUE (tenant_id, provider, resource_type, external_id)
```

---

# 32. Environment Scope

Never casually assume IDs are globally unique across:

```text
dev
staging
production
```

A sequence in each environment can legitimately produce the same numbers.

Similarly, a service-generated identifier may be unique only within a deployment or namespace.

When data moves between environments, the required uniqueness boundary must be explicit.

---

# 33. Merge and Data Migration Scenarios

Suppose two legacy databases are merged:

```text
Database A
customer_id 1..1M

Database B
customer_id 1..500K
```

A naive merge on `customer_id` creates collisions.

Possible strategies:

### Strategy A — Remap IDs

Maintain mapping tables:

```text
old_db
old_id
new_id
```

### Strategy B — Namespace IDs

Encode source identity into the new identifier.

### Strategy C — Move to globally generated UUIDs

Use a new stable identity while retaining legacy IDs as external references.

The best choice depends on migration duration, application compatibility, and relationship volume.

---

# 34. Identity Migration: BIGINT → UUID

A direct type replacement is usually not the safest migration.

A controlled approach is:

```text
1. Add new UUID column
2. Generate UUID for existing rows
3. Populate foreign-key columns
4. Backfill mappings
5. Add unique constraints
6. Update application reads/writes
7. Validate consistency
8. Switch references
9. Remove old dependency later
```

During the migration, the system may temporarily have:

```text
internal_id bigint
new_id uuid
```

The mapping must remain deterministic and testable.

---

# 35. Dual-ID Migration Pattern

Example:

```sql
ALTER TABLE customers
ADD COLUMN public_id uuid;
```

Backfill:

```sql
UPDATE customers
SET public_id = uuidv7()
WHERE public_id IS NULL;
```

Then:

```sql
ALTER TABLE customers
ALTER COLUMN public_id SET NOT NULL;
```

and:

```sql
CREATE UNIQUE INDEX customers_public_id_uq
ON customers (public_id);
```

Then deploy application code that understands both identifiers.

Only after dependency removal should the old strategy be retired.

---

# 36. Do Not Assume a UUID Migration Is Free

Changing the key type can affect:

- every foreign-key column
- every related index
- joins
- ORM mappings
- API schemas
- event payloads
- cache keys
- logs
- test fixtures
- ETL pipelines
- analytics queries
- warehouse dimensions
- external integrations

The migration blast radius is therefore much larger than:

```text
ALTER COLUMN id TYPE uuid
```

---

# 37. ORM Implications

In Node.js / NestJS systems, identifier choices propagate into:

```text
entities
DTOs
validation schemas
serialization
OpenAPI
repositories
migrations
event contracts
cache keys
tests
```

For example:

```ts
export interface Order {
  id: string;
}
```

may represent:

```text
UUID
```

while:

```ts
id: number
```

may represent:

```text
BIGINT
```

But beware language-runtime numeric limitations.

A PostgreSQL `bigint` should not automatically be assumed safe as a JavaScript `number` across all possible values. Many Node.js PostgreSQL drivers expose `int8` in a way that may require string handling or explicit parsing to preserve exactness.

A safer contract may therefore be:

```ts
id: string
```

for externally serialized 64-bit IDs, depending on the driver and application architecture.

---

# 38. BIGINT and JavaScript Number Precision

JavaScript `number` is IEEE-754 double precision.

Exact integer representation is guaranteed only through:

```text
2^53 - 1
```

A PostgreSQL signed `bigint` has a substantially larger range.

Therefore:

```text
PostgreSQL bigint
        ↓
JavaScript number
```

can silently lose integer precision for sufficiently large values.

Use:

```ts
bigint
```

or:

```ts
string
```

where appropriate, depending on your serialization contract.

Expert rule:

> **A database type boundary is also a runtime-type boundary. Validate representation at the application edge.**

---

# 39. API Representation

A public UUID is commonly serialized as:

```json
{
  "id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11"
}
```

A BIGINT may also be serialized as a string:

```json
{
  "id": "9223372036854770000"
}
```

This avoids JavaScript precision loss across clients.

The correct API representation is therefore not simply whatever the database driver returns.

Define an explicit contract.

---

# 40. When BIGINT Is Usually a Strong Choice

BIGINT is attractive when:

- one PostgreSQL cluster owns generation
- internal joins dominate
- compact indexes matter
- predictability is acceptable
- centralized allocation is acceptable
- distributed offline creation is not required
- identifiers remain internal
- throughput benefits from ordered insertion

Typical examples:

```text
internal ERP row identity
high-volume event tables
warehouse-internal dimensions
join-heavy transactional models
```

---

# 41. When UUID Is Usually a Strong Choice

UUID is attractive when:

- multiple writers generate IDs independently
- offline creation exists
- services need to allocate identity without coordination
- database merge is a realistic requirement
- public resource identity should not be sequential
- identity is useful before persistence

Typical examples:

```text
public API resources
offline-first records
distributed services
cross-database ingestion
integration-heavy entities
```

---

# 42. When UUIDv7 Is Particularly Interesting

UUIDv7 becomes compelling when you want:

```text
UUID properties
+
approximate time ordering
+
PostgreSQL-native generation
```

PostgreSQL 18 includes native UUIDv7 generation. citeturn185047search0turn185047search3

This can reduce one major trade-off of random UUIDs, but it does not erase:

- 16-byte key width
- index cost
- distributed generation complexity outside the database
- API/string overhead

Use it because its trade-off is appropriate, not because it is fashionable.

---

# 43. Anti-Pattern: “UUID Everywhere”

Replacing every integer with UUID without measuring workload can create unnecessary cost.

Potential issues:

```text
larger indexes
larger foreign keys
more memory pressure
more network payload
more verbose logs
harder manual inspection
```

A good design might instead use:

```text
BIGINT internal PK
UUID public ID
```

or:

```text
UUIDv7 PK
business number separate
```

depending on the system.

---

# 44. Anti-Pattern: “BIGINT Everywhere Because It Is Faster”

This fails when the architecture requires:

- offline identity
- distributed generation
- cross-cluster merges
- uncoordinated service creation
- public non-sequential identity

The correct question is not:

> “Which key is fastest?”

It is:

> **“What identifier architecture minimizes total system complexity for the required guarantees?”**

---

# 45. Anti-Pattern: Using IDs as Business State

Bad:

```text
invoice_id = 12345
```

and assuming:

```text
higher invoice_id = newer invoice
```

That may hold accidentally for a local sequence, but it is not a business invariant.

Likewise:

```text
UUIDv7 > UUIDv7
```

does not imply exact business chronology.

Use explicit fields:

```text
created_at
issued_at
effective_at
sequence_number
version
```

for explicit semantics.

---

# 46. Anti-Pattern: Reusing Deleted IDs

Suppose:

```text
customer 42 deleted
```

and later a new customer becomes:

```text
customer 42
```

This can break:

- audit interpretation
- caches
- external references
- event history
- debugging
- forensic reasoning

Unless the domain explicitly permits identity reuse, treat IDs as persistent identities across the logical lifetime of the system.

Sequences naturally avoid reuse under normal operation, but explicit manual insertion, reset, or custom allocation can violate assumptions.

---

# 47. Anti-Pattern: UUID Stored as TEXT

Prefer:

```sql
id uuid
```

over:

```sql
id text
```

when the value is genuinely a UUID.

The native type gives PostgreSQL stronger semantic typing and appropriate comparison/storage behavior.

A generic text column loses that type-level contract.

---

# 48. Anti-Pattern: VARCHAR UUIDs in Foreign Keys

This pattern is especially harmful:

```text
customers.id varchar
orders.customer_id varchar
```

when the logical identity is a UUID.

Prefer matching types:

```sql
customers.id uuid
orders.customer_id uuid
```

Matching identifier types reduce conversion confusion and make constraints clearer.

---

# 49. Identifier Equality Must Be Type-Stable

Do not casually mix:

```text
uuid
text
varchar
bigint
integer
```

for the same conceptual identity.

A mature schema prefers:

```text
same semantic identity
→ same database type
```

unless a deliberate boundary requires transformation.

---

# 50. Identity and Auditability

A good identifier should survive enough of the entity's lifecycle to make history understandable.

For an order:

```text
order_id
created_at
created_by
```

may provide enough identity context to reconstruct the history.

A generated key alone does not answer:

```text
who created it?
when?
under which tenant?
from which external system?
```

Identity design therefore works alongside audit design.

---

# 51. Identity and Event Streams

An event might contain:

```json
{
  "event_id": "...",
  "aggregate_id": "...",
  "occurred_at": "..."
}
```

Notice the separate identities:

```text
event_id
aggregate_id
```

Do not use the aggregate ID as the event ID.

One aggregate creates many events.

Likewise, do not use the database primary key as a universal distributed event identity unless the architecture explicitly requires that semantics.

---

# 52. Identity and Idempotent Event Consumption

Suppose a consumer receives:

```text
event E123
```

twice.

The consumer may enforce:

```sql
UNIQUE (consumer_name, event_id)
```

This has nothing to do with the aggregate's entity ID.

This is another demonstration that:

> **Different identities belong to different invariants.**

---

# 53. Distributed ID Uniqueness Is a Probabilistic or Coordinated Claim

UUID uniqueness is commonly discussed as though it were mathematical certainty.

In reality, UUID schemes rely on their specified generation algorithms and assumptions to make collisions extraordinarily unlikely.

That is different from a database primary key constraint, which provides deterministic enforcement at the database boundary.

Therefore use both concepts:

```text
generator design
+
PRIMARY KEY / UNIQUE constraint
```

The generator reduces collision likelihood.

The constraint protects the database from invalid duplicates.

---

# 54. Database Constraint Remains the Final Authority

Even if your application generates perfect UUIDs, keep:

```sql
PRIMARY KEY (id)
```

because the database must remain the final integrity boundary.

Likewise, even if a distributed ID algorithm is mathematically designed to avoid collisions, the receiving table should still enforce uniqueness.

Engineering principle:

> **Generation policy predicts uniqueness; the constraint enforces it.**

---

# 55. Production Pattern: BIGINT Internal + UUID Public

A common hybrid design:

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id uuid NOT NULL DEFAULT uuidv7(),
    tenant_id bigint NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (public_id)
);
```

The system gets:

```text
BIGINT
→ compact internal joins

UUIDv7
→ external resource identity
```

This can be an excellent compromise, but it adds two identity concepts that must be documented clearly.

---

# 56. Production Pattern: UUIDv7 as Primary Key

Another design:

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    tenant_id bigint NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Use this when distributed generation or direct public identity is valuable enough to justify the wider key.

Do not assume the presence of UUIDv7 removes the need for `created_at`.

Why?

Because business time should remain explicit and queryable.

---

# 57. Production Pattern: BIGINT PK + Business Number

ERP-style systems often benefit from:

```text
id
invoice_number
```

Example:

```sql
CREATE TABLE invoices (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    invoice_number bigint NOT NULL,
    tenant_id bigint NOT NULL,
    UNIQUE (tenant_id, invoice_number)
);
```

Now:

```text
id
→ technical row identity

invoice_number
→ business/document identity
```

This separation makes later migration much easier.

---

# 58. Tenant-Scoped Document Numbering

Suppose the business requires:

```text
Tenant A → INV-000001
Tenant B → INV-000001
```

A global sequence is the wrong conceptual model.

The number is scoped:

```text
(tenant_id, invoice_number)
```

The database should enforce that scope.

This is an example of a key that looks numeric but is not a universal entity identity.

---

# 59. Sequence Ownership and Migration Safety

When using sequence-backed IDs, understand ownership relationships and lifecycle.

Investigate:

```sql
SELECT *
FROM information_schema.sequences;
```

PostgreSQL exposes sequence metadata through the information schema. citeturn185047search4

For operational debugging, inspect:

```text
sequence name
current state
increment
minimum
maximum
cycle behavior
ownership
```

Do not manually reset sequences in production simply because a development script starts at 1.

Sequence synchronization is part of migration and operational correctness.

---

# 60. Sequence Reset Hazard

Suppose:

```text
existing max(id) = 5000
sequence next value = 100
```

A future insert may collide with existing rows.

This can happen after:

- manual inserts
- bulk imports
- data restores
- migrations
- explicit identity values
- sequence resets

Therefore after controlled imports, verify sequence state rather than assuming it follows table contents automatically.

# 61. Distributed IDs and Clock Skew Testing

If the application uses a time-based distributed ID generator, test:

```text
clock forward
clock backward
same millisecond
high concurrency
node restart
node ID collision
sequence overflow
process restart
```

Do not stop at unit tests such as:

```text
ID is 64-bit integer
```

The dangerous bugs live in boundary conditions.

# 64. Evidence-Driven Index Analysis

Inspect the actual primary-key index:

```sql
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE relname = 'orders';
```

Then compare equivalent workloads with different identifier strategies.

The goal is not:

```text
“UUID index is bigger.”
```

The real engineering question is:

> **Does the additional index footprint materially affect the workload's latency, cache residency, storage budget, or write amplification?**

# 65. Index Width Matters More at Scale

A small table may show negligible practical difference.

A table with:

```text
500 million rows
12 indexes
high write rate
```

is a different problem.

At scale, a few bytes per key can translate into:

```text
many gigabytes
```

across indexes.

This is why key-width trade-offs belong in architecture reviews for very large systems.

# 66. Identifier Choice and Partitioning

If a table is partitioned by a temporal or tenant key, the primary identifier may remain independent.

For example:

```text
PK = UUIDv7
partition = created_at month
```

or:

```text
PK = BIGINT
partition = tenant_id hash
```

Do not force the primary key to serve as the partition key unless that actually matches access and lifecycle requirements.

Identity and physical organization are related but different decisions.

# 67. Identifier Choice and Sharding

In sharded systems, ask:

```text
Does the ID identify the shard?

Does it encode routing?

Is routing external metadata?

Can records move between shards?

Can IDs collide after merge?
```

A distributed ID that embeds node information can simplify routing, but it also couples identifier semantics to topology.

That coupling must be intentional.

---

# 68. Topology Coupling

An ID algorithm that embeds:

```text
region
worker
machine
partition
```

can be operationally useful.

But now changing topology may affect:

- allocation rules
- decoding
- debugging
- migration
- capacity
- identifier semantics

Therefore compare:

```text
opaque global ID
```

against:

```text
topology-aware ID
```

based on operational requirements.

# 73. Expert Interview Questions

### Q1. Why is `PRIMARY KEY` still needed if a column uses an identity sequence?

Because identity specifies automatic generation; uniqueness still needs enforcement. PostgreSQL explicitly notes that identity alone does not guarantee uniqueness. citeturn185047search1

### Q2. Why can a sequence contain gaps?

Because sequence allocation is independent of transaction commit success; an allocated value can be consumed even when its transaction later fails.

### Q3. Why might UUIDv7 be preferable to UUIDv4 for a write-heavy table?

Because UUIDv7 introduces time ordering, generally giving better locality than random UUIDv4 values for B-tree insertion patterns, while preserving distributed generation benefits. PostgreSQL 18 provides native UUIDv7 generation. citeturn185047search0turn185047search3

### Q4. Why is a UUID not an authorization mechanism?

Because uniqueness or unpredictability does not establish whether the current principal is permitted to access the referenced resource.

### Q5. Why might you use BIGINT internally and UUID publicly?

To combine compact internal joins and indexes with externally stable, non-sequential identifiers.

### Q6. When would BIGINT be preferable in a distributed system?

When allocation can remain coordinated or centrally owned and the benefits of compact ordered keys outweigh the need for independently generated identities.

### Q7. Why are idempotency keys different from entity IDs?

They represent operation identity and retry deduplication, not persistent entity identity.

### Q8. Why is `MAX(id)+1` wrong even with a unique constraint?

Because the uniqueness constraint merely detects the race; it does not make the allocation algorithm safe or efficient.

### Q9. Why should business numbering be separated from primary identity?

Because business numbers often have scope, regulatory, lifecycle, or presentation semantics that differ from technical row identity.

### Q10. What can UUIDv7 leak?

Its structure includes time-related information, so it may reveal approximate generation timing. That may matter for privacy or information-disclosure considerations.

# 80. Summary

A production PostgreSQL system may legitimately use several kinds of IDs at once.

The strongest designs separate:

```text
technical identity
business identity
external identity
operation identity
```

`BIGINT` offers compact, ordered, sequence-backed identity when centralized generation is acceptable.

UUIDs provide a distributed-friendly 128-bit identity space, and PostgreSQL 18 provides native UUIDv4 and UUIDv7 generation. UUIDv7 adds useful time-oriented structure without requiring a centralized database sequence. citeturn185047search0turn185047search3

But no identifier solves:

```text
authorization
business numbering
idempotency
tenant isolation
audit semantics
event ordering
```

Those require explicit architecture.

The mature decision is not:

> “UUIDs are modern.”

or:

> “BIGINT is faster.”

It is:

> **“This identifier satisfies the required identity, generation, integrity, workload, security, and operational contracts at acceptable total system cost.”**
