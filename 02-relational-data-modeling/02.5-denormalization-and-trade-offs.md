# 02.5 — Denormalization & Trade-offs

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to intentionally introducing redundancy when workload, latency, operational simplicity, or read patterns justify the additional integrity cost.

---

## 1. Chapter Objective

Normalization gives a disciplined way to place facts at the correct grain and reduce accidental redundancy. But production systems are not judged only by theoretical elegance. They are judged by correctness, latency, throughput, operational cost, availability, and the ability of engineers to evolve them safely.

This chapter develops the skill of **denormalization by evidence**.

The goal is not to teach:

> “Duplicate data when queries are slow.”

The goal is to teach:

> **Identify a measured workload bottleneck, understand the invariant created by redundancy, choose the smallest useful optimization, and make consistency explicit.**

A useful decision chain is:

```text
Business Requirement
    ↓
Correct Normalized Model
    ↓
Observed Workload
    ↓
Measured Bottleneck
    ↓
Read/Write Cost Analysis
    ↓
Controlled Redundancy
    ↓
Synchronization Strategy
    ↓
Verification + Observability
```

---

# 2. Definitions at Three Levels

## 2.1 Simple definition

Denormalization means intentionally storing the same or derived information in more than one place so that some operation becomes cheaper or simpler.

Example:

```text
orders.customer_id
customers.name
```

is normalized.

Adding:

```text
orders.customer_name
```

creates redundant data.

## 2.2 Engineering definition

Denormalization is a schema or data-access design that duplicates, precomputes, materializes, aggregates, or co-locates information that could otherwise be derived from normalized relations.

Typical goals include:

- reducing joins
- reducing repeated aggregation
- reducing network round trips
- improving predictable read latency
- supporting search/read models
- isolating hot read paths
- simplifying reporting workloads

## 2.3 Expert definition

Denormalization changes the database's state space by introducing multiple physical representations of one logical fact or result.

Therefore it creates a new invariant:

```text
canonical fact
      ↕
derived / duplicated representation
```

The engineering problem becomes:

> **How is equivalence maintained, detected when broken, repaired, and observed?**

---

# 3. Normalization Is the Baseline, Not a Religion

A strong production workflow normally begins with a normalized representation because normalized data gives clear ownership and minimizes accidental update anomalies.

Denormalization should generally be a deliberate deviation from that baseline.

This distinction matters because two bad extremes are common:

### Extreme A — Normalize everything forever

Symptoms:

- excessive joins for dominant read paths
- repeated expensive aggregation
- unnecessarily wide query plans
- application code reconstructing the same projection repeatedly
- reporting queries competing with OLTP traffic

### Extreme B — Denormalize immediately

Symptoms:

- duplicated business facts
- conflicting values
- unclear source of truth
- synchronization triggers/events everywhere
- hard-to-debug stale reads
- migration complexity

The correct position is:

> **Normalize for semantic correctness. Denormalize only when a measured workload justifies a known consistency cost.**

---

# 4. What Exactly Are You Duplicating?

Not all duplication has the same risk.

## 4.1 Repeated canonical fact

Example:

```text
customer.email
orders.customer_email
```

Now the same fact is stored twice.

A change to the customer's email creates a synchronization problem.

## 4.2 Derived value

Example:

```text
order.total_amount
```

where the value could be calculated from line items.

This is different: the duplicated value is a **derived fact**.

The question becomes whether the derived value is maintained transactionally and whether historical semantics require it to remain fixed.

## 4.3 Cached value

Example:

```text
product.review_count
```

The count can be derived from another table, but a cached value may be maintained for performance.

The cache has different correctness requirements from a legal business fact.

## 4.4 Historical snapshot

Example:

```text
invoice_item.product_name
invoice_item.unit_price
```

At first this looks redundant because product data exists elsewhere.

But an invoice often needs the value **as it was at transaction time**.

That is not merely performance denormalization. It is historical modeling.

Expert lesson:

> **Do not “normalize away” a historical snapshot merely because the value exists in another table today.**

---

# 5. Denormalization Taxonomy

A useful classification is:

```text
1. Redundant Attribute
2. Precomputed Derived Value
3. Cached Counter
4. Materialized Aggregate
5. Read Model / Projection
6. Search Document
7. Summary Table
8. Horizontal Co-location
9. Historical Snapshot
```

These have different consistency and ownership models.

| Technique | Typical benefit | Main cost |
|---|---|---|
| Redundant attribute | Avoid join | Synchronization |
| Derived column | Faster computation | Recalculation |
| Cached counter | O(1)-like reads | Concurrent update correctness |
| Summary table | Fast reporting | Refresh complexity |
| Materialized view | Reusable expensive result | Staleness/refresh |
| Read model | Tailored reads | Multiple representations |
| Search document | Flexible retrieval | Index/update pipeline |
| Snapshot | Historical correctness | Intentional duplication |

# 6. The First Rule: Measure Before Denormalizing

A query feeling “slow” is not a sufficient reason.

Collect evidence:

```text
p50 latency
p95 latency
p99 latency
execution time
rows examined
rows returned
buffer hits
buffer reads
sort/hash memory
temporary files
CPU
lock waits
planning time
call frequency
```

A query that runs in 40 ms but is executed 200,000 times per minute can be more important than one query that takes 3 seconds and runs twice per hour.

Therefore prioritize by workload impact:

```text
Impact ≈ Frequency × Cost × Criticality
```

The exact formula is workload-specific, but the principle is stable: optimize the workload, not the prettiest query.

---

# 7. EXPLAIN First

Before denormalization, inspect the existing query.

Typical tools:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Look for:

- unexpectedly high row counts
- bad cardinality estimates
- repeated nested-loop work
- large sorts
- hash spills
- sequential scans on large relations
- excessive heap fetches
- join amplification
- unnecessary repeated aggregation

Sometimes the answer is not denormalization at all.

The real fix may be:

```text
missing index
bad predicate
wrong data type
implicit cast
poor statistics
query shape
pagination bug
N+1 query pattern
```

Denormalization before diagnosis is often permanent complexity used to treat a temporary or unrelated problem.

---

# 8. Naive Approach → Why It Fails

## Example: Copy Customer Name Into Every Order

### Naive Approach

```sql
ALTER TABLE orders
ADD COLUMN customer_name text;
```

Application writes:

```text
order.customer_name = customer.name
```

### Why It Fails

Suppose:

```text
Customer 42 = "Milan"
```

and 10,000 orders contain that name.

The customer changes the display name:

```text
"Milan" → "Milan Kumar"
```

Now the database contains contradictory states.

Questions immediately appear:

- Which value is canonical?
- Are historical orders supposed to change?
- Which code path updates both?
- What happens on bulk import?
- What happens after a retry?
- How are missing updates detected?

The schema has acquired an invariant without documenting or enforcing it.

---

# 9. Improved Approach: Snapshot vs Cache

Ask what the duplicate column means.

## Case A — Current customer name

The order is expected to show the customer's latest current name.

Then duplication is a cache.

Possible mechanisms:

- transactional update
- trigger
- asynchronous event consumer
- periodic rebuild

## Case B — Name at order creation time

Then the duplicate is a historical snapshot.

That can be the correct design even though it is redundant.

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers(id),
    customer_name_snapshot text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Now the column's meaning is explicit.

The key insight:

> **Semantic duplication can be correct when the duplicated value represents a different temporal fact.**

# 10. Cached Counters

A common denormalization is a counter.

Normalized source:

```text
posts
-----
id

comments
--------
id
post_id
```

Expensive read:

```sql
SELECT count(*)
FROM comments
WHERE post_id = $1;
```

Denormalized representation:

```text
posts.comment_count
```

## Why It Helps

A frequent dashboard request may become a single-row read.

## The Hard Part

Concurrency.

This is dangerous:

```sql
SELECT comment_count FROM posts WHERE id = $1;
-- application adds 1
UPDATE posts SET comment_count = $2 WHERE id = $1;
```

Two concurrent requests can overwrite each other's increments.

Prefer an atomic database operation when the invariant supports it:

```sql
UPDATE posts
SET comment_count = comment_count + 1
WHERE id = $1;
```

Or maintain the counter transactionally with the creation/deletion of the underlying row.

But even atomic increments do not solve every semantic problem. Retries, deletes, failed transactions, bulk loads, and reconciliation still matter.

---

# 11. The Counter Is a Derived Invariant

Suppose the rule is:

```text
posts.comment_count = count(comments for post)
```

Then you have two physical representations of one logical quantity.

That means you should be able to express a reconciliation query:

```sql
SELECT
    p.id,
    p.comment_count AS stored_count,
    count(c.id) AS actual_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.comment_count
HAVING p.comment_count <> count(c.id);
```

This is an important production pattern:

> **Every derived representation should have a way to verify itself against the canonical source.**

---

# 12. Materialized Aggregates

Suppose an ERP dashboard repeatedly asks:

```text
sales by branch by month by category
```

Computing the aggregation from millions of transactional rows on every request may be expensive.

A summary table can store:

```text
branch_id
month
category_id
sales_amount
invoice_count
```

This changes the cost model from:

```text
many detailed rows → expensive aggregation
```

to:

```text
small summary relation → cheap read
```

But now writes or refreshes have additional work.

This is useful when:

- reads dominate
- aggregates are reused
- exact freshness requirements are known
- the source changes predictably

---

# 13. Materialized View vs Summary Table

A materialized view can be useful when the query itself is the reusable definition of a derived dataset.

A summary table can be preferable when the system needs incremental updates, custom retention, explicit reconciliation, or application-specific write control.

The trade-off is roughly:

```text
Materialized View
    ↓
Simple derivation
    ↓
Refresh strategy

Summary Table
    ↓
More control
    ↓
More application/database responsibility
```

Neither is universally better.

Choose based on:

- freshness
- refresh cost
- write rate
- operational complexity
- recovery strategy
- query reuse

---

# 14. Read Models

A read model is often a cleaner form of denormalization than copying random columns into OLTP tables.

Normalized write model:

```text
customers
orders
order_items
payments
shipments
```

Read model:

```text
customer_order_summary
----------------------
customer_id
customer_name
order_count
lifetime_value
last_order_at
open_balance
```

The read model has an explicit purpose.

This is often preferable to making core transactional tables carry every dashboard optimization.

---

# 15. Denormalization and CQRS

A system may intentionally have:

```text
Write Model
    ↓
Canonical transactional state

Read Model
    ↓
Optimized projection
```

The read model can be rebuilt from canonical data if the architecture permits.

This property is extremely valuable.

A rebuildable projection is safer than an opaque duplicate whose history cannot be reconstructed.

Therefore ask:

> **Can this denormalized representation be regenerated?**

If yes, operational recovery is usually easier.

---

# 16. Keep One Clear Source of Truth

Bad architecture:

```text
Table A owns value X
Table B also owns value X
Application code decides which one is right
```

Better:

```text
Canonical Source
      ↓
Derived Representation
```

Document:

```text
Source of truth: customers.name
Derived copy: customer_search_document.display_name
Update path: asynchronous projection
Expected staleness: < 5 seconds
Recovery: full rebuild
```

That turns hidden coupling into an explicit contract.

---

# 17. Denormalization and Transaction Boundaries

A key design decision is whether the source and derived representation must change atomically.

## Strong consistency required

Use a single transaction when possible.

Example:

```text
create order
create order item
update order total
```

If readers must never observe an intermediate state, these changes belong within a transaction boundary that preserves the invariant.

## Eventual consistency acceptable

You may publish an event:

```text
transaction commits
    ↓
OrderCreated
    ↓
projection updates read model
```

Now readers may briefly see stale information.

That is acceptable only if the business semantics permit it.

---

# 18. Do Not Hide Eventual Consistency

If a value may be stale, the architecture should make that fact visible.

Bad assumption:

```text
read_model.balance == ledger.balance
```

always.

Potential reality:

```text
ledger.balance = canonical
read_model.balance = eventually consistent projection
```

This matters for financial systems, inventory, permissions, and workflows.

For high-risk decisions, read from the canonical source or use a consistency mechanism strong enough for the invariant.

---

# 19. Historical Snapshots Are Not “Bad Normalization”

Consider invoice lines:

```text
product_id
product_name_snapshot
unit_price_snapshot
vat_rate_snapshot
```

Why duplicate product data?

Because the invoice represents what was sold under a particular commercial state.

Product data may later change.

If the invoice instead joined the current product row:

```text
current product name
current product price
```

historical reporting could become incorrect.

Therefore model business snapshots intentionally:

```text
Current Product State
≠
Historical Transaction State
```

This distinction is essential in ERP, accounting, billing, taxation, inventory, and audit systems.

---

# 20. Denormalization by Co-location

Sometimes the optimization is not copying a value but storing frequently accessed attributes together.

For example, splitting a very wide table may make a hot query read fewer pages:

```text
users_core
users_profile
users_preferences
```

But excessive vertical splitting can create repeated joins.

The decision should consider:

- row width
- access frequency
- TOAST usage
- cache residency
- update frequency
- hot/cold column separation

The optimization is physical access behavior, not theoretical normalization.

---

# 21. Wide Tables Can Also Be a Denormalization Trade-off

A wide row can reduce joins but increase I/O for operations that need only a small subset of columns.

A narrow table can improve cache density but require more joins.

Think in terms of workload:

```text
Join Cost
vs
Row Width Cost
```

Measure both.

A schema should not be vertically split merely because “small tables are cleaner.”

---

# 22. Denormalization and Indexing

A common mistake is to denormalize when an index would solve the problem.

Example query:

```sql
SELECT *
FROM orders
WHERE customer_id = $1
ORDER BY created_at DESC
LIMIT 20;
```

The first investigation should include an index such as:

```sql
CREATE INDEX ON orders (customer_id, created_at DESC);
```

not immediately:

```text
customers.latest_order_1
customers.latest_order_2
...
```

Always compare:

```text
query rewrite
index
statistics
partitioning
cache behavior
materialization
schema change
```

in that order only when evidence supports it.

---

# 23. Denormalization Does Not Automatically Remove Joins

Suppose an order page needs:

```text
order
customer
items
payments
shipments
```

Copying `customer_name` into orders may remove one join, but the page still requires multiple relationships.

A small reduction in joins does not automatically produce a meaningful latency improvement.

Measure the actual critical path.

---

# 24. N+1 Is Usually an Application Problem First

Bad application pattern:

```text
GET orders
for each order:
    GET customer
```

An engineer may respond:

> “Let's copy customer data into orders.”

But the real fix may be:

```sql
SELECT ...
FROM orders o
JOIN customers c ON c.id = o.customer_id;
```

or a batched query.

Do not encode an application access-pattern bug into permanent schema redundancy.

---

# 25. JSONB as Denormalization

A JSONB document can itself be a denormalized read model.

For example:

```json
{
  "orderId": 1001,
  "customer": {
    "id": 42,
    "name": "Milan"
  },
  "totals": {
    "subtotal": 1000,
    "tax": 180,
    "grandTotal": 1180
  }
}
```

This can be excellent for read-oriented APIs.

But the document is now another representation of state.

Ask:

- Who owns the canonical customer name?
- Is the JSON current or historical?
- How is it rebuilt?
- How are partial failures handled?
- How large can documents become?
- Which fields are query-critical?

JSONB does not remove data modeling problems. It moves them.

---

# 26. Arrays Can Also Hide Denormalization

Example:

```text
users.role_ids bigint[]
```

instead of:

```text
user_roles(user_id, role_id)
```

This is not merely a storage choice. The array has replaced a relational relationship with a collection embedded in a row.

You lose or complicate:

- foreign-key enforcement
- row-level auditing
- relationship attributes
- referential actions
- natural uniqueness
- relationship-level concurrency

Use arrays when the collection is truly an attribute and its integrity requirements fit the type.

---

# 27. Denormalization and Multi-Tenancy

In a multi-tenant system, redundancy must preserve tenant boundaries.

Bad derived table:

```text
customer_id
order_total
```

without tenant identity when IDs are only meaningful inside a tenant.

Safer representation:

```text
tenant_id
customer_id
order_total
```

and, where required, composite foreign keys and uniqueness constraints that prevent cross-tenant associations.

Derived data is still security-sensitive data.

A denormalized read model must not create a new path around tenant isolation.

---

# 28. Soft Deletes and Derived Data

Soft deletion creates another common inconsistency.

Suppose:

```text
comments.deleted_at
posts.comment_count
```

What does the counter mean?

```text
all comments?
only visible comments?
only non-deleted comments?
```

The invariant must be explicit.

For example:

```text
comment_count = count(comments WHERE deleted_at IS NULL)
```

Then every delete/restore operation must preserve that definition.

Derived values fail most often when their semantic definition is ambiguous.

---

# 29. Cache Invalidation Is Still a Database Problem

The classic difficulty is not merely storing the cached value. It is determining when it becomes invalid.

Suppose:

```text
product.price
```

is copied into:

```text
homepage_product_cache.price
```

Any path that changes the price must account for the cache.

Paths may include:

```text
admin UI
bulk import
scheduled job
migration
manual SQL
integration webhook
promotion service
```

Therefore a denormalization strategy is only as reliable as the set of mutation paths it covers.

---

# 30. Prefer Rebuildable Derived Data

Strong architecture:

```text
Canonical Tables
       ↓
Projection Function
       ↓
Read Model
```

If the projection breaks:

```text
truncate/rebuild projection
```

Weak architecture:

```text
ten unrelated application paths
       ↓
ten duplicated updates
```

with no authoritative rebuild procedure.

Rebuildability is one of the strongest design criteria for denormalization.

---

# 31. Reconciliation Jobs

Production systems often need periodic checks.

Examples:

```text
stored counter != computed counter

search document version != source version

summary row total != transactional aggregate
```

A reconciliation process can:

1. detect mismatches
2. record them
3. repair safe cases
4. alert on abnormal rates

This transforms silent drift into observable system behavior.

---

# 32. Versioning Derived Representations

A simple technique is to store a source version or update timestamp.

Example:

```text
source.updated_at
projection.source_updated_at
```

Now a consumer can detect stale data.

Another pattern is:

```text
source_version bigint
projection_version bigint
```

Then:

```text
projection_version < source_version
```

means the projection is behind.

This is especially useful in asynchronous read models.

---

# 33. Idempotency Matters

Event-driven denormalization must handle retries.

Suppose:

```text
OrderCreated(order_id=100)
```

is delivered twice.

A projection must not create duplicate state.

Use patterns such as:

```text
unique source event id
upsert by business key
source sequence/version
```

Do not assume “exactly once delivery” will eliminate the need for idempotent projection logic.

---

# 34. Delete Semantics Become Harder

When canonical data disappears, what happens to derived data?

Possible choices:

```text
cascade
soft delete
retain snapshot
rebuild later
mark stale
```

A denormalized schema must define these transitions.

This is particularly important for:

- user deletion
- tenant deletion
- GDPR/privacy workflows
- archived records
- financial retention
- search indexes

---

# 35. Security Review for Denormalization

Redundancy can create unintended copies of sensitive information.

For every duplicate representation ask:

- Does it contain PII?
- Does it need separate access control?
- Does it appear in logs?
- Does it appear in search indexes?
- Does it survive deletion requests?
- Does backup retention create another copy?

A denormalized column can create a data-governance problem even when it solves a performance problem.

---

# 36. Observability for Denormalized Systems

Track metrics such as:

```text
projection lag
reconciliation mismatch count
repair count
cache hit ratio
refresh duration
refresh failures
stale-read rate
queue depth
projection throughput
```

The most useful signal is often **drift**, not raw storage size.

---

# 37. Testing Strategy

Denormalized designs require more than query tests.

## Invariant tests

Verify:

```text
stored value == recomputed value
```

where exact equality is the intended contract.

## Transaction tests

Test creation/update/deletion together with derived state.

## Concurrency tests

Exercise simultaneous operations:

```text
+1
+1
-1
retry
```

and verify the final invariant.

## Failure-injection tests

Simulate:

```text
transaction succeeds
projection fails
consumer retries
consumer restarts
partial batch failure
```

A denormalization design that only works on the happy path is not production-ready.

---

# 38. Performance Lab

Use a controlled experiment.

### Baseline

```text
Normalized query
p95 = 180 ms
```

### Candidate change

Add a summary/read model.

### Measure

```text
p95 = 18 ms
write overhead = +7%
storage = +12%
projection lag = 400 ms
```

Now the trade-off is concrete.

A decision can be justified with facts rather than preference.

---

# 39. Architecture Decision Framework

Use this sequence.

```text
1. Is the normalized model correct?
2. What exact workload is slow or expensive?
3. Can indexing/query changes solve it?
4. Can caching solve it externally?
5. Is the expensive result stable enough to materialize?
6. What is the source of truth?
7. What consistency level is required?
8. How is derived data updated?
9. How is drift detected?
10. Can it be rebuilt?
11. What happens on delete/restore?
12. What security/privacy copies are created?
13. What metrics prove the design works?
```

# 40. Production Decision Matrix

| Situation | Prefer |
|---|---|
| Accidental slow query | Diagnose query/index first |
| Repeated expensive aggregate | Summary/materialized representation |
| Historical transaction value | Explicit snapshot |
| High-frequency counter | Atomic cached counter + reconciliation |
| API-specific projection | Read model |
| Search-oriented representation | Search/index projection |
| Cross-system asynchronous view | Event-driven projection |
| Core business fact | Canonical normalized storage |
| Strong referential integrity required | Relational structure + constraints |
| Rare reporting query | Usually normalized source + analytical strategy |

# 41. Common Anti-Patterns

## Anti-pattern 1 — Denormalize before measuring

Why it fails:

```text
more complexity
no proven benefit
```

## Anti-pattern 2 — Duplicate canonical values with no ownership rule

Why it fails:

```text
conflicting truth
```

## Anti-pattern 3 — Application-only synchronization

Why it fails:

```text
one mutation path gets missed
```

## Anti-pattern 4 — No reconciliation mechanism

Why it fails:

```text
drift becomes silent
```

## Anti-pattern 5 — Treating eventual consistency as invisible

Why it fails:

```text
business code assumes stronger consistency than the architecture provides
```

## Anti-pattern 6 — Using a denormalized field to avoid fixing N+1

Why it fails:

```text
schema complexity replaces an access-layer bug
```

## Anti-pattern 7 — Copying sensitive data everywhere

Why it fails:

```text
security and retention surface expands
```

# 42. AI / Vibe-Coding Failure Modes

AI-generated schemas frequently produce patterns like:

```text
orders.customer_name
orders.customer_email
orders.customer_phone
customers.name
customers.email
customers.phone
```

without defining whether those fields are:

- cache values
- snapshots
- convenience copies
- canonical facts

Another common failure is:

```text
comment_count
```

without concurrency-safe maintenance.

Another is:

```text
summary table
```

with no rebuild procedure.

The review question should be:

> **“What invariant does this duplicate create, and who is responsible for maintaining it?”**

Follow with:

> **“Show me the recovery path when the invariant is violated.”**

# 43. Evidence-Driven Debugging Workflow

When a denormalized system is wrong:

```text
1. Identify canonical source.
2. Identify derived representation.
3. State expected invariant precisely.
4. Find first divergence.
5. Identify mutation path that caused it.
6. Determine whether transaction committed.
7. Check event/projection delivery.
8. Recompute canonical value.
9. Repair safely.
10. Add a regression or reconciliation check.
```

Do not start by manually editing the wrong value.

First determine why it became wrong.

# 44. Production Scenario — Jewellery ERP

Suppose an ERP has:

```text
products
branches
stock_movements
stock_balances
sales
sale_items
payments
```

The canonical inventory state may be derived from movements.

But branch dashboards may need:

```text
available_quantity
reserved_quantity
stock_value
last_movement_at
```

A summary relation can be justified if dashboards are high-frequency and movement history is large.

However:

```text
stock_movements = canonical ledger/fact source
stock_balances = derived operational representation
```

must remain conceptually distinct.

The system should define:

- transaction boundary
- reservation semantics
- concurrency strategy
- reconciliation logic
- rebuild process
- tenant/branch isolation
- audit requirements

This is denormalization as an engineering decision, not a shortcut.

---

# 45. Production Scenario — Customer Dashboard

Suppose a dashboard needs:

```text
customer name
order count
last order date
lifetime spend
open balance
```

Normalized joins and aggregates may be acceptable at low scale.

At high traffic, repeatedly calculating everything may become expensive.

A read model can precompute the projection.

The design question becomes:

```text
How fresh must each metric be?
```

For example:

```text
customer name → near real-time
order count   → seconds acceptable
lifetime spend → seconds acceptable
open balance  → perhaps strong consistency required
```

Different fields can have different consistency requirements.

Do not force every dashboard attribute into one consistency model without analysis.

---

# 46. When Denormalization Is Justified

A strong justification usually contains all of these:

```text
Observed workload problem
      +
Measured improvement opportunity
      +
Known source of truth
      +
Explicit consistency contract
      +
Safe update mechanism
      +
Reconciliation strategy
      +
Rebuild/recovery procedure
```

If several are missing, the design is probably premature.

---

# 47. Trade-off Summary

Denormalization can improve:

```text
read latency
throughput
predictability
query simplicity
API response construction
reporting efficiency
search access
```

But it can worsen:

```text
write amplification
storage
```

# 52. Final Mental Model

Keep this model permanently:

```text
NORMALIZATION
    ↓
Correct Facts
    ↓
Clear Ownership
    ↓
Explicit Dependencies

DENORMALIZATION
    ↓
Intentional Additional Representation
    ↓
Explicit Invariant
    ↓
Known Consistency Cost
    ↓
Measured Workload Benefit
    ↓
Update + Reconciliation + Recovery
```

The expert does not ask:

> “Can I avoid this join?”

The expert asks:

> **“What workload cost am I trying to remove, what invariant will redundancy create, and can the system maintain and recover that invariant safely?”**

That is the difference between accidental duplication and deliberate database engineering.
