# 02.13 — Multi-Tenant Modeling

> **Phase 02 — Relational Data Modeling**
>
> A production-grade guide to designing PostgreSQL data models where many independent tenants share one database, while preserving isolation, correctness, operability, and a credible path to scale.

---

## 1. Chapter Objective

Multi-tenancy is not simply adding a `tenant_id` column. It is the design of a system in which one physical database infrastructure serves multiple logically isolated customers while the application preserves the invariant:

> **A tenant must never be able to read, mutate, infer, or indirectly affect data belonging to another tenant unless an explicit cross-tenant capability exists.**

This chapter develops that invariant from first principles and turns it into schema, constraint, transaction, security, indexing, query, migration, and operational decisions.

By the end of this chapter you should be able to:

- distinguish shared-database, schema-per-tenant, and database-per-tenant architectures;
- decide where tenant identity belongs in a relational model;
- design composite foreign keys that preserve tenant boundaries;
- enforce tenant ownership in the database instead of relying only on application code;
- use PostgreSQL Row-Level Security (RLS) correctly;
- understand `USING` and `WITH CHECK` as different security properties;
- propagate tenant context safely through Node.js/NestJS transactions;
- prevent cross-tenant uniqueness and reference bugs;
- design tenant-aware indexes and query patterns;
- reason about noisy neighbors, hot tenants, connection pools, and large tenants;
- design migrations, archival, deletion, and restore workflows per tenant;
- understand when to choose row-level, schema-level, or database-level isolation;
- diagnose tenant leaks using evidence rather than intuition;
- design a model appropriate for production systems such as a multi-branch jewellery ERP.

---

## 2. Definitions

### 2.1 Simple definition

**Multi-tenancy** means one software system serves multiple customers while keeping each customer's data appropriately isolated.

### 2.2 Engineering definition

A multi-tenant relational system stores and processes data for multiple independent ownership domains and provides a reliable mechanism for enforcing tenant boundaries across reads, writes, relationships, uniqueness, transactions, background jobs, analytics, and operational workflows.

### 2.3 Expert definition

Multi-tenancy is an **isolation architecture**. The central design question is not "where do I store `tenant_id`?" but:

> **At which database boundary is tenant isolation enforced, and how does that boundary interact with every relational invariant and every execution path?**

That distinction matters because a system can contain `tenant_id` everywhere and still leak data through:

- missing query predicates;
- incorrect joins;
- foreign keys that are globally valid but not tenant-valid;
- unique constraints with the wrong scope;
- background workers without tenant context;
- reports that aggregate all tenants;
- RLS policies applied only to `SELECT` but not `INSERT`/`UPDATE`;
- privileged roles that bypass RLS;
- cross-tenant identifiers exposed through errors;
- caches keyed only by entity ID;
- event payloads missing tenant identity;
- administrative APIs with ambiguous tenant scope.

# 3. First Principles

## 3.1 A tenant is an ownership boundary

Suppose an application serves:

```text
Tenant A = Makkah Jewellers
Tenant B = Sharma Jewellers
Tenant C = Royal Gold House
```

An `invoice` belongs to exactly one tenant.

Conceptually:

```text
Tenant
  |
  +---- Customer
  |
  +---- Product
  |
  +---- Invoice
  |
  +---- Payment
  |
  +---- Inventory
```

The fundamental invariant is:

```text
entity.tenant_id = current_context.tenant_id
```

for all tenant-owned entities.

But relational integrity adds another invariant:

```text
child.tenant_id = parent.tenant_id
```

for tenant-scoped relationships.

These are different invariants.

The first protects **execution context**.
The second protects **relational ownership**.

A mature architecture enforces both.

---

## 3.2 Tenant isolation is a graph property

A common beginner model is:

```text
orders.tenant_id
customers.tenant_id
products.tenant_id
```

and then assumes isolation exists.

But the real schema is a graph:

```text
Tenant
  |
  +--> Customer
  |      |
  |      +--> Address
  |
  +--> Order
         |
         +--> OrderItem --> Product
```

A cross-tenant relationship can occur when:

```text
order.tenant_id = A
order_item.tenant_id = A
product.id = product owned by B
```

A normal single-column foreign key can permit that if `product.id` is globally unique.

So the deeper invariant is:

```text
(order_item.tenant_id, order_item.product_id)
    references
(product.tenant_id, product.id)
```

This is why tenant-aware composite keys are so important.

# 4. Multi-Tenancy Models

There are three classic physical isolation strategies.

## 4.1 Shared database + shared schema

```text
One PostgreSQL database
        |
        +-- customers(tenant_id, ...)
        +-- orders(tenant_id, ...)
        +-- products(tenant_id, ...)
```

Every tenant shares tables.

### Advantages

- lowest infrastructure cost;
- easiest global deployment model;
- simplest schema migration surface;
- high resource efficiency;
- easy global operational tooling.

### Risks

- strongest requirement for correct tenant enforcement;
- noisy-neighbor interactions;
- large tenant tables;
- harder tenant-level backup/restore;
- accidental cross-tenant queries can have large blast radius.

This is frequently the best default for SaaS systems with many tenants when the workload and compliance requirements permit shared infrastructure.

---

## 4.2 Shared database + schema per tenant

```text
Database
  |
  +-- tenant_a.orders
  +-- tenant_a.products
  +-- tenant_b.orders
  +-- tenant_b.products
```

### Advantages

- stronger namespace separation;
- easier tenant-focused dump/restore in some operational designs;
- tenant-specific schema objects become possible.

### Risks

- schema count grows with tenant count;
- migrations become operationally expensive;
- connection/search-path mistakes become dangerous;
- cross-tenant analytics becomes harder;
- PostgreSQL catalogs and DDL operations become increasingly complex at high tenant counts.

A schema-per-tenant design is not automatically "more secure". It changes the isolation mechanism.

---

## 4.3 Database per tenant

```text
Tenant A -> database A
Tenant B -> database B
Tenant C -> database C
```

### Advantages

- strongest physical logical boundary among the common patterns;
- tenant-specific backup/restore is natural;
- easier tenant-specific scaling and placement;
- useful for strict isolation requirements.

### Risks

- operational complexity;
- migrations across many databases;
- connection management;
- monitoring complexity;
- provisioning/deprovisioning cost;
- cross-tenant reporting complexity.

---

## 4.4 Hybrid isolation

Production systems frequently use a hybrid model:

```text
small tenants -> shared DB
large tenants -> isolated DB
regulated tenants -> dedicated DB
```

This can be an excellent architecture when the business needs tiered isolation.

The key is to make the tenant's physical placement a piece of explicit infrastructure metadata rather than accidental application state.

---

# 5. Choosing the Isolation Boundary

Use these questions:

| Question | Shared schema | Schema per tenant | DB per tenant |
|---|---:|---:|---:|
| Hundreds/thousands of small tenants? | Excellent | Possible | Expensive |
| Strict customer isolation? | Requires strong controls | Better namespace boundary | Strong |
| Tenant-specific restore? | Harder | Better | Excellent |
| Global analytics? | Easy | Moderate | Harder |
| Schema migrations? | Simple | More complex | Most complex |
| Tenant-specific scaling? | Limited | Moderate | Excellent |
| Infrastructure cost? | Lowest | Medium | Highest |

Do not select an architecture from a generic "best practice" list. Start from:

```text
Isolation requirement
+ compliance requirement
+ tenant count
+ tenant size distribution
+ operational model
+ backup/restore requirements
+ workload profile
```

# 6. The Shared-Schema Model

For the remainder of this chapter, most examples use:

```text
shared database + shared schema + tenant_id
```

Example:

```sql
CREATE TABLE tenants (
    id uuid PRIMARY KEY,
    name text NOT NULL,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    name text NOT NULL,
    phone text,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

At first glance this looks sufficient.

It is not.

The next question is: **what is the scope of every invariant?**

---

# 7. Tenant-Scoped Identity

## 7.1 Global identity vs tenant-local identity

There are two common identifiers:

```text
Globally unique entity ID:
customer.id = 8418292

Tenant-local business number:
customer.customer_code = CUST-00124
```

The former can be globally unique.
The latter is often unique only within a tenant.

Therefore:

```sql
UNIQUE (tenant_id, customer_code)
```

is usually correct when the business says:

> No two customers within one tenant may have the same customer code.

A global constraint would encode a different business rule.

---

## 7.2 Tenant-local natural keys

Suppose each branch can assign:

```text
INV-000001
INV-000002
```

A multi-tenant design may require:

```sql
UNIQUE (tenant_id, invoice_number)
```

A branch-aware system may require:

```sql
UNIQUE (tenant_id, branch_id, invoice_number)
```

Constraint design should follow the **actual ownership boundary**.

---

# 8. The Most Important Referential Integrity Pattern

Consider:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    sku text NOT NULL
);

CREATE TABLE order_items (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    product_id bigint NOT NULL REFERENCES products(id)
);
```

This permits a dangerous state:

```text
order_item.tenant_id = A
product_id = product owned by B
```

The FK verifies only:

```text
product_id exists
```

It does not verify:

```text
product belongs to same tenant
```

## 8.1 Correct composite reference

Create a uniqueness target:

```sql
ALTER TABLE products
ADD CONSTRAINT uq_products_tenant_id_id
UNIQUE (tenant_id, id);
```

Then:

```sql
ALTER TABLE order_items
ADD CONSTRAINT fk_order_items_product_same_tenant
FOREIGN KEY (tenant_id, product_id)
REFERENCES products (tenant_id, id);
```

Now PostgreSQL can enforce:

```text
order_items.tenant_id = products.tenant_id
```

as a relational invariant.

### Why this matters

Application code can accidentally perform:

```ts
await orderItemRepo.insert({
  tenantId: tenantA,
  productId: productFromTenantB,
});
```

A properly designed composite FK turns this from a silent data corruption bug into a rejected transaction.

This is one of the highest-value multi-tenant schema patterns to master.

# 9. Branches Inside Tenants

A jewellery ERP often has:

```text
Tenant
  |
  +-- Branch 1
  +-- Branch 2
  +-- Branch 3
```

A branch belongs to a tenant:

```sql
CREATE TABLE branches (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    name text NOT NULL,
    CONSTRAINT uq_branches_tenant_id_id UNIQUE (tenant_id, id),
    CONSTRAINT uq_branches_tenant_name UNIQUE (tenant_id, name)
);
```

Then a branch-owned entity can enforce both dimensions:

```sql
CREATE TABLE stock_locations (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL,
    branch_id bigint NOT NULL,
    name text NOT NULL,

    CONSTRAINT fk_stock_locations_branch
        FOREIGN KEY (tenant_id, branch_id)
        REFERENCES branches (tenant_id, id),

    CONSTRAINT uq_stock_locations_tenant_id_id
        UNIQUE (tenant_id, id),

    CONSTRAINT uq_stock_locations_branch_name
        UNIQUE (tenant_id, branch_id, name)
);
```

This establishes a hierarchy:

```text
stock_location
    -> branch
        -> tenant
```

without trusting the application to keep those IDs aligned.

---

# 10. Tenant Ownership Should Be Explicit

For most shared-schema designs, every tenant-owned row should have a clearly identifiable ownership path.

Good:

```text
orders.tenant_id
order_items.tenant_id
payments.tenant_id
products.tenant_id
```

Potentially unsafe:

```text
orders.tenant_id
order_items.order_id
payments.order_id
```

where downstream records rely on indirect joins to determine ownership.

## 10.1 Direct tenant ID vs inherited ownership

Direct `tenant_id` adds redundancy.

For example:

```text
order_items.tenant_id
order_items.order_id
```

is technically redundant if the order owns the item.

But it can be valuable because it enables:

- direct RLS policies;
- tenant-aware indexes;
- faster tenant filtering;
- explicit composite FKs;
- easier bulk deletion;
- easier operational diagnostics.

The redundancy is justified when the duplicated value is itself an important integrity boundary.

---

# 11. Tenant-Scoped Uniqueness

A frequent error is:

```sql
UNIQUE (email)
```

when the real rule is:

> The email must be unique within each tenant.

Correct:

```sql
UNIQUE (tenant_id, email)
```

Or, for soft-deleted records:

```sql
CREATE UNIQUE INDEX uq_active_user_email_per_tenant
ON users (tenant_id, lower(email))
WHERE deleted_at IS NULL;
```

This encodes:

```text
unique among active rows within tenant
```

---

# 12. Tenant-Scoped Case-Insensitive Uniqueness

Do not rely on application normalization alone:

```ts
email.toLowerCase()
```

A database invariant should be encoded where practical.

Example:

```sql
CREATE UNIQUE INDEX uq_users_tenant_email_ci
ON users (tenant_id, lower(email));
```

For more complex identity requirements, consider whether a normalized canonical column, generated column, or an appropriate PostgreSQL type/operator behavior better expresses the business rule.

The important question is not:

> "Can I lowercase it in Node?"

It is:

> "What exact equivalence relation defines identity in this tenant?"

---

# 13. Row-Level Security (RLS)

RLS is PostgreSQL's native row filtering/security mechanism for table access.

A policy can specify:

- which existing rows a role may see or modify (`USING`);
- which new row values may be inserted/produced (`WITH CHECK`).

RLS must be enabled on a table for its policies to apply. PostgreSQL 18 documents that multiple permissive policies combine with OR while restrictive policies combine with AND, and that `USING` filters existing rows while `WITH CHECK` validates new rows. citeturn987305search0

---

# 14. Basic RLS Tenant Pattern

Suppose the application establishes the current tenant in a transaction-local setting.

```sql
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;

CREATE POLICY customers_tenant_isolation
ON customers
USING (tenant_id = current_setting('app.tenant_id')::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

The conceptual model is:

```text
SELECT/UPDATE/DELETE existing rows
        -> USING

INSERT/UPDATE resulting rows
        -> WITH CHECK
```

Using both is usually essential for strict tenant isolation.

---

# 15. Why `USING` Alone Is Not Enough

Suppose you define:

```sql
CREATE POLICY customers_tenant_select
ON customers
USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

This protects row visibility but does not express the complete write invariant.

An update might attempt to move a row between tenants unless another invariant blocks it.

A complete policy commonly requires:

```sql
USING (...)
WITH CHECK (...)
```

The mental model is:

```text
USING    = Which existing rows may this role operate on?
WITH CHECK = What must the resulting/new row satisfy?
```

---

# 16. RLS Is Not a Replacement for Constraints

RLS and relational constraints solve different classes of problems.

```text
RLS
  -> who may access which rows

Constraints
  -> which database states are valid
```

For example:

```text
RLS: user may access only tenant A
FK: order_item.product must belong to tenant A
UNIQUE: invoice_number unique within tenant A
CHECK: amount >= 0
```

A secure design usually combines all of them.

---

# 17. Default Deny Is Valuable

When RLS is enabled and no applicable policy permits access, PostgreSQL uses a default-deny behavior for rows. This is useful as a fail-closed baseline. citeturn987305search0turn987305search4

This leads to an important deployment rule:

> Prefer a system where a missing policy causes visible failure rather than silent global visibility.

A missing predicate in application SQL is dangerous.
A missing RLS policy should be operationally obvious.

---

# 18. RLS and Privileged Roles

RLS must be evaluated with the actual database role model.

PostgreSQL roles with appropriate privileges can bypass RLS; superusers and roles with `BYPASSRLS` are not subject to normal RLS enforcement. PostgreSQL 18 explicitly documents `BYPASSRLS`/`NOBYPASSRLS` role attributes. citeturn987305search6turn987305search8

Therefore:

```text
"We have RLS"
```

is not enough.

You must know:

```text
Which DB role does the API use?
Which role do background workers use?
Which role runs migrations?
Which role performs reporting?
Which role performs support/admin actions?
Which roles bypass RLS?
```

---

# 19. RLS and Referential Integrity

A critical PostgreSQL detail is that internal referential-integrity checks are not ordinary user table queries governed in the same way by RLS policies. The PostgreSQL documentation notes that RLS policies are not applied while the system performs internal referential-integrity checks or validates constraints. citeturn987305search0

Security design therefore cannot assume:

```text
RLS + FK = zero existence inference
```

For some APIs, an attacker may infer whether a hidden referenced value exists from whether a mutation succeeds or fails.

This matters when identifiers have external meaning.

Prefer opaque/generated identifiers for externally exposed entities when existence inference would be sensitive.

---

# 20. Tenant Context Propagation

A tenant-aware request typically has a context chain:

```text
HTTP request
   |
   +-- authenticated principal
   |
   +-- resolved tenant
   |
   +-- transaction
          |
          +-- SQL statements
```

The database must receive the same authoritative tenant context used by authorization.

A common PostgreSQL pattern is a transaction-local custom setting:

```sql
BEGIN;

SET LOCAL app.tenant_id = '...uuid...';

-- all SQL for this transaction

COMMIT;
```

`SET LOCAL` is valuable because the setting lasts only for the current transaction.

That prevents tenant context from leaking across pooled connections when correctly managed.

---

# 21. Node.js / NestJS Transaction Boundary

A dangerous anti-pattern is:

```ts
await pool.query(`SET app.tenant_id = '${tenantId}'`);
```

followed later by a transaction using another client.

With pooled connections, the context can be applied to one physical connection and the query can execute on another.

A safer pattern is conceptually:

```ts
const client = await pool.connect();

try {
  await client.query('BEGIN');

  await client.query(
    `SELECT set_config('app.tenant_id', $1, true)`,
    [tenantId],
  );

  // all tenant SQL uses this same client

  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

The important property is not the exact API shape.

It is:

```text
tenant context + transaction + connection
must form one controlled execution boundary
```

---

# 22. Tenant Context Must Be Authorization-Derived

Never trust:

```http
X-Tenant-Id: attacker-chosen-value
```

by itself.

Tenant resolution should be derived from trusted authorization state.

Conceptually:

```text
JWT / session / API credential
          |
          v
allowed tenant memberships
          |
          v
requested tenant context
          |
          v
authorization check
          |
          v
DB transaction context
```

A user being authenticated does not mean they are authorized for every tenant.

---

# 23. Tenant Membership Model

A robust SaaS model often separates:

```text
users

tenants

tenant_memberships
```

Example:

```sql
CREATE TABLE tenant_memberships (
    user_id bigint NOT NULL,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    role text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),

    PRIMARY KEY (user_id, tenant_id)
);
```

This allows one user to belong to multiple tenants.

The application then resolves:

```text
user 42
  -> tenant A: owner
  -> tenant B: viewer
```

rather than pretending a user has exactly one tenant forever.

---

# 24. Authorization Has Multiple Dimensions

A production tenant system may need:

```text
Tenant scope
+ Branch scope
+ Role
+ Resource ownership
+ Action
```

For example:

```text
User can:
  read tenant A
  read branch 3
  create invoice
  approve payment
```

RLS can enforce row-level predicates, but business authorization may still require application/domain logic.

A good division is:

```text
Database:
  tenant boundary
  relational integrity
  critical invariants

Application:
  business authorization
  workflow permissions
  UI/domain policy
```

Do not move every rule into one layer simply because the layer exists.

---

# 25. Tenant-Aware Query Design

Even with RLS, explicit tenant-aware SQL can improve:

- query planning;
- index usefulness;
- developer clarity;
- operational diagnostics;
- defense in depth.

For example:

```sql
SELECT *
FROM orders
WHERE tenant_id = $1
  AND status = 'OPEN';
```

with:

```sql
CREATE INDEX idx_orders_tenant_status
ON orders (tenant_id, status);
```

RLS should not become an excuse to ignore data-access design.

---

# 26. Tenant-First Indexing

A tenant-aware index commonly starts with:

```text
tenant_id
```

because many queries have tenant scope as their leading selectivity/access dimension.

Typical examples:

```sql
CREATE INDEX idx_orders_tenant_created_at
ON orders (tenant_id, created_at DESC);

CREATE INDEX idx_products_tenant_sku
ON products (tenant_id, sku);

CREATE INDEX idx_customers_tenant_name
ON customers (tenant_id, name);
```

But never mechanically put `tenant_id` first in every index.

Measure workload and inspect plans.

A global analytical query may need a different access path.

---

# 27. Tenant ID and Cardinality

Suppose:

```text
10,000 tenants
100 rows per tenant
```

versus:

```text
10 tenants
100 million rows per tenant
```

The same index strategy may not behave identically.

Tenant cardinality distribution matters more than just tenant count.

You should measure:

```text
rows per tenant
reads per tenant
writes per tenant
storage per tenant
connections per tenant
long-running queries per tenant
cache footprint per tenant
```

This distribution is a critical scaling input.

---

# 28. Noisy Neighbors

In shared infrastructure, one tenant can disproportionately consume:

```text
CPU
I/O
connections
locks
WAL bandwidth
cache
worker capacity
```

This is the **noisy-neighbor problem**.

A tenant-aware schema does not automatically solve it.

Mitigations may include:

- workload quotas;
- API rate limits;
- per-tenant job queues;
- concurrency limits;
- statement timeouts;
- tenant-specific connection pools for exceptional customers;
- partitioning or isolation for very large tenants;
- workload routing;
- asynchronous reporting;
- precomputed aggregates.

---

# 29. Large Tenant vs Small Tenant

A healthy multi-tenant architecture often treats tenant size as a first-class operational dimension.

Example distribution:

```text
98% tenants -> < 1 GB
1.5%         -> 1–20 GB
0.5%         -> > 100 GB
```

The top 0.5% may dominate system behavior.

This suggests an architecture such as:

```text
standard tenants -> shared database
whale tenants    -> dedicated database or partitioning tier
```

The correct threshold is workload-specific.

Do not assume a fixed number is universally right.

---

# 30. Tenant-Aware Partitioning

Partitioning can be considered for very large workloads, but:

```text
partition by tenant
```

is not automatically the best design.

If there are thousands or millions of tenants, one partition per tenant is usually operationally unattractive.

Alternatives include:

```text
PARTITION BY HASH (tenant_id)
```

with a manageable number of partitions.

This can distribute tenant data while avoiding partition explosion.

Partitioning should be introduced only after workload analysis justifies its complexity.

---

# 31. Tenant-Aware Foreign Keys

The general design pattern is:

```text
Referenced table:
UNIQUE (tenant_id, id)

Referencing table:
FOREIGN KEY (tenant_id, referenced_id)
REFERENCES referenced (tenant_id, id)
```

Example:

```sql
CREATE TABLE accounts (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    CONSTRAINT uq_accounts_tenant_id_id UNIQUE (tenant_id, id)
);

CREATE TABLE transactions (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    account_id bigint NOT NULL,

    CONSTRAINT fk_transactions_account_same_tenant
      FOREIGN KEY (tenant_id, account_id)
      REFERENCES accounts (tenant_id, id)
);
```

This makes tenant ownership part of the reference itself.

---

# 32. When Global IDs Make Cross-Tenant References Still Possible

A common argument is:

> "Our UUIDs are globally unique, so a product from another tenant cannot accidentally collide."

Correct—but collision is not the only problem.

The issue is **authorization and ownership**.

A valid UUID belonging to tenant B can be supplied to a tenant A mutation.

Global uniqueness answers:

```text
Which row is this?
```

It does not answer:

```text
May this tenant reference this row?
```

That is why tenant-aware foreign keys remain valuable even with UUIDs.

---

# 33. Tenant-Scoped Soft Delete

Suppose:

```sql
deleted_at timestamptz
```

exists.

A uniqueness rule may need:

```sql
CREATE UNIQUE INDEX uq_customer_code_active
ON customers (tenant_id, customer_code)
WHERE deleted_at IS NULL;
```

This means deleted rows do not reserve the business identifier.

But first establish the real business requirement.

For some systems, deleting a customer and immediately reusing its identifier may be unacceptable for audit or legal reasons.

Data lifecycle policy determines constraint design.

---

# 34. Cross-Tenant Data Should Be Explicit

Some entities legitimately exist outside tenants.

Examples:

```text
ISO country codes
currency definitions
system configuration
platform-wide feature definitions
```

Do not add `tenant_id` everywhere blindly.

Instead classify entities:

```text
GLOBAL
TENANT_SCOPED
TENANT+BRANCH_SCOPED
PLATFORM_ADMIN_ONLY
DERIVED/CACHE
```

This classification should appear in schema design documentation.

---

# 35. Mixed-Scope Schemas Need Care

Suppose:

```text
currencies -> global
products -> tenant
```

A product references `currency_id` globally.

That is fine.

Now suppose:

```text
brands -> tenant
products -> tenant
```

Then:

```text
product -> brand
```

should enforce tenant consistency.

The rule is:

> **Scope of the reference target determines whether tenant identity belongs in the foreign key.**

---

# 36. Global Parent, Tenant Child

A system-wide product category could be:

```text
category(id, name)
```

while tenant-specific products are:

```text
product(tenant_id, category_id, ...)
```

No composite tenant FK is required if the target is intentionally global.

This is preferable to duplicating global reference tables per tenant without a business reason.

---

# 37. Tenant Parent, Global Child Is Suspicious

A global table that points into tenant-owned data raises an important question:

```text
audit_metadata -> tenant-owned invoice
```

If the global row references a tenant row, the global object is indirectly tenant-specific.

Classify the ownership intentionally.

Do not let global tables accidentally become unbounded cross-tenant data aggregators.

---

# 38. Cross-Tenant Operations

Some features genuinely need cross-tenant access:

```text
platform admin
central analytics
fraud detection
billing
support tooling
```

Do not solve this by disabling all isolation globally.

Instead define an explicit capability:

```text
tenant-scoped principal
vs
platform-scoped principal
```

and ensure privileged access is:

- authenticated;
- authorized;
- auditable;
- narrowly scoped;
- observable.

---

# 39. Administrative Tenant Impersonation

Support teams sometimes need to act "as" a tenant.

The dangerous model is:

```text
set tenant = requested header
```

The safer model is:

```text
support identity
    |
    +-- authorized impersonation action
             |
             +-- target tenant
             |
             +-- reason / ticket
             |
             +-- audit event
             v
       tenant DB context
```

Do not make impersonation indistinguishable from ordinary tenant activity in audit trails.

---

# 40. RLS Policy Composition

PostgreSQL supports permissive and restrictive policies.

Conceptually:

```text
permissive policies -> OR
restrictive policies -> AND
```

The presence of multiple policies therefore changes security semantics. PostgreSQL 18 documents these combination rules explicitly. citeturn987305search0

A mature team should inspect the resulting policy set rather than reasoning about each policy in isolation.

Use:

```sql
SELECT *
FROM pg_policies
WHERE tablename = 'orders';
```

PostgreSQL 18 exposes RLS policy definitions through `pg_policies`. citeturn987305search2

---

# 41. Avoid Policy Complexity Without Testing

A policy such as:

```sql
USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND deleted_at IS NULL
    AND EXISTS (...)
)
```

may encode useful business semantics.

But it also introduces:

- more planner work;
- dependency on helper functions/tables;
- possible permission issues;
- more difficult debugging;
- policy-composition complexity.

Keep tenant isolation itself simple wherever possible.

Complex authorization can be layered on top.

---

# 42. Security of Helper Functions

RLS policies often call helper functions.

For example:

```sql
current_tenant_id()
```

This can improve readability, but function security matters.

PostgreSQL's security documentation warns that functions, triggers, and RLS policies execute inside the backend and that untrusted object resolution through `search_path` can create security hazards. Carefully controlling object ownership and `search_path` is especially important for privileged functions. citeturn987305search3

A security-sensitive helper should be designed as security-critical database code, not convenience code.

---

# 43. The `current_setting` Trap

This is convenient:

```sql
current_setting('app.tenant_id')::uuid
```

But consider what happens if the setting is absent.

For systems that require fail-closed behavior, deliberately make absence produce an error rather than silently turning into an unexpected policy result.

You can use:

```sql
current_setting('app.tenant_id', true)
```

when you explicitly need NULL on absence, but then policy semantics must handle that state safely.

The tenant context contract should be documented and tested.

---

# 44. Transaction Pooling and Tenant Context

Connection pooling creates a subtle distinction:

```text
application request
!=
physical PostgreSQL connection
```

If connection state is session-scoped, a pool can accidentally reuse it.

Transaction-scoped settings are safer for per-request tenant context because they can be reset automatically when the transaction ends when set locally.

Your data-access layer should make it difficult to execute tenant-sensitive SQL outside the intended transaction context.

---

# 45. Background Jobs

HTTP requests are not the only execution path.

You also have:

```text
cron
BullMQ
Kafka consumers
RabbitMQ consumers
outbox processors
email workers
report workers
migration jobs
```

Every tenant-aware job should carry sufficient context.

Example event:

```json
{
  "eventType": "invoice.created",
  "tenantId": "...",
  "invoiceId": "...",
  "eventId": "..."
}
```

Do not reconstruct tenant identity from an arbitrary identifier if the event can carry the ownership context explicitly.

---

# 46. Caches Must Include Tenant Scope

A classic multi-tenant leak is:

```ts
cache.get(`customer:${customerId}`)
```

when IDs are not guaranteed to be globally inaccessible.

Safer:

```ts
cache.get(`tenant:${tenantId}:customer:${customerId}`)
```

Even with global IDs, tenant-scoped cache keys can act as defense in depth and make ownership explicit.

The same applies to:

- Redis;
- DataLoader caches;
- in-memory LRU caches;
- search indexes;
- object storage paths;
- CDN keys.

---

# 47. Search Indexes

If a tenant-scoped search system indexes database rows, the tenant boundary must survive the data pipeline:

```text
PostgreSQL
  -> CDC/outbox
  -> indexer
  -> search index
```

Every document should contain a tenant dimension such as:

```json
{
  "tenantId": "...",
  "entityId": "...",
  "name": "..."
}
```

And queries should constrain by it.

Database isolation does not protect a separately stored search copy.

---

# 48. Object Storage

A tenant-aware database row may reference:

```text
s3://bucket/invoices/abc.pdf
```

If object keys are globally addressable and authorization is not tenant-aware, the database can be perfectly isolated while documents leak.

Prefer ownership-aware paths such as:

```text
/{tenant_id}/invoices/{invoice_id}/{document_id}
```

combined with proper object-store authorization.

Multi-tenancy is an end-to-end system property, not merely a relational one.

---

# 49. Query Builder / ORM Risks

An ORM can make tenant filters look automatic:

```ts
repository.find({
  where: { tenantId },
});
```

But every escape hatch matters:

```text
raw SQL
query runners
admin repositories
report queries
migrations
relations
custom repositories
views
stored procedures
```

A mature architecture documents which access paths are tenant-safe by construction.

---

# 50. The "Forgot tenant_id" Bug

Naive query:

```sql
SELECT *
FROM invoices
WHERE status = 'OPEN';
```

Potential result:

```text
Tenant A invoices
Tenant B invoices
Tenant C invoices
```

Better:

```sql
SELECT *
FROM invoices
WHERE tenant_id = $1
  AND status = 'OPEN';
```

Best defense in a shared-schema system:

```text
explicit tenant-aware query
+
RLS defense in depth
+
correct authorization
+
tenant-aware tests
```

---

# 51. The "Wrong Join" Bug

Consider:

```sql
SELECT o.id, p.name
FROM orders o
JOIN products p
  ON p.id = o.product_id
WHERE o.tenant_id = $1;
```

This can join an order in tenant A with a product in tenant B if `product_id` is globally valid and the relationship is modeled incorrectly.

A tenant-aware relationship can be queried as:

```sql
SELECT o.id, p.name
FROM orders o
JOIN products p
  ON p.id = o.product_id
 AND p.tenant_id = o.tenant_id
WHERE o.tenant_id = $1;
```

And the stronger solution is to encode that relationship in a composite FK so the invalid state cannot be stored.

---

# 52. Tenant ID in Every Join Is Not Necessarily the Goal

Do not cargo-cult:

```sql
AND child.tenant_id = parent.tenant_id
```

into every query simply because it is a multi-tenant database.

The question is:

```text
Does this relationship cross a tenant ownership boundary?
```

If both tables are global, there is no tenant comparison.

If both are tenant-scoped and related, the relationship should normally make tenant equivalence explicit.

---

# 53. Application-Only Tenant Enforcement

## Naive approach

```ts
const tenantId = req.user.tenantId;
const orders = await db.query(
  'SELECT * FROM orders WHERE tenant_id = $1',
  [tenantId],
);
```

### Why it fails

One missed predicate can leak everything.

The danger grows as code paths increase:

```text
100 controllers
40 background jobs
25 reports
15 admin queries
```

The system's safety depends on humans remembering one rule everywhere.

---

# 54. Application Filter + Database RLS

### Improved approach

Use application tenant resolution:

```text
principal -> allowed tenant
```

then set transaction-local DB context:

```sql
SET LOCAL app.tenant_id = '...';
```

then RLS enforces the row boundary:

```sql
USING (...)
WITH CHECK (...)
```

### Why it works

The application expresses intent.
The database enforces the boundary.

This creates defense in depth.

---

# 55. RLS Does Not Replace Authorization

Suppose a user legitimately belongs to tenant A.

RLS prevents tenant B access.

But RLS alone may not determine:

```text
Can this user approve refunds?
Can this user modify accounting entries?
Can this user delete customers?
```

The architecture should separate:

```text
tenant isolation
from
business authorization
```

---

# 56. Tenant-Aware Transactions

Every transaction involving tenant-owned data should have a known tenant context.

A useful execution model is:

```text
BEGIN
  resolve authorization
  set tenant context
  validate command
  execute mutations
  emit audit/outbox rows
COMMIT
```

The critical invariant is:

```text
No tenant-sensitive mutation executes after tenant context is lost.
```

---

# 57. Cross-Tenant Transactions

Platform workflows may intentionally touch multiple tenants:

```text
central billing
```

A single tenant-context model may be inappropriate for these workflows.

Instead classify transactions:

```text
TENANT_SCOPED
PLATFORM_SCOPED
CROSS_TENANT_ADMIN
```

A cross-tenant operation should not accidentally masquerade as an ordinary tenant operation.

Audit it differently.

---

# 58. Tenant Deletion

Deleting a tenant may involve:

```text
tenant
 -> branches
 -> users/memberships
 -> products
 -> customers
 -> orders
 -> payments
 -> documents
 -> audit records
 -> search indexes
 -> object storage
 -> caches
```

Do not perform an enormous all-at-once cascade without considering:

- lock duration;
- transaction size;
- WAL growth;
- replication lag;
- worker capacity;
- retention obligations;
- legal holds;
- asynchronous systems.

Tenant deletion is often a **workflow**, not a single SQL statement.

---

# 59. Soft Delete vs Tenant Offboarding

These are different concepts.

```text
row soft delete
!=
tenant account disabled
!=
tenant retention hold
!=
tenant data destruction
```

Use explicit lifecycle states such as:

```text
ACTIVE
SUSPENDED
OFFBOARDING
RETAINED
DELETING
DELETED
```

The lifecycle model should be consistent with legal, business, and operational requirements.

---

# 60. Tenant Archival

For large tenants, archive strategies may include:

```text
hot tables
   -> historical tables
   -> object storage / warehouse
   -> purge
```

Tenant identity must remain part of the archival contract.

A historical record without tenant context can become operationally ambiguous and analytically dangerous.

---

# 61. Tenant Export

A customer may request:

> Export all of our data.

The export query must be designed around ownership, not around tables guessed manually.

A data inventory can classify:

```text
Tenant-owned
Tenant-derived
Global reference
Platform-generated
```

Then the export workflow follows the ownership graph.

---

# 62. Tenant Restore

Shared-schema databases make tenant-only point-in-time restore harder.

Common strategies include:

- restore whole database to a temporary environment;
- extract rows for the tenant;
- transform/reconcile IDs;
- re-import under controlled constraints;
- verify row counts and relationships.

This should be designed before the business needs it.

---

# 63. IDs and Tenant Data Export

Global surrogate IDs make references easier to preserve across the full system.

Tenant-local business IDs may make customer-facing exports easier to interpret.

A mature system can expose:

```text
internal immutable ID
business reference number
```

instead of forcing one identifier to serve every purpose.

---

# 64. Tenant-Level Audit

Tenant isolation must also apply to audit data.

Example:

```sql
CREATE TABLE audit_events (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid,
    actor_user_id bigint,
    action text NOT NULL,
    entity_type text NOT NULL,
    entity_id text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    metadata jsonb NOT NULL DEFAULT '{}'::jsonb
);
```

But platform-level events may legitimately have:

```text
tenant_id = NULL
```

So the schema should explicitly distinguish:

```text
TENANT event
PLATFORM event
CROSS_TENANT event
```

rather than allowing ambiguous NULL semantics everywhere.

---

# 65. Tenant-Aware Audit Security

An audit table can itself become a data leak.

For example:

```sql
SELECT * FROM audit_events;
```

must not expose all tenants to an ordinary tenant user.

Apply RLS or another explicit authorization boundary to audit storage when tenant users can query it.

Platform support queries should use a distinct privileged path.

---

# 66. Tenant-Aware Metrics

Observability needs tenant dimensions, but not every metric should include raw tenant IDs.

High-cardinality labels can damage metrics systems.

Prefer:

```text
aggregate tenant classes
largest tenants
sampled tenant diagnostics
```

when exact per-tenant labels would create unbounded cardinality.

Operational dashboards can separately support controlled tenant drill-down.

---

# 67. Detecting Tenant Leaks

Evidence-driven diagnostics should include:

```sql
SELECT tenant_id, count(*)
FROM orders
GROUP BY tenant_id
ORDER BY count(*) DESC;
```

and ownership validation queries such as:

```sql
SELECT COUNT(*)
FROM order_items oi
JOIN products p
  ON p.id = oi.product_id
WHERE oi.tenant_id <> p.tenant_id;
```

In a correctly constrained system, the second query should return zero.

If it returns rows, the database model itself may permit cross-tenant relationships.

---

# 68. Detecting Missing Tenant Foreign Keys

For each tenant-owned relationship, ask:

```text
Can the child point to a parent from another tenant?
```

A schema review should generate a relationship matrix:

| Child | Parent | Tenant-owned? | Same-tenant invariant? | Enforced by FK? |
|---|---|---:|---:|---:|
| order_item | product | yes | yes | yes |
| order_item | order | yes | yes | yes |
| product | currency | no | no | global FK |
| branch | tenant | yes | yes | yes |

This is substantially stronger than reviewing only table definitions one by one.

---

# 69. Testing Strategy

Tenant isolation requires adversarial tests.

## L1 — Basic

Test:

```text
tenant A -> tenant A row = visible
tenant A -> tenant B row = not visible
```

## L2 — Writes

Try:

```text
INSERT tenant B row while context = A
UPDATE row from A to B
DELETE row from B while context = A
```

## L3 — Relationships

Try:

```text
create tenant A order
reference tenant B product
```

Expected:

```text
rejected
```

## L4 — Concurrency

Run parallel transactions with different tenant contexts on pooled connections.

Verify context does not bleed across requests.

## L5 — Escape hatches

Test:

```text
raw SQL
admin repository
background worker
reporting query
cache
search index
object storage
```

## L6 — Security regression

Verify every deploy preserves:

```text
RLS enabled
correct policies
correct DB roles
no accidental BYPASSRLS usage
```

# 70. Property-Style Tenant Invariants

Useful invariants include:

```text
For every tenant-owned row r:
    r.tenant_id is valid
```

For every tenant-owned relationship:

```text
child.tenant_id = parent.tenant_id
```

For every tenant-sensitive request:

```text
effective_db_tenant = authorized_request_tenant
```

For every cache entry:

```text
cache_scope includes tenant identity
```

For every event:

```text
tenant-owned event contains tenant identity
```

These can become automated test properties.

---

# 71. Migration Strategy

Adding tenant isolation to an existing single-tenant system is not a simple column addition.

A common migration sequence is:

```text
1. Create tenants table
2. Create initial/default tenant
3. Add nullable tenant_id
4. Backfill existing rows
5. Validate ownership relationships
6. Add tenant-aware unique constraints/indexes
7. Add composite FK targets
8. Validate composite FKs
9. Set tenant_id NOT NULL where required
10. Enable RLS
11. Add policies
12. Change application tenant context
13. Remove legacy global assumptions
14. Add isolation regression tests
```

Large tables require careful lock and batch planning.

Do not combine every step into one risky deployment.

---

# 72. Backfill Validation

Before enforcing:

```sql
ALTER TABLE orders
ALTER COLUMN tenant_id SET NOT NULL;
```

verify:

```sql
SELECT count(*)
FROM orders
WHERE tenant_id IS NULL;
```

For ownership relationships:

```sql
SELECT count(*)
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
WHERE oi.tenant_id <> o.tenant_id;
```

Do not discover violations after adding a blocking constraint.

---

# 73. Constraint Rollout

For large systems, staged validation can reduce migration risk.

The general pattern is:

```text
add constraint/check in a staged mode where appropriate
        |
        v
clean existing violations
        |
        v
validate
        |
        v
switch application assumptions
```

The exact PostgreSQL feature should be selected based on the constraint type and operational requirements.

Never assume every constraint supports identical online-validation semantics.

---

# 74. Tenant Migration Between Databases

A hybrid system may eventually move a tenant:

```text
shared database
     |
     v
extract tenant
     |
     v
restore to dedicated DB
     |
     v
route tenant traffic
```

This creates a distributed consistency problem.

You need a migration state such as:

```text
SHARED
MOVING
DEDICATED
FAILED
```

and a routing source of truth.

The database move should be treated as an operational state machine.

---

# 75. Tenant Routing Metadata

A platform control plane may maintain:

```text
tenant_id
storage_tier
cluster
region
database_identifier
status
version
```

The application uses this to resolve where the tenant lives.

This allows:

```text
small tenant -> shared cluster A
enterprise tenant -> dedicated cluster B
```

without changing business identifiers.

---

# 76. Multi-Region Considerations

Multi-region systems introduce questions such as:

```text
tenant home region
read region
write region
failover region
```

Tenant identity should not be inferred from physical location alone.

A tenant can be moved between regions; tenant identity is business ownership, not infrastructure placement.

Store routing as explicit infrastructure metadata.

---

# 77. Security Principle: Fail Closed

A multi-tenant system should prefer:

```text
missing tenant context -> error
invalid tenant context -> error
unauthorized tenant -> error
missing policy -> deny
cross-tenant FK -> error
```

over:

```text
missing context -> show everything
```

This is a foundational security property.

---

# 78. Security Principle: Defense in Depth

A production architecture can use:

```text
Identity
  ↓
Authorization
  ↓
Application tenant context
  ↓
DB transaction context
  ↓
RLS
  ↓
Foreign keys
  ↓
Unique/check constraints
  ↓
Audit
```

Each layer solves a different failure mode.

No single layer should be the only thing preventing catastrophic tenant leakage.

---

# 79. Security Principle: Least Privilege

A useful role model may include:

```text
app_tenant_role
reporting_role
migration_role
platform_admin_role
backup_role
```

Do not run the API as a role with unnecessary powerful attributes.

In particular, understand which roles bypass RLS. PostgreSQL documents the `BYPASSRLS` role attribute explicitly. citeturn987305search8

---

# 80. Performance of RLS

RLS can affect query plans because policy expressions become part of query security semantics.

Do not benchmark:

```text
query without RLS
```

and conclude:

```text
query with RLS will be the same
```

Measure the actual workload.

Useful tools include:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

and workload monitoring.

Policy expressions should be simple, index-friendly, and stable where practical.

---

# 81. Tenant Predicate Selectivity

Suppose:

```text
tenant_id = 90% of table rows
```

for a dominant tenant.

An index only on:

```text
tenant_id
```

may provide limited benefit for queries against that tenant.

A composite index such as:

```sql
(tenant_id, status, created_at DESC)
```

may be more useful for real access patterns.

Again:

> Measure the workload, then design indexes.

---

# 82. Hot Tenant Concurrency

One tenant may have hundreds of simultaneous users.

This can create:

```text
hot rows
hot indexes
lock contention
sequence pressure
cache churn
```

Tenant modeling cannot eliminate all contention.

But tenant-aware architecture makes it easier to identify and isolate the responsible workload.

---

# 83. Tenant ID in Primary Keys

A design such as:

```sql
PRIMARY KEY (tenant_id, id)
```

can be useful when IDs are tenant-local.

A design such as:

```sql
PRIMARY KEY (id)
UNIQUE (tenant_id, id)
```

supports globally unique identity while also enabling tenant-scoped references.

Which is better depends on:

```text
external identity
join patterns
ORM assumptions
partitioning
index width
migration strategy
```

Do not assume one shape is universally superior.

---

# 84. UUID Keys and Multi-Tenancy

UUIDs simplify distributed uniqueness, but they do not solve tenant isolation.

This remains unsafe:

```text
tenant A
  -> knows tenant B UUID
  -> sends it to endpoint
```

because the identifier can still resolve to a real object.

Tenant security is about **authorized ownership**, not identifier collision.

---

# 85. Composite Foreign Key Cost

Composite foreign keys make tenant integrity stronger but may increase:

- index width;
- join complexity;
- migration complexity;
- ORM mapping complexity.

That is a real trade-off.

The correct question is:

> Is the cross-tenant relationship invariant important enough to encode as a database guarantee?

For core business entities, the answer is often yes.

---

# 86. Tenant Context and SQL Functions

A helper function such as:

```sql
CREATE FUNCTION current_tenant_id()
RETURNS uuid
LANGUAGE sql
STABLE
AS $$
  SELECT current_setting('app.tenant_id')::uuid
$$;
```

can simplify policies.

But before using helper functions in security policies, review:

- execution privileges;
- function volatility;
- search path;
- object qualification;
- ownership;
- role assumptions.

Security-sensitive SQL should be explicit and tested.

# 87. Common AI/Vibe-Coding Mistakes

### Mistake 1 — "Just add tenant_id everywhere"

Why it fails:

- foreign keys may still cross tenants;
- unique constraints may have wrong scope;
- caches/events/search may leak;
- RLS may be absent;
- global entities may be incorrectly scoped.

### Mistake 2 — "UUID means isolated"

Wrong. UUID uniqueness does not imply authorization.

### Mistake 3 — "RLS is enough"

RLS does not define every relational invariant or business permission.

### Mistake 4 — `USING` without `WITH CHECK`

This can create incomplete write protection.

### Mistake 5 — session-wide tenant state in a connection pool

This can create cross-request context bleed.

### Mistake 6 — tenant filter only in controllers

Background jobs, raw SQL, exports, and reports can bypass it.

### Mistake 7 — global unique constraint for tenant-local business data

This incorrectly rejects valid data across tenants.

### Mistake 8 — no tenant dimension in cache/search/event systems

Isolation in PostgreSQL does not protect external copies.

### Mistake 9 — one database role with excessive privileges

Security boundaries become difficult to reason about, especially around RLS bypass.

### Mistake 10 — assuming schema-per-tenant is always safer

It may improve namespace isolation but creates its own operational complexity and failure modes.

# 88. Production Jewellery ERP Model

Consider a multi-tenant jewellery ERP:

```text
Tenant
 |
 +-- Branch
 |    |
 |    +-- StockLocation
 |
 +-- Customer
 |
 +-- Product
 |
 +-- Purchase
 |    |
 |    +-- PurchaseItem -> Product
 |
 +-- Sale
 |    |
 |    +-- SaleItem -> Product
 |
 +-- Payment
 |
 +-- InventoryTransaction
 |
 +-- AuditEvent
```

Important invariants:

```text
branch.tenant_id = tenant.id
product.tenant_id = tenant.id
sale.tenant_id = tenant.id
sale_item.tenant_id = sale.tenant_id
sale_item.product_id belongs to same tenant
payment.tenant_id = sale.tenant_id
inventory_transaction.tenant_id = product.tenant_id
```

Then tenant isolation exists at several levels:

```text
Authorization
RLS
Composite FKs
Unique constraints
Indexes
Audit
Event propagation
Cache keys
```

This is substantially stronger than simply adding one column to each table.

# 89. Production Design Example

```sql
CREATE TABLE tenants (
    id uuid PRIMARY KEY,
    name text NOT NULL,
    status text NOT NULL
);

CREATE TABLE branches (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    name text NOT NULL,

    CONSTRAINT uq_branches_tenant_id_id
      UNIQUE (tenant_id, id),

    CONSTRAINT uq_branches_tenant_name
      UNIQUE (tenant_id, name)
);

CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    sku text NOT NULL,
    name text NOT NULL,

    CONSTRAINT uq_products_tenant_id_id
      UNIQUE (tenant_id, id),

    CONSTRAINT uq_products_tenant_sku
      UNIQUE (tenant_id, sku)
);

CREATE TABLE sales (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    branch_id bigint NOT NULL,
    invoice_number text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT uq_sales_tenant_id_id
      UNIQUE (tenant_id, id),

    CONSTRAINT fk_sales_branch_same_tenant
      FOREIGN KEY (tenant_id, branch_id)
      REFERENCES branches (tenant_id, id),

    CONSTRAINT uq_sales_invoice
      UNIQUE (tenant_id, branch_id, invoice_number)
);

CREATE TABLE sale_items (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id uuid NOT NULL REFERENCES tenants(id),
    sale_id bigint NOT NULL,
    product_id bigint NOT NULL,
    quantity numeric(18, 3) NOT NULL,

    CONSTRAINT fk_sale_items_sale_same_tenant
      FOREIGN KEY (tenant_id, sale_id)
      REFERENCES sales (tenant_id, id),

    CONSTRAINT fk_sale_items_product_same_tenant
      FOREIGN KEY (tenant_id, product_id)
      REFERENCES products (tenant_id, id),

    CONSTRAINT ck_sale_items_quantity_positive
      CHECK (quantity > 0)
);
```

The schema expresses a large part of the tenant integrity graph directly.

# 90. Production RLS Example

```sql
ALTER TABLE products ENABLE ROW LEVEL SECURITY;
ALTER TABLE sales ENABLE ROW LEVEL SECURITY;
ALTER TABLE sale_items ENABLE ROW LEVEL SECURITY;

CREATE POLICY products_tenant_isolation
ON products
USING (tenant_id = current_setting('app.tenant_id')::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

CREATE POLICY sales_tenant_isolation
ON sales
USING (tenant_id = current_setting('app.tenant_id')::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

CREATE POLICY sale_items_tenant_isolation
ON sale_items
USING (tenant_id = current_setting('app.tenant_id')::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

This gives the database a consistent row boundary.

Always verify the effective role and policy composition in the actual deployment.

# 95. Expert Interview Questions

### Q1. Why is `tenant_id` in a foreign key sometimes necessary even when IDs are globally unique?

Because uniqueness answers identity, not ownership authorization. A globally unique identifier from another tenant can still be referenced unless the relationship enforces same-tenant ownership.

### Q2. Why can `USING` and `WITH CHECK` not be treated as interchangeable?

They protect different states: `USING` governs which existing rows are accessible for relevant commands, while `WITH CHECK` validates proposed new row versions for writes. PostgreSQL documents this distinction explicitly. citeturn987305search0

### Q3. Why is application-only tenant filtering fragile?

Because tenant filtering must be implemented consistently across every query path, including raw SQL, background jobs, reports, exports, and operational scripts. One omitted predicate can expose unrelated rows.

### Q4. Why is transaction-local context preferable with pooling?

Because a session is attached to a physical connection that may be reused. Transaction-local state scopes tenant context to the controlled transaction rather than relying on persistent connection state.

### Q5. When is database-per-tenant justified?

When isolation, compliance, tenant-specific backup/restore, scaling, placement, or contractual requirements outweigh the additional operational complexity.

### Q6. What is the most dangerous misconception about multi-tenancy?

That a tenant column alone creates isolation.

# 100. Final Principle

> **Multi-tenancy is an isolation architecture, not a column.**
>
> Choose the physical isolation boundary deliberately. Make tenant ownership explicit in the relational model. Encode same-tenant relationships with database constraints where the invariant matters. Use RLS as a database-enforced access boundary. Bind tenant context to the transaction, not a reusable pooled connection. Carry tenant identity through background jobs, caches, events, search, and object storage. Measure tenant distribution and noisy-neighbor behavior. Design export, deletion, restore, and migration before they become emergencies. And treat every cross-tenant path as an explicit capability rather than an accidental side effect.

The strongest multi-tenant systems are not the ones with the most `tenant_id` columns. They are the ones where **tenant ownership is an explicit, testable, database-enforced, observable invariant across the entire architecture**.
