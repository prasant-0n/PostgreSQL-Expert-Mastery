# 02.7 — Multi-Tenant Data Modeling

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to designing PostgreSQL schemas where multiple customers, organizations, branches, or tenants share infrastructure without sacrificing correctness, isolation, performance, operability, or future migration options.

---

## 1. Chapter Objective

Multi-tenancy is not simply adding a `tenant_id` column to every table.

A production multi-tenant design must answer:

- What exactly is a tenant?
- Which records belong to which tenant?
- Which records are globally shared?
- Which relationships are tenant-scoped?
- How is cross-tenant access prevented?
- How is accidental tenant omission prevented in application queries?
- Which constraints must include tenant identity?
- How does Row-Level Security interact with the application's authorization model?
- How are indexes shaped for tenant-local access patterns?
- How do very large and very small tenants coexist?
- How are migrations, backups, exports, deletion, and tenant moves performed?
- At what scale should tenants be isolated physically rather than logically?

The central design question is:

> **What is the isolation boundary, and where is that boundary enforced?**

A useful model is:

```text
Business Tenancy Model
        ↓
Tenant Identity
        ↓
Data Ownership / Scope
        ↓
Keys + Foreign Keys + Constraints
        ↓
Authorization / RLS
        ↓
Indexes + Query Shape
        ↓
Operations + Backups + Migrations
        ↓
Measured Isolation Guarantees
```

---

# 2. Three Levels of Definition

## 2.1 Simple definition

Multi-tenancy means one application serves multiple independent customers or organizations while keeping their data appropriately separated.

## 2.2 Engineering definition

Multi-tenant data modeling introduces a tenant identity into the relational model so rows, relationships, constraints, indexes, authorization checks, and operational procedures can distinguish one tenant's state from another.

## 2.3 Expert definition

A multi-tenant schema is a constrained state machine whose legal data states preserve tenant boundaries across every path by which data can be inserted, read, updated, deleted, joined, aggregated, replicated, exported, restored, or administratively inspected.

That definition is deliberately stronger than:

```sql
WHERE tenant_id = $1
```

because tenant isolation can fail outside ordinary application `SELECT` queries.

---

# 3. Why Multi-Tenancy Is a Modeling Problem

Suppose an application has:

```text
organizations
users
customers
orders
products
payments
```

A weak design might be:

```sql
orders (
    id,
    customer_id,
    total
)
```

and rely on application code to remember:

```sql
WHERE tenant_id = $1
```

But application code is not the entire system.

Other write/read paths include:

- background workers
- reporting queries
- admin tools
- support scripts
- exports
- imports
- ETL
- scheduled jobs
- database functions
- triggers
- ad-hoc debugging
- future services
- migrations
- analytics pipelines

Tenant isolation therefore needs explicit representation in the data model.

---

# 4. First Principle: Tenant Scope Is Part of Row Meaning

Consider:

```text
product_id = 42
```

In a single-tenant database, that may be enough to identify the product.

In a shared multi-tenant database, it may not be enough.

A better conceptual identity can be:

```text
(tenant_id, product_id)
```

This distinction becomes critical when identifiers are generated independently or when business uniqueness is tenant-local.

For example:

```text
Tenant A: SKU = ABC-100
Tenant B: SKU = ABC-100
```

That may be perfectly valid.

Therefore:

```sql
UNIQUE (tenant_id, sku)
```

is different from:

```sql
UNIQUE (sku)
```

The latter silently creates a global business rule.

---

# 5. The Three Main Isolation Architectures

A multi-tenant system commonly uses one of three broad physical models.

## 5.1 Database-per-tenant

```text
Tenant A → Database A
Tenant B → Database B
Tenant C → Database C
```

### Strengths

- strong physical isolation
- easier per-tenant backup/restore concepts
- independent operational boundaries
- easy tenant export at database level

### Costs

- connection management grows
- schema migrations multiply
- monitoring becomes more complex
- many small databases can create operational overhead
- cross-tenant reporting is harder

Suitable when tenants require strong isolation or individual operational control.

---

# 6. Schema-per-Tenant

```text
Database
├── tenant_a.*
├── tenant_b.*
└── tenant_c.*
```

This provides more logical separation than a shared table, but less physical separation than separate databases.

Costs can become substantial when the tenant count is high because every schema requires duplicated database objects and migration work.

A schema-per-tenant design should therefore be chosen from operational requirements rather than aesthetic preference.

---

# 7. Shared Schema / Shared Tables

The common SaaS model is:

```text
organizations

orders
------
tenant_id
id
...
```

All tenants share physical tables.

Advantages:

- simple deployment
- one schema migration
- efficient resource sharing
- straightforward cross-tenant operational tooling
- good fit for many tenants

Risks:

- tenant leakage becomes a critical security threat
- indexes must be tenant-aware
- noisy neighbors are possible
- tenant-specific migrations are harder

This model requires the strongest discipline around scope enforcement.

---

# 8. Hybrid Tenancy

Large systems often evolve into:

```text
Small tenants
    ↓
Shared database / shared tables

Large or regulated tenants
    ↓
Dedicated database / cluster
```

This is not architectural inconsistency.

It can be a deliberate capacity and isolation strategy.

The application should represent tenancy independently from physical placement:

```text
Tenant Identity
      ↓
Placement Metadata
      ↓
Shared or Dedicated Storage
```

That abstraction allows a tenant to migrate without redesigning the business domain.

---

# 9. Choosing a Tenant Identifier

Common choices include:

```text
UUID
bigint
ULID-like application identifiers
composite organizational identifiers
```

The important question is not merely UUID vs integer.

Ask:

- Is the identifier globally unique?
- Is it externally exposed?
- Is it immutable?
- Is it generated centrally or locally?
- Does its width affect indexes materially at your scale?
- Is tenant identity part of external authorization claims?

A tenant ID should normally be immutable.

Changing tenant identity after data has spread through foreign keys, policies, indexes, logs, caches, and external systems is disproportionately expensive.

---

# 10. The Tenant Table

A basic model:

```sql
CREATE TABLE tenants (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Then:

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL REFERENCES tenants(id),
    name text NOT NULL
);
```

At first glance this is sufficient.

But it leaves an important modeling question unresolved:

> **How do we ensure that relationships cannot accidentally connect rows belonging to different tenants?**

---

# 11. The Cross-Tenant Foreign-Key Problem

Consider:

```text
customers
---------
id | tenant_id
1  | 10
2  | 20

orders
------
id | tenant_id | customer_id
100 | 20        | 1
```

A normal foreign key:

```sql
FOREIGN KEY (customer_id)
REFERENCES customers(id)
```

accepts the relationship because customer `1` exists.

But the business relationship is illegal because:

```text
order.tenant_id = 20
customer.tenant_id = 10
```

This is one of the most important multi-tenant integrity problems.

---

# 12. Tenant-Scoped Composite Foreign Keys

One strong solution is to encode tenant identity into the relationship key.

```sql
CREATE TABLE customers (
    tenant_id bigint NOT NULL REFERENCES tenants(id),
    id bigint GENERATED ALWAYS AS IDENTITY,
    name text NOT NULL,
    PRIMARY KEY (tenant_id, id),
    UNIQUE (tenant_id, id)
);
```

Then:

```sql
CREATE TABLE orders (
    tenant_id bigint NOT NULL REFERENCES tenants(id),
    id bigint GENERATED ALWAYS AS IDENTITY,
    customer_id bigint NOT NULL,
    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customers(tenant_id, id)
);
```

Now the relationship itself includes the tenant boundary.

Conceptually:

```text
Order
(tenant 20, customer 1)
        ↓
Customer
(tenant 20, customer 1)
```

Cross-tenant relationships become structurally invalid.

This is much stronger than trusting application code to compare tenant IDs.

---

# 13. Alternative: Global Entity IDs + Tenant Checks

Another design is:

```text
customers.id globally unique
customers.tenant_id
orders.id globally unique
orders.tenant_id
```

and enforce tenant consistency through:

- application logic
- triggers
- composite references where appropriate
- carefully designed data-access abstractions
- RLS

This can be easier when IDs are globally referenced across many systems.

However:

> A globally unique identifier does not prove tenant ownership.

Identity and scope remain different concepts.

---

# 14. Which Tables Need Tenant IDs?

Do not blindly add `tenant_id` to everything.

Classify tables.

## Tenant-owned

```text
orders
customers
invoices
employees
branches
```

These usually need tenant scope.

## Global reference data

```text
countries
currencies
ISO codes
standard tax classifications
```

These may legitimately be global.

## Mixed/global catalog data

A product catalog might be:

```text
global product definition
        +
tenant-specific price / inventory / settings
```

Forcing all data into one scope can create unnecessary duplication.

The correct question is:

> **Who owns this fact?**

---

# 15. Do Not Confuse Branch With Tenant

In an ERP system:

```text
Tenant
└── Branch A
└── Branch B
└── Branch C
```

A branch is often an organizational subdivision inside a tenant.

Therefore:

```text
tenant_id
branch_id
```

can represent different levels of scope.

An invoice might be:

```text
tenant = 10
branch = 3
```

But some tenant-level records may have no branch at all.

Do not use `branch_id` as a substitute for tenant identity unless branch is truly the security boundary.

---

# 16. Scope Hierarchies

A useful conceptual hierarchy is:

```text
Platform
   ↓
Tenant
   ↓
Division / Branch
   ↓
Location
   ↓
User / Team
```

A record may be visible based on several scopes.

For example:

```text
tenant_id = 10
branch_id = 3
```

might mean:

```text
Tenant 10 can access it.
Branch 3 has narrower operational ownership.
```

This distinction should be reflected in authorization policy rather than encoded through ad-hoc application filters.

---

# 17. Tenant-Local Uniqueness

Common requirements:

```text
email unique per tenant
SKU unique per tenant
invoice number unique per tenant
customer code unique per branch
```

Use composite uniqueness:

```sql
CREATE UNIQUE INDEX customers_tenant_email_uq
ON customers (tenant_id, lower(email));
```

Or:

```sql
CREATE UNIQUE INDEX products_tenant_sku_uq
ON products (tenant_id, sku);
```

This is different from:

```sql
UNIQUE (email)
```

which introduces a global invariant.

---

# 18. Conditional Tenant Uniqueness

Suppose only active customers must have a unique code.

```sql
CREATE UNIQUE INDEX customers_active_code_uq
ON customers (tenant_id, customer_code)
WHERE deleted_at IS NULL;
```

The tenant scope and lifecycle condition are both part of the business rule.

This is a useful example of a broader principle:

> **Business uniqueness often has both a scope and a state.**

---

# 19. Tenant-Scoped Relationships in Junction Tables

Suppose:

```text
users ↔ roles
```

and roles are tenant-specific.

A weak junction table:

```text
user_roles
----------
user_id
role_id
```

can permit a role from another tenant unless relationships are independently constrained.

A safer design is:

```text
user_roles
----------
tenant_id
user_id
role_id
```

with composite foreign keys matching tenant-local identities.

The relationship should not merely contain tenant metadata; it should participate in the integrity model where tenant consistency is a business invariant.

---

# 20. Row-Level Security

PostgreSQL Row-Level Security (RLS) can enforce row visibility and modification policies at the database layer.

A simplified design:

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_orders_policy
ON orders
USING (tenant_id = current_setting('app.tenant_id')::bigint)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

The two expressions have different roles:

```text
USING
→ controls which existing rows are visible / targetable

WITH CHECK
→ controls which rows may be inserted or updated into the allowed scope
```

The exact session-context mechanism must be designed carefully for connection pooling and transaction boundaries.

PostgreSQL documents that RLS policies can restrict rows returned and rows modified, and that `WITH CHECK` applies to rows being added or changed. citeturn368039search1turn368039search21

---

# 21. RLS Is a Defense Layer, Not a Substitute for Authorization

RLS can enforce:

```text
“This database role/session may access tenant 10 rows.”
```

It does not automatically answer:

```text
“Is this user an administrator of tenant 10?”
“Can this employee view payroll?”
“Can this branch manager edit invoices?”
```

Those are authorization questions.

A strong architecture often combines:

```text
Authentication
      ↓
Application Authorization
      ↓
Transaction Tenant Context
      ↓
Database RLS
      ↓
Constraints
```

Defense in depth is particularly valuable for multi-tenant systems because an isolation failure can expose another customer's data.

---

# 22. RLS Default-Deny Behavior

When RLS is enabled and no applicable policy permits an operation, PostgreSQL uses the default-deny behavior for ordinary access. The table owner is normally not subject to RLS unless `FORCE ROW LEVEL SECURITY` is used. citeturn368039search21turn368039search5

This has operational implications.

A common mistake is:

```text
Developer tests as privileged owner
        ↓
Everything works
        ↓
Application role behaves differently
        ↓
Production failure
```

Always test with the same effective database role model used in production.

---

# 23. Session Tenant Context and Connection Pooling

A pooled application connection may serve:

```text
Request A → Tenant 10
Request B → Tenant 20
Request C → Tenant 10
```

Therefore tenant context must never leak between requests.

A dangerous pattern is setting session state and assuming it will always be reset:

```sql
SET app.tenant_id = '10';
```

without controlled lifecycle management.

Safer patterns include transaction-scoped context and explicit reset mechanisms.

The core invariant is:

> **Tenant context must have the same lifecycle as the request/transaction that is authorized to use it.**

---

# 24. Application Query Filters Are Not Enough

This code looks correct:

```ts
return repository.find({
  where: {
    tenantId,
    id,
  },
});
```

But isolation can fail when one path does:

```ts
repository.findOne({ where: { id } });
```

The omission may be buried in:

- an ORM relation
- a service helper
- an admin endpoint
- a background worker
- a raw SQL query
- a reporting query

Therefore tenant safety should be encoded at as many structural layers as practical.

---

# 25. Repository Design

A useful application-level abstraction is:

```text
Tenant-aware repository
```

instead of:

```text
Generic repository
```

For example:

```ts
class TenantOrderRepository {
  constructor(private readonly tenantId: bigint) {}

  findById(orderId: bigint) {
    // Every query is tenant-scoped by construction.
  }
}
```

This reduces accidental omission.

But abstraction is not proof.

The database should still enforce critical invariants.

---

# 26. Tenant-First Index Design

Suppose most queries are:

```sql
SELECT *
FROM orders
WHERE tenant_id = $1
  AND created_at >= $2
ORDER BY created_at DESC
LIMIT 50;
```

A natural index candidate is:

```sql
CREATE INDEX orders_tenant_created_idx
ON orders (tenant_id, created_at DESC);
```

Why does tenant identity come first?

Because the workload first narrows the dataset by tenant and then searches within that tenant's time range/order.

Index order should follow actual predicate and ordering patterns rather than a universal “tenant_id must always be first” rule.

---

# 27. Tenant Scope and Index Selectivity

Suppose:

```text
1,000 tenants
1 billion orders
```

and one query asks for:

```text
tenant = 42
last 24 hours
```

A tenant-aware index can drastically reduce the candidate set.

But if one tenant owns 70% of all rows, the workload is asymmetric.

This creates the **heavy-tenant problem**.

The same logical index may behave very differently for:

```text
small tenant → 100 rows
large tenant → 700 million rows
```

Multi-tenant performance must therefore account for tenant distribution, not merely total row count.

---

# 28. Noisy Neighbors

A tenant can consume disproportionate resources through:

- massive reports
- bulk imports
- large scans
- high write volume
- aggressive API usage
- long transactions
- lock contention

This creates a noisy-neighbor problem.

Database modeling can help through:

```text
tenant-aware indexes
partitioning where justified
work queues
rate limits
resource governance
separate workers
connection limits
read replicas
physical tenant placement
```

Not every noisy-neighbor solution belongs in the schema, but schema design must support the operational strategy.

---

# 29. Partitioning by Tenant

Partitioning is not automatically the correct answer for multi-tenancy.

A naive design such as:

```text
one partition per tenant
```

can become operationally expensive when tenant counts grow very large.

PostgreSQL's current documentation explicitly warns that excessive partition counts can increase planning time and memory usage, and suggests considering future tenant growth rather than assuming a fixed number of tenants. citeturn368039search0

Better choices may include:

```text
HASH partition by tenant_id
RANGE partition by time
SUBPARTITIONING
```

but only when measured workload characteristics justify partitioning.

---

# 30. Partitioning Is Physical Data Layout, Not Authorization

This distinction is critical.

Partitioning says:

```text
Where rows are stored.
```

RLS says:

```text
Which rows a role may access.
```

Foreign keys say:

```text
Which relationships are legal.
```

Application authorization says:

```text
Which actor is allowed to perform an operation.
```

These mechanisms solve different problems.

Do not substitute one for another.

---

# 31. Global IDs vs Tenant-Local IDs

Two valid patterns are common.

## Global identity

```text
order.id = globally unique
```

Useful when:

- events cross systems
- URLs expose IDs
- distributed services reference records
- tracing benefits from globally recognizable identifiers

## Tenant-local identity

```text
PRIMARY KEY (tenant_id, order_id)
```

Useful when:

- identifiers are naturally scoped
- tenant-local numbering matters
- relational integrity should encode scope

A hybrid can also exist:

```text
global surrogate ID
+
tenant-local business number
```

Example:

```text
id = 92f...
invoice_number = INV-2026-000123
tenant_id = 10
```

---

# 32. Tenant-Scoped Sequences and Invoice Numbers

Suppose each tenant requires:

```text
INV-000001
INV-000002
INV-000003
```

A naive implementation:

```text
MAX(invoice_number) + 1
```

is race-prone.

Concurrent requests can compute the same next value.

Better approaches include:

- dedicated counter rows
- transactional locking
- sequences where global numbering is acceptable
- carefully designed per-tenant allocation

The schema must represent the uniqueness requirement:

```sql
UNIQUE (tenant_id, invoice_number)
```

Generating a number and enforcing uniqueness are separate concerns.

---

# 33. Shared Catalogs and Tenant Overrides

Suppose every tenant uses the same product master but has custom pricing.

A clean model can separate facts:

```text
global_products
--------------
id
name

branch_or_tenant_products
-------------------------
tenant_id
product_id
active
custom_name

prices
------
tenant_id
product_id
price
validity
```

This avoids copying global data unnecessarily while still allowing tenant-specific behavior.

Do not solve every tenant customization with JSONB simply because schema duplication is inconvenient.

---

# 34. Tenant Deletion

“Delete the tenant” is an architectural operation, not a simple row deletion.

Ask which data belongs to the tenant:

```text
customers
orders
payments
files
audit records
notifications
jobs
search documents
cache entries
analytics events
```

Then classify data as:

```text
tenant-owned
shared
derived
externally owned
regulatory-retained
```

A tenant deletion workflow should explicitly define what happens to each class.

---

# 35. Cascading Tenant Deletes

Cascades can be useful:

```text
tenant
  ↓
customers
  ↓
orders
  ↓
order_items
```

But massive cascades can generate:

- huge transactions
- lock pressure
- WAL spikes
- replication lag
- long-running statements
- operational surprises

For large tenants, controlled batch deletion or partition retirement may be more appropriate.

The correct strategy depends on data volume, retention rules, and operational SLOs.

---

# 36. Tenant Export / Portability

A mature multi-tenant system should answer:

> “Can we export one tenant without exporting another tenant?”

This is both a product and architecture requirement.

The schema should make tenant boundaries queryable.

Example:

```sql
SELECT *
FROM orders
WHERE tenant_id = $1;
```

But related records must be exported consistently.

Think in terms of a **tenant data graph**:

```text
tenant
 ├── users
 ├── customers
 ├── orders
 │    └── order_items
 ├── payments
 └── settings
```

A correct export follows relationships rather than independently dumping arbitrary tables.

---

# 37. Tenant Migration Between Clusters

A tenant may outgrow shared infrastructure.

A migration can look like:

```text
Shared Cluster
     ↓
Extract tenant graph
     ↓
Load dedicated cluster
     ↓
Validate counts/checksums
     ↓
Synchronize delta
     ↓
Switch placement
     ↓
Verify application traffic
```

Therefore tenant placement should be metadata:

```text
tenants
-------
id
storage_mode
placement_id
```

The business identity should not change merely because storage moved.

---

# 38. Backup and Restore Considerations

Shared storage changes the restore problem.

A physical database restore usually restores many tenants together.

Tenant-level recovery may require:

- logical export/import
- point-in-time recovery into a temporary environment
- tenant-specific reconstruction
- logical replication strategies
- application-level snapshots

This should influence schema design from early stages.

Do not discover at incident time that “restore one customer's data” is impossible.

---

# 39. Multi-Tenant Auditing

An audit record should normally retain tenant identity even if the target row can theoretically reveal it.

Why?

Because audit systems are often queried independently:

```text
Who changed what?
Within which tenant?
When?
Under which actor?
```

A useful audit grain might be:

```text
audit_event_id
tenant_id
actor_id
entity_type
entity_id
action
timestamp
metadata
```

Tenant identity should remain explicit when it is part of the audit business meaning.

---

# 40. Multi-Tenant Security and `search_path`

Tenant isolation does not eliminate broader PostgreSQL security concerns.

Database functions, triggers, and related backend code should be written with security boundaries in mind. PostgreSQL's security guidance specifically warns about unsafe object resolution through writable schemas in `search_path` and recommends trusted schema references for privileged code. citeturn368039search2

A tenant-aware function is not safe merely because its SQL includes:

```sql
WHERE tenant_id = ...
```

Review:

```text
function ownership
execution privileges
search_path
role privileges
RLS bypass attributes
SECURITY DEFINER usage
trusted schemas
```

---

# 41. RLS and Privileged Roles

PostgreSQL roles with superuser-level capabilities or `BYPASSRLS` are outside ordinary RLS enforcement. citeturn368039search4

Therefore an architecture must distinguish:

```text
Application runtime role
Administrative role
Migration role
Support/debug role
Break-glass role
```

Do not assume:

```text
RLS enabled = nobody can cross tenants
```

The effective role and privilege model matters.

---

# 42. RLS Policy Design Mistakes

Common failures include:

### Mistake 1 — `USING` without `WITH CHECK`

Reads may be isolated while writes can introduce incorrect tenant state.

### Mistake 2 — Policy uses client-supplied tenant ID

A malicious client may attempt:

```text
tenant_id = victim_tenant
```

The database policy should derive authorization context from trusted server-side context, not an untrusted payload field.

### Mistake 3 — Testing only as table owner

The owner normally bypasses ordinary RLS unless forced.

### Mistake 4 — Ignoring indirect relations

A parent table may be protected while a related table remains exposed.

### Mistake 5 — Privileged maintenance jobs unintentionally bypass policy

Background workers need explicit security design.

---

# 43. Query Planner and Tenant Filters

A query:

```sql
SELECT *
FROM orders
WHERE tenant_id = $1
  AND status = 'OPEN';
```

may have a very different plan from:

```sql
SELECT *
FROM orders
WHERE status = 'OPEN';
```

because tenant filtering changes selectivity.

Therefore tenant-aware queries should be benchmarked using realistic tenant sizes.

Do not benchmark only:

```text
average tenant
```

Test:

```text
small tenant
median tenant
large tenant
heavy tenant
```

---

# 44. Tenant-First Indexes Are Not Universal

Suppose the dominant query is:

```sql
WHERE tenant_id = $1
  AND status = 'OPEN'
ORDER BY priority DESC;
```

Potential index:

```sql
(tenant_id, status, priority DESC)
```

But another workload may be:

```sql
WHERE status = 'OPEN'
ORDER BY created_at DESC
```

for operational global processing.

A single index may not optimize both workloads.

Index design must follow workload shape.

---

# 45. Tenant-Aware Query Observability

Logs and traces should preserve tenant context where safe and appropriate.

Useful dimensions include:

```text
tenant_id
query family
latency
rows returned
rows examined
lock wait
connection wait
error class
```

Be careful with high-cardinality metrics.

A tenant ID may be useful in structured logs and traces but unsuitable as an unbounded metric label at enormous scale.

---

# 46. Detecting Tenant Leakage

A serious production strategy includes tests that deliberately attempt illegal cross-tenant operations.

Examples:

```text
Tenant A reads Tenant B order
Tenant A updates Tenant B customer
Tenant A deletes Tenant B invoice
Tenant A links its order to Tenant B customer
Tenant A sees Tenant B in aggregate query
```

The desired result is not merely:

```text
application returns 403
```

It is that all relevant enforcement layers behave correctly.

---

# 47. Property-Based Tenant Isolation Testing

A strong invariant can be stated mathematically:

```text
For request tenant T,
all returned tenant-owned rows must have tenant_id = T.
```

Generate multiple tenants and random operations.

Then assert:

```text
No operation can produce an observable cross-tenant result.
```

This tests the property rather than a small list of hand-written examples.

---

# 48. Transaction Isolation Is Not Tenant Isolation

These concepts are different.

Transaction isolation controls concurrency visibility such as:

```text
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

Tenant isolation controls:

```text
Which business principal may access which data.
```

A perfectly serializable transaction can still expose the wrong tenant's rows if authorization is incorrect.

Never substitute concurrency control for authorization.

---

# 49. Tenant Isolation vs Encryption

Encryption can protect data at rest or in transit.

It does not automatically prevent:

```text
Tenant A application query
    ↓
Tenant B row
```

because the decrypted database still contains all logical rows.

The primary controls are:

```text
correct modeling
+ constraints
+ authorization
+ RLS where appropriate
+ operational controls
```

Encryption is complementary.

# 50. AI / Vibe-Coding Failure Patterns

AI-generated multi-tenant schemas frequently produce plausible but unsafe code.

## Failure 1 — Add `tenant_id` everywhere and stop there

Why it fails:

Relationships can still cross tenants.

## Failure 2 — Filter every query manually

Why it fails:

One missed query becomes a data leak.

## Failure 3 — Use `tenant_id` only in controllers

Why it fails:

Background jobs and internal services bypass controllers.

## Failure 4 — Global `UNIQUE(email)` when email is tenant-local

Why it fails:

Different tenants cannot independently use the same address.

## Failure 5 — Trust request-body tenant IDs

Why it fails:

Clients can submit another tenant's identifier.

## Failure 6 — One partition per tenant

Why it fails:

Partition count can become operationally excessive.

## Failure 7 — RLS enabled but application role bypasses it

Why it fails:

Privilege configuration defeats the intended policy boundary.

## Failure 8 — Ignore large-tenant skew

Why it fails:

Average benchmarks hide pathological tenants.

# 51. Production Scenario — Multi-Branch Jewellery ERP

Consider:

```text
Tenant = Jewellery Company

Tenant 10
├── Branch Mumbai
├── Branch Hyderabad
└── Branch Delhi
```

Data:

```text
customers
orders
sales
purchase_orders
inventory
payments
employees
```

A robust model may use:

```text
tenant_id
branch_id
```

with rules such as:

```text
customer belongs to tenant
branch belongs to tenant
order belongs to tenant + branch
order.customer belongs to same tenant
inventory belongs to tenant + branch
```

This allows a database constraint to prevent:

```text
Tenant 10 Order
      ↓
Tenant 20 Customer
```

regardless of whether an application developer accidentally omits a comparison in one code path.

# 52. Production Scenario — SaaS With Large Tenants

Suppose:

```text
50,000 tenants
49,000 small
900 medium
100 huge
```

A single shared schema may work well initially.

But the huge tenants may produce:

```text
large scans
high writes
long exports
large indexes
replication pressure
```

A mature architecture can evolve toward:

```text
Shared storage
      ↓
Measure tenant workload
      ↓
Promote heavy tenants
      ↓
Dedicated placement
```

This demonstrates why tenancy should be a logical abstraction above physical storage.

# 55. Naive → Improved → Production-Hardened

## Naive

```sql
CREATE TABLE orders (
    id bigint PRIMARY KEY,
    tenant_id bigint,
    customer_id bigint
);
```

Application code filters by `tenant_id`.

### Why it fails

Cross-tenant references and forgotten query predicates can violate isolation.

## Improved

```text
tenant_id NOT NULL

UNIQUE (tenant_id, business_key)

tenant-scoped foreign keys

tenant-aware indexes
```

### Why it works

The relational model now expresses scope.

## Production-hardened

Add:

```text
RLS where appropriate
least-privilege roles
transaction-scoped tenant context
adversarial isolation tests
tenant-aware observability
large-tenant performance tests
export/delete/migration workflows
```

### Why it works

Isolation becomes a layered property instead of a convention.

# 56. Operational Checklist

Before production, verify:

### Data Model

- Every tenant-owned fact has an explicit owner/scope.
- Global reference data is intentionally global.
- Branch and tenant scopes are not conflated.
- Cross-tenant relationships are impossible or explicitly justified.

### Constraints

- Tenant-local uniqueness includes tenant scope.
- Foreign keys enforce tenant consistency where required.
- Required tenant IDs are `NOT NULL`.
- Lifecycle rules are explicit.

### Security

- Runtime role has least privilege.
- RLS policies are tested if used.
- `USING` and `WITH CHECK` semantics are understood.
- Owner/BYPASSRLS behavior is understood.
- Privileged functions have controlled `search_path` and ownership.

### Performance

- Tenant-aware indexes match actual workload.
- Large-tenant behavior has been benchmarked.
- Noisy-neighbor scenarios have limits.
- Partitioning has measurable justification.

### Operations

- Tenant export is possible.
- Tenant deletion is defined.
- Backup/restore strategy is known.
- Large-tenant migration is possible.
- Placement can evolve without changing tenant identity.

### Testing

- Cross-tenant reads fail.
- Cross-tenant writes fail.
- Cross-tenant deletes fail.
- Cross-tenant relationship creation fails.
- Background workers are tenant-safe.
- Admin tooling is intentionally scoped.

# 57. Expert Mental Model

Think of multi-tenancy as a graph property.

A tenant owns a subgraph:

```text
Tenant T
  │
  ├── User
  ├── Customer
  │    └── Order
  │         └── Order Item
  ├── Product
  └── Payment
```

Every edge between tenant-owned nodes should preserve the same tenant boundary unless a deliberately shared relationship exists.

The strongest schemas make invalid cross-tenant edges difficult or impossible to represent.

# 58. What “Production-Grade” Means

A production-grade multi-tenant schema is not defined by using `tenant_id`.

It is defined by whether the system can answer “no” to all of these:

```text
Can Tenant A read Tenant B data?
Can Tenant A mutate Tenant B data?
Can Tenant A create a cross-tenant relationship?
Can an application bug bypass scope accidentally?
Can a background job lose tenant context?
Can one tenant starve others indefinitely?
Can we export one tenant safely?
Can we delete one tenant correctly?
Can we move one tenant operationally?
Can we prove isolation with tests and evidence?
```

If those answers are not clearly controlled, tenancy is not finished.

# 60. Final Principles

1. **Tenant identity is a modeling concept, not merely an HTTP parameter.**
2. **Tenant-owned facts should carry explicit ownership.**
3. **Global IDs do not automatically guarantee tenant isolation.**
4. **Tenant-local uniqueness must encode tenant scope.**
5. **Cross-tenant foreign keys are one of the most important integrity failures to prevent.**
6. **RLS is a powerful database defense layer, but not a replacement for application authorization.**
7. **Transaction-scoped tenant context matters in pooled applications.**
8. **Tenant-aware indexes should follow real workload shape.**
9. **Average tenant behavior is not enough; large tenants must be measured separately.**
10. **One partition per tenant is not automatically scalable.**
11. **Partitioning solves physical layout, not authorization.**
12. **Tenant deletion, export, backup, and migration are part of the data model's operational contract.**
13. **The strongest tenant boundaries are encoded structurally, not remembered procedurally.**
14. **Defense in depth matters because a tenant-isolation failure can become a multi-customer data breach.**
15. **Measure tenant workload before choosing physical isolation.**
