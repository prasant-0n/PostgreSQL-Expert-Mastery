# 02.16 — State Machines

> **Phase 02 — Relational Data Modeling**  
> A production state machine makes business lifecycle rules explicit, atomic, testable, observable, and auditable.

## 1. Objective

This chapter teaches lifecycle modeling beyond a generic `status` column: explicit states, legal transitions, guards, authorization, state-specific invariants, concurrency, transition history, idempotency, recovery, outbox integration, multi-tenant isolation, workflow versioning, and production testing.

The key question is:

> **Which states exist, which transitions are legal, who may invoke them, which conditions must hold, and what evidence must remain?**

---

## 2. State Machine Fundamentals

### Simple definition

A state machine defines a finite set of states and legal movement between those states.

```text
DRAFT → SUBMITTED → APPROVED → FULFILLED → CLOSED
          │
          └────→ REJECTED
```

### Engineering definition

A workflow contains:

```text
States
Transitions
Commands
Guards
Authorization
Effects
History
```

### Expert definition

A production state machine is an **invariant system over current state, transition history, actor permissions, concurrency, and transaction boundaries**.

A database-backed workflow should make corruption difficult, not merely document the correct behavior.

---

## 3. State ≠ Transition

A **state** answers:

```text
What condition is the entity in now?
```

A **transition** answers:

```text
How can it legally move?
```

Example:

```text
DRAFT --submit--> SUBMITTED
SUBMITTED --approve--> APPROVED
SUBMITTED --reject--> REJECTED
```

A PostgreSQL `ENUM`, `CHECK`, or lookup table can restrict the state vocabulary. None of these alone defines legal movement between states.

---

## 4. Why `status` Columns Become Dangerous

A naïve application starts with:

```sql
status text
```

and:

```ts
if (order.status === 'submitted') {
  order.status = 'approved';
}
```

As the domain grows, requirements appear:

- cancelled orders cannot become approved;
- only managers may approve;
- approval requires prerequisite checks;
- some transitions require a reason;
- competing requests must not both win;
- important transitions need evidence;
- external events must correspond to committed business changes.

The current status is a **snapshot**. The state machine is the snapshot plus the legal movement around it.

---

## 5. State Taxonomy

### Stable states

Meaningful business conditions such as:

```text
ACTIVE
SUSPENDED
CLOSED
```

### Terminal states

States with no ordinary outgoing edge:

```text
CANCELLED
SETTLED
ARCHIVED
```

Terminality is an invariant, not a name.

### Failure states

Failure may be a domain state:

```text
PENDING → PROCESSING → COMPLETED
                    └→ FAILED
```

Or failure can remain operational metadata. Choose based on whether the business and operators must reason about it as a durable condition.

### Transitional states

Do not create `PROCESSING` or `BUSY` merely because one request is executing. A stored state should have business or operational meaning beyond the lifetime of one request.

---

## 6. Model the Transition Graph First

Represent an edge as:

```text
(source_state, command, target_state)
```

Example:

```text
(DRAFT, submit, SUBMITTED)
(SUBMITTED, approve, APPROVED)
(SUBMITTED, reject, REJECTED)
(DRAFT, cancel, CANCELLED)
(SUBMITTED, cancel, CANCELLED)
```

A graph exposes impossible edges during design instead of during incident response.

---

## 7. State Invariants

Define what must be true while an entity occupies a state.

```text
APPROVED  → approved_at IS NOT NULL
CANCELLED → cancellation_reason IS NOT NULL
SHIPPED   → shipment_id IS NOT NULL
CAPTURED  → captured_amount > 0
```

Example:

```sql
CHECK (
  status <> 'cancelled'
  OR cancellation_reason IS NOT NULL
)
```

Think in two layers:

```text
Transition invariant → which movement is legal?
State invariant      → what must be true in that state?
```

PostgreSQL `CHECK` constraints are row-level constraints; TRUE or UNKNOWN satisfies a check, so mandatory values may additionally need `NOT NULL`. PostgreSQL also warns that cross-row/table guarantees should not be faked with `CHECK`; use relational constraints or appropriate transactional/trigger designs instead. citeturn394659search7turn394659search4

## 8. Choosing a State Representation

### `text` + `CHECK`

```sql
status text NOT NULL CHECK (
  status IN ('draft', 'submitted', 'approved', 'rejected', 'cancelled')
)
```

Good for small, stable, easily migrated vocabularies.

### PostgreSQL `ENUM`

```sql
CREATE TYPE order_status AS ENUM (
  'draft', 'submitted', 'approved', 'rejected', 'cancelled'
);
```

Good for stable PostgreSQL-native vocabularies. PostgreSQL enums are static ordered sets; values can be added or renamed, while removing/reordering existing values is intentionally constrained. citeturn586348search0

### Lookup table

```sql
CREATE TABLE workflow_states (
  code text PRIMARY KEY,
  description text NOT NULL,
  is_terminal boolean NOT NULL DEFAULT false
);
```

Use when states have metadata, configuration, tenant variation, localization, or workflow versioning.

### Practical rule

```text
CHECK → small/local vocabulary
ENUM  → stable PostgreSQL-native vocabulary
TABLE → dynamic/configurable workflow
```

Do not build a workflow engine when a few explicit domain commands are sufficient.

---

## 9. Enum Is Not a Workflow

An enum can reject:

```text
status = 'does_not_exist'
```

It cannot, by itself, reject:

```text
CANCELLED → APPROVED
```

Therefore:

```text
Allowed states ≠ Allowed transitions
```

---

## 10. Transition Catalogs

For configurable workflows:

```sql
CREATE TABLE workflow_transitions (
  from_state text NOT NULL,
  command text NOT NULL,
  to_state text NOT NULL,
  PRIMARY KEY (from_state, command),
  CHECK (from_state <> to_state)
);
```

Useful for configurable workflows, shared workflow definitions, transition-specific permissions, and coexistence of workflow versions.

The catalog itself does not enforce the entity row. The transition operation still has to atomically assert the source state and mutate the target state.

---

## 11. The Critical Pattern: Atomic Transition

Preferred basic operation:

```sql
UPDATE orders
SET status = 'approved',
    approved_at = now()
WHERE id = $1
  AND status = 'submitted'
RETURNING *;
```

Interpretation:

```text
1 row → transition succeeded
0 rows → source-state precondition failed or entity absent
```

### Naïve

```text
SELECT state
→ application checks
→ UPDATE
```

### Why it fails

Another transaction can change the entity between the read and write.

### Improved

```text
Conditional UPDATE
```

### Why it works

The precondition and mutation are coupled in the database write path.

---

## 12. Compare-and-Swap Mental Model

Think:

```text
Expected = SUBMITTED
Desired  = APPROVED
```

Add optimistic versioning when stale clients matter:

```sql
UPDATE orders
SET status = $2,
    version = version + 1,
    updated_at = now()
WHERE id = $1
  AND status = $3
  AND version = $4
RETURNING *;
```

This makes stale updates fail rather than silently overwrite newer state.

---

## 13. Conditional Write vs `FOR UPDATE`

### Conditional write

```sql
UPDATE orders
SET status = 'approved'
WHERE id = $1 AND status = 'submitted';
```

Use when the invariant fits in one atomic write.

### Lock-and-inspect

```sql
SELECT *
FROM orders
WHERE id = $1
FOR UPDATE;
```

Use when the transition needs coordinated reads/writes across related rows inside one transaction.

Principle:

> **Use the smallest concurrency-control mechanism that preserves the invariant.**

Do not cargo-cult `FOR UPDATE`.

---

## 14. Domain Commands

Avoid generic status setters:

```ts
updateOrder(id, { status: 'approved' });
```

Prefer explicit commands:

```ts
submitOrder(id, actor);
approveOrder(id, actor);
cancelOrder(id, actor, reason);
```

Commands provide one place to enforce:

- source-state requirements;
- authorization;
- guards;
- required inputs;
- history;
- idempotency;
- outbox events.

The API should make invalid intent harder to express.

---

## 15. Guards vs Invariants

A transition may require:

```text
SUBMITTED → APPROVED
```

only when:

```text
credit_check = PASSED
inventory_verified = true
actor = authorized approver
```

Separate concerns:

```text
Durable relational invariant → database constraint where possible
Authorization               → application/security layer
External dependency         → service orchestration
```

Do not force every rule into SQL.

---

## 16. State-Specific Constraints

Example:

```sql
CREATE TABLE payments (
  id bigint PRIMARY KEY,
  status text NOT NULL CHECK (
    status IN ('pending', 'captured', 'failed', 'refunded')
  ),
  captured_at timestamptz,
  captured_amount numeric(18,2),
  failure_reason text,
  refunded_at timestamptz,
  CHECK (
    status <> 'captured'
    OR (captured_at IS NOT NULL AND captured_amount > 0)
  ),
  CHECK (
    status <> 'failed'
    OR failure_reason IS NOT NULL
  ),
  CHECK (
    status <> 'refunded'
    OR refunded_at IS NOT NULL
  )
);
```

The status now participates in persistent integrity rather than being a UI label.

---

## 17. Transition History

Current state cannot answer:

```text
Who approved it?
When was it rejected?
How long was it pending?
Which command caused the change?
Was it reopened?
```

Use explicit domain history where these answers matter:

```sql
CREATE TABLE order_state_history (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id bigint NOT NULL REFERENCES orders(id),
  from_status text,
  to_status text NOT NULL,
  command text NOT NULL,
  actor_id bigint,
  reason text,
  occurred_at timestamptz NOT NULL DEFAULT now()
);
```

State history and a generic audit log are related but not interchangeable.

---

## 18. Current State + History in One Transaction

Preferred lifecycle:

```text
BEGIN
  update current state
  insert state history
  insert outbox event
COMMIT
```

Never rely on:

```text
UPDATE
COMMIT
history later
```

because business truth can become disconnected from evidence.

---

## 19. Trigger-Based History

A trigger can record only actual state changes:

```text
IF NEW.status IS DISTINCT FROM OLD.status
THEN INSERT history
```

PostgreSQL supports row- and statement-level triggers for DML and supports transition tables that expose sets of rows affected by a statement. Trigger timing therefore becomes part of the architecture, not merely an implementation detail. citeturn394659search1

### Advantages

- captures changes from multiple clients;
- centralizes mandatory history;
- reduces forgotten audit calls.

### Costs

- hidden behavior;
- more difficult debugging;
- actor-context propagation;
- trigger ordering/recursion concerns;
- increased database/application coupling.

Use triggers deliberately rather than turning them into an invisible workflow engine.

---

## 20. Database Transition Functions

Sensitive transitions can be exposed as database functions:

```sql
CREATE FUNCTION approve_order(p_order_id bigint)
RETURNS orders
LANGUAGE plpgsql
AS $$
DECLARE
  result orders;
BEGIN
  UPDATE orders
  SET status = 'approved', approved_at = now()
  WHERE id = p_order_id
    AND status = 'submitted'
  RETURNING * INTO result;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Order cannot be approved';
  END IF;

  RETURN result;
END;
$$;
```

This can be valuable when several clients share the same database invariant or direct table permissions need to be reduced. The trade-off is stronger database coupling.

## 21. Idempotency

Duplicate commands happen through:

```text
double-clicks
network retries
worker retries
message redelivery
timeouts
```

Define outcomes explicitly:

```text
approve on SUBMITTED → transition
approve on APPROVED   → idempotent success or defined conflict
approve on CANCELLED  → invalid transition
```

Useful outcome classes:

```text
NOT_FOUND
FORBIDDEN
INVALID_TRANSITION
PRECONDITION_FAILED
CONFLICT
IDEMPOTENT_SUCCESS
DEPENDENCY_FAILURE
SYSTEM_FAILURE
```

---

## 22. Durable Command Receipts

For commands with external effects:

```sql
CREATE TABLE command_receipts (
  command_id uuid PRIMARY KEY,
  entity_id bigint NOT NULL,
  command text NOT NULL,
  result jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

When command receipt and business mutation share a transaction, retries can safely become duplicate deliveries rather than duplicate business effects.

Do not confuse idempotency with exactly-once message delivery. Repeated delivery is normal; the consumer or command boundary must make repetition safe.

---

## 23. Concurrency: Approve vs Cancel

Initial state:

```text
SUBMITTED
```

Two requests race:

```text
A → approve
B → cancel
```

Each uses a source-state predicate. Once one transaction changes the row, the other cannot also legitimately transition the same row from the old state.

The loser must interpret the result correctly instead of blindly retrying forever.

This is why state preconditions belong in the write itself.

---

## 24. Multi-Row Aggregate Transitions

Example:

```text
ORDER → READY_TO_SHIP
```

only when all order lines are fully allocated.

Now the transaction may need to coordinate:

```text
order
order_lines
allocation
history
outbox
```

A row-level `CHECK` is not the right mechanism for arbitrary cross-row consistency. PostgreSQL explicitly cautions against such designs and recommends appropriate relational constraints or trigger/transactional approaches. citeturn394659search7

---

## 25. State Machine + Outbox

Avoid:

```text
UPDATE database
publish event
```

with no atomic connection.

Prefer:

```text
BEGIN
  update state
  insert history
  insert outbox event
COMMIT
```

Then publish the durable outbox entry asynchronously.

This establishes:

```text
Committed business transition
        ↕
Durable intent to publish
```

---

## 26. State Machine vs Event Sourcing

A state machine defines legal movement.

Event sourcing uses a durable event stream as the authoritative representation from which state can be reconstructed.

You can have:

```text
state machine + current-state table
```

without event sourcing.

Use event sourcing when reconstruction and the event history itself are central domain requirements—not merely because the system has statuses.

---

## 27. State Machine vs Audit Log

A state history answers:

```text
How did this entity move through its lifecycle?
```

A generic audit system may answer:

```text
What row changed?
What values changed?
Who changed it?
```

A business audit layer may additionally capture:

```text
Why was the decision made?
Which command/approval caused it?
```

Design evidence structures intentionally.

---

## 28. Authorization Is Separate From Legality

A transition may exist in the graph but be inaccessible to a given actor.

```text
Legal transition
≠
Authorized transition
```

Example:

```text
submit  → sales operator
approve → manager
refund  → finance
```

Administrative override should be explicit, reasoned, authenticated, and audited. Avoid a generic “admin can set any status” escape hatch.

---

## 29. Multi-Tenant State Machines

Tenant scope should be part of the authorization and write boundary:

```sql
UPDATE orders
SET status = 'approved'
WHERE tenant_id = $1
  AND id = $2
  AND status = 'submitted';
```

Where appropriate, combine this with database-level isolation such as RLS.

A globally unique entity identifier does not remove the tenant-isolation requirement.

---

## 30. Workflow Versioning

Workflows evolve:

```text
v1: DRAFT → APPROVED → CLOSED
v2: DRAFT → REVIEW → APPROVED → FULFILLED → CLOSED
```

If old entities must retain old semantics, version the workflow definition or the entity's workflow version.

Configurable workflow engines commonly contain:

```text
workflow_definitions
workflow_states
workflow_transitions
workflow_transition_roles
workflow_instances
workflow_transition_history
```

Do not introduce this machinery without a real requirement.

---

## 31. Recovery and Stuck States

Recovery should be modeled, not hidden:

```text
PROCESSING → FAILED
FAILED → RETRYING
RETRYING → PROCESSING
FAILED → CANCELLED
```

Detect stuck work with an operational query:

```sql
SELECT id
FROM jobs
WHERE status = 'processing'
  AND processing_started_at < now() - interval '15 minutes';
```

Recovery commands should preserve the same concurrency, authorization, and evidence rules as normal transitions.

---

## 32. Observability

Track:

- transition counts by command/state;
- invalid-transition attempts;
- state duration;
- stuck-state counts;
- retry counts;
- transition latency;
- external dependency failures.

Useful metric:

```text
state_duration = exit_time - entry_time
```

For example:

```text
SUBMITTED p50: 2 min
SUBMITTED p95: 41 min
SUBMITTED p99: 4.5 hr
```

Tail latency often reveals workflow bottlenecks hidden by averages.

---

## 33. Performance

State transition scalability is usually dominated by surrounding behavior:

- hot-row contention;
- excessive history writes;
- high transition frequency;
- unnecessary `FOR UPDATE` locks;
- synchronous external calls;
- polling;
- missing indexes for queue predicates.

Example:

```sql
CREATE INDEX idx_orders_status_created
ON orders (status, created_at);
```

Validate with actual workload and `EXPLAIN`; “every status needs an index” is not a production principle.

---

## 34. Hot Rows

A single aggregate row may become a synchronization hotspot:

```text
one inventory counter
one account aggregate
one heavily retried job row
```

Possible solutions:

```text
reduce mutation frequency
partition work
append facts/events
use optimistic concurrency
redesign aggregate boundaries
```

Do not assume hardware alone fixes contention.

## 35. Introspection

PostgreSQL stores constraint metadata in `pg_constraint`, including constraint type and deferrability; PostgreSQL 18 also exposes temporal constraint metadata there. Trigger metadata is available through information-schema views. citeturn394659search0turn394659search3

Useful diagnostics:

```sql
SELECT conname, contype, condeferrable, condeferred
FROM pg_constraint
WHERE conrelid = 'orders'::regclass;
```

```sql
SELECT trigger_name,
       event_manipulation,
       action_timing,
       action_orientation
FROM information_schema.triggers
WHERE event_object_table = 'orders';
```

## 36. Evidence-Driven Debugging

Investigate a workflow incident using evidence in this order:

```text
1. current row
2. state history
3. command/idempotency record
4. actor identity
5. application/transaction logs
6. outbox/event records
7. lock/timing evidence
8. deployed version
```

A current status is a snapshot, not an explanation.

## 37. Migration Strategy

For a legacy free-form status column:

```text
1. inventory real values
2. classify legacy/invalid states
3. define target graph
4. map old values
5. repair data
6. add constraints
7. introduce command APIs
8. remove generic status writes
9. add history/backfill strategy
10. monitor invalid transitions
```

Do not discover the migration plan through a production constraint failure.

PostgreSQL requires existing table data to satisfy a newly added constraint when it is checked; therefore large or dirty migrations need an explicit validation/backfill strategy. citeturn394659search9

## 38. Testing Strategy

### Unit

Test all graph edges:

```text
DRAFT → SUBMITTED       valid
SUBMITTED → APPROVED    valid
APPROVED → DRAFT        invalid
CANCELLED → APPROVED    invalid
```

### Integration

Verify constraints, affected-row behavior, rollback, history, and outbox behavior.

### Concurrency

Test:

```text
approve vs cancel
approve vs approve
ship vs cancel
```

Assert invariants, not a guessed timing order.

### Failure injection

Simulate update success followed by history failure, outbox failure, worker crash, and connection loss. The desired outcome is consistent transaction state.

### Property-style testing

Generate command sequences and assert that:

```text
current state is valid
all edges are legal
terminal states stay terminal
state-specific invariants hold
```

## 39. AI / Vibe-Coding Failure Modes

### Generic status update

```ts
updateStatus(id, status)
```

**Problem:** arbitrary transitions.

### Read-then-write

```ts
const row = await find(id);
if (row.status === 'submitted') {
  await update(id, 'approved');
}
```

**Problem:** race between validation and mutation.

### Enum = workflow assumption

**Problem:** a type vocabulary does not define transition edges.

### History after commit

**Problem:** state and evidence can diverge.

### Admin bypass

**Problem:** invisible integrity exceptions.

### Trigger-everything architecture

**Problem:** hidden workflow behavior and difficult debugging.

Always ask:

> **What invariant is this code enforcing, and where is the atomic boundary?**

## 40. Jewellery ERP Example

A production order might move:

```text
DRAFT
  ↓
CONFIRMED
  ↓
ALLOCATED
  ↓
INVOICED
  ↓
PAID
  ↓
DISPATCHED
  ↓
DELIVERED
```

Cancellation may be legal only before certain accounting milestones:

```text
DRAFT ─────────→ CANCELLED
CONFIRMED ─────→ CANCELLED
ALLOCATED ─────→ CANCELLED
INVOICED ──────→ CREDIT_NOTE_REQUIRED
```

The meaning is important: after invoicing, “cancel” may imply accounting reversal rather than changing one status field. Inventory, accounting, document history, and authorization become part of the transition contract.

## 41. Common Anti-Patterns

```text
free-form status strings
generic updateStatus()
SELECT then UPDATE
no transition history
history after commit
silent admin bypass
one overloaded FAILED state
hidden repair scripts
synchronous external side effects inside the critical transaction
```

Each weakens a different consistency boundary.

## 42. Decision Framework

```text
Fixed workflow
→ explicit commands + relational constraints

Workflow with important history
→ current state + state history

Configurable workflow
→ versioned workflow/transition tables

Distributed effects
→ transaction + outbox

Event-centric domain
→ consider event sourcing
```

Prefer the simplest architecture that satisfies the real invariants.

## 43. Production Architecture

```text
HTTP / Worker / Command
          │
          ▼
    Domain Service
          │
 authorization + guards
          │
          ▼
      Transaction
       │    │    │
       │    │    └── outbox
       │    └─────── history
       └──────────── current state
          │
       COMMIT
          │
          ▼
 asynchronous external effects
```

The transaction is the consistency boundary. External systems consume durable intent after commit.

# Core Principle

> **A state machine is not a status field. It is an invariant system over legal transitions, authorization, concurrency, history, and side effects.**
>
> Model states explicitly, make transitions atomic, enforce durable invariants at the database boundary, preserve evidence, and treat failure/recovery behavior as first-class design concerns.
