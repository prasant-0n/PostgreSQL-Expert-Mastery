# 02.3 — Natural vs Surrogate Keys

> **Phase 02 — Relational Data Modeling**  
> A production-grade treatment of natural identifiers, surrogate identifiers, stability, uniqueness, composite identity, distributed systems, migrations, external references, and the architectural question: **what makes a row the same row?**

---

## 1. Chapter Objective

A database key is not merely a convenient column used by an ORM. A key answers a foundational modeling question:

> **How does the system identify one logical fact, and how stable is that identity across the lifetime of the system?**

By the end of this chapter you should be able to:

- distinguish **identity** from **attributes**;
- distinguish natural, surrogate, candidate, primary, alternate, and composite keys;
- explain when a natural key is a strong identifier and when it is not;
- explain why surrogate keys solve some problems but create others;
- model stable business identity without confusing it with mutable business data;
- choose between `BIGINT`, UUID, and other identifiers without cargo-cult rules;
- design uniqueness separately from physical row identity;
- model composite business identity correctly;
- reason about identifiers across APIs, imports, replicas, queues, caches, and distributed writers;
- understand identifier migration and key-change cost;
- prevent cross-tenant identity collisions;
- recognize AI-generated key designs that look reasonable but encode the wrong invariant.

---

# 2. Three Levels of Definition

## 2.1 Simple definition

A **key** is a value, or set of values, that identifies a row uniquely.

A **natural key** uses information that already has business meaning.

A **surrogate key** is an identifier introduced primarily for database/system identity and carries no required business meaning.

Examples:

```text
Natural:
    email
    ISBN
    country_code
    tax_identifier

Surrogate:
    customer_id = 847293
    order_id = 9128401
```

## 2.2 Engineering definition

A key is an attribute set whose uniqueness is an integrity rule over a relation.

The design question is not only:

```text
"Can this value identify the row today?"
```

but also:

```text
"Will the identifier remain valid, unique, stable, safe to expose,
and operationally manageable throughout the system lifecycle?"
```

## 2.3 Expert definition

A production identifier is an **identity contract** across multiple boundaries:

```text
Business identity
      ↓
Relational identity
      ↓
Foreign-key references
      ↓
Application references
      ↓
External/API identity
      ↓
Events / integrations
      ↓
Audit / history
      ↓
Backups / replicas / migrations
```

Changing an identifier may therefore be much more expensive than changing an ordinary attribute.

---

# 3. First Principle: Identity Is Not the Same as Meaning

Consider an employee:

```text
id = 501
employee_code = "EMP-2026-001"
email = "asha@example.com"
name = "Asha"
```

These values answer different questions.

```text
id
→ Which database entity is this?

employee_code
→ Which business identifier is this employee assigned?

email
→ Which address currently belongs to this employee?

name
→ What is the person's current display name?
```

A common modeling error is to choose a value because humans recognize it and assume that recognition implies permanence.

It does not.

An identifier can be meaningful without being stable.

---

# 4. Candidate Keys Come First

Before choosing a primary key, identify the **candidate keys**.

A candidate key is a minimal attribute set capable of uniquely identifying a relation tuple.

Example:

```text
users
-----
id
email
employee_number
```

Suppose business rules guarantee:

```text
id              unique
email           unique
employee_number unique
```

Then all three could potentially be candidate keys, depending on the semantic and lifecycle rules.

The primary key is a design choice among valid candidates; it does not magically create identity.

---

# 5. Natural Keys

A natural key is derived from domain meaning.

Examples:

```text
country.iso_code
book.isbn
currency.code
product.sku
employee.employee_number
organization.registration_number
```

A good natural key has strong properties such as:

- uniqueness within its intended scope;
- mandatory presence when identity requires it;
- semantic legitimacy;
- reasonable stability;
- deterministic representation;
- well-defined ownership of the namespace.

But these properties must be demonstrated, not assumed.

---

# 6. Natural-Key Stability

The most important question is not:

> "Is this value unique?"

It is:

> **"Does this value remain the identity of the same entity when the business changes it?"**

For example:

```text
email
```

may be unique today, but users can often change email addresses.

Therefore:

```text
email = unique business attribute
```

does not necessarily imply:

```text
email = immutable identity
```

The same applies to:

- phone numbers;
- usernames;
- employee codes;
- branch codes;
- SKU values;
- invoice numbers;
- government identifiers;
- external system identifiers.

Some are stable enough to be keys in their domain. Others are merely alternate identifiers.

---

# 7. Surrogate Keys

A surrogate key is introduced independently of business meaning.

Typical examples:

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

or:

```sql
id uuid PRIMARY KEY DEFAULT gen_random_uuid()
```

The surrogate key answers:

> "Which row/entity does this reference point to?"

It does not answer:

> "What business rule makes this entity unique?"

That second question still requires `UNIQUE` or other constraints.

---

# 8. Surrogate Key Does Not Replace Business Uniqueness

This is a critical distinction.

Bad design:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL
);
```

Now this is legal:

```text
id | sku
---|------
1  | A-100
2  | A-100
3  | A-100
```

The surrogate key guarantees row identity, but does not enforce SKU uniqueness.

Correct when SKU must be unique globally:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL UNIQUE
);
```

Correct when SKU is unique only inside a tenant:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    sku text NOT NULL,
    UNIQUE (tenant_id, sku)
);
```

Expert lesson:

> **Physical identity and domain uniqueness are separate invariants.**

---

# 9. Natural Primary Key vs Surrogate Primary Key

Suppose:

```text
country
-------
code
name
```

For a reference table, `code` may be an excellent primary key if the code is the authoritative identity in the domain.

For an operational entity:

```text
customer
--------
email
name
phone
```

using `email` as the primary key can couple every downstream foreign key to an attribute that may need to change.

An alternative:

```text
customer
--------
id PK
email UNIQUE
name
phone
```

Now:

```text
id → stable relational identity
email → alternate business identifier
```

This decouples identity from mutable attributes.

---

# 10. The Core Decision Matrix

| Question | Natural key tends to help | Surrogate key tends to help |
|---|---|---|
| Does the domain already define a stable identity? | Yes | Optional |
| Can the value change? | Risk | Stronger fit |
| Is the value large? | Can be costly | Usually smaller |
| Is the value composite? | Often awkward | Usually simpler |
| Is identity externally exposed? | Meaningful | Can separate public ID |
| Many downstream FKs? | Larger if wide | Usually simpler |
| Multiple data sources? | Collision risk | Can centralize generated identity |
| Distributed generation? | Depends | UUID/other generated IDs help |
| Human readability required? | Strong | Often needs separate code |
| Namespace is local to tenant? | Composite/scoped key needed | Surrogate + scoped unique constraint |

This is a trade-off matrix, not a universal rule.

---

# 11. Composite Natural Keys

Suppose product SKU is unique within a branch:

```text
(branch_id, sku)
```

The real business identity is not:

```text
sku
```

but:

```text
(branch_id, sku)
```

The correct uniqueness rule is:

```sql
UNIQUE (branch_id, sku)
```

An application may still use:

```text
product_id BIGINT
```

as the surrogate identity.

That gives:

```text
product_id
→ relational identity

(branch_id, sku)
→ business uniqueness
```

This is one of the strongest production patterns for multi-tenant systems.

---

# 12. Composite Primary Keys

Composite keys can be exactly correct when the tuple itself is the entity identity.

Example:

```text
order_items
-----------
(order_id, line_number)
```

If line number is meaningful only within an order, then:

```sql
PRIMARY KEY (order_id, line_number)
```

is a valid model.

Do not add:

```text
id
```

automatically just because ORMs prefer scalar identifiers.

First determine whether the row's natural identity is composite.

---

# 13. When Composite Keys Become Operationally Expensive

Suppose:

```text
order_item
----------
order_id
line_number
```

and many child tables reference it.

Then every child FK may need:

```text
(order_id, line_number)
```

This increases:

- index width;
- FK width;
- join predicates;
- API payload complexity;
- ORM mapping complexity;
- cache-key complexity.

A surrogate key can simplify physical referencing:

```text
order_item_id
```

while preserving:

```sql
UNIQUE (order_id, line_number)
```

This yields:

```text
surrogate identity
+
correct business uniqueness
```

---

# 14. Natural vs Surrogate Is Not Binary

A high-quality design frequently uses both.

Example:

```text
customer
--------
id BIGINT PRIMARY KEY
customer_number TEXT UNIQUE
email TEXT UNIQUE
```

Each serves a different role.

```text
id
→ internal relational references

customer_number
→ business-facing stable identifier

email
→ alternate contact identifier
```

This is usually superior to forcing one field to perform all three jobs.

---

# 15. Identity vs Identifier vs Display Code

These are often conflated.

### Database identity

```text
customer.id = 81273
```

### Business identifier

```text
customer_number = "CUS-2026-004812"
```

### Display label

```text
name = "Asha Retail"
```

### Contact attribute

```text
email = "billing@asha-retail.example"
```

Changing the display label should not change identity.

Changing the contact address should not change identity.

Even changing a business code may or may not change identity depending on domain rules.

Model these questions explicitly.

---

# 16. External IDs

A common production requirement is:

```text
internal ID
external/public ID
business code
```

Example:

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id uuid NOT NULL UNIQUE DEFAULT gen_random_uuid(),
    customer_number text NOT NULL,
    UNIQUE (customer_number)
);
```

Potential roles:

```text
id
→ database-local relational reference

public_id
→ API resource identifier

customer_number
→ human/business identifier
```

Do not expose internal implementation identity automatically just because the ORM returns it.

---

# 17. Security: Sequential IDs Are Not Authorization

Suppose an API exposes:

```text
GET /customers/1001
```

An attacker may try:

```text
GET /customers/1002
GET /customers/1003
GET /customers/1004
```

Changing from `BIGINT` to UUID does not solve authorization.

UUIDs may reduce easy enumeration, but the real control is:

```text
authentication
+
authorization
+
tenant isolation
+
object-level access checks
```

An opaque ID is useful as a defense-in-depth measure, not as a permission system.

---

# 18. Predictability and Enumeration

Sequential identifiers reveal some information:

```text
100
101
102
...
```

Depending on the system, they can expose rough creation volume or facilitate scraping.

UUID-based public identifiers make enumeration less convenient.

But the correct architecture is:

```text
Public ID
    ↓
Authorization check
    ↓
Tenant scope check
    ↓
Resource access
```

not:

```text
UUID
    ↓
Therefore secure
```

---

# 19. Key Width Has System-Wide Cost

Key choice propagates into every referencing structure.

A wide identifier affects:

```text
PK index
FK indexes
join buffers
sorts
hash tables
cache entries
network payloads
WAL volume
replication traffic
```

The effect is multiplied across large child tables.

For example, if a parent key is referenced by 500 million rows, even a small increase in key/index width can become material.

Therefore:

> **Key width is not only a table-design decision; it is an ecosystem-wide storage and performance decision.**

---

# 20. BIGINT as a Surrogate Key

Typical design:

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

Advantages:

- compact;
- ordered numerically;
- efficient comparisons;
- familiar to relational tooling;
- excellent for single-database generated identity;
- simple for human operators.

Potential concerns:

- globally guessable if exposed directly;
- generated sequence values are not necessarily gapless;
- distributed writers need coordination if IDs are not generated centrally.

Important:

> **A sequence-backed identity is an identity generator, not a guarantee of gap-free business numbering.**

---

# 21. Sequence Gaps Are Normal

Consider:

```sql
INSERT INTO customers (...) VALUES (...);
```

A sequence value may be allocated and the transaction later roll back.

This can produce:

```text
100
101
103
```

without `102`.

Do not infer:

```text
missing ID = missing business transaction
```

IDs are identifiers, not accounting numbers.

Where regulatory/business numbering must be controlled, model that numbering requirement separately.

---

# 22. Business Numbers Are Different from Surrogate IDs

An invoice may need:

```text
invoice.id            → relational identity
invoice.invoice_no    → business/legal number
```

The legal number may require:

- scoped uniqueness;
- controlled issuance;
- formatting;
- fiscal-year scope;
- branch scope;
- auditability;
- non-reuse;
- specialized allocation logic.

Do not overload:

```text
BIGINT id
```

with the semantics of a regulatory business number.

---

# 23. UUIDs as Surrogate Keys

UUIDs are useful when IDs need to be generated without a single central counter.

They are especially useful for:

- distributed producers;
- offline creation;
- multi-region ingestion;
- event identifiers;
- mergeable datasets;
- public resource identifiers.

Trade-offs depend on UUID version and indexing strategy.

Large random identifiers can produce less locality than monotonically increasing identifiers, which can affect index behavior and write patterns.

The correct lesson is not:

```text
UUID = bad
```

or:

```text
UUID = scalable
```

The correct question is:

> **What generation, locality, exposure, and replication properties does the workload require?**

---

# 24. Time-Ordered IDs

Some systems need distributed IDs while retaining better ordering/locality characteristics.

Examples include modern UUID variants and other distributed ID schemes designed to encode time or ordering.

The design goals may include:

```text
Globally unique
+
rough temporal ordering
+
independent generation
+
reasonable index locality
```

But ordering is usually not equivalent to exact creation order.

Distributed clocks, batching, transaction timing, and commit order can differ.

Therefore do not use ID ordering as a substitute for explicit temporal columns when business time matters.

---

# 25. Monotonic ID ≠ Chronological Truth

Bad assumption:

```sql
ORDER BY id DESC
```

therefore:

```text
most recently created business event
```

This may fail because:

- IDs may be allocated before commit;
- transactions may commit out of allocation order;
- multiple writers may exist;
- imports may assign IDs independently;
- records may be inserted later with historical timestamps.

Use explicit timestamps or sequence columns when ordering semantics matter.

---

# 26. Distributed Systems Change the Question

In one database:

```text
single sequence
```

is simple.

Across multiple writers:

```text
region A
region B
worker C
offline client D
```

central sequence coordination may become undesirable or unavailable.

Possible choices include:

```text
UUID
ULID-like identifiers
Snowflake-style identifiers
application-generated numeric IDs
partition-specific sequences
```

Each solves a different combination of:

- uniqueness;
- ordering;
- locality;
- coordination;
- clock dependency;
- bit width;
- human usability.

Do not choose a distributed ID because an architecture diagram contains the word “microservices.”

---

# 27. Natural Keys in Distributed Imports

Suppose two systems import customers.

System A:

```text
customer_code = CUST-001
```

System B:

```text
customer_code = CUST-001
```

If the identifiers are globally scoped, collision occurs.

Possible strategies:

```text
(source_system, external_id)
```

or:

```text
tenant_id + external_id
```

or a globally governed namespace.

The correct model depends on who owns the namespace.

---

# 28. Namespace Ownership

Every supposedly unique identifier needs a question answered:

> **Unique where?**

Possibilities:

```text
globally unique
per tenant
per branch
per fiscal year
per source system
per parent row
per jurisdiction
```

Examples:

```text
SKU
→ maybe unique per tenant

invoice_number
→ maybe unique per branch + financial year

email
→ possibly globally unique in the product

line_number
→ unique only within an order
```

A key without a namespace definition is incomplete.

---

# 29. Scoped Natural Keys

Example:

```sql
CREATE TABLE invoices (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    fiscal_year integer NOT NULL,
    invoice_number integer NOT NULL,
    UNIQUE (tenant_id, fiscal_year, invoice_number)
);
```

This is superior to pretending:

```text
invoice_number
```

is globally unique when the business only requires scoped uniqueness.

---

# 30. Key Mutation Cost

Imagine 200 tables reference:

```text
customer.email
```

Changing email now becomes a relational migration event.

Every child reference must be updated or the design must rely on `ON UPDATE CASCADE` where appropriate.

This is rarely desirable for a mutable business attribute.

Surrogate identity avoids this coupling:

```text
customer_id remains stable
email may change
```

This is one of the strongest practical reasons for surrogate keys.

---

# 31. ON UPDATE CASCADE Is Not a Universal Solution

Suppose:

```sql
FOREIGN KEY (email)
REFERENCES customers(email)
ON UPDATE CASCADE
```

Technically, this can propagate a key change.

But operationally it may cause:

- broad update work;
- locking;
- index maintenance;
- replication/WAL amplification;
- unexpected application behavior;
- complicated auditing.

A design should minimize key mutation rather than treating cascading mutation as free.

---

# 32. Natural Keys Can Be Better Than Surrogates

Surrogate keys are not automatically superior.

Examples where a natural key can be excellent:

```text
ISO currency code
country code
IANA-like controlled code
small stable reference vocabulary
```

For:

```text
currencies.code = 'INR'
```

forcing:

```text
id = 87
code = 'INR'
```

may add unnecessary indirection if `code` is authoritative, stable, small, and naturally unique.

The right question is lifecycle and semantics, not ideology.

---

# 33. Reference Data vs Operational Data

A useful heuristic:

### Reference data

Often has stable externally defined identifiers.

```text
currency
country
unit_of_measure
language
```

Natural codes can work very well.

### Operational entities

Often have mutable attributes and high fan-out.

```text
customer
order
invoice
inventory_lot
payment
```

Surrogate relational identity is often operationally attractive.

This is a heuristic, not a law.

---

# 34. Keys and Audit History

Consider:

```text
customer.id = 100
email changes
```

An audit record should generally continue to refer to:

```text
customer_id = 100
```

not:

```text
email = previous@example.com
```

because email is an attribute whose value changed.

If business identifiers themselves are significant historical facts, store snapshots explicitly.

Example:

```text
customer_business_identifier_history
-------------------------------------
customer_id
identifier
valid_from
valid_to
```

This separates:

```text
entity identity
```

from:

```text
historical identifier value
```

---

# 35. Soft Deletes and Identity

Suppose:

```text
customer id = 100
```

is soft-deleted.

Can the same natural identifier be reused?

For example:

```text
email = old@example.com
```

Possible business rules:

```text
never reusable
reusable after deletion
reusable within tenant
reusable after retention period
```

This directly affects uniqueness design.

Example:

```sql
CREATE UNIQUE INDEX users_email_active_uniq
ON users (lower(email))
WHERE deleted_at IS NULL;
```

This models:

```text
active users must have unique normalized email
```

rather than pretending the uniqueness rule applies forever.

---

# 36. Case Normalization and Natural Keys

Natural identifiers often have representation rules.

Example:

```text
ABC123
abc123
```

Are these the same business identifier?

If yes, uniqueness must be expressed accordingly.

Possible design:

```sql
CREATE UNIQUE INDEX products_sku_ci_uniq
ON products (lower(sku));
```

But this is only correct if case-insensitivity is actually a business rule.

Do not normalize values merely because an ORM or coding style guide prefers lowercase.

---

# 37. Whitespace and Canonicalization

For natural keys, representations matter.

Should these be equal?

```text
"ABC"
" ABC"
"ABC "
```

You need a defined canonicalization rule.

Potential strategies include:

```text
CHECK
application normalization
stored canonical value
expression-based uniqueness
custom domain logic
```

Be explicit.

Otherwise two representations may produce two supposedly identical business identities.

---

# 38. External Identifiers Should Usually Be Namespaced

Suppose an ERP integrates with multiple marketplaces.

You receive:

```text
external_order_id = 12345
```

Amazon may have order `12345`.

Another provider may also have order `12345`.

Therefore:

```text
(source_system, external_order_id)
```

is often the correct identity scope.

Example:

```sql
UNIQUE (integration_id, external_order_id)
```

A surrogate primary key can then represent your local order identity.

---

# 39. Key Design for Event-Driven Systems

A message may contain several identifiers:

```json
{
  "event_id": "...",
  "aggregate_id": "...",
  "tenant_id": "...",
  "external_id": "..."
}
```

Do not collapse these into one field.

Their roles are different:

```text
event_id
→ identity of this event occurrence/message

aggregate_id
→ identity of business aggregate

tenant_id
→ isolation scope

external_id
→ source-system identity
```

This separation is essential for idempotency and integration correctness.

---

# 40. Idempotency and Natural Keys

Suppose an external payment provider sends:

```text
provider = stripe
provider_payment_id = pi_123
```

You may want:

```sql
UNIQUE (provider, provider_payment_id)
```

This is not necessarily your row primary key.

It is an **idempotency/integration uniqueness constraint**.

You can then safely use:

```text
payment.id
```

as local identity.

This is a recurring architecture pattern:

```text
Local surrogate identity
+
External natural uniqueness
```

---

# 41. Keys and ORMs

ORMs often encourage:

```text
id
```

because identity mapping is easier.

That convenience should not override domain semantics.

A production schema can absolutely contain:

```text
id
UNIQUE(code)
UNIQUE(email)
UNIQUE(tenant_id, sku)
```

The ORM does not need one identifier to encode every business rule.

Use database constraints for the rules the database must protect.

---

# 42. AI / Vibe-Coding Failure Mode: "Always Use UUID"

Generated advice often says:

> "Use UUID for all primary keys because UUIDs are scalable and secure."

This is incomplete.

Questions it ignores:

- What is the workload?
- Is generation distributed?
- Do you need locality?
- How large are the child tables?
- Is the ID public?
- Is there a separate public identifier?
- What are indexing costs?
- What does the existing ecosystem expect?

Correct reasoning:

```text
Requirements
→ Identity characteristics
→ Generation model
→ Exposure model
→ Storage/index implications
→ Operational trade-offs
→ Decision
```

---

# 43. AI / Vibe-Coding Failure Mode: "Use Email as Primary Key"

Why it looks attractive:

```text
email already identifies the user
```

Why it can fail:

- email can change;
- external providers may change normalization semantics;
- case handling can be tricky;
- privacy concerns can arise;
- FKs become wider than necessary;
- changing an email can become a relational operation.

Better pattern in many systems:

```text
user.id PK
email UNIQUE / appropriately normalized
```

The natural identifier remains enforced without becoming physical identity.

---

# 44. AI / Vibe-Coding Failure Mode: "id Is Enough"

The reverse failure is also common.

Generated schema:

```sql
id bigint PRIMARY KEY
code text
```

with no uniqueness constraint on `code`.

Then the database may contain:

```text
id | code
---|------
1  | SKU-1
2  | SKU-1
```

The ORM can happily operate.

The business cannot.

Surrogate keys solve entity identity, not domain uniqueness.

---

# 45. Key Selection Procedure

Use this sequence during schema design.

## Step 1 — Define the entity grain

What exactly does one row represent?

## Step 2 — List candidate identifiers

What values can uniquely identify the entity today?

## Step 3 — Define namespace

Unique where?

## Step 4 — Test stability

Can the value change during normal lifecycle?

## Step 5 — Test ownership

Who controls the identifier namespace?

## Step 6 — Test width

How expensive is the value when referenced millions of times?

## Step 7 — Test distribution

How will IDs be generated across writers/regions/offline clients?

## Step 8 — Separate roles

Identity, business code, public ID, and external ID may all be different.

## Step 9 — Encode every uniqueness rule

Use `UNIQUE`, composite unique constraints, expression indexes, partial unique indexes, or other appropriate mechanisms.

## Step 10 — Validate lifecycle

Ask what happens on rename, merge, deletion, restoration, migration, and import.

---

# 46. Decision Framework

### Prefer a natural primary key when all of the following are true or substantially true:

```text
stable
small enough
meaningfully canonical
clearly owned
properly scoped
unlikely to change
naturally unique
```

### Prefer a surrogate primary key when one or more of these dominate:

```text
natural identifier is mutable
natural identifier is wide
natural identity is composite
entity has many references
multiple external namespaces exist
identity must outlive business-code changes
distributed generation is required
```

And in many real systems:

```text
surrogate PK
+
natural UNIQUE constraints
+
public ID if needed
+
external-ID uniqueness where needed
```

is the strongest overall design.

# 47. Production Example — Multi-Tenant Jewellery ERP

Consider:

```text
Tenant
Branch
Product
Supplier
PurchaseOrder
Invoice
```

A product SKU may be unique per tenant:

```text
(tenant_id, sku)
```

A branch code may be unique per tenant:

```text
(tenant_id, branch_code)
```

An invoice number may be unique per branch and fiscal year:

```text
(branch_id, fiscal_year, invoice_number)
```

Local relational IDs can remain:

```text
tenant.id
branch.id
product.id
supplier.id
purchase_order.id
invoice.id
```

This gives stable FK identity while preserving precise business uniqueness.

# 48. Production Example — Customer Identity

A robust customer table might look conceptually like:

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id uuid NOT NULL UNIQUE DEFAULT gen_random_uuid(),
    tenant_id bigint NOT NULL,
    customer_number text NOT NULL,
    email text,
    name text NOT NULL,

    UNIQUE (tenant_id, customer_number),
    UNIQUE (tenant_id, public_id)
);
```

Depending on the API and domain, email could additionally have scoped normalized uniqueness.

Each identifier has a different purpose.

---

# 49. Testing Key Design

Do not only test successful inserts.

Test the invariant boundary.

### Natural uniqueness

```text
insert A
insert same natural identifier
→ must fail
```

### Mutable attribute

```text
change email
→ entity ID remains unchanged
```

### Tenant scope

```text
Tenant A: SKU-100
Tenant B: SKU-100
→ allowed if uniqueness is tenant-scoped
```

### Same tenant

```text
Tenant A: SKU-100
Tenant A: SKU-100
→ rejected
```

### External integration

```text
provider X / id 123
provider X / id 123
→ duplicate rejected

provider X / id 123
provider Y / id 123
→ allowed if namespace is provider-scoped
```

---

# 50. Concurrency Test: Why Application Checks Are Insufficient

Bad pattern:

```text
SELECT 1
WHERE tenant_id = 10
  AND sku = 'SKU-1';

-- no row

INSERT ...;
```

Two transactions can both observe absence.

```text
T1: check → absent
T2: check → absent
T1: insert
T2: insert
```

Without database uniqueness, duplicates can occur.

Correct:

```sql
UNIQUE (tenant_id, sku)
```

and handle the possible uniqueness violation.

# 51. Key Changes and Migrations

Changing a primary key is high-impact.

Why?

Because it may touch:

```text
foreign keys
indexes
application code
APIs
caches
events
ETL jobs
reports
external integrations
audit references
```

A key migration should therefore be treated as an architectural migration, not a simple column edit.

Typical strategy:

```text
Add new identifier
→ backfill
→ dual-reference if necessary
→ migrate writers
→ migrate readers
→ validate
→ switch source of truth
→ remove old dependency later
```

---

# 52. Stable Identity During Entity Merges

Suppose two customer records are merged:

```text
customer 101
customer 208
```

One becomes canonical:

```text
canonical_customer_id = 101
```

Historical references to 208 may need a mapping:

```text
customer_merge_map
------------------
old_customer_id
canonical_customer_id
merged_at
```

This is easier when internal identities are stable and business identifiers can be redirected independently.

---

# 53. Key Reuse Is a Lifecycle Decision

Should an identifier ever be reused after deletion?

For internal surrogate IDs, reuse is generally unnecessary and can create historical ambiguity.

For business identifiers, reuse may or may not be allowed.

Examples:

```text
customer_number
invoice_number
username
SKU
employee_code
```

Never assume:

```text
"deleted" = "identifier becomes available"
```

The correct answer belongs to business lifecycle semantics.

# 54. Anti-Pattern Catalog

## Anti-pattern 1 — Mutable natural primary key

```text
email as PK
```

### Failure

Identity is coupled to mutable state.

### Better

```text
surrogate PK
+
email UNIQUE
```

---

## Anti-pattern 2 — Surrogate key without business uniqueness

### Failure

Duplicates become legal.

### Better

Encode the candidate key explicitly.

---

## Anti-pattern 3 — Global uniqueness where scope is local

### Failure

Valid tenant-local identifiers are rejected.

### Better

Use scoped uniqueness.

---

## Anti-pattern 4 — Local uniqueness where business requires global uniqueness

### Failure

Collisions appear across partitions/tenants/integrations.

### Better

Define and encode global namespace requirements.

---

## Anti-pattern 5 — Using ID order as business chronology

### Failure

Allocation order ≠ commit/business time.

### Better

Use explicit timestamps or sequence semantics.

---

## Anti-pattern 6 — UUID because "security"

### Failure

Authorization remains missing.

### Better

Treat opaque IDs as defense in depth only.

# 55. Performance Reasoning

Key choice influences performance through:

```text
width
locality
comparison cost
index depth
cache density
FK index size
join cost
WAL volume
replication volume
```

For enormous child tables, compact keys can matter materially.

But storage cost is only one dimension.

A slightly wider key may be worthwhile if it eliminates global coordination or enables safe distributed creation.

Measure the actual workload.

# 56. Observability for Identifier Problems

Useful telemetry includes:

```text
unique constraint violations
FK violations
duplicate integration identifiers
ID allocation failures
sequence exhaustion risk
invalid public-ID requests
cross-tenant lookup attempts
migration mismatch counts
```

Metrics can reveal design problems before users do.

For example:

```text

```

may indicate:

- duplicate webhook delivery;
- retry behavior;
- broken idempotency;
- unexpected provider semantics.

Constraint failures can therefore be valuable signals, not merely errors.

# 58. Expert Reasoning Exercise

Suppose you have:

```text
users
-----
id
email
employee_number
```

Business says:

1. email can change;
2. employee number changes only during rare organizational events;
3. employee number is unique within a tenant;
4. API clients should not receive sequential internal IDs;
5. imported HR records contain `(source_system, source_employee_id)`.

A strong design might be:

```text
id
→ internal surrogate identity

public_id
→ API identifier

(tenant_id, employee_number)
→ business uniqueness

(source_system, source_employee_id)
→ integration uniqueness

email
→ mutable alternate attribute
```

Notice that one entity can legitimately have several identifiers with different contracts.

# 63. Final Mental Model

Think of keys as layers:

```text
┌──────────────────────────────────────┐
│ Business identity                    │
│ "What does the domain call this?"    │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│ Namespace / uniqueness               │
│ "Unique where and under what rules?" │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│ Relational identity                  │
│ "Which row/entity is this?"          │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│ External/public identity             │
│ "How should other systems refer?"    │
└──────────────────────────────────────┘
```

The layers may use the same value.

They do not have to.

And in production systems, separating them is often what allows the system to survive:

```text
business change
+
scale
+
multiple integrations
+
security requirements
+
migrations
+
long-lived history
```

# 64. Final Principle

> **A primary key should represent stable relational identity; business identifiers should represent business uniqueness; public identifiers should represent external access semantics; and external identifiers should represent another system's namespace. Treating these as separate contracts produces schemas that remain correct when the business changes.**
