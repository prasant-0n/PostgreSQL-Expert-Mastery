# 02.14 — Data Lifecycle

> **Phase 02 — Relational Data Modeling**  
> **Chapter:** 02.14  
> **Focus:** Designing data from creation to active use, correction, retention, archival, deletion, and eventual proof of disposition.

---

## 1. Objective

A production database does not merely store data. It governs a data object's entire useful life.

A row usually passes through a sequence such as:

```text
Created
   ↓
Validated
   ↓
Active / Operational
   ↓
Updated / Superseded
   ↓
Inactive / Closed
   ↓
Retained for business, legal, or audit reasons
   ↓
Archived / Cold storage
   ↓
Deletion eligible
   ↓
Deleted / Anonymized / Destroyed
   ↓
Disposition evidenced
```

The purpose of this chapter is to make that lifecycle explicit and enforceable.

A weak design thinks:

> "We have a table and someday we can delete old rows."

A production design asks:

- Why is the data collected?
- What makes it active?
- What makes it immutable?
- What makes it obsolete?
- What is the retention rule?
- Who can override the normal lifecycle?
- What must never be deleted?
- What may be archived?
- What dependencies prevent deletion?
- What happens to references, audit records, caches, search indexes, files, and events?
- How do we prove that lifecycle automation did what it was supposed to do?

---

## 2. Definitions

### 2.1 Simple definition

A **data lifecycle** is the planned sequence of states and actions a piece of data experiences from creation until deletion, anonymization, archival, or permanent retention.

### 2.2 Engineering definition

A data lifecycle is a set of explicit state transitions, retention rules, ownership rules, dependency rules, operational processes, and observability controls governing data throughout its existence.

### 2.3 Expert definition

Data lifecycle architecture is the design of **state + time + policy + dependency + evidence** such that every class of data has a predictable and auditable answer to:

> What is this data allowed to do, how long must it exist, when does it stop being operationally active, and what conditions permit or prohibit its final disposition?

---

## 3. First Principles

### Principle 1 — Data has a purpose, therefore data needs a lifecycle boundary

A row should exist because some business or technical purpose requires it.

When that purpose ends, the system should know what happens next.

### Principle 2 — Retention is not the same as availability

Data can be retained while being removed from hot operational paths.

For example:

```text
Operational database
    ↓
recent invoices

Archive
    ↓
older invoices

Disposition store / evidence
    ↓
records proving archival or destruction
```

Retention answers **whether data must still exist**.

Availability answers **where and how quickly it must be accessible**.

These are different design dimensions.

### Principle 3 — Deletion is a business operation, not merely a SQL statement

`DELETE FROM ...` answers how to remove rows.

It does not answer:

- whether the row is eligible for deletion;
- whether dependent data can be removed;
- whether legal or audit retention applies;
- whether an external copy remains;
- whether deletion must be approved;
- whether a tombstone is required;
- whether caches and indexes need invalidation;
- whether the deletion itself must be audited.

### Principle 4 — Lifecycle rules must be deterministic

A rule such as:

> "Delete old records periodically."

is operationally weak.

Prefer:

```text
A record becomes deletion-eligible when:

closed_at < retention_boundary
AND legal_hold = false
AND outstanding_dependency_count = 0
AND financial_period_locked = true
```

The actual rule may be more complex, but it must be explicit.

### Principle 5 — Different data classes need different lifecycles

A customer session, product catalog row, invoice, payment ledger entry, audit record, uploaded document, and search index entry should not automatically share one lifecycle policy.

Lifecycle design starts with **data classification**.

# 4. Mental Model

Think of lifecycle management as a controlled state machine over time.

```text
                  ┌──────────────┐
                  │    CREATED   │
                  └──────┬───────┘
                         │ validate
                         ↓
                  ┌──────────────┐
          ┌──────→│    ACTIVE    │←──────┐
          │       └──────┬───────┘       │
          │              │ close         │ restore
          │              ↓               │
          │       ┌──────────────┐       │
          │       │    CLOSED    │───────┘
          │       └──────┬───────┘
          │              │ retention threshold
          │              ↓
          │       ┌──────────────┐
          │       │   ARCHIVED   │
          │       └──────┬───────┘
          │              │ disposition eligible
          │              ↓
          │       ┌──────────────┐
          └───────│  DISPOSED    │
                  └──────────────┘
```

Important distinction:

**State is not the same as age.**

A row can be 10 years old and still be active.

A row can be 1 day old and already be closed.

A timestamp provides evidence about time. A state provides business meaning.

Good lifecycle designs usually need both.

# 5. Data Classification Before Lifecycle Design

Do not design retention globally before identifying the data classes.

A useful classification table is:

| Data class | Typical examples | Operational need | Historical need | Typical lifecycle concern |
|---|---|---:|---:|---|
| Master data | products, branches | High | High | change history |
| Transactional data | sales, purchases | High | Very high | immutability / closure |
| Financial data | payments, ledger | High | Very high | retention / legal controls |
| Audit data | row history | Low to medium | Critical | tamper resistance |
| Sessions | login/session tokens | High briefly | Low | aggressive expiry |
| Temporary data | staging/import rows | Short | Low | cleanup |
| Derived data | caches, projections | Variable | Usually rebuildable | regeneration |
| Attachments | invoices, certificates | Variable | High | storage lifecycle |
| Analytics data | event streams | Variable | Variable | aggregation / cold storage |

A single `deleted_at` column does not solve the lifecycle problem for all of these classes.

# 7. Lifecycle Modeling Patterns

## 7.1 Status column

```sql
CREATE TYPE order_status AS ENUM (
    'draft',
    'confirmed',
    'completed',
    'cancelled'
);

CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status order_status NOT NULL DEFAULT 'draft',
    created_at timestamptz NOT NULL DEFAULT now(),
    completed_at timestamptz,
    cancelled_at timestamptz
);
```

This captures business state.

It does not automatically capture state history.

## 7.2 Timestamps + status

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    closed_at timestamptz
);

ALTER TABLE orders
ADD CONSTRAINT orders_closed_at_consistency
CHECK (
    (status IN ('completed', 'cancelled') AND closed_at IS NOT NULL)
    OR
    (status NOT IN ('completed', 'cancelled') AND closed_at IS NULL)
);
```

This creates an invariant between state and lifecycle time.

## 7.3 Explicit lifecycle fields

Useful when lifecycle has more than one independent dimension:

```text
status
retention_until
legal_hold
archived_at
purged_at
```

Do not create lifecycle fields merely because they sound useful. Every field should represent a meaningful invariant.

# 8. Soft Delete

Soft deletion commonly looks like:

```sql
deleted_at timestamptz
```

or:

```text
is_deleted boolean
```

### 8.1 Why teams use it

Soft deletion can support:

- accidental-delete recovery;
- user-facing restore workflows;
- historical references;
- asynchronous cleanup;
- audit requirements.

### 8.2 Why it becomes dangerous

Soft delete creates a second logical universe:

```text
alive rows
+
deleted-but-still-present rows
```

Every query must decide which universe it means.

This can cause:

- forgotten predicates;
- incorrect counts;
- uniqueness conflicts;
- larger indexes;
- larger table size;
- longer vacuum work;
- hidden data exposure.

### 8.3 Better uniqueness design

Suppose only active usernames must be unique:

```sql
CREATE UNIQUE INDEX users_active_username_uq
ON users (lower(username))
WHERE deleted_at IS NULL;
```

This turns the business rule into a database-enforced invariant.

### 8.4 Soft delete is not retention

A row with:

```text
deleted_at = yesterday
```

may still exist for years.

Therefore:

```text
soft deleted ≠ physically disposed
```

---

# 9. Hard Delete

Physical deletion is appropriate when the row has no continuing required value and all constraints and policies permit removal.

```sql
DELETE FROM temporary_import_rows
WHERE created_at < now() - interval '7 days';
```

But a production process should first establish eligibility.

Conceptually:

```text
SELECT candidates
        ↓
validate eligibility
        ↓
claim batch
        ↓
delete
        ↓
record outcome
        ↓
reconcile
```

Do not treat a large production purge as one enormous transaction unless workload characteristics explicitly support it.

---

# 10. Retention Policy Design

A retention policy should answer:

```text
WHAT data?
WHY retain it?
FOR HOW LONG?
FROM WHICH EVENT?
UNDER WHICH EXCEPTIONS?
WHO owns the policy?
WHAT happens after the period?
HOW is compliance evidenced?
```

## 10.1 Retention anchor

A common mistake is defining retention from `created_at` for every data class.

Possible anchors include:

```text
created_at
closed_at
completed_at
last_activity_at
contract_end_at
fiscal_period_end
case_resolution_at
```

For transactions, retention often makes more business sense from **completion/closure**, not creation.

---

# 11. Retention as a Derived Rule

Prefer deriving eligibility rather than storing a duplicated boolean such as:

```text
is_ready_for_deletion
```

unless there is a measured operational reason to materialize it.

Example:

```sql
SELECT id
FROM orders
WHERE status = 'completed'
  AND completed_at < now() - interval '7 years'
  AND legal_hold = false;
```

A derived predicate is easier to reason about than a flag that can become stale.

When performance requires materialization, define the source of truth and reconciliation process explicitly.

---

# 12. Legal Hold / Retention Hold

A deletion pipeline must be able to stop deletion when a hold applies.

```sql
CREATE TABLE customer_records (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status text NOT NULL,
    closed_at timestamptz,
    retention_until timestamptz,
    legal_hold boolean NOT NULL DEFAULT false
);
```

Deletion eligibility might require:

```text
retention_until <= current_time
AND legal_hold = false
```

### Expert consideration

A boolean hold can be insufficient when multiple independent holds can coexist.

A separate relation may be better:

```sql
CREATE TABLE data_holds (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    entity_type text NOT NULL,
    entity_id bigint NOT NULL,
    reason text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    released_at timestamptz
);
```

The important invariant becomes:

> A record cannot be disposed while any active hold exists.

---

# 13. Lifecycle and Foreign Keys

Referential integrity and lifecycle policy interact.

Suppose:

```text
customers
   ↓
orders
   ↓
order_items
```

Deleting the customer may not be permissible merely because the customer account is inactive.

Possible business rule:

```text
customer can become inactive
BUT
orders remain retained
AND
customer identity is preserved in historical records
```

This is why `ON DELETE CASCADE` should not be selected merely because it makes cleanup easy.

Cascade behavior is a relational action. Retention policy is a business/data-governance decision.

---

# 14. Lifecycle and Historical Truth

Some data becomes historical truth.

Examples:

- invoice totals;
- payment records;
- inventory movements;
- ledger entries;
- tax documents;
- audit evidence.

For these classes, lifecycle usually means:

```text
mutable during preparation
        ↓
controlled finalization
        ↓
immutable or append-only historical state
        ↓
retention
        ↓
archive
```

Do not use physical deletion as a normal correction mechanism for finalized financial history.

Correction should normally happen through domain-specific compensating or reversal records.

This chapter establishes the lifecycle principle; detailed ledger modeling is covered in `02.18`.

---

# 15. Active vs Inactive Data

A row does not necessarily need to be deleted when it stops being operationally active.

Examples:

```text
active product
inactive product
retired product
```

A retired product may still be referenced by historical transactions.

Therefore:

```text
operational availability
≠
existence in the database
```

This distinction prevents destructive designs that break history.

---

# 16. Archive vs Delete

Archival is appropriate when data still has value but does not belong in the hottest operational path.

Possible archive targets:

```text
same PostgreSQL cluster, separate table
separate PostgreSQL database
object storage
data warehouse
cold analytical store
compressed export format
```

### Decision dimensions

| Dimension | Hot operational | Warm archive | Cold archive |
|---|---|---|---|
| Access frequency | High | Medium | Low |
| Query latency | Low | Moderate | High |
| Cost | Higher | Lower | Lower |
| Write workload | Ongoing | Usually low | Usually append-only |
| Operational coupling | High | Medium | Low |
| Restoration complexity | Low | Medium | Higher |

Archival is successful only when retrieval requirements are also defined.

# 17. PostgreSQL Partitioning for Lifecycle Management

Partitioning can align physical storage with lifecycle boundaries.

For example:

```sql
CREATE TABLE audit_events (
    id bigint GENERATED ALWAYS AS IDENTITY,
    occurred_at timestamptz NOT NULL,
    payload jsonb NOT NULL
) PARTITION BY RANGE (occurred_at);
```

Monthly partitions can allow an operational process such as:

```text
recent partitions → hot
older partitions  → archive candidates
expired partitions → detach/drop
```

PostgreSQL documents partitioning as physically splitting one logical table into smaller pieces and specifically identifies fast removal of old data by dropping or detaching partitions as a major lifecycle benefit. citeturn982509search0turn982509search5

### Why this matters

A massive:

```sql
DELETE FROM audit_events
WHERE occurred_at < ...;
```

creates row-level work and subsequent cleanup pressure.

When the lifecycle policy aligns naturally with partition boundaries, removing an entire partition can avoid much of that bulk-delete overhead. PostgreSQL's current documentation explicitly notes that partition removal can avoid the `VACUUM` overhead associated with large bulk deletes. citeturn982509search0

### But partitioning is not automatically better

Too many partitions can increase planning and memory overhead. PostgreSQL recommends careful consideration of partition count and the relationship between partitioning, query patterns, and future growth. citeturn982509search0

---

# 18. Lifecycle-Aligned Partitioning

A strong partitioning key often comes from the lifecycle itself.

Example:

```text
orders
  2026-01
  2026-02
  2026-03
  ...
```

This can support:

- retention windows;
- month-end archival;
- fiscal-period boundaries;
- operational partition pruning;
- predictable maintenance.

However, the partition key must also fit query patterns and uniqueness/foreign-key requirements. Partitioning is a workload and lifecycle design decision, not merely a storage trick. PostgreSQL's documentation emphasizes choosing partition keys carefully and considering both query predicates and removal of unwanted data. citeturn982509search0

# 19. Archive Pipelines

A production archive pipeline should be stateful and observable.

Conceptual pipeline:

```text
Identify eligible rows
        ↓
Freeze eligibility snapshot
        ↓
Export / copy
        ↓
Validate archive completeness
        ↓
Record archive manifest
        ↓
Verify retrieval path
        ↓
Remove from hot store
        ↓
Reconcile counts / checksums / identities
```

The dangerous implementation is:

```text
COPY
DELETE
```

without evidence that the copy completed correctly.

---

# 20. Archive Manifest

An archive manifest can establish an operational chain of custody.

Example:

```sql
CREATE TABLE archive_batches (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    entity_type text NOT NULL,
    started_at timestamptz NOT NULL DEFAULT now(),
    completed_at timestamptz,
    source_count bigint,
    archived_count bigint,
    checksum text,
    storage_location text NOT NULL,
    status text NOT NULL
);
```

This is especially useful when archival happens outside PostgreSQL.

# 21. Batch Purging

Large deletes should normally be treated as a workload-management problem.

A conceptual pattern is:

```sql
DELETE FROM sessions
WHERE id IN (
    SELECT id
    FROM sessions
    WHERE expires_at < now()
    ORDER BY id
    LIMIT 5000
);
```

Repeat until no eligible rows remain.

The exact strategy depends on:

- indexes;
- concurrent writers;
- foreign keys;
- lock duration;
- WAL volume;
- replication lag;
- autovacuum behavior;
- partition layout.

### Why batching helps

Smaller transactions can reduce:

- transaction duration;
- lock duration;
- peak WAL bursts;
- rollback size;
- blast radius of failure.

But batching introduces its own concerns:

- more round trips;
- partial progress;
- retry logic;
- job state management.

Therefore the purge process itself becomes an operational state machine.

---

# 22. Idempotent Lifecycle Jobs

A lifecycle worker can fail after processing some rows but before recording success.

Therefore jobs should be designed so that rerunning them is safe.

Bad assumption:

```text
job runs exactly once
```

Production assumption:

```text
job may run again
```

Example job states:

```text
PENDING
RUNNING
SUCCEEDED
PARTIAL
FAILED
```

And each batch should have a deterministic identity or claim mechanism.

---

# 23. Concurrency and Lifecycle Races

Suppose a cleanup job decides a record is eligible:

```text
T1 cleanup:
    record is closed
    retention expired
```

Meanwhile another transaction changes the record:

```text
T2:
    legal hold added
```

Now the cleanup decision is stale.

This is why lifecycle eligibility must be evaluated with an appropriate transaction/isolation strategy and revalidated where necessary.

Do not assume:

```text
SELECT eligible
DELETE later
```

is equivalent to an atomic lifecycle decision.

---

# 24. Claiming Rows for Lifecycle Workers

For concurrent workers, row claiming can use PostgreSQL locking patterns such as:

```sql
SELECT id
FROM cleanup_candidates
WHERE eligible_at <= now()
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1000;
```

This can support multiple workers while allowing already-locked rows to be skipped.

The exact design must account for transaction duration and whether the claimed state is persisted before processing.

---

# 25. Lifecycle State Machine vs Boolean Flags

Avoid designs like:

```text
is_active
is_deleted
is_archived
is_locked
is_completed
```

without a clear state model.

These booleans can create impossible combinations:

```text
is_active = true
is_deleted = true
is_archived = true
```

A single explicit state can sometimes provide a stronger invariant:

```text
ACTIVE
ARCHIVED
PURGED
```

But independent dimensions may legitimately require separate fields.

The expert question is not:

> "Should I use enum or booleans?"

It is:

> "Which states are mutually exclusive, and which lifecycle dimensions are independent?"

# 26. Lifecycle State History

A current status does not explain how a record got there.

For important entities, model transition history:

```sql
CREATE TABLE order_status_history (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL REFERENCES orders(id),
    from_status text,
    to_status text NOT NULL,
    changed_at timestamptz NOT NULL DEFAULT now(),
    actor_id bigint,
    reason text
);
```

This allows questions such as:

```text
When was it closed?
Who closed it?
What was it before closure?
Why did it change?
```

Audit architecture is covered in `02.12`; this chapter focuses on lifecycle semantics.

# 27. Data Lifecycle and Derived Data

Derived data generally has a different lifecycle from source-of-truth data.

Example:

```text
orders → source of truth
    ↓
search index
    ↓
cache
    ↓
analytics projection
```

When an order is archived or deleted:

- the source record follows its retention policy;
- the search projection may be removed;
- the cache should expire;
- analytics may retain aggregated information.

Therefore lifecycle propagation across derived stores must be explicit.

---

# 28. Data Lifecycle and Event Streams

Deleting a source row does not delete the events emitted because of that row.

Possible states:

```text
source row deleted
but
retained event exists
```

The architecture must decide whether downstream systems are allowed to retain that information and whether erasure/anonymization events must propagate.

The key lesson:

> A data lifecycle is distributed across every materialized copy of the data.

---

# 29. PII and Lifecycle Separation

Personally identifiable information often requires a more explicit lifecycle than ordinary operational records.

Consider separating:

```text
business transaction identity
        ↓
customer reference
        ↓
PII profile
```

This can allow privacy-sensitive fields to be anonymized while the business transaction remains historically meaningful.

Example:

```text
customer.name → anonymized
customer.email → removed
invoice.customer_id → retained
invoice.total → retained
```

Whether this is appropriate depends on legal, regulatory, contractual, and business requirements. The architecture should never assume that anonymization is automatically equivalent to deletion.

---

# 30. Anonymization vs Deletion

These are distinct outcomes.

### Deletion

The information is removed from the target system.

### Anonymization

Identifying information is transformed so that the original identity should no longer be usable under the relevant policy definition.

### Pseudonymization

Identifiers are replaced but linkage may still be possible.

For example:

```text
real customer ID
      ↓
pseudonymous token
```

This can still be personal data depending on the surrounding information and applicable rules.

Do not call a hash operation "deletion" without understanding reversibility, joinability, auxiliary data, and the governing policy.

---

# 31. Lifecycle of Uploaded Files

Database rows are not the only data.

Suppose an invoice row points to:

```text
s3://bucket/invoices/2026/INV-123.pdf
```

Deleting the row but retaining the object creates an orphaned copy.

A complete lifecycle must include:

```text
database row
object storage object
CDN/cache
search index
backup copy
replica
export
analytics copy
```

The design must specify which systems are authoritative and how disposition propagates.

---

# 32. Backups Change the Meaning of Deletion

A production system may have:

```text
primary database
read replica
backup snapshots
WAL archives
analytics copies
exports
application caches
```

Removing a row from the primary database does not immediately mean that no historical copy exists elsewhere.

Therefore lifecycle documentation should distinguish:

```text
removed from operational store
vs
removed from all managed copies
```

Exact deletion guarantees depend on the organization's backup architecture and policy.

---

# 33. Disaster Recovery vs Retention

Backups exist to recover from operational failure.

Retention policies determine how long data should remain available.

These goals can conflict.

Example:

```text
business retention = 30 days
backup snapshot retention = 90 days
```

A record deleted on day 31 may still appear in a day-60 backup.

That does not automatically mean the lifecycle design is wrong. It means the organization must explicitly define how backup retention interacts with deletion and restoration obligations.

---

# 34. Restore Semantics

An expert lifecycle design answers:

> What happens if an archived or deleted record is restored from backup?

Possible behavior:

```text
restore exactly
restore but remain inactive
restore only into recovery environment
restore as a new record
reject restore after disposition
```

Restore must not silently violate current retention or legal policy.

---

# 35. Schema Design for Lifecycle Metadata

A common production pattern:

```sql
CREATE TABLE documents (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    closed_at timestamptz,
    retention_until timestamptz,
    archived_at timestamptz,
    purged_at timestamptz,
    CHECK (closed_at IS NULL OR closed_at >= created_at),
    CHECK (archived_at IS NULL OR closed_at IS NOT NULL),
    CHECK (purged_at IS NULL OR archived_at IS NOT NULL)
);
```

This is not universally correct. It demonstrates a principle:

> Encode lifecycle dependencies as constraints when they are local, deterministic invariants.

# 36. Naive Approach → Why It Fails → Improved Approach

## Naive Approach

```text
Every table gets:
    deleted_at
```

## Why It Fails

It ignores:

- legal holds;
- archive state;
- business closure;
- dependencies;
- object storage;
- derived copies;
- audit evidence;
- retention anchors.

## Improved Approach

Classify data and model the lifecycle dimensions that actually matter.

```text
state
+ timestamps
+ retention rule
+ holds
+ dependency checks
+ transition evidence
+ disposition workflow
```

## Why It Works

The lifecycle becomes explicit and testable.

## Production Considerations

Monitor:

- eligible-row backlog;
- failed archive batches;
- purge latency;
- orphaned external objects;
- lifecycle exceptions;
- records stuck in transitional states.

## Alternative

For very simple data, `expires_at` plus periodic deletion may be sufficient.

## Trade-Off

More explicit lifecycle models cost schema and operational complexity but reduce ambiguity and accidental data loss.

# 37. PostgreSQL Lifecycle Queries

## 37.1 Find stale active records

```sql
SELECT id, last_activity_at
FROM sessions
WHERE status = 'active'
  AND last_activity_at < now() - interval '30 days';
```

## 37.2 Find archive candidates

```sql
SELECT id
FROM orders
WHERE status = 'completed'
  AND completed_at < now() - interval '2 years';
```

## 37.3 Find held records

```sql
SELECT o.id
FROM orders o
WHERE o.completed_at < now() - interval '7 years'
  AND EXISTS (
      SELECT 1
      FROM data_holds h
      WHERE h.entity_type = 'order'
        AND h.entity_id = o.id
        AND h.released_at IS NULL
  );
```

## 37.4 Find lifecycle anomalies

```sql
SELECT id
FROM documents
WHERE purged_at IS NOT NULL
  AND archived_at IS NULL;
```

Queries like these are valuable as **health checks**, not just one-time diagnostics.

# 38. Lifecycle Integrity Checks

Production systems should periodically verify invariants.

Examples:

```text
purged_at implies archived_at
closed_at implies terminal business state
active records should not have purge timestamps
archived objects must have archive manifests
no active legal hold may coexist with disposal
all external objects should map to an owned record
```

These checks catch lifecycle drift.

# 39. Observability

Lifecycle operations need operational metrics.

Useful metrics include:


A lifecycle system without observability can silently fail for months.

# 40. Security

Lifecycle mechanisms are high-impact operations.

A purge worker effectively has destructive authority.

Use least privilege.

Consider separating:

```text
read eligibility
archive data
approve deletion
execute deletion
```

where risk requires it.

Lifecycle workers should not automatically have broad database ownership.

Also protect lifecycle metadata itself because retention bypasses and deletion controls can become security vulnerabilities.

---

# 41. Failure Handling

Consider the failure matrix:

| Step | Possible failure | Required response |
|---|---|---|
| Select | query timeout | retry |
| Claim | worker crash | release/reclaim safely |
| Archive | partial transfer | resumable or restartable transfer |
| Verify | mismatch | do not purge |
| Purge | transaction failure | rollback / retry |
| Record manifest | failure after purge | reconcile urgently |
| External delete | permission failure | quarantine / retry |

The key invariant is:

> Never destroy source data merely because the previous step was attempted.

Destroy only after the required preconditions are verified.

---

# 42. Lifecycle and Transactions

An ideal transaction boundary is often:

```text
claim batch
+
transition lifecycle metadata
+
perform tightly coupled database work
```

Do not hold a PostgreSQL transaction open while waiting on a slow external network transfer unless the workload and consistency requirements explicitly justify it.

Long transactions can increase:

- lock duration;
- old-row retention;
- vacuum pressure;
- replication lag;
- failure blast radius.

A better architecture often separates:

```text
DB eligibility / claim
        ↓
external work
        ↓
verification
        ↓
DB finalization
```

with explicit intermediate states.

---

# 43. Lifecycle Policy Versioning

Policies change.

For example:

```text
2026 policy: retain 7 years
2028 policy: retain 10 years
```

If the database stores only current policy configuration, historical reasoning can become difficult.

For high-assurance systems, consider recording the policy version used when making a lifecycle decision.

Example:

```text
policy_version = 2026-07-finance-retention-v3
```

This improves auditability and reproducibility.

---

# 44. Lifecycle and Multi-Tenancy

In a multi-tenant system, retention can vary by tenant.

Examples:

```text
tenant A → 3 years
tenant B → 7 years
tenant C → regulatory hold
```

The policy resolution must remain tenant-isolated.

Never allow a tenant-controlled value to override a globally required retention floor without authorization and policy validation.

Lifecycle queries must also be tenant-safe.

A cleanup job that accidentally processes another tenant is a catastrophic isolation failure, not merely a cleanup bug.

# 45. Jewellery ERP Example

Consider a multi-branch jewellery ERP.

Data classes might include:

```text
products
customers
sales invoices
purchase invoices
stock movements
payments
ledger entries
user sessions
audit records
uploaded certificates
```

A sensible lifecycle might be:

```text
product
  ACTIVE → RETIRED

invoice
  DRAFT → FINALIZED → CLOSED → ARCHIVE ELIGIBLE

session
  ACTIVE → EXPIRED → PURGE ELIGIBLE

stock movement
  APPEND-ONLY → RETAINED → ARCHIVE

ledger entry
  POSTED → IMMUTABLE → RETAINED

audit event
  APPEND-ONLY → RETAINED → ARCHIVE
```

Notice that the lifecycle differs by entity.

A product can be retired without deletion because old invoices still reference it.

A finalized invoice may remain queryable for years.

A session can disappear quickly.

A ledger entry should not be casually deleted merely because it is old.

This is exactly why lifecycle is a modeling concern.

# 46. ORM / Node.js / NestJS Considerations

A Node/NestJS application often exposes lifecycle actions such as:

```text
archiveOrder()
restoreOrder()
purgeExpiredSessions()
releaseHold()
```

The application service should express the business operation, but database invariants should remain protected in PostgreSQL wherever practical.

Avoid relying solely on application code for rules such as:

```text
purged_at cannot be set unless archived_at exists
```

A malicious or buggy alternate code path could bypass the service.

Use the database as the final integrity boundary.

For destructive operations:

- make commands idempotent;
- use transactions around tightly coupled state transitions;
- map constraint errors intentionally;
- make retries safe;
- record job/batch identity;
- avoid unbounded deletes.

# 47. AI / Vibe-Coding Failure Modes

## Failure 1 — `deleted_at` everywhere

AI generates a universal soft-delete pattern without understanding entity semantics.

**Why wrong:** lifecycle is domain-specific.

## Failure 2 — `ON DELETE CASCADE` everywhere

**Why wrong:** relational convenience can destroy retained business history.

## Failure 3 — delete by `created_at`

**Why wrong:** retention usually has a business anchor.

## Failure 4 — purge without legal-hold checks

**Why wrong:** destructive automation ignores policy exceptions.

## Failure 5 — archive then immediately delete

**Why wrong:** successful initiation is not successful verification.

## Failure 6 — massive one-shot delete

**Why wrong:** operational impact may include long transactions, WAL bursts, locks, and vacuum pressure.

## Failure 7 — lifecycle only in cron

```text
cron → delete
```

without persisted job state.

**Why wrong:** failure and replay become difficult to reason about.

## Failure 8 — backup copies ignored

**Why wrong:** deletion from primary storage does not necessarily eliminate backup copies.

## Failure 9 — no restore semantics

**Why wrong:** recovery can reintroduce data that was supposed to be disposed or held.

## Failure 10 — stale materialized flags

```text
is_ready_for_deletion = true
```

without reconciliation.

**Why wrong:** policy inputs may change after the flag was computed.

# 48. Performance Considerations

Lifecycle management becomes a performance problem when tables become large.

Watch:

```text
eligible-row scan cost
index selectivity
partition pruning
DELETE throughput
WAL generation
replication lag
vacuum backlog
bloat
lock contention
job overlap
```

For large datasets, indexes on lifecycle predicates can be useful, but should be justified by workload.

Example:

```sql
CREATE INDEX orders_archive_candidates_idx
ON orders (completed_at)
WHERE status = 'completed';
```

A partial index may make candidate discovery cheaper while avoiding entries for unrelated states.

Measure before adding lifecycle-specific indexes.

---

# 49. EXPLAIN and Evidence-Driven Tuning

Do not assume the cleanup query is cheap.

Inspect it:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM orders
WHERE status = 'completed'
  AND completed_at < now() - interval '2 years';
```

Questions:

```text
Is the predicate indexable?
How many rows are estimated?
How many are actually scanned?
Is the planner choosing a sequential scan?
Is that choice reasonable?
Does partition pruning occur?
```

For lifecycle architecture, the correct optimization is often changing the physical data lifecycle—not merely adding another index.

# 50. Testing Strategy

Lifecycle tests should cover both normal transitions and adversarial conditions.

## Unit / domain tests

```text
ACTIVE → CLOSED allowed
CLOSED → ACTIVE forbidden unless explicitly supported
PURGED → ACTIVE forbidden
```

## Database tests

Verify constraints.

## Integration tests

Run archive and purge workflows against real PostgreSQL.

## Concurrency tests

Run multiple cleanup workers simultaneously.

## Failure-injection tests

Simulate:

```text
archive success / verification failure
worker crash
DB failure after external copy
partial batch
retry
network interruption
hold added mid-workflow
```

## Recovery tests

Verify restore behavior and reconciliation.

## Retention tests

Use controlled timestamps to verify boundary conditions exactly.

# 51. Boundary Conditions

Time-based lifecycle rules fail frequently at boundaries.

Consider:

```text
retention_until = 2026-09-14 20:00:00
current time      = 2026-09-14 20:00:00
```

Is the row eligible at equality?

Define this explicitly.

Prefer precise predicates such as:

```sql
retention_until <= now()
```

rather than ambiguous application-side comparisons.

Also consider:

- timezone normalization;
- DST transitions;
- clock skew across services;
- timestamp precision;
- transaction time vs wall-clock time.

# 52. Lifecycle and Temporal Modeling

Temporal modeling and lifecycle modeling complement each other.

Temporal data answers:

> When was this true?

Lifecycle answers:

> What state is this data in, and what can happen next?

For example:

```text
invoice status history
        ↓
DRAFT → FINALIZED → CLOSED
                 
retention_until = 2033-12-31
```

The state transition and retention timeline form one coherent lifecycle model.

---

# 53. Lifecycle and Schema Evolution

Lifecycle rules themselves evolve.

A migration can introduce:

```text
archived_at
retention_until
legal_hold
```

but existing rows need deterministic backfill semantics.

Before migration, answer:

```text
What state are historical rows in?
What retention policy applies?
Can old rows already be disposed?
Do we need a one-time archive?
Can the new constraint be validated safely?
```

Do not add a lifecycle constraint blindly to data that predates the lifecycle model.

# 54. Data Lifecycle Runbook

A production runbook should define:

```text

How workers claim batches
How a batch is verified
What makes deletion safe
How failures are retried
How legal holds are respected
How incidents are escalated

```

# 59. Final Engineering Rules

1. **Model lifecycle by data class, not by table-count convention.**
2. **Separate business state from mere age.**
3. **Retention is not deletion.**
4. **Soft delete is not disposition.**
5. **Archive only after defining retrieval and verification semantics.**
6. **Never make destructive automation depend on an unverified previous step.**
7. **Use database constraints for local lifecycle invariants.**
8. **Use bounded, observable, retry-safe cleanup workflows.**
9. **Align partitioning with lifecycle only when workload and scale justify it.**
10. **Treat external copies, backups, projections, and files as part of the lifecycle architecture.**
11. **Make policy exceptions explicit.**
12. **Test the failure path, not just the happy path.**

---

# 60. Central Principle

> **A production data model is incomplete until it defines not only how data is created and queried, but also how data becomes inactive, how long it must remain available, what prevents its disposal, how it is archived, and how the system proves what happened.**

Data lifecycle architecture is the bridge between relational modeling and real operational responsibility.

A mature PostgreSQL engineer does not ask only:

> "How do I store this row?"

They also ask:

> **"What is the entire life of this data, and can the system enforce that life safely?"**
