# 02.11 — Temporal Data

## Chapter Objective

Temporal data models information **about time as part of the data model**, rather than treating timestamps as incidental metadata. A production-quality temporal design answers questions such as:

- What was true at a particular point in time?
- When did an entity become effective?
- When did that fact stop being effective?
- Which version of a business fact applied when an event occurred?
- Can two effective periods overlap when they must not?
- Can a child record be covered by a parent's validity period?
- What is the difference between when something happened, when it became valid, and when the database learned about it?
- How do we preserve history without making ordinary reads unnecessarily complicated?

Temporal modeling is not simply `created_at` + `updated_at`. It is a deliberate representation of **time-dependent business truth**.

> **Central principle:** Model the time semantics of the business explicitly, choose interval boundaries deliberately, enforce temporal invariants in the database where possible, and preserve enough historical information to answer the questions the system actually promises to answer.

---

## 1. What Is Temporal Data?

### 1.1 Simple definition

Temporal data is data whose meaning changes depending on a point or interval of time.

Example:

```text
Product price today      = ₹1200
Product price next month = ₹1300
Product price last month = ₹1100
```

A single `price` column cannot represent all three truths without losing history.

### 1.2 Engineering definition

A temporal model represents one or more business facts together with their applicable time period, so historical and current state can be queried correctly.

### 1.3 Expert definition

Temporal modeling is the explicit representation of **time-varying predicates** and their validity intervals, with defined boundary semantics, conflict rules, historical retention, and query semantics.

Think of a temporal fact as:

```text
Fact = (subject, value, validity interval, optional system metadata)
```

For example:

```text
(customer_id=42,
 credit_limit=500000,
 valid_during=[2026-01-01, 2026-07-01))
```

The value is not universally true. It is true **during an interval**.

---

# 2. Temporal Dimensions You Must Distinguish

The first major design mistake is using the word "time" as though it represented one thing.

Production systems often need several temporal dimensions.

## 2.1 Event time

The time when something actually happened in the business domain.

Example:

```text
invoice issued at 2026-09-14 10:30:00+05:30
```

## 2.2 Valid time

The period during which a business fact is considered true.

Example:

```text
Employee salary = ₹80,000
valid from 2026-07-01 until 2026-12-31
```

## 2.3 Transaction/system time

The period during which the database knew or stored that fact.

Suppose a salary became effective on July 1, but HR entered it on July 5.

```text
Business valid time:  Jul 1 → Dec 31
System knowledge:    Jul 5 → now
```

Those are different facts.

## 2.4 Processing time

The time an application or pipeline processed an event.

This becomes important in:

- event ingestion
- data warehouses
- streaming systems
- ETL
- reconciliation pipelines

## 2.5 Why this distinction matters

Consider a jewellery ERP where a purchase rate was effective from Monday, but someone corrected the record on Wednesday.

Question:

> What price was valid on Tuesday?

That is a **valid-time** question.

Question:

> When did the ERP first know that price?

That is a **system-time** question.

Question:

> When did the integration process the vendor file?

That is a **processing-time** question.

A single timestamp cannot reliably answer all three.

---

# 3. Temporal Modeling Is a Business Semantics Problem First

Before writing SQL, define the temporal invariant.

Bad design process:

```text
"Let's add start_date and end_date."
```

Better process:

```text
Business rule
    ↓
Temporal semantics
    ↓
Boundary convention
    ↓
Representation
    ↓
Constraint
    ↓
Queries
    ↓
Operational policy
```

Ask:

1. What does the interval represent?
2. Is the start included?
3. Is the end included?
4. Can the end be unknown/open-ended?
5. Can adjacent intervals touch?
6. Can intervals overlap?
7. Can two versions be valid simultaneously for the same business key?
8. Does history need to be immutable?
9. Can historical records be corrected?
10. Do child records need continuous parent coverage?

Without explicit answers, temporal data becomes ambiguous.

---

# 4. Point-in-Time vs Interval Data

There are two fundamental forms.

## 4.1 Point event

Represents something that happened at one instant.

```sql
occurred_at timestamptz NOT NULL
```

Examples:

- payment received
- order created
- login occurred
- stock adjustment posted

## 4.2 Interval fact

Represents a condition that holds over a period.

```text
[start, end)
```

Examples:

- employment period
- price validity
- promotional period
- membership validity
- machine availability
- exchange rate validity

These should not be modeled identically.

---

# 5. The Most Important Boundary Decision: Half-Open Intervals

A robust default for many interval models is:

```text
[start, end)
```

Meaning:

```text
start <= t < end
```

The start is included; the end is excluded.

## 5.1 Why this is powerful

Consider:

```text
A: [2026-01-01, 2026-02-01)
B: [2026-02-01, 2026-03-01)
```

They touch at exactly `2026-02-01` but do not overlap.

This creates clean adjacency.

Without half-open semantics, systems often produce ambiguity around midnight, nanoseconds, and boundary timestamps.

## 5.2 Example

At exactly:

```text
2026-02-01 00:00:00
```

record B becomes active while A stops being active.

No gap. No overlap.

## 5.3 PostgreSQL alignment

PostgreSQL's `OVERLAPS` semantics use half-open periods for ordinary non-degenerate intervals, so the boundary convention is consistent with a common relational interpretation of temporal intervals. citeturn550777search6

# 6. Representing Temporal Intervals

There are several choices.

## 6.1 Two scalar columns

```sql
valid_from timestamptz NOT NULL,
valid_to   timestamptz
```

Simple and ORM-friendly.

But every query must recreate interval logic.

## 6.2 PostgreSQL range type

```sql
valid_during tstzrange NOT NULL
```

A single value represents the interval.

Example:

```sql
'[2026-01-01 00:00:00+00, 2026-02-01 00:00:00+00)'
```

Range types make containment and overlap semantics first-class and integrate with exclusion constraints and GiST indexing. PostgreSQL documents range types as representing ranges over a subtype, and range operators include containment and overlap operations. citeturn550777search9turn550777search11

## 6.3 Multirange

A multirange can represent multiple non-contiguous intervals in a single value.

Conceptually:

```text
[Mon 09:00, Mon 12:00)
[Mon 14:00, Mon 18:00)
```

This is useful when availability or validity has intentional gaps.

---

# 7. Choosing a Timestamp Type

## 7.1 `timestamptz`

Use `timestamptz` when an instant in global time is what matters.

Typical examples:

```sql
created_at timestamptz NOT NULL DEFAULT now()
```

```sql
event_at timestamptz NOT NULL
```

## 7.2 `timestamp without time zone`

This represents a wall-clock date/time without a timezone interpretation.

Useful for business-local concepts where timezone conversion is not inherent to the stored value, but dangerous when an actual global instant is intended.

## 7.3 `date`

Use when time-of-day genuinely does not matter.

Example:

```sql
birth_date date NOT NULL
```

or:

```sql
valid_from date NOT NULL
```

## 7.4 Timezone awareness is domain-dependent

Do not blindly convert every temporal field to `timestamptz`.

Ask:

> Am I storing an instant, a local calendar value, or a business date?

PostgreSQL documents `timestamp` as equivalent to `timestamp without time zone`, with `timestamptz` as the PostgreSQL abbreviation for `timestamp with time zone`. citeturn550777search13

---

# 8. The Canonical Temporal Table Pattern

A common effective-dating model is:

```sql
CREATE TABLE product_price_history (
    product_id bigint NOT NULL,
    valid_during tstzrange NOT NULL,
    price numeric(18,2) NOT NULL,

    CHECK (price >= 0)
);
```

If only one price may exist for a product at any instant:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE product_price_history
ADD CONSTRAINT product_price_no_overlap
EXCLUDE USING gist (
    product_id WITH =,
    valid_during WITH &&
);
```

This expresses the actual business invariant:

```text
For the same product,
validity intervals must not overlap.
```

An exclusion constraint is specifically designed to prevent pairs of rows whose specified comparisons all succeed; PostgreSQL creates the required index as part of the exclusion constraint. citeturn550777search2

---

# 9. Why `start` + `end` Alone Is Not Enough

A naive model:

```sql
valid_from timestamptz,
valid_to   timestamptz
```

with:

```sql
CHECK (valid_to > valid_from)
```

prevents backwards ranges, but does **not** prevent:

```text
A: [Jan 01, Feb 01)
B: [Jan 15, Mar 01)
```

Both rows satisfy:

```text
valid_to > valid_from
```

Yet they overlap.

The database needs a cross-row invariant.

Possible solutions:

- exclusion constraint
- application locking + validation
- serializable transaction strategy
- controlled temporal allocation service

The database constraint is usually the strongest integrity boundary when the invariant belongs to the relational data.

---

# 10. `OVERLAPS` in Queries

PostgreSQL supports SQL `OVERLAPS` for comparing periods.

Example:

```sql
SELECT
    (TIMESTAMP '2026-01-01 10:00', TIMESTAMP '2026-01-01 12:00')
    OVERLAPS
    (TIMESTAMP '2026-01-01 11:00', TIMESTAMP '2026-01-01 13:00');
```

Result:

```text
true
```

Adjacent periods that only share an endpoint do not overlap under the half-open interpretation. citeturn550777search6

For PostgreSQL range columns, use range operators such as:

```sql
valid_during && tstzrange(...)
```

for overlap testing.

---

# 11. Range Operators You Must Know

For range `r` and value `x`:

```text
r @> x      contains value
x <@ r      value is contained by range
r && r2     overlap
r << r2     strictly left of
r >> r2     strictly right of
r -|- r2    adjacent
```

For a temporal engineer, these are not merely SQL syntax. They are domain predicates.

Example:

```sql
SELECT *
FROM employee_assignment
WHERE assignment_period @> TIMESTAMPTZ '2026-09-14 12:00:00+00';
```

Meaning:

> Find the assignment that is valid at this instant.

---

# 12. Current Row vs Historical Rows

A common strategy is to represent history as multiple versions.

```text
customer_id | valid_during                         | tier
------------+---------------------------------------+------
101         | [2025-01-01, 2026-01-01)              | SILVER
101         | [2026-01-01, 2027-01-01)              | GOLD
```

Current row:

```sql
WHERE valid_during @> now()
```

Historical lookup:

```sql
WHERE valid_during @> TIMESTAMPTZ '2025-06-01 00:00:00+00'
```

This creates a single representation that supports both current and historical questions.

---

# 13. Open-Ended Intervals

A currently active record often needs no known end.

With scalar columns:

```sql
valid_from timestamptz NOT NULL,
valid_to   timestamptz
```

where `NULL` means:

```text
still valid / no known end
```

With ranges, PostgreSQL supports unbounded endpoints:

```sql
tstzrange('2026-01-01', NULL, '[)')
```

Conceptually:

```text
[2026-01-01, infinity)
```

Do not confuse:

```text
NULL = unknown / absent value
```

with:

```text
infinite upper bound = explicitly unbounded interval
```

That semantic distinction can matter when the application needs to differentiate “we know this is ongoing” from “the end date has not yet been supplied.”

---

# 14. Preventing Invalid Empty Intervals

An interval like:

```text
[2026-01-01, 2026-01-01)
```

is empty.

Whether empty intervals are legal depends on the business.

For temporal identity/uniqueness constraints using `WITHOUT OVERLAPS`, PostgreSQL does not permit empty ranges or multiranges in those key positions. citeturn550777search0

For ordinary application ranges, decide explicitly whether an empty interval has meaning.

If not:

```sql
CHECK (NOT isempty(valid_during))
```

---

# 15. Adjacent vs Overlapping Intervals

This is a critical modeling distinction.

Suppose a customer's membership is:

```text
[Jan 01, Feb 01)
[Feb 01, Mar 01)
```

These are adjacent, not overlapping.

The query:

```sql
range1 && range2
```

returns false for merely adjacent intervals.

The predicate:

```sql
range1 -|- range2
```

represents adjacency.

This distinction matters for:

- subscriptions
- employment history
- contracts
- pricing periods
- machine schedules
- accounting periods

---

# 16. Continuity Is a Different Invariant from Non-Overlap

Preventing overlap does not guarantee continuity.

Example:

```text
[Jan 01, Feb 01)
[Mar 01, Apr 01)
```

There is no overlap, but there is a one-month gap.

So there are separate temporal invariants:

```text
NON-OVERLAP
CONTINUITY
COMPLETENESS
ORDER
```

Do not assume an exclusion constraint solves all of them.

---

# 17. Temporal Primary Keys and Unique Constraints in PostgreSQL 18

PostgreSQL 18 introduced native temporal constraints for primary keys and unique constraints through `WITHOUT OVERLAPS`. citeturn550777search1turn550777search7

Example:

```sql
CREATE TABLE product_price (
    product_id bigint NOT NULL,
    valid_during tstzrange NOT NULL,
    price numeric(18,2) NOT NULL,

    PRIMARY KEY (product_id, valid_during WITHOUT OVERLAPS)
);
```

Conceptually this means:

```text
The same product cannot have overlapping validity periods.
```

PostgreSQL documents this as effectively using exclusion-style semantics, with the temporal column requiring a range or multirange type. citeturn550777search0

This is a major evolution from manually expressing every temporal uniqueness rule through a separately written exclusion constraint.

---

# 18. Temporal Foreign Keys with `PERIOD`

PostgreSQL 18 also introduced temporal foreign-key support using `PERIOD`. citeturn550777search1turn550777search7

The conceptual rule is stronger than ordinary FK existence.

Ordinary FK:

```text
child key must match a parent key
```

Temporal FK:

```text
child duration must be completely covered
by matching parent validity periods.
```

For example:

```text
Parent:
customer_id = 42
[Jan 01, Jul 01)
[Jul 01, Jan 01)

Child:
customer_id = 42
[Mar 01, Sep 01)
```

The parent versions together cover the child's entire period, so the temporal relationship can be valid.

PostgreSQL's documentation states that the referenced records, based on the non-period key components, must collectively cover the referencing record's entire period, and the referenced side requires a `WITHOUT OVERLAPS` primary key or unique constraint. citeturn550777search0

---

# 19. Temporal Data and Referential Integrity

Traditional FK:

```text
order.customer_id → customer.id
```

Temporal relationship:

```text
order_period
    must be covered by
customer_validity_periods
```

This is fundamentally different.

A row can exist in a parent table but still be temporally invalid for the child event.

That matters in:

- contracts
- versioned product catalogs
- regulatory rules
- pricing
- memberships
- employment
- legal agreements

---

# 20. Bitemporal Modeling

Bitemporal data tracks two independent time axes.

Typical axes:

```text
Valid Time       = when reality says this was true
System Time      = when the database says this version was stored as true
```

Example:

```text
salary = 80000
valid:  2026-07-01 → 2026-12-31
stored: 2026-07-05 → 2026-09-14
```

Then a later correction may reveal that the correct salary should have been 85000 starting July 1.

You can preserve both:

```text
Business truth history
+
Knowledge/update history
```

This is valuable for:

- audit
- regulatory review
- financial reconciliation
- dispute resolution
- forensic analysis
- correction history

---

# 21. Temporal Corrections Are Not the Same as Temporal Updates

Suppose:

```text
July 01 → salary 80000
```

A correction on September 10 says:

```text
Actual July salary should have been 85000.
```

An ordinary update:

```sql
UPDATE salary_history
SET amount = 85000
WHERE ...;
```

may destroy evidence of what the system previously believed.

A more audit-sensitive model records the correction as a new version or preserves system-time history.

This leads to an important principle:

> Historical truth and current correctness are not always the same requirement.

---

# 22. Temporal Tables vs Event Sourcing

Temporal history and event sourcing are related but not equivalent.

## Temporal history

Stores versions of business state.

```text
price = 100
price = 120
price = 140
```

## Event sourcing

Stores the events that caused state transitions.

```text
PRICE_SET 100
PRICE_SET 120
PRICE_SET 140
```

Event sourcing can reconstruct state, but a temporal table does not necessarily preserve every event that produced that state.

Choose based on the question the system must answer.

---

# 23. Temporal Snapshot vs Derived Current State

A historical table may coexist with a current-state table.

Example:

```text
customer_current
customer_history
```

Advantages of a dedicated current table:

- simple hot-path reads
- straightforward indexing
- easy application semantics

Advantages of a unified history table:

- one canonical source
- direct point-in-time queries
- fewer synchronization surfaces

This is a denormalization/operational architecture decision, not a universal rule.

---

# 24. Temporal Uniqueness

A normal unique constraint says:

```text
No two rows have the same key.
```

A temporal unique rule says:

```text
No two rows for the same business key
have overlapping validity periods.
```

These are different constraints.

Example:

```text
customer_id | valid_during          | tier
------------+-----------------------+------
1           | [Jan, Apr)            | SILVER
1           | [Apr, Jul)            | GOLD
```

This is valid even though `customer_id = 1` appears twice.

Temporal uniqueness is therefore often closer to:

```text
UNIQUE(key, time interval)
```

than ordinary scalar uniqueness.

---

# 25. Temporal Query Patterns

## 25.1 What is valid now?

```sql
SELECT *
FROM product_price
WHERE product_id = $1
  AND valid_during @> now();
```

## 25.2 What was valid at a point?

```sql
SELECT *
FROM product_price
WHERE product_id = $1
  AND valid_during @> $2::timestamptz;
```

## 25.3 Which records overlap a requested period?

```sql
SELECT *
FROM booking
WHERE resource_id = $1
  AND booking_period && $2::tstzrange;
```

## 25.4 Which periods are adjacent?

```sql
SELECT *
FROM price_history a
JOIN price_history b
  ON a.product_id = b.product_id
 AND a.valid_during -|- b.valid_during;
```

## 25.5 Find the most recent version

When system-time history exists:

```sql
ORDER BY recorded_at DESC
LIMIT 1;
```

But do not use "latest" as a substitute for a clearly defined time axis.

---

# 26. Temporal Joins

Temporal joins answer:

> Which version of B was valid when A happened?

Example:

```sql
SELECT
    o.id,
    o.created_at,
    p.price
FROM orders o
JOIN product_price p
  ON p.product_id = o.product_id
 AND p.valid_during @> o.created_at;
```

This is vastly safer than joining to the current price when computing historical reports.

---

# 27. The Classic Historical Reporting Bug

Incorrect:

```sql
SELECT
    o.id,
    p.price
FROM orders o
JOIN product p
  ON p.id = o.product_id;
```

Suppose `product.price` now equals 1500, while the order was created when the price was 1100.

A historical report now incorrectly reports:

```text
order price = current price
```

Better:

```text
order line stores the transaction price
```

and/or:

```text
join against the effective price version at order time
```

Financial transaction records should generally preserve the actual transaction-time value rather than depending entirely on later reconstruction from mutable reference tables.

---

# 28. Transaction-Time Snapshots vs Historical Reconstruction

For a financial order line:

```sql
unit_price numeric(18,2) NOT NULL
```

is often necessary even when a product-price history exists.

Why?

Because the transaction is a fact:

```text
What price was actually charged?
```

That is not necessarily equivalent to:

```text
What price table says should have applied?
```

Production systems frequently need both:

```text
Reference temporal history
+
Immutable transaction snapshot
```

---

# 29. Temporal Data and Immutability

Not every temporal record should be mutable.

Consider:

```text
Ledger entry
Invoice issuance
Tax calculation snapshot
Payment posting
```

Changing the historical value silently can destroy auditability.

A strong design can separate:

```text
mutable temporal reference data
```

from:

```text
immutable financial facts
```

This distinction becomes particularly important in ERP systems.

---

# 30. Concurrency: The Temporal Race Condition

Naive pattern:

```text
Request A checks for overlap → none
Request B checks for overlap → none
Request A inserts
Request B inserts
```

Now both rows overlap.

Application-level validation alone is unsafe under concurrency unless paired with an appropriate transactional isolation/locking strategy.

Database-backed exclusion or temporal uniqueness constraints convert the invariant into an enforcement mechanism rather than a hope.

---

# 31. Temporal Constraints as Concurrency Control

For a business rule:

```text
One active price per product at any instant
```

the strongest design is not:

```javascript
if (!(await repo.hasOverlap(period))) {
    await repo.insert(row);
}
```

because the validation and insert are separate raceable operations.

Prefer a database constraint:

```text
Attempt insert
    ↓
Constraint checks concurrent state
    ↓
Success or integrity error
```

Then the application handles the integrity violation deliberately.

---

# 32. Temporal Updates and Interval Splitting

Suppose:

```text
[Jan 01, Dec 31) = price 100
```

A new price must apply from:

```text
Jun 01
```

A correct temporal transition may require:

```text
[Jan 01, Jun 01) = 100
[Jun 01, Dec 31) = 120
```

This is interval splitting.

Treating it as a simple row update can destroy historical validity.

A robust transition algorithm is:

```text
1. Lock or otherwise serialize the affected temporal key.
2. Find current containing interval.
3. Validate business transition.
4. Split/close existing interval.
5. Insert new interval.
6. Commit atomically.
```

The exact implementation depends on whether temporal constraints or application-level locking are used.

---

# 33. Gap Detection

If continuity is required, detect gaps explicitly.

A conceptual PostgreSQL approach is:

```sql
SELECT
    valid_during,
    lead(valid_during) OVER (
        PARTITION BY product_id
        ORDER BY lower(valid_during)
    ) AS next_period
FROM product_price;
```

Then compare:

```sql
upper(valid_during) = lower(next_period)
```

A temporal design that requires continuity should test continuity rather than assuming it from non-overlap.

---

# 34. Coalescing Temporal History

Temporal data may contain adjacent intervals with identical values:

```text
[Jan, Feb) price 100
[Feb, Mar) price 100
```

Semantically this may be equivalent to:

```text
[Jan, Mar) price 100
```

Combining adjacent equal-value periods is called **coalescing**.

Benefits:

- fewer rows
- cleaner reports
- simpler reasoning
- reduced temporal fragmentation

But coalescing may be incorrect when the historical record must preserve each administrative change separately.

Again, business semantics come first.

---

# 35. Temporal Precision

Choose precision based on the business invariant.

Examples:

```text
date      → calendar day

minute    → scheduling granularity

second    → operational event

microsecond → technical ordering where justified
```

Do not add precision merely because PostgreSQL supports it.

For example, a jewellery store's daily rate schedule may be date-based, while payment events may require timestamp precision.

---

# 36. Daylight Saving Time and Temporal Correctness

Global instants and local business schedules are different concepts.

For an international system:

```text
10:00 America/New_York
```

is not semantically identical to:

```text
10:00 UTC
```

For actual events, storing an absolute instant is usually appropriate.

For recurring local schedules:

```text
store opens at 09:00 local time
```

the timezone and recurrence rules are part of the business data.

Do not flatten recurring local schedules into UTC timestamps without understanding future timezone transitions.

---

# 37. PostgreSQL Range Canonicalization

Range types can have subtype-specific canonicalization behavior, especially for discrete ranges. PostgreSQL exposes range metadata including canonicalization and subtype-difference functions through `pg_range`. citeturn550777search8

This matters when reasoning about whether two textual range representations are semantically the same.

The important engineering lesson is:

> Treat range semantics as typed domain behavior, not merely string formatting.

---

# 38. Indexing Temporal Data

For range queries, GiST indexes are commonly relevant.

Example:

```sql
CREATE INDEX idx_product_price_period
ON product_price
USING gist (product_id, valid_during);
```

But do not blindly create a GiST index without understanding the workload.

Ask:

- Is the dominant predicate overlap?
- Point containment?
- Equality + overlap?
- Range ordering?
- How large is the table?
- What is the write rate?
- Does the constraint already create an index?

Exclusion constraints automatically create the associated index. citeturn550777search2

---

# 39. Temporal Query Performance

Common slow query:

```sql
SELECT *
FROM price_history
WHERE product_id = $1
  AND valid_from <= $2
  AND (valid_to IS NULL OR valid_to > $2);
```

This may be perfectly workable at modest scale with appropriate indexing, but temporal range predicates can become more expressive and maintainable with native range types.

For serious workloads, test with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

Measure:

- rows removed by filter
- index usage
- heap fetches
- buffer reads
- actual execution time

---

# 40. Partitioning Temporal Tables

Large temporal tables sometimes become candidates for range partitioning by time.

Example conceptual strategy:

```text
history_2025
history_2026
history_2027
```

Partitioning can help manage very large time-oriented datasets, but it does not automatically solve temporal integrity rules.

Remember:

```text
partitioning ≠ temporal constraint enforcement
```

PostgreSQL range partitioning itself uses non-overlapping partition bounds and can improve lifecycle operations such as dropping old partitions, which can avoid the vacuum work of deleting large numbers of rows. citeturn550777search3

---

# 41. Retention and Temporal Lifecycle

Temporal data naturally creates history growth.

Define:

```text
Hot history
Warm history
Cold archive
Deletion policy
Legal retention
```

For example:

```text
0–2 years  → primary database
2–7 years  → archive
>7 years   → deletion when legally permitted
```

Never assume temporal history means infinite retention.

Retention is governed by:

- compliance
- privacy
- storage cost
- business value
- legal requirements
- operational constraints

# 42. Temporal Data and Privacy

Historical records can preserve personal data for years.

A temporal architecture therefore creates privacy consequences:

```text
More history
    ↓
More stored personal information
    ↓
More retention / deletion complexity
```

For a personal-data field, decide whether history requires:

- immutable preservation
- redaction
- pseudonymization
- restricted access
- deletion after retention expiry

Do not use “audit requirement” as a blanket excuse for retaining everything forever.

# 43. Multi-Tenant Temporal Modeling

For SaaS systems, temporal keys often need tenant scope.

Example:

```sql
PRIMARY KEY (tenant_id, product_id, valid_during WITHOUT OVERLAPS)
```

Conceptually:

```text
Tenant A / Product 10
and
Tenant B / Product 10
```

may independently have overlapping periods.

Tenant isolation must be part of the key/invariant—not an accidental application filter.

# 44. Temporal Data in a Jewellery ERP

Consider metal pricing.

Requirement:

```text
Each branch can have effective metal rates.
The same metal/rate category cannot have overlapping effective periods.
Past sales must preserve the actual applied rate.
```

A reference table might be:

```sql
CREATE TABLE branch_metal_rate (
    branch_id bigint NOT NULL,
    metal_code text NOT NULL,
    valid_during tstzrange NOT NULL,
    rate numeric(18,4) NOT NULL CHECK (rate >= 0),

    PRIMARY KEY (branch_id, metal_code, valid_during WITHOUT OVERLAPS)
);
```

Then a transaction line still stores:

```sql
applied_rate numeric(18,4) NOT NULL
```

because the sale is an immutable transaction fact.

This yields:

```text
Temporal reference state
        +
Transaction snapshot
```

which is much safer than recomputing historical invoices from whatever rate is currently active.

# 45. Naive Approach → Why It Fails → Improved Approach

## Naive Approach

```text
start_date
end_date
```

and application code checks overlap.

## Why It Fails

- race conditions
- duplicated interval logic
- inconsistent boundary semantics
- poor historical query ergonomics
- no database-level cross-row invariant

## Improved Approach

Use a PostgreSQL range type where appropriate:

```sql
valid_during tstzrange NOT NULL
```

plus a database-level non-overlap constraint when the invariant requires it.

## Why It Works

The temporal fact and its interval semantics become first-class database concepts.

## Production Considerations

- define timezone semantics
- define open-ended behavior
- define adjacency
- define correction policy
- test concurrency
- index actual workload
- define retention

## Alternative

Two scalar columns remain reasonable when ORM compatibility or simple reporting dominates and cross-row temporal rules are handled elsewhere.

## Trade-Off

Range-based modeling is more expressive but introduces PostgreSQL-specific concepts that application teams must understand.

## 46.1 One mutable `current_price`

Fails historical reporting.

## 46.2 `start_date` but no end

Cannot represent bounded historical validity cleanly.

## 46.3 End-inclusive timestamps everywhere

Creates boundary ambiguity.

## 46.4 App-only overlap checking

Race condition under concurrency.

## 46.5 Using current state for historical facts

Rewrites the past through present-day data.

## 46.6 Storing local timestamps for global events

Creates timezone ambiguity.

## 46.7 Unlimited temporal retention

Creates privacy and storage problems.

## 46.8 Updating historical financial facts in place

Can destroy auditability.

# 47. AI / Vibe-Coding Failure Modes

AI-generated temporal schemas frequently look plausible but encode the wrong semantics.

### Failure 1 — `start_date` / `end_date` everywhere

Why it is dangerous:

The model may never define interval boundaries.

### Failure 2 — overlap check before insert

Why it is dangerous:

Concurrent requests can both pass the check.

### Failure 3 — current table used as historical source

Why it is dangerous:

Historical reports become dependent on mutable state.

### Failure 4 — no distinction between valid time and event time

Why it is dangerous:

Reports answer the wrong question.

### Failure 5 — timestamp without timezone for distributed systems

Why it is dangerous:

The same textual clock time can represent different instants.

### Failure 6 — no retention policy

Why it is dangerous:

History expands without operational or privacy controls.

### Failure 7 — assuming exclusion solves continuity

Why it is dangerous:

Non-overlap still permits gaps.

### Failure 8 — temporal reference table used to reconstruct immutable transactions

Why it is dangerous:

A later correction can change the apparent historical transaction result.

# 48. Evidence-Driven Temporal Debugging

When a temporal bug appears, do not immediately modify the model.

Collect evidence.

## Step 1 — Identify the time axis

```text
event?
valid?
system?
processing?
```

## Step 2 — Print exact boundaries

Use UTC-normalized output where appropriate.

## Step 3 — Check overlap

```sql
SELECT a.*, b.*
FROM history a
JOIN history b
  ON a.business_key = b.business_key
 AND a.id <> b.id
 AND a.valid_during && b.valid_during;
```

## Step 4 — Check gaps

Use `lead()` over ordered periods.

## Step 5 — Check concurrency evidence

Look at transaction IDs, timestamps, logs, and constraint violations.

## Step 6 — Check whether the transaction snapshot exists

A historical-reporting error may be caused by missing immutable facts rather than incorrect temporal reference data.

## 49.1 Boundary tests

Test:

```text

just before end
```

## 49.2 Overlap tests

```text
A fully contains B
B fully contains A
partial left overlap
partial right overlap
same interval
adjacent interval
```

## 49.3 Timezone tests

Test:

- UTC
- business timezone
- offset changes
- daylight-saving transitions where applicable

## 49.4 Concurrency tests

Run competing inserts concurrently and prove the invariant still holds.

## 49.5 Correction tests

Verify that historical corrections do not silently rewrite immutable facts.

# 50. Temporal Property Testing

Temporal invariants are excellent candidates for property-based tests.

Example property:

```text
For each business key,
no two active intervals overlap.
```

Another:

```text
For each transaction,
exactly one applicable historical price exists.
```

Another:

```text
All child validity periods are fully covered by valid parent periods.
```

Instead of testing only a few manually chosen dates, generate many interval combinations.

# 52. Migration Strategy for Existing Temporal Data

Suppose an existing table has:

```sql
valid_from
valid_to
```

and you want a range representation.

A safe strategy is:

```text
1. inventory existing values
2. identify NULL / invalid intervals
3. identify overlaps
4. identify gaps if continuity is required
5. define exact boundary semantics
6. introduce the new representation
7. backfill
8. validate equivalence
9. introduce constraints
10. migrate reads
11. migrate writes
12. remove obsolete representation later
```

Do not add an exclusion or temporal uniqueness constraint blindly to a table that already contains conflicting history.

# 53. Temporal Schema Evolution

Changing temporal semantics is especially dangerous.

Example:

```text
Old semantics: end inclusive
New semantics: end exclusive
```

This is not a cosmetic migration.

It can alter:

- report results
- overlap logic
- billing periods
- contract validity
- historical joins

Schema evolution must therefore include semantic migration—not only DDL.

# 54. Current PostgreSQL 18 Metadata

PostgreSQL 18 stores whether a constraint uses temporal semantics in `pg_constraint.conperiod`. This identifies constraints defined with `WITHOUT OVERLAPS` or `PERIOD`. citeturn550777search5

Example inspection:

```sql
SELECT
    conname,
    contype,
    condeferrable,
    condeferred,
    conperiod
FROM pg_constraint
WHERE conrelid = 'product_price'::regclass;
```

This can be useful for schema introspection and migration tooling.

# 55. Temporal Data + ORMs

ORMs commonly provide weak abstractions for temporal constraints.

An ORM may support:

```text
startDate
endDate
```

but not expose the full semantics of:

```sql
EXCLUDE USING gist
```

or:

```sql
WITHOUT OVERLAPS
```

Do not let ORM convenience dictate domain integrity.

A production approach is often:

```text
ORM for ordinary persistence
+
explicit migrations / SQL for advanced temporal invariants
```

In a Node.js/NestJS system, map database integrity violations into domain-level errors rather than duplicating the constraint logic in TypeScript.

---

# 56. Temporal Transactions in Node.js / NestJS

A temporal update often requires one transaction.

Conceptual service logic:

```text
BEGIN

lock or serialize affected business key

read current interval

close/split existing interval
insert new interval

COMMIT
```

The transaction boundary should cover the complete temporal state transition.

Do not:

```text
HTTP request
→ update current row
→ second query inserts history
```

without understanding failure behavior.

Otherwise the two representations can diverge.

# 57. Security Implications

Temporal history can reveal:

- salary changes
- customer status changes
- internal pricing
- approval history
- addresses
- account ownership
- operational schedules

Therefore:

```text
History is data.
History needs authorization.
```

A user authorized to see current customer state may not automatically be authorized to see every historical version.

Design row-level and application authorization accordingly.

# 58. Production Architecture Decision Matrix

| Requirement | Typical pattern |
|---|---|
| Current state only | ordinary table |
| Historical point lookup | effective-dated history |
| Non-overlapping validity | range + exclusion/temporal unique |
| Temporal parent coverage | temporal FK / `PERIOD` where appropriate |
| Immutable financial fact | snapshot columns / append-only ledger |
| Full business + correction history | bitemporal model |
| Event reconstruction required | event sourcing |
| Huge historical volume | partitioning + archival |
| Complex recurring schedules | explicit timezone + recurrence model |

These are patterns, not automatic prescriptions.

# 59. Decision Framework

Before introducing temporal complexity, answer:

### Question 1
Does the business need historical truth?

If no, do not add unnecessary versioning.

### Question 2
Does validity change over intervals?

If yes, model effective periods.

### Question 3
Can periods overlap?

If no, enforce that invariant.

### Question 4
Must periods be continuous?

If yes, add explicit continuity logic.

### Question 5
Must child periods be parent-covered?

If yes, consider temporal referential integrity.

### Question 6
Must administrative corrections be preserved?

If yes, consider system-time history or append-only records.

### Question 7
Is the business fact financial or legally significant?

If yes, preserve immutable transaction-time snapshots.

# 60. Expert Mental Model

Think of temporal data as a function:

```text
Business Key × Time → Value
```

For example:

```text
(product=42, 2026-01-15) → ₹1100
(product=42, 2026-07-15) → ₹1250
```

Temporal uniqueness says:

```text
At most one value is defined
for a key at a given instant.
```

Temporal continuity says:

```text
A value exists across the complete required interval.
```

Temporal referential integrity says:

```text
The referenced value exists for the complete required child interval.
```

Bitemporality says:

```text
Business truth depends on one time axis,
knowledge of that truth depends on another.
```

This mental model makes advanced temporal constraints much easier to reason about.

# 65. Final Takeaways

1. Temporal data is about **time-dependent truth**, not merely timestamps.
2. Distinguish event time, valid time, system time, and processing time.
3. Define interval semantics before choosing columns or types.
4. Half-open intervals are a powerful default for many temporal models.
5. PostgreSQL range types make interval semantics first-class.
6. Non-overlap, continuity, completeness, and referential coverage are different invariants.
7. Application-only overlap checks are race-prone.
8. Database constraints are the strongest integrity boundary for relational temporal invariants when the database can express the rule.
9. PostgreSQL 18 adds native temporal primary-key/unique semantics with `WITHOUT OVERLAPS` and temporal foreign keys with `PERIOD`. citeturn550777search0turn550777search1
10. Historical reference data does not eliminate the need for immutable transaction snapshots.
11. Bitemporal modeling is powerful, but should be introduced only when the business genuinely needs independent truth and knowledge timelines.
12. Temporal history creates operational, performance, retention, and privacy responsibilities.

> **Mastery principle:** The purpose of temporal modeling is not to store more timestamps. It is to make the database capable of answering the right question about the right version of reality at the right point in time—without silently rewriting the past.
