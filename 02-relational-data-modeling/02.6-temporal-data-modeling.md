# 02.6 — Temporal Data Modeling

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to modeling facts that change over time without confusing current state, historical truth, validity, transaction time, and system observation time.

---

## 1. Chapter Objective

Most business data is not timeless.

Prices change. Employees change roles. Customers change addresses. Contracts become effective and later expire. Inventory ownership changes. Tax rules change. A product may have one price today and another price tomorrow. An account can be active, suspended, and reactivated. A document may be valid for one period even though the database recorded that fact later.

A schema that stores only the latest value often answers:

> “What is true now?”

while the business eventually asks:

> “What was true then?”

Those are different questions and require different modeling decisions.

This chapter develops the ability to model temporal facts explicitly and correctly.

The central question is not:

> “Should I add `created_at` and `updated_at`?”

It is:

> **“Which notion of time belongs to this fact, what does a row's interval mean, what historical states must remain reconstructable, and which temporal invariants must the database enforce?”**

---

# 2. Three Levels of Definition

## 2.1 Simple definition

Temporal data is data whose meaning depends on time.

Examples:

- a product price valid from January through March
- an employee's assignment to a branch
- a customer's membership status
- a machine's operating interval
- a contract's effective period

## 2.2 Engineering definition

Temporal modeling represents facts together with one or more time dimensions that define when the fact was valid, when the database knew about it, or when it was observed.

## 2.3 Expert definition

Temporal modeling is the deliberate representation of time-varying predicates and their lifecycle, including interval semantics, boundary conventions, historical preservation, correction semantics, temporal uniqueness, temporal referential integrity, concurrency, and reconstruction requirements.

A useful model is:

```text
Business Fact
    ↓
Time Semantics
    ↓
Valid-Time / Transaction-Time / Observation-Time Decision
    ↓
Grain + Identity + Interval
    ↓
Relational Representation
    ↓
Constraints
    ↓
Queries / Transactions / Auditing
    ↓
Historical Reconstruction
```

---

# 3. The First Principle: “Time” Is Not One Thing

A common mistake is treating every timestamp as equivalent.

Consider:

```text
price = ₹500
```

There are several possible times associated with that statement.

### Valid time

When the business says the price is effective.

```text
2026-10-01 00:00 → 2026-10-31 23:59:59...
```

### Transaction time

When the database recorded the fact.

```text
2026-09-28 14:30 UTC
```

### Observation time

When a particular consumer observed or received the fact.

These can differ substantially.

For example:

```text
Business validity:
2026-10-01 → 2026-10-31

Database insertion:
2026-09-28

Correction entered:
2026-10-05
```

The price is valid for October, even though it was known and stored before October.

Expert lesson:

> **Do not infer business validity from `created_at`.**

---

# 4. Current-State Modeling vs Temporal Modeling

A current-state table might be:

```sql
CREATE TABLE product_price (
    product_id bigint PRIMARY KEY,
    amount numeric(18,2) NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

This answers:

```text
What is the current price?
```

It cannot reliably answer:

```text
What was the price on 2026-02-15?
```

A temporal model instead stores multiple versions or intervals.

```text
product_id | valid_during              | amount
-----------+---------------------------+-------
10         | [2026-01-01, 2026-02-01) | 450
10         | [2026-02-01, 2026-03-01) | 500
10         | [2026-03-01, 2026-04-01) | 550
```

Now historical questions become data queries instead of guesses.

---

# 5. The Four Questions Every Temporal Schema Must Answer

For every temporal fact, explicitly answer:

1. **What is changing?**
2. **When is each version/fact valid?**
3. **When did the database know about it?**
4. **Must old versions remain reconstructable?**

Optional fifth question:

5. **Must corrections preserve the original observation history?**

The last two questions often distinguish ordinary history tables from true bitemporal systems.

---

# 6. Time Dimensions

## 6.1 Valid Time

Valid time answers:

> When was the fact true in the modeled business world?

Example:

```text
employee 42
branch = Hyderabad
valid_from = 2026-01-01
valid_to   = 2026-06-01
```

The employee was assigned to Hyderabad during that period.

## 6.2 Transaction Time

Transaction time answers:

> When did the database record or maintain this version?

This is useful for auditability and reconstruction of database history.

## 6.3 Observation Time

Useful in event ingestion, integrations, sensors, and distributed systems:

> When did this system observe or receive the fact?

Example:

```text
source_event_time
received_at
processed_at
```

These timestamps should not be silently collapsed into one value.

---

# 7. Valid Time Is Usually an Interval Problem

Suppose a price is valid:

```text
from 1 Jan
until 1 Feb
```

A robust representation is a range:

```sql
valid_during daterange NOT NULL
```

or for timestamp semantics:

```sql
valid_during tstzrange NOT NULL
```

The half-open interval is usually the cleanest convention:

```text
[start, end)
```

Meaning:

```text
start is included
end is excluded
```

Thus:

```text
[2026-01-01, 2026-02-01)
[2026-02-01, 2026-03-01)
```

are adjacent without overlapping.

This removes a large class of boundary bugs.

---

# 8. Why Inclusive End Dates Cause Bugs

A naive model often uses:

```text
valid_from
valid_to
```

with an informal convention:

```text
both inclusive
```

Then adjacent values become awkward:

```text
Jan 1 - Jan 31
Feb 1 - Feb 28
```

For timestamps, inclusive upper bounds can become even worse:

```text
2026-01-01 00:00:00
through
2026-01-31 23:59:59.999999
```

This creates dependence on timestamp precision.

Half-open intervals avoid that.

```text
[2026-01-01, 2026-02-01)
```

The exact representation of time boundaries should be a documented domain rule, not an accident of UI formatting.

---

# 9. Range Types as Temporal Primitives

PostgreSQL provides native range types including:

```text
int4range
int8range
daterange
numrange
tsrange
tstzrange
```

For temporal business systems, common choices are:

```text
daterange → date-level validity

timestamp range → timestamps without timezone semantics

timestamptz range → absolute instants with timezone-aware interpretation
```

PostgreSQL range types support operators such as:

```sql
&&   -- overlap
@>   -- contains
<@   -- is contained by
-|-  -- adjacent
```

and functions such as:

```sql
lower()
upper()
lower_inc()
upper_inc()
 isempty()
```

Use native range semantics when the domain is genuinely interval-shaped rather than storing textual encodings such as:

```text
"2026-01-01 to 2026-02-01"
```

---

# 10. Empty, Unbounded, and NULL Are Different

These concepts must never be conflated.

### NULL range

The interval itself is unknown / absent.

### Unbounded range

The interval has no finite lower or upper boundary.

Example:

```text
[2026-01-01, infinity)
```

### Empty range

There is no duration in the range.

These states have different business meanings.

For a contract, for example:

```text
NULL       → contract period unknown
unbounded  → contract continues indefinitely
empty      → invalid for this business concept
```

Whether each state is allowed should be explicit.

---

# 11. Temporal Key Design

Suppose a product may have many price versions but never more than one active price at the same time.

The business invariant is:

```text
For a given product,
validity ranges must not overlap.
```

A conventional approach is an exclusion constraint:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE product_prices (
    product_id bigint NOT NULL,
    valid_during daterange NOT NULL,
    amount numeric(18,2) NOT NULL,
    CONSTRAINT product_prices_no_overlap
        EXCLUDE USING gist (
            product_id WITH =,
            valid_during WITH &&
        )
);
```

This is much stronger than checking overlap in application code.

Two concurrent requests can both observe a free interval before either commits. A database constraint provides the authoritative race-safe enforcement.

---

# 12. PostgreSQL 18 Temporal Constraints

PostgreSQL 18 adds temporal constraint support using `WITHOUT OVERLAPS` for primary/unique constraints and `PERIOD` for corresponding temporal foreign keys. citeturn154689search0turn154689search1

For example, a temporal uniqueness rule can be expressed in the shape:

```sql
PRIMARY KEY (product_id, valid_during WITHOUT OVERLAPS)
```

or:

```sql
UNIQUE (product_id, valid_during WITHOUT OVERLAPS)
```

The range/multirange column participates in non-overlapping uniqueness rather than ordinary equality. PostgreSQL documents this as effectively backed by exclusion-style semantics and a GiST index. Empty ranges/multiranges are not permitted for the `WITHOUT OVERLAPS` column. citeturn154689search0

This changes the modeling toolbox materially: temporal identity and uniqueness can be declared directly instead of always spelling the rule manually as an exclusion constraint.

---

# 13. Temporal Foreign Keys in PostgreSQL 18

PostgreSQL 18 also introduces temporal foreign keys using `PERIOD`. citeturn154689search1turn154689search2

The critical semantic difference is that ordinary referential integrity asks whether a parent key exists for a child key.

A temporal foreign key asks whether the referenced parent records collectively cover the child's full duration.

Conceptually:

```text
Child:
account = 7
period  = [Jan 1, Apr 1)

Parent versions:
account = 7  [Jan 1, Feb 15)
account = 7  [Feb 15, Apr 1)
```

Together, the parent rows cover the child's entire period.

That is a fundamentally stronger temporal invariant than ordinary equality-based FK semantics.

---

# 14. Slowly Changing Dimensions

Data warehousing commonly discusses Slowly Changing Dimensions (SCD).

## Type 1

Overwrite the value.

```text
old address → new address
```

History is lost.

## Type 2

Store separate historical versions.

```text
customer 10
----------------------------
Delhi     [Jan, Mar)
Mumbai    [Mar, Jul)
Hyderabad [Jul, infinity)
```

This preserves business history.

## Type 3

Keep selected prior state, often through additional columns.

```text
current_region
previous_region
```

Type 3 is limited historical memory, not arbitrary time travel.

The correct design depends on the questions the system must answer.

---

# 15. History Table vs Version Table

These are related but not identical patterns.

### History table

Designed primarily for audit/history.

Example:

```text
order_status_history
--------------------
order_id
status
changed_at
changed_by
```

### Version table

Designed so every business state is a first-class temporal version.

Example:

```text
customer_address_version
------------------------
customer_id
address_id
valid_during
```

A version table often becomes part of normal query semantics.

A history table may instead exist primarily for audit reconstruction.

Do not confuse:

```text
“what happened?”
```

with:

```text
“which version was legally/business-valid at that time?”
```

---

# 16. Effective-Dated Modeling

A classic schema is:

```sql
CREATE TABLE employee_assignment (
    employee_id bigint NOT NULL,
    branch_id bigint NOT NULL,
    valid_during daterange NOT NULL,
    PRIMARY KEY (employee_id, valid_during WITHOUT OVERLAPS)
);
```

Business invariant:

```text
An employee cannot have overlapping assignments.
```

But there may be another rule:

```text
A branch can have many employees.
```

These two facts imply the uniqueness constraint belongs around:

```text
employee_id + validity
```

not simply:

```text
branch_id
```

The key follows the business invariant.

---

# 17. “Current Row” Is Usually a Query, Not a Separate Truth

Given:

```text
valid_during
```

current state can be derived.

For timestamp validity:

```sql
SELECT *
FROM product_prices
WHERE product_id = $1
  AND valid_during @> now();
```

For date validity:

```sql
SELECT *
FROM tax_rates
WHERE jurisdiction_id = $1
  AND valid_during @> CURRENT_DATE;
```

This avoids maintaining redundant columns such as:

```text
is_current = true
```

unless there is a measured reason for the extra state.

If `is_current` is stored, it becomes another invariant that must remain synchronized with the interval.

---

# 18. Temporal Queries

## 18.1 Point-in-time query

“What was valid at instant X?”

```sql
SELECT *
FROM product_prices
WHERE product_id = $1
  AND valid_during @> $2::timestamptz;
```

## 18.2 Overlap query

“Which versions overlap this requested period?”

```sql
SELECT *
FROM bookings
WHERE room_id = $1
  AND reserved_during && tstzrange($2, $3, '[)');
```

## 18.3 Contained query

“Which intervals lie completely inside another interval?”

```sql
WHERE valid_during <@ tstzrange($2, $3, '[)')
```

## 18.4 Adjacent query

```sql
WHERE valid_during -|- daterange($2, $3, '[)')
```

Use temporal operators rather than reconstructing interval logic with fragile scalar comparisons whenever native range semantics express the business rule directly.

---

# 19. Two Timestamps vs One Range Column

Both approaches are possible.

### Separate columns

```text
valid_from
tvalid_to
```

Advantages:

- familiar to teams
- simple API serialization
- compatible with tooling expecting columns

Costs:

- boundary semantics are externalized
- overlap logic must be repeated
- inclusive/exclusive conventions can drift

### Range column

```text
valid_during daterange
```

Advantages:

- interval semantics are first-class
- native operators
- GiST support
- exclusion constraints
- temporal constraints in PostgreSQL 18

Costs:

- less familiar to some ORMs
- API mapping needs deliberate serialization
- range-specific semantics must be taught to application developers

The choice depends on domain and team maturity, but native range modeling is often superior when interval logic is central to the domain.

---

# 20. Temporal Modeling and Time Zones

For event instants, use `timestamptz` semantics.

For business-local calendar dates, use `date`.

Do not automatically use:

```sql
timestamp without time zone
```

for globally meaningful instants.

Example:

```text
2026-09-13 09:00 Asia/Kolkata
```

is an instant.

A business day such as:

```text
2026-09-13
```

may not be an instant at all.

The correct temporal type follows the meaning of the fact.

A common failure is taking a calendar date from a local business rule, converting it into UTC midnight, and accidentally changing its semantics.

---

# 21. Business Dates vs Timestamps

Examples:

```text
invoice_date          → date
birthday              → date
contract_effective_on → date
created_at            → timestamptz
processed_at          → timestamptz
observed_at           → timestamptz
```

Do not add time-of-day merely because the database supports it.

Precision is part of semantics.

---

# 22. Temporal Ordering and Late Arrivals

Distributed systems frequently receive facts out of order.

Example:

```text
Event A: valid 10:00, received 10:05
Event B: valid 09:00, received 10:10
```

The later database arrival does not mean event B happened later.

A robust event model may need:

```text
occurred_at
received_at
processed_at
```

and potentially a source sequence number.

Never reconstruct business chronology solely from insertion order when upstream systems provide their own event time.

---

# 23. Temporal Corrections

Suppose a tax rate was incorrectly recorded:

```text
20% valid Jan 1 → Mar 1
```

but the correct historical value should have been:

```text
18% valid Jan 1 → Mar 1
```

There are at least two different operations:

### Correct the business fact

Change what the business considers true for that period.

### Preserve audit history

Retain evidence that the database previously contained 20% and when that state existed.

A single version table may not satisfy both requirements unless transaction-time history is preserved separately.

This is where bitemporal modeling becomes relevant.

---

# 24. Bitemporal Modeling

Bitemporal data tracks two temporal dimensions:

```text
Valid time
+
Transaction time
```

Conceptually:

```text
fact
valid_during
recorded_during
```

Example:

```text
Tax rate = 18%
Business-valid:    [Jan 1, Mar 1)
Database-known:    [Feb 10, Mar 20)
```

A later correction might reveal that the 18% fact should have been valid since January 1 even though the database only knew it starting February 10.

Bitemporal modeling allows questions such as:

> What did we believe was true on February 15 about the business state of January 20?

That is fundamentally different from:

> What was actually valid on January 20?

Bitemporal schemas are substantially more complex and should not be introduced merely because “audit sounds good.”

---

# 25. Temporal Tables and Audit Logs Are Not Automatically the Same

An audit log usually answers:

```text
who changed what and when?
```

A temporal business table answers:

```text
what business state was valid during interval X?
```

A single audit log may not provide efficient or semantically correct point-in-time queries.

Conversely, a version table may not preserve enough details about the exact transaction that created each version.

Mature systems may use both:

```text
Business temporal model
        +
Audit/event history
```

Each serves a different purpose.

---

# 26. Temporal Constraints vs Application Checks

Naive implementation:

```text
BEGIN
SELECT whether interval is free
INSERT booking
COMMIT
```

Two concurrent requests can both see the interval as free.

Result:

```text
Request A → free
Request B → free
Request A → insert
Request B → insert
```

Application-level checking alone is not race-safe.

Improved approach:

```text
EXCLUDE / WITHOUT OVERLAPS
        ↓
Database checks conflicting committed/concurrent rows
        ↓
One transaction succeeds
Other transaction receives constraint violation
```

Then the application handles the error deterministically.

---

# 27. Reservation Example

Suppose rooms cannot have overlapping bookings.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL REFERENCES rooms(id),
    booked_during tstzrange NOT NULL,
    CONSTRAINT room_booking_no_overlap
        EXCLUDE USING gist (
            room_id WITH =,
            booked_during WITH &&
        )
);
```

The model states the rule directly:

```text
same room
AND
overlapping interval
→ forbidden
```

This is much stronger than an application convention.

---

# 28. PostgreSQL 18 `WITHOUT OVERLAPS` Example

The same category of temporal uniqueness can now be expressed with a temporal unique/primary key shape:

```sql
CREATE TABLE employee_assignment (
    employee_id bigint NOT NULL,
    valid_during daterange NOT NULL,
    branch_id bigint NOT NULL,
    PRIMARY KEY (employee_id, valid_during WITHOUT OVERLAPS)
);
```

This expresses:

```text
An employee may have multiple historical assignments,
but their valid periods cannot overlap.
```

PostgreSQL documents that the `WITHOUT OVERLAPS` column must be a range or multirange type and that the temporal constraint is implemented using GiST-style exclusion semantics. citeturn154689search0

# 29. Temporal Referential Integrity

A difficult business rule is:

> Every invoice line's tax jurisdiction must have had a valid tax configuration for the entire invoice line validity period.

Ordinary FK:

```text
invoice_line.tax_rule_id → tax_rule.id
```

proves only identity existence.

It does not prove temporal coverage.

Temporal referential integrity asks:

```text
Referenced versions
must collectively cover
referencing period
```

PostgreSQL 18's `PERIOD` foreign-key support directly addresses this class of invariant. citeturn154689search0turn154689search1

---

# 30. Temporal Coverage Is Different From Non-Overlap

These are separate invariants.

### Non-overlap

```text
No two periods conflict.
```

### Coverage

```text
The parent timeline fully covers the child timeline.
```

A set of parent rows can satisfy non-overlap but still contain gaps:

```text
Jan → Feb
Mar → Apr
```

The gap in February may violate a coverage rule.

Expert lesson:

> **Non-overlap and complete coverage are different temporal invariants.**

---

# 31. Temporal Aggregation

Time-aware reporting usually requires deciding the grain first.

Example:

```text
Daily sales
Monthly price history
Current active subscriptions
Revenue valid during a quarter
```

Never silently mix:

```text
transaction time
```

with:

```text
business valid time
```

For financial reporting, define explicitly whether a measure is grouped by:

```text
invoice date
payment date
posting date
business-valid date
```

The correct SQL depends on that semantic decision.

---

# 32. Temporal Joins

A temporal join typically joins on both identity and overlapping/containing time.

Conceptually:

```sql
SELECT ...
FROM employee_assignment ea
JOIN branch_policy bp
  ON bp.branch_id = ea.branch_id
 AND bp.valid_during && ea.valid_during;
```

But overlap alone may not be the desired semantic.

You may need:

```text
contains
intersection
full coverage
point-in-time equality
```

The business definition should determine the operator.

---

# 33. Interval Intersection

PostgreSQL range operators can compute intersections.

Conceptually:

```sql
SELECT ea.valid_during * bp.valid_during AS overlap_period
FROM employee_assignment ea
JOIN branch_policy bp
  ON bp.branch_id = ea.branch_id
 AND bp.valid_during && ea.valid_during;
```

This is useful in:

- revenue allocation
- policy matching
- availability systems
- workforce scheduling
- entitlement calculations

But be careful about empty intersections and endpoint semantics.

---

# 34. Temporal Version Number Is Not a Substitute for Time

A common design is:

```text
version = 1, 2, 3, 4
```

This gives ordering but not temporal meaning.

Version 4 does not tell you:

```text
when it became effective
```

or:

```text
how long it remained valid
```

Version numbers can complement temporal columns, not replace them when business time matters.

---

# 35. “Latest Row” Is Not Always “Current Row”

Consider:

```text
Row 1: valid [Jan, Feb), inserted Jan 1
Row 2: valid [Feb, Mar), inserted Jan 15
Row 3: correction to Row 1 inserted Mar 10
```

The latest inserted row may not be the row valid now.

Queries like:

```sql
ORDER BY created_at DESC
LIMIT 1
```

are often semantically wrong for temporal business state.

Use the correct time dimension.

---

# 36. Temporal Delete Semantics

Deleting a current row may erase history.

Potential alternatives include:

### Close the interval

```text
[Jan 1, infinity)
→
[Jan 1, Jun 1)
```

### Insert a new status/version

```text
ACTIVE
INACTIVE
```

### Tombstone event

Retain explicit evidence of deactivation.

The right design depends on whether deletion means:

```text
business ceases to be valid
```

or:

```text
physical data should disappear
```

These are not automatically the same operation.

---

# 37. Soft Delete Is Also a Temporal Problem

A column such as:

```sql
deleted_at timestamptz
```

is itself temporal state.

It answers:

```text
When was this entity considered deleted?
```

But it does not answer:

```text
When was it valid?
```

or:

```text
When was deletion recorded?
```

For systems requiring detailed history, a single `deleted_at` is not a substitute for a complete lifecycle model.

---

# 38. Temporal Partitioning Is a Separate Concern

Partitioning by time can improve management and retention:

```text
2026-01 partition
2026-02 partition
2026-03 partition
```

But partitioning is not itself temporal modeling.

A partition boundary describes physical storage organization.

A validity interval describes business meaning.

Do not assume:

```text
partitioned by date = temporal database
```

PostgreSQL's partitioning documentation describes range partitioning as a storage/data-placement mechanism where partition bounds define which key values belong to each partition. citeturn154689search7

---

# 39. Temporal Tables and Multi-Tenancy

For a multi-tenant system, temporal uniqueness is rarely just:

```text
product_id + valid_during
```

because the same product identifier may exist in multiple tenants.

The invariant may instead be:

```text
tenant_id
+
product_id
+
valid_during
```

For example:

```sql
PRIMARY KEY (
    tenant_id,
    product_id,
    valid_during WITHOUT OVERLAPS
)
```

or an equivalent exclusion design on supported PostgreSQL versions.

Tenant identity must participate in every invariant whose scope is tenant-local.

This is critical in ERP architectures.

---

# 40. Temporal Modeling in a Jewellery ERP

Consider a product price that changes over time by branch.

Business rule:

```text
One branch/product may have many historical prices,
but two active price periods cannot overlap.
```

A strong model is:

```text
product_price
-------------
tenant_id
branch_id
product_id
valid_during
amount
currency
source
created_at
created_by
```

The temporal identity might be:

```text
tenant + branch + product + validity
```

Business questions become direct:

```text
What was the price on a sale date?
What price was active when an invoice was posted?
Which future prices are scheduled?
Are there overlapping price definitions?
```

The database can enforce overlap instead of relying on the UI to prevent conflicting ranges.

---

# 41. Snapshot vs Reference Semantics

Suppose an invoice line stores:

```text
product_id
unit_price = 1500
```

Later the product price changes to 1700.

Should historical invoices display 1700 or 1500?

The answer is usually:

```text
1500
```

because invoice pricing is an historical snapshot of the transaction.

This is intentional denormalization, not bad normalization.

A live join to the current product price would corrupt historical semantics.

Expert principle:

> **Historical transactional truth often requires immutable snapshots even when a normalized reference remains available.**

---

# 42. Temporal Snapshot Design

A transaction record may intentionally contain:

```text
customer_name_snapshot
billing_address_snapshot
unit_price_snapshot
tax_rate_snapshot
currency_snapshot
```

These values describe what was used at transaction time.

The normalized entities still exist:

```text
customer
product
address
tax_rule
```

But historical documents should not depend on mutable current state.

Temporal modeling therefore interacts directly with denormalization decisions from Chapter 02.5.

---

# 43. Current State + History Hybrid

A common production architecture uses both:

```text
current table
+
history/version table
```

Example:

```text
customer
--------
id
current_status

customer_status_history
-----------------------
customer_id
status
valid_during
```

Advantages:

- simple hot-path current reads
- explicit history
- clear separation of operational and historical access patterns

Costs:

- synchronization complexity
- duplicated state
- migration complexity

This pattern is justified when current reads dominate and historical reconstruction has different access characteristics.

---

# 44. Anti-Pattern: One Row Plus `updated_at`

Naive design:

```sql
status text,
updated_at timestamptz
```

and later:

> “We can tell the history from updated_at.”

No.

`updated_at` tells you when the current row was last modified. It does not contain prior states.

Once the old value is overwritten, history is gone unless captured elsewhere.

---

# 45. Anti-Pattern: Storing Dates as Text

Bad:

```text
valid_period = '01-01-2026 to 31-03-2026'
```

This breaks:

- indexing
- comparison
- overlap semantics
- constraints
- timezone/type correctness
- queryability

Use typed temporal values.

---

# 46. Anti-Pattern: Overlap Check in Node.js Only

Bad:

```text
SELECT free interval
→ application decides yes
→ INSERT
```

This is vulnerable to concurrent races.

Improved:

```text
application performs optional pre-check
+
database constraint remains authoritative
```

The pre-check is UX optimization.

The constraint is correctness.

---

# 47. Anti-Pattern: Using `BETWEEN` Carelessly

Temporal boundaries require explicit semantics.

For half-open intervals:

```text
[start, end)
```

prefer range operators or explicit inequalities that match the contract.

A naive:

```sql
WHERE event_time BETWEEN start_time AND end_time
```

uses inclusive semantics and may produce endpoint bugs when adjacent intervals are expected to remain distinct.

---

# 48. Anti-Pattern: “Current = MAX(valid_from)”

This can fail when:

- future rows exist
- late-arriving corrections exist
- periods overlap due to corrupted data
- validity has explicit end times
- transaction time differs from valid time

Current state is a temporal predicate, not necessarily a maximum version number.

---

# 49. Performance: Indexing Temporal Queries

GiST indexes are particularly important for range overlap/containment workloads.

For example:

```sql
CREATE INDEX product_price_valid_during_gist
ON product_price
USING gist (valid_during);
```

For tenant/product scoped overlap searches, a multicolumn GiST or temporal constraint structure may be appropriate.

Performance should be measured with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

Do not assume that every temporal query automatically becomes index-friendly merely because a range column exists.

Planner selectivity, query shape, correlation, data distribution, and index design still matter.

---

# 50. `btree_gist` and Mixed Temporal Constraints

Suppose the invariant is:

```text
same tenant
same resource
intervals cannot overlap
```

You may need equality semantics for scalar identifiers alongside range overlap semantics.

`btree_gist` provides GiST operator classes for many data types commonly handled by B-tree semantics, enabling combinations such as:

```sql
EXCLUDE USING gist (
    tenant_id WITH =,
    resource_id WITH =,
    valid_during WITH &&
)
```

This lets one database-level rule encode the complete conflict condition.

---

# 51. Temporal Query Selectivity

A range query can still be expensive when most rows overlap the requested interval.

For example:

```text
99% of rows overlap this period
```

An index may provide little benefit compared with a sequential scan.

Thus:

```text
indexed ≠ guaranteed fast
```

Measure:

```text
rows examined
rows returned
buffer hits
buffer reads
execution time
planning time
```

Temporal optimization follows the same evidence-first discipline as ordinary SQL optimization.

---

# 52. Temporal Data and TOAST / Row Width

Historical schemas can grow rapidly.

A version table may multiply row counts:

```text
1 customer
→ 40 historical versions
```

If each version stores large JSON snapshots, documents, or addresses, storage growth becomes substantial.

Ask:

```text
What must be reconstructed?
What can be referenced?
What must be immutable?
```

Avoid blindly copying entire large objects into every historical version.

---

# 53. Temporal Retention

History is not automatically “keep forever.”

Different classes of temporal data may have different retention rules:

```text
operational history → 2 years
financial history   → 7+ years
debug telemetry    → 90 days
security audit     → policy-defined
```

Retention is both a storage and compliance design concern.

Deleting history can destroy the ability to answer historical queries, so retention policies belong in the data model and governance model.

---

# 54. Temporal Privacy and Security

Historical data can be more sensitive than current state.

An old address, phone number, pricing contract, or personal status may remain in history indefinitely.

Therefore:

```text
history visibility
≠ current-row visibility
```

Consider:

- row-level security
- role-specific history access
- masking
- retention
- encryption at rest
- secure audit channels
- data minimization

A history table is not automatically safe merely because the application hides it from the main UI.

---

# 55. RLS and Temporal Queries

In multi-tenant PostgreSQL systems, RLS policies must account for temporal rows.

A query such as:

```sql
WHERE valid_during @> now()
```

should not be treated as a substitute for tenant authorization.

Conceptually:

```text
tenant authorization
AND
point-in-time predicate
```

Both must hold.

Temporal correctness and security correctness are separate invariants.

---

# 56. Temporal Migrations

Adding temporal history to an existing current-state table is risky.

Current data may tell you:

```text
current_status
updated_at
```

but not:

```text
all prior states
```

A migration cannot reconstruct information that was never stored.

A sound rollout may therefore be:

```text
1. Create history/version structure
2. Define semantics
3. Capture new changes
4. Backfill only defensible historical facts
5. Validate
6. Switch read paths
7. Remove obsolete assumptions later
```

Be honest about the historical boundary:

> “Complete history begins on 2026-09-01.”

rather than inventing historical certainty.

---

# 57. Backfilling Validity Intervals

Suppose historical rows have:

```text
changed_at
```

but not `valid_from` and `valid_to`.

You may infer intervals using ordering:

```sql
lead(changed_at) over (
    partition by customer_id
    order by changed_at
)
```

Then derive:

```text
[changed_at, next_changed_at)
```

But that is only valid if `changed_at` actually means business-valid start time.

Do not confuse:

```text
recorded change time
```

with:

```text
business effective time
```

# 58. Testing Temporal Invariants

Temporal systems need adversarial tests.

Test:

```text
adjacent periods
identical boundaries
overlapping periods
contained periods
unbounded periods
empty ranges
NULL ranges
future periods
backdated corrections
concurrent inserts
concurrent updates
DST boundaries
timezone conversions
leap days
month-end
year-end
```

A temporal implementation that works only for ordinary dates is not production-ready.

---

# 59. Concurrency Test

A particularly valuable test is:

```text
Transaction A:
insert resource 7 [10:00, 11:00)

Transaction B:
insert resource 7 [10:30, 11:30)
```

Run them concurrently.

Expected:

```text
one transaction succeeds
one transaction fails due to temporal integrity
```

If both succeed, your correctness boundary is incomplete.

# 60. Node.js / NestJS Mapping

Application DTO:

```ts
interface PriceVersion {
  productId: string;
  validFrom: string;
  validTo: string | null;
  amount: string;
}
```

Database model:

```text
valid_during tstzrange
```

You must define a serialization contract.

A safe API representation may be:

```json
{
  "validFrom": "2026-10-01T00:00:00Z",
  "validTo": "2026-11-01T00:00:00Z",
  "bounds": "[)"
}
```

Do not let different endpoints silently adopt different boundary semantics.

---

# 61. API PATCH Semantics for Temporal Data

A generic PATCH like:

```json
{
  "price": 500
}
```

is insufficient when the business model is temporal.

An explicit command is safer:

```json
{
  "price": "500.00",
  "effectiveFrom": "2026-10-01"
}
```

The command handler then decides whether to:

```text
close current version
insert future version
split an interval
reject overlap
backdate correction
```

Temporal operations should be modeled as business commands, not generic property updates.

---

# 62. ORM Caveat

Some ORMs expose timestamp columns naturally but provide limited first-class support for PostgreSQL range semantics and temporal constraints.

Do not weaken the database model merely to fit ORM convenience.

The application layer can use:

- raw SQL for temporal predicates
- custom types
- query builders
- database views
- repository methods

The database remains authoritative for temporal integrity.

# 64. Debugging Temporal Bugs

When a temporal query is wrong, inspect the full state:

```text
business key
valid_during
transaction/recorded time
source event time
created_at
updated_at
actor
request id
```

Then ask:

```text
Which time dimension did this query use?
What was the intended boundary convention?
Were intervals normalized?
Could concurrency have created conflicting state?
Was the fact corrected later?
Was the current row confused with the latest row?
```

Temporal bugs are frequently semantic bugs before they are SQL syntax bugs.

# 65. Solution Pattern: Overlap Prevention

## Naive Approach

```text
SELECT ... overlap ...
if none:
    INSERT
```

## Why It Fails

Concurrent requests can race between the read and write.

## Improved Approach

Use a database temporal constraint.

```sql
EXCLUDE USING gist (... WITH &&)
```

or PostgreSQL 18 temporal uniqueness where appropriate:

```sql
UNIQUE (..., valid_during WITHOUT OVERLAPS)
```

## Why It Works

The database owns the correctness invariant.

## Production Considerations

Handle constraint violations explicitly and ensure retry/error semantics are deterministic.

## Alternative

Serializable transactions can protect certain conflict patterns, but are broader and can carry greater transaction-abort costs than a precise constraint.

## Trade-Off

Declarative temporal integrity is usually preferable when the business invariant is expressible directly, while application logic remains responsible for user-facing conflict resolution.

# 66. Solution Pattern: Historical Price

## Naive Approach

Store only:

```text
current_price
updated_at
```

## Why It Fails

Historical state disappears.

## Improved Approach

Use:

```text
price versions
+
validity interval
+
non-overlap invariant
```

## Why It Works

The database can reconstruct historical state using temporal predicates.

## Production Considerations

Keep transaction snapshots immutable where documents must preserve exact historical values.

## Alternative

Use an event-sourced pricing history if the organization already operates an event-sourcing architecture.

## Trade-Off

A temporal relational model is often simpler for direct SQL reporting; event sourcing can provide richer event history but adds considerable architectural complexity.

# 68. Common Developer Mistakes

## Mistake 1 — `updated_at` is treated as history

It is not.

## Mistake 2 — `valid_to = NULL` is left undefined

Decide whether NULL means:

```text
unknown
```

or:

```text
open-ended
```

and encode the intended semantics consistently.

## Mistake 3 — Endpoints are undocumented

Teams disagree about whether the upper bound is included.

## Mistake 4 — Overlap validation exists only in the service

Concurrency defeats it.

## Mistake 5 — Current price is joined into historical invoices

This rewrites history accidentally.

## Mistake 6 — Time zone semantics are implicit

A local business timestamp becomes a UTC bug.

## Mistake 7 — “Latest” is confused with “currently valid”

Insertion order and business validity are different concepts.

## Mistake 8 — History tables expose sensitive data without separate authorization

Historical rows can be more sensitive than current rows.

# 69. AI / Vibe-Coding Failure Patterns

AI-generated temporal schemas frequently look plausible while encoding the wrong semantics.

### Failure 1

```sql
valid_from timestamp,
valid_to timestamp
```

but no documented boundary convention.

### Failure 2

Generated query:

```sql
ORDER BY created_at DESC
LIMIT 1
```

used to answer “current version.”

### Failure 3

Application overlap query generated without a database constraint.

### Failure 4

Using `timestamp` where the domain requires an absolute instant.

### Failure 5

Replacing historical snapshots with live joins to current records.

### Failure 6

Adding temporal columns everywhere “for audit” without defining their meanings.

### Failure 7

Blindly introducing bitemporal complexity where ordinary valid-time history is sufficient.

AI-generated SQL must be challenged with:

```text
What time dimension is this?
What does the range mean?
Are boundaries inclusive?
What prevents overlap?
What happens concurrently?
Can historical state actually be reconstructed?
```

# 75. Final Mental Model

Think of temporal modeling as a chain:

```text
Business Fact
    ↓
What exactly changes?
    ↓
Which time dimension matters?
    ↓
What is the row grain?
    ↓
What interval semantics apply?
    ↓
Which states are legal?
    ↓
Which constraints enforce them?
    ↓
How does concurrency behave?
    ↓
How is current state queried?
    ↓
How is historical state reconstructed?
    ↓
How are corrections represented?
    ↓
How long is history retained?
    ↓
Who may access it?
```

The most important insight is:

> **Temporal data modeling is not adding timestamps. It is defining the meaning, validity, history, and reconstruction rules of facts whose truth changes over time.**

A production-quality temporal schema makes the time semantics explicit, turns temporal invariants into database-enforceable rules where possible, preserves historical truth intentionally, and makes concurrency and correction behavior part of the design rather than afterthoughts.
