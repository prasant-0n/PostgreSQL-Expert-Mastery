# 02.3 — Normalization & Functional Dependencies

> **Phase 02 — Relational Data Modeling**  
> **Level:** Core → Advanced → Production Design  
> **Goal:** Learn to derive relational schemas from facts and dependencies, recognize update anomalies, apply normalization deliberately, and make evidence-based denormalization decisions.

---

## 1. Chapter Objective

Normalization is often taught as a checklist — “1NF, 2NF, 3NF, BCNF.” That is useful for vocabulary, but insufficient for engineering.

The real skill is to answer:

> **What facts does this database represent, what determines what, and how should those facts be stored so that every fact has one authoritative home without making valid queries unnecessarily difficult?**

By the end of this chapter you should be able to:

- identify the **grain** of a relation before choosing columns;
- distinguish attributes from facts about relationships;
- express business rules as functional dependencies;
- find candidate keys and reason about superkeys;
- detect partial, transitive, multivalued, and join dependencies;
- explain update, insertion, and deletion anomalies from first principles;
- normalize schemas to 1NF, 2NF, 3NF, and BCNF when appropriate;
- understand why normalization is not “split every table”; 
- preserve lossless joins and, where possible, dependency preservation;
- distinguish normalization from indexing, partitioning, or general performance tuning;
- recognize intentional denormalization such as snapshots, cached aggregates, and immutable transaction facts;
- design normalized PostgreSQL schemas that remain correct under concurrency and evolving requirements;
- review AI-generated schemas for false dependencies, arbitrary normalization, and duplicated sources of truth.

---

## 2. Three Definitions

### Simple definition

Normalization is organizing relational data so that each fact is stored in an appropriate place and avoidable redundancy does not create inconsistent data.

### Engineering definition

Normalization decomposes relations according to their functional and other dependencies while preserving the ability to reconstruct the intended information and enforce business rules correctly.

### Expert definition

Normalization is a **schema synthesis and decomposition discipline** based on dependencies and relational semantics. A sound decomposition aims to represent facts at their correct grain, avoid anomalous redundancy, preserve required dependencies where practical, and guarantee lossless reconstruction of the original relation.

The important word is **dependencies**. You cannot normalize correctly if you do not know what the data means.

---

# 3. The First Principle: Model Facts, Not Screens

Suppose a screen displays:

```text
Order #10042
Customer: Priya
Customer Phone: +91...
Branch: Hyderabad
Salesperson: Arjun

Product      Qty    Unit Price
Ring          1       25,000
Chain         2       18,000
```

A novice may create one giant table because the UI appears to be one “order page.”

That is backwards.

The database should ask:

- What is an order?
- What is a customer?
- What is a product?
- What is an order line?
- Which facts belong to the relationship between order and product?
- Which values are current master data and which are historical transaction facts?

The screen is a **presentation model**.

The relational schema is a **fact model**.

They may overlap, but they are not the same thing.

---

# 4. Grain Comes Before Normalization

Before discussing normal forms, define the **grain** of a relation.

> The grain is what one row represents.

Examples:

```text
customer
→ one row = one customer

order
→ one row = one order

order_item
→ one row = one product occurrence in one order

employee_branch_assignment
→ one row = one employee assignment to one branch
```

A table with an unclear grain is almost impossible to normalize correctly.

## Example

Consider:

```text
order_id | customer_id | customer_name | product_id | product_name | qty
```

What does one row represent?

Possibilities:

- one order;
- one product inside an order;
- one customer-product combination;
- one order-product occurrence.

If the answer is “one order,” then repeated products reveal a grain violation.

If the answer is “one order line,” then customer attributes are duplicated across every line.

The first normalization question is therefore not:

> “Is this 3NF?”

It is:

> **“What does one row mean?”**

---

# 5. Functional Dependencies

Functional dependency is the core reasoning tool.

We write:

```text
X → Y
```

and read it as:

> If two rows agree on X, they must agree on Y.

X **functionally determines** Y.

## Example

Suppose `customer_id` uniquely identifies a customer:

```text
customer_id → customer_name, email, phone
```

That means a customer ID determines those attributes.

It does **not** automatically mean:

```text
customer_name → customer_id
```

A name may not be unique.

Do not confuse business intuition with an actual dependency.

---

# 6. Functional Dependency Is a Business Rule

Dependencies come from semantics, not from whatever values happen to appear in today’s data.

Suppose a dataset currently contains:

```text
branch_code | branch_manager
------------+---------------
HYD         | Ravi
BBS         | Sneha
```

You might infer:

```text
branch_code → branch_manager
```

But whether this is valid depends on the business rule.

If multiple managers can exist over time, the dependency may only be true for a temporal assignment relation.

A dependency is therefore a statement about **all valid states**, not merely the current sample.

---

# 7. Candidate Keys

A **superkey** is a set of attributes that uniquely identifies a row.

A **candidate key** is a minimal superkey.

A relation may have several candidate keys.

Example:

```text
employee
--------
employee_id
corporate_email
pan_number
```

Suppose all three are unique and stable enough to identify an employee.

Then you may have candidate keys such as:

```text
{employee_id}
{corporate_email}
{pan_number}
```

One is selected as the primary key, but the others remain candidate keys that usually deserve unique constraints if the business rule requires uniqueness.

## Important distinction

```text
Primary Key ≠ only key that can identify a row
```

It is the chosen primary identifier, not the mathematical definition of uniqueness.

---

# 8. Prime and Non-Prime Attributes

In classical normalization reasoning:

- **prime attribute** = part of at least one candidate key;
- **non-prime attribute** = not part of any candidate key.

These terms become important when evaluating 2NF and 3NF.

Do not memorize them separately from candidate keys. They are derived from candidate-key analysis.

---

# 9. Armstrong’s Axioms — The Reasoning Toolkit

Functional dependencies can be derived using inference rules.

The classic Armstrong axioms are:

### Reflexivity

If Y is a subset of X:

```text
X → Y
```

This is trivially true.

### Augmentation

If:

```text
X → Y
```

then:

```text
XZ → YZ
```

### Transitivity

If:

```text
X → Y
Y → Z
```

then:

```text
X → Z
```

These rules help reason about implied dependencies.

## Derived rules

Useful derived forms include:

```text
Union:
X → Y
X → Z
therefore X → YZ

Decomposition:
X → YZ
therefore X → Y
X → Z

Pseudotransitivity:
X → Y
WY → Z
therefore WX → Z
```

You rarely need to perform formal dependency inference in application code, but the mental model is extremely useful during schema design.

---

# 10. Attribute Closure

The closure of a set X under functional dependencies F, written roughly as:

```text
X+
```

is the set of attributes functionally determined by X.

This is one of the most useful manual techniques for finding candidate keys.

## Example

Relation:

```text
R(A, B, C, D)
```

Dependencies:

```text
A → B
B → C
AC → D
```

Start with:

```text
A+ = {A}
```

Using `A → B`:

```text
A+ = {A, B}
```

Using `B → C`:

```text
A+ = {A, B, C}
```

Now `AC → D` applies because A and C are known:

```text
A+ = {A, B, C, D}
```

Therefore A is a superkey.

If no proper subset of A is a superkey, A is a candidate key.

---

# 11. Why Redundancy Is Dangerous

Redundancy is not automatically wrong.

The problem is **duplicated facts that can disagree**.

Consider:

```text
order_id | customer_id | customer_name | product_id | product_name
```

Suppose one customer has 100 orders.

The customer's name may be repeated across 100 rows.

That creates several anomalies.

---

# 12. Update Anomaly

Suppose customer `C101` changes their legal name.

If the name is duplicated across 100 order rows, every copy must be updated.

If 99 are updated and one remains stale:

```text
same customer_id
→ two different customer names
```

The database now contains contradictory facts.

Normalization attempts to give the customer name one authoritative home.

---

# 13. Insert Anomaly

Suppose the only place product data can be stored is inside `order_item`.

Then you cannot register a product until someone creates an order.

But the business may need to create a product first.

That is an insertion anomaly.

The problem is not SQL syntax.

The problem is mixing two different facts:

```text
product exists
```

and:

```text
product was sold in an order
```

---

# 14. Delete Anomaly

Suppose a product's only stored row is the last order line containing it.

Deleting the order may accidentally delete the only record describing the product.

The order fact and the product fact should not have the same lifecycle if they are independent business concepts.

---

# 15. First Normal Form — 1NF

At a practical level, 1NF is commonly associated with relations whose attributes contain atomic values rather than repeating groups or nested relational structures.

For PostgreSQL engineers, be careful with the word **atomic**.

PostgreSQL supports arrays, JSONB, ranges, composite types, and other complex values.

That does not mean every complex value violates a useful relational design.

The better engineering question is:

> **Does the attribute represent one scalar fact for this relation's grain, or am I hiding a separate relation inside one column?**

## Bad design

```text
order_id | product_ids
---------+--------------------
1001     | {10,11,12}
```

If the business needs independent facts about each ordered product — quantity, price, tax, discount, fulfillment state — this is usually a hidden child relation.

Better:

```text
orders
order_items
```

with one row per order item.

## But arrays can be valid

```text
user
----
user_id
preferred_languages text[]
```

If the array is genuinely a single attribute with no independent identity or per-element lifecycle, it can be appropriate.

Normalization is semantic, not ideological.

---

# 16. Second Normal Form — 2NF

2NF matters primarily when a relation has a **composite candidate key**.

A relation is in 2NF when every non-prime attribute is fully functionally dependent on the whole candidate key, not merely part of it.

## Classic example

Suppose:

```text
enrollment
----------
student_id
course_id
student_name
course_name
grade
```

Candidate key:

```text
(student_id, course_id)
```

Dependencies:

```text
student_id → student_name
course_id → course_name
(student_id, course_id) → grade
```

`student_name` depends only on `student_id`.

`course_name` depends only on `course_id`.

These are **partial dependencies**.

Decompose:

```text
student
-------
student_id
student_name

course
------
course_id
course_name

enrollment
----------
student_id
course_id
grade
```

Now each fact is stored at its appropriate grain.

---

# 17. Third Normal Form — 3NF

3NF removes problematic **transitive dependencies** of non-key attributes on candidate keys.

Classic example:

```text
employee
--------
employee_id
employee_name
department_id
department_name
```

Dependencies:

```text
employee_id → department_id
department_id → department_name
```

Therefore:

```text
employee_id → department_name
```

through a non-key attribute.

Better:

```text
employee
--------
employee_id
employee_name
department_id

department
----------
department_id
department_name
```

Again, the deeper reason is not “3NF says split it.”

The reason is that department name is a fact about the department, not about each employee row.

---

# 18. A Practical Interpretation of 3NF

A useful engineering heuristic is:

> **Non-key attributes should describe the key, the whole key, and not another non-key fact.**

This is a memory aid, not a replacement for formal analysis.

The actual questions are:

1. What are the candidate keys?
2. What dependencies hold?
3. Where does each fact naturally belong?
4. Does redundancy create anomalies?

---

# 19. BCNF

Boyce–Codd Normal Form is stricter than 3NF.

For every non-trivial functional dependency:

```text
X → Y
```

X should be a superkey.

BCNF catches some dependency structures that can still satisfy 3NF.

## Why this matters

3NF sometimes permits a non-key determinant because protecting dependency preservation can be useful.

BCNF prioritizes stronger elimination of redundancy caused by functional dependencies.

In production design, you should know both, but do not mechanically chase BCNF without considering:

- required dependencies;
- enforcement mechanisms;
- query patterns;
- application workflows;
- performance;
- temporal semantics.

---

# 20. Lossless Join Decomposition

Normalization is not successful merely because several smaller tables look cleaner.

A decomposition must avoid inventing false rows when the original relation is reconstructed.

This is the **lossless join** requirement.

## Intuition

Suppose an original relation contains:

```text
customer_id | customer_name | branch_id | branch_name
```

and you decompose it into:

```text
customer(customer_id, customer_name)
branch(branch_id, branch_name)
```

Joining these without a relationship between customer and branch can create combinations that never existed.

That is a lossy decomposition.

The correct decomposition needs the relationship fact:

```text
customer(customer_id, customer_name, branch_id)
branch(branch_id, branch_name)
```

or another explicit assignment relation if the business allows many-to-many or temporal assignments.

---

# 21. Dependency Preservation

A decomposition is **dependency preserving** when important dependencies of the original relation can be enforced by checking the decomposed relations without reconstructing the original relation.

This matters operationally because database constraints work on actual stored structures.

If a business rule becomes impossible to enforce locally after decomposition, you may have increased theoretical purity while making the production system harder to guarantee.

---

# 22. 4NF and Multivalued Dependencies

4NF deals with **multivalued dependencies**, where independent multi-valued facts are represented together and create unnecessary combinations.

Consider:

```text
employee_id | skill  | language
```

Suppose an employee independently has:

```text
skills = {SQL, JS}
languages = {English, Hindi}
```

The combined relation may contain:

```text
SQL | English
SQL | Hindi
JS  | English
JS  | Hindi
```

If skill membership and language membership are independent facts, the four combinations are not four independent facts; they are a multiplication artifact.

Better:

```text
employee_skill(employee_id, skill)
employee_language(employee_id, language)
```

The key idea is independence of multi-valued facts.

---

# 23. 5NF and Join Dependencies

5NF deals with more complex cases where a relation can be decomposed into smaller relations and reconstructed only through multiple joins.

These cases are less common in ordinary application schemas, but the concept matters for expert-level relational reasoning:

> A relation should not represent a complex join relationship if the underlying business facts can be represented independently and reconstructed without spurious combinations.

Do not use 5NF vocabulary as decoration. It is useful when the actual dependency structure demands it.

---

# 24. Normalization Example — Jewellery ERP

Imagine an ERP initially stores:

```text
sales_line
----------
sale_id
branch_id
branch_name
customer_id
customer_name
salesperson_id
salesperson_name
item_id
item_name
metal_type
purity
quantity
unit_price
tax_rate
```

The row grain should be:

```text
one row = one sold item line in one sale
```

Now identify facts.

### Sale facts

```text
sale_id
customer_id
branch_id
salesperson_id
sale_date
```

### Customer facts

```text
customer_id
customer_name
...
```

### Branch facts

```text
branch_id
branch_name
...
```

### Employee facts

```text
salesperson_id
salesperson_name
...
```

### Item master facts

```text
item_id
item_name
metal_type
purity
...
```

### Sale-line facts

```text
sale_id
line_no
item_id
quantity
unit_price
line_discount
line_tax
```

But now an important historical question appears.

Should `unit_price` be copied from the current product master every time a sale is displayed?

Usually no.

The selling price at transaction time is a fact of the **sale line**.

That is deliberate redundancy only in the sense that a value also exists conceptually in product pricing structures. It is not necessarily bad normalization because the two values represent different facts with different lifecycles:

```text
current catalog price
vs
actual transaction price
```

This is why normalization must follow semantics, not column similarity.

---

# 25. Current-State Facts vs Historical Facts

This is one of the most important production distinctions.

Suppose:

```text
product.current_price = 30,000
```

and a historical sale contains:

```text
sale_item.unit_price = 24,500
```

These are both correct.

Do not “normalize” them by removing the historical transaction price.

Historical transactions often require **snapshot facts** because the world changes.

Common examples:

```text
invoice billing address
order shipping address
sale tax rate
transaction exchange rate
product name at transaction time
customer legal name printed on invoice
```

The snapshot is part of the transaction record's meaning.

---

# 26. Normalization vs Denormalization

A common false dichotomy is:

```text
normalized = good
 denormalized = bad
```

That is incorrect.

A better model is:

```text
Normalize for correctness.
Denormalize for a demonstrated workload requirement.
```

Denormalization should answer a concrete problem such as:

- repeated expensive aggregation;
- read-path latency requirements;
- reporting architecture;
- immutable historical snapshots;
- controlled cache projection.

It should not exist because “JOINs are slow.”

---

# 27. Examples of Intentional Denormalization

## Cached aggregate

```text
customer_order_stats
--------------------
customer_id
order_count
lifetime_value
updated_at
```

This may be valid if it is explicitly a derived projection with a defined refresh strategy.

## Search document

A denormalized search representation may combine fields from multiple normalized tables.

## Historical snapshot

An invoice can store customer address as it appeared when issued.

## Materialized reporting structure

Analytics systems commonly use dimensional models that intentionally duplicate descriptive attributes for reporting performance.

In each case, there should be a clear answer to:

> **Which copy is authoritative, and how is this copy maintained?**

---

# 28. The Duplicate Source-of-Truth Anti-Pattern

The dangerous design is not “duplicate data.”

It is:

> **multiple mutable copies that the system treats as independently authoritative.**

Example:

```text
customers.phone
orders.customer_phone
crm_customer.phone
user_profile.phone
```

If all four can independently change and no one knows which is authoritative, the system has integrity debt.

The safer pattern is:

```text
customers.phone        ← authoritative
orders.customer_phone  ← immutable snapshot only if required
```

The meaning of the second column must be explicit.

---

# 29. JSONB Does Not Eliminate Modeling

A common AI-generated schema is:

```text
orders
------
id
payload jsonb
```

with everything inside `payload`:

```json
{
  "customer": {...},
  "items": [...],
  "branch": {...},
  "salesperson": {...}
}
```

This may look flexible, but it often hides relational facts.

You lose or complicate:

- foreign keys;
- unique constraints;
- dependency clarity;
- referential integrity;
- type contracts;
- targeted statistics;
- straightforward relational joins;
- safe cross-record updates.

JSONB is excellent where document semantics are actually required. It is not a substitute for deciding the relational grain.

---

# 30. Arrays and Normalization

Similarly, an array may encode a valid single-valued attribute or may conceal a relationship.

### Potentially appropriate

```text
user.preferred_locales text[]
```

### Suspicious

```text
order.product_ids bigint[]
```

The second likely hides:

```text
order_item(order_id, product_id, quantity, price, ...)
```

A reliable test is:

> Does each element have its own identity, lifecycle, attributes, constraints, or relationship to another entity?

If yes, a child relation is usually the better model.

---

# 31. Normalization Does Not Mean “No Joins”

Joins are one of the defining operations of the relational model.

The existence of a join is not evidence of bad schema design.

Bad reasoning:

```text
5-table JOIN
→ too many tables
→ denormalize
```

Better reasoning:

```text
What is the workload?
How many rows are involved?
What predicates exist?
What indexes exist?
What does EXPLAIN show?
Is the query actually expensive?
Would denormalization introduce write anomalies?
```

Performance decisions require measurements.

---

# 32. Normalization Does Not Replace Indexing

If this query is slow:

```sql
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.branch_id = $1
  AND o.created_at >= $2;
```

The answer is not automatically:

```text
copy customer_name into orders
```

The correct next step is to inspect:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

Then determine whether the actual issue is:

- missing index;
- wrong index order;
- poor selectivity;
- stale statistics;
- excessive row count;
- bad query shape;
- unnecessary columns;
- poor pagination;
- I/O pressure;
- contention.

Normalization and performance engineering are different dimensions.

---

# 33. Constraints Make Normalization Real

A beautifully normalized model that has weak constraints can still contain invalid states.

Suppose:

```text
order_item(order_id, item_id)
```

The database should typically enforce relevant existence relationships through foreign keys.

Likewise:

```text
customer.email
```

may require uniqueness depending on actual business semantics.

Normalization identifies fact ownership.

Constraints make many of those semantic rules executable.

---

# 34. Concurrency Changes the Analysis

Consider a denormalized counter:

```text
customer.order_count
```

The fact is derived from child rows.

Under concurrent inserts, a naïve read-modify-write implementation can lose updates.

Normalization plus derived state introduces a new obligation:

> **How is the projection kept correct under concurrency, retry, crash, and partial failure?**

Possible strategies include:

- derive on demand;
- transactional update;
- trigger-maintained projection;
- asynchronous projection;
- periodic recomputation.

The choice is architectural, not merely SQL style.

---

# 35. Normalization and Multi-Tenancy

In a multi-tenant ERP, dependencies must respect tenant boundaries.

Suppose:

```text
branch_id → branch_name
```

If IDs are globally unique, that may be valid.

But if the business key is only unique within a tenant:

```text
(tenant_id, branch_code) → branch_name
```

Then treating `branch_code` alone as a determinant is incorrect.

This matters enormously for normalization because a wrong dependency produces a wrong schema.

Always ask:

> **At what scope is this identifier guaranteed to be unique?**

---

# 36. Temporal Dependencies

Functional dependencies can also change by time.

Example:

```text
employee_id → branch_id
```

may be true only for the employee's current assignment.

If an employee can move between branches, the historical relation may instead be:

```text
employee_branch_assignment
--------------------------------
employee_id
branch_id
valid_from
valid_to
```

Now the fact is not:

```text
employee_id → branch_id
```

but something closer to:

```text
(employee_id, effective_period) → branch_id
```

The time dimension changes the key and therefore changes the normalization problem.

---

# 37. Business Rules Must Not Be Invented from Sample Data

One of the most dangerous modeling errors is inferring a unique key because sample data happens to be unique.

Example:

```text
phone_number
```

Current dataset:

```text
+91... → customer A
+91... → customer B
```

Actually unique today.

That does not prove phone numbers are business keys.

A schema should encode **guaranteed semantics**, not accidental current values.

Ask product/business stakeholders:

- Is uniqueness guaranteed?
- At what scope?
- For how long?
- Can the value change?
- Can two entities share it?
- Does it have legal/business significance?

---

# 38. Common Wrong Approaches

## Wrong approach 1 — “One table is simpler”

Why it fails:

- combines multiple grains;
- duplicates facts;
- creates anomalies;
- makes lifecycle boundaries unclear.

Improved approach:

Identify entities, relationships, and row grain first.

---

## Wrong approach 2 — “Every duplicate value must be normalized”

Why it fails:

Not all repeated values are duplicated facts. Historical snapshots and derived projections may intentionally repeat information.

Improved approach:

Classify each repeated value:

```text
authoritative fact
snapshot fact
derived fact
cache
accidental duplicate
```

---

## Wrong approach 3 — “Use JSONB to avoid joins”

Why it fails:

You move relational semantics into an application-managed blob.

Improved approach:

Use JSONB for document-shaped data whose internal structure genuinely benefits from document semantics. Keep core transactional relationships relational when they need relational guarantees.

---

## Wrong approach 4 — “3NF automatically means production-ready”

Why it fails:

3NF says little about:

- indexing;
- concurrency;
- partitioning;
- security;
- workload shape;
- observability;
- historical semantics;
- operational architecture.

Improved approach:

Treat normal form as one layer of schema quality.

---

# 39. AI / Vibe-Coding Failure Modes

AI-generated schemas often exhibit recognizable patterns.

### Failure A — Foreign key in a comma-separated string

```text
participant_ids = '12,15,18'
```

This hides a relation.

### Failure B — Copying every display field into transactional rows

```text
order.customer_name
order.customer_phone
order.customer_email
order.customer_address
```

without documenting whether these are snapshots or accidental copies.

### Failure C — Arbitrary uniqueness

```sql
UNIQUE(phone)
```

added because the ORM model “looked like” phone numbers were unique.

### Failure D — One JSONB payload for the entire domain

This often sacrifices constraints for perceived flexibility.

### Failure E — Over-normalization

Splitting every meaningful value into separate tables:

```text
country
country_name_translation
currency
currency_code
status
status_translation
```

without a real business reason can produce excessive complexity.

### Failure F — Denormalization before measurement

Copying fields to “avoid joins” without an observed bottleneck.

### Review rule

For every generated table ask:

```text
What does one row represent?
What are the candidate keys?
What determines each non-key attribute?
Which fact is authoritative?
Which values are snapshots or derived projections?
What constraints enforce the dependencies?
```

---

# 40. Production Design Workflow

A reliable workflow is:

```text
1. Collect business rules
2. Identify facts
3. Define row grain
4. Identify candidate keys
5. Write important functional dependencies
6. Separate independent facts
7. Test for anomalies
8. Decompose where justified
9. Check lossless reconstruction
10. Check dependency preservation
11. Add constraints
12. Design indexes for actual workloads
13. Model historical snapshots explicitly
14. Measure production queries
15. Denormalize only when evidence justifies it
16. Document authoritative vs derived data
```

This workflow is more reliable than starting from an ORM entity diagram.

# 41. Practical Decomposition Exercise

Start with:

```text
sales
-----
sale_id
sale_date
customer_id
customer_name
customer_phone
branch_id
branch_name
employee_id
employee_name
product_id
product_name
quantity
unit_price
```

Assume:

```text
customer_id → customer_name, customer_phone
branch_id → branch_name
employee_id → employee_name
product_id → product_name
sale_id → sale_date, customer_id, branch_id, employee_id
(sale_id, product_id) → quantity, unit_price
```

A reasonable decomposition is:

```text
customer
branch
employee
product
sale
sale_item
```

with relationships represented through keys.

But then ask the crucial historical question:

Should a sale item retain `product_name`?

There is no universal answer.

If invoices must reproduce the exact printed product description even after product master changes, an immutable snapshot may be correct.

Normalization does not prohibit this because it represents a different historical fact.

---

# 42. Testing a Normalized Model

Schema correctness needs tests.

## Constraint tests

Verify:

- primary keys reject duplicates;
- unique constraints reject duplicate business keys;
- foreign keys reject orphan references;
- checks reject invalid states;
- nullability reflects actual optionality.

## Dependency tests

For every asserted dependency:

```text
X → Y
```

attempt to create two rows agreeing on X but disagreeing on Y.

The database should reject that state when the rule is intended to be enforced structurally.

## Concurrency tests

Test competing operations such as:

- concurrent creation of the same business key;
- concurrent assignment updates;
- retry after unique violation;
- simultaneous derived-state updates.

## Migration tests

Before normalizing an existing legacy table:

1. discover duplicates;
2. identify contradictions;
3. define survivor rules;
4. backfill target tables;
5. validate row counts and sums;
6. add constraints after cleanup when appropriate;
7. compare old and new results.

---

# 43. Data Migration Example

Suppose legacy data contains:

```text
customer_id | customer_name
------------+--------------
1           | Priya
1           | Priya S.
1           | Priya
```

Before creating:

```sql
UNIQUE(customer_id)
```

you must decide what the contradiction means.

Potential strategies:

- authoritative source wins;
- latest verified value wins;
- manual reconciliation;
- merge process.

A migration that merely adds a unique constraint is not a data-model migration.

It is a constraint deployment without semantic reconciliation.

# 44. Observability for Normalized Systems

Normalization itself is not directly observable, but the consequences are.

Monitor:

```text
constraint violations
foreign-key violation rates
unique-conflict rates
query latency
join row counts
unexpected table growth
projection lag
migration validation failures
```

A sudden increase in unique violations can indicate a product workflow change or an incorrect business assumption.

A sudden join explosion can indicate a broken relationship predicate or unexpected cardinality.

---

# 45. Performance Considerations

Normalization may increase joins.

That does not imply poor performance.

Potential benefits include:

- smaller rows;
- less duplicate storage;
- better cache utilization for hot master rows;
- clearer indexing targets;
- fewer write operations for shared facts;
- easier consistency enforcement.

Potential costs include:

- more joins;
- more complicated queries;
- additional indexes;
- more tables to operate and migrate.

The right design depends on workload.

---

# 46. Decision Framework: Normalize or Denormalize?

Use this sequence:

### Question 1
Is this fact independently identifiable?

If yes, it may deserve its own relation.

### Question 2
Does it have an independent lifecycle?

If yes, separate modeling becomes more likely.

### Question 3
Does duplicating it create contradictions?

If yes, normalization has a strong correctness case.

### Question 4
Is the repeated value a historical snapshot?

If yes, duplication may be intentional and correct.

### Question 5
Is performance actually a problem?

Measure.

### Question 6
Can a projection solve the problem without making the primary model ambiguous?

Often a derived table, materialized view, cache, or search projection is preferable to mutating the canonical relational model.

# 47. Production Checklist

Before approving a schema:

```text
[ ] Every table has an explicit row grain.
[ ] Candidate keys have been reasoned about.
[ ] Functional dependencies are known for important facts.
[ ] Composite-key partial dependencies were examined.
[ ] Transitive dependencies were examined.
[ ] Independent multi-valued facts were separated where necessary.
[ ] Important decompositions are lossless.
[ ] Critical dependencies remain enforceable.
[ ] Foreign keys match the real relationship semantics.
[ ] Business uniqueness is scoped correctly.
[ ] Tenant boundaries are included in determinants where required.
[ ] Historical snapshots are explicitly distinguished from current facts.
[ ] Derived/cache data has a defined source of truth.
[ ] Denormalization has a measured reason.
[ ] JSONB/arrays are not hiding relational relationships.
[ ] Constraints enforce important invariants.
[ ] Indexes are workload-driven.
[ ] Concurrency implications are understood.
[ ] Migration cleanup rules are defined.
```

Keep this chain in your head:

```text

    ↓

    ↓
```

The most important lesson is not:

> “Always use 3NF.”

It is:

> **Put each fact where its meaning, key, lifecycle, and integrity rules naturally belong. Then use measurement—not intuition—to decide whether a different physical representation is justified.**

That is the foundation for the deeper relational modeling chapters that follow.
