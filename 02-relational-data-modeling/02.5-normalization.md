# 02.5 — Normalization

> **Phase 02 — Relational Data Modeling**  
> A production-grade, first-principles treatment of normalization: functional dependencies, normal forms, lossless decomposition, dependency preservation, anomalies, and the boundary between normalized relational design and intentional denormalization.

---

## 1. Chapter Objective

Normalization is often taught as a sequence to memorize:

```text
1NF → 2NF → 3NF → BCNF → 4NF → 5NF
```

That is not enough for production engineering.

The real skill is the ability to answer:

> **Which facts belong together, at what grain, under which determinant, and what redundancy would create contradictory legal states?**

By the end of this chapter you should be able to:

- identify the true grain of a relation;
- derive candidate keys rather than guessing them;
- state functional dependencies precisely;
- detect insertion, update, and deletion anomalies;
- decompose relations without losing facts;
- reason about lossless join and dependency preservation;
- distinguish 3NF from BCNF trade-offs;
- recognize multivalued dependencies and when 4NF matters;
- understand join dependencies and the practical meaning of 5NF;
- decide when controlled redundancy is justified;
- preserve historical facts without mistaking snapshots for accidental duplication;
- use PostgreSQL constraints to enforce the assumptions that normalization depends on;
- challenge ORM- or AI-generated schemas using dependency reasoning rather than visual intuition.

Normalization is therefore not table-splitting. It is **constraint-aware fact placement**.

---

# 2. Three Levels of Definition

## 2.1 Simple definition

Normalization is the process of organizing related facts into relations so that the same fact is not unnecessarily stored in multiple places.

The goal is to reduce anomalies and make updates predictable.

## 2.2 Engineering definition

Normalization decomposes relations according to keys and dependencies so each fact is represented at the appropriate determinant and can be maintained without introducing avoidable inconsistency.

## 2.3 Expert definition

Normalization is a relational-design discipline based on dependencies among attributes and the properties of decompositions. A decomposition is valuable when it removes update anomalies while preserving the intended facts, ideally through a lossless join and, where feasible, dependency preservation.

A useful mental model is:

```text
Business Facts
    ↓
Determine Grain
    ↓
Discover Dependencies
    ↓
Find Candidate Keys
    ↓
Detect Redundancy / Anomalies
    ↓
Decompose
    ↓
Prove Losslessness
    ↓
Evaluate Dependency Preservation
    ↓
Add Database Constraints
    ↓
Measure Real Workload
    ↓
Denormalize only when justified
```

---

# 3. First Principle: A Relation Has a Grain

Before asking whether a table is normalized, ask:

> **What does one row represent?**

Suppose:

```text
order_id | customer_id | customer_name | product_id | product_name | quantity
---------|-------------|---------------|------------|--------------|--------
1001     | 7           | Asha          | 50         | Ring         | 2
1001     | 7           | Asha          | 51         | Chain        | 1
1002     | 8           | Rahul         | 50         | Ring         | 3
```

The grain is not:

```text
one row = one order
```

It is:

```text
one row = one order × one product line
```

That distinction changes every dependency.

Likely dependencies include:

```text
order_id → customer_id
order_id → customer_name   [assuming customer_name is current snapshot]
product_id → product_name
(order_id, product_id) → quantity
```

The quantity does not depend on `order_id` alone. It depends on the **line identity**.

A large percentage of normalization mistakes are actually **grain mistakes**.

---

# 4. Functional Dependency

A functional dependency is written as:

```text
X → Y
```

It means:

> Whenever two rows agree on X, they must also agree on Y.

Equivalently, X determines Y.

Examples:

```text
customer_id → customer_email
product_id → product_name
employee_id → employee_department_id
```

A dependency is a statement about the data model, not merely an observed coincidence in today's rows.

If today's data happens to have:

```text
city → country
```

because only one country is currently represented, that does not automatically make `city → country` a business truth.

Dependencies must come from semantics, keys, constraints, and domain rules.

---

# 5. Trivial and Non-Trivial Dependencies

A dependency:

```text
X → Y
```

is trivial when Y is already contained in X.

Example:

```text
(order_id, line_no) → line_no
```

This tells us little.

A non-trivial dependency carries additional information:

```text
product_id → product_name
```

Normalization reasoning focuses primarily on meaningful non-trivial dependencies.

---

# 6. Keys and Functional Dependencies

A superkey is a set of attributes that uniquely identifies a row.

If:

```text
customer_id
```

uniquely identifies a customer, then:

```text
customer_id → customer_id, email, name, created_at, ...
```

A candidate key is a minimal superkey.

If both are unique:

```text
customer_id
email
```

then both may be candidate keys.

A declared `PRIMARY KEY` chooses one candidate key as the table's primary identifier. A `UNIQUE` constraint can preserve another candidate key.

Normalization uses candidate keys, not just whatever column happens to be designated primary.

---

# 7. Armstrong's Axioms

For deeper reasoning, functional dependencies can be derived using Armstrong's axioms.

## 7.1 Reflexivity

If Y is a subset of X:

```text
X → Y
```

Example:

```text
(order_id, line_no) → order_id
```

## 7.2 Augmentation

If:

```text
X → Y
```

then:

```text
XZ → YZ
```

## 7.3 Transitivity

If:

```text
X → Y
Y → Z
```

then:

```text
X → Z
```

Example:

```text
employee_id → department_id
department_id → department_name
```

therefore:

```text
employee_id → department_name
```

The transitive dependency is exactly the kind of redundancy normalization tries to expose.

---

# 8. Attribute Closure

Given a set of dependencies F and an attribute set X, the closure X⁺ is the set of attributes functionally determined by X.

Why does this matter?

Because it lets you test whether X is a superkey.

Example:

```text
R(A, B, C, D, E)

Dependencies:
A → B
B → C
AC → D
D → E
```

Start with:

```text
A⁺ = {A}
```

Apply:

```text
A → B
```

Now:

```text
A⁺ = {A, B}
```

Then:

```text
B → C
```

so:

```text
A⁺ = {A, B, C}
```

Now `AC → D` applies:

```text
A⁺ = {A, B, C, D}
```

Then:

```text
D → E
```

so:

```text
A⁺ = {A, B, C, D, E}
```

Therefore A is a superkey.

If no proper subset of A is a superkey, A is a candidate key.

Closure is one of the strongest reasoning tools in advanced normalization.

---

# 9. Why Redundancy Creates Anomalies

Consider:

```text
student_course
--------------
student_id
student_name
course_id
course_name
instructor_name
```

Suppose each student appears once per course.

Example:

```text
student_id | student_name | course_id | course_name | instructor_name
-----------|--------------|-----------|-------------|----------------
1          | Asha         | 10        | SQL         | Dr. Rao
2          | Rahul        | 10        | SQL         | Dr. Rao
3          | Neha         | 10        | SQL         | Dr. Rao
```

The fact:

```text
course_id 10 → course_name SQL, instructor Dr. Rao
```

is repeated across multiple rows.

That produces anomalies.

---

# 10. Update Anomaly

Suppose the instructor changes:

```text
Dr. Rao → Dr. Sen
```

Every row for course 10 must be updated.

If one row is missed:

```text
course 10 → Dr. Rao
course 10 → Dr. Sen
```

The database now contains contradictory representations of one fact.

A normalized design places course facts in a relation whose grain is course.

---

# 11. Insert Anomaly

Suppose a new course exists:

```text
course_id = 20
course_name = PostgreSQL
```

but no student has enrolled yet.

If the only place course data can be stored is `student_course`, you cannot represent the course naturally without inventing a student enrollment.

That is an insertion anomaly.

A normalized design separates:

```text
courses
--------
id
name

student_courses
---------------
student_id
course_id
```

Now a course can exist independently of enrollment.

---

# 12. Delete Anomaly

Suppose one row is the only enrollment for course 20.

Deleting the student enrollment may unintentionally delete the only stored fact about the course itself.

That means one relationship lifecycle is accidentally controlling another entity's existence.

This is a structural smell.

---

# 13. First Normal Form — 1NF

At a practical relational level, 1NF means each attribute contains a single value from its domain rather than an unstructured repeating group.

Bad conceptual design:

```text
customer_id | phone_numbers
------------|----------------------
7           | +91..., +91..., +91...
```

Better relational representation when numbers are independent facts:

```text
customer_phones
---------------
customer_id
phone_number
phone_type
```

Do not interpret 1NF as “no arrays or JSON ever.”

PostgreSQL supports array and JSON types intentionally.

The correct question is whether the collection is truly one attribute value or whether it represents independently addressable relational facts.

That is a modeling decision, not a syntax taboo.

---

# 14. 1NF and PostgreSQL

A common beginner claim is:

> “PostgreSQL arrays violate normalization.”

That statement is too simplistic.

An array can be a legitimate attribute when the entire value has one semantic identity.

For example:

```text
allowed_weekdays integer[]
```

can reasonably mean one policy attribute.

But:

```text
phone_numbers text[]
```

may be a poor design if each phone number has its own type, verification state, owner, history, or uniqueness rule.

Therefore:

> **Ask whether the elements are independently meaningful facts.**

---

# 15. Second Normal Form — 2NF

A relation is in 2NF when it is in 1NF and every non-key attribute depends on the whole candidate key, not merely part of a composite candidate key.

This matters primarily when candidate keys are composite.

Example:

```text
order_lines
-----------
order_id
product_id
product_name
quantity
```

Suppose:

```text
(order_id, product_id) → quantity
product_id → product_name
```

The key is:

```text
(order_id, product_id)
```

But:

```text
product_id → product_name
```

means `product_name` depends only on part of the key.

That is a partial dependency.

Move product facts to:

```text
products
--------
product_id
product_name
```

and keep order-line facts in:

```text
order_lines
-----------
order_id
product_id
quantity
```

Now the order line relation contains facts about the line itself.

---

# 16. Third Normal Form — 3NF

A relation is in 3NF when it is in 2NF and non-key attributes do not transitively depend on a candidate key through another non-key attribute.

Classic example:

```text
employee
--------
employee_id PK
department_id
department_name
```

Dependencies:

```text
employee_id → department_id
department_id → department_name
```

Therefore:

```text
employee_id → department_name
```

through a non-key determinant.

This is a transitive dependency.

Better:

```text
employees
---------
employee_id
department_id

 departments
------------
department_id
department_name
```

---

# 17. 3NF Is About Determinants, Not “One Table Per Thing”

This schema is not automatically more normalized because it has more tables.

You must identify the actual dependencies.

For example:

```text
products
--------
product_id
product_code
product_name
```

If both:

```text
product_id → product_code
product_code → product_id
```

then `product_code` is an alternate candidate key.

You should usually enforce that with:

```sql
UNIQUE (product_code)
```

Normalization without corresponding constraints is incomplete engineering because the logical dependency remains unenforced.

---

# 18. BCNF — Boyce-Codd Normal Form

A relation is in BCNF if every non-trivial functional dependency has a determinant that is a superkey.

BCNF is stronger than 3NF.

Consider:

```text
teaching
--------
student
course
instructor
```

Suppose the business rules are:

```text
(student, course) → instructor
instructor → course
```

Then an instructor teaches only one course, but a course can have many instructors.

`instructor → course` is a non-trivial dependency where instructor is not necessarily a superkey of the full relation.

The relation can violate BCNF even if it satisfies 3NF under certain key structures.

The practical lesson is not to memorize the example.

It is:

> **Every determinant that claims to identify another fact should correspond to an enforced uniqueness boundary whenever that dependency is part of the model.**

---

# 19. 3NF vs BCNF Trade-off

BCNF reduces more redundancy, but decomposition can cause dependency-preservation problems.

A theoretically stronger normal form is not automatically the best operational choice.

You need to evaluate:

```text
Correctness
→ Constraint Enforceability
→ Losslessness
→ Dependency Preservation
→ Query Complexity
→ Write Complexity
→ Operational Cost
```

A slightly less decomposed 3NF design can sometimes make important constraints easier to enforce without procedural checks.

Expert design is about the full invariant system, not normal-form score alone.

---

# 20. Lossless Decomposition

A decomposition is lossless when joining the decomposed relations reconstructs exactly the original relation's information without introducing spurious tuples or losing facts.

Suppose:

```text
R(A, B, C)
```

with:

```text
A → B
```

Decompose into:

```text
R1(A, B)
R2(A, C)
```

The intersection is:

```text
R1 ∩ R2 = {A}
```

and because:

```text
A → B
```

A determines the attributes in R1.

This decomposition is lossless under the standard criterion.

The important practical idea:

> **A decomposition is only useful if reconstructing the facts does not invent relationships that never existed.**

---

# 21. Dependency Preservation

A decomposition is dependency preserving when the original dependencies can be enforced by checking the decomposed relations without requiring a join to verify them.

Why does this matter?

Suppose a business rule requires:

```text
A, B → C
```

but after decomposition, no single relation contains all attributes needed to enforce it naturally.

You may now need:

- triggers,
- application logic,
- procedural validation,
- or transactional join checks.

A mathematically elegant decomposition that makes core integrity difficult to enforce can be a poor production design.

---

# 22. Fourth Normal Form — 4NF

4NF deals with multivalued dependencies.

Consider:

```text
employee_skill_language
-----------------------
employee
skill
language
```

Suppose employee skills and languages are independent sets:

```text
employee →→ skill
employee →→ language
```

Then storing all combinations causes a Cartesian explosion.

If employee 7 has:

```text
skills:    SQL, Java
languages: English, Hindi
```

the combined relation must represent:

```text
SQL + English
SQL + Hindi
Java + English
Java + Hindi
```

Those combinations may not be real facts.

A 4NF-oriented design separates:

```text
employee_skills
---------------
employee_id
skill_id

employee_languages
------------------
employee_id
language_id
```

This is especially relevant when two independent multi-valued properties are stored in one relation.

---

# 23. Fifth Normal Form — 5NF

5NF addresses join dependencies.

It appears when a relation can be decomposed into smaller relations such that the original relation is exactly recoverable from their joins, and the dependency exists beyond ordinary functional and multivalued dependencies.

5NF is uncommon in everyday CRUD applications but matters in complex many-way relationship systems such as:

```text
supplier
part
project
```

where the business semantics may require subtle constraints about which combinations are legal.

The important engineering lesson:

> **Do not invent a 5NF decomposition because a textbook says it is elegant. First establish the business fact being represented.**

---

# 24. Normalization Is Not the Same as Eliminating All Duplication

This is one of the most important expert distinctions.

Suppose an order stores:

```text
product_id
product_name_at_purchase
```

You may argue:

```text
product_id → current product_name
```

so product name should live only in `products`.

That can be wrong for historical data.

If the product was named:

```text
“22K Gold Ring”
```

at the time of purchase, and later renamed:

```text
“Classic Gold Ring”
```

then an invoice may intentionally preserve:

```text
product_name_at_purchase = “22K Gold Ring”
```

That is not accidental redundancy.

It is a **historical snapshot fact**.

The correct model may contain both:

```text
products.product_name
order_lines.product_name_snapshot
```

because they answer different questions.

---

# 25. Current State vs Historical Fact

Always classify a duplicated attribute.

### Current state

```text
customer.email
```

### Historical snapshot

```text
invoice.billing_email_snapshot
```

### Derived cache

```text
customer.order_count_cache
```

### Materialized projection

```text
sales_daily_summary
```

These all duplicate information differently.

Normalization addresses **unjustified redundancy of the same fact**, not every repeated value in the database.

---

# 26. Normalization and Constraints

A logical dependency becomes operationally meaningful when the database can enforce it.

Suppose:

```text
email → user
```

If email truly identifies a user, declare:

```sql
CREATE TABLE users (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE
);
```

Now the database's legal states match the dependency assumption.

Without `UNIQUE`, the schema says:

```text
email does not necessarily identify one user
```

while your application may incorrectly assume that it does.

Therefore:

> **Normalization reasoning and constraint design should not be separated.**

---

# 27. Composite Dependencies in Multi-Tenant Systems

Consider:

```text
products
--------
tenant_id
product_id
sku
```

Suppose SKU uniqueness is tenant-local:

```text
(tenant_id, sku) → product
```

Then the candidate uniqueness boundary is:

```sql
UNIQUE (tenant_id, sku)
```

A global:

```sql
UNIQUE (sku)
```

would encode the wrong dependency.

This is why tenant identity often belongs in composite keys and foreign keys: it makes scope part of the determinant.

---

# 28. Normalization and Referential Integrity

Suppose:

```text
order_lines
-----------
tenant_id
order_id
product_id
```

and both order and product are tenant-scoped.

A weak design might use:

```sql
FOREIGN KEY (order_id) REFERENCES orders(id)
FOREIGN KEY (product_id) REFERENCES products(id)
```

while relying on application code to keep tenants aligned.

A stronger design may use composite foreign keys:

```sql
FOREIGN KEY (tenant_id, order_id)
    REFERENCES orders (tenant_id, id),

FOREIGN KEY (tenant_id, product_id)
    REFERENCES products (tenant_id, id)
```

This turns tenant scope into part of the relational invariant.

Normalization becomes a security concern when the wrong dependency permits cross-tenant associations.

---

# 29. Functional Dependencies from Business Rules

Do not derive dependencies only from current data.

Bad reasoning:

```text
“All current employees have unique phone numbers,
therefore phone_number is a key.”
```

Better:

```text
“Company policy explicitly guarantees one active account per
verified phone number.”
```

Then enforce it with the appropriate constraint, possibly a partial unique index if the policy is scoped to active rows.

Example:

```sql
CREATE UNIQUE INDEX users_verified_phone_uq
ON users (phone_number)
WHERE phone_verified_at IS NOT NULL
  AND deleted_at IS NULL;
```

The dependency is now represented as an explicit legal-state rule.

---

# 30. Partial Keys and Weak Entity Patterns

Sometimes identity depends partly on a parent.

Example:

```text
order_line
----------
order_id
line_no
```

where:

```text
(order_id, line_no)
```

is the true identity.

Then:

```text
line_no
```

alone is not a global identifier.

This matters when deciding whether to introduce a surrogate key.

You can have:

```sql
id bigint PRIMARY KEY,
UNIQUE (order_id, line_no)
```

but the business uniqueness constraint remains important.

A surrogate key can simplify references without replacing the logical key.

---

# 31. Normalization and Nulls

Functional dependency reasoning becomes more subtle with nullable values.

Suppose:

```text
employee_id → manager_id
```

but `manager_id` can be NULL because top-level employees have no manager.

That does not mean the dependency is false.

It means the determinant identifies a possibly unknown/unassigned attribute.

However, if uniqueness semantics depend on nullable columns, PostgreSQL's treatment of NULLs and the chosen unique-index behavior must be considered explicitly.

Do not reason about normalization independently of SQL's actual NULL semantics.

---

# 32. EAV Is Usually a Normalization Failure in Disguise

Entity-Attribute-Value designs often look flexible:

```text
entity_id
attribute_name
attribute_value
```

But important dependencies become difficult to represent.

Example:

```text
product_id → warranty_period
product_id → weight
product_id → material
```

An EAV table turns domain structure into rows of metadata and pushes:

- typing,
- requiredness,
- uniqueness,
- range checks,
- foreign keys,
- indexing,
- and dependency rules

into application code or procedural logic.

That is not automatically “more normalized.”

It can be less relational because the schema no longer expresses the domain's actual dependencies.

---

# 33. CSV-in-a-Column Is Not Normalization

Bad:

```text
roles = 'admin,manager,auditor'
```

If each role is an independently governed relationship, use:

```text
user_roles
----------
user_id
role_id
```

A string list prevents ordinary relational constraints from expressing the actual fact structure.

The problem is not merely query inconvenience.

It is loss of explicit grain and integrity.

---

# 34. Arrays vs Child Rows

Consider:

```text
products
--------
id
compatible_material_ids bigint[]
```

Ask:

1. Does each material need a foreign key?
2. Does each relation have attributes?
3. Must duplicates be impossible?
4. Must relationships be queried independently?
5. Does each relationship have history?
6. Does each element participate in authorization?

If yes, a child or junction table is often the normalized representation.

An array can still be correct when the collection is truly one semantic value and independently constraining each element is unnecessary.

---

# 35. JSONB and Normalization

JSONB is useful for semi-structured data, but:

```text
JSONB flexibility ≠ relational correctness
```

If a property has:

- a foreign key target,
- unique identity,
- lifecycle,
- independent permissions,
- joins,
- frequent analytical queries,
- or strict type/integrity requirements,

then storing it permanently inside one opaque JSON document may hide a relational dependency that should be modeled explicitly.

Conversely, sparse optional metadata can legitimately remain in JSONB.

The decision is semantic, not ideological.

---

# 36. Normalization and Query Cost

Normalization can increase joins.

For example:

```text
orders
customers
branches
```

may require more joins than a wide denormalized reporting row.

But the correct response is not immediately:

> “Denormalize everything.”

First investigate:

```text
Query frequency
→ Selectivity
→ Existing indexes
→ Join cardinality
→ Working set
→ Cache behavior
→ Planning cost
→ Row width
→ Network transfer
```

A normalized OLTP schema may be exactly what a transactional workload needs.

A separate read model may solve an analytical problem better than corrupting the source of truth.

---

# 37. Normalize First, Then Measure

A disciplined architecture sequence is:

```text
1. Establish correct grain.
2. Establish candidate keys.
3. Establish business dependencies.
4. Normalize obvious redundancy.
5. Add constraints.
6. Build representative workloads.
7. Measure.
8. Introduce targeted denormalization only where evidence supports it.
```

Do not start with:

```text
“Queries may be slow, so let's duplicate these fields.”
```

That is speculation, not engineering.

---

# 38. Denormalization Is a Separate Design Problem

Suppose a dashboard repeatedly needs:

```text
customer_id
customer_name
order_count
lifetime_value
last_order_at
```

You can preserve a normalized transactional model and create a projection:

```text
customer_metrics
---------------
customer_id
order_count
lifetime_value
last_order_at
```

The projection has its own consistency contract.

This is often better than embedding reporting aggregates into the source tables without a rebuild or reconciliation strategy.

---

# 39. When Denormalization Is Justified

Typical evidence-based reasons include:

- a proven read hot path;
- expensive repeated joins over stable relationships;
- aggregation cost that materially harms latency;
- search or analytics read models;
- snapshot requirements;
- external integration requirements;
- specialized storage projections;
- workload isolation.

The justification should state:

```text
Source of truth:
Consistency model:
Update mechanism:
Rebuild mechanism:
Failure behavior:
Observed performance gain:
```

Without those answers, denormalization is usually unfinished design.

---

# 40. Normalization and History

History often changes the apparent dependency graph.

Current-state table:

```text
customer_id → current_address
```

Historical address relation:

```text
(customer_id, valid_from) → address
```

A fact that looks redundant in a current-state table may be necessary when time becomes part of the grain.

Therefore normalization must be evaluated relative to:

```text
Entity grain
+ temporal grain
+ business semantics
```

---

# 41. Audit Columns Do Not Automatically Violate Normalization

Consider:

```text
orders
------
created_by
created_at
updated_by
updated_at
```

These attributes can legitimately depend on the order row.

They are not redundant merely because the user table contains:

```text
users.name
```

However:

```text
created_by_name
```

stored on the order is different.

If it means a historical snapshot, it may be intentional.

If it merely duplicates current user state, it is likely unjustified redundancy.

---

# 42. Normalization and Soft Deletes

Soft deletion introduces states such as:

```text
deleted_at IS NULL
```

Suppose business uniqueness applies only to active rows.

Then the logical key may be:

```text
(email, active_state)
```

or more practically a partial unique index:

```sql
CREATE UNIQUE INDEX users_email_active_uq
ON users (email)
WHERE deleted_at IS NULL;
```

This is an example of how physical constraints must reflect the semantic scope of a dependency.

---

# 43. Common Normalization Mistakes

## Mistake 1 — “More tables means more normalized”

False.

If the grain and dependencies are wrong, additional tables can make the model harder without making it correct.

## Mistake 2 — “Never duplicate any value”

False.

Snapshots, caches, projections, and historical facts can be intentionally duplicated.

## Mistake 3 — “3NF means no joins”

False.

Normalization often introduces relationships that must be joined to reconstruct business views.

## Mistake 4 — “Arrays always violate 1NF”

Too simplistic for PostgreSQL.

The semantic question matters.

## Mistake 5 — “A surrogate key fixes normalization”

False.

A surrogate key gives identity; it does not remove transitive or partial dependencies.

## Mistake 6 — “The ORM model is the normalized model”

False.

ORM object graphs and relational dependencies are different abstractions.

# 44. AI / Vibe-Coding Failure Modes

AI-generated database schemas frequently contain hidden normalization errors.

### Failure A — One giant table

```text
order_id
customer_name
customer_email
branch_name
product_name
supplier_name
category_name
...
```

Why it happens:

The model optimizes for immediate query convenience rather than fact ownership.

### Failure B — Repeating columns

```text
phone1
phone2
phone3
```

This hardcodes a collection's maximum size into the schema.

### Failure C — Blind JSONB

The AI moves every uncertain field into JSONB instead of investigating dependencies.

### Failure D — Surrogate-key-only thinking

The AI adds `id` to every table and forgets the actual business uniqueness constraints.

### Failure E — Snapshot confusion

The AI removes historical snapshot columns because they “duplicate” current master data.

### Failure F — Tenant dependency omission

The AI defines:

```text
UNIQUE(sku)
```

when the real rule is:

```text
UNIQUE(tenant_id, sku)
```

### Failure G — EAV for extensibility

The AI chooses EAV before determining whether the attributes have stable type and dependency semantics.

### Review method

Ask the generated schema:

```text
What is the row grain?
What are all candidate keys?
Which dependencies hold?
Which values depend on only part of the key?
Which values are transitive?
Which facts are historical snapshots?
Which constraints enforce the dependencies?
```

If those questions cannot be answered clearly, the model is not ready for production.

Consider an enterprise jewellery order system.

Naive table:

```text

```

That is dangerous.

A normalized transactional design separates facts:

```text
customers
```

```text
invoice.billing_name_snapshot

```

The model now distinguishes:

```text
Current Master Facts
        vs
Historical Transaction Facts
```

That distinction is far more important than simply counting tables.

# 46. Normalization Review Workflow

Use this workflow when reviewing a schema.

## Step 1 — Write the grain

For every table:

```text
One row represents __________
```

## Step 2 — List candidate keys

Do not stop at the primary key.

## Step 3 — State dependencies

Write:

```text
X → Y
```

for every meaningful business dependency.

## Step 4 — Identify anomalies

Ask:

```text
What happens when a fact changes?
What happens when a new fact exists without a related fact?
What happens when the final relationship row is deleted?
```

## Step 5 — Decompose

Move attributes toward the determinant that actually owns the fact.

## Step 6 — Prove the join

Check whether the decomposition is lossless.

## Step 7 — Check enforcement

Which dependencies are guaranteed by:

```text
PRIMARY KEY
UNIQUE
FOREIGN KEY
CHECK
EXCLUDE
partial unique index
```

## Step 8 — Measure

Only then evaluate performance trade-offs.

# 47. SQL Lab — Detecting Redundancy

Suppose:

```sql
CREATE TABLE enrollment (
    student_id bigint,
    student_name text,
    course_id bigint,
    course_name text,
    instructor text,
    PRIMARY KEY (student_id, course_id)
);
```

Potential dependencies:

```text
student_id → student_name
course_id → course_name, instructor
(student_id, course_id) → enrollment fact
```

A normalization exercise is to decompose into:

```sql
CREATE TABLE students (
    id bigint PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE courses (
    id bigint PRIMARY KEY,
    name text NOT NULL,
    instructor text NOT NULL
);

CREATE TABLE enrollments (
    student_id bigint NOT NULL REFERENCES students(id),
    course_id bigint NOT NULL REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)
);
```

The decomposition now makes the grains explicit.

# 48. Wrong Approach → Improved Approach

## Naive Approach

Keep all descriptive data in one wide transaction table because it avoids joins.

## Why It Fails

- repeated facts;
- update anomalies;
- contradictory values;
- poor lifecycle separation;
- difficult constraints;
- unclear grain;
- harder historical semantics.

## Improved Approach

Normalize master and relationship facts, then snapshot historical values deliberately where transactions require them.

## Why It Works

Each relation owns facts at an explicit grain while transaction rows preserve immutable business meaning where necessary.

## Production Considerations

Measure actual query paths before adding projections or redundant caches.

## Alternative

A dedicated read model or materialized view for reporting.

## Trade-Off

More joins and a more explicit schema in exchange for integrity and predictable updates.

# 49. Testing Normalized Schemas

Normalization assumptions should be tested as invariants.

### Constraint tests

Verify:

```text
duplicate candidate keys are rejected
invalid foreign keys are rejected
invalid NULL states are rejected
invalid relationship combinations are rejected
```

### Mutation tests

Change a master fact and verify exactly which historical or current values should change.

### Deletion tests

Delete the final child relation and ensure independent parent facts remain when they should.

### Property-style tests

Generate data and assert that known dependencies remain true.

Example property:

```text
For every product_id,
all rows with that product_id have the same current product_name.
```

The better long-term strategy is to enforce such properties through schema constraints whenever possible.

# 50. Evidence-Driven Debugging

When contradictory data appears, do not immediately “clean duplicates.”

First determine whether the contradiction reveals:

```text
Missing constraint
Wrong grain
Wrong candidate key
Incorrect historical semantics
Race condition
Application bug
Migration defect
```

Example:

```text
Two customers share the same email
```

Questions:

1. Is email truly globally unique?
2. Is uniqueness tenant-scoped?
3. Is the duplicate an inactive account?
4. Is normalization wrong or only the constraint?
5. Was the duplicate created concurrently?

Data cleanup without dependency analysis can destroy legitimate history.

# 51. Performance Considerations

Normalization can affect:

- join count;
- row width;
- index count;
- cache locality;
- network transfer;
- query complexity.

But denormalization also adds:

- write amplification;
- storage;
- synchronization cost;
- rebuild complexity;
- inconsistency risk.

The correct optimization target is the workload, not the aesthetic appearance of the schema.

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
...
```

to measure representative queries.

Do not infer performance solely from the number of joins.

---

# 52. Security Considerations

Incorrect normalization can become a security problem when it weakens scope boundaries.

Examples:

```text
wrong tenant key
wrong uniqueness scope
polymorphic references
application-only authorization relationships
JSONB fields bypassing foreign keys
```

A normalized relationship that includes tenant identity can make illegal cross-tenant states structurally impossible.

Security-sensitive dependencies belong as close to the database invariant layer as practical.

---

# 53. Reliability Considerations

A normalized system should make failure behavior explicit.

Ask:

```text
Can a partial write leave orphaned facts?
Can retries create duplicate relationship rows?
Can concurrent writers violate assumed dependencies?
Can a projection be rebuilt?
Can snapshots be distinguished from current state?
```

A good normalization design works together with:

- transactions;
- unique constraints;
- foreign keys;
- idempotency;
- reconciliation.

# 63. Final Mental Model

Do not look at normalization as:

```text
“Split this table until it looks textbook.”
```

Think instead:

```text
What does one row mean?
        ↓
What identifies it?
        ↓
What facts depend on that identity?
        ↓
Which facts depend on something else?
        ↓
Where can the same fact appear twice?
        ↓
Can those copies diverge?
        ↓
Can the database prevent divergence?
        ↓
Can the facts be reconstructed without invented relationships?
        ↓
What workload does the normalized model serve?
        ↓
What redundancy, if any, is intentionally justified?
```

That is normalization as database engineering.
