# 02.8 — Schema Design Patterns & Anti-Patterns

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to choosing schema structures deliberately, recognizing reusable relational patterns, rejecting seductive anti-patterns, and reasoning from business invariants rather than ORM defaults.

---

## 1. Chapter Objective

A database schema is one of the longest-lived parts of a software system. Application frameworks, APIs, UI flows, and even services may be replaced while the database continues carrying historical facts, enforcing contracts, and supporting operational workflows.

This chapter develops the ability to recognize **schema design patterns** that repeatedly solve real relational problems and, equally importantly, to identify **anti-patterns** that appear convenient but create integrity, query, migration, or operational problems later.

The central question is not:

> “What schema pattern is popular?”

It is:

> **“What business invariant, lifecycle, access pattern, and workload justify this structure?”**

A useful decision chain is:

```text
Business Requirement
    ↓
Facts + Invariants
    ↓
Row Grain + Identity
    ↓
Relationship + Lifecycle
    ↓
Constraint Model
    ↓
Access / Workload Model
    ↓
Schema Pattern
    ↓
Indexes + Transactions + Observability
    ↓
Migration / Evolution Plan
```

---

# 2. Three Levels of Definition

## 2.1 Simple definition

A schema design pattern is a reusable way to structure tables and constraints for a recurring problem.

An anti-pattern is a structure that appears useful but tends to produce predictable correctness, performance, security, or maintainability problems.

## 2.2 Engineering definition

A pattern is a relational design choice that organizes entities, relationships, keys, constraints, lifecycle, and access paths around a particular workload or invariant.

An anti-pattern is a design whose local convenience systematically shifts complexity into application code, query logic, migrations, operations, or failure handling.

## 2.3 Expert definition

A schema pattern is a deliberate encoding of a **legal-state model and operational contract**. Its quality is determined by whether the representation minimizes ambiguity and preserves required invariants at the correct enforcement boundary under concurrency and change.

A pattern should therefore be judged across at least six dimensions:

```text
Correctness
Integrity
Read Workload
Write Workload
Evolution
Operational Failure
```

# 3. Pattern Selection Starts With Invariants

Consider:

> “A customer may have only one primary address.”

Possible implementations include:

```text
application logic
partial UNIQUE index
boolean + trigger
separate primary-address FK
```

The first instinct should not be “Which pattern is easiest with my ORM?”

Instead ask:

1. What exactly is the invariant?
2. What is the row grain?
3. Can the invariant be expressed declaratively?
4. Does concurrency matter?
5. What reads dominate?
6. What happens when the business rule changes?

For the example, a partial uniqueness rule may be sufficient:

```sql
CREATE UNIQUE INDEX customer_one_primary_address
ON customer_addresses (customer_id)
WHERE is_primary;
```

The important lesson is broader:

> **Patterns are solutions to invariants, not decorations applied to tables.**

---

# 4. Pattern: Parent–Child Ownership

This is one of the most common relational patterns.

```text
orders
------
id

order_items
-----------
id
order_id FK
```

Use it when the child exists because the parent owns the lifecycle of the fact.

Typical examples:

```text
invoice → invoice_lines
order → order_items
purchase → purchase_lines
shipment → shipment_items
```

Typical constraints:

```sql
order_id bigint NOT NULL REFERENCES orders(id),
UNIQUE (order_id, line_number)
```

Potential delete rule:

```sql
ON DELETE CASCADE
```

but only when deleting the parent is semantically allowed to delete the child facts.

## Why it works

The parent controls identity and lifecycle; the child references it explicitly.

## Failure mode

A developer uses cascade merely because “the child belongs to the parent,” even though the child is an accounting or audit fact that must survive the parent lifecycle.

### Decision rule

> Cascade is a lifecycle statement, not a convenience statement.

---

# 5. Pattern: Associative Entity

Use a junction table when a many-to-many relationship exists.

```text
users
roles

user_roles
----------
user_id
role_id
```

If the relationship has attributes:

```text
assigned_at
assigned_by
expires_at
source
```

it becomes a first-class associative entity.

Example:

```sql
CREATE TABLE user_roles (
    user_id bigint NOT NULL REFERENCES users(id),
    role_id bigint NOT NULL REFERENCES roles(id),
    assigned_at timestamptz NOT NULL DEFAULT now(),
    assigned_by bigint REFERENCES users(id),
    expires_at timestamptz,
    PRIMARY KEY (user_id, role_id)
);
```

## Common anti-pattern

```text
users.role_ids = '{2,4,9}'
```

This weakens:

- foreign-key enforcement
- joins
- uniqueness
- relationship attributes
- referential lifecycle

Arrays are appropriate when the collection is genuinely a value. They are usually the wrong representation for independently governed relational relationships.

---

# 6. Pattern: Strong Identifier + Business Uniqueness

A common production design uses a stable surrogate key while preserving business uniqueness separately.

Example:

```sql
CREATE TABLE customers (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    external_code text NOT NULL,
    UNIQUE (tenant_id, external_code)
);
```

This separates:

```text
identity → id
business uniqueness → tenant_id + external_code
```

## Why it works

Business identifiers can change, while internal references remain stable.

## Anti-pattern

Using a surrogate key while forgetting the business uniqueness constraint.

This creates:

```text
id | tenant_id | external_code
---|-----------|--------------
1  | 10        | CUST-01
2  | 10        | CUST-01
```

The surrogate key correctly identifies two rows but fails to encode the business rule.

---

# 7. Pattern: Scoped Uniqueness

Many SaaS systems have values unique only within a scope.

Examples:

```text
SKU per tenant
invoice number per branch
username per organization
sequence per account
code per warehouse
```

Represent the full scope in the uniqueness constraint:

```sql
UNIQUE (tenant_id, sku)
```

or:

```sql
UNIQUE (tenant_id, branch_id, invoice_number)
```

## Common anti-pattern

```sql
UNIQUE (invoice_number)
```

when the business rule is actually scoped to a branch.

This incorrectly couples independent tenants or branches.

---

# 8. Pattern: Explicit State Machine

Many tables contain a lifecycle:

```text
DRAFT → SUBMITTED → APPROVED → POSTED
```

Do not treat state as arbitrary text.

At minimum:

```sql
status text NOT NULL
    CHECK (status IN ('draft', 'submitted', 'approved', 'posted'))
```

But state values alone do not necessarily encode valid transitions.

For stronger systems, model transition semantics explicitly:

```text
invoice
-------
id
status

invoice_status_history
----------------------
invoice_id
from_status
to_status
changed_at
changed_by
```

or maintain transition logic in transactional application/database procedures.

## Why this matters

The important question is not merely:

> “What statuses exist?”

but:

> “Which transitions are legal, under what authority, and what facts are recorded?”

---

# 9. Anti-Pattern: Boolean Explosion

A common schema begins like:

```text
is_active
is_approved
is_paid
is_cancelled
is_deleted
is_archived
is_processed
```

Soon contradictory states become possible:

```text
is_paid = true
is_cancelled = true
is_approved = false
```

Some booleans represent independent dimensions and are perfectly valid. Others are actually multiple representations of one lifecycle state.

### Better approach

Model mutually exclusive lifecycle state as one controlled attribute when the domain truly has one state machine.

```text
status = 'paid'
```

Keep booleans for genuinely orthogonal facts:

```text
is_exported
has_special_handling
requires_review
```

### Rule

> If two flags cannot legally be true together, ask whether they are fragments of one state machine.

---

# 10. Pattern: Audit Columns

Common operational metadata:

```text
created_at
created_by
updated_at
updated_by
```

These are useful for current-row accountability.

They are **not automatically a full audit trail**.

A row such as:

```text
price = 950
updated_at = 2026-09-13
```

does not tell you:

```text
previous price
who changed it
why it changed
which request caused it
```

A proper audit/history design may require a separate append-oriented relation.

---

# 11. Anti-Pattern: “updated_at Is Auditing”

This is a common misconception.

```text
users
-----
id
updated_at
```

only tells you approximately when the current representation changed.

It cannot reconstruct history.

If historical reconstruction matters, design for it explicitly.

```text
entity
------
id
current_state

entity_history
--------------
entity_id
version
changed_at
changed_by
old_state
new_state
```

The exact design depends on whether the requirement is:

- operational audit
- compliance audit
- business history
- temporal reconstruction
- debugging

These are not interchangeable.

---

# 12. Pattern: Immutable Business Facts

Some facts should become append-oriented after creation.

Examples:

```text
ledger entries
posted journal lines
payment events
shipment events
security events
```

A strong design may allow corrections through compensating facts instead of destructive mutation.

For accounting-like data:

```text
original entry
      ↓
reversal / correction entry
      ↓
new valid entry
```

instead of silently overwriting the original.

## Why it works

It preserves causality and makes reconciliation possible.

## Trade-off

Append-oriented models may require more sophisticated reporting.

The trade is often worth it when historical correctness matters more than update simplicity.

---

# 13. Pattern: Snapshot + Reference

Historical documents often need both:

```text
reference to current entity
```

and

```text
snapshot of historical facts
```

Example:

```text
invoice
-------
customer_id
customer_name_snapshot
billing_address_snapshot
```

At first glance this appears redundant.

But an invoice may need to preserve what was true **when it was issued**, even if the customer later changes address.

This is intentional denormalization rather than accidental duplication.

### Rule

> A historical snapshot is justified when the meaning of the past event depends on the value that existed at event time.

---

# 14. Anti-Pattern: False Normalization of Historical Facts

A developer may reason:

> “Never duplicate customer address because duplication violates normalization.”

That can be wrong.

Suppose an invoice must permanently represent the billed address at issuance.

If you only retain:

```text
invoice.customer_id
```

and always join the current address, historical invoices silently change meaning when the customer moves.

The correct question is not:

> “Is there duplication?”

It is:

> **“Are these values the same fact with redundant copies, or different facts with different temporal meaning?”**

---

# 15. Pattern: Reference Data

Stable classifications often deserve reference tables:

```text
currencies
countries
tax_codes
units
payment_methods
```

Typical structure:

```sql
CREATE TABLE currencies (
    code char(3) PRIMARY KEY,
    name text NOT NULL
);
```

Use a reference table when the value has:

- its own metadata
- lifecycle
- ownership
- translations
- regulatory meaning
- foreign references

An enum may be suitable for a small, tightly controlled set whose values are truly schema-level concepts.

---

# 16. Anti-Pattern: Everything Is an Enum

Enums can be useful, but they are often chosen simply because they feel strongly typed.

Avoid automatically using an enum for values that are really business-managed reference data.

For example:

```text
warehouse statuses
```

may need:

```text
label
sort_order
is_active
localized_name
```

A reference table is often more flexible.

### Decision question

> Will business users or migrations need to manage this value as data rather than as schema?

If yes, a table is often more appropriate.

---

# 17. Pattern: Soft Deletion With Explicit Semantics

Soft deletion can be useful:

```text
deleted_at
```

or:

```text
deleted_at
deleted_by
```

But it changes the meaning of every query.

A normal query such as:

```sql
SELECT * FROM products;
```

may now accidentally return deleted rows.

## Better design discipline

Define exactly:

```text
active record semantics
historical record semantics
unique constraints
FK behavior
reporting semantics
restoration semantics
```

A partial unique index may be needed:

```sql
CREATE UNIQUE INDEX products_tenant_sku_active
ON products (tenant_id, sku)
WHERE deleted_at IS NULL;
```

---

# 18. Anti-Pattern: Soft Delete Everywhere

Soft deletion is often introduced because:

> “We may need the data later.”

Then every table gains `deleted_at`, resulting in:

```text
query filters everywhere
larger indexes
complicated joins
unexpected uniqueness semantics
unclear retention policy
```

Potential alternatives include:

- archival tables
- immutable history
- retention partitions
- event storage
- business status instead of deletion
- actual deletion where data has no required history

Do not make every row immortal merely because one business entity needs retention.

---

# 19. Pattern: Subtype Tables

Some domains have a common entity with specialized attributes.

Example:

```text
payments
--------
id
payment_type
amount

card_payments
-------------
payment_id
card_brand
last4

bank_payments
-------------
payment_id
bank_reference
```

This can be preferable to a giant table full of nullable fields:

```text
card_brand NULL
last4 NULL
bank_reference NULL
upi_reference NULL
wallet_id NULL
```

Subtype tables make incompatible attribute sets explicit.

But do not overuse inheritance-like designs when one straightforward table is clearer.

---

# 20. Anti-Pattern: The God Table

A “god table” tries to represent many unrelated concepts in one table.

Typical symptoms:

```text
hundreds of columns
many nullable fields
multiple lifecycle concepts
unrelated foreign keys
wide indexes
ambiguous ownership
```

Example:

```text
transactions
-----------
customer_id
invoice_id
shipment_id
refund_id
purchase_id
warehouse_id
subscription_id
...
```

The table becomes a generic dumping ground.

## Why it fails

The row grain becomes unclear.

When the answer to:

> “What does one row represent?”

requires a paragraph containing multiple exceptions, the design is likely broken.

---

# 21. Pattern: Single Responsibility at the Table Grain

A table should have a coherent row meaning.

For example:

```text
orders
```

should represent orders.

```text
order_items
```

should represent line items.

This does not mean “one table per noun.”

It means:

> **One table should have a defensible statement describing what one row means.**

That sentence is a practical schema review tool.

---

# 22. Anti-Pattern: Generic Entity-Attribute-Value (EAV)

EAV commonly looks like:

```text
entity_id
attribute_name
attribute_value
```

Example:

```text
42 | color | red
42 | width | 10
42 | length | 20
```

It appears flexible but creates substantial costs:

```text
type ambiguity
constraint difficulty
join explosion
poor discoverability
hard indexing
complex uniqueness
awkward aggregation
```

EAV can be justified for specific metadata platforms, but it should be a deliberate architecture—not the default response to uncertainty.

---

# 23. Better Alternative to EAV: Typed Extension Tables

Instead of:

```text
entity_attributes
-----------------
entity_id
key
value
```

use a typed extension relation where the additional facts have coherent meaning.

For example:

```text
product
-------
id
name

product_dimensions
------------------
product_id
width_mm
height_mm
weight_g
```

This preserves:

- type safety
- constraints
- indexes
- discoverability
- clear semantics

Use JSONB when the data is genuinely semi-structured and does not require every key to behave as a relational key or independently governed attribute.

---

# 24. Anti-Pattern: CSV-in-a-Column

This is a classic relational failure:

```text
allowed_roles = 'admin,manager,auditor'
```

Problems:

```text
no FK
hard searching
ambiguous escaping
hard uniqueness
poor indexing
application parsing
```

Use a junction table for relationships.

Use arrays for actual typed collections that are truly values.

Use JSONB for genuinely document-like structure.

Do not use strings as an escape hatch from modeling.

---

# 25. Pattern: Current State + Event History

For operational systems, it is often useful to keep:

```text
current row
```

for fast transactional reads and:

```text
event/history table
```

for historical reconstruction.

Example:

```text
orders
------
status
current_total

order_events
------------
order_id
event_type
occurred_at
payload
```

This is not automatically event sourcing.

The distinction is important.

### Current-state + history

The current row remains the authoritative read model.

### Event sourcing

The event stream is the source of truth and current state is derived.

Do not call every audit table “event sourcing.”

---

# 26. Pattern: Outbox Table

When a transaction must atomically update database state and produce an integration event, an outbox pattern can bridge the boundary.

Example:

```text
orders
------

outbox
------
id
aggregate_type
aggregate_id
event_type
payload
created_at
published_at
```

The application transaction writes:

```text
order update
    +
outbox event
```

in the same database transaction.

A separate publisher reads pending outbox rows.

## Why it works

It avoids the dual-write failure:

```text
DB commit succeeds
message publish fails
```

or:

```text
message publishes
DB transaction rolls back
```

The outbox does not guarantee exactly-once processing. Consumers still need idempotency.

---

# 27. Anti-Pattern: Dual Writes Without a Contract

Example:

```typescript
await db.updateOrder(orderId);
await kafka.publish(event);
```

A process crash between the statements creates divergence.

“Retry later” does not solve the fundamental ordering problem unless the operation has an explicit recovery model.

The schema itself can help by storing a durable event/outbox record in the same transaction.

---

# 28. Pattern: Idempotency Key Table

For externally retried commands, create a durable idempotency record.

Example:

```sql
CREATE TABLE request_idempotency (
    tenant_id bigint NOT NULL,
    idempotency_key text NOT NULL,
    response_code integer,
    response_body jsonb,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, idempotency_key)
);
```

Now a repeated request can be recognized as the same logical operation.

This is especially useful for:

```text
payments
order creation
webhooks
inventory mutations
external integrations
```

The important idea is that idempotency is a **data property**, not just a retry-loop property.

---

# 29. Pattern: Ledger-Style Append Model

For balances or accounting-like systems, consider storing immutable entries:

```text
ledger_entries
--------------
id
account_id
amount
currency
occurred_at
reference
```

A balance may then be calculated from entries or maintained as an explicitly governed projection.

The key advantage is recoverability:

```text
Current state
      ↑
Derived from
      ↑
Immutable facts
```

The main trade-off is read complexity and the need for carefully designed indexes and reconciliation.

---

# 30. Pattern: Summary / Projection Table

When a read is expensive but deterministic, a derived table can cache a projection.

Example:

```text
customer_balance_summary
------------------------
customer_id
balance
updated_at
```

The projection is not the source of truth.

It must have a rebuild strategy:

```text
source facts
    ↓
recompute
    ↓
projection
```

A summary table without a reconciliation strategy is a latent consistency problem.

---

# 31. Anti-Pattern: Unrebuildable Derived State

Suppose:

```text
orders.total_amount
```

is manually updated by several code paths.

Months later, the total is wrong.

The team asks:

> “How do we recalculate the correct value?”

There is no answer.

That is a dangerous derived-state design.

Every denormalized value should have an explicit answer to:

```text
What is the source of truth?
How is it updated?
How is it validated?
How is it rebuilt?
How is drift detected?
```

---

# 32. Pattern: Tenant-Scoped Boundary

For shared SaaS tables, tenant ownership should be visible in the schema.

Example:

```sql
CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL REFERENCES tenants(id),
    sku text NOT NULL,
    UNIQUE (tenant_id, sku)
);
```

For sensitive relationships, composite foreign keys can prevent cross-tenant references.

Conceptually:

```text
(parent tenant_id, parent id)
          ↑
(child tenant_id, child parent_id)
```

This makes a security boundary part of relational integrity instead of relying exclusively on application filters.

---

# 33. Anti-Pattern: Tenant ID Exists but Is Not Part of Integrity

A table may contain:

```text
tenant_id
customer_id
```

while `customer_id` references a global customer ID with no verification that the customer belongs to the same tenant.

Then this invalid state may be possible:

```text
order.tenant_id = 10
order.customer_id = customer belonging to tenant 20
```

The query may still “work.”

But the schema permits a cross-tenant reference.

The lesson:

> **A tenant column that is not part of the relevant integrity boundary may be only metadata, not isolation.**

---

# 34. Pattern: Explicit Boundary Tables

Sometimes a business boundary deserves a dedicated entity:

```text
organization
branch
warehouse
legal_entity
account
project
```

rather than putting opaque IDs everywhere.

A boundary entity can own:

```text
permissions
configuration
currency
timezone
numbering rules
retention
```

This makes the architecture easier to reason about.

---

# 35. Pattern: Effective-Dated Configuration

Configuration that changes over time should often be modeled with validity intervals.

Example:

```text
branch_tax_rates
----------------
branch_id
rate
valid_during
```

PostgreSQL range types plus exclusion constraints are particularly useful for preventing overlapping configurations.

Conceptually:

```text
branch 7
[2026-01-01, 2026-04-01)
[2026-04-01, 2026-07-01)
```

rather than storing only:

```text
current_rate
```

when historical correctness matters.

---

# 36. Anti-Pattern: Current-Row Overwrite for Historical Configuration

Suppose tax rate changes from 18% to 20%.

Overwriting:

```text
rate = 20
```

destroys the historical relationship between old documents and the previous rate.

If past documents need to remain correct, choose one of:

```text
snapshot
version table
effective-dated rows
immutable transaction fact
```

depending on the domain.

---

# 37. Pattern: Polymorphic References — Use Carefully

A polymorphic reference often looks like:

```text
entity_type
entity_id
```

Example:

```text
comments
--------
commentable_type
commentable_id
```

This is flexible but cannot be protected by a conventional single foreign key to multiple possible tables.

Consequences include:

```text
orphan risk
application-enforced integrity
complex joins
hard cascades
hard indexing decisions
```

Use it only when the polymorphism is genuinely required.

Possible alternatives:

```text
common parent table
separate typed junctions
union-like modeling
```

---

# 38. Anti-Pattern: “One ID Column References Anything”

This is attractive in generic frameworks:

```text
owner_id
owner_type
```

but it shifts referential integrity into code.

A relational system is strongest when legal references are explicit enough for the database to enforce them.

Genericity has a cost.

The expert question is:

> “What integrity am I giving up to gain this flexibility?”

---

# 39. Pattern: Explicit Ordering

Suppose a relationship needs user-defined ordering:

```text
playlist_tracks
---------------
playlist_id
track_id
position
```

Do not infer ordering from:

```text
created_at
id
physical row order
```

unless the domain explicitly defines that semantics.

Use an attribute that represents the actual ordering rule.

Depending on the workload, consider whether the position is:

- dense integer positions
- sparse numeric positions
- lexicographic ordering keys
- timestamp ordering

The choice affects update cost when items are inserted in the middle.

---

# 40. Anti-Pattern: Relying on Row Order

This is invalid reasoning:

```sql
SELECT * FROM messages;
```

and assuming the returned rows are in insertion order.

SQL result ordering is not guaranteed without an explicit `ORDER BY`.

Likewise, PostgreSQL physical tuple order is not a business ordering contract.

Define the ordering fact explicitly.

---

# 41. Pattern: Canonical Identifier + Alternate Keys

Sometimes entities need several lookup identities:

```text
internal ID
external system ID
business code
email
```

A strong design separates:

```text
canonical identity
alternate unique keys
```

Example:

```sql
PRIMARY KEY (id),
UNIQUE (tenant_id, external_id),
UNIQUE (tenant_id, code)
```

Do not overload one field with multiple identity semantics.

---

# 42. Pattern: Boundary-Preserving Composite Keys

Composite keys can encode more than uniqueness.

Example:

```text
(tenant_id, customer_id)
```

can become the identity boundary for a tenant-owned entity.

Then a child can reference:

```text
(parent_tenant_id, customer_id)
```

This can make invalid cross-scope relationships structurally impossible.

Trade-off:

```text
larger indexes
wider FKs
more verbose joins
```

The benefit is stronger correctness and clearer scope.

---

# 43. Pattern: Specialized Search Columns

When one logical entity has a read pattern with strict performance requirements, derived search data may be represented explicitly.

Examples:

```text
normalized_email
search_vector
lowered_code
geography projection
```

Generated columns or expression indexes may avoid duplicating business state manually.

The key question is:

> “Is this column a source fact or a derived access structure?”

That distinction controls update and rebuild strategy.

---

# 44. Anti-Pattern: Storing Every Query Result

Teams sometimes denormalize aggressively:

```text
customer_name
customer_email
customer_city
customer_country
customer_order_count
customer_last_order_date
customer_balance
```

into every dependent row.

This can reduce joins for some reads but creates synchronization complexity.

Prefer:

```text
indexes
materialized views
projection tables
generated values
purposeful snapshots
```

based on measured workload.

Do not turn every join into duplicated state by default.

---

# 45. Pattern: Search / Operational Read Model Split

A transactional schema does not have to serve every read shape directly.

For example:

```text
OLTP tables
    ↓
projection process
    ↓
search/read model
```

The read model can be optimized for:

```text
search
analytics
API aggregation
reporting
```

The crucial requirement is a clearly defined source of truth and replay/rebuild path.

---

# 46. Anti-Pattern: ORM-Driven Schema Design

ORMs are useful application tools.

They should not become the database modeling authority by accident.

Common ORM-driven mistakes:

```text
one table per class
surrogate IDs everywhere
implicit cascade delete
hidden join tables
JSON for difficult relationships
nullable foreign keys to satisfy serializers
application-only uniqueness
```

The database schema should be explainable without referring to the ORM's conventions.

---

# 47. Pattern: Database-First Contract Review

Before implementation, review each table using a fixed checklist:

```text
What does one row mean?
What identifies it?
What makes two rows duplicates?
Which fields may be NULL?
Which relationships are mandatory?
Who owns the lifecycle?
Which values are historical snapshots?
Which rules need database constraints?
Which reads dominate?
What must remain rebuildable?
```

This catches many design defects before migrations are written.

---

# 48. Pattern: Migration-Friendly Evolution

A production schema must evolve without relying on perfect deployment timing.

Prefer changes that are compatible across rollout stages.

Typical sequence:

```text
Expand
→ Deploy application compatibility
→ Backfill
→ Validate
→ Switch reads/writes
→ Contract old structure
```

Examples:

```text
add nullable column
backfill in batches
start dual-read / dual-write where needed
make constraint stricter
remove obsolete column later
```

Avoid migrations that require every running process to understand a new schema instantaneously.

---

# 49. Anti-Pattern: “Add Constraint Later” Without a Data Plan

Suppose a team wants:

```sql
ALTER TABLE users
ADD CONSTRAINT users_email_key UNIQUE (email);
```

but existing duplicates exist.

The migration fails.

Worse, the team may temporarily omit the constraint and hope application code prevents new duplicates.

A correct migration plan includes:

```text
detect violations
classify duplicates
choose canonical records
repair references
add uniqueness
```

Integrity changes are data migrations, not merely DDL changes.

---

# 50. Pattern: Constraint-Backed Invariants

A production schema should push invariants down to the database whenever the database can reliably enforce them.

Examples:

```text
NOT NULL
CHECK
UNIQUE
PRIMARY KEY
FOREIGN KEY
EXCLUDE
partial unique index
```

Application validation remains useful for user experience and complex workflows.

But:

```text
application validation ≠ database integrity
```

The application can race.

The database sees concurrent transactions.

---

# 51. Anti-Pattern: Check-Then-Insert

This classic pattern is unsafe:

```sql
SELECT 1
FROM coupons
WHERE code = $1;

-- application sees no row

INSERT INTO coupons(code)
VALUES ($1);
```

Two transactions can both observe absence.

Correct solution:

```sql
UNIQUE (code)
```

and an atomic insertion strategy such as:

```sql
INSERT ... ON CONFLICT ...
```

The invariant belongs in the database.

---

# 52. Pattern: Explicit Nullability Semantics

Every nullable column creates at least three conceptual states in many application contexts:

```text
present value
NULL
not represented by query/API field
```

Do not use NULL merely because “the framework allows optional fields.”

Ask what NULL actually means:

```text
unknown
not applicable
not yet known
intentionally absent
not collected
```

If those meanings differ, they may require different schema representations.

---

# 53. Anti-Pattern: NULL as a State Machine

This becomes difficult to reason about:

```text
approved_at = NULL
cancelled_at = NULL
processed_at = NULL
```

and the application infers status from combinations.

Sometimes timestamps are excellent facts.

But if the domain has explicit workflow states, do not make developers reconstruct the state machine from a collection of nullable timestamps without a clear invariant model.

---

# 54. Pattern: Separate Facts From Projections

A healthy architecture distinguishes:

```text
Source facts
```

from:

```text
Derived projections
```

For example:

```text
order_items        ← source facts
orders.total       ← derived projection
customer_summary   ← derived projection
search_document    ← derived projection
```

This makes recovery possible:

```text
facts
  ↓
rebuild
  ↓
projections
```

It also improves incident response because teams know what can be safely recalculated.

# 56. Production Scenario — Jewellery ERP

Consider a multi-tenant jewellery ERP.

Business concepts may include:

```text
Tenant
Branch
Customer
Product
Inventory Item
Purchase
Sale
Invoice
Invoice Item
Payment
Price Rule
Stock Movement
Audit Event
```

A weak schema might put:

```text
customer_id
branch_id
product_ids
payment_ids
stock_ids
```

into a giant transaction document.

A stronger relational design separates facts:

```text
sale
----
id
tenant_id
branch_id
customer_id
status

sale_items
----------
sale_id
inventory_item_id
quantity
price

payments
--------
sale_id
amount
method

stock_movements
---------------
inventory_item_id
quantity_delta
reason
```

Historical values that must not change can be snapshotted deliberately.

Tenant boundaries are encoded through scoped keys and foreign keys where appropriate.

The result is more tables—but fewer ambiguous facts.

---

# 57. Production Scenario — Inventory Reservation

Requirement:

> A physical inventory item may not be reserved by two active reservations at overlapping times.

A naive design might use:

```text
reserved = true
```

This loses temporal semantics and makes future reservations difficult.

A stronger model may use:

```text
inventory_reservations
----------------------
inventory_item_id
reservation_window
status
```

with range semantics and appropriate constraints.

The pattern is valuable because it encodes the business rule near the data rather than relying solely on race-prone application checks.

---

# 58. Production Scenario — Invoice Numbering

Requirement:

> Invoice numbers are unique per branch and may follow a branch-specific sequence.

Possible design:

```text
branch_id
invoice_number
```

with:

```sql
UNIQUE (branch_id, invoice_number)
```

Do not use a single global uniqueness rule unless the business requires it.

If allocation is concurrent, use a transactional mechanism designed for sequence generation rather than:

```sql
SELECT MAX(invoice_number) + 1
```

The latter is a race condition.

---

# 59. Production Scenario — Product Attributes

Suppose products have standard attributes:

```text
metal
purity
weight
barcode
```

but occasional product families add:

```text
stone_count
stone_shape
certificate_id
```

Do not immediately choose EAV or a giant JSONB blob.

Classify the attributes.

If attributes are:

```text
stable
typed
heavily queried
constrained
indexed
```

relational columns or typed extension tables are usually preferable.

If they are:

```text
sparse
variable
document-like
rarely queried individually
```

JSONB may be justified.

The decision should follow workload and integrity needs.

---

# 60. Production Scenario — Reporting Database

A reporting workload may need denormalized structures that are intentionally poor OLTP representations.

For example:

```text
sales_daily_summary
-------------------
day
branch_id
product_category_id
gross_sales
net_sales
transaction_count
```

This may be an excellent analytical structure even though it duplicates facts from normalized transactional tables.

The pattern is justified when:

```text
read workload is known
refresh process is explicit
source of truth is clear
staleness is acceptable
rebuild is possible
```

The error is not denormalization itself.

The error is **uncontrolled denormalization**.

# 61. Performance Reasoning

Schema patterns affect performance in several dimensions.

## Read amplification

Normalized data may require more joins.

## Write amplification

Indexes, history rows, outbox records, projections, and constraints increase writes.

## Storage amplification

Snapshots and projections consume additional storage.

## Lock / contention amplification

Hot counters and centralized numbering rows may create contention.

## Query-planner complexity

Highly generic schemas can create complicated query shapes that are harder to estimate accurately.

There is no universally fastest pattern.

Measure the workload.

---

# 62. EXPLAIN-Based Pattern Validation

When a pattern is introduced for performance, validate the actual query plan.

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Look for:

```text
actual rows vs estimated rows
sequential scans
index scans
bitmap scans
sort cost
hash memory
buffer hits
buffer reads
```

Do not conclude:

> “This schema is faster because it has fewer joins.”

until workload evidence supports it.

A simpler query can still be slower because of poor selectivity or missing indexes.

---

# 63. Security Reasoning

Schema patterns can create security boundaries—or destroy them.

Examples:

```text
tenant-scoped foreign keys
RLS policies
least-privilege ownership
separate sensitive subtype tables
audit history
```

Anti-patterns include:

```text
polymorphic IDs with application-only authorization
shared generic ownership tables
implicit tenant filtering
unconstrained JSON authority fields
```

Never assume “the API always adds tenant_id” is equivalent to database-level isolation for security-sensitive data.

# 64. AI / Vibe-Coding Failure Modes

AI-generated schema proposals frequently exhibit the same patterns.

### Failure 1 — Giant JSONB object

Because requirements were ambiguous.

Problem:

```text
unknown structure becomes permanent structure
```

### Failure 2 — One generic table

Because the model tries to “avoid duplicate tables.”

Problem:

```text
row grain becomes ambiguous
```

### Failure 3 — Arrays for relationships

Because the API naturally exposes arrays.

Problem:

```text
API shape ≠ relational storage model
```

### Failure 4 — Application-only uniqueness

Because framework validation is easier to write.

Problem:

```text
race condition
```

### Failure 5 — `ON DELETE CASCADE` everywhere

Because it makes tests pass cleanly.

Problem:

```text
destructive lifecycle semantics
```

### Failure 6 — `updated_at` called “audit log”

Because the schema contains some metadata.

Problem:

```text
history is not reconstructible
```

### Failure 7 — `MAX(id) + 1`

Because it appears simple.

Problem:

```text
concurrent allocation race
```

### Failure 8 — Soft delete everywhere

Because deletion feels irreversible.

Problem:

```text
every query inherits hidden lifecycle semantics
```

The cure is not “never use these techniques.”

The cure is:

> **Demand the invariant, workload, and failure model behind the design.**

# 65. Review Workflow for New Schemas

Use this review order:

### Step 1 — Write row-grain sentences

For every table:

> “One row represents ______.”

### Step 2 — Identify identity

What makes two rows the same logical fact?

### Step 3 — Identify relationships

Who owns whom?

### Step 4 — Classify values

Are they:

```text
source fact
reference data
derived value
snapshot
configuration
history
projection
```

### Step 5 — Encode invariants

Use constraints where possible.

### Step 6 — Model lifecycle

What happens on:

```text
create
update
archive
delete
restore
correction
```

### Step 7 — Model concurrency

Ask:

> “What happens when two requests do this at the same time?”

### Step 8 — Evaluate workload

Measure:

```text
read/write ratio
hot paths
cardinality
selectivity
growth rate
retention
```

### Step 9 — Design observability

Determine what must be measurable when the schema misbehaves.

### Step 10 — Design evolution

Ask how version N+1 will migrate from version N.

# 66. Pattern vs Anti-Pattern Matrix

| Pattern | Strong when | Dangerous when |
|---|---|---|
| Parent-child | lifecycle is hierarchical | ownership is unclear |
| Junction table | relationship is many-to-many | relationship semantics are ignored |
| Scoped uniqueness | identity is tenant/branch scoped | scope is chosen incorrectly |
| State machine | lifecycle is explicit | booleans are already contradictory |
| Snapshot | historical meaning matters | copied facts are expected to stay synchronized |
| Outbox | DB + event must be durable | consumers assume exactly-once |
| Idempotency table | requests may retry | retention is unmanaged |
| Summary table | reads justify projection | no rebuild/reconciliation exists |
| Subtype table | specialized attributes differ | inheritance is forced everywhere |
| JSONB extension | structure is genuinely flexible | relational invariants disappear into JSON |
| Soft delete | retention/restoration is required | every table is made immortal |
| Polymorphic reference | true polymorphism is essential | referential integrity is critical |

# 67. Production Decision Framework

When two designs are both valid, score them on:

```text
1. Correctness
2. Integrity strength
3. Concurrency behavior
4. Query complexity
5. Write cost
6. Read cost
7. Index cost
8. Storage cost
9. Historical correctness
10. Migration safety
11. Rebuildability
12. Operational simplicity
13. Security boundary clarity
14. Team maintainability
```

A design that wins only on one dimension is not automatically better.

# 68. Expert Principle — Minimize Unstated Semantics

Bad schemas force developers to remember hidden rules:

```text
“this ID only belongs to the current tenant”
“these two booleans cannot both be true”
“this JSON field must always exist”
“deleted rows must be ignored”
“invoice address must never change”
```

Good schemas make as many of these rules explicit as practical.

```text
constraint
key
FK
CHECK
range
status
history
scope
```

This reduces the amount of correctness that exists only inside human memory.

# 69. Testing Strategy

A schema pattern should be tested against its intended invariant.

## Constraint tests

Attempt invalid states deliberately.

## Concurrency tests

Run competing transactions.

Examples:

```text
same unique key
same reservation window
same idempotency key
same balance update
```

## Migration tests

Test:

```text
existing bad data
partial rollout
retry
rollback path where supported
```

## Rebuild tests

For projections:

```text
wipe projection
rebuild from source
compare results
```

## Property-oriented testing

Example property:

> “There can never be two active primary addresses for one customer.”

The test should attempt to violate it through multiple paths.

# 75. Final Takeaway

The strongest database engineers do not memorize a catalog of “best schemas.”

They develop the ability to move from:

```text
business rule
```

to:

```text
fact
→ grain
→ identity
→ relationship
→ constraint
→ lifecycle
→ workload
→ pattern
→ operational contract
```

A pattern becomes valuable when it makes the right thing easier to preserve.

An anti-pattern becomes dangerous when it makes the wrong state easier to create.

The deepest rule for this chapter is:

> **Prefer schemas that make correctness obvious, invalid states difficult, historical meaning explicit, concurrency safe, derived state rebuildable, and future change survivable.**

That is the difference between a schema that merely works today and a schema that can support a production system for years.
