# 02.18 — Financial / Ledger Modeling

> **Phase 02 — Relational Data Modeling**
>
> Financial data is where relational modeling becomes a discipline of preserving **economic truth**. A production financial schema must do more than store amounts: it must define what financially happened, when it became authoritative, which accounts were affected, how the effect can be corrected, and how the resulting balance can be proven later.

---

## 1. Objective

This chapter explains how to model money, accounts, journal entries, ledger postings, double-entry invariants, currencies, rounding, corrections, reversals, accounting periods, idempotency, balance projections, reconciliation, and long-term financial history in PostgreSQL.

By the end, you should be able to reason about:

- what constitutes a financial fact;
- why a ledger is different from an operational table;
- how double-entry accounting maps to relational structures;
- how to represent money precisely;
- how to preserve currency and rounding semantics;
- how to make posting immutable;
- how to correct a posted transaction without destroying history;
- how to prevent duplicate financial effects during retries;
- how to protect closed accounting periods;
- how to model balance projections safely;
- how to reconcile projections and external systems;
- how to design multi-tenant financial data;
- how to analyze a financial discrepancy using evidence rather than guesswork.

---

# 2. Core Principle

> **A ledger is authoritative because it preserves a chain of financial facts from which balances can be derived and explained.**

A balance by itself tells you:

```text
Current balance = ₹9,75,000
```

A ledger can tell you:

```text
Opening balance
+ sale posting
+ payment posting
- refund
+ adjustment
- reversal
= current balance
```

The second representation is operationally and audit-wise much stronger because the result can be decomposed into explainable facts.

---

# 3. Financial Modeling Vocabulary

Terminology differs across accounting systems, but engineers need a stable mental model.

## 3.1 Account

An account is a financial bucket whose balance is tracked.

Examples:

```text
Cash
Bank
Accounts Receivable
Inventory Asset
Sales Revenue
Tax Payable
Supplier Payable
Discount Expense
```

## 3.2 Financial transaction

A business-level financial occurrence.

Examples:

```text
Sale
Payment
Refund
Supplier settlement
Inventory valuation adjustment
Tax posting
```

## 3.3 Journal entry

A logical accounting unit that groups postings which must be treated as one financial event.

```text
Journal J1001
├── Posting A
├── Posting B
└── Posting C
```

## 3.4 Posting / ledger entry

A posting is the effect of a journal entry on one account.

Example:

```text
Dr Customer Receivable  10,000
Cr Sales Revenue        10,000
```

## 3.5 Balance

A derived state representing the net effect of postings under a defined account-sign convention.

The exact debit/credit sign convention must be explicit in the system. Never let individual developers invent it independently.

# 4. Financial Fact vs Operational State

Consider an ecommerce or ERP application.

```text
orders.status = 'completed'
```

This is operational state.

It does not necessarily answer:

```text
Was revenue recognized?
Was payment settled?
Was tax posted?
Which accounts changed?
Which period was affected?
```

A financial transaction should therefore be modeled separately from workflow state.

A conceptual architecture is:

```text
Operational domain
      |
      v
Business event
      |
      v
Financial transaction
      |
      v
Journal entry
      |
      v
Ledger postings
      |
      v
Balance / reporting projections
```

# 5. Money Representation

## 5.1 Never make floating point the financial authority

Do not model authoritative money with a binary floating-point field merely because the application language has a `number` type.

Bad conceptual design:

```ts
const amount: number = ...;
```

and then assuming every arithmetic result is an exact decimal monetary result.

For PostgreSQL, exact decimal arithmetic is commonly represented with `numeric`/`decimal`. PostgreSQL documents `numeric` as an exact numeric type suitable for values where exactness is required. citeturn256961search11

Example:

```sql
amount numeric(20,4) NOT NULL
```

The appropriate precision and scale depend on the financial domain.

---

## 5.2 Minor-unit integers

Another valid strategy is storing the smallest monetary unit as an integer:

```sql
amount_minor bigint NOT NULL
```

For a currency with two minor decimal places:

```text
₹10.50 -> 1050
```

Advantages:

- exact integer arithmetic;
- clear comparisons;
- no decimal rounding during storage.

Limitations:

- assumes a fixed minor-unit convention;
- can complicate multi-currency support;
- intermediate calculations may need more precision than the final minor unit.

There is no universal rule that one representation is always correct.

---

## 5.3 PostgreSQL `money`

Do not select PostgreSQL `money` merely because the application is about money. It has fixed fractional behavior and locale/display considerations that may not fit a multi-currency application-facing ledger.

A general-purpose production design frequently has clearer semantics with `numeric`, but the final choice should come from domain requirements.

---

# 6. Currency Is Part of the Amount's Meaning

This is invalid as a financial concept:

```text
amount = 1000
```

because the unit is absent.

Use an explicit currency contract:

```text
amount = 1000
currency = INR
```

Example:

```sql
amount numeric(20,4) NOT NULL,
currency_code char(3) NOT NULL
```

The exact currency convention must be consistent across the system.

---

# 7. Transaction Currency vs Accounting Currency

A global system may require both.

Example:

```text
Transaction amount:   USD 100.00
Accounting amount:    INR 8,350.00
FX rate:              83.50
```

Modeling only one amount can destroy the ability to answer:

```text
What did the customer actually pay?
What amount entered the company's functional ledger?
What FX rule was used?
```

A multi-currency system may therefore need explicit fields such as:

```text
source_currency
source_amount
functional_currency
functional_amount
fx_rate
fx_rate_source
fx_observed_at
```

---

# 8. Rounding Is a Domain Rule

Rounding is not merely display formatting.

Possible rules include:

```text
round per line
round per tax component
round per invoice
round at final settlement
round only after FX conversion
```

These produce different results.

Therefore a financial system should make the rounding contract explicit rather than scattering arbitrary calls to:

```ts
Math.round(...)
```

through business logic.

---

# 9. Double-Entry Accounting as a Database Invariant

The classic ledger invariant is:

```text
Total Debits = Total Credits
```

Example:

```text
Sale of ₹11,800

Dr Customer Receivable  11,800
Cr Sales Revenue        10,000
Cr Tax Payable            1,800

Total Debits             11,800
Total Credits            11,800
```

The exact account classifications may vary, but the journal must balance according to the accounting model.

This is an aggregate invariant across multiple rows, not a simple per-row property.

---

# 10. Why a Row `CHECK` Cannot Solve Everything

A row-level constraint like:

```sql
CHECK (amount > 0)
```

can ensure each posting is individually valid.

It cannot by itself express:

```text
sum(all postings in this journal) must balance
```

This is a fundamental modeling lesson:

> **Some business invariants exist across rows and therefore require transaction/procedure/trigger architecture rather than a single row constraint.**

PostgreSQL's constraint system is powerful, but `CHECK` constraints are not an aggregate query language. PostgreSQL 18's documentation explicitly distinguishes ordinary constraint classes and their enforcement behavior. citeturn256961search0turn256961search1

# 11. Baseline Relational Model

A practical baseline is:

```text
accounts
   |
   v
journal_entries
   |
   v
ledger_postings
```

Potential schema:

```sql
CREATE TABLE accounts (
    id uuid PRIMARY KEY,
    code text NOT NULL UNIQUE,
    name text NOT NULL,
    account_type text NOT NULL,
    currency_code char(3),
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Journal header:

```sql
CREATE TABLE journal_entries (
    id uuid PRIMARY KEY,
    external_reference text,
    status text NOT NULL,
    occurred_at timestamptz NOT NULL,
    posted_at timestamptz,
    created_at timestamptz NOT NULL DEFAULT now(),
    CHECK (status IN ('draft', 'posted', 'reversed'))
);
```

Postings:

```sql
CREATE TABLE ledger_postings (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    journal_entry_id uuid NOT NULL
        REFERENCES journal_entries(id),
    account_id uuid NOT NULL
        REFERENCES accounts(id),
    direction char(1) NOT NULL
        CHECK (direction IN ('D', 'C')),
    amount numeric(20,4) NOT NULL
        CHECK (amount > 0),
    currency_code char(3) NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

This is intentionally incomplete. A production ledger still needs to solve balancing, currency consistency, posting immutability, idempotency, accounting periods, source provenance, tenant isolation, and projection strategy.

---

# 12. Journal Header + Posting Rows

The header/detail split is valuable because one financial event can affect many accounts.

```text
J1001
├── Cash               Dr 11,800
├── Sales Revenue      Cr 10,000
└── Tax Payable         Cr  1,800
```

It allows queries such as:

```text
Which accounts did this journal affect?

Which journals affected this account?

What source document created this journal?

Which journals were reversed?
```

It also provides a natural unit for posting and correction.

---

# 13. Journal State Model

A useful baseline is:

```text
DRAFT
  |
  v
POSTED
  |
  v
REVERSED
```

Typical semantic rule:

```text
DRAFT     -> mutable
POSTED    -> immutable financial fact
REVERSED  -> historical fact with compensating effect
```

Do not casually implement:

```text
POSTED -> DRAFT
```

because that makes historical financial state mutable.

---

# 14. Posting Is a Boundary

A useful workflow is:

```text
Create draft
    ↓
Build postings
    ↓
Validate
    ├── accounts valid
    ├── currency valid
    ├── amount valid
    ├── journal balances
    ├── period open
    ├── authorization valid
    ├── idempotency valid
    └── source valid
    ↓
POST
    ↓
IMMUTABLE
    ↓
OUTBOX EVENT
    ↓
PROJECTIONS
```

The posting boundary is therefore more important than the UI button named “Submit”.

---

# 15. Correcting a Posted Entry

Suppose the original entry is wrong:

```text
J100
Dr Customer Receivable 10,000
Cr Revenue             10,000
```

Do not edit:

```sql
UPDATE ledger_postings
SET account_id = ...
```

Instead create a compensating history:

```text
J100 original

J101 reversal
Dr Revenue             10,000
Cr Customer Receivable 10,000

J102 corrected entry
Dr Correct Account      10,000
Cr Correct Revenue      10,000
```

The exact entries depend on the error.

The architectural rule is:

> **Correct history with new history.**

---

# 16. Why DELETE Is Usually Wrong for Posted Facts

Deletion destroys the original evidence.

Problems include:

- audit gaps;
- unexplained balance movement;
- reconciliation difficulty;
- dispute investigation difficulty;
- inability to understand historical reporting.

Operational tables may use soft delete.

Posted ledger facts generally need a stronger immutability contract.

---

# 17. Reversal vs Refund vs Correction

Do not treat every negative amount as the same concept.

They may represent:

```text
reversal
refund
chargeback
adjustment
credit note
write-off
correction
```

These should remain distinguishable when their business meaning differs.

A generic:

```text
amount = -100
```

without a reason or source reference creates ambiguity.

---

# 18. Partial Reversal / Partial Refund

A full reversal and a partial refund are not identical.

Example:

```text
Original:  ₹10,000
Refund:     ₹2,000
Remaining economic effect: ₹8,000
```

Preserve:

```text
original_journal_id
related_operation_id
refund_amount
reason_code
```

Do not rewrite the original amount.

---

# 19. Source Provenance

A strong ledger can answer:

```text
Why does this posting exist?
Which business document caused it?
Which request initiated it?
Who created/approved it?
Which transaction does it reverse?
```

Useful dimensions may include:

```text
source_type
source_id
external_reference
idempotency_key
reason_code
created_by
approved_by
```

But avoid generic polymorphic references everywhere if doing so removes enforceable foreign-key integrity.

---

# 20. Polymorphic References: Trade-Off

Example:

```text
source_type = 'invoice'
source_id   = '...'
```

Advantages:

- flexible;
- simple generic schema.

Disadvantages:

- database cannot normally enforce a foreign key to multiple possible tables;
- dangling references become possible;
- integrity moves into application code.

A more relational alternative can use explicit relation tables or distinct source-specific references.

Choose based on the required integrity level.

---

# 21. Idempotency Is a Financial Invariant

Financial APIs are routinely retried.

Example:

```text
Client sends payment request
        ↓
Database commit succeeds
        ↓
HTTP response is lost
        ↓
Client retries
```

Without idempotency, the system can create two financial effects.

A stable operation identity is therefore essential.

Example:

```sql
CREATE TABLE financial_operations (
    id uuid PRIMARY KEY,
    idempotency_key text NOT NULL UNIQUE,
    operation_type text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

The unique constraint is the final database-level race barrier.

---

# 22. Why Check-Then-Insert Fails

Naive flow:

```text
SELECT idempotency_key
if absent:
    INSERT
```

Concurrent execution:

```text
T1: SELECT -> missing
T2: SELECT -> missing
T1: INSERT
T2: INSERT
```

Use a unique constraint and transactionally handle the conflict.

Do not trust a preceding `SELECT` as the sole uniqueness mechanism.

---

# 23. Account Balance as Projection

A strong mental model is:

```text
ledger = authority
balance = projection
```

Potential projection:

```sql
CREATE TABLE account_balances (
    account_id uuid PRIMARY KEY,
    balance numeric(20,4) NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

This is useful for fast reads.

But define a repair path:

```text
ledger postings
      ↓
recalculate
      ↓
compare projection
      ↓
repair
```

A projection that cannot be rebuilt is risky.

---

# 24. Compute vs Cache vs Hybrid

## Compute every time

```sql
SUM(...)
```

Strong correctness model, potentially expensive.

## Maintain a balance row transactionally

Fast reads, but introduces:

- write coupling;
- hot-row contention;
- more state to reconcile.

## Hybrid

```text
immutable ledger
+
transactional/current balance projection
+
periodic reconciliation
```

This is frequently a practical production architecture.

---

# 25. Hot Account Contention

Suppose thousands of payments update the same account.

```sql
UPDATE account_balances
SET balance = balance + :delta
WHERE account_id = :id;
```

The account row can become a concurrency hotspot.

Possible responses include:

- partitioned balance structures;
- period aggregates;
- append-first designs;
- asynchronous projections;
- account-level partitioning/sharding.

The right answer depends on workload.

Do not sacrifice correctness based on a hypothetical throughput problem.

---

# 26. Accounting Periods

A financial system often needs explicit periods.

Example:

```sql
CREATE TABLE accounting_periods (
    id uuid PRIMARY KEY,
    period_start date NOT NULL,
    period_end date NOT NULL,
    status text NOT NULL,
    CHECK (period_start < period_end),
    CHECK (status IN ('open', 'closed', 'locked'))
);
```

A posted transaction should reference or otherwise resolve to an accounting period.

The system must define when a period becomes unavailable for posting.

---

# 27. Period State Transitions

Conceptual lifecycle:

```text
OPEN
  ↓
SOFT_CLOSED
  ↓
CLOSED
  ↓
LOCKED
```

The exact states depend on the business.

What matters is that posting logic understands the state and enforces it transactionally.

---

# 28. Period Close Race Condition

Naive:

```text
T1 checks period = OPEN
T2 closes period
T1 posts
```

This can allow posting into a logically closed period.

The posting and close operations need explicit transactional coordination using suitable locking/isolation and a consistent rule for which operation wins.

`SERIALIZABLE` may be useful for some workloads, but it is not a substitute for a clearly defined invariant and transaction design.

---

# 29. Financial Timestamps

Avoid using one generic timestamp for every question.

Possible meanings:

```text
occurred_at
recorded_at
posted_at
settled_at
value_date
accounting_date
created_at
```

Example:

```text
Payment occurred: 2026-09-14 09:30
Recorded:          2026-09-14 09:35
Posted:             2026-09-14 09:36
Settled:            2026-09-15 10:10
```

Historical reporting must use the correct business timestamp, not whichever timestamp happens to be easiest to access.

---

# 30. Historical Rules Must Remain Explainable

Suppose a tax rule changes on:

```text
2026-07-01
```

A transaction from:

```text
2026-06-20
```

must not suddenly acquire a different historical meaning merely because today's service code changed.

Preserve enough information to explain the original result.

This is why financial modeling intersects with temporal and audit architecture.

---

# 31. Tax Modeling

A tax amount alone often does not explain enough.

Depending on the domain, preserve:

```text
taxable base
rate
jurisdiction
component
calculated amount
rounding rule/version
ledger account
```

This can answer:

```text
Why was tax 1,800?
Which rate generated it?
Which component created the posting?
```

The exact retention requirements are domain-specific.

---

# 32. Discounts

Two common models are:

### Net amount model

```text
Revenue = after-discount amount
```

### Explicit discount posting

```text
Gross Sales           1,000
Discount                100
Net Revenue             900
```

The right model depends on accounting/reporting requirements.

Do not collapse every adjustment into an unexplained signed number.

---

# 33. Multi-Currency Ledger Design

There are multiple valid approaches.

### One-currency journal

Every posting in a journal uses one currency.

### Dual-currency model

The transaction preserves source currency and functional/accounting amount.

### Multi-line FX journal

Explicit exchange-rate gain/loss accounts represent conversion effects.

The model must define what “balanced” means when multiple currencies are involved.

Numeric equality alone is not enough:

```text
1000 INR != 1000 USD
```

---

# 34. FX History

Do not silently recompute historical transactions using today's FX rate.

Potentially preserve:

```text
source amount
source currency
target amount
target currency
rate
rate source
rate timestamp
pricing policy/version
```

The exact data retained depends on the business and reporting requirements.

---

# 35. Suspense Accounts

External data may temporarily lack enough information for classification.

Instead of dropping it:

```text
Unknown payment
      ↓
Suspense account
      ↓
Reconciliation / classification
      ↓
Correct account
```

This makes uncertainty explicit rather than silently losing the financial effect.

Suspense balances should be monitored and aged.

---

# 36. Payment Lifecycle vs Ledger Lifecycle

Operational payment states might be:

```text
INITIATED
AUTHORIZED
CAPTURED
SETTLED
FAILED
REFUNDED
```

Accounting states may be different.

Do not assume:

```text
payment.status = CAPTURED
```

automatically means:

```text
journal.status = POSTED
```

The relationship must be explicitly defined.

---

# 37. Approval and Separation of Duties

Large financial adjustments may require:

```text
CREATED
  ↓
SUBMITTED
  ↓
APPROVED
  ↓
POSTED
```

Possible identities:

```text
created_by
approved_by
posted_by
reconciled_by
```

Do not rely on the UI alone for high-impact authorization controls.

---

# 38. Privileges and Direct SQL

The threat model includes more than REST endpoints.

Potential writers:

```text
application services
background jobs
migration scripts
support tooling
integration workers
DB administrators
```

A normal application role should not automatically have broad `UPDATE`/`DELETE` privileges over posted financial tables.

The database should make dangerous operations difficult.

---

# 39. RLS and Financial Data

In a multi-tenant system, RLS may help isolate tenant rows.

But RLS is not a replacement for financial integrity.

PostgreSQL documents that referential-integrity checks have special behavior with row security, because integrity checks must still be able to maintain valid relationships. citeturn256961search10

Therefore:

```text
RLS = access isolation
FK/UNIQUE/CHECK/etc. = integrity
```

They solve different problems.

---

# 40. Multi-Tenant Ledger

A tenant-aware ledger often needs:

```text
tenant
  ↓
chart of accounts
  ↓
journals
  ↓
postings
```

Tenant boundaries should be explicit in:

- ownership;
- uniqueness;
- foreign keys;
- RLS where appropriate;
- reporting;
- reconciliation;
- archival;
- export/deletion workflows.

A missing tenant predicate in a financial report is a severe correctness defect.

# 41. Jewellery ERP Example

Consider a multi-branch jewellery ERP.

```text
Tenant
  Makkah Jewellers

Branches
  BBS
  CTC
  BLR
```

A sale might produce:

```text
Dr Customer Receivable     118,000
Cr Sales Revenue           100,000
Cr Tax Payable              18,000
```

Inventory accounting might additionally recognize cost:

```text
Dr Cost of Goods Sold       70,000
Cr Inventory                 70,000
```

The operational sale, customer document, branch, tenant, payment, and ledger postings should be explicitly linked.

The accounting layer should not depend on developers remembering which optional service happened to update which balance field.

# 42. Inventory Quantity Is Not the Same as Inventory Value

These are separate concepts:

```text
Inventory quantity
Inventory movement history
Inventory valuation
Financial inventory asset balance
```

For example:

```text
Stock: 100 units
```

is operational quantity state.

A movement stream:

```text
+20 purchase
-5 sale
+2 adjustment
```

is event/history data.

A value ledger may represent:

```text
Inventory asset
Cost of goods sold
Valuation adjustment
```

Do not force all three concepts into one generic row.

---

# 43. Reconciliation

A production financial system needs independent checks.

Examples:

```text
Payment gateway total
    ==
Ledger cash postings
```

```text
Invoice total
    ==
Expected receivable postings
```

```text
Inventory valuation
    ==
Ledger inventory asset balance
```

Reconciliation results should be classified rather than reduced to “mismatch”.

Possible statuses:

```text
MATCHED
MISSING_LEDGER
UNEXPECTED_LEDGER
AMOUNT_MISMATCH
CURRENCY_MISMATCH
DUPLICATE
TIMING_MISMATCH
```

---

# 44. Reconciliation Must Be Repeatable

A reconciliation job should be safe to rerun.

Bad:

```text
Mismatch detected
→ create adjustment every run
```

Better:

```text
Mismatch detected
→ deterministic discrepancy identity
→ record discrepancy
→ unique adjustment reference
→ create/reuse adjustment
```

Idempotency applies to reconciliation too.

---

# 45. Projection Drift

Suppose:

```text
Projection balance = 9,80,000
Ledger-derived      = 9,75,000
```

Do not simply update the projection to `9,75,000` and close the incident.

First determine:

```text
Which postings are missing?
Were duplicate updates applied?
Did an event consumer fail?
Did an admin tool modify state?
Did an import replay?
```

Then repair the projection and preserve incident evidence.

---

# 46. Rebuilding a Balance

A ledger-derived balance might be computed conceptually as:

```sql
SELECT
    account_id,
    SUM(
        CASE
            WHEN direction = 'D' THEN amount
            WHEN direction = 'C' THEN -amount
        END
    ) AS ledger_balance
FROM ledger_postings
GROUP BY account_id;
```

The sign convention is only an example. Define the canonical meaning for the organization's chart of accounts.

A key property is:

```text
projection = deterministic function(ledger)
```

---

# 47. Financial Reconciliation With External Systems

For external providers, compare stable business identities, not timestamps alone.

Useful fields can include:

```text
provider_transaction_id
provider_reference
internal_operation_id
currency
amount
settlement_date
status
```

A timestamp can drift because of clocks, batching, or settlement windows.

Identity should be stronger than timing.

---

# 48. Ledger Numbering

A business-facing journal number might be:

```text
JV-2026-000001
```

Do not confuse it with the technical primary key.

Possible design:

```text
id          uuid
journal_no  text
```

The technical ID provides internal identity.

The journal number provides human/business semantics.

If strict contiguous legal numbering is required, model that requirement separately because concurrency and gap-free allocation can introduce serialization and operational complexity.

# 49. Immutable Evidence

A posted financial record should be capable of answering:

```text
Who?
What?
When?
Why?
Which account?
Which amount?
Which currency?
Which source?
Which period?
Which correction/reversal?
```

The evidence contract grows with financial consequence.

---

# 50. Hash Chains and Tamper Evidence

For particularly sensitive systems, a hash chain can provide tamper evidence.

Conceptually:

```text
hash_1 = H(record_1)
hash_2 = H(hash_1 + record_2)
hash_3 = H(hash_2 + record_3)
```

But this is not magical immutability.

If an attacker can rewrite both records and the trusted hash storage, the chain alone does not provide independent evidence.

The trust anchor must be protected.

---

# 51. Outbox Integration

After posting, downstream systems may need an event.

Dangerous pattern:

```text
COMMIT ledger
publish message
```

because the process can crash between the two steps.

Safer pattern:

```text
BEGIN
insert journal/postings
insert outbox event
COMMIT

outbox worker
    ↓
publish
```

The ledger and outbox record become one database transaction boundary.

---

# 52. Exactly-Once Is Not a Safe Assumption

Distributed delivery usually requires retry-safe consumers.

Design handlers so repeated processing of the same logical operation does not create multiple financial effects.

Use:

```text
stable operation identity
unique constraints
transaction boundaries
idempotent consumers
```

rather than assuming an infrastructure component guarantees one delivery forever.

---

# 53. `EXPLAIN` for Financial Reports

Example:

```sql
SELECT SUM(amount)
FROM ledger_postings
WHERE account_id = $1
  AND created_at >= $2
  AND created_at < $3;
```

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Investigate:

- scan type;
- row estimate accuracy;
- buffers;
- aggregation cost;
- partition pruning;
- unnecessary heap access;
- sort/hash memory.

Optimize based on measured workload.

---

# 54. Indexing Ledger Postings

Common patterns include:

```sql
CREATE INDEX ledger_postings_account_time_idx
ON ledger_postings (account_id, created_at);
```

Journal lookup:

```sql
CREATE INDEX ledger_postings_journal_idx
ON ledger_postings (journal_entry_id);
```

Tenant/account/time reporting:

```sql
CREATE INDEX ledger_postings_tenant_account_time_idx
ON ledger_postings (tenant_id, account_id, created_at);
```

These are examples, not universal requirements.

The correct index set follows actual query patterns.

# 55. Partitioning a Large Ledger

A very large append-heavy ledger may be partitioned by time.

Conceptually:

```text
ledger_postings_2026_01
ledger_postings_2026_02
ledger_postings_2026_03
```

Potential benefits:

- smaller active indexes;
- efficient lifecycle operations;
- partition pruning;
- easier archival/detachment of old data.

PostgreSQL 18 documents declarative partitioning and partition pruning as core data-definition features. citeturn256961search3turn256961search5

However, excessive partition counts add planning and operational complexity.

# 56. Financial Ledger + Analytics

Do not make the primary ledger schema excessively denormalized simply because BI scans are slow.

Often prefer:

```text
Transactional ledger
      ↓
read/analytics projection
      ↓
warehouse/reporting
```

The transactional model should optimize primarily for correctness and controlled writes.

The analytics model can optimize for scans and aggregations.

---

# 57. Schema Evolution

Financial history can live for years.

Never silently change the semantic meaning of a historical column.

Dangerous:

```text
amount meant gross before
amount means net after migration
```

Existing rows become ambiguous.

Safer pattern:

```text
explicit new semantics
→ backfill if justified
→ validate
→ migrate writers/readers
→ retire old path later
```

# 58. What Belongs in PostgreSQL?

Strong database candidates:

```text
NOT NULL
positive posting amount
valid direction
account existence
unique idempotency key
foreign keys
tenant ownership
unique document identity
immutability boundary where practical
```

More complex invariants may require:

```text

constraint triggers
transaction-scoped validation
application services
reconciliation jobs
```

The best financial systems layer these mechanisms rather than pretending one mechanism solves everything.

# 59. Financial Security Review

# 60. Failure Modes From AI / Vibe Coding

## Failure 1 — Floating-point money

```ts
number
```

Problem: implicit precision semantics.

## Failure 2 — Mutable posted ledger

```sql
UPDATE ledger_postings ...
```

Problem: destroys historical truth.

## Failure 3 — Delete as correction

Problem: hides history and breaks evidence.

## Failure 4 — Application-only balancing

```ts
if (debit !== credit) ...
```

Problem: another writer can bypass it.

## Failure 5 — Check-then-insert idempotency

Problem: concurrent race.

## Failure 6 — Balance used as source of truth

Problem: balance corruption becomes financial corruption.

## Failure 7 — No reconciliation

Problem: drift can remain invisible.

## Failure 8 — Historical data recomputed with current rules

Problem: prior periods change meaning.

## Failure 9 — Generic polymorphic references everywhere

Problem: relational integrity disappears.

## Failure 10 — One generic `status`

Problem: operational workflow and accounting state become entangled.

# 61. Naive → Improved → Production-Hardened

## Naive approach

```text
payments
 ├── amount
 ├── status
 └── balance
```

### Why it fails

- no double-entry model;
- weak provenance;
- mutable financial state;
- duplicate retry risk;
- no correction chain.

## Improved approach

```text
payment
  ↓
journal
  ↓
postings
  ↓
balance projection
```

### Why it works

The financial effect gets an explicit representation.

## Production-hardening

Add:

```text
immutability
idempotency
period controls
reconciliation
source provenance
approval workflow
tenant isolation
projection rebuild
outbox integration
observability
```

## Trade-off

The system becomes more deliberate and complex, but the complexity is solving real correctness problems rather than hiding them in mutable state.

# 62. Testing Financial Invariants

Test invariants directly.

## Balance invariant

```text
for every posted journal:
Debits = Credits
```

## Immutability invariant

```text
posted UPDATE -> rejected
posted DELETE -> rejected
```

## Idempotency invariant

```text
same operation identity
→ one financial effect
```

## Reversal invariant

For a full reversal:

```text
original + reversal = zero net economic effect
```

## Projection invariant

```text
incremental projection
==
ledger-derived projection
```

---

# 63. Property-Based Testing

Generate random valid and invalid journals.

Check properties such as:

```text
valid journals remain balanced
invalid journals are rejected
projection rebuild equals incremental projection
repeated operations remain idempotent
```

Financial models contain many combinatorial edge cases, so property-based testing can reveal defects beyond hand-picked examples.

---

# 64. Concurrency Testing

Run concurrent attempts for:

```text
same payment
same idempotency key
different postings to same account
period close + posting
same reversal operation
```

Verify the final state, not merely that one request returned success.

---

# 65. Failure Injection

Test:

```text
DB commit succeeds
HTTP response is lost
client retries
```

Also:

```text
ledger commit succeeds
outbox worker crashes
```

```text
projection update fails
ledger remains authoritative
projection is rebuilt
```

```text
consumer receives duplicate event
no duplicate financial effect
```

The architecture should be tested under failure, not only on the happy path.

# 66. Observability

Track financial metrics such as:

```text
posted journal count
rejected posting count
reversal count
idempotency conflict count
reconciliation mismatch count
suspense balance
projection drift
posting latency
ledger-to-projection lag

```

A generic API error metric cannot answer these questions.

# 67. Evidence-Driven Incident Investigation

Suppose a balance is wrong.

Investigate in this order:

```text
1. Expected amount
2. Actual amount
3. Currency
4. Account
5. Journal
6. Source transaction
7. Idempotency identity
8. Actor
9. Period
10. Projection history
11. External reconciliation
```

Do not begin by patching the number.

The root cause must be understood first.

# 68. Debugging Queries

All postings for a journal:

```sql
SELECT *
FROM ledger_postings
WHERE journal_entry_id = $1
ORDER BY id;
```

Debit/credit totals:

```sql
SELECT
    direction,
    SUM(amount) AS total
FROM ledger_postings
WHERE journal_entry_id = $1
GROUP BY direction;
```

Potential account drift:

```sql
SELECT
    account_id,
    SUM(
        CASE
            WHEN direction = 'D' THEN amount
            WHEN direction = 'C' THEN -amount
        END
    ) AS ledger_balance
FROM ledger_postings
GROUP BY account_id;
```

Again, the sign convention must be defined by the accounting model.

# 69. Constraint and Schema Introspection

PostgreSQL's `pg_constraint` catalog stores metadata for check, primary key, unique, foreign key, exclusion, not-null, and constraint-trigger objects. It also exposes whether a constraint is deferrable and whether it is deferred by default. citeturn256961search2

Example:

```sql
SELECT
    conname,
    contype,
    condeferrable,
    condeferred,
    convalidated
FROM pg_constraint
WHERE conrelid = 'ledger_postings'::regclass;
```

This is useful for verifying that the production database actually contains the invariants the design expects.

---

# 70. Why Constraint Metadata Matters

A developer can say:

```text
The idempotency key is unique.
```

A production investigation should be able to verify:

```text
Is the unique constraint actually present?
Is it the intended column set?
Is it validated?
Is it partial?
Was it changed by a migration?
```

Database introspection turns assumptions into evidence.

# 71. Financial Modeling and Partitioning Constraints

For large ledger workloads, partitioning can also affect the physical and query model.

PostgreSQL distinguishes declarative partition pruning from older constraint-exclusion techniques; partition pruning uses partition bounds. citeturn256961search3

This matters when designing date-bounded financial reports:

```text
report for January
→ planner should avoid irrelevant partitions
```

But partitioning should be adopted only when scale/workload justifies the additional design and operational complexity.

# 78. Final Engineering Principles

1. **Financial facts and operational workflow are different concepts.**
2. **Money requires explicit precision, currency, and rounding semantics.**
3. **A posted ledger is evidence, not a mutable document.**
4. **Corrections should preserve history rather than erase it.**
5. **Balances are projections unless the system explicitly defines otherwise.**
6. **Idempotency must survive concurrent retries.**
7. **Aggregate financial invariants need deliberate enforcement architecture.**
8. **Closed periods are a transactional integrity problem.**
9. **Every financial projection needs a repair/rebuild path.**
10. **Every production ledger needs reconciliation.**
11. **Historical financial meaning must remain explainable over time.**
12. **Operational dashboards should not become accidental accounting authorities.**
13. **Measure workload before introducing complex performance architecture.**
14. **When a number is wrong, investigate the chain of facts before patching the result.**

> **The deepest principle: a financial system earns trust when every balance can be decomposed into authoritative facts, every correction preserves history, and every discrepancy can be explained.**
