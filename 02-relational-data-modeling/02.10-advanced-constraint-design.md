# 02.10 — Advanced Constraint Design

> **Phase 02 — Relational Data Modeling**  
> Previous: [02.9 — Deferrable Constraints](./02.9-deferrable-constraints.md)  
> Next: [02.11 — Temporal Data](./02.11-temporal-data.md)

## 1. Objective

Advanced constraint design is the point where a database schema stops merely describing columns and starts expressing the **business invariants that must remain true under concurrency, retries, partial failures, migrations, and multiple application instances**.

A production PostgreSQL schema should not rely on application code alone to maintain invariants such as:

- one active SKU per tenant
- one primary address per customer
- no overlapping room/seat/resource reservations
- a child row cannot reference a missing parent
- a quantity cannot be negative
- an interval cannot be empty
- a status transition cannot produce contradictory state
- a historical effective-period cannot overlap another active version
- one logical identifier may be nullable, but at most one NULL is allowed
- a temporal key must not overlap another record's validity range

The advanced goal is not to create the largest possible collection of constraints. It is to identify the **smallest set of database-enforced predicates that completely and correctly express the invariants of the model**.

This chapter builds on `NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, and deferrable constraints and pushes them into PostgreSQL-specific design patterns.

---

## 2. Three Definitions

### 2.1 Simple definition

A constraint is a rule that PostgreSQL checks before accepting a database state.

### 2.2 Engineering definition

A constraint is a **declarative integrity invariant** attached to schema objects and enforced by PostgreSQL, independent of whether data came from an API, background worker, migration, SQL client, import process, or administrative script.

### 2.3 Expert definition

Advanced constraint design is the deliberate translation of business invariants into predicates whose enforcement semantics remain correct across:

- concurrent transactions
- transaction boundaries
- NULL semantics
- partial data states during migrations
- retries and idempotency
- tenant boundaries
- temporal dimensions
- index behavior
- partitioning
- replication and failover
- schema evolution

The critical phrase is **database state**, not request state.

---

## 3. The Core Mental Model

Think of a table as a set of possible states.

A constraint defines which states are legal.

```text
Application request
       |
       v
   SQL mutation
       |
       v
+-------------------+
| PostgreSQL        |
|                   |
|  proposed state   |
|       |           |
|       v           |
|  constraints      |
|       |           |
|   +---+---+       |
| valid   invalid   |
+---|-------|-------+
    |       |
   COMMIT   ERROR
```

The application proposes a state. PostgreSQL decides whether that state is valid.

This has an important consequence:

> **A validation performed only before the SQL statement is not equivalent to a constraint.**

For example:

```text
Application A: check whether email exists -> no
Application B: check whether email exists -> no
Application A: insert
Application B: insert
```

Application checks can race. A unique constraint can close the race at the database boundary.

# 4. Constraint Design Starts With Invariants

Do not begin by asking:

> Which PostgreSQL constraint should I use?

Begin with:

> What must never be false?

For example, in a jewellery ERP:

```text
Invariant 1:
A product code is unique within a tenant.

Invariant 2:
A sale line must reference an existing sale.

Invariant 3:
A sale quantity must be > 0.

Invariant 4:
A discount cannot exceed the line price.

Invariant 5:
Only one active price row may exist for a product at a branch.

Invariant 6:
Two reservations for the same physical asset may not overlap.
```

Only after identifying the invariant should you map it to a mechanism.

| Invariant shape | Preferred mechanism |
|---|---|
| Value must exist | `NOT NULL` |
| Value must satisfy a row-local predicate | `CHECK` |
| Values must be unique | `UNIQUE` |
| Nullable uniqueness with special NULL semantics | `UNIQUE NULLS NOT DISTINCT` or partial unique index |
| Row identity | `PRIMARY KEY` |
| Parent must exist | `FOREIGN KEY` |
| Values across rows may not conflict under operators | `EXCLUDE` |
| Conditional uniqueness | Partial unique index |
| Reusable scalar domain rule | Domain / domain constraint |
| Derived invariant from an expression | Generated column + constraint, where appropriate |
| Temporal non-overlap | `WITHOUT OVERLAPS` / `EXCLUDE` |
| Temporal referential coverage | `PERIOD` foreign key |
| Delayed validation within a transaction | Deferrable constraint |

---

# 5. Constraint Versus Index

This distinction becomes critical at an advanced level.

An **index** primarily exists to accelerate access.

A **constraint** exists to define an invariant.

Some PostgreSQL constraints are implemented using indexes. For example, `UNIQUE` and `PRIMARY KEY` create or use unique B-tree indexes; exclusion constraints use an index access method such as GiST. PostgreSQL documents these as constraint semantics even though an index is part of the implementation. citeturn763702search0turn763702search1

Therefore:

```text
Index goal:
    make lookup fast

Constraint goal:
    make an illegal state impossible
```

A useful design rule:

> Never add a unique index merely because a business rule sounds like uniqueness. First determine whether you need a constraint, a partial unique index, or a broader exclusion rule.

# 6. Advanced CHECK Constraint Design

## 6.1 Row-local invariants

A `CHECK` constraint is strongest when it expresses a property of the row itself.

```sql
CREATE TABLE sale_lines (
    id bigint PRIMARY KEY,
    quantity numeric NOT NULL,
    unit_price numeric(18,2) NOT NULL,
    discount numeric(18,2) NOT NULL DEFAULT 0,

    CONSTRAINT sale_lines_quantity_positive
        CHECK (quantity > 0),

    CONSTRAINT sale_lines_price_nonnegative
        CHECK (unit_price >= 0),

    CONSTRAINT sale_lines_discount_valid
        CHECK (discount >= 0 AND discount <= unit_price)
);
```

These rules are deterministic, local, and easy to reason about.

## 6.2 Cross-column invariants

A table-level `CHECK` can compare multiple columns.

```sql
CREATE TABLE employees (
    id bigint PRIMARY KEY,
    start_date date NOT NULL,
    end_date date,

    CONSTRAINT employees_valid_employment_period
        CHECK (end_date IS NULL OR end_date >= start_date)
);
```

The invariant is:

```text
end_date is absent
OR
end_date >= start_date
```

## 6.3 NULL is the advanced trap

A `CHECK` constraint is considered satisfied when the expression evaluates to `TRUE` **or NULL**. Therefore a `CHECK` alone does not necessarily reject NULL values. PostgreSQL explicitly documents this behavior. citeturn763702search0

This is wrong when absence is invalid:

```sql
CHECK (price > 0)
```

with:

```sql
price = NULL
```

The expression can evaluate to NULL, and the check does not reject the row.

Correct:

```sql
price numeric NOT NULL
    CHECK (price > 0)
```

Mental model:

```text
CHECK asks:
    Did the expression become FALSE?

TRUE  -> accepted
NULL  -> accepted
FALSE -> rejected
```

Not:

```text
CHECK asks:
    Is the expression TRUE?
```

# 7. Avoid Mutable External State in CHECK Constraints

A common advanced mistake is placing a function inside a `CHECK` that depends on mutable external state.

Example conceptually:

```sql
CHECK (is_business_day(order_date))
```

Suppose `is_business_day()` depends on a table of holidays or its function body changes later.

PostgreSQL assumes a check condition is effectively immutable for the same input. If the function's behavior changes later, PostgreSQL does not automatically revisit existing rows. The official documentation warns that changing behavior this way can leave already-stored rows inconsistent with the newly interpreted rule and can create dump/restore problems. citeturn763702search0

Better choices include:

- materialize the relevant decision into the row
- use a foreign key to reference a maintained calendar table when appropriate
- enforce the rule in a transaction with explicit locking when the invariant truly depends on other rows
- use an appropriate trigger when the invariant genuinely cannot be expressed declaratively

The principle is:

> A `CHECK` should describe a stable property of the row, not a moving external world.

# 8. Conditional Uniqueness

Business rules frequently say:

> Unique, but only for rows satisfying condition X.

A standard unique constraint cannot express arbitrary predicates over a subset of rows. PostgreSQL's documentation recommends a **unique partial index** for this problem. citeturn763702search0

## Example: one active email per tenant

```sql
CREATE UNIQUE INDEX users_one_active_email_per_tenant
ON users (tenant_id, lower(email))
WHERE deleted_at IS NULL;
```

This means:

```text
active rows:
    must be unique

soft-deleted rows:
    are excluded from the uniqueness rule
```

This is fundamentally different from:

```sql
UNIQUE (tenant_id, email, deleted_at)
```

because the latter changes the key shape rather than saying “uniqueness applies only to active rows.”

---

# 9. Partial Unique Index versus UNIQUE Constraint

Use a normal unique constraint when:

```text
all rows participate in the uniqueness rule
```

Use a partial unique index when:

```text
only a subset participates
```

Example:

```sql
CREATE UNIQUE INDEX users_one_primary_address
ON customer_addresses (customer_id)
WHERE is_primary;
```

This encodes:

```text
for each customer:
    count(primary address) <= 1
```

It does **not** encode:

```text
count(primary address) == 1
```

That distinction matters.

A uniqueness rule can often enforce “at most one.”

It usually cannot by itself enforce “at least one.”

The latter may require a different workflow, transaction protocol, or design.

# 10. Case-Insensitive Uniqueness

Do not assume the database's ordinary text equality exactly matches the business concept of identity.

For email-like identifiers, a common explicit design is:

```sql
CREATE UNIQUE INDEX users_email_ci_uidx
ON users (lower(email));
```

This is preferable to relying on application normalization alone.

But the semantic decision should come first:

```text
Is identity case-sensitive?
Is the normalization rule stable?
Does collation affect equality?
Should whitespace be canonicalized?
```

If the application and database use different notions of equality, subtle duplicates will eventually appear.

PostgreSQL 18 also tightened requirements around collation compatibility in primary/foreign-key relationships, reflecting the fact that equality semantics must be consistent between referencing and referenced values. citeturn746996search0turn746996search2

# 11. NULL-Aware Uniqueness

PostgreSQL supports explicit control over NULL treatment in unique constraints.

Default concept:

```sql
UNIQUE (email)
```

allows multiple NULL values because NULLs are normally distinct for uniqueness purposes.

PostgreSQL supports:

```sql
UNIQUE NULLS NOT DISTINCT (email)
```

which treats NULL values as equal for this uniqueness rule. This is documented in PostgreSQL 18. citeturn763702search0turn763702search1

Example:

```sql
CREATE TABLE accounts (
    id bigint PRIMARY KEY,
    external_reference text,
    CONSTRAINT accounts_external_reference_uq
        UNIQUE NULLS NOT DISTINCT (external_reference)
);
```

Now only one row may have `external_reference IS NULL`.

This is a powerful example of why semantic precision matters.

```text
UNIQUE(email)
!=
UNIQUE NULLS NOT DISTINCT(email)
```

---

# 12. Expression-Based Invariants

Business identity is sometimes derived from multiple stored values.

Example:

```sql
CREATE UNIQUE INDEX products_sku_normalized_uidx
ON products (
    tenant_id,
    upper(trim(sku))
);
```

This prevents variations such as:

```text
abc-100
ABC-100
 ABC-100 
```

from becoming distinct identifiers, assuming that normalization is truly part of the domain's identity semantics.

Do not normalize blindly. Every transformation changes equality.

The real question is:

> What does the business consider the same identifier?

# 13. Generated Columns as Constraint Inputs

PostgreSQL 18 supports generated columns, including virtual generated columns as the default generation mode. citeturn746996search3turn763702search1

A generated column can provide a stable relational representation of a derived value that can then participate in indexes and constraints where supported.

Conceptual pattern:

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    sku text NOT NULL,
    normalized_sku text
        GENERATED ALWAYS AS (upper(trim(sku))) VIRTUAL
);
```

Then the normalized representation can become part of an appropriate uniqueness design.

The architectural benefit is separation:

```text
raw input
   |
   v
canonical representation
   |
   v
constraint/index
```

This is often cleaner than duplicating normalization logic across every query and service.

However, the exact generated-column eligibility rules and index/constraint capabilities must be checked against the PostgreSQL version used by the production system. Do not assume features documented for one major version exist identically in another.

# 14. Exclusion Constraints

Exclusion constraints are one of PostgreSQL's most powerful advanced integrity tools.

A unique constraint essentially says:

```text
No two rows may be equal on these equality dimensions.
```

An exclusion constraint generalizes this idea:

```text
For any pair of rows,
not all specified operator comparisons may be TRUE.
```

PostgreSQL documents this as the purpose of `EXCLUDE`. citeturn763702search0turn763702search1

---

# 15. Reservation Example

Suppose a room cannot be double-booked.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_reservations (
    id bigint PRIMARY KEY,
    room_id bigint NOT NULL,
    occupied_during tstzrange NOT NULL,

    CONSTRAINT room_reservations_no_overlap
        EXCLUDE USING gist (
            room_id WITH =,
            occupied_during WITH &&
        )
);
```

Interpretation:

```text
same room
AND
overlapping interval
=
forbidden
```

Two different rooms may overlap.

Two reservations for the same room may coexist if their intervals do not overlap.

This is something an ordinary `UNIQUE` constraint cannot express elegantly.

---

# 16. Why Application-Level Overlap Checks Fail

Naive approach:

```sql
SELECT 1
FROM room_reservations
WHERE room_id = $1
  AND occupied_during && $2;
```

Application sees no conflict and then inserts.

Another concurrent transaction can do the same thing between the check and the insert.

```text
T1: SELECT -> no conflict
T2: SELECT -> no conflict
T1: INSERT
T2: INSERT
```

The invariant is violated.

With an exclusion constraint:

```text
T1: INSERT -> accepted
T2: INSERT -> constraint conflict
```

The database is enforcing the invariant at the serialization boundary relevant to the constraint.

# 17. Temporal Keys with WITHOUT OVERLAPS

PostgreSQL 18 introduces temporal primary/unique constraints through `WITHOUT OVERLAPS`. The final key component is treated as a range-like non-overlap dimension rather than ordinary equality. PostgreSQL implements the temporal uniqueness semantics using exclusion-style index behavior. citeturn746996search0turn746996search2

Example:

```sql
CREATE TABLE product_prices (
    product_id bigint NOT NULL,
    valid_during daterange NOT NULL,
    price numeric(18,2) NOT NULL,

    CONSTRAINT product_prices_pk
        PRIMARY KEY (product_id, valid_during WITHOUT OVERLAPS),

    CONSTRAINT product_prices_price_positive
        CHECK (price > 0)
);
```

The intent is:

```text
A product may have many historical price periods,
but those periods must not overlap.
```

This is much more expressive than trying to derive correctness from:

```text
start_date
end_date
```

plus application-level overlap checks.

---

# 18. Temporal Foreign-Key Coverage with PERIOD

PostgreSQL 18 also adds temporal foreign-key support through `PERIOD`. A period-based foreign key requires referenced records to collectively cover the full period of the referencing record. The referenced temporal key uses `WITHOUT OVERLAPS`. citeturn746996search2turn746996search7

Conceptual model:

```text
customer_contract
-----------------
customer_id
covered_during

customer_status_history
------------------------
customer_id
valid_during
```

A `PERIOD` foreign key can express:

```text
Every instant in the contract period
must have a corresponding valid customer record.
```

This is qualitatively different from an ordinary FK.

Ordinary FK:

```text
Does a matching key exist?
```

Temporal FK:

```text
Do matching records collectively cover the required duration?
```

That is a major modeling capability for effective-dated systems.

---

# 19. When EXCLUDE Is Too Broad

Exclusion constraints are powerful, but they should not be used merely because they are technically capable of expressing a rule.

For simple equality uniqueness:

```sql
EXCLUDE USING gist (
    tenant_id WITH =,
    code WITH =
)
```

may be semantically valid, but an ordinary unique constraint is generally the simpler and faster mechanism for pure equality uniqueness. PostgreSQL explicitly notes this distinction. citeturn763702search1

Rule:

```text
Use UNIQUE for equality uniqueness.
Use EXCLUDE when the relationship itself is operator-based.
```

# 20. Combining Multiple Constraint Dimensions

Advanced invariants frequently combine dimensions.

Example:

```text
Within one tenant:
    same product
    same branch
    validity periods cannot overlap
```

Possible design:

```sql
CREATE TABLE branch_product_prices (
    tenant_id bigint NOT NULL,
    branch_id bigint NOT NULL,
    product_id bigint NOT NULL,
    valid_during daterange NOT NULL,
    price numeric(18,2) NOT NULL,

    CONSTRAINT branch_product_prices_no_overlap
        EXCLUDE USING gist (
            tenant_id WITH =,
            branch_id WITH =,
            product_id WITH =,
            valid_during WITH &&
        ),

    CONSTRAINT branch_product_prices_price_positive
        CHECK (price > 0)
);
```

Now the invariant spans:

```text
tenant equality
AND branch equality
AND product equality
AND period overlap
```

This is a good illustration of why advanced relational modeling is fundamentally about predicates.

# 21. Constraint Composition

A mature schema does not attempt to solve every business rule with one giant constraint.

Instead, compose small invariants.

Example:

```sql
CREATE TABLE inventory_movements (
    id bigint PRIMARY KEY,
    tenant_id bigint NOT NULL,
    quantity numeric(18,3) NOT NULL,
    movement_type text NOT NULL,
    reference_id bigint,

    CONSTRAINT inventory_movements_quantity_positive
        CHECK (quantity > 0),

    CONSTRAINT inventory_movements_type_valid
        CHECK (movement_type IN ('RECEIPT', 'ISSUE', 'ADJUSTMENT'))
);
```

Then use foreign keys and uniqueness separately.

Benefits:

- simpler failure diagnosis
- clearer migration behavior
- easier documentation
- more precise application error handling
- smaller blast radius when a rule changes

Avoid “mega constraints” that encode unrelated business concerns into one opaque expression.

# 22. Constraints and State Machines

A state machine often involves both current-state validity and transition validity.

Current-state validity may be declarative:

```sql
CHECK (status IN ('DRAFT', 'CONFIRMED', 'CANCELLED'))
```

But legal transitions such as:

```text
DRAFT -> CONFIRMED
DRAFT -> CANCELLED
CONFIRMED -> CANCELLED
```

are harder to encode as a plain row-local check because the rule compares the previous state with the new state.

A robust architecture often separates:

```text
Current-state invariant
    -> CHECK / NOT NULL

Transition invariant
    -> transaction logic / trigger / state-transition table

History invariant
    -> append-only transition log
```

Advanced constraint design includes knowing where **not** to force a rule into a `CHECK`.

# 23. Domain Constraints

When the same scalar rule appears repeatedly across many tables, a PostgreSQL domain can centralize the type-level invariant.

Conceptual example:

```sql
CREATE DOMAIN positive_money AS numeric(18,2)
CHECK (VALUE >= 0);
```

Then:

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    price positive_money NOT NULL
);
```

Advantages:

- semantic reuse
- consistent validation
- reduced duplication

Risks:

- domain changes affect many consumers
- hidden coupling can surprise developers
- migrations require broader impact analysis

Use domains for genuinely reusable scalar semantics, not every repeated validation phrase.

---

# 24. Constraints on Partitioned Tables

Partitioning introduces another constraint-design question:

> Is the invariant global across the logical table, or local to each partition?

Unique and primary-key constraints on partitioned tables have restrictions because uniqueness must be enforceable within the partitioning structure. PostgreSQL 18 requires partition-key columns to be represented appropriately for unique constraints on partitioned table hierarchies. citeturn763702search1

This creates a critical architectural lesson:

```text
Partitioning key
        |
        v
Can the intended uniqueness be proven globally?
```

For example, if data is partitioned by:

```text
tenant_id
```

then a tenant-scoped key may naturally align with the partition strategy.

But a global identifier that does not include the partitioning dimension may require a different design.

Never treat partitioning as an invisible physical implementation detail when designing global integrity constraints.

---

# 25. INCLUDE Columns and Constraint Semantics

PostgreSQL supports `INCLUDE` payload columns on relevant index-backed constraints.

Example shape:

```sql
UNIQUE (tenant_id, external_id)
INCLUDE (updated_at)
```

The included columns do **not** participate in uniqueness. They are payload for index-only access. PostgreSQL explicitly documents that uniqueness is not enforced on included columns. citeturn746996search2

Therefore:

```text
UNIQUE (tenant_id, external_id)
INCLUDE (status)
```

means:

```text
(tenant_id, external_id) -> unique
status                  -> not part of uniqueness
```

A common AI-generated mistake is to assume `INCLUDE` expands the uniqueness key. It does not.

---

# 26. NOT ENFORCED: Advanced Schema Semantics

PostgreSQL 18 supports `NOT ENFORCED` for `CHECK` and foreign-key constraints. The constraint exists in the schema metadata without PostgreSQL enforcing it in the same way as an enforced constraint. PostgreSQL 18 also exposes enforcement metadata through catalogs/information schema. citeturn746996search0turn763702search1turn763702search4

This is an advanced migration and compatibility feature, not a substitute for integrity enforcement.

Do not write:

```sql
CHECK (...) NOT ENFORCED
```

and then mentally classify the invariant as guaranteed.

The correct mental model is:

```text
ENFORCED
    -> database rejects violating writes

NOT ENFORCED
    -> metadata expresses intent, but enforcement is absent
```

That distinction must be visible in operational documentation.

---

# 27. Naming Constraints for Operations

Bad:

```sql
CONSTRAINT products_check CHECK (...)
```

Better:

```sql
CONSTRAINT products_price_positive_chk
CHECK (price > 0)
```

Better names reduce debugging time.

Recommended convention:

```text
<table>_<business_subject>_<rule>_<type>
```

Examples:

```text
users_email_required_nn
users_tenant_email_unique_uq
orders_customer_fk
order_lines_quantity_positive_chk
room_reservations_no_overlap_excl
```

The exact naming convention can vary. Consistency matters more than the particular suffix.

# 28. Constraint Introspection

When debugging production integrity, inspect the database instead of trusting ORM metadata.

### Information schema

```sql
SELECT
    constraint_schema,
    table_name,
    constraint_name,
    constraint_type,
    is_deferrable,
    initially_deferred,
    enforced
FROM information_schema.table_constraints
WHERE table_schema = 'public'
ORDER BY table_name, constraint_name;
```

PostgreSQL 18's `table_constraints` view exposes constraint type, deferrability, enforcement state, and unique NULL behavior metadata. citeturn763702search4

### PostgreSQL catalog

```sql
SELECT
    conname,
    contype,
    condeferrable,
    condeferred,
    conenforced
FROM pg_constraint
WHERE conrelid = 'public.orders'::regclass;
```

`pg_constraint` stores constraint metadata including check, not-null, primary key, unique, foreign key, exclusion, deferrability, and enforcement properties. citeturn763702search3

For a readable definition:

```sql
SELECT pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'public.orders'::regclass;
```

This is often better than trying to reconstruct the schema from migration code.

# 29. Constraint Migration Strategy

Adding a constraint to an already-large production table is not simply:

```sql
ALTER TABLE ... ADD CONSTRAINT ...;
```

First ask:

```text
Does existing data satisfy the rule?
How much data must be scanned?
What locks are required?
How long may validation take?
What happens to concurrent writes?
Can deployment be staged?
```

PostgreSQL validates constraints when they are added unless the specific mechanism allows staged validation semantics. The official `ALTER TABLE` documentation describes the immediate validation behavior and the use of `NOT VALID`/subsequent validation for supported constraint workflows. citeturn763702search8

A production-safe pattern is frequently:

```text
1. discover violations
2. remediate data
3. add the constraint using an online-friendly strategy where supported
4. validate
5. remove temporary compatibility paths
```

Never make schema migration safety a purely theoretical concern.

# 30. Constraint Violations as Observability Signals

Integrity failures are not always “bugs.” They can be valuable signals.

A spike in:

```text
unique_violation
foreign_key_violation
check_violation
exclusion_violation
```

may indicate:

- duplicate API requests
- broken idempotency
- incorrect client assumptions
- missing tenant scoping
- stale caches
- race conditions
- a deployment mismatch
- an upstream integration regression

Node.js/NestJS should map database errors into meaningful domain responses rather than exposing raw driver errors.

Conceptually:

```text
PostgreSQL constraint violation
        |
        v
repository/data-access layer
        |
        v
recognized constraint name
        |
        v
domain error
        |
        v
HTTP / event response
```

The constraint name becomes part of operational design.

# 31. Concurrency: Why Constraints Matter More Than Validation

Suppose the API wants one active promotion per SKU.

Naive:

```sql
SELECT count(*)
FROM promotions
WHERE sku = $1
  AND active = true;
```

Then:

```text
if count = 0:
    INSERT
```

This has a race.

A correct database design uses an appropriate uniqueness mechanism:

```sql
CREATE UNIQUE INDEX promotions_one_active_sku
ON promotions (tenant_id, sku)
WHERE active;
```

Then application code treats a uniqueness violation as a concurrency outcome.

The deeper lesson:

> The application can request “create one.” Only the database can authoritatively decide whether the resulting state is legal under concurrent writers.

# 32. Constraint Selection Decision Tree

```text
Is the rule about one scalar being present?
    |
    +-- yes -> NOT NULL
    |
    +-- no

Is the rule row-local?
    |
    +-- yes -> CHECK
    |
    +-- no

Is the rule pure equality uniqueness across all rows?
    |
    +-- yes -> UNIQUE / PRIMARY KEY
    |
    +-- no

Is uniqueness conditional?
    |
    +-- yes -> partial unique index
    |
    +-- no

Is the rule parent-child existence?
    |
    +-- yes -> FOREIGN KEY
    |
    +-- no

Is the conflict defined by operators such as overlap?
    |
    +-- yes -> EXCLUDE / WITHOUT OVERLAPS
    |
    +-- no

Is the rule temporal referential coverage?
    |
    +-- yes -> PERIOD foreign key
    |
    +-- no

Does enforcement need to be delayed?
    |
    +-- yes -> DEFERRABLE constraint where supported
    |
    +-- no

Does the rule depend on mutable external state?
    |
    +-- yes -> reconsider CHECK; use FK, transaction logic, trigger,
              or another explicit mechanism
```

# 33. Naive → Improved → Production Pattern

## Scenario: one active price per branch/product

### Naive approach

```text
SELECT active price
if none:
    INSERT
```

### Why it fails

Concurrent workers can both observe no active price.

### Improved approach

```sql
CREATE UNIQUE INDEX branch_product_one_active_price
ON branch_product_prices (
    tenant_id,
    branch_id,
    product_id
)
WHERE ended_at IS NULL;
```

### Why it works

The invariant is enforced at the database boundary.

### Production considerations

The application must:

- handle unique violations predictably
- define whether retry is appropriate
- make updates idempotent
- avoid assuming “check then insert” is safe
- monitor violation rates

### Alternative

Use a temporal non-overlap design when the domain naturally models validity periods.

### Trade-off

Partial uniqueness is simple for active-state semantics. Temporal constraints are stronger when the business invariant is genuinely about non-overlapping time.

# 34. Security Considerations

Constraints are not authorization mechanisms.

For example:

```sql
CHECK (tenant_id IS NOT NULL)
```

does not guarantee that the current user is allowed to access that tenant.

You still need:

- authorization
- row-level security where appropriate
- secure database roles
- safe search paths
- restricted DDL privileges

However, constraints can strengthen isolation by preventing cross-tenant relationship mistakes.

Example:

```sql
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, id)
```

This makes it structurally impossible for a row in tenant A to reference customer B when the composite relationship is designed correctly.

That is much stronger than relying on every application query to remember:

```sql
WHERE tenant_id = $tenant_id
```

---

# 35. Multi-Tenant Constraint Design

Tenant-aware constraints are among the highest-value advanced patterns for SaaS and enterprise systems.

Bad:

```sql
UNIQUE (code)
```

when the business rule is:

```text
code unique per tenant
```

Correct:

```sql
UNIQUE (tenant_id, code)
```

Likewise, a child table may need:

```sql
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, id)
```

This makes tenant membership part of referential integrity.

The deeper pattern is:

```text
Tenant identity is not merely a query filter.
It is part of relational identity where the domain requires it.
```

# 36. Financial and Ledger Systems

Financial systems benefit disproportionately from database constraints because an integrity error can become an accounting error.

Example:

```sql
CREATE TABLE journal_lines (
    id bigint PRIMARY KEY,
    journal_id bigint NOT NULL,
    account_id bigint NOT NULL,
    debit numeric(18,2) NOT NULL DEFAULT 0,
    credit numeric(18,2) NOT NULL DEFAULT 0,

    CONSTRAINT journal_lines_amounts_nonnegative
        CHECK (debit >= 0 AND credit >= 0),

    CONSTRAINT journal_lines_not_both_sides
        CHECK (NOT (debit > 0 AND credit > 0)),

    CONSTRAINT journal_lines_has_amount
        CHECK (debit > 0 OR credit > 0)
);
```

This prevents invalid line shapes.

But note the limitation:

```text
sum(debit) = sum(credit)
```

is a cross-row invariant.

A plain row-level `CHECK` cannot enforce aggregate balance across arbitrary rows.

That may require:

- transactional service logic
- carefully designed summary structure
- deferred trigger-based enforcement
- ledger architecture where the invariant is represented differently

Advanced mastery includes knowing the exact expressive boundary of each constraint mechanism.

# 37. What CHECK Cannot Safely Replace

Avoid designs such as:

```sql
CHECK (
    (SELECT count(*) FROM other_table ...) = 0
)
```

The core issue is that ordinary check constraints are intended for row-local immutable semantics, not arbitrary relational queries over changing external tables. PostgreSQL explicitly documents this design assumption. citeturn763702search0

When the rule is cross-row, select a mechanism designed for cross-row semantics.

# 40. ORM and Migration Tooling Risks

Node.js applications often use ORMs such as Prisma, TypeORM, Sequelize, Drizzle, or custom migration layers.

A production engineer must distinguish:

```text
ORM schema abstraction
        vs
actual PostgreSQL schema
```

Potential failure modes:

- ORM lacks a feature such as a PostgreSQL-specific exclusion constraint
- migration generator removes and recreates a constraint unnecessarily
- expression indexes are unsupported by the abstraction
- partial unique indexes are represented incorrectly
- generated columns are emitted differently across versions
- constraint names are unstable
- a migration runs with unsafe lock behavior

For PostgreSQL-specific integrity features, inspect generated SQL.

Do not assume:

```text
ORM model == PostgreSQL semantics
```

# 41. AI / Vibe-Coding Failure Modes

AI-generated database designs often fail in predictable ways.

## Mistake 1 — Application validation instead of constraints

```text
if (!exists) create()
```

without a database uniqueness rule.

### Correction

Translate the invariant into database-enforced uniqueness whenever the domain requires it.

## Mistake 2 — `CHECK` without `NOT NULL`

```sql
CHECK (quantity > 0)
```

while allowing NULL.

### Correction

```sql
quantity numeric NOT NULL CHECK (quantity > 0)
```

## Mistake 3 — Unique constraint where conditional uniqueness is required

```sql
UNIQUE (customer_id, is_primary)
```

This usually allows one non-primary row rather than expressing “only one primary row.”

### Correction

Use a partial unique index.

## Mistake 4 — EXCLUDE for plain equality uniqueness

Technically possible, semantically noisy.

### Correction

Prefer ordinary `UNIQUE` for pure equality uniqueness.

## Mistake 5 — Treating a constraint as an authorization policy

Integrity does not equal access control.

## Mistake 6 — Ignoring NULL semantics

The generated schema may look correct while permitting multiple NULLs or allowing a `CHECK` to pass unexpectedly.

## Mistake 7 — Ignoring concurrency

A “check then write” flow is presented as race-free.

It is not.

## Mistake 8 — Giant opaque constraints

One 30-line condition may encode five unrelated business rules and become almost impossible to migrate safely.

# 42. Production Design Review Questions

Before approving a constraint, ask:

### Correctness

- What exact invariant does this enforce?
- What state remains legal after a violation?
- Are NULLs handled intentionally?
- Does the rule include tenant scope?

### Concurrency

- Can two concurrent transactions violate the business rule?
- Is enforcement performed atomically by PostgreSQL?

### Semantics

- Is equality really the relationship?
- Should the rule be conditional?
- Is overlap the real conflict definition?
- Is the rule temporal?

### Operations

- How is the constraint named?
- How will migrations add it safely?
- What happens to existing bad data?
- What application error should be returned?

### Performance

- Which index structure is created or used?
- What is the expected write amplification?
- Does the rule create contention on a hot key?

### Evolution

- What happens when the business rule changes?
- Can historical data still satisfy the future definition?
- Will the migration require a full-table scan?

# 43. Constraint Design Anti-Patterns

## Anti-pattern A — Constraint theater

Creating many constraints without identifying meaningful invariants.

More constraints are not automatically better.

## Anti-pattern B — ORM-only integrity

The database is left permissive because “the service validates everything.”

Administrative scripts, jobs, integrations, and future services eventually bypass the assumption.

## Anti-pattern C — Hidden uniqueness assumptions

Developers assume uniqueness because the UI prevents duplicates.

The database has no such protection.

## Anti-pattern D — Overconstrained history

A mutable current-state rule is incorrectly imposed on immutable historical records.

Example:

```text
current product price must be positive
```

may be appropriate.

But historical financial records may require preserving exactly what was recorded rather than reinterpreting them under today's rules.

## Anti-pattern E — Cross-table CHECK illusion

A check constraint is used as if it were a relational assertion across changing tables.

## Anti-pattern F — Misusing soft-delete columns for uniqueness

```sql
UNIQUE (email, deleted_at)
```

is often not the intended business rule.

A partial unique index is usually clearer:

```sql
UNIQUE(email) WHERE deleted_at IS NULL
```

# 44. A Constraint Architecture for a Production Jewellery ERP

Consider:

```text
Tenant
  |
  +-- Branch
  |
  +-- Product
  |
  +-- Customer
  |
  +-- Inventory
  |
  +-- Sale
  |
  +-- Purchase
```

### Product identity

```sql
UNIQUE (tenant_id, sku)
```

### Branch code

```sql

```

### Customer reference

```sql

```

### Sale line quantity

```sql
CHECK (quantity > 0)
```

### Money

```sql
CHECK (amount >= 0)
```

### Referential integrity

```sql
FOREIGN KEY (tenant_id, customer_id)
```

### Active assignment

```sql
CREATE UNIQUE INDEX ...
WHERE ended_at IS NULL;
```

### Historical pricing

```text
WITHOUT OVERLAPS / EXCLUDE
```

### Reservation inventory

```text
EXCLUDE USING gist
```

### Ledger line shape

```text
CHECK constraints
```

The point is not that every table should contain every advanced mechanism.

The point is that the schema should make the dangerous states structurally difficult or impossible.

# 45. Constraint Layering Strategy

A mature design commonly follows this order:

```text
Layer 1 — Type system
    numeric, date, timestamp, range, enum-like representation

Layer 2 — Presence
    NOT NULL

Layer 3 — Row-local semantics
    CHECK

Layer 4 — Identity
    PRIMARY KEY

Layer 5 — Uniqueness
    UNIQUE / partial unique index

Layer 6 — Relational existence
    FOREIGN KEY

Layer 7 — Cross-row conflict semantics
    EXCLUDE / temporal constraints

Layer 8 — Transaction timing
    DEFERRABLE where required

Layer 9 — Application authorization
    roles / RLS / service policy

Layer 10 — Workflow semantics
    transactions / triggers / domain services
```

Each layer answers a different question.

Avoid using a higher layer to compensate for a missing lower-layer invariant.

# 46. Performance Considerations

Every integrity mechanism has an operational cost.

### `NOT NULL`

Generally cheap, but still part of every relevant write path.

### `CHECK`

Adds expression evaluation to inserts/updates.

### `UNIQUE`

Requires index maintenance and uniqueness checks.

### Foreign keys

Reference integrity introduces checks on inserts/updates and can affect deletes/updates of referenced rows. Appropriate indexing of referencing columns is often essential for predictable performance.

### Exclusion constraints

Can require more sophisticated index processing than simple equality uniqueness.

### Deferrable constraints

Can move failure and work toward transaction end, changing where latency and contention appear.

### Temporal constraints

Can use GiST-based machinery and therefore have a different operational profile from ordinary B-tree equality uniqueness. PostgreSQL 18 documents `WITHOUT OVERLAPS` as using GiST-style exclusion enforcement. citeturn746996search2

The right question is never:

> Are constraints expensive?

It is:

> Is the integrity guarantee worth the measurable write, storage, locking, and operational cost for this workload?

For business-critical invariants, the answer is frequently yes.

# 47. Evidence-Driven Debugging

When a constraint failure appears, do not immediately change the schema.

Collect evidence:

```sql
SELECT *
FROM pg_constraint
WHERE conrelid = 'public.some_table'::regclass;
```

Then inspect the exact definition:

```sql
SELECT
    conname,
    pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'public.some_table'::regclass;
```

Then determine:

```text
Which SQL statement failed?
Which constraint failed?
What rows conflicted?
What was the transaction isolation level?
Was another transaction involved?
Did application retry incorrectly?
```

Only after that should you modify code or schema.

# 52. Final Principle

The mature PostgreSQL engineer does not ask:

> “How many constraints can I add?”

The better question is:

> **“Which database states are illegal, and what is the strongest, simplest, measurable PostgreSQL mechanism that makes those states impossible?”**

Advanced constraint design is the discipline of turning business truth into database truth.

Use:

```text
NOT NULL
for presence,

CHECK
for stable row-local predicates,

UNIQUE / PRIMARY KEY
for identity and equality uniqueness,

partial unique indexes
for conditional uniqueness,

FOREIGN KEY
for relational existence,

EXCLUDE
for operator-based conflicts,

WITHOUT OVERLAPS / PERIOD
for temporal integrity,

DEFERRABLE
when transaction timing is part of correctness,

and application/trigger/transaction mechanisms
when the invariant genuinely lies outside declarative constraint semantics.
```

The production standard is not maximal cleverness.

It is **correct invariants, correct semantics, predictable concurrency, safe migrations, measurable performance, and a schema that remains trustworthy even when the application does something unexpected**.
