# 02.17 — Immutable / Append-Only Data

> **Phase 02 — Relational Data Modeling**
>
> This chapter establishes how to model facts that must not be silently rewritten: audit history, financial movements, workflow transitions, measurements, domain events, inventory movements, and other append-only records.

## 1. Objective

By the end of this chapter, you should be able to:

- distinguish immutable data from merely historical data;
- distinguish append-only storage from event sourcing, auditing, and ledgers;
- define invariants for data that must never be edited or deleted;
- enforce those invariants at the PostgreSQL boundary rather than trusting application code alone;
- choose between permissions, views, triggers, procedures, and role separation;
- design safe correction mechanisms without rewriting history;
- reason about concurrency, idempotency, ordering, replay, retention, and archival;
- scale append-heavy tables without creating operational bottlenecks;
- design immutable financial and inventory flows;
- test immutability adversarially;
- explain the trade-offs of append-only architecture at L7 depth.

---

## 2. The Core Idea

An ordinary mutable table represents **current state**.

An immutable append-only table represents **facts that happened**.

For mutable state:

```text
UPDATE account SET balance = 1200 WHERE id = 42;
```

The old value is replaced from the application's point of view.

For append-only facts:

```text
INSERT INTO account_entries(account_id, amount, reason)
VALUES (42, 200, 'deposit');
```

The original fact remains present. A later correction is itself another fact.

That distinction is foundational:

```text
Mutable state:
    "What is true now?"

Immutable history:
    "What facts were recorded?"
```

A mature system often needs both.

---

# 3. Definitions

## 3.1 Simple definition

Immutable data is data that, once committed, is not changed in place.

Append-only data is data where new records may be inserted, but previously committed records are not updated or deleted as part of normal operation.

## 3.2 Engineering definition

An immutable model treats each committed row as a historical assertion. Corrections are represented through additional records or compensating facts rather than mutation of the original record.

## 3.3 Expert definition

Immutability is an **enforced write semantics and trust boundary** in which committed facts have stable identity and content, while subsequent changes are modeled as new facts. Append-only is the storage/write pattern; immutability is the stronger invariant that previously accepted facts cannot be silently rewritten.

The distinction matters because a table can be "append-only by convention" while technically permitting `UPDATE` and `DELETE`.

That is not strong immutability.

---

# 4. First Principles

## 4.1 Mutation destroys historical state

Suppose inventory quantity changes:

```text
10 → 7
```

A mutable row tells you the current quantity is `7`.

It does not, by itself, prove:

- who changed it;
- when the old value was 10;
- why three units disappeared;
- whether the change was authorized;
- whether a concurrent update happened first;
- whether the value was corrected later.

An immutable movement record can preserve the cause:

```text
+10 PURCHASE_RECEIPT
-3 SALE
------
 7 CURRENT_BALANCE
```

The current balance becomes a **projection of facts** rather than the only surviving representation.

---

## 4.2 Correction is not deletion

This principle appears repeatedly in production systems.

Bad mental model:

```text
Wrong row → UPDATE it to become correct
```

Immutable mental model:

```text
Wrong row → preserve it → append correction → derive corrected state
```

The second model preserves evidence.

---

# 5. Immutability Dimensions

"Immutable" is not one binary property. Define what is immutable.

| Dimension | Question |
|---|---|
| Identity | Can the record identifier change? |
| Payload | Can recorded business values change? |
| Timestamp | Can occurrence time change? |
| Actor | Can the recorded actor change? |
| Tenant | Can ownership move? |
| Ordering | Can sequence/order be rewritten? |
| Relationships | Can the record be re-parented? |
| Lifecycle | Can the record be deleted? |
| Visibility | Can a fact be hidden without changing it? |
| Derived state | Can projections change? |

A strong financial entry might guarantee all of these except derived metadata.

A log table might only guarantee payload and timestamp immutability.

Do not use the word *immutable* without specifying the invariant.

---

# 6. Append-Only Is Not the Same as Event Sourcing

These concepts overlap but are not identical.

## Append-only table

Stores records that are not normally edited.

## Audit history

Records changes to mutable entities.

## Event log

Stores domain events intended to describe facts significant to business behavior.

## Event sourcing

Treats the event stream as the authoritative source from which aggregate state is reconstructed.

## Ledger

Stores financially or quantitatively meaningful entries under stronger accounting invariants, usually including balancing and controlled correction.

A database may use append-only storage without doing event sourcing.

Example:

```text
orders           → mutable current order
order_history    → append-only history
```

That is not automatically event sourcing.

---

# 7. Why Immutability Exists

Use immutable data when the history itself has value.

Typical examples:

- money movements;
- inventory movements;
- payment attempts;
- state transitions;
- security events;
- audit records;
- device measurements;
- received external messages;
- integration deliveries;
- immutable business documents;
- usage events;
- signed or externally attested records;
- append-only workflow history.

Avoid immutability merely because it sounds safer.

It introduces storage growth, correction complexity, replay complexity, and operational cost.

---

# 8. Mutable State + Immutable Facts

A highly practical architecture keeps both.

```text
             ┌─────────────────┐
             │ Immutable facts │
             │ append-only     │
             └────────┬────────┘
                      │
                      ▼
             ┌─────────────────┐
             │ Projection      │
             │ / current state │
             └─────────────────┘
```

Example:

```text
inventory_movements
        ↓
stock_balance
```

The movement table preserves history.

The balance table makes reads fast.

This is a denormalized read model whose source is immutable facts.

That gives you both:

- historical truth;
- efficient current-state queries.

---

# 9. The Most Important Design Decision: Source of Truth

Before creating an append-only table, answer:

> Which representation is authoritative?

Possible answers:

```text
A. current row
B. history rows
C. event stream
D. financial ledger
E. external source
```

You must not have two independent authorities unless reconciliation is explicitly designed.

Bad:

```text
orders.status = PAID
payments.status = SUCCESS
ledger.amount = 100
```

with no defined authority.

Better:

```text
payment_events = immutable facts
payment_projection = current read model
```

The authority is explicit.

# 10. Schema Design for Immutable Rows

A robust append-only record commonly contains:

```sql
CREATE TABLE inventory_movements (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id       bigint NOT NULL,
    item_id         bigint NOT NULL,
    quantity_delta  numeric(20, 6) NOT NULL,
    movement_type   text NOT NULL,
    occurred_at     timestamptz NOT NULL,
    recorded_at     timestamptz NOT NULL DEFAULT now(),
    actor_id        bigint,
    correlation_id  uuid,
    idempotency_key text,
    reason          text,
    metadata        jsonb NOT NULL DEFAULT '{}'::jsonb
);
```

Important fields often include:

- stable primary key;
- tenant/aggregate ownership;
- business occurrence time;
- database recording time;
- actor or service identity;
- correlation/request identifier;
- idempotency key;
- immutable business payload;
- reason/reference;
- optional metadata.

Do not confuse `occurred_at` and `recorded_at`.

An external event can occur at 10:00 and reach the database at 10:03.

That distinction becomes critical in distributed systems.

---

# 11. Database-Enforced Immutability

Application discipline alone is insufficient.

This is weak:

```text
Repository.save(row)
```

combined with a developer convention saying:

> "Never update old rows."

Another service, migration script, analyst, ORM method, or admin account can violate it.

The database is the strongest practical enforcement boundary inside PostgreSQL.

---

# 12. Strategy A — Remove UPDATE/DELETE Privileges

A simple and powerful first layer is role separation.

```sql
REVOKE UPDATE, DELETE
ON inventory_movements
FROM app_writer;
```

Then grant only what is required:

```sql
GRANT INSERT, SELECT
ON inventory_movements
TO app_writer;
```

This makes the intended capability explicit.

However, table privileges must be designed together with ownership, maintenance roles, migrations, and operational access.

A privileged owner can still modify the table.

Therefore permissions are necessary but may not be sufficient for high-assurance systems.

---

# 13. Strategy B — Insert Through a Controlled API

Expose a database function or procedure to authorized application roles and deny direct table writes.

Conceptually:

```text
Application
    ↓
write function
    ↓
append-only table
```

Example:

```sql
CREATE FUNCTION append_inventory_movement(
    p_tenant_id bigint,
    p_item_id bigint,
    p_quantity_delta numeric,
    p_movement_type text,
    p_occurred_at timestamptz,
    p_actor_id bigint,
    p_idempotency_key text
)
RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
    v_id bigint;
BEGIN
    INSERT INTO inventory_movements (
        tenant_id,
        item_id,
        quantity_delta,
        movement_type,
        occurred_at,
        actor_id,
        idempotency_key
    )
    VALUES (
        p_tenant_id,
        p_item_id,
        p_quantity_delta,
        p_movement_type,
        p_occurred_at,
        p_actor_id,
        p_idempotency_key
    )
    RETURNING id INTO v_id;

    RETURN v_id;
END;
$$;
```

Then control who can execute the function and who can directly write the table.

PostgreSQL security-definer functions must be designed carefully: the official documentation warns about writable schemas and `search_path` manipulation, and recommends a secure path plus explicit privilege control. citeturn412657search0turn412657search2

# 14. Strategy C — Triggers That Reject Mutation

For defense in depth, a trigger can reject updates and deletes.

```sql
CREATE FUNCTION reject_immutable_mutation()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    RAISE EXCEPTION
        'table % is immutable; operation % is not allowed',
        TG_TABLE_NAME,
        TG_OP;
END;
$$;

CREATE TRIGGER inventory_movements_immutable
BEFORE UPDATE OR DELETE ON inventory_movements
FOR EACH ROW
EXECUTE FUNCTION reject_immutable_mutation();
```

PostgreSQL triggers can fire for `INSERT`, `UPDATE`, `DELETE`, and `TRUNCATE`, and can operate at row or statement level. Trigger execution occurs in the same transaction as the triggering operation, so an error rolls back the operation. citeturn412657search1

### Important limitation

A trigger is not a substitute for access control.

An administrator with enough authority can disable or replace database objects.

The correct architecture layers controls:

```text
Privileges
   ↓
Controlled write path
   ↓
Triggers / invariants
   ↓
Monitoring / reconciliation
```

---

# 15. Strategy D — Updatable View Becomes the API

Applications can be denied direct table access while interacting with a constrained view.

```sql
CREATE VIEW inventory_movement_input AS
SELECT
    tenant_id,
    item_id,
    quantity_delta,
    movement_type,
    occurred_at,
    actor_id,
    idempotency_key
FROM inventory_movements;
```

For true append-only APIs, a dedicated insert function is usually clearer than pretending the view represents a mutable table.

The lesson is broader:

> Design the allowed operation set first. Then choose the SQL object that exposes exactly that set.

---

# 16. Preventing UPDATE Through `WITH CHECK`

Row-level security can restrict writes, but it is authorization policy, not a complete immutable-history mechanism.

PostgreSQL RLS separates visibility conditions (`USING`) from checks on inserted/updated rows (`WITH CHECK`). citeturn412657search4

For an append-only table, permissions plus RLS can ensure that only the allowed tenant/application context can insert rows.

But do not assume:

```text
RLS enabled = immutable
```

RLS controls which rows a role can access under policy.

Immutability requires preventing mutation itself.

---

# 17. The Correction Pattern

The strongest immutable systems treat correction as a new fact.

Suppose a payment was recorded as 100 but should have been 90.

Do not:

```sql
UPDATE payments
SET amount = 90
WHERE id = 10;
```

Instead, model a correction:

```text
Payment #10    +100
Correction #11  -10
-------------------
Effective        90
```

The original fact remains auditable.

Depending on the domain, the correction might be represented as:

- reversal;
- compensating entry;
- cancellation event;
- adjustment event;
- replacement fact with explicit supersession.

The exact model is domain-specific.

---

# 18. Never Use "Magic Updates" to Simulate Immutability

A dangerous anti-pattern is:

```text
old_row.is_deleted = true
```

and then calling it immutable.

That row was mutated.

Soft delete provides lifecycle state; it does not provide immutability.

This distinction matters for evidence and high-assurance audit models.

---

# 19. Corrections Need Causality

Every corrective fact should answer:

```text
What was corrected?
Why?
Who authorized it?
Which operation caused it?
When was it recorded?
```

Useful fields include:

```sql
supersedes_id
correction_reason
corrected_by
correlation_id
```

But be careful with `supersedes_id` in graphs.

A chain should normally be queryable as:

```text
original
   ↓
correction
   ↓
second correction
```

rather than allowing arbitrary cyclic correction relationships.

---

# 20. Idempotency Is Essential

Append-only systems amplify retry risk.

Suppose an API inserts a payment event and times out before receiving the response.

The client retries.

Without idempotency:

```text
request → INSERT
request retry → INSERT
```

Now one business action may exist twice.

Use a business-scoped idempotency key:

```sql
CREATE UNIQUE INDEX payments_idempotency_uq
ON payment_events (tenant_id, idempotency_key)
WHERE idempotency_key IS NOT NULL;
```

Then a retry becomes safe at the database boundary.

The key should identify the intended business operation, not merely the HTTP request attempt.

---

# 21. Idempotency Is Not Uniqueness of Events

Do not blindly make:

```text
(tenant_id, idempotency_key)
```

unique unless the semantic contract really means one logical operation per key.

Sometimes the same external message ID is allowed across systems or namespaces.

Model the scope explicitly:

```text
(source_system, external_event_id)
```

or:

```text
(tenant_id, operation_type, idempotency_key)
```

The unique key must encode the business identity of the operation.

---

# 22. Ordering: The Hidden Problem

Immutable does not automatically mean ordered.

A common mistake is assuming:

```text
id = event order
```

That can be wrong in distributed systems.

Identity generation, transaction concurrency, retries, and timestamp differences can produce surprising ordering.

Define what ordering means:

### Database insertion order

Useful for some operational analysis, but not necessarily business order.

### Transaction commit order

Different from event occurrence time.

### Domain sequence

Explicit sequence number for an aggregate or stream.

Example:

```sql
aggregate_id bigint NOT NULL,
sequence_no bigint NOT NULL,
UNIQUE (aggregate_id, sequence_no)
```

This creates a stronger business ordering contract.

---

# 23. Aggregate-Local Sequencing

A powerful event-stream pattern is:

```text
order 42:
  sequence 1 CREATED
  sequence 2 PAID
  sequence 3 PACKED
  sequence 4 SHIPPED
```

The uniqueness invariant prevents two events from claiming the same aggregate sequence number.

But allocating sequence numbers concurrently requires careful transaction design.

A naive:

```sql
SELECT max(sequence_no) + 1
```

is race-prone.

Two concurrent transactions can compute the same value.

Safer designs include:

- locking the aggregate row;
- maintaining a counter with controlled locking;
- serializing append operations per aggregate;
- using database-side commands that establish the next sequence atomically.

Measure contention before selecting a mechanism.

---

# 24. Transaction Atomicity

An immutable event and its projection should often be committed together.

Example:

```text
BEGIN
  INSERT payment_event
  UPDATE payment_projection
  INSERT outbox_event
COMMIT
```

Now the database state and event are atomically related.

But this can increase transaction work.

Alternative architectures may allow asynchronous projections.

The choice depends on the consistency requirement.

---

# 25. Immutable Facts + Outbox

A useful production pattern is:

```text
business fact
     │
     ├── immutable domain row
     │
     └── outbox message
```

Both are written in one transaction.

Then a worker publishes the outbox message externally.

This avoids the classic dual-write problem:

```text
DB COMMIT succeeds
message publish fails
```

or:

```text
message publish succeeds
DB COMMIT fails
```

The outbox makes the pending external effect durable.

---

# 26. Append-Only Does Not Mean No Derived State

You generally should not recalculate everything from millions of historical rows for every request.

Use projections:

```text
immutable_events
       ↓
projection worker
       ↓
current_state
```

The projection can be rebuilt.

This creates an important operational property:

> **Rebuildability**

If the current state is corrupted, you can reconstruct it from immutable facts.

A projection that cannot be rebuilt is a second source of truth disguised as a cache.

---

# 27. Projection Rebuild Strategy

A robust rebuild plan answers:

```text
1. Where do facts begin?
2. What version of the projection logic is used?
3. Are events replayable?
4. Is ordering deterministic?
5. What external dependencies are involved?
6. Can rebuild happen offline?
7. How is the rebuilt result verified?
8. How is cutover performed?
```

For large systems:

```text
immutable facts
   ↓
new projection table
   ↓
validation
   ↓
atomic cutover / controlled switch
```

Avoid rebuilding a production projection in place when it creates an extended period of inconsistent reads.

---

# 28. Event Schema Evolution

Immutable history lasts longer than application versions.

That means old rows must remain interpretable.

Avoid designing events around unstable DTOs.

Example:

```json
{
  "type": "OrderPlaced",
  "version": 1,
  "payload": {
    "total": 100
  }
}
```

Later:

```json
{
  "type": "OrderPlaced",
  "version": 2,
  "payload": {
    "subtotal": 90,
    "tax": 10,
    "currency": "INR"
  }
}
```

The projection layer needs a deliberate compatibility strategy.

Historical facts should not become unreadable merely because the application moved from v1 to v2.

---

# 29. Do Not Rewrite Old Events During Schema Evolution

A common anti-pattern:

```text
migration scans event table
→ rewrites every historical payload
```

That can destroy the exact historical representation that was originally recorded.

Prefer one of:

- preserve original payload and interpret by version;
- maintain a canonical migration layer for reads;
- append a new corrective/migration event where domain semantics permit it.

Whether raw event payload is itself part of the legal/audit evidence must be explicitly decided.

---

# 30. JSONB vs Typed Columns

Append-only designs often use JSONB because event schemas evolve.

Example:

```sql
payload jsonb NOT NULL
```

Advantages:

- flexible schema;
- easy ingestion;
- supports versioned event payloads.

Costs:

- weaker structural guarantees;
- harder constraints;
- potentially expensive queries;
- larger storage;
- schema drift.

A strong design often puts invariants in typed columns:

```text
id
aggregate_id
event_type
version
occurred_at
recorded_at
tenant_id
```

and keeps less-stable attributes in `jsonb`.

---

# 31. Security: Who Can Break Immutability?

Ask this explicitly.

Potential actors:

```text
application role
migration role
DBA
superuser
backup/restore process
admin API
support tooling
ETL process
analytics role
replication consumer
```

A high-assurance design separates operational roles.

For example:

```text
app_reader
app_writer
projection_worker
migration_owner
security_admin
```

Do not grant the application role broad table ownership just because the ORM expects it.

PostgreSQL permissions and security-definer behavior must be reviewed together. PostgreSQL's documentation explicitly cautions that backend functions and triggers can become security hazards if object ownership and `search_path` are not controlled. citeturn412657search0turn412657search2

---

# 32. RLS and Append-Only Data

For multi-tenant immutable facts:

```text
immutability
     +
row isolation
     +
write authorization
```

These are three separate concerns.

Example:

```sql
ALTER TABLE payment_events ENABLE ROW LEVEL SECURITY;
```

Then tenant-specific policies can control which events a caller can see or insert.

Do not treat RLS as a replacement for grants or immutable-write controls.

PostgreSQL documents that `USING` governs visible/targetable existing rows, while `WITH CHECK` governs new rows produced by `INSERT` and `UPDATE`. citeturn412657search4

Also account for privileged roles and table-owner behavior when threat-modeling RLS. PostgreSQL documents that superusers and `BYPASSRLS` roles bypass RLS, while owners normally bypass it unless forced into RLS. citeturn412657search20

---

# 33. Tenant-Scoped Immutable Data

A typical invariant is:

```text
A fact belongs to exactly one tenant.
It cannot be reassigned to another tenant.
```

Therefore `tenant_id` is part of the immutable identity contract.

Do not allow:

```sql
UPDATE event
SET tenant_id = 20
WHERE id = 100;
```

Even if the business rarely performs such a move, cross-tenant reassignment is often a security boundary violation.

If data migration between tenants is legitimate, model it as an explicit business operation with a new representation and preserved provenance.

---

# 34. Financial / Ledger Connection

Immutable append-only modeling is especially strong for ledger systems.

Instead of:

```text
balance = 1000
```

store:

```text
entry +1000
entry -200
entry +50
```

Then derive:

```text
current balance = 850
```

But a ledger requires stronger rules than generic append-only history:

- account identity;
- currency;
- transaction identity;
- debit/credit semantics;
- balancing;
- effective time;
- posting time;
- correction/reversal semantics;
- authorization;
- reconciliation.

These are intentionally deferred to **02.18 — Financial / Ledger Modeling**, where they are treated as a complete domain architecture.

---

# 35. Inventory Connection

A jewellery ERP is a useful example.

Do not model inventory history only as:

```text
stock.quantity = 97
```

Instead:

```text
PURCHASE_RECEIPT  +100
SALE              -2
TRANSFER_OUT      -1
TRANSFER_IN       +1
ADJUSTMENT         -1
--------------------
CURRENT            97
```

The movements are immutable facts.

A current stock table is a projection.

This lets operations answer:

- where did the quantity change?
- which branch moved it?
- who recorded the movement?
- which document caused it?
- what was the stock at a historical point in time?

---

# 36. Immutable Is Not Automatically Auditable

A row being immutable does not prove who created it.

You still need provenance:

```text
actor_id
service_id
request_id
correlation_id
source_system
external_reference
```

Likewise, a timestamp without actor context is incomplete audit evidence.

Audit architecture and immutable data architecture complement each other.

---

# 37. Time Semantics

At minimum distinguish:

```text
occurred_at  = when the business event happened
recorded_at  = when PostgreSQL recorded it
```

In distributed systems you may also need:

```text
received_at
processed_at
published_at
```

Never infer business chronology from a field whose semantics were not explicitly defined.

---

# 38. Deletion Semantics

An append-only table is still vulnerable to destructive deletion if access allows it.

Possible policies:

### Strict immutable

No ordinary delete at all.

### Retained immutable

Rows cannot be modified, but approved lifecycle processes may physically remove data after retention expires.

### Cryptographically archived

Data is immutable within the primary system but later moved to protected archival storage.

### Legal evidence tier

A separate controlled system preserves the evidence independently.

Do not assume one policy is right for every domain.

---

# 39. TRUNCATE Is a Special Threat

Blocking `DELETE` is not enough.

Consider `TRUNCATE` explicitly.

Application roles should normally not have the ability to truncate high-assurance history tables.

A system that says:

```text
"developers cannot delete audit rows"
```

but grants broad table privileges is not necessarily protected from destructive administrative actions.

Review privileges as a complete capability set.

---

# 40. Partitioning Append-Only Data

Append-only tables naturally grow.

At scale, partitioning can separate data by time or another high-value lifecycle dimension.

Example conceptual layout:

```text
payment_events
├── 2026-01
├── 2026-02
├── 2026-03
└── ...
```

Potential benefits:

- easier retention management;
- partition pruning;
- smaller indexes per partition;
- lower operational cost for old data;
- easier archival workflows.

But partitioning is not free.

You add:

- partition management;
- more objects;
- routing considerations;
- operational complexity;
- possible query/planner overhead.

Use it because workload/lifecycle characteristics justify it, not because append-only automatically implies partitioning.

---

# 41. Index Design for Append-Heavy Tables

Append-only does not mean "index everything".

Each additional index adds write work and storage.

Common access paths might include:

```sql
CREATE INDEX payment_events_tenant_time_idx
ON payment_events (tenant_id, occurred_at DESC);
```

or aggregate-local retrieval:

```sql
CREATE INDEX order_events_order_seq_idx
ON order_events (order_id, sequence_no);
```

Choose indexes from actual queries.

Typical questions:

```text
What is the latest event for an aggregate?
What happened in a time range?
What events belong to a tenant?
Which events correspond to an external ID?
```

Do not create indexes for every JSONB property just because future queries are imaginable.

---

# 42. Hot Partitions and Contention

Append-only writes can still contend.

Potential hotspots include:

- one aggregate's sequence allocation;
- one global counter;
- one "latest state" row updated for every event;
- a unique index with highly concentrated keys;
- synchronous projection updates.

The event table itself can be append-heavy while the projection becomes the actual bottleneck.

Measure the whole write path.

---

# 43. Current-State Projection Pitfall

Consider:

```text
INSERT immutable_event
UPDATE account_balance
```

The event table is append-only.

The balance row is mutable.

That is fine—provided the architecture is explicit.

But now a hot account may receive thousands of transactions and every transaction updates one row.

That row becomes a concurrency hotspot.

Solutions might include:

- partitioning by account domain;
- batching projections;
- deriving state asynchronously;
- maintaining sharded counters;
- using account-level serialization.

There is no universal answer.

---

# 44. Reconciliation

Any derived representation should be periodically reconciled against immutable facts.

Example:

```sql
SELECT
    item_id,
    SUM(quantity_delta)
FROM inventory_movements
GROUP BY item_id;
```

Compare with:

```text
stock_balance
```

If they differ:

```text
projection ≠ facts
```

You have evidence of corruption, missed events, incorrect projection logic, or data-quality problems.

Reconciliation converts immutability into operational value.

---

# 45. Checksums and Evidence

For high-assurance archives, systems may maintain cryptographic digests over canonicalized records or batches.

Conceptually:

```text
row1
row2
row3
  ↓
canonical representation
  ↓
hash
```

Or a chain:

```text
hash_n = H(row_n || hash_(n-1))
```

This can help detect tampering.

But a hash is not magical proof of truth.

The trustworthiness of the hashing process, key management, canonicalization, access controls, and retention architecture also matter.

Use cryptographic evidence when the threat model requires it, not as decorative complexity.

---

# 46. `created_at` Does Not Make a Row Immutable

This is one of the most common mistakes.

Bad:

```sql
created_at timestamptz NOT NULL DEFAULT now()
```

followed by:

```sql
UPDATE events SET payload = ...;
```

The row has a timestamp, but it is still mutable.

Likewise:

```text
is_deleted = false
```

or:

```text
version = 1
```

does not make a record immutable.

Immutability is about what operations are permitted after commit.

---

# 47. Optimistic Locking Is Not Immutability

Another common confusion:

```sql
UPDATE orders
SET status = 'PAID', version = version + 1
WHERE id = 42
  AND version = 3;
```

This provides optimistic concurrency control.

It still mutates history.

Optimistic locking answers:

> Did somebody change this row before me?

Immutability answers:

> Can the committed fact itself be rewritten?

These solve different problems.

---

# 48. Triggers Are Transactional

A rejection trigger is attractive because the mutation fails inside the same transaction.

Example:

```text
BEGIN
UPDATE immutable_table ...
→ trigger raises exception
ROLLBACK
```

PostgreSQL documents that triggers execute within the triggering transaction; when the trigger or triggering statement errors, their effects roll back together. citeturn412657search1

This property makes trigger-based enforcement useful as a final defense layer.

---

# 49. Security-Definer Pitfall

Suppose you expose:

```sql
SECURITY DEFINER
```

and the function constructs dynamic SQL or resolves objects through a writable schema.

An attacker may be able to exploit object-name resolution.

PostgreSQL specifically recommends secure `search_path` handling for security-definer functions and warns about untrusted/writable schemas. citeturn412657search0turn412657search2

For immutable write APIs:

- use fully qualified object names where appropriate;
- set a secure `search_path`;
- revoke default `PUBLIC` execute where needed;
- expose only required arguments;
- validate business invariants in the function;
- separate ownership from application roles.

# 50. AI / Vibe-Coding Failure Modes

AI-generated database code commonly fails in predictable ways.

## Failure 1 — "Audit table means immutable"

Generated schema:

```sql
CREATE TABLE audit (...);
```

but application role still has `UPDATE` and `DELETE`.

### Fix

Audit the write capabilities themselves.

## Failure 2 — correction by update

AI sees a data error and suggests:

```sql
UPDATE ledger SET amount = ...;
```

### Fix

Ask:

> Is this a mutable state record or an immutable fact?

For facts, design a compensating entry.

## Failure 3 — event ordering from bigint ID

Generated code assumes:

```text
higher ID = later business event
```

### Fix

Define explicit chronology semantics.

---

## Failure 4 — no idempotency

Retrying an API creates duplicate events.

### Fix

Make business operation identity explicit and enforce uniqueness where appropriate.

---

## Failure 5 — RLS mistaken for immutability

Generated answer says:

```text
"RLS prevents users from changing historical records."
```

### Fix

Separate row authorization from operation authorization and mutation enforcement.

---

## Failure 6 — rebuildability ignored

System stores immutable events but cannot reconstruct state.

### Fix

Treat replay/rebuild as a production requirement, not a future luxury.

# 51. Production Pattern — Jewellery ERP

Suppose a jewellery ERP handles branch inventory.

A strong model might include:

```text
inventory_movements
sales_events
purchase_events
transfer_events
adjustment_events
```

Each event references:

```text
tenant
branch
item
source_document
actor
occurred_at
recorded_at
correlation_id
```

Current state:

```text
branch_stock
```

is derived.

A stock correction does not erase the old movement.

Instead:

```text
ADJUSTMENT +2
REVERSAL    -2
ADJUSTMENT +1
```

Now the system can explain the complete history.

# 52. Production Pattern — Payment Events

Consider:

```text

PaymentRefunded
```

These are facts.

Current payment status is a projection:


A support agent asking:

can inspect the immutable event chain rather than relying on one mutable status value.

# 53. What Should Remain Mutable?

Do not make everything immutable.

Common mutable data:

- user preferences;
- contact details;
- current workflow state;
- derived balances;
- cache tables;
- search indexes;
- materialized summaries;
- operational metadata.

A strong architecture asks:

```text
Does this represent a fact or a current view of facts?
```

Facts often benefit from immutability.

Views often benefit from controlled mutation.

# 55. Naive → Improved → Production

## Naive approach

```text
orders.status = 'PAID'
```

### Why it fails

It loses the causal history.

### Improved approach

```text
payment_events
+
payment_projection
```

### Why it works

The event preserves history while the projection provides fast current reads.

### Production considerations

Add:

- idempotency;
- authorization;
- tenant isolation;
- outbox;
- replay strategy;
- observability;
- reconciliation.

### Alternative

Full event sourcing.

### Trade-off

More historical integrity and replayability, but greater schema, operational, and projection complexity.

# 56. Testing Strategy

Immutability must be tested by trying to break it.

## Functional tests

Try:

```sql
UPDATE immutable_table ...;
DELETE FROM immutable_table ...;
TRUNCATE immutable_table;
```

Expected result:

```text
permission denied
```

or a deliberate immutable-operation error.

## Concurrency tests

Run concurrent append operations and verify:

- no duplicate business operation;
- no sequence collision;
- no missing events;
- projection remains reconcilable.

## Failure tests

Simulate:

- client timeout after commit;
- worker crash after event insert;
- duplicate delivery;
- projection failure;
- partial external outage;
- replay of historical data.

Useful queries include:

### Latest event per aggregate

```sql
SELECT DISTINCT ON (order_id)
    order_id,
    event_type,
    occurred_at
FROM order_events
ORDER BY order_id, sequence_no DESC;
```

### Event count by type

```sql
SELECT event_type, count(*)
FROM order_events
GROUP BY event_type;
```

### Idempotency conflicts

```sql
SELECT idempotency_key, count(*)
FROM payment_events
GROUP BY idempotency_key
HAVING count(*) > 1;
```

The precise query shape should follow the indexes and workload.

```text
audit records
transaction context
migration history

```

# 62. Performance Trade-offs

Immutable storage changes the performance profile.

### Benefits

- inserts can be operationally simple;
- history is naturally queryable;
- fewer in-place state changes for facts;
- replay and reconstruction are possible;
- analytical queries can exploit sequential/time-local patterns.

### Costs

- table growth;
- index growth;
- storage and backup cost;
- projection maintenance;
- more expensive current-state queries if no projection exists;
- retention and archival operations;
- replay cost.

Measure actual workload.

"Append-only is faster" is not a universal truth.

---

# 63. WAL, Replication, and Backup Implications

Large append rates create WAL volume.

Every append must be considered in relation to:

- WAL throughput;
- replication bandwidth;
- replica replay lag;
- backup size;
- index growth;
- retention operations.

An append-only architecture can produce extremely high write throughput while simultaneously producing large durable history.

Capacity planning must model both:

```text
write rate
+
retention horizon
```

not just requests per second.

---

# 64. Archive Before You Need It

An append-only table can grow indefinitely unless lifecycle is designed.

Typical strategy:

```text
hot facts
   ↓
warm historical partition
   ↓
archive
   ↓
retention expiry
   ↓
disposal
```

The exact boundary is domain-specific.

For regulated or financially important records, deletion may be restricted or delayed.

This is why **02.14 Data Lifecycle** and **02.15 Archival** are part of the same architectural story.

# 69. Final Mental Model

Remember the system as four layers:

```text
                ┌────────────────────┐
                │  Commands / APIs   │
                └──────────┬─────────┘
                           │
                           ▼
                ┌────────────────────┐
                │ Immutable Facts    │
                │ append-only        │
                └──────────┬─────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
   ┌───────────────────┐     ┌───────────────────┐
   │ Current Projection│     │ External Effects   │
   │ / read model      │     │ via outbox/CDC     │
   └───────────────────┘     └───────────────────┘
```

The facts are the historical record.

The projection is the optimized interpretation.

The outbox/CDC path transports durable consequences.

Corrections add facts rather than erase facts.

---

# 70. Central Principle

> **Immutability is not a timestamp, a coding convention, or a table name. It is an explicitly enforced invariant that a committed fact cannot be silently rewritten.**
>
> **Append-only architecture preserves historical truth by turning correction into another fact, while mutable projections provide efficient current state. The production goal is not to make everything immutable; it is to make the right facts immutable, make the trust boundary enforceable, make corrections explainable, make projections rebuildable, and make the whole system operationally sustainable.**
