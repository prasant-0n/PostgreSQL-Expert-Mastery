# 02.7 — Constraints

> **Phase 02 — Relational Data Modeling**  
> **Chapter 02.7 — Constraints**

Constraints are the database's executable definition of **what data is allowed to exist**.

A schema without meaningful constraints is often only a collection of columns and application assumptions. A production schema should instead encode the invariants that must remain true regardless of which service, job, migration, script, administrator, retry, or client attempts a write.

This chapter goes beyond syntax. The goal is to understand constraints as a **correctness architecture**: what they guarantee, when they are checked, how they interact with concurrency, how they affect migrations and performance, how to diagnose violations, and how to decide whether an invariant belongs in a constraint, a query, a transaction, application code, or another architectural mechanism.

---

## 1. Chapter Objective

By the end of this chapter, you should be able to:

- explain what a database constraint actually guarantees;
- distinguish `NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, and `EXCLUDE` constraints;
- understand column constraints versus table constraints;
- reason about `NULL`, `TRUE`, `FALSE`, and `UNKNOWN` in `CHECK` constraints;
- understand uniqueness, duplicate prevention, and PostgreSQL's handling of `NULL` values;
- design composite uniqueness correctly;
- design foreign keys and understand their delete/update actions;
- explain why foreign-key columns often need indexes even though PostgreSQL does not automatically create them;
- understand deferred constraints and transaction-time validation;
- understand `NOT VALID`, later validation, and migration implications;
- use named constraints as part of the application's error and observability contract;
- inspect constraints through `pg_constraint` and information-schema views;
- distinguish a constraint violation from a query-level validation failure;
- recognize invariants that can and cannot be represented with ordinary declarative constraints;
- avoid common AI-generated and application-driven integrity mistakes;
- select the strongest practical enforcement layer for a business rule;
- design constraint-heavy schemas that remain maintainable under concurrency and schema evolution.

# 2. What Is a Constraint?

## 2.1 Simple definition

A constraint is a rule that restricts which database states are valid.

For example:

```sql
price numeric(12,2) CHECK (price >= 0)
```

This states that a row with a negative price is not valid.

---

## 2.2 Engineering definition

A constraint is a **database-enforced invariant** attached to a relation, column, or set of columns that PostgreSQL evaluates at the appropriate point during data modification.

The important phrase is **database-enforced**.

Consider this application code:

```ts
if (price < 0) {
  throw new Error('Price cannot be negative');
}
```

That is validation.

Now compare it with:

```sql
CHECK (price >= 0)
```

That is an integrity constraint.

The distinction matters because the database rule survives:

- another API;
- another service;
- a background worker;
- a migration script;
- a direct SQL client;
- a batch import;
- an administrative operation;
- a future service written in another language;
- an accidental write from a debugging session.

Application validation can improve user experience. Database constraints defend the **database itself**.

---

## 2.3 Expert definition

A constraint defines a subset of the theoretically possible database states as **valid states**.

Let the unconstrained state space be:

```text
S = all states reachable by arbitrary writes
```

A constraint defines a valid subset:

```text
V ⊆ S
```

A write is acceptable only when the resulting state satisfies the applicable invariants.

This gives a useful architectural principle:

> A production database should make invalid states difficult or impossible to persist, not merely inconvenient to detect later.

---

# 3. The Constraint Mindset

A weak database design often asks:

> "How do I validate the input?"

A stronger database design asks:

> "What states must never be allowed to exist?"

These are not the same question.

For a jewellery ERP, for example:

```text
Requirement:
A stock movement must reference an existing stock item.
```

Weak approach:

```text
Check item existence in Node.js before inserting movement.
```

Strong approach:

```sql
FOREIGN KEY (item_id)
REFERENCES inventory_items(id)
```

The application check can remain for fast feedback, but the database constraint is the final integrity boundary.

---

# 4. The Major PostgreSQL Constraint Families

PostgreSQL supports several important constraint categories:

| Constraint | Primary purpose |
|---|---|
| `NOT NULL` | Require a value to exist |
| `CHECK` | Require a Boolean condition to hold |
| `UNIQUE` | Prevent duplicate key combinations |
| `PRIMARY KEY` | Define the row's primary identity and uniqueness |
| `FOREIGN KEY` | Enforce referential integrity |
| `EXCLUDE` | Prevent conflicting combinations according to operator semantics |
| `NOT ENFORCED` | Document certain constraints without runtime checking in supported cases |
| `DEFERRABLE` | Allow supported constraints to be checked later |

PostgreSQL 18 documents these constraint families and also supports `NOT ENFORCED` for `CHECK` and foreign-key constraints, plus temporal `WITHOUT OVERLAPS` / `PERIOD` forms for certain uniqueness and referential-integrity use cases. citeturn336142search0turn336142search1turn336142search2

This chapter focuses on the general constraint engineering principles first, then covers PostgreSQL-specific advanced behavior.

# 5. `NOT NULL`

## 5.1 What it means

`NOT NULL` says that the column cannot contain SQL `NULL`.

```sql
CREATE TABLE customers (
    id bigint PRIMARY KEY,
    name text NOT NULL
);
```

This prevents:

```sql
INSERT INTO customers (id, name)
VALUES (1, NULL);
```

---

## 5.2 Why `NOT NULL` matters

A nullable column has more possible states than many developers realize.

For a text field:

```text
NULL
''
'unknown'
'not provided'
'pending'
```

These are different states.

Every unnecessary nullable column increases the application's semantic state space.

Compare:

```sql
middle_name text
```

with:

```sql
middle_name text NOT NULL DEFAULT ''
```

Neither is universally correct. The correct choice depends on whether “no middle name/value” is semantically represented by `NULL`, empty text, or a separate state.

The key principle is:

> Nullability is part of the domain model, not merely a technical default.

---

## 5.3 `NOT NULL` versus `CHECK`

You may see:

```sql
CHECK (name IS NOT NULL)
```

instead of:

```sql
name text NOT NULL
```

For a direct non-null requirement, use `NOT NULL`.

It communicates intent better and is the specialized database mechanism for the rule.

---

# 6. `CHECK` Constraints

## 6.1 Basic form

```sql
CREATE TABLE products (
    id bigint PRIMARY KEY,
    price numeric(12,2) NOT NULL,
    CONSTRAINT products_price_nonnegative
        CHECK (price >= 0)
);
```

A `CHECK` constraint requires its expression not to evaluate to `FALSE`. PostgreSQL's documented semantics allow a `CHECK` expression evaluating to `TRUE` or `UNKNOWN` to pass. citeturn336142search0turn336142search1

This is one of the most important details in the entire chapter.

---

## 6.2 `CHECK` is a Boolean expression

Suppose:

```sql
CHECK (quantity > 0)
```

Then:

```text
quantity = 5      → TRUE   → accepted
quantity = 0      → FALSE  → rejected
quantity = -2     → FALSE  → rejected
quantity = NULL   → UNKNOWN → accepted by the CHECK itself
```

Therefore:

```sql
quantity integer CHECK (quantity > 0)
```

is not equivalent to:

```sql
quantity integer NOT NULL CHECK (quantity > 0)
```

The second version enforces both existence and positivity.

---

## 6.3 Developer mistake: forgetting NULL semantics

A common generated schema is:

```sql
age integer CHECK (age >= 18)
```

The developer thinks:

> "Only adults can be stored."

But the actual rule is:

> "If age is present, it must be at least 18."

If age must exist:

```sql
age integer NOT NULL
    CHECK (age >= 18)
```

---

## 6.4 Single-column checks

```sql
score integer
    CHECK (score BETWEEN 0 AND 100)
```

```sql
status text
    CHECK (status IN ('draft', 'active', 'archived'))
```

```sql
percentage numeric(5,2)
    CHECK (percentage >= 0 AND percentage <= 100)
```

---

## 6.5 Multi-column checks

Table-level constraints can express relationships between multiple columns:

```sql
CREATE TABLE orders (
    id bigint PRIMARY KEY,
    subtotal numeric(12,2) NOT NULL,
    tax numeric(12,2) NOT NULL,
    total numeric(12,2) NOT NULL,

    CONSTRAINT orders_total_matches_components
        CHECK (total = subtotal + tax)
);
```

This prevents an entire class of application bugs.

---

## 6.6 Conditional checks

Consider a shipment:

```sql
CREATE TABLE shipments (
    id bigint PRIMARY KEY,
    status text NOT NULL,
    shipped_at timestamptz,

    CONSTRAINT shipment_shipped_at_rule
        CHECK (
            status <> 'shipped'
            OR shipped_at IS NOT NULL
        )
);
```

This says:

```text
If status = shipped, shipped_at must exist.
```

A more complete state machine may require multiple constraints or a dedicated modeling approach, which is addressed later in this phase.

---

# 7. What a `CHECK` Constraint Should and Should Not Do

Good `CHECK` constraints generally describe **row-local invariants**.

Examples:

```sql
CHECK (amount >= 0)
```

```sql
CHECK (end_at > start_at)
```

```sql
CHECK (status IN ('pending', 'paid', 'cancelled'))
```

Risky or incorrect uses include attempting to encode arbitrary cross-row or cross-table logic inside a normal `CHECK`.

For example, a rule such as:

> "There must never be two active bookings for the same room."

is not fundamentally a simple row-local condition. A normal `CHECK` cannot safely express arbitrary cross-row uniqueness.

Use a suitable unique/exclusion constraint or a transaction/locking strategy depending on the rule.

---

# 8. `UNIQUE` Constraints

## 8.1 Purpose

A `UNIQUE` constraint says that a set of column values must be unique among rows.

```sql
CREATE TABLE users (
    id bigint PRIMARY KEY,
    email text NOT NULL,

    CONSTRAINT users_email_unique
        UNIQUE (email)
);
```

This establishes a database-enforced uniqueness invariant.

PostgreSQL automatically creates an index to enforce a unique constraint. citeturn336142search1

---

## 8.2 Why application-only uniqueness is broken

Naive code:

```text
1. SELECT whether email exists
2. If not, INSERT user
```

Two concurrent transactions can both observe:

```text
email does not exist
```

and both attempt the insert.

This is the classic time-of-check/time-of-use race.

The database constraint closes the race:

```sql
UNIQUE (email)
```

Then one transaction can succeed and the conflicting write fails or participates in an `ON CONFLICT` strategy.

---

## 8.3 Composite uniqueness

Suppose one SKU may exist once per tenant:

```sql
UNIQUE (tenant_id, sku)
```

This means:

```text
tenant 1 + SKU A = allowed
 tenant 1 + SKU A = rejected
 tenant 2 + SKU A = allowed
```

This is an important multi-tenant pattern.

---

## 8.4 Uniqueness is about the whole key

Given:

```sql
UNIQUE (branch_id, invoice_number)
```

The constraint is not:

```text
invoice_number globally unique
```

It is:

```text
(invoice_number, branch_id) combination is unique
```

Precision matters because schema-level semantics become application behavior.

---

## 8.5 NULL and uniqueness

One subtle PostgreSQL behavior is that the ordinary default treatment of `NULL` in unique constraints allows multiple `NULL` values because `NULL` values are treated as distinct for uniqueness purposes.

For example:

```sql
CREATE TABLE users (
    id bigint PRIMARY KEY,
    external_id text UNIQUE
);
```

Multiple rows can normally have:

```text
external_id = NULL
```

If the business rule is:

> "There can be at most one NULL, and otherwise values must be unique."

PostgreSQL 18 supports:

```sql
UNIQUE NULLS NOT DISTINCT (external_id)
```

This changes the uniqueness semantics so `NULL` values compare as not distinct for that constraint. citeturn336142search0turn336142search1

Do not memorize the syntax without understanding the business rule.

---

# 9. `PRIMARY KEY`

## 9.1 Definition

A primary key identifies the principal unique row identity of a table.

```sql
CREATE TABLE customers (
    id bigint PRIMARY KEY
);
```

A primary key provides:

- uniqueness;
- non-nullability;
- a strong relational identity target for referencing tables.

PostgreSQL automatically creates an index for a primary key. citeturn336142search1

---

## 9.2 Primary key versus unique key

A table may have multiple unique constraints:

```sql
PRIMARY KEY (id)
UNIQUE (email)
UNIQUE (tax_identifier)
```

Conceptually:

```text
Primary key = primary row identity
Unique key  = alternate candidate identity
```

A customer may be uniquely identified by both an internal ID and a tax identifier, but the model should still be explicit about which key is the primary relational identity.

---

## 9.3 Composite primary keys

Composite primary keys are valid:

```sql
PRIMARY KEY (tenant_id, user_id)
```

They can be useful when the model genuinely has a composite identity.

They also propagate into every foreign-key relationship that references that key.

Therefore, before choosing a composite primary key, consider the impact on:

- child tables;
- indexes;
- ORM mappings;
- API references;
- joins;
- cache keys;
- event payloads;
- migration complexity.

A composite primary key is not wrong. It is an architectural choice with consequences.

---

# 10. `FOREIGN KEY`

## 10.1 Purpose

A foreign key enforces **referential integrity**.

Example:

```sql
CREATE TABLE customers (
    id bigint PRIMARY KEY
);

CREATE TABLE orders (
    id bigint PRIMARY KEY,
    customer_id bigint NOT NULL,

    CONSTRAINT orders_customer_fk
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
```

This means an `orders.customer_id` value must correspond to a valid referenced key according to the foreign-key semantics.

PostgreSQL's current documentation supports references to a primary key, suitable unique constraints, and in some cases suitable unique indexes, with additional rules around deferrability and temporal forms. citeturn336142search1

---

# 11. Foreign Keys Are More Than "Join Columns"

A foreign key establishes a statement about **legal database states**.

Without the foreign key:

```text
orders.customer_id = 987
```

could point to no customer.

The database may still accept the row.

With the foreign key:

```text
orders.customer_id = 987
```

is only valid when it satisfies the referenced relationship.

This is one reason relational databases are powerful: relationships are not only represented by naming conventions. They can be **enforced**.

---

# 12. Foreign Key Actions

A foreign key can define what should happen when the referenced row changes or is deleted.

Common actions include:

```sql
ON DELETE NO ACTION
ON DELETE RESTRICT
ON DELETE CASCADE
ON DELETE SET NULL
ON DELETE SET DEFAULT
```

And analogous `ON UPDATE` behavior.

---

## 12.1 `NO ACTION`

This is the default referential action.

The delete/update is not allowed to leave the relationship invalid.

When the constraint is deferrable, `NO ACTION` can also participate in deferred checking.

That makes it different from simply thinking:

> "PostgreSQL immediately checks and rejects every delete."

Timing matters.

---

## 12.2 `RESTRICT`

`RESTRICT` prevents the referenced row from being removed/changed when dependent rows exist.

One critical distinction:

> `RESTRICT` is not deferrable in the same way `NO ACTION` can be.

Therefore, choosing between them is not only a semantic preference; it can affect transaction design.

---

## 12.3 `CASCADE`

```sql
FOREIGN KEY (order_id)
REFERENCES orders(id)
ON DELETE CASCADE
```

Deleting the parent can delete dependent rows.

This can be appropriate for tightly owned dependent records such as:

```text
order
└── order_items
```

But dangerous when the child has independent business meaning.

For example, cascading deletion through:

```text
customer → invoices → payments → audit records
```

may be disastrous.

Use `CASCADE` when the child is truly dependent, not merely because it makes cleanup convenient.

---

## 12.4 `SET NULL`

Useful when the relationship becomes optional after deletion:

```sql
assigned_user_id bigint
    REFERENCES users(id)
    ON DELETE SET NULL
```

The column must be nullable.

---

## 12.5 `SET DEFAULT`

The referencing column receives its default value when the referenced row is deleted/updated, subject to referential-integrity rules.

This is less common and should be chosen only when the default destination has explicit domain meaning.

---

# 13. The Child-Side Foreign Key Index Question

PostgreSQL automatically creates indexes for primary keys and unique constraints, but it does **not** automatically create an index on the referencing foreign-key columns. citeturn336142search1

This is an extremely important production detail.

Given:

```sql
CREATE TABLE orders (
    id bigint PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES customers(id)
);
```

you may need:

```sql
CREATE INDEX orders_customer_id_idx
ON orders(customer_id);
```

Why?

Because operations involving the referenced key may need to identify referencing rows efficiently, especially for parent-side updates/deletes and related joins.

The exact need depends on workload, cardinality, indexes, query patterns, and referential actions, so do not blindly add every possible index. But do not assume the foreign key itself gives you a child-side index.

---

# 14. Constraint Naming

Always consider explicitly naming important constraints.

Instead of:

```sql
CHECK (price >= 0)
```

prefer:

```sql
CONSTRAINT products_price_nonnegative
CHECK (price >= 0)
```

Instead of:

```sql
UNIQUE (tenant_id, sku)
```

prefer:

```sql
CONSTRAINT products_tenant_sku_unique
UNIQUE (tenant_id, sku)
```

PostgreSQL includes a named constraint in violation messages, making names useful as an application-facing and operationally useful diagnostic signal. citeturn336142search1

---

## 14.1 Good names

Prefer names that encode the business rule:

```text
customers_email_unique
products_tenant_sku_unique
invoice_total_nonnegative
order_customer_fk
payment_amount_positive
```

Avoid meaningless names such as:

```text
constraint_17
foo_check
x1
```

A good constraint name helps during:

- debugging;
- logs;
- tests;
- migrations;
- incident response;
- application error mapping.

---

# 15. Column Constraints vs Table Constraints

These are both valid styles.

### Column-level

```sql
CREATE TABLE products (
    price numeric(12,2)
        CONSTRAINT products_price_nonnegative CHECK (price >= 0)
);
```

### Table-level

```sql
CREATE TABLE products (
    price numeric(12,2),
    CONSTRAINT products_price_nonnegative
        CHECK (price >= 0)
);
```

Table-level syntax is generally preferable once the rule spans multiple columns or when you want schema declarations to have a consistent structural format.

PostgreSQL treats column constraints and table constraints as forms of the same underlying constraint model; current catalog documentation stores them in `pg_constraint`. citeturn336142search1turn336142search3

---

# 16. Constraint Timing

A critical advanced question is not only:

> "Does the database enforce this rule?"

but also:

> "When does PostgreSQL enforce this rule?"

For supported constraints, PostgreSQL distinguishes between immediate and deferred checking.

---

# 17. `DEFERRABLE`

A deferrable constraint may have its enforcement postponed until later in the transaction.

Example:

```sql
CONSTRAINT example_unique
UNIQUE (sort_order)
DEFERRABLE INITIALLY DEFERRED
```

Then a transaction may temporarily pass through an intermediate invalid state as long as the final transaction state satisfies the constraint.

Current PostgreSQL documentation identifies `UNIQUE`, `PRIMARY KEY`, `EXCLUDE`, and foreign-key constraints as supporting deferrability; `CHECK` and ordinary `NOT NULL` constraints are not deferrable. citeturn336142search18

---

# 18. Why Deferred Constraints Exist

Suppose an ordering system has:

```text
A sort_order = 1
B sort_order = 2
C sort_order = 3
```

You want:

```text
A → 2
B → 3
C → 1
```

A uniqueness constraint on `sort_order` might reject individual intermediate updates.

A deferrable uniqueness constraint can allow the transaction to temporarily contain duplicates while the final transaction state becomes valid.

This is not a hack.

It is a deliberate transaction-level modeling tool.

---

# 19. `INITIALLY IMMEDIATE` vs `INITIALLY DEFERRED`

### Initially immediate

The constraint is checked after each statement by default.

```sql
DEFERRABLE INITIALLY IMMEDIATE
```

### Initially deferred

The constraint is checked at transaction end by default.

```sql
DEFERRABLE INITIALLY DEFERRED
```

The mode can be changed for supported constraints with:

```sql
SET CONSTRAINTS constraint_name DEFERRED;
```

or:

```sql
SET CONSTRAINTS constraint_name IMMEDIATE;
```

The distinction is transaction behavior, not simply configuration syntax.

---

# 20. Deferred Constraint Example

```sql
CREATE TABLE task_positions (
    id bigint PRIMARY KEY,
    position integer NOT NULL,

    CONSTRAINT task_positions_position_unique
        UNIQUE (position)
        DEFERRABLE INITIALLY DEFERRED
);
```

Now a transaction can perform multiple changes before the final consistency check.

The mental model is:

```text
Immediate:
statement → validate

Deferred:
transaction work → validate final state
```

Use this deliberately. Deferrable constraints have performance and execution implications, and PostgreSQL notes that deferrable uniqueness can be significantly slower than immediate uniqueness checking in relevant cases. citeturn336142search1

---

# 21. Important `ON CONFLICT` Limitation

A subtle advanced point:

> A deferrable unique or primary-key constraint cannot be used as the conflict arbiter for an `INSERT ... ON CONFLICT DO UPDATE` operation.

This matters when developers try to combine:

```sql
UNIQUE ... DEFERRABLE
```

with:

```sql
INSERT ... ON CONFLICT DO UPDATE
```

Designing one feature can constrain another.

This is exactly why advanced schema design requires system-level reasoning rather than memorizing isolated features. citeturn336142search18

---

# 22. `EXCLUDE` Constraints

An exclusion constraint is one of PostgreSQL's most powerful advanced integrity features.

It is useful when ordinary equality-based uniqueness is not enough.

Conceptually:

> For each pair of rows, at least one specified comparison must be false or unknown.

This allows constraints over relationships such as:

```text
same room + overlapping reservation period
```

---

## 22.1 Example: no overlapping room reservations

A conceptual design can be:

```sql
CREATE TABLE room_reservations (
    room_id bigint NOT NULL,
    during tstzrange NOT NULL,

    CONSTRAINT room_reservations_no_overlap
        EXCLUDE USING gist (
            room_id WITH =,
            during WITH &&
        )
);
```

Meaning:

```text
same room
AND
overlapping time range
```

cannot both occur.

This is much stronger than trying to implement the rule as:

```text
SELECT overlap
INSERT row
```

because the constraint participates in database-level concurrency control.

---

# 23. Unique vs Exclusion Constraint

### Use `UNIQUE` when

The rule is equality-based:

```text
(tenant_id, sku) must be unique
```

### Use `EXCLUDE` when

The rule is about a combination of operators:

```text
same resource AND overlapping interval is forbidden
```

The distinction is conceptual:

```text
UNIQUE → no equal key values
EXCLUDE → no forbidden operator relationship between rows
```

---

# 24. Constraints and Concurrency

Constraints become especially important under concurrency.

Consider:

```text
Transaction A
Transaction B
```

Both may execute the same business workflow at nearly the same time.

Application-only code such as:

```sql
SELECT 1 FROM accounts WHERE external_id = 'X';
```

does not by itself prevent both transactions from attempting the same state transition.

Declarative uniqueness and referential constraints move the invariant into the database's concurrency-aware enforcement system.

This leads to an important design principle:

> A business rule that must remain true under concurrent writes should be enforced at a layer that participates in concurrency control.

---

# 25. Constraints vs Transactions

A common false choice is:

```text
constraint OR transaction
```

In strong systems, you often use both.

Example:

```text
Constraint:
Account email must be unique.

Transaction:
Create account + create profile + write audit event.
```

The transaction provides atomic state transition.

The constraint provides an invariant inside that transition.

They solve different problems.

---

# 26. Constraints vs Application Validation

Use both when appropriate.

### Application validation

Good for:

- user-friendly error messages;
- request shape validation;
- expensive pre-checks;
- UI feedback;
- domain workflows;
- avoiding unnecessary database round trips.

### Database constraints

Good for:

- final integrity enforcement;
- cross-client correctness;
- race prevention for supported invariants;
- durable business rules;
- relational consistency.

A mature application typically has:

```text
Validation layer
       ↓
Application/domain logic
       ↓
Transaction
       ↓
Database constraints
       ↓
Persistent valid state
```

---

# 27. Constraints as a Security Boundary

Constraints are not a replacement for authorization.

This is a common mistake.

A foreign key can say:

```text
order.customer_id must reference an existing customer
```

It cannot say:

```text
this authenticated employee is allowed to modify that customer
```

Likewise:

```sql
CHECK (amount >= 0)
```

does not answer:

```text
Who may set amount?
```

Therefore:

```text
Integrity ≠ Authorization
```

Both may be required.

---

# 28. Constraints and Business Rules

Not every business rule belongs in a constraint.

Use the following decision lens.

| Rule type | Typical best enforcement |
|---|---|
| Column cannot be null | `NOT NULL` |
| Numeric range | `CHECK` |
| Enum-like allowed values | `CHECK` / domain / enum depending on design |
| Unique business identifier | `UNIQUE` |
| Parent must exist | `FOREIGN KEY` |
| Dependent row deletion policy | FK action |
| No time overlap | `EXCLUDE` |
| Multi-step business workflow | Transaction + application/domain logic |
| Permission/authorization | Application + database security mechanisms |
| Cross-system invariant | Distributed workflow / coordination / reconciliation |
| Derived cache freshness | Projection/rebuild/reconciliation architecture |

The correct question is not:

> "Can SQL express this?"

It is:

> "What layer gives the strongest reliable enforcement with acceptable complexity?"

---

# 29. What Ordinary `CHECK` Constraints Should Not Pretend to Enforce

Avoid trying to make a normal row check behave like a general assertion mechanism over arbitrary database state.

For example, this requirement:

```text
Total active credit across all accounts for a customer <= 100000
```

is inherently cross-row.

A row-local `CHECK` is not the natural mechanism.

Depending on the invariant, you may instead need:

- transactional updates;
- locking;
- a serialized allocation row;
- a unique/exclusion constraint;
- trigger-based enforcement in carefully bounded cases;
- an immutable ledger with derived balance;
- an application-level workflow with reconciliation.

Do not force every rule into one feature.

---

# 30. Constraint Migrations

Constraints are easy to create on an empty table.

Production systems are different.

Suppose a table contains 500 million rows and you now decide:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_amount_positive
CHECK (amount > 0);
```

PostgreSQL may need to inspect existing rows before accepting the constraint as valid. The operational consequences matter.

---

# 31. `NOT VALID`

PostgreSQL supports adding certain constraints as `NOT VALID`, currently including foreign-key, `CHECK`, and not-null constraints in supported forms.

Conceptually:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_amount_positive
CHECK (amount > 0)
NOT VALID;
```

This can avoid an immediate full validation scan of all existing rows while the constraint still applies to subsequent inserts/updates. The constraint can later be validated with `VALIDATE CONSTRAINT`. citeturn336142search6

This is a major production migration technique.

---

# 32. Why `NOT VALID` Is Not "Ignore the Constraint"

A common misunderstanding is:

```text
NOT VALID = constraint disabled
```

Incorrect.

The useful mental model is:

```text
Existing historical rows:
    not yet proven valid

Future writes:
    must satisfy the constraint

Later:
    validate historical data
```

This gives you a path to gradually bring legacy data under stronger integrity rules.

---

# 33. Validation as a Migration Phase

A production-grade rollout might be:

```text
1. Discover existing violations
2. Repair legacy violations
3. Add constraint NOT VALID when useful
4. Deploy application changes
5. Validate the constraint
6. Remove temporary remediation paths
7. Monitor violation-free behavior
```

The exact lock and workload implications depend on the constraint and PostgreSQL operation. Current PostgreSQL documentation notes that adding most table constraints requires strong locking, while adding a foreign key uses a less restrictive lock mode on the declaring table but also locks the referenced table appropriately; plan migrations against your actual workload rather than assuming DDL is free. citeturn336142search6

# 34. Constraint Validation Is Data Quality Work

When a new constraint fails, the database is often telling you something valuable:

```text
The historical data does not satisfy the new model.
```

Do not immediately conclude:

> "The migration is broken."

Instead investigate:

```text
Is the rule correct?
Are old rows invalid?
Was the old business process incorrect?
Is there a legitimate legacy exception?
Should the schema model the exception?
```

Schema hardening often exposes latent data-quality debt.

# 35. Constraint Errors as Application Contracts

Suppose the database reports:



Still, application error handling should account for driver-specific error structures and version differences rather than treating raw database messages as a stable public API.

# 38. Constraint Introspection Pattern

A useful operational query is:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    con.conname AS constraint_name,
    con.contype AS constraint_type,
    con.convalidated AS validated,
    con.condeferrable AS deferrable,
    con.condeferred AS initially_deferred,
    con.conenforced AS enforced,
    pg_get_constraintdef(con.oid) AS definition
FROM pg_constraint AS con
JOIN pg_class AS c
    ON c.oid = con.conrelid
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, c.relname, con.conname;
```

This can become part of a schema-audit toolkit.

# 39. Constraint Design and Index Design

Constraints and indexes are related but not interchangeable.

Some constraints are implemented with indexes:

```text
PRIMARY KEY
UNIQUE
EXCLUSION
```

Other constraints do not automatically provide ordinary query indexes:

```text
CHECK
FOREIGN KEY on the child side
NOT NULL
```

Therefore:

> Constraint existence does not imply query performance.

The integrity model and access path model should be designed together.

# 40. Constraints and Query Planner Assumptions

Constraints provide semantic information about valid states, but planner behavior should not be guessed from a generic slogan such as:

> "The optimizer always knows this constraint."

PostgreSQL may exploit certain metadata for planning and optimization, but actual behavior depends on the constraint type, query form, statistics, version, and planner transformations.

Use:

```sql
EXPLAIN
EXPLAIN (ANALYZE, BUFFERS)
```

and authoritative documentation when validating planner assumptions.

# 41. Constraint Performance

Constraints have costs.

## 41.1 `NOT NULL`

Usually cheap because it is a direct value property.

## 41.2 `CHECK`

Adds expression evaluation during writes.

A cheap arithmetic check is different from a complex expression.

## 41.3 `UNIQUE`

Requires maintaining uniqueness structures and introduces index/write work.

## 41.4 `PRIMARY KEY`

Carries the costs of uniqueness and indexing plus relational importance.

## 41.5 `FOREIGN KEY`

Adds referential-integrity checks and can affect parent/child operations, especially under heavy write concurrency.

## 41.6 `EXCLUDE`

Can be more computationally involved because it compares operator relationships such as overlap.

The right question is:

> Is the integrity guarantee worth the write-path cost?

For critical invariants, the answer is often yes.

---

# 42. Constraint Cost vs Data Corruption Cost

A common optimization mistake is:

> "Constraints slow writes, so we should remove them."

That reasoning is usually incomplete.

Compare:

```text
Constraint cost:
small additional write work

No constraint:
possible corruption
↓
reconciliation
↓
incident response
↓
manual repair
↓
customer impact
↓
possible financial loss
```

Integrity is not a free performance feature, but correctness failures can be dramatically more expensive than the constraint overhead.

# 44. Common Developer Mistakes

## Mistake 1 — Application-only validation

```text
"We check it in NestJS."
```

Why it fails:

Other writers can bypass the rule and concurrency can create races.

Better:

Use application validation for UX plus a database constraint for integrity where appropriate.

---

## Mistake 2 — Forgetting `NOT NULL`

```sql
quantity integer CHECK (quantity > 0)
```

The developer forgets that `NULL` can pass the check.

Better:

```sql
quantity integer NOT NULL
    CHECK (quantity > 0)
```

when absence is invalid.

---

## Mistake 3 — Assuming a foreign key creates an index on the child

It does not automatically create the referencing-column index. citeturn336142search1

---

## Mistake 4 — Overusing `CASCADE`

A delete that should fail becomes a delete that destroys a graph of data.

---

## Mistake 5 — Using a `CHECK` for cross-row uniqueness

A row check is not a general concurrency-safe uniqueness mechanism.

Use the suitable relational constraint.

---

## Mistake 6 — Unnamed constraints

Unnamed generated identifiers make migrations and diagnostics harder.

---

## Mistake 7 — Creating constraints blindly on dirty legacy data

The migration fails because historical rows violate the desired rule.

The correct process is data-quality discovery followed by staged enforcement.

---

## Mistake 8 — Using deferrability without understanding transaction semantics

The developer creates a deferred constraint and later wonders why an invalid intermediate state was allowed.

---

## Mistake 9 — Treating constraints as authorization

Integrity is not access control.

---

## Mistake 10 — Disabling constraints to "fix" an incident

This may convert a visible failure into silent corruption.

A better incident response asks:

```text
What invariant is failing?
Why?
Can the bad input be isolated?
Can the data be repaired safely?
Can the workflow be corrected?
```

# 45. AI / Vibe-Coding Failure Modes

AI-generated schemas often contain technically valid SQL that is architecturally weak.

## Failure mode 1 — Every field becomes nullable

Typical output:

```sql
name text,
email text,
price numeric
```

Why it fails:

The schema encodes almost no domain guarantees.

---

## Failure mode 2 — Validation exists only in Zod/class-validator

The API is protected, but direct SQL and other services can create invalid states.

---

## Failure mode 3 — `UNIQUE` omitted because "we check before insert"

This fails under concurrency.

---

## Failure mode 4 — Every relation uses `ON DELETE CASCADE`

This creates destructive dependency graphs.

---

## Failure mode 5 — No named constraints

Operationally expensive when production errors appear.

---

## Failure mode 6 — Incorrect `NULL` assumptions

The generated code assumes a `CHECK` rejects nulls.

It does not necessarily do so.

---

## Failure mode 7 — Foreign keys everywhere without workload analysis

Relationships may be correct, but missing child-side indexes can make parent-side operations expensive.

---

## Failure mode 8 — Deferrable constraints treated as a performance optimization

They are primarily a correctness/timing mechanism and may carry additional overhead.

# 46. Production Jewellery ERP Example

Consider a simplified multi-tenant jewellery ERP.

```sql
CREATE TABLE tenants (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code text NOT NULL,

    CONSTRAINT tenants_code_unique
        UNIQUE (code)
);

CREATE TABLE products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    sku text NOT NULL,
    weight_grams numeric(12,3) NOT NULL,
    status text NOT NULL,

    CONSTRAINT products_tenant_fk
        FOREIGN KEY (tenant_id)
        REFERENCES tenants(id),

    CONSTRAINT products_tenant_sku_unique
        UNIQUE (tenant_id, sku),

    CONSTRAINT products_weight_positive
        CHECK (weight_grams > 0),

    CONSTRAINT products_status_valid
        CHECK (status IN ('active', 'inactive', 'archived'))
);
```

Notice how the schema itself now protects several invariants:

```text
tenant must exist
SKU unique within tenant
weight must be positive
status must be valid
required values cannot be null
```

The application still has domain logic, but the persistence boundary is no longer trusting every writer to remember every rule.

# 47. Constraint Design for Financial Data

Financial and inventory systems usually have stronger requirements than ordinary CRUD systems.

Example:

```sql
CREATE TABLE ledger_entries (
    id bigint PRIMARY KEY,
    account_id bigint NOT NULL,
    amount numeric(20,4) NOT NULL,
    entry_type text NOT NULL,

    CONSTRAINT ledger_amount_nonzero
        CHECK (amount <> 0),

    CONSTRAINT ledger_entry_type_valid
        CHECK (entry_type IN ('debit', 'credit'))
);
```

The constraint is not the entire accounting model.

It is one layer of a larger architecture containing:

- immutable event/ledger design;
- double-entry balancing;
- transactional posting;
- reconciliation;
- auditability;
- idempotency;
- authorization.

Constraint engineering should therefore be understood as one part of a correctness system.

# 48. Multi-Tenant Constraint Patterns

A frequent mistake is:

```sql
UNIQUE (sku)
```

when the real business rule is:

```text
SKU unique within tenant.
```

Correct:

```sql
UNIQUE (tenant_id, sku)
```

Similarly:

```sql
FOREIGN KEY (tenant_id)
REFERENCES tenants(id)
```

may establish tenant existence, but it does not by itself guarantee that every referenced object belongs to the same tenant.

This is a critical insight.

Suppose:

```text
orders.tenant_id = 1
orders.customer_id = customer from tenant 2
```

A foreign key to `customers(id)` may still be valid if the customer exists.

The FK proves existence, not necessarily **tenant-local ownership**.

Depending on the model, you may need composite keys or additional constraints to encode tenant consistency.

Example:

```sql
CREATE TABLE customers (
    tenant_id bigint NOT NULL,
    id bigint NOT NULL,

    PRIMARY KEY (tenant_id, id),

    FOREIGN KEY (tenant_id)
        REFERENCES tenants(id)
);
```

Then child references can use:

```sql
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, id)
```

This makes the tenancy boundary part of relational identity.

# 49. Constraint Design and Data Ownership

Ask:

> Who owns this row?

For dependent data, a foreign key answers structural ownership questions.

But business ownership may be richer:

```text
tenant
 branch
 customer
 order
 order_item
 payment
 ledger_entry
```

A strong schema should make invalid cross-boundary references difficult or impossible where the business model requires isolation.

This is especially important in multi-tenant systems because application-level tenant filtering is easy to forget.

Constraints can provide an additional structural defense.

# 51. `NOT ENFORCED` in PostgreSQL 18

PostgreSQL 18 supports `NOT ENFORCED` for `CHECK` and foreign-key constraints.

Conceptually:

```sql
CHECK (...) NOT ENFORCED
```

means the database does not perform the normal runtime enforcement for that supported constraint form.

This can be useful as schema documentation or in controlled migration/deployment strategies where immediate runtime checking is not appropriate, but it should never be confused with real integrity enforcement.

The PostgreSQL 18 documentation explicitly notes that `NOT ENFORCED` currently applies to `CHECK` and foreign-key constraints. citeturn336142search1turn336142search2

Production rule:

> Do not label a non-enforced rule as a correctness guarantee.

# 52. Strong vs Weak Invariants

It helps to classify invariants.

## Strong invariant

Must never be violated in the persistent database.

Examples:

```text
primary key uniqueness
foreign key existence
nonnegative amount
unique tenant SKU
```

These are excellent constraint candidates.

## Workflow invariant

Must be true at meaningful transaction boundaries but may involve temporary intermediate state.

Examples:

```text
moving a sequence of unique positions
posting a multi-row business operation
```

These may require transactions plus deferrable constraints.

## Cross-system invariant

Depends on other services or systems.

Examples:

```text
ERP stock matches warehouse device
payment status matches external provider
```

These generally need integration architecture and reconciliation rather than a simple database constraint.

# 53. Constraint Testing Strategy

Constraints should be tested directly.

## Test 1 — valid insert

```sql
INSERT INTO products (...)
VALUES (...);
```

Expected:

```text
success
```

## Test 2 — invalid insert

```sql
INSERT INTO products (... negative price ...);
```

Expected:

```text
constraint violation
```

## Test 3 — invalid update

The rule must protect updates, not just inserts.

## Test 4 — concurrent uniqueness

Run two transactions attempting the same business key.

Expected:

```text
one succeeds
one conflicts or follows ON CONFLICT logic
```

## Test 5 — parent deletion behavior

Verify the exact `ON DELETE` action.

## Test 6 — deferred behavior

For a deferrable constraint, verify:

```text
intermediate state
final state
commit behavior
```

## Test 7 — migration validation

For `NOT VALID`, verify both:

```text
future rows are checked
existing invalid rows remain until validation
```

# 57. Constraints and Idempotency

Constraints often become part of an idempotent design.

Suppose an external payment provider sends the same event twice.

You can establish:

```sql
UNIQUE (provider, provider_event_id)
```

Then duplicate delivery becomes a deterministic database event:

```text
first delivery → insert succeeds
retry           → unique conflict
```

Application logic can then safely treat the second delivery as already processed or invoke an idempotent upsert strategy.

Constraints are therefore useful not only for "bad data" but also for **safe retries**.

---

# 58. Constraints and Soft Deletes

A soft-delete model often looks like:

```sql
deleted_at timestamptz
```

Now consider:

```sql
UNIQUE (email)
```

Should deleted records still reserve the email?

There are multiple possible business rules.

### Rule A — deleted rows still reserve email

Ordinary uniqueness may be correct.

### Rule B — only active rows need unique email

A partial unique index may be more appropriate than a plain unique constraint:

```sql
CREATE UNIQUE INDEX users_active_email_unique
ON users(email)
WHERE deleted_at IS NULL;
```

This illustrates an important point:

> Not every integrity problem is solved by a table constraint alone; indexes can encode more specific uniqueness rules.

Do not confuse a unique index with a `UNIQUE` table constraint, even though both may enforce useful uniqueness behavior.

---

# 59. Constraints vs Partial Unique Indexes

Use a table `UNIQUE` constraint when the invariant naturally applies to all rows.

Use a partial unique index when the invariant applies only to a subset.

Example:

```text
Only active usernames must be unique.
```

Potential implementation:

```sql
CREATE UNIQUE INDEX users_active_username_unique
ON users(username)
WHERE status = 'active';
```

This is a more precise expression of the business rule than forcing every row into a global uniqueness model.

---

# 60. Constraints and Generated Data

Do not confuse a generated value with a guarantee.

Example:

```sql
id bigint GENERATED ALWAYS AS IDENTITY
```

This generates values, but identity generation itself is not a semantic substitute for the database uniqueness guarantee of a primary key or unique constraint.

General principle:

```text
Generation mechanism ≠ integrity constraint
```

# 61. Constraint Layering

A strong schema commonly layers multiple constraints.

Example:

```sql
CREATE TABLE invoice_items (
    id bigint PRIMARY KEY,
    invoice_id bigint NOT NULL,
    line_no integer NOT NULL,
    quantity numeric(12,3) NOT NULL,
    unit_price numeric(12,2) NOT NULL,

    CONSTRAINT invoice_items_invoice_fk
        FOREIGN KEY (invoice_id)
        REFERENCES invoices(id),

    CONSTRAINT invoice_items_line_unique
        UNIQUE (invoice_id, line_no),

    CONSTRAINT invoice_items_quantity_positive
        CHECK (quantity > 0),

    CONSTRAINT invoice_items_unit_price_nonnegative
        CHECK (unit_price >= 0)
);
```

Each constraint handles a distinct invariant.

That is better than a giant trigger or giant application validation function that silently owns every rule.

# 62. Constraint Granularity

A useful design principle is:

> One important invariant should have one clearly identifiable enforcement mechanism.

This does not mean literally one SQL object per rule in every situation, but your schema should make it obvious where the guarantee lives.

Avoid giant opaque constraints like:

```sql
CHECK (
    ... 300 lines of business logic ...
)
```

when the logic can be represented more clearly by:

```text
NOT NULL
CHECK
UNIQUE
FOREIGN KEY
transaction
application state machine
```

Clarity is part of correctness.

# 63. Constraint Composition

Constraints are most powerful when composed.

For example:

```text
NOT NULL
+ CHECK
+ UNIQUE
+ FOREIGN KEY
```

can define a precise domain:

```text
Product must exist
SKU must exist
SKU must be unique within tenant
Weight must be positive
Status must be from allowed set
Tenant must exist
```

Instead of storing informal assumptions in documentation, the schema becomes executable documentation.

# 64. When Not to Add a Constraint

A constraint should not be added merely because it sounds strict.

Question the rule when:

- the business explicitly allows exceptions;
- historical data intentionally contains legacy states;
- the rule changes frequently and belongs in workflow logic;
- the invariant spans systems;
- enforcement would be operationally disproportionate;
- the rule is advisory rather than mandatory.

Even then, document the decision.

The goal is not "maximum constraints."

The goal is:

> **Maximum justified integrity.**

# 65. Constraint Decision Framework

For every rule, ask these questions in order:

### 1. What exact invariant must hold?

Write it in plain language.

### 2. Is it row-local?

If yes, consider `NOT NULL` or `CHECK`.

### 3. Is it equality-based across rows?

Consider `UNIQUE`.

### 4. Is it relational existence?

Consider `FOREIGN KEY`.

### 5. Is it operator-based conflict detection?

Consider `EXCLUDE`.

### 6. Does it need temporary intermediate invalidity?

Consider `DEFERRABLE`.

### 7. Is historical data dirty?

Consider staged cleanup and `NOT VALID`/validation where supported.

### 8. Does it represent authorization?

Use the authorization/security layer, not only integrity constraints.

### 9. Does it span multiple systems?

Use distributed workflow and reconciliation mechanisms.

### 10. Can the rule be violated under concurrency if checked only in application code?

If yes, move the invariant closer to the database's concurrency-aware enforcement boundary.

# 66. Naive Approach → Why It Fails → Improved Approach

## Example: unique invoice number per branch

### Naive Approach

```ts
const existing = await repo.findOne({
  branchId,
  invoiceNumber,
});

if (existing) {
  throw new Error('Already exists');
}

await repo.insert({ branchId, invoiceNumber });
```

### Why It Fails

Two concurrent requests can both observe no row and then both attempt the insert.

### Improved Approach

```sql
ALTER TABLE invoices
ADD CONSTRAINT invoices_branch_invoice_no_unique
UNIQUE (branch_id, invoice_number);
```

### Why It Works

The invariant is enforced by the database itself.

### Production Considerations

- map unique violations to a domain error;
- decide whether retries are safe;
- use `ON CONFLICT` when appropriate;
- measure index/write costs;
- verify tenant/branch scope is part of the actual key.

### Alternative

A dedicated sequence/number-allocation workflow may be appropriate for stricter numbering requirements.

### Trade-Off

The constraint adds write/index overhead, but removes a critical race condition.

---

# 67. Naive Approach → Why It Fails → Improved Approach: Parent Deletion

### Naive Approach

```text
Delete parent
Then manually delete children
```

### Why It Fails

The dependency policy is duplicated in application code and may be forgotten by another writer.

### Improved Approach

Use an explicit foreign-key action:

```sql
ON DELETE CASCADE
```

or

```sql
ON DELETE RESTRICT
```

or

```sql
ON DELETE SET NULL
```

according to the business semantics.

### Production Considerations

Review deletion fan-out, locking, audit requirements, and whether the child has independent retention obligations.

---

# 68. Naive Approach → Why It Fails → Improved Approach: No Overlap

### Naive Approach

```sql
SELECT 1
FROM reservations
WHERE room_id = $1
  AND during && $2;
```

then insert.

### Why It Fails

Two transactions can both observe no overlap before either insert commits.

### Improved Approach

Use an exclusion constraint where the semantics match:

```sql
EXCLUDE USING gist (
    room_id WITH =,
    during WITH &&
)
```

### Why It Works

The conflict rule becomes a database-enforced invariant rather than an application race.

# 69. Production Debugging Workflow

When a constraint starts failing unexpectedly:

```text
1. Identify constraint name
2. Identify relation and columns
3. Capture failing operation
4. Classify violation
5. Determine whether it is expected or regression
6. Reproduce with minimal SQL
7. Inspect transaction/concurrency behavior
8. Check recent schema/application changes
9. Inspect affected data
10. Repair root cause
11. Add regression coverage
```

Do not disable the constraint first.

# 70. Evidence-Driven Constraint Debugging

Suppose the production error says:

```text
violates foreign key constraint "orders_customer_fk"
```

Do not immediately write:

> "Customer creation is broken."

Collect evidence:

```sql
SELECT *
FROM orders
WHERE customer_id = $1;
```

Then investigate:

```sql
SELECT *
FROM customers
WHERE id = $1;
```

Then inspect transaction ordering, deletes, retries, tenant scope, and application logs.

The error identifies the violated invariant, not automatically the root cause.

# 73. Master Mental Model

Think of constraints as a hierarchy of increasingly expressive integrity rules.

```text
NOT NULL
   ↓
Basic value presence

CHECK
   ↓
Value / row-local invariants

UNIQUE
   ↓
Cross-row equality uniqueness

PRIMARY KEY
   ↓
Primary relational identity

FOREIGN KEY
   ↓
Cross-table existence/integrity

EXCLUDE
   ↓
Operator-based conflict rules

DEFERRABLE
   ↓
Control WHEN certain supported invariants are checked

Transaction / domain logic
   ↓
Multi-step state transitions

Distributed architecture
   ↓
Cross-system invariants
```

This hierarchy prevents both under-engineering and over-engineering.

# 74. Expert-Level Questions

You should be able to answer these without memorized slogans.

### Q1. Why can a `CHECK` constraint allow `NULL`?

Because the expression can evaluate to `UNKNOWN`, and PostgreSQL treats `TRUE` or `UNKNOWN` as satisfying the check. citeturn336142search1

### Q2. Why is a unique constraint still necessary when the API checks first?

Because the pre-check is race-prone under concurrency.

### Q3. Why isn't a foreign key enough for fast parent-side deletes?

Because the child-side referencing columns do not automatically receive a supporting index. Workload may require one. citeturn336142search1

### Q4. When would you use `EXCLUDE` instead of `UNIQUE`?

When the forbidden relationship is not simple equality, such as overlapping time ranges.

### Q5. Why use `DEFERRABLE`?

To allow supported constraints to be checked at transaction time rather than forcing every intermediate statement to satisfy the final invariant.

### Q6. Why can `NOT VALID` be operationally useful?

It lets supported constraints be introduced without immediately validating all existing rows, while still enforcing the rule for subsequent changes; later validation can establish that existing data also complies. citeturn336142search6

### Q7. Why aren't constraints an authorization system?

They describe legal data states, not who is permitted to perform a state transition.

### Q8. Why can a foreign key fail to enforce tenant ownership?

Because referencing an existing row proves existence, not necessarily that both rows share the same tenant boundary.

### Q9. What does a good constraint name buy you?

Operational visibility, easier debugging, reliable migration targeting, and clearer application error mapping. citeturn336142search1

### Q10. When should you reject adding a constraint?

When the rule is not actually an invariant, belongs to another architectural layer, or requires an exception model that the proposed constraint would incorrectly forbid.

# 77. Production Readiness Checklist

Before shipping a production schema, ask:

### Integrity

- Are mandatory columns explicitly `NOT NULL`?
- Are important value invariants represented with `CHECK`?
- Are business keys protected with the correct uniqueness rule?
- Are foreign keys defined where referential integrity matters?
- Are cross-tenant relationships structurally safe?
- Are overlap/conflict rules modeled with appropriate constraints?

### Semantics

- Have `NULL` semantics been explicitly decided?
- Are composite keys actually representing the intended business identity?
- Are `CASCADE`, `SET NULL`, and `RESTRICT` choices intentional?
- Are any rules incorrectly implemented as application-only checks?

### Concurrency

- Can two concurrent writes violate the business rule?
- Does the chosen constraint participate in preventing that race?
- Is deferral actually necessary?
- Are retry/idempotency paths tested?

### Performance

- Are supporting indexes present where workload requires them?
- Has write amplification been considered?
- Have high-cardinality parent operations been tested?
- Have realistic `EXPLAIN`/lock measurements been performed?

### Migrations

- Is existing data already valid?
- Is staged validation required?
- Would `NOT VALID` be useful for the supported constraint type?
- What locks will the DDL acquire?
- What is the rollback/remediation plan?

### Operations

- Are constraints explicitly named?
- Can the application classify constraint violations?
- Are failures observable by constraint name?
- Is there documentation for important business invariants?

### Security

- Are integrity guarantees being confused with authorization?
- Are tenant boundaries protected structurally where appropriate?
- Are destructive cascades reviewed?

# 78. Final Principle

A database constraint is not merely SQL syntax.

It is a **promise encoded into the persistence layer**:

```text
This state is legal.
That state is not.
```

The strongest database designs do not rely on every programmer remembering every rule forever. They encode critical invariants close to the data, choose the correct constraint semantics, account for concurrency, understand constraint timing, plan migrations deliberately, and measure operational consequences.

The goal is not to put every business rule into a constraint.

The goal is to ensure that every important invariant has a **clear, deliberate, concurrency-safe enforcement owner**.

A useful final mental model is:

```text
Validation improves input quality.

Transactions protect atomic state transitions.

Constraints protect persistent invariants.

Indexes make access efficient.

Security controls who may act.

Distributed workflows protect cross-system consistency.

Reconciliation detects what escaped the boundaries.
```

Production-grade PostgreSQL engineering comes from understanding all of these layers and assigning each rule to the one that can enforce it most reliably.
