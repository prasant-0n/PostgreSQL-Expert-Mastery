# 02.9 — Schema Evolution & Migration Strategy

> **Phase 02 — Relational Data Modeling**  
> A production-grade guide to evolving live PostgreSQL schemas without treating production as an empty development database.

---

## 1. Chapter Objective

A schema is never finished. Production systems continuously change: fields become mandatory, relationships evolve, tables grow, business rules become stricter, data types are corrected, indexes are added, entities are split, and obsolete representations are retired.

The hard problem is not writing `ALTER TABLE`. The hard problem is changing the database's legal state while application servers, workers, reports, replicas, ETL jobs, CDC consumers, and older application versions may still be active.

The central question is:

> **How do we move from schema state A to schema state B through controlled, observable, recoverable intermediate states?**

A production migration should be treated as:

```text
Requirement
    ↓
Current State
    ↓
Dependency Discovery
    ↓
Compatibility Design
    ↓
Expand
    ↓
Backfill / Migrate
    ↓
Validate / Reconcile
    ↓
Switch Reads / Writes
    ↓
Contract
    ↓
Observe
```

---

# 2. Three Levels of Definition

## 2.1 Simple definition

A migration is a controlled change to database structure or database behavior.

Examples:

```text
add column
add index
add constraint
rename column
split table
change data type
remove obsolete field
```

## 2.2 Engineering definition

A migration is a versioned change that moves a database between supported schema states while coordinating application compatibility, data transformation, integrity, and operational risk.

## 2.3 Expert definition

A production schema migration is a **state transition protocol over a live distributed system**.

The database participates in a larger graph:

```text
Database
├── API servers
├── background workers
├── admin tools
├── reports
├── ETL / ELT
├── CDC consumers
├── read replicas
├── external integrations
└── older application binaries
```

Consequently, schema evolution is simultaneously a database, deployment, concurrency, data-correctness, and observability problem.

---

# 3. First Principle: Schema Evolution Is a State Machine

Imagine the old design:

```text
orders
------
id
customer_name
```

and the desired design:

```text
orders
------
id
customer_id
```

The unsafe mental model is:

```text
old schema → new schema
```

The stronger model is:

```text
State A
old representation only

    ↓ expand

State B
old + new representation

    ↓ dual-write / backfill

State C
both populated

    ↓ reconcile

State D
new representation authoritative

    ↓ contract

State E
new representation only
```

Every intermediate state should have an explicit correctness contract.

---

# 4. Expand–Migrate–Contract

The default pattern for many compatibility-sensitive changes is:

```text
EXPAND
→ add compatible structure

MIGRATE
→ populate new state
→ change application behavior
→ validate

CONTRACT
→ remove obsolete state
```

### Expand

Introduce the new schema without immediately breaking existing consumers.

### Migrate

Backfill historical rows and gradually move reads/writes.

### Contract

Remove old columns, tables, indexes, or constraints only after proving they are no longer required.

This pattern is especially useful for rolling and blue-green deployments where multiple application versions can coexist.

---

# 5. Why Destructive-First Migrations Fail

Bad sequence:

```sql
ALTER TABLE users DROP COLUMN name;
```

followed by a deployment that expects the replacement.

During a rolling deployment, an old process may still execute:

```sql
SELECT name FROM users;
```

and fail.

A safer sequence is:

```text
add replacement
→ deploy compatibility
→ migrate data
→ migrate reads
→ stop old writes
→ remove old field later
```

The schema should normally remain compatible with the old application until the old application has disappeared.

# 6. Migration Risk Classification

| Change | Typical Risk |
|---|---|
| Add nullable column | Low, usually |
| Add index concurrently | Moderate operational cost |
| Add constraint as `NOT VALID` | Moderate |
| Validate large constraint | Moderate / high |
| Add mandatory field to populated table | Potentially high |
| Large data rewrite | High |
| Change data type | Potentially high |
| Rename column | High compatibility risk |
| Drop column | High compatibility risk |
| Split table | High |
| Merge tables | High |
| Existing-table repartitioning | High |
| Rewrite business semantics | Very high |

Important:

> **Small SQL does not imply small operational impact.**

# 9. Dependency Graph Thinking

A column may participate in many systems:

```text
orders.customer_name
      ├── API response
      ├── report
      ├── export
      ├── background job
      └── external integration
```

Dropping the column removes the capability from every consumer.

Therefore ask:

> **Who reads this? Who writes this? Who assumes its shape? Who receives its output?**

# 10. Additive Changes Are Usually Easier

Example:

```sql
ALTER TABLE users
ADD COLUMN preferred_language text;
```

This is typically safer than removing an existing field because old versions can ignore the new column.

But still verify:

```text
default behavior
rewrite behavior
lock behavior
row size
index requirements
ORM behavior
application serialization
```

Current PostgreSQL documentation makes clear that the required lock depends on the exact `ALTER TABLE` form rather than the phrase `ALTER TABLE` itself. citeturn528289search0

---

# 11. Version-Sensitive Migration Behavior

Do not memorize rules such as:

> “Adding a default always rewrites the table.”

PostgreSQL behavior has evolved across versions.

The correct workflow is:

```text
identify target PostgreSQL version
→ inspect current documentation
→ reproduce on staging
→ measure on representative data
→ execute with monitoring
```

The current PostgreSQL 18 documentation should be treated as authoritative for PostgreSQL 18 behavior. citeturn528289search5

---

# 12. Backfills Are Separate Production Workloads

Suppose we add:

```sql
ALTER TABLE orders
ADD COLUMN normalized_total numeric;
```

Then a historical migration might run:

```sql
UPDATE orders
SET normalized_total = old_total;
```

That statement can touch millions of rows.

It can therefore create:

```text
WAL growth
→ replica lag
→ dead tuples
→ vacuum pressure
→ IO spikes
→ cache churn
→ longer recovery
```

Treat the data movement as an independent workload.

---

# 13. Chunked Backfills

Prefer bounded units of work for large tables.

Example:

```sql
UPDATE orders
SET normalized_total = old_total
WHERE id > $1
  AND id <= $2
  AND normalized_total IS NULL;
```

The exact batch size depends on:

```text
row width
index count
storage performance
CPU
WAL budget
replica capacity
transaction duration target
```

Do not choose a batch size because a blog post used it.

Measure.

---

# 14. Idempotent Backfills

A production migration must tolerate interruption.

Prefer:

```sql
WHERE normalized_total IS NULL
```

or another explicit progress predicate so repeated execution is safe.

The desired property is:

```text
failed halfway
    ↓
restart
    ↓
already-completed work remains correct
```

Idempotency converts failures into resumable states.

---

# 15. Stable Progress Tracking

For large migrations, track a monotonic cursor such as:

```text
last_processed_id
```

or a migration-specific checkpoint.

Avoid repeatedly scanning the entire table just to discover what remains.

A migration runner may record:

```text
migration
phase
last_key
rows_processed
started_at
updated_at
status
last_error
```

Now operational progress becomes inspectable instead of implicit.

---

# 16. Backfill Correctness Under Concurrent Writes

Suppose an application changes a row while the backfill is running.

The key question becomes:

> **Which value is authoritative?**

Possible approaches:

### Dual-write first

New mutations maintain both representations before historical data is backfilled.

### Database trigger synchronization

A trigger keeps old and new representations aligned during the transition.

### Immutable source derivation

The new field is deterministically reconstructed from authoritative facts rather than copied from another mutable cache.

Choose based on the domain and transaction model.

---

# 17. Never Use “Check Then Update” Without Race Analysis

Risky pattern:

```text
1. SELECT row
2. compute decision
3. UPDATE later
```

The row can change between steps.

Prefer operations whose correctness is evaluated by the database at mutation time, for example:

```sql
UPDATE orders
SET normalized_total = old_total
WHERE id = $1
  AND normalized_total IS NULL;
```

For more complex migrations, use version markers or authoritative-source rules.

---

# 18. Adding Constraints to Existing Data

Suppose the new rule is:

```text
customer_id may no longer be NULL
```

but historical rows violate it.

The safe process is usually:

```text
measure violations
→ repair data
→ introduce enforcement
→ validate historical rows
→ tighten permanently
```

Integrity strengthening is partly a data-cleaning task.

---

# 19. `NOT VALID` as a Staged Integrity Tool

For supported constraints, PostgreSQL can separate enforcement of new writes from validation of existing rows.

Conceptually:

```text
new rows
→ must obey constraint

existing rows
→ validated later
```

Example:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id)
REFERENCES customers(id)
NOT VALID;
```

Later:

```sql
ALTER TABLE orders
VALIDATE CONSTRAINT orders_customer_fk;
```

PostgreSQL documents `NOT VALID` specifically as a way to avoid scanning existing rows during initial constraint creation and then validate historical rows separately. citeturn528289search0

---

# 20. `NOT VALID` Is Not Permanent Data Corruption

Do not interpret:

```text
NOT VALID
```

as:

```text
constraint does not matter
```

It is an intermediate state.

A complete migration should eventually prove:

```text
historical rows valid
+
new writes enforced
```

The validation step is part of the migration's definition of done.

---

# 21. Safe Foreign-Key Introduction

For a large existing child table:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id)
REFERENCES customers(id)
NOT VALID;
```

Then discover and repair orphans before validation.

Finally:

```sql
ALTER TABLE orders
VALIDATE CONSTRAINT orders_customer_fk;
```

This can reduce blocking compared with requiring a full historical validation during the initial `ADD CONSTRAINT`. citeturn528289search0

---

# 22. Building Large Indexes

A conventional index build can interfere with writes on a live table.

For appropriate production cases:

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer_id
ON orders(customer_id);
```

`CONCURRENTLY` allows ordinary table operations to continue while the index is built, but requires additional work and takes longer. It also cannot run inside a transaction block. citeturn528289search1turn528289search12

Migration framework implication:

```text
not every migration can safely be wrapped in BEGIN/COMMIT
```

---

# 23. Migration Runners Must Understand Transaction Semantics

Do not assume:

```text
BEGIN
run every migration statement
COMMIT
```

is universally correct.

A serious migration system should understand:

```text
transactional migrations
non-transactional operations
lock_timeout
statement_timeout
retryable errors
advisory coordination
progress tracking
```

Migration infrastructure is production infrastructure.

---

# 24. Renames Are Compatibility Changes

A direct rename:

```sql
ALTER TABLE users
RENAME COLUMN name TO display_name;
```

changes the identifier immediately.

During rolling deployment, old processes may still query `name`.

Safer general strategy:

```text
add display_name
→ dual-write
→ migrate reads
→ stop name writes
→ remove name later
```

Direct rename is reasonable when all consumers are tightly controlled and deployment is effectively atomic.

---

# 25. Adding a New Required Column

Suppose every invoice must have:

```text
branch_id
```

Do not blindly start with:

```sql
ALTER TABLE invoices
ADD COLUMN branch_id bigint NOT NULL;
```

First answer:

```text
Can historical rows be assigned deterministically?
What should unknown mean?
Can new application writes populate it?
Are all existing rows repairable?
```

A common staged approach:

```text
add nullable field
→ backfill
→ add FK
→ enforce application writes
→ validate
→ enforce NOT NULL
```

---

# 26. Splitting a Table Safely

Initial:

```text
users
-----
id
email
name
phone
preferences
```

Target:

```text
users
-----
id
email
name

user_profiles
-------------
user_id
phone
preferences
```

Safe transition:

```text
create user_profiles
→ backfill
→ dual-write
→ reconcile
→ switch reads
→ stop old writes
→ contract old columns
```

Do not confuse structural elegance with operational necessity.

---

# 27. Merging Tables Has Different Failure Modes

A merge can produce:

```text
wider rows
more NULLs
larger hot tuples
security coupling
update contention
lifecycle coupling
```

Before merging, ask:

```text
Do these facts share lifecycle?
Do they share access patterns?
Do they share authorization?
Are they updated together?
Will row size increase materially?
```

---

# 28. Data Type Changes

A type change should be analyzed for both logical and physical effects.

Example:

```sql
ALTER TABLE accounts
ALTER COLUMN balance TYPE numeric(20,2);
```

Questions:

```text
Is conversion lossless?
Can every value fit?
Will the table be rewritten?
What locks are acquired?
What indexes are affected?
Are dependent objects compatible?
Will API serialization change?
```

Test with representative data before production.

---

# 29. Table Rewrite Awareness

Some operations can rewrite table storage.

Potential consequences include:

```text
large IO load
high WAL activity
extra disk requirements
cache disruption
replication lag
long operation time
```

PostgreSQL documents that table and index rebuilds on large relations may take significant time and can require substantial temporary disk space. citeturn528289search0

Estimate:

```text
heap size
index size
free disk
WAL capacity
replica replay capacity
maintenance window
```

---

# 30. Locking Is Part of the Design

For every DDL operation determine:

```text
lock level
lock acquisition point
potential blockers
expected duration
behavior under contention
failure/timeout behavior
```

Current PostgreSQL documentation explicitly notes that `ALTER TABLE` subforms can require different locks and that combined alterations use the strictest lock required by the group. citeturn528289search0

Therefore:

> **“It is just an ALTER TABLE” is not an operational analysis.**

---

# 31. Lock Timeouts

Migration sessions should have bounded waiting where operationally appropriate.

Example:

```sql
SET lock_timeout = '2s';
SET statement_timeout = '15min';
```

The values are workload-specific.

The principle is:

```text
cannot acquire lock quickly
→ fail safely
→ retry intentionally
```

instead of:

```text
wait indefinitely
→ request backlog
→ cascading incident
```

---

# 32. Deadlock Awareness

Migration work can participate in deadlocks with application transactions.

For example:

```text
Transaction A: locks users → wants orders
Migration:    locks orders → wants users
```

A production test should include realistic concurrency.

An idle staging database cannot reveal all lock interactions.

---

# 33. Rollback Is Bigger Than SQL ROLLBACK

Distinguish:

```text
transaction rollback
```

from:

```text
migration rollback
```

A migration may already have:

```text
backfilled rows
changed application behavior
emitted events
updated external systems
created files
changed downstream state
```

A database `ROLLBACK` cannot undo external side effects.

Plan recovery at system level.

---

# 34. Forward-Only Migrations

Some migrations should deliberately be forward-only.

Suppose:

```text
old = free-form name
new = normalized structured identity
```

The new representation may contain information that cannot be reconstructed perfectly into the old form.

Therefore:

```text
schema reversible
≠
business state reversible
```

A roll-forward path may be safer than a destructive down migration.

---

# 35. Shadow Tables

For high-risk transformations:

```text
old representation
        ↓
shadow/new representation
```

Then:

```text
writes → both
reads → old
compare → old vs new
cutover → new
```

This is useful when:

```text
transformation is complex
downtime is unacceptable
rollback is expensive
correctness is critical
```

The price is extra storage, write complexity, and operational machinery.

---

# 36. Dual Writes

Dual-write means:

```text
one business mutation
├── old representation
└── new representation
```

Failure modes include:

```text
old succeeds / new fails
new succeeds / old fails
partial application failure
retry divergence
cross-service inconsistency
```

Keeping both writes in one PostgreSQL transaction provides much stronger consistency than sending them to unrelated systems.

Dual-write should be temporary migration infrastructure, not an excuse for permanent duplicated truth.

---

# 37. Source of Truth Must Be Explicit

During migration you may have:

```text
old_field
new_field
```

State exactly which one is authoritative in each phase.

Example:

```text
Phase 1 → old authoritative
Phase 2 → both synchronized
Phase 3 → new authoritative
Phase 4 → old removed
```

Without this contract, reconciliation becomes ambiguous.

---

# 38. Reconciliation Queries Are Proof

Do not stop at:

```text
migration completed
```

Create proof queries.

Example:

```sql
SELECT count(*)
FROM orders
WHERE old_value IS DISTINCT FROM new_value;
```

Other useful checks:

```sql
SELECT count(*)
FROM orders
WHERE new_id IS NULL;
```

and:

```sql
SELECT count(*)
FROM orders o
LEFT JOIN customers c ON c.id = o.customer_id
WHERE o.customer_id IS NOT NULL
  AND c.id IS NULL;
```

The migration's definition of done should be measurable.

# 39. Four Layers of Verification

## Layer 1 — Structural

```text
column exists
index exists
constraint exists
expected type exists
```

## Layer 2 — Data

```text
row counts
null counts
mismatch counts
orphan counts
duplicate counts
```

## Layer 3 — Behavioral

```text
new writes work
old-compatible reads work during transition
business operations remain correct
```

## Layer 4 — Operational

```text
latency
errors
replica lag
locks
WAL
CPU
IO
disk
```

A green migration command is not enough.

---

# 40. Replica Lag Is a Migration Signal

A backfill may succeed on primary while replicas fall behind:

```text
large updates
→ WAL generated
→ replay capacity insufficient
→ lag increases
```

Consequences can include:

```text
stale reads
failover risk
replica overload
user-visible inconsistency
```

Therefore define operational thresholds before execution.

---

# 41. Adaptive Batch Sizing

Fixed row counts do not always produce fixed workload.

For example:

```text
10,000 narrow rows
```

and:

```text
10,000 wide rows + 8 indexes
```

can have dramatically different costs.

An adaptive system can target a transaction-duration or resource budget rather than a universal row count.

Measure and tune.

---

# 42. New Indexes Increase Backfill Cost

Suppose you:

```text
add column
add index on column
backfill every row
```

Every updated row may also cause index maintenance.

Thus:

```text
backfill cost
≈ heap work
+ index work
+ WAL
+ vacuum/recovery effects
```

Where safe, index creation timing can be separated from the data movement phase.

But never remove a required index merely to make a migration faster.

---

# 43. Constraint Ordering

Dependencies create ordering requirements.

Example:

```text
new table
↓
copy data
↓
create supporting unique index
↓
create foreign key
↓
validate
↓
switch consumers
```

The general rule is:

> **Introduce a dependent invariant only after its prerequisites exist.**

---

# 44. Dropping a Column Is a Contract Operation

Before:

```text
old application → old column
new application → old column
```

After:

```text
column no longer exists
```

Before dropping, prove:

```text
no application reads
no application writes
no views depend on it
no functions depend on it
no ETL depends on it
no external consumer depends on it
```

Also remember that a dropped column does not necessarily mean immediate physical disk reclamation; PostgreSQL documents that the column can become logically invisible before its physical space is reclaimed. citeturn528289search0

---

# 45. Rename vs Add-and-Migrate

### Direct rename

Appropriate when:

```text
all consumers are controlled
old binaries cannot coexist
no uncontrolled external consumer exists
```

### Add-and-migrate

Prefer when:

```text
rolling deployments exist
workers are long-lived
multiple services are involved
external consumers exist
availability requirements are high
```

The second costs more but protects compatibility.

---

# 46. Enum and Domain Evolution

When introducing a new valid state:

```text
schema supports it
→ application understands it
→ traffic begins using it
```

Do not create a state in production before the application can safely process it.

The reverse problem also matters when removing states: first stop generating them, then prove no existing data depends on them, then contract the schema.

---

# 47. Tightening CHECK Constraints

Suppose the current rule is:

```sql
CHECK (status IN ('draft', 'posted'))
```

and the new rule adds:

```text
cancelled
```

or later removes `draft`.

Treat this as a compatibility sequence:

```text
introduce application semantics
→ adjust database rule
→ migrate existing values
→ stop old behavior
→ contract
```

Strengthening constraints is both schema evolution and data migration.

---

# 48. Partitioning as Schema Evolution

Migrating an existing table toward partitioning involves more than declaring partitions.

Review:

```text
partition key
existing data placement
partition constraints
indexes
unique constraints
foreign keys
query plans
write routing
default partition
cutover
rollback
```

Current PostgreSQL 18 documentation also documents `DETACH PARTITION CONCURRENTLY` for reduced blocking in supported cases, with specific limitations and multi-transaction behavior. citeturn528289search0

---

# 49. ORM-Generated Migrations

ORM migrations are useful but can be operationally naive.

Common issues:

```text
rename represented as drop + add
unexpected table rewrite
huge transaction
blocking index build
constraint added without staging
```

Rule:

> **Review generated migration SQL as infrastructure code.**

The ORM understands the model diff. It does not automatically understand your production workload.

---

# 50. Node.js / NestJS Migration Discipline

Do not casually make every application instance execute migrations during startup in a horizontally scaled deployment.

Potential problems:

```text
startup races
migration lock contention
application startup blocked by long migration
multiple instances competing
hard-to-debug deployment failures
```

A cleaner production separation is often:

```text
CI/CD or dedicated migration job
        ↓
execute migration
        ↓
verify
        ↓
deploy application
```

Exact orchestration depends on infrastructure, but migration execution should be treated as a first-class deployment stage.

---

# 51. Separate DDL From Large Data Jobs

A robust architecture often separates:

```text
Migration A
schema expansion

Job B
large backfill

Migration C
constraint validation/enforcement

Job D
cleanup

Migration E
contract old schema
```

Benefits:

```text
bounded blast radius
independent retries
throttling
better observability
clearer rollback strategy
```

---

# 52. Retry Semantics

Classify failures.

| Failure | Typical Handling |
|---|---|
| lock timeout | Retry intentionally |
| deadlock | Retry can be appropriate |
| serialization failure | Retry can be appropriate |
| unique violation | Investigate data/model |
| FK violation | Investigate migration invariant |
| syntax error | Fix migration code |
| unexpected data conversion | Stop and investigate |

Blindly retrying all errors is dangerous.

---

# 53. Advisory Locks for Coordination

When multiple orchestration processes may run the same migration, database-level coordination can help.

Conceptually:

```text
runner A
   ↓
migration coordination lock
   ↓
execute

runner B
   ↓
wait or exit
```

Advisory locks coordinate actors that use the same protocol. They do not replace migration correctness or monitoring.

---

# 54. Rolling / Blue-Green Compatibility

A typical sequence is:

```text
old application
      ↓
expand schema
      ↓
old + new application coexist
      ↓
new application becomes dominant
      ↓
old behavior removed
      ↓
contract schema
```

This is why additive schema changes are such a valuable foundation for continuous delivery.

---

# 55. Backward and Forward Compatibility

### Backward compatible

Old application can operate against the intermediate schema.

### Forward compatible

New application can operate against the intermediate schema before every old consumer is gone.

For safe rolling deployment, both directions often matter.

---

# 56. API Versioning and Database Evolution

Do not let physical database column names become accidental public API contracts.

Use layers:

```text
Database representation
        ↕
Domain/service model
        ↕
API contract
```

This allows the database to evolve without forcing an immediate external API break.

---

# 57. Security During Migrations

Migration credentials are usually highly privileged.

Protect:

```text
credentials
migration logs
SQL scripts
temporary exports
backups
CI/CD secrets
```

Never print sensitive row contents merely to inspect progress.

For multi-tenant systems, every tenant-specific migration should make its scope explicit and should have validation queries proving that rows outside intended scope were untouched.

---

# 58. Multi-Tenant Backfills

For shared-table SaaS:

```text
global schema expansion
→ tenant-scoped backfill
→ throttle
→ reconcile per tenant
→ global validation
```

A very large tenant can create disproportionate load.

Useful controls include:

```text
tenant batching
priority classes
per-tenant rate limits
pause/resume
tenant-level progress
```

Migration correctness includes tenant isolation.

---

# 59. Migration Observability

At minimum track:

```text
start / end time
rows processed
rows remaining
batch duration
lock waits
replica lag
WAL rate
CPU
IO
disk
application error rate
```

For long-running index operations, PostgreSQL exposes progress information through `pg_stat_progress_create_index`. citeturn528289search6

The goal is to turn:

```text
migration running
```

into:

```text
migration state is measurable
```

# 60. Auditability

For important migrations, retain evidence:

```text
migration identifier
operator / deployment
start time
end time
scope
verification results
errors
final status
```

For complex data migrations, preserve the runbook and metrics used to decide that the operation was safe to continue.

# 61. Testing Strategy

Test more than a clean local database.

Include:

```text
empty database
small realistic data
large synthetic data
historical violations
concurrent writes
long transactions
old application version
new application version
interrupted backfill
retry after failure
replica lag
```

The most valuable test environment is often production-sized data with production-like concurrency.

# 62. Failure Injection

Interrupt deliberately:

```text
mid-batch
mid-backfill
while blocked on a lock
after partial validation
before cutover
between dual-write phases
```

Then prove:

```text
Can we resume?
Can we detect partial state?
Can we reconcile?
Can we roll forward safely?
```

A mature migration treats interruption as an expected scenario.

---

# 63. Migration Invariants

Before implementation, write the rules.

Example:

```text
Before:
customer_name is authoritative.

During:
customer_id is populated for every migrated row.
customer_name remains readable.

After:
customer_id is authoritative.
customer_name has no active consumers.
```

Then write SQL queries that prove each invariant.

This changes migration development from “write commands” into “prove state transitions.”

# 65. Common Anti-Patterns

## Anti-pattern 1 — One giant migration

```text
DDL + huge update + index creation + constraint validation + cleanup
```

### Why it fails
Large blast radius and poor recovery characteristics.

### Better
Separate structural changes, data movement, validation, and cleanup.

---

## Anti-pattern 2 — Destructive first

```sql
DROP COLUMN old_value;
ADD COLUMN new_value;
```

### Why it fails
Old application versions break.

### Better
Expand → migrate → switch → contract.

---

## Anti-pattern 3 — ORM SQL without review

### Why it fails
Generated SQL does not know your table size, lock budget, replica capacity, or external consumers.

### Better
Review the SQL and test it on representative data.

---

## Anti-pattern 4 — Unthrottled backfill

### Why it fails
A data migration becomes an uncontrolled production workload.

### Better
Bound batches and monitor system health.

---

## Anti-pattern 5 — No reconciliation

### Why it fails
Migration completion is mistaken for data correctness.

### Better
Define and run proof queries.

---

## Anti-pattern 6 — Permanent dual-write

### Why it fails
Two representations become competing sources of truth.

### Better
Use dual-write as temporary transition infrastructure and define a contract phase.

---

## Anti-pattern 7 — “Down migration” as the whole rollback plan

### Why it fails
External effects and non-lossless transformations may be impossible to reverse.

### Better
Design roll-forward and recovery explicitly.

---

# 66. AI / Vibe-Coding Migration Failures

AI-generated migrations often optimize for syntactic correctness instead of production state transitions.

## Failure 1 — Immediate destructive change

```sql
DROP COLUMN old;
```

The model sees the destination but ignores mixed-version deployment.

## Failure 2 — Assuming DDL is cheap

```sql
ALTER TABLE ...
```

is treated as an instantaneous operation without evaluating lock/rewrite behavior.

## Failure 3 — Giant backfill

```sql
UPDATE huge_table SET ...;
```

The source code is short while the workload is enormous.

## Failure 4 — No concurrent index strategy

Index creation can interfere with production writes when implemented naively.

## Failure 5 — Non-idempotent migration

Restarting may repeat work or produce inconsistent data.

## Failure 6 — No mixed-version test

Only the newest application is validated even though old workers still run.

## Failure 7 — No tenant scoping

A tenant-specific backfill accidentally affects every tenant.

## Failure 8 — No proof queries

The migration relies on logs saying “success” instead of verifying invariants.

Expert question for AI-generated SQL:

> **“What intermediate production states does this migration assume?”**

# 67. Production Scenario: Customer Identity Refactor

Initial:

```text
customers
---------
id
name
phone
```

Target:

```text
customers
---------
id

customer_profiles
-----------------
customer_id
name
phone
```

Migration protocol:

```text
1. Create customer_profiles
2. Backfill existing customers
3. Enable compatible dual-write
4. Reconcile old vs new values
5. Switch reads to profiles
6. Stop old-column writes
7. Prove no remaining dependencies
8. Drop old columns later
```

The data model, application, API, tests, reports, and operational workflows all participate in the migration.

# 68. Production Scenario: Tenant-Safe Foreign-Key Migration

Suppose:

```text
invoices(tenant_id, customer_id)
customers(tenant_id, id)
```

The real invariant may be:

```text
invoice.customer_id must belong to the same tenant
```

A single-column foreign key may not express this invariant correctly.

The migration should preserve the same modeling rule established earlier:

```text
repair invalid rows
→ create required supporting uniqueness
→ add composite FK
→ validate
→ enforce application behavior
```

This is an example of schema evolution exposing a previously hidden modeling weakness.

# 69. Performance Framework

For every migration ask:

### CPU

How much computation per row?

### IO

How much table and index data is touched?

### WAL

How much write-ahead log will be generated?

### Locks

Which queries can block or be blocked?

### Replication

Can replicas keep up?

### Cache

Will the migration evict hot working sets?

### Vacuum

Will dead tuples accumulate faster than cleanup can process them?

### Disk

Do we have enough free capacity for temporary and persistent effects?

Treat migration cost as a workload-estimation exercise.

# 70. EXPLAIN for Migration Queries

Complex migration queries deserve query-plan analysis.

Start with:

```sql
EXPLAIN (BUFFERS)

```

and test `EXPLAIN (ANALYZE, BUFFERS)` in a safe representative environment before executing the production-scale mutation.

Look for:

```text

bad join order
unexpected sorts
huge buffer reads
missing indexes
```

A migration query is still a query.

```text
    + compatibility protocol
    + data transformation
    + integrity proof
    + operational workload
    + observability
    + recovery strategy
```

```text
data is correct

+ replicas are healthy
```
